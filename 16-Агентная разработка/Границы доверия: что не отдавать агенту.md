# Границы доверия: что не отдавать агенту

> [!abstract] Коротко
> Не всё, что агент технически может сделать, стоит ему поручать без усиленного контроля. Граница проходит не по сложности задачи, а по цене ошибки и по тому, ловит ли её что-то автоматически до прода.

## Зачем это знать

Без явной границы решение «отдать это агенту или нет» принимается интуитивно и непоследовательно: одну задачу перепроверяют трижды из осторожности, другую, не менее рискованную, мержат с одного взгляда, потому что «код выглядел простым». Явная граница делает решение воспроизводимым.

## Модель

Граница доверия определяется двумя осями: **цена ошибки** (что сломается и насколько дорого это чинить) и **обнаружимость** (поймает ли ошибку тест, компилятор или ревью до прода, или она проявится только в проде спустя время).

```
                    высокая обнаружимость        низкая обнаружимость
цена ошибки          (компилятор/тест ловит)      (тихо расходится в проде)
низкая               ┌─────────────────────┐      ┌─────────────────────┐
                      │  доверять свободно  │      │   доверять, но с    │
                      │  (стиль, рефакторинг│      │   явным ревью       │
                      │  внутри метода)     │      │   (внутренние API)  │
                      └─────────────────────┘      └─────────────────────┘
цена ошибки          ┌─────────────────────┐      ┌─────────────────────┐
высокая               │  доверять с тестом  │      │  не отдавать без    │
                      │  до реализации      │      │  человека на каждом │
                      │  (бизнес-логика)    │      │  шаге (деньги,      │
                      │                     │      │  миграции, секреты) │
                      └─────────────────────┘      └─────────────────────┘
```

Правый нижний квадрант — зона, где ошибка одновременно дорогая и почти не обнаружима автоматически. Именно её стоит формализовать как список «не отдавать без усиленного контроля», а не решать по ситуации.

### Что в этой зоне обычно

- **Денежные расчёты и округление.** Ошибка на копейки в масштабе миллионов операций — не мелочь, а инцидент; тест на конкретных числах её не всегда ловит, если сам тест сгенерирован с той же логикой округления.
- **Схема БД и миграции.** Необратимая (или дорого обратимая) операция на проде; ошибка в порядке накатки или в типе колонки обнаруживается на реальных данных, не на тестовой базе.
- **Контракты интеграционных событий.** Если контракт меняется несовместимо, ошибка проявляется не у автора PR, а в другом модуле или сервисе, который его читает — обычно значительно позже.
- **Секреты и доступы.** Ключи, токены, строки подключения — попадание в код или в лог не обнаруживается компилятором вообще, только сканером секретов или человеком.
- **Логика авторизации.** Ошибка обычно не падает — она молча пропускает то, что должно быть запрещено, и это не проявляется ни в одном стандартном тесте, если тест не написан специально на негативный сценарий.

## Решения

| Задача | Можно поручить агенту | Обязателен человек на каждом шаге |
|---|---|---|
| CRUD-хендлер по образцу | Да, с ревью по обычному чек-листу | — |
| Финансовый расчёт (комиссия, рассрочка) | Черновик — да | Проверка формул и округления вручную, тест на граничные суммы до мержа |
| Новая миграция схемы | Черновик — да, но только через скилл `create-migration` | Ревью SQL, проверка на staging перед проду |
| Новое поле в контракте события | Черновик — да | Проверка обратной совместимости с существующими потребителями события |
| Правило авторизации (кто что может) | Не начинать с чистого агентского черновика | Спецификация правила пишет человек, агент реализует по ней, тест на «должно быть запрещено» пишет человек |
| Рефакторинг внутри метода без изменения поведения | Да, свободно | — |

## В ServiceShop

Три правила проекта из [[93 — Рабочий проект: Alif ServiceShop (обзор раздела)]] — уже формализованные границы доверия: миграции — только через скилл (устраняет ручную ошибку формата и порядка), интеграционные события — только через Outbox с явным контрактом в `IntegrationEvents` (снижает цену несовместимого изменения, потому что оно видно на уровне контракта), логирование — только Serilog (снижает риск утечки данных через неконтролируемый логгер). Модуль Orders с оплатой в рассрочку — верхний правый квадрант почти по определению: денежная логика, статусы кредитной заявки, синхронизация с внешним скорингом — здесь спецификацию пишет человек, а агентский черновик проходит ревью построчно, а не по диагонали.

## Где ошибаются

> [!warning] Где граница держится плохо
> - **Иллюзия, что «раз тесты сгенерированы вместе с кодом — покрытие есть».** Тест, написанный тем же агентом, что и реализация, с высокой вероятностью проверяет то же неверное понимание задачи, а не служит независимой проверкой.
> - **Постепенное расширение доверия без пересмотра.** Начали с «агент пишет только черновики», через месяц по инерции стали мержить финансовые расчёты без отдельной проверки округления — граница размылась незаметно.
> - **Агент часто:** при правке одного файла в зоне высокого риска (например, добавление поля в модель заказа) — не предупреждает, что это поле стоит добавить и в контракт события, потому что не видит всей цепочки потребителей без явного указания.

## Проверка на ревью

- Для задач из зоны «высокая цена + низкая обнаружимость» — явно указано, кто и на каком этапе проверял вручную (не полагаться на «CI зелёный»).
- Тест на денежный расчёт покрывает граничные и дробные суммы, а не только круглые числа из happy path.
- Изменение контракта события проверено на обратную совместимость с реальными потребителями, а не только с текущим producer'ом.
- В PR, трогающем авторизацию, есть тест на негативный сценарий («должно быть запрещено»), написанный человеком, а не только на позитивный.

## Проверь себя

> [!question]- Почему миграции схемы — зона повышенного контроля, если они проходят через скилл?
> Скилл убирает ошибки формата (имя файла, таймстемп, порядок накатки), но не проверяет содержание: корректность типа колонки, необходимость обратной совместимости при недоступном откате, влияние на существующие данные. Формальная процедура и содержательная проверка — разные вещи, скилл закрывает только первую.

> [!question]- Чем плох тест, сгенерированный тем же агентом, что и код, для проверки денежного расчёта?
> Если агент неверно понял формулу округления, эта же неверная формула, скорее всего, попадёт и в тест — тест подтвердит код, а не корректность. Независимая проверка формулы человеком (или тестом, написанным до реализации по спецификации) не разделяет эту слепую зону.

## Разбор

### Разбор 1. Классифицируй задачи

Даны четыре задачи: (1) добавить новое поле сортировки в существующий Dapper-запрос списка товаров; (2) изменить формулу расчёта скидки по промокоду; (3) добавить индекс в существующую таблицу через миграцию; (4) добавить логирование в существующий хендлер. Отнеси каждую к квадранту модели и скажи, что требуется дополнительно.

> [!success]- Разбор
> (1) — низкая цена, высокая обнаружимость: доверять свободно, обычное ревью. (2) — высокая цена, низкая обнаружимость: спецификация формулы человеком, тест на граничные суммы до мержа. (3) — высокая цена (может залочить таблицу на проде), средняя обнаружимость: ревью SQL и проверка на staging с объёмом данных, близким к боевому. (4) — низкая цена, но проверить обнаружимость: если в лог попадают персональные данные или токены — это сразу переходит в зону «секреты», требует явной проверки состава логируемых полей.

## Итог

- Граница доверия строится по двум осям: цена ошибки и обнаружимость до прода
- Опасная зона — дорогая ошибка, которую ничего не ловит автоматически: деньги, миграции, контракты событий, секреты, авторизация
- Тест, сгенерированный тем же агентом, что и код, не защищает от общей ошибки понимания задачи
- Формальная процедура (скилл) снимает ошибки формата, но не заменяет содержательную проверку человеком
