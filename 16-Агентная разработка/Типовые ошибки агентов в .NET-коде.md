# Типовые ошибки агентов в .NET-коде

> [!abstract] Коротко
> Конкретные паттерны, в которых сгенерированный C#/.NET-код регулярно ошибается — не гипотетически, а потому что обучающие данные агента перекошены в сторону старых статей, упрощённых примеров и общего среднего по экосистеме, а не по конкретному репозиторию. Заметка — прикладное дополнение к [[Ревью сгенерированного кода: чек-лист]]: что именно искать в C#/.NET-диффе.

## Зачем это знать

Общий чек-лист ревью говорит «проверь границы и побочные эффекты». Эта заметка говорит, в каких именно местах C#/.NET-кода границы теряются чаще всего — так проверка занимает не час вслепую, а пять минут прицельно.

## Модель: шесть повторяющихся паттернов

### 1. Версия вперёд репозитория

Агент обучен на большом количестве кода и статей, где .NET 9–10 и C# 13–14 представлены гуще, чем `net8.0` — просто потому, что новые статьи пишут активнее старых. Результат: предложенный `field`-аксессор, extension member или `?.=`, которых в `net8.0`/C# 12 не существует.

```csharp
// Агент предложит (C# 14, недоступно в net8.0):
public string Name { get => field; set => field = value.Trim(); }

// В net8.0 корректно:
private string _name;
public string Name { get => _name; set => _name = value.Trim(); }
```

### 2. Async-ловушки в старом стиле

Обучающие примеры async/await непропорционально часто показывают `.Result`, `.Wait()`, `async void` — потому что таких примеров в старых статьях и Stack Overflow больше, чем корректных. Агент, не имея контекста «это ASP.NET Core, здесь есть `SynchronizationContext`-нюансы», может предложить блокирующий вызов там, где сам же написал `async`-метод чуть выше.

### 3. Проглоченное исключение "для надёжности"

Частый паттерн — обернуть новый код в `try/catch` с логированием и проглатыванием, «чтобы не уронить процесс». Это выглядит как защитное программирование, а на деле прячет реальную ошибку и превращает падение в тихое неверное состояние — см. [[Когда исключение — плохой выбор]].

```csharp
// Агент часто:
try { await _repository.SaveAsync(order); }
catch (Exception ex) { _logger.LogError(ex, "Save failed"); }
// Заказ не сохранён, но метод вернул успех — вызывающий код не узнает
```

### 4. EF Core: N+1 и материализация в память

Без явного контекста о размере данных агент часто пишет запрос, который выглядит правильным на маленьком тестовом наборе и уходит в N+1 или полную материализацию на реальном объёме — например, `.ToList()` до фильтрации или обращение к навигационному свойству в цикле без `Include`. Разобрано в [[EF Core: производительность и типичные грабли]] и [[IEnumerable vs IQueryable]].

### 5. DTO и enum вместо доменного правила

Агент охотнее реализует проверку как `if`-цепочку в контроллере или сервисе, чем как метод доменного агрегата — потому что первое чаще встречается в обучающих примерах (Minimal API, простые CRUD-сервисы), а тактический DDD с бизнес-правилами внутри агрегата — паттерн, специфичный для конкретных проектов вроде ServiceShop, и агент его не выберет сам без явного указания следовать образцу.

### 6. Обобщённая обработка ошибок вместо доменной

`catch (Exception)` и generic `ProblemDetails` с текстом `"An error occurred"` вместо конкретного кода ошибки и HTTP-статуса — агент по умолчанию тяготеет к максимально общему решению, потому что оно реже ломается на тестах, но именно поэтому неинформативно для клиента API.

## Решения

| Паттерн | Как проверить за 30 секунд |
|---|---|
| Версия вперёд | Ctrl+F по `field`, `extension(`, `?.=` в новом коде — если есть, сверить с [[Новое в C# 12, 13, 14]] |
| Async-ловушка | Ctrl+F по `.Result`, `.Wait()`, `async void` в diff |
| Проглоченное исключение | Любой `catch` — проверить, пробрасывается ли исключение дальше или возвращается ли явный код ошибки |
| EF N+1 / память | Посмотреть сгенерированный SQL в логах на реальных данных, не только на тестовых trois-строчках |
| Правило не в домене | Если бизнес-условие (`if`) лежит в контроллере/сервисе, а не в агрегате — спросить, почему не в домене |
| Generic ошибка | Проверить, что клиент API получает достаточно информации, чтобы понять, что пошло не так |

## В ServiceShop

Правила проекта частично страхуют именно от этих паттернов: `TreatWarningsAsErrors` + StyleCop ловит часть стилистических отклонений; `ArchTests` — приватные конструкторы агрегатов не дадут агенту протащить бизнес-логику мимо домена в контроллер незаметно (хотя саму логику внутри метода агрегата тест не проверит); запрет `Microsoft.Extensions.Logging` в пользу Serilog отсекает паттерн 6 частично — но ни один автотест не поймает паттерн 3 (проглоченное исключение) и паттерн 4 (N+1 в конкретном запросе) — это чистая работа ревьюера.

## Где ошибаются

> [!warning] Мета-ловушка
> Все шесть паттернов объединяет одно: агент выбирает **самое общеупотребимое** решение, а не самое подходящее для конкретного проекта. Общеупотребимое — то, что чаще встречается в обучающих данных, а не то, что вернее. Отсюда практический вывод: чем специфичнее правило проекта (DDD-агрегаты, Outbox, конкретная версия языка), тем меньше агенту можно доверять без явного контекста и тем внимательнее это место на ревью.

## Проверка на ревью

- Использованные языковые фичи проверены на доступность в `net8.0`/C# 12.
- В новом асинхронном коде нет `.Result`, `.Wait()`, `async void` вне точки входа события.
- Каждый `catch` либо пробрасывает исключение, либо явно возвращает информативный результат ошибки — не проглатывает молча.
- SQL-запросы EF проверены на реальном объёме данных, а не только на тестовой выборке из нескольких строк.
- Бизнес-правило находится в домене (агрегате), а не размазано по контроллеру и сервису.
- Ошибка, возвращаемая клиенту API, содержит достаточно информации для диагностики, а не общий текст.

## Проверь себя

> [!question]- Почему агент чаще предлагает `.Result` вместо правильного `await`, если он «знает» про дедлоки?
> Модель обучена на всём корпусе кода и статей в интернете, где значительная часть материала — устаревшая или упрощённая, и там `.Result` встречается часто. Без явного контекста задачи («это ASP.NET Core с SynchronizationContext») агент опирается на статистически более частый паттерн, а не обязательно на самый корректный для конкретного окружения.

> [!question]- Почему проглоченное исключение хуже, чем упавшее приложение?
> Упавшее приложение — видимая проблема, которую заметят сразу. Проглоченное исключение превращает сбой в тихое неверное состояние: заказ выглядит обработанным, а на деле не сохранён — и это обнаружится не сразу, а когда несостыковка данных дойдёт до пользователя или до следующего этапа обработки, когда воспроизвести причину уже сложно.

## Разбор

### Разбор 1. Найди паттерн

```csharp
public async Task<IActionResult> Cancel(Guid orderId)
{
    try
    {
        var order = await _repository.GetByIdAsync(orderId);
        order.Status = OrderStatus.Cancelled;
        await _repository.SaveAsync(order).ConfigureAwait(false);
        return Ok();
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, "Cancel failed");
        return Ok();
    }
}
```

Найди все паттерны из списка выше, которые встречаются в этом фрагменте.

> [!success]- Разбор
> Паттерн 3 (проглоченное исключение): при ошибке клиент получает `200 OK`, будто заказ отменён, хотя это не так. Паттерн 5 (правило не в домене): статус меняется прямым присваиванием в контроллере, минуя бизнес-правило о допустимых переходах статуса и минуя доменное событие. Паттерн 6 (обобщённая ошибка): даже при доработке catch-блока для возврата ошибки, `"Cancel failed"` ничего не говорит клиенту о причине.

## Итог

- Агент чаще выбирает статистически распространённое решение, а не самое подходящее для конкретного проекта
- Шесть повторяющихся паттернов: версия вперёд, async-ловушки, проглоченные исключения, N+1/материализация, правило не в домене, обобщённая ошибка
- Автотесты проекта страхуют от части паттернов структурно, но не от логических (проглоченное исключение, N+1 в конкретном запросе)
- Чем специфичнее правило проекта, тем меньше агент угадает его без явного контекста
