# Тесты как контракт для агента

> [!abstract] Коротко
> Тест, написанный **до** реализации, — единственный способ формализовать намерение так, чтобы его нельзя было интерпретировать иначе. Текстовая спецификация всё ещё оставляет агенту (и человеку) простор для толкования; тест либо проходит, либо нет.

## Зачем это знать

[[Постановка задачи агенту: спецификация вместо инструкции]] решает разрыв между «что хочу» и «что понял агент» на уровне текста. Тесты решают ту же задачу на уровне, который не зависит от толкования: спецификация может быть прочитана по-разному, тест — нет. Разница особенно ощутима при доменных правилах, где формулировка «корзина не должна принимать недоступный товар» допускает десяток трактовок «недоступности», а тест с конкретным состоянием — ни одной.

## Модель

Порядок «тест до реализации» с агентом работает иначе, чем классический TDD с человеком, хотя механика та же:

```
Классический TDD:      человек пишет тест → человек пишет код → рефакторинг
С агентом:              человек пишет тест (или спецификацию сценариев) →
                         агент пишет реализацию → тест — единственный
                         независимый судья, не зависящий от того, кто писал код
```

Ключевое отличие: если и тест, и реализацию пишет один и тот же агент в одной сессии, тест перестаёт быть независимым судьёй — он с высокой вероятностью разделяет ту же ошибку понимания задачи, что и код (см. [[Ревью сгенерированного кода: чек-лист]]). Независимость тесту даёт только то, что его написал **до** реализации кто-то (человек), кто не видел ещё код, который будет его проходить.

### Что делает тест хорошим контрактом

1. **Тест описывает поведение, а не реализацию.** «Метод возвращает `Result.Failure(CartNotFound)`, если корзина отсутствует» — контракт; «метод вызывает `_repository.GetByIdAsync` один раз» — деталь реализации, которая ломается при любом рефакторинге без изменения поведения.
2. **Тест покрывает границы, не только happy path.** Пустая коллекция, `null`, повторный вызов, конкурентный доступ — именно те места, которые агент теряет чаще всего (см. [[Типовые ошибки агентов в .NET-коде]]).
3. **Тест написан до того, как агент увидел реализацию.** Иначе есть риск подгонки теста под уже написанный код, а не наоборот.

## Решения

| Ситуация | Стратегия с тестами |
|---|---|
| Новое бизнес-правило в домене | Человек пишет тест на правило (включая негативный сценарий) → агент реализует правило, пока тест не пройдёт |
| Рефакторинг существующего кода | Существующие тесты — контракт неизменности поведения; если тестов нет — написать их **до** рефакторинга агентом |
| Баг найден в проде | Сначала тест, воспроизводящий баг (падает на текущем коде) → затем агент чинит, пока тест не пройдёт |
| Исследовательская задача без чёткого поведения | Тесты писать рано не имеет смысла — сначала спецификация, тесты появляются, когда поведение прояснилось |

## В ServiceShop

`ArchTests` — тесты-контракты не для одной фичи, а для архитектуры целиком: приватность конструкторов агрегатов, соответствие хендлеров `ICommandHandler<,>`, изоляция модулей друг от друга. Они написаны один раз и с тех пор проверяют каждый PR, включая сгенерированный агентом код, не полагаясь на то, что кто-то не забудет проверить правило глазами. Юнит-тест на конкретное бизнес-правило (например, `OrderCannotBeCancelledRule`) — контракт более узкого масштаба: написан один раз человеком, понимающим правило, и с тех пор формализует его для любой последующей реализации или рефакторинга, включая агентские.

## Где ошибаются

> [!warning] Где контракт тестов слабеет
> - **Тест написан после реализации, глядя на неё.** Тест, подогнанный под уже написанный код, проверяет «код делает то, что делает», а не «код делает то, что нужно» — это не контракт, а зеркало.
> - **Тест проверяет вызовы, а не результат.** Мок, проверяющий, что метод репозитория был вызван с определёнными параметрами, ломается при любом эквивалентном по результату рефакторинге и не ловит реальную ошибку в бизнес-логике, если она не связана с этим вызовом.
> - **Агент часто:** генерирует тест вместе с реализацией в одном проходе — такой тест по умолчанию не независимый контракт, а фиксация того, что модель уже решила сделать. Стоит явно просить писать тест первым отдельным шагом либо писать его самому.

## Проверка на ревью

- Тест на новое бизнес-правило написан (или хотя бы явно проверен) человеком, а не сгенерирован в одном проходе с реализацией.
- Тесты проверяют результат и поведение, а не детали вызовов внутренней реализации.
- Есть тест на негативный сценарий (что должно быть отклонено/запрещено), а не только на happy path.
- При рефакторинге существующий набор тестов не менялся вместе с кодом без явного обоснования, зачем.

## Проверь себя

> [!question]- Почему тест, написанный до реализации, надёжнее текстовой спецификации задачи?
> Текстовая спецификация описывает намерение на естественном языке, который допускает разное толкование даже при добросовестном чтении. Тест либо проходит на конкретном входе, либо нет — толкования не остаётся. Спецификация всё ещё нужна для контекста и границ, но именно тест устраняет последний зазор интерпретации.

> [!question]- Почему тест, сгенерированный агентом вместе с реализацией в одной сессии, не даёт той же гарантии, что тест, написанный человеком заранее?
> Если один и тот же процесс породил и код, и тест, они с высокой вероятностью опираются на одно и то же (возможно, неверное) понимание задачи — тест в этом случае подтверждает код, а не проверяет его независимо. Независимость появляется только тогда, когда тест зафиксировал ожидание до того, как реализация была написана, — тогда расхождение между ожиданием и кодом реально может проявиться.

## Разбор

### Разбор 1. Контракт вместо инструкции

Дана задача: «корзина не должна принимать товар, если его модерация ещё не пройдена». Напиши тест (в виде псевдокода на xUnit), который формализует это правило как контракт для агента, до того как агент напишет реализацию.

> [!success]- Пример решения
> ```csharp
> [Fact]
> public void AddItem_ShouldFail_WhenOfferIsNotModerated()
> {
>     var cart = Cart.Create(customerId);
>     var unmoderatedOffer = OfferId.New(); // оффер без ModeratedOffer-записи
>
>     var result = cart.AddItem(unmoderatedOffer, quantity: 1);
>
>     result.IsFailure.Should().BeTrue();
>     result.Error.Should().Be(CartErrors.OfferNotModerated);
>     cart.Items.Should().BeEmpty();
> }
> ```
> Тест фиксирует три вещи одновременно: результат — явный провал, а не тихое игнорирование; конкретный код ошибки, а не общее исключение; отсутствие побочного эффекта (товар не попал в корзину). Любая реализация, которую напишет агент, либо проходит этот тест буквально, либо нет — толкования «а что если частично добавить» не остаётся.

## Итог

- Тест, написанный до реализации, устраняет последний зазор интерпретации, который текстовая спецификация оставляет
- Тест, сгенерированный вместе с реализацией в одном проходе, не является независимым контрактом
- Контракт описывает результат и поведение, а не детали вызовов реализации
- Архитектурные тесты — контракт уровня всего проекта, юнит-тест на правило — контракт уровня одной фичи; оба нужны
