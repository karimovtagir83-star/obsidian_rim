# Задачи — Асинхронность

> [!abstract] Коротко
> 40 задач по разделу [[06 — Асинхронность (обзор раздела)]]: `Task` и механика `async`/`await`, контекст синхронизации и дедлоки, отмена и исключения, примитивы синхронизации, каналы и параллелизм. Много задач вида «предскажи вывод» и «найди все ошибки» — именно так асинхронные баги выглядят на ревью и на собеседовании.

> [!tip] Как решать
> - Задачи на предсказание вывода решай **до** запуска: почти вся ценность в этом.
> - В задачах «найди ошибки» выписывай список до того, как открывать решение: обычно ошибок больше, чем кажется.
> - Проверять поведение потоков удобно печатью `Thread.CurrentThread.ManagedThreadId` и `dotnet-counters` для пула.
> - Гонки не воспроизводятся с первого раза: гоняй проблемный код в цикле с сотней потоков.

## 1. Task и основы async

### 1.1. Порядок вывода
```csharp
Console.Write("A");
var t = WorkAsync();
Console.Write("C");
await t;
Console.Write("E");

async Task WorkAsync() { Console.Write("B"); await Task.Delay(100); Console.Write("D"); }
```

> [!success]- Решение
> `ABCDE`. Тело `WorkAsync` выполняется синхронно до первого «неготового» `await`, поэтому «B» печатается до возврата из метода. На `Task.Delay` метод возвращает управление, печатается «C», затем после задержки — «D», и по завершении задачи — «E».

### 1.2. Task и поток
Создаёт ли `async`-метод новый поток?

> [!success]- Решение
> Нет. `async` позволяет **не занимать** поток на время ожидания ввода-вывода. Поток появляется только при явном `Task.Run` (вычисления в пуле) и при выполнении продолжений — их берёт свободный поток пула.

### 1.3. Горячие задачи
Выполнится ли операция, если результат `LoadAsync()` не ожидать?

> [!success]- Решение
> Да: задачи в .NET «горячие», метод начинает работу до возврата. Но исключения потеряются, а приложение может завершиться раньше её окончания. Компилятор предупреждает (CS4014).

### 1.4. Повторный await
Что произойдёт при двух `await` над одной задачей?

> [!success]- Решение
> Второй `await` вернёт готовый результат мгновенно: результат сохранён в задаче, операция не выполняется заново. Для `ValueTask` так делать нельзя — повторное ожидание даёт неопределённое поведение.

### 1.5. Ускорить метод
Три независимых `await` по 100 мс подряд. Как сделать за 100 мс?

> [!success]- Решение
> ```csharp
> var t1 = A(ct); var t2 = B(ct); var t3 = C(ct);
> await Task.WhenAll(t1, t2, t3);
> return new Result(await t1, await t2, await t3);
> ```
> Задачи стартуют в момент вызова; достаточно не ставить `await` сразу. Оговорка: зависимости должны быть потокобезопасны — один `DbContext` так использовать нельзя.

### 1.6. Task.Run в ASP.NET Core
Ускорит ли `await Task.Run(() => _service.LoadAsync())` обработку запроса?

> [!success]- Решение
> Нет, замедлит: запрос уже выполняется в потоке пула, а `Task.Run` забирает ещё один поток из того же пула и добавляет планирование. Оправдан только для длительных вычислений, и то лучше вынести их в фоновую службу.

### 1.7. ValueTask
Когда `ValueTask<T>` уместен и какие у него ограничения?

> [!success]- Решение
> Когда метод в большинстве вызовов завершается синхронно (попадание в кеш) и вызывается очень часто — экономится аллокация задачи. Ограничения: ждать можно только один раз, нельзя хранить, передавать и ожидать параллельно; для этого нужен `.AsTask()`.

### 1.8. TaskCompletionSource
Зачем нужен флаг `RunContinuationsAsynchronously`?

> [!success]- Решение
> Без него продолжения выполняются **синхронно в потоке, вызвавшем `TrySetResult`**: чужая обработка выполняется в вашем потоке, что может его надолго занять или привести к дедлоку. Флаг переносит продолжения в пул.

## 2. Контекст, дедлоки, ошибки

### 2.1. Дедлок в WPF
Почему `LoadAsync().Result` в обработчике кнопки вешает приложение?

> [!success]- Решение
> UI-поток блокируется на `.Result`; продолжение `LoadAsync` планируется в захваченный контекст синхронизации — то есть в этот же UI-поток, который занят ожиданием. Взаимная блокировка.

### 2.2. То же в ASP.NET Core
Будет ли дедлок в ASP.NET Core и что будет вместо него?

> [!success]- Решение
> Дедлока не будет — контекста синхронизации нет, продолжение выполнит любой поток пула. Вместо этого поток пула блокируется на время операции; под нагрузкой это исчерпание пула: растёт очередь и латентность при простаивающем процессоре.

### 2.3. ConfigureAwait
Где нужен `ConfigureAwait(false)`: контроллер ASP.NET Core, NuGet-библиотека, обработчик кнопки WPF?

> [!success]- Решение
> Только в библиотеке: она не знает среду вызова. В ASP.NET Core контекста нет — вызов бессмыслен. В обработчике WPF вреден: после `await` нужен UI-поток для доступа к элементам.

### 2.4. async void
Почему `catch` вокруг вызова `async void`-метода не срабатывает?

> [!success]- Решение
> Метод возвращает управление на первом `await`, и `try` завершается раньше, чем возникнет исключение. Задачи, куда его положить, нет: построитель отправляет исключение в контекст синхронизации, где оно становится необработанным и обычно роняет процесс.

### 2.5. Скрытый async void
Что не так с `Parallel.ForEach(items, async x => await ProcessAsync(x));`?

> [!success]- Решение
> Лямбда приводится к `Action`, то есть становится `async void`: `Parallel.ForEach` завершится мгновенно, не дождавшись операций, ошибки потеряются. Нужен `Parallel.ForEachAsync`.

### 2.6. Поток после await
Может ли код после `await` выполняться в другом потоке и что при этом сохраняется?

> [!success]- Решение
> В ASP.NET Core — как правило, да. Переносится `ExecutionContext` (значения `AsyncLocal`, культура, идентификация), поэтому `HttpContext` доступен. Не переносится привязка к потоку: `ThreadLocal` и захваченный `Monitor` работать не будут.

### 2.7. lock и await
Почему нельзя написать `await` внутри `lock`?

> [!success]- Решение
> `Monitor` привязан к потоку: освободить блокировку обязан захвативший поток, а после `await` продолжение может выполняться в другом. Компилятор запрещает это. Асинхронный аналог — `SemaphoreSlim(1,1)` с `Release` в `finally`.

### 2.8. Диагностика
Латентность выросла в 100 раз, CPU 15 %, память в норме. Что смотреть?

> [!success]- Решение
> Счётчики пула: `threadpool-queue-length` (растёт) и `threadpool-thread-count` (медленно ползёт вверх) — признак исчерпания пула из-за блокирующих вызовов. Дальше дамп: `pstacks` покажет, где стоят потоки, `dumpasync` — зависшие асинхронные цепочки.

## 3. Отмена и исключения

### 3.1. Где хранится исключение
Когда выбрасывается исключение из `async`-метода?

> [!success]- Решение
> Оно сохраняется в задаче (`SetException`) и перебрасывается в момент `await` с сохранением исходного стека через `ExceptionDispatchInfo`. До `await` вызывающий ничего не замечает.

### 3.2. await против .Result
Почему `await` бросает исходное исключение, а `.Wait()` — `AggregateException`?

> [!success]- Решение
> Задача может завершиться несколькими исключениями, поэтому её `Exception` всегда `AggregateException`. `await` разворачивает и бросает первое внутреннее ради читаемости; блокирующие методы отдают обёртку как есть.

### 3.3. WhenAll и ошибки
Три задачи, две упали. Сколько исключений увидит `catch` вокруг `await Task.WhenAll(...)`?

> [!success]- Решение
> Одно — первое. Остальные лежат в `task.Exception.InnerExceptions`, и без явного обхода останутся незамеченными. Плюс `WhenAll` дожидается всех задач: чтобы прервать остальные, нужен общий `CancellationTokenSource`.

### 3.4. Кооперативная отмена
Почему нельзя прервать метод, который не проверяет токен?

> [!success]- Решение
> Отмена в .NET кооперативная: это сигнал, а не принудительное прерывание. Принудительный `Thread.Abort` удалён, потому что оставлял данные в несогласованном состоянии. Метод, не проверяющий токен и не передающий его дальше, отменить невозможно.

### 3.5. Логирование отмены
Как обработать `OperationCanceledException`?

> [!success]- Решение
> Отдельным `catch` **до** общего, с уровнем Information и, как правило, пробросом дальше. Иначе штатная отмена (клиент закрыл вкладку, деплой) заполнит логи ложными ошибками. Проглатывать нельзя: прерванная работа станет выглядеть успешной.

### 3.6. Таймаут поверх отмены
Как сделать «не дольше 5 секунд, но и отменяемо извне»?

> [!success]- Решение
> ```csharp
> using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
> cts.CancelAfter(TimeSpan.FromSeconds(5));
> try { await CallAsync(cts.Token); }
> catch (OperationCanceledException) when (!ct.IsCancellationRequested) { throw new TimeoutException(); }
> ```
> Связанный источник обязательно в `using` — иначе подписка на родительский токен утечёт.

### 3.7. Забытый Dispose
Чем опасен `CancellationTokenSource` без освобождения?

> [!success]- Решение
> Он держит таймер (при `CancelAfter`) и список регистраций; в цикле или на каждый запрос это утечка. Плюс связанный источник остаётся подписанным на родительский токен.

### 3.8. Fire-and-forget
Как правильно запустить фоновую работу из обработчика запроса?

> [!success]- Решение
> Не через `_ = Task.Run(...)`: ошибки теряются, при остановке приложения работа обрывается. Правильно — положить задание в `Channel` и обрабатывать в `BackgroundService`, где есть логирование, отмена и корректное завершение. Для критичных задач — очередь или outbox.

## 4. Синхронизация

### 4.1. Потерянные инкременты
Почему `_counter++` из трёх потоков даёт меньше ожидаемого?

> [!success]- Решение
> Инкремент не атомарен: чтение, увеличение, запись. Два потока читают одно значение и записывают одинаковый результат — одно увеличение теряется. Лечение — `Interlocked.Increment`.

### 4.2. Флаг остановки
Почему цикл `while (_running)` не завершается в Release?

> [!success]- Решение
> JIT видит, что поле не меняется внутри цикла, и кеширует его в регистре. Нужен `volatile`/`Volatile.Read` — или, что правильнее для фоновой работы, `CancellationToken`.

### 4.3. На чём блокироваться
Почему нельзя `lock (this)`, `lock (typeof(T))`, `lock ("key")`?

> [!success]- Решение
> Все три объекта доступны извне: посторонний код может захватить ту же блокировку и создать непредсказуемый дедлок. Строковые литералы к тому же интернируются. Нужно приватное `readonly`-поле, в новом коде — `System.Threading.Lock`.

### 4.4. Дедлок из двух блокировок
Как он возникает и как его избежать?

> [!success]- Решение
> Потоки берут A и B в разном порядке: каждый держит нужное другому. Средства: единый порядок захвата, отказ от вложенных блокировок, `TryEnter` с таймаутом, запрет вызывать чужой код под блокировкой.

### 4.5. Interlocked или lock
Что выбрать для счётчика и что — для обновления двух связанных полей?

> [!success]- Решение
> Счётчик — `Interlocked.Increment`: атомарная инструкция, единицы наносекунд, без риска дедлока. Два связанных поля — `lock`: они должны меняться согласованно, иначе другой поток увидит промежуточное состояние. Альтернатива для второго случая — иммутабельный объект и `Interlocked.Exchange` ссылки.

### 4.6. Ошибка с семафором
Найди дефект:
```csharp
await _gate.WaitAsync(ct);
if (_token is { IsValid: true }) return _token;
_token = await RequestAsync(ct);
_gate.Release();
```

> [!success]- Решение
> При раннем `return` и при исключении `Release` не вызывается — разрешение теряется навсегда, и все последующие вызовы зависнут. `Release` всегда в `finally`. Плюс полезно добавить быструю проверку до захвата и повторную под ним.

### 4.7. Реентерабельность
Чем `lock` отличается от `SemaphoreSlim` в этом отношении?

> [!success]- Решение
> `lock` (Monitor) реентерабелен: поток, уже владеющий блокировкой, входит повторно. `SemaphoreSlim` — нет: повторный `WaitAsync` из той же операции заблокируется навсегда (самодедлок).

### 4.8. ARM и модель памяти
Почему код может работать на x86 и ломаться на Apple Silicon?

> [!success]- Решение
> У ARM64 более слабая модель памяти: процессор свободнее переупорядочивает записи и чтения. Гонка, существовавшая всегда, на x86 просто не проявлялась. Лечение — корректная синхронизация (`Interlocked`, `volatile`, `lock`), а не «работает же на проде».

## 5. Потоки данных и параллелизм

### 5.1. IAsyncEnumerable или список
Когда возвращать `IAsyncEnumerable<T>` вместо `Task<List<T>>`?

> [!success]- Решение
> Когда данных много или поток бесконечен: обработка начинается с первого элемента, память постоянна, темп задаёт потребитель. Для небольшой выборки проще список — он переиспользуется и перечисляется многократно.

### 5.2. EnumeratorCancellation
Что будет, если забыть этот атрибут?

> [!success]- Решение
> Токен, переданный через `WithCancellation`, не попадёт в итератор — отмена молча не сработает. Ошибка обнаруживается в проде, когда запросы перестают прерываться.

### 5.3. Обратное давление
Зачем ограничивать ёмкость канала?

> [!success]- Решение
> Иначе при отставании потребителя очередь растёт до исчерпания памяти. Ограниченная ёмкость заставляет производителя ждать (или отбрасывать элементы по политике), делая перегрузку видимой и управляемой.

### 5.4. Канал вместо брокера
Можно ли заменить RabbitMQ каналом?

> [!success]- Решение
> Нет для критичных данных: канал живёт в памяти процесса, при перезапуске содержимое теряется, гарантий доставки и повторов нет. Он годится для внутрипроцессной развязки и данных, которые можно потерять или легко повторить.

### 5.5. Parallel для I/O
Что не так с `Parallel.ForEach` над сетевыми вызовами?

> [!success]- Решение
> Потоки блокируются в ожидании, ядра простаивают, а число одновременных запросов не ограничено. Нужен `Parallel.ForEachAsync` с `MaxDegreeOfParallelism`.

### 5.6. Агрегация в Parallel.For
Почему `lock (gate) { total += x; }` внутри цикла — плохо?

> [!success]- Решение
> Все потоки конкурируют за одну блокировку на каждой итерации — часто медленнее последовательного цикла. Нужна перегрузка с `localInit`/`localFinally`: каждый поток копит своё, объединение — один раз на поток.

### 5.7. Ложное разделение
Что это и как проявляется?

> [!success]- Решение
> Потоки пишут в разные переменные, попадающие в одну строку кеша; она «прыгает» между ядрами, и параллельный код замедляется в разы. Лечение — локальные накопители и разнесение данных по кеш-линиям.

### 5.8. Стоит ли распараллеливать
Обработчик HTTP-запроса маппит 200 записей в DTO. Применять PLINQ?

> [!success]- Решение
> Нет. Маппинг занимает микросекунды, узкое место — запрос к базе; накладные расходы PLINQ превысят выигрыш, а на сервере параллелизм уже обеспечен одновременными запросами. Оптимизировать надо запрос.

## Итоговые задачи

### 6.1. Найти все ошибки
```csharp
public class OrderProcessor
{
    private readonly List<Order> _processed = new();
    private readonly object _lock = new();

    public async void ProcessAll(List<long> ids)
    {
        Parallel.ForEach(ids, async id =>
        {
            var order = _repo.GetAsync(id).Result;
            lock (_lock) { _processed.Add(order); }
            await NotifyAsync(order);
        });
    }
}
```

> [!success]- Решение
> Шесть ошибок: `async void` в публичном методе (исключения роняют процесс, дождаться нельзя); асинхронная лямбда в `Parallel.ForEach` — скрытый `async void`, операции не дожидаются; `.Result` блокирует потоки и грозит исчерпанием пула; `Parallel.ForEach` применён к вводу-выводу; нет ограничения параллелизма; нет токена отмены. Блокировка вокруг `Add` формально корректна, но при правильной переработке не нужна.
> ```csharp
> public async Task<IReadOnlyList<Order>> ProcessAllAsync(IReadOnlyList<long> ids, CancellationToken ct)
> {
>     var processed = new ConcurrentBag<Order>();
>
>     await Parallel.ForEachAsync(ids,
>         new ParallelOptions { MaxDegreeOfParallelism = 10, CancellationToken = ct },
>         async (id, token) =>
>         {
>             var order = await _repo.GetAsync(id, token);
>             processed.Add(order);
>             await NotifyAsync(order, token);
>         });
>
>     return processed.ToArray();
> }
> ```

### 6.2. Спроектировать фоновую обработку
Эндпоинт принимает файл и должен ответить сразу, а обработка занимает до минуты. Требования: не терять задания при перезапуске, не более 4 одновременных обработок, видеть очередь в метриках.

> [!success]- Решение
> Схема из трёх частей.
> **Приём.** Эндпоинт сохраняет файл в хранилище и запись о задании в базу со статусом `Pending` — в одной транзакции. Отвечает 202 с идентификатором задания. Это и есть требование «не терять при перезапуске»: канал в памяти его не обеспечивает.
> **Диспетчер.** `BackgroundService` периодически выбирает `Pending`-задания (с блокировкой строки или `SELECT ... FOR UPDATE SKIP LOCKED`, чтобы несколько инстансов не взяли одно и то же) и кладёт их в ограниченный `Channel<JobId>` с ёмкостью, скажем, 100.
> **Обработчики.** Четыре потребителя читают канал через `ReadAllAsync(stoppingToken)`; каждый обрабатывает задание, обновляет статус на `Done` или `Failed` с числом попыток, ошибки логирует и не останавливает цикл.
> **Метрики.** Счётчик длины очереди в канале, число заданий по статусам в базе, время обработки. Рост очереди — ранний сигнал, что четырёх обработчиков мало.
> Почему не просто `Task.Run` или неограниченный канал: первое теряет задания и ошибки, второе не даёт обратного давления и не переживает перезапуск. Почему не только база без канала: можно и так, но канал сглаживает всплески и даёт естественное ограничение параллелизма. Если инстансов много и нужна честная очередь между ними — вместо канала брокер ([[RabbitMQ: основы и паттерны]]).
