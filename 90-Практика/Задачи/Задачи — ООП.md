# Задачи — ООП

> [!abstract] Коротко
> 50 задач по разделу [[03 — ООП (обзор раздела)]]: классы и инициализация, инкапсуляция, наследование и полиморфизм, интерфейсы, равенство и сравнение, проектирование. Последний блок — самый ценный: там нет однозначно правильного ответа, есть обоснованный выбор. Решения свёрнуты; открывай после своей попытки, а в задачах на проектирование сравнивай не код, а аргументы.

> [!tip] Как решать
> - Задачи «что выведет» решай **до** запуска: ценность в предсказании.
> - В задачах на рефакторинг сначала выпиши, что именно плохо, и только потом переписывай.
> - После каждого решения задай вопрос: какое изменение требований сломает этот код и во скольких файлах.
> - Через неделю вернись к блоку 6 — проектные решения переосмысливаются лучше всего на второй проход.

Код рассчитан на .NET 10 / C# 14 с включёнными nullable reference types.

## 1. Классы, конструкторы, инициализация

### 1.1. Порядок инициализации
Что выведет?

```csharp
class A { public A() { Console.Write("A"); Init(); } protected virtual void Init() => Console.Write("a"); }
class B : A { private readonly string _s = "s"; protected override void Init() => Console.Write(_s ?? "null"); }
_ = new B();
```

> [!success]- Решение
> Выведет `Anull`. Порядок: инициализаторы полей наследника (`_s = "s"`) выполняются **до** конструктора базы... на самом деле в C# именно так, но виртуальный вызов происходит внутри конструктора `A`, который выполняется после инициализаторов полей `B` — поэтому `_s` уже равно `"s"`. Однако если бы поле присваивалось в **теле** конструктора `B`, оно ещё было бы `null`. Проверь оба варианта — и запомни правило: виртуальные методы из конструктора не вызывают.

### 1.2. Цепочка конструкторов
Сделай класс `Range` с конструкторами `(int from, int to)` и `(int to)`, чтобы второй делегировал первому.

> [!success]- Решение
> ```csharp
> public sealed class Range
> {
>     public Range(int from, int to)
>     {
>         if (from > to) throw new ArgumentException("from больше to", nameof(from));
>         From = from; To = to;
>     }
>     public Range(int to) : this(0, to) { }      // делегирование: валидация в одном месте
>     public int From { get; }
>     public int To { get; }
> }
> ```

### 1.3. Первичный конструктор
Перепиши класс с тремя зависимостями через первичный конструктор C# 12 и скажи, чем он отличается от `record`.

> [!success]- Решение
> ```csharp
> public sealed class OrderService(IOrderRepository repo, ILogger<OrderService> logger, TimeProvider clock);
> ```
> В отличие от `record`: свойства не создаются, `Equals`/`ToString` не генерируются, параметры не `readonly` — их можно переприсвоить внутри класса.

### 1.4. Инициализатор объекта против конструктора
Когда инициализатор объекта опасен?

> [!success]- Решение
> Когда обязательные поля можно не задать: объект окажется в некорректном состоянии. Лечится `required` (C# 11) или конструктором с обязательными параметрами.

### 1.5. Статический конструктор
Что произойдёт, если статический конструктор бросит исключение?

> [!success]- Решение
> Рантайм обернёт его в `TypeInitializationException`, а тип пометит как непригодный: **все** последующие обращения будут бросать то же исключение до перезапуска процесса. Поэтому в статических конструкторах не читают файлы и не ходят в сеть.

### 1.6. Объект без валидного состояния
Сделай так, чтобы `Temperature` нельзя было создать со значением ниже абсолютного нуля.

> [!success]- Решение
> ```csharp
> public readonly record struct Temperature
> {
>     public Temperature(double celsius)
>     {
>         if (celsius < -273.15) throw new ArgumentOutOfRangeException(nameof(celsius));
>         Celsius = celsius;
>     }
>     public double Celsius { get; }
> }
> ```
> Оговорка: у структуры остаётся `default` в обход конструктора (0 °C — здесь безобидно). Для строгих инвариантов нужен класс.

### 1.7. Фабричный метод
Когда фабричный метод лучше конструктора?

> [!success]- Решение
> Когда нужно осмысленное имя (`Money.FromCents(500)`), возможность вернуть `null` или Result вместо исключения, кеширование экземпляров, выбор конкретного типа наследника или асинхронная инициализация (конструктор не может быть `async`).

### 1.8. Деконструктор
Добавь деконструкцию к обычному классу.

> [!success]- Решение
> ```csharp
> public sealed class Point(int x, int y)
> {
>     public int X { get; } = x;
>     public int Y { get; } = y;
>     public void Deconstruct(out int x, out int y) { x = X; y = Y; }
> }
> var (a, b) = new Point(1, 2);
> ```
> Метод `Deconstruct` распознаётся по форме — интерфейс не нужен; он же включает позиционные паттерны.

## 2. Инкапсуляция и свойства

### 2.1. Найди дыру
```csharp
public class Cart { public List<Item> Items { get; } = []; public decimal Total { get; set; } }
```

> [!success]- Решение
> Две дыры: `Items` доступен на изменение (`Clear`, `Add`) в обход правил, `Total` можно установить произвольно и рассинхронизировать с составом. Лечение: приватный список плюс `IReadOnlyList<Item>`, `Total` — вычисляемое свойство, изменения через методы.

### 2.2. Защитная копия
Почему конструктор, принимающий `List<T>`, должен копировать его?

> [!success]- Решение
> Иначе вызывающий сохраняет ссылку и меняет состояние объекта снаружи. `_items = [..items];` решает проблему.

### 2.3. Свойство или метод
Какие из этих членов должны быть методами: `Count`, `Total` (сумма 10 позиций), `LatestFromDb`, `ToArray()`, `IsValid` (проверка 5 полей)?

> [!success]- Решение
> Методом обязан быть `LatestFromDb` (ввод-вывод, асинхронность) и `ToArray()` (создаёт новый объект каждый раз). Остальные — свойства: дёшево, детерминированно, без побочных эффектов.

### 2.4. `field`
Сделай свойство `Discount`, которое обрезает значение к диапазону 0–100, не заводя приватного поля.

> [!success]- Решение
> ```csharp
> public int Discount { get; set => field = Math.Clamp(value, 0, 100); }
> ```

### 2.5. init против private set
В чём разница и что выбрать для `Id` сущности?

> [!success]- Решение
> `init` фиксирует значение после создания навсегда, `private set` разрешает менять изнутри в любой момент. Для `Id` — `init` (или `{ get; }`), потому что идентичность не меняется.

### 2.6. internal как граница
Как запретить другому модулю использовать реализацию репозитория?

> [!success]- Решение
> Вынести модуль в отдельную сборку: публичны интерфейс и DTO, реализация — `internal`. Компилятор не даст обратиться напрямую; пространство имён такой гарантии не даёт.

### 2.7. protected
Почему `protected`-поле — плохая идея?

> [!success]- Решение
> Оно становится частью публичного контракта для всех наследников (в том числе из чужих сборок) и фиксирует реализацию базы навсегда. Лучше приватное поле плюс `protected`-метод, а ещё лучше — `private protected`.

### 2.8. Анемичность
Является ли DTO с публичными сеттерами нарушением инкапсуляции?

> [!success]- Решение
> Нет. У DTO нет инвариантов и поведения — прятать нечего. Нарушение начинается там, где у типа есть правила, но их можно обойти извне.

## 3. Наследование и полиморфизм

### 3.1. override против new
```csharp
class A { public virtual string N() => "A"; }
class B : A { public new string N() => "B"; }
A x = new B();
Console.WriteLine(x.N());
```

> [!success]- Решение
> `A`. `new` не участвует в виртуальной диспетчеризации: вызов разрешается по статическому типу переменной. Нужен `override`.

### 3.2. Ковариантный возврат
Перепиши `abstract Animal Clone()` так, чтобы наследник возвращал свой тип.

> [!success]- Решение
> ```csharp
> abstract class Animal { public abstract Animal Clone(); }
> sealed class Cat : Animal { public override Cat Clone() => new(); }   // C# 9
> ```

### 3.3. Нарушение подстановки
Приведи пример наследника, ломающего LSP, и способ это исправить.

> [!success]- Решение
> `Square : Rectangle` с зависимыми сеттерами: код, ожидающий независимые ширину и высоту, получает неверную площадь. Исправление — сделать типы иммутабельными или не связывать их наследованием вовсе.

### 3.4. sealed
Зачем помечать классы `sealed` по умолчанию?

> [!success]- Решение
> Убирает незапланированное наследование (а с ним обязательства поддерживать поведение для потомков) и помогает JIT девиртуализировать вызовы.

### 3.5. Шаблонный метод
Спроектируй базовый класс так, чтобы наследник не мог пропустить валидацию.

> [!success]- Решение
> Публичный **невиртуальный** метод в базе задаёт алгоритм и вызывает `protected abstract` шаги. Если сделать сам метод виртуальным, наследник переопределит его целиком и пропустит валидацию.

### 3.6. Вызов base
Когда переопределение обязано вызывать `base.Method()`?

> [!success]- Решение
> Когда оно расширяет поведение (`Dispose`, `OnConfiguring`, обработчики жизненного цикла). Если поведение заменяется полностью — не должно. Правило фиксируют в документации базового класса.

### 3.7. Что вызовется
```csharp
class A { public void Run() => Step(); protected virtual void Step() => Console.Write("A"); }
class B : A { protected override void Step() => Console.Write("B"); }
new B().Run();
```

> [!success]- Решение
> `B`. Невиртуальный `Run` вызывает виртуальный `Step`, диспетчеризация — по фактическому типу. Это и есть механика шаблонного метода.

### 3.8. Перегрузка и статический тип
```csharp
void Handle(object o) => Console.Write("object");
void Handle(string s) => Console.Write("string");
object arg = "текст";
Handle(arg);
```

> [!success]- Решение
> `object`. Перегрузки разрешаются на этапе компиляции по статическому типу, в отличие от переопределений.

### 3.9. Глубина иерархии
Иерархия из пяти уровней с переопределениями на каждом. Чем это плохо и что делать?

> [!success]- Решение
> Чтобы понять поведение метода, нужно прочитать все пять классов; изменение базы ломает потомков; тестировать промежуточные уровни неудобно. Лечение — плоская структура плюс композиция: стратегии и декораторы вместо уровней.

## 4. Интерфейсы и абстракции

### 4.1. Интерфейс или абстрактный класс
Нужен контракт «отправитель уведомлений» и общий код валидации получателя. Что выбрать?

> [!success]- Решение
> Оба: интерфейс `INotificationChannel` как контракт для DI и потребителей, абстрактный класс `NotificationChannelBase` с общей валидацией — как необязательная база для реализаций.

### 4.2. Толстый интерфейс
Чем плох интерфейс на 15 методов?

> [!success]- Решение
> Потребители зависят от того, чем не пользуются; реализации вынуждены поддерживать всё (иногда через `NotSupportedException`); моки в тестах громоздкие. Делят по ролям.

### 4.3. Реализация по умолчанию
Почему метод по умолчанию не виден через конкретный класс?

> [!success]- Решение
> Он принадлежит интерфейсу, а не типу: класс его не наследует как свой член. Нужно приведение к интерфейсу. Часто удобнее метод расширения.

### 4.4. Явная реализация
Когда она необходима?

> [!success]- Решение
> Конфликт одинаковых членов двух интерфейсов; сокрытие служебных членов (не-обобщённые `GetEnumerator`, `CompareTo(object)`); отдельное поведение или сигнатура для интерфейсной версии.

### 4.5. Структура и интерфейс
Почему `((IShape)square).Area` может быть дороже, чем кажется?

> [!success]- Решение
> Приведение структуры к интерфейсу упаковывает её — аллокация плюс виртуальный вызов. В дженерике с ограничением `where T : IShape` упаковки нет.

### 4.6. Маркерный интерфейс
Стоит ли делать пустой `IAggregateRoot`?

> [!success]- Решение
> Иногда да — для сканирования сборки и ограничений дженериков (`where T : IAggregateRoot`). Но чаще то же решается атрибутом или явной регистрацией; пустой интерфейс не выражает поведения.

### 4.7. Абстракция «течёт»
Что не так с `IRepository { IQueryable<T> Query(); }`?

> [!success]- Решение
> Контракт раскрывает LINQ-провайдер: поведение зависит от ORM, реализовать его на Dapper или списке в памяти честно невозможно. Нужны методы в терминах задачи.

### 4.8. Статические абстрактные члены
Зачем они нужны и где используются?

> [!success]- Решение
> Позволяют вызывать статические члены типа-параметра в обобщённом коде (`T.Parse`, `T.Zero`). На этом построена обобщённая математика: `INumber<T>`, `IParsable<T>`.

## 5. Равенство и сравнение

### 5.1. Классика
Почему при переопределении `Equals` обязателен `GetHashCode`?

> [!success]- Решение
> Хеш-коллекции выбирают корзину по хешу и только внутри неё сравнивают: равные объекты с разными хешами попадут в разные корзины, и поиск не найдёт элемент.

### 5.2. Мутирующий ключ
```csharp
var set = new HashSet<Box>(); var b = new Box { Size = 1 }; set.Add(b); b.Size = 2;
Console.WriteLine(set.Contains(b));
```

> [!success]- Решение
> `False`, если хеш зависит от `Size`: объект остался в старой корзине. Ключи должны быть иммутабельными.

### 5.3. Симметричность
Почему `base.Equals(derived)` может вернуть `true`, а обратное — `false`?

> [!success]- Решение
> База сравнивает свои поля через `is`, наследник требует свой тип. Лечение — сравнение `GetType()` или `sealed`-типы; `record` решает это через `EqualityContract`.

### 5.4. Что генерирует record
Какие члены создаст компилятор для `record struct Money(decimal A, string C)`?

> [!success]- Решение
> `Equals`, `GetHashCode`, `IEquatable<T>`, `==`/`!=`, `ToString`, `Deconstruct`, поддержку `with`. **Не** создаст `IComparable<T>` и операторы `<`/`>`.

### 5.5. Хеш строки
Можно ли сохранить `"abc".GetHashCode()` в базу?

> [!success]- Решение
> Нет: хеш строк рандомизирован при каждом запуске процесса. Для стабильного значения нужен явный алгоритм (SHA-256, xxHash).

### 5.6. CompareTo
Почему `x.Id - y.Id` — плохая реализация?

> [!success]- Решение
> Вычитание переполняется на больших значениях и даёт неверный знак. Правильно — `x.Id.CompareTo(y.Id)`.

### 5.7. Стабильность сортировки
Почему `List.Sort` опасен в пагинации?

> [!success]- Решение
> Он нестабилен: элементы с равными ключами могут менять порядок, и один и тот же элемент попадёт на две страницы. Лечение — доопределить сортировку уникальным ключом.

### 5.8. Внешний компаратор
Как сравнивать товары по-разному в двух местах, не меняя `Equals`?

> [!success]- Решение
> Написать `IEqualityComparer<T>`/`IComparer<T>` и передать его в конструктор коллекции или в LINQ-метод. У типа остаётся одно естественное сравнение.

## 6. Проектирование: найди проблему и переделай

### 6.1. Бог-объект
`OrderManager` на 900 строк: создание, оплата, экспорт, письма, отчёты. План рефакторинга?

> [!success]- Решение
> Разделить по причинам изменения: `OrderCreator`, `PaymentProcessor`, `OrderExporter`, `OrderNotifier`. Порядок действий: сначала покрыть текущее поведение тестами, затем выносить по одной ответственности за коммит, оставляя старый класс фасадом, пока вызывающие не переедут.

### 6.2. Флаги в параметрах
`Save(order, true, false, true)`. Что предложить?

> [!success]- Решение
> Отдельные методы с именами (`Save`, `SaveAndNotify`) или объект параметров с `init`-свойствами. Булевы флаги делают вызов нечитаемым и означают, что метод делает несколько дел.

### 6.3. Утечка коллекции
Сервис возвращает `List<Order>`, вызывающий его меняет. Как закрыть?

> [!success]- Решение
> Возвращать `IReadOnlyList<Order>` или `ImmutableArray<Order>`; если данные кешируются — обязательно иммутабельную копию, иначе кеш испортят снаружи.

### 6.4. Наследование ради переиспользования
`class ReportService : HttpHelper`. Что не так?

> [!success]- Решение
> Отношения «является» нет: сервис не является помощником по HTTP. Правильно — внедрить `HttpClient` или свой клиент как зависимость.

### 6.5. Зависть к данным
Метод калькулятора обращается только к полям заказа. Что делать?

> [!success]- Решение
> Перенести поведение в `Order` (или в value object), оставив калькулятору только то, что зависит от внешних правил (тарифы, конфигурация).

### 6.6. Статическое состояние
`public static class Session { public static User? Current { get; set; } }`. Чем опасно?

> [!success]- Решение
> Скрытая зависимость, невидимая в подписи; гонки в многопоточной среде; тесты влияют друг на друга. Заменить на внедряемый `IUserContext` со scoped-временем жизни.

### 6.7. Интерфейс-копия
`IOrderService` дословно повторяет `OrderService` и меняется вместе с ним. Оставить?

> [!success]- Решение
> Это не абстракция, а точка подмены для DI и тестов — допустимо, но не стоит считать развязкой. Если тесты пишутся на реальном объекте, интерфейс можно убрать.

### 6.8. Выбор модели
Спроектируй типы для «перевод денег между счетами»: что будет сущностью, что значением, что сервисом.

> [!success]- Решение
> `Account` — сущность (идентичность, состояние, методы `Withdraw`/`Deposit` с правилами). `Money` — `readonly record struct` (значение). `Transfer` — либо доменная служба `TransferService`, если операция затрагивает два агрегата, либо сущность, если перевод сам по себе имеет жизненный цикл и статусы. Правило: операция, не принадлежащая ни одному объекту целиком, становится доменной службой.

### 6.9. Спроектировать заново
Требования: система скидок, где правила меняются маркетингом, могут комбинироваться и включаться по датам. Первая версия — `switch` по типу клиента. Как сделать правильно?

> [!success]- Решение
> ```csharp
> public interface IDiscountRule
> {
>     bool AppliesTo(Order order, DateTimeOffset now);
>     Money Calculate(Order order);
> }
>
> public sealed class DiscountEngine(IEnumerable<IDiscountRule> rules, TimeProvider clock)
> {
>     public Money Total(Order order)
>     {
>         var now = clock.GetUtcNow();
>         return rules.Where(r => r.AppliesTo(order, now))
>                     .Aggregate(Money.Zero(order.Currency), (sum, r) => sum + r.Calculate(order));
>     }
> }
> ```
> Почему так: правила становятся независимыми объектами, поэтому добавление нового не меняет существующий код (открытость/закрытость); комбинируемость получается бесплатно — движок складывает применимые; даты и клиент передаются в правило, а не зашиваются в `switch`. Набор правил приходит из DI, а значит может собираться из конфигурации или из базы.
> Что обсудить дополнительно: порядок применения и взаимоисключающие правила (нужна приоритезация или политика «только лучшая скидка»), ограничение суммарной скидки, и то, что правила должны быть чистыми функциями — иначе их нельзя ни протестировать, ни закешировать.
