# Задачи — CLR и память

> [!abstract] Коротко
> 30 задач по разделу [[04 — Типы, память, CLR (обзор раздела)]]: где что лежит, упаковка и специализация дженериков, поведение сборщика мусора, освобождение ресурсов и поиск утечек, работа без аллокаций, устройство платформы. Много задач вида «предскажи поведение» и «найди причину» — именно так эти знания применяются на практике и проверяются на собеседовании.

> [!tip] Как решать
> - Задачи «что выведет» и «сколько аллокаций» решай **до** запуска: ценность в предсказании.
> - Проверять предсказания удобно на sharplab.io (IL и декомпиляция) и в BenchmarkDotNet с `MemoryDiagnoser`.
> - В задачах на диагностику сначала выпиши гипотезы, потом сверяйся с решением: правильный ход мысли важнее точного ответа.
> - Задачи с дампами имеет смысл действительно прогнать через `dotnet-dump` хотя бы раз — иначе навык не появится.

## 1. Типы и память

### 1.1. Где что лежит
Для каждого значения скажи, где оно находится: `int` — локальная переменная; `int` — поле класса; `int` — элемент `int[]`; `int`, захваченный лямбдой; `int`, приведённый к `object`.

> [!success]- Решение
> Стек (или регистр); куча — внутри объекта; куча — внутри массива; куча — в поле класса замыкания; куча — в упакованном объекте. Правило: значимый тип живёт там, где объявлен, а «переезд» в кучу происходит при захвате замыканием, попадании в объект-автомат `async`/итератора и при упаковке.

### 1.2. Размер объекта
Сколько занимает в куче экземпляр `class Empty { }` и `class WithInt { int X; }` на x64?

> [!success]- Решение
> Оба 24 байта: 8 байт слово синхронизации + 8 байт указатель на таблицу методов + поля с выравниванием до 8. Минимальный объект — 24 байта даже без полей. Отсюда правило: миллион мелких объектов дороже массива структур не только по сумме полей, но и на заголовках.

### 1.3. Массив структур против массива классов
`Point[] 1_000_000` (структура из двух `int`) против `PointClass[] 1_000_000`. Сколько объектов в куче и почему разница в скорости обхода?

> [!success]- Решение
> Первый — **один** объект (заголовок + 8 млн байт данных подряд). Второй — 1 000 001 объект: массив ссылок плюс миллион объектов по 24 байта, разбросанных по куче. Разница в обходе достигает 5–10 раз: в первом случае данные читаются последовательно и попадают в кеш строками, во втором каждое обращение — переход по ссылке и вероятный промах.

### 1.4. Копирование структуры
Что выведет?
```csharp
struct Counter { public int Value; }
var list = new List<Counter> { new() };
var item = list[0];
item.Value = 5;
Console.WriteLine(list[0].Value);
```

> [!success]- Решение
> `0`. Индексатор `List<T>` возвращает **копию** структуры, изменение уходит в неё. У массива было бы иначе: `array[0].Value = 5` работает, потому что индексатор массива даёт ссылку на элемент. Это одна из причин делать структуры `readonly`.

### 1.5. Переполнение стека
Почему `StackOverflowException` нельзя перехватить и как писать обход дерева неизвестной глубины?

> [!success]- Решение
> Для выполнения блока `catch` нужен стек, а он исчерпан, поэтому рантайм сразу завершает процесс. Обход пишут итеративно с явным `Stack<T>` в куче — тогда глубина ограничена только памятью, и при её нехватке возникает перехватываемое `OutOfMemoryException`.

### 1.6. async и локальные переменные
Почему асинхронный метод с десятью локальными переменными дороже синхронного?

> [!success]- Решение
> Компилятор превращает его в конечный автомат: все локальные переменные, живущие через `await`, становятся полями объекта состояния, который после первого приостанавливающего `await` размещается в куче. Синхронный метод держал бы их в кадре стека бесплатно.

## 2. Упаковка и дженерики

### 2.1. Найди упаковки
```csharp
struct P { public int X; }
var p = new P();
object o = p;
IComparable c = 42;
var list = new List<P> { p };
Console.WriteLine($"{p.X}");
Console.WriteLine(string.Format("{0}", p.X));
```

> [!success]- Решение
> Упаковки: `object o = p` и `IComparable c = 42` (приведение к `object`/интерфейсу); `string.Format` — аргумент уходит в `params object[]`, плюс аллокация массива. Не упаковывают: `List<P>` (обобщённая коллекция хранит структуры по значению) и интерполяция начиная с C# 10 (handler пишет `int` прямо в буфер).

### 2.2. Структура как ключ
Почему `Dictionary<PointStruct, string>` может работать в разы медленнее ожидаемого?

> [!success]- Решение
> Без `IEquatable<T>` сравнение идёт через `ValueType.Equals(object)`: упаковка обоих операндов на каждое сравнение, а внутри — сравнение полей рефлексией, если структура содержит ссылки или имеет промежутки выравнивания. Плюс `ValueType.GetHashCode` даёт плохое распределение. Лечение — `readonly record struct` или ручная реализация `IEquatable<T>` и `GetHashCode`.

### 2.3. Дженерик против интерфейса
Почему `Sum<T>(ReadOnlySpan<T>) where T : IShape` не аллоцирует, а `Sum(ReadOnlySpan<IShape>)` — да?

> [!success]- Решение
> Для значимого типа JIT создаёт отдельную специализацию машинного кода: элементы лежат по значению, вызов через ограничение разрешается статически (`constrained.callvirt`) и обычно встраивается. Во втором варианте каждый элемент приводится к интерфейсу, то есть упаковывается, и вызовы становятся виртуальными.

### 2.4. Статика в дженерике
Что выведет?
```csharp
static class Counter<T> { public static int Value; }
Counter<int>.Value = 1;
Counter<string>.Value = 2;
Console.WriteLine(Counter<int>.Value + Counter<string>.Value);
```

> [!success]- Решение
> `3`. `Counter<int>` и `Counter<string>` — разные закрытые типы со своими статическими полями. Это используют как быстрый кеш «по типу»: доступ — чтение поля, без словаря и блокировок.

### 2.5. Распаковка
Почему падает и как исправить?
```csharp
object boxed = 42;
long value = (long)boxed;
```

> [!success]- Решение
> `InvalidCastException`: распаковать можно только в исходный тип, даже если целевой шире. Правильно `(long)(int)boxed` — сначала распаковка в `int`, потом расширяющее преобразование.

### 2.6. Nullable в упаковке
Что выведет?
```csharp
int? a = null;
object o = a;
Console.WriteLine(o is null);
int? b = 5;
object o2 = b;
Console.WriteLine(o2!.GetType().Name);
```

> [!success]- Решение
> `True` и `Int32`. Рантайм обрабатывает `Nullable<T>` особо: пустое значение упаковывается в `null`, а непустое — как сам `T`, без обёртки. Поэтому `o.GetType()` для первого случая бросил бы `NullReferenceException`.

## 3. Сборка мусора

### 3.1. Циклические ссылки
Соберёт ли GC два объекта, ссылающихся друг на друга и больше ни на кого?

> [!success]- Решение
> Да. .NET использует обход графа достижимости от корней, а не подсчёт ссылок: цикл, недостижимый от корней, считается мусором. Именно поэтому в .NET нет проблемы циклов, характерной для схем с подсчётом ссылок.

### 3.2. Поколения
Почему объекты «средней» продолжительности жизни хуже всего для сборщика?

> [!success]- Решение
> Они переживают молодые сборки и продвигаются в gen 2, где мусор убирается только полными сборками — самыми дорогими. Схема поколений эффективна на крайностях: умереть в gen 0 или жить долго и переиспользоваться. Типичный источник проблемы — кеш с коротким временем жизни элементов.

### 3.3. LOH
С какого размера массив попадает в LOH и почему это заметно?

> [!success]- Решение
> От 85 000 байт: для `byte[]` это ~85 000 элементов, для `int[]` ~21 250. LOH относится к gen 2 (собирается редко) и по умолчанию не уплотняется, поэтому частое выделение больших массивов даёт фрагментацию: свободной памяти много, а непрерывного блока нет, и куча растёт. Лечение — `ArrayPool<T>` и потоковая обработка.

### 3.4. GC.Collect
Когда вызов `GC.Collect()` оправдан?

> [!success]- Решение
> Практически только в тестах и бенчмарках, где нужен детерминизм, и изредка — после разового освобождения очень большого объёма данных. В обычном коде он запускает самую дорогую полную сборку и сбивает эвристики бюджетов, ухудшая последующие сборки.

### 3.5. Барьер записи
Как GC собирает gen 0, не обходя gen 2, если из старого объекта есть ссылка на новый?

> [!success]- Решение
> Через таблицу карт: каждая запись ссылки в поле проходит барьер записи, помечающий соответствующий участок старой памяти «грязным». При молодой сборке обходятся только помеченные участки. Побочный эффект — присваивание ссылочного поля чуть дороже, чем значимого.

### 3.6. Память не падает
После обработки большого файла `GC.GetTotalMemory(true)` показывает 80 МБ, а RSS процесса — 1,2 ГБ. Утечка?

> [!success]- Решение
> Нет: живых данных 80 МБ, значит утечки нет. Рантайм не возвращает освобождённые сегменты ОС немедленно — они удерживаются для повторного использования. Если высокий RSS мешает (лимит контейнера), надо снижать пик потребления: потоковая обработка, пул буферов, а не `GC.Collect()`.

## 4. Ресурсы и утечки

### 4.1. Зачем Dispose, если есть GC
Ответь одним абзацем.

> [!success]- Решение
> GC управляет только управляемой памятью и не знает про файловые дескрипторы, сокеты, соединения с БД и хендлы ОС. Даже став недостижимым, объект-обёртка будет собран недетерминированно, а ресурс всё это время останется занятым — вплоть до исчерпания лимитов ОС. `IDisposable` и `using` дают детерминированное освобождение в конце области видимости, в том числе при исключении.

### 4.2. Финализатор
Сколько сборок переживает объект с финализатором и почему?

> [!success]- Решение
> Минимум две. При первой сборке он не освобождается: попадает в очередь готовых к финализации и тем самым снова становится достижимым; отдельный поток вызывает финализатор; память освобождается только на следующей сборке. При этом объект уже оказался в старшем поколении, где сборки редки.

### 4.3. Найди ошибки
```csharp
public class Service : IDisposable
{
    private readonly DbContext _db;
    private readonly HttpClient _http = new();
    public Service(DbContext db) => _db = db;
    public void Dispose() { _db.Dispose(); _http.Dispose(); }
    ~Service() => Dispose();
}
```

> [!success]- Решение
> Освобождается чужой `DbContext` (его создал и освободит контейнер) — другие потребители получат `ObjectDisposedException`. Свой `HttpClient` на каждый экземпляр исчерпывает эфемерные порты — нужен `IHttpClientFactory`. Финализатор лишний (нативных ресурсов нет) и опасен: он вызывает полный `Dispose`, трогающий управляемые объекты, которые могут быть уже финализированы. Нет защиты от повторного вызова.

### 4.4. Утечка через событие
Почему подписка scoped-объекта на событие синглтона — утечка?

> [!success]- Решение
> Делегат хранит ссылку на подписчика в `Target`, а событие хранит делегаты. Пока жив синглтон, живы все подписчики. Лечение — отписка в `Dispose` (с сохранением того же экземпляра делегата) или отказ от событий между компонентами разного времени жизни в пользу очереди.

### 4.5. Маршрут расследования
Память растёт на 50 МБ в час. Опиши последовательность действий.

> [!success]- Решение
> `dotnet-counters monitor` — подтвердить рост управляемой кучи после полных сборок; два дампа с интервалом (`dotnet-dump collect`); в `dotnet-dump analyze` — `dumpheap -stat` для поиска типа с растущим количеством; `dumpheap -type <Имя>` для адресов; `gcroot <адрес>` — цепочка от корня, то есть ответ «кто держит». Дальше исправление по находке: статический кеш, подписка, незавершённая задача.

### 4.6. Transient и IDisposable
Почему `Transient`-сервис с `IDisposable` может выглядеть как утечка?

> [!success]- Решение
> Контейнер удерживает ссылки на все созданные им освобождаемые экземпляры до конца области, чтобы вызвать `Dispose`. В singleton-области это означает накопление объектов на всё время жизни приложения. Решение — сделать сервис `Scoped` или создавать его фабрикой и освобождать самостоятельно.

## 5. Span, аллокации, платформа

### 5.1. Срез
В чём разница между `array[1..4]` и `array.AsSpan()[1..4]`?

> [!success]- Решение
> Первое создаёт новый массив и копирует элементы — аллокация, независимая жизнь. Второе создаёт окно в ту же память — ни аллокации, ни копирования, запись через срез меняет исходные данные. Для строк аналогично: `Substring` против `AsSpan`.

### 5.2. Почему нельзя
Почему `Span<T>` нельзя сохранить в поле класса и использовать после `await`?

> [!success]- Решение
> Он может указывать на стек, а объект в куче и продолжение после `await` переживают кадр метода: ссылка стала бы висячей. Правила `ref struct` запрещают это на этапе компиляции. Для хранения и асинхронных API есть `Memory<T>`.

### 5.3. stackalloc в цикле
Найди ошибку.
```csharp
for (int i = 0; i < 10_000; i++)
{
    Span<byte> buf = stackalloc byte[256];
    Process(buf);
}
```

> [!success]- Решение
> Память из `stackalloc` освобождается при выходе из **метода**, а не блока: 10 000 × 256 байт = 2,5 МБ накопятся в кадре и переполнят стек. Буфер нужно выделить один раз до цикла и при необходимости очищать `Clear()`.

### 5.4. Гибридный шаблон
Напиши схему «маленькое на стеке, большое из пула».

> [!success]- Решение
> ```csharp
> const int MaxStack = 256;
> char[]? rented = null;
> Span<char> buffer = needed <= MaxStack
>     ? stackalloc char[MaxStack]
>     : (rented = ArrayPool<char>.Shared.Rent(needed));
> try { /* работа со Span */ }
> finally { if (rented is not null) ArrayPool<char>.Shared.Return(rented); }
> ```
> Так написаны форматтеры чисел и дат в BCL: нулевые аллокации на типичных данных и безопасность на больших.

### 5.5. ArrayPool
Три ошибки при работе с пулом?

> [!success]- Решение
> Ориентироваться на `rented.Length` вместо запрошенной длины (лишние байты содержат чужой мусор); использовать массив после `Return` (его уже мог получить другой поток); не очищать буфер с чувствительными данными (`Return(array, clearArray: true)`). Плюс забытый `Return` — не утечка, но пул перестаёт помогать.

### 5.6. Первый запрос
Почему первый HTTP-запрос к свежему инстансу медленнее остальных в 100 раз?

> [!success]- Решение
> JIT компилирует весь путь запроса в tier 0 (Kestrel, middleware, роутинг, сериализация, EF Core); устанавливается физическое соединение с БД и наполняется пул; EF Core компилирует модель и планы; кеши пусты. Дальше горячие методы уходят в tier 1 с профилем, и время падает на порядок. Лечение — ReadyToRun и прогревочные запросы в readiness-пробе.

## Итоговые задачи

### 6.1. Собрать всё вместе
Что происходит при выполнении `var s = new string('a', 100_000)`? Разбери по шагам.

> [!success]- Решение
> Вычисляется требуемый размер: 100 000 символов по 2 байта (UTF-16) плюс заголовок объекта (16 байт) и поле длины — примерно 200 KБ. Это **больше порога LOH в 85 000 байт**, поэтому объект выделяется не в gen 0, а сразу в Large Object Heap и логически относится к gen 2. Рантайм резервирует место (при нехватке — расширяет кучу или запускает сборку), заполняет заголовок указателем на таблицу методов `System.String`, записывает длину и заполняет буфер символом `'a'`. Переменная `s` на стеке получает ссылку.
> Практические следствия: такая строка будет освобождена только при полной сборке; частое создание подобных строк фрагментирует LOH; если строка нужна для дальнейшей обработки по частям, лучше работать со `Span<char>` или писать в буфер из пула, а не материализовать её целиком. Это стандартный вопрос на собеседовании именно потому, что связывает сразу три темы: размер объекта, LOH и поколения.

### 6.2. Диагностика по симптомам
Для каждого симптома назови вероятную причину и первый шаг: (а) память растёт монотонно; (б) память высокая, но живых данных мало, `gc-fragmentation` высокая; (в) время в GC 30 %; (г) приложение перестало открывать файлы, память в норме.

> [!success]- Решение
> **(а)** Утечка — лишняя достижимость. Первый шаг: два дампа с интервалом, `dumpheap -stat`, `gcroot` для растущего типа. Типичные держатели — статические коллекции, подписки, незавершённые задачи.
> **(б)** Фрагментация LOH от частых больших массивов. Первый шаг: найти источник больших аллокаций (`dotnet-gcdump` или профиль аллокаций) и перевести на `ArrayPool`/потоковую обработку. Разовое уплотнение LOH — временная мера.
> **(в)** Слишком высокая скорость аллокаций. Первый шаг: `dotnet-counters` для `alloc-rate`, затем профиль аллокаций и устранение мусора в горячем пути (упаковка, замыкания, промежуточные строки и коллекции).
> **(г)** Утечка неуправляемых ресурсов — незакрытые файлы или сокеты. Память здесь ни при чём: смотреть число открытых дескрипторов (`lsof`), искать пропущенный `using`, `HttpClient` на каждый запрос, незакрытые соединения.

### 6.3. Обосновать выбор
Нужно хранить 5 миллионов записей «идентификатор + цена + флаг» в памяти для быстрого перебора. Что выбрать и почему?

> [!success]- Решение
> ```csharp
> readonly record struct Row(long Id, decimal Price, bool IsActive);
> Row[] rows = new Row[5_000_000];
> ```
> Обоснование: структура в массиве даёт **один** объект в куче и непрерывное размещение данных — обход идёт последовательно и попадает в кеш, тогда как массив классов создал бы 5 000 001 объект, добавил по 16 байт заголовка на каждый и разбросал данные по памяти (в 5–10 раз медленнее на переборе, плюс существенно больше работы для GC). `readonly` исключает случайные копии-мутации, `record struct` даёт равенство и хеш без упаковки.
> Оговорки, которые стоит проговорить: размер массива (`long` 8 + `decimal` 16 + `bool` с выравниванием ≈ 32 байта × 5 млн ≈ 160 МБ) заведомо превышает порог LOH, значит массив живёт в LOH и собирается только при полных сборках — это нормально для долгоживущего кеша, но плохо, если он часто пересоздаётся. Если данные пересоздаются регулярно, стоит переиспользовать один массив. И если `decimal` избыточен по точности, замена на `long` в минимальных единицах уменьшит запись до 24 байт и объём почти на треть.
