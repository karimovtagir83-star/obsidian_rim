# Дата и время: DateTime, DateTimeOffset, TimeProvider

> [!abstract] Коротко
> `DateTime` хранит момент времени и слабый признак `Kind` (Local/Utc/Unspecified), который ничего не гарантирует и легко теряется. `DateTimeOffset` хранит момент времени вместе со смещением от UTC явно — однозначно, без Kind-путаницы. `TimeProvider` (.NET 8+, доступен в net8.0) — абстракция над «текущим временем», которая делает код с датами тестируемым.

## Зачем это знать

Баг с часовыми поясами почти никогда не проявляется у автора кода — он находится за одним поясом с сервером разработки и не замечает проблему до тех пор, пока пользователь или сервер в другом поясе не получит заказ, «созданный завтра», или пока переход на летнее время не сдвинет расчёт на час.

## Модель

| Тип | Что хранит | Проблема |
|---|---|---|
| `DateTime` | момент времени + `Kind` (`Utc`/`Local`/`Unspecified`) | `Kind` — это метка, не гарантия: можно создать `DateTime` с `Kind.Utc`, содержащий локальное время, и ничто не помешает |
| `DateTimeOffset` | момент времени + явное смещение от UTC | однозначен: два `DateTimeOffset` с одинаковым UTC-моментом равны независимо от смещения, сравнение корректно всегда |
| `TimeSpan` | продолжительность (не момент времени) | не путать с разницей дат — `TimeSpan` не знает, к какому моменту относится |

`DateTime.Now` — источник большинства проблем: возвращает локальное время сервера, `Kind = Local`. Если сервер задеплоен в другом часовом поясе, чем предполагал разработчик, всё сравнение дат сдвигается незаметно. `DateTime.UtcNow` — лучше, но всё ещё `DateTime`, а не `DateTimeOffset`, и Kind можно случайно потерять при сериализации через некоторые пути.

```csharp
// Ловушка: сравнение DateTime с разным Kind не бросает исключение,
// но даёт неверный результат
var utc = DateTime.UtcNow;              // Kind = Utc
var local = DateTime.Now;                // Kind = Local, тот же физический момент +N часов

Console.WriteLine(utc < local);          // true, хотя это один и тот же момент времени
// Сравнение DateTime игнорирует Kind при вычитании/сравнении —
// оба значения трактуются как "число тиков", без учёта смещения
```

```csharp
// DateTimeOffset сравнивается по абсолютному моменту, а не по "сырому" значению
var utcOffset = DateTimeOffset.UtcNow;
var localOffset = DateTimeOffset.Now;

Console.WriteLine(utcOffset == localOffset);   // true — один и тот же момент
```

### TimeProvider — абстракция времени для тестов (.NET 8+)

Прямой вызов `DateTime.UtcNow` внутри бизнес-логики делает код невозможным протестировать без реального ожидания времени. `TimeProvider` — абстрактный класс, который внедряется через DI и подменяется в тестах:

```csharp
public sealed class OrderExpirationChecker(TimeProvider timeProvider)
{
    public bool IsExpired(Order order) =>
        order.CreatedAt.AddHours(24) < timeProvider.GetUtcNow();
}

// В тесте — управляемое время без Thread.Sleep и без реального ожидания:
var fakeTime = new FakeTimeProvider(startTime: DateTimeOffset.Parse("2026-01-01T00:00:00Z"));
var checker = new OrderExpirationChecker(fakeTime);
fakeTime.Advance(TimeSpan.FromHours(25));
Assert.True(checker.IsExpired(order));
```

## Решения

| Ситуация | Что использовать |
|---|---|
| Хранение момента времени в БД, передача между сервисами | `DateTimeOffset` — однозначен независимо от часового пояса читателя |
| Локальное время для отображения пользователю | `DateTimeOffset` + явное преобразование в нужный часовой пояс на этапе отображения, не раньше |
| Бизнес-логика, зависящая от "текущего момента" | внедрять `TimeProvider`, не вызывать `DateTime.Now`/`UtcNow` напрямую внутри метода |
| Продолжительность (сколько прошло, таймаут) | `TimeSpan` |
| Только дата без времени (день рождения, дата документа) | `DateOnly` (.NET 6+, доступен в net8.0) — не `DateTime` с обнулённым временем |

## В ServiceShop

Расчёт сроков — истечение резерва товара, дедлайн ответа кредитного скоринга Nasiya/BML, время жизни промокода — всё это моменты времени, которые должны сравниваться однозначно независимо от того, в каком часовом поясе физически находится сервер или клиент. `DateTimeOffset` в доменных сущностях и `TimeProvider` в местах, где логика зависит от "сейчас" и должна быть тестируема (например, правило "заказ истекает через 24 часа"), — прямое применение модели из этой заметки.

## Где ошибаются

> [!warning] Подводные камни
> - **`DateTime.Now` в бизнес-логике вместо `UtcNow` или `DateTimeOffset`.** Работает на машине разработчика, ломается при смене часового пояса сервера или при переходе на летнее время.
> - **Сравнение `DateTime` с разным `Kind` без явного приведения к общему представлению.** Компилятор не подскажет — сравнение просто даст неверный, но синтаксически валидный результат.
> - **Прямой вызов `DateTime.UtcNow` внутри метода с бизнес-логикой.** Делает юнит-тест невозможным без реального ожидания времени или без хрупких трюков — тест либо flaky, либо не пишется вообще.
> - **Агент часто:** предлагает `DateTime.Now` как источник "текущего времени" в новом коде, потому что это более частый паттерн в обучающих примерах, чем `TimeProvider` — который появился относительно недавно (.NET 8) и реже встречается в старых материалах.

## Проверка на ревью

- Новый код для хранения/передачи моментов времени использует `DateTimeOffset`, а не голый `DateTime`.
- Бизнес-логика, зависящая от текущего времени, получает его через `TimeProvider` (или обёртку над ним), а не через прямой статический вызов.
- Сравнения дат не смешивают значения с разным `Kind` без явного приведения.
- Только дата без времени представлена `DateOnly`, а не `DateTime` с обнулённым временем суток.

## Проверь себя

> [!question]- Почему `DateTime` с `Kind.Utc` и `DateTime` с `Kind.Local` для одного и того же физического момента не равны при прямом сравнении?
> Оператор сравнения для `DateTime` работает с "сырым" числом тиков и не учитывает `Kind` при вычислении разницы — `Kind` это просто метка на значении, а не часть значения, влияющая на арифметику. Поэтому `DateTime.UtcNow` (условно 10:00 UTC) и `DateTime.Now` (тот же момент, условно 15:00 в поясе +5) сравниваются как два разных числа тиков, хотя физически это один момент времени.

> [!question]- Зачем нужен `TimeProvider`, если можно тестировать через `Thread.Sleep` в тесте?
> `Thread.Sleep` заставляет тест реально ждать физическое время — тест становится медленным и неустойчивым (flaky) при малейшей задержке окружения. `TimeProvider` позволяет "промотать" время мгновенно (`FakeTimeProvider.Advance(...)`) в тесте, оставляя реальный код неизменным — бизнес-логика получает время через абстракцию, а не через статический вызов, который невозможно подменить.

## Разбор

### Разбор 1. Найди причину бага

Сервис развёрнут на сервере в часовом поясе UTC+5. Бизнес-правило «заказ автоматически отменяется, если не оплачен в течение 30 минут» реализовано так:

```csharp
if (DateTime.Now - order.CreatedAt > TimeSpan.FromMinutes(30))
    CancelOrder(order);
```

`order.CreatedAt` был сохранён как `DateTime.UtcNow` в момент создания. Объясни, что произойдёт, и почини.

> [!success]- Разбор
> `DateTime.Now` возвращает локальное время сервера (UTC+5), а `order.CreatedAt` — время в UTC. Разница между ними включает пятичасовое смещение как часть "прошедшего времени" — заказ будет отменён почти сразу после создания (или наоборот, никогда, в зависимости от знака смещения), а не через 30 минут. Починка: сравнивать в одной системе координат — `DateTime.UtcNow - order.CreatedAt`, а лучше — хранить `CreatedAt` как `DateTimeOffset` и сравнивать через `TimeProvider.GetUtcNow()`, чтобы правило было ещё и тестируемым.

## Итог

- `DateTime` несёт `Kind` как необязательную метку; `DateTimeOffset` несёт смещение как часть значения и сравнивается однозначно
- Сравнение `DateTime` с разным `Kind` не бросает исключение, а тихо даёт неверный результат
- `TimeProvider` (.NET 8+) внедряется через DI и делает зависящую от времени логику тестируемой без реального ожидания
- Момент времени — `DateTimeOffset`, продолжительность — `TimeSpan`, только дата — `DateOnly`; смешивать роли этих типов — источник багов
