# Дженерики: ограничения и вариантность

> [!abstract] Коротко
> Ограничения (`where T : ...`) сообщают компилятору, что тип-аргумент умеет делать, — без них внутри дженерика доступны только члены `object`. Вариантность (`in`/`out` у параметров интерфейсов и делегатов) определяет, можно ли `IEnumerable<Кошка>` присвоить в `IEnumerable<Животное>`. Правило простое: **out — только на выход, in — только на вход**, и оба безопасны, пока тип-параметр не появляется «не на своей стороне». Массивы в .NET ковариантны исторически, и это признанная ошибка дизайна, за которую платят проверкой типа на каждой записи.

## Зачем это нужно

Без ограничений дженерик почти бесполезен:

```csharp
public static T Max<T>(T a, T b)
{
    // Ошибка CS0019: оператор '>' неприменим к операндам типа 'T' и 'T'
    return a > b ? a : b;
}
```

Компилятор компилирует тело дженерика **один раз**, не зная будущих типов, поэтому он обязан заранее убедиться, что `>` есть. Единственное, что он знает про голый `T`, — что это `object`. Ограничение возвращает знание:

```csharp
public static T Max<T>(T a, T b) where T : IComparable<T>
    => a.CompareTo(b) >= 0 ? a : b;
```

Вариантность решает другую задачу — присваиваемость. Естественная интуиция «список кошек — это список животных» в общем случае неверна, и вариантность формализует, когда именно она верна.

## Ограничения: полный список

| Ограничение | Что требует | Версия |
|---|---|---|
| `where T : struct` | Non-nullable value type | 2.0 |
| `where T : class` | Ссылочный тип (в nullable-контексте — non-nullable) | 2.0 |
| `where T : class?` | Ссылочный тип, допускается nullable | 8.0 |
| `where T : notnull` | Не-nullable: либо value type, либо non-nullable reference. Нарушение — **warning**, не error | 8.0 |
| `where T : unmanaged` | Unmanaged-тип (нет ссылочных полей на любой глубине). Подразумевает `struct` | 7.3 |
| `where T : BaseClass` | Наследник (или сам) `BaseClass` | 2.0 |
| `where T : IInterface` | Реализует интерфейс | 2.0 |
| `where T : U` | «Голое» ограничение: `T` конвертируется в другой тип-параметр `U` | 2.0 |
| `where T : new()` | Есть публичный конструктор без параметров | 2.0 |
| `where T : default` | Разрешает неоднозначность `T?` при переопределении | 9.0 |
| `where T : System.Enum` / `Delegate` / `MulticastDelegate` | Enum, делегат | 7.3 |
| `where T : allows ref struct` | **Анти-ограничение**: разрешает передавать `ref struct` | 13 |

Порядок в объявлении фиксированный: сначала `class`/`struct`/`unmanaged`/`notnull`, затем базовый класс, затем интерфейсы, затем `new()`, и только потом `allows ref struct`.

### Ограничения, которых нет

Нельзя написать `where T : Enum with flags`, `where T : операторы +`, `where T : конструктор с параметрами`. Первые два раньше приходилось имитировать; сегодня арифметику решает `static abstract` (см. ниже), а конструктор с параметрами — фабричным делегатом:

```csharp
public sealed class Pool<T>(Func<T> factory)   // вместо where T : new(...)
{
    private readonly Stack<T> _items = new();
    public T Rent() => _items.TryPop(out var x) ? x : factory();
    public void Return(T item) => _items.Push(item);
}
```

### `notnull`, `class` и `class?` — тонкость

```csharp
#nullable enable

static void A<T>(T value) where T : class { }   // T — non-nullable ref type
static void B<T>(T value) where T : class? { }  // T может быть string?
static void C<T>(T value) where T : notnull { } // T: int, string, но не string?

A<string>("x");     // ок
A<string?>(null!);  // warning CS8634
B<string?>(null);   // ок
C<int>(0);          // ок
C<string?>(null!);  // warning
```

`notnull` намеренно даёт **предупреждение, а не ошибку**: nullable-аннотации — это анализ, а не система типов CLR, и ломать сборку из-за них было бы слишком жёстко. См. [[Nullable reference types]].

### `unmanaged` — зачем

`unmanaged` означает: тип можно безопасно скопировать побайтово, взять его адрес и передать в нативный код. Формально — это `struct`, все поля которого рекурсивно тоже unmanaged (примитивы, enum, указатели, unmanaged-структуры).

```csharp
public static unsafe int SizeOf<T>() where T : unmanaged => sizeof(T);

Console.WriteLine(SizeOf<int>());        // Вывод: 4
Console.WriteLine(SizeOf<Guid>());       // Вывод: 16
// SizeOf<string>() — ошибка компиляции
```

Это фундамент для [[Span, ReadOnlySpan и Memory]], [[stackalloc и работа без аллокаций]] и [[Interop и P/Invoke]].

### `allows ref struct` — анти-ограничение (C# 13)

До C# 13 `ref struct` (например, `Span<T>`) нельзя было подставить в дженерик вообще: `List<Span<byte>>` невозможен, потому что `Span` обязан жить только на стеке. Это ломало даже простые вещи вроде `Where<T>` для спанов.

`allows ref struct` — не ограничение, а **разрешение**: оно расширяет множество допустимых типов, а не сужает.

```csharp
public static void ForEach<T, TAction>(Span<T> span, TAction action)
    where TAction : IAction<T>, allows ref struct
{
    foreach (ref var item in span)
        action.Invoke(ref item);
}
```

Плата: внутри такого дженерика `T` подчиняется правилам ref safety — нельзя боксить, класть в поле класса, использовать в асинхронном методе или в лямбде-замыкании.

```csharp
public class Box<T> where T : allows ref struct
{
    // Ошибка: T может быть ref struct, а поле класса живёт в куче
    // private T _field;

    public void M(scoped T parm) { }  // scoped разрешён именно потому, что T может быть ref struct
}
```

Нельзя комбинировать с `class`/`class?` — `ref struct` заведомо не ссылочный тип.

### `static abstract` в интерфейсах и generic math

C# 11 разрешил статические абстрактные члены в интерфейсах. Это дало то, чего дженерикам не хватало 20 лет: **операторы через ограничение**.

```csharp
public interface IAddable<TSelf> where TSelf : IAddable<TSelf>
{
    static abstract TSelf operator +(TSelf left, TSelf right);
    static abstract TSelf Zero { get; }
}

public static T Sum<T>(IEnumerable<T> items) where T : IAddable<T>
{
    T acc = T.Zero;                 // вызов статического члена через тип-параметр
    foreach (var x in items) acc += x;
    return acc;
}
```

В BCL это уже сделано: `System.Numerics.INumber<T>` и родня.

```csharp
using System.Numerics;

public static T Average<T>(ReadOnlySpan<T> values) where T : INumber<T>
{
    T sum = T.Zero;
    foreach (var v in values) sum += v;
    return sum / T.CreateChecked(values.Length);
}

Console.WriteLine(Average<int>([1, 2, 3, 4]));      // Вывод: 2
Console.WriteLine(Average<double>([1, 2, 3, 4]));   // Вывод: 2.5
Console.WriteLine(Average<decimal>([1, 2, 3, 4]));  // Вывод: 2.5
```

Механика: для value-типов CLR специализирует код под каждый `T` (см. [[Дженерики в CLR: как устроены]]), поэтому вызов `T.Zero` девиртуализируется и инлайнится — накладных расходов нет. Для ссылочных типов код разделяется, и вызов идёт через таблицу интерфейса.

Паттерн `where TSelf : IAddable<TSelf>` называется **CRTP** (curiously recurring template pattern) — интерфейс параметризован тем типом, который его реализует, иначе оператор не смог бы вернуть конкретный тип.

## Вариантность

### На пальцах

Есть `Животное` и `Кошка : Животное`. Вопрос: `IX<Кошка>` — это `IX<Животное>`?

- Если из `IX<T>` можно только **доставать** `T` — да. Достали кошку, а её ждали как животное. Безопасно. Это **ковариантность**, `out`.
- Если в `IX<T>` можно только **класть** `T` — наоборот: `IX<Животное>` можно использовать как `IX<Кошка>`. Приёмник, который переваривает любое животное, переварит и кошку. Это **контравариантность**, `in`.
- Если можно и класть, и доставать — никак. Это **инвариантность**.

```csharp
IEnumerable<string> strings = new List<string> { "a", "b" };
IEnumerable<object> objects = strings;   // ок: IEnumerable<out T>

Action<object> printAny = o => Console.WriteLine(o);
Action<string> printStr = printAny;      // ок: Action<in T>

IList<string> listOfStrings = new List<string>();
// IList<object> listOfObjects = listOfStrings;  // ошибка: IList<T> инвариантен
```

Почему `IList<T>` инвариантен, видно сразу, если представить, что было бы можно:

```csharp
IList<object> bad = listOfStrings;   // если бы разрешили...
bad.Add(42);                         // ...сюда попал бы int в List<string>
string s = listOfStrings[0];         // ...и здесь бы взорвалось
```

### Ключевые слова и правила

`out T` — тип-параметр может встречаться только в **выходных** позициях: возвращаемые значения, геттеры свойств, `out`-параметры.
`in T` — только во **входных**: параметры методов, сеттеры свойств.

```csharp
public interface IProducer<out T>
{
    T Produce();
    // void Consume(T item);        // ошибка CS1961: T в входной позиции
    // T Property { get; set; }     // ошибка: сеттер — входная позиция
    T Property { get; }             // ок
}

public interface IConsumer<in T>
{
    void Consume(T item);
    // T Produce();                 // ошибка CS1961
}

public interface ITransformer<in TIn, out TOut>
{
    TOut Transform(TIn input);
}
```

Компилятор проверяет это статически — «на вход/на выход» не соглашение, а правило языка.

### Где вариантность в BCL

| Тип | Вариантность |
|---|---|
| `IEnumerable<out T>`, `IEnumerator<out T>` | ковариантный |
| `IReadOnlyList<out T>`, `IReadOnlyCollection<out T>` | ковариантный |
| `IQueryable<out T>` | ковариантный |
| `IGrouping<out TKey, out TElement>` | ковариантный |
| `Func<in T1, ..., out TResult>` | контравариантен по аргументам, ковариантен по результату |
| `Action<in T1, ...>` | контравариантный |
| `Predicate<in T>`, `Comparison<in T>` | контравариантный |
| `IComparer<in T>`, `IEqualityComparer<in T>` | контравариантный |
| `IList<T>`, `ICollection<T>`, `IDictionary<K,V>` | инвариантные |
| `Task<T>`, `ValueTask<T>` | инвариантные (классы/структуры — вариантность возможна только у интерфейсов и делегатов) |

> [!info] Почему `Task<T>` инвариантен
> Вариантность в CLR разрешена только для **интерфейсов и делегатов**. Классы и структуры всегда инвариантны, потому что у класса есть поля, а поле — это одновременно и вход, и выход. Отсюда же невозможность сделать `List<out T>`.

### Ограничения вариантности

Вариантность **не работает для value-типов**:

```csharp
IEnumerable<int> ints = new List<int> { 1, 2, 3 };
// IEnumerable<object> objs = ints;   // ошибка!
```

Причина в механике: ковариантное присваивание — это ссылочное преобразование (`castclass` в IL), которое ничего не делает с самим значением. Для `int` → `object` нужен [[Boxing и unboxing]], то есть новое размещение в куче и другое представление в памяти. Ссылочного преобразования нет — вариантности нет.

Вариантность не транзитивна через несколько уровней автоматически, но композиция работает:

```csharp
IEnumerable<IEnumerable<string>> nested = new List<List<string>>();  // ошибка: List<T> инвариантен
IEnumerable<IEnumerable<string>> ok = new List<IEnumerable<string>>(); // ок
IEnumerable<IEnumerable<object>> alsoOk = ok;  // ок: два уровня out
```

### Практический пример: контравариантный компаратор

```csharp
public sealed class ByIdComparer : IEqualityComparer<IHasId>
{
    public bool Equals(IHasId? x, IHasId? y) => x?.Id == y?.Id;
    public int GetHashCode(IHasId obj) => obj.Id.GetHashCode();
}

public interface IHasId { Guid Id { get; } }
public sealed record User(Guid Id, string Name) : IHasId;

// Компаратор для IHasId используется как компаратор для User — благодаря in T
var set = new HashSet<User>(new ByIdComparer());
```

Без контравариантности пришлось бы писать компаратор под каждый тип.

## Массивы: ковариантность как ошибка дизайна

```csharp
object[] objects = new string[3];   // компилируется!
objects[0] = 42;                    // ArrayTypeMismatchException в рантайме
```

Массивы в .NET **ковариантны**: `Derived[]` присваивается в `Base[]`. Это унаследовано из Java 1.0 и заложено в CLR.

### Зачем так сделали

В 1995 году в Java не было дженериков. Чтобы написать `Arrays.sort(Object[] a)` и применить её к `String[]`, требовалась ковариантность массивов — иначе универсальные утилиты были невозможны. .NET 1.0 повторил решение ради совместимости с Java-подобной моделью и потому, что дженерики появились только в 2.0.

### Чем платим

Раз массив может «на самом деле» быть массивом более узкого типа, CLR обязана проверять тип **при каждой записи** в массив ссылочных типов:

```
arr[i] = value;
   │
   ├─ проверка границ (bounds check)
   └─ проверка типа (covariance check) — только для ссылочных типов
```

JIT умеет убирать проверку, если может доказать точный тип массива (например, массив создан в этом же методе), но в общем случае — не может. Замер на записи в `string[]` через переменную типа `object[]` даёт заметно худший результат, чем запись в массив value-типов, где covariance check не нужен вовсе.

```csharp
// Здесь JIT знает точный тип и уберёт проверку
var arr = new string[1000];
for (int i = 0; i < arr.Length; i++) arr[i] = "x";

// Здесь тип массива неизвестен статически — проверка на каждой итерации
static void Fill(object[] arr, object value)
{
    for (int i = 0; i < arr.Length; i++) arr[i] = value;
}
```

### Как правильно сегодня

Дженерики решили задачу без дыры: `IEnumerable<out T>` даёт ковариантность там, где она безопасна (только чтение), а `IList<T>` инвариантен там, где нет. Если нужен «ковариантный массив» — возвращайте `IReadOnlyList<T>` или `ReadOnlySpan<T>`.

```csharp
// Плохо: вызывающий может записать что угодно, а тип массива уже сужен
public object[] GetItems() => _strings;

// Хорошо
public IReadOnlyList<object> GetItems() => _strings;
```

> [!quote] Из книги «CLR via C#»
> Ковариантность массивов — известная ошибка. Она существует только ради обратной совместимости, и любой новый API следует проектировать без опоры на неё.

## Как дженерики устроены в рантайме (кратко)

CLR специализирует код по-разному:

| Тип-аргумент | Что происходит |
|---|---|
| Value type (`int`, `Guid`, свой `struct`) | Отдельный машинный код на каждый тип. Нет боксинга, всё инлайнится |
| Reference type (`string`, любой класс) | Один общий машинный код на все ссылочные типы (shared generics), тип передаётся через скрытый аргумент |

Отсюда практические следствия: `List<int>` не боксит, а `List<string>` и `List<User>` делят один код. Подробнее — [[Дженерики в CLR: как устроены]].

> [!warning] Подводные камни
>
> **1. `default(T)` неоднозначен.** Для `T : class` это `null`, для `T : struct` — нулевая структура. В обобщённом коде без ограничений `default(T)` может быть чем угодно, и сравнение `x == default` не скомпилируется (оператор `==` для голого `T` недоступен). Используйте `EqualityComparer<T>.Default.Equals(x, default)`.
>
> **2. `where T : new()` вызывает `Activator.CreateInstance` — не всегда.** Для value-типов JIT генерирует прямое обнуление. Для ссылочных до .NET 5 действительно вызывался `Activator.CreateInstance<T>()`, что было медленно; современный рантайм кеширует делегат конструктора, но это всё равно дороже прямого `new`. В горячем пути передавайте `Func<T>`.
>
> **3. Ковариантность массивов маскирует баги до рантайма.** Классика: метод принимает `object[]`, кто-то передал `string[]`, метод пишет в него `int` — `ArrayTypeMismatchException` в проде. Анализатор CA2021 не ловит это; спасает только дисциплина «не принимай `T[]` на запись».
>
> **4. Вариантность не работает для value-типов, и это ловят не сразу.** Код `IEnumerable<object> x = listOfInts;` не компилируется, но `IEnumerable<object> x = listOfInts.Cast<object>();` компилируется и боксит каждый элемент. Незаметная аллокация на каждый элемент.
>
> **5. Constraint не участвует в разрешении перегрузок.** Два метода `M<T>(T x) where T : class` и `M<T>(T x) where T : struct` — это ошибка «член с такой сигнатурой уже объявлен». Ограничения проверяются *после* выбора перегрузки, а не во время.
>
> **6. `allows ref struct` заразен вверх по стеку.** Если ваш дженерик разрешает ref struct, всё, что вы вызываете внутри, тоже должно это разрешать. Добавление `allows ref struct` в публичный API — не breaking change для потребителей, но серьёзное ограничение для реализации.

> [!example] Как делают в бою
>
> **Generic math в валидаторах и агрегаторах.** Раньше писали `SumInt`, `SumDecimal`, `SumDouble` или гоняли всё через `decimal`. Сейчас — один метод с `where T : INumber<T>`. Особенно выигрывают библиотеки метрик и финансовых расчётов.
>
> **Контравариантные компараторы для полиморфных коллекций.** Один `IComparer<IOrderable>` обслуживает все типы заказов. Экономит десятки классов в доменных проектах.
>
> **Маркерные интерфейсы + constraint вместо рефлексии.** Вместо `if (type.IsAssignableTo(typeof(IEvent)))` в рантайме — `where TEvent : IEvent` на этапе компиляции. Быстрее, работает под AOT, ошибки видны в IDE. Так устроены MediatR-подобные библиотеки (см. [[MediatR и альтернативы]]).
>
> **`IReadOnlyList<T>` в публичных контрактах.** В большинстве команд действует правило: наружу отдаём `IReadOnlyList<T>`/`IReadOnlyCollection<T>`, а не `T[]` и не `List<T>`. Ковариантность как бонус, отсутствие мутации как основной эффект.

## Вопросы с собеседований

> [!question]- Что такое ковариантность и контравариантность? Приведите пример из BCL.
> Ковариантность (`out T`) — возможность использовать `IX<Derived>` там, где ожидается `IX<Base>`. Безопасна, когда `T` встречается только в выходных позициях: `IEnumerable<out T>`, `IReadOnlyList<out T>`, `Func<..., out TResult>`. Контравариантность (`in T`) — обратное: `IX<Base>` подходит там, где ждут `IX<Derived>`. Безопасна, когда `T` только на входе: `Action<in T>`, `IComparer<in T>`, `IEqualityComparer<in T>`. Инвариантность — когда `T` и на входе, и на выходе: `IList<T>`. В CLR вариантность возможна только у интерфейсов и делегатов, но не у классов и структур, потому что поле класса — одновременно вход и выход.

> [!question]- Почему `IEnumerable<int>` нельзя присвоить в `IEnumerable<object>`?
> Вариантность реализуется как ссылочное преобразование: ссылка остаётся той же, меняется только статический тип. Для `int` → `object` требуется боксинг — создание объекта в куче с заголовком и копией значения. Это не ссылочное преобразование, а совсем другая операция, поэтому вариантность для value-типов запрещена на уровне CLR. Обходной путь `Cast<object>()` работает, но боксит каждый элемент, и это надо осознавать.

> [!question]- Почему массивы в .NET ковариантны и почему это считается ошибкой?
> `string[]` присваивается в `object[]` — это унаследовано из Java, где до дженериков иначе было невозможно написать универсальные утилиты вроде сортировки. Ошибка в том, что типобезопасность нарушается: запись в такой массив может кинуть `ArrayTypeMismatchException` в рантайме, то есть ошибка типов обнаруживается не при компиляции. Дополнительно CLR обязана делать covariance check при каждой записи в массив ссылочных типов, что стоит производительности. Дженерики решили ту же задачу корректно: ковариантность разрешена только там, где `T` не может попасть внутрь.

> [!question]- Зачем нужно ограничение `where T : notnull` и почему его нарушение — предупреждение, а не ошибка?
> `notnull` требует, чтобы `T` был либо value-типом, либо non-nullable ссылочным типом. Классический пример — `Dictionary<TKey, TValue> where TKey : notnull`: ключ `null` бессмыслен. Нарушение даёт warning, а не error, потому что nullable reference types — это статический анализ поверх системы типов CLR, а не часть самой системы типов. Метаданные о nullability хранятся в атрибутах, старые сборки их не имеют, и превращать всё это в ошибки компиляции сломало бы совместимость.

> [!question]- Что такое `allows ref struct` и зачем оно появилось?
> Это анти-ограничение из C# 13: оно не сужает множество допустимых типов, а расширяет его, разрешая подставлять `ref struct` (`Span<T>`, `ReadOnlySpan<T>`, `ref struct`-обёртки). До него `Span<T>` вообще не мог быть аргументом дженерика, потому что `ref struct` обязан жить на стеке, а дженерик мог бы положить его в поле класса или заboxить. Взамен внутри такого дженерика действуют правила ref safety: нельзя боксить `T`, класть в поля классов, захватывать в лямбды и использовать в async-методах. Комбинировать с `class` нельзя.

> [!question]- Как реализовать метод `Sum<T>` для любого числового типа?
> Через generic math, появившийся в C# 11 / .NET 7: `static T Sum<T>(IEnumerable<T> src) where T : INumber<T>`. Внутри доступны `T.Zero`, `T.One`, операторы `+`, `-`, `*`, `/`, `T.CreateChecked`. Работает это благодаря `static abstract` членам в интерфейсах: `INumber<T>` объявляет операторы как статические абстрактные, а для value-типов CLR специализирует код и девиртуализирует вызовы, так что накладных расходов практически нет. До .NET 7 обходились либо перегрузками под каждый тип, либо `dynamic` (медленно), либо скомпилированными деревьями выражений.

> [!question]- Можно ли сделать `class MyList<out T>`?
> Нет. Вариантность в CLR разрешена только для интерфейсов и делегатов. Причина: у класса могут быть поля типа `T`, а поле — это одновременно и чтение, и запись, то есть и выходная, и входная позиция. Компилятор не смог бы гарантировать безопасность. Именно поэтому `List<T>` инвариантен, а `IEnumerable<out T>` — нет; чтобы получить ковариантность, работайте через интерфейс.

## Задачи

### Задача 1. Найти нарушение вариантности

Почему следующий интерфейс не компилируется, и как его починить, сохранив обе операции?

```csharp
public interface IRepository<out T>
{
    T GetById(int id);
    void Save(T entity);
}
```

> [!success]- Решение
> `Save(T entity)` ставит `T` во входную позицию — это запрещено при `out`. Ошибка CS1961.
>
> Правильно — разделить интерфейс по направлению данных:
>
> ```csharp
> public interface IReadRepository<out T>
> {
>     T GetById(int id);
>     IEnumerable<T> GetAll();
> }
>
> public interface IWriteRepository<in T>
> {
>     void Save(T entity);
>     void Delete(T entity);
> }
>
> public interface IRepository<T> : IReadRepository<T>, IWriteRepository<T>;
> ```
>
> Теперь `IReadRepository<Admin>` можно передать туда, где ждут `IReadRepository<User>`, а `IWriteRepository<User>` — туда, где ждут `IWriteRepository<Admin>`. Это ровно ISP из [[SOLID]], только выведенный из правил вариантности.

### Задача 2. Обобщённое усреднение

Напишите метод, который считает среднее для любой числовой последовательности так, чтобы для `int` результат тоже был `int` (целочисленное деление), а для `decimal` — `decimal`, без боксинга и без перегрузок.

> [!success]- Решение
> ```csharp
> using System.Numerics;
>
> public static T Average<T>(IEnumerable<T> source) where T : INumber<T>
> {
>     T sum = T.Zero;
>     int count = 0;
>     foreach (var item in source)
>     {
>         sum += item;
>         count++;
>     }
>     if (count == 0) throw new InvalidOperationException("Пустая последовательность");
>     return sum / T.CreateChecked(count);
> }
>
> Console.WriteLine(Average(new[] { 1, 2, 3, 4 }));            // Вывод: 2
> Console.WriteLine(Average(new[] { 1m, 2m, 3m, 4m }));        // Вывод: 2.5
> ```
>
> `T.CreateChecked(count)` конвертирует `int` в `T` с проверкой переполнения — это статический абстрактный метод из `INumberBase<T>`. Боксинга нет: для каждого value-типа JIT генерирует отдельный код, где `+` и `/` — обычные машинные инструкции.

### Задача 3. Поймать `ArrayTypeMismatchException`

Напишите минимальный пример, который компилируется без предупреждений, но падает в рантайме из-за ковариантности массивов. Затем перепишите его безопасно.

> [!success]- Решение
> ```csharp
> // Падает
> static void FillWithDefault(object[] items)
> {
>     for (int i = 0; i < items.Length; i++)
>         items[i] = new object();   // ArrayTypeMismatchException, если items — string[]
> }
>
> FillWithDefault(new string[3]);
> ```
>
> Безопасный вариант — не принимать массив на запись в ослабленном типе, а сделать метод обобщённым с фабрикой:
>
> ```csharp
> static void Fill<T>(T[] items, Func<T> factory)
> {
>     for (int i = 0; i < items.Length; i++)
>         items[i] = factory();
> }
>
> Fill(new string[3], () => string.Empty);   // тип проверен на компиляции
> ```
>
> `T[]` инвариантен относительно самого `T` в сигнатуре обобщённого метода: вывод типов даст `T = string`, и положить туда `object` компилятор не даст.

### Задача 4. Кеш с ограничением

Реализуйте типобезопасный кеш `TypedCache`, который хранит по одному значению на тип и умеет создавать значение по требованию, если тип имеет конструктор без параметров.

> [!success]- Решение
> ```csharp
> public sealed class TypedCache
> {
>     private readonly Dictionary<Type, object> _items = [];
>
>     public T GetOrCreate<T>() where T : class, new()
>     {
>         if (_items.TryGetValue(typeof(T), out var existing))
>             return (T)existing;
>
>         var created = new T();
>         _items[typeof(T)] = created;
>         return created;
>     }
>
>     public void Set<T>(T value) where T : class
>         => _items[typeof(T)] = value;
> }
> ```
>
> Ограничение `class` здесь важно: без него значение при записи в `Dictionary<Type, object>` боксилось бы, а при чтении разбоксивалось, и `GetOrCreate<int>()` каждый раз возвращал бы копию, а не «тот же» экземпляр. Для value-типов нужен другой дизайн — например, `Dictionary<Type, StrongBox<T>>` или отдельное статическое поле в generic-классе (`static class Holder<T> { public static T Value; }`), которое CLR создаёт отдельно на каждый `T`.

## Итог

- Ограничения нужны, потому что дженерик компилируется один раз, до знания конкретных типов; без `where` доступны только члены `object`.
- Полный набор: `struct`, `class`, `class?`, `notnull`, `unmanaged`, базовый класс, интерфейсы, `T : U`, `new()`, `default`, `Enum`/`Delegate`, и анти-ограничение `allows ref struct` (C# 13).
- `static abstract` в интерфейсах (C# 11) дал generic math: `where T : INumber<T>` позволяет писать арифметику обобщённо и без потери производительности.
- `out` — только выходные позиции, `in` — только входные; компилятор проверяет это статически. Вариантность возможна только у интерфейсов и делегатов.
- Вариантность не работает для value-типов: это ссылочное преобразование, а боксинг им не является.
- Ковариантность массивов — историческая ошибка: она нарушает типобезопасность (`ArrayTypeMismatchException`) и заставляет CLR проверять тип при каждой записи. Используйте `IReadOnlyList<T>`/`ReadOnlySpan<T>`.
