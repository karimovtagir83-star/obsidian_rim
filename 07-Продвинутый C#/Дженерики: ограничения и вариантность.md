# Дженерики: ограничения и вариантность

> [!abstract] Коротко
> Ограничения (`where T : ...`) сообщают компилятору, что тип-аргумент умеет делать, — без них внутри дженерика доступны только члены `object`. Вариантность (`in`/`out`) определяет, можно ли `IProducer<Кошка>` присвоить в `IProducer<Животное>`: **out — только на выход, in — только на вход**. Обе модели существуют потому, что в CLR дженерики — не фикция компилятора, а часть рантайма: `List<int>` и `List<string>` — разные типы, и это напрямую решает, боксится значение или нет.

## Зачем это знать

- Без правильного ограничения дженерик либо не компилируется, либо компилируется, но боксит каждый элемент — это разница на порядок в аллокациях для горячего кода.
- Вариантность — источник частых ошибок ревью: агент нередко пишет `IEnumerable<object> x = list.Cast<object>()`, где `Cast` молча боксит каждый элемент, вместо того чтобы понять, что `IEnumerable<int>` в `IEnumerable<object>` не приводится в принципе.
- Понимание специализации CLR объясняет, почему `T where T : IShape` в цикле над структурами быстрее `IShape`-параметра, и почему `static`-поле в обобщённом классе — рабочий приём кеширования «по типу» без словаря.

## Модель

### Ограничения: чего компилятору не хватает без них

Тело дженерика компилируется **один раз**, до знания будущих типов-аргументов. Компилятор обязан заранее убедиться, что операция допустима, а единственное, что он гарантированно знает про голый `T`, — что это `object`:

```csharp
public static T Max<T>(T a, T b)
{
    // CS0019: оператор '>' неприменим к операндам типа 'T' и 'T'
    return a > b ? a : b;
}

public static T Max<T>(T a, T b) where T : IComparable<T>
    => a.CompareTo(b) >= 0 ? a : b;
```

Основные ограничения: `struct` / `class` / `class?` / `notnull` — форма типа; `unmanaged` — можно скопировать побайтово и передать в нативный код; интерфейс или базовый класс — доступны его члены; `new()` — есть конструктор без параметров; `allows ref struct` (C# 13) — анти-ограничение, разрешает `Span<T>` там, где раньше было нельзя, но обязывает соблюдать ref safety (нельзя боксить `T`, класть в поле класса, захватывать в лямбду).

`static abstract` в интерфейсах (C# 11) добавил операторы через ограничение — generic math:

```csharp
static T Average<T>(ReadOnlySpan<T> values) where T : INumber<T>
{
    T sum = T.Zero;
    foreach (var v in values) sum += v;
    return sum / T.CreateChecked(values.Length);
}

Console.WriteLine(Average<int>([1, 2, 3, 4]));      // Вывод: 2
Console.WriteLine(Average<decimal>([1.5m, 2.5m]));  // Вывод: 2
```

### Вариантность: направление решает присваиваемость

Есть `Животное` и `Кошка : Животное`. Если из `IX<T>` можно только **доставать** `T` — присваивание безопасно (`out`, ковариантность). Если можно только **класть** — безопасно в обратную сторону (`in`, контравариантность). Если и то и другое — только инвариантность:

```csharp
public interface IProducer<out T> { T Get(); }              // T только на выходе
public interface IConsumer<in T> { void Accept(T item); }   // T только на входе

IProducer<object> producer = new Producer<string>();   // ок
IConsumer<string> consumer = new Consumer<object>();   // ок

IList<string> strings = new List<string>();
// IList<object> asObjects = strings;   // ошибка: IList<T> инвариантен — Add(object) сломал бы List<string>
```

Компилятор проверяет позиции статически: `out T` — только в возвращаемых значениях и геттерах, `in T` — только в параметрах. Вариантность в CLR разрешена **только для интерфейсов и делегатов**: у класса есть поля, а поле — это одновременно вход и выход, поэтому `List<out T>` невозможен в принципе.

Ключевое ограничение — **вариантность не работает для value-типов**:

```csharp
IEnumerable<int> ints = [1, 2, 3];
// IEnumerable<object> objs = ints;              // ошибка компиляции
IEnumerable<object> boxed = ints.Cast<object>();  // компилируется, но боксит КАЖДЫЙ элемент
```

Причина в механике: ковариантное присваивание — это ссылочное преобразование (`castclass` в IL), которое не трогает само значение. Переход `int → object` требует боксинга — нового размещения в куче, а это другая операция, не бесплатная.

Массивы — историческое исключение: `Derived[]` присваивается в `Base[]` (наследие Java 1.0, где дженериков ещё не было), и CLR платит за это проверкой типа при каждой записи в массив ссылочных типов, а ошибка (`ArrayTypeMismatchException`) всплывает в рантайме, а не на компиляции. Дженерики решили ту же задачу без дыры: `IReadOnlyList<T>`/`IEnumerable<out T>` дают безопасную ковариантность там, где `T` не может попасть внутрь.

### Как CLR реализует дженерики под капотом

В отличие от Java, где дженерики стираются при компиляции (`List<Integer>` и `List<String>` в байт-коде неразличимы), в .NET дженерики существуют **в рантайме**: в метаданных хранится открытое определение (`List<>`) с ограничениями, а закрытые конструкции (`List<int>`, `List<string>`) — полноценные типы со своими таблицами методов и статическими полями:

```csharp
typeof(List<int>) == typeof(List<string>);                          // False — разные типы
typeof(List<int>).GetGenericTypeDefinition() == typeof(List<>);     // True
```

JIT компилирует обобщённый метод по-разному в зависимости от типа-аргумента:

```
Method<int>, Method<Point>       → своя специализация машинного кода на каждый value type:
                                    размер и раскладка данных известны, боксинга нет
Method<string>, Method<Order>    → ОДНА общая копия (shared generics, "__Canon"):
                                    все ссылки одного размера, тип берётся из скрытого параметра
```

Отсюда прямые следствия для производительности:

```csharp
// Без упаковки: JIT сделал версию под конкретный T, вызов через ограничение разрешается статически
static double Sum<T>(ReadOnlySpan<T> shapes) where T : IShape
{
    double total = 0;
    foreach (var s in shapes) total += s.Area;   // constrained call, часто встраивается
    return total;
}

// С упаковкой каждого элемента структуры при приведении к интерфейсу
static double Sum(ReadOnlySpan<IShape> shapes) { /* ... */ }
```

Цена специализации — раздувание кода: каждый значимый тип-аргумент даёт свою копию машинного кода. Для двух-трёх типов выгодно; для метода, инстанцированного двадцатью структурами, стоит подумать о размере сборки и промахах кеша инструкций.

Побочный эффект той же механики — статическое поле обобщённого класса своё у **каждой** закрытой конструкции:

```csharp
internal static class TypeCache<T>
{
    public static readonly string Name = typeof(T).FullName ?? typeof(T).Name;   // своё на каждый T
}
```

Это быстрее `ConcurrentDictionary<Type, ...>`: доступ — чтение статического поля, без хеширования и блокировок, а инициализация потокобезопасна по гарантиям статического конструктора.

Через рефлексию можно создавать закрытые конструкции динамически (`typeof(Repository<>).MakeGenericType(typeof(Order))`) — так работают DI-контейнеры и сериализаторы, — но это на порядки дороже прямого вызова и требует кеширования результата. Под Native AOT для значимых типов, не встречающихся в коде статически, `MakeGenericType` может не найти специализацию вовсе: JIT-компилятора там нет.

## Решения

| Нужно | Ограничение / приём | Почему |
|---|---|---|
| Сравнивать значения | `where T : IComparable<T>` | член доступен только через ограничение |
| Ключ словаря не может быть `null` | `where T : notnull` | нарушение — warning, а не error: это анализ поверх системы типов, а не сама система типов |
| Работа с указателями, `stackalloc`, P/Invoke | `where T : unmanaged` | гарантирует отсутствие ссылочных полей на любой глубине |
| Создавать экземпляр по требованию, без параметров | `where T : new()` | в горячем коде — дороже прямого `new` (кешируемый делегат конструктора); альтернатива — `Func<T>`-фабрика |
| Принять `Span<T>` внутрь дженерика | `where T : allows ref struct` (C# 13) | внутри действуют правила ref safety: без боксинга, без полей класса, без замыканий |
| Числовая арифметика без перегрузок под каждый тип | `where T : INumber<T>` | generic math на `static abstract`, для value-типов без накладных расходов |
| API отдаёт коллекцию наружу, не даёт мутировать | `IReadOnlyList<out T>` вместо `T[]`/`List<T>` | безопасная ковариантность без ошибки массивов |
| Компаратор/обработчик один на семейство типов | интерфейс с `in T` (`IComparer<in T>`, `IEqualityComparer<in T>`) | контравариантность вместо копии класса под каждый подтип |
| Разделить чтение и запись в одном контракте | `IReadRepository<out T>` + `IWriteRepository<in T>` вместо `IRepository<out T>` | `Save(T)` во входной позиции ломает `out`; разделение — ISP, выведенный из правил вариантности |

## В ServiceShop

> [!example] В ServiceShop
> Собственные интерфейсы поверх MediatR — прямое применение вариантности:
> ```csharp
> public interface ICommandHandler<in TCommand>
>     : IRequestHandler<TCommand> where TCommand : ICommand;
>
> public interface ICommandHandler<in TCommand, TResult>
>     : IRequestHandler<TCommand, TResult> where TCommand : ICommand<TResult>;
> ```
> `in TCommand` — контравариантность параметра, `where TCommand : ICommand` — ограничение, а не альтернатива вариантности: оно решает другую задачу — не даёт по ошибке объявить `ICommandHandler` для запроса, а не присваиваемость типов. Autofac декорирует именно `ICommandHandler<,>` (транзакция, логирование, валидация), а не `IRequestHandler<,>` из MediatR — иначе декораторы навесились бы и на запросы. Подробности пути команды — [[ServiceShop: CQRS и путь запроса]].
>
> Второй пример — `IBusinessRule` в домене (`BuildingBlocks.Domain`): маркерный интерфейс без параметра типа, но каждый агрегат вызывает `CheckRuleAsync(IBusinessRule rule)` обобщённо через сигнатуру метода, а не через `if (rule is SpecificRule)`. Ограничение на уровне контракта (`IBusinessRule`), а не рефлексия — быстрее и проверяется компилятором, а не в рантайме.

## Где ошибаются

> [!warning] Где ошибаются
> - **`default(T)` неоднозначен без ограничения.** Для `T : class` это `null`, для `T : struct` — нулевая структура; `x == default` без ограничения не скомпилируется вовсе. Нужен `EqualityComparer<T>.Default.Equals(x, default)`.
> - **Вариантность не работает для value-типов, и это не всегда видно.** `IEnumerable<object> x = listOfInts;` не компилируется, а `listOfInts.Cast<object>()` компилируется и боксит каждый элемент — тихая аллокация на ревью не заметна без знания механики.
> - **Ограничение не участвует в разрешении перегрузок.** `M<T>(T x) where T : class` и `M<T>(T x) where T : struct` — это не две перегрузки, а ошибка компиляции: ограничения проверяются после выбора сигнатуры.
> - **Ковариантность массивов маскирует баг до рантайма.** Метод принимает `object[]`, вызывающий передал `string[]`, метод пишет в него не тот тип — `ArrayTypeMismatchException` в проде, а не ошибка компиляции.
> - **Агент часто:** превращает `where T : IFoo` в параметр `IFoo` «для простоты» в коде, где `T` — value type в горячем пути; это незаметно на ревью, но добавляет боксинг на каждый вызов.
> - **Агент часто:** использует `MakeGenericType`/рефлексию по дженерикам там, где достаточно ограничения интерфейсом на этапе компиляции — это медленнее, не ловится компилятором и ломается под Native AOT.

## Проверка на ревью

- Дженерик над значимыми типами в горячем пути принимает `T where T : IInterface`, а не параметр типа `IInterface` напрямую.
- Ключ `Dictionary<TKey, ...>` помечен `where TKey : notnull`, если это не обеспечено типом ключа заранее.
- Публичный API отдаёт `IReadOnlyList<T>`/`IReadOnlyCollection<T>`, а не `T[]` или `List<T>`, если вызывающий не должен мутировать коллекцию.
- Нет `Cast<object>()` или неявного приведения дженерика над value-типом там, где боксинг не осознан явно.
- Новый обработчик команды реализует `ICommandHandler<,>`, а не `IRequestHandler<,>` напрямую — иначе декораторы Autofac его не увидят.
- `where T : new()` не стоит в методе, вызываемом в цикле на горячем пути, — там ожидается `Func<T>`-фабрика.

## Проверь себя

> [!question]- Почему `IEnumerable<int>` нельзя присвоить в `IEnumerable<object>`, а `IEnumerable<string>` в `IEnumerable<object>` — можно?
> Ковариантное присваивание реализуется как ссылочное преобразование: адрес объекта не меняется, меняется только статический тип ссылки. Для `string → object` это ровно то, что происходит — оба ссылочные типы. Для `int → object` нужен боксинг: создание нового объекта в куче с копией значения, то есть совсем другая операция, не бесплатное приведение. Поэтому вариантность в CLR ограничена ссылочными типами.

> [!question]- Зачем ServiceShop заводит `ICommandHandler<,>` поверх `IRequestHandler<,>` из MediatR, если оба варианта — обобщённые интерфейсы с той же ролью?
> Три причины, и все — следствие того, что `ICommandHandler` несёт собственное ограничение и собственную идентичность типа. Во-первых, Autofac декорирует именно `ICommandHandler<,>`, поэтому транзакция и логирование не навешиваются на запросы. Во-вторых, `where TCommand : ICommand` не даст объявить обработчик команды для запроса — ошибка ловится на компиляции. В-третьих, ArchTests могут проверить конвенцию имени и интерфейса — через общий `IRequestHandler` команду от запроса не отличить.

> [!question]- Почему статическое поле обобщённого класса `Cache<T>.Value` — рабочий кеш «по типу», а не баг?
> `Cache<int>` и `Cache<string>` — разные закрытые типы в рантайме, у каждого своя таблица методов и своя копия статических полей. Присваивание в `Cache<int>.Value` не видно из `Cache<string>.Value`, и это не расшаренный счётчик, а независимое хранилище на тип. Доступ — чтение поля, без хеширования и блокировок, поэтому приём быстрее словаря `Type → значение` и им пользуются сериализаторы для кеша метаданных.

> [!question]- Почему `where T : new()` не стоит использовать в методе, который вызывается миллион раз в секунду?
> Для ссылочных типов ограничение `new()` компилируется в вызов конструктора через кешируемый делегат, а не в прямой `new T()` — это дороже прямого создания объекта, хотя современный рантайм и не вызывает `Activator.CreateInstance` напрямую при каждом обращении. Для значимых типов JIT генерирует прямое обнуление, и разницы почти нет. В смешанном или неизвестном заранее случае в горячем пути правильнее принять `Func<T> factory` параметром и убрать вопрос производительности конструктора из дженерика вовсе.

## Разбор

### Задача 1. Найти нарушение вариантности

Интерфейс не компилируется. Почему, и как починить, сохранив обе операции?

```csharp
public interface IRepository<out T>
{
    T GetById(int id);
    void Save(T entity);
}
```

> [!success]- Решение
> `Save(T entity)` ставит `T` во входную позицию — запрещено при `out` (CS1961). Разделение по направлению данных чинит и сохраняет обе операции:
> ```csharp
> public interface IReadRepository<out T> { T GetById(int id); }
> public interface IWriteRepository<in T> { void Save(T entity); }
> public interface IRepository<T> : IReadRepository<T>, IWriteRepository<T>;
> ```
> Теперь `IReadRepository<Admin>` подставляется туда, где ждут `IReadRepository<User>` — это ISP из [[SOLID]], выведенный из правил вариантности, а не придуманный отдельно.

### Задача 2. Объяснить разницу в аллокациях

Почему первый вариант аллоцирует на каждый элемент, а второй — нет?

```csharp
static bool Contains(IEnumerable<IComparable> items, IComparable value) { /* ... */ }
static bool Contains<T>(ReadOnlySpan<T> items, T value) where T : IComparable<T> { /* ... */ }
```

> [!success]- Решение
> В первом варианте каждый элемент значимого типа при попадании в `IEnumerable<IComparable>` боксится: объект в куче на каждый элемент, `CompareTo` — через интерфейсную диспетчеризацию. Во втором JIT создаёт специализацию под конкретный `T`: элементы лежат в спане по значению, вызов `CompareTo` — `constrained.callvirt`, для значимого типа разрешается статически и часто встраивается. Для ссылочных типов разница почти исчезает, потому что там используется одна общая (canonical) версия кода в обоих случаях — выбор тогда делают по читаемости.

## Итог

- Ограничения нужны, потому что тело дженерика компилируется один раз до знания конкретных типов; без `where` доступны только члены `object`.
- `out` — только выходные позиции, `in` — только входные; вариантность возможна лишь у интерфейсов и делегатов, потому что поле класса — одновременно вход и выход.
- Вариантность не работает для value-типов: переход требует боксинга, а не ссылочного преобразования.
- В CLR дженерики существуют в рантайме: для value-типов JIT генерирует отдельную специализацию кода (без боксинга), для ссылочных — одну общую (shared generics).
- Статическое поле обобщённого класса своё на каждый закрытый тип — рабочий приём кеширования без словаря и блокировок.
- Ковариантность массивов — историческая ошибка дизайна: проверка типа на каждой записи и падение в рантайме вместо ошибки компиляции.
