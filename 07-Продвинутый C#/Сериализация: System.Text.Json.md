# Сериализация: System.Text.Json

> [!abstract] Коротко
> `System.Text.Json` (STJ) — встроенный в BCL сериализатор JSON, основной в ASP.NET Core с .NET Core 3.0. Он проектировался как более быстрая и менее выделяющая память альтернатива `Newtonsoft.Json` (Json.NET), но не полностью с ним совместим по поведению по умолчанию — большинство сюрпризов при миграции и при работе с внешними API растут именно из этой разницы поведения.

## Зачем это знать

Каждый HTTP-запрос и ответ в ASP.NET Core проходит через сериализацию. Ошибка здесь не абстрактна: неверная сериализация `enum`, потерянное поле из-за регистра, `DateTime` в неожиданном формате — то, что видит внешний клиент API или другой сервис в контракте события.

## Модель

STJ по умолчанию строже и быстрее Json.NET, но с другими значениями по умолчанию:

| Поведение | System.Text.Json (по умолчанию) | Newtonsoft.Json (по умолчанию) |
|---|---|---|
| Регистр имён свойств | точное совпадение (`PropertyNamingPolicy` для camelCase) | без учёта регистра при десериализации |
| Приватные сеттеры/поля | не пишет и не читает без `[JsonInclude]` | приватные поля тоже не сериализует, но **при десериализации пишет через непубличный сеттер** публичного свойства |
| Циклические ссылки | исключение; для API нужен `ReferenceHandler.IgnoreCycles`, а не `Preserve` — последний вносит в контракт `$id`/`$ref`, которых внешний клиент не ждёт | исключение по умолчанию, тоже настраивается |
| `enum` | число, если не указан `JsonStringEnumConverter` | число, если не указан конвертер |
| Комментарии/висячие запятые в JSON | ошибка, пока не выставлены `ReadCommentHandling` и `AllowTrailingCommas` (`JsonCommentHandling` — это тип enum, а не опция) | **проглатывает и то, и другое** |
| Производительность и аллокации | значительно быстрее, меньше аллокаций (`Utf8JsonReader`/`Writer` работают с UTF-8 напрямую) | медленнее, больше промежуточных строк |

Из таблицы следует направление сюрпризов при миграции: STJ падает там, где Newtonsoft молчал. Конфиг с комментарием, полусамодельный JSON от партнёра с висячей запятой, DTO с приватным сеттером, который Newtonsoft заполнял, — всё это перестаёт работать, причём на границе с внешним миром, а не в юнит-тестах. Отдельно про регистр: «точное совпадение» верно для голого `JsonSerializer`, но MVC-конвейер ASP.NET Core ставит camelCase-политику **и** `PropertyNameCaseInsensitive = true`. Поэтому тест на `JsonSerializer.Deserialize` и живой контроллер ведут себя по-разному, и это регулярно стоит часа отладки.

Ключевая архитектурная идея STJ — работа с UTF-8 байтами напрямую, без промежуточного преобразования в UTF-16 строки, которое использует .NET internally для `string`. Отсюда и выигрыш в производительности: меньше копирований и меньше давления на GC.

```csharp
public sealed class OrderDto
{
    public Guid Id { get; init; }
    public decimal Total { get; init; }
    public OrderStatus Status { get; init; }
}

var options = new JsonSerializerOptions
{
    PropertyNamingPolicy = JsonNamingPolicy.CamelCase,
    Converters = { new JsonStringEnumConverter() }
};

var json = JsonSerializer.Serialize(order, options);
// {"id":"...","total":100.50,"status":"Paid"}  — enum как строка, не число
```

### Source generators для сериализации (.NET 7+, доступно в net8.0)

STJ поддерживает генерацию кода сериализации на этапе компиляции вместо рефлексии в рантайме — это не только быстрее, но и совместимо с trimming/Native AOT, где рефлексия ограничена.

```csharp
[JsonSerializable(typeof(OrderDto))]
internal partial class AppJsonContext : JsonSerializerContext { }

// Использование без рефлексии в рантайме:
var json = JsonSerializer.Serialize(order, AppJsonContext.Default.OrderDto);
```

## Решения

| Ситуация | Что делать |
|---|---|
| Новый ASP.NET Core проект | STJ по умолчанию, не добавлять Newtonsoft без причины |
| Нужна совместимость с внешним API, который ожидает поведение Newtonsoft (`NullValueHandling`, кастомные конвертеры Json.NET) | явный пакет `Microsoft.AspNetCore.Mvc.NewtonsoftJson` — осознанное решение, не по умолчанию |
| `enum` в контракте API/события | явный `JsonStringEnumConverter` — число вместо имени ломается при изменении порядка значений enum |
| Высоконагруженный путь сериализации, важна каждая аллокация | source generator контекст вместо рефлексии |
| Циклические ссылки в графе объектов (навигационные свойства EF Core) | `ReferenceHandler.IgnoreCycles` или явные DTO вместо сериализации сущностей напрямую |

## В ServiceShop

DTO для ответов API и контракты интеграционных событий (`IntegrationEvents`) — типичное место, где сериализация должна быть предсказуемой и стабильной: изменение регистра свойства или переход с числового enum на строковый в контракте события — это breaking change для модуля-потребителя, даже если сериализатор не выдал ошибки на своей стороне.

## Где ошибаются

> [!warning] Подводные камни
> - **Сериализация сущности EF Core напрямую вместо DTO.** Навигационные свойства создают циклы (`Order` → `Purchase` → `Order`), и сериализатор либо падает, либо (с `IgnoreCycles`) выдаёт частично усечённый граф, который клиент не ожидает.
> - **`enum` как число в публичном контракте.** Если позже кто-то вставит новое значение в середину `enum`, все числовые значения после него сдвинутся по смыслу — старые сохранённые/переданные данные начнут читаться неверно.
> - **Молчаливое игнорирование неизвестных свойств при десериализации.** По умолчанию STJ игнорирует лишние поля во входном JSON — это удобно для эволюции API, но может маскировать опечатку в имени поля на стороне клиента.
> - **Агент часто:** при миграции с Newtonsoft на STJ (или наоборот, по привычке из старых примеров) не переносит явные настройки регистра и enum-конвертации, полагаясь на "стандартное поведение", которое у двух библиотек разное — код компилируется, но реальный JSON на выходе отличается от ожидаемого.

## Проверка на ревью

- Новые DTO для API/событий — не сериализуемые сущности EF Core, а явные плоские классы или record.
- `enum` в публичном контракте сериализуется как строка (`JsonStringEnumConverter`), а не как число, если контракт может пережить добавление новых значений.
- Настройки сериализации (`PropertyNamingPolicy`, конвертеры) заданы явно и одинаково для всего приложения, а не разбросаны по отдельным вызовам `Serialize`.
- Для высоконагруженного пути рассмотрен source generator вместо рефлексии, особенно если планируется Native AOT.

## Проверь себя

> [!question]- Почему сериализация `enum` как числа опасна для контракта интеграционного события, а не только для REST API?
> Контракт события хранится и передаётся дольше, чем живёт единственный HTTP-запрос — событие может лежать в Outbox, обрабатываться с задержкой, читаться другим сервисом с собственной версией enum. Если порядок значений enum изменится (вставят новое значение не в конец), числовое представление события, записанное раньше, будет читаться уже с другим смыслом — тихая порча данных, а не ошибка на этапе десериализации.

> [!question]- Почему System.Text.Json обычно эффективнее Newtonsoft.Json по памяти?
> STJ работает с UTF-8 байтами напрямую через `Utf8JsonReader`/`Utf8JsonWriter`, минуя промежуточное представление в виде управляемых UTF-16 строк и объектного дерева `JObject`, которое использует Newtonsoft. Меньше копирований и меньше временных объектов — меньше давления на сборщик мусора, особенно на больших или частых полезных нагрузках.

## Разбор

### Разбор 1. Найди источник несовместимости

Сервис А сериализует `OrderStatus.Cancelled` (значение enum = 3) в событие. Через полгода в `OrderStatus` добавили новое значение `PartiallyRefunded` со значением 3, сдвинув `Cancelled` на 4. Сервис Б, читающий старые записи из очереди с задержкой, десериализует прежнее событие. Что произойдёт и как это предотвратить на уровне сериализации?

> [!success]- Разбор
> Старое событие, сериализованное с числом `3`, после изменения enum в коде будет прочитано как `PartiallyRefunded`, а не `Cancelled` — тихая порча данных без единой ошибки на любом этапе. Предотвращается на уровне сериализации явным `JsonStringEnumConverter`: событие хранит и передаёт имя `"Cancelled"`, а не число, и остаётся корректным независимо от того, что происходит с порядком значений enum в коде.

## Итог

- System.Text.Json — сериализатор по умолчанию в ASP.NET Core, быстрее Newtonsoft.Json за счёт прямой работы с UTF-8
- Поведение по умолчанию различается (регистр, приватные члены, enum) — миграция между библиотеками требует явной настройки, а не полагания на "то же самое"
- `enum` в долгоживущих контрактах (API, события) должен сериализоваться как строка, а не как число
- Source generator для сериализации даёт выигрыш в производительности и совместим с Native AOT/trimming, в отличие от рефлексии
