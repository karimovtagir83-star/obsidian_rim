# CLAUDE.md

Инструкции для агента, работающего в этом хранилище Obsidian.

## Что это за база

База знаний **«C# / .NET: инженер в агентной разработке»**. Не учебник и не справочник: цель — модели, решения и разборы, которые нужны, чтобы ставить задачу агенту, понимать систему и ловить баги на ревью. Справку (перечни API, синтаксис, флаги CLI) агент выдаёт быстрее — в базе её быть не должно.

Язык базы — **русский**. Все заметки, коммиты и ответы — по-русски.

Точка входа для человека: [[00-Старт/🏠 Главная.md]] · [[00-Старт/Как пользоваться базой.md]]

## Главный принцип: модель, а не справка

Узкое место разработчика сместилось с «написать код» на **поставить задачу, понять систему и проверить результат**. Отсюда единственный критерий полезности текста в базе.

**Модель** — то, что должно быть в голове без запроса: как устроено под капотом, почему так, что при этом ломается, какие есть альтернативы и чем они различаются, где границы применимости.
**Справка** — то, что агент выдаёт за три секунды и что проверяет компилятор: перечни API, перегрузки, операторы, флаги, синтаксис.

Пиши модель. Справку не пиши вообще.

### Фильтр темы — применять к каждой заметке и каждому абзацу

Материал остаётся, если проходит хотя бы один вопрос:

| Вопрос | Что проверяет |
|---|---|
| **Ревью** | Нужно ли это знать, чтобы заметить ошибку в чужом или сгенерированном коде? |
| **Решение** | Нужно ли это до написания кода — выбрать структуру, схему, транзакционную границу, способ обмена? |
| **Инцидент** | Нужно ли это, когда в проде уже сломалось и надо понять почему? |

Не проходит ни одного — выкинуть, даже если написано хорошо.

> [!important] Проверочный вопрос
> «Если я этого не знаю, я приму неверное решение или пропущу баг на ревью?» Нет — темы в базе нет.

### Как это выглядит на практике

- Не «какие бывают перегрузки `Enumerable.GroupBy`», а «почему `GroupBy` в LINQ to Entities транслируется иначе, чем в LINQ to Objects, и когда это уронит запрос».
- Не «как объявить `record`», а «когда value-семантика равенства меняет поведение кеша и словаря».
- Не «список кодов HTTP», а «что выбрать при конфликте версий и почему 409, а не 400».
- Код — фрагмент 5–25 строк, показывающий **механику или ловушку**, с контрастом «сломано / починено». Не листинг, не boilerplate, не полный CRUD — это работа агента.
- Упражнения — «найди баг», «отревьюй PR», «обоснуй выбор из двух решений», «дан PR агента — что вернёшь на доработку». Задач «напиши цикл, который...» быть не должно.
- Ловушки, типичные для сгенерированного кода, помечаются явно: `**Агент часто:** ...`.
- Устаревшее не удаляется молча, а помечается `#устарело` с объяснением, почему ушли: это встретится в легаси и в ответах агента, обученного на старых статьях.

Тон — инженер пишет коллеге того же уровня. Без воды, без «в этой статье мы рассмотрим», без учебниковой интонации. Таблицы вместо абзацев для сравнений, ASCII-схемы для процессов.

## Формат заметки (кратко; детали — в СПЕЦИФИКАЦИИ)

```markdown
---
tags: [раздел-XX, тема, модель|решение|инцидент, ревью, агент-ловушка]
aliases: [Альтернативное название, English name]
---

# Название заметки

> [!abstract] Коротко
> 2–3 предложения.
```

Порядок секций фиксирован: `Коротко` → `Зачем это знать` → `Модель` → `Решения` (таблица) → `> [!example] В ServiceShop` → `> [!warning] Где ошибаются` → `## Проверка на ревью` → `## Проверь себя` → `## Разбор` → `## Итог` → `## Связанное`.

Обязательны блоки **«В ServiceShop»** (путь к реальному файлу проекта) и **«Проверка на ревью»** (проверяемый чек-лист по диффу).

Объём: обычная заметка 120–220 строк, несущая — до 300, обзор раздела — до 120. Превышение = внутрь заехала справка.

## Целевой стек — критично для примеров кода

Код в заметках должен быть валиден для **`net8.0` / C# 12** и применим в рабочем проекте сегодня.

`.NET 8 LTS` · ASP.NET Core MVC-контроллеры (не Minimal API) · **Autofac** · MediatR 12 · EF Core 8 + Pomelo (MySQL 8) · Dapper + Ardalis.Specification для чтения · **FluentMigrator** (не EF Migrations) · FluentValidation · Kafka через KafkaFlow 4 + Outbox/Inbox · Quartz · MySQL 8 / MongoDB / Redis · **Serilog** (`Microsoft.Extensions.Logging` запрещён) · OpenTelemetry, Sentry, Prometheus · xUnit, NSubstitute/Moq, FluentAssertions 7, NetArchTest · Docker, K8s, Werf, Helm.

Актуальные версии индустрии (.NET 10 LTS, C# 14, EF Core 10) подаются **только** врезкой:

```markdown
> [!info] Куда идёт индустрия
> В .NET 10 / EF Core 10 это делают так: ... В `net8.0` недоступно.
```

Лицензии: MediatR платный с v13, FluentAssertions с v8, MassTransit v9 коммерческая — апгрейд не советовать.

Факты про .NET и библиотеки, в которых не уверен, — проверять в вебе (learn.microsoft.com). **Лучше не написать, чем написать неверно.**

## Правила работы в хранилище

- Пути **относительные от корня** хранилища: `02-Язык C#/Pattern matching.md`. Ведущий слэш и абсолютный путь не работают.
- Имена файлов содержат пробелы, `#`, `:`, кириллицу и эмодзи — в bash всегда закавычивать целиком.
- В `СПЕЦИФИКАЦИИ` указан устаревший путь базы (`/Users/rimkarimov/work/obsidian_rim`); фактический — iCloud-каталог, из которого запущена сессия. На путь из спецификации не опираться.
- Вики-ссылки: `[[Точное имя файла без .md]]`, регистр и пробелы важны. Только имена из МАНИФЕСТа.
- Перед удалением файла (слияние) — поиск по его имени во всей базе, иначе останутся битые ссылки.
- Эмодзи внутри текста заметок не использовать (исключение — уже существующие имена файлов: `🏠 Главная`, `🗺️ Роадмап (полный)`).
- `.obsidian/` не трогать без явной просьбы. Плагины: `obsidian-git`, `realclaudian`.
- Git: ветка `master`, коммиты автобэкапом от obsidian-git. Коммитить и пушить только по просьбе.

## Чего не делать

- Справочники API, перечни перегрузок и операторов, шпаргалки по CLI.
- Пошаговые инструкции «сделай 1, 2, 3» (кроме операционных регламентов: миграции, релиз).
- Внешние URL как источник знания — база самодостаточна.
- Заглушки, TODO, недописанные примеры.
- Дублирование соседних заметок — вместо этого ссылка.
- Выдуманные API, сигнатуры и версии.
- Новые задачники вида «напиши код»: вместо них разборы «найди баг», «отревьюй PR», «расследуй инцидент».
