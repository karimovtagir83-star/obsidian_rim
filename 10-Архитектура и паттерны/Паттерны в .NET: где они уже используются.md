# Паттерны в .NET: где они уже используются

> [!abstract] Коротко
> Паттерны бесполезно заучивать по каталогу: в вакууме они выглядят как двадцать три способа завести лишний интерфейс. Зато в исходниках .NET они лежат в готовом, проверенном миллионами приложений виде — и там видно не только «как», но и «зачем именно так».
> Эта заметка разбирает конкретные места фреймворка: конвейер middleware, `IEnumerable<T>`, `HttpClient`, `DbContext`, `ILogger`, `IOptions<T>`, `Stream`, `BackgroundService`, `IResult`, `JsonConverter<T>`. Цель — научиться узнавать паттерн в незнакомом коде и отвечать на главный вопрос проектирования: какая ось изменчивости здесь вынесена в абстракцию.

## Зачем это нужно

Три практических выгоды от этого навыка.

**Первая: вы перестаёте изобретать заново.** Когда нужно добавить сквозное поведение к цепочке HTTP-вызовов, человек, узнающий Decorator, сразу пишет `DelegatingHandler`. Человек, не узнающий, пишет статический хелпер `HttpHelper.SendWithRetry` и вызывает его из сорока мест.

**Вторая: вы быстрее читаете чужой код.** Увидев `Func<RequestDelegate, RequestDelegate>`, вы понимаете структуру целиком, не вчитываясь: это цепочка, порядок регистрации значим, у каждого звена есть «до» и «после».

**Третья, самая важная для собеседования и для работы: вы видите цену.** Фреймворк платит за свои абстракции — косвенностью, аллокациями, сложностью отладки. Он платит осознанно, потому что должен поддерживать неизвестные заранее расширения. Ваше приложение обычно не должно, потому что вы знаете свои требования. Понимание, почему `ILogger` устроен как фасад над композитом провайдеров, помогает не строить такой же фасад над одним-единственным Serilog.

> [!tip] Один вопрос, который надо задавать каждому куску кода фреймворка
> «Какая ось изменчивости здесь вынесена в абстракцию?» У middleware ось — набор и порядок этапов обработки. У `Stream` — способ преобразования байтов. У `JsonConverter<T>` — правило сериализации конкретного типа. Если на вопрос нет ответа, абстракции быть не должно.

## Конвейер middleware: Chain of Responsibility + Decorator

Самый показательный пример в ASP.NET Core. Механика проще, чем кажется, и вся построена на одном делегате:

```csharp
// Вся суть конвейера — этот делегат.
public delegate Task RequestDelegate(HttpContext context);
```

`IApplicationBuilder.Use` принимает не middleware, а функцию, которая из «следующего» делегата делает «текущий». Упрощённая, но структурно точная реализация:

```csharp
public class ApplicationBuilder
{
    // Список фабрик middleware в порядке регистрации.
    private readonly List<Func<RequestDelegate, RequestDelegate>> _components = new();

    public ApplicationBuilder Use(Func<RequestDelegate, RequestDelegate> middleware)
    {
        _components.Add(middleware);
        return this; // fluent-стиль, чтобы вызовы цеплялись друг за друга
    }

    public RequestDelegate Build()
    {
        // Конец конвейера: если никто не обработал — 404.
        RequestDelegate next = context =>
        {
            context.Response.StatusCode = StatusCodes.Status404NotFound;
            return Task.CompletedTask;
        };

        // КЛЮЧЕВОЕ МЕСТО: идём с конца к началу и оборачиваем.
        for (int i = _components.Count - 1; i >= 0; i--)
        {
            next = _components[i](next);
        }

        return next; // возвращается САМОЕ ВНЕШНЕЕ звено
    }
}
```

Отсюда сразу следуют два факта, которые обычно заучивают наизусть, хотя их можно вывести.

**Почему порядок регистрации = порядок выполнения.** Сборка идёт с конца, поэтому первый зарегистрированный компонент оказывается самой внешней обёрткой и получает запрос первым. Именно поэтому `UseAuthentication()` обязан стоять до `UseAuthorization()`: авторизации нужен уже заполненный `HttpContext.User`, а заполняет его аутентификация, и сделать это она может только если стоит снаружи.

**Почему `next()` даёт «до» и «после».** Каждое звено — это замыкание над следующим, то есть классический декоратор. Код до `await next()` выполняется на пути запроса внутрь, код после — на пути ответа наружу:

```csharp
app.Use(async (context, next) =>
{
    var sw = Stopwatch.StartNew();          // ДО: путь внутрь
    try
    {
        await next(context);                 // передаём управление вглубь цепочки
    }
    finally
    {
        sw.Stop();                           // ПОСЛЕ: путь наружу, ответ уже сформирован
        logger.LogInformation("{Path} заняло {Ms} мс", context.Request.Path, sw.ElapsedMilliseconds);
    }
});
```

Схема вложенности для трёх компонентов:

```
Запрос ->  Logging (до)
             |
             v
           Auth (до)
             |
             v
           Endpoint  ---> формирует ответ
             |
             ^
           Auth (после)
             ^
           Logging (после)  -> Ответ
```

Где здесь какой паттерн:

- **Chain of Responsibility** — звено может обработать запрос само и НЕ вызывать `next`, оборвав цепочку. Так работает `UseAuthorization` при 403: дальше запрос не идёт.
- **Decorator** — звено вызывает `next` и добавляет поведение вокруг. Так работает логирование, трассировка, `UseExceptionHandler`.

Один и тот же механизм даёт оба паттерна. Разница только в том, вызывается `next` или нет.

> [!danger] Практическое следствие
> Если middleware начало писать в тело ответа, менять статус-код и заголовки уже нельзя — они улетели клиенту. Поэтому `UseResponseCompression` и `UseExceptionHandler` регистрируют максимально снаружи: им нужно быть в цепочке раньше того, кто начнёт запись. Механику см. в [[Middleware и конвейер обработки запроса]].

## `IEnumerable<T>` и `yield return`: Iterator

Iterator из GoF в чистом виде: отделить обход коллекции от её внутреннего устройства. Коллекция отвечает за «дай мне обходчик», обходчик — за состояние обхода.

```csharp
public interface IEnumerable<out T> { IEnumerator<T> GetEnumerator(); }

public interface IEnumerator<out T> : IDisposable
{
    T Current { get; }
    bool MoveNext();   // сдвинуть позицию; false = элементы кончились
    void Reset();      // на практике почти не используется
}
```

Выигрыш: `foreach`, LINQ и любой обобщённый алгоритм работают одинаково над массивом, списком, деревом, строками из файла и результатом SQL-запроса. Внутреннее устройство скрыто полностью.

Компилятор C# генерирует итератор за вас. Метод с `yield return` превращается в класс — конечный автомат:

```csharp
// Что пишете вы
public static IEnumerable<int> ЧётныеДо(int max)
{
    for (int i = 0; i <= max; i++)
        if (i % 2 == 0)
            yield return i;   // здесь метод "замирает" и отдаёт значение
}
```

Компилятор превращает это примерно в такое (имена в реальности вида `<ЧётныеДо>d__0`):

```csharp
private sealed class Итератор : IEnumerable<int>, IEnumerator<int>
{
    private int _state;      // на какой строке метода мы "остановились"
    private int _current;
    private int _i;          // локальная переменная стала ПОЛЕМ — она должна жить между вызовами
    private int _max;

    public int Current => _current;

    public bool MoveNext()
    {
        switch (_state)
        {
            case 0:                  // первый вызов
                _i = 0;
                goto проверка;
            case 1:                  // вернулись после yield return
                _i++;
                goto проверка;
        }
        return false;

        проверка:
        while (_i <= _max)
        {
            if (_i % 2 == 0)
            {
                _current = _i;
                _state = 1;          // запомнили точку возврата
                return true;
            }
            _i++;
        }
        return false;
    }
}
```

Чему это учит: локальные переменные метода становятся полями объекта, потому что должны переживать возврат управления. Тот же приём — основа `async/await` (см. [[async и await: как это работает на самом деле]]) и корутин в других языках. Подробнее про сам итератор — [[IEnumerable, IEnumerator и yield return]].

> [!warning] Цена абстракции
> `foreach` по `IEnumerable<T>` через интерфейс делает два виртуальных вызова на элемент (`MoveNext` + `Current`) и аллоцирует объект итератора. `foreach` по `List<T>`, объявленному как `List<T>`, использует struct-энумератор и не аллоцирует вообще. Это ровно тот случай, когда абстракция стоит денег и в горячем цикле от неё отказываются осознанно ([[LINQ: производительность и аллокации]]).

## `HttpMessageHandler`, `DelegatingHandler`, `IHttpClientFactory`

Здесь сразу три паттерна.

**`DelegatingHandler` — Decorator в виде цепочки.** У него есть `InnerHandler`, и он оборачивает его вызов:

```csharp
public abstract class DelegatingHandler : HttpMessageHandler
{
    public HttpMessageHandler? InnerHandler { get; set; }

    protected internal override Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken ct)
        => InnerHandler!.SendAsync(request, ct);
}
```

Свой обработчик — это декоратор с логикой «до» и «после»:

```csharp
// Добавляет заголовок корреляции ко всем исходящим запросам.
public sealed class CorrelationHandler : DelegatingHandler
{
    private readonly ICorrelationContext _ctx;
    public CorrelationHandler(ICorrelationContext ctx) => _ctx = ctx;

    protected override async Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken ct)
    {
        // ДО: модифицируем запрос
        request.Headers.TryAddWithoutValidation("X-Correlation-Id", _ctx.Id);

        var response = await base.SendAsync(request, ct); // передаём вглубь

        // ПОСЛЕ: можно посмотреть на ответ
        if (!response.IsSuccessStatusCode)
            _ctx.MarkFailure(request.RequestUri!, (int)response.StatusCode);

        return response;
    }
}
```

Регистрация выстраивает цепочку — и снова порядок значим:

```csharp
builder.Services.AddHttpClient<BillingClient>(c => c.BaseAddress = new Uri("https://billing.internal"))
    .AddHttpMessageHandler<CorrelationHandler>()   // внешний
    .AddHttpMessageHandler<AuthHandler>()          // внутренний
    .AddStandardResilienceHandler();               // Polly: retry, circuit breaker, timeout
```

Обратите внимание: конвейер middleware для входящих запросов и конвейер handler'ов для исходящих — структурно одна и та же идея, применённая в двух направлениях. Полезно держать эту симметрию в голове.

**`IHttpClientFactory` — Factory плюс управление жизненным циклом.** Он решает не задачу «создать объект», а задачу «переиспользовать дорогой ресурс»: сам `HttpClient` дёшев, дорог лежащий под ним `SocketsHttpHandler` с пулом TCP-соединений. Фабрика кеширует цепочку handler'ов по имени клиента и по умолчанию раз в две минуты помечает её как устаревшую, чтобы подхватывались изменения DNS. Именно поэтому `new HttpClient()` в цикле приводит к исчерпанию сокетов, а `static readonly HttpClient` — к тому, что приложение не видит смену IP-адреса сервиса. Подробнее — [[HttpClient и IHttpClientFactory]].

**Polly-политики — тоже декораторы.** `AddStandardResilienceHandler` добавляет в цепочку handler, который оборачивает вызов в конвейер стратегий: rate limiter, total timeout, retry, circuit breaker, attempt timeout. Каждая стратегия — обёртка вокруг следующей, поэтому порядок стратегий определяет семантику (retry внутри circuit breaker считает попытки, снаружи — считает открытия). См. [[Устойчивость: retry, circuit breaker, Polly]].

## EF Core: сразу пять паттернов

`DbContext` — самый плотно упакованный паттернами класс в .NET.

**`DbContext` = Unit of Work.** Он отслеживает изменения нескольких объектов и фиксирует их одной транзакцией:

```csharp
var order = await db.Orders.FirstAsync(o => o.Id == id);
order.Status = OrderStatus.Paid;                  // изменение отслеживается
db.Payments.Add(new Payment(order.Id, order.Total)); // вставка отслеживается

await db.SaveChangesAsync();
// Один вызов -> одна транзакция -> UPDATE + INSERT, всё или ничего.
```

**`DbSet<T>` = Repository.** Коллекция объектов домена с операциями поиска и добавления, скрывающая SQL. Это именно поэтому обёртка `IRepository<T>` поверх `DbSet<T>` чаще всего лишняя — вы заворачиваете репозиторий в репозиторий, теряя по пути `Include`, проекции и `ExecuteUpdateAsync` ([[Repository и Unit of Work: нужны ли поверх EF Core]]).

**Lazy loading через прокси = Proxy.** При `UseLazyLoadingProxies()` EF Core с помощью Castle.DynamicProxy создаёт наследника вашей сущности, переопределяя виртуальные навигационные свойства:

```csharp
// Ваш класс
public class Order
{
    public int Id { get; set; }
    public virtual Customer Customer { get; set; } = null!; // virtual обязателен
}

// Что примерно генерируется в рантайме
public class OrderProxy : Order
{
    private readonly ILazyLoader _loader;
    private Customer? _customer;

    public override Customer Customer
    {
        // Обращение к свойству инициирует SELECT — вот он, Proxy:
        // тот же интерфейс, дополнительное поведение при доступе.
        get => _loader.Load(this, ref _customer)!;
        set => _customer = value;
    }
}
```

Цена прозрачности — проблема N+1: цикл по 100 заказам с обращением к `Customer` выпустит 101 запрос, и в коде это никак не видно.

**`ChangeTracker` = хранение состояния, близкое к Memento.** Для каждой отслеживаемой сущности хранится снимок значений на момент загрузки:

```csharp
var entry = db.Entry(order);
var было = entry.Property(o => o.Status).OriginalValue;  // снимок при загрузке
var стало = entry.Property(o => o.Status).CurrentValue;  // текущее значение
bool изменено = entry.Property(o => o.Status).IsModified;

// На этом же снимке держится оптимистичная конкурентность:
// WHERE RowVersion = <OriginalValue>
```

Отсюда две вещи: `UPDATE` содержит только изменённые колонки, а `AsNoTracking()` даёт заметный выигрыш именно потому, что снимок не создаётся ([[EF Core: change tracking и AsNoTracking]]).

**`IQueryable` = Interpreter/Visitor через деревья выражений.** Ключевое отличие от `IEnumerable`: лямбда не компилируется в делегат, а сохраняется как дерево:

```csharp
public interface IQueryable<T> : IEnumerable<T>
{
    Expression Expression { get; }   // ДЕРЕВО, а не делегат
    IQueryProvider Provider { get; } // тот, кто умеет это дерево истолковать
}
```

Провайдер EF Core обходит дерево наследниками `ExpressionVisitor` (это буквально Visitor из GoF) и переводит узлы в SQL:

```csharp
var q = db.Orders.Where(o => o.Total > 1000).Select(o => o.Id);
// Дерево: Select(Where(Orders, o => o.Total > 1000), o => o.Id)
// После обхода: SELECT o."Id" FROM "Orders" AS o WHERE o."Total" > 1000
```

Практический вывод, который часто спрашивают: если провайдер не умеет перевести узел, вы получите исключение о невозможности трансляции — либо, в старых версиях, тихое переключение на выполнение в памяти. Именно поэтому важно понимать, где кончается `IQueryable` и начинается `IEnumerable` ([[IEnumerable vs IQueryable]], [[Деревья выражений]]).

## `ILogger` и `ILoggerFactory`: Facade + Abstract Factory + Composite

Три паттерна в одной подсистеме, и каждый на своём месте.

```csharp
// Facade: один простой интерфейс поверх сложной подсистемы провайдеров,
// фильтров, scope и форматирования.
public interface ILogger
{
    void Log<TState>(LogLevel level, EventId id, TState state,
                     Exception? ex, Func<TState, Exception?, string> formatter);
    bool IsEnabled(LogLevel level);
    IDisposable? BeginScope<TState>(TState state) where TState : notnull;
}

// Abstract Factory: создаёт семейство логгеров, не раскрывая конкретные типы.
public interface ILoggerFactory : IDisposable
{
    ILogger CreateLogger(string categoryName);
    void AddProvider(ILoggerProvider provider);
}
```

**Composite** — внутри. `LoggerFactory.CreateLogger` спрашивает логгер у каждого зарегистрированного провайдера и складывает их в один объект, который выглядит как одиночный логгер:

```csharp
// Упрощённая структура того, что возвращает CreateLogger.
internal sealed class СоставнойЛоггер : ILogger
{
    // По одному настоящему логгеру на провайдера: Console, Debug, OpenTelemetry, Serilog...
    private readonly (ILogger Logger, LogLevel Min)[] _логгеры;

    public void Log<TState>(LogLevel level, EventId id, TState state,
                            Exception? ex, Func<TState, Exception?, string> fmt)
    {
        List<Exception>? ошибки = null;
        foreach (var (логгер, минимум) in _логгеры)
        {
            if (level < минимум) continue;          // фильтр на провайдера
            try { логгер.Log(level, id, state, ex, fmt); }
            catch (Exception e) { (ошибки ??= new()).Add(e); } // один сбойный провайдер не роняет остальные
        }
        if (ошибки is not null) throw new AggregateException(ошибки);
    }

    public bool IsEnabled(LogLevel level) => _логгеры.Any(x => level >= x.Min);
}
```

Composite здесь узнаётся по признаку: объект реализует тот же интерфейс, что и его элементы, и вызывающий не различает один это логгер или двенадцать. Тот же приём — в `CompositeFormat`, в композитных `IConfigurationProvider`, в `CompositeValidator` у FluentValidation.

Чему учит: `IsEnabled` существует, чтобы не платить за форматирование сообщения, которое никто не запишет. Именно поэтому структурные логи пишут шаблоном (`LogInformation("Заказ {Id}", id)`), а не интерполяцией — форматирование отложено до момента, когда точно известно, что запись нужна ([[Логирование и структурные логи]]).

## DI-контейнер: Service Locator внутри, Dependency Injection снаружи

Один и тот же класс `ServiceProvider` — и антипаттерн, и правильный подход. Разница в том, кто его вызывает.

```csharp
// DEPENDENCY INJECTION: зависимости приходят извне, класс о контейнере не знает.
public sealed class OrderService
{
    private readonly IPaymentGateway _gateway;
    private readonly ILogger<OrderService> _logger;

    public OrderService(IPaymentGateway gateway, ILogger<OrderService> logger)
        => (_gateway, _logger) = (gateway, logger);
    // Контракт класса виден в конструкторе целиком.
}

// SERVICE LOCATOR: класс сам достаёт зависимости из контейнера.
public sealed class OrderServiceПлохо
{
    private readonly IServiceProvider _sp;
    public OrderServiceПлохо(IServiceProvider sp) => _sp = sp;

    public async Task Обработать(Guid id)
    {
        // Зависимость спрятана в глубине метода.
        var gateway = _sp.GetRequiredService<IPaymentGateway>();
        await gateway.ChargeAsync(id);
    }
}
```

Почему второе — антипаттерн, конкретно и без морализаторства:

1. **Контракт становится ложью.** По конструктору невозможно узнать, что нужно классу. Единственный способ — прочитать все методы.
2. **Ошибка съезжает с запуска на рантайм.** Незарегистрированную зависимость в первом варианте контейнер обнаружит при построении графа (а `ValidateOnBuild` — прямо на старте приложения). Во втором — только когда выполнится конкретная ветка кода, возможно, в проде в три ночи.
3. **Тест становится дороже.** Вместо передачи двух заглушек в конструктор надо собрать мок `IServiceProvider` или полноценный контейнер.
4. **Прячутся ошибки жизненного цикла.** Резолв scoped-сервиса из корневого провайдера в singleton — классическая утечка на весь срок жизни приложения ([[Captive dependency и типичные ошибки DI]]).

Где `IServiceProvider` использовать законно: в composition root (в `Program.cs`), в фабриках и factory-делегатах регистрации, в местах, где тип зависимости определяется только в рантайме (например, диспетчеризация по типу сообщения), и в `IServiceScopeFactory` внутри фонового сервиса — там scope надо создавать вручную. Общее правило: обращение к контейнеру допустимо в инфраструктурном коде и недопустимо в бизнес-логике ([[Dependency Injection: контейнер ASP.NET Core]]).

`IServiceProviderIsService` — отдельный любопытный кусок этой же подсистемы. Это не GoF-паттерн, а интерфейс интроспекции контейнера: он позволяет спросить «зарегистрирован ли такой тип», не создавая экземпляр. Им пользуются Minimal API и MVC, чтобы решить, откуда брать параметр метода-обработчика: из DI или из тела запроса. Полезная иллюстрация того, что абстракция иногда нужна не для подмены реализации, а для того, чтобы задать вопрос о возможностях.

## `IOptions<T>` и `IOptionsMonitor<T>`: Observer + Proxy

`IOptions<T>` — это Proxy над конфигурацией: вместо значения вы получаете обёртку, которая построит и провалидирует объект при первом обращении к `Value` и закеширует его на всё время жизни приложения.

`IOptionsMonitor<T>` добавляет Observer:

```csharp
public interface IOptionsMonitor<out T>
{
    T CurrentValue;                                     // всегда актуальное значение
    IDisposable? OnChange(Action<T, string?> listener);  // подписка = Observer
}

public sealed class RateLimitService : IDisposable
{
    private readonly IDisposable? _подписка;
    private RateLimitOptions _настройки;

    public RateLimitService(IOptionsMonitor<RateLimitOptions> monitor)
    {
        _настройки = monitor.CurrentValue;
        // Вызовется при изменении appsettings.json (reloadOnChange) или другого источника.
        _подписка = monitor.OnChange(новые => _настройки = новые);
    }

    public void Dispose() => _подписка?.Dispose(); // отписка обязательна: иначе утечка
}
```

Три интерфейса — три разных решения о времени жизни, и это хороший пример того, как правильная абстракция делает выбор явным:

| Интерфейс | Время жизни значения | Когда использовать |
|---|---|---|
| `IOptions<T>` | singleton, читается один раз | настройки, не меняющиеся без рестарта |
| `IOptionsSnapshot<T>` | стабильно в пределах одного запроса (scoped) | нужна согласованность внутри запроса |
| `IOptionsMonitor<T>` | всегда актуально, есть уведомления | singleton-сервисы, hot reload |

Классическая ошибка — внедрить `IOptionsSnapshot<T>` (scoped) в singleton и получить captive dependency. Разбор — [[Options pattern и конфигурация сервисов]].

## `Stream` и его наследники: Decorator в учебном виде

Пример из книги GoF, который в .NET существует по-настоящему и используется каждый день:

```csharp
// Сжать и зашифровать файл: три декоратора поверх одного источника.
await using var файл = File.Create("отчёт.dat");            // источник байтов
using var aes = Aes.Create();
aes.Key = ключ;
aes.IV = вектор;

await using var шифр = new CryptoStream(файл, aes.CreateEncryptor(), CryptoStreamMode.Write);
await using var сжатие = new GZipStream(шифр, CompressionLevel.SmallestSize);
await using var буфер = new BufferedStream(сжатие, 64 * 1024);
await using var писатель = new StreamWriter(буфер, Encoding.UTF8);

await писатель.WriteLineAsync("Строка отчёта");
// Путь байтов: текст -> UTF-8 -> буфер -> gzip -> AES -> файл
```

Каждый декоратор — сам `Stream`, поэтому обёртки складываются в любом порядке и в любом количестве. Ось изменчивости — преобразование байтов; она вынесена в абстракцию `Stream`, и добавление нового преобразования (например, `BrotliStream`) не требует правок ни в источниках, ни в потребителях.

Порядок здесь тоже смысловой: сжимать надо до шифрования, потому что зашифрованные данные выглядят как случайный шум и не сжимаются. Это тот же принцип, что с порядком middleware — декораторы не коммутативны.

> [!warning] Цена: `Dispose` каскадом
> По умолчанию каждый поток при `Dispose` закрывает вложенный. Если внешний поток не освободить, `GZipStream` не допишет свой финальный блок, и файл окажется битым — при этом никакой ошибки не будет. Порядок `using` в примере (объявление снаружи внутрь, освобождение внутрь наружу) обязателен. Когда каскад не нужен, у многих потоков есть параметр `leaveOpen: true` ([[Файлы, потоки и System.IO]]).

## `BackgroundService`: Template Method

Template Method — алгоритм зафиксирован в базовом классе, наследник подставляет один шаг:

```csharp
public abstract class BackgroundService : IHostedService, IDisposable
{
    private Task? _выполнение;
    private CancellationTokenSource? _cts;

    // Шаг, который обязан определить наследник. Это и есть "дырка" в шаблоне.
    protected abstract Task ExecuteAsync(CancellationToken stoppingToken);

    // Алгоритм запуска зафиксирован здесь и одинаков для всех наследников.
    public virtual Task StartAsync(CancellationToken cancellationToken)
    {
        _cts = CancellationTokenSource.CreateLinkedTokenSource(cancellationToken);
        _выполнение = ExecuteAsync(_cts.Token);

        // Тонкость: если ExecuteAsync завершился синхронно (или упал до первого await),
        // возвращаем его Task, чтобы ошибка не потерялась.
        return _выполнение.IsCompleted ? _выполнение : Task.CompletedTask;
    }

    public virtual async Task StopAsync(CancellationToken cancellationToken)
    {
        if (_выполнение is null) return;
        try { _cts!.Cancel(); }
        finally
        {
            // Ждём завершения работы или таймаута остановки хоста.
            await Task.WhenAny(_выполнение, Task.Delay(Timeout.Infinite, cancellationToken));
        }
    }
}
```

Вы пишете только `ExecuteAsync`, а весь протокол взаимодействия с хостом — привязка токенов, порядок остановки, обработка синхронного завершения — уже реализован. Тот же паттерн: `ControllerBase` с хуками фильтров, `DbContext.OnModelCreating`, `Profile` в мапперах, `IValidator` с `RuleFor` в базовом `AbstractValidator<T>`. См. [[Background services и IHostedService]].

## `IResult` и `TypedResults` в Minimal API: Command + Strategy

```csharp
// Объект, инкапсулирующий действие "записать этот ответ в HttpContext".
public interface IResult
{
    Task ExecuteAsync(HttpContext httpContext);
}
```

Это **Command**: действие упаковано в объект, его можно создать, передать, сохранить в переменную, вернуть из метода — и выполнить позже, кто-то другой. Обработчик эндпоинта не пишет в поток напрямую, он возвращает описание того, что надо сделать:

```csharp
app.MapGet("/orders/{id:guid}", async (Guid id, IOrderQueries queries) =>
{
    var заказ = await queries.НайтиAsync(id);

    // Возвращаем КОМАНДУ, а не выполняем запись.
    return заказ is null
        ? Results.Problem(statusCode: 404, title: "Заказ не найден")
        : TypedResults.Ok(заказ);
});
```

**Strategy** проявляется в том, что реализации `IResult` взаимозаменяемы: `Ok<T>`, `NotFound`, `ProblemHttpResult`, `FileStreamHttpResult`, `ServerSentEventsResult<T>` (появился в .NET 10) — разные алгоритмы формирования ответа за одним интерфейсом. Инфраструктура вызывает `ExecuteAsync` и не знает, что именно произойдёт.

Выигрыш от такой упаковки очень практичный: результат обработчика можно проверить в тесте без HTTP-сервера. Именно поэтому `TypedResults` предпочтительнее `Results` — он возвращает конкретные типы вроде `Ok<Order>` вместо `IResult`, и в тесте можно проверить и статус, и содержимое, а генератор OpenAPI автоматически выводит схему ответа ([[Minimal API]]).

## `System.Text.Json`: `JsonConverter<T>` как Strategy

```csharp
// Стратегия сериализации одного типа. Взаимозаменяема, подключается через опции.
public sealed class МоняetaJsonConverter : JsonConverter<Money>
{
    public override Money Read(ref Utf8JsonReader reader, Type type, JsonSerializerOptions options)
    {
        // Формат "1234.56 USD"
        var s = reader.GetString() ?? throw new JsonException("Ожидалась строка");
        var части = s.Split(' ');
        return new Money(decimal.Parse(части[0], CultureInfo.InvariantCulture), части[1]);
    }

    public override void Write(Utf8JsonWriter writer, Money value, JsonSerializerOptions options)
        => writer.WriteStringValue($"{value.Amount.ToString(CultureInfo.InvariantCulture)} {value.Currency}");
}

var options = new JsonSerializerOptions
{
    Converters = { new МоняetaJsonConverter() } // подмена алгоритма без изменения сериализатора
};
```

`JsonSerializerOptions.Converters` — коллекция стратегий, а сам сериализатор реализует Chain of Responsibility при их выборе: он идёт по списку и берёт первый конвертер, у которого `CanConvert(type)` вернул `true`; если ни один не подошёл — используется встроенный.

Source-generated контексты добавляют к этому ещё одно измерение:

```csharp
// Компилятор сгенерирует метаданные и код сериализации на этапе сборки.
[JsonSerializable(typeof(OrderDto))]
[JsonSerializable(typeof(List<OrderDto>))]
internal partial class ApiJsonContext : JsonSerializerContext { }

// Использование: рефлексия в рантайме не нужна.
var json = JsonSerializer.Serialize(dto, ApiJsonContext.Default.OrderDto);
```

Паттерн тут — тот же Strategy, но выбор стратегии перенесён с рантайма на этап компиляции. Это ключ к Native AOT и заметно меньшим стартовым задержкам: рефлексия исключена, код обхода объекта известен заранее ([[Сериализация: System.Text.Json]], [[Source Generators]]).

> [!warning] Подводные камни
> **1. Узнать паттерн — не значит скопировать его.** Фреймворк платит за расширяемость, потому что не знает своих пользователей. Ваше приложение знает. Прочитав про Chain of Responsibility в middleware, легко захотеть свою «шину обработчиков» для трёх операций — где обычный вызов метода был бы понятнее и отлаживался бы в один шаг.
>
> **2. Названия обманывают.** `DbSet<T>` — это Repository, но не называется репозиторием. `IServiceProvider` называется провайдером, но по факту это Service Locator. `MediatR` — это не Mediator из GoF (медиатор GoF знает участников и координирует их взаимодействие), а диспетчер сообщений, ближе к Command Dispatcher. Ориентироваться надо на структуру и на решаемую задачу, а не на имя типа.
>
> **3. Один класс — несколько паттернов, и это норма.** `DbContext` — Unit of Work, фабрика `DbSet`, фасад над провайдером БД и хранилище снимков одновременно. Попытка загнать реальный код в одну карточку из каталога только мешает понимать.
>
> **4. Цена косвенности реальна.** Каждый уровень декораторов — это кадр в стеке, лишний виртуальный вызов и, как правило, аллокация. В стеке вызовов исключения из middleware легко видеть двадцать кадров инфраструктуры. При отладке цепочки полезно ставить точку останова не в звене, а в `Build`, чтобы увидеть фактический порядок сборки.
>
> **5. Порядок в цепочке — часть контракта, и компилятор его не проверит.** `UseAuthorization` до `UseAuthentication`, retry снаружи или внутри circuit breaker, gzip после шифрования — всё это ошибки, которые собираются и запускаются, а проявляются странным поведением в проде. Такие требования надо покрывать интеграционным тестом, а не комментарием.

> [!example] Как делают в бою
> Как этот навык реально применяют.
>
> **Сквозное поведение — через штатные точки расширения.** Нужен аудит всех изменений в БД — перехватчик EF Core, а не вызов `_audit.Log()` в тридцати сервисах. Нужны заголовки во всех исходящих вызовах — `DelegatingHandler`. Нужна валидация всех команд — endpoint filter или pipeline behavior. Каждый раз это на порядок меньше кода, чем ручное протаскивание.
>
> **Чтение исходников как рабочая практика.** При непонятном поведении фреймворка полезнее посмотреть исходник, чем гуглить. `dotnet/aspnetcore` и `dotnet/runtime` открыты, а в IDE достаточно включить Source Link и отключить «только мой код», чтобы шагать отладчиком прямо внутрь. Пятнадцать минут в исходнике `ApplicationBuilder` заменяют час чтения статей про порядок middleware.
>
> **Диагностика через понимание структуры.** «Почему мой middleware не срабатывает» почти всегда означает, что выше в цепочке кто-то не вызвал `next` (терминальное звено, короткое замыкание авторизации, `UseStaticFiles`). Знание, что это цепочка декораторов, сокращает поиск с получаса до минуты.
>
> **Своя абстракция — только после третьего случая.** Полезное правило: если сквозное поведение нужно в одном месте — пишите прямо; в двух — копируйте; в трёх — выносите декоратор. К этому моменту уже видно, что действительно общее.

## Как тренировать распознавание

Навык вырабатывается упражнениями, а не чтением каталога.

**Упражнение 1: один вопрос к каждому интерфейсу.** Встретив интерфейс во фреймворке, спросите: какая ось изменчивости за ним стоит? У `IAuthorizationHandler` — правила доступа. У `IModelBinder` — способ извлечь параметр из запроса. У `IExceptionHandler` — реакция на сбой. Если ответить не получается, скорее всего абстракция здесь не про изменчивость, а про интроспекцию или про совместимость.

**Упражнение 2: читать исходники по конкретному вопросу.** Не «изучить `dotnet/aspnetcore`», а «понять, почему `UseRouting` обязателен перед `UseEndpoints`». Хорошие маршруты для старта:

- `src/Http/Http/src/Builder/ApplicationBuilder.cs` — 80 строк, вся механика конвейера
- `src/Logging/Logging/src/LoggerFactory.cs` и `Logger.cs` — композит провайдеров
- `src/Extensions/Options/src/OptionsMonitor.cs` — Observer на `IChangeToken`
- `System.Linq.Enumerable` в `dotnet/runtime` — итераторы, написанные вручную, а не через `yield`
- `Microsoft.EntityFrameworkCore.Query` — визиторы дерева выражений

**Упражнение 3: реализовать в миниатюре.** Напишите свой конвейер на `Func<Ctx, Task>`, свой `IEnumerator<T>` без `yield`, свой декоратор `Stream`, считающий байты. После этого паттерн опознаётся мгновенно, потому что вы знаете его на ощупь.

**Упражнение 4: обратный ход — от боли к месту в .NET.** Появилась задача «добавить заголовок ко всем исходящим запросам» — вспомните, где .NET решает похожую задачу. Такой рефлекс экономит часы и обычно даёт решение из десяти строк вместо своего механизма.

**Упражнение 5: смотреть на цену, а не только на структуру.** Найдя паттерн, посчитайте: сколько виртуальных вызовов добавилось, сколько аллокаций, сколько кадров в стеке. Тогда следующая абстракция в вашем коде появится осознанно.

## Вопросы с собеседований

> [!question]- Какие паттерны реализует конвейер middleware в ASP.NET Core и почему порядок регистрации имеет значение?
> Chain of Responsibility и Decorator одновременно. `IApplicationBuilder.Use` принимает `Func<RequestDelegate, RequestDelegate>` — функцию, которая по «следующему» делегату строит «текущий». В `Build()` список компонентов обходится **с конца к началу**, и каждый оборачивает уже собранный хвост. Поэтому первый зарегистрированный компонент оказывается самой внешней обёрткой и получает запрос первым. Chain of Responsibility проявляется в том, что звено может не вызвать `next` и оборвать обработку (например, авторизация с 403). Decorator — в том, что звено, вызвавшее `await next()`, получает код «до» (путь внутрь) и «после» (путь наружу, ответ уже почти сформирован). Отсюда практические правила: `UseAuthentication` до `UseAuthorization`, потому что второму нужен заполненный `HttpContext.User`; `UseExceptionHandler` максимально снаружи, потому что после начала записи в тело ответа менять статус-код уже нельзя.
>
> ```csharp
> for (int i = _components.Count - 1; i >= 0; i--)
>     next = _components[i](next);   // сборка идёт с конца
> ```

> [!question]- `DbContext` — это какой паттерн? А `DbSet<T>`?
> `DbContext` — Unit of Work: он накапливает изменения нескольких объектов в `ChangeTracker` и фиксирует их одним `SaveChanges` в одной транзакции. `DbSet<T>` — Repository: коллекция объектов домена с операциями поиска и добавления, скрывающая SQL. Помимо этого `DbContext` — фабрика `DbSet`, фасад над провайдером БД и хранилище снимков значений (`OriginalValues`, близко к Memento), а `IQueryable` в нём работает через Interpreter/Visitor по деревьям выражений. Практический вывод: писать `IRepository<T>`/`IUnitOfWork` поверх EF Core чаще всего значит заворачивать репозиторий в репозиторий и терять `Include`, проекции, `AsSplitQuery` и `ExecuteUpdateAsync`. Обёртка оправдана, только если у неё есть своя причина существовать: доменно-осмысленный интерфейс агрегата, работа с несколькими источниками данных или необходимость держать домен без ссылки на EF Core.

> [!question]- В чём разница между Dependency Injection и Service Locator, если оба используют один контейнер?
> Разница в направлении управления. При DI зависимости приходят в конструктор извне, класс о контейнере не знает, и его контракт полностью виден в сигнатуре конструктора. При Service Locator класс сам вызывает `IServiceProvider.GetRequiredService<T>()` внутри метода. Четыре конкретных последствия второго варианта: контракт класса становится ложью, и узнать зависимости можно только прочитав все методы; ошибка отсутствующей регистрации переезжает с момента построения графа (или со старта, при `ValidateOnBuild`) на момент выполнения конкретной ветки; тест требует мока контейнера вместо двух заглушек; легко получить captive dependency, резолвя scoped-сервис из корневого провайдера. Законные применения `IServiceProvider`: composition root, factory-делегаты регистрации, `IServiceScopeFactory` в фоновых сервисах и диспетчеризация по типу, известному только в рантайме. Правило: контейнер допустим в инфраструктурном коде, недопустим в бизнес-логике.

> [!question]- Почему `MediatR` — это не Mediator из GoF?
> Mediator из GoF — объект, который знает конкретных участников и координирует их взаимодействие, чтобы они не ссылались друг на друга напрямую (классический пример: диалоговое окно, координирующее свои элементы управления). MediatR ничего не координирует и участников не знает: он принимает сообщение, находит по типу единственный зарегистрированный обработчик и вызывает его, попутно прогоняя запрос через pipeline behaviors. Это скорее Command Dispatcher плюс цепочка декораторов. Различие не терминологическое: из него следует, что настоящая ценность MediatR — не «развязка» (контроллер всё равно зависит от типа команды), а единая точка для сквозного поведения — логирования, валидации, транзакций, метрик. Если behaviors не используются, библиотека приносит только потерю навигации в IDE. С версии 13.0.0 добавился ещё и лицензионный фактор: двойная лицензия RPL-1.5 плюс коммерческая, бесплатная Community-редакция только при выручке организации меньше 5 млн USD. Разбор альтернатив — [[MediatR и альтернативы]].

> [!question]- Как `yield return` работает под капотом и почему это важно?
> Компилятор превращает метод с `yield return` в приватный вложенный класс, реализующий сразу `IEnumerable<T>` и `IEnumerator<T>` (одним объектом ради экономии аллокации при первом обходе). Локальные переменные метода становятся полями этого класса, потому что должны переживать возврат управления между вызовами `MoveNext`; текущая точка выполнения хранится в поле `_state`, а тело метода превращается в `switch` с переходами. Практических следствий три. Первое: тело метода не выполняется до первого `MoveNext` — поэтому проверки аргументов в итераторе срабатывают не при вызове, а при начале обхода, и их выносят в обёртку. Второе: каждый обход `IEnumerable` запускает генератор заново, поэтому двойной проход по ленивой последовательности выполняет работу дважды. Третье: это тот же механизм, что у `async/await`, только там автомат управляется не `MoveNext` от потребителя, а продолжениями.

> [!question]- Приведите три примера паттерна Decorator в .NET и объясните, чем платят за него.
> Первый: `Stream` и его наследники — `GZipStream`, `CryptoStream`, `BufferedStream` оборачивают другой `Stream` и добавляют преобразование байтов. Второй: `DelegatingHandler` в цепочке `HttpClient` — добавляет заголовки, повторы, логирование вокруг `SendAsync` внутреннего handler'а. Третий: middleware в ASP.NET Core — каждое звено оборачивает `RequestDelegate` следующего. Четвёртый, из прикладного кода: регистрация декоратора кеширования поверх сервиса в DI. Цена: каждый уровень добавляет виртуальный вызов, обычно аллокацию и кадр в стеке — стек исключения из глубины конвейера содержит десятки кадров инфраструктуры. Плюс декораторы не коммутативны: сжатие после шифрования не сжимает, retry снаружи circuit breaker считает не то, что retry внутри. И каскадный `Dispose`: если не освободить внешний `GZipStream`, файл останется без финального блока и окажется битым — молча, без исключения.

> [!question]- Зачем в `ILogger` метод `IsEnabled`, если уровень всё равно проверяется внутри `Log`?
> Чтобы не платить за подготовку данных для записи, которая не состоится. `Log` действительно проверит уровень, но к моменту вызова аргументы уже вычислены: строки склеены, объекты созданы, `ToString()` вызван, в случае интерполяции произошла аллокация. `IsEnabled` позволяет пропустить этот код целиком. Именно поэтому структурные логи пишут шаблоном (`LogInformation("Заказ {Id} на {Sum}", id, sum)`), а не интерполированной строкой: форматирование отложено внутрь и выполняется только если хотя бы один провайдер принимает такой уровень. Для дорогих операций в логе явная проверка оправдана: `if (logger.IsEnabled(LogLevel.Debug)) logger.LogDebug("Дамп: {D}", ДорогойДамп());`. Само устройство `ILogger` — фасад над композитом провайдеров, каждый со своим минимальным уровнем, поэтому `IsEnabled` возвращает `true`, если принимает хотя бы один.

> [!question]- `IQueryable` и `IEnumerable` — в чём принципиальная разница с точки зрения паттернов?
> `IEnumerable<T>` — Iterator: последовательность, которую можно обойти, лямбды в LINQ-операторах компилируются в делегаты и выполняются в памяти. `IQueryable<T>` — Interpreter: лямбда сохраняется как дерево выражений (`Expression`), а `IQueryProvider` обходит это дерево наследниками `ExpressionVisitor` (Visitor из GoF) и переводит в другой язык — SQL. Отсюда практические следствия. Провайдер понимает только те узлы, которые умеет переводить: собственный метод в `Where` даст исключение о невозможности трансляции. Приведение `IQueryable` к `IEnumerable` (например, `AsEnumerable()` или вызов, который EF не может транслировать) переносит фильтрацию на клиента: база отдаёт всё, отбор идёт в памяти. Это же объясняет, почему `IRepository<T>`, возвращающий `IEnumerable<T>`, опасен: он навсегда закрывает возможность отфильтровать данные на стороне БД.

### Задача 1. Свой мини-конвейер

Реализуйте конвейер обработки сообщений по образцу ASP.NET Core: тип контекста, делегат, метод `Use`, метод `Build`. Проверьте, что порядок регистрации совпадает с порядком выполнения и что звено может оборвать цепочку.

> [!success]- Решение
> ```csharp
> public sealed class Ctx
> {
>     public string Сообщение { get; set; } = "";
>     public List<string> След { get; } = new();
> }
>
> public delegate Task Обработчик(Ctx ctx);
>
> public sealed class Конвейер
> {
>     private readonly List<Func<Обработчик, Обработчик>> _звенья = new();
>
>     public Конвейер Use(Func<Обработчик, Обработчик> звено)
>     {
>         _звенья.Add(звено);
>         return this;
>     }
>
>     public Обработчик Build()
>     {
>         // Терминальное звено: дальше идти некуда.
>         Обработчик next = _ => Task.CompletedTask;
>
>         // Обход с конца: последнее зарегистрированное окажется самым внутренним.
>         for (int i = _звенья.Count - 1; i >= 0; i--)
>             next = _звенья[i](next);
>
>         return next;
>     }
> }
>
> // Использование
> var конвейер = new Конвейер()
>     .Use(next => async ctx =>
>     {
>         ctx.След.Add("A:до");
>         await next(ctx);
>         ctx.След.Add("A:после");
>     })
>     .Use(next => async ctx =>
>     {
>         ctx.След.Add("B:до");
>         if (ctx.Сообщение == "стоп")
>         {
>             ctx.След.Add("B:обрыв");
>             return;                 // next НЕ вызван -> Chain of Responsibility
>         }
>         await next(ctx);
>         ctx.След.Add("B:после");
>     })
>     .Use(next => ctx =>
>     {
>         ctx.След.Add("C");
>         return next(ctx);
>     })
>     .Build();
>
> var ctx1 = new Ctx { Сообщение = "ок" };
> await конвейер(ctx1);
> Console.WriteLine(string.Join(" -> ", ctx1.След));
> // Вывод: A:до -> B:до -> C -> B:после -> A:после
>
> var ctx2 = new Ctx { Сообщение = "стоп" };
> await конвейер(ctx2);
> Console.WriteLine(string.Join(" -> ", ctx2.След));
> // Вывод: A:до -> B:до -> B:обрыв -> A:после
> ```
> Вся механика — в обходе списка с конца в `Build`. Симметричный вывод «до/после» получается автоматически, потому что каждое звено — замыкание над следующим, то есть декоратор. Второй запуск показывает Chain of Responsibility: звено `B` не вызвало `next`, поэтому `C` не выполнилось, но код «после» у внешнего `A` всё равно отработал — он находится снаружи от обрыва.

### Задача 2. Декоратор `Stream`, считающий байты

Напишите `CountingStream` — декоратор, который проксирует все операции во вложенный поток и подсчитывает прочитанные и записанные байты. Убедитесь, что он корректно работает в связке с `GZipStream`.

> [!success]- Решение
> ```csharp
> public sealed class CountingStream : Stream
> {
>     private readonly Stream _внутренний;
>     private readonly bool _оставитьОткрытым;
>
>     public long Прочитано { get; private set; }
>     public long Записано { get; private set; }
>
>     public CountingStream(Stream внутренний, bool оставитьОткрытым = false)
>         => (_внутренний, _оставитьОткрытым) = (внутренний, оставитьОткрытым);
>
>     // Свойства делегируются: декоратор не меняет природу потока.
>     public override bool CanRead => _внутренний.CanRead;
>     public override bool CanSeek => _внутренний.CanSeek;
>     public override bool CanWrite => _внутренний.CanWrite;
>     public override long Length => _внутренний.Length;
>     public override long Position
>     {
>         get => _внутренний.Position;
>         set => _внутренний.Position = value;
>     }
>
>     public override int Read(byte[] buffer, int offset, int count)
>     {
>         int n = _внутренний.Read(buffer, offset, count);
>         Прочитано += n;                   // добавленное поведение
>         return n;
>     }
>
>     public override void Write(byte[] buffer, int offset, int count)
>     {
>         _внутренний.Write(buffer, offset, count);
>         Записано += count;
>     }
>
>     public override void Flush() => _внутренний.Flush();
>     public override long Seek(long offset, SeekOrigin origin) => _внутренний.Seek(offset, origin);
>     public override void SetLength(long value) => _внутренний.SetLength(value);
>
>     protected override void Dispose(bool disposing)
>     {
>         // Каскадное освобождение — как у штатных декораторов Stream.
>         if (disposing && !_оставитьОткрытым) _внутренний.Dispose();
>         base.Dispose(disposing);
>     }
> }
>
> // Проверка: считаем, сколько байт реально ушло в файл после сжатия.
> await using var файл = File.Create("данные.gz");
> await using var счётчик = new CountingStream(файл, оставитьОткрытым: true);
> await using (var gzip = new GZipStream(счётчик, CompressionLevel.SmallestSize, leaveOpen: true))
> await using (var writer = new StreamWriter(gzip))
> {
>     for (int i = 0; i < 1000; i++)

> Ключевые моменты. `GZipStream` надо освободить до чтения счётчика, иначе финальный блок не дописан и число неполное — отсюда вложенные `await using` в блоке. Позиция счётчика в цепочке определяет, что он измеряет: между `GZipStream` и файлом — сжатый объём, а если поставить его между `StreamWriter` и `GZipStream`, получится объём до сжатия. Это наглядная демонстрация того, что декораторы не коммутативны.

### Задача 3. Итератор без `yield return`

Реализуйте `IEnumerable<T>` вручную, без `yield`: класс `Диапазон`, отдающий числа от `начало` до `конец` с шагом. Объясните, зачем `GetEnumerator` каждый раз возвращает новый объект.

> [!success]- Решение
> ```csharp
> public sealed class Диапазон : IEnumerable<int>
> {
>     private readonly int _начало, _конец, _шаг;
>
>     public Диапазон(int начало, int конец, int шаг = 1)
>     {
>         if (шаг <= 0) throw new ArgumentOutOfRangeException(nameof(шаг));
>         (_начало, _конец, _шаг) = (начало, конец, шаг);
>     }
>
>     // Каждый вызов — НОВЫЙ обходчик со своим состоянием.
>     public IEnumerator<int> GetEnumerator() => new Обходчик(_начало, _конец, _шаг);
>     IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();
>
>     private sealed class Обходчик : IEnumerator<int>
>     {
>         private readonly int _начало, _конец, _шаг;
>         private int _текущий;
>         private bool _начали;
>
>         public Обходчик(int начало, int конец, int шаг)
>         {
>             (_начало, _конец, _шаг) = (начало, конец, шаг);
>             _текущий = начало;
>         }
>
>         public int Current => _текущий;
>         object IEnumerator.Current => Current;
>
>         public bool MoveNext()
>         {
>             if (!_начали)
>             {
>                 _начали = true;
>                 return _начало <= _конец;   // первый элемент — само начало
>             }
>             _текущий += _шаг;
>             return _текущий <= _конец;
>         }
>
>         public void Reset() { _текущий = _начало; _начали = false; }
>         public void Dispose() { }
>     }
> }
>
> var д = new Диапазон(0, 10, 3);
> Console.WriteLine(string.Join(", ", д));   // Вывод: 0, 3, 6, 9
> Console.WriteLine(string.Join(", ", д));   // Вывод: 0, 3, 6, 9 — повторный обход работает
>
> // Два независимых обхода одновременно
> foreach (var a in д)
>     foreach (var b in д)
>         { /* вложенные циклы не мешают друг другу */ }
> ```
> Отдельный объект обходчика на каждый вызов `GetEnumerator` — это и есть суть Iterator: состояние обхода отделено от коллекции. Если бы состояние хранилось в самой коллекции, вложенные `foreach` по одному экземпляру ломались бы, а повторный обход возвращал бы пустую последовательность. Ровно это и генерирует компилятор для `yield return`, с одной оптимизацией: он использует один класс для `IEnumerable<T>` и `IEnumerator<T>` и при первом обходе возвращает сам себя, экономя аллокацию.

### Задача 4. Найти паттерн в чужом коде

Определите, какой паттерн (или паттерны) реализует этот фрагмент, и назовите вынесенную ось изменчивости.

```csharp
public interface IУведомление
{
    Task ОтправитьAsync(string получатель, string текст, CancellationToken ct);
    bool Поддерживает(КаналУведомления канал);
}

public sealed class Уведомитель
{
    private readonly IEnumerable<IУведомление> _каналы;
    public Уведомитель(IEnumerable<IУведомление> каналы) => _каналы = каналы;

    public async Task ОтправитьAsync(КаналУведомления канал, string кому, string текст, CancellationToken ct)
    {
        foreach (var к in _каналы)
        {
            if (!к.Поддерживает(канал)) continue;
            await к.ОтправитьAsync(кому, текст, ct);
            return;
        }
        throw new InvalidOperationException($"Нет обработчика для канала {канал}");
    }
}
```

> [!success]- Решение
> Здесь два паттерна.
>
> **Strategy** — `IУведомление` описывает взаимозаменяемые алгоритмы отправки (email, SMS, push), и `Уведомитель` работает с любым из них, не зная конкретного типа. Вынесенная ось изменчивости — способ доставки сообщения. Добавление нового канала не требует правок в `Уведомитель`, достаточно зарегистрировать реализацию в DI.
>
> **Chain of Responsibility** — в способе выбора: `Уведомитель` идёт по списку и передаёт работу первому, кто заявил `Поддерживает(канал) == true`. Ровно так `System.Text.Json` выбирает `JsonConverter` по `CanConvert`, а ASP.NET Core — `IModelBinderProvider`.
>
> Что стоит заметить как ревьюер: перебор со `Поддерживает` — линейный поиск, и при большом числе каналов это лишняя работа на каждый вызов. В .NET есть более прямое средство — keyed services:
>
> ```csharp
> builder.Services.AddKeyedScoped<IУведомление, EmailУведомление>(КаналУведомления.Email);
> builder.Services.AddKeyedScoped<IУведомление, SmsУведомление>(КаналУведомления.Sms);
>
> // Внутри Уведомителя:
> var канал = _sp.GetRequiredKeyedService<IУведомление>(канал); // O(1), без метода Поддерживает
> ```
>
> Это компромисс: выбор становится дешевле и явнее, но появляется обращение к контейнеру, то есть локальный Service Locator, — оправданный ровно потому, что ключ известен только в рантайме. См. [[Keyed services и продвинутая регистрация]].

## Итог

- Паттерны надо не заучивать, а узнавать: в .NET они лежат в проверенном виде, и там видно и мотивацию, и цену.
- Middleware, `DelegatingHandler` и `Stream` — одна и та же идея цепочки декораторов в трёх местах; во всех трёх порядок значим, а звено может оборвать цепочку и превратить Decorator в Chain of Responsibility.
- `DbContext` — Unit of Work, `DbSet<T>` — Repository, `IQueryable` — Interpreter с Visitor. Отсюда прямо следует, почему обёртка `IRepository<T>` поверх EF Core обычно вычитает возможности, а не добавляет.
- `IServiceProvider` — одна техника с двумя лицами: DI на границе приложения и Service Locator в бизнес-логике. Вред второго конкретен: ложный контракт, ошибки в рантайме, дорогие тесты, captive dependency.
- Названия обманывают: `DbSet` не называется репозиторием, `MediatR` не Mediator из GoF, а `IServiceProviderIsService` вообще не паттерн, а интроспекция.
- Главный вопрос к любой абстракции — какая ось изменчивости за ней стоит. Нет ответа — нет причины для абстракции.
- Фреймворк платит за расширяемость осознанно, потому что не знает своих пользователей. Ваш код знает — поэтому копировать уровень косвенности фреймворка не нужно.
