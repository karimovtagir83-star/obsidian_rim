# Паттерны GoF: что реально встречается

> [!abstract] Коротко
> Из 23 паттернов «Банды четырёх» в типичном .NET backend реально встречается штук семь, и почти всегда не в книжном виде, а растворённые в DI-контейнере, делегатах и BCL. Знать нужно не каталог, а то, как узнать паттерн в чужом коде и не завести его там, где хватило бы одного класса. Это главный навык ревью в этой теме: паттерн ради паттерна — самый частый мусор в сгенерированном коде.

## Зачем это знать

Раньше паттерны учили как справочник на 23 карточки — это ушло вместе с редакцией 1 базы. Осталось то, что реально нужно на ревью и в проектировании: узнать Decorator в цепочке `DelegatingHandler`, не дать агенту завести `ICustomerFactory` вокруг одного `new Customer()`, объяснить, зачем в MediatR-пайплайне три декоратора, а не `if` внутри хендлера. Паттерн — это имя для уже существующего решения, а не цель работы.

## Модель

### Singleton — через DI, не через `.Instance`

**Проблема:** нужен один экземпляр на процесс (кеш, клиент, конфигурация).

**Решение:** `AddSingleton<IFoo, Foo>()`. Экземпляр один — гарантирует контейнер, но зависимость получают через конструктор, а не статику.

```csharp
// Program.cs
builder.Services.AddSingleton<IConfigCache, ConfigCache>();

public sealed class OrderService(IConfigCache config, TimeProvider time);
```

Классический `static Instance` — антипаттерн не потому, что «один экземпляр» плохо, а потому что вместе с ним склеена глобальная точка доступа: зависимость невидима в сигнатуре, тест нельзя изолировать без глобального состояния, а самое опасное — синглтон может незаметно захватить scoped-зависимость (`DbContext`) и упасть `ObjectDisposedException`-ом после первого запроса. Где статика всё ещё нормальна: `Encoding.UTF8`, `ArrayPool<T>.Shared`, `static readonly JsonSerializerOptions` — иммутабельные значения без прикладного состояния, которые незачем подменять в тестах.

### Factory (Method) — когда тип решается в рантайме

**Проблема:** класс не знает конкретный тип продукта до момента вызова — тип зависит от кода из БД, конфигурации, входных данных.

**Решение:** интерфейс с одним методом `Create`, зарегистрированный в DI, либо просто `Func<T>`/keyed-сервис, если логики меньше, чем один `switch`.

```csharp
public sealed class PaymentGatewayFactory(IServiceProvider sp) : IPaymentGatewayFactory
{
    public IPaymentGateway Create(string providerCode) => providerCode switch
    {
        "stripe" => sp.GetRequiredKeyedService<IPaymentGateway>("stripe"),
        "click"  => sp.GetRequiredKeyedService<IPaymentGateway>("click"),
        _ => throw new NotSupportedException(providerCode)
    };
}
```

Живой пример в BCL — `IHttpClientFactory`: настоящая задача фабрики здесь не «создать `HttpClient`» (он дёшев), а управлять пулом `HttpMessageHandler`, который держит TCP-соединения и должен ротироваться по таймауту, чтобы не залипать на устаревшей DNS-записи. Фабрика без выбора реализации — не фабрика, а лишний слой: если тип продукта один, пишите `new`.

### Builder — пошаговая сборка с валидацией целого

**Проблема:** конструктор с десятком параметров нечитаем, часть опциональна, а инвариант проверяется только когда собраны все поля сразу («ретраи для POST требуют заголовок идемпотентности»).

**Решение:** объект с fluent-методами и `Build()`, где и только где происходит финальная проверка.

```csharp
public HttpRequestSpec Build()
{
    if (_url is null) throw new InvalidOperationException("Не задан URL");
    if (_retryCount > 0 && _method == HttpMethod.Post && !_headers.ContainsKey("Idempotency-Key"))
        throw new InvalidOperationException("Ретраи для POST без Idempotency-Key приведут к дублям.");
    return new HttpRequestSpec { Url = _url, Method = _method, RetryCount = _retryCount };
}
```

В BCL: `WebApplicationBuilder`, `DbContextOptionsBuilder`, `ModelBuilder`, `AuthorizationPolicyBuilder` — все показывают вторую функцию Builder, фазу «конфигурация закрыта»: до `Build()` объект мутабелен, после — заморожен. Если валидации целого нет, а нужна только читаемость — Builder избыточен: `record` с `required`-свойствами и `with` даёт то же самое и проверяется компилятором, а не рантаймом. Единственное место, где Builder всегда оправдан без вопросов, — тестовые данные: билдер с разумными дефолтами и точечным переопределением делает падающий тест читаемым.

### Decorator — сквозное поведение вокруг существующего интерфейса

**Проблема:** нужно добавить поведение «до/после» вызова (логирование, ретраи, валидация, кеш), не трогая сам вызываемый код и не размазывая его по десяткам мест вручную.

**Решение:** обёртка с тем же интерфейсом, которая вызывает исходный объект и добавляет код вокруг вызова.

```csharp
public sealed class CorrelationHandler : DelegatingHandler
{
    protected override async Task<HttpResponseMessage> SendAsync(HttpRequestMessage req, CancellationToken ct)
    {
        req.Headers.TryAddWithoutValidation("X-Correlation-Id", _ctx.Id); // до
        var resp = await base.SendAsync(req, ct);                        // вглубь
        if (!resp.IsSuccessStatusCode) _ctx.MarkFailure(req.RequestUri!); // после
        return resp;
    }
}
```

Три готовых места в .NET: `DelegatingHandler` вокруг `HttpClient`, `Stream`-обёртки (`GZipStream` вокруг `CryptoStream` вокруг файла), и конвейер middleware ASP.NET Core — там же, где `next()` не вызван, декоратор превращается в Chain of Responsibility (обрыв цепочки). Порядок обёрток не коммутативен: сжатие после шифрования не сжимает ничего, retry снаружи circuit breaker считает не то, что retry внутри.

### Strategy — взаимозаменяемые алгоритмы за одним интерфейсом

**Проблема:** есть несколько способов сделать одно и то же (посчитать скидку, отправить уведомление, сериализовать тип), и выбор между ними должен подставляться, а не разрастаться в `if/switch` по всему коду.

**Решение:** общий интерфейс, реализации регистрируются в DI, выбор — по ключу или по предикату.

```csharp
public interface IDiscountStrategy { decimal Apply(Order order); }
// регистрация: AddKeyedScoped<IDiscountStrategy, LoyaltyDiscount>("loyalty");
```

`JsonConverter<T>` в System.Text.Json — Strategy: подмена алгоритма сериализации одного типа без изменения самого сериализатора. `IResult`/`TypedResults` в Minimal API — тоже Strategy поверх общего `ExecuteAsync`. Признак, что Strategy не нужна: одна-единственная реализация интерфейса без плана на вторую — тогда это просто лишняя абстракция вокруг метода.

### Observer — события и подписки

**Проблема:** объект должен уведомить неизвестное заранее число подписчиков об изменении состояния, не зная их напрямую.

**Решение:** делегаты/события в языке — встроенная, компилятором проверяемая форма Observer.

```csharp
public sealed class OrderAggregate
{
    public event EventHandler<OrderPaidEventArgs>? Paid;
    private void RaisePaid(Order order) => Paid?.Invoke(this, new(order));
}
```

В BCL: `IOptionsMonitor<T>.OnChange` (подписка на изменение конфигурации), `IChangeToken`/`CancellationToken` (уведомление об отмене). В проекте — доменные события через MediatR `Publish`, разбор в [[Доменные события]]. Ловушка Observer одна и та же везде: забытая отписка держит подписчика живым дольше, чем нужно, — классическая утечка памяти.

### Adapter — привести чужой интерфейс к своему

**Проблема:** внешняя библиотека или legacy-код имеет интерфейс, несовместимый с тем, что ожидает остальная система, а переписывать библиотеку нельзя.

**Решение:** тонкая обёртка, транслирующая один интерфейс в другой.

```csharp
// Внешний SDK банка отдаёт свой DTO и свои коды ошибок.
public sealed class LegacyBankGatewayAdapter(LegacyBankSdk sdk) : IPaymentGateway
{
    public async Task<PaymentResult> ChargeAsync(Charge charge, CancellationToken ct)
    {
        var raw = await sdk.DoChargeXml(charge.Amount, charge.Currency, charge.CardToken);
        return raw.ResultCode == "00" ? PaymentResult.Success(raw.Ref) : PaymentResult.Failed(raw.ErrorText);
    }
}
```

Отличие от Decorator принципиально: Decorator сохраняет тот же интерфейс и добавляет поведение, Adapter меняет интерфейс на другой, не добавляя логики сверх трансляции. Путают их часто — при ревью проверяйте, реализует ли обёртка тот же контракт (Decorator) или другой (Adapter).

## Решения

| Паттерн | Когда применять | Чем грозит избыточное применение |
|---|---|---|
| Singleton (`AddSingleton`) | общий кеш, клиент, конфигурация без per-request состояния | захват scoped-зависимости → `ObjectDisposedException` под нагрузкой; скрытое общее состояние между тестами |
| Factory | тип продукта известен только в рантайме, из данных | интерфейс-фабрика с одним методом и единственной реализацией — лишний файл, который ничего не выбирает |
| Builder | валидация инварианта возможна только по всем полям сразу; тест-данные | fluent-обёртка вокруг объекта, где `record` + `required` дал бы то же самое дешевле |
| Decorator | сквозное поведение (лог, ретраи, кеш) вокруг существующего интерфейса | лишний уровень косвенности и аллокаций там, где хватило бы одного `if` в вызывающем коде |
| Strategy | 2+ реальных, взаимозаменяемых алгоритма | интерфейс на единственную реализацию «на будущее», которое не наступает |
| Observer / события | подписчиков несколько или их число не фиксировано | забытая отписка → утечка; событие как замена прямому вызову там, где порядок и результат важны |
| Adapter | нужно подружить внешний/legacy API с внутренним контрактом без переписывания источника | адаптер, который тащит в себе бизнес-логику вместо чистой трансляции интерфейсов |

> [!example] В ServiceShop
> Три декоратора вокруг MediatR-хендлеров — эталонный пример практичного Decorator: `LoggingCommandHandlerDecorator → ValidationCommandHandlerDecorator → UnitOfWorkCommandHandlerDecorator → сам хендлер`. Каждый навешивается Autofac-ом на **свой** интерфейс `ICommandHandler<,>`, а не на `IRequestHandler<,>` из MediatR — иначе транзакция открывалась бы и на запросах. Порядок `Logging → Validation → UnitOfWork` не случаен: валидация должна отсеять мусор до открытия транзакции, а коммит — стоять максимально близко к бизнес-логике. Подробный путь запроса — [[ServiceShop: CQRS и путь запроса]].
>
> `IPaymentGatewayFactory` в модуле платежей — Factory Method: провайдер (`stripe`/`click`/`payme`) известен только из данных платежа, поэтому фабрика резолвит конкретную реализацию через keyed-сервисы Autofac, а не через `switch` с `new`.
>
> `ICartRepository`/`IOrderRepository` в командах — Repository (не из GoF-каталога, но та же идея инкапсуляции доступа к данным), намеренно не используемый в запросах: запросы идут через Dapper мимо домена. Это форсируется архитектурным тестом, см. [[Repository и Unit of Work: нужны ли поверх EF Core]].

> [!warning] Где ошибаются
> - Заводят `IFooFactory` вокруг класса с одним конструктором и без вариативности — фабрика ничего не выбирает, это просто лишний файл и лишний прыжок при чтении кода.
> - Путают Decorator с Adapter: обёртка меняет интерфейс, но её называют декоратором, потому что «она что-то оборачивает».
> - Строят Strategy на одну реализацию «про запас» — вторая так и не появляется, а код читается на уровень косвенности дороже.
> - Синглтон-кеш получает `DbContext` в конструктор — captive dependency, разбор в [[Жизненные циклы сервисов: Singleton, Scoped, Transient]].
> - **Агент часто:** реагирует на слово «фабрика»/«стратегия» в задаче буквальным GoF-паттерном вместо простого метода — например, пишет `OrderValidatorStrategyFactory` там, где нужен один приватный метод с `if`.
> - **Агент часто:** оборачивает DTO в Builder ради fluent-синтаксиса, хотя валидации целого нет и объектный инициализатор с `required` читается не хуже.
> - **Агент часто:** добавляет `ICloneable`/ручной `Clone()` там, где достаточно `record` и `with` — и не замечает, что `with` копирует поверхностно, если внутри мутабельная коллекция.

## Проверка на ревью

- Если в PR появился новый `I...Factory` — проверьте, есть ли у него больше одной реализации или причина резолвить тип в рантайме. Если нет — предложите `new` или `Func<T>`.
- Если появился `Builder` — есть ли в `Build()` проверка, которую нельзя вынести в отдельный сеттер? Если нет — предложите `record` + `required`.
- Если добавлен декоратор (или `IPipelineBehavior`) — задан ли порядок относительно существующих декораторов явно, а не выводится из порядка регистрации по совпадению?
- Если новый `IFoo`-интерфейс имеет ровно одну реализацию и в задаче не сказано про тесты/подмену — это повод спросить, зачем интерфейс.
- Синглтон-регистрация (`AddSingleton`) — не захватывает ли конструктор scoped-зависимость (`DbContext`, `IHttpContextAccessor`)?
- Adapter — не содержит ли он бизнес-логики сверх трансляции полей и кодов ошибок.

## Проверь себя

> [!question]- Почему `AddSingleton<IFoo, Foo>()` не считается тем же антипаттерном, что классический `Foo.Instance`?
> Потому что вредна не «одна инстанция», а глобальная статическая точка доступа к ней. `AddSingleton` даёт тот же единственный экземпляр, но получают его через конструктор — зависимость видна в сигнатуре, подменяется в тестах моком, а жизненный цикл меняется одной строкой регистрации. Контейнер к тому же не даст (при включённой валидации скоупов) внедрить в такой синглтон scoped-зависимость.

> [!question]- Чем Factory Method отличается от Strategy, если оба выбирают реализацию по интерфейсу?
> Factory Method создаёт объект и возвращает его тому, кто попросил. Strategy — это уже сам выбранный объект, который вызывающий код использует для выполнения алгоритма. Часто это две половины одной схемы: фабрика резолвит нужную стратегию по ключу, а дальше вызывающий код работает со стратегией напрямую.

> [!question]- Когда Decorator оправдан, а когда это лишняя косвенность?
> Оправдан, когда сквозное поведение нужно в нескольких местах и должно применяться единообразно — тогда декоратор убирает дублирование и делает порядок применения (лог → валидация → транзакция) явным местом в коде, а не «где вспомнили». Лишний, если поведение нужно ровно в одном месте вызова — там декоратор добавляет виртуальный вызов, аллокацию и кадр в стеке ради того, что решается одним `if` внутри существующего метода.

> [!question]- В чём разница между Decorator и Adapter на практике ревью?
> Decorator сохраняет тот же интерфейс, что и обёрнутый объект, и добавляет поведение вокруг вызова — вызывающий код не замечает подмены. Adapter меняет интерфейс на другой: он нужен, чтобы подключить объект с несовместимым контрактом (внешний SDK, legacy-класс) туда, где ожидают свой интерфейс. Если обёртка транслирует один API в другой без побочного поведения — это Adapter; если оставляет контракт как есть и добавляет «до/после» — Decorator.

> [!question]- Почему интерфейс с единственной реализацией — не всегда лишний, но чаще всего лишний?
> Интерфейс оправдан, если нужна подмена в тестах, планируется вторая реализация в обозримом будущем, или это граница модуля (изоляция домена от инфраструктуры). Если ни одного из условий нет — это дополнительный файл, дополнительный прыжок при чтении и ложный сигнал «здесь есть вариативность», которой на самом деле нет. Агент особенно любит эту ошибку: видит слово «сервис» и заводит интерфейс по рефлексу, даже когда прикладной код нигде не подставляет вторую реализацию.

## Разбор

**Задача 1.** Ревьюер видит PR: агент добавил `ICustomerFactory` с единственным методом `Create(string name, string email) => new Customer(name, email)` и единственной реализацией `CustomerFactory`. Что вернуть на доработку?

> [!success]- Решение
> Вернуть с комментарием: фабрика не выбирает между вариантами и не управляет жизненным циклом ресурса — она оборачивает `new` в интерфейс без причины. Если конструктор `Customer` иногда меняется или нужен для теста — подмените напрямую конструктором `Customer`, а не фабрикой. Заводить интерфейс имеет смысл только если появится вторая реализация (например, `Customer` создаётся по-разному для юридических и физических лиц) или если конструктор делает что-то, что нужно мокать в тестах отдельно от самого объекта.

**Задача 2.** Дан фрагмент: агент реализовал уведомления через перебор списка `IEnumerable<INotifier>` с методом `bool CanHandle(channel)` у каждого, выбирая первый подошедший. Обоснуйте, стоит ли оставить как есть или заменить на keyed-сервисы, и в каких случаях каждый вариант лучше.

> [!success]- Решение
> Оба варианта — Strategy, различие в способе выбора. Линейный перебор с `CanHandle` — Chain of Responsibility поверх Strategy: удобен, если критерий выбора сложнее одного ключа (например, зависит от нескольких полей запроса) или если реализации могут перекрываться и порядок важен. Keyed-сервисы (`GetRequiredKeyedService<INotifier>(channel)`) дешевле (O(1) вместо перебора) и уместны, если выбор всегда идёт по одному явному ключу. Если каналов немного и ключ один — заменить на keyed-сервисы; если критерий составной — оставить `CanHandle`, но не плодить его без необходимости при малом числе вариантов.

## Итог

- Из каталога GoF в повседневном .NET-коде реально нужны единицы паттернов: Singleton через DI, Factory при рантайм-выборе типа, Builder при валидации целого, Decorator для сквозного поведения, Strategy при реальной вариативности алгоритма, Observer как события, Adapter на границе с чужим API.
- Большинство книжных паттернов либо съедены языком (`record`, делегаты, дженерики), либо живут внутри BCL и ASP.NET Core в готовом виде — их нужно узнавать, а не переписывать заново.
- Главный вопрос при виде нового интерфейса или фабрики: какая реальная вариативность за ним стоит? Нет ответа — паттерна не должно быть, только простой код.
- Сгенерированный код особенно склонен заводить паттерн ради структуры, а не ради задачи — фабрику на одну реализацию, билдер без валидации целого, интерфейс без второй реализации.
- В ServiceShop практичный пример — три декоратора вокруг MediatR-хендлеров с явным порядком (Logging → Validation → UnitOfWork), а не абстрактная демонстрация паттерна.
