# Стек и куча: что где лежит

> [!abstract] Коротко
> Стек — область на каждый поток (по умолчанию 1 МБ), работающая как LIFO: вход в метод кладёт кадр с параметрами и локальными переменными, выход снимает. Выделение стоит одну инструкцию, освобождение бесплатно. Куча — общая на процесс область, где живут все экземпляры ссылочных типов и всё, что переживает вызов метода; освобождением занимается GC. Ключевое уточнение к популярному упрощению: «структуры лежат на стеке» неверно — **значимый тип живёт там, где объявлен**: локальная переменная на стеке, поле класса — в куче внутри объекта, элемент массива — в куче внутри массива.

## Зачем это нужно

Это база для трёх практических тем: почему `struct` бывает быстрее `class` (и когда наоборот), откуда берётся мусор для GC, и почему одна и та же структура в одном месте кода бесплатна, а в другом вызывает аллокацию.

Плюс два вопроса, которые задают почти на каждом собеседовании: «чем стек отличается от кучи» и «сколько занимает объект в памяти».

## Стек

```
   Поток 1, стек 1 МБ                 Растёт вниз
 ┌────────────────────────┐
 │ кадр Main              │  локальные Main, адрес возврата
 ├────────────────────────┤
 │ кадр Process           │  параметры, локальные, сохранённые регистры
 ├────────────────────────┤
 │ кадр Calculate  ← SP   │  текущий кадр, регистр указателя стека
 └────────────────────────┘
```

Что лежит в кадре: аргументы (часть передаётся в регистрах), локальные переменные, адрес возврата, сохранённые регистры, иногда буфер `stackalloc`. Выделение — сдвиг регистра указателя стека на нужное число байт, то есть одна инструкция; освобождение — обратный сдвиг при выходе.

Свойства, из которых следует всё остальное:

- **Свой стек у каждого потока.** Поэтому локальные переменные потокобезопасны по построению: два потока не видят друг друга.
- **Размер фиксирован** (1 МБ по умолчанию для управляемых потоков; задаётся в конструкторе `Thread`). Исчерпание даёт `StackOverflowException`, который **нельзя поймать** — процесс завершается немедленно, потому что для выполнения `catch` нужен стек.
- **Память всегда «горячая»** в кеше процессора: верхушка стека только что использовалась.
- **Время жизни строго связано с вызовом.** Именно поэтому нельзя вернуть ссылку на локальную переменную (компилятор это запрещает) и нельзя сохранить `Span<T>` в поле объекта.

```csharp
static long Depth(int n) => n == 0 ? 0 : n + Depth(n - 1);
Depth(1_000_000);            // StackOverflowException, процесс убит; catch не поможет
```

## Куча

Управляемая куча делится на области, и это разделение важно для понимания GC:

```
 Small Object Heap (SOH)              Large Object Heap (LOH)     POH
 ┌──────────┬──────────┬──────────┐   ┌─────────────────────┐    ┌──────┐
 │  gen 0   │  gen 1   │  gen 2   │   │ объекты ≥ 85 000 Б  │    │ pinned│
 │ новые    │ выжившие │ долгожив.│   │ (обычно массивы)    │    │ объекты│
 └──────────┴──────────┴──────────┘   └─────────────────────┘    └──────┘
```

Выделение в куче .NET дешёвое: аллокатор просто сдвигает указатель в текущем сегменте gen 0 (bump-pointer allocation) — это несколько инструкций, сравнимо со стеком. Дорого не выделение, а **последующая сборка** и промахи кеша из-за разбросанности объектов. Отсюда правильная формулировка совета «меньше аллокаций»: он про работу GC и локальность, а не про сам `new`. Подробно — [[Сборка мусора (GC): как работает]] и [[Поколения GC, LOH и режимы сборщика]].

### Устройство объекта

```
На 64-битной платформе экземпляр класса:

 адрес-8   ┌──────────────────────┐
           │ Sync block index     │ 8 байт — блокировка, хеш, GC-биты
 ссылка →  ├──────────────────────┤
           │ Method table pointer │ 8 байт — указатель на таблицу типа
           ├──────────────────────┤
           │ поля объекта         │ с выравниванием
           └──────────────────────┘
```

Заголовок — 16 байт, из которых ссылка указывает на второе слово. Минимальный размер объекта — 24 байта (заголовок плюс выравнивание), даже у класса без полей.

```csharp
class Empty { }                       // 24 байта в куче
class OneInt { int X; }               // 24 байта: 16 заголовок + 4 поля + 4 выравнивание
class TwoLongs { long A, B; }         // 32 байта
struct Point { int X, Y; }            // 8 байт — как поле или локальная, без заголовка

// Массив: заголовок + длина + элементы
// int[100] ≈ 16 + 8 + 400 = 424 байта
```

Практический вывод: **мелкие объекты дороги относительно своего содержимого**. Список из миллиона объектов с одним `int` внутри — это 24 МБ вместо 4 МБ у массива структур, плюс миллион ссылок и разбросанность по памяти. Это главная причина, по которой в горячем коде предпочитают массивы структур ([[Value types vs Reference types]]).

Посмотреть фактическое устройство можно так:

```csharp
Console.WriteLine(System.Runtime.InteropServices.Marshal.SizeOf<Point>());   // размер структуры при маршалинге
// Точный размер объекта в куче — только через дамп: dotnet-dump + SOS (!objsize, !dumpheap -stat)
// Или через библиотеку ObjectLayoutInspector в тестовом проекте
```

## Где что лежит: таблица

| Что | Где | Примечание |
|---|---|---|
| Локальная переменная значимого типа | стек (или регистр) | если не захвачена и не в `async` |
| Локальная переменная ссылочного типа | ссылка на стеке, объект в куче | |
| Параметр метода | стек или регистр | часть аргументов передаётся в регистрах |
| Поле класса (любого типа) | куча, внутри объекта | структура-поле лежит в куче |
| Поле структуры | там, где сама структура | |
| Элемент массива | куча, внутри массива | массив структур — данные подряд |
| Статическое поле | куча (в области загрузчика типа) | живёт до конца процесса |
| Строковый литерал | куча, таблица интернирования | не собирается GC |
| Захваченная переменная замыкания | куча, в объекте класса замыкания | даже если это `int` |
| Локальные `async`-метода | куча, в объекте автомата | после первого `await` |
| Локальные итератора (`yield return`) | куча, в объекте автомата | |
| `stackalloc` буфер | стек | ограничен размером стека |
| Упакованное значение | куча | результат `box` |

Три последних случая — самые неочевидные. Смотри:

```csharp
void Example()
{
    int a = 5;                       // стек

    Func<int> f = () => a;           // a переехала в поле класса замыкания → куча

    Span<byte> buffer = stackalloc byte[128];   // стек

    object boxed = a;                // копия в куче
}

async Task Work()
{
    int local = 5;                   // до первого await — на стеке;
    await Task.Delay(1);             // после — поле объекта-автомата в куче
    Console.WriteLine(local);
}
```

Именно поэтому асинхронный метод с большим числом локальных переменных дороже синхронного: все они переезжают в объект состояния ([[async и await: как это работает на самом деле]]).

### Escape analysis: граница размывается

Начиная с .NET 9 JIT умеет размещать **некоторые объекты на стеке**, если доказал, что ссылка не покидает метод:

```csharp
static int Sum()
{
    var box = new int[3] { 1, 2, 3 };   // может не попасть в кучу вовсе,
    return box[0] + box[1] + box[2];    // если JIT доказал, что массив не «убегает»
}
```

Это делает старое правило «`new` всегда значит куча» приблизительным. Полагаться на оптимизацию нельзя (она применяется в ограниченных случаях), но знать о ней стоит: часть «очевидных» аллокаций в бенчмарках новых версий .NET исчезает сама.

## Практические следствия

**Передача больших структур дорога.** Копирование 64-байтной структуры при каждом вызове заметно; лечится `in`-параметром для `readonly struct` или переходом на класс ([[Методы и параметры]]).

**Массив структур против массива классов.** Первый — один объект и непрерывные данные, второй — N+1 объект и обход по ссылкам. Разница на обходе достигает 5–10 раз из-за кеша процессора ([[Как работает компьютер: процессор, память, ОС]]).

**Замыкание в цикле — аллокация на итерацию.** Класс замыкания создаётся каждый раз, когда захватываются новые значения.

**Глубокая рекурсия небезопасна.** Обход дерева большой или неизвестной глубины пишут с явным стеком (`Stack<T>`) в цикле, а не рекурсией.

**Статические поля живут вечно.** Кеш в статическом словаре без вытеснения — типичная утечка ([[Слабые ссылки и утечки памяти в .NET]]).

> [!warning] Подводные камни
> - **«Структуры на стеке».** Неточность: значимый тип живёт там, где объявлен. Поле класса, элемент массива, захваченная переменная — в куче.
> - **`StackOverflowException` нельзя поймать.** Процесс завершается немедленно; спасает только ограничение глубины.
> - **`stackalloc` в цикле.** Память не освобождается до выхода из метода: `stackalloc` внутри цикла на тысячу итераций переполнит стек. Выделять надо до цикла.
> - **Большой `stackalloc`.** Больше нескольких килобайт — риск переполнения; для больших буферов `ArrayPool<T>`.
> - **`Marshal.SizeOf` как размер объекта.** Он даёт размер для маршалинга в нативный код, а не фактический размер в управляемой куче.
> - **Много мелких объектов.** Заголовок 16 байт и выравнивание делают миллион объектов с одним полем в шесть раз дороже массива структур.
> - **Ожидание, что `Span<T>` можно сохранить.** Он может указывать на стек, поэтому запрещён в полях, `async`-методах и лямбдах — иначе ссылка переживёт кадр.

> [!example] Как делают в бою
> В прикладном коде о стеке и куче не думают: объекты создаются свободно, и GC справляется. Тема становится практической в трёх местах.
> Первое — горячие пути с большим числом однотипных данных: там переходят на массивы структур и `Span<T>`, чтобы данные лежали подряд и не создавали мусор. Так написаны сериализаторы, парсеры и сетевой стек самого .NET.
> Второе — диагностика памяти: при росте потребления снимают дамп (`dotnet-dump collect`), смотрят `!dumpheap -stat`, находят типы, которых неожиданно много, и по цепочке ссылок (`!gcroot`) выясняют, кто их держит. Почти всегда это статический кеш, подписка на событие или незакрытый `IDisposable`.
> Третье — асинхронные горячие пути: каждый `async`-метод создаёт объект состояния, поэтому в очень нагруженных участках используют `ValueTask` и избегают дробления на множество мелких `async`-методов ([[Асинхронность и производительность: ValueTask, пулинг]]).
> Что не делают: не переводят прикладные модели в структуры «ради стека» — выигрыш иллюзорен, а проблемы с копированием и упаковкой реальны.

## Вопросы с собеседований

> [!question]- Чем стек отличается от кучи?
> Стек существует на каждый поток, имеет фиксированный размер (по умолчанию 1 МБ) и работает как LIFO: кадр вызова кладётся при входе в метод и снимается при выходе. Выделение — сдвиг указателя, то есть одна инструкция; освобождение автоматическое и бесплатное; память всегда горячая в кеше. Куча общая на процесс, объекты живут произвольное время, освобождением занимается сборщик мусора; выделение тоже дешёвое (сдвиг указателя в gen 0), но дорога последующая сборка и разбросанность объектов по памяти. В стеке лежат кадры вызовов: параметры, локальные переменные значимых типов, ссылки на объекты, адреса возврата. В куче — экземпляры классов, массивы, строки, боксированные значения, объекты замыканий и автоматов `async`. Исчерпание стека фатально и неперехватываемо, исчерпание кучи даёт `OutOfMemoryException`.

> [!question]- Верно ли, что структуры всегда лежат на стеке?
> Нет, это распространённое упрощение. Значимый тип располагается там, где объявлена переменная или поле: локальная переменная — на стеке (или в регистре), поле класса — в куче внутри объекта, элемент массива структур — в куче внутри массива, поле структуры — там же, где сама структура. Дополнительно есть случаи, когда локальная переменная значимого типа неизбежно переезжает в кучу: если она захвачена лямбдой или локальной функцией (попадает в поле класса замыкания), если это локальная переменная `async`-метода или итератора, пережившая точку приостановки (попадает в объект автомата), и если значение упаковано приведением к `object` или к интерфейсу. Правильная формулировка: значимый тип не имеет собственного заголовка и живёт внутри того контейнера, которому принадлежит.

> [!question]- Сколько памяти занимает объект в .NET?
> На 64-битной платформе у каждого объекта есть заголовок в 16 байт: слово индекса синхронизации (используется для блокировки, хеш-кода и служебных битов GC) и указатель на таблицу методов типа. Далее идут поля с выравниванием по 8 байт. Минимальный размер объекта — 24 байта, даже если полей нет вовсе. У массива дополнительно хранится длина, поэтому `int[100]` занимает примерно 424 байта. Структура собственного заголовка не имеет: `struct` из двух `int` занимает 8 байт там, где объявлена. Практическое следствие: миллион объектов с единственным полем `int` займёт около 24 МБ плюс массив ссылок на них, тогда как миллион структур в массиве — 4 МБ непрерывной памяти, что вдобавок кратно быстрее обходится из-за кеша процессора. Точный размер конкретного объекта в рантайме измеряется по дампу через SOS (`!objsize`), а не `Marshal.SizeOf`, который считает размер для маршалинга.

> [!question]- Почему нельзя вернуть `Span<T>`, указывающий на `stackalloc`-буфер?
> Потому что `Span<T>` — это ссылка на память плюс длина, а память из `stackalloc` живёт в кадре текущего метода и исчезает при выходе. Возвращённый спан указывал бы на уже освобождённую часть стека, которую немедленно переиспользует следующий вызов, — это классическая ошибка «висячего указателя», приводящая к порче произвольных данных. Компилятор такое запрещает благодаря правилам безопасности ссылок (`ref safety`): `Span<T>` объявлен как `ref struct`, поэтому его нельзя ни сохранить в поле обычного класса, ни использовать в `async`-методе или лямбде, ни вернуть, если он может ссылаться на локальные данные. Управлять этим точнее позволяет модификатор `scoped` и правила `ref`-возврата; если результат должен жить дольше метода, память нужно взять не из стека, а из массива, `ArrayPool<T>` или `Memory<T>`.

## Задачи

### Задача 1. Определить, где что лежит

```csharp
class Container { public int Count; public Point Position; }
struct Point { public int X, Y; }

void Run()
{
    int local = 1;
    Point p = new() { X = 1, Y = 2 };
    var c = new Container { Count = 5 };
    var arr = new Point[10];
    Action a = () => Console.Write(local);
    object boxed = p;
}
```

Где физически находится каждое значение?

> [!success]- Решение
> `local` — переехала **в кучу**, в поле класса замыкания, потому что захвачена лямбдой `a`. Если бы лямбды не было — стек или регистр.
> `p` — стек (8 байт), пока её не упаковали.
> `c` — ссылка на стеке, объект `Container` в куче: 16 байт заголовка + 4 байта `Count` + 8 байт `Position` + выравнивание. Важно: структура `Position` лежит **в куче**, внутри объекта.
> `arr` — ссылка на стеке, массив в куче: заголовок, длина и 10 структур подряд (80 байт данных) — без отдельных объектов на элементы.
> `a` — ссылка на стеке; в куче два объекта: класс замыкания (с полем `local`) и сам делегат.
> `boxed` — ссылка на стеке; в куче новый объект с копией `p`: 16 байт заголовка + 8 байт данных.
> Итого аллокаций в куче: класс замыкания, делегат, `Container`, массив, боксированная копия — пять объектов, из которых два появились «незаметно».

### Задача 2. Найти проблему со стеком

Метод обрабатывает дерево каталогов и падает на реальных данных с необрабатываемым исключением, хотя логика верна.

```csharp
static long Size(DirectoryInfo dir)
{
    Span<char> buffer = stackalloc char[1024];
    long total = dir.GetFiles().Sum(f => f.Length);
    foreach (var sub in dir.GetDirectories())
        total += Size(sub);
    return total;
}
```

> [!success]- Решение
> Два дефекта, оба про стек. Первый: `stackalloc` в **рекурсивном** методе — каждый уровень рекурсии добавляет к кадру 2 КБ (1024 символа по 2 байта), и на глубине нескольких сотен каталогов стек исчерпывается. Второй: сама рекурсия по дереву неизвестной глубины — символические ссылки или очень глубокая структура дают `StackOverflowException`, который нельзя поймать, поэтому процесс просто умирает без внятной диагностики.
> ```csharp
> static long Size(DirectoryInfo root)
> {
>     long total = 0;
>     var pending = new Stack<DirectoryInfo>();      // явный стек в КУЧЕ, глубина не ограничена 1 МБ
>     pending.Push(root);
>
>     while (pending.TryPop(out var dir))
>     {
>         foreach (var file in dir.EnumerateFiles()) total += file.Length;
>         foreach (var sub in dir.EnumerateDirectories()) pending.Push(sub);
>     }
>     return total;
> }
> ```
> Что изменилось: обход стал итеративным с явным `Stack<T>`, поэтому глубина ограничена только памятью кучи; неиспользуемый `stackalloc` убран; `GetFiles`/`GetDirectories` заменены на ленивые `Enumerate*`, чтобы не материализовать массивы на каждом уровне. Общее правило: если `stackalloc` нужен, он выделяется **один раз до цикла и вне рекурсии**, а обход структур неизвестной глубины пишется циклом.

## Итог

- Стек — на поток, 1 МБ, LIFO, выделение в одну инструкцию, освобождение бесплатно, память горячая.
- Куча — общая, произвольное время жизни, дешёвое выделение и дорогая сборка; делится на gen 0/1/2, LOH и POH.
- Значимый тип живёт там, где объявлен: локальная — стек, поле класса и элемент массива — куча.
- В кучу неявно переезжают захваченные переменные, локальные `async`-методов и итераторов, упакованные значения.
- Заголовок объекта — 16 байт на x64, минимальный объект — 24 байта: мелкие объекты дороги относительно содержимого.
- Массив структур — один объект с непрерывными данными; массив классов — N+1 объект и обход по ссылкам.
- `StackOverflowException` неперехватываем: глубокие обходы пишутся циклом с явным стеком.
- С .NET 9 JIT может размещать не «убегающие» объекты на стеке — правило «`new` = куча» стало приблизительным.
