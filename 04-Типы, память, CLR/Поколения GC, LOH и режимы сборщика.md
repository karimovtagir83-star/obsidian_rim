# Поколения GC, LOH и режимы сборщика

> [!abstract] Коротко
> Управляемая куча состоит из четырёх частей: gen 0/1/2 для обычных объектов, LOH для объектов от 85 000 байт и POH для закреплённых. LOH важен тем, что объекты в нём **сразу считаются старым поколением** и по умолчанию **не уплотняются** — отсюда фрагментация и растущее потребление при частом выделении больших массивов. Режимов сборщика два: workstation (одна куча, компромисс в пользу отзывчивости) и server (по куче и потоку на ядро, максимальная пропускная способность) — для серверных приложений второй включён по умолчанию. В .NET 9 к серверному режиму добавилась динамическая адаптация числа куч под нагрузку (DATAS), которая заметно снизила потребление памяти в контейнерах.

## Зачем это нужно

Настройки GC трогают редко, но знать их устройство нужно, чтобы понимать три типовые ситуации: сервис в контейнере потребляет больше лимита и падает по OOM; потребление растёт при работе с большими файлами, хотя утечки нет; после перехода на новую версию .NET память изменилась без изменений в коде.

## Бюджеты поколений

Сборка gen 0 запускается не по таймеру, а когда **исчерпан бюджет** — объём аллокаций, накопленный с прошлой сборки. Бюджет динамический: рантайм подстраивает его по статистике выживаемости и размеру кешей процессора (ориентир для gen 0 — единицы–десятки мегабайт).

```
Аллокация → бюджет gen 0 исчерпан → сборка gen 0
                                     выжившие → gen 1
Бюджет gen 1 исчерпан              → сборка gen 0 + gen 1
                                     выжившие → gen 2
Бюджет gen 2 / нехватка памяти /   → полная сборка (gen 0 + 1 + 2 + LOH)
внешнее давление
```

Практический смысл: **что выживает, то дорожает**. Объект, переживший две сборки, попадает в gen 2, и дальше его судьба решается только при полных сборках. Отсюда рекомендация «либо очень коротко, либо очень долго»: временные объекты должны умирать в gen 0, а долгоживущие — оседать в gen 2 и не создаваться заново. Хуже всего объекты «средней» жизни, которые постоянно доживают до gen 1 и gen 2 и делают полные сборки частыми — типичный пример — кеш с коротким временем жизни элементов.

## Large Object Heap

Объекты **от 85 000 байт** размещаются в отдельной куче. Порог считается по размеру объекта целиком, поэтому в LOH почти всегда попадают массивы:

| Тип массива | Число элементов до LOH (x64) |
|---|---|
| `byte[]` | ~85 000 |
| `int[]` | ~21 250 |
| `long[]`, `double[]` | ~10 600 |
| массив ссылок (`object[]`, `string[]`) | ~10 600 |

Особенности LOH:

- **Считается частью gen 2.** Он собирается только при полных сборках, то есть редко.
- **По умолчанию не уплотняется.** Освобождённые участки помечаются свободными и переиспользуются, но не сдвигаются: куча фрагментируется. Возможна ситуация, когда свободных байт много, а выделить новый большой массив некуда — рантайм расширяет кучу, и потребление растёт.
- **Уплотнить можно вручную, разово:**

```csharp
System.Runtime.GCSettings.LargeObjectHeapCompactionMode =
    System.Runtime.GCLatencyMode.Batch is var _ ? System.Runtime.GCLargeObjectHeapCompactionMode.CompactOnce
                                                : default;
GC.Collect();     // применится к следующей полной сборке, стоит дорого
```

Это тяжёлая операция (перемещение мегабайт с обновлением ссылок), уместная разве что после разового пика, а не в цикле.

Порог настраивается (`GCLOHThreshold` в `runtimeconfig`), но менять его почти никогда не нужно.

### Как не создавать давление на LOH

```csharp
// Плохо: новый большой буфер на каждый вызов — прямая дорога в LOH
byte[] buffer = new byte[100_000];

// Хорошо: переиспользование через пул
var pool = System.Buffers.ArrayPool<byte>.Shared;
byte[] rented = pool.Rent(100_000);          // может вернуть больший массив
try { /* работать с rented.AsSpan(0, 100_000) */ }
finally { pool.Return(rented); }
```

Другие приёмы: потоковая обработка вместо чтения файла целиком, `RecyclableMemoryStream` вместо `MemoryStream` для больших данных, разбиение больших массивов на страницы, `Span<T>`-срезы вместо копий ([[Span, Memory и ArrayPool на практике]]).

### Pinned Object Heap

С .NET 5 закреплённые объекты выделяются в отдельной куче (POH) через `GC.AllocateArray<T>(length, pinned: true)`. Смысл в том, чтобы закреплённые буферы (для interop и сетевого ввода-вывода) не мешали уплотнению обычной кучи.

## Режимы сборщика

### Workstation против Server

| | Workstation | Server |
|---|---|---|
| Куч | одна | по одной на логическое ядро |
| Потоков GC | сборка в потоке, вызвавшем аллокацию | выделенный поток на каждую кучу |
| Оптимизируется под | отзывчивость, малое потребление | пропускную способность |
| По умолчанию | консольные и десктопные приложения | ASP.NET Core и другие серверные хосты |
| Паузы | короче | реже, но потенциально длиннее |
| Память | меньше | больше (несколько куч, больше бюджеты) |

```xml
<PropertyGroup>
  <ServerGarbageCollection>true</ServerGarbageCollection>       <!-- по умолчанию для web-хоста -->
  <ConcurrentGarbageCollection>true</ConcurrentGarbageCollection><!-- фоновая сборка gen 2 -->
</PropertyGroup>
```

Практическое правило: серверный режим выигрывает, когда у процесса несколько ядер и высокая скорость аллокаций. Но в контейнере с лимитом в одно-два ядра он может проигрывать: куч меньше не становится автоматически, а память расходуется щедрее. Именно эту проблему решает DATAS.

### DATAS

**Dynamic Adaptation To Application Sizes** — механизм, который подстраивает число куч серверного GC под фактическую нагрузку: при небольшой нагрузке используется меньше куч и меньше памяти, при росте — число куч увеличивается. Появился в .NET 8 как опция, в **.NET 9 включён по умолчанию** для серверного режима и сохраняется таковым в .NET 10.

Эффект заметен именно в контейнерах: типичный веб-сервис после обновления потребляет ощутимо меньше памяти при сопоставимой пропускной способности. Отключается при необходимости:

```xml
<PropertyGroup>
  <GarbageCollectionAdaptationMode>0</GarbageCollectionAdaptationMode>
</PropertyGroup>
```

Отключать стоит только по результатам измерений: если нагрузка стабильно высокая и важна максимальная пропускная способность, фиксированное число куч может быть чуть выгоднее.

### Контейнеры и лимиты

Рантайм читает лимиты cgroup и подстраивается: по умолчанию жёсткий предел управляемой кучи — около **75 % от лимита памяти контейнера**. Это защищает от того, чтобы GC считал доступной всю память узла.

```xml
<PropertyGroup>
  <!-- Явные лимиты, если нужен более тонкий контроль -->
  <GCHeapHardLimitPercent>0x50</GCHeapHardLimitPercent>   <!-- шестнадцатеричное: 80 % -->
</PropertyGroup>
```

Практика: **всегда задавать лимит памяти контейнера**. Без него рантайм ориентируется на память узла, держит большие бюджеты, и под давлением соседей процесс убивает OOM-killer — при этом в метриках самого приложения ничего подозрительного не видно.

## Режимы задержки

```csharp
using System.Runtime;

GCSettings.LatencyMode = GCLatencyMode.SustainedLowLatency;   // избегать блокирующих сборок gen 2

// Критический участок без сборок вообще (если удастся зарезервировать бюджет)
if (GC.TryStartNoGCRegion(totalSize: 50_000_000))
{
    try { /* обработка без пауз GC */ }
    finally { GC.EndNoGCRegion(); }
}
```

Это инструменты для узких сценариев: торговые системы, обработка в реальном времени, короткие критичные участки. В обычном веб-сервисе они не нужны, а неправильное использование `TryStartNoGCRegion` (слишком большой бюджет, отсутствие `EndNoGCRegion`) приводит к резкому росту памяти.

## Что смотреть в метриках

```bash
dotnet-counters monitor -p <pid> --counters System.Runtime
```

| Счётчик | Норма | О чём говорит отклонение |
|---|---|---|
| `time-in-gc` | единицы процентов | 20 %+ — слишком много мусора или неверные настройки |
| `gen-2-gc-count` | редкие | частые полные сборки: утечка или много долгоживущих данных |
| `alloc-rate` | зависит от нагрузки | резкий рост — регрессия в коде |
| `gc-fragmentation` | низкая | высокая — фрагментация, часто из-за LOH или закрепления |
| `gc-heap-size` | стабильна между рестартами | монотонный рост — утечка |

> [!warning] Подводные камни
> - **Большие массивы в цикле.** Каждый `new byte[100_000]` уходит в LOH, который собирается только при полных сборках; лечится `ArrayPool`.
> - **`MemoryStream` для больших данных.** При росте он пересоздаёт внутренний массив и оставляет в LOH мусор; нужен пул или потоковая обработка.
> - **Фрагментация LOH.** Свободной памяти много, а выделить большой блок некуда: потребление растёт при неизменных живых данных.
> - **Отсутствие лимита памяти в контейнере.** Рантайм ориентируется на память узла и держит слишком много.
> - **Включение серверного GC для маленького процесса.** Несколько куч в контейнере на одно ядро — лишняя память без выигрыша.
> - **`TryStartNoGCRegion` без `EndNoGCRegion`.** Аллокации продолжаются, бюджет исчерпывается, поведение непредсказуемо.
> - **Настройка GC вместо сокращения мусора.** Почти всегда правильнее уменьшить аллокации, чем крутить параметры сборщика.
> - **Кеш со средним временем жизни.** Объекты стабильно доживают до gen 2 и делают полные сборки частыми — худший режим для GC.

> [!example] Как делают в бою
> Настройки GC в подавляющем большинстве сервисов оставляют по умолчанию: серверный режим с фоновой сборкой и DATAS подобраны разумно. Что действительно делают всегда — задают лимит памяти контейнеру и следят за метриками времени в GC и размера кучи.
> Основная работа по памяти идёт не в настройках, а в коде: буферы через `ArrayPool`, потоковая обработка файлов и HTTP-тел вместо загрузки целиком, `Span<T>` вместо промежуточных массивов и строк, ограниченные кеши с вытеснением. Именно это убирает давление на LOH и снижает частоту полных сборок.
> При переходе на новую LTS-версию сначала измеряют: изменения в GC между версиями (особенно включение DATAS по умолчанию в .NET 9) меняют профиль потребления, и старые эмпирические лимиты контейнеров могут оказаться неактуальными — обычно в лучшую сторону.
> Отдельная практика для сервисов, обрабатывающих большие файлы: после завершения тяжёлой операции иногда делают разовое уплотнение LOH — но только по факту измеренной фрагментации, а не «на всякий случай».

## Вопросы с собеседований

> [!question]- Что такое LOH и чем он опасен?
> Large Object Heap — отдельная область управляемой кучи для объектов от 85 000 байт; почти всегда это массивы (для `byte[]` порог примерно 85 000 элементов, для `int[]` — около 21 250). Две особенности делают его источником проблем. Во-первых, LOH логически относится к gen 2 и собирается только при полных сборках, то есть редко и дорого. Во-вторых, по умолчанию он не уплотняется: освобождённые участки переиспользуются, но не сдвигаются, поэтому куча фрагментируется — возникает ситуация, когда суммарно свободной памяти достаточно, а непрерывного блока под новый массив нет, и рантайм расширяет кучу. Симптом — рост потребления при неизменном объёме живых данных. Уплотнение можно запросить разово через `GCSettings.LargeObjectHeapCompactionMode`, но это дорогая операция. Правильное решение — не создавать большие массивы часто: пул буферов (`ArrayPool<T>`), потоковая обработка, `Span<T>`-срезы вместо копий.

> [!question]- Чем серверный GC отличается от рабочего?
> Рабочий (workstation) режим использует одну управляемую кучу, и сборка выполняется в потоке, который спровоцировал аллокацию; он оптимизирован под отзывчивость и небольшое потребление памяти — это умолчание для консольных и десктопных приложений. Серверный режим создаёт отдельную кучу и выделенный поток сборки на каждое логическое ядро, что даёт существенно большую пропускную способность при высокой скорости аллокаций; он включён по умолчанию для ASP.NET Core. Плата — большее потребление памяти (несколько куч со своими бюджетами) и потенциально более длинные, хотя и более редкие, паузы. В контейнерах с одним-двумя ядрами серверный режим раньше нередко проигрывал, поэтому в .NET 8 появился, а в .NET 9 стал умолчанием механизм DATAS: число куч динамически подстраивается под фактическую нагрузку, и потребление памяти заметно снижается без потери пропускной способности.

> [!question]- Почему объекты «средней» продолжительности жизни хуже всего для GC?
> Потому что они переживают молодые сборки и попадают в старшие поколения, но затем всё равно умирают — а мусор в gen 2 убирается только полными сборками, самыми дорогими. Схема поколений эффективна на двух крайностях: объекты, умирающие в gen 0, освобождаются почти бесплатно, а долгоживущие (синглтоны, прогретые кеши) просто оседают в gen 2 и не создаются заново. Промежуточный случай — например, кеш с временем жизни в несколько секунд или буферы, живущие дольше одного запроса, — постоянно продвигает объекты в gen 2, повышает частоту полных сборок и увеличивает фрагментацию. Практический вывод: время жизни объектов стоит делать либо коротким (умирают в рамках операции), либо длинным (переиспользуются), а промежуточные сценарии закрывать пулами, чтобы объекты не создавались и не умирали, а брались и возвращались.

## Задачи

### Задача 1. Диагностировать рост памяти

Сервис конвертирует изображения. Живых данных всегда около 100 МБ, но потребление растёт до 3 ГБ за сутки и не падает. `gen-2-gc-count` низкий, `gc-fragmentation` высокая. Диагноз?

> [!success]- Решение
> Картина указывает на фрагментацию LOH. Конвертация изображений почти наверняка создаёт большие буферы (`byte[]` на несколько мегабайт) на каждый файл; такие массивы сразу попадают в LOH, который собирается только при полных сборках и по умолчанию не уплотняется. Разные размеры буферов оставляют между собой свободные участки, непригодные для следующих аллокаций, — суммарно свободно много, но непрерывных блоков нужного размера нет, и рантайм расширяет кучу. Низкое число сборок gen 2 подтверждает: полные сборки редки, значит LOH почти не подчищается.
> Что делать по порядку. Основное — перестать создавать большие массивы: брать буферы из `ArrayPool<byte>.Shared` (для очень больших — `ArrayPool<byte>.Create` со своими лимитами), использовать `RecyclableMemoryStream` вместо `MemoryStream`, обрабатывать изображение потоком там, где это возможно, и выравнивать размеры буферов (пул сам выдаёт массивы степеней двойки, что снижает фрагментацию). Как временная мера — разовое уплотнение LOH после пиков через `GCSettings.LargeObjectHeapCompactionMode = CompactOnce` с последующим `GC.Collect()`, но это лечение симптома. И обязательно задать лимит памяти контейнеру, чтобы рантайм вёл себя консервативнее.

### Задача 2. Выбрать конфигурацию

Микросервис в Kubernetes: лимит 512 МБ, 1 CPU, умеренная нагрузка. Какие настройки GC проверить?

> [!success]- Решение
> Первое — убедиться, что лимиты контейнера заданы (`resources.limits.memory` и `cpu`): рантайм читает cgroup и без лимита считает доступной память всего узла, из-за чего держит большие бюджеты и рискует быть убитым OOM-killer.
> Второе — режим сборщика. ASP.NET Core по умолчанию включает серверный GC, который на одном ядре и 512 МБ раньше был скорее вреден. В .NET 9+ это во многом снимается DATAS (включён по умолчанию): число куч подстраивается под нагрузку. Поэтому порядок такой — сначала измерить на умолчаниях, и только если потребление близко к лимиту, попробовать `<ServerGarbageCollection>false</ServerGarbageCollection>` и сравнить пропускную способность и потребление.
> Третье — оставить фоновую сборку включённой (умолчание), она уменьшает паузы.
> Чего делать не стоит: крутить `GCHeapCount`, `GCgen0size` и подобные параметры вслепую. Если памяти не хватает при разумной нагрузке, причина почти всегда в коде — неограниченный кеш, большие буферы, материализация всей выборки из БД в память, — и настройки сборщика это не лечат.

## Итог

- Сборка запускается по исчерпании бюджета поколения; бюджеты динамические и подстраиваются рантаймом.
- Объекты «средней» жизни хуже всего: они доживают до gen 2 и учащают полные сборки.
- LOH — от 85 000 байт, относится к gen 2, по умолчанию не уплотняется: отсюда фрагментация и рост потребления.
- Давление на LOH снимают пулами буферов, потоковой обработкой и срезами вместо копий.
- Workstation GC — одна куча и отзывчивость; Server GC — куча на ядро и пропускная способность (умолчание для веба).
- DATAS (умолчание с .NET 9) подстраивает число куч под нагрузку и заметно снижает память в контейнерах.
- Рантайм учитывает лимиты cgroup: лимит памяти контейнеру надо задавать всегда.
- Настройки сборщика трогают в последнюю очередь; сначала сокращают мусор в коде.
