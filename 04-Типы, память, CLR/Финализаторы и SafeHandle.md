# Финализаторы и SafeHandle

> [!abstract] Коротко
> Финализатор (`~MyClass()`) — метод, который GC вызывает перед освобождением объекта. Он выглядит как деструктор из C++, но ведёт себя иначе: момент вызова недетерминирован, порядок между объектами не гарантирован, выполнение при завершении процесса не гарантировано вовсе, а сам объект из-за него переживает лишнюю сборку и попадает в старшее поколение. Поэтому правило современного .NET простое: **финализаторы в прикладном коде не пишут**. Единственная законная причина — прямое владение неуправляемым ресурсом, и для этого случая есть `SafeHandle`, у которого финализация уже реализована правильно и безопасно.

## Зачем это нужно

Тема нужна по двум причинам: понимать, почему «на всякий случай добавлю финализатор» — вредный совет, и уметь корректно обернуть нативный ресурс, если это всё-таки требуется (P/Invoke, работа с библиотеками ОС).

Плюс это классический вопрос на собеседовании про уровень понимания GC: чем финализатор отличается от `Dispose`, сколько сборок переживает объект с финализатором, зачем нужен `GC.SuppressFinalize`.

## Как работает финализация

```csharp
public class Legacy
{
    ~Legacy()                       // синтаксис похож на деструктор C++
    {
        // на самом деле компилируется в override Finalize()
    }
}
```

Жизненный цикл объекта с финализатором:

```
1. new Legacy()      → объект создан, его ссылка добавлена в очередь финализации
2. объект стал недостижим
3. Сборка №1         → GC видит финализатор: объект НЕ освобождается,
                       он переносится в очередь «готовых к финализации» (freachable)
                       и тем самым снова становится достижимым — то есть выживает
4. Поток финализации → отдельный поток рантайма вызывает ~Legacy()
5. Сборка №2         → только теперь память освобождается
```

Отсюда все последствия:

- **Объект живёт дольше.** Минимум две сборки, а поскольку он пережил первую — он уже в старшем поколении, где сборки редки.
- **Момент вызова неизвестен.** Между «объект стал не нужен» и «финализатор выполнился» могут пройти минуты.
- **Порядок не определён.** Нельзя рассчитывать, что финализатор поля выполнится позже финализатора владельца, — и трогать другие управляемые объекты в финализаторе нельзя.
- **Выполнение не гарантировано.** В .NET Core и новее финализаторы **не запускаются** при штатном завершении процесса, а при аварийном — тем более.
- **Один поток на всё приложение.** Долгий или зависший финализатор блокирует финализацию всех остальных объектов — очередь растёт, память не освобождается.
- **Исключение из финализатора** завершает процесс.

```csharp
GC.SuppressFinalize(this);      // сказать GC: финализатор не нужен, объект уже освобождён вручную
GC.ReRegisterForFinalize(this); // вернуть обратно в очередь (нужно крайне редко)
```

Именно поэтому `Dispose()` в каноническом паттерне вызывает `GC.SuppressFinalize(this)`: ресурс уже освобождён явно, и заставлять объект проходить через финализацию незачем ([[IDisposable, using и паттерн Dispose]]).

## Почему финализатор не заменяет Dispose

| | `Dispose` | Финализатор |
|---|---|---|
| Момент вызова | детерминированный, в конце `using` | неизвестен |
| Кто вызывает | код (или DI-контейнер) | поток финализации GC |
| Порядок | контролируется программистом | не определён |
| Гарантия выполнения | да, если написан `using` | нет |
| Стоимость | нулевая | +1 сборка, старшее поколение, отдельный поток |
| Доступ к управляемым объектам | можно | нельзя |

Финализатор — не альтернатива, а **страховка последней надежды** для нативного ресурса на случай, если `Dispose` забыли. Для управляемых ресурсов он бесполезен: они и так будут собраны.

## SafeHandle

`SafeHandle` — абстрактный класс из BCL, оборачивающий нативный дескриптор и решающий сразу несколько проблем финализации:

- **Критическая финализация.** Наследуется от `CriticalFinalizerObject`: рантайм гарантирует, что такой финализатор выполнится даже при выгрузке домена или в условиях нехватки памяти, и выполнит его раньше обычных финализаторов.
- **Защита от повторного использования дескриптора (handle recycling).** Внутри есть счётчик ссылок: пока дескриптор используется в P/Invoke-вызове, он не может быть закрыт другим потоком. Без этого возможна уязвимость, когда закрытый дескриптор переиспользуется ОС под другой ресурс, а старый код продолжает в него писать.
- **Корректное взаимодействие с маршалингом.** `SafeHandle` в сигнатуре P/Invoke обрабатывается рантаймом специально: он увеличивает счётчик перед вызовом и уменьшает после.
- **Готовая реализация `IDisposable`.**

Готовые наследники: `SafeFileHandle`, `SafeWaitHandle`, `SafeProcessHandle`, `SafeMemoryMappedFileHandle`, `SafeSocketHandle` и другие — почти всегда нужный уже существует.

### Свой SafeHandle

```csharp
using System.Runtime.InteropServices;
using Microsoft.Win32.SafeHandles;

public sealed class NativeLibraryHandle : SafeHandleZeroOrMinusOneIsInvalid
{
    public NativeLibraryHandle() : base(ownsHandle: true) { }

    protected override bool ReleaseHandle()
    {
        // Вызывается ровно один раз: из Dispose или из критического финализатора.
        // Здесь НЕЛЬЗЯ обращаться к другим управляемым объектам и бросать исключения.
        return NativeMethods.CloseLibrary(handle);
    }
}

internal static partial class NativeMethods
{
    [LibraryImport("mylib", SetLastError = true)]          // source-generated P/Invoke, .NET 7+
    internal static partial NativeLibraryHandle OpenLibrary(string path);

    [LibraryImport("mylib")]
    [return: MarshalAs(UnmanagedType.Bool)]
    internal static partial bool CloseLibrary(IntPtr handle);
}

// Использование — как с любым IDisposable
using var lib = NativeMethods.OpenLibrary("/usr/lib/mylib.so");
```

Базовые классы выбирают по тому, какое значение дескриптора считается невалидным: `SafeHandleZeroOrMinusOneIsInvalid` (типично для Windows API и большинства библиотек) или `SafeHandleMinusOneIsInvalid`.

### Класс, владеющий SafeHandle

```csharp
public sealed class NativeResource : IDisposable
{
    private readonly NativeLibraryHandle _handle = NativeMethods.OpenLibrary("mylib");

    public void Dispose() => _handle.Dispose();     // всё; финализатор не нужен
}
```

Финализатор здесь не пишется: если `Dispose` забудут, сработает критический финализатор самого `SafeHandle`. Это и есть современный паттерн — вместо `Dispose(bool)` с финализатором остаётся одна строка.

## Когда финализатор всё-таки пишут

Исчерпывающий список для прикладного кода: практически никогда. Возможные случаи в библиотеках:

- нативный ресурс, для которого нельзя использовать `SafeHandle` (например, освобождение требует нескольких значений, а не одного дескриптора) — тогда лучше сделать свою обёртку поверх `SafeHandle`, а не финализатор;
- диагностика: обнаружить, что объект не был освобождён, и записать предупреждение в лог. Такой финализатор оставляют только в отладочных сборках через `#if DEBUG`.

```csharp
#if DEBUG
    ~ResourceOwner()
    {
        // Сигнализировать разработчику, что забыли Dispose.
        // В Release этого кода нет — цена финализации не платится.
        System.Diagnostics.Debug.Fail($"{nameof(ResourceOwner)} не был освобождён");
    }
#endif
```

> [!warning] Подводные камни
> - **Финализатор «на всякий случай».** Объект переживает лишнюю сборку, попадает в gen 2 и освобождается заметно позже; выигрыша нет никакого.
> - **Обращение к управляемым объектам в финализаторе.** Они могут быть уже финализированы: порядок не определён. Отсюда параметр `disposing` в каноническом паттерне.
> - **Исключение в финализаторе.** Не перехватывается и завершает процесс.
> - **Долгая работа в финализаторе.** Поток финализации один: очередь встаёт, память не освобождается.
> - **Расчёт на финализацию при выходе.** В .NET Core и новее финализаторы при завершении процесса не выполняются.
> - **Забытый `GC.SuppressFinalize` в `Dispose`.** Объект без нужды проходит через очередь финализации.
> - **`IntPtr` вместо `SafeHandle`.** Нет счётчика ссылок и критической финализации — возможны утечка дескриптора и гонка при закрытии.
> - **Воскрешение объекта** (сохранение `this` в статическое поле из финализатора) — технически возможно, но приводит к трудноуловимым ошибкам; так не делают.

> [!example] Как делают в бою
> В прикладном .NET-коде финализаторов нет вовсе. Ресурсы — это `FileStream`, `DbConnection`, `HttpClient`, `Socket`, и все они уже корректно реализованы в BCL поверх `SafeHandle`; от разработчика требуется только `using`.
> Финализаторы появляются в двух местах: в библиотеках, оборачивающих нативный код (и там их прячут внутрь `SafeHandle`), и в отладочной диагностике «забыли `Dispose`» под `#if DEBUG`.
> При написании P/Invoke современный подход — генератор `[LibraryImport]` вместо `[DllImport]` (он совместим с Native AOT и не требует маршалинга в рантайме) плюс `SafeHandle` в сигнатурах вместо `IntPtr`. Это закрывает и производительность, и безопасность дескрипторов.
> Если в дампе видно растущую очередь финализации (`!finalizequeue` в SOS), это почти всегда означает либо забытый `SuppressFinalize`, либо зависший финализатор — и то и другое чинится удалением финализатора.

## Вопросы с собеседований

> [!question]- Чем финализатор отличается от `Dispose`?
> `Dispose` — обычный метод, который вызывает код в детерминированный момент, обычно через `using`; он может обращаться к другим управляемым объектам, его порядок и время известны, стоимость нулевая. Финализатор вызывает сборщик мусора в отдельном потоке в неизвестный момент; обращаться к другим управляемым объектам в нём нельзя, потому что порядок финализации не определён и они могут быть уже обработаны; при штатном завершении процесса в .NET Core и новее финализаторы вообще не запускаются. Кроме того, объект с финализатором дороже: при первой сборке он не освобождается, а помещается в очередь готовых к финализации и тем самым выживает, попадая в старшее поколение, — реальное освобождение памяти происходит минимум на второй сборке. Поэтому финализатор — не альтернатива `Dispose`, а страховка последней надежды для неуправляемого ресурса, и в современном коде её роль выполняет `SafeHandle`.

> [!question]- Зачем `Dispose` вызывает `GC.SuppressFinalize(this)`?
> Чтобы снять объект с очереди финализации: ресурс уже освобождён явно, повторное освобождение не нужно, а прохождение через финализацию стоит дорого — объект пережил бы лишнюю сборку и задержался в памяти. Вызов имеет смысл только у типов, у которых финализатор действительно есть (своя реализация или унаследованная); для класса без финализатора он безвреден, но бесполезен, и анализатор CA1816 подсказывает, где он нужен, а где лишний. Обратная операция `GC.ReRegisterForFinalize` возвращает объект в очередь и применяется в исключительных сценариях вроде пулов объектов, которые переиспользуют экземпляры. В современном стиле, где нативный ресурс обёрнут в `SafeHandle`, собственного финализатора у класса нет, и `SuppressFinalize` тоже не требуется.

> [!question]- Что такое `SafeHandle` и какие проблемы он решает?
> Это абстрактный класс BCL для оборачивания нативных дескрипторов. Он решает четыре проблемы. Первая — гарантированное освобождение: `SafeHandle` наследуется от `CriticalFinalizerObject`, поэтому его финализатор рантайм выполняет с повышенными гарантиями и раньше обычных. Вторая — гонка повторного использования дескриптора: внутри ведётся счётчик ссылок, и пока дескриптор задействован в P/Invoke-вызове, закрыть его нельзя; без этого закрытый дескриптор мог бы быть переиспользован операционной системой под другой ресурс, а старый код продолжал бы в него писать — известная уязвимость handle recycling. Третья — корректный маршалинг: рантайм понимает `SafeHandle` в сигнатурах P/Invoke и сам управляет счётчиком. Четвёртая — готовая реализация `IDisposable`. Практический итог: владеющему классу не нужен ни собственный финализатор, ни паттерн `Dispose(bool)` — достаточно освободить `SafeHandle` в `Dispose`.

## Задачи

### Задача 1. Убрать лишнее

```csharp
public class CacheEntry : IDisposable
{
    private readonly Dictionary<string, byte[]> _data = new();
    private bool _disposed;

    public void Dispose() { Dispose(true); GC.SuppressFinalize(this); }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;
        if (disposing) _data.Clear();
        _disposed = true;
    }

    ~CacheEntry() => Dispose(false);
}
```

> [!success]- Решение
> Здесь нет ни одного неуправляемого ресурса: словарь с массивами — обычные управляемые объекты, которые соберёт GC. Значит, лишним является всё: финализатор (заставляет объект пережить лишнюю сборку и попасть в gen 2), `Dispose(bool)` с `virtual`, `SuppressFinalize`, да и сам `IDisposable`. Более того, `_data.Clear()` в `Dispose` не освобождает память немедленно — он лишь убирает ссылки, что произошло бы и так, когда сам `CacheEntry` станет недостижим.
> ```csharp
> public sealed class CacheEntry
> {
>     private readonly Dictionary<string, byte[]> _data = new();
> }
> ```
> Если бы освобождение всё-таки требовалось (например, массивы взяты из `ArrayPool` и их надо вернуть), реализация выглядела бы так: `sealed`-класс, `IDisposable`, флаг, возврат буферов в пул — и по-прежнему без финализатора, потому что забытый `Dispose` в этом случае приводит лишь к потере переиспользования, а не к утечке ресурса ОС.

### Задача 2. Обернуть нативный ресурс

Есть C-библиотека с функциями `int db_open(const char* path)` (возвращает дескриптор или −1) и `void db_close(int handle)`. Напиши безопасную обёртку.

> [!success]- Решение
> ```csharp
> using System.Runtime.InteropServices;
> using Microsoft.Win32.SafeHandles;
>
> public sealed class DbHandle : SafeHandleMinusOneIsInvalid          // невалидное значение — −1
> {
>     public DbHandle() : base(ownsHandle: true) { }
>
>     protected override bool ReleaseHandle()
>     {
>         NativeMethods.db_close(handle.ToInt32());
>         return true;                                                 // без исключений и логирования
>     }
> }
>
> internal static partial class NativeMethods
> {
>     [LibraryImport("mydb", StringMarshalling = StringMarshalling.Utf8)]
>     internal static partial DbHandle db_open(string path);
>
>     [LibraryImport("mydb")]
>     internal static partial void db_close(int handle);
> }
>
> public sealed class Database(string path) : IDisposable
> {
>     private readonly DbHandle _handle = NativeMethods.db_open(path);
>
>     public void Dispose() => _handle.Dispose();                      // финализатор не нужен
> }
>
> using var db = new Database("/data/app.db");
> ```
> Что здесь важно. Возвращаемым типом P/Invoke объявлен сам `DbHandle`, а не `int`: тогда рантайм создаёт обёртку атомарно и дескриптор не может «потеряться» между вызовом и присваиванием. Базовый класс выбран по соглашению библиотеки о невалидном значении. В `ReleaseHandle` нет ни исключений, ни обращений к управляемым объектам — он может выполняться из критического финализатора. Владеющий класс не пишет ни финализатора, ни `Dispose(bool)`: страховку обеспечивает сам `SafeHandle`. Использован `[LibraryImport]` вместо `[DllImport]` — генератор создаёт маршалинг на этапе компиляции, что быстрее и совместимо с Native AOT.

---

## Итог

- Финализатор вызывается GC недетерминированно, в отдельном потоке, без гарантий порядка и без гарантии выполнения при завершении процесса.
- Объект с финализатором переживает лишнюю сборку и попадает в старшее поколение.
- В финализаторе нельзя обращаться к другим управляемым объектам и нельзя бросать исключения.
- `Dispose` вызывает `GC.SuppressFinalize(this)`, чтобы снять объект с очереди финализации.
- Для неуправляемых ресурсов правильный инструмент — `SafeHandle`: критическая финализация, счётчик ссылок, корректный маршалинг.
- Класс, владеющий `SafeHandle`, не пишет собственный финализатор — достаточно освободить дескриптор в `Dispose`.
- В прикладном коде финализаторы не нужны; допустима только диагностика под `#if DEBUG`.
