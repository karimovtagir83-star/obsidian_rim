# Устройство .NET: CLR, BCL, SDK, рантаймы

> [!abstract] Коротко
> .NET — стопка слоёв: твой код в виде сборки (IL + метаданные) лежит поверх библиотеки классов (BCL), та поверх среды выполнения (CLR), та поверх ОС. SDK — отдельный набор инструментов для сборки (компилятор, MSBuild, `dotnet` CLI), который на проде не нужен вовсе. `dotnet` CLI — не программа, а диспетчер: он определяет, что ты просишь (собрать, запустить, опубликовать), и либо запускает MSBuild/Roslyn из SDK, либо передаёт управление хосту CLR. Понимание, кто из них что делает и где физически лежит на диске, снимает большинство вопросов вида «почему в контейнере не запускается», «какой пакет ставить» и «во что компилируется этот код».

## Зачем это знать

Три ситуации, где это окупается в первый же день:

1. **Прод падает с `You must install .NET to run this application`.** Нужно сразу понимать: не хватает рантайма, а не SDK; какого именно — `Microsoft.NETCore.App` или `Microsoft.AspNetCore.App`; почему `rollForward` не спас.
2. **Образ Docker весит 800 МБ вместо 110.** Потому что в него положили `sdk`-образ вместо `aspnet`. Сборка и запуск — разные образы, разные слои.
3. **Ревью сгенерированного кода.** Вопросы «сколько тут аллокаций», «упаковывается ли структура», «во что развернулся `foreach`» решаются одним взглядом в IL, а не спором в комментариях к PR.

## Модель

### Слои: от кода до железа

```
ТВОЙ КОД        MyApi.dll — IL + метаданные (не машинный код!)
БИБЛИОТЕКИ      NuGet: Npgsql.dll, Serilog.dll ... (тоже IL)
SHARED FW       Microsoft.AspNetCore.App (веб-стек)
                Microsoft.NETCore.App (BCL) + System.Private.CoreLib
CLR (CoreCLR)   загрузчик типов │ JIT │ GC │ исключения │ interop
ХОСТ            dotnet (muxer) / apphost → hostfxr → hostpolicy
ОС              syscalls, виртуальная память, планировщик потоков
```

Ключевая мысль: **компилятор C# не производит машинный код**. `csc`/Roslyn выдаёт сборку с IL и метаданными. Машинный код появляется в момент выполнения силами JIT — механика в [[JIT, Tiered Compilation, ReadyToRun, Native AOT]].

### CLR: что именно он делает

CLR — среда выполнения, а не «виртуальная машина» в смысле интерпретатора: IL не интерпретируется, а компилируется в нативный код.

- **Загрузчик типов.** При первом упоминании типа CLR находит сборку через метаданные, строит в памяти **MethodTable** (указатель на базовый тип, флаги, карту GC-указателей, таблицу методов) и раскладывает поля. Каждый объект в куче первым словом указывает на свой MethodTable — отсюда 16 байт служебных данных на объект на x64.
- **JIT.** Слоты MethodTable сначала указывают на стаб; первый вызов метода дёргает JIT, тот компилирует IL в машинный код и переписывает слот. Дальше — многоуровневая компиляция и PGO.
- **GC — часть CLR, не библиотеки.** Написан на C++, живёт внутри `libcoreclr.so`, управляет управляемой кучей. Подробности — [[Сборка мусора (GC): как работает]].
- **Верификация и безопасность — по большей части в прошлом.** IL-верификатор, Code Access Security, `AppDomain` как граница безопасности — всё это работало в .NET Framework на модели «частично доверенного кода в процессе». Модель признана нерабочей: сегодня изоляция плагинов — не защита от вредоносного кода, а границы процессов/контейнеров. Ответ «CLR проверяет типобезопасность через verifier» на собеседовании — устаревшее знание, актуальное лишь как контекст.

### BCL: одна реализация, много фасадов

**BCL** (Base Class Library) — `System.Object`, коллекции, строки, LINQ, IO. Физически реальный код лежит в одной сборке — **`System.Private.CoreLib.dll`**: там `Object`, `String`, `Array`, `Exception`, `Span<T>`, GC-интринсики. Компилятор её не видит: на неё нельзя сослаться напрямую.

Десятки `System.Runtime.dll`, `System.Collections.dll` и подобных в shared framework — **фасады** (type forwarders): пустые сборки с записями `[assembly: TypeForwardedTo(...)]`, указывающими на CoreLib. Это наследие эпохи «à la carte NuGet» (.NET Core 1.x–2.x): библиотеку тогда разбили на мелкие пакеты, идея не взлетела (версионный ад), в 3.0 вернулись к монолитному shared framework, а фасады остались ради совместимости старых сборок.

Отдельно — **ссылочные сборки** (reference assemblies), на которые компилятор ссылается при сборке:

| | Ссылочная сборка | Сборка реализации |
|---|---|---|
| Где | `packs/*.Ref/<TFM>` (targeting pack) | `shared/Microsoft.NETCore.App/<версия>` |
| Тела методов | `throw null;` — заглушка | настоящий IL |
| Кто использует | Roslyn при компиляции | CLR в рантайме |

Отсюда классический баг: код собрался, а в рантайме `MissingMethodException` — targeting pack на CI новее рантайма, установленного на сервере.

### Сборка: единица развёртывания, а не файл с машинным кодом

Сборка (`.dll`/`.exe`) содержит PE-заголовок, CLI-заголовок, **метаданные** (таблицы `TypeDef`/`MethodDef`/`FieldDef`, ссылки `AssemblyRef`/`TypeRef`, манифест с именем/версией/зависимостями) и **IL-код методов**. Метаданные полны и обязательны — в отличие от нативного C++, где после компиляции остаются только адреса. Именно поэтому в .NET работают рефлексия, декомпиляция в читаемый код, DI-контейнеры и сериализаторы: сборка описывает саму себя.

Три версии, которые путают:

```xml
<AssemblyVersion>1.0.0.0</AssemblyVersion>  <!-- идентичность сборки, влияет на разрешение ссылок -->
<FileVersion>1.2.3.456</FileVersion>         <!-- для ОС, ни на что в рантайме не влияет -->
<Version>1.2.3-beta.1</Version>              <!-- версия NuGet-пакета -->
```

`AssemblyVersion` меняют редко и осознанно — её рост внутри мажорной версии ломает разрешение ссылок без пересборки зависимых сборок.

### IL: зачем в него смотреть

IL — стековый байт-код без регистров: инструкции берут операнды со стека вычислений и кладут результат обратно.

```
int Add(int a, int b) => a + b;
// ldarg.1   → [a]
// ldarg.2   → [a, b]
// add       → [a+b]
// ret
```

Читать IL целиком не нужно — нужно узнавать две инструкции, которые отвечают на 90 % вопросов о производительности: **`box`** — упаковка value-типа, аллокация в куче; **`newobj`** — создание объекта, в том числе скрытого (класс замыкания для лямбды с захватом, `async`-автомат). Если в IL горячего метода их нет — аллокаций нет. Смотреть удобнее всего на sharplab.io (C# → IL → низкоуровневый C# рядом) или декомпиляцией в Rider/ILSpy — это быстрее, чем искать документацию по чужому NuGet-пакету.

Практическое следствие для современного .NET: **trimming и Native AOT удаляют то, что не видно статически**. Рефлексия по строковому имени типа не оставляет в метаданных явной ссылки — компоновщик выбрасывает тип, приложение падает только в опубликованном виде. Отсюда движение к генераторам исходного кода вместо сканирования сборок в рантайме.

### SDK, рантайм, shared framework — что ставить куда

| Сущность | Что это | Нужно для сборки | Нужно в проде |
|---|---|---|---|
| **SDK** | Roslyn, MSBuild, `dotnet` CLI, NuGet-клиент, targeting packs | Да | Нет |
| **Shared framework** (рантайм) | CoreCLR + BCL реального исполнения | Нет | Да |
| **Runtime pack** | Рантайм как NuGet-пакет для self-contained | Только при `publish` | Нет |

SDK включает рантайм, обратное неверно. Отсюда правило для Docker: собирать в `sdk`-образе, запускать в `aspnet`/`runtime`-образе — разница в размере в 6–7 раз.

Раскладка на диске (Linux, пакетная установка):

```
/usr/share/dotnet/
├── dotnet                              ← muxer, точка входа
├── host/fxr/8.0.x/libhostfxr.so        ← поиск и выбор рантайма
├── sdk/8.0.4xx/                        ← MSBuild, Roslyn, шаблоны
├── shared/Microsoft.NETCore.App/8.0.x/     ← BCL + libcoreclr.so
├── shared/Microsoft.AspNetCore.App/8.0.x/  ← Kestrel, MVC, DI-хостинг
└── packs/Microsoft.NETCore.App.Ref/8.0.x/  ← ссылочные сборки
```

### dotnet CLI: интерфейс к SDK, не самостоятельный инструмент

`dotnet` — диспетчер с двумя режимами работы, и это единственное, что важно держать в голове:

- Если аргумент — путь к `.dll` (`dotnet MyApi.dll`), muxer сразу передаёт управление **хосту рантайма**: читает `runtimeconfig.json`, находит через `hostfxr` подходящий shared framework, запускает CLR. SDK для этого не нужен вообще — только рантайм на машине.
- Если аргумент — команда SDK (`build`, `run`, `test`, `publish`, `new`, `add package`), muxer находит установленный SDK и вызывает **MSBuild**, который дальше вызывает Roslyn для компиляции, NuGet-клиент для восстановления зависимостей и т. д. IDE не делает ничего, чего нельзя сделать этими же командами — она их и вызывает.

Отсюда правило: `dotnet run` уместен в разработке (пересобирает и запускает), в проде запускают уже собранный `dotnet MyApi.dll` или самодостаточный exe — пересборка на старте недопустима и просто требует SDK там, где его быть не должно.

Команды, которые реально нужны в голове, не как список флагов:

| Команда | Что решает |
|---|---|
| `dotnet --info` / `--list-runtimes` / `--list-sdks` | Первый шаг любой диагностики «не собирается»/«не запускается»: что физически стоит на машине |
| `dotnet build -c Release` / `dotnet publish -c Release -o out` | Release — не косметика: включает оптимизации и убирает Debug-проверки; Debug на проде — источник ложной оценки производительности |
| `dotnet run --project src/Api -- --arg` | Аргументы после `--` уходят в приложение, а не в CLI — частая причина «почему флаг не сработал» |
| `dotnet test --filter "FullyQualifiedName~OrderTests"` | Гонять один тест вместо всего набора при локальной отладке |
| `dotnet tool restore` / `dotnet-counters`, `dotnet-dump` | Локальные инструменты фиксируются манифестом в репозитории (одинаковые версии у всех); в проде из CLI остаётся только диагностика — сборки и SDK там нет |

`global.json` фиксирует версию **SDK** для репозитория (не рантайма!) — без него команда с более новым SDK получает другие анализаторы и предупреждения, чем CI:

```json
{ "sdk": { "version": "8.0.400", "rollForward": "latestFeature" } }
```

## Решения

| Ситуация | Что выбрать | Последствия |
|---|---|---|
| Прод-сервер с несколькими сервисами | Framework-dependent (`dotnet publish`) | Мелкий артефакт, обновления безопасности рантайма прилетают с пакетом ОС; сервер обязан иметь совместимый рантайм |
| Изолированный стенд / CLI-утилита для не-.NET-окружения | Self-contained (`--self-contained -r linux-x64`) | Десятки МБ, но не требует ничего на машине; патчи безопасности — только пересборкой |
| Docker-образ для сборки vs для запуска | `sdk`-образ на этапе build, `aspnet`/`runtime` — на этапе финального образа | Многостадийная сборка обязательна; иначе лишние гигабайты и раздутая поверхность атаки |
| Политика подбора версии рантайма на сервере | `RollForward=Minor` (по умолчанию) для гибкости, `Disable` — только если ты контролируешь и артефакт, и машину | `Disable` в контейнере ломается при обычном патче базового образа |
| Нужно понять, есть ли лишние аллокации в горячем пути | Посмотреть IL на sharplab.io, а не спорить | Быстрый качественный ответ («есть/нет»); для количественной оценки всё равно нужен `BenchmarkDotNet` |

> [!info] Куда идёт индустрия
> В .NET 10 появились файловые приложения (`dotnet run script.cs` без `.csproj`), а `dotnet` умеет публиковать такой файл с директивами `#:package` прямо внутри него. В `net8.0` этого нет — используется только полноценный проект. Значимо для чтения чужих примеров в статьях и в ответах ИИ-агентов, но применять в `alifshop.backend.service-shop` нельзя.

> [!example] В ServiceShop
> `Alif.ServiceShop.API` — единственный проект, который реально запускается (`dotnet run` локально, `dotnet MyApi.dll` в контейнере); пять модулей работают внутри одного процесса на общем CLR и общей BCL, но у каждого свой Autofac-контейнер и своя строка подключения — граница логическая, а не по сборкам рантайма (см. [[ServiceShop: модульный монолит и изоляция модулей]]).
> Сборка образа — классический многостадийный Dockerfile: `sdk`-образ тянет `dotnet restore`/`dotnet publish`, финальный слой — `aspnet`-образ той же мажорной версии, что и `net8.0` в `.csproj`. Смешение SDK 8.0.4xx на CI и рантайма другой patch-версии на проде — обычная причина `MissingMethodException`, которую ловят только интеграционным прогоном на том же образе.
> В IL заглядывают редко и по конкретному поводу: на ревью PR, где под вопросом лишняя аллокация в цикле обработки заказов, — быстрее вставить фрагмент в sharplab.io и посмотреть на `box`/`newobj`, чем спорить в комментариях.

> [!warning] Где ошибаются
> - **Кладут `sdk`-образ в прод-Dockerfile «для простоты».** Раздувает образ в разы и оставляет в контейнере компилятор и MSBuild — лишняя поверхность атаки, если получат RCE.
> - **Путают `AssemblyVersion` и `Version` пакета.** Поднимают `AssemblyVersion` при каждом релизе — ломают разрешение ссылок у зависимых сборок без пересборки.
> - **Считают, что в `.dll` лежит машинный код.** Там IL и метаданные; машинный код появляется в момент выполнения (кроме ReadyToRun и Native AOT, где это явный отдельный шаг публикации).
> - **`rollForward: Disable` в контейнере «для надёжности».** Ломается на первом же патче безопасности базового образа: версия рантайма сдвинулась на патч, точное совпадение больше не выполняется.
> - **Агент часто:** предлагает `dotnet run` в шаге деплоя или в Dockerfile ENTRYPOINT вместо `dotnet MyApi.dll` — работает локально, но тянет SDK и пересборку туда, где должен быть только рантайм.
> - **Агент часто:** объясняет `MissingMethodException` как «баг в коде» и предлагает добавить проверки, вместо того чтобы сравнить версию targeting pack на CI и версию рантайма на целевой машине.

## Проверка на ревью

- В Dockerfile сборка и запуск разнесены по стадиям: `sdk`-образ не попадает в финальный слой.
- `TargetFramework` в `.csproj` соответствует установленному в проекте `net8.0`, а не скопирован из примера с `net10.0`.
- Изменение `AssemblyVersion` в PR обосновано (major-релиз), а не случайный побочный эффект скрипта версионирования.
- Диагностика `MissingMethodException`/`FileNotFoundException` в PR-описании ссылается на сравнение версий SDK/рантайма/targeting pack, а не на «непонятно почему».
- В коде нет рефлексии по строковому имени типа там, где предполагается будущий trimming/Native AOT.
- CI-шаги используют `--no-restore`/`--no-build`, где предыдущий шаг уже выполнил эту работу — иначе тестируется не то, что собрано.

## Проверь себя

> [!question]- Почему CLR — не «виртуальная машина» в привычном смысле?
> Потому что он не интерпретирует IL построчно, а компилирует его в нативный машинный код через JIT: первый вызов метода идёт через стаб, который дёргает JIT, тот генерирует машинный код и переписывает слот в MethodTable, чтобы следующий вызов шёл напрямую. Термин «виртуальная машина» вводит в заблуждение и на собеседовании засчитывается как «не совсем понимает механику».

> [!question]- Почему `System.Runtime.dll` в shared framework не содержит реализации `System.String`?
> Потому что это фасад — сборка с записями type forwarder, указывающими на `System.Private.CoreLib.dll`, где лежит реальный код. Разделение осталось от эпохи «à la carte NuGet»: BCL когда-то раздробили на мелкие пакеты, идея не прижилась из-за версионного ада, вернулись к монолитному shared framework, а фасады оставили ради совместимости старых сборок, ссылавшихся на прежние имена.

> [!question]- Приложение собрано под .NET 8.0.0, на сервере стоит 8.0.5. Запустится?
> Да — по умолчанию действует политика `rollForward: Minor`: рантайм должен иметь ту же major-версию, minor не ниже запрошенной, а внутри выбранной minor берётся последний доступный патч. Не запустится в обратном случае (собрано под более новую версию, чем стоит) и при явном `rollForward: Disable`, требующем точного совпадения.

> [!question]- Зачем нужны ссылочные сборки, если есть настоящие с тем же именем?
> Ссылочные сборки (в targeting pack) содержат только сигнатуры членов, тела методов заменены на `throw null`, и используются исключительно компилятором на этапе сборки. Это позволяет компилировать под версию фреймворка, не установленную на машине разработчика, и не даёт компилятору случайно завязаться на детали реализации. Расплата — если targeting pack на CI новее рантайма в проде, код соберётся, но упадёт `MissingMethodException` в момент первого вызова.

> [!question]- В чём разница между `dotnet run` и `dotnet MyApi.dll`, и почему это важно для Dockerfile?
> `dotnet run` — команда SDK: восстанавливает зависимости, собирает проект и только потом запускает результат; требует установленного SDK и исходников. `dotnet MyApi.dll` — прямой запуск уже собранной сборки через хост рантайма, SDK не нужен. В финальном образе Dockerfile, построенном на `aspnet`-рантайме, SDK физически отсутствует — `dotnet run` там не сработает, и это осознанное ограничение, а не недосмотр.

## Разбор

### Разбор 1. Диагностика «You must install .NET»

Приложение падает на новом сервере:

```
You must install or update .NET to run this application.
Framework: 'Microsoft.AspNetCore.App', version '8.0.0' (x64)
```

`dotnet --list-runtimes` на сервере показывает только `Microsoft.NETCore.App 8.0.5`. Что не так и какие есть варианты починить, не трогая код?

> [!success]- Разбор
> На сервере стоит только базовый рантайм, а приложению нужен ASP.NET Core shared framework — отдельный набор сборок (Kestrel, MVC, хостинг), не входящий в `Microsoft.NETCore.App`. Версия `8.0.5` тут ни при чём: roll-forward подбирает версию внутри одного фреймворка, а не подставляет один фреймворк вместо другого.
> Варианты: поставить `aspnetcore-runtime-8.0` (или сменить базовый образ на `mcr.microsoft.com/dotnet/aspnet:8.0`); опубликовать self-contained, чтобы рантайм ехал вместе с приложением; если веб-стек на самом деле не нужен (фоновая служба без Kestrel) — пересмотреть `Sdk` проекта.

### Разбор 2. PR агента с рефлексией и планами на Native AOT

Агент добавил в код регистрацию обработчиков через `Assembly.GetTypes().Where(t => t.Name.EndsWith("Handler"))`, сославшись на то, что «так короче, чем явная регистрация». В roadmap проекта есть пункт про переход части сервисов на Native AOT. Что вернуть на доработку?

> [!success]- Разбор
> Сканирование сборки по имени типа читает метаданные в рантайме и не оставляет статически видимой ссылки на конкретные типы-обработчики. Trimming и Native AOT удаляют код, использование которого не видно на этапе анализа графа зависимостей, — такая регистрация в лучшем случае перестанет находить часть хендлеров только в опубликованном виде, а не в Debug-сборке, что затруднит диагностику. На ревью стоит указать на риск и предложить явную регистрацию (или, для DI-контейнера проекта, обычные модули Autofac) — короче в написании не значит дешевле в поддержке, если ломается только при публикации.

## Итог

- .NET — слои: сборка (IL + метаданные) → BCL → CLR → ОС; SDK — отдельный набор инструментов, нужный только для сборки.
- CLR не интерпретирует IL, а компилирует его JIT-ом; GC — часть CLR, а не библиотеки; верификация и Code Access Security из .NET Framework — устаревшая модель.
- Реальный код BCL — в `System.Private.CoreLib.dll`; остальные `System.*.dll` в shared framework — фасады ради совместимости.
- Компилируешься против ссылочных сборок (`throw null` в телах), исполняешься против shared framework — расхождение версий даёт `MissingMethodException` в рантайме, а не ошибку сборки.
- IL читают не ради экзамена, а чтобы быстро ответить «есть аллокация или нет» — по `box` и `newobj`; для количественной оценки нужен бенчмарк.
- `dotnet` CLI — диспетчер: либо запускает MSBuild/Roslyn из SDK (`build`, `test`, `publish`), либо напрямую передаёт управление хосту CLR (`dotnet app.dll`). В проде нужен только второй путь.
- SDK на проде не нужен вовсе: Docker — всегда многостадийная сборка, `sdk` для публикации, `aspnet`/`runtime` для запуска.
- `global.json` фиксирует версию SDK, `RollForward` в `runtimeconfig.json` — версию рантайма; это разные механизмы с разными наборами значений.
