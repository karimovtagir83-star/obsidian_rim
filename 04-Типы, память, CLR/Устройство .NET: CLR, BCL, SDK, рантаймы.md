# Устройство .NET: CLR, BCL, SDK, рантаймы

> [!abstract] Коротко
> .NET — это не «одна программа», а стопка слоёв: твой код на IL лежит поверх библиотеки классов (BCL), она поверх среды выполнения (CLR), та поверх ОС. Отдельно живёт SDK — набор инструментов для сборки, который на проде не нужен вовсе. Понимание, кто из них что делает и где физически лежит на диске, снимает 90 % вопросов вида «почему в контейнере не запускается» и «какой пакет ставить».

## Зачем это нужно

Три ситуации, в которых это знание окупается в первый же день:

1. **Прод падает с `You must install .NET to run this application`.** Надо мгновенно понимать: не хватает рантайма, а не SDK; какого именно рантайма (`Microsoft.NETCore.App` или `Microsoft.AspNetCore.App`); и почему `rollForward` не спас.
2. **Образ Docker весит 800 МБ.** Потому что в него положили SDK вместо рантайма. Разница — примерно в 4–5 раз.
3. **Собеседование.** «Что такое CLR?» — вопрос-фильтр. Ответ «это виртуальная машина» засчитывается как «не знаю».

Всё, что ниже, — про физическое устройство: какие файлы, какие процессы, в каком порядке.

## Слои: от твоего кода до железа

```
┌─────────────────────────────────────────────────────────────┐
│  ТВОЙ КОД                                                   │
│  MyApi.dll — IL-инструкции + метаданные (не машинный код!)  │
├─────────────────────────────────────────────────────────────┤
│  БИБЛИОТЕКИ                                                 │
│  NuGet: Npgsql.dll, Serilog.dll, ...  (тоже IL)             │
├─────────────────────────────────────────────────────────────┤
│  SHARED FRAMEWORK                                           │
│  Microsoft.AspNetCore.App  — веб-стек                       │
│  Microsoft.NETCore.App     — BCL: System.Runtime,           │
│    System.Collections, System.Text.Json, ...                │
│    и System.Private.CoreLib — «сердце» библиотеки           │
├─────────────────────────────────────────────────────────────┤
│  CLR (CoreCLR)                                              │
│  загрузчик типов │ JIT │ GC │ обработка исключений │        │
│  interop/P-Invoke │ потоки │ verifier                       │
├─────────────────────────────────────────────────────────────┤
│  ХОСТ                                                       │
│  dotnet (muxer) / apphost → hostfxr → hostpolicy            │
├─────────────────────────────────────────────────────────────┤
│  ОПЕРАЦИОННАЯ СИСТЕМА                                       │
│  syscalls, виртуальная память (mmap/VirtualAlloc),          │
│  планировщик потоков, файловая система                      │
├─────────────────────────────────────────────────────────────┤
│  ЖЕЛЕЗО: CPU (x64 / Arm64), RAM, кеши L1–L3                 │
└─────────────────────────────────────────────────────────────┘
```

Ключевая мысль: **компилятор C# не производит машинный код**. `csc` выдаёт сборку с IL и метаданными — см. [[Сборки, метаданные и IL]]. Машинный код появляется уже во время выполнения, силами JIT — см. [[JIT, Tiered Compilation, ReadyToRun, Native AOT]].

## CLR: что именно он делает

CLR (Common Language Runtime) — среда выполнения. Слово «виртуальная машина» тут вводит в заблуждение: CLR не интерпретирует IL (за редкими исключениями вроде Mono-интерпретатора в браузере), а компилирует его в нативный код. Подробнее про разницу подходов — [[Компиляция, интерпретация и виртуальные машины]].

### Загрузчик типов (type loader)

Когда впервые упоминается тип, CLR:

1. Находит сборку, в которой он объявлен (через `AssemblyRef` в метаданных и текущий контекст загрузки — см. [[AssemblyLoadContext и загрузка плагинов]]).
2. Читает `TypeDef`, раскручивает цепочку базовых типов и интерфейсов.
3. Строит в нативной памяти **MethodTable** — служебную структуру: указатель на базовый MethodTable, размер экземпляра, флаги, карту GC-указателей (какие поля объекта являются ссылками), таблицу интерфейсов и массив слотов методов.
4. Раскладывает поля (field layout): по умолчанию `LayoutKind.Auto` — рантайм сам переставляет поля для выравнивания.
5. Прогоняет статический конструктор при первом обращении (см. [[Статические члены, классы и конструкторы]]).

MethodTable — это то, на что указывает каждый объект в куче своим первым словом. Именно поэтому у объекта есть накладной расход в 16 байт на x64 (8 байт указателя на MethodTable + 8 байт заголовка объекта); детали — [[Стек и куча: что где лежит]].

### JIT-компилятор

Слоты MethodTable изначально указывают не на код, а на **стабы**. Первый вызов проходит через стаб, тот дёргает JIT, JIT компилирует IL метода в машинный код и **переписывает слот**, чтобы следующий вызов шёл напрямую. Дальше — многоуровневая компиляция, PGO, девиртуализация; всё это разобрано в [[JIT, Tiered Compilation, ReadyToRun, Native AOT]].

### Сборщик мусора

GC управляет управляемой кучей: выделяет, находит недостижимые объекты, освобождает, компактит. У него есть поколения, регионы, режимы Workstation/Server, DATAS. Целиком — в [[Сборка мусора (GC): как работает]] и [[Поколения GC, LOH и режимы сборщика]]. Здесь важно одно: **GC — часть CLR, а не библиотеки**. Он написан на C++ и живёт в `libclrgc.so`/внутри `libcoreclr.so`, а не в BCL.

### Verifier и type safety

IL-верификатор проверяет, что код типобезопасен: нельзя положить `string` туда, где ждут `int`, нельзя выйти за границы вычислительного стека, нельзя прыгнуть в середину инструкции. Исторически verifier был центральным элементом модели безопасности .NET Framework — непроверенный код просто не запускался в частично доверенной среде.

В .NET (Core и дальше) **полная верификация при загрузке выключена**: она стоила времени старта, а модель «частично доверенного кода внутри процесса» признана нерабочей. Проверки живут в JIT и в самих инструкциях (например, `castclass` бросает `InvalidCastException`, обращение к массиву проверяет границы). Код с `unsafe` типобезопасность нарушает осознанно — см. [[unsafe, указатели и fixed]].

### Безопасность: чего больше нет

Code Access Security (CAS), `AppDomain` как граница безопасности, partial trust, `machine.config` с политиками — всё это #устарело и в современном .NET отсутствует. `AppDomain` формально существует как класс, но домен ровно один на процесс; изоляция плагинов делается через `AssemblyLoadContext`, а изоляция недоверенного кода — через процессы и контейнеры, а не внутри рантайма.

### Что ещё внутри CLR

| Подсистема | За что отвечает |
|---|---|
| Exception handling | Двухпроходная раскрутка стека, фильтры `when`, см. [[Обработка исключений]] |
| Interop | P/Invoke, маршалинг, COM на Windows, см. [[Interop и P-Invoke]] |
| Threading | Управляемые потоки поверх ОС-потоков, ThreadPool, см. [[Thread и ThreadPool]] |
| Reflection | Чтение метаданных в рантайме, см. [[Рефлексия]] |
| Generics | Специализация по value-типам, разделяемый код для ссылочных, см. [[Дженерики в CLR: как устроены]] |
| Stub/дженерик-словари | Виртуальные вызовы, интерфейсная диспетчеризация |

## BCL: как библиотека поделена на сборки

**BCL** (Base Class Library) — базовая библиотека: `System.Object`, коллекции, строки, ввод-вывод, LINQ, потоки. Термин **FCL** (Framework Class Library) — из времён .NET Framework, там он охватывал и WinForms/ASP.NET/WCF; сейчас его почти не используют, кроме как в старых книгах.

Физически всё интересное лежит в одной сборке:

- **`System.Private.CoreLib.dll`** — реальная реализация. Здесь `Object`, `String`, `Array`, `Int32`, `Exception`, `Span<T>`, GC-интринсики. Эта сборка особая: она загружается первой, JIT знает её типы «в лицо», и часть её методов — интринсики, у которых IL-тело подменяется на машинные инструкции. Ссылаться на неё напрямую из кода нельзя, компилятор её не видит.
- **`System.Runtime.dll`, `System.Collections.dll`, `System.Linq.dll` и ещё сотня** — в `shared/Microsoft.NETCore.App` это в основном **фасады** (type forwarders): `[assembly: TypeForwardedTo(typeof(System.String))]`. Они существуют, чтобы старые сборки, скомпилированные против `mscorlib` или против `System.Runtime`, продолжали находить типы.

Зачем такая раздвоенность? Исторически .NET Core разбили библиотеку на мелкие NuGet-пакеты («la carte»), чтобы можно было ставить только нужное. Идея не взлетела: версионный ад и медленный restore. В .NET Core 3.0 вернулись к монолитному shared framework, а фасады остались ради совместимости.

### Ссылочные сборки против реализации

При компиляции ты ссылаешься **не** на те DLL, которые будут исполняться.

| | Ссылочная сборка (reference assembly) | Сборка реализации |
|---|---|---|
| Где | `packs/Microsoft.NETCore.App.Ref/10.0.x/ref/net10.0/` | `shared/Microsoft.NETCore.App/10.0.x/` |
| Что внутри | Только метаданные: сигнатуры публичных и защищённых членов | Полный IL |
| Тела методов | `throw null;` — заглушка, чтобы IL был валиден | Настоящий код |
| Кто использует | Компилятор Roslyn | CLR в рантайме |
| Размер | Единицы мегабайт на весь фреймворк | Десятки мегабайт |

Отсюда классическое расхождение: код скомпилировался, а в рантайме `MissingMethodException` — значит, ссылочная сборка (targeting pack) новее, чем рантайм на машине. Подробнее про механику ссылочных сборок — в [[Сборки, метаданные и IL]].

## SDK, рантайм, shared framework, targeting pack

Четыре сущности, которые постоянно путают.

| Сущность | Что это | Нужно для сборки | Нужно в проде |
|---|---|---|---|
| **SDK** | MSBuild, Roslyn, `dotnet` CLI, шаблоны, NuGet-клиент | Да | Нет |
| **Targeting pack** (`.Ref`) | Ссылочные сборки для конкретного TFM | Да | Нет |
| **Shared framework** (рантайм) | CoreCLR + BCL реального исполнения | Нет | Да (для framework-dependent) |
| **Runtime pack** | Рантайм в виде NuGet-пакета для self-contained/AOT публикации | Только при publish | Нет |

Что ставят пакеты дистрибутива:

| Пакет | Что кладёт | Кому |
|---|---|---|
| `dotnet-sdk-10.0` | SDK + оба рантайма + targeting packs | Разработчику, CI |
| `aspnetcore-runtime-10.0` | `Microsoft.AspNetCore.App` + `Microsoft.NETCore.App` | Проду с веб-приложением |
| `dotnet-runtime-10.0` | Только `Microsoft.NETCore.App` | Проду с консольной службой |

SDK включает рантайм — обратное неверно. Отсюда правило для Docker: собирать в `sdk`-образе, запускать в `aspnet`-образе. См. [[Docker: образы для .NET]].

### Раскладка на диске

Linux (пакетная установка):

```
/usr/share/dotnet/
├── dotnet                                     ← muxer, ~100 КБ, точка входа
├── host/
│   └── fxr/
│       └── 10.0.3/
│           └── libhostfxr.so                  ← поиск и выбор рантайма
├── sdk/
│   └── 10.0.100/                              ← MSBuild, Roslyn, шаблоны (~350 МБ)
├── shared/
│   ├── Microsoft.NETCore.App/
│   │   ├── 10.0.2/
│   │   └── 10.0.3/                            ← BCL + libcoreclr.so + libclrjit.so
│   └── Microsoft.AspNetCore.App/
│       └── 10.0.3/                            ← Kestrel, MVC, DI-хостинг
├── packs/
│   ├── Microsoft.NETCore.App.Ref/10.0.3/      ← ссылочные сборки
│   ├── Microsoft.NETCore.App.Host.linux-x64/  ← шаблон apphost
│   └── Microsoft.AspNetCore.App.Ref/10.0.3/
└── templates/
```

Windows — `C:\Program Files\dotnet\` с той же структурой. Переменная `DOTNET_ROOT` указывает, где искать, если каталог нестандартный.

Проверить, что реально стоит:

```bash
dotnet --info                 # всё сразу: SDK, рантаймы, RID, пути
dotnet --list-runtimes        # только рантаймы
dotnet --list-sdks            # только SDK
```

## Хост: что происходит при запуске

Опубликованное framework-dependent приложение — это папка примерно такого вида:

```
publish/
├── MyApi                      ← apphost: нативный exe, ~70 КБ, без IL
├── MyApi.dll                  ← твой код (IL)
├── MyApi.runtimeconfig.json   ← какой рантайм нужен
├── MyApi.deps.json            ← полный граф зависимостей
├── MyApi.pdb                  ← отладочные символы
└── Npgsql.dll, ...            ← NuGet-зависимости
```

`MyApi.runtimeconfig.json`:

```json
{
  "runtimeOptions": {
    "tfm": "net10.0",
    "frameworks": [
      { "name": "Microsoft.AspNetCore.App", "version": "10.0.0" }
    ],
    "rollForward": "Minor",
    "configProperties": {
      "System.GC.Server": true,
      "System.Runtime.TieredPGO": true
    }
  }
}
```

Цепочка запуска:

```
  ./MyApi                          или        dotnet MyApi.dll
      │                                            │
      │ apphost: внутри бинаря зашита              │ muxer: тот же код,
      │ строка "MyApi.dll" рядом с собой           │ но путь берёт из argv
      └──────────────────┬─────────────────────────┘
                         ▼
              ┌──────────────────────┐
              │  libhostfxr.so       │  «где взять рантайм?»
              └──────────────────────┘
                 1. читает MyApi.runtimeconfig.json
                 2. видит: нужен Microsoft.AspNetCore.App 10.0.0,
                    rollForward = Minor
                 3. сканирует /usr/share/dotnet/shared/
                 4. кандидаты: 10.0.2, 10.0.3 → берёт 10.0.3
                    (в пределах выбранной minor всегда последний патч)
                 5. если ничего не подошло — печатает
                    "You must install .NET to run this application"
                         │
                         ▼
              ┌──────────────────────┐
              │  libhostpolicy.so    │  «какие файлы грузить?»
              └──────────────────────┘
                 6. читает MyApi.deps.json + deps.json фреймворка
                 7. строит TPA-список (Trusted Platform Assemblies) —
                    плоский список абсолютных путей ко всем управляемым DLL
                 8. вычисляет пути поиска нативных библиотек
                         │
                         ▼
              ┌──────────────────────┐
              │  libcoreclr.so       │  собственно рантайм
              └──────────────────────┘
                 9. coreclr_initialize: GC-куча, ThreadPool,
                    единственный AppDomain, загрузка
                    System.Private.CoreLib
                10. загружает MyApi.dll, находит в метаданных
                    .entrypoint (метод Main)
                11. JIT компилирует Main (tier0) → передаёт управление
                         │
                         ▼
                    твой код исполняется
```

Разделение hostfxr/hostpolicy нужно для side-by-side: hostfxr один на машину и умеет работать с любыми версиями рантайма, hostpolicy идёт из конкретной версии фреймворка.

### Roll-forward: как выбирается версия

Приложение просит `10.0.0`, а на машине стоит `10.0.3`. Запустится ли? Да — по умолчанию.

| `rollForward` | Поведение |
|---|---|
| `Minor` | **По умолчанию.** Точная major, minor не ниже запрошенной, внутри — последний патч |
| `LatestPatch` | Та же major.minor, последний патч. Вверх по minor не идёт |
| `Major` | Разрешает подняться на следующую major (10 → 11) |
| `LatestMinor` | Всегда берёт самую свежую minor в пределах major |
| `LatestMajor` | Самая свежая версия вообще |
| `Disable` | Только точное совпадение. Для воспроизводимости в жёстко контролируемой среде |

Задаётся в `.csproj` (`<RollForward>LatestMinor</RollForward>`), ключом `dotnet MyApi.dll --roll-forward Major` или переменной `DOTNET_ROLL_FORWARD`. Приоритет: CLI > переменная окружения > runtimeconfig.

**`global.json` — это про другое.** Он фиксирует версию **SDK**, а не рантайма, и действует на каталог с проектом и все вложенные:

```json
{
  "sdk": {
    "version": "10.0.100",
    "rollForward": "latestFeature",
    "allowPrerelease": false
  }
}
```

Значения `rollForward` здесь свои: `patch`, `feature`, `latestPatch`, `latestFeature`, `latestMinor`, `latestMajor`, `disable`. Файл ищется вверх по дереву каталогов от текущего. Классическая боль: разработчик поставил preview-SDK, CI собирает стабильным — расходятся генераторы и анализаторы. Лечится `global.json` в корне репозитория.

## Framework-dependent или self-contained

| | Framework-dependent (FDD) | Self-contained (SCD) |
|---|---|---|
| Команда | `dotnet publish` | `dotnet publish -r linux-x64 --self-contained` |
| Размер каталога | Единицы МБ | Десятки МБ (с trimming меньше) |
| Нужен рантайм на машине | Да | Нет |
| Патчи безопасности рантайма | Прилетают с обновлением ОС/пакета | Надо пересобирать и передеплоивать |
| Кроссплатформенность артефакта | Да (один и тот же вывод) | Нет, привязан к RID |
| Типичный сценарий | Docker-образ на базе `aspnet`, серверы под контролем | Утилита для пользователя, изолированный стенд |

Отдельный случай — `PublishSingleFile`: всё складывается в один исполняемый файл, который при старте распаковывает или мапит содержимое. Это про упаковку, не про модель исполнения. Native AOT — третий вариант, там рантайм линкуется статически и IL в артефакте не остаётся вовсе; см. [[JIT, Tiered Compilation, ReadyToRun, Native AOT]] и [[Native AOT: когда стоит]].

## Рантаймы: CoreCLR, Mono, Native AOT

Под зонтиком «.NET» живёт больше одного рантайма.

| | **CoreCLR** | **Mono** | **Native AOT** |
|---|---|---|---|
| Модель исполнения | JIT (+ R2R как разогрев) | JIT, интерпретатор, AOT — в зависимости от платформы | AOT целиком на этапе публикации |
| Где применяется | Серверы, десктоп, CLI — 95 % backend-кода | Blazor WebAssembly, iOS/Android, Unity (форк) | CLI, serverless, контейнеры |
| Время старта | Десятки–сотни мс | В браузере хуже (загрузка WASM) | Единицы–десятки мс |
| Пиковая производительность | Наивысшая (tier1 + Dynamic PGO) | Ниже CoreCLR | Близко к tier1, но без PGO-переоптимизации |
| Размер артефакта | Средний (FDD — мал, SCD — десятки МБ) | Зависит от платформы | Единицы–десятки МБ, всё включено |
| Рефлексия | Полная | Полная (с оговорками при full AOT на iOS) | Ограниченная: только то, что сохранил трим |
| `Assembly.Load`, `Reflection.Emit` | Да | Emit не везде | Нет |
| GC | Полноценный поколенческий, регионы, Server/DATAS | SGen | Тот же GC, что в CoreCLR |
| Динамические плагины | Да, через `AssemblyLoadContext` | Да | Нет |

Важно: **Native AOT — не «третий рантайм» в классическом смысле**. Там нет JIT и нет загрузчика сборок, но есть GC, обработка исключений, потоки и вся BCL, вкомпилированная в бинарь. Правильнее говорить «альтернативная модель исполнения на базе того же кода рантайма».

Исторические имена, которые встретятся в старых статьях и которые больше не существуют как отдельные продукты:

- **.NET Native** — AOT для UWP-приложений (2015). #устарело
- **CoreRT** — исследовательский проект, прямой предок Native AOT. #устарело
- **NGen** — Native Image Generator в .NET Framework, прекомпиляция сборок в машинный код в GAC. Идейный предок ReadyToRun. #устарело

## ECMA-335, CTS, CLS

**ECMA-335 (Common Language Infrastructure, CLI)** — международный стандарт, описывающий: формат метаданных, набор IL-инструкций, систему типов и требования к среде исполнения. Именно он делает возможным существование Mono и других реализаций. Отдельно стандартизован язык C# — ECMA-334.

Три аббревиатуры, которые спрашивают на собеседовании:

- **CTS (Common Type System)** — единая система типов: что такое класс, структура, интерфейс, делегат, перечисление; что все типы наследуются от `System.Object`; что value-типы наследуются от `System.ValueType`. Это то, что рантайм понимает и умеет проверять. См. [[Value types vs Reference types]].
- **CLS (Common Language Specification)** — подмножество CTS, на которое договорились языки, чтобы гарантированно понимать друг друга. Примеры правил CLS: публичные имена не должны различаться только регистром; `uint`/`ulong`/`sbyte` нельзя в публичном API; нельзя перегрузку только по `ref`/`out`. Проверяется атрибутом `[assembly: CLSCompliant(true)]`.
- **CIL / IL / MSIL** — три названия одного и того же промежуточного языка. MSIL — самое старое, из документации Microsoft; CIL — как в стандарте; IL — как говорят в жизни.

## Код

Узнать, где именно исполняется процесс:

```csharp
using System.Reflection;
using System.Runtime.InteropServices;

// "10.0.3" — версия рантайма, а не SDK и не TFM
Console.WriteLine($"Environment.Version : {Environment.Version}");

// ".NET 10.0.3" — человекочитаемое описание
Console.WriteLine($"FrameworkDescription: {RuntimeInformation.FrameworkDescription}");

// RID процесса, например "linux-x64" или "win-arm64"
Console.WriteLine($"RuntimeIdentifier   : {RuntimeInformation.RuntimeIdentifier}");

// Каталог shared framework: /usr/share/dotnet/shared/Microsoft.NETCore.App/10.0.3
Console.WriteLine($"Runtime dir         : {RuntimeEnvironment.GetRuntimeDirectory()}");

// Каталог с ЕГО собственными dll — не путать с Environment.CurrentDirectory
Console.WriteLine($"AppContext.BaseDir  : {AppContext.BaseDirectory}");

// Где реально живёт System.Object
Console.WriteLine($"CoreLib             : {typeof(object).Assembly.Location}");
//  → /usr/share/dotnet/shared/Microsoft.NETCore.App/10.0.3/System.Private.CoreLib.dll

// А вот TFM, под который компилировали, — это метаданные сборки
var tfm = Assembly.GetEntryAssembly()!
    .GetCustomAttribute<System.Runtime.Versioning.TargetFrameworkAttribute>()!
    .FrameworkName;
Console.WriteLine($"TargetFramework     : {tfm}");   // ".NETCoreApp,Version=v10.0"
```

Обрати внимание: `AppContext.BaseDirectory` — правильный способ найти файлы рядом с приложением. `Environment.CurrentDirectory` зависит от того, из какого каталога запустили, и в systemd-юните это будет `/`.

Что положить в `.csproj`, чтобы управлять хостом:

```xml
<Project Sdk="Microsoft.NET.Sdk.Web">
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>

    <!-- Политика выбора рантайма: строже, чем дефолтный Minor -->
    <RollForward>LatestPatch</RollForward>

    <!-- Не генерировать нативный apphost: запуск только через `dotnet MyApi.dll`.
         Экономит ~70 КБ и упрощает кросс-сборку -->
    <UseAppHost>false</UseAppHost>

    <!-- Инварианты: без ICU. Уменьшает образ, но ломает культурное
         сравнение строк — включать осознанно -->
    <InvariantGlobalization>true</InvariantGlobalization>

    <!-- Эти два попадут в runtimeconfig.json как configProperties -->
    <ServerGarbageCollection>true</ServerGarbageCollection>
    <ConcurrentGarbageCollection>true</ConcurrentGarbageCollection>
  </PropertyGroup>
</Project>
```

Прочитать реально применённые настройки рантайма из кода:

```csharp
// Что рантайм на самом деле применил — не то, что ты просил, а что вышло
foreach (var (key, value) in GC.GetConfigurationVariables().OrderBy(kv => kv.Key))
    Console.WriteLine($"{key,-32} = {value}");
// GCHeapHardLimit, GCHeapCount, gcServer, gcConcurrent, GCDynamicAdaptationMode ...
```

Проверка версии перед стартом в контейнере (типичный healthcheck на этапе сборки образа):

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish MyApi/MyApi.csproj -c Release -o /app

# Рантайм-образ: ~110 МБ против ~800 МБ у sdk
FROM mcr.microsoft.com/dotnet/aspnet:10.0
WORKDIR /app
COPY --from=build /app .
ENTRYPOINT ["dotnet", "MyApi.dll"]
```

> [!warning] Подводные камни
> **1. SDK в проде.** `mcr.microsoft.com/dotnet/sdk` весит примерно в 6–7 раз больше `aspnet`-образа и тащит компилятор, MSBuild и NuGet-клиент. Это и лишние гигабайты в реестре, и лишняя поверхность атаки: если кто-то получит выполнение команд, у него будет полноценный тулчейн. Всегда многостадийная сборка.
>
> **2. `Environment.Version` не равно версии .NET Framework.** В .NET Framework 4.8 этот же вызов возвращал `4.0.30319.42000` — версию CLR, а не продукта. В современном .NET он честно возвращает версию рантайма (`10.0.3`). Код, который парсит `Environment.Version` для определения «какой .NET», в 99 % случаев сломан; используй `RuntimeInformation.FrameworkDescription`.
>
> **3. `rollForward: Disable` в контейнере.** Кажется хорошей идеей «зафиксировать всё». На практике: вышел патч безопасности, базовый образ обновился с `10.0.3` на `10.0.4`, приложение просит ровно `10.0.3` — и не стартует. `Disable` уместен только там, где ты контролируешь и артефакт, и машину, и обновления.
>
> **4. Смешивание targeting pack и рантайма разных версий.** Собрали на CI с SDK 10.0.200 (targeting pack 10.0.4), задеплоили на хост с рантаймом 10.0.1. Компилятор разрешил новый API, рантайма с ним нет — `MissingMethodException` в момент первого вызова, а не при старте. Ловится только интеграционным прогоном на том же образе, что и прод.
>
> **5. `InvariantGlobalization=true` ради размера образа.** Убирает зависимость от ICU, экономит десятки мегабайт — и молча меняет поведение `string.Compare`, `ToUpper` для турецкого `i`, парсинг дат по культуре. В API, который принимает пользовательский ввод на разных языках, это баг, который найдут пользователи, а не тесты. Подробнее — [[Строки и работа с текстом]].

> [!example] Как делают в бою
> **Фиксация SDK.** В корне репозитория лежит `global.json` с `rollForward: latestFeature`. Это гарантирует, что локально и на CI берётся один и тот же feature-band SDK, а патчи прилетают свободно. Без него достаточно одному разработчику поставить preview, чтобы билд на CI начал вести себя иначе.
>
> **Один base image на всю организацию.** Внутренний образ на базе `mcr.microsoft.com/dotnet/aspnet:10.0` с добавленным CA-бандлом, non-root пользователем и `DOTNET_gcServer=1`. Обновляется централизованно при выходе патчей рантайма — команды не думают о версиях.
>
> **Диагностика «не запускается» в три шага.** `dotnet --list-runtimes` на хосте → сравнить с `frameworks` в `runtimeconfig.json` приложения → если совпадает, включить `DOTNET_MULTILEVEL_LOOKUP`-независимый трейс хоста через `COREHOST_TRACE=1 COREHOST_TRACEFILE=host.log ./MyApi`. Последнее печатает пошагово, где hostfxr искал рантайм и почему отверг кандидатов. Это единственный надёжный способ разобраться с чужим окружением.
>
> **Self-contained для внутренних CLI-утилит.** Скрипты для админов и миграций публикуют self-contained: у человека на машине может не быть .NET вообще, а объяснять «поставьте рантайм» дороже, чем отдать 30 МБ. Для serverless-функций — Native AOT, см. [[Native AOT: когда стоит]].

## Вопросы с собеседований

> [!question]- Что такое CLR и что конкретно он делает?
> CLR (Common Language Runtime) — среда выполнения .NET, реализация стандарта ECMA-335. Её основные подсистемы: загрузчик типов (читает метаданные сборки, строит MethodTable, раскладывает поля), JIT-компилятор (превращает IL в машинный код при первом вызове метода), сборщик мусора (управляет управляемой кучей), механизм обработки исключений с двухпроходной раскруткой стека, поддержка потоков и interop с нативным кодом. Называть CLR «виртуальной машиной» неточно: IL не интерпретируется, а компилируется в нативный код. Физически это `libcoreclr.so` (или `coreclr.dll`) внутри shared framework.

> [!question]- В чём разница между SDK и рантаймом? Что ставить на прод-сервер?
> SDK — набор инструментов для разработки: компилятор Roslyn, MSBuild, `dotnet` CLI, шаблоны, NuGet-клиент, ссылочные сборки. Рантайм — CLR плюс BCL, то, что нужно для исполнения уже скомпилированного приложения. SDK включает в себя рантайм, обратное неверно. На прод ставится только рантайм: `aspnetcore-runtime` для веб-приложений (он тянет за собой и базовый `dotnet-runtime`), `dotnet-runtime` для консольных служб. В Docker это выражается многостадийной сборкой: `sdk`-образ для `dotnet publish`, `aspnet`-образ для запуска.

> [!question]- Что такое shared framework и чем он отличается от NuGet-пакета?
> Shared framework — набор сборок, установленный в системе один раз и разделяемый всеми приложениями (`/usr/share/dotnet/shared/Microsoft.NETCore.App/10.0.3`). Приложение ссылается на него декларативно через `frameworks` в `runtimeconfig.json`, а не тащит копии файлов в свой каталог публикации. NuGet-пакеты, наоборот, копируются в вывод публикации у каждого приложения свои. Плюс shared framework — обновления безопасности прилетают всем сразу без пересборки; минус — приложение зависит от того, что стоит на машине. В .NET 10 SDK ещё и вырезает из `deps.json` транзитивные пакеты, которые уже есть во фреймворке (`RestoreEnablePackagePruning`), — см. [[NuGet: пакеты, версии, транзитивные зависимости]].

> [!question]- Приложение собрано под .NET 10.0.0, на сервере стоит 10.0.5. Запустится?
> Да. По умолчанию действует политика `rollForward: Minor`: рантайм обязан иметь ту же major-версию, minor не ниже запрошенной, и в пределах выбранной minor всегда берётся последний доступный патч. То есть 10.0.0 → 10.0.5 — штатная ситуация, ради неё политика и сделана. Не запустится в обратном случае (собрано под 10.0.5, стоит 10.0.0) и при `rollForward: Disable`, который требует точного совпадения. Перейти с 10.x на 11.x автоматически нельзя — для этого нужен явный `Major` или `LatestMajor`.

> [!question]- Что такое ссылочные сборки и зачем они нужны, если есть настоящие?
> Ссылочные сборки (reference assemblies) содержат только метаданные — сигнатуры публичных и защищённых членов, — а тела всех методов заменены на `throw null`. Они лежат в targeting pack (`packs/Microsoft.NETCore.App.Ref`) и используются компилятором. Смысл в трёх вещах: компилятор не видит внутренностей и не может случайно завязаться на детали реализации; можно компилировать под версию фреймворка, которая на машине не установлена; резко меньше данных для чтения при компиляции. Побочный эффект: если targeting pack новее рантайма на проде, код соберётся, а в рантайме упадёт `MissingMethodException`.

> [!question]- Почему после .NET Core 3.1 сразу .NET 5, без четвёрки?
> Номер 4 занят .NET Framework 4.x, который на момент выпуска (2020) был жив и широко использовался. «.NET 4.0» в логах, в TFM (`net40` уже означал .NET Framework 4.0) и в разговоре было бы неотличимо от Framework. Взяли 5 как первую свободную цифру, которая при этом больше и Framework 4.8, и Core 3.1. Заодно из имени убрали слово «Core»: .NET 5 стал точкой объединения CoreCLR, Mono и Xamarin под одним SDK и одной BCL.

> [!question]- В чём разница между CoreCLR, Mono и Native AOT?
> CoreCLR — основной рантайм: JIT-компиляция, многоуровневая компиляция, Dynamic PGO, полная рефлексия. Используется для серверных и десктопных приложений. Mono — второй рантайм в том же репозитории: он умеет JIT, интерпретацию и полную AOT-компиляцию, применяется там, где CoreCLR неприменим — WebAssembly (Blazor), iOS с запретом на генерацию кода, Android, игровые движки. Native AOT — не отдельный рантайм, а модель публикации: весь код компилируется в нативный бинарь на этапе `dotnet publish`, JIT и загрузчик сборок в артефакте отсутствуют, но GC, обработка исключений и BCL остаются. Цена — отсутствие `Assembly.Load`, `Reflection.Emit` и рефлексии по типам, которые не пережили trimming.

> [!question]- Что такое CTS и CLS?
> CTS (Common Type System) — часть стандарта ECMA-335, описывающая систему типов рантайма: категории типов (классы, структуры, интерфейсы, делегаты, перечисления), единый корень `System.Object`, правила наследования и приведения. Это то, что CLR понимает и умеет проверять. CLS (Common Language Specification) — подмножество CTS, минимальный набор правил, которому должен следовать публичный API сборки, чтобы её мог свободно использовать код на любом .NET-языке: не различать публичные имена только регистром, не выставлять беззнаковые типы наружу, не перегружать методы только по `ref`/`out`. Проверяется атрибутом `[assembly: CLSCompliant(true)]`; на практике сегодня почти не используется, потому что F# и VB.NET в backend-командах редкость.

## Задачи

### Задача 1. Найти, где живёт `System.String`

Не заглядывая в файловую систему вручную, напиши код, который выведет полный путь к файлу, где физически реализован `System.String`, и объяснит, почему это не `System.Runtime.dll`.

> [!success]- Решение
> ```csharp
> using System.Reflection;
>
> var asm = typeof(string).Assembly;
> Console.WriteLine(asm.GetName().Name);   // System.Private.CoreLib
> Console.WriteLine(asm.Location);
> //  /usr/share/dotnet/shared/Microsoft.NETCore.App/10.0.3/System.Private.CoreLib.dll
>
> // А теперь посмотрим, что внутри System.Runtime.dll
> var runtime = Assembly.Load("System.Runtime");
> var stringType = runtime.GetType("System.String", throwOnError: false);
> Console.WriteLine(stringType is null
>     ? "В System.Runtime типа String НЕТ — только type forward"
>     : $"Найден, но объявлен в {stringType.Assembly.GetName().Name}");
> ```
>
> `System.Runtime.dll` в shared framework — фасад: в его метаданных для `System.String` стоит запись `ExportedType` с флагом type forwarder, указывающая на `System.Private.CoreLib`. Компилятор видит тип в ссылочной сборке `System.Runtime` (targeting pack), а рантайм при загрузке идёт по форварду в реальную реализацию. Разделение позволяет менять внутреннее устройство CoreLib, не ломая скомпилированные сборки.

### Задача 2. Диагностика «You must install .NET»

Коллега задеплоил приложение на новый сервер, оно падает при старте:

```
You must install or update .NET to run this application.
App: /opt/myapi/MyApi
Architecture: x64
Framework: 'Microsoft.AspNetCore.App', version '10.0.0' (x64)
```

`dotnet --list-runtimes` на сервере показывает:

```
Microsoft.NETCore.App 10.0.3 [/usr/share/dotnet/shared/Microsoft.NETCore.App]
```

Что не так и какие есть три способа починить?

> [!success]- Решение
> На сервере стоит только базовый рантайм (`dotnet-runtime`), а приложению нужен ASP.NET Core shared framework — это отдельный набор сборок (Kestrel, MVC, хостинг), который в `Microsoft.NETCore.App` не входит. Версия `10.0.3` тут вообще ни при чём: roll-forward не может подставить один фреймворк вместо другого, имя должно совпадать точно.
>
> Три способа:
>
> ```bash
> # 1. Поставить нужный shared framework (правильный вариант в 90 % случаев)
> sudo apt install aspnetcore-runtime-10.0
> # или образ mcr.microsoft.com/dotnet/aspnet:10.0 вместо dotnet/runtime:10.0
> ```
>
> ```xml
> <!-- 2. Публиковать self-contained: рантайм едет вместе с приложением -->
> <PropertyGroup>
>   <RuntimeIdentifier>linux-x64</RuntimeIdentifier>
>   <SelfContained>true</SelfContained>
> </PropertyGroup>
> ```
>
> ```xml
> <!-- 3. Если веб-стек на самом деле не нужен (фоновая служба на IHostedService
>        без Kestrel) — сменить SDK проекта и убрать зависимость от ASP.NET Core -->
> <Project Sdk="Microsoft.NET.Sdk.Worker">
> ```
>
> Диагностировать вслепую помогает `COREHOST_TRACE=1 ./MyApi 2>host.log` — в логе видно все каталоги, где hostfxr искал фреймворк, и по какому критерию отверг найденное.

### Задача 3. Разложить артефакты по слоям

Дана папка публикации framework-dependent веб-API. Для каждого файла скажи, кто его читает: компилятор, хост, CLR или никто из них.

```
MyApi                      MyApi.dll               MyApi.pdb
MyApi.runtimeconfig.json   MyApi.deps.json         Npgsql.dll
MyApi.staticwebassets.endpoints.json               appsettings.json
```

> [!success]- Решение
>
> | Файл | Кто читает | Когда |
> |---|---|---|
> | `MyApi` | ОС (`execve`) | Это apphost — нативный exe, внутри зашито имя `MyApi.dll` |
> | `MyApi.runtimeconfig.json` | **hostfxr** | Сразу после старта: какой фреймворк и какая политика roll-forward |
> | `MyApi.deps.json` | **hostpolicy** | После выбора рантайма: строит TPA-список и пути к нативным библиотекам |
> | `MyApi.dll` | **CLR** | Загружается после инициализации, оттуда берётся `.entrypoint` |
> | `Npgsql.dll` | **CLR** | Лениво, при первом обращении к типу из неё |
> | `MyApi.pdb` | CLR, но только при исключении | Нужен, чтобы в стектрейсе были имена файлов и номера строк |
> | `appsettings.json` | Твой код (`ConfigurationBuilder`) | Ни хост, ни CLR о нём не знают |
> | `*.staticwebassets.endpoints.json` | Твой код (ASP.NET Core) | Опять же обычный файл данных для приложения |
>
> Главное различие: `runtimeconfig.json` и `deps.json` — часть протокола запуска, их формат определяет хост, и опечатка там ломает приложение до того, как выполнится хоть одна строка твоего кода. Компилятор в этом списке не участвует вообще — на этапе публикации его работа уже закончена, он читал ссылочные сборки из targeting pack, которых в папке публикации нет.

## Итог

- CLR — не интерпретатор, а среда выполнения: загрузчик типов, JIT, GC, обработка исключений, interop. Верификация IL и Code Access Security из .NET Framework #устарело и в современном .NET отсутствуют.
- Реальная реализация BCL живёт в `System.Private.CoreLib.dll`; десятки `System.*.dll` в shared framework — фасады с type forwarder'ами ради совместимости.
- Компилируешься против ссылочных сборок из targeting pack (`throw null` в телах), исполняешься против shared framework. Расхождение версий даёт `MissingMethodException` в рантайме, а не ошибку компиляции.
- Запуск идёт по цепочке apphost/muxer → hostfxr (выбирает версию рантайма по `runtimeconfig.json` и roll-forward) → hostpolicy (строит список сборок по `deps.json`) → `libcoreclr.so`.
- SDK нужен только для сборки. На проде — `aspnetcore-runtime` или `dotnet-runtime`; в Docker это всегда многостадийная сборка.
- `global.json` фиксирует версию SDK, `RollForward` — версию рантайма. Это разные механизмы с разными наборами значений.
- Под зонтиком .NET три модели исполнения: CoreCLR (JIT, основной путь), Mono (WASM, мобильные, игры), Native AOT (компиляция в нативный бинарь при публикации). CoreRT, .NET Native, NGen — #устарело.
- Нумерация прыгнула с Core 3.1 на .NET 5, потому что «4» занял .NET Framework 4.x. LTS — нечётные версии, 3 года поддержки; STS — чётные, 18 месяцев.
