# Сборки, метаданные и IL

> [!abstract] Коротко
> Сборка (assembly) — единица развёртывания и версионирования .NET: файл `.dll` или `.exe`, внутри которого лежат три вещи — **IL** (платформенно-независимый байт-код), **метаданные** (полное описание всех типов и членов) и ресурсы. Машинного кода там нет: его создаёт JIT при запуске. Метаданные — то, что делает возможными рефлексию, сериализаторы, DI-контейнеры, отладчики, анализаторы и декомпиляторы: сборка описывает саму себя, и по ней можно восстановить почти исходный код. Уметь читать IL полезно не ради IL, а чтобы отвечать на вопросы «сколько здесь аллокаций», «во что развернулся `foreach`», «что делает `async`».

## Зачем это нужно

Три практических повода.

**Понимать, что происходит.** Вопросы вида «создаёт ли этот код мусор», «упаковывается ли структура», «во что превращается `await`» решаются одним взглядом в IL — а не спорами на ревью.

**Читать чужие библиотеки.** Декомпилятор (ILSpy, встроенный в Rider) показывает реализацию любого NuGet-пакета и самой BCL. Это часто быстрее, чем искать документацию.

**Понимать инструменты.** Анализаторы, source generators, мокинг-фреймворки, ORM, сериализаторы — все они работают с метаданными. Не зная, что там лежит, невозможно понять их ограничения (например, почему Native AOT ломает рефлексию).

## Что внутри сборки

```
MyApp.dll
├── PE-заголовок          — формат исполняемого файла Windows (используется и на Linux/macOS)
├── CLI-заголовок         — «это управляемая сборка», точка входа, флаги
├── Метаданные
│   ├── Manifest          — имя сборки, версия, культура, ссылки на другие сборки
│   ├── Таблицы типов     — TypeDef, MethodDef, FieldDef, PropertyDef, ParamDef…
│   ├── Таблицы ссылок    — AssemblyRef, TypeRef, MemberRef (что мы используем извне)
│   ├── Атрибуты          — все `[Attribute]` из кода
│   └── Строковые кучи    — имена, строковые литералы, подписи, GUID
├── IL-код методов
└── Ресурсы               — встроенные файлы, локализация
```

Ключевое отличие .NET от нативных платформ: **метаданные полные и обязательные**. В нативной библиотеке C++ после компиляции остаются только адреса и (опционально) искажённые имена; в .NET-сборке сохранено всё — иерархия типов, имена параметров, сигнатуры, атрибуты. Именно поэтому декомпиляция .NET даёт читаемый код, а C++ — почти нет.

```csharp
// Посмотреть манифест и содержимое сборки можно из кода
var asm = typeof(Program).Assembly;
Console.WriteLine(asm.FullName);      // MyApp, Version=1.0.0.0, Culture=neutral, PublicKeyToken=null
Console.WriteLine(asm.Location);
foreach (var t in asm.GetTypes()) Console.WriteLine(t.FullName);
foreach (var r in asm.GetReferencedAssemblies()) Console.WriteLine(r.Name);
```

### Имя сборки и версии

Полное имя состоит из четырёх частей: имя, версия, культура, токен публичного ключа. Версий в проекте на самом деле три, и их путают:

```xml
<PropertyGroup>
  <AssemblyVersion>1.0.0.0</AssemblyVersion>   <!-- участвует в идентичности сборки -->
  <FileVersion>1.2.3.456</FileVersion>          <!-- версия файла для ОС, произвольная -->
  <Version>1.2.3-beta.1</Version>               <!-- версия пакета NuGet, семантическая -->
</PropertyGroup>
```

`AssemblyVersion` менять при каждой сборке не стоит: она участвует в разрешении ссылок. Практика — держать её как `1.0.0.0` в пределах мажорной версии, а различать сборки через `FileVersion` и `Version` ([[NuGet: пакеты, версии, транзитивные зависимости]]).

## IL: стековая машина

IL — байт-код абстрактной машины, у которой нет регистров: все операции работают со **стеком вычислений** (evaluation stack). Инструкция забирает операнды со стека и кладёт результат обратно.

```csharp
int Add(int a, int b) => a + b;
```

```
.method public hidebysig instance int32 Add(int32 a, int32 b) cil managed
{
  .maxstack 2
  ldarg.1      // положить на стек аргумент a  → [a]
  ldarg.2      // положить b                   → [a, b]
  add          // снять два, положить сумму    → [a+b]
  ret          // вернуть верх стека
}
```

Обрати внимание на `ldarg.1`, а не `ldarg.0`: у метода экземпляра нулевой аргумент — это `this`.

### Инструкции, которые надо узнавать

| Группа | Инструкции | Что делают |
|---|---|---|
| Загрузка | `ldarg`, `ldloc`, `ldfld`, `ldsfld`, `ldc.i4`, `ldstr`, `ldnull` | положить на стек аргумент, локальную, поле, константу, строку |
| Сохранение | `starg`, `stloc`, `stfld`, `stsfld` | снять со стека и записать |
| Арифметика | `add`, `sub`, `mul`, `div`, `rem`, `and`, `or`, `shl` | над двумя верхними значениями |
| Вызовы | `call`, `callvirt`, `calli` | статический/прямой, виртуальный, по указателю |
| Создание | `newobj`, `newarr`, `initobj` | объект, массив, обнуление структуры |
| Приведение | `box`, `unbox.any`, `castclass`, `isinst`, `conv.i8` | упаковка, распаковка, приведение, проверка типа, конверсия |
| Переходы | `br`, `brtrue`, `brfalse`, `beq`, `blt`, `switch` | безусловный и условные переходы |
| Исключения | `throw`, `rethrow`, `leave`, `endfinally` | работа с блоками `try`/`catch`/`finally` |

Двух инструкций достаточно, чтобы отвечать на большинство вопросов о производительности: **`box`** означает аллокацию в куче, **`newobj`** — создание объекта. Если в IL горячего метода их нет, аллокаций нет.

### Как смотреть IL

- **sharplab.io** — вставил C#, сразу видишь IL, декомпиляцию в «низкоуровневый C#» и даже машинный код. Лучший инструмент для обучения.
- **ILSpy** (кроссплатформенный, есть плагин для VS Code) — декомпиляция готовых сборок.
- **Rider / dotPeek** — встроенный просмотр IL и декомпиляция.
- **`ildasm`** из SDK — классический дизассемблер (`dotnet ildasm` через пакет `Microsoft.NET.ILDAsm`).
- **`dotnet-ildasm`** — глобальный инструмент: `dotnet tool install -g dotnet-ildasm`.

## Что видно в IL: четыре поучительных примера

### 1. Конкатенация строк

```csharp
string s = a + b + c;
// IL: один вызов System.String::Concat(string, string, string) — компилятор объединил
```

Зато в цикле каждый `+=` — отдельный `Concat` с копированием, отсюда квадратичность ([[Строки и работа с текстом]]).

### 2. `foreach` по списку

```csharp
foreach (var x in list) Use(x);
```

В IL видно `List<T>.GetEnumerator()`, возвращающий **структуру**, вызовы `MoveNext`/`get_Current` и `try/finally` с `Dispose`. Если тот же список обходить через `IEnumerable<T>`, появится `box` — перечислитель-структура упакуется ([[Циклы и итерация]]).

### 3. Лямбда с захватом

```csharp
int factor = 3;
Func<int, int> f = x => x * factor;
```

В IL появится `newobj` скрытого класса `<>c__DisplayClass0_0`, запись `factor` в его поле и `newobj Func<int,int>` — две аллокации. Лямбда без захвата вместо этого кешируется в статическом поле ([[Локальные функции и замыкания]]).

### 4. `async`-метод

```csharp
async Task<int> LoadAsync() { await Task.Delay(1); return 42; }
```

В IL от исходного метода остаётся почти ничего: создание структуры-автомата `<LoadAsync>d__0`, вызов `AsyncTaskMethodBuilder.Start`, возврат `Task`. Вся логика переехала в метод `MoveNext` автомата — именно это разбирает [[async и await: как это работает на самом деле]].

## Метаданные и рефлексия

Метаданные организованы в таблицы, а ссылки между ними — это **токены** (4-байтные числа: старший байт — тип таблицы, три младших — индекс строки). `MethodDef` описывает метод в этой сборке, `MemberRef` — метод из чужой. Рефлексия — это API поверх чтения этих таблиц:

```csharp
var method = typeof(string).GetMethod(nameof(string.Concat), [typeof(string), typeof(string)]);
Console.WriteLine(method!.MetadataToken.ToString("X8"));    // токен строки в таблице метаданных
Console.WriteLine(method.GetParameters()[0].Name);          // имена параметров сохранены в метаданных
```

Отсюда важное следствие для современного .NET: **обрезка (trimming) и Native AOT удаляют то, что не видно статически**. Если тип используется только через рефлексию по строковому имени, компоновщик его выбросит, и приложение упадёт в рантайме. Поэтому платформа движется к генераторам исходного кода: `[JsonSerializable]`, `[LoggerMessage]`, `[GeneratedRegex]` делают ту же работу на этапе компиляции ([[Source Generators]], [[Native AOT: когда стоит]]).

### PDB и Source Link

Отладочная информация (соответствие IL-смещений строкам исходника, имена локальных переменных) лежит не в сборке, а в `.pdb`. Варианты: `portable` (по умолчанию, кроссплатформенный), `embedded` (внутрь сборки — удобно для контейнеров).

**Source Link** записывает в PDB ссылку на коммит в репозитории, поэтому отладчик может скачать исходники нужной версии — так работает пошаговая отладка внутрь кода .NET и NuGet-пакетов.

```xml
<PropertyGroup>
  <DebugType>embedded</DebugType>
  <PublishRepositoryUrl>true</PublishRepositoryUrl>
  <EmbedUntrackedSources>true</EmbedUntrackedSources>
</PropertyGroup>
```

## Границы сборки

Сборка — не только единица развёртывания, но и **граница доступа**: `internal` действует внутри сборки. Отсюда два практических приёма:

```xml
<!-- Открыть internal-типы тестовому проекту -->
<ItemGroup>
  <InternalsVisibleTo Include="MyApp.Tests" />
</ItemGroup>
```

```csharp
// Проверить, откуда фактически загружен тип (полезно при конфликтах версий)
Console.WriteLine(typeof(JsonSerializer).Assembly.Location);
```

Одна сборка может содержать много пространств имён, и наоборот — пространство имён может быть размазано по сборкам (так устроена BCL). Настоящие архитектурные границы задаются сборками, а не пространствами имён ([[Namespace, using, глобальные using]], [[Инкапсуляция и модификаторы доступа]]).

> [!warning] Подводные камни
> - **«В `.dll` лежит машинный код».** Нет: там IL и метаданные, машинный код появляется в рантайме (кроме ReadyToRun и Native AOT).
> - **Путаница трёх версий.** `AssemblyVersion` участвует в идентичности сборки, `FileVersion` — информационная, `Version` — версия NuGet-пакета.
> - **Изменение `AssemblyVersion` на каждой сборке.** Ломает разрешение ссылок и провоцирует ошибки загрузки; менять её нужно осознанно.
> - **Рефлексия по строковым именам плюс trimming.** Компоновщик не видит использования и удаляет тип — падение только в опубликованном виде, не в Debug.
> - **Декомпиляция ≠ исходник.** Восстановленный код эквивалентен по поведению, но не совпадает текстуально: `async`, `yield`, лямбды, `foreach` разворачиваются.
> - **Секреты в сборке.** Строковые литералы лежат в метаданных открытым текстом; обфускация от чтения не спасает. Ключи и пароли не должны попадать в код.
> - **`typeof(T).Assembly.Location` в single-file публикации.** Может вернуть пустую строку: сборка не лежит отдельным файлом на диске.

> [!example] Как делают в бою
> IL читают редко, но в конкретных ситуациях он экономит часы. Первая — спор о производительности: вместо аргументов открывают sharplab.io и смотрят, есть ли `box` и `newobj`. Вторая — разбор поведения библиотеки без документации: декомпиляция в Rider или ILSpy показывает реализацию метода за секунды. Третья — понимание того, что сгенерировал компилятор или source generator: `async`-автоматы, замыкания, записи, `[LoggerMessage]`.
> В настройках проектов стандартом стало `DebugType=embedded` плюс Source Link: PDB внутри сборки, исходники подтягиваются из репозитория, поэтому стек в логах читаемый, а отладка контейнера возможна без ручного копирования файлов.
> При переходе на Native AOT первым делом ищут рефлексию по строкам и динамическую загрузку сборок — именно они ломаются после обрезки. Замена — генераторы исходного кода и явная регистрация вместо сканирования сборок.

## Вопросы с собеседований

> [!question]- Что лежит внутри сборки .NET?
> Четыре вещи: PE-заголовок (формат исполняемого файла), CLI-заголовок с признаком управляемой сборки и точкой входа, метаданные и IL-код методов, плюс опционально встроенные ресурсы. Машинного кода в обычной сборке нет — его порождает JIT при первом вызове каждого метода (исключения: ReadyToRun, где предкомпилированный код лежит рядом с IL, и Native AOT, где сборка вообще заменяется нативным исполняемым файлом). Метаданные — самая важная часть: они содержат полное описание всех типов, членов, сигнатур, параметров и атрибутов, организованное в таблицы, на которые ссылаются токены. Именно полнота метаданных делает возможными рефлексию, сериализаторы, DI-контейнеры, отладчики, анализаторы и декомпиляцию в читаемый код.

> [!question]- Что такое IL и почему он стековый?
> IL (Intermediate Language, он же CIL/MSIL) — платформенно-независимый байт-код, в который компилируется C#. Он основан на стеке вычислений: инструкции забирают операнды с вершины стека и кладут результат обратно, регистров в модели нет. Такой выбор упрощает и генерацию кода компилятором (не надо решать задачу распределения регистров, у разных процессоров их разное количество), и верификацию: по стековой модели легко проверить типовую корректность. Отображением на регистры конкретного процессора занимается JIT, у которого есть точная информация о целевой платформе. Побочные выгоды IL — многоязычность (C#, F#, VB компилируются в один байт-код и совместимы между собой) и возможность отложить оптимизацию до момента запуска, когда известны и модель CPU, и профиль исполнения.

> [!question]- Как по IL понять, есть ли в коде лишние аллокации?
> Искать три инструкции. `box` — упаковка значимого типа: аллокация в куче с копированием значения, типична при передаче структуры в `object`, в не-обобщённый интерфейс или в `string.Format`. `newobj` — создание объекта: сюда попадают и явные `new`, и скрытые — класс замыкания для лямбды с захватом, делегат, перечислитель-класс у итераторов. `newarr` — создание массива, в том числе неявное при `params`. Если в IL горячего метода этих инструкций нет, аллокаций в нём тоже нет. Удобнее всего смотреть на sharplab.io: он показывает и IL, и «декомпилированный C#», где видны сгенерированные компилятором классы. Для количественной оценки этого недостаточно — нужен бенчмарк с `MemoryDiagnoser` ([[Как измерять: BenchmarkDotNet]]), но IL отвечает на вопрос «есть или нет» мгновенно.

> [!question]- Чем отличаются AssemblyVersion, FileVersion и версия пакета?
> `AssemblyVersion` записывается в манифест и участвует в идентичности сборки: по ней рантайм разрешает ссылки, и её изменение влияет на загрузку. Поэтому её обычно держат стабильной в пределах мажорной версии (`1.0.0.0`), меняя только при несовместимых изменениях. `FileVersion` — версия файла для операционной системы, произвольная, ни на что в рантайме не влияет; в неё удобно писать номер сборки CI. `Version` (`PackageVersion`) — семантическая версия NuGet-пакета, именно её видят потребители при установке; она может содержать префикс предварительного выпуска (`1.2.3-beta.1`). На практике задают `Version` в одном месте, а `AssemblyVersion` фиксируют отдельно, чтобы каждая сборка CI не создавала новую идентичность.

## Задачи

### Задача 1. Предсказать IL

Сколько аллокаций сделает каждый фрагмент?

```csharp
// A
int x = 5;
object o = x;

// B
Func<int,int> f = v => v * 2;

// C
int factor = 3;
Func<int,int> g = v => v * factor;

// D
string s = "a" + "b";
```

> [!success]- Решение
> **A — одна.** Инструкция `box`: значение `int` копируется в новый объект в куче.
> **B — ноль** (после первого вызова). Лямбда без захвата компилируется в статический метод, а созданный делегат кешируется в статическом поле сгенерированного класса — при повторных проходах `newobj` не выполняется.
> **C — две.** `newobj` класса замыкания (`<>c__DisplayClass`) для хранения `factor` плюс `newobj` делегата, ссылающегося на метод этого класса. И делегат уже не кешируется: он привязан к конкретному экземпляру замыкания.
> **D — ноль.** Оба операнда — константы, компилятор выполняет свёртку и кладёт в IL готовый литерал `"ab"` через `ldstr`; строковые литералы к тому же интернируются.
> Проверить всё это можно за минуту на sharplab.io — и это лучший способ закрепить понимание.

### Задача 2. Разобраться, откуда загружен тип

В проде появляется `MissingMethodException` на методе, который точно есть в исходниках. Как выяснить причину?

> [!success]- Решение
> Симптом типичен для конфликта версий сборок: код скомпилирован против одной версии библиотеки, а в рантайме загружена другая, где метода нет или изменилась сигнатура. Порядок диагностики:
> ```csharp
> var asm = typeof(SomeType).Assembly;
> Console.WriteLine(asm.FullName);    // фактическая версия
> Console.WriteLine(asm.Location);    // откуда физически загружена
> foreach (var r in typeof(Program).Assembly.GetReferencedAssemblies())
>     Console.WriteLine($"{r.Name} {r.Version}");   // на что ссылались при компиляции
> ```
> Дальше сравнивают ожидаемую и фактическую версии. Частые причины: транзитивная зависимость подтянула другую версию (проверяется `dotnet list package --include-transitive`), в папке публикации осталась старая `.dll` от предыдущего деплоя, или один и тот же пакет пришёл из двух источников. Лечение — единая версия через `Directory.Packages.props` с централизованным управлением версиями и чистая публикация. Подробнее о разрешении версий — [[NuGet: пакеты, версии, транзитивные зависимости]].

## Итог

- Сборка = IL + метаданные + ресурсы; машинный код появляется в рантайме силами JIT.
- Метаданные полны: типы, члены, сигнатуры, имена параметров, атрибуты — отсюда рефлексия и читаемая декомпиляция.
- IL — стековый байт-код без регистров; распределением регистров занимается JIT.
- Ключевые инструкции для оценки аллокаций: `box`, `newobj`, `newarr`.
- В IL видно то, что скрывает синтаксис: разворачивание `foreach`, классы замыканий, автоматы `async`.
- Версий три: `AssemblyVersion` (идентичность), `FileVersion` (информационная), `Version` (пакет NuGet).
- PDB хранит отладочную информацию; `embedded` плюс Source Link делают отладку и стеки удобными.
- Сборка — граница `internal` и настоящая архитектурная граница, в отличие от пространства имён.
