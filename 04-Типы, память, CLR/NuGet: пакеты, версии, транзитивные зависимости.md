# NuGet: пакеты, версии, транзитивные зависимости

> [!abstract] Коротко
> NuGet-пакет — это архив со сборками под разные целевые платформы, метаданными и списком собственных зависимостей. Ссылки описываются элементом `PackageReference` в файле проекта, а при восстановлении NuGet строит **полный граф зависимостей**, включая транзитивные (зависимости зависимостей). Два правила разрешения версий надо знать наизусть: при конфликте выигрывает **ближайшая** ссылка в графе, а при указании диапазона берётся **минимальная подходящая** версия. Отсюда практика зрелых проектов: централизованное управление версиями (`Directory.Packages.props`), файл блокировки для воспроизводимости и регулярная проверка на уязвимости.

## Зачем это нужно

Пакеты — это чужой код, который выполняется в твоём процессе. Три класса проблем, которые от этого возникают:

- **Конфликты версий.** Две библиотеки требуют разные версии третьей — приложение собирается, но падает в рантайме с `MissingMethodException` ([[Сборки, метаданные и IL]]).
- **Уязвимости и лицензии.** Транзитивная зависимость с известной уязвимостью попадает в прод; библиотека меняет лицензию на коммерческую при обновлении мажорной версии.
- **Невоспроизводимая сборка.** Локально собирается одно, в CI — другое, потому что диапазон версий подтянул новый патч.

## Как устроен пакет

```
Serilog.4.1.0.nupkg (обычный zip)
├── Serilog.nuspec              метаданные: id, версия, авторы, лицензия, зависимости
├── lib/
│   ├── net8.0/Serilog.dll      сборка под .NET 8
│   ├── net9.0/Serilog.dll
│   └── netstandard2.0/…        для совместимости со старыми платформами
├── build/                       props/targets, вливаемые в сборку потребителя
├── runtimes/                    нативные библиотеки под конкретные RID
└── README.md, icon.png
```

При восстановлении NuGet выбирает папку `lib/<tfm>`, наиболее подходящую целевой платформе проекта ([[Target Framework Moniker и мультитаргетинг]]). Пакеты кешируются глобально в `~/.nuget/packages` — поэтому вторая сборка того же проекта не ходит в сеть.

```bash
dotnet nuget locals all --list      # где лежит кеш
dotnet nuget locals all --clear     # очистить (иногда лечит странности восстановления)
```

## PackageReference

```xml
<ItemGroup>
  <PackageReference Include="Serilog.AspNetCore" Version="9.0.0" />
  <PackageReference Include="Npgsql.EntityFrameworkCore.PostgreSQL" Version="10.0.0" />

  <!-- Только на этапе сборки: анализаторы, генераторы -->
  <PackageReference Include="Roslynator.Analyzers" Version="4.13.1">
    <PrivateAssets>all</PrivateAssets>
    <IncludeAssets>runtime; build; native; contentfiles; analyzers</IncludeAssets>
  </PackageReference>
</ItemGroup>
```

`PrivateAssets="all"` означает «эта зависимость не передаётся дальше»: если проект упакуют, потребитель её не получит. Так помечают анализаторы, генераторы и инструменты сборки.

Старый формат `packages.config` встречается только в легаси на .NET Framework: там ссылки хранились отдельным файлом, транзитивные зависимости записывались в проект явно и постоянно расходились. `PackageReference` решает это, вычисляя граф при восстановлении.

## Версии и SemVer

Семантическое версионирование: `МАЖОР.МИНОР.ПАТЧ[-предрелиз][+метаданные]`.

| Часть | Когда увеличивается |
|---|---|
| МАЖОР | ломающие изменения API |
| МИНОР | новая функциональность, совместимая назад |
| ПАТЧ | исправления без изменения API |
| предрелиз | `-beta.1`, `-rc.2` — версия ниже соответствующей стабильной |

```xml
<PackageReference Include="X" Version="9.0.0" />       <!-- «не ниже 9.0.0» -->
<PackageReference Include="X" Version="[9.0.0]" />      <!-- ровно 9.0.0 -->
<PackageReference Include="X" Version="[9.0.0,10.0.0)" /><!-- от 9.0.0 включительно до 10.0.0 -->
<PackageReference Include="X" Version="9.*" />          <!-- плавающая: последняя 9.x -->
```

Важная тонкость: **`Version="9.0.0"` — это не «ровно 9.0.0», а минимально допустимая версия**. Если граф потребует 9.2.0, будет взята она. Точное закрепление — квадратные скобки.

Плавающие версии (`9.*`) удобны локально и вредны в CI: сборка перестаёт быть воспроизводимой, и обновление зависимости приходит без единого изменения в коде.

## Транзитивные зависимости и разрешение конфликтов

```
MyApp
├── LibA 1.0        →  Newtonsoft.Json 12.0.0
└── LibB 2.0        →  Newtonsoft.Json 13.0.1
                        ↓
   NuGet выберет одну версию для всего графа
```

Правила, по которым выбирается версия:

1. **Ближайшая побеждает** (nearest wins). Прямая ссылка в твоём проекте перекрывает любые транзитивные требования — это способ разрешить конфликт вручную.
2. **Минимальная подходящая** (lowest applicable). Из требований `>= 12.0.0` и `>= 13.0.1` берётся 13.0.1 — наименьшая версия, удовлетворяющая всем.
3. При несовместимых требованиях (`[12.0.0]` и `[13.0.1]`) восстановление завершается ошибкой NU1107 — это лучше, чем тихое несоответствие.

```bash
dotnet list package --include-transitive     # весь граф
dotnet nuget why MyApp Newtonsoft.Json       # ПОЧЕМУ пакет попал в проект (.NET 8+)
```

`dotnet nuget why` — самая полезная команда при разборе «откуда это взялось»: она печатает цепочку от твоего проекта до транзитивного пакета.

Если нужная версия не подтягивается сама, её закрепляют прямой ссылкой:

```xml
<!-- Транзитивная уязвимая версия перекрывается явной прямой ссылкой -->
<PackageReference Include="System.Text.Json" Version="10.0.0" />
```

## Централизованное управление версиями

В решении из десяти проектов версии расползаются: один проект на EF Core 10.0.0, другой на 10.0.1. Лечится централизацией:

```xml
<!-- Directory.Packages.props в корне решения -->
<Project>
  <PropertyGroup>
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
    <CentralPackageTransitivePinningEnabled>true</CentralPackageTransitivePinningEnabled>
  </PropertyGroup>

  <ItemGroup>
    <PackageVersion Include="Serilog.AspNetCore" Version="9.0.0" />
    <PackageVersion Include="Npgsql.EntityFrameworkCore.PostgreSQL" Version="10.0.0" />
    <PackageVersion Include="xunit" Version="2.9.3" />
  </ItemGroup>
</Project>
```

```xml
<!-- В проекте версия больше не указывается -->
<PackageReference Include="Serilog.AspNetCore" />
```

`CentralPackageTransitivePinningEnabled` дополнительно закрепляет транзитивные пакеты: указав версию в центральном файле, ты фиксируешь её, даже если сам на пакет не ссылаешься. Это стандартный способ закрыть уязвимость в транзитивной зависимости без ожидания обновления промежуточной библиотеки.

### Файл блокировки

```xml
<PropertyGroup>
  <RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>
</PropertyGroup>
```

Создаётся `packages.lock.json` с точными версиями всего графа и хешами. В CI восстановление запускают в строгом режиме:

```bash
dotnet restore --locked-mode      # упадёт, если граф отличается от зафиксированного
```

Это даёт воспроизводимость: сборка месячной давности соберётся с теми же версиями. Файл коммитится в репозиторий.

## Безопасность и здоровье зависимостей

```bash
dotnet list package --vulnerable --include-transitive   # известные уязвимости
dotnet list package --outdated                          # есть более новые версии
dotnet list package --deprecated                        # объявленные устаревшими
```

Начиная с .NET 8 аудит включён по умолчанию: при восстановлении NuGet сверяется с базой уязвимостей и печатает предупреждения. Строгий режим:

```xml
<PropertyGroup>
  <NuGetAudit>true</NuGetAudit>
  <NuGetAuditMode>all</NuGetAuditMode>          <!-- включая транзитивные -->
  <NuGetAuditLevel>moderate</NuGetAuditLevel>   <!-- порог серьёзности -->
  <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
</PropertyGroup>
```

> [!danger] Лицензии меняются с мажорными версиями
> Несколько популярных в .NET библиотек за 2024–2026 годы перешли на коммерческие условия для организаций: **MediatR** (с v13), **FluentAssertions** (с v8), **MassTransit** (v9; v8 остаётся бесплатной). Обновление мажорной версии может внезапно потребовать оплаты. Практика: перед мажорным обновлением проверять лицензию, а в проектах фиксировать её через автоматическую проверку (например, отдельным шагом CI, сверяющим список лицензий с разрешённым набором). Актуальные альтернативы: Shouldly вместо FluentAssertions, собственный диспетчер или Wolverine вместо MediatR ([[MediatR и альтернативы]]).

## Свой пакет

```xml
<PropertyGroup>
  <PackageId>Alif.ServiceShop.Contracts</PackageId>
  <Version>1.2.0</Version>
  <Authors>Alif</Authors>
  <Description>Контракты модуля заказов</Description>
  <PackageLicenseExpression>MIT</PackageLicenseExpression>
  <PackageReadmeFile>README.md</PackageReadmeFile>
  <RepositoryUrl>https://github.com/company/repo</RepositoryUrl>
  <PublishRepositoryUrl>true</PublishRepositoryUrl>
  <IncludeSymbols>true</IncludeSymbols>
  <SymbolPackageFormat>snupkg</SymbolPackageFormat>
  <GenerateDocumentationFile>true</GenerateDocumentationFile>
</PropertyGroup>
```

```bash
dotnet pack -c Release
dotnet nuget push bin/Release/*.nupkg -s https://api.nuget.org/v3/index.json -k $API_KEY

# Локальная проверка перед публикацией: свой каталог как источник
dotnet nuget add source ~/local-packages -n local
```

Полезные детали: `IncludeSymbols` плюс Source Link дают потребителям возможность отлаживать твой код; `GenerateDocumentationFile` кладёт XML-комментарии в пакет, и они появляются в подсказках IDE; `PackageReadmeFile` показывается на странице пакета.

Для библиотек с публичным API стоит включить проверку совместимости:

```xml
<EnablePackageValidation>true</EnablePackageValidation>
<PackageValidationBaselineVersion>1.1.0</PackageValidationBaselineVersion>
```

Она сравнивает API с предыдущей версией и ругается на ломающие изменения — это защита от случайного нарушения SemVer.

## Восстановление в CI и Docker

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src

# Сначала копируем только файлы проектов — слой кешируется, пока зависимости не менялись
COPY Directory.Packages.props Directory.Build.props ./
COPY src/Api/Api.csproj src/Api/
COPY src/Domain/Domain.csproj src/Domain/
RUN dotnet restore src/Api/Api.csproj

# Потом весь код: изменение кода не сбрасывает кеш восстановления
COPY . .
RUN dotnet publish src/Api/Api.csproj -c Release -o /app --no-restore
```

Этот порядок слоёв экономит минуты на каждой сборке. Дополнительно в CI используют `--locked-mode` и приватный кеш пакетов.

> [!warning] Подводные камни
> - **`Version="9.0.0"` понимают как «ровно».** Это минимум; точное закрепление — `[9.0.0]`.
> - **Плавающие версии в CI.** Сборка перестаёт быть воспроизводимой; обновление приходит само.
> - **Разные версии одного пакета в проектах решения.** Классика конфликтов; лечится `Directory.Packages.props`.
> - **Уязвимость в транзитивной зависимости.** Прямая ссылка или транзитивное закрепление решают её, не дожидаясь обновления промежуточной библиотеки.
> - **`MissingMethodException` в рантайме.** Обычно означает, что загружена не та версия, против которой компилировали: смотреть `dotnet list package --include-transitive` и фактическую версию сборки.
> - **Мажорное обновление без проверки лицензии.** MediatR, FluentAssertions, MassTransit — реальные примеры смены условий.
> - **Пакеты только из nuget.org без аудита.** Аудит с .NET 8 включён по умолчанию — не отключать.
> - **`dotnet restore` после копирования всего кода в Docker.** Слой кеша сбрасывается на каждое изменение исходников.

> [!example] Как делают в бою
> Стандартный набор файлов в корне решения: `Directory.Packages.props` с централизованными версиями и транзитивным закреплением, `Directory.Build.props` с общими свойствами сборки, `nuget.config` с перечнем источников (в том числе приватного фида компании) и `packages.lock.json` в каждом проекте.
> В CI: `dotnet restore --locked-mode`, затем сборка с `TreatWarningsAsErrors`, затем отдельный шаг проверки уязвимостей (`dotnet list package --vulnerable --include-transitive` с падением при находках). Обновление зависимостей автоматизируют Dependabot или Renovate — они открывают PR с обновлением, и решение принимает человек.
> Правило по добавлению новой зависимости: смотреть на дату последнего релиза, число сопровождающих, лицензию и размер транзитивного хвоста. Пакет ради одной функции на двадцать строк почти всегда дороже собственной реализации — не в момент добавления, а через год, когда его перестанут поддерживать.
> Внутренние библиотеки компании публикуют в приватный фид с обязательным Source Link и символами: это позволяет отлаживаться внутрь чужого модуля, не выкачивая его исходники.

## Вопросы с собеседований

> [!question]- Как NuGet выбирает версию при конфликте зависимостей?
> Действуют два правила. Первое — «ближайшая побеждает»: прямая ссылка в проекте имеет приоритет над любыми транзитивными требованиями, поэтому явное указание пакета в своём `.csproj` — штатный способ разрешить конфликт. Второе — «минимальная подходящая версия»: запись `Version="9.0.0"` означает «не ниже 9.0.0», и если другие участники графа требуют более высокую версию, будет выбрана наименьшая, удовлетворяющая всем требованиям, а не самая свежая доступная. Если требования несовместимы (например, две библиотеки жёстко закрепили разные версии в квадратных скобках), восстановление падает с ошибкой NU1107, и это правильное поведение — тихое несоответствие в рантайме было бы хуже. Разобраться, откуда взялся конкретный пакет, помогает `dotnet nuget why`, а увидеть весь граф — `dotnet list package --include-transitive`.

> [!question]- Что такое централизованное управление версиями и зачем нужен файл блокировки?
> Централизованное управление (`Directory.Packages.props` с `ManagePackageVersionsCentrally`) выносит версии всех пакетов в один файл: проекты ссылаются на пакеты без указания версии. Это устраняет расхождения между проектами решения и делает обновление одной правкой. Дополнительная опция `CentralPackageTransitivePinningEnabled` позволяет закрепить версию транзитивного пакета, на который проект не ссылается напрямую, — стандартный способ закрыть уязвимость, не дожидаясь обновления промежуточной библиотеки. Файл блокировки (`packages.lock.json`, включается свойством `RestorePackagesWithLockFile`) фиксирует точные версии всего графа вместе с хешами; в CI восстановление запускают с `--locked-mode`, и оно падает, если фактический граф отличается. Вместе это даёт воспроизводимость: сборка полугодовой давности соберётся с теми же зависимостями.

> [!question]- Как найти и закрыть уязвимость в зависимостях?
> Начиная с .NET 8 аудит выполняется при каждом восстановлении и печатает предупреждения о пакетах с известными уязвимостями; строгость настраивается свойствами `NuGetAuditMode` и `NuGetAuditLevel`, а вместе с `TreatWarningsAsErrors` это ломает сборку и не даёт проблеме доехать до прода. Для ручной проверки есть `dotnet list package --vulnerable --include-transitive`, а также `--outdated` и `--deprecated`. Если уязвим прямой пакет, его просто обновляют. Если транзитивный — обновляют промежуточную библиотеку, а когда её обновления нет, добавляют прямую ссылку на исправленную версию (правило «ближайшая побеждает») или закрепляют версию через транзитивное закрепление в центральном файле. Отдельно стоит следить за лицензиями: несколько популярных библиотек перешли на коммерческие условия в мажорных версиях, поэтому обновление стоит проверять не только на совместимость API.

## Задачи

### Задача 1. Разобрать конфликт

Приложение падает в рантайме с `MissingMethodException` на методе из `System.Text.Json`. Компилируется без ошибок. Что делать?

> [!success]- Решение
> Симптом означает, что во время выполнения загружена версия сборки, отличная от той, против которой компилировали. Порядок разбора:
> ```bash
> dotnet list package --include-transitive | grep -i "System.Text.Json"
> dotnet nuget why MyApp System.Text.Json      # цепочка: кто её притащил
> ```
> Дальше проверить, что фактически лежит в папке публикации (`ls out/System.Text.Json.dll`) и какая у неё версия — часто в опубликованной папке остаётся файл от предыдущего деплоя.
> Типичные причины и лечение: две библиотеки требуют разные мажорные версии — закрепить нужную прямой ссылкой в своём проекте (правило «ближайшая побеждает»); в решении разные проекты используют разные версии — перейти на `Directory.Packages.props`; в контейнере или на сервере остались старые файлы — публиковать в чистый каталог.
> Профилактика на будущее: `packages.lock.json` с `--locked-mode` в CI, чтобы граф версий не менялся незаметно между сборками.

### Задача 2. Закрыть уязвимость в транзитивной зависимости

`dotnet list package --vulnerable --include-transitive` показывает уязвимость в пакете, который тянет сторонняя библиотека. Обновления библиотеки нет. Варианты?

> [!success]- Решение
> Три рабочих варианта в порядке предпочтения.
> **Прямая ссылка на исправленную версию.** Работает благодаря правилу «ближайшая побеждает»:
> ```xml
> <PackageReference Include="Уязвимый.Пакет" Version="8.0.5" />
> ```
> Риск — совместимость: промежуточная библиотека компилировалась против старой версии, и если там были ломающие изменения, появится `MissingMethodException`. Поэтому после такого закрепления нужны интеграционные тесты.
> **Транзитивное закрепление в центральном файле** — то же самое, но декларативно и для всего решения сразу:
> ```xml
> <CentralPackageTransitivePinningEnabled>true</CentralPackageTransitivePinningEnabled>
> <PackageVersion Include="Уязвимый.Пакет" Version="8.0.5" />
> ```
> **Отказ от библиотеки-посредника**, если уязвимость серьёзная, а сопровождение библиотеки заброшено. Это дороже, но иногда единственный честный выход.
> Чего делать не стоит: отключать аудит или понижать `NuGetAuditLevel`, чтобы предупреждение исчезло. И полезно завести правило: уязвимости уровня high и critical блокируют релиз, остальные — попадают в бэклог с сроком.

## Итог

- Пакет — архив со сборками под разные TFM, метаданными и списком зависимостей; кеш лежит в `~/.nuget/packages`.
- `Version="X"` означает «не ниже X»; точное закрепление — квадратные скобки; плавающие версии ломают воспроизводимость.
- Конфликты разрешаются правилами «ближайшая побеждает» и «минимальная подходящая»; несовместимые требования дают ошибку восстановления.
- `dotnet nuget why` отвечает на вопрос «откуда взялся этот пакет».
- `Directory.Packages.props` централизует версии, транзитивное закрепление позволяет чинить чужие зависимости.
- `packages.lock.json` плюс `--locked-mode` дают воспроизводимую сборку.
- Аудит уязвимостей включён по умолчанию с .NET 8; проверка лицензий при мажорных обновлениях обязательна.
- В Docker сначала копируют файлы проектов и восстанавливают, потом код — иначе кеш слоёв бесполезен.
