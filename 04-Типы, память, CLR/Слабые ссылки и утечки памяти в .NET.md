# Слабые ссылки и утечки памяти в .NET

> [!abstract] Коротко
> Утечка в языке со сборщиком мусора выглядит иначе, чем в C++: память не «теряется», она остаётся **достижимой**, хотя больше не нужна. Виновником всегда оказывается ссылка от какого-то корня: статическое поле, подписка на событие долгоживущего объекта, незавершённая задача, таймер, захваченное замыкание, кеш без вытеснения. Слабая ссылка (`WeakReference<T>`) позволяет ссылаться на объект, не удерживая его, — но она нужна реже, чем кажется: в большинстве случаев правильный ответ не «сделать ссылку слабой», а «убрать лишнюю ссылку» или «ограничить размер кеша».

## Зачем это нужно

Симптом всегда один: потребление памяти растёт со временем при неизменной нагрузке и не падает после сборок; в контейнере это заканчивается убийством процесса по OOM. При этом код «ничего не выделяет лишнего», и найти причину без понимания механики достижимости невозможно.

---

## Что считается утечкой

```csharp
// Не утечка: объект недостижим, GC его заберёт
void Method() { var big = new byte[10_000_000]; }

// Утечка: объект достижим из статического поля навсегда
static readonly List<byte[]> Cache = [];
void Leak() => Cache.Add(new byte[10_000_000]);
```

GC освобождает всё недостижимое, включая циклы. Значит, утечка — это всегда **лишняя достижимость**. Диагностический вопрос всегда один и тот же: «какая цепочка ссылок ведёт от корня к этому объекту».

Корни: локальные переменные и регистры всех потоков, статические поля, GC-дескрипторы, очередь финализации ([[Сборка мусора (GC): как работает]]).

## Каталог типичных утечек

### 1. Статические коллекции и кеши без вытеснения

```csharp
// Растёт бесконечно
private static readonly Dictionary<long, Order> Cache = new();

// Ограниченный кеш с вытеснением и временем жизни
services.AddMemoryCache(options => options.SizeLimit = 10_000);
cache.Set(key, order, new MemoryCacheEntryOptions
{
    Size = 1,
    AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10),
    SlidingExpiration = TimeSpan.FromMinutes(2)
});
```

Самая частая утечка в бэкенде. Ключевое правило: **у любого кеша должен быть предел** — по размеру, по времени жизни или по обоим.

### 2. Подписки на события

```csharp
// Издатель-синглтон держит каждого подписчика
public sealed class Subscriber : IDisposable
{
    private readonly EventHub _hub;
    private readonly EventHandler<Message> _handler;

    public Subscriber(EventHub hub)
    {
        _hub = hub;
        _handler = OnMessage;                 // сохраняем ТОТ ЖЕ делегат
        _hub.MessageReceived += _handler;
    }

    private void OnMessage(object? sender, Message m) { }
    public void Dispose() => _hub.MessageReceived -= _handler;
}
```

Делегат хранит ссылку на `Target`, то есть на подписчика; событие хранит делегаты. Пока жив издатель, живы все подписчики ([[Делегаты, события и лямбды]]).

### 3. Захват `this` в долгоживущем делегате

```csharp
public sealed class Widget
{
    private readonly byte[] _buffer = new byte[1_000_000];

    public Widget(Timer timer)
        => timer.Elapsed += (s, e) => Console.WriteLine(_buffer.Length);   // захвачен this
}
```

Лямбда, обращающаяся к полю, захватывает весь объект. Если делегат живёт в таймере, кеше или статическом поле, объект не будет собран никогда.

### 4. Таймеры и фоновые задачи

```csharp
// System.Threading.Timer держит колбэк и state; без Dispose живёт вечно
private readonly Timer _timer = new(Tick, state: this, dueTime: 0, period: 1000);
public void Dispose() => _timer.Dispose();

// Задача, которая никогда не завершается, держит своё замыкание и стек состояния
_ = Task.Run(async () => { while (true) await DoAsync(); });   // нет отмены — нет освобождения
```

Правильно — `CancellationToken`, ожидание завершения и `Dispose` в остановке приложения ([[Background services и IHostedService]]).

### 5. `Transient`-сервисы с `IDisposable`

Контейнер удерживает созданные им освобождаемые экземпляры до конца области, чтобы вызвать `Dispose`. Часто создаваемый `Transient` с `IDisposable` в singleton-области — гарантированный рост памяти ([[Жизненные циклы сервисов: Singleton, Scoped, Transient]]).

### 6. `AsyncLocal` и `ThreadLocal`

Значения `AsyncLocal<T>` живут вместе с контекстом исполнения и копируются в дочерние задачи; тяжёлый объект, положенный туда, может удерживаться дольше ожидаемого. `ThreadLocal<T>` без `Dispose` удерживает значения для всех потоков пула — а они живут до конца процесса.

### 7. Строки в таблице интернирования

`string.Intern` помещает строку в таблицу, которая живёт до конца домена приложения. Интернирование строк, приходящих извне (идентификаторов, ключей), — необратимая утечка ([[Строки и работа с текстом]]).

### 8. Неуправляемые ресурсы

Незакрытые файлы, сокеты, соединения — утечка не памяти, а дескрипторов; проявляется как исчерпание лимита ОС при нормальном потреблении памяти ([[IDisposable, using и паттерн Dispose]]).

## Слабые ссылки

```csharp
var weak = new WeakReference<Order>(order);

if (weak.TryGetTarget(out var alive))
    Use(alive);            // объект ещё жив
else
    Reload();              // уже собран

// Длинная слабая ссылка отслеживает объект и после финализации (нужна крайне редко)
var longWeak = new WeakReference<Order>(order, trackResurrection: true);
```

Слабая ссылка не удерживает объект: GC соберёт его, как только исчезнут все обычные (сильные) ссылки. Применения:

- **Кеш «пока помещается в памяти»**: значение можно потерять, восстановление дёшево.
- **Наблюдение без владения**: реестр объектов для диагностики, который не должен продлевать им жизнь.
- **Слабые события**: издатель не удерживает подписчиков.

Ограничения, из-за которых слабые ссылки редко бывают правильным ответом: момент исчезновения непредсказуем, поведение кеша становится недетерминированным (в тестах объект жив, в проде — нет), а стоимость проверки и создания дескриптора не нулевая. Для кеширования почти всегда лучше `IMemoryCache` или `HybridCache` с явной политикой вытеснения — они предсказуемы и наблюдаемы.

### ConditionalWeakTable

```csharp
// Привязать данные к чужому объекту, не продлевая ему жизнь
private static readonly System.Runtime.CompilerServices.ConditionalWeakTable<Order, Metadata> Meta = new();

Meta.Add(order, new Metadata());
if (Meta.TryGetValue(order, out var m)) Use(m);
```

Таблица держит **слабую** ссылку на ключ и освобождает пару, когда ключ становится недостижимым; при этом значение может ссылаться на ключ, и цикл будет корректно собран. Это правильный инструмент для «прикрепления» дополнительных данных к объектам, которыми ты не владеешь, — так реализованы, например, некоторые механизмы расширения в самой платформе.

## Как искать утечку

```bash
# 1. Подтвердить: растёт ли куча между сборками
dotnet-counters monitor -p <pid> --counters System.Runtime

# 2. Снять два дампа с интервалом
dotnet-dump collect -p <pid> -o dump1.dmp
# ...через час...
dotnet-dump collect -p <pid> -o dump2.dmp

# 3. Анализ
dotnet-dump analyze dump2.dmp
> dumpheap -stat            # какие типы занимают больше всего и сколько их
> dumpheap -type OrderDto   # адреса экземпляров
> gcroot 00007f9c1a2b3c40   # ЦЕПОЧКА ССЫЛОК ОТ КОРНЯ — главный ответ
> finalizequeue             # не растёт ли очередь финализации
> dumpheap -stat -mt <MT>   # детализация по конкретному типу
```

Ключевая команда — `gcroot`: она показывает, кто именно держит объект. Всё остальное — подготовка к ней.

Альтернатива с графическим интерфейсом — dotMemory или Visual Studio Diagnostic Tools: там удобно сравнивать два снимка и смотреть «новые объекты, выжившие между снимками».

Тест на утечку тоже возможен:

```csharp
[Fact]
public void Subscriber_IsCollected_AfterDispose()
{
    var hub = new EventHub();
    var weak = CreateAndDispose(hub);

    GC.Collect();
    GC.WaitForPendingFinalizers();
    GC.Collect();

    Assert.False(weak.TryGetTarget(out _));   // подписчик должен быть собран

    static WeakReference<Subscriber> CreateAndDispose(EventHub hub)
    {
        var s = new Subscriber(hub);
        s.Dispose();
        return new WeakReference<Subscriber>(s);
    }
}
```

Здесь `GC.Collect()` оправдан: это тест, где нужен детерминизм. Локальная функция нужна, чтобы ссылка на объект гарантированно вышла из области видимости.

> [!warning] Подводные камни
> - **Кеш без ограничения.** Самая частая утечка; предел по размеру и времени обязателен.
> - **Подписка без отписки.** Издатель держит подписчиков; отписаться лямбдой невозможно.
> - **Захват `this` в долгоживущей лямбде.** Обращение к полю тянет весь объект.
> - **`static` для «удобства».** Любое статическое поле — корень до конца процесса.
> - **Слабая ссылка как решение проблемы дизайна.** Она маскирует лишнюю связь вместо того, чтобы её убрать.
> - **`GC.Collect()` в проде «чтобы проверить утечку».** Проверять надо метриками и дампами.
> - **Рост RSS как признак утечки.** Рантайм не возвращает сегменты ОС сразу; смотреть надо размер управляемой кучи и число живых объектов.
> - **Фрагментация LOH.** Выглядит как утечка (память растёт), но живых данных мало — лечится иначе ([[Поколения GC, LOH и режимы сборщика]]).

> [!example] Как делают в бою
> Профилактика в проекте сводится к нескольким привычкам: у всех кешей есть лимит и время жизни; подписки на события оформляются как ресурс с отпиской в `Dispose`; фоновые циклы принимают `CancellationToken`; статические изменяемые поля не заводятся без крайней необходимости; в контейнере задан лимит памяти, а метрики кучи и времени в GC выведены на дашборд.
> Расследование всегда идёт по одному маршруту: счётчики подтверждают монотонный рост → два дампа с интервалом → `dumpheap -stat` показывает подозрительный тип → `gcroot` показывает держателя. Девять из десяти находок — статический словарь, подписка или незавершённая задача.
> Слабые ссылки в прикладном коде почти не встречаются: их вытеснили `IMemoryCache` с политиками вытеснения и `HybridCache`. `ConditionalWeakTable` применяют в библиотеках, когда нужно прикрепить данные к чужим объектам, не влияя на их время жизни.
> Отдельная полезная практика — тест на утечку для компонентов с подписками: он дешёвый, детерминированный и ловит регрессию сразу, а не через неделю работы в проде.

## Вопросы с собеседований

> [!question]- Что такое утечка памяти в .NET, если есть сборщик мусора?
> Это ситуация, когда объект остаётся **достижимым** от какого-либо корня, хотя приложению больше не нужен. GC освобождает всё недостижимое, включая циклические ссылки, поэтому «забыли освободить» в смысле C++ невозможно; зато возможно «забыли убрать ссылку». Корнями считаются статические поля, локальные переменные и регистры всех работающих потоков, GC-дескрипторы и очередь финализации. Отсюда каталог типичных причин: статические коллекции и кеши без ограничения размера, подписки на события долгоживущих издателей, лямбды, захватившие `this` и живущие в таймерах или пулах, незавершённые фоновые задачи, `Transient`-сервисы с `IDisposable` в singleton-области, `string.Intern` для внешних данных. Отдельно стоит различать утечку памяти и утечку неуправляемых ресурсов — незакрытые файлы и сокеты исчерпывают лимиты ОС при нормальном потреблении памяти.

> [!question]- Как найти утечку в работающем сервисе?
> Сначала подтвердить её метриками: `dotnet-counters monitor` показывает размер управляемой кучи, число сборок и время в GC; утечка выглядит как монотонный рост кучи, не спадающий после полных сборок. Затем снять два дампа с интервалом (`dotnet-dump collect`), чтобы видеть динамику, а не срез. В `dotnet-dump analyze` команда `dumpheap -stat` даёт распределение по типам — ищем тип, чьё количество выросло пропорционально времени. Дальше `dumpheap -type <Имя>` даёт адреса экземпляров, а `gcroot <адрес>` — цепочку ссылок от корня, то есть прямой ответ на вопрос «кто держит». Полезно также проверить `finalizequeue`: растущая очередь финализации означает зависший или медленный финализатор. Графические альтернативы — dotMemory и диагностические инструменты Visual Studio, где удобно сравнивать снимки. Важная оговорка: рост RSS сам по себе не доказывает утечку, потому что рантайм не возвращает сегменты ОС немедленно.

> [!question]- Что такое `WeakReference` и когда он действительно нужен?
> Это ссылка, которая не удерживает объект: сборщик соберёт его, как только исчезнут все обычные ссылки, а `TryGetTarget` начнёт возвращать `false`. Различают короткую и длинную формы: длинная (`trackResurrection: true`) продолжает отслеживать объект после выполнения финализатора и нужна в редких сценариях. Оправданные применения: кеш, значения которого не жалко потерять и дёшево восстановить; реестры и диагностические структуры, которые не должны продлевать жизнь наблюдаемым объектам; реализация слабых событий, чтобы издатель не удерживал подписчиков. Ограничения существенны: момент исчезновения объекта непредсказуем, поведение становится недетерминированным и плохо тестируемым, а сам дескриптор не бесплатен. Поэтому для кеширования в прикладном коде почти всегда выбирают `IMemoryCache`/`HybridCache` с явными политиками вытеснения, а `ConditionalWeakTable` используют, когда нужно прикрепить данные к чужому объекту, не влияя на его время жизни.

## Задачи

### Задача 1. Найти держателя

```csharp
public sealed class PriceWatcher
{
    private readonly List<decimal> _history = new();

    public PriceWatcher(IPriceFeed feed)
        => feed.PriceChanged += (s, e) => _history.Add(e.Price);
}
```

`IPriceFeed` — синглтон, `PriceWatcher` создаётся на каждый запрос. Что произойдёт и как исправить?

> [!success]- Решение
> Лямбда обращается к полю `_history`, значит захватывает `this` — весь `PriceWatcher`. Делегат хранится в событии синглтона, поэтому каждый созданный за время работы приложения наблюдатель остаётся достижимым вместе со своим списком истории. За сутки это тысячи объектов и постоянно растущий список подписчиков, из-за чего ещё и `PriceChanged` начинает выполняться всё дольше. Отписаться невозможно: ссылка на делегат нигде не сохранена.
> ```csharp
> public sealed class PriceWatcher : IDisposable
> {
>     private readonly IPriceFeed _feed;
>     private readonly EventHandler<PriceEventArgs> _handler;
>     private readonly List<decimal> _history = [];
>
>     public PriceWatcher(IPriceFeed feed)
>     {
>         _feed = feed;
>         _handler = (_, e) => _history.Add(e.Price);   // сохраняем экземпляр делегата
>         _feed.PriceChanged += _handler;
>     }
>
>     public void Dispose() => _feed.PriceChanged -= _handler;
> }
> ```
> При регистрации как `Scoped` контейнер вызовет `Dispose` в конце запроса. Но более здоровое решение — не связывать компоненты разного времени жизни событиями вовсе: для передачи данных от синглтона к короткоживущим потребителям лучше подходит очередь (`Channel<T>`) или явный опрос, потому что там подписчик не удерживается издателем.

### Задача 2. Выбрать инструмент

Нужно кешировать результаты дорогих вычислений по ключу. Данных может быть много, потеря значения допустима. Что использовать: `Dictionary`, `WeakReference`, `ConditionalWeakTable` или `IMemoryCache`?

> [!success]- Решение
> **`IMemoryCache`** — правильный выбор по умолчанию. Он даёт то, чего нет у остальных вариантов: явный лимит размера, вытеснение по времени (абсолютному и скользящему), приоритеты, обратные вызовы при удалении и метрики. Поведение предсказуемо и одинаково в тестах и в проде.
> Почему не остальные: обычный `Dictionary` не имеет вытеснения — это и есть каноническая утечка; `WeakReference` делает поведение недетерминированным (объект может исчезнуть сразу после сборки или прожить долго — зависит от давления на память), что плохо и для стабильности задержек, и для тестируемости; `ConditionalWeakTable` решает другую задачу — привязку данных к времени жизни **ключа**, а не кеширование по значению, и ключ там должен быть объектом, а не строкой или числом.
> Дополнение: если кеш нужен нескольким инстансам сервиса, вместо `IMemoryCache` берут `HybridCache` (.NET 9) — он объединяет локальный и распределённый уровни и решает проблему одновременного пересчёта одного и того же значения.

## Итог

- Утечка в .NET — это лишняя достижимость: объект жив, потому что на него ссылаются от корня.
- Главные источники: кеши без вытеснения, подписки без отписки, захват `this` в долгоживущих делегатах, таймеры и незавершённые задачи, статические поля.
- Слабая ссылка не удерживает объект, но делает поведение недетерминированным; для кеша обычно лучше `IMemoryCache` с политиками.
- `ConditionalWeakTable` привязывает данные к времени жизни ключа и корректно собирает циклы.
- Поиск: счётчики → два дампа → `dumpheap -stat` → `gcroot`; последняя команда и даёт ответ.
- Рост RSS сам по себе не доказывает утечку: рантайм удерживает сегменты, а фрагментация LOH выглядит похоже.
- Тест на утечку с `WeakReference` и принудительной сборкой — дешёвая защита от регрессий.
