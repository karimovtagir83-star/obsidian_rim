# Файл проекта .csproj изнутри

> [!abstract] Коротко
> `.csproj` — это файл MSBuild: XML со свойствами (`PropertyGroup`), элементами (`ItemGroup`) и целями (`Target`). В SDK-стиле, который используется с .NET Core, он стал коротким: файлы подключаются автоматически по маске, а разумные умолчания приходят из SDK (`Microsoft.NET.Sdk`). Понимать его нужно, потому что именно здесь задаются целевая платформа, `Nullable`, предупреждения-ошибки, анализаторы, параметры публикации и всё остальное поведение сборки — а `Directory.Build.props` позволяет задать это один раз на всё решение.

## Зачем это нужно

Половина «настроек проекта» в IDE — это правка `.csproj`. Практические поводы залезть туда руками: включить строгий режим (`Nullable`, `TreatWarningsAsErrors`), настроить публикацию (AOT, ReadyToRun, single-file), добавить копирование файлов в вывод, разнести настройки по конфигурациям, вынести общие свойства в одно место для всего решения.

---

## Минимальный файл

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
  </PropertyGroup>

</Project>
```

Всё остальное — умолчания SDK. Сравни со старым форматом (.NET Framework), где перечислялся каждый файл, каждая ссылка и каждая цель, а файл занимал сотни строк. Основные различия:

| | SDK-стиль | Старый формат |
|---|---|---|
| Файлы `.cs` | подключаются автоматически по маске | перечисляются явно |
| Добавление файла | ничего не нужно | правка `.csproj`, конфликты слияния |
| Пакеты | `PackageReference` | `packages.config` + `Reference` с путями |
| Размер | 10–40 строк | сотни строк |
| Мультитаргетинг | `TargetFrameworks` через точку с запятой | отдельные проекты |

Атрибут `Sdk` определяет набор умолчаний: `Microsoft.NET.Sdk` (библиотека, консоль), `Microsoft.NET.Sdk.Web` (веб), `Microsoft.NET.Sdk.Worker` (фоновая служба), `Microsoft.NET.Sdk.Razor`.

## Свойства, которые ставят почти всегда

```xml
<PropertyGroup>
  <!-- Платформа и язык -->
  <TargetFramework>net10.0</TargetFramework>
  <LangVersion>latest</LangVersion>
  <OutputType>Exe</OutputType>              <!-- Library по умолчанию -->

  <!-- Строгость -->
  <Nullable>enable</Nullable>
  <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  <WarningsNotAsErrors>CS1591</WarningsNotAsErrors>
  <AnalysisLevel>latest-recommended</AnalysisLevel>
  <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>

  <!-- Удобство -->
  <ImplicitUsings>enable</ImplicitUsings>
  <RootNamespace>Alif.ServiceShop.Orders</RootNamespace>
  <AssemblyName>Alif.ServiceShop.Orders</AssemblyName>

  <!-- Документация и отладка -->
  <GenerateDocumentationFile>true</GenerateDocumentationFile>
  <DebugType>embedded</DebugType>
  <PublishRepositoryUrl>true</PublishRepositoryUrl>

  <!-- Публикация -->
  <InvariantGlobalization>true</InvariantGlobalization>
  <PublishReadyToRun>true</PublishReadyToRun>
  <PublishAot>false</PublishAot>

  <!-- Проверки -->
  <CheckForOverflowUnderflow Condition="'$(Configuration)'=='Debug'">true</CheckForOverflowUnderflow>
</PropertyGroup>
```

Несколько пояснений к неочевидным:

- **`InvariantGlobalization`** убирает зависимость от ICU: меньше размер образа и предсказуемое поведение культур, но перестают работать культурные сравнения и форматирование по локали. Для API-сервисов обычно уместно, для приложений с локализацией — нет ([[Строки и работа с текстом]]).
- **`EnforceCodeStyleInBuild`** заставляет правила `IDE*` из `.editorconfig` применяться при сборке, а не только в IDE ([[Стиль кода, соглашения и .editorconfig]]).
- **`DebugType=embedded`** кладёт отладочные символы внутрь сборки — удобно для контейнеров ([[Сборки, метаданные и IL]]).

## Элементы (ItemGroup)

```xml
<ItemGroup>
  <!-- Ссылки -->
  <PackageReference Include="Serilog.AspNetCore" Version="9.0.0" />
  <ProjectReference Include="../Domain/Domain.csproj" />

  <!-- Файлы, копируемые в вывод -->
  <Content Include="appsettings.json" CopyToOutputDirectory="PreserveNewest" />
  <None Include="scripts/init.sql" CopyToOutputDirectory="Always" />

  <!-- Встроенные ресурсы: доступны через Assembly.GetManifestResourceStream -->
  <EmbeddedResource Include="Templates/*.html" />

  <!-- Исключить файл из компиляции -->
  <Compile Remove="Legacy/**/*.cs" />

  <!-- Глобальные using из файла проекта -->
  <Using Include="System.Diagnostics" />
  <Using Include="MyApp.Domain.OrderId" Alias="OrderId" />
  <Using Include="System.Math" Static="true" />
</ItemGroup>
```

Значения `CopyToOutputDirectory`: `Never` (по умолчанию), `PreserveNewest` (копировать, если изменился) и `Always`. Практически всегда нужен `PreserveNewest`: `Always` замедляет сборку, копируя файлы каждый раз.

Автоматическое подключение файлов можно отключить, если нужно управлять списком вручную:

```xml
<EnableDefaultCompileItems>false</EnableDefaultCompileItems>
```

Так почти никогда не делают — это возврат к проблемам старого формата.

## Условия

```xml
<PropertyGroup Condition="'$(Configuration)' == 'Release'">
  <Optimize>true</Optimize>
  <DefineConstants>$(DefineConstants);PRODUCTION</DefineConstants>
</PropertyGroup>

<ItemGroup Condition="'$(TargetFramework)' == 'netstandard2.0'">
  <PackageReference Include="System.Text.Json" Version="9.0.0" />
</ItemGroup>

<PropertyGroup Condition="$([MSBuild]::IsOSPlatform('Windows'))">
  <DefineConstants>$(DefineConstants);WINDOWS</DefineConstants>
</PropertyGroup>
```

Условия можно ставить на любой элемент: `PropertyGroup`, `ItemGroup`, отдельное свойство, `Target`. Синтаксис `$(Property)` — обращение к свойству, `@(Item)` — к списку элементов, `%(Metadata)` — к метаданным элемента.

Мультитаргетинг:

```xml
<TargetFrameworks>net10.0;netstandard2.0</TargetFrameworks>
```

Сборка выполняется отдельно для каждого TFM, и внутри кода доступны символы вроде `NET10_0_OR_GREATER` ([[Target Framework Moniker и мультитаргетинг]]).

## Directory.Build.props и Directory.Build.targets

Общие настройки выносят на уровень решения. MSBuild сам находит эти файлы, поднимаясь вверх по дереву каталогов от проекта:

```xml
<!-- Directory.Build.props — импортируется В НАЧАЛЕ, до свойств проекта -->
<Project>
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <AnalysisLevel>latest-recommended</AnalysisLevel>
    <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="Roslynator.Analyzers" Version="4.13.1" PrivateAssets="all" />
  </ItemGroup>
</Project>
```

```xml
<!-- Directory.Build.targets — импортируется В КОНЦЕ, после свойств проекта -->
<Project>
  <PropertyGroup Condition="'$(IsTestProject)' == 'true'">
    <IsPackable>false</IsPackable>
  </PropertyGroup>
</Project>
```

Разница принципиальна: `.props` задаёт **умолчания**, которые проект может переопределить; `.targets` применяется **после** и потому побеждает. Свойства, которые нельзя менять на уровне проекта, ставят в `.targets`.

Рядом обычно живут `Directory.Packages.props` с централизованными версиями ([[NuGet: пакеты, версии, транзитивные зависимости]]) и `.editorconfig`.

Порядок вычисления в целом такой:

```
Directory.Build.props  →  Sdk.props  →  сам .csproj  →  Sdk.targets  →  Directory.Build.targets
```

## Свои цели

```xml
<Target Name="PrintVersion" AfterTargets="Build">
  <Message Importance="high" Text="Собрано: $(AssemblyName) $(Version) ($(Configuration))" />
</Target>

<Target Name="CopyConfigs" BeforeTargets="Publish">
  <ItemGroup>
    <ConfigFiles Include="config/*.json" />
  </ItemGroup>
  <Copy SourceFiles="@(ConfigFiles)" DestinationFolder="$(PublishDir)config" />
</Target>

<Target Name="FailOnTodo" BeforeTargets="Build" Condition="'$(Configuration)'=='Release'">
  <Error Condition="$([System.IO.File]::Exists('TODO.txt'))" Text="Остались незакрытые TODO" />
</Target>
```

Цели полезны, но злоупотребление ими превращает сборку в непрозрачный скрипт. Практическое правило: в `.csproj` держать декларативные настройки, а сложную логику выносить в отдельный скрипт или в CI ([[CI/CD: GitHub Actions]]).

## Что лежит в obj и bin

```
obj/
├── project.assets.json      граф зависимостей после restore
├── project.nuget.cache
├── Debug/net10.0/
│   ├── *.g.cs               сгенерированные файлы (в т.ч. GlobalUsings.g.cs)
│   ├── *.AssemblyInfo.cs    атрибуты сборки, генерируемые SDK
│   └── ref/                 reference assembly для компиляции зависимых проектов
bin/
└── Debug/net10.0/           итоговые сборки, PDB, appsettings, зависимости
```

Оба каталога — результат сборки и в репозиторий не попадают (`dotnet new gitignore` их исключает). Странности сборки часто лечатся удалением `obj` и `bin`: там кешируется граф зависимостей, и он может разойтись с текущим состоянием.

Посмотреть сгенерированные глобальные using можно в `obj/Debug/net10.0/<Проект>.GlobalUsings.g.cs` ([[Namespace, using, глобальные using]]).

## Отладка сборки

```bash
dotnet build -v detailed      # подробный вывод
dotnet build -bl              # бинарный лог msbuild.binlog
```

Бинарный лог открывается в MSBuild Structured Log Viewer и показывает всё: какие цели выполнялись, в каком порядке, какие значения приняли свойства, откуда пришёл каждый элемент. Это единственный надёжный способ понять, почему свойство имеет неожиданное значение или откуда взялся лишний файл в выводе.

> [!warning] Подводные камни
> - **Свойство после его использования.** MSBuild вычисляет свойства по порядку: значение, заданное ниже места использования, не подействует.
> - **Путаница `.props` и `.targets`.** `.props` можно переопределить в проекте, `.targets` — нет; для «жёстких» правил нужен второй.
> - **`CopyToOutputDirectory="Always"`.** Замедляет сборку; почти всегда нужен `PreserveNewest`.
> - **Ручное перечисление файлов.** В SDK-стиле не нужно и приводит к дублированию элементов (ошибка о повторном `Compile`).
> - **Настройки в каждом проекте вместо `Directory.Build.props`.** Со временем расходятся, и разные проекты собираются с разной строгостью.
> - **`obj`/`bin` в репозитории.** Постоянные конфликты и мусор в истории.
> - **Сложная логика в целях.** Сборка становится непрозрачной и не воспроизводится вне IDE.
> - **`InvariantGlobalization` без проверки.** Ломает культурное сравнение и форматирование, что проявляется только на данных с локалью.

> [!example] Как делают в бою
> В корне решения лежат четыре файла: `Directory.Build.props` (TFM, `Nullable`, предупреждения-ошибки, анализаторы, общие свойства), `Directory.Packages.props` (версии пакетов), `.editorconfig` (стиль и severity правил) и `global.json` (версия SDK). Файлы отдельных проектов после этого короткие: `Sdk`, специфичные свойства и ссылки — обычно 10–20 строк.
> Публикацию настраивают свойствами, а не флагами в скриптах: тогда локальная сборка и CI ведут себя одинаково. Параметры, зависящие от окружения (RID, версия), передают через `-p:`.
> Правило по целям: если появляется соблазн написать цель со сложной логикой, это обычно означает, что задача принадлежит CI или отдельному скрипту. Исключение — простые вещи вроде копирования файлов и проверок перед публикацией.
> Когда сборка ведёт себя необъяснимо, первым делом чистят `obj`/`bin`, затем снимают бинарный лог `-bl` и смотрят фактический порядок вычисления свойств.

## Вопросы с собеседований

> [!question]- Чем SDK-стиль проекта отличается от старого формата?
> В SDK-стиле файл ссылается на SDK атрибутом `Sdk="Microsoft.NET.Sdk"`, который приносит все умолчания: правила подключения исходных файлов по маске, стандартные цели сборки, набор свойств. Файлы `.cs` не перечисляются — они включаются автоматически, поэтому добавление файла не требует правки проекта и не создаёт конфликтов слияния. Зависимости описываются элементами `PackageReference` с транзитивным разрешением, а не файлом `packages.config` со списком всех, включая транзитивные. Поддерживается мультитаргетинг в одном проекте через `TargetFrameworks`. Итог — файл на 10–40 строк вместо нескольких сотен. Старый формат сегодня встречается только в легаси на .NET Framework, и первый шаг миграции такого проекта — как раз перевод на SDK-стиль.

> [!question]- Зачем нужны `Directory.Build.props` и `Directory.Build.targets`?
> Они задают настройки сразу для всех проектов в дереве каталогов: MSBuild автоматически находит эти файлы, поднимаясь вверх от каждого проекта. `Directory.Build.props` импортируется **до** содержимого `.csproj` и потому задаёт умолчания, которые конкретный проект может переопределить; `Directory.Build.targets` импортируется **после** и переопределяет то, что задано в проекте, — туда помещают правила, которые не должны нарушаться. Типичное содержимое `.props`: целевая платформа, `Nullable`, `ImplicitUsings`, `TreatWarningsAsErrors`, уровень анализаторов, общие пакеты-анализаторы. Выигрыш в том, что настройки не расползаются: без централизации через полгода разные проекты решения собираются с разной строгостью, и часть предупреждений теряется. Рядом обычно лежит `Directory.Packages.props` для централизованных версий пакетов.

> [!question]- Как отладить непонятное поведение сборки?
> Сначала удалить `obj` и `bin`: там кешируется граф зависимостей (`project.assets.json`) и промежуточные файлы, которые могут разойтись с текущим состоянием проекта. Затем собрать с подробным выводом (`dotnet build -v detailed`) или, что лучше, снять бинарный лог (`dotnet build -bl`) и открыть его в MSBuild Structured Log Viewer: там видно все выполненные цели в порядке выполнения, фактические значения свойств и то, откуда каждое из них пришло — из SDK, из `Directory.Build.props`, из самого проекта или из командной строки. Это единственный надёжный способ понять, почему свойство имеет неожиданное значение или откуда взялся лишний файл в выводе. Дополнительно `dotnet --info` и `global.json` помогают исключить расхождение версий SDK как причину.

## Задачи

### Задача 1. Вынести настройки

В решении шесть проектов, в каждом продублированы `TargetFramework`, `Nullable`, `ImplicitUsings` и ссылка на анализаторы. Как привести в порядок?

> [!success]- Решение
> ```xml
> <!-- Directory.Build.props в корне решения -->
> <Project>
>   <PropertyGroup>
>     <TargetFramework>net10.0</TargetFramework>
>     <Nullable>enable</Nullable>
>     <ImplicitUsings>enable</ImplicitUsings>
>     <LangVersion>latest</LangVersion>
>     <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
>     <AnalysisLevel>latest-recommended</AnalysisLevel>
>     <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
>   </PropertyGroup>
>
>   <ItemGroup>
>     <PackageReference Include="Roslynator.Analyzers" Version="4.13.1" PrivateAssets="all" />
>   </ItemGroup>
> </Project>
> ```
> ```xml
> <!-- Файл проекта становится коротким -->
> <Project Sdk="Microsoft.NET.Sdk.Web">
>   <ItemGroup>
>     <ProjectReference Include="../Domain/Domain.csproj" />
>     <PackageReference Include="Serilog.AspNetCore" />
>   </ItemGroup>
> </Project>
> ```
> Дополнительно стоит завести `Directory.Packages.props` с `ManagePackageVersionsCentrally`, чтобы версии пакетов тоже жили в одном месте. Для тестовых проектов различия оформляют условием в `Directory.Build.targets` (например, `IsPackable=false` при `IsTestProject`), а не дублированием.
> Проверить результат: `dotnet build -bl` и убедиться, что свойства пришли из ожидаемого файла — в логе видно источник каждого значения.

### Задача 2. Настроить публикацию

Нужно: сборка в Release, предкомпиляция для быстрого старта в контейнере, отладочные символы внутри сборки, XML-документация, версия из переменной CI.

> [!success]- Решение
> ```xml
> <PropertyGroup>
>   <PublishReadyToRun>true</PublishReadyToRun>
>   <DebugType>embedded</DebugType>
>   <GenerateDocumentationFile>true</GenerateDocumentationFile>
>   <InvariantGlobalization>true</InvariantGlobalization>
>   <PublishRepositoryUrl>true</PublishRepositoryUrl>
>   <EmbedUntrackedSources>true</EmbedUntrackedSources>
> </PropertyGroup>
> ```
> ```bash
> dotnet publish src/Api -c Release -r linux-x64 --self-contained false \
>   -p:Version=$CI_VERSION -o artifacts
> ```
> Почему так: `PublishReadyToRun` требует указания RID и заметно сокращает холодный старт в контейнере, сохраняя при этом полноценный JIT для горячих путей; `DebugType=embedded` вместе с Source Link даёт читаемые стеки и возможность отладки без отдельного файла символов; версия передаётся флагом, а не хардкодится, потому что она приходит из CI. `InvariantGlobalization` уменьшает образ, но его включают только убедившись, что приложению не нужны культурные сравнения и форматирование по локали.
> Отдельно: `--self-contained false` оставляет зависимость от рантайма в базовом образе (`mcr.microsoft.com/dotnet/aspnet:10.0`), что даёт меньший размер и централизованное обновление патчей безопасности.

## Итог

- `.csproj` — файл MSBuild: свойства, элементы, цели; в SDK-стиле он короткий за счёт умолчаний SDK.
- Файлы подключаются автоматически по маске: перечислять их не нужно.
- Ключевые свойства строгости: `Nullable`, `TreatWarningsAsErrors`, `AnalysisLevel`, `EnforceCodeStyleInBuild`.
- `Directory.Build.props` задаёт умолчания для всех проектов, `Directory.Build.targets` переопределяет их после проекта.
- Условия работают на любом элементе; мультитаргетинг задаётся `TargetFrameworks`.
- `obj`/`bin` — результат сборки, не коммитятся; их удаление лечит часть странностей.
- Свои цели уместны для простых действий; сложная логика принадлежит CI.
- При необъяснимом поведении — бинарный лог `dotnet build -bl`.
