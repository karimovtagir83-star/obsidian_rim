# Файл проекта .csproj изнутри

> [!abstract] Коротко
> `.csproj` — файл MSBuild: свойства (`PropertyGroup`), элементы (`ItemGroup`) и цели (`Target`). В SDK-стиле, который используется в .NET Core и позже, он короткий: файлы подключаются автоматически по маске, а умолчания приходят из SDK и из `Directory.Build.props`/`Directory.Packages.props` на уровне решения. Ключевое свойство — `TargetFramework` (TFM, например `net8.0`): оно определяет доступный API, версию C# по умолчанию и то, какую сборку NuGet возьмёт из пакета.

## Зачем это знать

Половина «настроек проекта» в IDE — это правка `.csproj`. Здесь задаются строгость (`Nullable`, `TreatWarningsAsErrors`), целевая платформа, параметры публикации, централизация версий пакетов. На ревью сгенерированного кода это первое место, где видно, унаследовал ли агент строгость решения или тихо ослабил её локальным свойством. При инциденте «пакет собрался, но упал в рантайме с `MissingMethodException`» ответ почти всегда лежит в TFM и в том, какую сборку из NuGet-пакета подобрал restore.

## Модель

### SDK-стиль вместо старого формата

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
  </PropertyGroup>
</Project>
```

Всё остальное — умолчания SDK. В старом формате (.NET Framework) перечислялся каждый файл, каждая ссылка и каждая цель — файл на сотни строк.

| | SDK-стиль | Старый формат |
|---|---|---|
| Файлы `.cs` | подключаются автоматически по маске | перечисляются явно |
| Пакеты | `PackageReference`, транзитивное разрешение | `packages.config` с явным списком |
| Мультитаргетинг | `TargetFrameworks` через `;` | отдельные проекты |
| Размер | 10–40 строк | сотни строк |

Атрибут `Sdk` задаёт набор умолчаний: `Microsoft.NET.Sdk` (библиотека, консоль), `Microsoft.NET.Sdk.Web` (веб), `Microsoft.NET.Sdk.Worker` (фоновая служба).

### TFM: что определяет и где границы

`net8.0` — контракт «какой поверхностью BCL можно пользоваться» и одновременно источник версии C# по умолчанию (для `net8.0` — C# 12). NuGet при restore берёт из пакета папку `lib/net8.0`, а если её нет — ближайшую совместимую более старую (`netstandard2.0` и т.д.); более новую — никогда. Если подходящей папки не нашлось вовсе, `AssetTargetFallback` может тихо подсунуть сборку для .NET Framework — restore напечатает `NU1701`. Это не шум: такая сборка может дёргать API, которого в `net8.0` нет (`System.Configuration`, P/Invoke в `user32.dll`), и упасть в рантайме уже после успешной компиляции. Разбираться с `NU1701` нужно точечно — найти замену пакету или заглушить предупреждение на конкретном `PackageReference`, а не глобально в `Directory.Build.props`.

Мультитаргетинг — сборка одного проекта под несколько TFM сразу (нужен библиотекам, которые потребляют и современный, и легаси-код):

```xml
<PropertyGroup>
  <!-- множественное число: MSBuild соберёт проект N раз -->
  <TargetFrameworks>net8.0;netstandard2.0</TargetFrameworks>
</PropertyGroup>
```

Для сервисов и приложений мультитаргетинг не нужен — у приложения всегда один рантайм и один TFM.

### Свойства, которые ставят почти всегда

```xml
<PropertyGroup>
  <TargetFramework>net8.0</TargetFramework>
  <LangVersion>latest</LangVersion>

  <Nullable>enable</Nullable>
  <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  <AnalysisLevel>latest-recommended</AnalysisLevel>
  <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>

  <ImplicitUsings>enable</ImplicitUsings>
  <InvariantGlobalization>true</InvariantGlobalization>
</PropertyGroup>
```

`EnforceCodeStyleInBuild` заставляет правила `.editorconfig` работать при сборке, а не только в IDE — см. [[Стиль кода, соглашения и .editorconfig]]. `InvariantGlobalization` убирает зависимость от ICU и уменьшает образ, но ломает культурные сравнения и форматирование — включать только убедившись, что локаль сервису не нужна.

### ItemGroup и условия

```xml
<ItemGroup>
  <PackageReference Include="Serilog.AspNetCore" Version="9.0.0" />
  <ProjectReference Include="../Domain/Domain.csproj" />
  <Content Include="appsettings.json" CopyToOutputDirectory="PreserveNewest" />
</ItemGroup>

<ItemGroup Condition="'$(TargetFramework)' == 'netstandard2.0'">
  <PackageReference Include="Microsoft.Bcl.AsyncInterfaces" Version="8.0.0" />
</ItemGroup>
```

`CopyToOutputDirectory="Always"` замедляет сборку — почти всегда нужен `PreserveNewest`. Условия ставятся на любой элемент через `$(Property)`, `@(Item)`, `%(Metadata)`.

### Directory.Build.props / Directory.Build.targets / Directory.Packages.props

MSBuild сам находит эти файлы, поднимаясь вверх по дереву каталогов от каждого проекта — их не нужно подключать явно.

```xml
<!-- Directory.Build.props — импортируется ДО свойств проекта -->
<Project>
  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
    <Nullable>enable</Nullable>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  </PropertyGroup>
</Project>
```

```xml
<!-- Directory.Packages.props — версии пакетов в одном месте -->
<Project>
  <PropertyGroup>
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
  </PropertyGroup>
  <ItemGroup>
    <PackageVersion Include="Serilog.AspNetCore" Version="9.0.0" />
  </ItemGroup>
</Project>
```

При `ManagePackageVersionsCentrally=true` в `.csproj` версию у `PackageReference` писать нельзя — только `Include`, версия приходит из `Directory.Packages.props`.

Порядок вычисления:

```
Directory.Build.props → Sdk.props → сам .csproj → Sdk.targets → Directory.Build.targets
```

Разница принципиальна: `.props` задаёт умолчания, которые проект может переопределить локально; `.targets` применяется после и потому побеждает — туда кладут правила, которые нарушать нельзя.

## Решения

| Ситуация | Что выбрать | Почему |
|---|---|---|
| Один проект в решении | Свойства в самом `.csproj` | Централизация не окупается на одном файле |
| Несколько проектов, общая строгость | `Directory.Build.props` | Апгрейд TFM/анализаторов — правка одной строки, а не N файлов |
| Версии пакетов расползаются по проектам | `Directory.Packages.props` + `ManagePackageVersionsCentrally` | Одна версия пакета на всё решение, конфликты видны в ревью |
| Правило нельзя переопределить в проекте | `Directory.Build.targets` | `.targets` импортируется после и побеждает |
| Библиотека для внешних потребителей на .NET Framework | `TargetFrameworks` с `netstandard2.0` | Мультитаргетинг оправдан только когда есть легаси-потребители |
| Сервис/приложение | Один TFM, LTS (`net8.0`) | У приложения один рантайм — мультитаргетинг не нужен никогда |

> [!example] В ServiceShop
> В `Directory.Build.props` на уровне решения зафиксированы `TreatWarningsAsErrors=true` (любое предупреждение компилятора и StyleCop-анализаторов ломает сборку — это норма проекта, а не поломка CI) и `Nullable enable` (строгий nullable-режим по всей кодовой базе, см. [[Nullable reference types]]). Версии пакетов централизованы через `ManagePackageVersionsCentrally` в `Directory.Packages.props` — в `.csproj` отдельных модулей версию у `PackageReference` не пишут, только `Include`. Подробности — в [[93 — Рабочий проект: Alif ServiceShop (обзор раздела)]].

> [!warning] Где ошибаются
> - **`TargetFramework` вместо `TargetFrameworks`.** Опечатка на одну букву в мультитаргет-проекте: MSBuild не ругается, просто соберёт под один странный TFM. Проверка — `dotnet build -v:n`, посмотреть, сколько раз выполнился `CoreCompile`.
> - **`NU1701` заглушённый глобально в `Directory.Build.props`.** Через полгода никто не знает, какие пакеты в решении реально собраны под .NET Framework. Глушить точечно, на конкретном `PackageReference` через `NoWarn="NU1701"`, с комментарием.
> - **Настройки строгости в каждом `.csproj` вместо `Directory.Build.props`.** Со временем проекты решения расходятся по строгости, часть предупреждений теряется незаметно.
> - **Агент часто:** добавляет `<Version>` к `PackageReference` в проекте, где уже включён `ManagePackageVersionsCentrally` — сборка падает с NU1008/NU1009, и это выглядит как случайная поломка, а не следствие явного решения.
> - **Агент часто:** пишет версию пакета для мультитаргет-`ItemGroup` без учёта, что на `net8.0` пакет уже часть рантайма (например, `System.Text.Json`) — лишняя транзитивная зависимость вместо использования BCL.
> - **`obj`/`bin` в репозитории или не почищены после смены TFM.** Кешированный `project.assets.json` расходится с текущим состоянием — сборка ведёт себя необъяснимо, пока не удалить оба каталога.

## Проверка на ревью

- В `.csproj` нет версии у `PackageReference`, если в решении включён `ManagePackageVersionsCentrally`.
- Новые свойства строгости (`Nullable`, `TreatWarningsAsErrors`, `AnalysisLevel`) не продублированы локально там, где они уже заданы в `Directory.Build.props`.
- Локальное переопределение свойства из `Directory.Build.props` объяснено в PR, а не оставлено немым диффом.
- `NoWarn`/подавление анализатора стоит на конкретном элементе, а не глобально.
- `CopyToOutputDirectory="Always"` не появился там, где достаточно `PreserveNewest`.
- Мультитаргетинг (`TargetFrameworks`) не добавлен без реальной причины (внешние потребители на другом TFM).

## Проверь себя

> [!question]- Чем SDK-стиль проекта отличается от старого формата?
> В SDK-стиле файл ссылается на `Sdk="Microsoft.NET.Sdk"`, который приносит умолчания: файлы `.cs` подключаются автоматически по маске, зависимости описываются `PackageReference` с транзитивным разрешением вместо `packages.config`. Поддерживается мультитаргетинг через `TargetFrameworks` в одном файле. Итог — 10–40 строк вместо сотен. Старый формат встречается в легаси на .NET Framework, и первый шаг миграции такого проекта — перевод на SDK-стиль.

> [!question]- Зачем нужны `Directory.Build.props` и `Directory.Build.targets`, и чем они отличаются?
> Оба задают настройки сразу для всех проектов в дереве каталогов — MSBuild находит их сам, поднимаясь вверх от каждого проекта. `.props` импортируется до содержимого `.csproj`, поэтому задаёт умолчания, которые проект может переопределить. `.targets` импортируется после и потому побеждает — туда кладут правила, которые не должны нарушаться (например, `IsPackable=false` для тестовых проектов). Без централизации через полгода разные проекты решения собираются с разной строгостью.

> [!question]- Что означает NU1701 и почему опасно глушить его глобально?
> NU1701 означает, что для пакета не нашлось ассетов под ваш TFM, и restore по правилу `AssetTargetFallback` подставил сборку, собранную под .NET Framework. Компиляция пройдёт, потому что публичные сигнатуры совпадают, но в рантайме такая сборка может дёрнуть API, которого в современном .NET нет, и упасть с `PlatformNotSupportedException`. Глобальное подавление в `Directory.Build.props` скрывает это для всего решения сразу, и через полгода никто не знает, какие пакеты реально несовместимы.

> [!question]- Зачем нужен `Directory.Packages.props` и что ломается, если про него забыть?
> Он централизует версии пакетов: `ManagePackageVersionsCentrally=true` запрещает указывать версию прямо в `PackageReference` внутри `.csproj`, версия приходит одна на всё решение из `PackageVersion`. Если про это забыть и всё же прописать `Version` локально — сборка падает с ошибкой NU1008/NU1009. Без централизации разные модули решения со временем расходятся по версиям одного и того же пакета, и баг может проявляться только в одном модуле.

> [!question]- Мультитаргетинг библиотеки: когда он оправдан, а когда — просто лишняя работа?
> Оправдан, когда у библиотеки есть реальные потребители на другом TFM — например, внутренние клиенты на .NET Framework 4.6.2+ или Unity, и тогда добавляют `netstandard2.0` вторым таргетом. Для приложений и сервисов мультитаргетинг не нужен никогда — у них один рантайм. Для внутренних библиотек монорепозитория, где все потребители на одном TFM, каждый лишний таргет — это кратный рост времени сборки и отдельная матрица тестов ради несуществующего потребителя.

## Разбор

Дан фрагмент `.csproj` из PR, который ревьюер должен оценить:

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
    <Nullable>enable</Nullable>
  </PropertyGroup>
  <ItemGroup>
    <PackageReference Include="Serilog.AspNetCore" Version="9.0.0" />
  </ItemGroup>
</Project>
```

Решение находится в модуле, где корневой `Directory.Packages.props` включает `ManagePackageVersionsCentrally=true`, а `Directory.Build.props` уже задаёт `TargetFramework`, `Nullable` и `TreatWarningsAsErrors`. Что вернуть автору PR на доработку?

> [!success]- Решение
> Две проблемы. Во-первых, `TargetFramework` и `Nullable` продублированы — они уже заданы в `Directory.Build.props`, и локальное присваивание либо избыточно, либо (если значение расходится) незаметно переопределяет решение уровня решения; такое переопределение допустимо, только если явно обосновано в PR. Во-вторых, `PackageReference` указывает `Version="9.0.0"` при включённой центральной версионности — это либо конфликтует с версией из `Directory.Packages.props` и упадёт с NU1008, либо (если версии случайно совпали) создаёт ложное впечатление, что версию можно менять точечно, хотя решение должно приниматься на уровне `Directory.Packages.props`. Правка: убрать `TargetFramework`/`Nullable` из `.csproj`, убрать `Version` у `PackageReference`, оставив только `Include`.

## Итог

- `.csproj` — файл MSBuild: свойства, элементы, цели; в SDK-стиле короткий за счёт умолчаний SDK.
- `TargetFramework` определяет доступный API, версию C# по умолчанию и то, какую сборку возьмёт NuGet; `NU1701` — сигнал, что restore тихо подставил несовместимую сборку.
- Мультитаргетинг (`TargetFrameworks`) нужен библиотекам с легаси-потребителями, приложениям — никогда.
- `Directory.Build.props` задаёт умолчания для всего решения, `Directory.Build.targets` — правила, которые нельзя переопределить; `Directory.Packages.props` централизует версии пакетов.
- В ServiceShop строгость (`TreatWarningsAsErrors`, `Nullable enable`) и версии пакетов (`ManagePackageVersionsCentrally`) заданы один раз на решение — расхождение локального `.csproj` с этим контрактом стоит ловить на ревью.
