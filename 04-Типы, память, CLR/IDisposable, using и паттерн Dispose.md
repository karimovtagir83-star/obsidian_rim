# IDisposable, using и паттерн Dispose

> [!abstract] Коротко
> Сборщик мусора управляет только памятью. Файловые дескрипторы, сокеты, соединения с БД, хендлы ОС, нативные буферы он не видит, а держать их «до когда-нибудь» нельзя. Для детерминированного освобождения существует `IDisposable` с единственным методом `Dispose()` и синтаксис `using`, который разворачивается в `try/finally`. Асинхронный аналог — `IAsyncDisposable` и `await using` для ресурсов, чьё освобождение само является операцией ввода-вывода. Классический «паттерн Dispose» с `protected virtual Dispose(bool)` и финализатором нужен редко: в современном .NET нативные ресурсы оборачивают в `SafeHandle`, и финализатор писать не приходится.

## Зачем это нужно

```csharp
// Без освобождения: файл остаётся заблокированным до сборки мусора — то есть неизвестно когда
var reader = new StreamReader("data.txt");
var line = reader.ReadLine();
// файл занят; в Linux расходуется дескриптор, в Windows файл нельзя удалить или перезаписать

// С using: ресурс освобождается на выходе из области видимости, в том числе при исключении
using var reader2 = new StreamReader("data.txt");
var line2 = reader2.ReadLine();
```

Утечка дескрипторов проявляется неприятно: приложение работает часами, а потом перестаёт открывать файлы и сокеты, упираясь в лимит ОС (`ulimit -n`). Причём сборщик мусора не поможет — памяти достаточно, и сборка может не запускаться.

## `using`: что это на самом деле

```csharp
using (var stream = File.OpenRead(path))
{
    Process(stream);
}

// Компилятор разворачивает в:
var stream = File.OpenRead(path);
try { Process(stream); }
finally { if (stream is not null) ((IDisposable)stream).Dispose(); }
```

С C# 8 есть более короткая форма — **using-объявление**, освобождающее ресурс в конце области видимости:

```csharp
static async Task<string> ReadAsync(string path, CancellationToken ct)
{
    using var reader = new StreamReader(path);
    return await reader.ReadToEndAsync(ct);
}   // Dispose здесь
```

Несколько ресурсов освобождаются в порядке, обратном созданию:

```csharp
using var connection = new NpgsqlConnection(cs);
using var command = connection.CreateCommand();     // будет освобождён первым
```

Тонкость: `using` работает и по форме (pattern-based) — для `ref struct` достаточно публичного метода `Dispose()` без реализации интерфейса, поскольку `ref struct` не может реализовывать интерфейсы старым способом.

## Реализация: три варианта

### 1. Класс владеет только управляемыми ресурсами (частый случай)

```csharp
public sealed class OrderProcessor : IDisposable
{
    private readonly StreamWriter _log = new("processor.log", append: true);
    private bool _disposed;

    public void Process(Order order)
    {
        ObjectDisposedException.ThrowIf(_disposed, this);      // .NET 7+
        _log.WriteLine(order.Id);
    }

    public void Dispose()
    {
        if (_disposed) return;         // повторный вызов должен быть безопасен
        _log.Dispose();                 // освобождаем то, чем владеем
        _disposed = true;
    }
}
```

Здесь **не нужен ни финализатор, ни `GC.SuppressFinalize`, ни `virtual`**: класс `sealed`, нативных ресурсов напрямую он не держит. Это самый распространённый и самый правильный вариант.

### 2. Класс рассчитан на наследование

Тогда применяется канонический паттерн:

```csharp
public class ResourceHolder : IDisposable
{
    private bool _disposed;

    public void Dispose()
    {
        Dispose(disposing: true);
        GC.SuppressFinalize(this);      // финализатор больше не нужен
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;

        if (disposing)
        {
            // освободить УПРАВЛЯЕМЫЕ ресурсы (другие IDisposable)
        }
        // освободить НЕуправляемые ресурсы (хендлы) — выполняется и из финализатора

        _disposed = true;
    }
}

public sealed class DerivedHolder : ResourceHolder
{
    protected override void Dispose(bool disposing)
    {
        if (disposing) { /* свои управляемые ресурсы */ }
        base.Dispose(disposing);        // обязательно
    }
}
```

Смысл параметра `disposing`: при явном вызове (`true`) можно трогать другие управляемые объекты; при вызове из финализатора (`false`) — нельзя, потому что они могут быть уже собраны, а порядок финализации не определён.

### 3. Класс напрямую владеет нативным ресурсом

Здесь нужен финализатор — но в современном .NET его не пишут вручную, а используют `SafeHandle`:

```csharp
public sealed class NativeBuffer : IDisposable
{
    private readonly SafeFileHandle _handle;    // SafeHandle сам содержит финализатор
    public void Dispose() => _handle.Dispose();
}
```

`SafeHandle` решает и проблему освобождения, и проблему гонок при финализации ([[Финализаторы и SafeHandle]]).

## Асинхронное освобождение

```csharp
public sealed class MessagePublisher : IAsyncDisposable
{
    private readonly IConnection _connection;

    public async ValueTask DisposeAsync()
    {
        await _connection.CloseAsync().ConfigureAwait(false);   // закрытие — это I/O
        _connection.Dispose();
    }
}

await using var publisher = new MessagePublisher();
```

`IAsyncDisposable` нужен, когда освобождение само требует ожидания: сброс буферов на диск, корректное закрытие соединения с сервером, отправка «прощального» сообщения. Синхронный `Dispose` в таких случаях либо блокирует поток, либо (что хуже) выполняет `.GetAwaiter().GetResult()` и рискует дедлоком.

Правила:

- Тип может реализовывать **оба** интерфейса; тогда `await using` предпочтёт асинхронную версию.
- Если реализован только `IAsyncDisposable`, обычный `using` для него не скомпилируется.
- В `DisposeAsync` принято использовать `ConfigureAwait(false)` — метод библиотечный и не должен зависеть от контекста синхронизации ([[Контекст синхронизации и ConfigureAwait]]).
- `DisposeAsync` возвращает `ValueTask`: освобождение часто завершается синхронно, и аллокация `Task` была бы лишней.

## Кто вызывает Dispose в приложении

**DI-контейнер.** ASP.NET Core освобождает зарегистрированные сервисы, реализующие `IDisposable`/`IAsyncDisposable`: `Scoped` — в конце запроса, `Singleton` — при остановке приложения. Важная тонкость: **`Transient`-сервисы, созданные контейнером, тоже удерживаются им до конца области** — если такой сервис реализует `IDisposable` и создаётся часто, это выглядит как утечка. Решение — регистрировать такие типы как `Scoped`, либо создавать их фабрикой и освобождать самому ([[Жизненные циклы сервисов: Singleton, Scoped, Transient]]).

**Фреймворк.** `HttpClient`, полученный из `IHttpClientFactory`, освобождать не нужно — жизненным циклом обработчиков управляет фабрика. Отдельный `HttpClient`, созданный вручную как синглтон, тоже не освобождают до конца работы приложения ([[HttpClient и IHttpClientFactory]]).

**Ты сам** — для локальных ресурсов: потоков, соединений, `CancellationTokenSource`, таймеров, подписок.

```csharp
// CancellationTokenSource — часто забывают, а он держит таймер и регистрации
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(30));
await DoWorkAsync(cts.Token);
```

## Правила хорошей реализации

1. **Идемпотентность.** Повторный `Dispose()` не должен бросать исключение и делать что-то повторно.
2. **Никаких исключений.** `Dispose` вызывается из `finally`, в том числе во время раскрутки другого исключения; выброшенное здесь исключение затрёт исходное.
3. **Освобождать только то, чем владеешь.** Если объект получен извне (через конструктор, из DI), его освобождает владелец. Освобождение чужого `DbContext` — типичная ошибка.
4. **После освобождения — `ObjectDisposedException`.** Использовать освобождённый объект нельзя; проверка через `ObjectDisposedException.ThrowIf(_disposed, this)`.
5. **Не блокировать в `Dispose`.** Долгие операции и ожидания асинхронных задач — признак того, что нужен `IAsyncDisposable`.
6. **Не писать финализатор без нативного ресурса.** Он замедляет сборку и почти никогда не нужен.

> [!warning] Подводные камни
> - **Забытый `using`.** Файл заблокирован, дескриптор занят, соединение не возвращено в пул. Анализатор CA2000 находит часть таких мест.
> - **`Dispose` чужого объекта.** Освобождение внедрённой зависимости ломает других её пользователей — особенно заметно с `DbContext` и `HttpClient`.
> - **`using` для `HttpClient`.** Каждый экземпляр открывает свои соединения; их закрытие оставляет порты в `TIME_WAIT` — под нагрузкой это исчерпание портов ([[Сети для бэкендера: TCP, DNS, порты]]).
> - **Исключение из `Dispose`.** Затирает исходное исключение и превращает диагностику в загадку.
> - **Финализатор «на всякий случай».** Объект переживает лишнюю сборку, попадает в старшее поколение и освобождается позже.
> - **`Transient`-сервис с `IDisposable`.** Контейнер удерживает все экземпляры до конца области: тысячи объектов на запрос.
> - **`Dispose` вместо `DisposeAsync`.** Синхронное закрытие сетевого соединения блокирует поток, а `.Result` внутри `Dispose` может дать дедлок.
> - **Освобождение в неверном порядке.** Сначала должен освобождаться тот, кто зависит от другого; `using`-объявления делают это автоматически.

> [!example] Как делают в бою
> В прикладном коде `IDisposable` реализуют редко: почти всё, чем владеет типичный сервис, — это внедрённые зависимости, освобождать которые не его дело. Реализация появляется там, где класс сам создаёт ресурс: обёртка над соединением, потребитель очереди, кеш с таймером, подписчик на событие долгоживущего объекта.
> Форма при этом почти всегда простая: `sealed`-класс, флаг `_disposed`, освобождение своих полей — без `virtual Dispose(bool)` и без финализатора. Канонический паттерн с финализатором встречается только в библиотеках, работающих с нативным кодом, да и там его вытеснил `SafeHandle`.
> Асинхронное освобождение стало нормой для всего, что связано с сетью: соединения RabbitMQ и Kafka, gRPC-каналы, `DbConnection`. Правило простое: если закрытие ресурса делает ввод-вывод, тип реализует `IAsyncDisposable`, а вызывающие пишут `await using`.
> В CI включают анализаторы CA2000 (объект не освобождён) и CA1816 (`Dispose` без `SuppressFinalize` при наличии финализатора) — они ловят большую часть ошибок до ревью.

## Вопросы с собеседований

> [!question]- Зачем нужен `IDisposable`, если есть сборщик мусора?
> Потому что GC управляет только управляемой памятью и ничего не знает о внешних ресурсах: файловых дескрипторах, сокетах, соединениях с базой, хендлах ОС, нативных буферах, блокировках. Даже когда объект-обёртка становится недостижимым, сборщик заберёт лишь его память, и только когда решит, что пора, — момент недетерминирован и может не наступить долго. Всё это время файл остаётся заблокированным, соединение не возвращено в пул, дескриптор израсходован. `IDisposable` даёт детерминированное освобождение: `Dispose` вызывается точно в конце области видимости благодаря `using`, который разворачивается в `try/finally` и работает в том числе при исключении. Финализатор служит страховкой на случай, если освобождение забыли, но полагаться на него нельзя — он выполняется недетерминированно, откладывает сборку объекта и не гарантируется при завершении процесса.

> [!question]- Как выглядит канонический паттерн Dispose и когда он нужен целиком?
> Полный паттерн — это публичный `Dispose()`, который вызывает `Dispose(disposing: true)` и `GC.SuppressFinalize(this)`; защищённый виртуальный `Dispose(bool disposing)`, где при `true` освобождаются управляемые ресурсы, а неуправляемые — в обоих случаях; и финализатор, вызывающий `Dispose(false)`. Параметр `disposing` нужен потому, что при вызове из финализатора трогать другие управляемые объекты нельзя: они могут быть уже собраны, порядок финализации не определён. Целиком этот паттерн нужен только классу, который **напрямую** владеет неуправляемым ресурсом и при этом рассчитан на наследование. В подавляющем большинстве случаев достаточно `sealed`-класса с флагом и освобождением своих полей — без `virtual`, без финализатора и без `SuppressFinalize`. А если нативный ресурс всё же есть, современный подход — обернуть его в `SafeHandle`, у которого финализатор уже реализован корректно.

> [!question]- Чем `IAsyncDisposable` отличается от `IDisposable` и когда он нужен?
> `IAsyncDisposable` объявляет `ValueTask DisposeAsync()` и используется с `await using`. Он нужен, когда само освобождение является операцией ввода-вывода: сброс буферов на диск, корректное закрытие сетевого соединения с обменом пакетами, завершение сессии на сервере. Синхронный `Dispose` в таких случаях либо блокирует поток пула на время сетевой операции, либо содержит `.GetAwaiter().GetResult()`, что в некоторых контекстах приводит к дедлоку. Возврат `ValueTask`, а не `Task`, выбран потому, что освобождение часто завершается синхронно, и лишняя аллокация была бы неоправданной. Тип может реализовывать оба интерфейса — тогда `await using` выберет асинхронную версию, а `using` синхронную; если реализован только асинхронный, обычный `using` не скомпилируется. Внутри `DisposeAsync` принято писать `ConfigureAwait(false)`.

> [!question]- Что произойдёт, если освободить объект, полученный через DI?
> Скорее всего, сломается работа других потребителей. Контейнер сам управляет временем жизни созданных им сервисов: `Scoped` освобождаются в конце области (для веб-приложения — в конце запроса), `Singleton` — при остановке приложения. Если внедрённую зависимость освободить вручную, остальные её пользователи получат `ObjectDisposedException` — особенно болезненно это с `DbContext` (`Scoped`) и синглтонами. Общее правило: освобождает тот, кто создал. Отдельно стоит знать о ловушке с `Transient`: контейнер удерживает ссылки на все созданные им освобождаемые экземпляры до конца области, чтобы освободить их, поэтому часто создаваемый `Transient`-сервис с `IDisposable` выглядит как утечка памяти. Решение — либо сделать его `Scoped`, либо создавать через фабрику и освобождать самостоятельно.

## Задачи

### Задача 1. Найти ошибки

```csharp
public class ReportService : IDisposable
{
    private readonly DbContext _db;
    private readonly StreamWriter _log;
    private readonly HttpClient _http = new();

    public ReportService(DbContext db) { _db = db; _log = new StreamWriter("report.log"); }

    public void Dispose()
    {
        _db.Dispose();
        _log.Dispose();
        _http.Dispose();
    }

    ~ReportService() => Dispose();
}
```

> [!success]- Решение
> Четыре проблемы.
> `_db` пришёл извне (через DI) — освобождать его нельзя: контейнер сделает это сам в конце области, а преждевременный `Dispose` сломает других потребителей.
> `_http` создан вручную на каждый экземпляр сервиса: каждый открывает свои соединения, а `Dispose` оставляет порты в `TIME_WAIT`. Нужен `IHttpClientFactory`.
> Финализатор не нужен: класс не владеет неуправляемыми ресурсами напрямую. Он лишь заставляет объект пережить лишнюю сборку и попасть в старшее поколение. Хуже того, из финализатора вызывается полный `Dispose`, который трогает управляемые объекты, — они могут быть уже собраны.
> Нет защиты от повторного вызова и нет `ObjectDisposedException` при использовании после освобождения.
> ```csharp
> public sealed class ReportService(DbContext db, HttpClient http) : IDisposable
> {
>     private readonly StreamWriter _log = new("report.log");
>     private bool _disposed;
>
>     public void Write(string line)
>     {
>         ObjectDisposedException.ThrowIf(_disposed, this);
>         _log.WriteLine(line);
>     }
>
>     public void Dispose()
>     {
>         if (_disposed) return;
>         _log.Dispose();        // освобождаем ТОЛЬКО то, что создали сами
>         _disposed = true;
>     }
> }
> ```
> `HttpClient` теперь внедряется (зарегистрирован через `AddHttpClient`), `DbContext` не трогается, финализатор убран, класс `sealed`.

### Задача 2. Асинхронное освобождение

Класс-потребитель очереди держит соединение, которое нужно корректно закрыть с уведомлением брокера. Как оформить?

> [!success]- Решение
> ```csharp
> public sealed class QueueConsumer : IAsyncDisposable
> {
>     private readonly IConnection _connection;
>     private readonly CancellationTokenSource _cts = new();
>     private readonly Task _worker;
>     private bool _disposed;
>
>     public QueueConsumer(IConnection connection)
>     {
>         _connection = connection;
>         _worker = Task.Run(() => ConsumeAsync(_cts.Token));
>     }
>
>     public async ValueTask DisposeAsync()
>     {
>         if (_disposed) return;
>         _disposed = true;
>
>         await _cts.CancelAsync().ConfigureAwait(false);      // сначала просим остановиться
>         try { await _worker.ConfigureAwait(false); }          // дожидаемся завершения обработки
>         catch (OperationCanceledException) { }                // штатная отмена — не ошибка
>
>         await _connection.CloseAsync().ConfigureAwait(false); // корректное прощание с брокером
>         _cts.Dispose();
>     }
> }
>
> await using var consumer = new QueueConsumer(connection);
> ```
> Ключевые моменты: закрытие соединения — операция ввода-вывода, поэтому нужен именно `IAsyncDisposable`, а не блокирующий `Dispose`. Порядок важен: сначала отмена и ожидание завершения обработчика, иначе он продолжит работать с закрытым соединением. `OperationCanceledException` при ожидании задачи — ожидаемый исход, а не сбой. `CancellationTokenSource` тоже освобождается: он держит таймер и регистрации. Флаг делает повторный вызов безопасным. И `ConfigureAwait(false)` — потому что это библиотечный код, которому не нужен контекст синхронизации.

## Итог

- GC управляет памятью, но не внешними ресурсами: для них нужен детерминированный `Dispose`.
- `using` — синтаксический сахар над `try/finally`; using-объявление освобождает в конце области видимости.
- Обычному классу достаточно: `sealed`, флаг `_disposed`, освобождение своих полей. Ни финализатора, ни `virtual`.
- Полный паттерн с `Dispose(bool)` и финализатором нужен только при прямом владении нативным ресурсом и наследовании; лучше `SafeHandle`.
- `IAsyncDisposable` и `await using` — когда освобождение само является операцией ввода-вывода.
- Освобождает тот, кто создал: внедрённые зависимости трогать нельзя.
- `Dispose` обязан быть идемпотентным и не бросать исключений.
- `Transient`-сервисы с `IDisposable` удерживаются контейнером до конца области — частая причина «утечки».
