# IDisposable, using и паттерн Dispose

> [!abstract] Коротко
> Сборщик мусора управляет только памятью. Файловые дескрипторы, сокеты, соединения с БД, хендлы ОС он не видит, а держать их «до когда-нибудь» нельзя. `IDisposable` даёт детерминированное освобождение, `using`/`using var` вызывают его автоматически на выходе из области видимости. Финализатор — страховка на случай, если `Dispose` забыли, и нужен только там, где класс напрямую владеет неуправляемым ресурсом; в современном .NET эту роль почти всегда закрывает готовый `SafeHandle`, а не собственный финализатор.

## Зачем это знать

На ревью это разница между «дескриптор закрылся» и «приложение через сутки упирается в лимит открытых файлов, хотя памяти достаточно». В сгенерированном коде типичны обе крайности: агент забывает `using` для нового ресурса или, начитавшись старых статей про C++-подобные деструкторы, дописывает финализатор туда, где неуправляемого ресурса нет вовсе. Обе ошибки не ловит компилятор.

## Модель

### `using` — синтаксический сахар над `try/finally`

```csharp
using (var stream = File.OpenRead(path))
{
    Process(stream);
}
// разворачивается в:
var stream = File.OpenRead(path);
try { Process(stream); }
finally { if (stream is not null) ((IDisposable)stream).Dispose(); }
```

С C# 8 есть **using-объявление** — освобождает ресурс в конце текущего блока без вложенных скобок:

```csharp
static async Task<string> ReadAsync(string path, CancellationToken ct)
{
    using var reader = new StreamReader(path);
    return await reader.ReadToEndAsync(ct);
}   // Dispose здесь
```

Несколько ресурсов освобождаются в порядке, обратном созданию. Работает и по форме (pattern-based): для `ref struct` достаточно публичного `Dispose()` без реализации интерфейса, так как `ref struct` не может реализовывать интерфейсы старым способом.

### Реализация: обычный случай

Почти всегда классу, владеющему только управляемыми ресурсами, достаточно этого:

```csharp
public sealed class OrderProcessor : IDisposable
{
    private readonly StreamWriter _log = new("processor.log", append: true);
    private bool _disposed;

    public void Process(Order order)
    {
        ObjectDisposedException.ThrowIf(_disposed, this);   // .NET 7+
        _log.WriteLine(order.Id);
    }

    public void Dispose()
    {
        if (_disposed) return;      // повторный вызов должен быть безопасен
        _log.Dispose();
        _disposed = true;
    }
}
```

`sealed`, флаг `_disposed`, освобождение своих полей — без `virtual`, без финализатора, без `GC.SuppressFinalize`. Это самый частый и самый правильный вариант.

### Финализатор: как страховка, а не альтернатива Dispose

Финализатор (`~MyClass()`) вызывает не код, а GC — в отдельном потоке, в неизвестный момент. При первой сборке GC видит финализатор и не освобождает объект: тот переносится в очередь «готовых к финализации» (freachable) и тем самым снова становится достижимым, то есть выживает и попадает в старшее поколение. Поток финализации вызывает `~Legacy()`, и только при следующей сборке память действительно освобождается — минимум на одну сборку позже, чем без финализатора.

Отсюда все свойства, которые делают финализатор непригодным на замену `Dispose`:

| | `Dispose` | Финализатор |
|---|---|---|
| Момент вызова | детерминированный | неизвестен |
| Кто вызывает | код / DI-контейнер | поток финализации GC |
| Порядок | контролируется программистом | не определён |
| Гарантия выполнения | да, если есть `using` | нет (не гарантирован при завершении процесса) |
| Стоимость | нулевая | +1 сборка, старшее поколение, отдельный поток |
| Доступ к управляемым объектам | можно | нельзя |

Именно поэтому канонический паттерн вызывает `GC.SuppressFinalize(this)` — ресурс уже освобождён явно, проходить через финализацию незачем:

```csharp
public class ResourceHolder : IDisposable
{
    private bool _disposed;

    public void Dispose()
    {
        Dispose(disposing: true);
        GC.SuppressFinalize(this);
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;
        if (disposing) { /* освободить УПРАВЛЯЕМЫЕ ресурсы */ }
        // освободить НЕуправляемые ресурсы — выполняется и из финализатора
        _disposed = true;
    }

    ~ResourceHolder() => Dispose(disposing: false);
}
```

Параметр `disposing`: при явном вызове (`true`) можно трогать другие управляемые объекты; при вызове из финализатора (`false`) — нельзя, порядок финализации между объектами не определён, они могут быть уже собраны. Полный паттерн целиком нужен только классу, который **напрямую** владеет неуправляемым ресурсом и рассчитан на наследование.

### SafeHandle — тот же паттерн, но реализованный один раз в BCL

`SafeHandle` — абстрактный класс, оборачивающий нативный дескриптор и снимающий необходимость писать финализатор руками:

- наследуется от `CriticalFinalizerObject` — рантайм гарантирует выполнение даже при нехватке памяти, раньше обычных финализаторов;
- держит счётчик ссылок — пока дескриптор используется в P/Invoke, его нельзя закрыть из другого потока (защита от handle recycling);
- уже реализует `IDisposable`.

Готовые наследники есть почти всегда: `SafeFileHandle`, `SafeWaitHandle`, `SafeProcessHandle`, `SafeSocketHandle`. Класс, владеющий таким хендлом, финализатор не пишет вовсе:

```csharp
public sealed class NativeBuffer : IDisposable
{
    private readonly SafeFileHandle _handle;
    public void Dispose() => _handle.Dispose();   // страховку даёт сам SafeHandle
}
```

Свой `SafeHandle` (наследник `SafeHandleZeroOrMinusOneIsInvalid` или `SafeHandleMinusOneIsInvalid`) пишут редко — когда оборачивают P/Invoke к нативной библиотеке: там переопределяют только `ReleaseHandle()`, которая вызывается ровно один раз, может выполняться из критического финализатора и поэтому не должна бросать исключений или трогать управляемые объекты. Единственный случай финализатора в прикладном коде — диагностика «забыли Dispose» под `#if DEBUG`, и то не как замена паттерну, а как логирование ошибки.

### Асинхронное освобождение

```csharp
public sealed class MessagePublisher : IAsyncDisposable
{
    private readonly IConnection _connection;

    public async ValueTask DisposeAsync()
    {
        await _connection.CloseAsync().ConfigureAwait(false);   // закрытие — это I/O
        _connection.Dispose();
    }
}

await using var publisher = new MessagePublisher();
```

Нужен, когда само освобождение требует ожидания: сброс буферов, закрытие сетевого соединения с обменом пакетами. Синхронный `Dispose` в таких случаях либо блокирует поток, либо содержит `.GetAwaiter().GetResult()` и рискует дедлоком. Тип может реализовывать оба интерфейса — `await using` выберет асинхронную версию.

### Кто вызывает Dispose

DI-контейнер освобождает `Scoped` в конце запроса и `Singleton` при остановке приложения; `Transient`, созданные контейнером, тоже удерживаются им до конца области — часто создаваемый `Transient` с `IDisposable` выглядит как утечка ([[Жизненные циклы сервисов: Singleton, Scoped, Transient]]). `HttpClient` из `IHttpClientFactory` освобождать не нужно — жизненным циклом обработчиков управляет фабрика ([[HttpClient и IHttpClientFactory]]). Всё остальное — локальные ресурсы вроде `CancellationTokenSource` — освобождает тот, кто их создал.

## Решения

| Ситуация | Что писать |
|---|---|
| Класс владеет только управляемыми `IDisposable`-полями | простой `IDisposable`: `sealed`, флаг, освобождение полей — без финализатора |
| Освобождение — операция ввода-вывода (сеть, брокер) | `IAsyncDisposable` + `await using` |
| Класс напрямую держит нативный дескриптор | обернуть в готовый или свой `SafeHandle`, финализатор не писать |
| Нужно поддержать наследование над нативным ресурсом | полный паттерн `Dispose(bool)` + финализатор, вызывающий `Dispose(false)` |
| Ресурс получен извне (DI, параметр конструктора) | не освобождать вообще — освобождает владелец |
| Хочется поймать «забыли Dispose» на этапе разработки | финализатор только под `#if DEBUG`, логирует и ничего не освобождает |

> [!example] В ServiceShop
> `IEventsBus : IDisposable` в модуле обмена событиями оборачивает соединение с Kafka: `Dispose` закрывает продюсера и консьюмера при остановке хоста, финализатора нет — тип `sealed`, ресурс освобождается детерминированно через `IHostedService.StopAsync` ([[ServiceShop: Outbox, Inbox и обмен событиями]]). `DbContext` в обработчиках команд никогда не диспозится вручную: он `Scoped`, и это дело контейнера — преждевременный `Dispose` в перехватчике или в декораторе ломает соединение для остальных участников того же запроса.

> [!warning] Где ошибаются
> - **Забытый `using`.** Файл заблокирован, соединение не возвращено в пул. **Агент часто:** заводит новый `IDisposable`-ресурс (`StreamReader`, `SqlConnection`, `HttpResponseMessage`) внутри метода и не оборачивает его в `using`, потому что код компилируется и работает на тесте с одним вызовом.
> - **Финализатор без нативного ресурса.** **Агент часто:** увидев `IDisposable` в интерфейсе, копирует канонический паттерн целиком — с `Dispose(bool)` и `~ClassName()` — даже когда класс владеет только управляемыми полями. Итог: объект переживает лишнюю сборку и без всякой пользы попадает в старшее поколение.
> - **`Dispose` чужого объекта.** Освобождение внедрённой зависимости ломает других её потребителей — особенно с `DbContext` и `HttpClient`.
> - **Синхронный `Dispose` для сетевого ресурса.** Блокирует поток или скрывает `.GetAwaiter().GetResult()` с риском дедлока — нужен `IAsyncDisposable`.

## Проверка на ревью

- У каждого локально созданного `IDisposable`-ресурса есть `using`/`using var`, включая `CancellationTokenSource` и `HttpResponseMessage`.
- Класс без прямого владения нативным ресурсом не содержит финализатора и `Dispose(bool)`.
- `Dispose` не трогает объекты, полученные через конструктор или DI.
- `Dispose`/`DisposeAsync` идемпотентны и не бросают исключений.
- Ресурс, чьё освобождение делает I/O (сеть, брокер), реализует `IAsyncDisposable`, а не блокирующий `Dispose`.
- Если финализатор всё-таки есть — рядом действительно есть неуправляемый ресурс, и `Dispose` вызывает `GC.SuppressFinalize(this)`.

## Проверь себя

> [!question]- Зачем нужен `IDisposable`, если есть сборщик мусора?
> GC управляет только управляемой памятью и ничего не знает о внешних ресурсах: дескрипторах, сокетах, соединениях, хендлах ОС. Даже когда объект-обёртка становится недостижимым, GC заберёт лишь его память, и то недетерминированно — сборка может не запускаться долго, если памяти достаточно. `IDisposable` даёт детерминированное освобождение: `Dispose` вызывается точно в конце области видимости через `using`, который разворачивается в `try/finally` и срабатывает даже при исключении.

> [!question]- Почему финализатор не заменяет Dispose, а объект с финализатором «живёт дольше»?
> При первой сборке GC видит финализатор и не освобождает объект: он переносится в очередь freachable и тем самым снова становится достижимым — то есть выживает и попадает в старшее поколение, где сборки реже. Реальное освобождение памяти происходит минимум на второй сборке, силами отдельного потока финализации, в неизвестный момент и без гарантии порядка между объектами. Поэтому финализатор годится только как страховка последней надежды для забытого `Dispose` неуправляемого ресурса, а не как основной механизм освобождения.

> [!question]- Что решает SafeHandle и почему его предпочитают собственному финализатору?
> `SafeHandle` наследуется от `CriticalFinalizerObject`, поэтому рантайм выполняет его финализацию с повышенными гарантиями и раньше обычных финализаторов, даже при нехватке памяти. Внутри ведётся счётчик ссылок: пока дескриптор используется в P/Invoke-вызове, его нельзя закрыть из другого потока — это закрывает уязвимость handle recycling, когда закрытый дескриптор переиспользуется ОС под другой ресурс. `SafeHandle` уже реализует `IDisposable`, поэтому владеющему классу не нужны ни собственный финализатор, ни `Dispose(bool)` — достаточно освободить хендл в `Dispose`.

> [!question]- Что произойдёт, если явно освободить объект, полученный через DI?
> Контейнер сам управляет временем жизни созданных им сервисов: `Scoped` освобождаются в конце области, `Singleton` — при остановке приложения. Если внедрённую зависимость освободить вручную, остальные её потребители получат `ObjectDisposedException` при следующем обращении — особенно болезненно с `DbContext` и синглтонами. Правило простое: освобождает тот, кто создал.

## Разбор

Дан фрагмент — что вернёшь на доработку и почему:

```csharp
public class ReportService : IDisposable
{
    private readonly DbContext _db;
    private readonly StreamWriter _log;

    public ReportService(DbContext db) { _db = db; _log = new StreamWriter("report.log"); }

    public void Dispose()
    {
        _db.Dispose();
        _log.Dispose();
    }

    ~ReportService() => Dispose();
}
```

> [!success]- Решение
> Три проблемы. `_db` пришёл извне через DI — освобождать его нельзя, контейнер сделает это сам, а преждевременный `Dispose` сломает других потребителей того же `DbContext` в рамках запроса. Финализатор не нужен: класс не владеет неуправляемым ресурсом напрямую, `StreamWriter` — управляемый объект, который и так будет собран; вызов из финализатора полного `Dispose()`, трогающего `_db`, — вдвойне ошибка, поскольку к моменту финализации `_db` может быть уже собран. Нет защиты от повторного вызова.
> Правка: убрать `_db` из полей и финализатор, оставить `sealed`-класс с `_log`, флагом `_disposed` и освобождением только своего поля в `Dispose()`.

## Итог

- GC управляет памятью, но не внешними ресурсами — для них нужен детерминированный `Dispose`.
- `using`/`using var` — синтаксический сахар над `try/finally`, освобождают ресурс даже при исключении.
- Обычному классу достаточно `sealed` + флаг `_disposed` + освобождение своих полей — без финализатора и без `virtual`.
- Финализатор — страховка для прямого владения неуправляемым ресурсом, а не альтернатива `Dispose`; он замедляет сборку и не гарантирован при завершении процесса.
- Современный способ владеть нативным ресурсом — `SafeHandle`: критическая финализация, счётчик ссылок, готовый `IDisposable`.
- `IAsyncDisposable`/`await using` — когда освобождение само является операцией ввода-вывода.
- Освобождает тот, кто создал: внедрённые зависимости трогать нельзя.
