# Value types vs Reference types

> [!abstract] Коротко
> В CLR все типы делятся на две категории: значимые (value types) — переменная **содержит** сами данные, и ссылочные (reference types) — переменная содержит **адрес** объекта в управляемой куче. Из этого одного различия вытекает всё остальное: семантика копирования, равенство по умолчанию, значение по умолчанию, стоимость передачи в метод, боксинг и давление на сборщик мусора. Это самая часто спрашиваемая тема на собеседованиях по .NET, и почти все «странности» C# объясняются именно ею.

## Зачем это нужно

Три сценария, где непонимание этой темы стоит денег.

1. **Логическая ошибка.** Метод «изменил» структуру, а вызывающий код этого не увидел, потому что работал с копией. Такие баги не ловятся типами и живут в проде месяцами.
2. **Производительность.** Класс на 8 байт полезных данных занимает в куче минимум 24 байта и создаёт работу сборщику мусора. Миллион таких объектов в секунду — это gen0-сборка каждые несколько миллисекунд. Замена на структуру убирает аллокации полностью, см. [[Аллокации и как их избегать]].
3. **Обратная ошибка.** Структура на 200 байт, передаваемая по значению в цикле, копируется на каждом вызове. Здесь «оптимизация» делает хуже, чем класс.

Правильный выбор требует понимания механики, а не заучивания «struct на стеке, class в куче» — это неверное упрощение, разобранное в [[Стек и куча: что где лежит]].

## Иерархия типов CLR

```
                        System.Object
                       /             \
                      /               \
          System.ValueType           (ссылочные типы напрямую)
           /          \                  class, interface,
          /            \                 delegate, string,
   System.Enum      структуры            array, object
        |            (struct)
     enum-типы
```

Ключевые наблюдения:

- Значимые типы наследуются от `System.ValueType`, который сам является **ссылочным** типом (он наследуется от `Object`). Это не парадокс: `ValueType` — это тип-маркер, по которому рантайм отличает категорию, плюс место для переопределённых `Equals`/`GetHashCode`/`ToString`.
- `System.Enum` наследуется от `ValueType`, а конкретные `enum` — от `Enum`. Поэтому у перечислений есть `ToString()`, `HasFlag()` и вся рефлексия имён.
- Любой значимый тип **можно** привести к `object` — но не бесплатно: это боксинг, см. [[Boxing и unboxing]].
- Структура не может наследоваться и не может быть базой. Она неявно `sealed` и неявно наследует `ValueType`. Реализовывать интерфейсы — может.

```csharp
Console.WriteLine(typeof(int).BaseType);        // System.ValueType
Console.WriteLine(typeof(DayOfWeek).BaseType);  // System.Enum
Console.WriteLine(typeof(Enum).BaseType);       // System.ValueType
Console.WriteLine(typeof(ValueType).BaseType);  // System.Object
Console.WriteLine(typeof(ValueType).IsClass);   // True — сам ValueType ссылочный
Console.WriteLine(typeof(int).IsValueType);     // True
```

## Два вида переменных

Разница видна на уровне того, что физически лежит в слоте переменной.

```
Значимый тип:  int x = 42;

   слот x  ┌────────────┐
           │     42     │   ← данные лежат прямо здесь
           └────────────┘


Ссылочный тип: object o = new Foo();

   слот o  ┌────────────┐            куча
           │ 0x7F3A0140 │──────────▶ ┌──────────────┐ 0x7F3A0140
           └────────────┘            │ header       │
        (8 байт адреса)              │ MT pointer   │
                                     │ поля Foo...  │
                                     └──────────────┘
```

Отсюда всё остальное: присвоение значимого копирует данные, присвоение ссылочного копирует адрес; два ссылочных «указывают» на один объект, две структуры всегда независимы.

### Что относится к значимым типам

| Категория | Примеры |
|---|---|
| Целочисленные | `byte`, `sbyte`, `short`, `ushort`, `int`, `uint`, `long`, `ulong`, `nint`, `nuint`, `Int128`, `UInt128` |
| Вещественные | `float`, `double`, `decimal`, `Half` |
| Прочие примитивы | `bool`, `char` |
| Дата и время | `DateTime`, `DateOnly`, `TimeOnly`, `TimeSpan`, `DateTimeOffset` |
| Идентификаторы | `Guid` |
| Кортежи | `ValueTuple<...>` — это `(int, string)` из C# 7 |
| Обёртки | `Nullable<T>` (`int?`), `Memory<T>`, `ReadOnlyMemory<T>` |
| `ref struct` | `Span<T>`, `ReadOnlySpan<T>` — см. [[Span, ReadOnlySpan и Memory]] |
| Пользовательские | любой `struct`, любой `enum`, любой `record struct` |

### Что относится к ссылочным типам

| Категория | Примеры |
|---|---|
| Базовые | `object`, `string`, `dynamic` (это `object` с особым поведением компилятора) |
| Классы | любой `class`, `record class`, анонимные типы |
| Массивы | `int[]`, `Point[]` — **массив всегда объект в куче, даже массив структур** |
| Делегаты | `Action`, `Func<T>`, `EventHandler`, любой `delegate` — см. [[Делегаты, события и лямбды]] |
| Интерфейсы | как **тип переменной** — переменная типа `IComparable` хранит ссылку |
| Старые кортежи | `Tuple<...>` (класс), в отличие от `ValueTuple` (структура) |

Пункт про интерфейсы — источник половины скрытых боксингов. Сам интерфейс — контракт, он не задаёт категорию: структура может его реализовать. Но переменная типа интерфейса физически хранит ссылку, значит, структуру при присваивании придётся упаковать.

```csharp
struct Money : IComparable<Money> { /* ... */ }

Money m = new(100);
IComparable<Money> boxed = m;   // боксинг: копия Money уехала в кучу
Money copy = (Money)boxed;      // анбоксинг: ещё одна копия
```

### Особый случай: string

`string` — ссылочный тип, но ведёт себя «как значение»:

```csharp
string a = "hello";
string b = "hel" + "lo";                       // склеено компилятором в литерал
Console.WriteLine(a == b);                     // True — оператор == сравнивает содержимое
Console.WriteLine(ReferenceEquals(a, b));      // True — оба указывают на интернированный литерал

string c = new string("hello".ToCharArray());
Console.WriteLine(a == c);                     // True — содержимое одинаковое
Console.WriteLine(ReferenceEquals(a, c));      // False — разные объекты в куче
Console.WriteLine(ReferenceEquals(a, string.Intern(c))); // True
```

Причины две. Первая: `string` перегружает `operator ==` на ординальное сравнение содержимого. Вторая: строковые литералы **интернируются** — компилятор складывает их в таблицу констант, рантайм кладёт в интерн-пул, и одинаковые литералы во всей программе — один объект. Плюс строка иммутабельна, поэтому разделять её безопасно. Подробности — [[Строки и работа с текстом]] и [[Строки: производительность и интернирование]].

Практический вывод: не полагайтесь на `ReferenceEquals` для строк и не используйте строки как объект для `lock` — литерал разделяется всей программой, включая чужие библиотеки.

## Устройство объекта в куче

На x64 объект выглядит так:

```
     адрес, который лежит в ссылке ───────┐
                                          ▼
  ┌──────────────────────┬────────────────────────┬──────────────────┐
  │  object header word  │  MethodTable pointer   │  поля экземпляра │
  │      8 байт          │        8 байт          │   ... N байт     │
  └──────────────────────┴────────────────────────┴──────────────────┘
   -8                     0                        8
   (sync block index)     ссылка указывает СЮДА

  Итого накладных расходов: 16 байт на каждый объект.
  Размер выравнивается вверх до кратного 8.
  Минимальный размер объекта на x64 — 24 байта.
```

Почему минимум 24, а не 16: сборщику мусора нужно уметь превращать мёртвый объект в элемент списка свободных блоков, а для этого в теле объекта должно быть место хотя бы под один указатель. Поэтому `new object()` — 16 байт заголовка плюс 8 байт «пустоты» = 24 байта. На 32-битном рантайме арифметика та же, но всё вдвое уже: 4 + 4 + 4 = 12 байт.

Отсюда важная цифра: класс с единственным полем `int` (4 байта полезных данных) занимает 24 байта — накладные расходы 500 %. Структура с тем же полем — 4 байта.

```csharp
class BoxedInt { public int Value; }   // 24 байта в куче + 8 байт ссылки у владельца
struct PlainInt { public int Value; }  // 4 байта там, где живёт владелец
```

### MethodTable

`MethodTable` (MT) — рантайм-представление типа, по одному экземпляру на тип (на замкнутый generic-тип, см. [[Дженерики в CLR: как устроены]]). Внутри, упрощённо:

| Что лежит в MT | Зачем |
|---|---|
| Размер экземпляра (`BaseSize`) | GC знает, сколько байт занимает объект |
| Флаги типа | ссылочный/значимый, содержит ли GC-указатели, есть ли финализатор |
| Указатель на `EEClass` | «холодные» данные типа: поля, метаданные, имя — нужны редко |
| Указатель на родительский MT | приведения, `is`, `as` |
| Указатель на модуль/сборку | загрузка, рефлексия |
| Таблица слотов методов | сначала виртуальные слоты, потом невиртуальные; сюда JIT ставит адреса скомпилированного кода |
| Карта интерфейсов | реализация вызова через интерфейс |
| GC-серии (перед MT, по отрицательным смещениям) | описание, где внутри объекта лежат ссылки — GC обходит только их |

Разделение MT/EEClass сделано ради кеша: горячий путь (виртуальный вызов, проверка типа, обход GC) читает только MT, который компактен и лежит рядом.

Именно MT-указатель делает возможными `GetType()`, `is`/`as`, `callvirt` и всю рефлексию ([[Рефлексия]]). У структуры MT-указателя нет — потому что тип структуры известен статически на месте использования. Как только структура попадает в кучу через боксинг, у боксированной копии появляется полноценный заголовок с MT.

### Заголовок объекта и sync block

Слово заголовка (8 байт до MT-указателя) — это мультиплексор. В разные моменты оно хранит разное:

- **Индекс sync block** — если объекту понадобился «тяжёлый» монитор (`lock`, `Monitor.Wait`), слабая ссылка или COM-обёртка. Sync block выделяется лениво в отдельной таблице.
- **Thin lock** — если объект захвачен `lock` без конкуренции, идентификатор потока и счётчик рекурсии пишутся прямо в заголовок, без выделения sync block. Это делает неконкурентный `lock` очень дешёвым.
- **Хеш-код по умолчанию** — `Object.GetHashCode()` для ссылочного типа возвращает псевдослучайное число, привязанное к экземпляру. Оно **вычисляется один раз и кешируется в заголовке**, поэтому одинаково на протяжении жизни объекта и не зависит от адреса (объект переезжает при компактизации, а хеш нет).
- **Служебные биты GC** — метка при маркировке, признак закрепления (pinned).

Если объекту нужны и хеш, и монитор одновременно, заголовок «повышается» до полноценного sync block.

> Практическое следствие: `lock` на объекте не бесплатен, но и не катастрофичен. А вот `lock` на строке или на `typeof(X)` — плохо, потому что эти объекты разделяются с чужим кодом.

## Устройство структуры

У структуры нет ни заголовка, ни MT-указателя. Только поля, уложенные подряд с учётом выравнивания.

```
struct Point3 { public double X, Y, Z; }

  ┌──────────┬──────────┬──────────┐
  │    X     │    Y     │    Z     │   = 24 байта, ни байта накладных
  └──────────┴──────────┴──────────┘
   0          8          16

class Point3C { public double X, Y, Z; }

  ┌────────┬────────┬──────────┬──────────┬──────────┐
  │ header │   MT   │    X     │    Y     │    Z     │  = 40 байт в куче
  └────────┴────────┴──────────┴──────────┴──────────┘
      8        8         8          8          8
  + 8 байт на ссылку у владельца + работа GC
```

### Как узнать размер

```csharp
// 1) sizeof — константа времени компиляции для примитивов;
//    для пользовательских unmanaged-структур требует unsafe-контекста
unsafe { Console.WriteLine(sizeof(Point3)); }        // 24

// 2) Unsafe.SizeOf<T>() — безопасный аналог, работает для любых T,
//    возвращает управляемый размер (то, что реально в памяти)
Console.WriteLine(Unsafe.SizeOf<Point3>());          // 24
Console.WriteLine(Unsafe.SizeOf<string>());          // 8 — размер ССЫЛКИ, не строки

// 3) Marshal.SizeOf — размер после маршалинга в неуправляемый мир.
//    Может отличаться: bool там 4 байта, char зависит от CharSet
Console.WriteLine(Marshal.SizeOf<Point3>());         // 24
```

Разница между `Unsafe.SizeOf` и `Marshal.SizeOf` — классическая ловушка при P/Invoke, см. [[Interop и P-Invoke]].

### Паддинг: почему порядок полей меняет размер

Процессор читает выровненные данные быстрее (а на некоторых архитектурах — только выровненные). Поэтому компоновщик вставляет пустые байты, чтобы каждое поле начиналось с адреса, кратного его размеру.

```csharp
struct Bad   { public byte A; public long B; public byte C; }   // 24 байта
struct Good  { public byte A; public byte C; public long B; }   // 16 байт
```

```
Bad (порядок объявления сохраняется):
  ┌───┬───────────────────────┬───────────────────────────────┐
  │ A │  padding 7 байт       │            B (8)              │
  └───┴───────────────────────┴───────────────────────────────┘
  ┌───┬───────────────────────────────────────────────────────┐
  │ C │  padding 7 байт (выравнивание всей структуры до 8)     │
  └───┴───────────────────────────────────────────────────────┘
  Итого 24 байта, полезных — 10.

Good:
  ┌───┬───┬───────────────────┬───────────────────────────────┐
  │ A │ C │  padding 6 байт   │            B (8)              │
  └───┴───┴───────────────────┴───────────────────────────────┘
  Итого 16 байт.
```

Правило укладки полей вручную: **от больших к меньшим**. Массив на миллион элементов такой структуры — это разница в 8 МБ памяти и трафика через кеш.

### StructLayout

```csharp
// Явно задать порядок и упаковку
[StructLayout(LayoutKind.Sequential, Pack = 1)]
struct PackedHeader
{
    public byte  Version;   // offset 0
    public ushort Length;   // offset 1 — благодаря Pack = 1 без выравнивания
    public uint  Crc;       // offset 3
}                           // 7 байт вместо 8

// Разрешить рантайму раскладывать поля как ему удобнее
[StructLayout(LayoutKind.Auto)]
struct Optimized { public byte A; public long B; public byte C; }  // рантайм упакует в 16

// Наложение полей друг на друга (union из C)
[StructLayout(LayoutKind.Explicit)]
struct FloatBits
{
    [FieldOffset(0)] public float  AsFloat;
    [FieldOffset(0)] public uint   AsBits;
}
```

Что важно знать про значения по умолчанию:

- Компилятор C# помечает **структуры** как `sequential`, а **классы** как `auto`. То есть поля структуры по умолчанию идут в порядке объявления — именно поэтому пример с `Bad`/`Good` выше вообще что-то демонстрирует.
- Для `auto`-раскладки (классы, а также структуры с явным `LayoutKind.Auto`) рантайм имеет право **переставлять поля**, чтобы убрать паддинг и сгруппировать ссылки. Полагаться на порядок полей класса в памяти нельзя.
- `Pack = 1` экономит байты, но даёт невыровненный доступ — на горячем пути это может стоить дороже сэкономленной памяти. Используйте для парсинга бинарных форматов и interop, не для внутренних структур.
- `LayoutKind.Explicit` с перекрытием ссылочного и значимого поля рантайм запретит (это дыра в безопасности типов) — `TypeLoadException`.

## Семантика присваивания и передачи

### Присваивание

```csharp
struct SPoint { public int X, Y; }
class  CPoint { public int X, Y; }

var s1 = new SPoint { X = 1, Y = 2 };
var s2 = s1;          // скопированы 8 байт
s2.X = 100;
Console.WriteLine(s1.X);   // 1 — s1 не тронут

var c1 = new CPoint { X = 1, Y = 2 };
var c2 = c1;          // скопированы 8 байт АДРЕСА
c2.X = 100;
Console.WriteLine(c1.X);   // 100 — это один и тот же объект
```

```
ДО:  s1 [1|2]   s2 [ - ]          c1 [addr]──▶ obj{1,2} ◀──[addr] c2
ПОСЛЕ s2 = s1 и мутации:
     s1 [1|2]   s2 [100|2]        c1 [addr]──▶ obj{100,2} ◀─[addr] c2
      два независимых значения       одна общая цель у двух ссылок
```

### Передача в метод

По умолчанию **всё** в C# передаётся по значению. Для класса «значение» — это ссылка. Отсюда постоянная путаница.

```csharp
static void MutateFields(CPoint p) { p.X = 999; }   // видно снаружи: меняем общий объект
static void Reassign(CPoint p)     { p = new CPoint { X = 999 }; }  // НЕ видно: переприсвоили копию ссылки
static void ReassignRef(ref CPoint p) { p = new CPoint { X = 999 }; } // видно: работаем с самим слотом
```

| Модификатор | Что передаётся | Мутации видны вызывающему | Требует инициализации до вызова | Метод обязан присвоить |
|---|---|---|---|---|
| (нет) | копия значения | нет (для struct) | да | нет |
| `ref` | адрес слота | да | да | нет |
| `out` | адрес слота | да | нет | да |
| `in` | адрес слота, только чтение | нет (нельзя менять) | да | нет |
| `ref readonly` (параметр) | как `in`, но требует `ref`/`in` на месте вызова | нет | да | нет |

```csharp
// in — передать большую структуру без копирования, но запретить мутации
static double Length(in Matrix4x4 m) => /* ... */;

// ref — двусторонняя работа с чужим слотом
static void Swap<T>(ref T a, ref T b) => (a, b) = (b, a);

// out — вернуть несколько значений (классика: TryParse)
static bool TryParsePoint(string s, out SPoint p) { p = default; /* ... */ return true; }
```

### Защитные копии и readonly struct

`in` передаёт адрес, но компилятор обязан гарантировать, что метод не изменит значение вызывающего. Если структура **не** `readonly`, компилятор не может доказать, что вызываемый член её не мутирует, и вставляет **защитную копию** (defensive copy) — то самое копирование, которого мы избегали.

```csharp
struct Big               // НЕ readonly
{
    public double A, B, C, D, E, F, G, H;   // 64 байта
    public double Sum() => A + B + C + D + E + F + G + H;  // не readonly-член
}

static double Total(in Big b)
{
    // компилятор вставит: Big tmp = b; tmp.Sum();
    // на каждый вызов — копирование 64 байт
    return b.Sum() + b.Sum() + b.Sum();     // ТРИ копии
}
```

Лечится двумя способами:

```csharp
// Способ 1: readonly struct — все поля readonly, все члены неявно readonly
readonly struct BigOk
{
    public readonly double A, B, C, D, E, F, G, H;
    public double Sum() => A + B + C + D + E + F + G + H;   // защитных копий не будет
}

// Способ 2: точечно пометить члены readonly (C# 8+),
// если структуру целиком иммутабельной сделать нельзя
struct BigPartial
{
    public double A, B, C, D, E, F, G, H;
    public readonly double Sum() => A + B + C + D + E + F + G + H;
}
```

Те же защитные копии возникают при обращении к `readonly`-полю структурного типа и к `ref readonly` локальной переменной. Это самый частый источник «а почему структура медленнее класса» — измеряется через [[Как измерять: BenchmarkDotNet]] с `[MemoryDiagnoser]` и `[DisassemblyDiagnoser]`.

Мотивация цифрами: для структуры на 64 байта разница между «передали адрес» и «скопировали и передали адрес копии» — это 8 инструкций записи в память на вызов. В цикле на миллион итераций с тремя вызовами это 24 миллиона лишних записей. Компилятор не сообщает об этом никак — только дизассемблер или замер.

### ref readonly возврат

```csharp
readonly struct Vector3D { public readonly double X, Y, Z; /* ... */ }

class Scene
{
    private Vector3D[] _points = new Vector3D[1000];

    // Возвращаем ссылку на элемент, а не копию 24 байт
    public ref readonly Vector3D GetPoint(int i) => ref _points[i];
}

// Использование
ref readonly Vector3D p = ref scene.GetPoint(5);   // без копирования
Vector3D copy = scene.GetPoint(5);                 // с копированием — тоже законно
```

`ref readonly` — это «дай посмотреть, не трогай». Компилятор проверит, что вы не пишете в возвращённую ссылку, и не даст ей пережить владельца (ref safety). Похожая механика лежит в основе `Span<T>` — см. [[Span, ReadOnlySpan и Memory]].

## Равенство

### По умолчанию у классов

`Object.Equals` и `Object.operator ==` сравнивают **ссылки**: два объекта равны, только если это буквально один объект. Это разумный дефолт для сущностей с идентичностью (пользователь, заказ) и неудобный для значений (деньги, координата).

```csharp
class P { public int X; }
Console.WriteLine(new P { X = 1 } == new P { X = 1 });   // False
```

### По умолчанию у структур

`ValueType.Equals` сравнивает **поля**, но платит за это дорого. Механика в современном CoreCLR:

1. Рантайм проверяет, можно ли сравнить экземпляры побитово. Условие: в типе нет ссылочных полей и нет «дырок» от паддинга (структура плотно упакована), а вложенные поля не переопределяют `Equals` своим способом.
2. Если можно — быстрый путь: сравнение блока памяти целиком.
3. Если нельзя — **медленный путь через рефлексию**: перебор полей и вызов `Equals` на каждом. Это десятки-сотни наносекунд и аллокации от боксинга полей.

```csharp
struct HasRef { public int Id; public string Name; }   // ссылочное поле → медленный путь
struct HasPad { public byte A; public long B; }        // паддинг → медленный путь
struct Blit   { public int A; public int B; }          // плотно, без ссылок → быстрый путь
```

Дополнительно `ValueType.Equals(object)` принимает `object`, то есть сравнение через него **боксит** обе стороны. И `ValueType.GetHashCode()` исторически строился по первому подходящему полю, что давало катастрофическое распределение (все `struct Money { decimal Amount; Currency C; }` с одинаковой суммой в разных валютах — в одну корзину). Современная реализация хеширует все байты, когда может, но полагаться на неё в горячем коде всё равно не стоит.

**Вывод: для любой структуры, которую вы сравниваете или кладёте в `Dictionary`/`HashSet`, переопределяйте `Equals`/`GetHashCode` и реализуйте `IEquatable<T>` — или возьмите `record struct`, который сделает это за вас.**

```csharp
readonly struct Money : IEquatable<Money>
{
    public readonly decimal Amount;
    public readonly string Currency;

    public Money(decimal amount, string currency) => (Amount, Currency) = (amount, currency);

    // Типизированный Equals — без боксинга, вызывается EqualityComparer<Money>.Default
    public bool Equals(Money other)
        => Amount == other.Amount && Currency == other.Currency;

    // Переопределение object.Equals — чтобы не унаследовать медленный ValueType.Equals
    public override bool Equals(object? obj) => obj is Money m && Equals(m);

    public override int GetHashCode() => HashCode.Combine(Amount, Currency);

    public static bool operator ==(Money a, Money b) => a.Equals(b);
    public static bool operator !=(Money a, Money b) => !a.Equals(b);
}
```

Подробнее о контракте — [[Object: Equals, GetHashCode, ToString]] и [[Сравнение объектов: IEquatable, IComparable, компараторы]].

### record class, record struct, readonly record struct

| Конструкция | Категория | Равенство | Мутабельность по умолчанию | `with` | Наследование |
|---|---|---|---|---|---|
| `class` | ссылочный | по ссылке | мутабельный | нет | да |
| `record class` (= `record`) | ссылочный | по значению (все поля) | init-only для позиционных | да | да, с учётом `EqualityContract` |
| `struct` | значимый | `ValueType.Equals` (медленно) | мутабельный | нет | нет |
| `record struct` | значимый | сгенерированный `IEquatable<T>` | **мутабельный** (позиционные — get/set) | да | нет |
| `readonly record struct` | значимый | сгенерированный `IEquatable<T>` | иммутабельный | да | нет |

```csharp
public readonly record struct Point(int X, int Y);
// компилятор сгенерирует: Equals(Point), Equals(object), GetHashCode,
// ==, !=, ToString() вида "Point { X = 1, Y = 2 }", Deconstruct, IEquatable<Point>

var p1 = new Point(1, 2);
var p2 = p1 with { Y = 5 };        // копия с изменением, оригинал цел
Console.WriteLine(p1 == new Point(1, 2));   // True — сравнение по значению
```

Практика: для маленького иммутабельного значения `readonly record struct` — почти всегда лучший выбор. Мутабельный `record struct` — редкий случай (буфер, счётчик). Подробности — [[Записи (record) и структуры]].

## default(T) и new T()

Для структуры `default` — это «все байты в ноль». Никакой конструктор при этом не выполняется.

```csharp
struct Temperature
{
    public double Celsius;
    public Temperature() => Celsius = 20.0;    // C# 10+: конструктор без параметров разрешён
}

var a = new Temperature();       // 20.0  — конструктор ВЫЗВАН
var b = default(Temperature);    // 0.0   — конструктор НЕ вызван
Temperature[] arr = new Temperature[3];
Console.WriteLine(arr[0].Celsius);           // 0.0 — массив просто обнулён
Console.WriteLine(Activator.CreateInstance<Temperature>().Celsius);  // 20.0 — вызван
```

Где ещё структура появится «мимо конструктора»:

- поле класса, которое не инициализировали явно;
- `new T[n]`, `Array.Resize`, `List<T>` с `Capacity`;
- `default` в generic-коде (`T value = default;`);
- `stackalloc` без инициализатора;
- значение из `Dictionary.TryGetValue`, когда ключа нет.

Отсюда правило проектирования: **`default` должно быть валидным состоянием структуры**. Если у вас `struct Percent`, где допустимы 0..100 — всё в порядке. Если `struct NonEmptyString`, где `null` внутри недопустим — структура для этого не подходит, потому что вы не можете запретить `default`.

```csharp
// Плохо: невалидное состояние достижимо и не отлавливается
public readonly struct Email
{
    private readonly string _value;
    public Email(string v) => _value = v ?? throw new ArgumentNullException(nameof(v));
    public int Length => _value.Length;    // NullReferenceException при default(Email)
}

// Лучше: сделать default безопасным
public readonly struct Email
{
    private readonly string? _value;
    public Email(string v) => _value = v ?? throw new ArgumentNullException(nameof(v));
    public string Value => _value ?? string.Empty;
    public bool IsEmpty => _value is null;
}
```

## Nullable&lt;T&gt;

`int?` — это `Nullable<int>`, обычная структура:

```csharp
public struct Nullable<T> where T : struct
{
    private readonly bool hasValue;
    internal T value;
    public bool HasValue => hasValue;
    public T Value => hasValue ? value : throw new InvalidOperationException();
    // ...
}
```

Ключевые особенности:

```csharp
int? x = 5;
object o = x;                     // боксится ЗНАЧЕНИЕ int, а не Nullable<int>
Console.WriteLine(o.GetType());   // System.Int32 — не System.Nullable`1[System.Int32]
Console.WriteLine(o is int);      // True
Console.WriteLine(o is int?);     // True (компилятор сводит к тому же)

int? y = null;
object o2 = y;                    // боксинг null-состояния даёт NULL-ссылку
Console.WriteLine(o2 is null);    // True
Console.WriteLine(y.GetType());   // NullReferenceException!  Нечего вызывать GetType на

int? a = null, b = null;
Console.WriteLine(a == b);        // True — lifted-оператор: оба «пустые»
Console.WriteLine(a > b);         // False — сравнения с null всегда false
Console.WriteLine(a.Equals(b));   // True
```

Не путайте с nullable reference types (`string?`) — это **только статический анализ компилятора**, в скомпилированном коде ничего не меняется, `string?` и `string` — один и тот же тип на уровне IL (различаются лишь атрибутами метаданных `NullableAttribute`). Подробно — [[Nullable reference types]].

## Когда выбирать struct

Официальные рекомендации Microsoft и объяснение, откуда они взялись:

| Правило | Почему именно так | Когда нарушают осознанно |
|---|---|---|
| Логически представляет одно значение | Копирование по значению должно быть семантически осмысленным. Копия «денег» — это те же деньги; копия «пользователя» — уже другой пользователь | почти никогда |
| Размер до 16 байт | Два машинных слова помещаются в регистры; копирование стоит одну-две инструкции | большие математические структуры (`Matrix4x4`) — передают по `in`/`ref` |
| Иммутабельность | Мутабельная структура даёт баги «изменил копию»; иммутабельная безопасна при любом копировании | буферы, аккумуляторы в горячем цикле |
| Не боксится часто | Один боксинг съедает всю экономию и добавляет 24 байта в gen0 | если боксинг единичный, а экземпляров миллионы — всё равно выгодно |

Простое операционное правило: **пишите `class` по умолчанию**. Переходите на `struct`, когда выполнено всё сразу: тип маленький, иммутабельный, создаётся в больших количествах, и профилировщик показывает, что аллокации мешают.

И зеркальный случай: большая `readonly struct` вполне легитимна, если её всегда передают по `in`/`ref` и хранят в массиве. Это даёт лучшую локальность кеша, чем массив ссылок, — см. [[Стек и куча: что где лежит]].

## Код

Сводный пример с обоими вариантами и измерением:

```csharp
using System.Runtime.CompilerServices;

// Значимый тип, спроектированный правильно
public readonly record struct Rgb(byte R, byte G, byte B)
{
    public int ToArgb() => (0xFF << 24) | (R << 16) | (G << 8) | B;
}

// Ссылочный тип для сущности с идентичностью
public sealed class Pixel
{
    public required int X { get; init; }
    public required int Y { get; init; }
    public Rgb Color { get; set; }
}

public static class Demo
{
    public static void Show()
    {
        Console.WriteLine(Unsafe.SizeOf<Rgb>());        // 3
        Console.WriteLine(Unsafe.SizeOf<Pixel>());      // 8 — размер ссылки

        // Массив структур: ОДИН объект в куче, 1 000 000 значений подряд
        var buffer = new Rgb[1_000_000];                // ~3 МБ + заголовок массива

        // Массив классов: один объект-массив + 1 000 000 объектов по 24+ байта
        var pixels = new Pixel[1_000_000];              // 8 МБ только под ссылки

        // Работа с элементом массива структур без копирования
        ref Rgb first = ref buffer[0];
        first = first with { R = 255 };                 // пишем прямо в массив

        // Передача большой структуры без копий
        Console.WriteLine(Brightness(in buffer[0]));
    }

    private static double Brightness(in Rgb c)
        => 0.299 * c.R + 0.587 * c.G + 0.114 * c.B;
}
```

## IL: что видит рантайм

Разница между категориями видна прямо в байткоде.

```csharp
class C { public int X; }
struct S { public int X; }

C c = new C();
S s = new S();
S t = new S(5);
```

```il
// new C() — выделение в куче и вызов конструктора одной инструкцией
IL_0000: newobj     instance void C::.ctor()
IL_0005: stloc.0

// new S() без объявленного конструктора — просто обнуление слота, аллокации НЕТ
IL_0006: ldloca.s   s          // адрес локальной переменной
IL_0008: initobj    S

// new S(5) — адрес слота + вызов конструктора «поверх» существующей памяти
IL_000e: ldloca.s   t
IL_0010: ldc.i4.5
IL_0011: call       instance void S::.ctor(int32)
```

Вызов метода:

```csharp
c.ToString();   // ссылочный тип
s.ToString();   // структура с переопределённым ToString
```

```il
// На ссылочном типе — callvirt даже для невиртуального метода:
// это даёт бесплатную проверку на null
IL_0000: ldloc.0
IL_0001: callvirt   instance string [System.Runtime]System.Object::ToString()

// На структуре с ПЕРЕОПРЕДЕЛЁННЫМ ToString — прямой call по адресу слота.
// Ни боксинга, ни виртуальной диспетчеризации
IL_0006: ldloca.s   s
IL_0008: call       instance string S::ToString()
```

Обобщённый код и `constrained.`:

```csharp
static string Describe<T>(T value) => value.ToString()!;
```

```il
IL_0000: ldarga.s   value
IL_0002: constrained. !!T
IL_0008: callvirt   instance string [System.Runtime]System.Object::ToString()
```

Префикс `constrained.` говорит JIT: «получатель — адрес значения типа `T`». Если `T` — структура, **переопределившая** `ToString`, JIT вызовет её метод напрямую, без боксинга. Если структура метод не переопределила, вызвать унаследованный от `ValueType`/`Object` метод можно только на объекте — и JIT вставит боксинг. Отсюда практическое правило: **переопределяйте `ToString`, `Equals` и `GetHashCode` на структурах**, иначе они будут боксироваться в обобщённом коде. Подробности — [[Boxing и unboxing]].

Копирование:

```il
// s2 = s1 для структуры: значение целиком через стек вычислений
IL_0000: ldloc.0
IL_0001: stloc.1

// присваивание в поле объекта — stfld копирует всю структуру
IL_0002: ldloc.2          // this
IL_0003: ldloc.0          // s1
IL_0004: stfld            valuetype S Holder::Field

// работа по адресу — без копий
IL_0009: ldflda           valuetype S Holder::Field   // адрес поля
IL_000e: call             instance void S::Mutate()
```

## Полная таблица сравнения

| Критерий | Значимый тип (struct) | Ссылочный тип (class) |
|---|---|---|
| Базовый тип | `System.ValueType` | `System.Object` |
| Что в переменной | сами данные | адрес (8 байт на x64) |
| Где физически | там, где объявлена переменная/владелец | управляемая куча (иногда стек — escape analysis) |
| Накладные расходы | нет | 16 байт заголовка, минимум 24 байта объект |
| Присваивание | копия всех полей | копия ссылки, объект общий |
| Передача в метод | копия (или адрес при `ref`/`in`/`out`) | копия ссылки |
| Значение по умолчанию | все поля обнулены, не `null` | `null` |
| Может быть `null` | только через `Nullable<T>` или `T?` | да |
| Наследование | нет, неявно `sealed` | да |
| Реализация интерфейсов | да (приведение к интерфейсу боксит) | да |
| Равенство по умолчанию | по полям, часто через рефлексию | по ссылке |
| `GetHashCode` по умолчанию | по содержимому | случайный, кешируется в заголовке |
| Участие в GC | не отслеживается отдельно | отслеживается, влияет на паузы |
| Финализатор | нельзя | можно (нежелательно, см. [[Финализаторы и SafeHandle]]) |
| Массив из N элементов | 1 объект, N значений подряд | 1 объект + N объектов |
| Атомарность присваивания | только для типов ≤ размера слова | ссылка всегда пишется атомарно |
| Виртуальный вызов | нет (тип известен статически) | да, через MethodTable |
| Стоимость создания | ~0 (обнуление слота) | аллокация + будущая работа GC |

> [!warning] Подводные камни
> **1. Мутабельная структура в свойстве.** Свойство возвращает **копию**, поэтому мутация уходит в никуда:
> ```csharp
> struct Counter { public int Value; public void Inc() => Value++; }
> class Holder { public Counter C { get; set; } }
>
> var h = new Holder();
> h.C.Inc();   // ошибка компиляции: нельзя менять возвращаемое значение
> var tmp = h.C; tmp.Inc(); h.C = tmp;   // приходится так
> ```
> С полем компилятор пропустит `h.CField.Inc()`, потому что поле — это адрес. Разное поведение поля и свойства при одинаковом синтаксисе — главная причина, почему структуры делают иммутабельными.
>
> **2. Структура в `foreach` по коллекции.** Переменная цикла — копия элемента. Мутация внутри цикла не попадёт в коллекцию:
> ```csharp
> var arr = new Counter[3];
> foreach (var c in arr) c.Inc();      // ничего не изменилось
> for (int i = 0; i < arr.Length; i++) arr[i].Inc();  // а вот так работает: индексатор массива даёт адрес
> ```
>
> **3. Структура без переопределённого `Equals` в `Dictionary`.** Работать будет, но каждое сравнение пойдёт через `ValueType.Equals` с рефлексией. На словаре в сотню тысяч записей это разница в порядок величины. Реализуйте `IEquatable<T>` — `EqualityComparer<T>.Default` подхватит его автоматически.
>
> **4. `readonly` поле структурного типа.** Обращение к его члену создаёт защитную копию, даже для чтения. Если структура большая и не `readonly struct`, `readonly`-поле работает медленнее обычного.
>
> **5. Большая структура как параметр асинхронного метода.** Она станет полем машины состояний, которая при первом настоящем `await` уедет в кучу целиком. Экономии не будет, см. [[async и await: как это работает на самом деле]].

> [!example] Как делают в бою
> - Идентификаторы доменных сущностей — `readonly record struct OrderId(Guid Value)`. Даёт типобезопасность (нельзя передать `CustomerId` вместо `OrderId`) без единой аллокации.
> - Деньги, координаты, диапазоны дат, единицы измерения — `readonly record struct`. Всё, что «одно значение» и меньше 24 байт.
> - Результаты парсинга и промежуточные структуры в горячем цикле — `struct` + `Span<T>`, чтобы не аллоцировать вовсе.
> - Сущности домена, агрегаты, DTO с десятком полей, всё, что живёт в DI-контейнере, — `class` без обсуждений.
> - Массивы структур вместо массивов классов в вычислительных ядрах (обработка изображений, физика, парсинг протоколов). Выигрыш идёт не от «нет аллокаций», а от локальности кеша.
> - Правило код-ревью: если структура мутабельная и не `ref struct` — требуется обоснование в комментарии.

## Вопросы с собеседований

> [!question]- В чём принципиальная разница между значимым и ссылочным типом?
> Переменная значимого типа содержит сами данные, переменная ссылочного — адрес объекта в управляемой куче. Из этого следует всё остальное: присваивание копирует данные против копирования адреса, значение по умолчанию — обнулённые поля против `null`, равенство по умолчанию — по полям против по ссылке, наличие 16 байт заголовка у объекта против его отсутствия у структуры. Формально: значимые типы наследуются от `System.ValueType`, ссылочные — напрямую от `System.Object`.

> [!question]- Правда ли, что структуры всегда лежат на стеке?
> Нет, это неверное упрощение. Место жизни данных определяется не категорией типа, а тем, где живёт владелец. Поле структуры внутри класса лежит в куче, элемент `Point[]` лежит в куче, локальная переменная, захваченная замыканием, становится полем closure-класса в куче, боксированная структура — в куче. И наоборот: JIT в .NET 10 умеет размещать на стеке объекты ссылочных типов, если escape analysis доказал, что они не убегают из метода. Подробный разбор — в заметке [[Стек и куча: что где лежит]].

> [!question]- Почему `ValueType.Equals` считается медленным?
> Потому что у него два пути. Быстрый — побитовое сравнение блока памяти — доступен только для плотно упакованных структур без ссылочных полей и без паддинга. Во всех остальных случаях рантайм идёт через рефлексию: перебирает поля и вызывает `Equals` на каждом, что даёт боксинг и десятки-сотни наносекунд на сравнение. Лечится реализацией `IEquatable<T>` и переопределением `Equals(object)`/`GetHashCode`, либо использованием `record struct`.

> [!question]- Что такое защитная копия и когда она возникает?
> Компилятор вставляет скрытое копирование структуры, когда обязан гарантировать неизменность значения, но не может доказать, что вызываемый член его не изменит. Возникает при вызове не-`readonly` члена не-`readonly` структуры через параметр `in`, через `readonly`-поле, через `ref readonly` локальную переменную или через `in`-элемент. Убирается объявлением `readonly struct` или пометкой конкретных членов как `readonly`. Это главная причина, по которой «оптимизация через `in`» иногда делает код медленнее.

> [!question]- Чем `default(S)` отличается от `new S()` в C# 10 и новее?
> `default(S)` всегда даёт байтовый ноль и никогда не вызывает конструктор. `new S()` вызовет объявленный конструктор без параметров, если он есть, и обнулит память, если его нет. Разница появилась в C# 10, когда структурам разрешили объявлять `public S()`. При этом `new S[10]`, `default`, `stackalloc` и неинициализированные поля класса конструктор не вызывают, а `Activator.CreateInstance<S>()` — вызывает. Практический вывод: `default` должно быть валидным состоянием структуры, иначе тип спроектирован неправильно.

> [!question]- Почему `string` — ссылочный тип, но `==` сравнивает содержимое?
> Потому что `string` перегружает `operator ==`, вызывая ординальное сравнение символов. Ссылочная семантика при этом никуда не делась: `ReferenceEquals` для двух одинаковых по содержимому строк, созданных в рантайме, вернёт `false`. Отдельно работает интернирование: строковые литералы складываются в общий пул, поэтому одинаковые литералы — это один объект. Строку нельзя использовать как объект блокировки именно потому, что литерал разделяется со всем процессом.

> [!question]- Что произойдёт при боксинге `int?` со значением `null`?
> Получится обычная `null`-ссылка, а не объект-обёртка. Боксинг `Nullable<T>` — особый случай в CLR: при `HasValue == true` в кучу упаковывается само значение `T` (то есть `((object)(int?)5).GetType()` вернёт `System.Int32`), при `HasValue == false` результатом становится `null`. Обратная операция тоже работает: боксированный `int` можно распаковать в `int?`, а `null` — в `int?` со значением `null`.

> [!question]- Когда стоит писать `struct` вместо `class`?
> Когда выполнены все условия сразу: тип логически представляет одно значение, размер до 16 байт, тип иммутабельный, и он не будет часто боксироваться. По умолчанию всегда пишется `class` — структура берётся как оптимизация под конкретный замеренный сценарий. Осознанное нарушение правила про размер допустимо для больших `readonly struct`, которые всегда передаются по `in`/`ref` и хранятся в массивах ради локальности кеша.

## Задачи

### Задача 1. Найти четыре копии

Сколько раз структура `Big` будет скопирована при выполнении `Run()`? Как переписать, чтобы копий не было?

```csharp
struct Big
{
    public long A, B, C, D;
    public long Sum() => A + B + C + D;
}

class Holder
{
    public readonly Big Field = new Big { A = 1, B = 2, C = 3, D = 4 };
    public Big Prop => Field;
}

static long Run(Holder h)
{
    Big local = h.Prop;
    return local.Sum() + h.Field.Sum() + Total(in local);
}

static long Total(in Big b) => b.Sum();
```

> [!success]- Решение
> Копий четыре:
> 1. `h.Prop` — свойство возвращает `Field` по значению, копия при возврате.
> 2. `Big local = h.Prop` — копия при присваивании (JIT может её устранить, но в IL она есть).
> 3. `h.Field.Sum()` — `Field` объявлено `readonly`, а `Sum()` не помечен `readonly`, значит компилятор делает защитную копию.
> 4. `Total(in local)` внутри вызывает `b.Sum()` на не-`readonly` члене не-`readonly` структуры через `in` — ещё одна защитная копия.
>
> ```csharp
> readonly struct Big                       // все поля readonly, все члены неявно readonly
> {
>     public readonly long A, B, C, D;
>     public Big(long a, long b, long c, long d) => (A, B, C, D) = (a, b, c, d);
>     public long Sum() => A + B + C + D;   // защитных копий больше не будет
> }
>
> class Holder
> {
>     private readonly Big _field = new(1, 2, 3, 4);
>     public ref readonly Big Field => ref _field;   // возврат по ссылке вместо копии
> }
>
> static long Run(Holder h)
> {
>     ref readonly Big local = ref h.Field;          // без копирования
>     return local.Sum() + h.Field.Sum() + Total(in local);
> }
> ```
> Осталось ноль копий: `readonly struct` снимает защитные копии, `ref readonly` убирает копию при возврате.

### Задача 2. Размер структуры

Не запуская код, определите размер каждой структуры на x64 и объясните разницу.

```csharp
struct A { public byte X; public byte Y; public byte Z; }
struct B { public int X; public byte Y; }
struct C { public byte X; public int Y; public byte Z; public long W; }
struct D { public string Name; public byte Flag; }
struct E { public byte Flag; public DateTime Stamp; }
```

> [!success]- Решение
> ```csharp
> Unsafe.SizeOf<A>();  // 3  — три байта подряд, выравнивание структуры = 1
> Unsafe.SizeOf<B>();  // 8  — int (0..3), byte (4), паддинг до кратного 4
> Unsafe.SizeOf<C>();  // 24 — byte(0) + pad(1..3) + int(4..7) + byte(8) + pad(9..15) + long(16..23)
> Unsafe.SizeOf<D>();  // 16 — ссылка 8 байт, byte, паддинг до кратного 8
> Unsafe.SizeOf<E>();  // 16 — byte, паддинг 7, DateTime внутри это один ulong = 8 байт
> ```
> Правило: выравнивание всей структуры равно максимальному выравниванию её полей, а общий размер округляется вверх до кратного этому значению. Структура `C`, переписанная как `long W; int Y; byte X; byte Z;`, займёт 16 байт вместо 24 — на миллионе элементов это 8 МБ экономии.

### Задача 3. Что выведет программа

```csharp
struct Item { public int Count; }

var list = new List<Item> { new Item { Count = 1 } };
var array = new Item[] { new Item { Count = 1 } };

foreach (var i in array) { /* ничего */ }
array[0].Count = 10;
list[0] = new Item { Count = 20 };

Console.WriteLine(array[0].Count);
Console.WriteLine(list[0].Count);

// а эта строка не компилируется — почему?
// list[0].Count = 30;
```

> [!success]- Решение
> Выведет `10` и `20`.
>
> `array[0].Count = 10` работает, потому что индексатор массива — это не метод, а инструкция IL, дающая **адрес** элемента. Компилятор пишет прямо в память массива.
>
> `list[0].Count = 30` не компилируется, потому что индексатор `List<T>` — обычное свойство, его `get` возвращает **копию** элемента. Присвоить полю временной копии бессмысленно, и компилятор это запрещает (CS1612). Приходится читать элемент, менять и класть обратно — либо использовать `CollectionsMarshal.AsSpan(list)[0].Count = 30`, который даёт доступ к внутреннему массиву по ссылке.
>
> Это ровно тот случай, ради которого структуры делают иммутабельными: одинаковый синтаксис `x[0].Field = v` работает для массива и не работает для списка.

### Задача 4. Ловушка равенства

Почему второе сравнение возвращает `false`, и как это исправить?

```csharp
struct Version2 { public int Major; public int Minor; }

var set = new HashSet<Version2>();
set.Add(new Version2 { Major = 1, Minor = 0 });
Console.WriteLine(set.Contains(new Version2 { Major = 1, Minor = 0 }));  // ?

struct Tagged { public int Id; public string Tag; }
var set2 = new HashSet<Tagged>();
set2.Add(new Tagged { Id = 1, Tag = "a" });
Console.WriteLine(set2.Contains(new Tagged { Id = 1, Tag = string.Concat("a", "") }));  // ?
```

> [!success]- Решение
> Оба вернут `true` — но по совершенно разной цене, и второй случай хрупок.
>
> `Version2` плотно упакована и не содержит ссылок, поэтому `ValueType.Equals` идёт быстрым побитовым путём, а хеш считается по всем байтам. `Tagged` содержит `string`, поэтому и `Equals`, и `GetHashCode` идут медленным путём через рефлексию: перебор полей с боксингом каждого. Работает корректно, но в десятки раз медленнее и с аллокациями на каждой операции со множеством.
>
> Правильное решение — не полагаться на дефолт:
> ```csharp
> readonly record struct Version2(int Major, int Minor);
> readonly record struct Tagged(int Id, string Tag);
> ```
> Компилятор сгенерирует `IEquatable<T>.Equals`, `GetHashCode` через `EqualityComparer<T>.Default` по каждому полю, `==`/`!=` и `ToString`. `HashSet<T>` и `Dictionary<T,V>` автоматически подхватят типизированный `Equals` без боксинга.

## Итог

- Значимый тип хранит данные в переменной, ссылочный — адрес объекта в куче. Всё остальное — следствия.
- Объект на x64 стоит минимум 24 байта: 8 байт заголовка (sync block, хеш, биты GC), 8 байт указателя на MethodTable, дальше поля с выравниванием до 8.
- У структуры нет заголовка, только поля. Порядок полей влияет на размер из-за паддинга: укладывайте от больших к меньшим.
- Присваивание структуры копирует данные, присваивание класса копирует ссылку. `ref`/`in`/`out` дают доступ к слоту вызывающего; `in` без `readonly struct` порождает защитные копии.
- `ValueType.Equals`/`GetHashCode` по умолчанию медленные. Для любой структуры, участвующей в сравнениях, реализуйте `IEquatable<T>` или берите `readonly record struct`.
- `default(T)` для структуры не вызывает конструктор — проектируйте так, чтобы нулевое состояние было валидным.
- По умолчанию `class`. `struct` — осознанная оптимизация: маленький, иммутабельный, массовый, не боксится.
