# Дженерики в CLR: как устроены

> [!abstract] Коротко
> В отличие от Java, где дженерики стираются при компиляции, в .NET они существуют **в рантайме**: `List<int>` и `List<string>` — разные типы со своими таблицами методов и своими статическими полями. Для значимых типов JIT генерирует **отдельную специализацию** машинного кода (`List<int>` работает с `int` напрямую, без упаковки и без приведений), а все ссылочные типы разделяют одну общую версию кода, потому что ссылка везде одинакова по размеру. Отсюда практические следствия: обобщённый код над структурами быстрее интерфейсного, `typeof(List<int>) != typeof(List<string>)`, а `static`-поле в обобщённом классе своё у каждой закрытой конструкции — это удобный приём для кеширования.

## Зачем это нужно

Три практических вопроса:

- почему `void M<T>(T x) where T : IShape` не упаковывает структуру, а `void M(IShape x)` упаковывает;
- почему `Dictionary<int, string>` работает быстрее, чем `Hashtable`, не только из-за типобезопасности;
- почему `MakeGenericType` ломается под Native AOT и что с этим делать.

## Дженерики существуют в рантайме

```csharp
Console.WriteLine(typeof(List<int>) == typeof(List<string>));    // False — разные типы
Console.WriteLine(typeof(List<>).IsGenericTypeDefinition);        // True — открытый тип
Console.WriteLine(typeof(List<int>).GetGenericTypeDefinition() == typeof(List<>));   // True

// Информация о параметрах типа доступна в рантайме
foreach (var arg in typeof(Dictionary<string, int>).GetGenericArguments())
    Console.WriteLine(arg.Name);       // String, Int32
```

В метаданных сборки хранится **открытое** определение (`List<>`) с параметрами типа и ограничениями; закрытые конструкции (`List<int>`) создаются рантаймом по мере необходимости. Это принципиальное отличие от стирания типов в Java, где `List<Integer>` и `List<String>` в байт-коде неразличимы и `new T[]` невозможен в принципе.

Что даёт наличие дженериков в рантайме:

- **типобезопасность сохраняется** после компиляции: нельзя положить `string` в `List<int>` даже через рефлексию;
- **значимые типы не упаковываются** — это главный выигрыш по производительности;
- **рефлексия видит параметры типа**, поэтому работают контейнеры DI, сериализаторы и ORM;
- **можно создавать типы динамически**: `typeof(List<>).MakeGenericType(typeof(int))`.

## Специализация кода

Ключевой механизм: как JIT генерирует машинный код для `Method<T>`.

```
Method<int>     → своя копия машинного кода: int лежит по значению, размер 4 байта
Method<double>  → своя копия: double, 8 байт
Method<Point>   → своя копия: структура целиком, размер по её полям

Method<string>  ┐
Method<Order>   ├─► ОДНА общая копия (canonical, __Canon): все ссылки одного размера,
Method<byte[]>  ┘   а конкретный тип берётся из скрытого параметра
```

Причина проста: машинный код зависит от размера и раскладки данных. Для ссылочных типов это всегда указатель, поэтому одна версия обслуживает всех; для значимых типов раскладка разная, и нужна отдельная компиляция.

Практические следствия:

```csharp
// Без упаковки: JIT сделал версию под Point, вызов Area разрешается статически
static double Sum<T>(ReadOnlySpan<T> shapes) where T : IShape
{
    double total = 0;
    foreach (var s in shapes) total += s.Area;      // constrained call, обычно встраивается
    return total;
}

// С упаковкой: каждый элемент приводится к интерфейсу
static double Sum(ReadOnlySpan<IShape> shapes) { /* ... */ }
```

Цена специализации — **раздувание кода**: каждый значимый тип-аргумент даёт свою копию машинного кода, что увеличивает размер и давление на кеш инструкций. Для двух-трёх типов это выгодно; для обобщённого метода, инстанцированного двадцатью структурами, стоит подумать.

### Статические поля

```csharp
public static class Counter<T>
{
    public static int Value;               // СВОЁ поле у каждой закрытой конструкции
}

Counter<int>.Value = 1;
Counter<string>.Value = 2;
Console.WriteLine(Counter<int>.Value);      // 1 — независимы
```

Это регулярно используют как кеш «по типу», который не требует словаря и блокировок:

```csharp
internal static class TypeCache<T>
{
    // Вычисляется один раз на тип, дальше — чтение поля, без словаря и хеширования
    public static readonly string Name = typeof(T).FullName ?? typeof(T).Name;
    public static readonly bool IsSimple = typeof(T).IsPrimitive || typeof(T) == typeof(string);
}
```

Приём быстрее `ConcurrentDictionary<Type, ...>` и широко применяется в сериализаторах.

## Ограничения в рантайме

```csharp
where T : struct              // значимый тип; включает специализацию
where T : class               // ссылочный тип
where T : notnull             // ни null-ссылка, ни Nullable
where T : unmanaged           // структура без ссылок — можно stackalloc и указатели
where T : new()               // есть конструктор без параметров
where T : IShape              // реализует интерфейс — constrained call без упаковки
where T : Base                // наследник
where T : allows ref struct   // C# 13: допускает Span<T> и другие ref struct
where T : IParsable<T>        // статические абстрактные члены (C# 11)
```

Ограничения хранятся в метаданных и проверяются как компилятором, так и рантаймом при создании закрытого типа. Наиболее важное для производительности — ограничение интерфейсом: оно превращает виртуальный вызов в `constrained.callvirt`, который для значимого типа разрешается напрямую, без упаковки.

### Обобщённая математика

Статические абстрактные члены интерфейсов (C# 11) позволили написать то, что раньше требовало `dynamic` или генерации кода:

```csharp
static T Average<T>(ReadOnlySpan<T> values) where T : INumber<T>
{
    T sum = T.Zero;
    foreach (var v in values) sum += v;
    return sum / T.CreateChecked(values.Length);
}

Console.WriteLine(Average<int>([1, 2, 3]));
Console.WriteLine(Average<decimal>([1.5m, 2.5m]));
```

Для каждого значимого типа JIT создаёт свою специализацию, где операции компилируются в обычные машинные инструкции — то есть абстракция бесплатна ([[Интерфейсы]]).

## Вариантность

```csharp
public interface IProducer<out T> { T Get(); }        // ковариантность: только «наружу»
public interface IConsumer<in T> { void Accept(T item); }   // контравариантность: только «внутрь»

IProducer<object> producer = new Producer<string>();   // ок: строку можно отдать как object
IConsumer<string> consumer = new Consumer<object>();   // ок: потребитель object примет string
```

Вариантность работает **только для ссылочных типов**: `IEnumerable<int>` нельзя присвоить `IEnumerable<object>`, потому что это потребовало бы упаковки каждого элемента, а такое преобразование не может быть бесплатным приведением ссылки.

Массивы ковариантны исторически и небезопасно (проверка при записи в рантайме), интерфейсы — безопасно, потому что вариантность разрешена только там, где параметр используется в одном направлении ([[Дженерики: ограничения и вариантность]]).

## Дженерики и рефлексия

```csharp
// Создание закрытого типа в рантайме
Type openType = typeof(Repository<>);
Type closed = openType.MakeGenericType(typeof(Order));
object repo = Activator.CreateInstance(closed)!;

// Вызов обобщённого метода
MethodInfo open = typeof(Helper).GetMethod(nameof(Helper.Process))!;
MethodInfo closedMethod = open.MakeGenericMethod(typeof(Order));
closedMethod.Invoke(null, [order]);
```

Так работают DI-контейнеры (регистрация `typeof(IRepository<>)` с открытым типом), сериализаторы и валидаторы. Но у этого есть цена и ограничение:

- **Медленно**: создание закрытого типа и вызов через `Invoke` в сотни раз дороже прямого вызова; результат обязательно кешируют (например, через `TypeCache<T>` или скомпилированный делегат).
- **Native AOT**: специализация под значимый тип, не встречающийся статически в коде, не может быть создана в рантайме — JIT-компилятора нет. `MakeGenericType(typeof(SomeStruct))` бросит исключение, если такая комбинация не была сгенерирована при публикации. Для ссылочных типов ситуация мягче: работает общая канонная версия ([[Native AOT: когда стоит]]).

Отсюда общее направление платформы: вместо рефлексии по дженерикам — генераторы исходного кода, которые создают нужные закрытые типы на этапе компиляции ([[Source Generators]]).

> [!warning] Подводные камни
> - **`typeof(List<int>) == typeof(List<string>)` — `false`.** Это разные типы; ожидание «одного типа» приходит из Java.
> - **Статическое поле в обобщённом классе своё на каждый тип.** Полезно для кеша, но неожиданно, если рассчитывали на общий счётчик.
> - **Раздувание кода при многих значимых типах.** Двадцать специализаций тяжёлого метода — заметный рост размера и промахи кеша инструкций.
> - **Обобщённые виртуальные методы дороги.** Комбинация виртуального вызова и специализации требует поиска в таблице; в горячем коде их избегают.
> - **`MakeGenericType` под AOT.** Для значимых типов, не встречающихся статически, специализации не существует.
> - **Вариантность и значимые типы.** `IEnumerable<int>` не приводится к `IEnumerable<object>` — нужна упаковка, а бесплатного приведения ссылки здесь нет.
> - **Ограничение `new()` в горячем коде.** Оно реализуется через `Activator.CreateInstance`, что медленнее прямого `new`; лучше принимать фабрику-делегат.

> [!example] Как делают в бою
> Главное практическое применение знаний об устройстве дженериков — выбор между `T where T : IFoo` и параметром-интерфейсом. В библиотечном и горячем коде выбирают обобщённую форму: она убирает упаковку структур и позволяет встроить вызов. В прикладном коде разница незаметна, и интерфейсный параметр читается лучше.
> Второй приём — кеш по типу через статическое поле обобщённого класса (`Cache<T>.Value`): он быстрее словаря по `Type` и не требует блокировок. Так кешируют метаданные сериализации, имена таблиц, скомпилированные делегаты.
> Третий — регистрация открытых обобщённых типов в DI (`services.AddScoped(typeof(IRepository<>), typeof(EfRepository<>))`), которая избавляет от десятков однотипных регистраций.
> При движении в сторону Native AOT именно дженерики через рефлексию оказываются главным препятствием: `MakeGenericType` с неизвестными статически значимыми типами не работает. Решение — генераторы исходного кода и явные регистрации вместо сканирования сборок.

## Вопросы с собеседований

> [!question]- Чем дженерики в .NET отличаются от дженериков в Java?
> В Java применяется стирание типов: после компиляции `List<String>` и `List<Integer>` неразличимы, информация о параметре типа существует только для компилятора, а значимые типы приходится «оборачивать» (`Integer` вместо `int`), что означает постоянную упаковку. В .NET дженерики поддержаны на уровне рантайма: в метаданных хранится открытое определение с ограничениями, а закрытые конструкции — полноценные типы со своими таблицами методов и статическими полями. Отсюда четыре практических отличия: значимые типы не упаковываются, потому что JIT генерирует под них отдельную специализацию кода; типобезопасность сохраняется в рантайме; рефлексия видит фактические аргументы типа, что делает возможными DI-контейнеры и сериализаторы; можно создавать закрытые типы динамически через `MakeGenericType`. Цена — раздувание кода при большом числе значимых типов-аргументов.

> [!question]- Как JIT компилирует обобщённый код?
> Для каждого значимого типа-аргумента создаётся отдельная специализация машинного кода: раскладка и размер данных различаются, поэтому общий код невозможен — зато `int`, `double` или структура обрабатываются напрямую, без упаковки и приведений, а вызовы через ограничение интерфейсом разрешаются статически и обычно встраиваются. Для всех ссылочных типов используется одна общая («канонная») версия кода, потому что ссылка везде одного размера; конкретный тип при необходимости берётся из скрытого параметра. Отсюда и польза, и цена: обобщённый метод над структурами быстрее любой интерфейсной альтернативы, но десятки инстанцирований тяжёлого метода значимыми типами раздувают код и портят попадание в кеш инструкций. Отдельно стоит знать, что обобщённые **виртуальные** методы дороже обычных: их диспетчеризация требует дополнительного поиска.

> [!question]- Почему статическое поле в обобщённом классе своё для каждого T?
> Потому что `Counter<int>` и `Counter<string>` — разные закрытые типы, а статические поля принадлежат типу. Рантайм инициализирует их независимо, и присваивание в одном не влияет на другое. Иногда это удивляет (счётчик «на всё» не получится), но чаще используется намеренно: обобщённый статический класс — самый быстрый способ закешировать что-то по типу, потому что доступ превращается в чтение поля, без словаря, хеширования и блокировок. Именно так сериализаторы кешируют метаданные типа, а фреймворки — скомпилированные делегаты. Ограничение приёма: значение живёт до конца процесса и не может быть вытеснено, поэтому в кеш кладут только небольшие неизменяемые данные, а не результаты запросов.

## Задачи

### Задача 1. Объяснить разницу

Почему первый вариант аллоцирует, а второй нет?

```csharp
static bool Contains(IEnumerable<IComparable> items, IComparable value) { /* ... */ }
static bool Contains<T>(ReadOnlySpan<T> items, T value) where T : IComparable<T> { /* ... */ }
```

> [!success]- Решение
> В первом варианте каждый элемент значимого типа при попадании в `IEnumerable<IComparable>` упаковывается: создаётся объект в куче с копией значения, вызовы `CompareTo` идут через интерфейсную диспетчеризацию, и на миллион элементов получается миллион аллокаций. Дополнительно сам перечислитель, полученный через интерфейс, тоже упаковывается, если это структура.
> Во втором варианте JIT создаёт специализацию под конкретный `T`: элементы лежат в спане по значению, `CompareTo` вызывается через `constrained.callvirt`, что для значимого типа разрешается статически и обычно встраивается. Аллокаций нет ни одной, а цикл ещё и векторизуется в простых случаях.
> Практический вывод и оговорка: обобщённая форма выигрывает всегда, когда речь о значимых типах; для ссылочных разницы почти нет (используется общая канонная версия), поэтому там выбор делают по читаемости. И не стоит забывать про раздувание кода: если метод большой и инстанцируется десятком структур, размер кода растёт пропорционально.

### Задача 2. Кеш по типу

Сериализатору нужно для каждого типа один раз получить список свойств и дальше использовать его на каждом вызове. Как сделать это быстро?

> [!success]- Решение
> ```csharp
> internal static class PropertyCache<T>
> {
>     // Инициализируется один раз при первом обращении к PropertyCache<T>
>     public static readonly System.Reflection.PropertyInfo[] Properties =
>         typeof(T).GetProperties(System.Reflection.BindingFlags.Public | System.Reflection.BindingFlags.Instance);
> }
>
> static void Serialize<T>(T value)
> {
>     foreach (var p in PropertyCache<T>.Properties) { /* ... */ }
> }
> ```
> Почему это лучше `ConcurrentDictionary<Type, PropertyInfo[]>`: доступ превращается в чтение статического поля закрытого типа — без вычисления хеша, без поиска в корзине и без синхронизации. Инициализацию рантайм выполняет один раз и потокобезопасно (гарантии статического конструктора), поэтому блокировки не нужны.
> Ограничения, которые надо назвать честно: приём работает только когда тип известен статически (`T` в обобщённом методе), а не когда он получен как `Type` в рантайме — там всё же нужен словарь. Значение живёт до конца процесса и не вытесняется, поэтому кешировать так стоит только небольшие неизменяемые данные. И для по-настоящему горячих путей следующий шаг — не рефлексия вовсе, а генератор исходного кода, который создаст код сериализации на этапе компиляции ([[Source Generators]]).

## Итог

- В .NET дженерики существуют в рантайме: закрытые конструкции — полноценные типы со своими таблицами методов и статикой.
- Для значимых типов JIT создаёт отдельную специализацию кода: нет упаковки, вызовы по ограничению разрешаются статически.
- Все ссылочные типы разделяют одну канонную версию кода.
- Цена специализации — раздувание кода при многих значимых типах-аргументах.
- Статическое поле обобщённого класса своё у каждого `T` — быстрый кеш по типу без словаря.
- Вариантность (`in`/`out`) работает только для ссылочных типов.
- `MakeGenericType`/`MakeGenericMethod` дороги и ограничены под Native AOT для значимых типов.
- Обобщённая математика (`INumber<T>`) построена на статических абстрактных членах и специализации.
