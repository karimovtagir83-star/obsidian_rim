# Рефлексия

> [!abstract] Коротко
> Рефлексия — чтение метаданных сборки в рантайме и работа с типами, которых не было в коде на этапе компиляции: найти тип по имени, перечислить его члены, прочитать атрибуты, создать экземпляр, вызвать метод, прочитать и записать поле. На ней построены DI-контейнеры, сериализаторы, ORM, тестовые раннеры и валидаторы. Цена — производительность (вызов через `Invoke` в сотни раз дороже прямого) и несовместимость с обрезкой и Native AOT. Поэтому современный подход двухступенчатый: рефлексию используют **один раз при старте**, кешируя результат в делегаты, а лучше — заменяют генераторами исходного кода.

## Зачем это нужно

Без рефлексии невозможны фреймворки: контейнер не смог бы создать сервис по интерфейсу, сериализатор — прочитать свойства неизвестного типа, xUnit — найти методы с `[Fact]`, EF Core — построить модель по классам. Понимать её нужно и чтобы пользоваться этими инструментами осознанно, и чтобы не написать медленный код там, где он вызывается миллион раз.

## Основные операции

```csharp
using System.Reflection;

// Получить Type
Type t1 = typeof(Order);                          // статически, на этапе компиляции
Type t2 = order.GetType();                        // фактический тип объекта
Type? t3 = Type.GetType("MyApp.Domain.Order, MyApp");   // по строке, с именем сборки

// Исследовать
foreach (var p in t1.GetProperties(BindingFlags.Public | BindingFlags.Instance))
    Console.WriteLine($"{p.PropertyType.Name} {p.Name}");

foreach (var m in t1.GetMethods(BindingFlags.Public | BindingFlags.Instance | BindingFlags.DeclaredOnly))
    Console.WriteLine(m.Name);

var attr = t1.GetCustomAttribute<TableAttribute>();

// Создать и вызвать
var instance = Activator.CreateInstance<Order>();
var ctor = t1.GetConstructor([typeof(long), typeof(string)]);
var order2 = ctor!.Invoke([1L, "ORD-1"]);

var method = t1.GetMethod(nameof(Order.MarkPaid))!;
method.Invoke(order2, null);

// Прочитать и записать
var prop = t1.GetProperty(nameof(Order.Total))!;
var total = prop.GetValue(order2);
prop.SetValue(order2, 100m);

// Приватные члены — тоже доступны
var field = t1.GetField("_items", BindingFlags.NonPublic | BindingFlags.Instance);
```

`BindingFlags` — обязательный параметр в большинстве запросов: без него не видно ни приватных, ни статических членов. Частая ошибка — забыть `BindingFlags.Instance` и получить пустой список.

## Сколько это стоит

Порядок величин на одну операцию (ориентировочно, для сравнения между собой):

| Операция | Относительная стоимость |
|---|---|
| Прямой вызов метода | 1 |
| Вызов через закешированный делегат | ~1–2 |
| `MethodInfo.Invoke` (закешированный `MethodInfo`) | ~100–500 |
| `GetMethod` + `Invoke` каждый раз | ~1000+ |
| `Activator.CreateInstance<T>()` | ~10 |
| `Activator.CreateInstance(type)` | ~50–100 |

Главный вывод: дорог не столько сам вызов, сколько **поиск члена**. Поэтому первое правило — кешировать `Type`, `MethodInfo`, `PropertyInfo`; второе — заменять `Invoke` делегатом.

### Кеширование в делегат

```csharp
// Было: рефлексия на каждый вызов
object? value = property.GetValue(instance);

// Стало: один раз строим делегат, дальше — почти прямой вызов
static Func<T, TValue> BuildGetter<T, TValue>(PropertyInfo property)
{
    var parameter = System.Linq.Expressions.Expression.Parameter(typeof(T), "x");
    var access = System.Linq.Expressions.Expression.Property(parameter, property);
    return System.Linq.Expressions.Expression.Lambda<Func<T, TValue>>(access, parameter).Compile();
}

private static readonly Func<Order, decimal> GetTotal =
    BuildGetter<Order, decimal>(typeof(Order).GetProperty(nameof(Order.Total))!);

decimal total = GetTotal(order);     // скорость близка к прямому обращению
```

Ещё быстрее и проще, если сигнатура известна:

```csharp
var getter = (Func<Order, decimal>)Delegate.CreateDelegate(
    typeof(Func<Order, decimal>), property.GetGetMethod()!);
```

Так работают все зрелые библиотеки: рефлексия выполняется один раз при инициализации, дальше вызываются скомпилированные делегаты ([[Деревья выражений]]).

Кеш удобно держать в статическом поле обобщённого класса — доступ без словаря и блокировок ([[Дженерики в CLR: как устроены]]):

```csharp
internal static class Accessor<T>
{
    public static readonly PropertyInfo[] Properties = typeof(T).GetProperties();
}
```

## Рефлексия, обрезка и AOT

Компоновщик (trimming) удаляет из сборки всё, что не используется **статически**. Обращение по строковому имени статически не видно:

```csharp
var type = Type.GetType("MyApp.Handlers.OrderHandler");   // после обрезки тип может исчезнуть
```

Результат — `NullReferenceException` или `MissingMethodException` только в опубликованном виде, при том что в Debug всё работает. Компилятор предупреждает об этом диагностиками `IL2xxx`; игнорировать их нельзя.

Способы жить с этим:

```csharp
// 1. Явно указать, что тип нужен целиком
[System.Diagnostics.CodeAnalysis.DynamicallyAccessedMembers(
    System.Diagnostics.CodeAnalysis.DynamicallyAccessedMemberTypes.PublicProperties)]
static void Serialize(Type type) { }

// 2. Сохранить тип от обрезки через TrimmerRootDescriptor или явную ссылку в коде

// 3. Правильный путь — генератор исходного кода вместо рефлексии
[System.Text.Json.Serialization.JsonSerializable(typeof(Order))]
internal sealed partial class AppJsonContext : System.Text.Json.Serialization.JsonSerializerContext;

var json = System.Text.Json.JsonSerializer.Serialize(order, AppJsonContext.Default.Order);
```

Под Native AOT ограничения жёстче: нет генерации кода в рантайме (`Reflection.Emit`, `Expression.Compile` работают только в интерпретируемом режиме или не работают вовсе), нельзя создать специализацию обобщённого типа для значимого аргумента, не встречавшегося статически. Поэтому платформа последовательно переводит инфраструктуру на генераторы: `[JsonSerializable]`, `[LoggerMessage]`, `[GeneratedRegex]`, `[LibraryImport]`, валидация Minimal API в .NET 10 ([[Source Generators]], [[Native AOT: когда стоит]]).

## Где рефлексия уместна

| Сценарий | Комментарий |
|---|---|
| Сканирование сборки при старте (регистрация обработчиков, валидаторов) | один раз, результат кешируется |
| Плагины и модули, загружаемые динамически | других вариантов нет ([[AssemblyLoadContext и загрузка плагинов]]) |
| Инструменты разработчика, миграции, кодогенерация | производительность не критична |
| Тесты: доступ к внутренностям, построение фикстур | лучше `InternalsVisibleTo`, но допустимо |
| Диагностика и отладочный вывод | редкие вызовы |

Где не уместна: в горячем пути на каждый запрос без кеширования; для обхода инкапсуляции в продовом коде (чтение приватных полей чужого класса — договор, который сломается при обновлении библиотеки); там, где задачу решает интерфейс или дженерик.

```csharp
// Плохо: рефлексия вместо полиморфизма
var method = handler.GetType().GetMethod("Handle");
method!.Invoke(handler, [message]);

// Хорошо: интерфейс
public interface IHandler<in T> { Task HandleAsync(T message, CancellationToken ct); }
```

## Практический пример: регистрация обработчиков при старте

```csharp
public static IServiceCollection AddHandlers(this IServiceCollection services, Assembly assembly)
{
    var handlerInterface = typeof(IHandler<>);

    // Рефлексия выполняется ОДИН раз при конфигурации приложения
    var registrations = assembly.GetTypes()
        .Where(t => t is { IsAbstract: false, IsInterface: false })
        .SelectMany(t => t.GetInterfaces()
            .Where(i => i.IsGenericType && i.GetGenericTypeDefinition() == handlerInterface)
            .Select(i => (Service: i, Implementation: t)));

    foreach (var (service, implementation) in registrations)
        services.AddScoped(service, implementation);

    return services;
}
```

Дальше в рантайме контейнер работает с уже построенной картой — рефлексии на каждый запрос нет. Это и есть канонический способ применения: **сканирование на старте, кеш на всё время работы**.

Ограничение честно назвать: такое сканирование несовместимо с обрезкой и AOT, поэтому в проектах, нацеленных на Native AOT, регистрации либо пишут явно, либо генерируют.

> [!warning] Подводные камни
> - **Рефлексия в горячем пути.** `GetMethod` + `Invoke` на каждый вызов — сотни-тысячи наносекунд вместо единиц.
> - **Отсутствие `BindingFlags`.** Без `Instance`/`NonPublic` члены просто не находятся, и это выглядит как «метода нет».
> - **`Type.GetType("...")` без имени сборки.** Ищет только в текущей сборке и в `System.Private.CoreLib`.
> - **Строковые имена вместо `nameof`.** Не переживают переименование; `nameof` проверяется компилятором.
> - **Обрезка и AOT.** Типы, используемые только через рефлексию, удаляются — падение только в публикации.
> - **Обход инкапсуляции.** Чтение приватных полей чужой библиотеки ломается при её обновлении.
> - **Исключения из `Invoke`.** Оборачиваются в `TargetInvocationException`: настоящая причина в `InnerException`.
> - **Рефлексия вместо дизайна.** Если задача решается интерфейсом, дженериком или делегатом — так и надо решать.

> [!example] Как делают в бою
> Рефлексия в прикладном коде почти не пишется руками: её используют фреймворки. Там, где она всё же нужна, действует правило «один раз при старте»: сканирование сборки, построение карты типов и делегатов, кеш в статических полях. В рантайме работают уже делегаты, а не `Invoke`.
> Для типовых задач берут готовые механизмы: сериализация — `System.Text.Json` с генератором контекста, логирование — `[LoggerMessage]`, маппинг — либо ручной код, либо генератор (Mapperly), валидация — FluentValidation или атрибуты. Все они выигрывают у рефлексии и по скорости, и по совместимости с AOT.
> Проекты, которые планируют Native AOT или агрессивную обрезку, с самого начала включают предупреждения анализа (`IsTrimmable`, `EnableAotAnalyzer`) и не используют сканирование сборок — регистрации пишут явно. Это дисциплина, которую дешевле принять сразу, чем внедрять потом.
> Тестам иногда нужна рефлексия для доступа к внутренним членам, но и там предпочитают `InternalsVisibleTo`: тест, лезущий в приватные поля, ломается на любом рефакторинге.

## Вопросы с собеседований

> [!question]- Что такое рефлексия и на чём она основана?
> Это API для чтения метаданных сборки в рантайме и работы с типами, неизвестными на этапе компиляции. Основана она на том, что .NET-сборка полностью описывает саму себя: в метаданных хранятся все типы, их члены, сигнатуры, имена параметров и атрибуты. Через `System.Reflection` можно найти тип по имени, перечислить свойства и методы, прочитать атрибуты, создать экземпляр, вызвать метод, получить и установить значение поля — в том числе приватного. На этом построены DI-контейнеры, сериализаторы, ORM, тестовые раннеры, валидаторы и мокинг-фреймворки. Обратная сторона — производительность (поиск члена и `Invoke` на порядки дороже прямого вызова) и несовместимость с обрезкой и Native AOT, потому что используемые только через рефлексию типы не видны статическому анализу и удаляются при публикации.

> [!question]- Как ускорить код, использующий рефлексию?
> Двумя приёмами. Первый — кешировать результаты поиска: `Type`, `MethodInfo`, `PropertyInfo` находятся один раз и сохраняются в статическом поле или словаре; сам поиск обычно дороже вызова. Второй, более важный — превратить рефлексию в делегат: `Delegate.CreateDelegate` для известных сигнатур или построение и компиляция дерева выражений (`Expression.Lambda(...).Compile()`) для произвольных. Скомпилированный делегат вызывается почти так же быстро, как прямой метод, потому что за ним стоит настоящий сгенерированный код, а не интерпретация. Схема, которую применяют все зрелые библиотеки: рефлексия при инициализации, делегаты в рантайме, кеш в статических полях обобщённых классов. Радикальное решение — вообще убрать рефлексию из рантайма и переложить работу на генератор исходного кода: так сделано в `System.Text.Json`, логировании и регулярных выражениях.

> [!question]- Почему рефлексия мешает Native AOT и обрезке?
> Потому что оба механизма опираются на статический анализ: компоновщик удаляет типы и члены, на которые нет видимых ссылок, а AOT-компилятор заранее генерирует машинный код только для того, что встречается в программе. Обращение по строковому имени (`Type.GetType("...")`, `GetMethod("Handle")`) статически невидимо, поэтому нужный тип может быть вырезан, и ошибка проявится только в опубликованном приложении. Под Native AOT добавляется ещё одно ограничение: нет JIT, значит нельзя сгенерировать код в рантайме — `Reflection.Emit` недоступен, а создать специализацию обобщённого типа для значимого аргумента, не встречавшегося статически, невозможно. Смягчить это можно атрибутами `DynamicallyAccessedMembers` и корневыми дескрипторами компоновщика, но правильное направление — заменять рефлексию генераторами исходного кода, что платформа и делает последовательно.

## Задачи

### Задача 1. Ускорить маппинг

Метод копирует одноимённые свойства из одного объекта в другой и вызывается на каждый запрос.

```csharp
static void CopyTo<TSource, TTarget>(TSource source, TTarget target)
{
    foreach (var sp in typeof(TSource).GetProperties())
    {
        var tp = typeof(TTarget).GetProperty(sp.Name);
        if (tp is not null && tp.CanWrite) tp.SetValue(target, sp.GetValue(source));
    }
}
```

> [!success]- Решение
> Здесь на каждый вызов происходит перечисление свойств, поиск по имени и два вызова через рефлексию на каждое свойство — то есть тысячи наносекунд там, где хватило бы десятков.
> ```csharp
> internal static class Copier<TSource, TTarget>
> {
>     // Строится один раз на пару типов благодаря статике обобщённого класса
>     private static readonly Action<TSource, TTarget> Copy = Build();
>
>     public static void Run(TSource source, TTarget target) => Copy(source, target);
>
>     private static Action<TSource, TTarget> Build()
>     {
>         var src = Expression.Parameter(typeof(TSource), "src");
>         var dst = Expression.Parameter(typeof(TTarget), "dst");
>
>         var assignments = typeof(TSource).GetProperties()
>             .Select(sp => (Source: sp, Target: typeof(TTarget).GetProperty(sp.Name)))
>             .Where(x => x.Target is { CanWrite: true } && x.Target.PropertyType == x.Source.PropertyType)
>             .Select(x => (Expression)Expression.Assign(
>                 Expression.Property(dst, x.Target!), Expression.Property(src, x.Source)));
>
>         var body = assignments.Any() ? Expression.Block(assignments) : (Expression)Expression.Empty();
>         return Expression.Lambda<Action<TSource, TTarget>>(body, src, dst).Compile();
>     }
> }
> ```
> Рефлексия выполняется один раз на пару типов, дальше вызывается скомпилированный делегат — скорость близка к рукописному коду. Кеш бесплатен: статическое поле обобщённого класса своё для каждой комбинации `TSource`/`TTarget`.
> Оговорка, которую стоит сделать: под Native AOT `Expression.Compile` не работает, а рукописный маппинг или генератор (например, Mapperly) быстрее и безопаснее в принципе. Автоматический маппинг вообще спорен — он скрывает несоответствия моделей, которые компилятор поймал бы при явном присваивании.

### Задача 2. Найти проблему

```csharp
var handlerType = Type.GetType($"MyApp.Handlers.{messageType.Name}Handler");
var handler = Activator.CreateInstance(handlerType!)!;
var method = handlerType.GetMethod("Handle");
method!.Invoke(handler, [message]);
```

> [!success]- Решение
> Проблем несколько, и все системные.
> Тип ищется по строке, собранной из имени сообщения: переименование класса ломает код молча, а `Type.GetType` без имени сборки найдёт тип только в текущей сборке. При обрезке или AOT такой тип будет вырезан. Экземпляр создаётся `Activator.CreateInstance` без параметров, то есть зависимости обработчика внедрить невозможно. Метод ищется по строковому имени на каждый вызов — самая дорогая часть. Исключение из обработчика будет обёрнуто в `TargetInvocationException`, и настоящая причина окажется во внутреннем исключении, что усложнит диагностику.
> ```csharp
> public interface IHandler<in TMessage> { Task HandleAsync(TMessage message, CancellationToken ct); }
>
> // Регистрация — один раз при старте (сканированием или явно)
> services.AddScoped<IHandler<OrderCreated>, OrderCreatedHandler>();
>
> // Вызов — обычный, типобезопасный, с внедрением зависимостей
> var handler = provider.GetRequiredService<IHandler<OrderCreated>>();
> await handler.HandleAsync(message, ct);
> ```
> Если тип сообщения известен только в рантайме (например, приходит из брокера по имени), правильная схема — построить при старте словарь «имя сообщения → делегат-диспетчер», где делегат уже типизирован и получает обработчик из контейнера. Тогда в рантайме остаётся поиск по словарю и обычный вызов, без рефлексии.

## Итог

- Рефлексия читает метаданные сборки и позволяет работать с типами, неизвестными на этапе компиляции.
- Дороже всего поиск члена; `Invoke` в сотни раз медленнее прямого вызова.
- Правильная схема: рефлексия один раз при старте, кеш в статических полях, вызовы через делегаты.
- `Delegate.CreateDelegate` и скомпилированные деревья выражений возвращают скорость почти прямого вызова.
- `BindingFlags` обязателен для поиска приватных и статических членов; `Type.GetType` требует имени сборки.
- Обрезка и Native AOT удаляют то, что видно только через строковые имена: нужны атрибуты или генераторы.
- Исключения из `Invoke` приходят обёрнутыми в `TargetInvocationException`.
- Если задача решается интерфейсом или дженериком, рефлексия не нужна.
