# Рефлексия

> [!abstract] Коротко
> Рефлексия — чтение метаданных сборки в рантайме: найти тип по имени, перечислить его члены, прочитать атрибуты, создать экземпляр, вызвать метод. Атрибуты — как раз та метадата, ради которой рефлексию чаще всего и включают: `[Required]` или `[Table]` сами по себе ничего не делают, они лишь данные, записанные в метаданные сборки, — действует тот, кто их прочитает через `GetCustomAttribute`. На этой связке стоят DI-контейнеры, ORM, сериализаторы и тестовые раннеры. Цена — производительность и несовместимость с обрезкой и Native AOT, поэтому современный подход: рефлексия один раз при старте, дальше — кеш или генератор исходного кода.

## Зачем это знать

Без рефлексии непонятно, как контейнер создаёт сервис по интерфейсу, как MediatR находит хендлер под конкретную команду, как EF Core строит модель по классам с `[Key]`/`[Table]`, а ASP.NET Core — таблицу маршрутов по `[HttpGet]`. Модель нужна для трёх вещей: понять, почему код фреймворка «работает по атрибуту» без единого `if`; заметить в ревью рефлексию там, где решает интерфейс; и не удивиться, когда после публикации под trimming/AOT что-то из этого молча перестаёт находиться.

## Модель

### Типы и члены — это данные, доступные в рантайме

Каждая сборка .NET несёт в себе полное описание самой себя: типы, их члены, сигнатуры, имена параметров, атрибуты. `System.Reflection` — API поверх этого описания.

```csharp
using System.Reflection;

Type t1 = typeof(Order);                                // статически
Type t2 = order.GetType();                               // фактический тип объекта
Type? t3 = Type.GetType("MyApp.Domain.Order, MyApp");    // по строке, с именем сборки

foreach (var p in t1.GetProperties(BindingFlags.Public | BindingFlags.Instance))
    Console.WriteLine($"{p.PropertyType.Name} {p.Name}");

var ctor = t1.GetConstructor([typeof(long), typeof(string)]);
var order2 = ctor!.Invoke([1L, "ORD-1"]);

var method = t1.GetMethod(nameof(Order.MarkPaid))!;
method.Invoke(order2, null);
```

`BindingFlags` — обязательный параметр в большинстве запросов: без него не видно ни приватных, ни статических членов; забытый `BindingFlags.Instance` даёт пустой список и выглядит как «метода нет».

### Атрибуты — метаданные, а не поведение

Атрибут — класс, унаследованный от `Attribute`, экземпляр которого записан в метаданные сборки рядом с помеченным элементом. Сам по себе он ничего не делает: `[Obsolete]` не запрещает вызов, `[Required]` не проверяет строку — эффект появляется только тогда, когда атрибут кто-то читает.

```csharp
[AttributeUsage(AttributeTargets.Class, AllowMultiple = false, Inherited = false)]
public sealed class AuditAttribute(string action) : Attribute
{
    public string Action { get; } = action;      // позиционный параметр
    public bool IncludePayload { get; init; }     // именованный параметр
}

[Audit("order.create", IncludePayload = true)]
public sealed class CreateOrderHandler;
```

Аргументы атрибута обязаны быть константами времени компиляции (числа, строки, `bool`, `enum`, `typeof(T)`) — они физически записываются в метаданные, поэтому `[Range(1, DateTime.Now.Year)]` не скомпилируется. Соглашения: `sealed`, суффикс `Attribute` в имени класса (при использовании опускается), `[AttributeUsage]` ограничивает допустимые цели.

Читают атрибуты той же рефлексией:

```csharp
var audit = typeof(CreateOrderHandler).GetCustomAttribute<AuditAttribute>();
if (audit is not null) Console.WriteLine($"{audit.Action}, payload={audit.IncludePayload}");
```

Ловушка наследования: `Inherited = true` работает для наследования классов, но не для реализации интерфейса — атрибут, объявленный на члене интерфейса, не виден через `GetCustomAttribute` на реализующем классе, нужен ручной обход `GetInterfaceMap`.

Отдельная категория — атрибуты вызывающего (`[CallerMemberName]`, `[CallerArgumentExpression]`): их подставляет компилятор в месте вызова, это не рефлексия и стоимость нулевая. Именно так `ArgumentNullException.ThrowIfNull(order.Customer)` печатает в сообщении текст `"order.Customer"`.

### Сколько это стоит

| Операция | Относительная стоимость |
|---|---|
| Прямой вызов метода | 1 |
| Вызов через закешированный делегат | ~1–2 |
| `MethodInfo.Invoke` (закешированный `MethodInfo`) | ~100–500 |
| `GetMethod`/`GetCustomAttribute` + `Invoke` каждый раз | ~1000+ |
| `Activator.CreateInstance<T>()` | ~10 |
| `Activator.CreateInstance(type)` | ~50–100 |

Дорог не столько вызов, сколько **поиск члена** — по имени метода, по типу атрибута. Поэтому первое правило: кешировать `Type`/`MethodInfo`/`PropertyInfo`/найденный атрибут по ключу `Type`; второе — заменять `Invoke` делегатом:

```csharp
static class AuditCache
{
    private static readonly System.Collections.Concurrent.ConcurrentDictionary<Type, AuditAttribute?> Cache = new();
    public static AuditAttribute? Get(Type type) => Cache.GetOrAdd(type, static t => t.GetCustomAttribute<AuditAttribute>());
}

// Делегат вместо Invoke — построен раз, вызывается почти как прямой метод
private static readonly Func<Order, decimal> GetTotal = BuildGetter<Order, decimal>(
    typeof(Order).GetProperty(nameof(Order.Total))!);
```

Именно так поступают все фреймворки: ASP.NET Core и EF Core читают типы и атрибуты один раз при старте, строят модель (таблицу маршрутов, карту EF) и дальше работают с ней, а не с рефлексией на каждый запрос.

### Обрезка и Native AOT

Компоновщик удаляет из сборки всё, что не используется статически. Обращение по строке (`Type.GetType("...")`, `GetMethod("Handle")`) статически не видно — тип может исчезнуть после публикации, хотя в Debug всё работало. Компилятор предупреждает диагностиками `IL2xxx`. Смягчить: атрибут `[DynamicallyAccessedMembers]`, корневые дескрипторы компоновщика — но правильное направление, которое использует сама платформа, это генераторы исходного кода: `[JsonSerializable]`, `[LoggerMessage]`, `[GeneratedRegex]` читают атрибуты **на этапе компиляции** и порождают обычный код без рефлексии в рантайме. Под Native AOT ограничения жёстче: нет JIT, значит `Reflection.Emit` и `Expression.Compile` недоступны или работают только интерпретируемо.

## Решения

| Где применяется | Когда оправдано | Когда нет |
|---|---|---|
| Рефлексия на каждый запрос | Никогда без кеша | Горячий путь — заменить кешем или делегатом |
| Рефлексия + кеш при старте | Сканирование сборки для DI, поиск обработчиков/валидаторов | Если набор типов известен заранее — явная регистрация проще и быстрее |
| Атрибуты + рефлексия (валидация, маппинг) | Простые декларативные правила (обязательность, длина, диапазон) | Правила из нескольких полей или с обращением к БД — код, не атрибут |
| Генератор исходного кода вместо рефлексии | Проект целится в Native AOT/trimming, или сценарий горячий и известен на этапе компиляции | Разовый инструмент, миграция, редко вызываемый код — не стоит усложнения |
| Интерфейс/дженерик вместо рефлексии | Задача — выбрать поведение по типу, известному в коде | — рефлексия здесь всегда лишняя |

> [!example] В ServiceShop
> MediatR находит `IRequestHandler<TRequest, TResponse>` под конкретную команду через сканирование сборки при регистрации в Autofac-модуле: один раз при старте рефлексией собирается карта «тип команды → тип хендлера», а на каждый запрос уже работает обычный резолв по интерфейсу — рефлексии в рантайме нет. Атрибуты `[Required]`, `[StringLength]` на DTO читает ASP.NET Core model binding при валидации входящего запроса ([[Model binding и валидация]]); там, где правило зависит от нескольких полей или от состояния в БД, в проекте используется FluentValidation, а не декларативные атрибуты. Общий принцип, который стоит держать в голове при ревью: свой атрибут без кода, который его читает, — не функциональность, а комментарий, который выглядит как код.

> [!warning] Где ошибаются
> - **Рефлексия в горячем пути.** `GetMethod`/`GetCustomAttribute` + `Invoke` на каждый вызов — сотни-тысячи наносекунд там, где хватило бы единиц. **Агент часто** генерирует именно такой код при первой попытке решить задачу через рефлексию, не задумываясь о частоте вызова.
> - **Рефлексия там, где хватило бы интерфейса.** **Агент часто** предлагает `GetMethod("Handle").Invoke(...)` вместо `IHandler<T>` — рефлексия «на глаз» выглядит как гибкое решение, но теряет типобезопасность и производительность там, где типы известны на этапе компиляции.
> - **Атрибут без потребителя.** Свой `[Audit]`, который никто не читает через `GetCustomAttribute`, — мёртвый код с виду функциональности. **Агент часто** расставляет такие атрибуты по образцу увиденного в других местах кода, не проверяя, что где-то есть код, который их считывает.
> - **`Inherited = true` не работает для интерфейсов.** Атрибут на члене интерфейса не наследуется реализацией — `GetCustomAttribute` на конкретном классе его не увидит.
> - **Обрезка и AOT молчаливо ломают строковый поиск.** `Type.GetType("...")`, `GetMethod("Handle")` работают в Debug и исчезают после публикации под trimming — диагностику `IL2xxx` игнорировать нельзя.
> - **Исключения из `Invoke` теряются.** Настоящая причина падения обёрнута в `TargetInvocationException.InnerException`, а не видна напрямую.

## Проверка на ревью

- В диффе нет `GetMethod`/`GetCustomAttribute`/`Invoke` на пути, вызываемом на каждый запрос без кеша.
- Рефлексия и сканирование сборки (DI, поиск хендлеров) выполняются один раз при старте, а не лениво на каждый вызов.
- У своего атрибута есть код, который явно вызывает `GetCustomAttribute` для него — иначе атрибут декоративный.
- `Type.GetType("...")` не используется без имени сборки и не заменяет типобезопасный `typeof`/`nameof`.
- Валидация через атрибуты покрывает только простые правила; правила с несколькими полями или обращением к БД — в FluentValidation или домене, не «как-нибудь через атрибут».
- Там, где рефлексия используется для выбора поведения по типу, проверено — не решает ли задачу простой интерфейс или дженерик.

## Проверь себя

> [!question]- Что делает атрибут сам по себе и кто заставляет его работать?
> Ничего — это данные в метаданных сборки, привязанные к элементу кода. Эффект появляется, только когда кто-то явно читает этот атрибут: компилятор (`[Obsolete]`), рантайм (`[ThreadStatic]`), фреймворк через рефлексию (валидация, маршрутизация, сериализация) или генератор исходного кода на этапе компиляции. Отсюда типичная ошибка — расставить атрибут и ждать эффекта без кода-потребителя.

> [!question]- Почему `GetCustomAttribute`/`GetMethod` дорого и что с этим делают на практике?
> Каждый вызов обращается к метаданным сборки, разбирает описание члена или атрибута и в случае атрибута создаёт его экземпляр — поиск члена дороже самого вызова. Решения два: кешировать результат по `Type` в статическом поле или словаре (так строят модель EF Core и таблицу маршрутов ASP.NET Core), либо вообще убрать рефлексию из рантайма, переложив работу на генератор исходного кода (`[JsonSerializable]`, `[LoggerMessage]`).

> [!question]- Почему рефлексия по строковому имени ломается под trimming/Native AOT?
> Обрезка и AOT-компиляция опираются на статический анализ: удаляется или не компилируется то, на что нет видимой ссылки в коде. Обращение по строке (`Type.GetType("...")`, `GetMethod("Handle")`) для анализатора невидимо, поэтому нужный тип может быть вырезан — ошибка проявится только в опубликованном приложении, хотя в Debug всё работало. Смягчают атрибутами `DynamicallyAccessedMembers`, но системное решение — генератор вместо рефлексии.

> [!question]- Когда рефлексия в прикладном коде оправдана, а когда нет?
> Оправдана при сканировании сборки один раз при старте (регистрация хендлеров, валидаторов), в инструментах разработчика и миграциях, где производительность не критична, и в загрузке динамических плагинов, где другого пути нет. Не оправдана в горячем пути без кеша, для обхода инкапсуляции чужого кода и там, где задачу решает обычный интерфейс или дженерик, известный на этапе компиляции.

## Разбор

Дан код: интерфейс с атрибутом на методе, ожидание, что атрибут «унаследуется» реализацией.

```csharp
public interface ICommand
{
    [Audit("unknown")]
    void Execute();
}

public sealed class CreateOrder : ICommand
{
    public void Execute() { }
}

var attr = typeof(CreateOrder).GetMethod(nameof(ICommand.Execute))!
                              .GetCustomAttribute<AuditAttribute>();
Console.WriteLine(attr?.Action ?? "не найден");
```

> [!success]- Решение
> Выведет «не найден». Атрибуты на членах интерфейса не наследуются реализующим типом — `Inherited = true` относится только к наследованию классов. Чтобы получить атрибут, нужно явно обойти интерфейсы через `GetInterfaceMap`. Практический вывод: метаданные для инфраструктуры размещают на конкретных классах, а не на интерфейсах, иначе обработка требует нетривиального кода, который к тому же нельзя вызывать в горячем пути.

Дан PR агента: обработчик сообщения ищется и создаётся полностью через рефлексию по строковому имени.

```csharp
var handlerType = Type.GetType($"MyApp.Handlers.{messageType.Name}Handler");
var handler = Activator.CreateInstance(handlerType!)!;
var method = handlerType.GetMethod("Handle");
method!.Invoke(handler, [message]);
```

> [!success]- Решение
> Возврат на доработку. Проблем несколько: `Type.GetType` без имени сборки ищет только в текущей сборке и в `CoreLib`, а после trimming/AOT такой тип может быть вырезан; `Activator.CreateInstance` без параметров не даёт внедрить зависимости обработчика; поиск метода по строке на каждый вызов — самая дорогая часть; исключение из `Invoke` обернётся в `TargetInvocationException`, усложняя диагностику. Правильная схема — регистрация `IHandler<TMessage>` в DI один раз при старте (явно или сканированием), а на message-broker выбор конкретного обработчика — через словарь «имя сообщения → типизированный делегат», построенный тоже один раз, без рефлексии в рантайме.

## Итог

- Рефлексия читает метаданные сборки; атрибуты — метаданные, ради которых её чаще всего включают.
- Атрибут сам по себе не действует — эффект даёт код, который его читает через `GetCustomAttribute`.
- Дороже всего поиск члена/атрибута; правильная схема — рефлексия один раз при старте, дальше кеш или делегат.
- Атрибуты на членах интерфейса не наследуются реализацией — нужен явный обход `GetInterfaceMap`.
- Обрезка и Native AOT убирают то, что видно только по строковому имени, — нужны аннотации или переход на генераторы исходного кода.
- Если задачу решает интерфейс или дженерик, известный на этапе компиляции, рефлексия не нужна.
