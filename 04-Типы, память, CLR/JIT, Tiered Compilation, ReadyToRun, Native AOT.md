# JIT, Tiered Compilation, ReadyToRun, Native AOT

> [!abstract] Коротко
> IL сам по себе не исполняется: машинный код создаёт **JIT** — по одному методу, при первом вызове. Чтобы не платить за оптимизацию на старте, .NET использует многоуровневую компиляцию: сначала быстрый неоптимизированный код (tier 0), затем для горячих методов — полностью оптимизированный (tier 1), причём с учётом собранной статистики (dynamic PGO). Две альтернативы меняют компромисс: **ReadyToRun** кладёт предкомпилированный код в сборку и ускоряет старт, оставляя JIT для горячих путей; **Native AOT** убирает JIT совсем — мгновенный старт и меньше памяти ценой рефлексии, динамической загрузки и отдельной сборки под каждую платформу.

## Зачем это нужно

Три вопроса, на которые без этой темы нет ответа:

- почему первый запрос к свежему инстансу отвечает за 300 мс, а следующие за 3 мс;
- почему бенчмарк без прогрева врёт в разы;
- почему serverless-функция на .NET «холодно» стартует секунду и что с этим делать.

Плюс это водораздел в понимании производительности: JIT — не «медленная штука, которая мешает», а компилятор, который знает больше, чем любой AOT: конкретную модель процессора и фактическое поведение программы.

## Как работает JIT

```
Первый вызов метода:
  заглушка (stub) → JIT компилирует ИМЕННО ЭТОТ метод → машинный код в памяти
                  → адрес подставляется в таблицу методов
Повторные вызовы: прямой переход в скомпилированный код
```

Компиляция идёт **по одному методу**, лениво: код, который не вызвался, не компилируется никогда. Отсюда две особенности: старт зависит от того, сколько кода реально исполняется, и «первый проход» всегда дороже последующих.

Что JIT делает помимо трансляции:

- **распределяет регистры** — держит горячие переменные в регистрах процессора;
- **встраивает методы** (inlining) — убирает накладные расходы на вызов; ориентир для кандидата — небольшое тело (десятки байт IL), отсутствие исключений и `try`, невиртуальность или доказанный тип;
- **устраняет проверки границ** массивов, когда может доказать безопасность индекса;
- **девиртуализирует** вызовы, если тип точно известен (`sealed`-класс, только что созданный объект) или доминирует по профилю;
- **сворачивает константы** и удаляет мёртвый код, в том числе с учётом рантайм-констант (`RuntimeInformation.IsOSPlatform`, размер вектора);
- **векторизует** отдельные операции и использует доступные расширения процессора: в .NET 10 JIT задействует AVX-512, AVX10.2 и ARM SVE2, что даёт 15–30 % на подходящем железе;
- начиная с .NET 9 умеет **размещать некоторые объекты на стеке**, если доказал, что ссылка не покидает метод (escape analysis) — то есть часть аллокаций исчезает без изменений в коде.

## Многоуровневая компиляция

```
     первый вызов                        ~30 вызовов или горячий цикл
IL ──────────────► tier 0 ──────────────────────────────────────► tier 1
                   быстрый JIT,          собирает статистику       полные оптимизации
                   без оптимизаций       (инструментирование)      + профиль (PGO)
```

- **Tier 0** — компиляция без оптимизаций: быстро генерируется, медленно работает. Задача — как можно быстрее начать исполнение.
- **Tier 1** — полностью оптимизированный код. Метод перекомпилируется, когда счётчик вызовов переходит порог (по умолчанию порядка 30) либо когда обнаружен долгий цикл.
- **OSR** (on-stack replacement) — замена кода метода, который **уже выполняется**. Без него метод с циклом на миллион итераций, попавший в tier 0, так и доработал бы неоптимизированным.
- **Dynamic PGO** (включён по умолчанию с .NET 8) — tier 0 собирает статистику: какие типы приходят в виртуальные вызовы, какие ветви берутся, сколько раз выполняются циклы. Tier 1 использует её: девиртуализирует доминирующий тип с проверкой и запасной ветвью, переупорядочивает блоки, агрессивнее встраивает.

Практические следствия:

```csharp
// Замер без прогрева меряет tier 0, а не ваш алгоритм
var sw = Stopwatch.StartNew();
DoWork();                       // здесь ещё и JIT-компиляция внутри замера
sw.Stop();                      // цифра не имеет отношения к прогретой производительности
```

Именно поэтому существует BenchmarkDotNet: он прогревает код, дожидается tier 1, запускает множество итераций и считает статистику ([[Как измерять: BenchmarkDotNet]]).

Второе следствие — «медленный первый запрос» в веб-приложении: JIT компилирует весь конвейер (Kestrel, middleware, роутинг, сериализацию, EF Core). Дальше горячие методы уходят в tier 1, и время падает на порядок.

Настройки (менять стоит только с бенчмарком в руках):

```bash
DOTNET_TieredCompilation=0        # отключить многоуровневость: сразу tier 1, медленный старт
DOTNET_TieredPGO=0                # отключить динамический профиль
DOTNET_TC_QuickJitForLoops=0      # не применять tier 0 к методам с циклами (до OSR так и делали)
DOTNET_ReadyToRun=0               # игнорировать предкомпилированный код в сборках
```

## ReadyToRun

Публикация с `PublishReadyToRun` кладёт в сборку **предкомпилированный машинный код** рядом с IL:

```bash
dotnet publish -c Release -r linux-x64 --self-contained false -p:PublishReadyToRun=true
```

| | Обычная публикация | ReadyToRun |
|---|---|---|
| Старт | JIT компилирует всё с нуля | код уже готов, JIT почти не нужен |
| Пиковая производительность | максимальная (tier 1 + PGO) | сначала ниже, затем горячие методы перекомпилируются в tier 1 |
| Размер сборки | меньше | больше (IL + машинный код) |
| Привязка к платформе | нет | нужен RID (`linux-x64`, `osx-arm64`) |

Смысл в том, что R2R-код — компромисс: он собран без знания конкретного процессора и профиля, поэтому хуже tier 1, но лучше, чем ничего на старте. Горячие методы всё равно дойдут до tier 1, так что пиковая производительность не теряется.

Типичное применение — контейнеры, которые часто перезапускаются и масштабируются: выигрыш в холодном старте 20–40 % при небольшом росте образа. Composite R2R (`PublishReadyToRunComposite`) компилирует приложение вместе с рантаймом в один образ, ускоряя старт ещё сильнее, но привязывая к конкретной версии рантайма.

## Native AOT

Полная компиляция в нативный исполняемый файл на этапе публикации. JIT в поставку не входит.

```xml
<PropertyGroup>
  <PublishAot>true</PublishAot>
  <InvariantGlobalization>true</InvariantGlobalization>
  <StripSymbols>true</StripSymbols>
</PropertyGroup>
```

```bash
dotnet publish -c Release -r osx-arm64
```

| Что | Native AOT | JIT |
|---|---|---|
| Холодный старт | единицы миллисекунд | десятки–сотни мс |
| Потребление памяти | ниже (нет JIT, нет метаданных для него) | выше |
| Размер артефакта | один файл, обычно 10–30 МБ | меньше при framework-dependent |
| Пиковая производительность | обычно чуть ниже | выше (PGO, знание CPU) |
| Рефлексия | ограничена | полная |
| Динамическая загрузка сборок, `Reflection.Emit` | недоступны | доступны |
| Сборка под платформу | отдельная на каждый RID | одна на все |

Ограничения — не мелочь, а критерий применимости:

- **Обрезка (trimming) обязательна.** Всё, что не видно статически, удаляется; рефлексия по строковым именам ломается. Предупреждения `IL2xxx`/`IL3xxx` игнорировать нельзя.
- **Нет генерации кода в рантайме.** Значит, не работают библиотеки, строящие типы на лету: часть мокинг-фреймворков, старые ORM, динамические прокси.
- **Нет плагинов.** `Assembly.LoadFrom` и `AssemblyLoadContext` недоступны ([[AssemblyLoadContext и загрузка плагинов]]).
- **Дженерики над значимыми типами** должны быть известны статически: `MakeGenericType` в рантайме не сработает.

Где Native AOT оправдан: CLI-утилиты, serverless-функции, короткоживущие джобы, микросервисы с жёстким требованием к холодному старту и памяти, консольные инструменты для распространения. Где обычно не нужен: долгоживущий веб-сервис, где инстанс живёт часами и стартовые миллисекунды не важны, зато важны совместимость с библиотеками и пиковая производительность.

ASP.NET Core поддерживает AOT для Minimal API (с ограничениями: без MVC, без Razor); в .NET 8+ для этого есть шаблон `webapiaot`.

## Как посмотреть, что сгенерировал JIT

```bash
# Дизассемблер конкретного метода — работает и в release-рантайме (с .NET 7)
DOTNET_JitDisasm="MyApp.OrderService:Calculate" dotnet run -c Release

# Сообщать о встраивании и его отказах
DOTNET_JitPrintInlinedMethods=1 dotnet run -c Release
```

В BenchmarkDotNet для этого есть `[DisassemblyDiagnoser]`, показывающий машинный код измеряемых методов, и `[MemoryDiagnoser]` для аллокаций. Для быстрых экспериментов удобнее sharplab.io: он показывает и IL, и ассемблер ([[Сборки, метаданные и IL]]).

Подсказка компилятору по встраиванию есть, но применять её нужно осторожно:

```csharp
[MethodImpl(MethodImplOptions.AggressiveInlining)]
public static int Square(int x) => x * x;          // просьба встроить даже если эвристика против

[MethodImpl(MethodImplOptions.NoInlining)]
public static void Measure() { }                    // запретить: нужно для точности замеров
```

> [!warning] Подводные камни
> - **Замеры без прогрева.** `Stopwatch` вокруг первого вызова измеряет JIT и tier 0, а не алгоритм.
> - **Отключение многоуровневой компиляции «для скорости».** Пиковая производительность не вырастет (tier 1 достигается и так), а старт станет заметно медленнее.
> - **Ожидание, что Native AOT ускорит вычисления.** Он ускоряет старт и снижает память; пиковая пропускная способность обычно чуть **ниже** JIT из-за отсутствия PGO и знания процессора.
> - **AOT без проверки предупреждений обрезки.** Приложение собирается, а падает в рантайме на рефлексии — и только в опубликованном виде, не в Debug.
> - **R2R без указания RID.** Предкомпиляция требует целевой платформы; без неё эффекта не будет.
> - **Частый рестарт инстансов в Kubernetes.** Каждый рестарт — заново прогрев JIT и кешей; отсюда важность readiness-проб и разумных лимитов CPU (при жёстком троттлинге прогрев тянется дольше).
> - **`AggressiveInlining` везде.** Раздувает код, ухудшает попадание в кеш инструкций и может замедлить; применяется точечно и по бенчмарку.

> [!example] Как делают в бою
> Для обычного веб-сервиса оставляют JIT и включают ReadyToRun при публикации в контейнер: старт быстрее, совместимость полная, пиковая производительность не страдает. Прогрев после старта делают явно — readiness-проба дергает несколько ключевых эндпоинтов, чтобы первые пользовательские запросы не платили за JIT и заполнение пулов соединений.
> Для CLI-утилит, serverless и sidecar-процессов выбирают Native AOT: старт в единицы миллисекунд и в разы меньше памяти решают, а ограничения по рефлексии для такого кода несущественны.
> Обновление рантайма рассматривают как бесплатную оптимизацию: каждый релиз .NET улучшает JIT и BCL, и переход на новую LTS-версию обычно даёт единицы–десятки процентов без единой строки изменений. Это самый дешёвый способ ускорить сервис.
> Что не делают: не крутят переменные `DOTNET_Tiered*` в проде без бенчмарка — умолчания подобраны хорошо, и почти всякая ручная настройка делает хуже.

## Вопросы с собеседований

> [!question]- Как работает многоуровневая компиляция и зачем она нужна?
> JIT компилирует каждый метод при первом вызове, и полная оптимизация стоит времени — на старте это заметно. Поэтому первый вариант кода генерируется быстро и без оптимизаций (tier 0): приложение начинает работать раньше. Рантайм считает вызовы, и когда метод оказывается горячим (порядка тридцати вызовов) или содержит долгий цикл, он перекомпилируется с полными оптимизациями (tier 1); для метода, который уже выполняется, применяется on-stack replacement — подмена кода на ходу. Дополнительно tier 0 инструментирован и собирает профиль: какие типы приходят в виртуальные вызовы, какие ветви берутся; tier 1 использует эту статистику (dynamic PGO, включён по умолчанию с .NET 8), девиртуализируя доминирующий тип и переупорядочивая код. Итог — быстрый старт и высокая пиковая производительность одновременно; цена в том, что первые вызовы медленнее, из-за чего замеры без прогрева бессмысленны.

> [!question]- Чем ReadyToRun отличается от Native AOT?
> ReadyToRun добавляет в сборку предкомпилированный машинный код **рядом с IL**: старт ускоряется, потому что JIT не нужно компилировать всё с нуля, но рантайм остаётся полноценным — горячие методы перекомпилируются в tier 1 с профилем и знанием процессора, рефлексия и динамическая загрузка работают. Native AOT компилирует приложение в нативный исполняемый файл целиком и **исключает JIT** из поставки: старт падает до единиц миллисекунд, потребление памяти снижается, но теряются рефлексия по неизвестным статически членам, генерация кода в рантайме, загрузка плагинов, и требуется отдельная сборка под каждую платформу. По производительности после прогрева JIT обычно немного выигрывает у AOT. Выбор по сценарию: долгоживущий сервис — JIT (плюс R2R), короткоживущий процесс или CLI — Native AOT.

> [!question]- Почему первый запрос к ASP.NET Core приложению медленнее остальных?
> Складывается несколько факторов. Основной — JIT-компиляция всего пути запроса в tier 0: Kestrel, конвейер middleware, роутинг, привязка модели, сериализация, EF Core. Дальше первое обращение к базе устанавливает физическое соединение и наполняет пул, EF Core компилирует модель и планы запросов, кеши приложения пусты, страницы памяти ещё не тронуты. После нескольких десятков запросов горячие методы переходят в tier 1 с профилем, соединения переиспользуются, кеши прогреты — и время отклика падает на порядок. Стандартные меры: публикация с ReadyToRun, прогревочные запросы в readiness-пробе, отказ от частых рестартов инстансов, а при жёстких требованиях к холодному старту — Native AOT.

> [!question]- Что JIT умеет такого, чего не может AOT-компилятор?
> Главное — он знает целевую машину и фактическое поведение программы. Знание процессора позволяет использовать доступные векторные расширения (в .NET 10 — AVX-512, AVX10.2, ARM SVE2) вместо кода под общий знаменатель. Знание профиля (dynamic PGO) даёт девиртуализацию виртуальных и интерфейсных вызовов по доминирующему типу с проверкой и запасной ветвью, более точное встраивание, переупорядочивание горячих и холодных блоков. Плюс JIT сворачивает как константы значения, известные только в рантайме, — платформу, размер вектора, конфигурационные флаги, — и убирает соответствующие ветви целиком. Наконец, начиная с .NET 9 работает escape-анализ: объекты, ссылки на которые не покидают метод, могут размещаться на стеке, то есть часть аллокаций исчезает без изменений в коде. AOT всё это делает статически и потому консервативнее.

## Задачи

### Задача 1. Объяснить замер

Разработчик мерит два варианта кода в `Main` через `Stopwatch` и получает, что первый вариант в 8 раз медленнее. При переносе в BenchmarkDotNet разница исчезает. Что произошло?

> [!success]- Решение
> В первом варианте в замер попала JIT-компиляция: сам метод и всё, что он вызывает, компилировались в момент измерения, причём в tier 0 — без оптимизаций. Дополнительно первый прогон подтягивал страницы памяти, заполнял кеши процессора и, если использовались коллекции, выполнял начальные аллокации внутренних буферов. Второй вариант выполнялся уже на прогретом коде и потому «выиграл» — измерена разница в прогреве, а не в алгоритме.
> BenchmarkDotNet устраняет это: он запускает измеряемый метод многократно, отбрасывает прогревочные итерации, дожидается перехода в tier 1, считает статистику по множеству запусков и изолирует процесс. Правильный вывод — микрозамеры в `Main` не показывают ничего, кроме порядка величины, и то не всегда; для сравнения вариантов нужен либо BenchmarkDotNet, либо профилировщик на реальной нагрузке.

### Задача 2. Выбрать конфигурацию публикации

Для каждого случая выбери: обычная публикация, ReadyToRun или Native AOT. 1) Веб-API в Kubernetes, 20 инстансов, живут сутками. 2) AWS Lambda, вызывается редко, требование к холодному старту 200 мс. 3) CLI-утилита для коллег без установленного .NET. 4) Плагинная система, загружающая сборки по конфигурации.

> [!success]- Решение
> 1. **Обычная публикация плюс ReadyToRun.** Инстансы долгоживущие, поэтому важна пиковая производительность (JIT с PGO), но R2R сокращает время до готовности при масштабировании и перезапусках. Прогрев дополняют readiness-пробой. Native AOT здесь не нужен и вреден: потеря совместимости с частью библиотек не компенсируется выигрышем в стартовых миллисекундах.
> 2. **Native AOT.** Холодный старт — главный критерий, а требование 200 мс для JIT-варианта труднодостижимо. AOT даёт единицы миллисекунд и меньше памяти, что вдобавок снижает стоимость выполнения. Ограничения по рефлексии для функции обычно приемлемы, но их надо проверить: сериализация — через генератор `[JsonSerializable]`.
> 3. **Native AOT plus self-contained.** Рантайма у коллег нет, значит нужна самодостаточная поставка; AOT даёт один файл заметно меньшего размера, чем self-contained с полным рантаймом, и мгновенный старт. Цена — отдельная сборка под каждую платформу (`osx-arm64`, `win-x64`, `linux-x64`).
> 4. **Обычная публикация.** Native AOT исключён принципиально: он не поддерживает динамическую загрузку сборок и `AssemblyLoadContext`. ReadyToRun возможен, но польза невелика, если приложение долгоживущее.

## Итог

- JIT компилирует по одному методу при первом вызове; невызванный код не компилируется никогда.
- Многоуровневая компиляция: tier 0 для быстрого старта, tier 1 для скорости, OSR для уже идущих циклов.
- Dynamic PGO (по умолчанию с .NET 8) даёт девиртуализацию и точное встраивание по фактическому профилю.
- JIT знает процессор и профиль — этого AOT не может; в .NET 9+ он ещё и размещает часть объектов на стеке.
- ReadyToRun ускоряет старт, сохраняя все возможности рантайма и путь к tier 1.
- Native AOT даёт старт в миллисекунды и меньше памяти ценой рефлексии, плагинов и отдельной сборки под платформу.
- Замеры обязательно с прогревом: без него измеряется tier 0 и JIT-компиляция.
- Обновление рантайма — самая дешёвая оптимизация: каждый релиз улучшает JIT и BCL.
