# AssemblyLoadContext и загрузка плагинов

> [!abstract] Коротко
> `AssemblyLoadContext` (ALC) — механизм изоляции загруженных сборок в .NET Core и новее, заменивший домены приложений (`AppDomain`) из .NET Framework. Каждый контекст загружает свои сборки, и одна и та же библиотека, загруженная в двух контекстах, даёт **два разных типа**: приведение между ними невозможно. Это и есть основа плагинной архитектуры — плагины с конфликтующими версиями зависимостей могут сосуществовать. Контекст можно объявить выгружаемым (`isCollectible`), и тогда после освобождения всех ссылок сборки будут выгружены сборщиком мусора — но добиться этого на практике сложно, поэтому в серверных приложениях чаще выбирают изоляцию процессами.

## Зачем это нужно

Три реальных сценария: система расширений, где сторонние модули поставляются отдельно от приложения; конфликт версий, когда два модуля требуют несовместимые версии одной библиотеки; горячая перезагрузка кода без перезапуска процесса.

Плюс это ответ на классический вопрос: «а где в .NET Core домены приложений и как теперь выгружать сборки».

---

## Что заменило AppDomain

В .NET Framework `AppDomain` давал изоляцию, выгрузку и границу безопасности внутри процесса. В .NET Core от этого осталась только изоляция и (частично) выгрузка:

| | `AppDomain` (.NET Framework) | `AssemblyLoadContext` (.NET Core+) |
|---|---|---|
| Изоляция типов | да | да |
| Выгрузка | да, домена целиком | да, если контекст `isCollectible` |
| Граница безопасности | да (Code Access Security) | нет — CAS удалён |
| Вызовы между границами | через маршалинг и прокси | обычные вызовы, но типы разные |
| Существует в .NET 10 | нет (только заглушка API) | да |

Главное следствие: **изоляция ненадёжной сборки внутри процесса больше не является механизмом безопасности**. Плагин, загруженный в свой ALC, выполняется с теми же правами, что и хост: он может читать файлы, ходить в сеть и уронить процесс. Для настоящей изоляции нужен отдельный процесс или контейнер.

## Как работает загрузка

```csharp
using System.Runtime.Loader;

// Контекст по умолчанию: сюда попадает всё, на что ссылается приложение
var defaultAlc = AssemblyLoadContext.Default;

// Свой контекст
var alc = new AssemblyLoadContext("Plugins", isCollectible: true);
Assembly asm = alc.LoadFromAssemblyPath("/plugins/MyPlugin.dll");

foreach (var ctx in AssemblyLoadContext.All)
    Console.WriteLine($"{ctx.Name}: {ctx.Assemblies.Count()} сборок");
```

Ключевое правило разрешения ссылок: когда сборке из контекста нужна зависимость, сначала спрашивается **контекст по умолчанию** (если сборка там уже есть — берётся оттуда), затем вызывается переопределённый метод `Load` контекста. Это позволяет разделять общие контракты и изолировать всё остальное.

### Проблема идентичности типов

```csharp
// Contracts.dll загружена и в Default, и в plugin-контексте
var pluginType = asm.GetType("MyPlugin.Handler")!;
object instance = Activator.CreateInstance(pluginType)!;

// InvalidCastException: интерфейс из другого контекста — ДРУГОЙ тип
IPlugin plugin = (IPlugin)instance;
```

Тип в CLR идентифицируется парой «сборка + полное имя», а сборка — ещё и контекстом загрузки. `IPlugin` из `Default` и `IPlugin` из плагинного ALC — разные типы, и приведение падает.

Правильное решение — сборка контрактов должна загружаться **только в контексте по умолчанию** и быть общей для всех:

```csharp
public sealed class PluginLoadContext : AssemblyLoadContext
{
    private readonly AssemblyDependencyResolver _resolver;

    public PluginLoadContext(string pluginPath)
        : base(name: Path.GetFileNameWithoutExtension(pluginPath), isCollectible: true)
        => _resolver = new AssemblyDependencyResolver(pluginPath);

    protected override Assembly? Load(AssemblyName name)
    {
        // Контракты не загружаем — пусть придут из Default, тогда типы совпадут
        if (name.Name == "MyApp.Contracts") return null;

        string? path = _resolver.ResolveAssemblyToPath(name);
        return path is null ? null : LoadFromAssemblyPath(path);
    }

    protected override IntPtr LoadUnmanagedDll(string name)
    {
        string? path = _resolver.ResolveUnmanagedDllToPath(name);
        return path is null ? IntPtr.Zero : LoadUnmanagedDllFromPath(path);
    }
}
```

`AssemblyDependencyResolver` читает `.deps.json` плагина и разрешает его зависимости так же, как это делает хост для основного приложения, — включая выбор нужного RID для нативных библиотек.

## Полный пример плагинной системы

```csharp
// Контракт — в отдельной сборке, на которую ссылаются и хост, и плагины
public interface IPlugin
{
    string Name { get; }
    Task<string> ExecuteAsync(string input, CancellationToken ct);
}

// Загрузка
public sealed class PluginHost
{
    public static IReadOnlyList<IPlugin> Load(string pluginDirectory)
    {
        var plugins = new List<IPlugin>();

        foreach (var dll in Directory.EnumerateFiles(pluginDirectory, "*.dll"))
        {
            var context = new PluginLoadContext(dll);
            var assembly = context.LoadFromAssemblyPath(Path.GetFullPath(dll));

            foreach (var type in assembly.GetTypes())
            {
                if (!typeof(IPlugin).IsAssignableFrom(type) || type.IsAbstract) continue;
                if (Activator.CreateInstance(type) is IPlugin plugin) plugins.Add(plugin);
            }
        }

        return plugins;
    }
}
```

Плагин собирается как обычная библиотека, но ссылка на контракты помечается так, чтобы она не копировалась рядом с плагином:

```xml
<ProjectReference Include="../MyApp.Contracts/MyApp.Contracts.csproj">
  <Private>false</Private>
  <ExcludeAssets>runtime</ExcludeAssets>
</ProjectReference>
```

Иначе рядом с плагином окажется своя копия `Contracts.dll`, она загрузится в его контекст, и приведение снова сломается.

## Выгрузка

```csharp
static (WeakReference Reference, string Result) Run(string pluginPath)
{
    var context = new PluginLoadContext(pluginPath);
    var weak = new WeakReference(context);

    var assembly = context.LoadFromAssemblyPath(pluginPath);
    var plugin = (IPlugin)Activator.CreateInstance(assembly.GetType("Plugin.Main")!)!;
    var result = plugin.ExecuteAsync("данные", CancellationToken.None).GetAwaiter().GetResult();

    context.Unload();                     // запрос на выгрузку
    return (weak, result);                // ВСЕ ссылки на плагин должны выйти из области
}

var (weak, _) = Run("/plugins/A.dll");
for (int i = 0; weak.IsAlive && i < 10; i++)
{
    GC.Collect();
    GC.WaitForPendingFinalizers();
}
Console.WriteLine(weak.IsAlive ? "не выгрузился" : "выгружен");
```

Выгрузка происходит, только когда **не осталось ни одной ссылки** на что-либо из контекста: ни на объекты плагина, ни на его типы (`Type`, `MethodInfo`), ни на делегаты, указывающие на его методы. Достаточно одной забытой подписки на событие хоста, одного закешированного `Type` или значения в статическом поле — и контекст останется навсегда.

Именно поэтому метод `Run` в примере отделён: локальные переменные с плагином должны выйти из области видимости до сборки. Отсюда практическое ограничение: **выгрузка работает, но требует дисциплины**, а отладка «почему не выгружается» сводится к поиску держателя в дампе ([[Слабые ссылки и утечки памяти в .NET]]).

### Только для чтения метаданных

Если сборку нужно лишь проанализировать (найти типы, прочитать атрибуты) и не выполнять, применяют `MetadataLoadContext`:

```csharp
using System.Reflection;
using System.Reflection.PortableExecutable;

var resolver = new PathAssemblyResolver(Directory.GetFiles(runtimeDir, "*.dll"));
using var mlc = new MetadataLoadContext(resolver);
Assembly asm = mlc.LoadFromAssemblyPath("/plugins/MyPlugin.dll");

foreach (var t in asm.GetTypes()) Console.WriteLine(t.FullName);   // выполнить код нельзя
```

Такой контекст не выполняет код и легко освобождается — это правильный выбор для инструментов анализа, генераторов и валидаторов пакетов.

## Когда плагины вообще не нужны

Динамическая загрузка сборок — тяжёлое решение с реальными издержками: изоляция без границы безопасности, сложная выгрузка, конфликты версий, несовместимость с Native AOT и обрезкой ([[Native AOT: когда стоит]]).

Альтернативы, которые в серверных приложениях выбирают чаще:

| Задача | Альтернатива |
|---|---|
| Расширяемость поведения | стратегии и DI: реализации регистрируются в контейнере |
| Сторонние расширения | отдельный процесс или контейнер, взаимодействие по HTTP/gRPC |
| Пользовательские правила | скриптовый движок с песочницей или декларативный DSL |
| Модульность внутри решения | модульный монолит с `internal` и явными контрактами |
| Горячее обновление | перезапуск инстанса при деплое, blue-green |

Отдельный процесс даёт настоящую изоляцию: сбой плагина не роняет хост, ограничение ресурсов делается средствами ОС, версии зависимостей независимы. Цена — сериализация на границе и накладные расходы вызова, но для большинства сценариев это дешевле, чем ловить утечки контекстов.

> [!warning] Подводные камни
> - **Копия контрактов рядом с плагином.** Загружается в его контекст, и приведение к интерфейсу падает с `InvalidCastException`. Ссылку помечают `Private=false`.
> - **Ожидание безопасности.** ALC изолирует типы, но не права: плагин может всё, что может процесс. CAS в .NET Core удалён.
> - **Контекст не выгружается.** Любая оставшаяся ссылка — объект, `Type`, делегат, подписка, статическое поле — удерживает его целиком.
> - **`Assembly.LoadFrom` вместо контекста.** Грузит в контекст по умолчанию, теряя изоляцию и делая выгрузку невозможной.
> - **Загрузка одного файла дважды.** `LoadFromAssemblyPath` в разных контекстах даёт разные типы; в одном — вернёт уже загруженный экземпляр.
> - **Native AOT и обрезка.** Динамическая загрузка недоступна в AOT, а компоновщик удаляет типы, используемые только через рефлексию.
> - **Плагины в веб-приложении «для удобства».** Обычно достаточно DI-регистрации; ALC добавляет класс проблем, который потом придётся отлаживать в проде.

> [!example] Как делают в бою
> В типичном .NET-сервисе `AssemblyLoadContext` не встречается вовсе: расширяемость реализуется интерфейсами и регистрацией в DI, а модульность — сборками с `internal`-типами. Динамическая загрузка появляется в специфических продуктах: платформы с пользовательскими расширениями, IDE и редакторы, серверы сборки, инструменты миграции данных, где набор обработчиков не известен заранее.
> Когда её всё же применяют, схема устоявшаяся: отдельная сборка контрактов, загружаемая только в контекст по умолчанию; свой `PluginLoadContext` с `AssemblyDependencyResolver`, читающим `.deps.json` плагина; создание экземпляров по интерфейсу; никакого кеширования `Type` и делегатов вне контекста, если планируется выгрузка.
> Выгрузку в долгоживущих сервисах стараются не использовать: гарантировать отсутствие ссылок сложно, а неудача проявляется как медленная утечка. Вместо этого либо перезапускают процесс, либо изначально выносят плагины в отдельные процессы — тогда «выгрузка» превращается в завершение процесса, что надёжно по построению.
> Для инструментов, которым нужно лишь прочитать метаданные (анализаторы, генераторы документации, проверки совместимости API), используют `MetadataLoadContext`: он не выполняет код и не создаёт проблем с выгрузкой.

## Вопросы с собеседований

> [!question]- Что заменило `AppDomain` в .NET Core и чем отличается?
> `AssemblyLoadContext`. Он сохранил изоляцию сборок (типы из разных контекстов различаются) и возможность выгрузки — если контекст создан как `isCollectible`. Но он **не** является границей безопасности: механизм Code Access Security из .NET Framework удалён, поэтому загруженный код выполняется с теми же правами, что и хост, и может сделать всё, что может процесс. Ещё одно отличие — способ взаимодействия: между доменами приложения требовался маршалинг и прокси, а между контекстами вызовы обычные, просто типы из разных контекстов несовместимы. Практический вывод: если задача — изоляция ненадёжного кода, `AssemblyLoadContext` её не решает, нужен отдельный процесс или контейнер; если задача — разрешить конфликт версий зависимостей между модулями, он подходит.

> [!question]- Почему плагин не приводится к интерфейсу, объявленному в хосте?
> Потому что тип в CLR идентифицируется не только полным именем, но и сборкой, а сборка — контекстом загрузки. Если рядом с плагином лежит своя копия сборки контрактов, она загрузится в плагинный контекст, и получится два разных типа `IPlugin`, между которыми приведение невозможно — отсюда `InvalidCastException` при формально идентичных интерфейсах. Решение состоит из двух частей. В коде: переопределённый метод `Load` контекста должен возвращать `null` для сборки контрактов, тогда она будет взята из контекста по умолчанию. В сборке плагина: ссылка на проект контрактов помечается `Private=false` и `ExcludeAssets=runtime`, чтобы её копия не попала в каталог плагина. Общее правило — контракты общие и живут в контексте по умолчанию, всё остальное изолировано.

> [!question]- Как выгрузить сборку и почему это часто не получается?
> Контекст создаётся с `isCollectible: true`, затем вызывается `Unload()`, после чего сборщик мусора выгрузит сборки — но только когда исчезнут **все** ссылки на что-либо из этого контекста: экземпляры типов плагина, объекты `Type` и `MethodInfo`, делегаты на его методы, подписки на события хоста, значения в статических полях, закешированные результаты. Достаточно одной такой ссылки, чтобы контекст остался в памяти навсегда. Проверяют выгрузку через `WeakReference` на контекст и цикл с принудительной сборкой. На практике в долгоживущих сервисах добиться выгрузки сложно, и неудача выглядит как медленная утечка памяти, которую приходится искать по дампу командой `gcroot`. Поэтому чаще выбирают либо перезапуск процесса, либо вынесение плагинов в отдельные процессы, где освобождение гарантируется завершением процесса.

## Задачи

### Задача 1. Найти причину `InvalidCastException`

Плагинная система: хост объявляет `IPlugin`, плагин его реализует, загрузка идёт через свой `AssemblyLoadContext`. При приведении — `InvalidCastException`, хотя интерфейс тот же. Что проверить?

> [!success]- Решение
> Почти наверняка сборка контрактов загружена дважды — в контексте по умолчанию (её тянет хост) и в плагинном (её копия лежит рядом с плагином). Проверка:
> ```csharp
> var hostType = typeof(IPlugin);
> var pluginInterface = pluginType.GetInterfaces().First(i => i.FullName == hostType.FullName);
> Console.WriteLine(hostType.Assembly.Location);
> Console.WriteLine(pluginInterface.Assembly.Location);        // разные пути — вот и причина
> Console.WriteLine(AssemblyLoadContext.GetLoadContext(hostType.Assembly)?.Name);
> Console.WriteLine(AssemblyLoadContext.GetLoadContext(pluginInterface.Assembly)?.Name);
> ```
> Лечение с двух сторон. В контексте — не загружать контракты самому:
> ```csharp
> protected override Assembly? Load(AssemblyName name)
>     => name.Name == "MyApp.Contracts" ? null : LoadFromResolver(name);
> ```
> В проекте плагина — не копировать контракты в его каталог:
> ```xml
> <ProjectReference Include="../MyApp.Contracts/MyApp.Contracts.csproj" Private="false" ExcludeAssets="runtime" />
> ```
> Проверка после исправления: `hostType.Assembly.Location` и `pluginInterface.Assembly.Location` должны совпадать, а контекст обоих — быть `Default`.

### Задача 2. Выбрать архитектуру

Нужно дать клиентам возможность писать свои правила обработки заказов. Правила могут быть произвольным кодом. Что предложить?

> [!success]- Решение
> Плагины в том же процессе через `AssemblyLoadContext` здесь неправильный выбор: изоляция ALC не является границей безопасности, поэтому чужой код сможет читать конфигурацию, ходить в сеть, исчерпать память и уронить сервис вместе со всеми клиентами. Плюс появятся проблемы выгрузки и конфликтов версий.
> Варианты по возрастанию гибкости и стоимости:
> **Декларативные правила.** Если задача сводится к условиям и коэффициентам, лучший вариант — DSL или конфигурация (набор предикатов и действий), интерпретируемая своим движком. Безопасно, тестируемо, доступно неразработчикам.
> **Скриптовый движок с песочницей.** Выполнение скриптов с ограничением API, времени и памяти. Даёт выразительность без произвольного кода на .NET.
> **Отдельный процесс или контейнер.** Правила клиента собираются в свой образ, запускаются изолированно, взаимодействие по gRPC или через очередь, ресурсы ограничены средствами платформы. Сбой и злоупотребление затрагивают только этого клиента.
> Практический выбор в большинстве продуктов — первый вариант, а если нужна полная свобода, третий. Загрузка чужих сборок в свой процесс остаётся уместной только для доверенного кода — например, модулей, которые пишет та же команда.

## Итог

- `AssemblyLoadContext` заменил `AppDomain`: изоляция типов и выгрузка есть, границы безопасности нет.
- Тип идентифицируется парой «сборка + имя», а сборка — контекстом: одна библиотека в двух контекстах даёт два разных типа.
- Контракты должны загружаться только в контекст по умолчанию; в проекте плагина ссылку помечают `Private=false`.
- `AssemblyDependencyResolver` разрешает зависимости плагина по его `.deps.json`, включая нативные библиотеки.
- Выгрузка требует `isCollectible` и полного отсутствия ссылок — любая забытая подписка или закешированный `Type` её блокирует.
- `MetadataLoadContext` — для анализа сборок без выполнения кода.
- Динамическая загрузка несовместима с Native AOT и осложняет обрезку.
- Для ненадёжного кода изоляция нужна процессом или контейнером, а не контекстом загрузки.
