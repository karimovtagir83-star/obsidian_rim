# Span, ReadOnlySpan и Memory

> [!abstract] Коротко
> `Span<T>` — это ссылка на непрерывный участок памяти плюс длина: два поля, никакой аллокации. Он умеет указывать на массив, на буфер из `stackalloc`, на нативную память и на часть строки, а срез (`span[1..4]`) создаёт новое окно в **ту же** память вместо копии. Цена — жёсткие ограничения: `Span<T>` объявлен как `ref struct` и не может быть полем класса, использоваться в `async`-методе, захватываться лямбдой или упаковываться, потому что он может ссылаться на стек. Там, где эти ограничения мешают, применяют `Memory<T>` — он живёт в куче и отдаёт `Span<T>` по требованию.

## Зачем это нужно

Классическая проблема .NET-кода — промежуточные копии:

```csharp
// Разбор "key=value": три аллокации на строку, миллион строк → три миллиона объектов
var parts = line.Split('=');
var key = parts[0].Trim();
var value = parts[1].Trim();

// То же самое без единой аллокации
var span = line.AsSpan();
int sep = span.IndexOf('=');
ReadOnlySpan<char> key2 = span[..sep].Trim();
ReadOnlySpan<char> value2 = span[(sep + 1)..].Trim();
```

Именно на `Span<T>` переписаны `System.Text.Json`, Kestrel, форматирование чисел и дат, регулярные выражения — поэтому современный .NET заметно быстрее версий пятилетней давности при том же прикладном коде.

## Устройство

```csharp
// Упрощённо Span<T> — это:
public readonly ref struct Span<T>
{
    internal readonly ref T _reference;   // управляемая ссылка на первый элемент
    private readonly int _length;
}
```

Два поля, 16 байт на x64, размещается на стеке. Никакого объекта в куче не создаётся, поэтому создание спана бесплатно.

```csharp
int[] array = [1, 2, 3, 4, 5];

Span<int> fromArray = array;                       // весь массив
Span<int> slice = array.AsSpan(1, 3);              // окно [2,3,4] — без копирования
Span<byte> onStack = stackalloc byte[128];         // буфер на стеке
ReadOnlySpan<char> fromString = "текст".AsSpan();  // строку менять нельзя — только ReadOnly
ReadOnlySpan<byte> utf8 = "OK"u8;                  // UTF-8 литерал (C# 11), без аллокации вовсе

slice[0] = 99;
Console.WriteLine(array[1]);                        // 99 — это та же память
```

`ReadOnlySpan<T>` — версия только для чтения. Правило API: принимай `ReadOnlySpan<T>`, если только читаешь, и `Span<T>`, если изменяешь на месте; тогда метод одинаково работает с массивом, стековым буфером, строкой и срезом.

### Что даёт

- **Ноль аллокаций** при срезах и передаче частей данных.
- **Единый API** для массива, стека, нативной памяти и строки.
- **Безопасность**: проверка границ сохраняется, в отличие от указателей.
- **Оптимизации JIT**: устранение проверок границ в канонических циклах и векторизация операций (`IndexOf`, `SequenceEqual`, `Sum` работают через SIMD).

## Ограничения: почему `ref struct`

`Span<T>` может указывать на стек. Если бы его разрешили сохранить в поле объекта или захватить в лямбду, ссылка пережила бы кадр метода и стала «висячей» — то есть указывала бы на переиспользованную память. Компилятор это предотвращает правилами безопасности ссылок:

```csharp
class Holder
{
    // Span<int> _field;                 // Ошибка: ref struct не может быть полем класса
}

async Task WrongAsync()
{
    Span<int> s = stackalloc int[10];
    // await Task.Delay(1);              // Ошибка: span не может пережить await
}

void Wrong2()
{
    Span<int> s = stackalloc int[10];
    // Action a = () => s[0] = 1;        // Ошибка: захват в лямбду запрещён
}

// object o = span;                       // Ошибка: упаковка запрещена
// var list = new List<Span<int>>();      // Ошибка: не может быть аргументом типа (до C# 13)
```

С C# 13 ограничение частично снято: `ref struct` может реализовывать интерфейсы, а обобщённый параметр может быть объявлен как `where T : allows ref struct`. Это позволило писать обобщённые алгоритмы над спанами, но фундаментальное правило осталось: значение не должно пережить память, на которую ссылается.

## Memory\<T\>: когда ограничения мешают

```csharp
public sealed class BufferHolder
{
    private readonly Memory<byte> _buffer;          // Memory можно хранить в поле

    public BufferHolder(byte[] data) => _buffer = data;

    public async Task WriteAsync(Stream stream, CancellationToken ct)
    {
        await stream.WriteAsync(_buffer, ct);        // и использовать в async
        ProcessSync(_buffer.Span);                   // Span получаем в момент использования
    }

    private static void ProcessSync(Span<byte> span) { }
}
```

| | `Span<T>` | `Memory<T>` |
|---|---|---|
| Тип | `ref struct`, только стек | обычная структура |
| Поле класса | нельзя | можно |
| `async`, лямбды, дженерики | нельзя (с оговорками C# 13) | можно |
| Может указывать на стек | да | нет (только куча или нативная память) |
| Доступ к элементам | напрямую | через `.Span` |
| Где применять | синхронный горячий код, парсинг | асинхронные API, хранение, конвейеры |

Правило: **`Memory<T>` для хранения и передачи через асинхронные границы, `Span<T>` — для непосредственной работы**. Асинхронные методы BCL (`Stream.ReadAsync`, `Socket.SendAsync`, `PipeWriter`) принимают именно `Memory<T>`.

## Типовые приёмы

### Разбор без аллокаций

```csharp
static bool TryParseCsvLine(ReadOnlySpan<char> line, out long id, out decimal amount)
{
    id = 0; amount = 0;

    int first = line.IndexOf(';');
    if (first < 0) return false;
    if (!long.TryParse(line[..first], out id)) return false;      // TryParse умеет спаны

    var rest = line[(first + 1)..];
    int second = rest.IndexOf(';');
    var amountSpan = second < 0 ? rest : rest[..second];

    return decimal.TryParse(amountSpan, System.Globalization.NumberStyles.Number,
                            System.Globalization.CultureInfo.InvariantCulture, out amount);
}
```

### Форматирование в буфер

```csharp
Span<char> buffer = stackalloc char[32];
if (DateTime.UtcNow.TryFormat(buffer, out int written, "yyyy-MM-dd"))
{
    ReadOnlySpan<char> formatted = buffer[..written];   // строка так и не создалась
}
```

Интерфейсы `ISpanFormattable` и `ISpanParsable<T>` реализованы почти для всех примитивов — это позволяет форматировать и разбирать без промежуточных строк.

### Поиск по набору символов

```csharp
using System.Buffers;

private static readonly SearchValues<char> Separators = SearchValues.Create([',', ';', '\t']);

int index = line.AsSpan().IndexOfAny(Separators);       // .NET 8+, векторизовано
```

### Работа с большими буферами

```csharp
var pool = System.Buffers.ArrayPool<byte>.Shared;
byte[] rented = pool.Rent(64 * 1024);
try
{
    Span<byte> buffer = rented.AsSpan(0, 64 * 1024);    // работаем со спаном
    int read = stream.Read(buffer);
    Process(buffer[..read]);
}
finally { pool.Return(rented); }
```

Комбинация «пул массивов плюс `Span<T>`-срезы» — стандартный способ обработки потоков данных без давления на GC и LOH ([[Поколения GC, LOH и режимы сборщика]]).

### Полезные операции

```csharp
Span<int> data = [5, 3, 1, 4];
data.Sort();                                  // на месте
data.Reverse();
data.Fill(0);
data.Clear();
bool eq = data.SequenceEqual([0, 0, 0, 0]);   // векторизованное сравнение
int idx = data.IndexOf(3);
data[..2].CopyTo(other);
```

Плюс низкоуровневый мост между представлениями:

```csharp
using System.Runtime.InteropServices;

Span<byte> bytes = MemoryMarshal.AsBytes(data);                 // тот же буфер как байты
ref int first = ref MemoryMarshal.GetReference(data);            // ссылка на первый элемент
Span<int> fromList = CollectionsMarshal.AsSpan(list);            // прямой доступ к буферу List<T>
```

`CollectionsMarshal.AsSpan` даёт доступ к внутреннему массиву `List<T>` без копирования — быстро, но небезопасно: любое изменение размера списка делает спан невалидным.

## Совместимость

```csharp
// Спан → массив (копия, аллокация): только когда результат должен жить дольше
byte[] copy = span.ToArray();

// Массив/строка → спан (без копии)
ReadOnlySpan<char> s = text.AsSpan();
Span<byte> b = array.AsSpan(offset, length);

// Memory → Span
Span<byte> view = memory.Span;

// C# 14 расширил неявные преобразования между Span<T>, ReadOnlySpan<T> и T[],
// поэтому явных AsSpan() в коде стало меньше
```

Метод, принимающий `ReadOnlySpan<T>`, можно вызвать и с массивом, и со строкой, и со стековым буфером — без единой конверсии в рантайме. Именно поэтому современный BCL объявляет параметры именно так.

> [!warning] Подводные камни
> - **`stackalloc` в цикле.** Память освобождается только при выходе из метода: тысяча итераций переполнит стек. Выделять до цикла.
> - **Большой `stackalloc`.** Больше нескольких килобайт — риск переполнения; для крупных буферов `ArrayPool`.
> - **Спан на `List<T>` через `CollectionsMarshal`.** После `Add`/`Remove` внутренний массив может быть пересоздан — спан начнёт указывать на старый.
> - **`ToArray()` из привычки.** Сводит на нет весь смысл: копия и аллокация.
> - **Попытка сохранить `Span<T>`.** Компилятор запретит; если нужно хранить, это `Memory<T>` или массив.
> - **`Memory<T>` не значит «безопасно всегда».** Если он получен из пула и массив уже возвращён, доступ через `.Span` читает чужие данные.
> - **Изменение через `ReadOnlySpan<char>` над строкой.** Прямого способа нет, но `MemoryMarshal` позволяет обойти защиту — так делать нельзя: строки иммутабельны и интернированы, порча одной затронет весь процесс.
> - **Преждевременная оптимизация.** В обработчике HTTP-запроса `Split` вместо спанов не заметен; спаны нужны там, где счёт идёт на миллионы операций.

> [!example] Как делают в бою
> В прикладном коде спаны появляются точечно: разбор больших файлов и логов, обработка бинарных протоколов, форматирование в горячих путях. Обычная бизнес-логика по-прежнему пишется на строках и коллекциях — читаемость важнее, а выигрыш незаметен.
> Где спаны обязательны — в библиотечном и инфраструктурном коде. Стандартный приём для парсера: принимать `ReadOnlySpan<char>` (тогда метод работает и со строкой, и со срезом, и со стековым буфером), внутри искать разделители через `IndexOf`/`SearchValues`, разбирать значения через `TryParse` по спану и не создавать ни одной промежуточной строки.
> Для ввода-вывода схема другая: буфер берётся из `ArrayPool`, передаётся в асинхронные методы как `Memory<byte>`, а синхронная обработка внутри работает со `Span<byte>`. Так устроены `PipeReader`/`PipeWriter` и весь сетевой стек.
> Проверяют эффект всегда бенчмарком с `MemoryDiagnoser`: цель — нулевые аллокации на операцию. Если после перехода на спаны аллокации остались, значит где-то остался `ToArray`, `ToString` или упаковка.

## Вопросы с собеседований

> [!question]- Что такое `Span<T>` и почему он `ref struct`?
> `Span<T>` — структура из двух полей: управляемой ссылки на начало непрерывного участка памяти и длины. Она даёт единый безопасный доступ к массиву, буферу из `stackalloc`, нативной памяти и части строки, причём срез создаёт новое окно в ту же память без копирования и без аллокации. Объявлен он как `ref struct`, потому что может ссылаться на стек: если бы такое значение разрешили сохранить в поле объекта, захватить в лямбду, упаковать или пронести через `await`, ссылка пережила бы кадр метода и указывала бы на уже переиспользованную память — то есть появилась бы возможность повредить произвольные данные. Правила `ref struct` (нельзя быть полем класса, элементом массива, аргументом типа без `allows ref struct`, нельзя упаковывать, нельзя использовать в асинхронных методах и итераторах) как раз и гарантируют, что значение не переживёт свою память.

> [!question]- Чем `Memory<T>` отличается от `Span<T>`?
> `Memory<T>` — обычная структура, а не `ref struct`, поэтому её можно хранить в поле класса, передавать в асинхронные методы, захватывать в лямбды и использовать как аргумент типа. Плата за это — она не может ссылаться на стек: только на массив в куче, на нативную память или на сегмент владельца буфера. Прямого доступа к элементам у неё нет: чтобы читать и писать, нужно взять `Span<T>` через свойство `.Span` — уже в том синхронном участке кода, где он безопасен. Практическое разделение простое: `Memory<T>` для хранения и передачи через асинхронные границы (именно его принимают `Stream.ReadAsync`, `Socket.SendAsync`, `PipeWriter`), `Span<T>` — для непосредственной работы с данными в синхронном коде. Для доступа только на чтение есть соответствующие `ReadOnlySpan<T>` и `ReadOnlyMemory<T>`.

> [!question]- Почему срез массива копирует, а срез спана — нет?
> Потому что это разные операции. `array[1..4]` для массива вызывает `RuntimeHelpers.GetSubArray`, который создаёт **новый массив** и копирует в него элементы: результат — самостоятельный объект в куче со своим временем жизни, изменения в нём не видны в исходном массиве. `array.AsSpan()[1..4]` создаёт `Span<T>` — структуру из ссылки и длины, указывающую внутрь исходного массива: аллокации нет, копирования нет, запись через срез изменяет исходные данные. Для строк аналогично: `text[1..4]` вызывает `Substring` и создаёт новую строку, а `text.AsSpan(1..4)` — нет. Выбор зависит от того, должен ли результат жить независимо от источника: если да — копия неизбежна, если нет — спан дешевле. В горячем коде разница накапливается быстро: на миллионе строк это миллион лишних объектов.

> [!question]- Когда `stackalloc` уместен, а когда опасен?
> Уместен для небольших буферов известного размера в пределах одного метода: форматирование числа или даты, временный буфер для разбора, короткий массив для вычислений. Типичный безопасный порог — до одного-двух килобайт. Опасен в трёх случаях. Первый — большой размер: стек потока ограничен примерно мегабайтом, и переполнение даёт `StackOverflowException`, который нельзя перехватить, процесс просто умирает. Второй — выделение внутри цикла: память из `stackalloc` освобождается только при выходе из метода, поэтому тысяча итераций тысячекратно увеличит кадр; выделять надо один раз до цикла. Третий — рекурсия: каждый уровень добавляет свой буфер. Когда размер зависит от входных данных, применяют гибридный приём: маленькие размеры через `stackalloc`, большие — через `ArrayPool`, выбирая по порогу в одном условии.

## Задачи

### Задача 1. Переписать без аллокаций

```csharp
static int CountValidLines(string[] lines)
{
    int count = 0;
    foreach (var line in lines)
    {
        var parts = line.Split(':');
        if (parts.Length != 2) continue;
        if (int.TryParse(parts[1].Trim(), out var value) && value > 0) count++;
    }
    return count;
}
```

> [!success]- Решение
> На каждой строке `Split` создаёт массив и две строки, а `Trim` — ещё одну. На миллионе строк это четыре миллиона объектов.
> ```csharp
> static int CountValidLines(string[] lines)
> {
>     int count = 0;
>     foreach (var line in lines)
>     {
>         ReadOnlySpan<char> span = line;
>         int sep = span.IndexOf(':');
>         if (sep < 0) continue;
>
>         ReadOnlySpan<char> value = span[(sep + 1)..].Trim();
>         if (value.IndexOf(':') >= 0) continue;              // ровно один разделитель
>
>         if (int.TryParse(value, out var parsed) && parsed > 0) count++;
>     }
>     return count;
> }
> ```
> Ключевые моменты: неявное преобразование `string` в `ReadOnlySpan<char>` работает без вызова `AsSpan()`; `IndexOf`, `Trim` и срезы у спана не создают объектов; `int.TryParse` имеет перегрузку под спан. Проверка «ровно два поля» выражена через отсутствие второго разделителя — так не приходится материализовать массив частей. Итог: ноль аллокаций в цикле, что подтверждается `MemoryDiagnoser` в бенчмарке.

### Задача 2. Найти ошибку

```csharp
public sealed class Accumulator
{
    private Span<byte> _buffer;                     // (1)

    public async Task ProcessAsync(Stream stream, CancellationToken ct)
    {
        Span<byte> buffer = stackalloc byte[4096];  // (2)
        int read = await stream.ReadAsync(buffer, ct);
    }

    public Span<byte> GetTemp()
    {
        Span<byte> temp = stackalloc byte[16];
        return temp;                                 // (3)
    }
}
```

> [!success]- Решение
> Все три строки не скомпилируются, и в каждом случае компилятор предотвращает реальную ошибку памяти.
> (1) `Span<T>` — `ref struct`, он не может быть полем класса: объект живёт в куче неопределённо долго, а спан мог бы ссылаться на стек, кадр которого давно исчез. Правильно — `Memory<byte>` или обычный массив.
> (2) Спан нельзя пронести через `await`: после возобновления метод может выполняться в другом потоке с другим стеком. Правильно — взять буфер из пула и передать `Memory<byte>`.
> (3) Нельзя вернуть спан на `stackalloc`: память кадра будет переиспользована сразу после возврата.
> ```csharp
> public sealed class Accumulator
> {
>     private readonly Memory<byte> _buffer = new byte[4096];
>
>     public async Task ProcessAsync(Stream stream, CancellationToken ct)
>     {
>         var pool = System.Buffers.ArrayPool<byte>.Shared;
>         byte[] rented = pool.Rent(4096);
>         try
>         {
>             int read = await stream.ReadAsync(rented.AsMemory(0, 4096), ct);
>             Process(rented.AsSpan(0, read));      // Span берём в синхронном участке
>         }
>         finally { pool.Return(rented); }
>     }
>
>     private static void Process(ReadOnlySpan<byte> data) { }
> }
> ```
> Схема каноническая: хранение и асинхронные вызовы — через `Memory<T>` и пул, непосредственная обработка — через `Span<T>` в синхронном коде.

## Итог

- `Span<T>` — ссылка плюс длина: срезы и передача частей данных без аллокаций и копирования.
- Работает поверх массива, `stackalloc`, нативной памяти и строки; проверка границ сохраняется.
- `ref struct`-ограничения (не поле класса, не в `async`, не в лямбде, не упаковывается) защищают от висячих ссылок.
- `Memory<T>` живёт в куче и снимает ограничения; `Span<T>` берут из него в момент использования.
- Принимай `ReadOnlySpan<T>` для чтения — метод станет универсальным для строк, массивов и буферов.
- BCL полна span-перегрузок: `TryParse`, `TryFormat`, `IndexOf`, `SequenceEqual`, `Stream.Read`.
- Стандартная схема ввода-вывода: буфер из `ArrayPool`, передача как `Memory<T>`, обработка как `Span<T>`.
- В прикладном коде спаны нужны точечно; в библиотечном и горячем — по умолчанию.
