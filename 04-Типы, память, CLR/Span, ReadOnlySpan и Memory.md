# Span, ReadOnlySpan и Memory

> [!abstract] Коротко
> `Span<T>` — это ссылка на непрерывный участок памяти плюс длина: два поля, ни одной аллокации. Он умеет указывать на массив, на буфер из `stackalloc`, на нативную память и на часть строки, а срез (`span[1..4]`) — это новое окно в **ту же** память, а не копия. `ReadOnlySpan<T>` — версия только для чтения, `Memory<T>` — версия, которую можно хранить в поле и проносить через `await`. `stackalloc` — один из способов получить память под `Span<T>`, а не отдельная тема: буфер на стеке вместо буфера из массива или пула.

## Зачем это знать

Промежуточные строки и массивы — самый частый источник давления на GC в парсинге, сериализации и сетевом коде: `Split`, `Substring`, `ToString()` плодят объекты там, где данные нужны только на прочтение. `Span<T>` даёт единый способ работать с срезом без копии, но это `ref struct` с жёсткими правилами — не поле, не `async`, не лямбда. Не зная границ, легко предложить `Span<T>` там, где он не скомпилируется (после `await`), или, наоборот, не заметить горячий путь, где он убрал бы реальные аллокации. На ревью это тема про то, оправдана ли сложность, а не про синтаксис.

## Модель

`Span<T>` — структура из двух полей: управляемой ссылки на первый элемент и длины.

```csharp
// Упрощённо:
public readonly ref struct Span<T>
{
    internal readonly ref T _reference;
    private readonly int _length;
}
```

16 байт на x64, размещается на стеке, создание ничего не стоит.

```csharp
int[] array = [1, 2, 3, 4, 5];

Span<int> fromArray = array;                       // весь массив, без копии
Span<int> slice = array.AsSpan(1, 3);              // окно [2,3,4], без копии
Span<byte> onStack = stackalloc byte[128];         // буфер на стеке, тоже без кучи
ReadOnlySpan<char> fromString = "текст".AsSpan();  // строку менять нельзя — только ReadOnly

slice[0] = 99;
Console.WriteLine(array[1]);                        // 99 — это та же память
```

Разница со срезом массива принципиальна: `array[1..4]` вызывает `GetSubArray` и создаёт новый массив с копией; `array.AsSpan()[1..4]` — окно в исходную память. Одно и то же слово «срез» означает разные операции по стоимости.

**Почему `ref struct`.** Span может указывать на стек. Если бы его разрешили сохранить в поле класса, захватить в лямбду или пронести через `await`, ссылка пережила бы кадр метода и указывала бы на уже переиспользованную память. Компилятор запрещает это статически:

```csharp
class Holder { /* Span<int> _field; */ }        // нельзя: поле класса живёт дольше стека

async Task Wrong()
{
    Span<int> s = stackalloc int[10];
    // await Task.Delay(1);                     // нельзя: после возобновления стек другой
}
```

С C# 13 `ref struct` может реализовывать интерфейсы (`where T : allows ref struct`), но правило «значение не переживает свою память» осталось.

**`stackalloc` — способ получить память для Span, а не альтернатива ему.** Выделяет буфер прямо в кадре метода: без кучи, без работы для GC, освобождение — просто выход из метода.

```csharp
Span<byte> buffer = stackalloc byte[128];   // безопасно без unsafe с C# 7.2
```

Два правила, которые ловят большинство ошибок: память живёт **до конца метода**, а не блока — поэтому `stackalloc` в цикле копит буферы вплоть до переполнения стека; и размер не должен зависеть от внешних данных — стек потока около мегабайта, а его переполнение нельзя перехватить (`StackOverflowException` не ловится, процесс просто умирает). Практический ориентир — буферы до одного-двух килобайт; больше — `ArrayPool<T>.Shared.Rent`, гибридно, по порогу в одном условии.

**`Memory<T>`** снимает ограничения `ref struct` ценой того, что не может указывать на стек — только на кучу или нативную память:

```csharp
public sealed class BufferHolder
{
    private readonly Memory<byte> _buffer;           // Memory можно хранить в поле

    public BufferHolder(byte[] data) => _buffer = data;

    public async Task WriteAsync(Stream stream, CancellationToken ct)
    {
        await stream.WriteAsync(_buffer, ct);         // и проносить через await
        Process(_buffer.Span);                        // Span берём в момент использования
    }

    private static void Process(Span<byte> span) { }
}
```

Отсюда практическая схема ввода-вывода: буфер из `ArrayPool<byte>` или `MemoryPool<byte>`, передача в асинхронные методы как `Memory<T>` (`Stream.ReadAsync`, `Socket.SendAsync`, `PipeWriter` принимают именно его), а непосредственная обработка внутри синхронного участка — через `.Span`. Так устроен весь сетевой стек Kestrel.

## Решения

| Ситуация | Что выбрать |
|---|---|
| Разбор строки/бинарных данных внутри одного метода, без `await` | `ReadOnlySpan<T>` |
| Нужно изменить данные на месте (сортировка, форматирование в буфер) | `Span<T>` |
| Буфер нужно хранить в поле, передать в `async`, захватить в лямбду | `Memory<T>` / `ReadOnlyMemory<T>` |
| Небольшой временный буфер известного размера в пределах метода | `stackalloc` (обычно до 1–2 КБ) |
| Размер буфера зависит от входных данных или может быть большим | `ArrayPool<T>.Rent`, не `stackalloc` |
| Результат должен жить дольше источника или уйти за границу API, которое спанов не знает | обычный массив/строка (`.ToArray()`, `new string(...)`) |
| Обычный контроллер, обработчик запроса, DTO-маппинг — не горячий путь | просто строка/массив/LINQ, без спанов |

Правило по умолчанию: применять `Span<T>`/`Memory<T>` там, где профиль или счётчик показал давление на GC, а не «на всякий случай». Для одиночного запроса в MVC-контроллере разница неизмерима, а код становится сложнее для ревью.

> [!example] В ServiceShop
> Спаны и `stackalloc` в прикладном коде модулей — не то, что стоит вносить по умолчанию: обработчики MediatR, мапперы DTO, Fluent-конфигурации EF Core читаются лучше на строках и LINQ, и лишняя аллокация на один запрос не видна на фоне похода в MySQL или Kafka. Место, где это оправдано, — общая инфраструктура: кастомный `JsonConverter`, парсинг заголовков/идентификаторов в middleware, форматирование ключей для Redis-кеша на горячем пути (тысячи операций в секунду), сборка Outbox-сообщений перед отправкой в Kafka. Если такой код появляется, ожидаемая форма — `ReadOnlySpan<char>` на входе парсера и бенчмарк с `MemoryDiagnoser`, подтверждающий, что аллокации действительно ушли, а не просто переместились в `ToArray()` в конце метода.

> [!warning] Где ошибаются
> - **`stackalloc` в цикле или в рекурсии.** Память освобождается только при выходе из метода — тысяча итераций накапливает буферы и переполняет стек без единого шанса на диагностику.
> - **Размер `stackalloc` из внешних данных.** `stackalloc byte[userLength]` — прямой путь к падению процесса; размер обязан быть ограничен константой или порогом с переходом на `ArrayPool`.
> - **Попытка сохранить `Span<T>`.** Компилятор не даст сделать его полем, обойти это через `MemoryMarshal` — испортить память; правильный инструмент для хранения — `Memory<T>`.
> - **`ToArray()`/`ToString()` по привычке в конце метода.** Сводит на нет весь смысл перехода на спаны — копия и аллокация происходят там же, только позже.
> - **Агент часто:** предлагает `Span<T>`/`stackalloc` в обычном обработчике HTTP-запроса или в разовом маппинге DTO — код усложняется, а выигрыш ниже погрешности измерения на фоне похода в БД.
> - **Агент часто:** пишет `Span<T> Foo() => stackalloc byte[16]` или сохраняет спан в поле — такой код не компилируется, но в сгенерированном виде выглядит правдоподобно и проходит поверхностное ревью до первой сборки.
> - **Агент часто:** не предлагает `ReadOnlySpan<char>` там, где парсер реально в горячем пути (аутентификация на каждый запрос, обработка потока сообщений Kafka), и оставляет `Split`/`Substring`, потому что это «привычный» способ — заметно это только по профилю или alloc-rate в проде.

## Проверка на ревью

- В сигнатуре метода, который только читает данные, стоит `ReadOnlySpan<T>`, а не `Span<T>` или строка/массив без причины.
- Нет `stackalloc` с размером, вычисленным из длины входных данных без верхней границы.
- Нет `stackalloc`/выделения буфера внутри цикла или рекурсии — буфер выносится наружу.
- Каждый `ArrayPool<T>.Rent` имеет парный `Return` в `finally`.
- Спан не используется после `await`, не сохраняется в поле, не захватывается лямбдой.
- Переход на `Span<T>` подтверждён бенчмарком (`MemoryDiagnoser`) или обоснован явным горячим путём — не добавлен «про запас» в обычный CRUD-хендлер.

## Проверь себя

> [!question]- Почему `Span<T>` объявлен как `ref struct` и что это запрещает?
> Потому что он может указывать на стек — на буфер из `stackalloc`. Если бы такое значение разрешили сохранить в поле класса, захватить в лямбду, упаковать в `object` или пронести через `await`, ссылка пережила бы кадр метода и указывала бы на уже переиспользованную память. `ref struct` живёт только на стеке текущего вызова, поэтому компилятор статически запрещает всё, что могло бы продлить его жизнь: поле класса, элемент массива, аргумент дженерика без `allows ref struct`, асинхронные методы и итераторы.

> [!question]- Чем `Memory<T>` отличается от `Span<T>` и когда он нужен?
> `Memory<T>` — обычная структура, не `ref struct`: её можно хранить в поле, передавать в `async`-методы, захватывать в лямбды. Плата — она не может ссылаться на стек, только на массив в куче или нативную память. Прямого доступа к элементам нет: чтобы читать и писать, берут `Span<T>` через `.Span` — уже в синхронном участке, где это безопасно. Практическое разделение: `Memory<T>` для хранения и асинхронных границ (`Stream.ReadAsync`, `PipeWriter`), `Span<T>` — для непосредственной работы с данными.

> [!question]- Чем срез спана отличается от среза массива или строки по цене?
> `array[1..4]` и `text.Substring(...)` создают новый объект в куче и копируют в него элементы — результат живёт независимо от источника, но каждая такая операция это аллокация. `array.AsSpan()[1..4]` и `text.AsSpan(1..4)` — структура из ссылки и длины, указывающая внутрь исходных данных: без копии, без аллокации, изменения через срез видны в источнике. Выбор зависит от того, должен ли результат пережить источник: если да — копия неизбежна, если нужно только прочитать — спан дешевле.

> [!question]- Когда `stackalloc` уместен, а когда опасен?
> Уместен для небольших буферов известного размера в пределах одного метода — форматирование числа, временный буфер для разбора. Безопасный ориентир — до одного-двух килобайт. Опасен в трёх случаях: размер зависит от входных данных (переполнение стека без возможности перехвата), выделение в цикле (память копится до конца метода), рекурсия (каждый уровень добавляет свой буфер). Когда размер непредсказуем, применяют гибрид: маленькое — `stackalloc`, большое — `ArrayPool<T>`, порог в одном условии.

> [!question]- Почему в MVC-контроллере ServiceShop обычно не нужен `Span<T>`, а в парсере Kafka-сообщений — нужен?
> Контроллер обрабатывает один запрос, и время уходит на поход в MySQL, Redis или Kafka — аллокации на строку в маппинге DTO не видны на этом фоне, а спаны добавляют ограничения `ref struct`, которые усложняют код без измеримой пользы. Обработчик, который парсит каждое входящее Kafka-сообщение (тысячи в секунду), работает в горячем пути: аллокация на сообщение умножается на частоту и создаёт заметное давление на GC — здесь `ReadOnlySpan<char>`/`byte` и `TryParse` по спану дают реальный, измеримый эффект.

## Разбор

### Задача 1. Что не скомпилируется и почему

```csharp
public sealed class Accumulator
{
    private Span<byte> _buffer;                     // (1)

    public async Task ProcessAsync(Stream stream, CancellationToken ct)
    {
        Span<byte> buffer = stackalloc byte[4096];
        int read = await stream.ReadAsync(buffer, ct);   // (2)
    }

    public Span<byte> GetTemp()
    {
        Span<byte> temp = stackalloc byte[16];
        return temp;                                 // (3)
    }
}
```

> [!success]- Решение
> Все три строки — ошибки компиляции, и в каждом случае компилятор предотвращает порчу памяти.
> (1) `Span<T>` не может быть полем класса: объект живёт в куче неопределённо долго, а спан мог бы ссылаться на стек, кадр которого уже исчез.
> (2) `stream.ReadAsync` принимает `Memory<byte>`, а не `Span<byte>` — спан нельзя пронести через `await`, потому что после возобновления метод может выполняться с другим стеком.
> (3) Нельзя вернуть спан на `stackalloc`: память кадра переиспользуется сразу после возврата.
> ```csharp
> public sealed class Accumulator
> {
>     private readonly Memory<byte> _buffer = new byte[4096];
>
>     public async Task ProcessAsync(Stream stream, CancellationToken ct)
>     {
>         var pool = System.Buffers.ArrayPool<byte>.Shared;
>         byte[] rented = pool.Rent(4096);
>         try
>         {
>             int read = await stream.ReadAsync(rented.AsMemory(0, 4096), ct);
>             Process(rented.AsSpan(0, read));      // Span берём в синхронном участке
>         }
>         finally { pool.Return(rented); }
>     }
>
>     private static void Process(ReadOnlySpan<byte> data) { }
> }
> ```
> Схема каноническая: хранение и асинхронные вызовы — через `Memory<T>` и пул, непосредственная обработка — через `Span<T>` в синхронном коде.

### Задача 2. Ревью PR агента

Агент прислал утилиту разбора ключа кеша вида `"orders:{id}:{region}"`, вызывается на каждое сообщение из Kafka (сотни тысяч в секунду):

```csharp
static bool TryParseKey(string key, out long id, out string region)
{
    id = 0; region = "";
    var parts = key.Split(':');
    if (parts.Length != 3) return false;
    if (!long.TryParse(parts[1], out id)) return false;
    region = parts[2];
    return true;
}
```

> [!success]- Решение
> На каждый вызов `Split` создаёт массив и три строки-подстроки — на сотнях тысяч сообщений в секунду это заметная нагрузка на gen 0. Это тот случай, где переход на спаны оправдан частотой вызова:
> ```csharp
> static bool TryParseKey(ReadOnlySpan<char> key, out long id, out ReadOnlySpan<char> region)
> {
>     id = 0; region = default;
>     int first = key.IndexOf(':');
>     if (first < 0) return false;
>     var rest = key[(first + 1)..];
>     int second = rest.IndexOf(':');
>     if (second < 0) return false;
>     if (!long.TryParse(rest[..second], out id)) return false;
>     region = rest[(second + 1)..];
>     return true;
> }
> ```
> Что вернуть на доработку: `region` как `ReadOnlySpan<char>` живёт только пока жив `key` — если значение должно пережить вызов (уйти в другой поток, лечь в словарь), потребитель обязан сам сделать `region.ToString()` в этой точке. Стоит явно написать это в комментарии к методу, иначе следующий разработчик (или агент) попробует сохранить `region` в поле и получит ошибку компиляции только на следующем шаге.

## Итог

- `Span<T>` — ссылка плюс длина: срезы и передача частей данных без аллокаций и копий, поверх массива, `stackalloc`, нативной памяти или строки.
- `ref struct`-ограничения (не поле, не `async`, не лямбда, не упаковка) защищают от висячих ссылок на переиспользованную память.
- `stackalloc` — способ получить память для `Span<T>` без кучи; опасен в цикле, в рекурсии и при размере из внешних данных.
- `Memory<T>` снимает ограничения `ref struct` ценой того, что не может указывать на стек — им хранят и передают через `await`, а `Span<T>` берут из него в момент использования.
- Правило по умолчанию — спаны там, где профиль или частота вызова показали давление на GC; в обычном CRUD-коде они добавляют сложность без измеримой пользы.
- Эффект всегда подтверждают `MemoryDiagnoser`, а не ощущением, что «так быстрее».
