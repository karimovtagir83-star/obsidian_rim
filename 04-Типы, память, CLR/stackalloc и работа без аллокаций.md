# stackalloc и работа без аллокаций

> [!abstract] Коротко
> `stackalloc` выделяет буфер прямо в кадре метода: аллокации в куче нет, освобождение бесплатно, работы для GC не возникает. С C# 7.2 результат можно присвоить `Span<T>`, поэтому `unsafe` больше не нужен. Ограничение фундаментальное: стек потока около мегабайта, память живёт до выхода из метода, и вернуть её наружу нельзя. Отсюда стандартная стратегия «zero-allocation» кода: маленькие буферы — на стеке, большие — из `ArrayPool<T>`, а выбор между ними делается по порогу в одном условии.

## Зачем это нужно

Аллокация в .NET дешёвая, но не бесплатная: она увеличивает частоту сборок gen 0, портит локальность кеша, а большие буферы уходят в LOH и живут до полной сборки. В горячем коде — парсерах, сериализаторах, сетевом слое — целью становится **ноль аллокаций на операцию**.

```csharp
// 3 аллокации на каждое число
string text = value.ToString();
byte[] bytes = Encoding.UTF8.GetBytes(text);
stream.Write(bytes);

// 0 аллокаций
Span<char> chars = stackalloc char[16];
value.TryFormat(chars, out int written);
Span<byte> utf8 = stackalloc byte[32];
int len = Encoding.UTF8.GetBytes(chars[..written], utf8);
stream.Write(utf8[..len]);
```

## Синтаксис и правила

```csharp
Span<byte> buffer = stackalloc byte[128];          // безопасно, без unsafe (C# 7.2+)
Span<int> numbers = stackalloc int[] { 1, 2, 3 };
ReadOnlySpan<char> chars = stackalloc char[4] { 'a', 'b', 'c', 'd' };

// В выражениях (C# 8): можно передавать напрямую
Process(stackalloc byte[64]);
```

Что важно знать:

- **Только значимые типы без ссылок** (`unmanaged`): `byte`, `int`, `double`, структуры из таких полей. Массив ссылок на стеке выделить нельзя — GC не отслеживает ссылки в стековых буферах таким образом.
- **Память не обнуляется автоматически** в некоторых сценариях компиляции; полагаться на нули не стоит, при необходимости — `buffer.Clear()`.
- **Живёт до конца метода**, а не до конца блока. Это ключевое отличие от локальной переменной.
- **Возврат наружу невозможен**: компилятор не даст вернуть `Span<T>`, который может указывать на стек ([[Span, ReadOnlySpan и Memory]]).

### Главная ошибка: stackalloc в цикле

```csharp
// ОПАСНО: память копится до выхода из метода
for (int i = 0; i < 10_000; i++)
{
    Span<byte> temp = stackalloc byte[256];        // 2,5 МБ суммарно → переполнение стека
    Process(temp);
}

// Правильно: выделить один раз и переиспользовать
Span<byte> temp = stackalloc byte[256];
for (int i = 0; i < 10_000; i++)
{
    temp.Clear();
    Process(temp);
}
```

То же относится к рекурсии: каждый уровень добавляет свой буфер к общему стеку.

## Сколько можно выделять

Стек управляемого потока — 1 МБ по умолчанию, и он уже частично занят кадрами вызовов. Безопасный ориентир для одного буфера — **до 1–2 КБ**; в ASP.NET Core, где стек делят с глубоким конвейером middleware, лучше держаться ближе к нижней границе.

Проблема в том, что переполнение стека нельзя перехватить: процесс завершается мгновенно, без стектрейса и без шанса на диагностику. Поэтому размер, зависящий от входных данных, всегда ограничивают:

```csharp
const int MaxStack = 256;

static string Encode(ReadOnlySpan<byte> data)
{
    // Гибридная стратегия: маленькое — на стеке, большое — из пула
    char[]? rented = null;
    Span<char> buffer = data.Length <= MaxStack
        ? stackalloc char[MaxStack]
        : (rented = System.Buffers.ArrayPool<char>.Shared.Rent(data.Length * 2));

    try
    {
        int written = EncodeCore(data, buffer);
        return new string(buffer[..written]);
    }
    finally
    {
        if (rented is not null) System.Buffers.ArrayPool<char>.Shared.Return(rented);
    }
}
```

Этот шаблон — самый частый в BCL: он встречается в форматировании чисел, дат, кодировании строк, работе с путями. Стоит запомнить его целиком.

## ArrayPool: пул массивов

Для буферов, которые не помещаются на стек или должны пережить метод, используется пул:

```csharp
var pool = System.Buffers.ArrayPool<byte>.Shared;
byte[] rented = pool.Rent(64 * 1024);        // может вернуть БОЛЬШИЙ массив
try
{
    Span<byte> buffer = rented.AsSpan(0, 64 * 1024);   // работать только с запрошенной частью
    int read = stream.Read(buffer);
    Process(buffer[..read]);
}
finally
{
    pool.Return(rented, clearArray: false);   // clearArray: true, если в буфере были секреты
}
```

Правила работы с пулом:

- **`Rent` возвращает массив не меньше запрошенного**, часто больше (округление до степени двойки). Ориентироваться надо на запрошенную длину, а не на `buffer.Length`.
- **Возврат обязателен** и обязательно в `finally`, иначе пул просто перестаёт помогать.
- **После `Return` массив трогать нельзя**: его уже может использовать другой поток.
- **`clearArray: true`** — когда в буфере были чувствительные данные: пул отдаст массив следующему потребителю как есть.
- Для очень больших или специфичных буферов создают отдельный пул через `ArrayPool<T>.Create(maxArrayLength, maxArraysPerBucket)`, чтобы не засорять общий.

`MemoryPool<T>` — аналог, возвращающий `IMemoryOwner<T>` с `IDisposable`, что удобнее в асинхронном коде:

```csharp
using System.Buffers;
using IMemoryOwner<byte> owner = MemoryPool<byte>.Shared.Rent(4096);
Memory<byte> memory = owner.Memory[..4096];
await stream.ReadAsync(memory, ct);
```

## Прочие приёмы «нулевых аллокаций»

| Проблема | Решение |
|---|---|
| Промежуточные строки при разборе | `ReadOnlySpan<char>` и срезы |
| `ToString()` ради конкатенации | `TryFormat` в `Span<char>` |
| `Split` на части | `IndexOf` + срезы, `MemoryExtensions.Split` (.NET 8+) |
| Массив ради `params` | `params ReadOnlySpan<T>` (C# 13) |
| Замыкание в лямбде | `static`-лямбда или перегрузка с параметром состояния |
| Упаковка структуры | дженерик с ограничением вместо интерфейса |
| Перечислитель `IEnumerable<T>` | конкретный тип со структурным перечислителем |
| Логирование с параметрами | генератор `[LoggerMessage]` |
| Большой `MemoryStream` | `RecyclableMemoryStream` или запись прямо в целевой поток |
| Промежуточные коллекции LINQ | цикл или `CollectionsMarshal.AsSpan` |

```csharp
// Проверка результата: MemoryDiagnoser должен показать 0 B allocated
[MemoryDiagnoser]
public class ParserBench
{
    [Benchmark] public int Parse() => ParseWithSpans(_line);
}
```

Без бенчмарка эта работа бессмысленна: «оптимизация» часто добавляет аллокации в неожиданных местах, и увидеть это можно только измерением.

> [!warning] Подводные камни
> - **`stackalloc` в цикле или в рекурсии.** Память накапливается до выхода из метода.
> - **Размер из внешних данных.** `stackalloc buffer[userLength]` — прямой путь к переполнению стека, которое нельзя перехватить.
> - **Возврат спана наружу.** Компилятор запретит, но попытка обойти через `MemoryMarshal` даёт порчу памяти.
> - **Забытый `Return` в пул.** Пул не течёт (массивы соберёт GC), но смысла в нём не остаётся.
> - **Использование массива после `Return`.** Его уже мог получить другой поток — гонка с непредсказуемыми данными.
> - **Опора на `rented.Length`.** Пул возвращает массив большего размера; работать надо с запрошенной длиной.
> - **Секреты в переиспользуемом буфере.** Без `clearArray: true` данные увидит следующий потребитель.
> - **Zero-allocation везде.** В обычном обработчике запроса это усложняет код без измеримой пользы; оптимизировать надо горячие пути, подтверждённые профилем.

> [!example] Как делают в бою
> Правило простое: прикладной код пишется читаемо, а «нулевые аллокации» применяются там, где профилировщик показал давление на GC — обычно это парсинг больших объёмов, сериализация, сетевой слой и форматирование в логах.
> Канонический шаблон в библиотеках — гибрид: буфер до нескольких сотен байт берётся `stackalloc`, больший арендуется из `ArrayPool`, а весь код работает со `Span<T>`, не зная, откуда пришла память. Именно так написаны форматтеры чисел и дат в BCL.
> Для асинхронных путей вместо `stackalloc` используют `MemoryPool<T>`/`ArrayPool<T>` и `Memory<T>`: спан не переживает `await`.
> Результат всегда фиксируют бенчмарком с `MemoryDiagnoser` и, если это горячий путь в сервисе, — счётчиком `alloc-rate` в проде до и после. Цель формулируется как «ноль аллокаций на операцию», и она проверяема, в отличие от «сделали быстрее».

## Вопросы с собеседований

> [!question]- Что делает `stackalloc` и какие у него ограничения?
> Он выделяет непрерывный блок памяти в кадре текущего метода — то есть на стеке потока. Аллокации в куче нет, освобождение происходит автоматически при выходе из метода и ничего не стоит, сборщик мусора этот буфер не видит. С C# 7.2 результат можно присвоить `Span<T>`, поэтому небезопасный контекст не требуется. Ограничения: только неуправляемые типы (структуры без ссылочных полей); память живёт до конца **метода**, а не блока, поэтому `stackalloc` в цикле или в рекурсии накапливает расход и переполняет стек; вернуть буфер наружу нельзя, компилятор запрещает возврат спана, который может ссылаться на стек; общий размер стека около мегабайта, и его переполнение фатально — `StackOverflowException` перехватить невозможно. Практический ориентир — буферы до одного-двух килобайт, а размер, зависящий от входных данных, обязательно ограничивают порогом с переходом на `ArrayPool`.

> [!question]- Как устроен `ArrayPool<T>` и какие с ним бывают ошибки?
> Это пул переиспользуемых массивов: `Rent` выдаёт массив **не меньше** запрошенного размера (обычно округлённый вверх до степени двойки), `Return` возвращает его обратно. Общий экземпляр `ArrayPool<T>.Shared` разбит на корзины по размерам и по потокам, поэтому аренда дешева и почти не требует синхронизации. Типичные ошибки: работать с `rented.Length` вместо запрошенной длины (лишние байты содержат мусор от предыдущего использования); забывать `Return` — утечки не будет, массив соберёт GC, но пул перестанет приносить пользу; использовать массив после возврата — его уже мог получить другой поток; не очищать буфер с чувствительными данными (для этого есть `Return(array, clearArray: true)`); возвращать один и тот же массив дважды, что нарушает внутреннее состояние пула. Для очень больших буферов создают отдельный пул через `ArrayPool<T>.Create`, чтобы не вытеснять из общего мелкие массивы.

> [!question]- Как выглядит стандартный шаблон «маленькое на стеке, большое из пула»?
> Порог задаётся константой (обычно от 128 до 512 элементов). Если требуемый размер не превышает порога, буфер берётся `stackalloc`; иначе арендуется из `ArrayPool<T>`, а переменная-массив запоминается в локальной переменной, инициализированной `null`. Дальше весь код работает со `Span<T>`, которому безразлично происхождение памяти. В блоке `finally` арендованный массив возвращается, если он был взят. Такой шаблон даёт нулевые аллокации на типичных коротких данных и корректно работает на длинных, не рискуя переполнить стек. Он широко используется в самой BCL — в форматировании чисел и дат, кодировании строк, работе с путями — и его стоит воспроизводить в своих библиотечных методах. В асинхронном коде вместо `stackalloc` берут `MemoryPool<T>` или `ArrayPool<T>` с `Memory<T>`, потому что спан не может пережить `await`.

## Задачи

### Задача 1. Найти ошибку

```csharp
static string ToHex(byte[] data)
{
    Span<char> buffer = stackalloc char[data.Length * 2];
    for (int i = 0; i < data.Length; i++)
    {
        buffer[i * 2] = GetHexChar(data[i] >> 4);
        buffer[i * 2 + 1] = GetHexChar(data[i] & 0xF);
    }
    return new string(buffer);
}
```

> [!success]- Решение
> Размер буфера зависит от входных данных: массив на 1 МБ даст `stackalloc` на 2 миллиона символов (4 МБ), что мгновенно переполнит стек и убьёт процесс без возможности перехвата. Это классическая уязвимость, если размер приходит извне.
> ```csharp
> static string ToHex(ReadOnlySpan<byte> data)
> {
>     const int MaxStack = 256;
>     int needed = data.Length * 2;
>
>     char[]? rented = null;
>     Span<char> buffer = needed <= MaxStack
>         ? stackalloc char[MaxStack]
>         : (rented = System.Buffers.ArrayPool<char>.Shared.Rent(needed));
>
>     try
>     {
>         for (int i = 0; i < data.Length; i++)
>         {
>             buffer[i * 2] = GetHexChar(data[i] >> 4);
>             buffer[i * 2 + 1] = GetHexChar(data[i] & 0xF);
>         }
>         return new string(buffer[..needed]);
>     }
>     finally
>     {
>         if (rented is not null) System.Buffers.ArrayPool<char>.Shared.Return(rented);
>     }
> }
> ```
> Дополнительно параметр стал `ReadOnlySpan<byte>` — метод теперь работает и с массивом, и со срезом без копирования. И практическое замечание: в BCL для этой задачи уже есть `Convert.ToHexString`, который делает всё то же самое оптимально; свою реализацию имеет смысл писать только при нестандартном формате.

### Задача 2. Убрать аллокации из горячего пути

Метод вызывается на каждое сообщение (сотни тысяч в секунду) и формирует ключ вида `"orders:{id}:{region}"`.

```csharp
static string BuildKey(long id, string region) => $"orders:{id}:{region}";
```

> [!success]- Решение
> Строку в итоге всё равно нужно создать (её кладут в кеш или отправляют), поэтому одна аллокация неизбежна. Но интерполяция в старых версиях создавала бы больше; в C# 10+ handler уже пишет напрямую в буфер, так что заметного выигрыша от ручного форматирования не будет — и это важный вывод: **иногда правильный ответ «оптимизировать нечего»**.
> Реальный выигрыш появляется, если ключ не обязан быть строкой:
> ```csharp
> // Вариант 1: писать сразу в целевой буфер, строка не нужна вовсе
> static bool TryWriteKey(Span<char> destination, long id, string region, out int written)
> {
>     var handler = new System.Runtime.CompilerServices.TryWriteInterpolatedStringHandler(
>         literalLength: 9, formattedCount: 2, destination, out bool shouldAppend);
>     written = 0;
>     if (!shouldAppend) return false;
>     return destination.TryWrite($"orders:{id}:{region}", out written);
> }
>
> // Вариант 2: если ключ нужен только для поиска в словаре — использовать составной ключ
> var cache = new Dictionary<(long Id, string Region), Order>();   // без строк вообще
> ```
> Второй вариант обычно и есть настоящее решение: строковый ключ существовал только потому, что «так привычно», а кортеж сравнивается быстрее и не создаёт мусора. Общий принцип оптимизации: сначала спросить, нужна ли операция вообще, и только потом ускорять её.

## Итог

- `stackalloc` выделяет буфер в кадре метода: без аллокации в куче и без работы для GC; с C# 7.2 — без `unsafe`.
- Только неуправляемые типы; память живёт до конца метода, наружу не возвращается.
- Опасности: выделение в цикле и в рекурсии, размер из внешних данных, переполнение стека без возможности перехвата.
- Безопасный ориентир — буферы до 1–2 КБ; больше — `ArrayPool<T>`.
- Канонический шаблон: маленькое на стеке, большое из пула, работа через `Span<T>`, возврат в `finally`.
- `ArrayPool.Rent` даёт массив не меньше запрошенного: ориентироваться на свою длину, а не на `Length`.
- В асинхронном коде вместо стека — `MemoryPool<T>`/`ArrayPool<T>` и `Memory<T>`.
- Цель «ноль аллокаций» проверяется `MemoryDiagnoser`, а не ощущениями; и применяется только к горячим путям.
