# Boxing и unboxing

> [!abstract] Коротко
> Упаковка (boxing) — преобразование значимого типа в ссылочный: рантайм выделяет объект в куче, копирует туда значение и возвращает ссылку. Распаковка (unboxing) — обратное копирование, причём **только в исходный тип**: `int`, упакованный в `object`, нельзя распаковать в `long`. Каждая упаковка — аллокация (24+ байта) плюс копирование, поэтому в горячем коде она незаметно съедает производительность и нагружает GC. Главная сложность в том, что упаковка чаще всего происходит **неявно**: при приведении к `object` или к не-обобщённому интерфейсу, при вызове унаследованных методов `object` на структуре, при использовании старых не-обобщённых API.

## Зачем это нужно

Упаковка — самая частая «невидимая» аллокация в .NET. Код выглядит безобидно, а профилировщик показывает миллионы объектов:

```csharp
// Каждая строка — упаковка
object o = 42;
IComparable c = 42;
Console.WriteLine(string.Format("{0}", 42));
var list = new System.Collections.ArrayList { 42 };
bool eq = 42.Equals((object)42);
```

Плюс это один из любимых вопросов на собеседовании: он проверяет, понимает ли кандидат разницу между значимыми и ссылочными типами не на уровне определения, а на уровне того, что происходит в памяти.

## Механика

```csharp
int value = 42;
object boxed = value;      // упаковка: IL-инструкция box
int back = (int)boxed;     // распаковка: IL-инструкция unbox.any
```

```
Стек                     Куча
┌──────────┐            ┌────────────────────────┐
│ value=42 │            │ Sync block             │ 8 байт
├──────────┤            │ Method table (Int32)   │ 8 байт
│ boxed ───┼───────────►│ 42                     │ 4 байта + выравнивание
└──────────┘            └────────────────────────┘
                          итого 24 байта на 4 байта данных
```

Три свойства, которые надо помнить:

1. **Упакованное значение — копия.** Изменение исходной переменной не влияет на упакованную и наоборот.
2. **Каждая упаковка — новый объект.** `ReferenceEquals((object)42, (object)42)` даёт `false`.
3. **Распаковка требует точного типа.** `(long)(object)42` бросает `InvalidCastException`; нужно `(long)(int)(object)42`.

```csharp
int a = 42;
object box1 = a;
object box2 = a;
Console.WriteLine(ReferenceEquals(box1, box2));   // False — два разных объекта
Console.WriteLine(box1.Equals(box2));             // True  — сравнение значений

a = 100;
Console.WriteLine((int)box1);                      // 42 — копия не изменилась
```

### Изменяемая структура в коробке

```csharp
struct Counter { public int Value; public void Increment() => Value++; }

object boxed = new Counter();
((Counter)boxed).Increment();          // распаковали копию, увеличили её, копию выбросили
Console.WriteLine(((Counter)boxed).Value);   // 0

// Через интерфейс — меняется значение ВНУТРИ коробки, но не исходная переменная
```

Ещё один аргумент за `readonly struct`: у неизменяемой структуры такой проблемы не возникает в принципе ([[Записи (record) и структуры]]).

## Где упаковка происходит незаметно

| Ситуация | Пример | Как избежать |
|---|---|---|
| Приведение к `object` | `object o = 42;` | дженерики |
| Приведение к не-обобщённому интерфейсу | `IComparable c = 42;` | `IComparable<T>` |
| Не-обобщённые коллекции | `ArrayList`, `Hashtable` | `List<T>`, `Dictionary<K,V>` |
| `params object[]` | `string.Format("{0}", 42)` | интерполяция (C# 10+), перегрузки с дженериками |
| `Equals(object)` у структуры | `point.Equals(other)` без `IEquatable<T>` | реализовать `IEquatable<T>` |
| `GetHashCode` из `ValueType` | ключ-структура без переопределения | переопределить или `record struct` |
| Сравнение в не-обобщённом виде | `Comparer.Default` вместо `Comparer<T>` | обобщённые компараторы |
| `enum` в старых API | `Enum.HasFlag` до .NET Core | битовая проверка `(x & f) != 0` |
| LINQ над `IEnumerable` (не-обобщённым) | `ArrayList.Cast<int>()` | обобщённые источники |
| Значимый тип в `Dictionary<K, object>` | кеш «всего подряд» | типизированное хранилище |

Два примера, которые встречаются чаще прочих:

```csharp
// 1. Структура без IEquatable<T> в словаре
struct Key { public int A, B; }
var dict = new Dictionary<Key, string>();
dict[new Key { A = 1, B = 2 }] = "x";
// Каждое сравнение вызывает ValueType.Equals(object) → упаковка обоих операндов
// плюс сравнение полей через рефлексию, если структура содержит ссылки

// Лечение:
readonly record struct Key2(int A, int B);    // компилятор сгенерирует IEquatable<T>
```

```csharp
// 2. Логирование и форматирование
logger.LogInformation("Заказ {OrderId} на сумму {Total}", orderId, total);
// Параметры уходят в params object?[] → две упаковки на каждый вызов.
// Лечение для горячего пути — генератор:
[LoggerMessage(Level = LogLevel.Information, Message = "Заказ {OrderId} на сумму {Total}")]
static partial void LogOrder(ILogger logger, long orderId, decimal total);
```

### Интерполяция строк: что изменилось

До C# 10 интерполированная строка компилировалась в `string.Format` с массивом `object[]` — то есть упаковывала каждый значимый аргумент. С C# 10 используется `DefaultInterpolatedStringHandler`, который форматирует значимые типы напрямую в буфер, **без упаковки**. Это один из случаев, когда обновление языка убрало целый класс аллокаций без изменений в коде ([[Строки и работа с текстом]]).

## Как упаковки избегать

### Дженерики с ограничениями

```csharp
// Упаковывает: параметр приведён к интерфейсу
static bool AreEqual(IEquatable<int> a, int b) => a.Equals(b);

// Не упаковывает: JIT создаёт специализацию под каждый значимый тип,
// вызов разрешается напрямую (constrained call)
static bool AreEqual<T>(T a, T b) where T : IEquatable<T> => a.Equals(b);
```

Это ключевое различие: обобщённый код над значимым типом компилируется в отдельную версию машинного кода, где нет ни упаковки, ни виртуального вызова ([[Дженерики в CLR: как устроены]]).

### Реализовать нужные интерфейсы

```csharp
public readonly record struct Money(decimal Amount, string Currency);
// record struct сам генерирует Equals(T), GetHashCode, IEquatable<T> — упаковки при сравнении нет
```

`EqualityComparer<T>.Default`, `Comparer<T>.Default`, `Dictionary`, `HashSet`, `List.Contains`, LINQ — все они проверяют `IEquatable<T>`/`IComparable<T>` и при их наличии вызывают типизированную версию.

### Не приводить структуры к интерфейсам

```csharp
IShape shape = square;                       // упаковка
static double Area<T>(T shape) where T : IShape => shape.Area;   // без упаковки
```

### Обобщённая математика вместо `object`

```csharp
static T Sum<T>(ReadOnlySpan<T> values) where T : INumber<T>
{
    T total = T.Zero;
    foreach (var v in values) total += v;
    return total;
}
```

Раньше такой универсальный код писали через `dynamic` или `object` с упаковкой на каждой операции; с .NET 7 он полностью статичен ([[Интерфейсы]]).

## Как обнаружить упаковку

```csharp
[MemoryDiagnoser]                       // BenchmarkDotNet покажет Allocated и Gen0 на операцию
public class Bench
{
    [Benchmark] public bool WithBoxing() => _key.Equals((object)_other);
    [Benchmark] public bool NoBoxing() => _key.Equals(_other);
}
```

Другие способы: посмотреть IL на sharplab.io и найти инструкцию `box`; включить анализаторы (`CA1854`, правила из `Meziantou.Analyzer` и `Roslynator` подсказывают часть случаев); снять профиль аллокаций в dotMemory или через `dotnet-counters monitor` (счётчик `alloc-rate`).

Порядок величин, чтобы понимать масштаб: упаковка — примерно 24 байта и десяток наносекунд. В обработчике HTTP-запроса это ничто. В цикле на 10 миллионов итераций — 240 МБ мусора и несколько сборок gen 0.

> [!warning] Подводные камни
> - **Распаковка в «совместимый» тип.** `(long)(object)42` — `InvalidCastException`: только исходный тип, потом расширение.
> - **`ReferenceEquals` для упакованных значений.** Всегда `false` для разных упаковок одного числа.
> - **Изменяемая структура в коробке.** Изменения через приведение уходят в копию и теряются.
> - **Структура-ключ без `IEquatable<T>`.** Упаковка на каждое сравнение плюс сравнение полей рефлексией в `ValueType.Equals`.
> - **`Nullable<T>` в упаковке.** `object o = (int?)null;` даёт **`null`**, а не «упакованный Nullable»: рантайм обрабатывает этот случай особо, и `o.GetType()` вызовет `NullReferenceException`.
> - **`enum` и старые API.** `Enum.HasFlag` в .NET Framework упаковывал оба операнда; в современном .NET JIT это устраняет, но в легаси-коде остаётся горячей точкой.
> - **Оптимизация без замера.** Устранение упаковок в холодном коде не даёт ничего; сначала бенчмарк, потом правки.

> [!example] Как делают в бою
> В прикладном коде упаковку не ищут специально: пара аллокаций на запрос ничего не решает. Она становится темой в трёх местах.
> Первое — библиотеки и инфраструктура: сериализаторы, логгеры, парсеры, сетевой стек. Там правило простое — обобщённые API с ограничениями вместо `object`, `IEquatable<T>`/`IComparable<T>` на всех значимых типах, `Span<T>` вместо массивов-параметров.
> Второе — структуры, используемые как ключи словарей и элементы больших коллекций: они всегда объявляются как `readonly record struct` либо с ручной реализацией `IEquatable<T>`. Это одна из самых окупаемых микрооптимизаций: она убирает и упаковку, и медленный путь `ValueType.Equals` через рефлексию.
> Третье — логирование в горячих путях: там переходят на `[LoggerMessage]`-генератор, который убирает и упаковку параметров, и форматирование при отключённом уровне.
> Диагностика всегда начинается с измерения: `MemoryDiagnoser` в бенчмарке или счётчик скорости аллокаций в проде. Найденные упаковки чинят точечно, а не «на всякий случай» по всему коду.

## Вопросы с собеседований

> [!question]- Что такое упаковка и сколько она стоит?
> Упаковка — преобразование значения значимого типа в объект ссылочного типа: рантайм выделяет в управляемой куче объект с полным заголовком, копирует туда значение и возвращает ссылку. Стоимость складывается из трёх частей: аллокация (для `int` это 24 байта на 4 байта полезных данных из-за 16-байтного заголовка и выравнивания), копирование значения и последующая работа сборщика мусора. Единичная упаковка занимает порядка десятка наносекунд и в обычном коде незаметна; проблема возникает в горячих циклах, где миллионы упаковок дают сотни мегабайт мусора и частые сборки gen 0. Распаковка — обратное копирование с проверкой типа, причём тип должен совпадать точно: значение, упакованное как `int`, нельзя распаковать в `long`, будет `InvalidCastException`.

> [!question]- В каких неочевидных местах происходит упаковка?
> Самые частые: приведение структуры к `object` или к не-обобщённому интерфейсу (`IComparable`, `IFormattable`, `IEnumerable`); вызов унаследованных от `object` методов на структуре, которая не переопределяет их или не реализует `IEquatable<T>` — тогда работает `ValueType.Equals(object)` с упаковкой обоих операндов и сравнением полей через рефлексию; передача значимых типов в `params object[]`, что происходит в `string.Format`, старом логировании и `Console.WriteLine` с несколькими аргументами; использование не-обобщённых коллекций `ArrayList` и `Hashtable`; хранение значений в `Dictionary<string, object>`. Отдельно стоит помнить, что интерполяция строк упаковывала аргументы до C# 10, а начиная с него использует handler и форматирует значимые типы напрямую в буфер. Обнаруживают упаковку по инструкции `box` в IL и по `MemoryDiagnoser` в бенчмарке.

> [!question]- Почему `IEquatable<T>` важен именно для структур?
> Потому что без него сравнение идёт через унаследованный `object.Equals(object)`: оба операнда упаковываются, то есть на каждое сравнение приходятся две аллокации, а внутри `ValueType.Equals` рантайм сравнивает поля побитово только если структура не содержит ссылок и не имеет промежутков выравнивания — иначе обходит поля рефлексией, что медленнее в десятки раз. Коллекции и LINQ обращаются к `EqualityComparer<T>.Default`, который проверяет наличие `IEquatable<T>` и вызывает типизированный метод напрямую, без упаковки и без рефлексии. Поэтому любая структура, которая используется как ключ словаря, попадает в `HashSet`, сравнивается в LINQ или лежит в больших коллекциях, обязана реализовывать `IEquatable<T>` — либо быть объявленной как `record struct`, где компилятор сгенерирует всё сам.

> [!question]- Что происходит при упаковке `Nullable<T>`?
> Рантайм обрабатывает этот случай специально. Если `HasValue` равно `false`, результатом упаковки будет обычный `null`, а не объект-обёртка над `Nullable<T>`; если значение есть — упаковывается **само значение** типа `T`, а не структура `Nullable<T>`. Отсюда практические следствия: `object o = (int?)null;` даёт `o == null`, и обращение к `o.GetType()` бросит `NullReferenceException`; `object o = (int?)5;` даёт объект, у которого `GetType()` вернёт `System.Int32`, а не `System.Nullable<System.Int32>`; распаковать такой объект можно и в `int`, и в `int?`. Это сделано именно для того, чтобы `null`-семантика вела себя ожидаемо при работе через `object`, но при чтении кода эффект выглядит неочевидно.

## Задачи

### Задача 1. Найти упаковки

```csharp
struct Point { public int X, Y; }

var p = new Point { X = 1, Y = 2 };
var dict = new Dictionary<Point, string>();
dict[p] = "origin";
Console.WriteLine(dict.ContainsKey(new Point { X = 1, Y = 2 }));
Console.WriteLine($"Точка: {p.X}, {p.Y}");
Console.WriteLine(string.Format("Точка: {0}, {1}", p.X, p.Y));
var list = new System.Collections.ArrayList { p };
```

> [!success]- Решение
> Упаковки по строкам:
> - `dict[p] = ...` и `ContainsKey(...)` — структура не реализует `IEquatable<Point>`, поэтому `EqualityComparer<Point>.Default` использует `ValueType.Equals(object)`: упаковка обоих операндов на каждое сравнение, плюс вычисление хеша через `ValueType.GetHashCode`, которое тоже небесплатно и даёт плохое распределение.
> - Интерполяция `$"Точка: {p.X}, {p.Y}"` — **без упаковки** начиная с C# 10: handler форматирует `int` напрямую в буфер.
> - `string.Format("{0}, {1}", p.X, p.Y)` — две упаковки: аргументы уходят в `params object[]`, плюс аллокация самого массива.
> - `ArrayList { p }` — упаковка при добавлении: не-обобщённая коллекция хранит `object`.
> ```csharp
> readonly record struct Point(int X, int Y);      // Equals(T), GetHashCode, IEquatable<T> — даром
> var dict = new Dictionary<Point, string>();       // сравнение без упаковки
> Console.WriteLine($"Точка: {p.X}, {p.Y}");        // handler, без упаковки
> var list = new List<Point>();                      // обобщённая коллекция, без упаковки
> ```

### Задача 2. Убрать аллокации из горячего метода

Метод вызывается миллион раз в секунду и, по данным профилировщика, аллоцирует. Найди причину.

```csharp
public interface IValidator { bool IsValid(int value); }
public readonly struct RangeValidator(int min, int max) : IValidator
{
    public bool IsValid(int value) => value >= min && value <= max;
}

public static int CountValid(ReadOnlySpan<int> data, IValidator validator)
{
    int count = 0;
    foreach (var x in data) if (validator.IsValid(x)) count++;
    return count;
}

// Вызов
CountValid(data, new RangeValidator(0, 100));
```

> [!success]- Решение
> Аллокация одна, но на каждый вызов `CountValid`: структура `RangeValidator` приводится к интерфейсу `IValidator`, то есть упаковывается. Дополнительно все вызовы `IsValid` внутри цикла становятся интерфейсными (виртуальными) и не встраиваются — на миллионе элементов это заметно само по себе.
> ```csharp
> public static int CountValid<TValidator>(ReadOnlySpan<int> data, TValidator validator)
>     where TValidator : IValidator            // ограничение вместо параметра-интерфейса
> {
>     int count = 0;
>     foreach (var x in data) if (validator.IsValid(x)) count++;
>     return count;
> }
>
> CountValid(data, new RangeValidator(0, 100));   // тип выводится, упаковки нет
> ```
> Почему это работает: для значимого типа-аргумента JIT создаёт отдельную специализацию машинного кода, где `validator` лежит по значению, вызов `IsValid` разрешается статически (constrained call) и, как правило, встраивается — исчезают и аллокация, и виртуальный вызов, и барьер для оптимизаций внутри цикла.
> Оговорка: у обобщённой версии есть цена — по копии кода на каждый значимый тип-аргумент (рост размера кода и давление на кеш инструкций). Для двух-трёх реализаций это выгодно; если валидаторов десятки и вызовы редкие, интерфейсный параметр честнее.

## Итог

- Упаковка — аллокация объекта в куче с копией значения; распаковка — копирование обратно с точной проверкой типа.
- Упакованное значение — копия и всегда новый объект: `ReferenceEquals` для двух упаковок одного числа даёт `false`.
- Распаковывать можно только в исходный тип: `(long)(object)42` — исключение.
- Основные источники: приведение к `object` и не-обобщённым интерфейсам, `params object[]`, `ArrayList`/`Hashtable`, `ValueType.Equals` у структур без `IEquatable<T>`.
- Интерполяция строк с C# 10 не упаковывает значимые типы.
- Главное средство борьбы — дженерики с ограничениями: JIT специализирует код под значимый тип, упаковки и виртуального вызова нет.
- Структуры-ключи обязаны реализовывать `IEquatable<T>` или быть `record struct`.
- `Nullable<T>` упаковывается особым образом: `null` даёт `null`, значение — упакованный `T`.
