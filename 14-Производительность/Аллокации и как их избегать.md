# Аллокации и как их избегать

> [!abstract] Коротко
> Сама аллокация в .NET почти бесплатна: сдвинуть указатель в allocation context потока — единицы наносекунд. Платите вы не за выделение, а за **сборку**: чем выше allocation rate (байт в секунду), тем чаще Gen0-сборки, тем больше объектов успевает промотироваться в Gen1/Gen2, тем чаще дорогие сборки старших поколений и паузы. Поэтому цель оптимизации — не «ноль аллокаций ради красоты», а снижение allocation rate в горячих путях. Главный навык здесь — видеть аллокации, которых в коде не видно: замыкания, boxing, LINQ-итераторы, `params`-массивы, async state machine.

## Зачем это нужно

Типичная история из финтеха. Сервис приёма платежей держит 3 000 rps, p99 = 40 мс. После релиза p99 прыгнул до 180 мс, CPU вырос вдвое, хотя логика не поменялась — добавили «безобидный» лог с интерполяцией и валидацию через LINQ на каждое поле. В профайлере видно: allocation rate вырос с 200 МБ/с до 1,8 ГБ/с, Gen0-сборок стало 40 в секунду вместо 5, % Time in GC — 18 % вместо 2 %.

Никакой отдельной «медленной операции» в трейсе нет. Медленно стало *везде*, потому что GC — глобальный налог: он приостанавливает потоки, инвалидирует кеши процессора и конкурирует с вашим кодом за ядра.

Обратная сторона: если сервис делает 100 rps и каждый запрос ждёт 5 мс ответа PostgreSQL, аллокации — не ваша проблема, и охота за ними только ухудшит читаемость. Умение отличить первый случай от второго — и есть тема заметки.

## Экономика аллокаций

### Аллокация дешёвая, сборка — нет

Выделение объекта в managed heap — это:

```
allocation context потока:
  ┌──────────────────────────── alloc quantum (~8 КБ) ────────────────────────────┐
  │ [obj][obj][obj][obj]        ▲                                                 │
  └─────────────────────────────│─────────────────────────────────────────────────┘
                          alloc_ptr        ...                              alloc_limit

new Foo():
  1. если alloc_ptr + size <= alloc_limit:
       result = alloc_ptr; alloc_ptr += size;  // bump pointer, ~2-5 нс
       записать method table pointer, обнулить поля
  2. иначе — медленный путь: взять новый quantum из Gen0-бюджета.
     Если бюджет Gen0 исчерпан → триггер Gen0 GC.
```

У каждого потока свой allocation context, поэтому быстрый путь идёт **без блокировок** — это ключ к тому, почему аллокация в .NET быстрее `malloc`. Когда quantum кончился, рантайм выдаёт следующий из текущего Gen0-сегмента; когда сегмент кончился — запускается сборка.

Что происходит на Gen0 GC:

```
1. Suspend EE — все managed-потоки останавливаются на safe point.
2. Mark: обход корней (стеки потоков, статики, GC handles, remembered set
   из card table) → помечаем живые объекты в Gen0.
3. Sweep + Compact: живые объекты Gen0 копируются в Gen1, адреса
   переписываются во всех ссылках.
4. Resume EE.
```

Стоимость шага 3 пропорциональна **объёму выживших**, а не объёму мусора. Мусор бесплатен: он просто не копируется. Отсюда generational hypothesis: «большинство объектов умирает молодыми». Если ваши объекты действительно живут доли миллисекунды, Gen0-сборка стоит десятки-сотни микросекунд и это нормально.

### Почему высокий allocation rate ломает всё

```
allocation rate ↑
  → Gen0 GC чаще
    → объект, живущий 10 мс, попадает под 2-3 сборки вместо 0
      → промотируется Gen0 → Gen1 → Gen2
        → Gen2 растёт → фоновая (background) Gen2-сборка чаще
          → больше CPU на GC-потоки, длиннее паузы, фрагментация
            → p99 растёт, CPU растёт, throughput падает
```

Это называется **premature promotion**. Классический случай: обработчик HTTP-запроса живёт 30 мс и аллоцирует 500 КБ. При Gen0-бюджете в несколько мегабайт сборка случается несколько раз за время запроса, и его промежуточные объекты уезжают в Gen1/Gen2, откуда их вымоет только дорогая сборка.

> [!info] Allocation rate — главная метрика
> Не «сколько байт аллоцирует метод», а **байт в секунду на инстанс**. 1 КБ на запрос при 100 rps = 100 КБ/с (плевать). 1 КБ на запрос при 50 000 rps = 50 МБ/с (уже считаем). Ориентир для веб-сервиса: до ~100–200 МБ/с на ядро — обычно терпимо; выше 500 МБ/с — GC заметен в профиле; выше 1 ГБ/с — почти наверняка узкое место.

### Card table и write barrier

Чтобы собрать Gen0, не обходя всю кучу, GC должен знать, какие объекты старших поколений ссылаются на молодые. Для этого при **каждой записи ссылки в поле объекта** JIT вставляет write barrier — код, который помечает соответствующую «карту» (обычно 256 байт кучи на 1 байт card table) как «грязную»:

```csharp
public sealed class Order
{
    public Customer? Customer { get; set; } // запись ссылки => write barrier
    public decimal Amount   { get; set; }   // запись значения => просто mov
}

order.Customer = customer; // ~mov + вызов JIT_WriteBarrier: пометить карту
order.Amount   = 100m;     // просто копирование 16 байт
```

Практические следствия:
- запись **ссылочного** поля дороже записи значимого — не радикально, но в горячих циклах на миллионы итераций видно;
- структура из значимых полей (`long`, `decimal`, `DateTime`) вообще не платит write barrier, структура с полем-ссылкой — платит;
- если объект в Gen2 держит ссылки на кучу молодых объектов, его карты вечно грязные и Gen0-сборка обходит их каждый раз. Отсюда правило: не подвешивайте изменчивый граф молодых объектов к долгоживущему кешу.

Подробнее про поколения, LOH и режимы — [[Сборка мусора (GC): как работает]].

## Что аллоцирует незаметно

Это главный раздел. Размеры — для x64, где минимальный размер объекта 24 байта (8 байт sync block + 8 байт method table pointer + данные, выровненные до 8).

### 1. Замыкания

Лямбда, захватывающая переменную, — это **два** объекта: класс-замыкание (compiler-generated display class) и делегат.

```csharp
public IReadOnlyList<Payment> FindByAmount(List<Payment> all, decimal min)
{
    // Компилятор генерирует:
    //   class <>c__DisplayClass0_0 { public decimal min; }
    //   new <>c__DisplayClass0_0 { min = min }       => 24 байта (16 + 16 decimal → 32)
    //   new Func<Payment,bool>(dc.<FindByAmount>b__0) => 64 байта
    return all.Where(p => p.Amount >= min).ToList();
}
```

Лямбда **без** захвата кешируется компилятором в статическое поле — аллокация происходит один раз за время жизни процесса:

```csharp
// Компилятор: static readonly Func<Payment,bool> <>9__0;
//   if (<>9__0 is null) <>9__0 = new Func<...>(<>c.<>9.b__0);
list.Where(p => p.Amount > 0);  // делегат создаётся один раз на весь процесс
```

Захват `this` не создаёт display class (замыкание — сам `this`), но создаёт делегат и, что важнее, **продлевает жизнь всего объекта**:

```csharp
public sealed class PaymentService
{
    private readonly decimal _limit;

    // захват this: делегат держит ссылку на PaymentService целиком.
    // Если делегат уедет в долгоживущий кеш — утечка. См. [[Слабые ссылки и утечки памяти в .NET]]
    public bool AnyOverLimit(List<Payment> p) => p.Any(x => x.Amount > _limit);
}
```

Захват в цикле — объект **на каждую итерацию**:

```csharp
// ПЛОХО: 1000 display class + 1000 делегатов
foreach (var id in ids)                        // id — переменная итерации, захватывается
    tasks.Add(Task.Run(() => Process(id)));

// ХОРОШО: состояние передаётся аргументом, лямбда не захватывает => один делегат
foreach (var id in ids)
    tasks.Add(Task.Factory.StartNew(static o => Process((Guid)o!), id));
```

`static` лямбды (C# 9) — не оптимизация, а **страховка**: компилятор запрещает любой захват, поэтому случайный захват станет ошибкой компиляции, а не тихой аллокацией.

```csharp
// CS8820: static-лямбда не может обращаться к нестатическому члену
// list.Where(static p => p.Amount >= _limit);

// Так — можно, замыкания нет:
list.Where(static p => p.Amount > 0);
```

Правильный способ передать состояние без захвата — перегрузка с `TState`. В BCL их специально добавляли:

```csharp
// ILogger: TState вместо замыкания, форматтер — static-лямбда
logger.Log(LogLevel.Information, default, (id: paymentId, amount), null,
    static (s, _) => $"Платёж {s.id} на {s.amount}");

// ConcurrentDictionary: factoryArgument вместо захвата
cache.GetOrAdd(key, static (k, arg) => Build(k, arg), request);

// Task.Run перегрузки с состоянием НЕТ — используйте Task.Factory.StartNew(Action<object?>, object?)
```

Для `Dictionary<K,V>` замена «двойного поиска» — не лямбда, а `TryGetValue` или `CollectionsMarshal`:

```csharp
using System.Runtime.InteropServices;

// ПЛОХО: два хеша и два поиска
if (!totals.ContainsKey(currency)) totals[currency] = 0m;
totals[currency] += amount;

// ЛУЧШЕ: один поиск
ref decimal slot = ref CollectionsMarshal.GetValueRefOrAddDefault(totals, currency, out _);
slot += amount;
```

Подробности синтаксиса — [[Делегаты, события и лямбды]] и [[Делегаты, события и лямбды]].

### 2. LINQ-итераторы

Каждый оператор цепочки — объект-итератор плюс делегат плюс, при перечислении, вызов `GetEnumerator()`.

```csharp
// Аллокации на один вызов (порядок величины, x64):
var result = payments
    .Where(p => p.Status == Status.Ok)   // WhereListIterator ~40 B (+ делегат, кеширован)
    .Select(p => p.Amount)              // WhereSelectListIterator ~48 B (+ делегат)
    .ToList();                          // List ~32 B + рост массива

// Итого ~5 объектов и ~200 B оверхеда сверх самого результата.
```

Ключевая асимметрия `foreach`:

```csharp
List<int> list = GetList();

foreach (var x in list) { }                    // 0 B: List<T>.Enumerator — struct,
                                               // компилятор вызывает его напрямую

IEnumerable<int> seq = list;
foreach (var x in seq) { }                     // ~40 B: интерфейсный GetEnumerator()
                                               // боксит struct-enumerator в куче
```

Отсюда правило: **не возвращайте `IEnumerable<T>` из горячих методов, если у вас на руках `List<T>`/массив** — возвращайте конкретный тип или `ReadOnlySpan<T>`. Подробный разбор — [[LINQ: производительность и аллокации]].

### 3. Boxing

Любое помещение значимого типа в `object`/интерфейс — аллокация минимум 24 байта.

```csharp
object o = 42;                        // 24 B
IComparable c = 42;                   // 24 B
int? n = 5; object b = n;             // 24 B — боксится int, не Nullable<int>

// В легаси-коде (.NET Framework):
string s = string.Format("id={0}", id);   // int → object: 24 B + params object[]: 32 B
bool f = flags.HasFlag(Status.Ok);        // 2 бокса. В .NET Core 2.1+ JIT это
                                          // раскрывает в побитовое И — 0 B. #устарело

// struct, реализующий интерфейс, вызванный ЧЕРЕЗ интерфейс:
struct Money : IComparable<Money> { public decimal V; public int CompareTo(Money o) => V.CompareTo(o.V); }

Money a = default, b2 = default;
a.CompareTo(b2);                      // 0 B — прямой вызов
IComparable<Money> ic = a;            // 24+ B — бокс при приведении к интерфейсу

// Дженерик БЕЗ бокса: JIT специализирует код под Money
static int Cmp<T>(T x, T y) where T : IComparable<T> => x.CompareTo(y);  // 0 B
```

Последний пример — почему `where T : IComparable<T>` вместо параметра типа `IComparable`: для value types JIT генерирует отдельный код и вызывает метод напрямую. См. [[Дженерики: ограничения и вариантность]] и [[Value types vs Reference types]].

### 4. `params`-массивы

```csharp
static void Audit(string op, params object[] data) { }

Audit("transfer", accountId, amount);
// каждый вызов: object[2] (40 B) + бокс Guid (~40 B) + бокс decimal (~40 B)
```

C# 13 добавил `params` для span-типов — компилятор может выделить буфер на стеке или в статике, аллокации нет:

```csharp
static decimal Sum(params ReadOnlySpan<decimal> values)   // C# 13+
{
    decimal total = 0;
    foreach (var v in values) total += v;
    return total;
}

var t = Sum(10m, 20m, 30m);   // 0 B: буфер на стеке вызывающего
```

Для строк то же решение сделали раньше — перегрузки `string.Concat` на 2/3/4 аргумента не создают массив:

```csharp
string a = string.Concat(prefix, id);            // 0 массивов
string b = string.Concat(prefix, id, suffix);    // 0 массивов
string c = string.Concat(p1, p2, p3, p4, p5);    // params string[] — массив есть
```

### 5. Строки

Строки иммутабельны, поэтому **любая** операция, дающая другой текст, — новая строка: `+`, интерполяция, `Substring`, `Split`, `ToUpper`, `Trim`, `PadLeft`, `Replace`, `ToString()`. `Split` на 10 полей — это 11 объектов (массив + 10 строк).

```csharp
// 200-символьная строка, 10 полей:
string[] parts = line.Split(';');   // ~1 массив + 10 строк ≈ 600 B
```

Полный разбор — [[Строки: производительность и интернирование]].

### 6. Async state machine

В Release для `async`-метода компилятор генерирует **struct**-машину состояний. Пока метод не дошёл до реального `await` с незавершённой задачей, машина живёт на стеке. При первом «настоящем» `await` её нужно сохранить — и она боксится в кучу, плюс аллоцируется `Task`/`AsyncStateMachineBox`.

```csharp
// Метод, который в 99 % случаев отвечает из кеша, всё равно платит Task (~80-100 B)
public async Task<Rate?> GetRateAsync(string pair)
{
    if (_cache.TryGetValue(pair, out var r)) return r;   // синхронный путь
    return await _client.FetchAsync(pair);
}

// ValueTask + кеширование пути — см. [[Асинхронность и производительность: ValueTask, пулинг]]
public ValueTask<Rate?> GetRateFastAsync(string pair)
    => _cache.TryGetValue(pair, out var r)
        ? new ValueTask<Rate?>(r)                        // 0 B на синхронном пути
        : new ValueTask<Rate?>(FetchSlowAsync(pair));
```

`Task.CompletedTask` и `Task.FromResult` для маленьких значений частично кешируются рантаймом (например, `Task.FromResult(true)`), но в общем случае — аллокация.

### 7. Итераторы `yield return`

```csharp
public IEnumerable<Payment> Pending()      // вызов метода = 1 объект-итератор (~48-64 B),
{                                          // ещё один при повторном GetEnumerator()
    foreach (var p in _all)
        if (p.Status == Status.Pending) yield return p;
}
```

Плюс к этому вызывающий получает `IEnumerable<T>`, то есть `foreach` по нему пойдёт через интерфейс. Для горячего пути отдавайте готовый `List<T>` или пишите struct-enumerator вручную.

### 8. `Task.WhenAll`, `CancellationTokenSource`, `Timer`

```csharp
// params Task[] массив + внутренний Task + список продолжений
await Task.WhenAll(t1, t2, t3);

// CTS — объект + внутренние структуры; каждая регистрация Register() — ещё объект
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(5)); // + Timer внутри
using var reg = token.Register(static s => ((Socket)s!).Dispose(), socket);

// Связанный CTS дороже: держит регистрации на всех родителях
using var linked = CancellationTokenSource.CreateLinkedTokenSource(a, b);
```

В горячем пути: не создавайте CTS с таймаутом, если таймаут уже задан выше; переиспользуйте `CancellationToken.None` вместо `new CancellationTokenSource().Token`.

### 9. `ToString()` и форматирование значимых типов

```csharp
long id = 12345;
string s1 = id.ToString();                     // строка: 24 B + 2 байта на символ
string s2 = DateTime.UtcNow.ToString("O");     // ~28 символов => ~80 B
string s3 = amount.ToString("F2", CultureInfo.InvariantCulture);
```

Замена — `TryFormat` прямо в буфер:

```csharp
Span<char> buf = stackalloc char[32];
if (id.TryFormat(buf, out int written))
    Write(buf[..written]);                     // 0 B
```

### 10. Лишние делегаты в горячем пути

```csharp
// ПЛОХО: новый делегат на каждый вызов
public void Handle(Request r) => _bus.Subscribe(msg => Process(msg, r));

// ХОРОШО: делегат создаётся один раз
private static readonly Func<int, bool> IsPositive = static x => x > 0;

// Событие: += внутри цикла/обработчика запроса — и аллокация, и утечка
// (список подписчиков растёт, объекты не собираются)
```

### 11. Необобщённые коллекции в легаси #устарело

```csharp
// .NET Framework-код, который вы встретите в легаси:
var list = new ArrayList();
list.Add(42);                 // бокс каждого int: 24 B
int x = (int)list[0];          // unbox + приведение

var ht = new Hashtable();
ht[key] = 100m;                // бокс decimal
```

От этого ушли с приходом дженериков в .NET 2.0: `List<int>` хранит `int` инлайн в массиве, аллокаций на элемент нет. В новом коде `ArrayList`/`Hashtable`/`Queue` (необобщённые) не используются никогда.

### 12. Defensive copies у не-`readonly` структур

Формально это не heap-аллокация, но это скрытое копирование, которое часто и делает «оптимизацию структурами» медленнее.

```csharp
public struct Money            // НЕ readonly
{
    public decimal Amount;
    public decimal Doubled => Amount * 2;   // не readonly-член
}

public sealed class Cart
{
    private readonly Money _total;          // readonly ПОЛЕ структуры

    // Компилятор не знает, что Doubled не мутирует this,
    // поэтому копирует _total (16 байт) перед каждым обращением
    public decimal X => _total.Doubled;
}

// Лечение: readonly struct (или readonly у членов)
public readonly struct MoneyOk
{
    public decimal Amount { get; init; }
    public decimal Doubled => Amount * 2;   // копий нет
}
```

Тот же эффект даёт параметр `in` у не-`readonly` структуры. Включите анализаторы CA1815/CA1051 и правило «структура — всегда `readonly`, если нет причин иначе».

## Как это увидеть

### BenchmarkDotNet + MemoryDiagnoser

```csharp
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

[MemoryDiagnoser]                 // колонки Gen0/Gen1/Gen2 и Allocated
public class ParseBench
{
    private readonly string _line = "UZ82;4111111111111111;1500.55;UZS";

    [Benchmark(Baseline = true)]
    public decimal Split() => decimal.Parse(_line.Split(';')[2],
        System.Globalization.CultureInfo.InvariantCulture);

    [Benchmark]
    public decimal Span()
    {
        ReadOnlySpan<char> s = _line;
        for (int i = 0; i < 2; i++) s = s[(s.IndexOf(';') + 1)..];
        return decimal.Parse(s[..s.IndexOf(';')],
            provider: System.Globalization.CultureInfo.InvariantCulture);
    }
}

// dotnet run -c Release
```

Ориентируйтесь на колонку `Allocated`: она детерминирована и не шумит, в отличие от времени. Подробнее — [[Как измерять: BenchmarkDotNet]].

### Кто именно аллоцирует


### Тест-регрессия на аллокации

Самый ценный инструмент: unit-тест, который падает, если кто-то вернул аллокацию в горячий путь.

```csharp
using Xunit;

public class AllocationRegressionTests
{
    [Fact]
    public void ParseIban_НеАллоцирует()
    {
        const string iban = "UZ82ABCD1234567890123456";

        // 1. Прогреваем: JIT, статические конструкторы, кеши делегатов
        for (int i = 0; i < 200; i++) _ = IbanValidator.IsValid(iban);

        // 2. Меряем ровно свой поток — не зависит от фонового шума
        long before = GC.GetAllocatedBytesForCurrentThread();
        for (int i = 0; i < 1_000; i++) _ = IbanValidator.IsValid(iban);
        long allocated = GC.GetAllocatedBytesForCurrentThread() - before;

        Assert.Equal(0, allocated);
    }

    [Fact]
    public void ФорматированиеЧека_ВБюджете()
    {
        var receipt = Receipt.Sample();
        for (int i = 0; i < 200; i++) _ = ReceiptFormatter.Render(receipt);

        long before = GC.GetAllocatedBytesForCurrentThread();
        _ = ReceiptFormatter.Render(receipt);
        long allocated = GC.GetAllocatedBytesForCurrentThread() - before;

        // Бюджет с запасом: тест ловит регрессию в разы, а не ±8 байт
        Assert.InRange(allocated, 0, 512);
    }
}
```

Для многопоточного сценария — `GC.GetTotalAllocatedBytes(precise: true)`: он суммирует по всем потокам и с `precise: true` учитывает недоиспользованные части allocation context (без него значение округлено до quantum и «шагает» по ~8 КБ).

```csharp
long before = GC.GetTotalAllocatedBytes(precise: true);
await RunLoadAsync(requests: 1_000);
long perRequest = (GC.GetTotalAllocatedBytes(precise: true) - before) / 1_000;
```

> [!tip] Запускайте такие тесты в отдельной коллекции без параллелизма
> `GC.GetAllocatedBytesForCurrentThread` меряет свой поток, но xUnit может выполнить `async`-продолжение на другом потоке пула. Для async-кода либо считайте `GetTotalAllocatedBytes`, либо делайте тело теста синхронным.

## Приёмы борьбы

### struct вместо class

```csharp
// Было: 1 000 000 объектов по 32 байта = 32 МБ в куче + давление на GC
public sealed class Point3 { public double X, Y, Z; }

// Стало: массив значений, 24 байта на элемент, один объект-массив
public readonly struct Point3S(double x, double y, double z)
{
    public double X { get; } = x;
    public double Y { get; } = y;
    public double Z { get; } = z;
}
Point3S[] points = new Point3S[1_000_000];  // 1 аллокация вместо 1 000 001
```

**Границы применимости.** Структура выигрывает, когда: размер небольшой (ориентир — до 16–24 байт, то есть 2–3 машинных слова), она иммутабельна, живёт недолго или лежит в массиве. Структура **проигрывает**, когда её копируют по значению между методами, когда она большая, когда её кладут в `object`/интерфейс (бокс возвращает всё назад, и хуже), когда она уезжает в LINQ (каждый `Select` копирует). Полный разбор — [[Value types vs Reference types]].

### readonly struct и ref struct

`readonly struct` убирает defensive copies. `ref struct` (как `Span<T>`) гарантирует, что тип **не может** попасть в кучу: он не может быть полем класса, элементом массива, обобщённым аргументом в общем случае, использоваться в `async`-методе или лямбде. Это компилятором проверяемая гарантия «только стек».

### Предварительная ёмкость коллекций

`List<T>` растёт удвоением, начиная с 4. До 1000 элементов это 9 промежуточных массивов, которые все становятся мусором:

| Способ | Аллокаций массивов | Скопировано элементов | Байт (для `List<int>`) |
|---|---|---|---|
| `new List<int>()` + 1000 `Add` | 9 (4, 8, 16, … 1024) | 1020 | ~8,4 КБ |
| `new List<int>(1000)` + 1000 `Add` | 1 | 0 | ~4,0 КБ |
| `new List<int>()`, затем `EnsureCapacity(1000)` | 1 | 0 | ~4,0 КБ |

```csharp
var result = new List<Payment>(source.Count);      // знаем размер — задаём
var dict = new Dictionary<string, decimal>(capacity: 64, StringComparer.Ordinal);
var sb = new StringBuilder(capacity: 256);
```

Для `Dictionary`/`HashSet` эффект сильнее: рост означает не только новый массив, но и **рехеширование** всех элементов.

### Object pooling

```csharp
using Microsoft.Extensions.ObjectPool;

public sealed class ReceiptRenderer
{
    private static readonly ObjectPool<System.Text.StringBuilder> Pool =
        new DefaultObjectPoolProvider()
            .CreateStringBuilderPool(initialCapacity: 256, maximumRetainedCapacity: 4 * 1024);

    public string Render(Receipt r)
    {
        var sb = Pool.Get();
        try
        {
            sb.Append("Платёж ").Append(r.Id).Append(": ").Append(r.Amount);
            return sb.ToString();
        }
        finally
        {
            Pool.Return(sb);   // StringBuilderPooledObjectPolicy сама вызовет Clear()
        }
    }
}
```

Свой пул требует политики со сбросом состояния:

```csharp
public sealed class BufferPolicy : IPooledObjectPolicy<List<Payment>>
{
    public List<Payment> Create() => new(capacity: 64);

    public bool Return(List<Payment> obj)
    {
        if (obj.Capacity > 1024) return false;   // не держим раздутые объекты
        obj.Clear();                             // БЕЗ ЭТОГО — утечка данных между запросами
        return true;
    }
}
```

> [!danger] Пул без сброса состояния — это уязвимость, а не просто баг
> Объект из пула переходит от запроса A к запросу B. Если в нём остались данные — номер карты, идентификатор клиента, JWT — они попадут в ответ другому пользователю. Такие инциденты происходили в реальных сервисах: переиспользованный `StringBuilder` без `Clear()` дописывал новый ответ к хвосту предыдущего, и клиент получал фрагмент чужой транзакции. Правило: `Return` **всегда** сбрасывает состояние в известное, а не «обычно пустое».

## Server GC, Concurrent GC и DATAS

| Режим | Кому | Что делает |
|---|---|---|
| Workstation GC | десктоп, CLI-утилиты, мелкие контейнеры | одна куча, GC на потоке-аллокаторе, короткие паузы, меньше памяти |
| Server GC | серверные приложения на многоядерных машинах | по куче и выделенному GC-потоку на ядро, выше throughput, больше RAM |
| Concurrent / Background GC | по умолчанию включён | Gen2 собирается фоново, паузы короче |
| DATAS | Server GC, .NET 9+ по умолчанию | динамически подстраивает число куч под реальную нагрузку — Server GC перестал «съедать» память на мелких контейнерах |

```xml
<PropertyGroup>
  <ServerGarbageCollector>true</ServerGarbageCollector>
  <ConcurrentGarbageCollector>true</ConcurrentGarbageCollector>
  <!-- DATAS: включён по умолчанию для Server GC с .NET 9; выключается так -->
  <GarbageCollectionAdaptationMode>0</GarbageCollectionAdaptationMode>
</PropertyGroup>
```

Через переменные окружения: `DOTNET_gcServer=1`, `DOTNET_gcConcurrent=1`, `DOTNET_GCDynamicAdaptationMode=1`. ASP.NET Core-шаблоны включают Server GC. В Kubernetes с лимитом в 1 ядро Server GC раньше был вреден — DATAS это в значительной степени вылечил. Детали — [[Сборка мусора (GC): как работает]].

## Когда бороться НЕ надо

- Сервис делает 100 rps, каждый запрос — 5 мс в PostgreSQL. Ваш бюджет времени съеден сетью и БД; аллокации в C# здесь шум. Идите в [[Оптимизация запросов к БД]].
- Код вызывается **один раз на запрос**. Экономия 200 байт при 1 КБ HTTP-заголовков — самообман.
- Читаемость дороже. `payments.Where(p => p.IsOk).Sum(p => p.Amount)` в сервисном слое понятнее ручного цикла, и это правильный выбор.
- Порог, ниже которого не начинаем: **< 1000 вызовов в секунду и это не библиотека**. Библиотечный код — исключение: вы не знаете, в каком цикле его вызовут, поэтому в публичном API коллекций/парсеров/сериализаторов аллокации считают всегда.
- Нет измерения — нет оптимизации. Сначала [[Профилирование и dotnet-counters]], потом код.

> [!warning] Подводные камни
> - **LOH и арифметика порога.** В LOH попадают объекты **≥ 85 000 байт**. Считайте байты, а не элементы: `int[20_000]` = 80 024 байта — это обычная куча, а `int[21_250]` = 85 024 байта — уже LOH. Для массива ссылок или `long` на x64 порог наступает уже на 10 625 элементах. LOH по умолчанию не компактится, поэтому фрагментируется: куча в 800 МБ, в которой не находится 100 МБ подряд — типичная картина. Лечение — `ArrayPool`/`RecyclableMemoryStream`, а не `GCSettings.LargeObjectHeapCompactionMode`.
> - **Pinning.** `fixed`, `GCHandle.Alloc(..., GCHandleType.Pinned)`, старые Socket/Stream API закрепляют объект — GC не может его переместить и обходит при компакции. Много закреплённых мелких объектов = дырявая куча. Массивы из `ArrayPool` живут долго и закрепляются относительно безопасно; закреплять свежеаллоцированные мелкие буферы — плохо. В .NET 5+ есть Pinned Object Heap: `GC.AllocateArray<T>(size, pinned: true)` — отдельный регион для намеренно закреплённых буферов.
> - **Пул без Reset.** См. блок выше. Отдельный подвид — вернуть объект в пул и продолжить им пользоваться: два владельца одного буфера, порча данных без исключения.
> - **struct больше 16–24 байт в LINQ и делегатах.** `Select(x => bigStruct)` копирует структуру на каждом шаге, и «оптимизация» становится медленнее исходного класса. Меряйте, а не предполагайте.
> - **«Убрали аллокации — стало медленнее».** Самая частая причина — копирование структур и потеря инлайнинга (метод с большой структурой JIT не встраивает). Вторая — `stackalloc` в горячем методе с большим буфером: стек растёт, кеш процессора мажет.
> - **Финализаторы задерживают освобождение.** Объект с финализатором выживает первую сборку, попадает в очередь финализации, освобождается только следующей сборкой. Один медленный финализатор блокирует поток финализации и подвешивает освобождение всех остальных. Отсюда `SafeHandle` + `Dispose` вместо `~Finalize`. См. [[IDisposable, using и паттерн Dispose]].
> - **Замыкание, продлевающее жизнь графа.** Лямбда, захватившая `this`, попавшая в статический кеш или в подписку на событие, держит весь объект. Утечка выглядит как «GC не работает». См. [[Слабые ссылки и утечки памяти в .NET]].

> [!example] Как делают в бою
> **1. Бюджет аллокаций на запрос.** В фининтеграции задают явную цифру: «обработка одного платёжного сообщения — не более 4 КБ аллокаций». Цифра берётся из целевого allocation rate: 20 000 сообщений/с × 4 КБ = 80 МБ/с, что комфортно.
>
> **2. `[MemoryDiagnoser]`-бенчмарки на границах API.** Не на каждом методе, а на входных точках: парсер сообщения, сериализация ответа, ключевой запрос к кешу. Результаты коммитятся в репозиторий как baseline.
>
> **3. Тест-регрессия в CI.** Тесты вида «этот путь аллоцирует 0 байт / не более N байт» из раздела выше запускаются в обычном прогоне. Они дешёвые и ловят регрессию в момент код-ревью, а не через месяц в проде. Пороги ставят с запасом ×2, иначе тест начинает флакать после апгрейда SDK.
>
> **4. Метрика в проде.** `Allocation Rate` и `% Time in GC` выводят на дашборд рядом с p99 latency. При инциденте первый вопрос — «GC или нет», и ответ должен быть на графике, а не в предположениях. См. [[Метрики и Prometheus]].
>
> **5. Порядок работ.** Сначала алгоритм и запросы к БД, потом аллокации, потом микрооптимизации. Обратный порядок — почти всегда потерянное время.

## Вопросы с собеседований

> [!question]- Аллокация в .NET дорогая?
> Сама аллокация — почти бесплатная: у каждого потока есть allocation context, и выделение объекта в быстром пути — это инкремент указателя (bump pointer) без блокировок, единицы наносекунд, плюс запись method table pointer и обнуление полей. Дорога **сборка**: чем выше allocation rate, тем чаще срабатывает Gen0 GC, тем больше объектов не успевает умереть и промотируется в Gen1/Gen2, тем чаще приходят дорогие сборки старших поколений. Поэтому правильная метрика — не «сколько стоит один `new`», а байт в секунду, и правильная цель — чтобы объекты умирали до первой сборки.

> [!question]- Почему `foreach` по `List<T>` не аллоцирует, а по `IEnumerable<T>` — аллоцирует?
> `List<T>.GetEnumerator()` возвращает `List<T>.Enumerator` — **структуру**. Компилятор при `foreach` по переменной типа `List<T>` находит этот метод по duck typing и вызывает его напрямую, енумератор живёт на стеке. Если переменная объявлена как `IEnumerable<T>`, вызывается интерфейсная реализация `IEnumerable<T>.GetEnumerator()`, которая возвращает `IEnumerator<T>` — а значит структуру приходится боксить в кучу, около 40 байт на цикл. Плюс каждый `MoveNext`/`Current` становится интерфейсным вызовом, который JIT не всегда девиртуализует. Практический вывод: в горячем коде типизируйте переменную конкретным типом и не возвращайте `IEnumerable<T>` без нужды.

> [!question]- Как лямбда превращается в аллокации? Что даёт `static` лямбда?
> Лямбда без захвата компилируется в статический метод, а делегат на него кешируется в статическом поле — аллокация одна на процесс. Лямбда, захватывающая локальную переменную, компилируется в поле сгенерированного класса-замыкания: на каждый вызов метода создаётся экземпляр этого класса (24+ байта) и делегат (64 байта на x64). Захват `this` класса замыкания не создаёт, но делегат держит ссылку на весь объект, что продлевает его жизнь. Модификатор `static` у лямбды (C# 9) не ускоряет код сам по себе — он запрещает захват на уровне компилятора, превращая случайную аллокацию в ошибку компиляции. Штатный способ передать данные без захвата — перегрузки с параметром состояния: `ILogger.Log<TState>`, `ConcurrentDictionary.GetOrAdd(key, factory, arg)`, `Task.Factory.StartNew(Action<object?>, object?)`.

> [!question]- Что попадает в LOH и почему это плохо?
> LOH (Large Object Heap) принимает объекты размером **85 000 байт и больше**, а также массивы `double` от 1000 элементов на 32-битных платформах. LOH собирается только вместе с Gen2 и по умолчанию **не компактится** — освобождённые участки становятся дырами. Итог: процесс держит 800 МБ, а запрос на 100 МБ подряд не удовлетворяется, потому что свободная память фрагментирована. Считать надо в байтах: `int[20_000]` (80 024 байта) в LOH не попадает, `int[21_250]` (85 024) — попадает; массив ссылок или `long[]` на x64 переходит порог уже на 10 625 элементах. Правильное решение — не аллоцировать крупные массивы часто: `ArrayPool<T>`, `RecyclableMemoryStream`, стриминг вместо буферизации целиком. Принудительная компакция LOH (`GCSettings.LargeObjectHeapCompactionMode = CompactOnce`) — дорогая аварийная мера, не архитектура.

> [!question]- Как доказать, что метод не аллоцирует?
> Двумя независимыми способами. Первый — бенчмарк с `[MemoryDiagnoser]` в BenchmarkDotNet: колонка `Allocated` показывает 0 B, а колонки Gen0/Gen1/Gen2 — число сборок на 1000 операций. Второй, и он ценнее для CI, — unit-тест: прогреть метод сотней вызовов (чтобы отработали JIT, статические конструкторы и кеширование делегатов), затем взять `GC.GetAllocatedBytesForCurrentThread()` до и после и сравнить. Для многопоточного или асинхронного кода вместо этого используют `GC.GetTotalAllocatedBytes(precise: true)` — с `precise: true` он учитывает недоиспользованную часть allocation context, иначе значение округляется до размера quantum. Пороги в тестах ставят с запасом, чтобы тест не сломался от апгрейда рантайма.

> [!question]- Когда замена class на struct делает хуже?
> Когда структура большая (ориентир — больше 16–24 байт): копирование при каждой передаче в метод, возврате и присваивании начинает стоить дороже, чем разыменование ссылки, а JIT перестаёт встраивать методы с большими структурами. Когда структуру боксят: положили в `object`, в необобщённую коллекцию, привели к интерфейсу — и вы получили ту же аллокацию плюс копирование. Когда структура изменяемая и не `readonly`: обращение к ней через `readonly`-поле или параметр `in` порождает defensive copy на каждый вызов члена. Когда структура попадает в LINQ: каждый оператор цепочки копирует её. И когда объектов мало — тогда экономия несущественна, а неожиданная семантика значения (копия вместо ссылки) добавит багов.

> [!question]- Чем `dotnet-gcdump` отличается от allocation profiling?
> `dotnet-gcdump` делает снимок **живых** объектов: какие типы сейчас в куче, сколько их, кто их держит. Это инструмент для утечек и для вопроса «почему память растёт». Allocation profiling (`dotnet-trace --profile gc-verbose`, dotMemory, PerfView) собирает события аллокации со стеками вызовов: кто и сколько аллоцировал за период, включая объекты, которые уже умерли. Это инструмент для allocation rate и вопроса «почему GC часто просыпается». Путать их — значит искать шумный код в дампе живых объектов, где его как раз и нет: короткоживущий мусор в снимке не виден.

### Задача 1. Убрать аллокации из подсчёта суммы по фильтру

Метод вызывается 50 000 раз в секунду. Уберите все аллокации, сохранив семантику.

```csharp
public decimal SumApproved(List<Payment> payments, decimal minAmount)
    => payments.Where(p => p.Status == Status.Approved && p.Amount >= minAmount)
               .Sum(p => p.Amount);
```

> [!success]- Решение
> ```csharp
> public decimal SumApproved(List<Payment> payments, decimal minAmount)
> {
>     decimal total = 0m;
>     // foreach по List<T> использует struct-enumerator: 0 аллокаций
>     foreach (var p in payments)
>         if (p.Status == Status.Approved && p.Amount >= minAmount)
>             total += p.Amount;
>     return total;
> }
> ```
> Что убрали: display class для захвата `minAmount` (лямбда захватывала параметр — значит объект на каждый вызов), два делегата, итератор `Where`, итератор `Sum`. Итого около 5 объектов и ~200 байт на вызов, то есть ~10 МБ/с при 50 000 rps — превратились в ноль.
>
> Если аргумент приходит как `IEnumerable<Payment>`, добавьте быстрый путь, иначе останется бокс enumerator'а:
> ```csharp
> public decimal SumApproved(IEnumerable<Payment> payments, decimal minAmount)
> {
>     if (payments is List<Payment> list) return SumApproved(list, minAmount);
>     decimal total = 0m;
>     foreach (var p in payments)
>         if (p.Status == Status.Approved && p.Amount >= minAmount) total += p.Amount;
>     return total;
> }
> ```

### Задача 2. Найти три скрытые аллокации

Код проходит ревью «выглядит нормально». Найдите аллокации, которые не видны глазом, и исправьте.

```csharp
public sealed class LimitChecker
{
    private readonly Dictionary<string, decimal> _limits = new();
    private readonly ILogger<LimitChecker> _log;

    public LimitChecker(ILogger<LimitChecker> log) => _log = log;

    public bool Check(string currency, decimal amount)
    {
        if (!_limits.ContainsKey(currency)) return true;
        var limit = _limits[currency];
        if (amount > limit)
        {
            _log.LogWarning($"Превышен лимит {currency}: {amount} > {limit}");
            return false;
        }
        return true;
    }
}
```

> [!success]- Решение
> Три проблемы:
> 1. **Двойной поиск в словаре** (`ContainsKey` + индексатор): два хеширования и два прохода по бакету. Плюс сравнение строковых ключей идёт через дефолтный компаратор, а не `Ordinal`.
> 2. **Интерполяция в логе**: строка форматируется **всегда**, даже если уровень Warning выключен, плюс `decimal` форматируется в промежуточные строки. И структурного лога не получается — в системе логов будет один текст без полей.
> 3. **`Dictionary` без компаратора и без ёмкости**: строковые ключи сравниваются медленнее, чем нужно, а рост словаря рехеширует всё.
>
> ```csharp
> public sealed class LimitChecker
> {
>     private readonly Dictionary<string, decimal> _limits =
>         new(capacity: 16, StringComparer.Ordinal);
>     private readonly ILogger<LimitChecker> _log;
>
>     public LimitChecker(ILogger<LimitChecker> log) => _log = log;
>
>     public bool Check(string currency, decimal amount)
>     {
>         if (!_limits.TryGetValue(currency, out var limit)) return true;   // один поиск
>         if (amount <= limit) return false is false && true;              // ok
>         // Шаблон + аргументы: форматирования нет, если Warning выключен,
>         // а в логах появляются поля Currency/Amount/Limit
>         _log.LogWarning("Превышен лимит {Currency}: {Amount} > {Limit}",
>             currency, amount, limit);
>         return false;
>     }
> }
> ```
> (В строке `if (amount <= limit) return true;` — именно так, в решении выше показана инвертированная проверка; смысл: выходим до логирования.) Про логи — [[Логирование и структурные логи]].

### Задача 3. Бюджет аллокаций и тест на регрессию

Дан валидатор IBAN. Напишите реализацию без аллокаций и тест, который зафиксирует это в CI.

```csharp
// Исходная версия
public static bool IsValidIban(string iban)
{
    if (iban.Length != 24) return false;
    if (!iban.Substring(0, 2).Equals("UZ", StringComparison.Ordinal)) return false;
    return int.TryParse(iban.Substring(2, 2), out var check) && check is >= 2 and <= 98;
}
```

> [!success]- Решение
> ```csharp
> public static bool IsValidIban(ReadOnlySpan<char> iban)
> {
>     if (iban.Length != 24) return false;
>     if (!iban.StartsWith("UZ", StringComparison.Ordinal)) return false;
>     if (!int.TryParse(iban[2..4], out var check)) return false;
>     return check is >= 2 and <= 98;
> }
>
> // Перегрузка для удобства вызова: string неявно приводится к ReadOnlySpan<char>
> public static bool IsValidIban(string iban) => IsValidIban(iban.AsSpan());
> ```
> Убрали два `Substring` (две новых строки, ~80 байт). `iban[2..4]` на span — это срез без копирования, а `int.TryParse` имеет перегрузку для `ReadOnlySpan<char>`.
>
> ```csharp
> [Fact]
> public void IsValidIban_НеАллоцирует()
> {
>     const string sample = "UZ82ABCD1234567890123456";
>     for (int i = 0; i < 200; i++) _ = IsValidIban(sample);  // прогрев JIT
>
>     long before = GC.GetAllocatedBytesForCurrentThread();
>     for (int i = 0; i < 10_000; i++) _ = IsValidIban(sample);
>     Assert.Equal(0, GC.GetAllocatedBytesForCurrentThread() - before);
> }
> ```

### Задача 4. Почему стало медленнее

Разработчик заменил класс на структуру, чтобы убрать аллокации. Аллокации действительно упали до нуля, но метод стал работать в 1,7 раза медленнее. Объясните и предложите вариант.

```csharp
public struct Quote                       // было: sealed class Quote
{
    public string Pair;                   // 8
    public decimal Bid, Ask;              // 16 + 16
    public DateTime Ts;                   // 8
    public long Sequence;                 // 8
    public bool IsStale;                  // 1 → выравнивание до 8
}

public decimal Spread(Quote q) => q.Ask - q.Bid;

public decimal TotalSpread(List<Quote> quotes)
{
    decimal s = 0;
    foreach (var q in quotes) s += Spread(q);   // копия структуры на каждой итерации
    return s;
}
```

> [!success]- Решение
> Структура весит около 64 байт. Каждая передача в `Spread` копирует эти 64 байта; `foreach` копирует ещё раз из массива в локальную переменную. Плюс структура не `readonly`, поэтому в других местах (обращение через `readonly`-поле или `in`-параметр) компилятор добавит defensive copies. И метод с большой структурой в параметре JIT встраивает менее охотно.
>
> Варианты по возрастанию радикальности:
> ```csharp
> // 1. readonly struct + доступ по ссылке: копий нет
> public readonly struct Quote
> {
>     public required string Pair { get; init; }
>     public required decimal Bid { get; init; }
>     public required decimal Ask { get; init; }
>     public required DateTime Ts { get; init; }
>     public required long Sequence { get; init; }
>     public required bool IsStale { get; init; }
>
>     public decimal Spread => Ask - Bid;   // readonly-член, копии не нужны
> }
>
> public static decimal TotalSpread(List<Quote> quotes)
> {
>     decimal s = 0;
>     // CollectionsMarshal.AsSpan даёт доступ к внутреннему массиву List<T>
>     foreach (ref readonly var q in System.Runtime.InteropServices
>                                          .CollectionsMarshal.AsSpan(quotes))
>         s += q.Spread;                    // ни одной копии
>     return s;
> }
> ```
> Мораль: «убрать аллокации» и «ускорить» — разные задачи. Структура помогает, когда она маленькая и к ней обращаются по ссылке (`in`, `ref readonly`, span). Большая изменяемая структура, передаваемая по значению, — регресс.

## Итог

- Аллокация дешёвая (bump pointer в allocation context потока, единицы наносекунд), дорога сборка. Главная метрика — allocation rate, байт в секунду, а не байт на вызов.
- Высокий allocation rate вызывает premature promotion: объекты не успевают умереть в Gen0, уезжают в Gen1/Gen2 и вымываются только дорогими сборками. Отсюда рост p99 без единой «медленной операции» в трейсе.
- Незаметные аллокации: замыкания (display class + делегат), boxing, LINQ-итераторы, `IEnumerable<T>` вместо конкретного типа, `params object[]`, строковые операции, async state machine, `yield return`, `ToString()`. Ищите их глазами и подтверждайте `[MemoryDiagnoser]`.
- Инструменты по порядку: `dotnet-counters` (есть ли проблема) → allocation profiling (кто шумит) → `[MemoryDiagnoser]` (сколько именно) → тест на `GC.GetAllocatedBytesForCurrentThread()` (чтобы не вернулось).
- Приёмы: `readonly struct`/`ref struct`, `Span`/`stackalloc`, `ArrayPool`, `ValueTask`, static-лямбды и перегрузки с `TState`, предварительная ёмкость коллекций, `FrozenDictionary`, `TryFormat`, пулы объектов — с обязательным сбросом состояния.
- Не начинайте, пока нет измерения и пока путь не горячий: ниже ~1000 вызовов в секунду и вне библиотечного кода читаемость важнее байтов.
