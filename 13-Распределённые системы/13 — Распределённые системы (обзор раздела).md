# 13 — Распределённые системы (обзор раздела)

> [!abstract] Коротко
> Раздел о том, что происходит, когда одно приложение перестаёт быть одним процессом. Главная мысль: распределённость не добавляет возможностей — она добавляет режимы отказа. Всё остальное в разделе (брокеры, outbox, saga, идемпотентность, retry) — это инструменты борьбы с последствиями одного решения: «мы разнесли состояние по сети».
> Порядок чтения ниже неслучайный: сначала «надо ли вообще», потом «как общаться», потом «как не потерять деньги».

## Зачем это нужно

В монолите вызов метода либо выполнился, либо бросил исключение. Двух других вариантов нет. Как только между вызывающим и вызываемым появляется сеть, появляется третий вариант — **неизвестно**. Запрос ушёл, ответ не пришёл. Операция могла выполниться, могла не выполниться, могла выполниться дважды. Вы не можете это отличить изнутри клиента.

Весь этот раздел — про то, как строить финансовую систему в мире, где «неизвестно» — нормальное состояние. Для фронтенд-сервиса каталога товаров цена ошибки — неточная выдача. Для платёжного сервиса цена ошибки — двойное списание с карты клиента и разбор с регулятором.

```
Монолит:                          Распределённая система:

  вызов                             запрос ──► сеть ──► сервис
    │                                 │                   │
    ├─ успех                          │                   ├─ выполнил
    └─ исключение                     │                   └─ упал
                                      │
                                      ├─ пришёл ответ «ок»
                                      ├─ пришёл ответ «ошибка»
                                      ├─ таймаут (что там было?!)
                                      └─ TCP reset (а что там было?!)
```

## Восемь заблуждений о распределённых вычислениях

Список сформулирован в Sun Microsystems: первые четыре — Питер Дойч (1994), восьмой добавил Джеймс Гослинг. Это не историческая справка — это диагностический чек-лист. Практически любой инцидент в распределённой системе сводится к тому, что кто-то в коде неявно предположил один из этих пунктов.

Читайте каждый как «мы ошибочно считаем, что…».

### 1. Сеть надёжна

**Во что верят:** если я отправил HTTP-запрос, он дойдёт.
**Реальность:** пакеты теряются, соединения рвутся, поды перезапускаются посередине запроса, сетевые политики меняются на лету.
**Что из этого следует:** любой сетевой вызов может провалиться, и провалиться *после* того, как удалённая сторона выполнила работу. Отсюда — [[Идемпотентность]] и [[Отказоустойчивость: retry, backoff, circuit breaker]].

### 2. Задержка равна нулю

**Во что верят:** вызов по сети — это как вызов метода, только немного медленнее.
**Реальность:** локальный вызов — единицы наносекунд. Вызов внутри дата-центра — сотни микросекунд—единицы миллисекунд. Между регионами — десятки-сотни миллисекунд. Это разница в 5–7 порядков.
**Что из этого следует:** цикл `foreach` с сетевым вызовом внутри — это не «немного медленнее», это катастрофа. N+1 внутри одного процесса — плохо; N+1 по сети — инцидент. Отсюда — агрегация в [[API Gateway и BFF]] и батчинг.

```
Порядок величин (запомнить как ориентир):
  вызов метода в процессе      ~ 1 нс
  чтение из L2-кеша            ~ 5 нс
  мьютекс без конкуренции      ~ 20 нс
  чтение 1 МБ из RAM           ~ 100 мкс
  round-trip внутри ДЦ         ~ 500 мкс
  запрос к PostgreSQL рядом    ~ 1 мс
  round-trip Москва—Франкфурт  ~ 40 мс
```

### 3. Пропускная способность бесконечна

**Во что верят:** можно передавать сколько угодно данных.
**Реальность:** сериализация, дешифрование TLS, копирование буферов и сетевой канал стоят денег и времени. Ответ на 5 МБ JSON — это не «жирный DTO», это загруженный CPU на обеих сторонах и заполненный GC.
**Что из этого следует:** пагинация, проекции вместо полных сущностей, сжатие, gRPC/Protobuf вместо JSON там, где трафик действительно велик.

### 4. Сеть безопасна

**Во что верят:** «это же внутренний трафик, внутри кластера».
**Реальность:** «внутри» — понятие условное. Скомпрометированный под, зашедший в сеть подрядчик, неправильно настроенный service mesh. В финтехе плоская доверенная внутренняя сеть — прямое нарушение требований аудита.
**Что из этого следует:** mTLS между сервисами, аутентификация на каждом хопе, а не только на границе, — см. [[API Gateway и BFF]] и [[HTTPS, TLS и сертификаты]].

### 5. Топология не меняется

**Во что верят:** сервис живёт по адресу `10.0.3.17:8080`.
**Реальность:** в Kubernetes пода с таким адресом не будет через час. Инстансы приходят, уходят, масштабируются, переезжают между узлами.
**Что из этого следует:** никаких зашитых IP. См. [[Service Discovery и конфигурация]].

### 6. Администратор один

**Во что верят:** есть один человек/команда, кто понимает конфигурацию всей системы.
**Реальность:** ваш сервис зависит от сервиса другой команды, который зависит от внешнего провайдера платежей, у которого свой регламент обновлений. Никто не видит картину целиком.
**Что из этого следует:** контракты как формальная граница, версионирование, обратная совместимость — см. [[Способы межсервисного взаимодействия]]. И наблюдаемость, потому что понять систему можно только по телеметрии: [[Наблюдаемость: логи, метрики, трейсы]].

### 7. Стоимость передачи равна нулю

**Во что верят:** передать объект по сети бесплатно.
**Реальность:** есть стоимость сериализации/десериализации (CPU), стоимость трафика (в облаке cross-AZ трафик — отдельная строка в счёте), стоимость поддержки схемы.
**Что из этого следует:** проектируйте границы так, чтобы за одну операцию проходил один-два сетевых хопа, а не двенадцать.

### 8. Сеть однородна

**Во что верят:** все узлы одинаковые, все стеки одинаковые.
**Реальность:** ваш .NET-сервис говорит с Java-сервисом через Kafka, а он — с легаси на COBOL через файловый обмен. Разные представления decimal, разные часовые пояса, разные кодировки, разное поведение при переполнении.
**Что из этого следует:** явные схемы сообщений (Protobuf/Avro/JSON Schema), явные типы для денег (никогда `double`), явный UTC.

> [!danger] Как это выглядит на практике
> Классический инцидент в платёжном сервисе: клиент нажал «Оплатить», запрос ушёл в провайдер, провайдер списал деньги, но ответ не дошёл из-за таймаута (заблуждение 1 и 2). Наш код увидел ошибку и сделал retry (заблуждение: «повтор безопасен»). Провайдер списал второй раз, потому что мы не передали ключ идемпотентности (заблуждение 1 в чистом виде). Клиент видит одно списание в приложении и два в SMS от банка. Всё это — один неучтённый режим отказа.

## Что должен уметь Middle 2 по этому разделу

Не «знать слова», а именно уметь:

1. Объяснить, почему конкретную систему не стоит (или стоит) резать на сервисы, с опорой на организационные, а не технические аргументы.
2. Выбрать между синхронным вызовом и сообщением и обосновать выбор через режимы отказа, а не через «модно».
3. Реализовать outbox на EF Core с нуля, не подглядывая: таблица, транзакция, publisher, очистка.
4. Реализовать дедупликацию на потребителе, включая гонку двух параллельных доставок одного сообщения.
5. Спроектировать сагу перевода денег и на доске разобрать, что происходит при отказе на каждом шаге.
6. Настроить retry так, чтобы он не устроил retry storm, и объяснить, зачем нужен jitter.
7. Сказать «здесь eventual consistency недопустима, потому что…» и быть правым.

## Терминологический минимум

| Термин | Русский | Смысл в одной строке |
|---|---|---|
| at-most-once | не более одного раза | Можем потерять, но не удвоим |
| at-least-once | хотя бы один раз | Не потеряем, но можем удвоить |
| exactly-once | ровно один раз | Достижимо только как at-least-once + дедупликация |
| idempotency | идемпотентность | Повторное применение не меняет результат |
| eventual consistency | согласованность в конечном счёте | Разойдётся, но потом сойдётся |
| compensation | компенсация | Бизнес-действие, откатывающее эффект, а не откат транзакции |
| backpressure | обратное давление | Механизм «мне слишком много, притормози» |
| fan-out | веерная рассылка | Одно событие — много получателей |
| poison message | отравленное сообщение | То, что падает всегда и блокирует очередь |
| split brain | расщепление сознания | Два узла считают себя главными |

> [!warning] Подводные камни всего раздела
> - **«У нас микросервисы» ≠ «у нас распределённая система под контролем».** Чаще всего это распределённый монолит: сервисы разделены по коду, но связаны синхронными вызовами так, что падение одного роняет все. Хуже монолита по всем параметрам.
> - **Асинхронность не убирает связанность, а делает её невидимой.** Если сервис A публикует событие, а B не может работать без него, связанность осталась — просто теперь она не видна в компиляторе. Компилятор больше не поймает несовместимое изменение схемы.
> - **Локальная транзакция — самое ценное, что у вас есть.** Каждая граница сервиса, которую вы проводите, потенциально разрывает транзакцию. Проводите границы там, где транзакция не нужна.
> - **Отладка распределённой системы без трассировки невозможна.** Не «сложна» — невозможна. Прежде чем разрезать монолит, поднимите [[OpenTelemetry в .NET]].

## Вопросы с собеседований

> [!question]- Перечислите заблуждения о распределённых вычислениях и приведите пример инцидента по каждому из первых четырёх.
> 1. Сеть надёжна — таймаут при вызове платёжного провайдера, повтор, двойное списание. 2. Задержка нулевая — сервис заказов в цикле дёргает сервис товаров по одному SKU, страница корзины из 30 позиций грузится 4 секунды. 3. Пропускная способность бесконечна — эндпоинт отдаёт всю историю транзакций без пагинации, при 500 клиентах сеть и GC насыщаются, сервис падает по OOM. 4. Сеть безопасна — внутренний эндпоинт без аутентификации, скомпрометированный под из другого namespace вызывает `POST /internal/refund`. Остальные четыре: топология не меняется (зашитый IP), администратор один (несогласованный деплой ломает контракт), стоимость передачи нулевая (cross-AZ трафик в счёте облака), сеть однородна (Java-сервис прислал число с плавающей точкой там, где ждали `decimal`).

> [!question]- Почему «неизвестный результат» опаснее ошибки?
> Ошибка — это информация: операция не выполнена, можно повторить или откатить. Таймаут информации не даёт: удалённая сторона могла выполнить операцию целиком, выполнить частично или не начать. Клиент не может это различить. Поэтому в распределённой системе нельзя строить логику на «если исключение — значит не выполнилось»; нужно либо делать операции идемпотентными и повторять, либо иметь способ узнать реальное состояние (запрос статуса, сверка). В финтехе это отдельный процесс — реконсиляция с провайдером по выпискам.

> [!question]- Что такое «распределённый монолит» и почему это хуже монолита?
> Это набор сервисов, которые нельзя деплоить и эксплуатировать независимо: они связаны синхронными вызовами, общей базой или общей схемой сообщений, меняющейся не обратно совместимо. Вы получили все издержки распределённости (сетевые отказы, сложность отладки, отсутствие транзакций, эксплуатационная нагрузка) и ни одной выгоды (независимый деплой, изоляция отказов, независимое масштабирование). Монолит хотя бы даёт транзакции, стектрейсы и один деплой. Подробно — в [[Монолит vs микросервисы: как решать]].

> [!question]- С чего начать проектирование распределённой системы в финтехе?
> С границ транзакций, а не с сервисов. Выпишите бизнес-операции, для каждой определите набор данных, который должен меняться атомарно. Эти наборы — кандидаты в агрегаты и границы сервисов ([[DDD: стратегические паттерны]]). Затем для каждой операции, пересекающей границу, ответьте: допустима ли здесь eventual consistency, какая компенсация возможна, как обеспечить идемпотентность. Только после этого выбирайте брокер и фреймворк. Обратный порядок («возьмём Kafka и разложим сервисы») даёт систему, где деньги теряются.

## Итог

- Распределённость — это не фича, а плата. Платят за независимость деплоя и масштабирование команд; всё остальное — издержки.
- Восемь заблуждений — рабочий чек-лист для code review любой интеграции. Проверяйте по нему каждый сетевой вызов.
- Ключевая разница с монолитом: появляется третий исход операции — «неизвестно». Вся архитектура строится вокруг него.
- Ядро раздела — три заметки: outbox, saga, идемпотентность. Они дают гарантии, на которых держатся деньги.
- Прежде чем распределять систему, обеспечьте наблюдаемость. Без трассировки распределённая система — чёрный ящик.
