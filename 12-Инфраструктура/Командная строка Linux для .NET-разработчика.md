# Командная строка Linux для .NET-разработчика

> [!abstract] Коротко
> Прод .NET-приложений — почти всегда Linux (контейнер), а машина разработчика часто macOS. Обе системы Unix-подобные, поэтому 90 % команд совпадают, и различия стоит знать точечно: в macOS утилиты из BSD, в Linux — из GNU, и у них расходятся флаги у `sed`, `stat`, `date`. Минимум для бэкендера — навигация, права, конвейеры, поиск в файлах и логах, работа с процессами и портами, переменные окружения. Всё остальное гуглится, но эти вещи нужны каждый день.

> [!info] Про название и про твою машину
> Заметка называется «Linux», потому что прод и контейнеры — Linux. Локально ты работаешь на macOS с оболочкой **zsh**, и она ведёт себя почти идентично. Все места, где различия существенны, отмечены явно: **macOS** и **Linux**. Команды из блоков без пометки работают одинаково в обеих системах.

## Зачем это нужно

- `dotnet` — инструмент командной строки. `dotnet new`, `build`, `test`, `publish`, `dotnet ef migrations add` — всё это терминал, IDE лишь кнопки поверх.
- Docker-образ .NET-приложения внутри — Linux. Отладка «почему не запускается в контейнере» — это `docker exec -it ... /bin/sh` и разбор руками.
- Логи на сервере читаются `grep`/`tail`/`journalctl`, а не мышкой.
- CI-пайплайн — это скрипт shell. Не читая shell, невозможно понять, почему упала сборка.
- Диагностика на проде (`dotnet-counters`, `dotnet-trace`, дампы) живёт только в терминале.

## Оболочка и файловая система

**Оболочка** (shell) — программа, которая читает команды и запускает процессы. `zsh` — по умолчанию в macOS с версии Catalina, `bash` — в большинстве Linux-дистрибутивов и почти во всех контейнерах. Различия для повседневных задач минимальны; скрипты стоит писать на `bash`/POSIX sh, потому что именно они будут исполняться в CI и в образах.

```bash
echo $SHELL                 # какая оболочка сейчас: /bin/zsh
zsh --version
```

Файловая система — единое дерево от корня `/`, без букв диска:

| Путь | Что там |
|---|---|
| `/` | корень |
| `~` | домашний каталог (`/Users/rimkarimov` в macOS, `/home/<user>` в Linux) |
| `.` / `..` | текущий / родительский каталог |
| `/etc` | конфигурация системы (`/etc/hosts`) |
| `/var/log` | логи (**Linux**; в macOS системные логи — в `log show` и `/var/log` частично) |
| `/tmp` | временные файлы, чистятся |
| `/usr/local/bin`, `/opt/homebrew/bin` | пользовательские программы (второй — Homebrew на Apple Silicon) |
| `/proc` | **только Linux**: виртуальная ФС с состоянием процессов и ядра. В macOS её нет |

Файл, имя которого начинается с точки, — скрытый: `.gitignore`, `.zshrc`, `.env`.

### Навигация и просмотр

```bash
pwd                         # где я
ls -lah                     # список: длинный формат, скрытые, человекочитаемые размеры
cd /path/to/dir             # перейти
cd -                        # вернуться в предыдущий каталог
tree -L 2                   # дерево на 2 уровня (brew install tree)

cat appsettings.json        # вывести целиком
less app.log                # постранично: / — поиск, n — следующее, q — выход
head -n 20 data.csv         # первые 20 строк
tail -n 100 app.log         # последние 100 строк
tail -f app.log             # следить за файлом в реальном времени — главная команда при отладке
wc -l data.csv              # сколько строк
```

`tail -f` (или `tail -F`, который переживает пересоздание файла при ротации) — то, с чего начинается разбор любой проблемы на сервере.

### Работа с файлами

```bash
mkdir -p src/Pricing/Rules  # создать со всеми промежуточными каталогами
touch Program.cs            # создать пустой файл / обновить дату
cp -r src backup            # копировать каталог рекурсивно
mv old.cs new.cs            # переместить или переименовать
rm -rf obj bin              # удалить рекурсивно и без вопросов
ln -s ../shared shared      # символическая ссылка
du -sh *                    # размер каждого элемента в текущем каталоге
df -h                       # свободное место на диске
```

> [!danger] `rm -rf` не спрашивает и не имеет корзины
> `rm -rf $DIR/` при пустой переменной `DIR` превращается в `rm -rf /`. Правила: не набирать `rm -rf` с переменными без проверки, сначала посмотреть, что попадёт под удаление (`ls $DIR`), а в скриптах использовать `set -u`, чтобы обращение к неустановленной переменной было ошибкой.

### Права доступа

```bash
ls -l entrypoint.sh
# -rwxr-xr--  1 rim  staff  512 Aug 12 10:00 entrypoint.sh
#  │└┬┘└┬┘└┬┘
#  │ │  │  └── others: r-- (чтение)
#  │ │  └───── group:  r-x (чтение, исполнение)
#  │ └──────── user:   rwx (чтение, запись, исполнение)
#  └────────── тип: - файл, d каталог, l ссылка

chmod +x entrypoint.sh      # сделать исполняемым
chmod 644 appsettings.json  # rw- r-- r--
chown -R app:app /app       # сменить владельца (нужны права root)
```

Восьмеричная запись: `r=4`, `w=2`, `x=1`. `755` = `rwxr-xr-x`, `644` = `rw-r--r--`.

Где это кусает .NET-разработчика: скрипт, скопированный в Docker-образ без бита исполнения, даёт `permission denied` при запуске контейнера. И вторая классика — контейнер, запущенный от непривилегированного пользователя (правильная практика), не может писать в каталог, созданный от root.

## Конвейеры и перенаправление

Идея Unix: маленькие программы, соединённые в конвейер. У процесса три стандартных потока: `stdin` (0), `stdout` (1), `stderr` (2).

```bash
command > file.txt          # stdout в файл (перезаписать)
command >> file.txt         # дописать
command 2> errors.txt       # только stderr
command > all.log 2>&1      # оба потока в один файл
command < input.txt         # stdin из файла
command1 | command2         # stdout первой на stdin второй

dotnet test 2>&1 | tee test.log     # и на экран, и в файл
grep -i error app.log | wc -l       # сколько строк с ошибками
```

Разделение `stdout`/`stderr` практично: `dotnet build 2> errors.txt` оставит в файле только ошибки компиляции.

### Инструменты поиска

```bash
# grep — поиск по содержимому
grep -rn "ConnectionString" src/          # рекурсивно, с номерами строк
grep -i "error" app.log                   # без учёта регистра
grep -v "HealthCheck" app.log             # исключить строки
grep -A 5 -B 2 "Exception" app.log        # 2 строки до и 5 после совпадения
grep -c "Exception" app.log               # только количество
grep -E "5[0-9]{2}" access.log            # расширенные регулярки: коды 5xx

# find — поиск файлов
find . -name "*.csproj"                   # по имени
find . -type d -name "obj" -exec rm -rf {} +   # найти и удалить все obj/
find . -name "*.cs" -newermt "2026-08-01" # изменённые после даты
find . -size +100M                        # больше 100 МБ

# современная замена, стоит поставить: brew install ripgrep fd
rg "CalculateDiscount" --type cs          # быстрее grep, уважает .gitignore
fd -e csproj                              # быстрее find, дружелюбный синтаксис
```

`grep -A/-B` вокруг `Exception` — то, чем читают стектрейсы в логах: само сообщение бесполезно без строк вокруг.

### sed и awk по минимуму

```bash
# sed — потоковая замена
sed 's/localhost/db.internal/g' appsettings.json     # вывести с заменой
sed -i '' 's/8080/5000/g' docker-compose.yml         # macOS: -i требует аргумент ''
sed -i    's/8080/5000/g' docker-compose.yml         # Linux (GNU): аргумент не нужен

# awk — обработка по колонкам
awk '{print $1, $9}' access.log                      # 1-е и 9-е поле каждой строки
awk -F';' '{sum += $3} END {print sum}' orders.csv    # сумма третьей колонки CSV
ps aux | awk '$3 > 50 {print $2, $3, $11}'            # процессы с CPU > 50 %
```

Различие `sed -i` между macOS и Linux — самая частая мелкая заноза: скрипт, отлаженный локально, падает в CI или наоборот. В переносимых скриптах проще использовать `perl -pi -e` либо явно передавать суффикс: `sed -i.bak`.

## Процессы, порты, ресурсы

```bash
ps aux | grep dotnet         # найти процессы
top                          # интерактивный монитор (htop приятнее: brew install htop)
kill 12345                   # послать SIGTERM — корректное завершение
kill -9 12345                # SIGKILL — убить без шансов на очистку
pkill -f "MyApp.dll"         # убить по шаблону командной строки

lsof -nP -iTCP -sTCP:LISTEN  # кто слушает порты (macOS и Linux)
lsof -nP -i :5000            # кто занял порт 5000 — «Address already in use»
ss -tulpn                    # Linux: то же самое современными средствами

# Linux: сколько ядер и памяти видит процесс
nproc && free -h
# macOS: аналоги
sysctl -n hw.ncpu && vm_stat
```

Разница между `SIGTERM` (`kill`) и `SIGKILL` (`kill -9`) важна для .NET: по `SIGTERM` хост запускает штатное завершение — `IHostApplicationLifetime.ApplicationStopping`, `IHostedService.StopAsync`, дренаж активных запросов. По `SIGKILL` процесс умирает мгновенно: незакоммиченные транзакции, недописанные буферы, неотправленные сообщения теряются. Именно поэтому Kubernetes сначала посылает `SIGTERM` и лишь по истечении `terminationGracePeriodSeconds` — `SIGKILL`, и именно поэтому обработку `SIGTERM` в сервисе надо реализовывать (в ASP.NET Core она есть по умолчанию, но долгие фоновые задачи должны уважать `CancellationToken`).

## Переменные окружения

```bash
echo $HOME
echo $PATH                                  # где ищутся исполняемые файлы
export ASPNETCORE_ENVIRONMENT=Development    # на текущую сессию
env | sort                                   # все переменные
printenv ASPNETCORE_URLS

# Только на один запуск команды:
ASPNETCORE_ENVIRONMENT=Staging dotnet run
```

Для .NET это не абстракция, а основной механизм конфигурации: `ASPNETCORE_ENVIRONMENT` выбирает `appsettings.{Environment}.json`, а любую настройку можно переопределить переменной с двойным подчёркиванием вместо двоеточия:

```bash
export ConnectionStrings__Default="Host=localhost;Database=shop;Username=app;Password=secret"
export Logging__LogLevel__Default=Debug
```

Двойное подчёркивание используется потому, что двоеточие недопустимо в именах переменных в некоторых оболочках. Подробно — [[Host, конфигурация и окружения]].

Постоянные настройки для своей оболочки живут в `~/.zshrc` (macOS/zsh) или `~/.bashrc` (Linux/bash):

```bash
# ~/.zshrc
export PATH="$HOME/.dotnet/tools:$PATH"     # чтобы работали dotnet-ef, dotnet-counters
export DOTNET_CLI_TELEMETRY_OPTOUT=1
alias gs='git status'
alias dr='dotnet run'
alias dwatch='dotnet watch'
```

После правки — `source ~/.zshrc` либо новый терминал.

## Что нужно именно .NET-разработчику

```bash
# Проект и сборка
dotnet new console -o Sandbox && cd Sandbox
dotnet run
dotnet watch                       # перезапуск при изменении файлов
dotnet build -c Release
dotnet test --filter "FullyQualifiedName~DiscountTests"
dotnet publish -c Release -o out

# Что вообще установлено
dotnet --info                      # версии SDK и рантаймов, RID, пути
dotnet --list-sdks

# Инструменты, устанавливаемые как global tools
dotnet tool install -g dotnet-ef
dotnet tool install -g dotnet-counters
dotnet tool install -g dotnet-trace
dotnet tool list -g

# Диагностика живого процесса (работает и локально, и в контейнере)
dotnet-counters monitor -p 12345 --counters System.Runtime
dotnet-counters ps                 # какие .NET-процессы видны

# HTTP и JSON руками
curl -s localhost:5000/api/orders | jq '.[0]'
curl -i -X POST localhost:5000/api/orders \
     -H "Content-Type: application/json" \
     -d '{"customerId": 42, "total": 199.99}'

# Контейнеры
docker compose up -d
docker compose logs -f api
docker exec -it shop-api /bin/sh   # внутрь контейнера; в alpine-образах именно sh, не bash
docker stats
```

`jq` — обязательный инструмент для API (`brew install jq`): без него JSON в терминале нечитаем.

Внутри контейнера с .NET-образом полезно помнить, что там нет ни `curl`, ни `ps` — образы минимальные. Отсюда практика: диагностировать снаружи (`docker exec` + то, что есть), а health-check делать средствами приложения, а не `curl` внутри образа.

## Скрипты: минимум, чтобы читать CI

```bash
#!/usr/bin/env bash
set -euo pipefail            # обязательная первая строка любого рабочего скрипта

# -e  прервать выполнение при первой ошибке
# -u  обращение к неустановленной переменной — ошибка
# -o pipefail  ошибка в любом звене конвейера роняет весь конвейер

PROJECT="${1:?укажите путь к проекту}"       # обязательный аргумент с сообщением
CONFIG="${2:-Release}"                        # аргумент со значением по умолчанию

echo "Собираю $PROJECT в конфигурации $CONFIG"
dotnet build "$PROJECT" -c "$CONFIG"

if [[ -f "$PROJECT/appsettings.json" ]]; then
    echo "Конфигурация найдена"
fi

for proj in $(find . -name "*.Tests.csproj"); do
    dotnet test "$proj" --no-build -c "$CONFIG"
done
```

Без `set -euo pipefail` скрипт продолжает работать после ошибки — и деплой «успешно» проходит на несобранном коде. Это самая частая причина «зелёного» пайплайна с нерабочим результатом.

Код возврата процесса: `0` — успех, всё остальное — ошибка. Проверяется через `$?`, и на этом построены `&&` (выполнить при успехе) и `||` (при неудаче):

```bash
dotnet test && dotnet publish -c Release     # публикуем только если тесты прошли
dotnet build || echo "Сборка упала"
echo $?                                      # код возврата последней команды
```

> [!warning] Подводные камни
> - **`sed -i` без аргумента в macOS.** BSD-версия требует суффикс: `sed -i '' 's/a/b/' file`. GNU-версия в Linux — наоборот, суффикс не нужен. Один и тот же скрипт ломается при переезде между машиной и CI.
> - **Регистр в именах файлов.** APFS в macOS по умолчанию регистронезависима, Linux — регистрозависим. `using` и имена файлов сойдутся локально и развалятся в Docker: `Could not find file 'Appsettings.json'`. Отсюда правило точных имён с самого начала.
> - **Переводы строк CRLF в shell-скриптах.** Скрипт с `\r\n` внутри Linux-контейнера падает с `bad interpreter: /bin/bash^M`. Лечится `.gitattributes` с `*.sh text eol=lf`.
> - **Пробелы в путях без кавычек.** `cd $DIR` при `DIR="/Users/rim/My Projects"` разъедется на два аргумента. Всегда `"$DIR"`.
> - **`kill -9` как рефлекс.** Убивает без корректного завершения: теряются буферы логов, активные запросы, транзакции. Сначала `kill`, `-9` — только если не помогло.
> - **Пути к `dotnet tool` не в `PATH`.** `dotnet-ef: command not found` после успешной установки — почти всегда отсутствие `~/.dotnet/tools` в `PATH`.

> [!example] Как делают в бою
> Разбор проблемы на сервере или в контейнере почти всегда одна и та же цепочка: `docker compose ps` (жив ли контейнер и не в цикле ли рестартов) → `docker compose logs --tail=200 -f api` (что в логах) → `grep -A 20 "Exception"` по логу (найти стектрейс) → `lsof -nP -i :5000` или `curl -v localhost:5000/health` (слушает ли, отвечает ли) → `dotnet-counters monitor` (что с памятью, GC и пулом потоков, если сервис жив, но медленный).
> Локально каждый день реально используются десяток команд: `ls`, `cd`, `grep`, `tail -f`, `find`, `ps`, `lsof`, `curl`, `docker`, `dotnet`. Всё остальное — по мере надобности, и это нормально: цель не выучить man-страницы, а не бояться терминала.

## Различия macOS и Linux: короткая таблица

| Задача | macOS (BSD) | Linux (GNU) |
|---|---|---|
| Замена в файле | `sed -i '' 's/a/b/' f` | `sed -i 's/a/b/' f` |
| Число ядер | `sysctl -n hw.ncpu` | `nproc` |
| Память | `vm_stat` | `free -h` |
| Слушающие порты | `lsof -nP -iTCP -sTCP:LISTEN` | `ss -tulpn` |
| Информация о процессах | `ps aux`, нет `/proc` | `ps aux`, есть `/proc/<pid>` |
| Установка пакетов | `brew install` | `apt install` / `dnf install` |
| Дата с арифметикой | `date -v-1d` | `date -d "1 day ago"` |
| Просмотр логов системы | `log show --last 1h` | `journalctl -u service -f` |
| Регистр в именах файлов | не различается (APFS) | различается |

Практический вывод: **не полагайся на локальное поведение как на истину**. Итоговая проверка любого скрипта — прогон в том же образе, что и в CI: `docker run --rm -v "$PWD":/w -w /w mcr.microsoft.com/dotnet/sdk:10.0 ./build.sh`.

## Вопросы с собеседований

> [!question]- Что произойдёт с .NET-приложением при `kill` и при `kill -9`?
> `kill` посылает `SIGTERM`. .NET-хост перехватывает его и запускает штатное завершение: срабатывает `ApplicationStopping`, вызываются `StopAsync` у зарегистрированных `IHostedService`, ASP.NET Core перестаёт принимать новые соединения и дожидается завершения текущих запросов, освобождаются ресурсы через `IDisposable`/`IAsyncDisposable`, флашатся логи. `kill -9` посылает `SIGKILL`, который перехватить невозможно: процесс снимается ядром немедленно, буферы не сбрасываются, обработчики завершения не выполняются — теряются активные запросы, недописанные логи, незавершённые транзакции. Поэтому оркестраторы делают именно так: сначала `SIGTERM`, затем ожидание grace-периода, и только потом `SIGKILL`. Со стороны кода это означает, что долгие фоновые операции обязаны уважать `CancellationToken`, иначе grace-период истечёт и завершение всё равно станет жёстким.

> [!question]- Как найти, кто занял порт, и как это связано с ошибкой запуска приложения?
> `lsof -nP -i :5000` в macOS и Linux, `ss -tulpn | grep 5000` в Linux — покажут PID и имя процесса. Ошибка `Address already in use` при старте Kestrel означает, что порт уже привязан другим процессом: чаще всего это предыдущий, не завершившийся экземпляр приложения (запущенный из IDE и не остановленный) либо второй экземпляр в контейнере с тем же пробросом. Решение — завершить процесс или сменить порт через `ASPNETCORE_URLS`. Отдельный случай той же ошибки — исчерпание эфемерных портов при массовых исходящих соединениях, но там она возникает не при старте, а под нагрузкой.

> [!question]- Зачем в shell-скрипте строка `set -euo pipefail`?
> По умолчанию shell продолжает выполнение после ошибки команды, подставляет пустую строку вместо неустановленной переменной и считает код возврата конвейера равным коду последней команды. Все три поведения опасны в скриптах сборки и деплоя. `-e` прерывает выполнение при первой ошибке, `-u` превращает обращение к неопределённой переменной в ошибку (это же спасает от `rm -rf $DIR/` с пустым `DIR`), `-o pipefail` заставляет конвейер вернуть ошибку, если упало любое звено, а не только последнее. Без этого пайплайн может «успешно» задеплоить результат провалившейся сборки — классическая авария, у которой нет ни ошибки в логах, ни красного статуса.

> [!question]- Почему приложение работает локально на macOS, но падает в Linux-контейнере с ошибкой «файл не найден»?
> Самая частая причина — регистр. APFS в macOS по умолчанию регистронезависима: `Appsettings.json` и `appsettings.json` для неё один файл. Linux регистр различает, и обращение с неверным регистром не находит ничего. Вторая причина того же класса — разделители путей и жёстко прописанные абсолютные пути; лечится `Path.Combine` и относительными путями от `AppContext.BaseDirectory`. Третья — файл не попал в образ: не скопирован в Dockerfile или исключён `.dockerignore`, либо у него нет прав на чтение под непривилегированным пользователем контейнера. Проверяется одной командой: `docker exec -it <container> ls -la /app`.

## Задачи

### Задача 1. Найти ошибки в логе

Из файла `app.log` (миллион строк) нужно получить: сколько всего исключений, какие типы исключений встречались и сколько раз каждый, и полный стектрейс последнего.

> [!success]- Решение
> ```bash
> # Сколько всего
> grep -c "Exception" app.log
>
> # Какие типы и сколько раз — классический конвейер «извлечь, отсортировать, посчитать»
> grep -o "[A-Za-z.]*Exception" app.log | sort | uniq -c | sort -rn
> #  412 System.Net.Http.HttpRequestException
> #   57 Npgsql.NpgsqlException
> #    3 System.NullReferenceException
>
> # Стектрейс последнего: найти последнее вхождение и показать строки после
> grep -n "Exception" app.log | tail -1        # узнать номер строки, например 998123
> tail -n +998123 app.log | head -40
> ```
> Идиома `sort | uniq -c | sort -rn` — самая полезная в анализе логов: `uniq -c` считает только соседние одинаковые строки, поэтому сортировка перед ним обязательна, а `sort -rn` в конце выводит частое сверху. `grep -o` печатает только совпавшую часть, а не всю строку, — именно это позволяет группировать.

### Задача 2. Почистить проект

Напиши команду, которая рекурсивно удаляет все каталоги `bin` и `obj` в дереве решения, но не трогает `node_modules` и `.git`.

> [!success]- Решение
> ```bash
> find . -type d \( -name bin -o -name obj \) \
>        -not -path "*/node_modules/*" -not -path "*/.git/*" \
>        -prune -exec rm -rf {} +
> ```
> Разбор: `\( ... -o ... \)` группирует условия «или» (скобки экранируются, иначе их съест shell); `-not -path` исключает поддеревья; `-prune` не заходит внутрь уже найденного каталога — без него `find` будет спускаться в каталог, который сейчас удаляется; `-exec ... {} +` передаёт найденное пачками, а не по одному вызову на файл, что заметно быстрее.
> Перед удалением стоит сначала посмотреть, что нашлось: заменить `-exec rm -rf {} +` на `-print`. И к слову, для .NET есть штатный способ: `dotnet clean` — но он чистит только то, что знает MSBuild, и не убирает каталоги от удалённых проектов.

### Задача 3. Проверить сервис одной строкой

Напиши команду, которая раз в 2 секунды опрашивает `/health` и печатает время и код ответа, чтобы поймать момент, когда сервис перестаёт отвечать.

> [!success]- Решение
> ```bash
> while true; do
>   printf '%s %s\n' "$(date '+%H:%M:%S')" \
>     "$(curl -s -o /dev/null -w '%{http_code} %{time_total}s' --max-time 3 localhost:5000/health)"
>   sleep 2
> done
> ```
> Ключевые флаги `curl`: `-s` убирает индикатор прогресса, `-o /dev/null` выбрасывает тело ответа, `-w` печатает только нужные поля (код и полное время), `--max-time 3` не даёт зависнуть навсегда — без него залипший запрос остановит весь цикл и ты не увидишь момент отказа. Вывод даёт ровно то, что нужно для корреляции: время, код и длительность. Дальше это сопоставляется с логами приложения по времени. Для более серьёзных проверок есть `watch -n 2` (в macOS ставится через `brew install watch`) и нагрузочные инструменты вроде `hey` или `k6`, но приведённый цикл не требует ничего лишнего.

## Итог

- macOS и Linux устроены одинаково по сути; отличаются утилиты (BSD против GNU) — помнить про `sed -i`, `nproc`/`sysctl`, регистр в именах файлов.
- Основа терминала: навигация, права, потоки и конвейеры. Всё остальное надстраивается.
- `grep`, `find`, `tail -f`, `sort | uniq -c | sort -rn` покрывают почти весь анализ логов.
- `SIGTERM` даёт приложению завершиться корректно, `SIGKILL` — нет; отсюда важность `CancellationToken` в фоновых задачах.
- Конфигурация .NET через переменные окружения: `ASPNETCORE_ENVIRONMENT`, `ConnectionStrings__Default`.
- В любом рабочем скрипте — `set -euo pipefail`, иначе ошибка проходит незамеченной.
- Финальная проверка скрипта — прогон в том же образе, что в CI, а не «у меня локально работает».
