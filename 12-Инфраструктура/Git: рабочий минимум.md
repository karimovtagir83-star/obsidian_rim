# Git: рабочий минимум

> [!abstract] Коротко
> Git хранит не «изменения», а полные снимки дерева файлов, связанные ссылками на родителей — получается направленный граф коммитов. Коммит идентифицируется хешем своего содержимого, ветка — это просто подвижный указатель на коммит, а `HEAD` — указатель на текущую ветку. Если держать в голове эту модель, все команды становятся предсказуемыми: `merge`, `rebase`, `reset` и `revert` — разные способы двигать указатели и создавать коммиты. Этот конспект — минимум для работы в команде: восемь команд на каждый день плюс умение выпутаться из типовых аварий.

## Зачем это нужно

Git — не «место, куда складывают код». Это инструмент, который отвечает на вопросы: кто и зачем изменил эту строку полгода назад, что именно уйдёт в релиз, как откатить вчерашнее без потери сегодняшнего, как двое могут править один файл и не затереть друг друга.

Без внутренней модели работа с Git превращается в набор заученных заклинаний, а первый же конфликт или случайный `reset --hard` — в панику и «удалю папку, клонирую заново». Поэтому сначала модель, потом команды.

## Модель: граф коммитов

**Коммит** — это снимок всего дерева файлов плюс метаданные: автор, дата, сообщение и ссылки на родительские коммиты. Идентификатор — SHA-1/SHA-256 хеш от содержимого, поэтому изменить историю незаметно невозможно: изменился коммит — изменился его хеш, а значит и хеши всех потомков.

```
       A ── B ── C ── D          ← main
                 \
                  E ── F        ← feature/discounts
                       ▲
                     HEAD
```

- **Ветка** — не копия файлов, а *подвижный указатель* на коммит. Создание ветки — запись 40 байт в файл, поэтому это бесплатно и делать это нужно постоянно.
- **HEAD** — указатель на текущую ветку (или прямо на коммит — тогда это «detached HEAD»).
- **Merge-коммит** — коммит с двумя родителями. Так две линии истории соединяются.

Три области, между которыми ходят файлы:

```
 рабочая копия  ──  git add  ──►  индекс (staging)  ──  git commit  ──►  репозиторий
   (файлы на           ◄── git restore ──               ◄── git reset ──
    диске)
```

Индекс (staging area) — то, что отличает Git от большинства предшественников: коммит собирается вручную, и можно закоммитить часть изменений файла (`git add -p`), оставив остальное в работе. Это не бюрократия, а инструмент: коммит должен содержать одно логическое изменение, а не «всё, что накопилось за день».

## Восемь команд на каждый день

```bash
git status                      # что изменено, что в индексе, на какой ветке — самая частая команда
git switch -c feature/discounts # создать ветку и перейти в неё
git add .                       # положить изменения в индекс
git add -p                      # то же, но по частям — с выбором конкретных кусков
git commit -m "Add discount calculation for loyalty tiers"
git fetch                       # забрать чужие изменения в локальные копии remote-веток
git pull --rebase               # забрать и перенести свои коммиты сверху (см. ниже)
git push -u origin feature/discounts
git log --oneline --graph --decorate --all     # посмотреть граф
git diff                        # что изменено и не в индексе
git diff --staged               # что уже в индексе и уйдёт в коммит
```

`switch` и `restore` появились в Git 2.23 и разделили то, что раньше делал перегруженный `checkout`: `switch` меняет ветку, `restore` восстанавливает файлы. В командах старых статей встречается `checkout` — он работает, но новые команды понятнее и безопаснее.

### Настройка, которую делают один раз

```bash
git config --global user.name "Rim Karimov"
git config --global user.email "rim.karimov@alif.uz"
git config --global init.defaultBranch main
git config --global pull.ff only          # pull только fast-forward: никаких неожиданных merge-коммитов
git config --global core.editor "code --wait"
git config --global diff.colorMoved zebra # перемещённые строки видно отдельно
```

`pull.ff only` — полезная защита: если `pull` не может обойтись перемоткой, он останавливается и просит решить явно (`git pull --rebase` или `git merge`). Вместо тихого merge-коммита получается осознанный выбор.

## Ветки и синхронизация

### fetch, pull, push

- `git fetch` — скачивает изменения с сервера и обновляет **локальные копии** серверных ветвей (`origin/main`). Рабочую копию не трогает. Безопасен всегда.
- `git pull` = `fetch` + интеграция (`merge` или `rebase`) в текущую ветку.
- `git push` — отправляет свои коммиты на сервер. Отклоняется, если на сервере есть коммиты, которых нет у тебя, — это защита от потери чужой работы.

```
до fetch:   локально main ── A ── B
            origin/main  ── A          (устаревшее представление)

после fetch: локально main ── A ── B
             origin/main  ── A ── C ── D   (теперь видно, что там появилось)
```

### merge против rebase

Два способа соединить свою ветку с обновившимся `main`:

```
Исходно:        A ── B ── C          main
                     \
                      D ── E         feature

merge (git merge main, находясь в feature):
                A ── B ── C          main
                     \      \
                      D ── E ── M    feature   ← M: merge-коммит с двумя родителями

rebase (git rebase main, находясь в feature):
                A ── B ── C          main
                            \
                             D'── E' feature   ← коммиты пересозданы поверх C,
                                                  у них НОВЫЕ хеши
```

| | merge | rebase |
|---|---|---|
| История | сохраняется как было, с точкой соединения | линейная, как будто работал после `C` |
| Хеши коммитов | не меняются | меняются — это новые коммиты |
| Конфликты | разрешаются один раз | могут возникнуть на каждом переносимом коммите |
| Безопасно для опубликованных ветвей | да | **нет** |
| Когда применять | вливание готовой ветки в `main` | подтягивание `main` в свою ветку до ревью |

Главное правило: **не переписывать историю, которая уже видна другим**. `rebase` своей личной ветки до пуша — нормальная практика, она делает историю читаемой. `rebase` ветки, из которой кто-то уже ответвился, — гарантированная боль у коллег. Подробнее о командных сценариях — [[Git: командные стратегии]].

## Конфликты: как их разрешают

Конфликт возникает, когда две линии истории изменили один и тот же участок файла и Git не может выбрать за тебя. Это не ошибка, а нормальная часть работы.

```bash
git switch feature/discounts
git rebase main
# CONFLICT (content): Merge conflict in src/Pricing/DiscountCalculator.cs
```

В файле появляются маркеры:

```csharp
public decimal Apply(decimal amount)
{
<<<<<<< HEAD                      // то, что уже в целевой ветке (main при rebase)
    return amount * 0.9m;
=======                            // разделитель
    return amount - amount * DiscountRate;   // твоё изменение
>>>>>>> feature/discounts
}
```

Порядок действий:

1. `git status` — какие файлы в конфликте.
2. Открыть файл, **понять оба изменения** и написать правильный итоговый код. Маркеры удалить целиком. Частая ошибка — механически оставить «свою» версию: так теряются чужие исправления.
3. `git add <файл>` — помечает конфликт разрешённым.
4. `git rebase --continue` (или `git merge --continue`).
5. Собрать и запустить тесты. Компилируемость после разрешения конфликта не гарантирована никем.

Полезные команды на время конфликта:

```bash
git diff                        # что именно конфликтует
git checkout --ours file.cs     # взять целиком версию целевой ветки
git checkout --theirs file.cs   # взять целиком свою версию (при rebase значения инвертированы!)
git rebase --abort              # передумать и вернуться в исходное состояние
git merge --abort
```

> [!warning] `--ours` и `--theirs` при rebase означают обратное интуиции
> При `merge` «ours» — текущая ветка, «theirs» — вливаемая. При `rebase` Git временно переключается на целевую ветку и накладывает твои коммиты поверх, поэтому «ours» — это `main`, а «theirs» — твоя работа. Проверять надо не по названию, а по содержимому.

## Как выпутаться: отмена изменений

Самая полезная часть Git и самая пугающая. Разложим по ситуациям.

```bash
# Изменил файл, ещё не добавил в индекс — откатить к последнему коммиту
git restore src/Program.cs
git restore .                       # всё сразу (изменения теряются безвозвратно)

# Добавил в индекс, но передумал коммитить (файл остаётся изменённым)
git restore --staged src/Program.cs

# Коммит сделан, но сообщение плохое или забыл файл — правим последний коммит
git commit --amend -m "Точное сообщение"
git add forgotten.cs && git commit --amend --no-edit

# Откатить последний коммит, СОХРАНИВ изменения в рабочей копии
git reset --soft HEAD~1             # изменения остаются в индексе
git reset HEAD~1                    # (--mixed по умолчанию) изменения остаются в файлах

# Откатить последний коммит вместе с изменениями — необратимо
git reset --hard HEAD~1

# Отменить УЖЕ ОПУБЛИКОВАННЫЙ коммит: создаётся новый коммит-антипод
git revert a1b2c3d

# Спрятать незакоммиченное, чтобы срочно переключиться
git stash push -m "черновик расчёта скидок"
git stash list
git stash pop

# Забрать один конкретный коммит из другой ветки
git cherry-pick a1b2c3d
```

`reset` против `revert` — водораздел: `reset` переписывает историю (можно только в своей неопубликованной ветке), `revert` добавляет новый коммит, отменяющий старый (единственно правильный способ для `main`).

### Спасательный круг: reflog

```bash
git reflog                          # журнал всех перемещений HEAD за последние 90 дней
# a1b2c3d HEAD@{0}: reset: moving to HEAD~1
# f4e5d6c HEAD@{1}: commit: Add discount calculation
git reset --hard f4e5d6c            # вернуться в состояние ДО неудачного reset
```

Пока коммит есть в reflog, он не потерян — даже после `reset --hard`. Это причина не паниковать: «потерять коммиты» в Git по-настоящему трудно. Действительно теряются только изменения, которые никогда не коммитили.

## Что не должно попадать в репозиторий

Для .NET-проекта `.gitignore` создаётся одной командой:

```bash
dotnet new gitignore
```

Он исключает `bin/`, `obj/`, `.vs/`, `*.user`, кеши. Помнить надо три правила:

1. **Результаты сборки — никогда.** `bin/` и `obj/` содержат мегабайты меняющихся бинарников; они превращают историю в кашу и порождают конфликты на каждом коммите.
2. **Секреты — никогда.** Строки подключения с паролями, ключи API, сертификаты. Локально их держат в `appsettings.Development.json` (в `.gitignore`) или в user secrets: `dotnet user-secrets set "ConnectionStrings:Default" "..."`. См. [[Конфигурация и секреты]].
3. **Большие бинарные файлы** — дампы, архивы, видео. Git хранит все версии всех файлов навсегда: репозиторий распухает необратимо.

> [!danger] Секрет, попавший в историю, считай утёкшим
> Удалить его следующим коммитом недостаточно: он остаётся в истории и доступен любому, у кого есть клон. Правильный порядок — **сразу отозвать и перевыпустить ключ**, а потом уже чистить историю (`git filter-repo`, с принудительным пушем и предупреждением всей команды). Порядок именно такой: чистка без ротации ключа — самообман.

Для кросс-платформенной команды полезен `.gitattributes`, чтобы переводы строк не создавали фантомных изменений:

```gitattributes
* text=auto
*.cs text eol=lf
*.sh text eol=lf
*.png binary
```

## Сообщения коммитов

Сообщение коммита — это письмо себе через полгода. Практика, принятая почти везде:

```
Краткая суть в императиве, до 72 символов

Зачем это изменение, если из кода неочевидно. Что было не так,
какой подход выбран и почему отвергнуты альтернативы.

Refs: SHOP-1423
```

Часто применяют Conventional Commits — префикс типа изменения, на нём же строят автоматические changelog'и:

```
feat: добавить расчёт скидок по уровням лояльности
fix: не терять копейки при округлении итога заказа
refactor: вынести правила скидок в отдельный сервис
test: покрыть граничные случаи расчёта скидки
chore: обновить EF Core до 10.0.1
```

Что плохо: «фикс», «wip», «правки после ревью», «asdf». Через месяц такая история не отвечает ни на один вопрос, а `git log` — это основной инструмент архитектурной археологии.

## Чтение истории

```bash
git log --oneline -20                            # последние 20 коммитов кратко
git log --graph --oneline --all                  # граф со всеми ветками
git log -p src/Pricing/DiscountCalculator.cs     # история одного файла с диффами
git log -S "CalculateDiscount"                   # когда появилась/исчезла строка кода
git log --author="Rim" --since="2 weeks ago"
git blame src/Pricing/DiscountCalculator.cs      # кто последним менял каждую строку
git show a1b2c3d                                 # что было в конкретном коммите
git bisect start                                 # бинарный поиск коммита, который сломал
```

`git bisect` стоит попробовать хотя бы раз: указываешь заведомо хороший и заведомо плохой коммит, Git методом деления пополам за `log₂ n` шагов находит виновника. На истории из 1000 коммитов — 10 проверок вместо перебора.

`git log -S` («pickaxe») находит коммит, где строка появилась или исчезла, — это быстрее, чем листать историю файла глазами.

> [!warning] Подводные камни
> - **`git pull` без понимания, что он делает.** Это `fetch` + `merge`; при расходящихся историях он молча создаёт merge-коммит, и история превращается в паутину. `pull.ff only` в конфиге заставляет решать явно.
> - **`git push --force` в общую ветку.** Затирает чужие коммиты на сервере. Если переписать историю действительно нужно, есть `--force-with-lease`: он откажется пушить, если на сервере появилось что-то, чего ты не видел.
> - **`git reset --hard` с незакоммиченными изменениями.** Reflog спасает коммиты, но не спасает то, что никогда не коммитили. Перед любым `reset --hard` — `git stash`.
> - **Коммит-«всё сразу».** Один коммит на 40 файлов и три несвязанные задачи невозможно ни отревьюить, ни отменить частично, ни найти через bisect. Дели по смыслу: `git add -p` для этого и существует.
> - **`bin/`/`obj/` в репозитории.** Кроме мусора это вечные конфликты: два человека собрали проект — и вот уже разные бинарники в одном файле.
> - **Ветка, живущая три недели.** Чем дольше ветка в отрыве от `main`, тем больнее вливание. Правило: подтягивать `main` в свою ветку ежедневно, а саму ветку держать не длиннее пары дней.

> [!example] Как делают в бою
> Типичный цикл работы над задачей: `git switch main && git pull` → `git switch -c feature/SHOP-1423-discounts` → маленькие коммиты по мере работы → ежедневно `git fetch && git rebase origin/main`, чтобы не копить расхождение → `git push -u origin ...` → pull request → правки по ревью новыми коммитами (не `amend`, чтобы ревьюер видел, что изменилось) → squash-merge в `main` силами платформы, чтобы в `main` попал один осмысленный коммит.
> Ветка `main` защищена настройками репозитория: прямой пуш запрещён, требуется ревью и зелёный CI. Это не бюрократия: главная ветка должна быть всегда собираемой, потому что из неё разворачивают.
> Отдельная практика — коммит перед любым рискованным действием. Локальный коммит бесплатен и всегда позволяет вернуться; «сделаю ребейз на грязной рабочей копии» — не позволяет.

## Вопросы с собеседований

> [!question]- Чем отличается merge от rebase и когда что применять?
> `merge` создаёт коммит с двумя родителями и сохраняет фактическую историю: видно, что ветка существовала и когда была влита. `rebase` пересоздаёт коммиты ветки поверх новой базы — история становится линейной, но у коммитов новые хеши, то есть это уже другие коммиты. Практика: `rebase` для подтягивания `main` в свою ещё не опубликованную (или опубликованную только для себя) ветку — так ревью выглядит как аккуратная линейка; `merge` (обычно squash-merge) для вливания готовой ветки в `main`. Железное правило: не делать `rebase` истории, на которую уже могли ответвиться другие, — их коммиты станут дубликатами, и разгребать это придётся всей команде.

> [!question]- Чем отличаются `reset --soft`, `--mixed` и `--hard`?
> Все три двигают указатель ветки на другой коммит, разница — что происходит с индексом и рабочей копией. `--soft`: изменения отменённых коммитов остаются в индексе, можно сразу сделать новый коммит — удобно, чтобы «пересобрать» серию коммитов в один. `--mixed` (по умолчанию): изменения остаются в файлах, но индекс очищается — надо заново `git add`. `--hard`: индекс и рабочая копия приводятся к состоянию целевого коммита, незакоммиченные изменения теряются безвозвратно. Коммиты после `--hard` ещё около 90 дней доступны через `git reflog`, а вот никогда не коммитившиеся изменения не восстановит ничто.

> [!question]- Как отменить коммит, который уже в main и его забрали другие?
> Только `git revert`: он создаёт новый коммит, применяющий обратные изменения. История остаётся неизменной, у всех сходится, никаких принудительных пушей. `reset` и `rebase` тут неприменимы — они переписывают историю, и у каждого, кто уже забрал старую версию, при следующем `pull` возникнет расхождение. Если отменять надо merge-коммит, нужен `git revert -m 1 <hash>`: указывается, какого из родителей считать «основной линией». Отдельно стоит помнить, что revert отменяет изменения, но сам факт первого коммита остаётся в истории — если в нём был секрет, revert его не убирает.

> [!question]- Что такое detached HEAD и как из него выйти?
> `HEAD` обычно указывает на ветку, а ветка — на коммит. Если переключиться прямо на коммит (`git checkout a1b2c3d`), тег или `origin/main`, то `HEAD` указывает на коммит напрямую — это detached HEAD. Работать так можно, но новые коммиты не принадлежат ни одной ветке: при переключении на ветку они станут недостижимыми и со временем будут удалены сборщиком мусора Git. Выход: если коммиты нужны — `git switch -c new-branch` (создаст ветку на текущем месте); если не нужны — просто `git switch main`. Найти «потерянные» коммиты после этого можно через `git reflog`.

> [!question]- Зачем нужен индекс (staging area)?
> Индекс — промежуточная область, где коммит собирается до фиксации. Он позволяет закоммитить не всё, что изменено, а только связанную часть — вплоть до отдельных кусков одного файла через `git add -p`. Это напрямую влияет на качество истории: коммит с одним логическим изменением можно отревьюить, отменить через `revert` и найти через `bisect`, а коммит «всё за день» — нельзя ни одно из трёх. Вторая функция индекса — площадка для разрешения конфликтов: `git add` файла означает «конфликт разрешён». В системах без индекса (или при работе `git commit -a`) эта возможность просто отсутствует.

## Задачи

### Задача 1. Забыл файл в коммите

Сделал коммит и запушил, потом обнаружил, что забыл добавить один файл, относящийся к тому же изменению. Как поступить, если ветка личная и если ветка общая?

> [!success]- Решение
> Личная ветка (никто больше на неё не смотрит):
> ```bash
> git add src/Pricing/DiscountRules.cs
> git commit --amend --no-edit        # тот же коммит, дополненный файлом, но с новым хешем
> git push --force-with-lease          # переписать свою ветку на сервере
> ```
> `--force-with-lease` вместо `--force`: он проверит, что на сервере ровно тот коммит, который ты видел последним, и откажется затирать чужую работу.
> Общая ветка (из неё ответвлялись, её ревьюят):
> ```bash
> git add src/Pricing/DiscountRules.cs
> git commit -m "Add missing DiscountRules file"
> git push
> ```
> Отдельный коммит, никакого переписывания. Косметику истории потом решит squash-merge при вливании в `main`.

### Задача 2. Разобрать конфликт

При `git rebase main` возник конфликт в файле. Ты решил, что оба изменения нужны. Опиши последовательность действий и что проверить перед `--continue`.

> [!success]- Решение
> ```bash
> git status                         # список файлов в конфликте
> # открыть файл, объединить обе версии руками, удалить все маркеры
> # <<<<<<<, =======, >>>>>>>
> git diff --check                   # убедиться, что маркеров не осталось
> dotnet build                       # код должен компилироваться
> dotnet test                        # и проходить тесты
> git add src/Pricing/DiscountCalculator.cs
> git rebase --continue
> ```
> Ключевые моменты: маркеры конфликта удаляются полностью — оставленный `=======` даёт синтаксическую ошибку компиляции, а оставленный внутри строкового литерала может уехать в прод незамеченным. Сборка и тесты после разрешения обязательны: Git объединяет текст, а не смысл, и «успешно разрешённый» конфликт часто не компилируется или ломает логику. При rebase конфликт может возникнуть повторно на каждом переносимом коммите — это нормально, цикл повторяется. Если стало ясно, что разрешать нечего или запутался, `git rebase --abort` возвращает всё как было.

### Задача 3. Найти, когда сломалось

Тест, который раньше проходил, теперь падает. Известно, что две недели назад всё было хорошо; с тех пор 200 коммитов. Как найти виновника, не проверяя все?

> [!success]- Решение
> ```bash
> git bisect start
> git bisect bad                     # текущее состояние — плохое
> git bisect good HEAD~200           # 200 коммитов назад — хорошее
> # Git переключается на середину; проверяем:
> dotnet test --filter FullyQualifiedName~DiscountTests
> git bisect bad     # или git bisect good — по результату
> # ...повторяем ~8 раз, Git сам сужает интервал
> git bisect reset                   # вернуться на исходную ветку
> ```
> Это бинарный поиск: 200 коммитов проверяются примерно за 8 шагов (`log₂ 200 ≈ 7,6`). Если проверку можно автоматизировать, весь процесс сводится к одной команде: `git bisect run dotnet test --filter ...` — Git сам прогонит тест на каждом шаге и назовёт первый плохой коммит. Именно ради bisect стоит делать маленькие коммиты: найденный коммит на 3 файла сразу показывает причину, а коммит на 40 файлов — только начало поиска.

## Итог

- Коммит — снимок дерева с ссылками на родителей; хеш зависит от содержимого, поэтому историю нельзя изменить незаметно.
- Ветка — просто указатель на коммит, `HEAD` — указатель на ветку. Создавать ветки бесплатно.
- Индекс существует, чтобы коммит содержал одно логическое изменение: `git add -p` — рабочий инструмент, а не экзотика.
- `fetch` безопасен всегда, `pull` = fetch + интеграция; `pull.ff only` избавляет от неожиданных merge-коммитов.
- `rebase` — только для своей неопубликованной истории; `merge`/squash — для вливания в общую ветку.
- Отмена: `restore` для файлов, `reset` для своей истории, `revert` для опубликованной, `reflog` — спасательный круг.
- В репозиторий не попадают результаты сборки, секреты и большие бинарники. Утёкший секрет сначала отзывают, потом чистят историю.
- Сообщения коммитов пишутся для того, кто будет читать `git log` через полгода. Это ты.
