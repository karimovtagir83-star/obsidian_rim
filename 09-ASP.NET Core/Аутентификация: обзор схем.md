# Аутентификация: обзор схем

> [!abstract] Коротко
> Аутентификация в ASP.NET Core — это набор именованных **схем**, каждая из которых состоит из имени, handler'а и options. `UseAuthentication()` вызывает handler схемы по умолчанию и заполняет `HttpContext.User` объектом `ClaimsPrincipal`. Дальше уже [[Авторизация: роли, политики, claims]] решает, пускать ли этого пользователя к эндпоинту. Схем в приложении может быть несколько одновременно (cookie для MVC + Bearer для API), и выбор нужной — осознанное решение, а не дефолт.

## Зачем это нужно

До ASP.NET Core аутентификация в ASP.NET была прибита к `IPrincipal`, `HttpContext.User` и модулям IIS: `FormsAuthentication`, `WindowsAuthentication`, membership-провайдеры. Добавить второй способ входа означало лезть в `web.config` и надеяться, что модули не подерутся.

ASP.NET Core перевернул модель: аутентификация — это **сервис в DI + middleware**, а конкретные способы входа — плагины («схемы»), которые регистрируются рядом и не знают друг о друге. Отсюда практическая выгода:

- один процесс может обслуживать браузерный MVC на cookie и мобильное приложение на JWT;
- добавить вход через Google — это одна строка `.AddGoogle(...)`, а не переписывание пайплайна;
- тестировать можно, подсунув фейковую схему, а не поднимая identity-провайдер;
- всё, что аутентификация умеет отдать наружу, унифицировано в `ClaimsPrincipal` — код бизнес-логики не знает, откуда пришёл пользователь.

## Аутентификация vs авторизация

Это два разных вопроса, и путают их постоянно.

| | Аутентификация (authentication, authn) | Авторизация (authorization, authz) |
|---|---|---|
| Вопрос | Кто ты? | Что тебе можно? |
| Результат | `ClaimsPrincipal` в `HttpContext.User` | «да» / «нет» для конкретного эндпоинта или ресурса |
| Когда | В начале конвейера, `UseAuthentication()` | После, `UseAuthorization()` и/или явный вызов |
| HTTP-код при неудаче | **401 Unauthorized** | **403 Forbidden** |
| API | `IAuthenticationService`, схемы, handler'ы | `IAuthorizationService`, политики, requirements |

Почему коды путают: имя `401 Unauthorized` исторически неудачное — по смыслу это «Unauthenticated». Правило простое:

- **401** — «я не знаю, кто ты». Клиент должен предъявить (или обновить) credentials. Ответ по спецификации должен содержать `WWW-Authenticate`.
- **403** — «я знаю, кто ты, и тебе нельзя». Повторять запрос с теми же credentials бессмысленно.

В финтехе разница не косметическая: SPA на 401 запускает refresh-токен и повторяет запрос, а на 403 показывает «нет доступа». Если сервер путает коды, клиент попадает в цикл бесконечных refresh.

Отдельный случай — когда сам факт существования ресурса секретен («есть ли счёт с таким номером»). Тогда правильный ответ — **404**, а не 403. Подробнее в [[Авторизация: роли, политики, claims]].

## Как устроена аутентификация: схемы и handler'ы

Схема (scheme) = **имя (строка) + тип handler'а + объект options**.

```csharp
builder.Services
    .AddAuthentication(CookieAuthenticationDefaults.AuthenticationScheme) // "Cookies" — дефолт
    .AddCookie(CookieAuthenticationDefaults.AuthenticationScheme, options =>
    {
        options.LoginPath = "/account/login";
    });
```

Что здесь происходит внутри:

1. `AddAuthentication(defaultScheme)` регистрирует `IAuthenticationService` (реализация — `AuthenticationService`), `IAuthenticationSchemeProvider`, `IAuthenticationHandlerProvider` и настраивает `AuthenticationOptions.DefaultScheme`.
2. `AddCookie(name, configure)` кладёт в `AuthenticationOptions.SchemeMap` запись `AuthenticationScheme(name, displayName, handlerType)` и настраивает named options `CookieAuthenticationOptions` под этим же именем. Named options — обычный [[Options pattern и конфигурация сервисов]]: имя схемы = имя options.
3. Handler'ы регистрируются как **transient** и создаются на запрос. Поэтому в handler'е можно спокойно держать состояние текущего запроса, но нельзя кешировать его в статике.

Базовый класс handler'а:

```csharp
public abstract class AuthenticationHandler<TOptions> :
    IAuthenticationHandler where TOptions : AuthenticationSchemeOptions
{
    // Единственный обязательный метод: разобрать запрос и вернуть результат
    protected abstract Task<AuthenticateResult> HandleAuthenticateAsync();

    // Необязательные: что делать при Challenge / Forbid
    protected virtual Task HandleChallengeAsync(AuthenticationProperties properties);
    protected virtual Task HandleForbiddenAsync(AuthenticationProperties properties);
}
```

`HandleAuthenticateAsync` возвращает один из трёх исходов, и разница между ними важна:

| Результат | Смысл | Типичный случай |
|---|---|---|
| `AuthenticateResult.Success(ticket)` | Пользователь опознан | валидный токен/cookie |
| `AuthenticateResult.NoResult()` | Данных этой схемы в запросе нет | нет заголовка `Authorization` |
| `AuthenticateResult.Fail(reason)` | Данные есть, но битые | истёкшая подпись, неверный ключ |

Путать `NoResult` и `Fail` — классическая ошибка своего handler'а. `NoResult` означает «не моё, пусть решают дальше», `Fail` попадёт в логи и метрики как ошибка аутентификации.

### Пять операций

Всё взаимодействие с аутентификацией сводится к пяти операциям `IAuthenticationService`. У каждой — своя схема по умолчанию, и это источник половины загадочных багов.

| Операция | Что делает | Схема по умолчанию |
|---|---|---|
| `AuthenticateAsync` | Разобрать запрос → `ClaimsPrincipal` | `DefaultAuthenticateScheme` → `DefaultScheme` |
| `ChallengeAsync` | «Представься»: 401 или редирект на логин | `DefaultChallengeScheme` → `DefaultScheme` |
| `ForbidAsync` | «Тебе нельзя»: 403 или страница отказа | `DefaultForbidScheme` → `DefaultChallengeScheme` → `DefaultScheme` |
| `SignInAsync` | Выдать удостоверение (записать cookie) | `DefaultSignInScheme` → `DefaultScheme` |
| `SignOutAsync` | Отозвать удостоверение (удалить cookie) | `DefaultSignOutScheme` → `DefaultSignInScheme` → `DefaultScheme` |

`SignIn`/`SignOut` имеют смысл только для схем, которые умеют хранить состояние на клиенте (cookie). Bearer-схема на `SignInAsync` бросит исключение: JWT выдаёт не она, а ваш эндпоинт `/login`. См. [[JWT и Bearer-аутентификация]].

### Механика в конвейере

```
Запрос
  │
  ├─ UseRouting()            ← определён endpoint и его метаданные
  │
  ├─ UseAuthentication()     ← вызывает AuthenticateAsync(DefaultAuthenticateScheme),
  │                            кладёт результат в HttpContext.User
  ├─ UseAuthorization()      ← читает HttpContext.User + метаданные эндпоинта
  │                            (IAuthorizeData), при отказе → Challenge (401) / Forbid (403)
  │
  └─ эндпоинт                ← здесь User уже заполнен
```

```csharp
var app = builder.Build();

app.UseRouting();          // сначала знаем, КУДА идёт запрос
app.UseAuthentication();   // потом КТО пришёл
app.UseAuthorization();    // потом МОЖНО ли
app.MapControllers();
```

Ключевой момент: `UseAuthentication()` **не отклоняет** анонимный запрос. Он просто заполняет `HttpContext.User` — либо реальным принципалом, либо пустым (`ClaimsPrincipal` с неаутентифицированной идентичностью). Отклоняет только авторизация. Поэтому приложение без `UseAuthorization()` и без `[Authorize]` будет с радостью пускать всех, хотя аутентификация «настроена».

Порядок из примера обязателен. Почему именно так:

- **после `UseRouting`** — потому что авторизации нужны метаданные эндпоинта, а cookie-схеме в .NET 10 нужно знать, API это или нет (см. ниже);
- **до `UseAuthorization`** — иначе авторизация проверяет пустого пользователя и всё падает в 401;
- **до эндпоинтов** — очевидно.

Подробнее про порядок middleware — [[Middleware и конвейер обработки запроса]] и [[Роутинг]].

## ClaimsPrincipal, ClaimsIdentity, Claim

`HttpContext.User` — это `ClaimsPrincipal`. Модель трёхуровневая, и её часто представляют плоской, что приводит к ошибкам.

```
ClaimsPrincipal (User)
│
├── Identities: ICollection<ClaimsIdentity>
│   │
│   ├── ClaimsIdentity #1  (AuthenticationType = "Cookies", IsAuthenticated = true)
│   │   ├── Claim { Type = ClaimTypes.NameIdentifier, Value = "user-42" }
│   │   ├── Claim { Type = ClaimTypes.Name,           Value = "rim" }
│   │   ├── Claim { Type = ClaimTypes.Role,           Value = "operator" }
│   │   └── Claim { Type = "tenant",                  Value = "uz-01" }
│   │
│   └── ClaimsIdentity #2  (AuthenticationType = "ApiKey", IsAuthenticated = true)
│       └── Claim { Type = "partner_id", Value = "acme" }
│
└── Identity => Identities.First()   // "основная" идентичность
```

Что важно знать:

- **Принципал = человек, идентичность = один способ его опознать.** Обычно идентичность одна, но при нескольких схемах или при внешнем логине их бывает больше.
- `ClaimsPrincipal.Claims` возвращает claims **всех** идентичностей, а `FindFirst` ищет по всем. Поэтому «лишняя» идентичность может незаметно подарить пользователю роль.
- `ClaimsIdentity.IsAuthenticated` — это `!string.IsNullOrEmpty(AuthenticationType)`. Не флаг, а следствие. Если создать `new ClaimsIdentity(claims)` без указания authenticationType, `IsAuthenticated` будет `false`, и `[Authorize]` отклонит запрос, хотя claims на месте. Это самая частая ошибка в своих handler'ах.
- `Claim` — это тройка `Type` / `Value` (+ `Issuer`, `OriginalIssuer`, `ValueType`, `Subject`, `Properties`). Value **всегда строка**: число, дату, bool парсите сами.
- `ClaimTypes.*` — константы с длинными URI из времён WS-Federation: `ClaimTypes.NameIdentifier` = `"http://schemas.xmlsoap.org/ws/2005/05/identity/claims/nameidentifier"`, `ClaimTypes.Role` = `"http://schemas.microsoft.com/ws/2008/06/identity/claims/role"`. Они попадают в cookie в таком виде — отсюда раздутый размер тикета. В JWT принято короткое: `sub`, `role`, `name`.
- `User.IsInRole("admin")` не магия: он ищет claim типа `identity.RoleClaimType` (по умолчанию `ClaimTypes.Role`) со значением `"admin"`. Меняете тип role-claim'а — `IsInRole` и `[Authorize(Roles = ...)]` перестают работать молча.

```csharp
// Читаем claims правильно
var userId = User.FindFirstValue(ClaimTypes.NameIdentifier);   // string? — может быть null
var tenant = User.FindFirstValue("tenant");
var isOperator = User.IsInRole("operator");

// Множественные claims одного типа — норма (роли, скоупы)
var roles = User.FindAll(ClaimTypes.Role).Select(c => c.Value).ToArray();

// Не так: User.Identity!.Name — Name зависит от NameClaimType и часто null
```

## Cookie или токен

Решение принимается один раз и потом дорого меняется. Сравнение по существу:

| Критерий | Cookie-аутентификация | Bearer-токен (JWT) |
|---|---|---|
| Состояние | Тикет самодостаточен, но привязан к домену и ключам Data Protection | Токен самодостаточен, валидируется по подписи |
| Масштабирование | Нужен общий ключ Data Protection на все инстансы | Общий публичный ключ/JWKS, инстансы независимы |
| Отправка | Браузер прикрепляет **автоматически** | Клиент явно ставит `Authorization: Bearer ...` |
| CSRF | **Уязвимо** — нужен antiforgery + `SameSite` | Не уязвимо (браузер не отправляет сам) |
| XSS | Меньше рискa: `HttpOnly` скрывает от JS | Токен обычно в JS-памяти/localStorage — при XSS утекает |
| Отзыв | Легко: `SignOutAsync`, `ITicketStore`, `OnValidatePrincipal` | Тяжело: до истечения `exp` токен валиден. Нужен blacklist или короткий TTL + refresh |
| Мобильные/десктоп клиенты | Неудобно (cookie-контейнер, домены) | Естественно |
| Кросс-домен / сторонний API | Ломается на `SameSite`, нужен CORS с credentials | Работает |
| Размер | 1–4 КБ на **каждый** запрос, лимит браузера ~4 КБ на cookie | 0.5–2 КБ в заголовке |
| TTL | `ExpireTimeSpan` + `SlidingExpiration` — продлевается сам | Фиксированный `exp`, продление через refresh-токен |
| Где живёт логика валидации | Расшифровка тикета Data Protection | Проверка подписи, `iss`, `aud`, `exp` |

Практический вывод:

- **Браузерное same-site приложение** (MVC, Razor Pages, SPA на том же домене) → cookie. `HttpOnly` + `SameSite=Lax/Strict` + antiforgery закрывают и XSS-кражу, и CSRF. Мгновенный отзыв сессии — бесплатно.
- **Публичный API, мобильное приложение, SPA на другом домене, межсервисные вызовы** → bearer-токены.
- **Гибрид** (одно приложение отдаёт и HTML, и API) → две схемы + policy scheme, см. ниже.

Чего делать не надо: класть JWT в cookie «чтобы было удобно» — получите худшее из двух миров (CSRF вернулся, отзыв всё ещё невозможен). Про CSRF-часть — [[XSS, CSRF и защита от них]].

## Cookie-аутентификация

```csharp
builder.Services
    .AddAuthentication(CookieAuthenticationDefaults.AuthenticationScheme)
    .AddCookie(options =>
    {
        options.Cookie.Name = "__Host-app-auth";        // префикс __Host- : только HTTPS, без Domain
        options.Cookie.HttpOnly = true;                  // JS не видит cookie
        options.Cookie.SecurePolicy = CookieSecurePolicy.Always;  // только по HTTPS
        options.Cookie.SameSite = SameSiteMode.Lax;      // Strict ломает переход по внешним ссылкам
        options.Cookie.IsEssential = true;               // не вырезается политикой cookie-consent

        options.ExpireTimeSpan = TimeSpan.FromMinutes(30);
        options.SlidingExpiration = true;                // активность продлевает сессию
        options.LoginPath = "/account/login";
        options.LogoutPath = "/account/logout";
        options.AccessDeniedPath = "/account/denied";
        options.ReturnUrlParameter = "returnUrl";

        options.Events.OnValidatePrincipal = async context =>
        {
            // Вызывается на КАЖДЫЙ запрос: точка отзыва сессии
            var stamp = context.Principal?.FindFirstValue("security_stamp");
            var users = context.HttpContext.RequestServices.GetRequiredService<IUserStateChecker>();

            if (stamp is null || !await users.IsStampValidAsync(stamp))
            {
                context.RejectPrincipal();               // тикет считается невалидным
                await context.HttpContext.SignOutAsync(); // и cookie удаляется
            }
        };
    });
```

Вход и выход:

```csharp
app.MapPost("/account/login", async (LoginRequest req, HttpContext http, IUserService users) =>
{
    var user = await users.VerifyPasswordAsync(req.Login, req.Password);
    if (user is null)
        return Results.Unauthorized();   // 401, не 400: credentials не подошли

    var claims = new List<Claim>
    {
        new(ClaimTypes.NameIdentifier, user.Id.ToString()),
        new(ClaimTypes.Name, user.Login),
        new("security_stamp", user.SecurityStamp),
    };
    claims.AddRange(user.Roles.Select(r => new Claim(ClaimTypes.Role, r)));

    // ВАЖНО: authenticationType обязателен, иначе IsAuthenticated == false
    var identity = new ClaimsIdentity(claims, CookieAuthenticationDefaults.AuthenticationScheme);

    await http.SignInAsync(
        CookieAuthenticationDefaults.AuthenticationScheme,
        new ClaimsPrincipal(identity),
        new AuthenticationProperties
        {
            IsPersistent = req.RememberMe,               // cookie выживет закрытие браузера
            ExpiresUtc = DateTimeOffset.UtcNow.AddDays(req.RememberMe ? 14 : 0),
        });

    return Results.NoContent();
});

app.MapPost("/account/logout", async (HttpContext http) =>
{
    await http.SignOutAsync(CookieAuthenticationDefaults.AuthenticationScheme);
    return Results.NoContent();
});
```

Сам тикет — это claims, сериализованные и **зашифрованные Data Protection**. Отсюда два следствия для прода: при нескольких инстансах ключи должны быть общими (иначе после балансировки тикет не расшифруется и пользователя выкинет), и при пересоздании контейнера без персистентного хранилища ключей все сессии умрут. Подробно — [[Защита данных (Data Protection API)]].

Если тикет разрастается (много claims, длинные URI типов) — переносите его в серверное хранилище через `options.SessionStore` (`ITicketStore`), в cookie останется только идентификатор. Это уже серверная сессия со всеми плюсами (мгновенный отзыв) и минусами (нужно общее хранилище, обычно Redis).

## Новое в .NET 10: cookie-схема возвращает 401/403 вместо редиректа

Это изменение стоит знать наизусть — оно и полезное, и **breaking**.

**Как было.** `CookieAuthenticationHandler` на challenge всегда отвечал `302 Found` с `Location: /account/login?returnUrl=...`. Для браузерной навигации это правильно. Но SPA, который делает `fetch('/api/accounts')`, получал вот что: `fetch` прозрачно шёл по редиректу, сервер отдавал HTML страницы логина со статусом **200**, и клиентский код видел «успех» с невалидным JSON. Отличить «не авторизован» от «успех» было невозможно без хаков вроде проверки `Content-Type` или своего заголовка `X-Requested-With`.

**Как стало в ASP.NET Core 10.** Cookie-схема смотрит на метаданные эндпоинта. Если среди них есть маркерный интерфейс `IApiEndpointMetadata` — эндпоинт считается API-эндпоинтом, и вместо редиректа отдаётся честный **401** (на challenge) или **403** (на forbid).

Маркер добавляется автоматически для:

- контроллеров, помеченных `[ApiController]`;
- Minimal API эндпоинтов, возвращающих JSON / `TypedResults` (см. [[Minimal API]]);
- эндпоинтов [[SignalR]].

Обычные MVC-контроллеры и Razor Pages, отдающие HTML, метаданного маркера не получают и продолжают редиректить.

```csharp
// .NET 10: fetch к [ApiController]-эндпоинту без cookie → 401, а не 302 + HTML
[ApiController]
[Route("api/accounts")]
public sealed class AccountsController : ControllerBase
{
    [HttpGet, Authorize]
    public IActionResult Get() => Ok(new { balance = 1000m });
}
```

**Как вернуть старое поведение** (или сделать своё) — через события схемы:

```csharp
.AddCookie(options =>
{
    options.LoginPath = "/account/login";

    options.Events.OnRedirectToLogin = context =>
    {
        // Например: API отдаёт ProblemDetails, остальное — редирект
        if (context.Request.Path.StartsWithSegments("/api"))
        {
            context.Response.StatusCode = StatusCodes.Status401Unauthorized;
            return Task.CompletedTask;
        }
        context.Response.Redirect(context.RedirectUri);
        return Task.CompletedTask;
    };

    options.Events.OnRedirectToAccessDenied = context =>
    {
        context.Response.StatusCode = StatusCodes.Status403Forbidden;
        return Task.CompletedTask;
    };
})
```

**Что ломается при апгрейде.** Если ваш фронтенд (или интеграционный тест, или внешний партнёр) полагался на 302 → HTML → 200, после апгрейда он увидит 401. Это правильное поведение, но проверить надо: интеграционные тесты с `Assert` на `HttpStatusCode.Redirect` или `Found` покраснеют, а фронтовые перехватчики, ищущие редирект на `/login`, перестанут срабатывать. Обратно к 302 — только через `OnRedirectToLogin`. Остальные изменения релиза — в [[ASP.NET Core 10: что нового]].

## Несколько схем одновременно

Классический сценарий: одно приложение обслуживает и MVC-страницы (cookie), и API (JWT).

```csharp
builder.Services
    .AddAuthentication("smart")                // дефолт — policy scheme, см. ниже
    .AddJwtBearer(JwtBearerDefaults.AuthenticationScheme, options =>
    {
        options.Authority = builder.Configuration["Auth:Authority"];
        options.Audience = "accounts-api";
    })
    .AddCookie(CookieAuthenticationDefaults.AuthenticationScheme, options =>
    {
        options.LoginPath = "/account/login";
    })
    .AddPolicyScheme("smart", "JWT или cookie", options =>
    {
        // Выбор схемы на каждый запрос
        options.ForwardDefaultSelector = context =>
        {
            string? header = context.Request.Headers.Authorization;
            return header?.StartsWith("Bearer ", StringComparison.Ordinal) == true
                ? JwtBearerDefaults.AuthenticationScheme
                : CookieAuthenticationDefaults.AuthenticationScheme;
        };
    });
```

`AddPolicyScheme` создаёт «виртуальную» схему: у неё нет своего handler'а, она только **пересылает** операции другой схеме по результату `ForwardDefaultSelector`. Есть и точечные форварды: `ForwardAuthenticate`, `ForwardChallenge`, `ForwardForbid`, `ForwardSignIn`, `ForwardSignOut` — они объявлены прямо в `AuthenticationSchemeOptions`, то есть форвардить умеет любая схема.

Явный выбор схемы, когда пересылка не нужна:

```csharp
// В политике авторизации
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("ApiOnly", policy =>
    {
        policy.AddAuthenticationSchemes(JwtBearerDefaults.AuthenticationScheme);
        policy.RequireAuthenticatedUser();
    });
});

// В атрибуте — принимаются несколько схем через запятую, проверяются по очереди
[Authorize(AuthenticationSchemes = "Bearer,Cookies")]
public sealed class ReportsController : ControllerBase { }

// В Minimal API
app.MapGet("/api/me", (ClaimsPrincipal user) => user.FindFirstValue(ClaimTypes.NameIdentifier))
   .RequireAuthorization("ApiOnly");
```

Когда политика указывает `AuthenticationSchemes`, middleware авторизации **сам** вызывает `AuthenticateAsync` для этих схем и собирает результат — независимо от того, что положил в `User` глобальный `UseAuthentication()`.

## Ручная проверка и инспекция схем

Иногда нужно проверить дополнительную схему, не меняя `HttpContext.User`:

```csharp
app.MapGet("/whoami", async (HttpContext http) =>
{
    // Явно спрашиваем конкретную схему
    var result = await http.AuthenticateAsync(JwtBearerDefaults.AuthenticationScheme);

    if (!result.Succeeded)
        return Results.Unauthorized();

    return Results.Ok(new
    {
        scheme = result.Ticket!.AuthenticationScheme,
        sub = result.Principal!.FindFirstValue(ClaimTypes.NameIdentifier),
        // AuthenticationProperties хранит служебные данные тикета
        expires = result.Properties?.ExpiresUtc,
    });
});

// Диагностика: какие схемы вообще зарегистрированы
app.MapGet("/debug/schemes", async (IAuthenticationSchemeProvider provider) =>
{
    var all = await provider.GetAllSchemesAsync();
    var defaultAuth = await provider.GetDefaultAuthenticateSchemeAsync();

    return Results.Ok(new
    {
        Default = defaultAuth?.Name,
        Schemes = all.Select(s => new { s.Name, s.DisplayName, Handler = s.HandlerType.Name }),
    });
}).RequireAuthorization("AdminOnly");   // такой эндпоинт нельзя оставлять публичным
```

`IAuthenticationSchemeProvider` умеет и добавлять схемы в рантайме (`AddScheme`) — это используется для мультитенантных сценариев, где у каждого тенанта свой OIDC-провайдер.

## Своя схема аутентификации

Свой handler оправдан, когда протокол нестандартный и готовой схемы нет:

- **API-key** для внутренних/партнёрских интеграций;
- **HMAC-подпись запроса** (партнёр подписывает тело + timestamp секретом) — типовой финтех-контракт с процессингом;
- mTLS-сертификат с нестандартным маппингом в claims;
- легаси-протокол внутреннего шлюза.

Свой handler **не нужен**, если задача решается стандартной схемой: не пишите свой JWT-парсер, не изобретайте OAuth. Про готовое — [[JWT и Bearer-аутентификация]] и [[OAuth 2.0 и OpenID Connect]].

```csharp
using System.Security.Claims;
using System.Security.Cryptography;
using System.Text;
using System.Text.Encodings.Web;
using Microsoft.AspNetCore.Authentication;
using Microsoft.Extensions.Options;

public sealed class ApiKeyOptions : AuthenticationSchemeOptions
{
    public string HeaderName { get; set; } = "X-Api-Key";
}

public sealed class ApiKeyHandler : AuthenticationHandler<ApiKeyOptions>
{
    public const string SchemeName = "ApiKey";

    private readonly IApiKeyStore _store;

    // .NET 8+: конструктор без ISystemClock (устаревшая перегрузка с клоком удалена из рекомендаций)
    public ApiKeyHandler(
        IOptionsMonitor<ApiKeyOptions> options,
        ILoggerFactory logger,
        UrlEncoder encoder,
        IApiKeyStore store)
        : base(options, logger, encoder)
    {
        _store = store;
    }

    protected override async Task<AuthenticateResult> HandleAuthenticateAsync()
    {
        // Заголовка нет — это не наш запрос. Именно NoResult, а не Fail:
        // иначе каждый анонимный запрос попадёт в логи как ошибка аутентификации.
        if (!Request.Headers.TryGetValue(Options.HeaderName, out var values))
            return AuthenticateResult.NoResult();

        var presented = values.ToString();
        if (string.IsNullOrEmpty(presented))
            return AuthenticateResult.Fail("Пустой API-ключ.");

        var candidates = await _store.GetActiveKeysAsync(Context.RequestAborted);

        // Константное по времени сравнение: обычное == даёт timing-oracle,
        // по которому ключ восстанавливается побайтово.
        var presentedBytes = Encoding.UTF8.GetBytes(presented);
        ApiKeyRecord? matched = null;

        foreach (var candidate in candidates)
        {
            var candidateBytes = Encoding.UTF8.GetBytes(candidate.Value);
            if (CryptographicOperations.FixedTimeEquals(presentedBytes, candidateBytes))
                matched = candidate;
        }

        if (matched is null)
            return AuthenticateResult.Fail("Неизвестный API-ключ.");

        var claims = new[]
        {
            new Claim(ClaimTypes.NameIdentifier, matched.PartnerId),
            new Claim("partner_id", matched.PartnerId),
            new Claim(ClaimTypes.Role, "partner"),
        };

        // Scheme.Name как authenticationType — иначе IsAuthenticated == false
        var identity = new ClaimsIdentity(claims, Scheme.Name);
        var ticket = new AuthenticationTicket(new ClaimsPrincipal(identity), Scheme.Name);

        return AuthenticateResult.Success(ticket);
    }

    // Без переопределения ответ был бы 401 без WWW-Authenticate
    protected override Task HandleChallengeAsync(AuthenticationProperties properties)
    {
        Response.StatusCode = StatusCodes.Status401Unauthorized;
        Response.Headers.WWWAuthenticate = $"{SchemeName} realm=\"partner-api\"";
        return Task.CompletedTask;
    }
}
```

Регистрация:

```csharp
builder.Services.AddSingleton<IApiKeyStore, CachedApiKeyStore>();

builder.Services
    .AddAuthentication(ApiKeyHandler.SchemeName)
    .AddScheme<ApiKeyOptions, ApiKeyHandler>(
        ApiKeyHandler.SchemeName,
        options => options.HeaderName = "X-Api-Key");
```

Обратите внимание: перебор всех кандидатов без раннего `break` — намеренно, чтобы время ответа не зависело от позиции найденного ключа. И сами ключи в хранилище должны лежать как хеши, а не в открытом виде — тогда сравнивать надо хеш предъявленного (см. [[Хранение паролей и хеширование]]).

> [!warning] Подводные камни
> **1. Порядок middleware.** `UseAuthentication()` после `UseAuthorization()` — и авторизация всегда видит пустого `User`, то есть весь трафик получает 401. Оба должны идти после `UseRouting()`: авторизации нужны метаданные эндпоинта, а cookie-схеме в .NET 10 — маркер `IApiEndpointMetadata`. При `UseAuthorization()` до `UseRouting()` метаданных ещё нет и route values недоступны.
>
> **2. `[Authorize]` без `UseAuthentication()`.** Приложение стартует без ошибок. На первом же защищённом запросе `UseAuthorization` попробует сделать challenge, схем нет — `InvalidOperationException` про отсутствующий authenticationScheme. Ошибка появляется только в рантайме и только на защищённом эндпоинте, поэтому легко доехать до прода.
>
> **3. `HttpContext.User` пустой в раннем middleware.** Логирующий или мультитенантный middleware, зарегистрированный до `UseAuthentication()`, увидит `User.Identity!.IsAuthenticated == false` **всегда**. Классика: «в логах все запросы анонимные». Лечится переносом middleware после `UseAuthentication()` или явным `await context.AuthenticateAsync(scheme)`.
>
> **4. Забытый `DefaultChallengeScheme`.** При нескольких схемах `AddAuthentication()` без аргумента и без явных дефолтов даёт `InvalidOperationException` на первом challenge/`SignInAsync`. При одной схеме дефолт выставляется автоматически, поэтому баг «появляется» ровно в момент добавления второй схемы.
>
> **5. Молчаливый выбор дефолтной схемы.** `[Authorize]` без `AuthenticationSchemes` использует дефолт. Если дефолт — cookie, а клиент присылает Bearer, вы получите 401 «без причины»: cookie-handler просто не нашёл своих данных и вернул `NoResult`. Явно указывайте схему в политике или ставьте policy scheme.
>
> **6. `NoResult` vs `Fail` в своём handler'е.** `Fail` на отсутствующие credentials засоряет логи и метрику `challenges`, а при цепочке схем ломает fallback. «Моих данных нет» — это `NoResult`.
>
> **7. `ClaimsIdentity` без authenticationType.** `new ClaimsIdentity(claims)` даёт `IsAuthenticated == false`. `[Authorize]` отклонит запрос, а claims при этом будут видны в `User.Claims` — отладка превращается в детектив.
>
> **8. `RoleClaimType` и роли из токена.** `IsInRole` и `RequireRole` смотрят на `identity.RoleClaimType`. У JWT-схемы маппинг короткого `role` в `ClaimTypes.Role` зависит от настроек `TokenValidationParameters.RoleClaimType` и `MapInboundClaims`. Настроили не то — роли молча перестают работать, никаких ошибок нет.

> [!example] Как делают в бою
> **Одно приложение — две схемы.** В типовом финтех-монолите: `/api/**` на Bearer (мобильный клиент и партнёры), админка на cookie. Policy scheme со `ForwardDefaultSelector` по наличию `Authorization: Bearer` — самый дешёвый способ, потому что не требует ни разделения приложений, ни двух хостов. Альтернатива без policy scheme — явные `AuthenticationSchemes` в двух политиках; она честнее (нет неявного выбора), но её приходится помнить в каждой новой политике.
>
> **Cookie для админки, а не токен.** Причина одна: **мгновенный отзыв**. Уволили сотрудника — `security_stamp` меняется, `OnValidatePrincipal` на следующем же запросе выкидывает сессию. С JWT пришлось бы держать blacklist или TTL в минуту. Для админ-панели, где ставка — доступ к деньгам, это решающий аргумент.
>
> **Ключи Data Protection в общем хранилище.** Первое, что ломается при переезде в Kubernetes: у каждого пода свои ключи, балансировщик кидает запрос на другой под, тикет не расшифровывается, пользователь «случайно разлогинивается». Ключи — в Redis, БД или Key Vault, с отдельным сроком ротации.
>
> **Апгрейд на .NET 10 через фича-флаг.** Изменение 302 → 401 обкатывают, оставляя `OnRedirectToLogin` со старым поведением за конфигом: сначала деплой бэкенда, потом фронтенд учится понимать 401, потом флаг убирают. Иначе одновременный деплой двух компонентов — и любой откат ломает вход.
>
> **`WWW-Authenticate` заполняют всерьёз.** Для партнёрских API это часть контракта: партнёр по заголовку понимает, какой механизм ожидается. Пустой 401 без заголовка формально нарушает HTTP и мешает автоматическим клиентам.
>
> **Аудит входов отдельно от метрик.** Метрики отвечают «сколько», аудит — «кто, откуда, когда, чем закончилось». Событие входа/выхода/отказа пишут структурным логом с `sub`, IP, user-agent и идентификатором схемы: [[Аудит и логирование безопасности]].

## Вопросы с собеседований

> [!question]- Чем отличаются 401 и 403, и кто их возвращает в ASP.NET Core?
> 401 Unauthorized означает «личность не установлена» — это результат операции **Challenge**: клиент должен предъявить или обновить credentials, и ответ должен содержать заголовок `WWW-Authenticate`. 403 Forbidden означает «личность установлена, но прав не хватает» — результат операции **Forbid**, повторять запрос с теми же credentials бессмысленно. Возвращает их не аутентификация, а middleware авторизации: если `HttpContext.User` не аутентифицирован — вызывается `ChallengeAsync` (401), если аутентифицирован, но политика не выполнена — `ForbidAsync` (403). Конкретный ответ формирует handler схемы: cookie-схема исторически отвечала редиректом вместо 401, а в .NET 10 для API-эндпоинтов отдаёт настоящий 401.

> [!question]- Что такое схема аутентификации и зачем их может быть несколько?
> Схема — это тройка: имя-строка, тип handler'а (`AuthenticationHandler<TOptions>`) и named options под тем же именем. `AddAuthentication` регистрирует инфраструктуру и дефолты, `AddCookie`/`AddJwtBearer`/`AddScheme` добавляют записи в `SchemeMap`. Несколько схем нужны, когда одно приложение обслуживает разные типы клиентов: браузер на cookie и мобильное приложение на Bearer; или когда есть внешние логины (Google, OIDC), которые сами по себе не создают сессию, а только передают identity в cookie-схему через `DefaultSignInScheme`. Выбирать схему можно явно (`AuthenticationSchemes` в политике или атрибуте) или через policy scheme с `ForwardDefaultSelector`.

> [!question]- Что делает `UseAuthentication()` и почему он не отклоняет анонимные запросы?
> `UseAuthentication()` вызывает `AuthenticateAsync` для схемы по умолчанию и, если та вернула `Success`, кладёт принципала в `HttpContext.User`. Если схема вернула `NoResult` или `Fail`, `User` остаётся неаутентифицированным `ClaimsPrincipal`, но запрос **продолжает** идти по конвейеру. Так и должно быть: аутентификация отвечает на вопрос «кто», а решение «пускать или нет» принимает авторизация, которая знает метаданные конкретного эндпоинта, — на публичный `/health` анонимного пускать надо. Отсюда следует, что приложение без `UseAuthorization()` и без атрибутов авторизации остаётся полностью открытым, несмотря на настроенную аутентификацию.

> [!question]- Почему `[Authorize]` не пускает пользователя, хотя claims в принципале есть?
> Почти всегда потому, что `ClaimsIdentity` создан без `authenticationType`: `new ClaimsIdentity(claims)` вместо `new ClaimsIdentity(claims, "MyScheme")`. Свойство `IsAuthenticated` вычисляется как `!string.IsNullOrEmpty(AuthenticationType)`, а `DefaultPolicy` требует `RequireAuthenticatedUser()`, поэтому запрос отклоняется. Второй по частоте вариант — не совпал тип role-claim'а: `RequireRole`/`IsInRole` ищут claim типа `identity.RoleClaimType`, и если токен принёс короткий `role`, а `RoleClaimType` остался `ClaimTypes.Role`, роли не находятся. Оба случая не дают никакой ошибки — только 401/403.

> [!question]- Cookie или JWT для нового SPA — как выбирать?
> Если SPA и API живут на одном origin, cookie обычно лучше: `HttpOnly` защищает от кражи через XSS, отзыв сессии мгновенный через `OnValidatePrincipal`, обновление TTL бесплатное через `SlidingExpiration`. Платить придётся защитой от CSRF (antiforgery + `SameSite`) и общими ключами Data Protection между инстансами. JWT выбирают, когда клиентов много и они разные (мобильные, партнёры, другие сервисы), origin'ы разные или нужна stateless-валидация без общего секрета для сессий. Главный минус JWT — невозможность отзыва до `exp`: приходится делать короткий access-токен плюс refresh, а это уже состояние на сервере, то есть часть выигрыша теряется. Класть JWT в cookie — плохой компромисс: возвращается CSRF, а отзыв так и не появляется.

> [!question]- В чём смысл изменения cookie-аутентификации в .NET 10 и как его откатить?
> Раньше challenge cookie-схемы всегда давал `302` на `LoginPath`. Для `fetch` из SPA это означало прозрачный переход по редиректу и ответ `200` с HTML страницы логина — клиент не мог отличить «не авторизован» от «успех». В ASP.NET Core 10 схема проверяет метаданные эндпоинта на маркерный интерфейс `IApiEndpointMetadata` (он ставится для `[ApiController]`, Minimal API с JSON/`TypedResults`, SignalR) и для таких эндпоинтов отдаёт 401 на challenge и 403 на forbid вместо редиректа. Это breaking change: тесты и фронтовые перехватчики, ожидавшие 302, перестанут работать. Откатывается событиями `OnRedirectToLogin` и `OnRedirectToAccessDenied` — в них можно вернуть `context.Response.Redirect(context.RedirectUri)` или реализовать своё правило по пути запроса.

## Задачы

### Задача 1. Policy scheme для API и MVC в одном приложении

Приложение отдаёт админку (Razor/MVC, вход по паролю, cookie) и API под `/api` (мобильный клиент, JWT). Требуется: браузер, зашедший на админку без сессии, попадает на `/account/login`; клиент API без токена получает 401 с корректным `WWW-Authenticate`; в коде эндпоинтов не должно быть упоминаний схем.

> [!success]- Решение
> ```csharp
> const string SmartScheme = "smart";
>
> builder.Services
>     .AddAuthentication(SmartScheme)
>     .AddJwtBearer(JwtBearerDefaults.AuthenticationScheme, o =>
>     {
>         o.Authority = builder.Configuration["Auth:Authority"];
>         o.Audience = "admin-api";
>     })
>     .AddCookie(CookieAuthenticationDefaults.AuthenticationScheme, o =>
>     {
>         o.LoginPath = "/account/login";
>         o.AccessDeniedPath = "/account/denied";
>         o.Cookie.HttpOnly = true;
>         o.Cookie.SecurePolicy = CookieSecurePolicy.Always;
>         o.Cookie.SameSite = SameSiteMode.Lax;
>     })
>     .AddPolicyScheme(SmartScheme, "Bearer для API, cookie для UI", o =>
>     {
>         o.ForwardDefaultSelector = context =>
>         {
>             // Решаем по запросу, а не по конфигурации: один хост, два типа клиентов
>             string? auth = context.Request.Headers.Authorization;
>             if (auth?.StartsWith("Bearer ", StringComparison.Ordinal) == true)
>                 return JwtBearerDefaults.AuthenticationScheme;
>
>             return context.Request.Path.StartsWithSegments("/api")
>                 ? JwtBearerDefaults.AuthenticationScheme
>                 : CookieAuthenticationDefaults.AuthenticationScheme;
>         };
>     });
>
> var app = builder.Build();
> app.UseRouting();
> app.UseAuthentication();
> app.UseAuthorization();
> app.MapControllers();   // и [ApiController], и обычные MVC-контроллеры
> ```
> Почему так. `AddPolicyScheme` не имеет своего handler'а — он только форвардит все пять операций выбранной схеме, поэтому и `AuthenticateAsync`, и `ChallengeAsync` попадают куда надо. Проверка `Path` нужна дополнительно к заголовку: запрос к `/api` **без** токена тоже должен уйти в Bearer-схему, иначе challenge сделает cookie-схема и вернёт редирект. В .NET 10 для `[ApiController]` cookie-схема отдала бы 401 и сама, но полагаться на это не стоит — маркер ставится не для всех форм эндпоинтов, а логика выбора должна быть явной.

### Задача 2. Своя схема ApiKey для партнёрской интеграции

Партнёры зовут `/partner/**`, предъявляя `X-Api-Key`. Ключи хранятся в БД как SHA-256 хеши и кешируются. Требования: сравнение устойчиво к timing-атаке, отсутствие заголовка не считается ошибкой, партнёр получает claim `partner_id`, эндпоинты защищены политикой, а `/partner/ping` доступен без ключа.

> [!success]- Решение
> ```csharp
> public sealed class ApiKeyOptions : AuthenticationSchemeOptions
> {
>     public string HeaderName { get; set; } = "X-Api-Key";
> }
>
> public sealed class ApiKeyHandler(
>     IOptionsMonitor<ApiKeyOptions> options,
>     ILoggerFactory logger,
>     UrlEncoder encoder,
>     IApiKeyStore store) : AuthenticationHandler<ApiKeyOptions>(options, logger, encoder)
> {
>     public const string SchemeName = "ApiKey";
>
>     protected override async Task<AuthenticateResult> HandleAuthenticateAsync()
>     {
>         if (!Request.Headers.TryGetValue(Options.HeaderName, out var raw) ||
>             string.IsNullOrEmpty(raw.ToString()))
>         {
>             return AuthenticateResult.NoResult();   // не наш запрос
>         }
>
>         // Сравниваем хеши: в БД открытых ключей нет
>         var presentedHash = SHA256.HashData(Encoding.UTF8.GetBytes(raw.ToString()));
>
>         PartnerKey? matched = null;
>         foreach (var key in await store.GetActiveAsync(Context.RequestAborted))
>         {
>             // Без break: время ответа не должно зависеть от позиции совпадения
>             if (CryptographicOperations.FixedTimeEquals(presentedHash, key.Sha256))
>                 matched = key;
>         }
>
>         if (matched is null)
>             return AuthenticateResult.Fail("Неизвестный API-ключ.");
>
>         var identity = new ClaimsIdentity(
>             [
>                 new Claim(ClaimTypes.NameIdentifier, matched.PartnerId),
>                 new Claim("partner_id", matched.PartnerId),
>             ],
>             Scheme.Name);   // без этого IsAuthenticated == false
>
>         return AuthenticateResult.Success(
>             new AuthenticationTicket(new ClaimsPrincipal(identity), Scheme.Name));
>     }
>
>     protected override Task HandleChallengeAsync(AuthenticationProperties properties)
>     {
>         Response.StatusCode = StatusCodes.Status401Unauthorized;
>         Response.Headers.WWWAuthenticate = $"{SchemeName} realm=\"partner-api\"";
>         return Task.CompletedTask;
>     }
> }
> ```
> ```csharp
> builder.Services.AddAuthentication()
>     .AddScheme<ApiKeyOptions, ApiKeyHandler>(ApiKeyHandler.SchemeName, _ => { });
>
> builder.Services.AddAuthorization(o => o.AddPolicy("Partner", p =>
> {
>     p.AddAuthenticationSchemes(ApiKeyHandler.SchemeName);
>     p.RequireAuthenticatedUser();
>     p.RequireClaim("partner_id");
> }));
>
> var partners = app.MapGroup("/partner").RequireAuthorization("Partner");
> partners.MapGet("/ping", () => Results.Ok("pong")).AllowAnonymous();

> Почему так. `FixedTimeEquals` над хешами фиксированной длины закрывает и timing-oracle, и утечку длины ключа. Политика с явным `AddAuthenticationSchemes` не зависит от того, какая схема дефолтная, — партнёрская группа изолирована от остального приложения. `AllowAnonymous()` на `/partner/ping` переопределяет требование группы, что удобно для health-проверок со стороны партнёра.

### Задача 3. Мгновенный отзыв сессии в админке

В админке используется cookie-схема с `ExpireTimeSpan = 30 минут`. Нужно: после блокировки сотрудника его активная сессия завершается на следующем же запросе, но при этом БД не опрашивается на каждый запрос каждого пользователя.

> [!success]- Решение
> ```csharp
> .AddCookie(o =>
> {
>     o.ExpireTimeSpan = TimeSpan.FromMinutes(30);
>     o.SlidingExpiration = true;
>
>     o.Events.OnValidatePrincipal = async context =>
>     {
>         // Проверяем не чаще раза в минуту: IssuedUtc обновляется при перевыдаче тикета
>         var issued = context.Properties.IssuedUtc;
>         if (issued is not null && DateTimeOffset.UtcNow - issued < TimeSpan.FromMinutes(1))
>             return;
>
>         var userId = context.Principal?.FindFirstValue(ClaimTypes.NameIdentifier);
>         var stamp = context.Principal?.FindFirstValue("security_stamp");
>
>         var checker = context.HttpContext.RequestServices
>             .GetRequiredService<IUserStateChecker>();
>
>         if (userId is null || stamp is null ||
>             !await checker.IsActiveAsync(userId, stamp, context.HttpContext.RequestAborted))
>         {
>             context.RejectPrincipal();
>             await context.HttpContext.SignOutAsync(
>                 CookieAuthenticationDefaults.AuthenticationScheme);
>             return;
>         }
>
>         // Тикет валиден — просим перевыдать его, чтобы обновился IssuedUtc
>         context.ShouldRenew = true;
>     };
> });
> ```
> Почему так. `OnValidatePrincipal` — единственная точка, вызываемая на каждый запрос до того, как принципал попадёт в `HttpContext.User`, поэтому отзыв здесь честный, а не «когда-нибудь при следующем логине». Дросселирование по `IssuedUtc` + `ShouldRenew` даёт компромисс: задержка отзыва не больше минуты, а нагрузка на БД — один запрос в минуту на активную сессию. `RejectPrincipal()` без `SignOutAsync` оставил бы у клиента мёртвую cookie, которая заново отклонялась бы на каждом запросе. `IUserStateChecker` внутри стоит закрыть коротким кешем — тогда даже пиковая нагрузка не доходит до БД (см. [[Кеширование: Output, Response, HybridCache]]).

## Итог

- Аутентификация отвечает «кто ты» и заполняет `HttpContext.User`; авторизация отвечает «что тебе можно». 401 — не опознан (Challenge), 403 — опознан, но нельзя (Forbid).
- Схема = имя + handler + named options. Пять операций (`Authenticate`, `Challenge`, `Forbid`, `SignIn`, `SignOut`) у каждой имеют свою схему по умолчанию — при нескольких схемах дефолты надо задавать явно.
- Порядок `UseRouting` → `UseAuthentication` → `UseAuthorization` → эндпоинты обязателен. `UseAuthentication` сам никого не отклоняет.
- `ClaimsPrincipal` содержит несколько `ClaimsIdentity`, у каждой — набор `Claim`. `IsAuthenticated` истинно только при заданном `AuthenticationType`; `IsInRole` работает через `RoleClaimType`.
- Cookie — для браузерных same-site приложений (мгновенный отзыв, `HttpOnly`, но CSRF и общие ключи Data Protection). Bearer — для API, SPA на другом origin, мобильных и межсервисных вызовов (stateless, но отзыв до `exp` невозможен).
- .NET 10: cookie-схема возвращает 401/403 вместо 302 для эндпоинтов с метаданным `IApiEndpointMetadata` (`[ApiController]`, Minimal API с JSON/`TypedResults`, SignalR). Это breaking change; переопределяется через `OnRedirectToLogin` / `OnRedirectToAccessDenied`.
- Метрики meter'а `Microsoft.AspNetCore.Authentication` (`challenges`, `forbids`, `sign_ins`, `sign_outs`, `authenticate.duration`) — базовый инструмент детекта проблем с входом и попыток перебора.
- Свой `AuthenticationHandler<TOptions>` оправдан для API-key, HMAC-подписи и легаси-протоколов; для JWT и OAuth используйте готовые схемы. `NoResult` для «не моё», `Fail` только для битых данных, сравнение секретов — `CryptographicOperations.FixedTimeEquals`.
