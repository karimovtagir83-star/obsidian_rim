# Статические члены, классы и конструкторы

> [!abstract] Коротко
> Статический член принадлежит типу, а не экземпляру: он существует в одном экземпляре на тип (а для дженериков — на каждую конкретизацию отдельно) и живёт столько же, сколько загруженный `AssemblyLoadContext`. Статический конструктор (`.cctor`, он же type initializer) рантайм вызывает ровно один раз и потокобезопасно — но момент вызова зависит от флага `beforefieldinit`, который компилятор ставит автоматически. Отсюда растут все интересные баги: дедлоки при инициализации, «отравленный» тип после `TypeInitializationException` и невозможность подменить статику в тестах.

## Зачем это нужно

Не всё в программе имеет смысл как состояние конкретного объекта. `Math.PI` не принадлежит «экземпляру математики». `int.Parse` не требует существующего числа. Кэш метаданных, счётчик созданных объектов, пул переиспользуемых буферов, реестр конвертеров — это состояние *типа*, а не *объекта*.

Статика решает три задачи:

1. **Утилитарные функции без состояния** — `string.Join`, `File.ReadAllText`, `Enumerable.Range`.
2. **Разделяемое состояние на весь процесс** — кэши, счётчики, конфигурация, пулы.
3. **Фабрики и «именованные конструкторы»** — `TimeSpan.FromSeconds(5)`, `Result.Ok(value)`.

И создаёт одну большую проблему: глобальное изменяемое состояние. Об этом — в конце заметки.

## Что бывает статическим

```csharp
public class Counter
{
    // Статическое поле: одно на весь тип
    private static int _total;

    // Статическое свойство
    public static int Total => _total;

    // Статический метод
    public static void Reset() => _total = 0;

    // Статическое событие (осторожно: вечная подписка = утечка)
    public static event Action<int>? Incremented;

    // Обычное поле экземпляра
    private int _own;

    public void Increment()
    {
        _own++;
        _total++;                     // из экземплярного метода к статике — можно
        Incremented?.Invoke(_total);
    }
}
```

Правило доступа одностороннее: экземплярный код видит статику, статический код **не видит** `this` и экземплярные члены — их просто нет в контексте.

```csharp
public class Foo
{
    private int _x;
    public static void Bad() => Console.WriteLine(_x);
    // Ошибка CS0120: для нестатического поля требуется ссылка на объект
}
```

Статическими могут быть также: конструктор (ровно один, без модификаторов и параметров), класс целиком, локальная функция, лямбда, `using static`, а с C# 14 — extension-члены (см. [[Расширяющие методы и extension members]]).

## Где на самом деле живут статические поля

Частый вопрос собеседования: «статические поля лежат в куче или на стеке?» Ответ «в куче» неполный.

В CoreCLR статические поля **не хранятся внутри объектов** — их там физически нет. Они живут в структурах рантайма, привязанных к паре «тип + LoaderAllocator». LoaderAllocator принадлежит [[AssemblyLoadContext и загрузка плагинов]], в котором загружена сборка типа.

```
AssemblyLoadContext (Default)
└── LoaderAllocator
    ├── MethodTable для Counter
    │   └── статический блок Counter:
    │        ├── ссылочная статика  → managed-объект (виден GC как корень)
    │        └── примитивная статика → блок памяти вне GC-кучи
    └── MethodTable для Cache<int>
        └── свой отдельный статический блок
```

Практические следствия:

| Следствие | Что это значит |
|---|---|
| Ссылочная статика — GC-корень | Объект, на который ссылается `static`, не будет собран, пока жив ALC. Классический источник утечек, см. [[Слабые ссылки и утечки памяти в .NET]] |
| Статика живёт до выгрузки ALC | В обычном приложении — весь процесс. В плагинной архитектуре — до выгрузки collectible-контекста |
| Один и тот же тип в двух ALC — две разные статики | Плагин, загруженный дважды, получит два независимых кэша |
| Доступ к статике почти бесплатный | JIT после инициализации типа зашивает адрес блока прямо в машинный код |

### Статика в дженериках: копия на каждую конкретизацию

Это спрашивают на собеседованиях постоянно. `Foo<int>` и `Foo<string>` — **разные типы времени выполнения**, и статические поля у них разные.

```csharp
public class Box<T>
{
    public static int Count;
    public static readonly string TypeName = typeof(T).Name;
}

Box<int>.Count = 10;
Box<string>.Count = 20;
Box<object>.Count = 30;

Console.WriteLine(Box<int>.Count);     // Вывод: 10
Console.WriteLine(Box<string>.Count);  // Вывод: 20
Console.WriteLine(Box<object>.Count);  // Вывод: 30

Console.WriteLine(Box<string>.TypeName); // Вывод: String
Console.WriteLine(Box<object>.TypeName); // Вывод: Object
```

Тонкость, которая отделяет мидла от джуна: `Box<string>` и `Box<object>` **разделяют один и тот же JIT-скомпилированный машинный код** (canonical instantiation `Box<__Canon>` — все ссылочные типы делят реализацию), но **статические поля у них всё равно раздельные**. Рантайм на входе в метод достаёт нужный статический блок через скрытый параметр generic-контекста. Подробнее — [[Дженерики в CLR: как устроены]].

Этот механизм часто используют намеренно, как быстрый типизированный кэш:

```csharp
// Кэш "одно значение на тип" без словаря и без блокировок
internal static class TypeCache<T>
{
    // Инициализируется один раз на каждый T, потокобезопасно, дальше — чтение поля
    public static readonly PropertyInfo[] Properties =
        typeof(T).GetProperties(BindingFlags.Public | BindingFlags.Instance);
}

// Дешевле, чем ConcurrentDictionary<Type, PropertyInfo[]>: нет хеширования вообще
var props = TypeCache<Order>.Properties;
```

## `static class`

```csharp
public static class MathUtils
{
    public static double Hypotenuse(double a, double b) => Math.Sqrt(a * a + b * b);
}
```

В IL статический класс компилируется как `abstract sealed`:

```
.class public abstract auto ansi sealed beforefieldinit MathUtils
```

`abstract` — нельзя создать экземпляр, `sealed` — нельзя унаследовать. Отсюда все ограничения:

| Ограничение | Причина |
|---|---|
| Нет экземплярных членов и конструктора экземпляра | Экземпляра не бывает |
| Нельзя унаследовать и нельзя от чего-то наследоваться (кроме `object`) | `sealed` |
| Нельзя реализовать интерфейс | Интерфейс подразумевает экземпляр (кроме статических абстрактных членов интерфейса — но их реализует обычный тип) |
| Нельзя использовать как тип переменной, параметра, аргумента дженерика | Нет значений этого типа |
| Только контейнер для extension-методов (до C# 14 — обязательное требование) | Синтаксическое правило языка |

> [!info] С C# 14 появился новый синтаксис extension-членов (`extension(Type receiver) { ... }`), который позволяет объявлять extension-свойства, статические extension-члены и операторы. Контейнер по-прежнему статический класс. См. [[Расширяющие методы и extension members]].

## `const` против `static readonly`

Оба выглядят как «константа», но ведут себя принципиально по-разному.

| | `const` | `static readonly` |
|---|---|---|
| Когда вычисляется | На этапе компиляции | На этапе выполнения (в `.cctor`) |
| Где хранится | Значение вшито в IL **каждого** места использования | Поле в статическом блоке типа |
| Неявно | `static` | Только то, что написано |
| Допустимые типы | Примитивы, `string`, `enum`, `null`-литерал ссылочного типа | Любой тип |
| Можно вычислять | Только константное выражение | Любой код, включая чтение конфигурации |
| Виден в `switch`/атрибутах/дефолтах параметров | Да | Нет |
| Версионирование между сборками | **Ломается** | Безопасно |

### Проблема версионирования `const` — покажу сценарий

Сборка `Config.dll`:

```csharp
public static class Limits
{
    public const int MaxRetries = 3;          // вшивается в потребителей
    public static readonly int MaxBatch = 100; // читается через поле
}
```

Сборка `App.dll` использует их:

```csharp
Console.WriteLine(Limits.MaxRetries); // Вывод: 3
Console.WriteLine(Limits.MaxBatch);   // Вывод: 100
```

В IL `App.dll` это скомпилируется так:

```
ldc.i4.3                                   // MaxRetries — литерал 3, ссылки на Config.dll нет!
ldsfld int32 Limits::MaxBatch              // MaxBatch — реальное чтение поля
```

Теперь в `Config.dll` меняют значения на `5` и `200`, пересобирают **только** `Config.dll` и подкладывают её рядом (типичный хотфикс, замена одной dll, NuGet-обновление без пересборки, плагин):

```csharp
Console.WriteLine(Limits.MaxRetries); // Вывод: 3   ← СТАРОЕ значение!
Console.WriteLine(Limits.MaxBatch);   // Вывод: 200 ← новое
```

Приложение продолжает ретраить 3 раза, хотя в конфиге давно 5. Отладка такого — часы.

**Правило:** `const` — только для значений, которые не изменятся никогда по определению (`Math.PI`, `"application/json"`, `MaxValue` формата). Всё, что может поменяться в следующей версии, — `static readonly`. Внутри одной сборки разницы нет, проблема только на границе сборок. Подробнее про `readonly` — [[Переменные, const и readonly]].

## Статический конструктор (`.cctor`, type initializer)

```csharp
public class Settings
{
    public static readonly string ConnectionString;

    // Статический конструктор: без модификаторов доступа, без параметров, ровно один
    static Settings()
    {
        ConnectionString = Environment.GetEnvironmentVariable("DB_CONN")
                           ?? "Host=localhost";
        Console.WriteLine("Settings инициализирован");
    }
}
```

### Гарантии CLR

Спецификация CLI даёт три жёсткие гарантии, и это главное, что нужно знать:

1. **Ровно один раз** на тип и на AssemblyLoadContext за всё время жизни.
2. **Потокобезопасно**: рантайм сам ставит блокировку. Если два потока одновременно тронули тип, один выполняет `.cctor`, второй ждёт. Писать `lock` внутри `.cctor` не нужно.
3. **До первого обращения** к любому статическому полю / статическому методу / до первого создания экземпляра.

Из пункта 2 следует важное: инициализация статических полей **потокобезопасна из коробки**. Именно поэтому `static readonly`-синглтон корректен без единого `lock`.

### `beforefieldinit` — флаг, из-за которого «точно» превращается в «когда-нибудь»

Компилятор C# ставит на тип флаг `beforefieldinit`, **если статический конструктор не объявлен явно**, но есть инициализаторы статических полей. Флаг говорит рантайму: «инициализируй когда хочешь, лишь бы до первого чтения статического поля».

| | Есть явный `static Ctor()` | Только инициализаторы полей |
|---|---|---|
| Флаг в IL | нет `beforefieldinit` | `beforefieldinit` |
| Момент инициализации | **Точно** перед первым обращением к статическому члену | В **любой** момент до первого обращения к статическому полю — рантайм волен сделать это раньше |
| Стоимость доступа | JIT вставляет проверку «тип инициализирован?» перед доступом (в tier-1 обычно вырезается) | JIT может инициализировать тип при компиляции метода и убрать проверку совсем |
| Побочные эффекты | Строго упорядочены | Могут случиться раньше, чем вы ожидаете |

Демонстрация:

```csharp
class Eager   // beforefieldinit: явного .cctor нет
{
    public static readonly string Value = Log("Eager");
    static string Log(string s) { Console.WriteLine($"init {s}"); return s; }
}

class Precise // без beforefieldinit: есть явный .cctor
{
    public static readonly string Value;
    static Precise() { Value = Log("Precise"); }
    static string Log(string s) { Console.WriteLine($"init {s}"); return s; }
}

static void RunEager()
{
    Console.WriteLine("до обращения");
    Console.WriteLine(Eager.Value);
}

static void RunPrecise()
{
    Console.WriteLine("до обращения");
    Console.WriteLine(Precise.Value);
}

RunEager();
// Типичный вывод на CoreCLR:
// init Eager
// до обращения
// Eager
//   ← инициализация произошла ДО первой строки метода: рантайму это разрешено

RunPrecise();
// Гарантированный вывод:
// до обращения
// init Precise
// Precise
```

> [!warning] Вывод `RunEager` не гарантирован спецификацией и зависит от JIT, tiered compilation и того, инлайнится ли метод. В этом и суть: с `beforefieldinit` вы **не можете полагаться** на момент инициализации. Если побочный эффект в инициализаторе важен по времени (открытие файла, запись в лог, регистрация в реестре) — объявляйте явный `static` конструктор.

Обратная сторона: явный `.cctor` **стоит производительности**. JIT обязан вставлять проверку инициализации перед каждым обращением к статике такого типа из другой сборки. Для типов, к статике которых обращаются в горячем цикле, лучше обойтись инициализаторами полей и оставить `beforefieldinit`.

Проверить наличие флага можно через `ildasm`/ILSpy или так:

```csharp
Console.WriteLine(typeof(Eager).Attributes.HasFlag(TypeAttributes.BeforeFieldInit));   // Вывод: True
Console.WriteLine(typeof(Precise).Attributes.HasFlag(TypeAttributes.BeforeFieldInit)); // Вывод: False
```

### Порядок инициализации статических полей

Инициализаторы выполняются **в порядке объявления в исходном коде**, затем тело `static` конструктора.

```csharp
class Order
{
    public static readonly int A = B + 1;  // B ещё 0 → A = 1
    public static readonly int B = 10;

    static Order() => Console.WriteLine($"A={A}, B={B}");
}
_ = Order.A;
// Вывод: A=1, B=10
```

Компилятор выдаст предупреждение только для локальных переменных, для статики — молча. Это реальная ловушка: перестановка двух строк меняет поведение.

## Дедлок в статическом конструкторе

Рантайм берёт блокировку на инициализацию типа. Если два `.cctor` ждут друг друга из разных потоков — классический дедлок, который невозможно поймать таймаутом и который не виден в коде без внимательного чтения.

```csharp
class A
{
    public static readonly int Value;
    static A()
    {
        Thread.Sleep(50);      // имитируем небыструю инициализацию
        Value = B.Value + 1;   // A ждёт инициализации B
    }
}

class B
{
    public static readonly int Value;
    static B()
    {
        Thread.Sleep(50);
        Value = A.Value + 1;   // B ждёт инициализации A
    }
}

// Однопоточно дедлока НЕ будет: рантайм видит рекурсивный вход в свою же
// инициализацию из того же потока и пропускает его — но вы получите ЧАСТИЧНО
// инициализированный тип и мусорное значение:
Console.WriteLine(A.Value); // Вывод: 1 (B.Value было ещё 0) — тихо неверный результат

// А вот так — настоящий вечный дедлок:
var t1 = Task.Run(() => _ = A.Value);
var t2 = Task.Run(() => _ = B.Value);
Task.WaitAll(t1, t2); // зависает навсегда
```

> [!danger] Это одна из самых неприятных проблем прода: приложение стартует, поднимает пул потоков, два потока одновременно трогают взаимозависимые типы — и хост висит без единого исключения в логах. Диагностируется только дампом (`dotnet-dump` + `clrstack`, потоки стоят в `JIT_GetSharedNonGCStaticBase`). См. [[Диагностика в проде: дампы и dotnet-tools]].

Как не попасть:

- Не вызывайте из `.cctor` ничего, что может задеть другой тип с нетривиальной статикой.
- Никогда не делайте в `.cctor` блокирующих операций: `.Result`, `.Wait()`, `lock`, сетевые вызовы, чтение БД.
- Тяжёлую инициализацию выносите в `Lazy<T>` или, лучше, в DI-регистрацию с явным временем жизни.

## Исключение в статическом конструкторе: тип «отравлен»

Если `.cctor` бросает, CLR оборачивает исключение в `TypeInitializationException` и **навсегда помечает тип как непригодный** в этом AssemblyLoadContext. Повторная попытка не перезапустит инициализацию — вы получите тот же самый закэшированный экземпляр исключения.

```csharp
class Poisoned
{
    public static readonly string Value;
    static Poisoned()
    {
        throw new InvalidOperationException("конфиг не найден");
    }
}

for (int i = 0; i < 2; i++)
{
    try { Console.WriteLine(Poisoned.Value); }
    catch (TypeInitializationException ex)
    {
        Console.WriteLine($"{i}: {ex.InnerException!.Message}");
    }
}
// Вывод:
// 0: конфиг не найден
// 1: конфиг не найден   ← .cctor больше НЕ выполнялся, исключение отдано из кэша
```

Практика: сообщение об ошибке всегда ищите в `InnerException` — верхнее `TypeInitializationException` бесполезно («The type initializer for 'Poisoned' threw an exception»).

Типичный источник в реальных проектах: `static readonly Regex Rx = new(pattern)` с битым паттерном, `static readonly JsonSerializerOptions` с некорректным конвертером, чтение переменной окружения с `!` или `int.Parse`. Один плохой env-var — и весь тип мёртв до перезапуска процесса.

## Ленивая инициализация: `Lazy<T>` вместо ручного double-checked locking

Раньше писали так:

```csharp
// #устарело — так больше не пишут
public sealed class Cache
{
    private static volatile Cache? _instance;   // volatile обязателен!
    private static readonly object _gate = new();

    public static Cache Instance
    {
        get
        {
            if (_instance is null)              // быстрая проверка без блокировки
            {
                lock (_gate)
                {
                    if (_instance is null)      // повторная под блокировкой
                        _instance = new Cache();
                }
            }
            return _instance;
        }
    }
}
```

Почему это плохо: легко забыть `volatile` (без него на слабой модели памяти ARM другой поток может увидеть ненулевую ссылку на **недостроенный** объект), легко перепутать порядок проверок, невозможно выразить «если фабрика бросила — попробовать ещё раз». Про модель памяти — [[Interlocked, volatile и модель памяти]].

Правильно:

```csharp
public sealed class Cache
{
    private static readonly Lazy<Cache> _lazy = new(() => new Cache(), isThreadSafe: true);
    public static Cache Instance => _lazy.Value;

    private Cache() { }
}
```

`Lazy<T>` даёт три режима через `LazyThreadSafetyMode`:

| Режим | Поведение | Когда |
|---|---|---|
| `ExecutionAndPublication` (по умолчанию) | Фабрика выполняется ровно один раз, остальные ждут | Дорогая инициализация, побочные эффекты |
| `PublicationOnly` | Фабрика может выполниться несколько раз параллельно, победит первый результат, остальные будут отброшены (и `IDisposable` не будет освобождён!) | Дешёвая идемпотентная фабрика, нельзя допустить блокировку |
| `None` | Без синхронизации | Гарантированно однопоточный доступ |

> [!warning] В режиме `ExecutionAndPublication` исключение из фабрики **кэшируется**, как в `.cctor`: все последующие обращения к `.Value` получат то же исключение. Если нужен повтор — `PublicationOnly` (там исключение не кэшируется) или `LazyInitializer.EnsureInitialized`.

А если нужен просто «инициализировать один раз без объекта-обёртки» — самый дешёвый способ уже показан выше: `static readonly` поле. Рантайм всё сделает за вас.

## Синглтон через статику — и почему в ASP.NET Core так не делают

Классический статический синглтон:

```csharp
public sealed class PriceCache
{
    public static readonly PriceCache Instance = new();
    private PriceCache() { }
    public decimal Get(string sku) => 0m;
}

// Использование — жёстко зашито в вызывающем коде
var price = PriceCache.Instance.Get("ABC");
```

В ASP.NET Core вместо этого регистрируют singleton в контейнере:

```csharp
builder.Services.AddSingleton<IPriceCache, PriceCache>();

public sealed class OrderService(IPriceCache cache)   // зависимость видна в сигнатуре
{
    public decimal Total(string sku) => cache.Get(sku);
}
```

| | Статический синглтон | DI-синглтон |
|---|---|---|
| Зависимость видна в сигнатуре | Нет, спрятана в теле метода | Да, в конструкторе |
| Подмена в тесте | Только через хаки (интерфейс + сеттер, Fody, TypeMock) | Регистрируешь мок |
| Время жизни контролирует | Рантайм, до конца процесса | Контейнер, можно пересоздать (например, на новый scope в тесте) |
| Освобождение (`IDisposable`) | Никогда не вызовется штатно | Контейнер вызовет `Dispose` при остановке хоста |
| Порядок инициализации | Непредсказуем (`beforefieldinit`) | Явный, при первом резолве или на старте |
| Циклические зависимости | Дедлок в `.cctor` | Понятное исключение при построении графа |

Подробности времён жизни — [[Жизненные циклы сервисов: Singleton, Scoped, Transient]] и [[Dependency Injection: контейнер ASP.NET Core]].

## Статика и тестируемость — главный аргумент против

```csharp
// Плохо: время и «сейчас» зашиты в реализацию
public class TrialService
{
    public bool IsExpired(User u) => DateTime.UtcNow > u.TrialEndsAt;
    // Как протестировать «через 31 день»? Только менять часы машины.
}

// Хорошо: зависимость от абстракции времени
public class TrialService(TimeProvider clock)
{
    public bool IsExpired(User u) => clock.GetUtcNow() > u.TrialEndsAt;
}

// В тесте
var clock = new FakeTimeProvider(new DateTimeOffset(2026, 9, 1, 0, 0, 0, TimeSpan.Zero));
var sut = new TrialService(clock);
```

`TimeProvider` — стандартная абстракция из BCL (`System.TimeProvider`, доступна с .NET 8), `FakeTimeProvider` — из пакета `Microsoft.Extensions.TimeProvider.Testing`. См. [[Дата и время: DateTime, DateTimeOffset, TimeProvider]].

Обобщение: **статический вызов — это жёстко зашитая зависимость на этапе компиляции**. Её нельзя подменить, потому что нет точки расширения. Каждый `File.ReadAllText`, `HttpClient` в статическом поле, `Console.WriteLine`, `Guid.NewGuid()` в бизнес-логике — потенциально нетестируемый кусок. См. [[Инверсия зависимостей на практике]] и [[Связанность и связность (coupling, cohesion)]].

Когда статика безопасна для тестов:

- Чистая функция без состояния и без обращения к внешнему миру: `MathUtils.Hypotenuse`, `StringExtensions.ToSlug`. Тестируется напрямую, подменять нечего.
- Иммутабельное значение, вычисленное один раз: `static readonly JsonSerializerOptions`.

Когда опасна: любое **изменяемое** статическое состояние. Тесты начинают влиять друг на друга через общий кэш, порядок выполнения становится значимым, параллельный прогон падает случайным образом.

## Статические локальные функции и `static`-лямбды

С C# 8 локальную функцию можно пометить `static` — это запрещает захват `this` и локальных переменных внешнего метода. С C# 9 то же самое доступно лямбдам.

```csharp
public IEnumerable<int> Process(int[] data)
{
    int threshold = 10;

    // Обычная лямбда: захватывает threshold → компилятор создаёт класс замыкания,
    // аллокация в куче на каждый вызов Process
    var a = data.Where(x => x > threshold);

    // static-лямбда: захват запрещён компилятором
    var b = data.Where(static x => x > 10);   // делегат кэшируется в статическом поле, 0 аллокаций

    // Ошибка CS8820: static-лямбда не может захватывать threshold
    // var c = data.Where(static x => x > threshold);

    static bool IsEven(int x) => x % 2 == 0;  // static-локальная функция
    return b.Where(IsEven);
}
```

Зачем: `static` здесь — это **гарантия от компилятора**, что случайного захвата не произошло. В горячем коде захват означает лишнюю аллокацию на каждый вызов, а в async-коде — ещё и продление жизни захваченных объектов. Ставьте `static` на все лямбды, которым нечего захватывать. См. [[Локальные функции и замыкания]] и [[Аллокации и как их избегать]].

> [!warning] Подводные камни
> - **`beforefieldinit` ломает интуицию о моменте инициализации.** Если инициализатор статического поля пишет в лог, регистрирует обработчик или открывает соединение, побочный эффект может случиться заметно раньше первого обращения — или наоборот, никогда, если поле не читается. Нужен точный момент — пишите явный `static` конструктор.
> - **Статическое событие — вечная утечка.** Подписчик, зарегистрированный на `static event`, живёт до конца процесса вместе со всем, что он захватил. Экземплярный объект, подписавшийся на статическое событие и «удалённый», на самом деле остаётся в памяти. Всегда отписывайтесь или используйте слабые ссылки.
> - **`const` через границу сборок** вшивается в потребителя и не обновляется при подмене dll. Публичные константы в библиотеке — почти всегда должны быть `static readonly`.
> - **Изменяемая статика + многопоточность = гонка.** `static int _counter; _counter++;` не атомарно. Нужен `Interlocked.Increment` или `lock`. Коллекции в статических полях должны быть конкурентными или иммутабельными.
> - **`.cctor` не должен блокировать.** `.Result`, `.Wait()`, `Task.Run(...).Wait()` в статическом конструкторе — рецепт дедлока: блокировка инициализации типа держится, пока не завершится ожидание, а пул потоков может быть занят ожидающими того же типа.
> - **Порядок инициализаторов статических полей — порядок объявления.** Поле, инициализированное значением ещё не инициализированного поля, получит `default` без предупреждения.
> - **Статика в дженерике на каждый `T`.** Если у вас `static Dictionary` в `Cache<T>` и сотни конкретизаций — это сотни словарей, и все они живут вечно.

> [!example] Как делают в бою
> **1. Дешёвый типизированный кэш метаданных.** `static readonly` поле в дженерик-классе — самый быстрый способ закэшировать что-то «по типу». Так устроены внутренности `System.Text.Json`, `EqualityComparer<T>.Default`, многих мапперов.
>
> ```csharp
> internal static class JsonOpts
> {
>     // Один экземпляр на процесс. JsonSerializerOptions дорогой: он кэширует
>     // скомпилированные метаданные типов и после первого использования замораживается.
>     public static readonly JsonSerializerOptions Web = new(JsonSerializerDefaults.Web)
>     {
>         DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull
>     };
> }
> ```
> Создавать `new JsonSerializerOptions()` на каждый вызов сериализации — известная ошибка, съедающая десятки процентов производительности. См. [[Сериализация: System.Text.Json]].
>
> **2. Скомпилированные регулярки — статикой или source generator.**
> ```csharp
> internal static partial class Patterns
> {
>     [GeneratedRegex(@"^[a-z0-9-]+$", RegexOptions.IgnoreCase)]
>     public static partial Regex Slug { get; }   // C# 13+: свойство вместо метода
> }
> ```
> Source generator строит автомат на этапе компиляции: нет ни `.cctor`-риска, ни расходов на разбор паттерна в рантайме. См. [[Регулярные выражения]].
>
> **3. Статика в приложении — только immutable.** Практическое правило команды: в статическом поле может лежать либо примитив/строка, либо иммутабельная структура данных (`FrozenDictionary`, `ImmutableArray`), либо потокобезопасный сервис без изменяемого состояния. Всё остальное — в DI-синглтон, где хотя бы видно, кто им пользуется. См. [[Frozen и Immutable коллекции]] и [[Иммутабельность как приём проектирования]].
>
> **4. Никакого «сервис-локатора» через статику.** `ServiceLocator.Current.Resolve<IFoo>()` — антипаттерн: зависимости невидимы, тесты хрупкие, время жизни неуправляемо. Единственное легитимное место для доступа к контейнеру напрямую — точка композиции (`Program.cs`) и фабрики. См. [[Антипаттерны и code smells]].

## Вопросы с собеседований

> [!question]- Когда вызывается статический конструктор?
> Формально — рантаймом, один раз на тип и на AssemblyLoadContext, перед первым обращением к типу. Точный момент зависит от флага `beforefieldinit`. Если статический конструктор объявлен **явно**, флага нет, и CLR гарантирует вызов строго перед первым обращением к любому статическому члену или созданием первого экземпляра. Если явного `.cctor` нет, но есть инициализаторы статических полей, компилятор ставит `beforefieldinit`, и рантайм вправе инициализировать тип в любой момент до первого чтения статического поля — на практике часто при JIT-компиляции метода, который к нему обращается. Вызов всегда потокобезопасен: CLR сам держит блокировку, второй поток ждёт.

> [!question]- Что такое `beforefieldinit` и зачем он нужен?
> Флаг в метаданных типа (`TypeAttributes.BeforeFieldInit`), ослабляющий требование к моменту инициализации: «до первого доступа к статическому полю» вместо «строго перед первым обращением к типу». Компилятор C# ставит его автоматически, когда явного статического конструктора нет. Зачем: без флага JIT обязан вставлять проверку «тип уже инициализирован?» перед каждым обращением к статике из другой сборки, что стоит производительности. С флагом JIT может инициализировать тип заранее и выкинуть проверку целиком. Цена — вы теряете контроль над моментом побочных эффектов.

> [!question]- Чем `const` отличается от `static readonly`? Когда `const` опасен?
> `const` вычисляется компилятором и **вшивается литералом в каждое место использования**, включая другие сборки; ссылки на объявляющий тип в IL не остаётся. `static readonly` — настоящее поле, читается в рантайме. Опасность `const` — версионирование: если библиотеку пересобрали с новым значением константы, а потребителя нет, потребитель продолжит работать со старым значением. Плюс `const` ограничен примитивами, `string` и `enum`, и требует константного выражения. Правило: в публичном API библиотеки `const` только для того, что не изменится никогда.

> [!question]- Что произойдёт, если статический конструктор бросит исключение?
> CLR обернёт его в `TypeInitializationException` (оригинал будет в `InnerException`) и пометит тип как непригодный к использованию в текущем AssemblyLoadContext навсегда. Повторное обращение не перезапустит инициализацию — вернётся тот же закэшированный экземпляр исключения. Восстановить можно только перезапуском процесса (или, для collectible ALC, выгрузкой и повторной загрузкой контекста). Поэтому в `.cctor` не должно быть ничего, что может упасть от внешних условий: чтения переменных окружения без дефолта, парсинга, обращения к сети или файлам.

> [!question]- Есть ли у `Cache<int>` и `Cache<string>` общие статические поля?
> Нет. Каждая конкретизация дженерика — отдельный тип времени выполнения со своим блоком статики. При этом `Cache<string>` и `Cache<object>` разделяют один скомпилированный машинный код (все ссылочные типы используют канонический код `Cache<__Canon>`), но статические поля у них всё равно раздельные: рантайм подставляет нужный статический блок через скрытый generic-контекст. Это свойство часто используют как быстрый кэш «одно значение на тип» — без словаря и хеширования.

> [!question]- Как статический класс выглядит в IL и почему у него такие ограничения?
> Как `abstract sealed`. `abstract` не даёт создать экземпляр, `sealed` — унаследовать. Отсюда: нет конструктора экземпляра и экземплярных членов, нельзя реализовать интерфейс, нельзя использовать как тип переменной, параметра или аргумента дженерика. Статический конструктор при этом иметь можно — он не про экземпляр, а про тип.

> [!question]- Почему статика мешает тестировать и что делать?
> Статический вызов — это зависимость, зашитая на этапе компиляции: нет шва, куда подставить заглушку. `DateTime.UtcNow`, `File.ReadAllText`, `Guid.NewGuid()` внутри бизнес-логики делают её недетерминированной. Второй эффект — изменяемое статическое состояние переживает тест и протекает в следующий, из-за чего тесты становятся зависимыми от порядка и падают при параллельном прогоне. Решение: выносить такие вещи за интерфейс и внедрять через конструктор (`TimeProvider`, `IFileSystem`, `IGuidProvider`), а разделяемое состояние регистрировать singleton-ом в DI, где им хотя бы управляет контейнер.

> [!question]- Чем `Lazy<T>` лучше самописного double-checked locking?
> Корректностью и выразительностью. В ручной реализации легко забыть `volatile` у поля — тогда на архитектурах со слабой моделью памяти (ARM) другой поток может увидеть опубликованную ссылку раньше, чем записанные поля объекта, то есть получить недостроенный экземпляр. `Lazy<T>` инкапсулирует это, плюс даёт выбор политики (`ExecutionAndPublication`, `PublicationOnly`, `None`) и корректное поведение при исключении из фабрики. А если ленивость нужна «на уровне типа», часто вообще достаточно `static readonly` — рантайм даст те же гарантии бесплатно.

## Задачи

### Задача 1. Счётчик экземпляров на тип

Напишите базовый класс, который считает, сколько объектов **каждого конкретного** производного типа было создано. `Dog` и `Cat` должны иметь независимые счётчики, добавление нового наследника не должно требовать правки базового класса.

> [!success]- Решение
> ```csharp
> public abstract class Tracked<TSelf> where TSelf : Tracked<TSelf>
> {
>     private static int _count;
>     public static int Count => Volatile.Read(ref _count);
>
>     protected Tracked() => Interlocked.Increment(ref _count);
> }
>
> public sealed class Dog : Tracked<Dog> { }
> public sealed class Cat : Tracked<Cat> { }
>
> _ = new Dog(); _ = new Dog(); _ = new Cat();
> Console.WriteLine($"{Dog.Count} {Cat.Count}"); // Вывод: 2 1
> ```
> Приём называется CRTP (curiously recurring template pattern). Работает именно потому, что статика у `Tracked<Dog>` и `Tracked<Cat>` раздельная. `Interlocked.Increment` нужен, потому что обычный `_count++` не атомарен: это чтение, инкремент и запись. Без дженерика пришлось бы держать `ConcurrentDictionary<Type,int>` и платить за хеширование на каждом создании объекта.

### Задача 2. Найдите ошибку версионирования

Библиотека `Billing.dll` v1.0:
```csharp
public static class Tariff
{
    public const decimal Vat = 0.20m;
    public const string Currency = "USD";
}
```
С 1 января ставку НДС меняют на 0.22. Команда пересобирает `Billing.dll` v1.1 и выкатывает её, заменив файл на сервере. Приложение продолжает считать по 20 %. Почему и как починить?

> [!success]- Решение
> ```csharp
> // Причина: const-значения вшиты в IL приложения на этапе его компиляции.
> // В коде приложения после компиляции стоит буквально `ldc.i4 0.20`,
> // обращения к Billing.dll нет вообще — подмена dll ничего не меняет.
>
> // Починка 1 (минимальная): сделать поле рантайм-полем
> public static class Tariff
> {
>     public static readonly decimal Vat = 0.20m;   // теперь ldsfld, читается из dll
>     public const string Currency = "USD";          // это менять не будут — можно оставить const
> }
> // ...и всё равно пересобрать приложение один раз, чтобы избавиться от старого литерала.
>
> // Починка 2 (правильная для бизнес-параметра): вынести в конфигурацию
> public sealed class TariffOptions { public decimal Vat { get; init; } = 0.20m; }
> builder.Services.Configure<TariffOptions>(builder.Configuration.GetSection("Tariff"));
> ```
> Общее правило: значение, которое может изменить бизнес, вообще не должно быть константой в коде. Ставка налога — конфигурация, а не `const`. См. [[Options pattern и конфигурация сервисов]].

### Задача 3. Обезвредьте `.cctor`

Код падает на старте под нагрузкой с `TypeInitializationException`, и после этого сервис не восстанавливается до рестарта. Найдите все проблемы и перепишите.

```csharp
public static class Geo
{
    public static readonly HttpClient Client = new();
    public static readonly Dictionary<string, string> Countries;

    static Geo()
    {
        var json = Client.GetStringAsync("https://geo.example/countries").Result;
        Countries = JsonSerializer.Deserialize<Dictionary<string, string>>(json)!;
    }
}
```

> [!success]- Решение
> ```csharp
> // Проблемы:
> // 1. Блокирующее ожидание (.Result) внутри .cctor — риск дедлока и залипания старта.
> // 2. Сетевой вызов в .cctor — любая недоступность сервиса «отравляет» тип навсегда.
> // 3. Dictionary изменяемый и статический — гонка при параллельном чтении/записи.
> // 4. Спрятанная зависимость: невозможно подменить в тесте.
>
> public sealed class GeoCatalog(HttpClient http)
> {
>     private FrozenDictionary<string, string>? _countries;
>
>     public async ValueTask<FrozenDictionary<string, string>> GetAsync(CancellationToken ct)
>     {
>         if (_countries is { } cached) return cached;
>
>         var json = await http.GetStringAsync("countries", ct);
>         var map = JsonSerializer.Deserialize<Dictionary<string, string>>(json)!;
>         var frozen = map.ToFrozenDictionary(StringComparer.Ordinal);
>
>         // Публикуем атомарно; при гонке победит первый, лишняя копия просто отбросится
>         Interlocked.CompareExchange(ref _countries, frozen, null);
>         return _countries!;
>     }
> }
>
> // Регистрация
> builder.Services.AddHttpClient<GeoCatalog>(c => c.BaseAddress = new Uri("https://geo.example/"));
> builder.Services.AddSingleton<GeoCatalog>();
> ```
> Ключевое: инициализация стала асинхронной, отменяемой, повторяемой после сбоя и подменяемой в тестах. `FrozenDictionary` даёт быстрый потокобезопасный доступ на чтение. `HttpClient` создаётся через `IHttpClientFactory`, а не статикой — статический `HttpClient` не подхватывает изменения DNS. См. [[HttpClient и IHttpClientFactory]].

### Задача 4. Предскажите вывод

```csharp
class X
{
    public static int A = Print("A", 1);
    static X() { Print("cctor", 0); }
    public static int B = Print("B", 2);

    static int Print(string s, int v) { Console.WriteLine(s); return v; }
}

Console.WriteLine("start");
Console.WriteLine(X.B);
```

> [!success]- Решение
> ```
> start
> A
> B
> cctor
> 2
> ```
> Разбор:
> 1. У типа есть **явный** `static X()`, значит `beforefieldinit` не ставится и инициализация произойдёт строго в момент первого обращения — уже после печати `start`.
> 2. Компилятор собирает `.cctor` так: сначала все инициализаторы полей **в порядке объявления в коде** (`A`, потом `B` — расположение объявления `static X()` между ними роли не играет), затем тело написанного вами статического конструктора.
> 3. Поэтому `A`, `B`, `cctor`, и только потом печатается значение `X.B` = 2.
>
> Если убрать `static X() {...}`, вывод станет непредсказуемым по месту: `A` и `B` могут напечататься до `start`.

## Итог

- Статический член принадлежит типу; хранится не в объекте, а в блоке статики, привязанном к типу и его AssemblyLoadContext. Ссылочная статика — GC-корень, живёт до выгрузки ALC.
- У каждой конкретизации дженерика **своя** статика, даже если машинный код общий. Это основа приёма «кэш по типу».
- `static class` в IL — `abstract sealed`: нет экземпляров, нет наследования, нет реализации интерфейсов.
- `const` вшивается в потребителя на этапе компиляции и ломает версионирование между сборками; `static readonly` безопасен.
- CLR гарантирует вызов `.cctor` ровно один раз и потокобезопасно. Но с `beforefieldinit` (флаг ставится при отсутствии явного статического конструктора) момент вызова становится неопределённым «когда-то до первого чтения поля».
- Исключение в `.cctor` → `TypeInitializationException`, и тип отравлен навсегда. Блокирующие и сетевые операции в `.cctor` — прямой путь к дедлоку и незапускающемуся сервису.
- Ленивость: `static readonly` (бесплатно) → `Lazy<T>` (когда нужен контроль) → ручной DCL (не нужен никогда).
- Главная цена статики — невидимая, неподменяемая зависимость. В приложении держите в статике только иммутабельное; всё с состоянием — в DI-синглтон.
