# Свойства и field-backed properties

> [!abstract] Коротко
> Свойство — пара методов (`get_X`/`set_X`), которая внешне выглядит как поле. Автосвойство `public string Name { get; set; }` заставляет компилятор создать скрытое поле и оба аксессора; с C# 14 к этому полю можно обратиться прямо из аксессора через ключевое слово `field`, и «полуручные» свойства с явным приватным полем почти исчезли. Ключевые формы: `get; set;` (изменяемое), `get; private set;` (меняется только изнутри), `get; init;` (только при создании), `required` (обязательно задать), вычисляемое `=> выражение`. Вызов аксессора JIT встраивает, поэтому свойство не медленнее поля.

## Зачем это нужно

Свойство — способ дать доступ к данным, не отдавая контроль над ними. Оно решает три задачи сразу: позволяет добавить логику (проверку, нормализацию, ленивое вычисление) не меняя вызывающий код, участвует в интерфейсах, привязке данных, сериализации и ORM (поля туда не попадают), и сохраняет бинарную совместимость при развитии типа.

```csharp
// Начали так
public string Email { get; set; } = "";

// Потребовалась нормализация — вызывающий код не меняется вообще (C# 14)
public string Email
{
    get;
    set => field = value?.Trim().ToLowerInvariant() ?? "";
}
```

Замена публичного поля на свойство таким «бесшовным» не была бы: это ломающее изменение на уровне IL, требующее пересборки всех потребителей.

## Формы свойств

```csharp
public sealed class Product
{
    // 1. Автосвойство: компилятор создаёт скрытое поле и оба аксессора
    public string Name { get; set; } = "";

    // 2. Только для чтения снаружи, меняется внутри класса
    public decimal Price { get; private set; }

    // 3. Только при создании объекта (C# 9): работает в инициализаторе и в конструкторе
    public long Id { get; init; }

    // 4. Обязательное к заполнению (C# 11)
    public required string Sku { get; init; }

    // 5. Полностью неизменяемое: присвоить можно только в конструкторе
    public DateTimeOffset CreatedAt { get; }

    // 6. Вычисляемое (expression-bodied) — поля нет вообще
    public bool IsFree => Price == 0;

    // 7. С логикой в аксессоре через field (C# 14)
    public int Stock
    {
        get;
        set => field = value < 0 ? 0 : value;
    }

    // 8. Разные модификаторы у аксессоров
    public string InternalCode { get; internal set; } = "";

    // 9. Статическое свойство
    public static Product Empty { get; } = new() { Sku = "" };

    public Product() => CreatedAt = DateTimeOffset.UtcNow;
}

var p = new Product { Sku = "ABC-1", Id = 7, Name = "Кофе" };
```

Что во что превращается: `public string Name { get; set; }` компилируется в приватное поле `<Name>k__BackingField` плюс методы `get_Name()`/`set_Name(value)`, помеченные как аксессоры свойства. Никакой магии, и никакой дополнительной стоимости — JIT встраивает тривиальные аксессоры, и обращение к свойству превращается в обращение к полю.

### `init` и `required`

```csharp
public sealed class Order
{
    public required long CustomerId { get; init; }
    public required string Address { get; init; }
    public string? Comment { get; init; }
}

var order = new Order { CustomerId = 1, Address = "Ташкент" };   // ок
// var bad = new Order { CustomerId = 1 };                        // Ошибка: Address не задан
// order.Address = "другой";                                      // Ошибка: init-свойство
```

`init` — сеттер, доступный только на этапе инициализации объекта: в конструкторе, в инициализаторе и в выражении `with`. Это способ получить иммутабельность, не отказываясь от удобного синтаксиса инициализации.

`required` — требование компилятора задать свойство при создании. Заменяет два костыля: конструктор со всеми параметрами (который разрастается) и `= null!;` для свойств, которые «точно будут заполнены» ([[Nullable reference types]]).

Комбинация `required` + `init` — стандартная форма для DTO и моделей конфигурации.

### Ключевое слово `field` (C# 14)

```csharp
// Было: ради одной проверки приходилось заводить поле руками
private string _name = "";
public string Name
{
    get => _name;
    set => _name = string.IsNullOrWhiteSpace(value)
        ? throw new ArgumentException("Имя обязательно", nameof(value))
        : value.Trim();
}

// Стало: геттер остаётся автоматическим, поле доступно как field
public string Name
{
    get;
    set => field = string.IsNullOrWhiteSpace(value)
        ? throw new ArgumentException("Имя обязательно", nameof(value))
        : value.Trim();
} = "";
```

`field` доступен внутри любого аксессора и ссылается на сгенерированное backing-поле. Типичные применения: нормализация (обрезка пробелов, регистр), валидация, ограничение диапазона, ленивая инициализация, счётчик обращений.

Тонкость совместимости: если в области видимости уже есть идентификатор `field` (например, параметр или локальная переменная), возникает конфликт — компилятор предупредит, обойти можно через `@field`.

### Вычисляемые свойства

```csharp
public decimal Total => _items.Sum(i => i.Price * i.Quantity);
public bool IsEmpty => _items.Count == 0;
public string FullName => $"{FirstName} {LastName}";
```

Вычисляемое свойство не хранит состояние, поэтому рассинхронизация невозможна — это лучший способ поддерживать инварианты вида «итог = сумма позиций» ([[Инкапсуляция и модификаторы доступа]]). Ограничение: вычисление происходит **при каждом обращении**, поэтому оно должно быть дешёвым.

## Свойство или метод

Свойство должно вести себя как доступ к данным. Метод — как действие.

| Признак | Свойство | Метод |
|---|---|---|
| Стоимость | O(1) или близко | любая |
| Побочные эффекты | нет | допустимы |
| Каждый вызов даёт то же значение | да (если состояние не менялось) | не обязательно |
| Может бросать исключение | в норме нет | да |
| Асинхронность | невозможна | да |
| Принимает аргументы | нет (кроме индексатора) | да |

```csharp
public int Count => _items.Count;                          // свойство: дешёво, без эффектов
public decimal Total => _items.Sum(i => i.Price);           // свойство: O(n), но n мал и предсказуем

public Task<Report> BuildReportAsync(CancellationToken ct);  // метод: асинхронно
public byte[] Serialize();                                   // метод: создаёт новый объект каждый раз
public Order LoadFromDatabase();                             // метод: обращение к внешней системе
```

Практическое правило: **если за точкой стоит работа, а не значение — это метод**. Свойство, которое ходит в базу или считает пять секунд, обманывает читателя: в коде `if (service.CurrentUser.Permissions.Count > 0)` никто не ожидает трёх сетевых вызовов.

Особый случай — свойство, возвращающее новый объект при каждом обращении:

```csharp
public byte[] Data => _buffer.ToArray();     // плохо: каждое чтение — копия и аллокация
if (obj.Data.Length > 0 && obj.Data[0] == 1) // две копии в одном выражении
```

Такое лучше делать методом с говорящим именем (`ToArray()`), чтобы стоимость была видна.

## Свойства в интерфейсах и наследовании

```csharp
public interface IEntity
{
    long Id { get; }                       // требуется только геттер
    DateTimeOffset CreatedAt { get; init; } // init тоже можно объявить в интерфейсе
}

public class Base
{
    public virtual string Title { get; set; } = "";    // виртуальное свойство
}

public sealed class Derived : Base
{
    public override string Title
    {
        get => base.Title;
        set => base.Title = value?.Trim() ?? "";
    }
}
```

Реализация может быть «шире» контракта: интерфейс требует `get`, класс может дать и `set`. Наоборот нельзя — реализация обязана предоставить всё, что объявлено.

Переопределять можно свойство целиком, но не отдельный аксессор: `override` пишется на всё свойство, при этом внутри можно вызвать `base`.

Про механику `virtual`/`override`/`new` — [[Полиморфизм: virtual, override, new]].

## Практические приёмы

```csharp
// Ленивая инициализация — с C# 14 без отдельного поля
public IReadOnlyList<string> Items => field ??= LoadItems();
// Для потокобезопасного варианта — Lazy<T>:
private readonly Lazy<IReadOnlyList<string>> _items = new(LoadItems);
public IReadOnlyList<string> Items => _items.Value;

// Уведомление об изменении (UI, MVVM)
public string Name
{
    get;
    set
    {
        if (field == value) return;
        field = value;
        OnPropertyChanged();                 // [CallerMemberName] подставит "Name"
    }
}

// Свойство только для чтения снаружи и внутри — присваивается в конструкторе
public IReadOnlyList<OrderItem> Items { get; }

// Атрибуты на свойстве и на его аксессорах
[JsonPropertyName("customer_id")]
public long CustomerId { get; init; }

[property: Obsolete("Используй Total")]     // атрибут на свойство record'а
public decimal Sum => Total;
```

> [!warning] Подводные камни
> - **Публичный `set` на доменной модели.** Инвариант нарушается одной строкой извне; нужен `private set` или `init` плюс методы-переходы.
> - **Дорогое вычисление в геттере.** `Total => _items.Sum(...)` в цикле по 10 000 итераций пересчитывается 10 000 раз. Либо кешировать внутри, либо делать методом.
> - **Побочные эффекты в геттере.** Запрос к базе, запись в лог, мутация состояния — читатель этого не ждёт, а отладчик вычисляет свойства при показе объекта, то есть эффекты сработают ещё и при просмотре в watch.
> - **Исключение из геттера.** Нарушает ожидания и ломает отладку и сериализацию. Геттер должен возвращать значение всегда.
> - **`{ get; }` для коллекции.** Ссылку заменить нельзя, содержимое — можно. Наружу отдавать `IReadOnlyList<T>`.
> - **Виртуальное свойство, вызываемое из конструктора базового класса.** Оно уйдёт в переопределение наследника, поля которого ещё не инициализированы.
> - **`init` не делает объект иммутабельным целиком.** Изменяемая коллекция внутри `init`-свойства меняется свободно.
> - **Свойство без сеттера и без инициализации при включённых NRT.** Даст предупреждение; лечится `required`, конструктором или значением по умолчанию, но не `= null!` как привычкой.

> [!example] Как делают в бою
> В доменных сущностях свойства почти всегда `{ get; private set; }` или `{ get; }`, а изменение состояния происходит методами с бизнес-именами. В DTO и моделях конфигурации — `required` + `init`, никакого поведения. В моделях EF Core — обычные `{ get; set; }`, потому что ORM материализует объекты, присваивая свойства (для навигационных свойств там же встречается `= null!`).
> `field` из C# 14 быстро вытеснил «полуручные» свойства: сейчас типичный вид свойства с проверкой — три строки вместо семи, и приватного поля рядом больше не видно.
> Отдельная договорённость, которую стоит держать в голове на ревью: вычисляемое свойство допустимо, пока оно дешёвое и детерминированное. Как только внутри появляется обращение к внешнему ресурсу или заметная работа — это метод, и лучше асинхронный.

## Вопросы с собеседований

> [!question]- Чем свойство отличается от поля и почему рекомендуют свойства?
> Поле — участок памяти в объекте, свойство — пара методов (`get_X`/`set_X`), которые компилятор позволяет вызывать синтаксисом поля. Причины предпочитать свойства: можно добавить логику (валидацию, нормализацию, ленивую инициализацию, уведомление) не меняя вызывающий код; свойства участвуют в интерфейсах, привязке данных, сериализации и ORM, а поля — нет; замена поля на свойство является ломающим изменением на уровне IL, то есть потребуется пересборка всех потребителей; поле можно передать по `ref` и изменить в обход владельца. Стоимость нулевая: тривиальные аксессоры JIT встраивает, и обращение к автосвойству компилируется в то же самое обращение к полю.

> [!question]- Что делает ключевое слово `field` и какую проблему решает?
> `field` (C# 14) внутри аксессора ссылается на автоматически создаваемое backing-поле свойства. Раньше добавление любой логики хотя бы в один аксессор требовало объявить приватное поле вручную и написать оба аксессора целиком; теперь можно оставить `get;` автоматическим и написать только нужную часть: `set => field = value?.Trim() ?? "";`. Это чисто синтаксическое удобство — генерируется то же самое поле, поведение в рантайме не меняется. Единственная тонкость: если в области видимости уже есть идентификатор с именем `field`, возникает конфликт, и обращаться к нему нужно как `@field`.

> [!question]- Чем `init` отличается от `private set`?
> `private set` разрешает менять свойство в любой момент, но только из кода самого типа: объект остаётся изменяемым, просто изменения контролируются классом. `init` разрешает присваивание только на этапе инициализации — в конструкторе, в инициализаторе объекта и в выражении `with`, — после чего значение фиксируется навсегда, даже для кода внутри класса. Соответственно `init` выбирают для по-настоящему неизменяемых данных (DTO, value objects, конфигурация), а `private set` — когда состояние должно меняться, но по правилам класса (статус заказа, баланс счёта). Дополнительная выгода `init` — совместимость с синтаксисом инициализатора объекта, которого лишены свойства только с конструктором, и с `required`, требующим задать значение при создании.

> [!question]- Когда стоит сделать метод, а не свойство?
> Когда обращение выполняет работу, а не возвращает значение. Конкретные признаки: стоимость заметно выше константной, есть побочные эффекты, результат может отличаться при двух подряд обращениях без изменения состояния, возможны исключения в нормальном сценарии, операция асинхронная (свойство не может возвращать `Task` осмысленно), при каждом обращении создаётся новый объект. Классические ошибки: свойство, которое ходит в базу или по сети; свойство `Data => _buffer.ToArray()`, копирующее массив на каждое чтение; свойство, кидающее исключение, если объект «ещё не готов». Практический ориентир — как код читается в выражении: `if (user.Permissions.Count > 0)` подразумевает мгновенную проверку, и если за этим стоят три сетевых вызова, API вводит в заблуждение.

## Задачи

### Задача 1. Свойство с нормализацией

Сделай свойство `Email`: пустая строка недопустима, значение обрезается и приводится к нижнему регистру, читать можно всем, задавать — только при создании.

> [!success]- Решение
> ```csharp
> public sealed class User
> {
>     public required string Email
>     {
>         get;
>         init => field = string.IsNullOrWhiteSpace(value)
>             ? throw new ArgumentException("Email обязателен", nameof(value))
>             : value.Trim().ToLowerInvariant();
>     }
> }
>
> var u = new User { Email = "  Ivan@Example.COM " };
> Console.WriteLine(u.Email);      // ivan@example.com
> ```
> `required` гарантирует, что свойство нельзя не задать; `init` — что нельзя изменить потом; `field` позволяет добавить нормализацию, оставив геттер автоматическим. Валидация выполняется один раз при создании, поэтому дальше по коду `Email` можно считать корректным — проверок в остальных методах не нужно.

### Задача 2. Найти проблемы

```csharp
public class ReportService
{
    public List<Report> Reports { get; set; } = [];
    public Report LatestReport => _db.Reports.OrderByDescending(r => r.Date).First();
    public byte[] Logo => File.ReadAllBytes("logo.png");
    public int Count { get { _accessCount++; return Reports.Count; } }
}
```

> [!success]- Решение
> Четыре проблемы, все — про нарушение ожиданий от свойства.
> `Reports` с публичным сеттером и изменяемым списком: состояние сервиса меняется извне полностью. Нужно приватное поле и `IReadOnlyList<Report>`.
> `LatestReport` делает запрос к базе при каждом обращении и бросает `InvalidOperationException` на пустой таблице (`First`). Это метод, причём асинхронный: `Task<Report?> GetLatestAsync(CancellationToken ct)`.
> `Logo` читает файл с диска на каждое чтение — операция ввода-вывода в геттере, плюс аллокация массива. Либо метод, либо закешированное поле.
> `Count` имеет побочный эффект (инкремент счётчика). Отладчик вычисляет свойства при показе объекта, поэтому счётчик будет расти просто от просмотра в watch — классический источник «невозможных» цифр в метриках.
> ```csharp
> public sealed class ReportService(AppDbContext db)
> {
>     private readonly List<Report> _reports = [];
>     public IReadOnlyList<Report> Reports => _reports;
>     public int Count => _reports.Count;
>
>     public Task<Report?> GetLatestAsync(CancellationToken ct)
>         => db.Reports.OrderByDescending(r => r.Date).FirstOrDefaultAsync(ct);
>
>     public byte[] ReadLogo() => File.ReadAllBytes(_logoPath);
> }
> ```

## Итог

- Свойство — пара методов, выглядящая как поле; тривиальные аксессоры встраиваются JIT, стоимости нет.
- Формы: `get; set;`, `get; private set;`, `get; init;`, `required`, вычисляемое `=>`, разные модификаторы у аксессоров.
- `init` фиксирует значение после инициализации, `required` требует его задать — вместе это стандарт для DTO.
- `field` (C# 14) даёт доступ к backing-полю из аксессора: «полуручные» свойства больше не нужны.
- Вычисляемое свойство исключает рассинхронизацию, но выполняется при каждом обращении.
- Свойство — про значение, метод — про работу: побочные эффекты, I/O, асинхронность и исключения — признаки метода.
- `{ get; }` для коллекции защищает ссылку, но не содержимое: наружу — `IReadOnlyList<T>`.
