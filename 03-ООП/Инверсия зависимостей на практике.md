# Инверсия зависимостей на практике

> [!abstract] Коротко
> Принцип инверсии зависимостей (D в [[SOLID]]) состоит из двух частей: модули верхнего уровня не должны зависеть от модулей нижнего уровня — оба зависят от абстракций; и абстракции не должны зависеть от деталей — детали зависят от абстракций. Практически это означает, что **интерфейс принадлежит потребителю, а не реализации**: `IOrderRepository` объявлен в слое приложения, а реализован в инфраструктуре, поэтому стрелка зависимости между сборками разворачивается. Не путать три вещи: DIP — принцип, IoC — общая идея передачи управления, DI — техника внедрения зависимостей, обычно через конструктор.

## Зачем это нужно

```csharp
// Прямая зависимость: бизнес-логика знает про EF Core, SMTP и системные часы
public sealed class OrderService
{
    private readonly AppDbContext _db = new();
    public void Create(Order order)
    {
        order.CreatedAt = DateTime.Now;
        _db.Orders.Add(order);
        _db.SaveChanges();
        new SmtpClient("smtp.company.uz").Send(...);
    }
}
```

Проблемы: сервис невозможно протестировать без базы и почтового сервера; замена хранилища требует правки бизнес-логики; `DateTime.Now` делает поведение недетерминированным; сборка с доменом ссылается на EF Core и `System.Net.Mail`.

```csharp
// Инвертированная зависимость: сервис знает только контракты
public sealed class OrderService(
    IOrderRepository repository,
    INotificationSender notifications,
    TimeProvider clock)
{
    public async Task CreateAsync(Order order, CancellationToken ct)
    {
        order.CreatedAt = clock.GetUtcNow();
        await repository.AddAsync(order, ct);
        await notifications.SendAsync(order.CustomerId, "Заказ создан", ct);
    }
}
```

Теперь тест подставляет список в памяти, фейковый отправитель и `FakeTimeProvider` — и проверяет логику за миллисекунды.

## Что именно инвертируется

Инвертируется **направление зависимости между слоями**, а не порядок вызовов.

```
Было (зависимость вниз):
   Application  ──►  Infrastructure (EF Core, HTTP, SMTP)

Стало (зависимость вверх):
   Application  ◄──  Infrastructure
        │
        └── объявляет IOrderRepository, INotificationSender
            Infrastructure их реализует и ссылается на Application
```

Ключевой момент, который обычно упускают: недостаточно «завести интерфейс». Важно, **где он объявлен**. Если `IOrderRepository` лежит в инфраструктурной сборке, приложение по-прежнему на неё ссылается — инверсии нет, есть только лишний файл.

```
Alif.ServiceShop.Domain          — сущности, правила. Не ссылается ни на кого.
Alif.ServiceShop.Application     — сценарии + интерфейсы IOrderRepository, IClock.
Alif.ServiceShop.Infrastructure  — EF Core, HTTP-клиенты. Ссылается на Application.
Alif.ServiceShop.Api             — композиционный корень: собирает всё вместе.
```

Проверяется это архитектурным тестом: «сборка Application не ссылается на Microsoft.EntityFrameworkCore» ([[Связанность и связность (coupling, cohesion)]]).

## Три термина, которые путают

| Термин | Что это |
|---|---|
| **DIP** (Dependency Inversion Principle) | принцип: зависеть от абстракций, абстракции принадлежат потребителю |
| **IoC** (Inversion of Control) | общая идея: управление передаётся фреймворку/окружению, а не пишется в коде («не звони нам, мы позвоним») |
| **DI** (Dependency Injection) | техника: зависимости передаются извне — через конструктор, свойство или метод |
| **IoC-контейнер** | инструмент, автоматизирующий DI: `IServiceCollection` в ASP.NET Core |

DI можно делать без контейнера (руками, в `Main`), а контейнер сам по себе не гарантирует соблюдения DIP: если интерфейсы объявлены в инфраструктуре, ничего не инвертировано.

## Способы внедрения

```csharp
// 1. Через конструктор — основной способ (обязательные зависимости)
public sealed class OrderService(IOrderRepository repository) { }

// 2. Через метод — если зависимость нужна только в одной операции
public Task ExportAsync(IReportRenderer renderer, CancellationToken ct) => ...;

// 3. Через свойство — только для необязательных зависимостей с разумным умолчанием
public ILogger Logger { get; set; } = NullLogger.Instance;
```

Конструктор предпочтителен, потому что делает зависимости **обязательными и видимыми**: объект нельзя создать в неработоспособном состоянии, а разросшийся список параметров сразу сигнализирует, что класс делает слишком много.

### Антипаттерн: локатор служб

```csharp
// Плохо: зависимость спрятана, её не видно в подписи
public sealed class OrderService
{
    public void Create(Order order)
    {
        var repo = ServiceLocator.Resolve<IOrderRepository>();   // сюрприз в рантайме
        repo.Add(order);
    }
}
```

Проблемы: зависимости не видны в конструкторе, поэтому тест падает уже во время выполнения; класс зависит от контейнера, то есть от инфраструктуры; отсутствующую регистрацию компилятор не поймает. То же относится к `IServiceProvider`, внедрённому напрямую: это тот же локатор, только замаскированный.

Исключения, где обращение к провайдеру допустимо: фабрики (создание объекта по данным в рантайме), фоновые службы, создающие scope на каждую итерацию, и сам композиционный корень.

## Композиционный корень

Единственное место, где приложение знает и абстракции, и реализации, — точка сборки:

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddSingleton(TimeProvider.System);
builder.Services.AddScoped<IOrderRepository, EfOrderRepository>();
builder.Services.AddScoped<INotificationSender, EmailNotificationSender>();
builder.Services.AddScoped<OrderService>();

// Декораторы навешиваются здесь же — порядок явный
builder.Services.Decorate<IOrderRepository, CachingOrderRepository>();
```

Правило: **проводка живёт в одном месте и только там**. Регистрации, разбросанные по коду, превращают приложение в набор скрытых зависимостей. Для модульного монолита каждый модуль публикует один метод-расширение (`AddOrdersModule`), внутри которого регистрирует свои `internal`-типы.

Про жизненные циклы (`Singleton`, `Scoped`, `Transient`) и типичные ошибки вроде захваченной зависимости — [[Жизненные циклы сервисов: Singleton, Scoped, Transient]] и [[Captive dependency и типичные ошибки DI]].

## Абстракции, которые не текут

Плохая абстракция раскрывает деталь и связывает потребителя с технологией:

```csharp
// Течёт: контракт домена завязан на EF Core и на модель ленивой загрузки
public interface IOrderRepository
{
    IQueryable<Order> Query();                       // LINQ-провайдер, поведение зависит от ORM
    DbSet<Order> Orders { get; }                     // прямая утечка типа EF Core
    Task<Order> GetAsync(long id, bool includeItems); // деталь загрузки в контракте
}

// Не течёт: контракт выражен в терминах задачи
public interface IOrderRepository
{
    Task<Order?> FindAsync(long id, CancellationToken ct);
    Task<IReadOnlyList<Order>> FindOverdueAsync(DateTimeOffset asOf, CancellationToken ct);
    Task AddAsync(Order order, CancellationToken ct);
}
```

Признак утечки: реализовать интерфейс другой технологией (Dapper, список в памяти, HTTP-клиент) невозможно или бессмысленно. Другие частые утечки — `HttpResponseMessage`, `SqlParameter`, `Stream` с ожиданием конкретной семантики, атрибуты ORM на доменных сущностях.

Отдельный спорный случай — стоит ли вообще заводить репозиторий поверх EF Core: `DbContext` сам по себе является реализацией паттернов «Репозиторий» и «Единица работы» ([[Repository и Unit of Work: нужны ли поверх EF Core]]).

## Когда абстракция не нужна

DIP — не требование заворачивать всё в интерфейсы. Абстракция оправдана там, где есть **граница**: другой процесс, другая технология, недетерминированность, необходимость подмены.

| Заворачивать | Не заворачивать |
|---|---|
| база данных, HTTP-клиенты, брокер | `List<T>`, `StringBuilder`, `Math` |
| файловая система, часы, генератор идентификаторов | value objects, DTO |
| внешние платёжные и SMS-шлюзы | чистые функции без зависимостей |
| то, что подменяется по конфигурации | классы одного модуля, меняющиеся вместе |

Признак лишней абстракции — интерфейс с единственной реализацией, который меняется всегда вместе с ней и существует только «чтобы было». Он не развязывает, а добавляет файл и переход при чтении ([[Интерфейсы]]).

Для часов, случайных чисел и файловой системы в .NET уже есть готовые абстракции: `TimeProvider` (.NET 8) с `FakeTimeProvider` для тестов, `Random.Shared`, `IFileSystem` из сторонних библиотек. Свои `IClock` писать больше не нужно.

> [!warning] Подводные камни
> - **Интерфейс в инфраструктуре.** Самая частая ошибка: интерфейсы есть, а зависимость по-прежнему направлена вниз. Абстракция принадлежит потребителю.
> - **Локатор служб и внедрённый `IServiceProvider`.** Зависимости скрыты, ошибки всплывают в рантайме.
> - **Абстракция ради абстракции.** Интерфейс на каждый класс удваивает число файлов и ничего не даёт.
> - **Текущая абстракция.** `IQueryable`, `DbSet`, `HttpResponseMessage` в контракте связывают потребителя с технологией сильнее, чем прямой вызов.
> - **Разбросанная регистрация.** Проводка в десяти местах вместо композиционного корня.
> - **`new` конкретного сервиса внутри доменного типа.** Домен начинает зависеть от инфраструктуры, даже если формально интерфейсы есть.
> - **Слишком много зависимостей в конструкторе.** Не проблема DI, а сигнал низкой связности: класс делает слишком много.
> - **Подмена реализации ради тестов там, где проще реальный объект.** Мок для чистой функции только усложняет тест.

> [!example] Как делают в бою
> Структура сборок задаёт направление зависимостей физически: домен ни на что не ссылается, приложение объявляет нужные ему контракты, инфраструктура их реализует и ссылается вверх, а хост собирает всё в композиционном корне. Это проверяется архитектурным тестом в CI — договорённостями такие границы не держатся.
> Контракты пишут в терминах задачи, а не технологии: `FindOverdueAsync(asOf)` вместо `Query()`, `PublishAsync(@event)` вместо `GetChannel()`. Тогда замена ORM или брокера остаётся работой инфраструктурного слоя.
> Тестируемость получается побочным эффектом, а не целью: если единственное обоснование интерфейса — «чтобы мокать», стоит проверить, не проще ли использовать реальный объект (например, EF Core с SQLite in-memory или Testcontainers) — интеграционный тест на настоящей базе часто полезнее мока ([[Testcontainers]]).
> И практическая мелочь, экономящая много времени: `TimeProvider` вместо `DateTime.Now` с первого дня. Недетерминированное время — самая частая причина плавающих тестов и багов с часовыми поясами.

## Вопросы с собеседований

> [!question]- В чём суть принципа инверсии зависимостей?
> В двух утверждениях: модули верхнего уровня не должны зависеть от модулей нижнего уровня — оба зависят от абстракций; и абстракции не должны зависеть от деталей — детали зависят от абстракций. Практический смысл в том, что владельцем контракта становится потребитель: интерфейс `IOrderRepository` объявляется в слое, который им пользуется, а инфраструктура его реализует и ссылается на этот слой. Именно поэтому направление зависимости между сборками разворачивается по сравнению с наивной многослойной схемой, где приложение ссылалось на инфраструктуру. Типичная ошибка при внедрении — объявить интерфейсы, но оставить их в инфраструктурной сборке: тогда ссылки идут по-прежнему вниз, и инверсии не происходит.

> [!question]- Чем отличаются DIP, IoC и DI?
> DIP — принцип проектирования о направлении зависимостей и владении абстракциями. IoC — более широкая идея инверсии управления: не приложение вызывает фреймворк, а фреймворк вызывает приложение (обработчики событий, шаблонный метод, конвейер middleware — всё это IoC без всякого DI). DI — конкретная техника реализации DIP: зависимости передаются объекту извне, чаще всего через конструктор. IoC-контейнер — инструмент, автоматизирующий DI, но его наличие не означает соблюдения DIP: можно зарегистрировать в контейнере конкретные типы, объявить интерфейсы в инфраструктуре и не получить никакой инверсии. Верно и обратное: DI прекрасно делается вручную в композиционном корне, без контейнера, и для небольших приложений это нормальный вариант.

> [!question]- Почему локатор служб считается антипаттерном?
> Потому что он скрывает зависимости. При внедрении через конструктор список зависимостей виден в подписи: компилятор не даст создать объект без них, а разросшийся конструктор сигнализирует о проблемах с ответственностью класса. Локатор превращает это в обращение внутри метода: понять, что нужно классу, можно только прочитав всю реализацию, тесты падают в рантайме из-за незарегистрированной службы, а сам класс начинает зависеть от контейнера, то есть от инфраструктуры — ровно то, что DIP пытается устранить. Внедрённый `IServiceProvider` — та же проблема в замаскированном виде. Законные исключения существуют: фабрики, создающие объекты по данным времени выполнения, фоновые службы, создающие область на каждую итерацию, и сам композиционный корень, который по определению знает контейнер.

> [!question]- Как понять, что абстракция «течёт»?
> По тому, можно ли реализовать её другой технологией без искажений. Если интерфейс возвращает `IQueryable<T>`, `DbSet<T>`, `HttpResponseMessage` или `SqlParameter`, то потребитель фактически программирует против конкретной библиотеки: поведение зависит от LINQ-провайдера, от семантики отложенного выполнения, от деталей HTTP. Другие признаки: в контракте есть параметры, описывающие способ загрузки данных (`includeItems`), доменные сущности размечены атрибутами ORM, а реализация «в памяти» для тестов оказывается либо невозможной, либо ведёт себя иначе. Хорошая абстракция выражена в терминах задачи: `FindOverdueAsync(asOf, ct)`, `PublishAsync(@event, ct)` — их одинаково честно реализуют и EF Core, и Dapper, и список в памяти.

## Задачи

### Задача 1. Инвертировать зависимости

```csharp
namespace App.Infrastructure;

public sealed class ReportGenerator
{
    private readonly SqlConnection _connection = new(Config.ConnectionString);

    public byte[] Generate(long customerId)
    {
        var orders = LoadOrders(customerId);
        var html = string.Join("", orders.Select(o => $"<tr><td>{o.Id}</td></tr>"));
        File.WriteAllText($"/reports/{customerId}_{DateTime.Now:yyyyMMdd}.html", html);
        return System.Text.Encoding.UTF8.GetBytes(html);
    }
}
```

> [!success]- Решение
> ```csharp
> // Слой приложения: контракты объявлены здесь, реализаций не знает
> namespace App.Application;
>
> public interface IOrderReader
> {
>     Task<IReadOnlyList<Order>> GetByCustomerAsync(long customerId, CancellationToken ct);
> }
>
> public interface IReportStorage
> {
>     Task SaveAsync(string name, ReadOnlyMemory<byte> content, CancellationToken ct);
> }
>
> public sealed class ReportGenerator(IOrderReader orders, IReportStorage storage, TimeProvider clock)
> {
>     public async Task<byte[]> GenerateAsync(long customerId, CancellationToken ct)
>     {
>         var items = await orders.GetByCustomerAsync(customerId, ct);
>         var html = Render(items);
>         var bytes = System.Text.Encoding.UTF8.GetBytes(html);
>
>         var name = $"{customerId}_{clock.GetUtcNow():yyyyMMdd}.html";
>         await storage.SaveAsync(name, bytes, ct);
>         return bytes;
>     }
>
>     private static string Render(IReadOnlyList<Order> orders) => ...;
> }
> ```
> Что изменилось: генератор переехал в слой приложения и зависит только от контрактов, объявленных там же; SQL-соединение и запись файла ушли в инфраструктуру (`SqlOrderReader`, `FileReportStorage`), которая ссылается на приложение, а не наоборот; `DateTime.Now` заменён на `TimeProvider` — тест теперь детерминирован и не зависит от часового пояса сервера; хранилище абстрагировано так, что завтра это может быть S3 без изменений в генераторе; добавлены асинхронность и токен отмены, потому что операции идут в базу и на диск. Проводка (`AddScoped<IOrderReader, SqlOrderReader>()`) живёт в композиционном корне.

### Задача 2. Решить, нужна ли абстракция

Для каждой зависимости реши, стоит ли вводить интерфейс: 1) `HttpClient` к платёжному шлюзу; 2) `StringBuilder` внутри метода форматирования; 3) `DateTime.UtcNow`; 4) `IMemoryCache`; 5) калькулятор НДС — чистая функция без зависимостей.

> [!success]- Решение
> 1. **Да.** Внешняя система, сеть, недетерминированность, необходимость тестировать сценарии отказа и таймаутов. Но абстрагировать надо не `HttpClient`, а операцию: `IPaymentGateway.ChargeAsync(...)`, чтобы в контракте не осталось `HttpResponseMessage`.
> 2. **Нет.** Деталь реализации внутри метода, детерминированная, без побочных эффектов. Абстракция здесь — чистые накладные расходы.
> 3. **Да, но готовой.** Недетерминированность делает тесты плавающими, поэтому время внедряют. Свой `IClock` писать не нужно: в .NET 8 есть `TimeProvider` и `FakeTimeProvider` для тестов.
> 4. **Обычно нет.** `IMemoryCache` уже интерфейс, и в тестах можно подставить реальный экземпляр `MemoryCache` — он работает в памяти и детерминирован. Своя обёртка нужна, только если планируется переход на распределённый кеш с иной семантикой, и тогда абстрагируют операцию (`IOrderCache`), а не кеш вообще.
> 5. **Нет.** Чистая функция тестируется напрямую, подменять нечего. Интерфейс понадобится, только если появятся варианты правил (разные ставки по странам) — и тогда это будет стратегия, а не абстракция ради тестов.

## Итог

- DIP: и верхний, и нижний уровни зависят от абстракций; абстракция принадлежит потребителю, а не реализации.
- Инвертируется направление ссылок между сборками; проверяется архитектурным тестом.
- DIP — принцип, IoC — идея передачи управления, DI — техника; контейнер сам по себе DIP не обеспечивает.
- Внедрение через конструктор делает зависимости обязательными и видимыми; локатор служб их прячет.
- Вся проводка живёт в композиционном корне, по модулю на метод-расширение.
- Абстракция не должна течь: `IQueryable`, `DbSet`, `HttpResponseMessage` в контракте связывают с технологией.
- Заворачивать надо границы (БД, сеть, время, файлы), а не всё подряд; для времени есть готовый `TimeProvider`.
- Много зависимостей в конструкторе — не проблема DI, а сигнал низкой связности класса.
