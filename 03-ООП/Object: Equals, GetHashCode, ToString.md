# Object: Equals, GetHashCode, ToString

> [!abstract] Коротко
> От `System.Object` наследуются все типы, и три его виртуальных метода определяют, как объект ведёт себя в сравнениях, в хеш-таблицах и в логах. По умолчанию `Equals` для класса сравнивает ссылки, для структуры — поля (медленно, через рефлексию, если структура содержит ссылки). Главное правило, которое спрашивают на каждом собеседовании: **если переопределяешь `Equals`, обязан переопределить `GetHashCode`**, потому что `Dictionary` и `HashSet` сначала ищут корзину по хешу и только потом сравнивают. Нарушение этого правила даёт объект, который «есть в словаре, но не находится».

## Зачем это нужно

```csharp
public class Money            // Equals не переопределён
{
    public decimal Amount { get; init; }
    public string Currency { get; init; } = "";
}

var a = new Money { Amount = 100, Currency = "UZS" };
var b = new Money { Amount = 100, Currency = "UZS" };

Console.WriteLine(a.Equals(b));                 // False — сравнение ссылок
Console.WriteLine(new HashSet<Money> { a, b }.Count);   // 2 — «дубликат» не распознан
Console.WriteLine(a);                            // MyApp.Money — бесполезно в логе
```

Три симптома одной причины: тип, который по смыслу является значением, ведёт себя как ссылка. Это ломает поиск в коллекциях, `Distinct()`, сравнение в тестах и читаемость логов.

## Что есть у Object

| Член | Виртуальный | Что делает по умолчанию |
|---|---|---|
| `Equals(object?)` | да | классы — сравнение ссылок; структуры — сравнение полей |
| `GetHashCode()` | да | классы — по идентичности объекта; структуры — по полям |
| `ToString()` | да | полное имя типа |
| `GetType()` | нет | фактический тип объекта |
| `MemberwiseClone()` | нет, `protected` | поверхностная копия |
| `Finalize()` | да, `protected` | финализатор ([[Финализаторы и SafeHandle]]) |
| `ReferenceEquals(a, b)` | статический | сравнение ссылок, игнорируя перегрузки |
| `Equals(a, b)` | статический | безопасный к `null` вызов `a.Equals(b)` |

Значимые типы наследуют реализации от `System.ValueType`, который сравнивает поля. Быстрый путь (побитовое сравнение) применяется, только если структура не содержит ссылочных полей и не имеет «дырок» выравнивания; иначе поля обходятся **рефлексией** — это в разы медленнее и создаёт упаковку. Поэтому структура, участвующая в сравнениях или используемая как ключ, обязана переопределять `Equals`/`GetHashCode` или быть `record struct`.

## Контракт Equals

Реализация обязана удовлетворять пяти правилам, иначе коллекции и алгоритмы начнут вести себя непредсказуемо:

1. **Рефлексивность:** `x.Equals(x)` — всегда `true`.
2. **Симметричность:** `x.Equals(y) == y.Equals(x)`.
3. **Транзитивность:** если `x.Equals(y)` и `y.Equals(z)`, то `x.Equals(z)`.
4. **Согласованность:** повторные вызовы дают тот же результат, пока объекты не изменились.
5. **`x.Equals(null)` — всегда `false`** (и не бросает исключение).

Плюс требование к `GetHashCode`: **равные объекты обязаны иметь одинаковый хеш**. Обратное неверно — разные объекты могут иметь одинаковый хеш (коллизия), это нормально.

### Канонический ручной вариант

```csharp
public sealed class Money : IEquatable<Money>
{
    public required decimal Amount { get; init; }
    public required string Currency { get; init; }

    // Типизированная версия: без упаковки, вызывается коллекциями через EqualityComparer<T>.Default
    public bool Equals(Money? other)
    {
        if (other is null) return false;
        if (ReferenceEquals(this, other)) return true;      // быстрый путь
        return Amount == other.Amount
            && string.Equals(Currency, other.Currency, StringComparison.Ordinal);
    }

    public override bool Equals(object? obj) => Equals(obj as Money);

    public override int GetHashCode() => HashCode.Combine(Amount, Currency);

    public static bool operator ==(Money? left, Money? right) => Equals(left, right);
    public static bool operator !=(Money? left, Money? right) => !Equals(left, right);

    public override string ToString() => $"{Amount:0.##} {Currency}";
}
```

Разбор деталей:

- **`IEquatable<T>`** нужен, чтобы коллекции вызывали типизированную версию без упаковки; `Dictionary`, `HashSet`, `List.Contains` используют `EqualityComparer<T>.Default`, который её находит.
- **`HashCode.Combine`** (начиная с .NET Core 2.1) заменяет ручные `hash * 31 + field`: он даёт хорошее распределение и рандомизирован между запусками процесса. Для большего числа полей — `HashCode` в виде структуры с `Add`.
- **Операторы `==`/`!=`** переопределяют не обязательно, но если не переопределить, `a == b` для класса будет сравнивать ссылки, а `a.Equals(b)` — значения. Такое расхождение — источник багов, поэтому либо переопределяй оба, либо не переопределяй ни один и явно используй `Equals`.
- **`sealed`** упрощает жизнь: с наследованием симметричность равенства ломается (см. ниже).

### Или просто record

```csharp
public readonly record struct Money(decimal Amount, string Currency);
```

Одна строка вместо тридцати: компилятор генерирует `Equals`, `GetHashCode`, `IEquatable<T>`, операторы, `ToString` и `Deconstruct`. В новом коде значения объявляют именно так, а ручная реализация остаётся для случаев, где нужно нестандартное сравнение (например, `Currency` без учёта регистра) — [[Записи (record) и структуры]].

## Почему GetHashCode обязателен

```
Dictionary.Add(key, value):
   1. hash = key.GetHashCode()
   2. bucket = hash % capacity          ← корзина выбирается ТОЛЬКО по хешу
   3. в корзине сравнить ключи через Equals
```

Если `Equals` переопределён, а `GetHashCode` нет, то два «равных» объекта получают разные хеши, попадают в разные корзины — и поиск не находит ничего:

```csharp
var dict = new Dictionary<Money, string>();
dict[new Money { Amount = 100, Currency = "UZS" }] = "сто";
Console.WriteLine(dict.ContainsKey(new Money { Amount = 100, Currency = "UZS" }));
// Без GetHashCode: False. С ним: True.
```

Компилятор выдаёт предупреждение CS0659 при переопределении `Equals` без `GetHashCode` — игнорировать его нельзя.

### Требования к хешу

- **Согласованность с `Equals`** — обязательно.
- **Стабильность на время жизни в коллекции**: хеш не должен меняться, пока объект лежит в словаре или множестве. Отсюда правило — считать хеш только по **неизменяемым** полям.
- **Хорошее распределение**: `GetHashCode() => 0` формально корректен (равные объекты дают равные хеши), но превращает словарь в связный список — все ключи в одну корзину, поиск деградирует до `O(n)` ([[Dictionary и HashSet изнутри]]).
- **Не сохранять хеш вне процесса.** Хеш строк в .NET рандомизирован при каждом запуске (защита от hash-flooding атак), поэтому `"abc".GetHashCode()` даёт разные значения в разных запусках. Для стабильного хеша нужен явный алгоритм (SHA-256, xxHash), а не `GetHashCode`.

```csharp
// Мина: хеш зависит от изменяемого поля
public class MutableKey
{
    public string Name { get; set; } = "";
    public override int GetHashCode() => Name.GetHashCode();
    public override bool Equals(object? o) => o is MutableKey k && k.Name == Name;
}

var key = new MutableKey { Name = "a" };
var set = new HashSet<MutableKey> { key };
key.Name = "b";                       // хеш изменился, объект остался в старой корзине
Console.WriteLine(set.Contains(key)); // False — объект «потерян» внутри собственного множества
```

Лечение: ключи должны быть иммутабельными. Это одна из главных причин, по которым value objects делают `readonly record struct`.

## Равенство и наследование

```csharp
public class Point2D
{
    public int X { get; init; }
    public int Y { get; init; }
    public override bool Equals(object? obj) => obj is Point2D p && p.X == X && p.Y == Y;
    public override int GetHashCode() => HashCode.Combine(X, Y);
}

public sealed class Point3D : Point2D
{
    public int Z { get; init; }
    public override bool Equals(object? obj) => obj is Point3D p && base.Equals(p) && p.Z == Z;
    public override int GetHashCode() => HashCode.Combine(X, Y, Z);
}

var a = new Point2D { X = 1, Y = 2 };
var b = new Point3D { X = 1, Y = 2, Z = 3 };
Console.WriteLine(a.Equals(b));   // True  — Point2D видит совпадение X и Y
Console.WriteLine(b.Equals(a));   // False — Point3D требует тип Point3D
```

Симметричность нарушена, и коллекции начинают вести себя по-разному в зависимости от порядка сравнения. Решения:

- **Сравнивать точные типы:** `GetType() == obj.GetType()` вместо `is` — тогда `Point2D` и `Point3D` никогда не равны, симметричность восстановлена;
- **Делать типы `sealed`** — проблема исчезает вместе с наследованием;
- Именно так поступает компилятор для `record`: он генерирует свойство `EqualityContract` с типом и сравнивает его.

Отдельный случай — **сущности** в предметной модели: у них равенство определяется идентификатором, а не полями, и сравнение типов через `GetType()` тоже обязательно ([[Абстрактные классы]], задача про `Entity<TId>`).

## `==` против `Equals`

```csharp
object a = "текст";
object b = string.Concat("тек", "ст");

Console.WriteLine(a == b);              // False — оператор выбран по статическому типу object
Console.WriteLine(a.Equals(b));         // True  — виртуальный вызов String.Equals
Console.WriteLine(Equals(a, b));        // True  — статический Object.Equals, безопасен к null
Console.WriteLine(ReferenceEquals(a, b));// False
```

Ключевое: **оператор `==` разрешается на этапе компиляции по статическим типам операндов**, а `Equals` — виртуальный и разрешается в рантайме. Поэтому в обобщённом коде сравнивать надо не оператором:

```csharp
static bool AreEqual<T>(T x, T y) => EqualityComparer<T>.Default.Equals(x, y);
// x == y в дженерике без ограничений вообще не скомпилируется
```

`EqualityComparer<T>.Default` сам выбирает лучший путь: `IEquatable<T>` без упаковки, если тип его реализует, иначе `object.Equals`.

## ToString

`ToString` — то, что видно в логах, в отладчике, в сообщениях об ошибках и при интерполяции строк. Значение по умолчанию (полное имя типа) бесполезно.

```csharp
public override string ToString() => $"Order #{Id}, {Total:0.##} {Currency}, {Status}";
```

Правила:

- **Коротко и информативно**: идентификатор и пара ключевых полей, а не дамп всего объекта.
- **Без секретов и персональных данных**: строка уедет в логи и трассировку. У `record` `ToString` печатает **все** свойства автоматически — для типов с чувствительными полями его нужно переопределить.
- **Без исключений и тяжёлых вычислений**: `ToString` вызывается отладчиком при просмотре объекта.
- **Инвариантная культура для машинных форматов**; если нужна культура — реализуй `IFormattable` и его `ToString(format, provider)`.
- Для отладки удобнее `[DebuggerDisplay("Order {Id}: {Total}")]` — он не влияет на логи и работает даже без переопределения ([[Отладка: точки останова, watch, immediate]]).

> [!warning] Подводные камни
> - **`Equals` без `GetHashCode`.** Объекты «теряются» в словарях и множествах; предупреждение CS0659 — не формальность.
> - **Хеш по изменяемому полю.** Изменение поля после добавления в коллекцию делает элемент недостижимым.
> - **`GetHashCode() => 0` или по одному малоразличимому полю.** Все ключи в одной корзине, `O(n)` вместо `O(1)`.
> - **Сохранение `GetHashCode` в базу или файл.** Хеш строк рандомизирован между запусками процесса — сохранённые значения перестанут совпадать.
> - **Переопределение `Equals` без `==`.** Два разных смысла у сравнения в одном типе; для `record` компилятор делает и то и другое.
> - **`is` вместо `GetType()` при наследовании.** Нарушается симметричность равенства.
> - **`ToString` с персональными данными.** Особенно у `record`, где он генерируется автоматически по всем свойствам.
> - **Сравнение `double`/`float` в `Equals`.** Наследует все проблемы точности: два «равных» значения могут отличаться в последнем бите.

> [!example] Как делают в бою
> Практика простая: value objects и DTO объявляются как `record`/`readonly record struct`, и вопрос равенства закрывается генерацией. Ручная реализация остаётся для двух случаев — когда нужно нестандартное сравнение (строки без учёта регистра, округление денег до копеек, игнорирование служебных полей) и для сущностей, у которых равенство по идентификатору.
> Для сущностей заводят базовый `Entity<TId>` с равенством по `Id` и типу, а `GetHashCode` считают от `Id` — он неизменяем, поэтому объект не «теряется» в коллекциях даже после изменения остальных полей.
> Когда нужно сравнивать по-разному в разных местах, вместо перегрузки `Equals` пишут отдельный `IEqualityComparer<T>` и передают его в конструктор словаря или в LINQ-метод — тип остаётся с одним «естественным» равенством, а варианты живут снаружи ([[Сравнение объектов: IEquatable, IComparable, компараторы]]).
> `ToString` переопределяют почти у всех доменных типов ради логов, но с оглядкой на приватность: телефон, email и адрес в строку не попадают.

## Вопросы с собеседований

> [!question]- Почему при переопределении `Equals` обязательно переопределять `GetHashCode`?
> Потому что хеш-коллекции (`Dictionary`, `HashSet`, группировки LINQ) ищут не перебором: сначала по хешу вычисляется корзина, и только внутри неё ключи сравниваются через `Equals`. Если два объекта равны по `Equals`, но имеют разные хеши, они попадают в разные корзины, и поиск второго объекта не дойдёт до сравнения — элемент «есть в словаре, но не находится». Формальный контракт: равные объекты обязаны возвращать одинаковый хеш; обратное не требуется — коллизии допустимы и обрабатываются сравнением внутри корзины. Компилятор предупреждает об этом (CS0659). Дополнительные требования: хеш должен быть стабилен, пока объект находится в коллекции (поэтому считать его нужно по неизменяемым полям), и должен хорошо распределять значения — константа технически корректна, но превращает словарь в список.

> [!question]- Чем `==` отличается от `Equals` и когда что использовать?
> `==` — статический оператор, перегрузка которого выбирается компилятором по **статическим** типам операндов; `Equals` — виртуальный метод, разрешаемый в рантайме по фактическому типу. Отсюда классический пример: две одинаковые строки, присвоенные переменным типа `object`, дают `False` при `==` (выбрана перегрузка для `object`, то есть сравнение ссылок) и `True` при `Equals`. Практические правила: для строк и записей `==` переопределён и означает сравнение по значению; для обычных классов `==` по умолчанию сравнивает ссылки; в обобщённом коде оператор `==` вообще недоступен без ограничений, и сравнивать нужно через `EqualityComparer<T>.Default.Equals`. Если переопределяешь `Equals` у класса, стоит переопределить и операторы — иначе в одном типе окажутся два разных смысла сравнения.

> [!question]- Как устроено равенство по умолчанию у классов и структур?
> У классов `object.Equals` сравнивает ссылки: два объекта равны, только если это один и тот же объект. У структур работает `ValueType.Equals`, который сравнивает поля: если структура не содержит ссылочных полей и её раскладка не имеет промежутков от выравнивания, рантайм применяет быстрое побитовое сравнение памяти, иначе обходит поля через рефлексию — это в разы медленнее и вдобавок упаковывает значения. `ValueType.GetHashCode` тоже реализован консервативно и может учитывать не все поля, что даёт плохое распределение. Поэтому структура, участвующая в сравнениях или используемая как ключ словаря, должна либо переопределять `Equals`/`GetHashCode` и реализовывать `IEquatable<T>`, либо объявляться как `record struct`, где компилятор сгенерирует прямое сравнение полей.

> [!question]- Как правильно реализовать равенство при наследовании?
> Основная проблема — симметричность: если базовый класс сравнивает только свои поля через `is`, то `base.Equals(derived)` вернёт `true`, а `derived.Equals(base)` — `false`, что нарушает контракт и приводит к разному поведению коллекций в зависимости от порядка операндов. Надёжные решения: сравнивать точные типы через `GetType() == obj.GetType()`, а не `is`; или, что проще, делать типы `sealed` и не наследовать типы-значения вовсе. Компилятор для `record` решает это через сгенерированное свойство `EqualityContract`, которое возвращает тип и участвует в сравнении. Отдельный случай — доменные сущности: там равенство определяется идентификатором, а не полями, но сравнение типов всё равно обязательно, иначе `Order` и `Customer` с одинаковым `Id` окажутся равными.

## Задачи

### Задача 1. Найти три ошибки

```csharp
public class Product
{
    public string Sku { get; set; } = "";
    public string Name { get; set; } = "";

    public override bool Equals(object? obj) => obj is Product p && p.Sku == Sku;
    public override int GetHashCode() => Sku.GetHashCode() + Name.GetHashCode();
}
```

> [!success]- Решение
> Ошибки: `GetHashCode` учитывает `Name`, которого нет в `Equals` — два равных объекта с разными именами получат разные хеши и «потеряются» в словаре; оба поля изменяемые, поэтому хеш меняется после добавления в коллекцию; сложение хешей даёт плохое распределение и может переполниться (формально безопасно в unchecked, но качество распределения страдает). Плюс нет `IEquatable<Product>` — сравнения идут через упаковку.
> ```csharp
> public sealed class Product : IEquatable<Product>
> {
>     public required string Sku { get; init; }        // ключ неизменяем
>     public required string Name { get; init; }
>
>     public bool Equals(Product? other)
>         => other is not null && string.Equals(Sku, other.Sku, StringComparison.Ordinal);
>
>     public override bool Equals(object? obj) => Equals(obj as Product);
>     public override int GetHashCode() => Sku.GetHashCode(StringComparison.Ordinal);
>     public override string ToString() => $"{Sku} ({Name})";
> }
> ```
> Хеш считается ровно от того поля, что участвует в `Equals`; свойства стали `init`, поэтому ключ стабилен; сравнение строк ординальное и явное; добавлен `IEquatable<T>` и осмысленный `ToString`.

### Задача 2. Сравнение по-разному в разных местах

Нужно, чтобы в одном месте товары сравнивались по артикулу, а в другом — по артикулу и складу. Как это сделать, не переопределяя `Equals` дважды?

> [!success]- Решение
> ```csharp
> public sealed class ProductBySkuAndWarehouseComparer : IEqualityComparer<Product>
> {
>     public static readonly ProductBySkuAndWarehouseComparer Instance = new();
>
>     public bool Equals(Product? x, Product? y)
>         => x is not null && y is not null
>            && string.Equals(x.Sku, y.Sku, StringComparison.Ordinal)
>            && x.WarehouseId == y.WarehouseId;
>
>     public int GetHashCode(Product obj) => HashCode.Combine(obj.Sku, obj.WarehouseId);
> }
>
> var set = new HashSet<Product>(ProductBySkuAndWarehouseComparer.Instance);
> var grouped = products.GroupBy(p => p, ProductBySkuAndWarehouseComparer.Instance);
> var distinct = products.Distinct(ProductBySkuAndWarehouseComparer.Instance);
> ```
> У типа остаётся одно «естественное» равенство (по артикулу), а альтернативное живёт снаружи и передаётся туда, где нужно. Это правильнее, чем пытаться уместить оба смысла в `Equals`: коллекции, LINQ и сортировки принимают компаратор параметром именно для таких случаев. Экземпляр компаратора делают статическим синглтоном — он не имеет состояния, и создавать его на каждый вызов незачем. Подробнее — [[Сравнение объектов: IEquatable, IComparable, компараторы]].

## Итог

- Все типы наследуют `Equals`, `GetHashCode`, `ToString`; по умолчанию классы сравниваются по ссылке, структуры — по полям (медленно).
- Контракт `Equals`: рефлексивность, симметричность, транзитивность, согласованность, `false` для `null`.
- Переопределил `Equals` — обязан переопределить `GetHashCode`: корзина в хеш-таблице выбирается только по хешу.
- Хеш считается по неизменяемым полям, тем же, что участвуют в `Equals`; `HashCode.Combine` вместо ручных формул.
- Хеш строк рандомизирован между запусками — его нельзя сохранять и передавать наружу.
- `==` разрешается статически, `Equals` — виртуально; в дженериках сравнивают через `EqualityComparer<T>.Default`.
- При наследовании сравнивай `GetType()`, а лучше делай типы `sealed`; `record` решает это генерацией.
- Альтернативные правила сравнения выносят в `IEqualityComparer<T>`, а не в `Equals`.
