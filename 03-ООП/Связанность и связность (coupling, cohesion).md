# Связанность и связность (coupling, cohesion)

> [!abstract] Коротко
> **Связанность** (coupling) — насколько сильно модули зависят друг от друга; её снижают. **Связность** (cohesion) — насколько элементы внутри модуля относятся к одной задаче; её повышают. Закон Деметры («не разговаривай с незнакомцами») и «Tell, Don't Ask» — не отдельная теория, а конкретные проявления этой модели на уровне одного вызова: оба правила про то, что метод не должен знать устройство чужих объектов и принимать решения на основе их внутренностей. Практический индикатор — стоимость изменения: сколько файлов правим ради одного требования и по скольким причинам меняется один файл.

## Зачем это знать

Связанность и связность объясняют, почему один проект остаётся понятным через два года, а другой — нет. Единственная ответственность из [[SOLID]] — это про связность, инверсия зависимостей — про связанность. Закон Деметры и Tell-Don't-Ask — их практическое приложение к отдельному вызову: то же самое «слабая связанность, сильная связность», только на уровне `a.B.C.D()`, а не на уровне модулей.

```
Требование: «добавить поле «комментарий» к заказу»

Слабая связанность:  правим модуль заказов — 3 файла, 20 минут.
Сильная связанность: правим модуль заказов, потом отчёты, потом уведомления,
                     потом три теста, которые мокали внутренности заказа, — 15 файлов, полдня.
```

## Модель

### Связанность: степени

| Степень | Что это | Пример в C# |
|---|---|---|
| Содержательная | лезет во внутренности другого | рефлексия по приватным полям |
| Общая | общие глобальные данные | статический изменяемый синглтон |
| Внешняя | общий формат/протокол | два сервиса читают одну таблицу |
| Управляющая | один модуль управляет ветвлением другого | `bool`-флаг, меняющий поведение метода |
| По структуре | передан объект, а нужна пара полей | метод принимает `Order`, использует только `Total` |
| По данным | передаются только нужные значения | `CalculateFee(decimal amount)` |
| Нет связи | модули не знают друг о друге | взаимодействие через события |

Идеал — данные и события; в реальном коде цель — не опуститься ниже уровня «по структуре».

### Связность: степени

| Степень | Что объединяет | Пример |
|---|---|---|
| Случайная | ничего | `Helpers`, `Utils` |
| Логическая | похожие по типу действия | `Validators` со всеми валидаторами |
| Коммуникационная | работают с одними данными | всё, что читает таблицу заказов |
| Последовательная | выход одного — вход другого | парсер → валидатор → маппер |
| Функциональная | решают одну задачу | `OrderPricing` |

Тест на связность: **описать класс одним предложением без союза «и»**. «Создаёт заказы **и** экспортирует в Excel» — два класса.

### Закон Деметры — coupling на уровне вызова

Метод может обращаться только к: себе (`this`), своим полям, своим параметрам, объектам, которые сам создал. Всё остальное — «незнакомцы».

```csharp
// Нарушение: три «прыжка» вглубь чужих типов
if (order.Customer.Address.Country == "UZ") { }

// Метод знает только про Order
if (order.IsDomestic) { }   // внутри: Customer.IsFromCountry("UZ")
```

Это не про количество точек. Fluent-билдеры (`services.AddControllers().AddJsonOptions(...)`), LINQ-цепочки и доступ к полям DTO (`request.Address.City`) законом не запрещены — у них нет поведения и нет чужого решения, принятого снаружи. Нарушение — когда вызывающий на основе чужих внутренностей принимает решение, которое должен принимать владелец данных. Это ровно **feature envy** (зависть к чужим данным): метод чаще трогает поля другого объекта, чем свои — сигнал, что поведение живёт не там, где данные.

### Tell, Don't Ask — cohesion на уровне вызова

Не запрашивай состояние объекта, чтобы решить, что с ним делать, — скажи ему, что сделать.

```csharp
// Ask: правило снаружи, будет продублировано в переводах, возвратах, комиссиях
if (account.Balance >= amount && !account.IsBlocked) account.Balance -= amount;

// Tell: правило в одном месте
account.Withdraw(new Money(amount, "UZS"));
```

Систематическое нарушение даёт анемичную модель: классы-структуры данных плюс сервисы со всей логикой. Это не всегда плохо — для CRUD, где правил мало, богатая модель добавляет только слои. Проблема возникает, когда правило начинает дублироваться по сервисам ([[Антипаттерны и code smells]], [[DDD: тактические паттерны]]).

## Решения

| Признак высокой связанности | Как исправить |
|---|---|
| `new` конкретной зависимости внутри класса | внедрять интерфейс через конструктор |
| Статическое изменяемое состояние | явная зависимость (`IUserContext` вместо `static CurrentUser`) |
| Булев флаг, меняющий поведение метода | разделить на два метода или передать объект намерения |
| Метод принимает объект, использует одно поле | принимать значение вместо объекта («по данным» вместо «по структуре») |
| Цепочка `a.B.C.D` с решением на её основе | перенести поведение к данным — свойство/метод на ближайшем соседе |
| Дублирующаяся проверка состояния перед изменением (`Ask`) | заменить на `Tell`-метод, инкапсулирующий правило |
| Мок, возвращающий мок, возвращающий мок | признак нарушения закона Деметры — переносить поведение, а не наращивать стабы |
| Утечка инфраструктурных типов в контракт домена | контракт домена — свои DTO, не `DbDataReader`/`HttpResponseMessage` |

> [!example] В ServiceShop
> Правило соблюдается на уровне модулей буквально: каждый модуль (`Orders`, `Cart`, ...) выставляет наружу ровно один фасад с `ExecuteCommandAsync`/`ExecuteQueryAsync`. Обратиться к репозиторию или `DbContext` другого модуля напрямую нельзя — их не видно, потому что они сидят в своём Autofac-контейнере ([[ServiceShop: модульный монолит и изоляция модулей]]). Это закон Деметры, доведённый до архитектурной границы: код общается только с непосредственным соседом (фасадом), а не «прыгает» внутрь чужого модуля. То же самое правило, которое на уровне метода запрещает `order.Customer.Address.City`, на уровне модулей запрещает `OrdersDbContext` из кода `Cart`.

> [!warning] Где ошибаются
> - **Агент часто** пишет цепочку вида `a.GetB().GetC().DoSomething()`, если в контексте уже есть похожий пример для копирования — паттерн копируется буквально вместе с нарушением закона Деметры, даже когда рядом есть подходящее свойство или метод на ближайшем объекте.
> - **Буквальный счёт точек.** `request.Address.City` в DTO — не нарушение; нарушение — принятие решения на основе чужих внутренностей.
> - **Обвязка делегирующих свойств.** Десяток сквозных `CustomerName`, `CustomerCity` — тот же граф, только размазанный по фасаду; если делегирующих свойств набирается больше двух-трёх, вызывающему нужен сам объект, и его стоит передать явно.
> - **Группировка по техническим слоям** (`Services/`, `Repositories/`, `Validators/`) разносит связанное и собирает несвязанное — самый частый источник «дробовика» (одно требование задевает четыре папки).
> - **Метрики как цель.** «Снизить LCOM до 0,2» — плохая задача; «разделить класс, который меняется по трём причинам» — хорошая.

## Проверка на ревью

- В диффе нет цепочки из трёх и более обращений (`a.B.C.D`) с последующим `if`/решением на её основе.
- Новый класс не создаёт конкретные зависимости через `new` — они приходят через конструктор как интерфейсы.
- Нет булевых флагов-параметров, меняющих ветвление в чужом методе.
- Тест не собирает мок, возвращающий мок, возвращающий мок, — это сигнал, что поведение написано не в том классе.
- Метод не читает поле объекта только для того, чтобы принять решение снаружи, которое можно передать самому объекту.
- Класс можно описать одним предложением без союза «и».

## Проверь себя

> [!question]- Чем нарушение закона Деметры отличается от обычного доступа к вложенным свойствам DTO?
> Дело не в количестве точек, а в том, кто принимает решение. `request.Address.City` в DTO — просто чтение данных, у DTO нет ни поведения, ни инвариантов, прятать нечего. `order.Customer.Address.Country == "UZ"` в доменной логике — нарушение, потому что вызывающий код узнаёт устройство трёх чужих типов и принимает на его основе решение, которое должен принимать владелец данных (`Customer` или `Order`). Критерий: если чужая структура используется для отображения/сериализации — это нормально; если на её основе ветвится бизнес-логика — это coupling, который надо снижать.

> [!question]- Как Tell-Don't-Ask связано со связностью, а не только с инкапсуляцией?
> Если правило проверки состояния вынесено наружу (`Ask`), оно неизбежно дублируется в каждом месте, где объект меняют, — и эти копии начинают жить в разных классах по разным причинам, снижая связность каждого из них. Когда правило переносится внутрь объекта (`Tell`), оно живёт в одном месте — сам объект становится единственной точкой, отвечающей за своё изменение, то есть growing cohesion за счёт того, что данные и правила над ними наконец рядом.

> [!question]- Всегда ли нужно устранять цепочку вызовов длиной больше одной точки?
> Нет. Правило — эвристика, а не закон физики. Fluent-конфигурация, LINQ-цепочки над одной последовательностью и обход графа в мапперах/вьюмоделях цепочку не нарушают, потому что там нет решения на основе чужих внутренностей. Также не стоит устранять цепочку, если для этого придётся добавить пять сквозных делегирующих свойств в базовый тип — лекарство станет дороже болезни.

## Разбор

**Дан фрагмент — найди проблему.**

```csharp
public sealed class ShippingCalculator
{
    public decimal Calculate(Order order)
    {
        if (order.Customer.Address.Country == "UZ" && order.Customer.Address.City == "Ташкент")
            return 0;
        if (order.Customer.Subscription.Level == SubscriptionLevel.Gold)
            return 0;
        return order.Items.Sum(i => i.Weight) * 1500;
    }
}
```

> [!success]- Решение
> Калькулятор знает про устройство четырёх чужих типов (`Customer`, `Address`, `Subscription`, `Items`) — высокая связанность по структуре плюс нарушение закона Деметры. Лечение — перенести решения туда, где данные:
> ```csharp
> public sealed class Customer
> {
>     public bool HasFreeShipping => _address.IsInCity("UZ", "Ташкент") || _subscription.IsGold;
> }
> public sealed class Order
> {
>     public bool QualifiesForFreeShipping => _customer.HasFreeShipping;
>     public decimal TotalWeight => _items.Sum(i => i.Weight);
> }
> public sealed class ShippingCalculator(decimal ratePerKg)
> {
>     public decimal Calculate(Order order)
>         => order.QualifiesForFreeShipping ? 0 : order.TotalWeight * ratePerKg;
> }
> ```
> Теперь каждый объект спрашивает только непосредственного соседа, правило «бесплатная доставка» существует в одном месте, а тест калькулятора требует одного объекта вместо графа из четырёх моков.

## Итог

- Связанность снижают, связность повышают; практическое измерение обеих — стоимость изменения.
- Закон Деметры — coupling на уровне вызова: метод не должен знать устройство чужих объектов, чтобы принять решение на основе их внутренностей.
- Tell-Don't-Ask — cohesion на уровне вызова: правило должно жить рядом с данными, а не размазываться по вызывающему коду.
- Fluent-API, LINQ и доступ к полям DTO ни один из принципов не нарушают — важно решение, а не количество точек.
- Мок, возвращающий мок, — надёжный тестовый сигнал нарушения закона Деметры.
- Анемичная модель — не всегда зло: проблема начинается, когда правило дублируется по сервисам.
- В ServiceShop правило масштабировано на модули: обращение только к фасаду, а не к внутренностям чужого модуля.
