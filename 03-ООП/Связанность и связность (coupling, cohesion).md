# Связанность и связность (coupling, cohesion)

> [!abstract] Коротко
> Две характеристики, которыми измеряют качество разбиения кода на части. **Связанность** (coupling) — насколько сильно модули зависят друг от друга; её нужно снижать. **Связность** (cohesion) — насколько элементы внутри модуля относятся к одной задаче; её нужно повышать. Цель — «слабая связанность, сильная связность»: тогда изменение требования затрагивает один модуль, а не десять, и модуль можно понять, не читая остальные. Практический индикатор проблем — не метрики, а два наблюдения: приходится ли править много файлов ради одного изменения (высокая связанность) и меняется ли один файл по несвязанным причинам (низкая связность).

## Зачем это нужно

Связанность и связность объясняют, почему один проект остаётся понятным через два года, а другой — нет. Они же стоят за большинством принципов проектирования: единственная ответственность из [[SOLID]] — это про связность, инверсия зависимостей — про связанность, [[Закон Деметры и Tell, Don't Ask]] — про то и другое.

Стоимость измеряется временем изменения:

```
Требование: «добавить поле «комментарий» к заказу»

Слабая связанность:  правим модуль заказов — 3 файла, 20 минут.
Сильная связанность: правим модуль заказов, потом отчёты, потом уведомления,
                     потом экспорт, потом кеш, потом три теста, которые
                     мокали внутренности заказа, — 15 файлов, полдня, и что-то забыли.
```

## Связанность: степени

От худшей к лучшей. В C# они выглядят так:

| Степень | Что это | Пример |
|---|---|---|
| **Содержательная** (content) | модуль лезет во внутренности другого | рефлексия по приватным полям, `InternalsVisibleTo` ради обхода API |
| **Общая** (common) | общие глобальные данные | статическое изменяемое состояние, синглтон с состоянием |
| **Внешняя** (external) | общий формат данных или протокол | два сервиса читают одну таблицу БД |
| **Управляющая** (control) | один модуль управляет ветвлением другого | `bool`-флаг, меняющий поведение метода |
| **По структуре** (stamp) | передаётся объект, а нужна пара полей | метод принимает `Order`, использует только `Total` |
| **По данным** (data) | передаются только нужные значения | `CalculateFee(decimal amount, string currency)` |
| **Нет связи** | модули не знают друг о друге | взаимодействие через события |

Идеал — данные и события; в реальном коде цель — не опуститься ниже уровня «по структуре».

```csharp
// Управляющая связанность: вызывающий управляет логикой флагами
public void Save(Order order, bool validate, bool sendEmail, bool useTransaction) { }
Save(order, true, false, true);       // что здесь происходит — непонятно

// Лучше: разные методы или объект намерения
public Task SaveAsync(Order order, CancellationToken ct);
public Task SaveAndNotifyAsync(Order order, CancellationToken ct);
```

```csharp
// Общая связанность: скрытое глобальное состояние
public static class CurrentUser { public static User? Value { get; set; } }
// Любой код может прочитать и записать; тесты влияют друг на друга; в многопоточной среде — гонка.

// Лучше: явная зависимость
public sealed class OrderService(IUserContext userContext) { }
```

### Как связанность выглядит в .NET

```csharp
// Жёсткая связанность: класс сам создаёт зависимости и знает их конкретные типы
public sealed class OrderService
{
    private readonly SqlOrderRepository _repo = new(ConfigurationManager.AppSettings["cs"]);
    private readonly SmtpEmailSender _mail = new();

    public void Create(Order o) { _repo.Add(o); _mail.Send(o.Customer.Email, "Заказ создан"); }
}
// Подменить хранилище нельзя, протестировать без базы и SMTP нельзя,
// изменение конструктора репозитория ломает сервис.

// Слабая связанность: зависимости приходят снаружи как контракты
public sealed class OrderService(IOrderRepository repository, INotificationSender notifications)
{
    public async Task CreateAsync(Order order, CancellationToken ct)
    {
        await repository.AddAsync(order, ct);
        await notifications.SendAsync(order.CustomerId, "Заказ создан", ct);
    }
}
```

Второй вариант связан только с контрактами, а конкретные реализации подставляет композиционный корень ([[Инверсия зависимостей на практике]]).

## Связность: степени

От худшей к лучшей:

| Степень | Что объединяет элементы | Пример |
|---|---|---|
| **Случайная** | ничего | `Helpers`, `Utils`, `Common` |
| **Логическая** | похожие по типу действия | `Validators` со всеми валидаторами приложения |
| **Временная** | выполняются в один момент | `StartupTasks`, инициализация всего подряд |
| **Процедурная** | идут одна за другой | «шаг 1, шаг 2» из разных областей |
| **Коммуникационная** | работают с одними данными | всё, что читает таблицу заказов |
| **Последовательная** | выход одного — вход другого | парсер → валидатор → маппер |
| **Функциональная** | решают одну задачу | `OrderPricing`: всё про расчёт цены заказа |

Классы `Helpers`, `Managers`, `Utils` — канонический пример случайной связности: они собирают несвязанные методы «чтобы где-то лежали», растут бесконечно и меняются по десятку разных причин.

```csharp
// Низкая связность: класс делает всё
public sealed class OrderManager
{
    public void Create(Order o) { }
    public byte[] ExportToExcel() => [];
    public void SendEmail(string to) { }
    public decimal CalculateTax(Order o) => 0;
    public string FormatDate(DateTime d) => "";
}

// Высокая: каждый тип про одно
public sealed class OrderCreator { }
public sealed class OrderExcelExporter { }
public sealed class TaxCalculator { }
```

Практический тест на связность — **описать класс одним предложением без союза «и»**. «Создаёт заказы **и** экспортирует в Excel **и** отправляет письма» — три класса.

## Два симптома, по которым это видно на практике

**Дробовик (shotgun surgery)** — одно изменение требует правок во многих местах. Признак **высокой связанности**: знание размазано. Пример — формат номера заказа, продублированный в шести местах.

**Расходящиеся изменения (divergent change)** — один класс меняется по разным причинам: сегодня из-за налогов, завтра из-за формата экспорта. Признак **низкой связности**: в классе живут несколько ответственностей.

Эти два запаха взаимно обратны, и лечатся они по-разному: первый — собрать знание в одно место, второй — разделить класс. Подробнее в [[Антипаттерны и code smells]].

Третий полезный признак — **зависть к чужим данным** (feature envy): метод чаще обращается к полям другого объекта, чем к своим. Значит, поведение живёт не там, где данные:

```csharp
// Зависть: калькулятор ковыряется во внутренностях заказа
public decimal CalculateDiscount(Order order)
    => order.Customer.IsVip && order.Items.Sum(i => i.Price * i.Quantity) > 1000 ? 100 : 0;

// Лечение: перенести поведение к данным
public sealed class Order
{
    public decimal Total => _items.Sum(i => i.Price * i.Quantity);
    public bool QualifiesForVipDiscount => Customer.IsVip && Total > 1000;
}
```

## Метрики (и их пределы)

- **Эфферентная связанность (Ce)** — сколько типов зависят **от** нашего модуля наружу; **афферентная (Ca)** — сколько зависят от него. Нестабильность `I = Ce / (Ce + Ca)`: 0 — максимально устойчивый модуль (от него зависят, он ни от кого), 1 — максимально изменчивый.
- **LCOM** (lack of cohesion of methods) — доля методов, не использующих общие поля; чем выше, тем ниже связность.
- **Цикломатическая сложность** — не про связанность, но коррелирует: сложный метод обычно делает несколько дел.

Метрики полезны как индикатор направления, а не как цель: «снизить LCOM до 0,2» — плохая задача, «разделить класс, который меняется по трём причинам» — хорошая. Автоматизировать полезнее правила зависимостей: архитектурные тесты (NetArchTest, ArchUnitNET) проверяют, что домен не ссылается на инфраструктуру, а модуль A не обращается к внутренностям модуля B. Такой тест ловит деградацию раньше, чем ревью.

## Как снижать связанность на практике

1. **Зависимости через интерфейсы, объявленные потребителем.** Домен объявляет `IOrderRepository`, инфраструктура реализует — направление ссылок разворачивается.
2. **Инъекция вместо создания.** `new` конкретного сервиса внутри класса — жёсткая связь; исключение — value objects и DTO, их создавать нормально.
3. **Передавать данные, а не объекты.** Метод, которому нужна сумма, должен принимать сумму, а не весь заказ (уровень «по данным» вместо «по структуре»).
4. **События вместо прямых вызовов** там, где отправитель не должен знать получателей ([[Доменные события]]).
5. **Границы модулей на уровне сборок** и `internal` — компилятор удержит то, что не удержит дисциплина ([[Инкапсуляция и модификаторы доступа]]).
6. **Не «выставлять наружу» типы инфраструктуры.** Если контракт домена возвращает `DbDataReader` или `HttpResponseMessage`, вся система связана с этими библиотеками.

И симметрично — как повышать связность: группировать код по **функции**, а не по техническому типу (`Orders/` вместо `Services/`, `Repositories/`, `Validators/`), выносить растущие классы по ответственностям, не создавать `Common` и `Utils`.

> [!warning] Подводные камни
> - **Борьба со связанностью абстракциями «на всякий случай».** Интерфейс с единственной реализацией, добавленный ради «развязки», часто просто добавляет файл. Абстракция нужна там, где есть граница.
> - **Мнимая развязка через события.** Событие, на которое подписан ровно один обработчик и без которого система не работает, — тот же прямой вызов, только его труднее проследить.
> - **Слишком мелкое дробление.** Двадцать классов по одному методу дают низкую связанность и нулевую связность: логика размазана, и понять сценарий целиком невозможно.
> - **Группировка по техническим слоям.** Папки `Services`, `Models`, `Repositories` собирают вместе несвязанные вещи и разносят связанные — прямой удар по связности.
> - **Общая «модель на всё».** Один класс `Order`, используемый доменом, API и отчётами, связывает эти части: изменение ради отчёта ломает домен.
> - **Статическое изменяемое состояние.** Самая незаметная форма сильной связанности: зависимость есть, но её не видно в подписи.
> - **Метрики как цель.** Оптимизация ради цифр даёт странные решения; ориентироваться надо на стоимость изменений.

> [!example] Как делают в бою
> Ключевое решение, влияющее и на связанность, и на связность, — **как нарезаны папки и сборки**. Нарезка по функциям (`Orders`, `Payments`, `Catalog`, внутри каждой — свои модели, обработчики, репозитории) даёт высокую связность: всё про заказы лежит рядом, и типичное изменение затрагивает одну папку. Нарезка по техническим слоям даёт обратное.
> Границы модулей закрепляют сборками и `internal`, а на связи между ними пишут архитектурные тесты: «Domain не ссылается на EntityFrameworkCore», «модуль Payments не обращается к типам модуля Orders, кроме контрактов». Такой тест — самый дешёвый способ не дать архитектуре расползтись.
> Внутри модуля не боятся связанности: соседние классы одного модуля знают друг о друге, и это нормально. Строго контролируют только связи **между** модулями — они идут через явные контракты и события.
> Отдельная привычка: отчёты, экспорт и интеграции работают со своими моделями, а не с доменной. Общая модель «на всё» — самая частая причина того, что домен меняется из-за требований к выгрузке в Excel.

## Вопросы с собеседований

> [!question]- Что такое связанность и связность и почему их рассматривают вместе?
> Связанность (coupling) — мера зависимости между модулями: сколько модуль знает о других и насколько сильно на них завязан. Связность (cohesion) — мера того, насколько элементы внутри модуля служат одной задаче. Цель — слабая связанность и сильная связность, и рассматривают их вместе, потому что оптимизация одной без другой даёт вырожденные решения: можно получить нулевую связанность, свалив всё в один гигантский класс (и уничтожив связность), или максимальную связность, раздробив систему на сотни микроклассов, каждый из которых зависит от десятка соседей. Практический смысл обеих характеристик — стоимость изменения: при хорошем разбиении типичное требование затрагивает один модуль, а понять этот модуль можно, не читая остальные.

> [!question]- Как проявляется высокая связанность в коде на C#?
> Самые частые формы: создание зависимостей через `new` внутри класса (подменить нельзя, тестировать без реальной базы и сети нельзя); обращение к статическому изменяемому состоянию, из-за чего зависимость не видна в подписи и появляется гонка в многопоточной среде; передача «толстых» объектов туда, где нужны два поля; булевы флаги, управляющие поведением чужого метода; утечка инфраструктурных типов в контракты домена; общая модель, используемая одновременно доменом, API и отчётами. Симптом на уровне процесса — «дробовик»: одно требование заставляет править множество файлов в разных частях системы. Лечение: зависимости через интерфейсы, внедряемые снаружи; передача данных вместо объектов; отдельные модели для разных задач; границы модулей на уровне сборок с `internal` и архитектурными тестами.

> [!question]- Чем плохи классы вроде `Helpers` и `Utils`?
> У них случайная связность — самая низкая: методы объединены не задачей, а тем, что их некуда было положить. Последствия предсказуемы: такой класс растёт без предела, меняется по десятку несвязанных причин, его невозможно описать одним предложением, а зависимости от него появляются по всему проекту, что заодно повышает связанность. Кроме того, статические утилиты трудно подменить в тестах. Правильные альтернативы: методы расширения рядом с типом, к которому они относятся (`OrderExtensions` в модуле заказов); отдельный сервис с внятным именем и внедряемый через DI, если есть состояние или зависимости; перенос поведения в сам доменный тип, если метод работает преимущественно с его данными. Признак, по которому проверяют: если из имени класса непонятно, что в нём лежит, значит связности нет.

## Задачи

### Задача 1. Найти проблемы связанности

```csharp
public sealed class ReportService
{
    public byte[] Build(long orderId, bool asPdf, bool includeVat, bool sendByEmail)
    {
        var conn = new SqlConnection(ConfigurationManager.ConnectionStrings["db"].ConnectionString);
        var order = LoadOrder(conn, orderId);
        var total = includeVat ? order.Total * 1.12m : order.Total;
        var bytes = asPdf ? RenderPdf(order, total) : RenderExcel(order, total);
        if (sendByEmail) new SmtpClient("smtp.company.uz").Send(BuildMessage(order, bytes));
        return bytes;
    }
}
```

> [!success]- Решение
> Проблемы по слоям. Связанность: класс сам создаёт соединение с базой и SMTP-клиент (жёсткая зависимость от конкретных технологий и от конфигурации), читает настройки из глобального `ConfigurationManager` (скрытая общая связанность), и его поведением управляют три булевых флага (управляющая связанность — вызывающий фактически программирует метод параметрами). Связность: класс одновременно загружает данные, считает налог, рендерит два формата и отправляет почту — четыре причины для изменения.
> ```csharp
> public interface IReportRenderer { string Format { get; } byte[] Render(ReportData data); }
>
> public sealed class ReportService(
>     IOrderReader orders,
>     ITaxCalculator tax,
>     IReadOnlyDictionary<string, IReportRenderer> renderers)
> {
>     public async Task<byte[]> BuildAsync(long orderId, string format, CancellationToken ct)
>     {
>         var order = await orders.GetAsync(orderId, ct)
>                     ?? throw new OrderNotFoundException(orderId);
>         var data = new ReportData(order, tax.Calculate(order));
>         return renderers[format].Render(data);
>     }
> }
> ```
> Отправка письма ушла из сервиса совсем: это отдельная ответственность, и вызывающий (или обработчик события «отчёт построен») решает, нужна ли она. Формат стал данными, а не флагом, поэтому добавление CSV не требует правок в сервисе. Зависимости — контракты, значит тест не требует ни базы, ни SMTP.

### Задача 2. Улучшить связность

Проект организован по слоям: `Services/` (30 файлов), `Models/` (40), `Repositories/` (20), `Validators/` (15). Команда жалуется, что любое изменение задевает четыре папки. Что предложить?

> [!success]- Решение
> Симптом классический: техническая нарезка разносит связанное и собирает несвязанное. Всё про заказы лежит в четырёх разных папках, а рядом с `OrderService` — `PaymentService`, с которым у него ничего общего.
> Предложение — нарезка по функциям:
> ```
> Orders/        OrderService.cs, Order.cs, OrderRepository.cs, CreateOrderValidator.cs, ...
> Payments/      PaymentService.cs, Payment.cs, PaymentRepository.cs, ...
> Catalog/       ...
> Shared/        то, что действительно общее: базовые типы, Result, инфраструктура
> ```
> Что это даёт: типичное изменение («добавить поле в заказ») затрагивает одну папку; внутри папки видно всё, что относится к теме; появляется естественная граница для последующего выделения модуля в отдельную сборку с `internal`-типами, а затем, при необходимости, и в отдельный сервис.
> Оговорки, которые честно стоит проговорить: миграция делается постепенно, по одной функции за раз, а не одним коммитом (иначе `git blame` и ревью станут бесполезны); часть кода действительно общая, и для неё нужна папка `Shared`, но за её ростом надо следить — она легко превращается в `Utils`; технические слои внутри модуля остаются, просто уходят на уровень ниже. Дальше этот подход раскрывается в [[Vertical Slice Architecture]] и [[ServiceShop: модульный монолит и изоляция модулей]].

## Итог

- Связанность — зависимость между модулями, её снижают; связность — единство внутри модуля, её повышают.
- Практическое измерение — стоимость изменения: сколько файлов правим ради одного требования и по скольким причинам меняется один файл.
- Худшие формы связанности в C#: `new` конкретных зависимостей внутри класса, статическое изменяемое состояние, булевы флаги-переключатели, утечка инфраструктурных типов в контракты.
- Худшая форма связности — `Helpers`/`Utils`: элементы объединены ничем.
- «Дробовик» указывает на высокую связанность, «расходящиеся изменения» — на низкую связность; лечатся противоположно.
- Нарезка по функциям вместо технических слоёв повышает связность больше любых рефакторингов внутри классов.
- Границы модулей держат сборки, `internal` и архитектурные тесты, а не договорённости.
- Метрики полезны как индикатор, но целью должна быть стоимость изменений.
