# Конструкторы и инициализация

> [!abstract] Короток
> Конструктор — это не «метод для заполнения полей», а место, где объект получает право на существование: после его выхода все инварианты типа должны выполняться. C# даёт много способов положить значение в объект — инициализаторы полей, `base(...)`/`this(...)`, primary constructors, object initializers, `init`, `required` — и у каждого свой момент выполнения. Порядок инициализации при наследовании спрашивают почти на каждом собеседовании, а виртуальный вызов из конструктора базового класса — классическая ловушка. Толстый конструктор с логикой — почти всегда ошибка проектирования.

## Зачем это нужно

Половина багов «объект в невалидном состоянии» возникает потому, что кто-то создал экземпляр не полностью. Конструктор — единственное место, где язык гарантирует: без прохождения через него объекта не существует. Всё, что нужно объекту для корректной работы, должно попасть в него здесь и быть проверено здесь.

Обратная сторона: конструктор нельзя переопределить, из него нельзя вернуть `null`, из него нельзя вернуть кешированный экземпляр, и он не умеет быть асинхронным. Как только требуется что-то из этого — конструктор перестаёт быть подходящим инструментом, и на сцену выходят фабричные методы.

## Виды конструкторов

| Вид | Синтаксис | Когда вызывается |
|---|---|---|
| Экземплярный | `public Foo(int x)` | при `new Foo(x)` |
| Без параметров (неявный) | генерируется компилятором | если у класса нет ни одного явного конструктора |
| Статический | `static Foo()` | один раз, лениво, перед первым обращением к типу |
| Приватный | `private Foo()` | из фабрик, ORM, сериализаторов; блокирует прямой `new` |
| Копирующий | `protected Foo(Foo other)` | вручную либо сгенерированный в `record` для `with` |
| Primary constructor | `class Foo(int x)` | C# 12+, единственная «входная точка» типа |
| Деконструктор | `Deconstruct(out ...)` | это не конструктор, см. [[Классы и объекты]] |

```csharp
public sealed class Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    // Экземплярный конструктор с валидацией: после выхода инварианты держатся.
    public Money(decimal amount, string currency)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(currency);
        if (amount < 0) throw new ArgumentOutOfRangeException(nameof(amount));
        Amount = amount;
        Currency = currency.ToUpperInvariant();
    }

    // Приватный конструктор без валидации — только для внутренних быстрых путей.
    private Money(decimal amount, string currency, bool _) => (Amount, Currency) = (amount, currency);

    internal static Money Unchecked(decimal amount, string currency) => new(amount, currency, true);
}
```

> [!info] Неявный конструктор исчезает
> Как только ты объявил хотя бы один конструктор в `class`, компилятор перестаёт генерировать конструктор без параметров. Для `struct` конструктор без параметров есть всегда — либо неявный (обнуляет всё), либо явно объявленный (C# 10+), причём `default(T)` и `new T[10]` всё равно используют обнуление, минуя явный конструктор.

### Копирующий конструктор в record

```csharp
public record Person(string Name, int Age)
{
    private readonly Guid _traceId = Guid.NewGuid();   // инициализатор поля
    public Guid TraceId => _traceId;
}

var a = new Person("Азиз", 30);
var b = a with { Age = 31 };
Console.WriteLine(a.TraceId == b.TraceId);   // Вывод: True
```

Компилятор сгенерировал в `Person` защищённый копирующий конструктор `protected Person(Person original)` (для `sealed record` — приватный), который **побайтово копирует все поля и НЕ выполняет инициализаторы полей**. Поэтому `_traceId` не перегенерировался. Выражение `a with { Age = 31 }` разворачивается в вызов синтезированного метода `<Clone>$`, который зовёт копирующий конструктор, а затем присваивает `Age`. Подробности — в [[Записи (record) и структуры]].

## Порядок инициализации при наследовании

Это спрашивают постоянно. Точная последовательность для `new Derived()`:

```
1. Выделение и обнуление памяти (все поля = default)
2. Инициализаторы полей ПРОИЗВОДНОГО класса
3. Переход к конструктору базового класса (base(...)):
      3a. Инициализаторы полей БАЗОВОГО класса
      3b. Тело конструктора БАЗОВОГО класса
      (рекурсивно вверх до System.Object)
4. Тело конструктора ПРОИЗВОДНОГО класса
```

Ключевое и контринтуитивное: **инициализаторы полей производного класса выполняются ДО конструктора базового**. В C++ и Java наоборот — там сначала полностью строится база. Это одно из немногих мест, где C# осознанно разошёлся с обоими.

### Демонстрация с точным выводом

```csharp
public class Base
{
    private readonly string _baseField = Log("инициализатор поля Base");

    public Base()
    {
        Log("тело конструктора Base");
        Describe();                       // ОПАСНО: виртуальный вызов из конструктора
    }

    protected virtual void Describe() => Console.WriteLine("  Base.Describe");

    protected static string Log(string message)
    {
        Console.WriteLine(message);
        return message;
    }
}

public class Derived : Base
{
    private readonly string? _fromInitializer = Log("инициализатор поля Derived");
    private readonly string? _fromBody;
    private readonly int _countFromBody;

    public Derived()
    {
        _fromBody = Log("тело конструктора Derived");
        _countFromBody = 42;
    }

    protected override void Describe() => Console.WriteLine(
        $"  Derived.Describe: init='{_fromInitializer ?? "null"}', " +
        $"body='{_fromBody ?? "null"}', count={_countFromBody}");
}

_ = new Derived();
```

Вывод:

```
инициализатор поля Derived
инициализатор поля Base
тело конструктора Base
  Derived.Describe: init='инициализатор поля Derived', body='null', count=0
тело конструктора Derived
```

Разбор каждой строки:

1. Инициализатор `_fromInitializer` производного класса — да, он первый.
2. Управление ушло в неявный `base()`, отработал инициализатор поля базового класса.
3. Тело конструктора базового класса.
4. Из тела базового конструктора вызван `Describe()`. Вызов **виртуальный**, поэтому диспетчеризация ушла в `Derived.Describe` — уже сейчас, когда конструктор производного класса ещё не начинался. Значения полей, присвоенные в *инициализаторах*, уже видны. Значения, присваиваемые в *теле* конструктора производного класса, ещё нет: `_fromBody` = `null`, `_countFromBody` = `0`.
5. Только теперь тело конструктора производного класса.

### Почему виртуальный вызов из конструктора — ловушка

Method table объекта устанавливается **до** вызова любого конструктора. Значит, с самой первой инструкции объект уже «знает», что он `Derived`, и любой виртуальный вызов уходит в самую производную реализацию. Но состояние производного класса ещё не достроено.

В боевом коде это выглядит так:

```csharp
// ПЛОХО
public abstract class Repository
{
    protected Repository() => Cache = BuildCache();   // виртуальный вызов
    protected Dictionary<string, string> Cache { get; }
    protected abstract Dictionary<string, string> BuildCache();
}

public sealed class SqlRepository : Repository
{
    private readonly string _connectionString;

    public SqlRepository(string connectionString) => _connectionString = connectionString;

    protected override Dictionary<string, string> BuildCache()
        => Load(_connectionString);      // NullReferenceException: _connectionString ещё null
}
```

Как чинить:

```csharp
// ХОРОШО: никаких виртуальных вызовов из конструктора.
// Всё, что нужно наследнику, он передаёт вверх сам.
public abstract class Repository
{
    protected Repository(Dictionary<string, string> cache) => Cache = cache;
    protected Dictionary<string, string> Cache { get; }
}

public sealed class SqlRepository : Repository
{
    public SqlRepository(string connectionString) : base(Load(connectionString)) { }

    private static Dictionary<string, string> Load(string cs) => /* ... */ [];
}
```

Обрати внимание: `Load` — **статический** метод. В аргументах `base(...)` нельзя обратиться к `this`, и это ровно та защита, которая здесь нужна.

Правило: **из конструктора нельзя вызывать `virtual`/`abstract` члены и нельзя выпускать `this` наружу.** Если очень нужно — помечай класс `sealed` (тогда переопределения не будет) или выноси инициализацию в отдельный метод/фабрику. Анализатор CA2214 ловит такие вызовы.

## Цепочки `: this(...)` и `: base(...)`

```csharp
public class Connection
{
    public string Host { get; }
    public int Port { get; }
    public TimeSpan Timeout { get; }

    // Один "настоящий" конструктор — вся валидация в нём.
    public Connection(string host, int port, TimeSpan timeout)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(host);
        if (port is < 1 or > 65535) throw new ArgumentOutOfRangeException(nameof(port));
        (Host, Port, Timeout) = (host, port, timeout);
    }

    public Connection(string host, int port) : this(host, port, TimeSpan.FromSeconds(30)) { }
    public Connection(string host)            : this(host, 5432) { }
}
```

Важная деталь, о которой забывают: **инициализаторы полей выполняются ровно один раз, в том конструкторе, который вызывает `base(...)`**. Конструктор, делегирующий через `: this(...)`, инициализаторы полей не запускает — иначе они отработали бы дважды.

```csharp
public class Counter
{
    private readonly List<int> _items = Init();

    public Counter() : this(0) { }              // инициализатор здесь НЕ выполняется
    public Counter(int seed) { _items.Add(seed); }  // выполняется здесь

    private static List<int> Init()
    {
        Console.WriteLine("инициализатор");
        return [];
    }
}

_ = new Counter();
// Вывод: инициализатор     ← один раз, а не два
```

Если ни `this(...)`, ни `base(...)` не указаны, компилятор неявно подставляет `: base()`. Если у базового класса нет доступного конструктора без параметров — ошибка компиляции, придётся вызывать `base(...)` явно.

## Primary constructors (C# 12)

Primary constructor — это параметры, объявленные прямо у типа. Они в области видимости всего тела типа.

```csharp
public class OrderService(IOrderRepository repository, ILogger<OrderService> logger)
{
    public async Task<Order> GetAsync(Guid id, CancellationToken ct)
    {
        logger.LogInformation("Загружаем заказ {Id}", id);
        return await repository.GetAsync(id, ct);
    }
}
```

Это ровно то, ради чего фичу делали: убрать три строки шаблона на каждую зависимость в сервисах с [[Инверсия зависимостей на практике]].

### Семантика: параметр захватывается, только если используется

Компилятор создаёт скрытое приватное поле под параметр **только если параметр читается из члена типа**. Если параметр используется исключительно в инициализаторах полей/свойств и в аргументах `base(...)`, поле не создаётся — значение просто проходит транзитом.

```csharp
public class Widget(string name, int width, int height) : NamedItem(name)
{
    // name ушёл в base(...) и больше нигде не используется → поля НЕТ
    public int Area => width * height;   // width и height читаются в члене → ДВА скрытых поля
}
```

Порядок работы primary constructor, по спецификации:

```
1. Значения параметров сохраняются в скрытые capture-поля (если они есть)
2. Выполняются инициализаторы полей и свойств
3. Вызывается конструктор базового класса base(...)
```

То есть относительный порядок «инициализаторы → база» такой же, как у обычного конструктора.

Любой другой конструктор типа обязан пройти через primary constructor:

```csharp
public class Widget(string name, int width, int height) : NamedItem(name)
{
    public Widget(string name) : this(name, 1, 1) { }   // : base(...) здесь запрещён
    public int Area => width * height;
}
```

### Primary constructor в record vs в обычном классе

Это ключевая разница, которую путают.

| | `record` | `class` / `struct` |
|---|---|---|
| Что генерируется на параметр | публичное `init`-свойство с тем же именем | ничего публичного; при необходимости — скрытое приватное поле |
| Доступ снаружи | `person.Name` работает | доступа нет |
| `Deconstruct` | генерируется | нет |
| `Equals`/`GetHashCode`/`ToString` по значению | генерируются | нет |
| `with` | работает | нет |
| Иммутабельность параметра | свойство `init`-only | параметр **изменяемый** |

```csharp
public record PersonRecord(string Name);
public class  PersonClass(string Name);

var r = new PersonRecord("Азиз");
Console.WriteLine(r.Name);   // Вывод: Азиз

var c = new PersonClass("Азиз");
// Console.WriteLine(c.Name);  // Ошибка компиляции: у PersonClass нет члена Name
```

### Предупреждение: параметр primary constructor — изменяемая переменная

```csharp
public class Counter(int value)
{
    public int Value => value;
    public void Increment() => value++;   // компилируется! мутирует скрытое поле
}

var counter = new Counter(0);
counter.Increment();
counter.Increment();
Console.WriteLine(counter.Value);   // Вывод: 2
```

Скрытое capture-поле **не** `readonly` (кроме `readonly struct`). Это значит, что primary constructor сам по себе не даёт иммутабельности и не защищает от случайного присваивания. Если тип должен быть неизменяемым, объявляй поля явно:

```csharp
public class Counter(int value)
{
    private readonly int _value = value;   // теперь компилятор запретит мутацию
    public int Value => _value;
}
```

Ещё два предупреждения компилятора, о которых полезно знать:

- Если параметр и передан в `base(...)`, и захвачен в поле — компилятор предупредит о **двойном хранении**: одно и то же значение лежит в объекте дважды (в поле базового класса и в capture-поле производного).
- Если параметр использован в инициализаторе свойства и одновременно захвачен, компилятор тоже предупредит:

```csharp
public class Person(string name)
{
    public string Name { get; set; } = name;     // копия в свойстве
    public override string ToString() => name;   // а тут читается capture-поле
}
// Изменение Name не отразится на ToString() — почти наверняка баг.
```

> [!tip] Когда primary constructor уместен
> Отлично: DI-сервисы, тонкие обёртки, `record`-типы, тестовые заглушки. Плохо: типы с валидацией (валидацию некуда написать — тела у primary constructor нет), типы с несколькими равноправными способами создания, типы, где нужна нормализация входа. Для них — обычный конструктор.

## Object initializers

```csharp
var order = new Order { Id = 1, Customer = "Азиз", Comment = "срочно" };
```

Разворачивается компилятором ровно в это:

```csharp
Order <>temp = new Order();     // конструктор без параметров вызывается ПЕРВЫМ
<>temp.Id = 1;                  // затем присваивания, строго в порядке записи
<>temp.Customer = "Азиз";
<>temp.Comment = "срочно";
Order order = <>temp;           // и только теперь ссылка попадает в переменную
```

Три следствия, о которых нужно помнить:

1. Присваивание переменной происходит **последним**. Пока идут присваивания свойств, ссылка на объект есть только у компилятора. Если сеттер бросит исключение — объект потерян, и `Dispose` ты ему уже не вызовешь.
2. Конструктор ничего не знает о значениях из инициализатора. Валидировать в конструкторе комбинацию свойств, задаваемых через object initializer, невозможно — их там ещё нет. Это главная причина, по которой `required` появился только в C# 11.
3. Порядок присваиваний — исходный порядок в коде. Если сеттеры зависят друг от друга (сами по себе это уже плохо), результат зависит от порядка.

> [!danger] Утечка ресурса из-за object initializer
> ```csharp
> // ПЛОХО: если сеттер Position бросит, FileStream не будет закрыт
> using var stream = new FileStream(path, FileMode.Open) { Position = -1 };
> ```
> `using` привязывается к переменной, а переменная получит значение только после всех присваиваний. Исключение в сеттере — и открытый файловый дескриптор остаётся висеть до финализации. Для типов с `IDisposable` инициализируй в теле, а не в object initializer.

Инициализатор умеет присваивать и вложенные объекты, и коллекции без `new`:

```csharp
var config = new ServerConfig
{
    Name = "api",
    Limits = { MaxConnections = 100 },   // НЕ new Limits(), а config.Limits.MaxConnections = 100
    Tags = { "prod", "eu" }              // НЕ new List, а config.Tags.Add("prod"); ...
};
```

Такая форма требует, чтобы `Limits` и `Tags` уже были не-`null` после конструктора, иначе `NullReferenceException` в момент создания.

## Collection initializers и collection expressions

```csharp
// Collection initializer (C# 3). Требует IEnumerable + доступный метод Add.
var list = new List<int> { 1, 2, 3 };
// разворачивается в: temp = new List<int>(); temp.Add(1); temp.Add(2); temp.Add(3);

var dict = new Dictionary<string, int> { ["a"] = 1, ["b"] = 2 };
// эта форма разворачивается в индексатор: temp["a"] = 1; temp["b"] = 2;
```

С C# 12 есть **collection expressions** — единый синтаксис для любых коллекций:

```csharp
int[] array       = [1, 2, 3];
List<int> list    = [1, 2, 3];
Span<int> span    = [1, 2, 3];
HashSet<int> set  = [1, 2, 3];
ImmutableArray<int> immutable = [1, 2, 3];

int[] head = [1, 2];
int[] tail = [4, 5];
int[] all  = [..head, 3, ..tail];   // spread-оператор: [1, 2, 3, 4, 5]

int[] empty = [];                    // пустой массив без аллокации (Array.Empty<int>())
```

Почему это лучше старой формы:

- Компилятор сам выбирает эффективный способ построения. Для массивов и `Span<T>` он не создаёт промежуточный `List<T>`. Для типов с атрибутом `[CollectionBuilder]` (например, `ImmutableArray<T>`) он зовёт указанный builder-метод вместо цепочки `Add`.
- Работает там, где `new T[] { ... }` не работал: для `Span<T>`, `ReadOnlySpan<T>`, интерфейсов `IEnumerable<T>`/`IReadOnlyList<T>`.
- Пустой литерал `[]` не аллоцирует.

Ограничение: у коллекционного выражения нет естественного типа, поэтому нужен целевой тип. `var x = [1, 2, 3];` — ошибка компиляции; пиши `int[] x = [1, 2, 3];`.

## `init`-only сеттеры

```csharp
public class Settings
{
    public string Host { get; init; } = "localhost";
    public int Port { get; init; } = 5432;
}

var s = new Settings { Host = "db.local", Port = 6432 };   // можно
// s.Port = 1;                                             // ошибка: init-only
```

`init` — это обычный сеттер, помеченный в IL модификатором `modreq(System.Runtime.CompilerServices.IsExternalInit)`. Компилятор разрешает вызывать его только «в фазе инициализации»: внутри object initializer, в конструкторе того же типа или производного, в `with`-выражении, а также в инициализаторе другого свойства того же объекта. Проверку делает компилятор, не рантайм — через рефлексию `init`-свойство ставится как обычное, чем и пользуются сериализаторы. Поэтому `init` — это про удобство и намерение, а не про защиту.

## `required` члены (C# 11)

`init` решил «нельзя менять после создания», но не решил «нельзя забыть задать». Это делает `required`:

```csharp
public class User
{
    public required string Email { get; init; }
    public required string Name { get; init; }
    public int? Age { get; set; }
}

// var u = new User();                      // ошибка CS9035: Email и Name не заданы
var u = new User { Email = "a@b.uz", Name = "Азиз" };   // ок
```

Правила, которые стоит помнить:

- Применяется к полям и свойствам классов, структур, `record`. К членам интерфейса — нельзя. К явной реализации интерфейса — нельзя.
- Требуемый член должен быть **не менее доступен**, чем сам тип, и его сеттер (`set` или `init`) — тоже. Иначе вызывающий не сможет его задать.
- Наследник не может ни скрыть `required`-член, ни снять модификатор при переопределении. Добавить `required` при переопределении можно.
- Тип с `required`-членами **нельзя** использовать как аргумент дженерика с ограничением `new()` — компилятор не может гарантировать инициализацию.
- В метаданные компилятор пишет `[RequiredMember]` и `[CompilerFeatureRequired("RequiredMembers")]`, чтобы старые компиляторы отказались собирать код против такого типа, а не молча создали невалидный объект.

### `[SetsRequiredMembers]`

Если объект создаётся конструктором, а не object initializer, требование «задай все required» нужно снять:

```csharp
using System.Diagnostics.CodeAnalysis;

public class User
{
    public User() { }                          // требует object initializer

    [SetsRequiredMembers]
    public User(string email, string name)     // а этот конструктор всё задаёт сам
        => (Email, Name) = (email, name);

    public required string Email { get; init; }
    public required string Name { get; init; }
}

var u = new User("a@b.uz", "Азиз");   // ок, компилятор верит атрибуту
```

> [!warning] Атрибут — это обещание, а не проверка
> Компилятор **не верифицирует**, что конструктор действительно присваивает все `required`-члены. `[SetsRequiredMembers]` просто отключает диагностику. Поставил атрибут и забыл присвоить поле — получишь `null` в non-nullable свойстве и никакого предупреждения. Дополнительные правила: конструктор, делегирующий через `this()`/`base()` в конструктор с `[SetsRequiredMembers]`, обязан сам иметь этот атрибут. Копирующие конструкторы `record` получают атрибут автоматически, если у типа есть `required`-члены.

### Что выбрать

| Задача | Инструмент |
|---|---|
| Значение обязательно и не должно меняться | `required` + `init` |
| Значение обязательно, но нужна нормализация/валидация | обычный конструктор |
| Значение опционально | обычное свойство со значением по умолчанию |
| Тип создаётся десериализатором | `required` + `init` либо конструктор с `[SetsRequiredMembers]` |
| Много параметров, комбинации взаимозависимы | фабричный метод или builder |

## `readonly` поля

```csharp
public class Report
{
    private readonly DateTime _createdAt = DateTime.UtcNow;   // 1) в инициализаторе
    private readonly string _title;
    private static readonly string s_machine;

    public Report(string title)
    {
        _title = title;             // 2) в конструкторе экземпляра ЭТОГО типа
    }

    static Report()
    {
        s_machine = Environment.MachineName;   // 3) static readonly — в статическом конструкторе
    }

    public void Rename(string title)
    {
        // _title = title;          // ошибка CS0191: только в конструкторе
    }
}
```

Итого `readonly`-поле можно присвоить в трёх местах: в инициализаторе объявления, в любом экземплярном конструкторе объявляющего типа (для `static readonly` — в статическом конструкторе). **Не** в конструкторе производного класса, **не** в методах, **не** в `init`-сеттере другого свойства.

Что `readonly` не делает:

- Не делает объект неизменяемым: `private readonly List<int> _items` защищает только саму ссылку. `_items.Add(1)` работает.
- Не защищает от рефлексии: `FieldInfo.SetValue` на `readonly`-поле в общем случае проходит, хотя поведение для `static readonly` не гарантируется и может ломать оптимизации JIT.
- Для `readonly`-полей структур в контексте только-для-чтения компилятор делает защитные копии — см. [[Свойства и field-backed properties]].

## Статический конструктор — кратко

```csharp
public static class Config
{
    public static readonly string Environment;

    static Config() => Environment = System.Environment.GetEnvironmentVariable("ASPNETCORE_ENVIRONMENT") ?? "Production";
}
```

Гарантии: вызывается ровно один раз на домен приложения, потокобезопасно (рантайм сам ставит блокировку), лениво — перед первым обращением к любому статическому члену или созданием первого экземпляра. Исключение внутри превращается в `TypeInitializationException`, и тип становится **непригодным до конца жизни процесса** — любое следующее обращение бросит то же исключение. Подробности, `beforefieldinit` и дедлоки — в [[Статические члены, классы и конструкторы]].

## Исключения в конструкторе

Бросать из конструктора — нормально и правильно: это единственный способ сказать «такой объект существовать не может». Но нужно понимать, что происходит.

```csharp
var order = new Order(-5);   // конструктор бросил ArgumentOutOfRangeException
// переменная order не создана, ссылка на недостроенный объект никуда не попала
```

Что важно:

- Объект **уже выделен** в куче и **уже частично инициализирован**. Просто ссылку на него никто не получил, поэтому он сразу становится мусором и будет собран.
- **Финализатор всё равно вызовется.** Объект регистрируется в очереди финализации в момент аллокации, а не в конце конструктора. Значит, финализатор обязан корректно работать с наполовину инициализированным объектом: проверять поля на `null`, не обращаться к тому, чего может не быть.

```csharp
// ПЛОХО: финализатор упадёт, если конструктор бросил до присваивания _handle
public class NativeBuffer
{
    private readonly IntPtr _handle;
    private readonly Stream _log;

    public NativeBuffer(int size, string logPath)
    {
        _handle = Allocate(size);
        _log = File.OpenWrite(logPath);   // если бросит — _handle уже выделен
    }

    ~NativeBuffer() => Free(_handle);     // при исключении выше _handle корректен, но так везёт не всегда
}
```

```csharp
// ХОРОШО: ресурс завёрнут в SafeHandle — он сам себя освобождает,
// свой финализатор писать не нужно вовсе
public sealed class NativeBuffer : IDisposable
{
    private readonly BufferSafeHandle _handle;
    private readonly Stream _log;

    public NativeBuffer(int size, string logPath)
    {
        _handle = Allocate(size);         // SafeHandle зарегистрирован сразу
        _log = File.OpenWrite(logPath);
    }

    public void Dispose() { _log.Dispose(); _handle.Dispose(); }
}
```

Полностью тема разобрана в [[Финализаторы и SafeHandle]]. Практическое правило: **не пиши финализаторы**, оборачивай неуправляемые ресурсы в `SafeHandle`, а конструктор, захватывающий больше одного ресурса, оборачивай в try/catch с освобождением уже захваченного.

## Почему «толстые» конструкторы — плохо

```csharp
// ПЛОХО
public class ReportGenerator
{
    private readonly List<Row> _rows;

    public ReportGenerator(string connectionString, DateOnly from, DateOnly to)
    {
        using var conn = new SqlConnection(connectionString);
        conn.Open();                                    // I/O в конструкторе
        _rows = LoadRows(conn, from, to);               // может занять 30 секунд
        _rows.Sort(RowComparer.Default);                // бизнес-логика в конструкторе
        Log.Information("Загружено {Count} строк", _rows.Count);   // побочный эффект
    }
}
```

Что здесь не так:

| Проблема | Последствие |
|---|---|
| I/O в конструкторе | `new` может «повиснуть» на 30 секунд; тест этого класса требует базу |
| Нет асинхронности | конструктор не может быть `async`, приходится блокировать поток |
| Исключение при создании | вызывающий получает объект-«призрак» и невнятный стектрейс |
| Побочные эффекты | `new` пишет в лог — сюрприз для читателя кода |
| Невозможно вернуть кеш | конструктор обязан создать новый объект |

```csharp
// ХОРОШО: конструктор только присваивает и валидирует,
// работа вынесена в асинхронный фабричный метод
public sealed class Report
{
    private readonly IReadOnlyList<Row> _rows;

    private Report(IReadOnlyList<Row> rows) => _rows = rows;   // дёшево, без сюрпризов

    public static async Task<Report> LoadAsync(
        IRowSource source, DateOnly from, DateOnly to, CancellationToken ct)
    {
        if (to < from) throw new ArgumentException("Конец периода раньше начала.", nameof(to));

        var rows = await source.QueryAsync(from, to, ct);
        return new Report([.. rows.OrderBy(r => r.Date)]);
    }
}
```

### Named constructors

Когда у типа несколько осмысленных способов создания, перегрузки конструктора становятся нечитаемыми. Статические фабрики с говорящими именами решают это:

```csharp
public readonly struct Temperature
{
    private readonly double _kelvin;
    private Temperature(double kelvin) => _kelvin = kelvin;

    public static Temperature FromKelvin(double k) =>
        k >= 0 ? new(k) : throw new ArgumentOutOfRangeException(nameof(k));

    public static Temperature FromCelsius(double c)    => FromKelvin(c + 273.15);
    public static Temperature FromFahrenheit(double f) => FromKelvin((f - 32) * 5 / 9 + 273.15);

    public double Kelvin  => _kelvin;
    public double Celsius => _kelvin - 273.15;
}

var t = Temperature.FromCelsius(25);
```

Двумя конструкторами `Temperature(double)` это выразить нельзя вовсе — сигнатуры совпадают. Фабрика ещё и умеет то, чего конструктор не умеет: вернуть кешированный экземпляр, вернуть подтип, вернуть `Result` вместо исключения (см. [[Паттерны GoF: порождающие]]).

### Валидация и инварианты

Инвариант — утверждение, истинное всё время жизни объекта. Конструктор его устанавливает, методы обязаны сохранять.

```csharp
public sealed class DateRange
{
    public DateOnly Start { get; }
    public DateOnly End { get; }

    public DateRange(DateOnly start, DateOnly end)
    {
        // Инвариант: Start <= End. Устанавливаем здесь и больше нигде не проверяем.
        if (end < start)
            throw new ArgumentException($"Конец {end} раньше начала {start}.", nameof(end));
        Start = start;
        End = end;
    }

    public bool Contains(DateOnly d) => d >= Start && d <= End;   // проверка не нужна: инвариант держится
    public int Days => End.DayNumber - Start.DayNumber + 1;
}
```

Проверяй в конструкторе только то, что можно проверить дёшево и локально. Обращение к базе «а существует ли такой клиент» — это не валидация конструктора, это отдельный шаг сценария. Подробнее про guard clauses и `ArgumentNullException.ThrowIfNull` — в [[Защитное программирование и guard clauses]].

> [!warning] Подводные камни
> **1. Виртуальный вызов из конструктора базового класса.** Method table стоит с момента аллокации, вызов уйдёт в наследника, чьи поля, присваиваемые в теле конструктора, ещё `null`/`0`. Ловится анализатором CA2214.
>
> **2. Инициализаторы полей производного класса выполняются до конструктора базового.** Если ты пришёл из Java или C++, интуиция подскажет обратное. Проверяй на конкретном примере, а не по памяти.
>
> **3. `: this(...)` не запускает инициализаторы полей.** Они выполняются только в том конструкторе цепочки, который вызывает `base(...)`. Логика вида «дублируем инициализацию в каждом конструкторе» после добавления делегирования начинает молча пропускать шаг.
>
> **4. Object initializer выполняется после конструктора.** Валидация в конструкторе не видит значений, заданных через `{ ... }`. Если сеттер бросит, частично созданный `IDisposable` не будет освобождён.
>
> **5. `[SetsRequiredMembers]` ничего не проверяет.** Атрибут только глушит диагностику. Поставил и не присвоил — получишь `null` в свойстве, объявленном как non-nullable.
>
> **6. Параметр primary constructor изменяемый.** Скрытое capture-поле не `readonly`, любой метод типа может его переприсвоить. Для иммутабельности объявляй `private readonly` поле явно.
>
> **7. Исключение из конструктора не отменяет финализацию.** Объект уже в очереди финализации, финализатор увидит недостроенное состояние. Ещё один довод в пользу `SafeHandle` вместо ручных финализаторов.
>
> **8. Исключение в статическом конструкторе убивает тип насовсем.** `TypeInitializationException` кешируется: каждое следующее обращение к типу в этом процессе бросит то же исключение.

> [!example] Как делают в бою
> - В DI-сервисах — primary constructor: `public class OrderService(IRepo repo, ILogger<OrderService> log)`. Конструктор только сохраняет зависимости; никакого I/O, никакой логики, никаких `.Result`.
> - В доменных сущностях — обычный конструктор с валидацией плюс приватный конструктор без параметров для EF Core. EF умеет писать в backing field, поэтому публичные сеттеры ради ORM не нужны.
> - В DTO и конфигах — `required` + `init`: `public sealed class ApiOptions { public required string BaseUrl { get; init; } public int TimeoutSeconds { get; init; } = 30; }`. Забыть поле становится ошибкой компиляции, а не `NullReferenceException` в проде.
> - Асинхронное создание — всегда статический `CreateAsync`/`LoadAsync` с приватным конструктором. `new` в C# синхронный, и обойти это нельзя.
> - Если параметров конструктора стало больше пяти-шести — это сигнал, что класс делает слишком много. Сначала пересмотри ответственность (см. [[SOLID]]), и только потом вводи parameter object или builder.

## Вопросы с собеседований

> [!question]- В каком порядке выполняется инициализация при создании объекта производного класса?
> 1) Память выделяется и обнуляется. 2) Выполняются инициализаторы полей **производного** класса. 3) Управление уходит в конструктор базового класса: сначала инициализаторы полей базового, затем тело конструктора базового (и так рекурсивно вверх до `System.Object`). 4) Выполняется тело конструктора производного класса. Ключевой и неочевидный момент — шаг 2 идёт **до** конструктора базового класса; в Java и C++ порядок обратный. Ещё одна деталь: инициализаторы полей выполняются ровно один раз, в том конструкторе цепочки, который вызывает `base(...)`; конструктор, делегирующий через `: this(...)`, их не запускает.

> [!question]- Что напечатает виртуальный метод, вызванный из конструктора базового класса?
> Он уйдёт в переопределение производного класса — указатель на method table установлен до вызова любого конструктора, поэтому объект «знает» свой точный тип с момента аллокации. Поля производного класса, заданные **инициализаторами**, к этому моменту уже проинициализированы. Поля, присваиваемые в **теле** конструктора производного класса, ещё содержат значения по умолчанию: `null` для ссылок, `0` для чисел. На практике это даёт `NullReferenceException` или тихо неверные значения. Лечится тем, что виртуальные вызовы из конструкторов просто не делают: нужные наследнику данные передают через `base(...)`, вычисляя их статическим методом.

> [!question]- Чем `init` отличается от `set` и от `readonly`-поля? Даёт ли `init` настоящую иммутабельность?
> `set` можно вызвать в любой момент. `init` — только в «фазе инициализации»: в object initializer, в конструкторе своего или производного типа, в `with`-выражении. В IL это обычный сеттер с модификатором `modreq(IsExternalInit)`, и проверку делает **компилятор**, а не рантайм — через рефлексию `init`-свойство ставится как обычное, чем и пользуются сериализаторы. `readonly`-поле проверяется рантаймом жёстче, но его нельзя задать из object initializer. Настоящей иммутабельности `init` не даёт: если свойство возвращает `List<T>`, содержимое коллекции менять никто не мешает.

> [!question]- Зачем нужен `required`, если есть конструктор с обязательными параметрами?
> Конструктор и object initializer — два разных способа создания, и раньше выбрать «обязательность без конструктора» было нельзя. `required` закрывает случай, когда тип должен быть заполнен через object initializer (DTO, options, конфиги, типы для десериализаторов), но пропуск поля должен быть ошибкой компиляции, а не `null` в рантайме. При этом остаётся возможность добавлять новые необязательные свойства, не ломая существующий код, — с конструктором каждое новое обязательное поле требует новой перегрузки. Если нужен конструктор, который сам всё заполняет, помечаешь его `[SetsRequiredMembers]`, но помни: компилятор атрибут не проверяет, он просто выключает диагностику.

> [!question]- Чем primary constructor в `record` отличается от primary constructor в обычном `class`?
> В `record` на каждый параметр синтезируется **публичное `init`-свойство** с тем же именем, плюс `Deconstruct`, `Equals`/`GetHashCode`/`ToString` по значению и поддержка `with`. В обычном `class` не генерируется ничего публичного: параметр просто находится в области видимости всего тела типа и захватывается в **скрытое приватное поле**, причём только если он реально читается из какого-нибудь члена. Если параметр используется лишь в инициализаторах полей и в аргументах `base(...)` — поля не будет вовсе. Ещё разница: свойство record'а `init`-only, а capture-поле обычного класса изменяемо, так что `void Inc() => value++` в классе с primary constructor компилируется и работает.

> [!question]- Во что разворачивается `new Foo { A = 1, B = 2 }`?
> В создание временной переменной, вызов конструктора без параметров и последовательность присваиваний в порядке записи: `var t = new Foo(); t.A = 1; t.B = 2;` — и только затем результат присваивается целевой переменной. Три следствия: конструктор ничего не знает о значениях из инициализатора (валидировать их там нельзя); присваивания идут строго в исходном порядке; если сеттер бросит, ссылка на частично созданный объект нигде не сохранится, и для `IDisposable` это означает утечку ресурса, потому что `using var x = new FileStream(...) { Position = ... }` привяжется к переменной уже после присваиваний.

> [!question]- Что произойдёт, если конструктор бросит исключение? Соберётся ли объект?
> Объект уже выделен в куче и частично инициализирован; ссылка на него нигде не сохраняется, поэтому он немедленно становится недостижимым и будет собран GC. Но если у типа есть финализатор, он **всё равно будет вызван** — регистрация в очереди финализации происходит при аллокации, а не при успешном завершении конструктора. Поэтому финализатор обязан переживать полуинициализированное состояние: проверять поля на `null`, не обращаться к тому, чего может не быть. Практический вывод — не писать финализаторы вручную, оборачивать неуправляемые ресурсы в `SafeHandle`, а конструктор, захватывающий несколько ресурсов, защищать try/catch с откатом.

> [!question]- Почему I/O в конструкторе — плохая идея?
> Конструктор не может быть асинхронным, поэтому I/O в нём превращается в блокирующий вызов, а `new` — в операцию неизвестной длительности. Такой класс невозможно создать в тесте без реальной базы или сети. Исключение при `new` даёт вызывающему невнятную ошибку вместо осмысленного результата. Конструктор также не может вернуть кешированный экземпляр или подтип. Правильный приём — конструктор только присваивает и валидирует дёшево, а всё остальное уходит в статический асинхронный фабричный метод (`public static Task<Report> LoadAsync(...)`) при приватном конструкторе.

## Задачи

### Задача 1. Порядок вывода

Что напечатает этот код?

```csharp
class A
{
    public A() { Console.WriteLine("A ctor"); Print(); }
    protected virtual void Print() => Console.WriteLine("A.Print");
}

class B : A
{
    private string _s = "инициализатор";
    private string? _t;

    public B() { _t = "тело"; Console.WriteLine("B ctor"); }
    protected override void Print() => Console.WriteLine($"B.Print s={_s} t={_t ?? "null"}");
}

_ = new B();
```

> [!success]- Решение
> ```
> A ctor
> B.Print s=инициализатор t=null
> B ctor
> ```
> Сначала выполняется инициализатор `_s` производного класса `B` (ничего не печатает, но присваивает значение). Затем неявный `base()` уходит в конструктор `A`: тело печатает «A ctor» и делает виртуальный вызов `Print()`, который диспетчеризуется в `B.Print`. К этому моменту `_s` уже проинициализирован инициализатором, а `_t` присваивается только в теле конструктора `B`, которое ещё не выполнялось, — поэтому `null`. Последним отрабатывает тело конструктора `B`.

### Задача 2. Найди ошибку

Класс должен гарантировать, что `Items` никогда не `null` и содержит минимум один элемент. Что не так?

```csharp
public class Basket
{
    public List<string> Items { get; init; }

    public Basket()
    {
        if (Items is null || Items.Count == 0)
            throw new ArgumentException("Корзина не может быть пустой");
    }
}

var b = new Basket { Items = ["хлеб"] };
```

> [!success]- Решение
> Проверка в конструкторе выполняется **до** присваиваний из object initializer, поэтому `Items` там всегда `null` и код бросит исключение на любом создании. Object initializer разворачивается в `var t = new Basket(); t.Items = ["хлеб"];` — конструктор физически не может увидеть значение.
>
> Правильно — либо перенести обязательность в конструктор:
> ```csharp
> public sealed class Basket
> {
>     private readonly List<string> _items;
>
>     public Basket(IEnumerable<string> items)
>     {
>         ArgumentNullException.ThrowIfNull(items);
>         _items = [.. items];
>         if (_items.Count == 0)
>             throw new ArgumentException("Корзина не может быть пустой.", nameof(items));
>     }
>
>     public IReadOnlyList<string> Items => _items;
> }
> ```
> либо, если object initializer принципиален, проверять в сеттере:
> ```csharp
> public sealed class Basket
> {
>     public required IReadOnlyList<string> Items
> 	{
>         get;
>         init => field = value is { Count: > 0 }
>             ? value
>             : throw new ArgumentException("Корзина не может быть пустой.", nameof(value));
>     }
> }
> ```
> Второй вариант использует ключевое слово `field` из C# 14 — см. [[Свойства и field-backed properties]]. Он гарантирует непустоту, а `required` не даст забыть свойство.

### Задача 3. Убери дублирование инициализации

Перепиши так, чтобы валидация была написана один раз.

```csharp
public class HttpEndpoint
{
    public string Url { get; }
    public int RetryCount { get; }
    public TimeSpan Timeout { get; }

    public HttpEndpoint(string url)
    {
        if (string.IsNullOrWhiteSpace(url)) throw new ArgumentException(null, nameof(url));
        Url = url; RetryCount = 3; Timeout = TimeSpan.FromSeconds(30);
    }

    public HttpEndpoint(string url, int retryCount)
    {
        if (string.IsNullOrWhiteSpace(url)) throw new ArgumentException(null, nameof(url));
        if (retryCount < 0) throw new ArgumentOutOfRangeException(nameof(retryCount));
        Url = url; RetryCount = retryCount; Timeout = TimeSpan.FromSeconds(30);
    }

    public HttpEndpoint(string url, int retryCount, TimeSpan timeout)
    {
        if (string.IsNullOrWhiteSpace(url)) throw new ArgumentException(null, nameof(url));
        if (retryCount < 0) throw new ArgumentOutOfRangeException(nameof(retryCount));
        if (timeout <= TimeSpan.Zero) throw new ArgumentOutOfRangeException(nameof(timeout));
        Url = url; RetryCount = retryCount; Timeout = timeout;
    }
}
```

> [!success]- Решение
> ```csharp
> public sealed class HttpEndpoint
> {
>     public string Url { get; }
>     public int RetryCount { get; }
>     public TimeSpan Timeout { get; }
>
>     // Единственный "настоящий" конструктор: вся валидация здесь.
>     public HttpEndpoint(string url, int retryCount, TimeSpan timeout)
>     {
>         ArgumentException.ThrowIfNullOrWhiteSpace(url);
>         ArgumentOutOfRangeException.ThrowIfNegative(retryCount);
>         ArgumentOutOfRangeException.ThrowIfLessThanOrEqual(timeout, TimeSpan.Zero);
>
>         Url = url;
>         RetryCount = retryCount;
>         Timeout = timeout;
>     }
>
>     public HttpEndpoint(string url, int retryCount) : this(url, retryCount, DefaultTimeout) { }
>     public HttpEndpoint(string url)                 : this(url, DefaultRetries, DefaultTimeout) { }
>
>     private const int DefaultRetries = 3;
>     private static readonly TimeSpan DefaultTimeout = TimeSpan.FromSeconds(30);
> }
> ```
> Всё сводится к одному конструктору через `: this(...)`. Добавление новой проверки правится в одном месте. Альтернатива на C# 8+ — необязательные параметры (`int retryCount = 3`), но у них есть неприятная особенность: значения по умолчанию вшиваются в **вызывающую** сборку на этапе компиляции, поэтому изменение дефолта не подхватится без пересборки клиентов. Для публичных библиотек перегрузки надёжнее.

### Задача 4. Что напечатает primary constructor

```csharp
public class Base2(string tag)
{
    public string Tag { get; } = tag;
}

public class Derived2(string tag, int n) : Base2(tag)
{
    private readonly int _doubled = n * 2;
    public int N => n;
    public int Doubled => _doubled;
    public void Bump() => n++;
}

var d = new Derived2("x", 5);
d.Bump();
Console.WriteLine($"{d.Tag} {d.N} {d.Doubled}");
```

> [!success]- Решение
> ```
> x 6 10
> ```
> `n` читается из члена `N` и мутируется в `Bump()`, поэтому компилятор захватил его в скрытое приватное **не-readonly** поле — `n++` легально меняет состояние объекта, и `N` возвращает 6. `_doubled` вычислился один раз в инициализаторе поля (до вызова `base(...)`), значение 10 зафиксировалось и на `Bump()` не реагирует. Параметр `tag` передан в `base(...)` и больше нигде в `Derived2` не используется, поэтому capture-поля для него нет — значение живёт только в свойстве `Tag` базового класса.
>
> Мораль: primary constructor сам по себе не даёт иммутабельности. Нужна неизменяемость — заводи `private readonly` поле явно.

## Итог

- Порядок при наследовании: инициализаторы полей производного → инициализаторы полей базового → тело конструктора базового → тело конструктора производного. Инициализаторы выполняются только в конструкторе, вызывающем `base(...)`.
- Виртуальный вызов из конструктора базового класса уходит в наследника, поля которого, присваиваемые в теле конструктора, ещё `null`/`0`. Не делай так.
- Object initializer выполняется после конструктора: валидировать его значения в конструкторе невозможно, а исключение в сеттере теряет частично созданный объект.
- `init` — «задать только при создании», `required` — «нельзя забыть задать». Вместе они закрывают DTO и options; `[SetsRequiredMembers]` — обещание компилятору, а не проверка.
- Primary constructor захватывает параметр в скрытое **изменяемое** поле и только если параметр реально используется. В `record` он вдобавок генерирует публичные `init`-свойства, в `class` — нет.
- Конструктор присваивает и валидирует дёшево. I/O, асинхронность, кеширование, выбор подтипа — это фабричные методы.
