# Наследование

> [!abstract] Коротко
> Наследование (inheritance) — механизм, при котором производный тип получает все члены базового и может их дополнять и переопределять. В C# у класса ровно один базовый класс, но сколько угодно интерфейсов: единственное наследование реализации дало CLR простую раскладку полей в памяти и простую таблицу методов. Наследование создаёт самую жёсткую связь между типами из всех доступных в языке, поэтому по умолчанию берут композицию, а наследование — только когда действительно нужен подтип.

## Зачем это нужно

Под одним словом «наследование» прячутся три разные задачи, и путать их дорого:

1. **Подтипизация (subtyping)** — «`Dog` можно подставить везде, где ожидают `Animal`». Это про заменяемость и полиморфизм.
2. **Наследование реализации (implementation inheritance)** — «не хочу писать эти сорок строк второй раз». Это про переиспользование кода.
3. **Дифференциальное программирование** — «возьми вот это и поменяй одну деталь».

C# даёт все три одним двоеточием. Нужен обычно только первый пункт, а получаешь сразу три — вместе с жёсткой связью с внутренностями базового класса, которую потом невозможно разорвать без переписывания иерархии.

До наследования переиспользование делали копипастой или свободными функциями. Наследование дало формальный подтип: компилятор и рантайм гарантируют, что ссылка на `Animal` действительно указывает на объект, у которого есть все члены `Animal`. Это фундамент [[Полиморфизм: virtual, override, new]] и вообще всей объектной модели CLR.

## Синтаксис и базовые правила

```csharp
public class Animal
{
    protected readonly string _name;         // виден производным классам
    private int _secretId;                    // НЕ виден производным

    public Animal(string name) => _name = name;

    public string Name => _name;
    public virtual string Speak() => "...";
}

public class Dog : Animal                     // единственный базовый класс
{
    private readonly string _breed;

    public Dog(string name, string breed) : base(name)   // вызов конструктора базы
        => _breed = breed;

    public override string Speak() => "Гав";

    public string Describe() => $"{_name} — {_breed}";   // _name доступен: protected
}
```

Что происходит и почему:

- `: Animal` в списке базовых типов — базовый класс всегда первым, интерфейсы после.
- `base(name)` — явный вызов конструктора базового класса. Если не написать, компилятор подставит `base()`; если у базы нет конструктора без параметров — ошибка компиляции. Подробности порядка инициализации в [[Конструкторы и инициализация]].
- `protected` — доступ из производных классов, но не извне. `private` члены базы физически присутствуют в объекте, но недоступны по имени. Разбор всех уровней — в [[Инкапсуляция и модификаторы доступа]].
- Все классы неявно наследуются от `System.Object`, поэтому у любого типа есть `ToString`, `Equals`, `GetHashCode` ([[Object: Equals, GetHashCode, ToString]]).

## Почему один базовый класс, но много интерфейсов

Это не вкусовщина авторов языка, а три конкретных инженерных ограничения.

### 1. Проблема ромба (diamond problem)

```
        Base
       /    \
      A      B          A и B по-своему переопределяют Base.Draw()
       \    /
        Derived        какой Draw() вызывать у Derived?
```

Если бы `Derived` наследовал реализацию от `A` и от `B`, рантайм не смог бы однозначно выбрать метод. C++ решает это виртуальным наследованием и явной квалификацией — ценой сложности, которую мало кто держит в голове. CLR решил проще: реализация приходит ровно из одного места.

С интерфейсами ромба нет, потому что до C# 8 интерфейс не нёс реализации: две одинаковые сигнатуры схлопывались в один слот, который класс реализует один раз. Когда в C# 8 появились реализации по умолчанию (default interface methods), ромб вернулся — и язык потребовал явного разрешения конфликта. Подробности в [[Интерфейсы]].

### 2. Порядок полей в памяти

При единственном наследовании поля базового класса всегда лежат в начале объекта, а поля производного — сразу после. Значит, ссылка на `Dog` и ссылка на тот же объект как на `Animal` — это **один и тот же адрес**. Приведение вверх бесплатно, оно вообще ничего не делает в рантайме.

При множественном наследовании реализации адрес пришлось бы сдвигать при каждом приведении (в C++ это называется thunk-адаптация указателя), и понятие «адрес объекта» перестало бы быть единственным. Для GC, который ходит по ссылкам и перемещает объекты, это катастрофа.

### 3. Простота таблицы методов

Таблица виртуальных методов производного класса — это копия таблицы базового с перезаписанными слотами и дописанными в конец новыми. Индекс слота метода одинаков во всей ветке иерархии, поэтому виртуальный вызов — это две загрузки из памяти. При множественном наследовании реализации таблиц было бы несколько, и вызов усложнился бы. Механика в [[Полиморфизм: virtual, override, new]].

## Как выглядит объект производного класса в памяти

x64, обычный ссылочный тип:

```
 ссылка на объект (переменная в стеке / поле) ──┐
                                                v
        ┌───────────────────────────────────────────────┐
 -8     │  Object Header / Sync Block Index   (8 байт)  │  ЛЕВЕЕ адреса ссылки
        ╞═══════════════════════════════════════════════╡ <── сюда указывает ссылка
 +0     │  Method Table Pointer (указатель на MT Dog)   │  8 байт
        ├───────────────────────────────────────────────┤
 +8     │  Animal._name        (ссылка на string)       │ ┐
 +16    │  Animal._secretId    (int)                    │ ├ поля БАЗОВОГО класса
 +20    │  padding (выравнивание до 8)                  │ ┘
        ├───────────────────────────────────────────────┤
 +24    │  Dog._breed          (ссылка на string)       │ ┐ поля ПРОИЗВОДНОГО
        └───────────────────────────────────────────────┘ ┘
```

Ключевые следствия:

- **Поля базового класса идут первыми, всегда.** Внутри одного класса CLR имеет право переставлять поля (`LayoutKind.Auto` по умолчанию для классов), но границу «база → производный» не нарушает.
- **Указатель на MethodTable в объекте один**, и он указывает на MT самого точного типа (`Dog`), даже если переменная объявлена как `Animal`. Именно поэтому виртуальные вызовы работают.
- **Приведение вверх ничего не стоит** — адрес тот же, меняется только статический тип переменной для компилятора.
- Размер объекта растёт вниз по иерархии. Глубокая иерархия — это лишние байты на каждом экземпляре, но главная плата не в этом, а в связности.

Подробнее про header и раскладку — в [[Value types vs Reference types]].

## `base`: доступ к базовой реализации

```csharp
public class AuditedRepository : Repository
{
    public override void Save(Order order)
    {
        _log.Information("Сохраняем заказ {Id}", order.Id);
        base.Save(order);          // невиртуальный вызов Repository.Save
        _log.Information("Сохранили заказ {Id}", order.Id);
    }
}
```

`base.Save(...)` компилируется в IL-инструкцию `call` (не `callvirt`) — это единственный способ вызвать конкретную реализацию в обход виртуальной диспетчеризации. Без этого невозможно было бы «расширить» поведение базы.

`base` доступен только внутри экземплярных членов и только на уровень вверх: `base.base` не существует. Если очень надо перепрыгнуть уровень — это признак сломанного дизайна иерархии.

## Сокрытие членов: `new`

```csharp
public class Base    { public void Log() => Console.WriteLine("Base"); }
public class Derived : Base
{
    public new void Log() => Console.WriteLine("Derived");   // СКРЫВАЕТ, а не переопределяет
}

Derived d = new();
Base    b = d;

d.Log();   // Derived
b.Log();   // Base   ← тот же объект, другой ответ
```

Без `new` компилятор выдаст предупреждение CS0108: «член скрывает унаследованный член, добавьте `new`, если это намеренно». `new` — это не оптимизация и не «переопределение для невиртуальных методов», это два независимых метода с одинаковым именем. Какой вызовется, решает **статический тип переменной** на этапе компиляции.

Полный разбор `new` против `override`, включая коварный `new virtual`, — в [[Полиморфизм: virtual, override, new]].

## Преобразования по иерархии

```csharp
Animal a = new Dog("Рекс", "хаски");   // upcast — неявный, всегда безопасен

Dog  d1 = (Dog)a;                       // downcast — явный, InvalidCastException при промахе
Dog? d2 = a as Dog;                     // null при промахе, без исключения
if (a is Dog d3) { /* d3 уже типизирован */ }        // проверка + приведение
bool isDog = a is Dog;                  // просто проверка

string sound = a switch                 // pattern matching по типу
{
    Dog dog when dog.Name == "Рекс" => "Гав, я Рекс",
    Dog                             => "Гав",
    Cat                             => "Мяу",
    null                            => "нет животного",
    _                               => "..."
};
```

| Конструкция | IL | Что при промахе | Когда применять |
|---|---|---|---|
| неявный upcast | ничего | невозможен | всегда |
| `(Dog)a` | `castclass` | `InvalidCastException` | промах = баг, хочу упасть громко |
| `a as Dog` | `isinst` | `null` | промах — норма, дальше проверка на null |
| `a is Dog d` | `isinst` + branch | ветка не берётся | стандартный выбор в современном коде |
| `switch` по типам | серия `isinst` | ветка `_` | разбор нескольких вариантов |

`as` + проверка на null и `is` с паттерном компилируются в одно и то же — `isinst` и переход. Так что писать `if (a is Dog d)` не медленнее, чем `var d = a as Dog; if (d != null)`, а читается лучше. Подробнее про паттерны — [[Pattern matching]].

> [!info] Почему downcast — это запах
> Каждый `(Dog)animal` в коде говорит: «я знаю про объект больше, чем говорит его тип». Иногда это неизбежно (десериализация, границы фреймворка), но частые downcast'ы в бизнес-логике означают, что абстракция выбрана неправильно: либо метод должен быть виртуальным, либо иерархия должна быть плоской, а различия — данными.

## `sealed`: запрет наследования

```csharp
public sealed class MoneyFormatter { /* от меня нельзя наследоваться */ }

public class Repo
{
    public virtual void Save() { }
}
public class CachingRepo : Repo
{
    public sealed override void Save() { }   // дальше переопределять нельзя
}
```

Зачем запечатывать:

- **Дизайн.** Класс, не спроектированный под наследование, лучше запечатать, чем чинить чужие сломанные наследники. Наследование — часть публичного контракта, и его тоже придётся поддерживать.
- **Производительность.** JIT знает точный тип и может девиртуализировать вызов и встроить его. Проверка приведения к `sealed`-типу тоже дешевле: достаточно сравнить указатели на MethodTable, не идя вверх по иерархии.
- **Инварианты.** Иммутабельный класс перестаёт быть иммутабельным, если наследник добавит изменяемое поле. `sealed` закрывает лазейку — см. [[Иммутабельность как приём проектирования]].

Структуры и `record struct` запечатаны неявно. Строковые и числовые типы BCL — тоже.

## Почему нельзя наследоваться от `string` и `int`

```csharp
public class MyString : string { }   // CS0509: 'MyString': cannot derive from sealed type 'string'
public class MyInt : int { }         // CS0509 — int это struct, структуры запечатаны неявно
```

Причины разные:

- **`System.String` объявлен `sealed`.** У строки особое устройство: длина хранится в объекте, символы лежат сразу за ней переменной длиной, рантайм и JIT знают эту раскладку и генерируют для неё специальный код (интернирование, литералы, `RuntimeHelpers`). Наследник с дополнительными полями разрушил бы эту раскладку. Плюс строка иммутабельна, и на этом держатся семантика значений, безопасность и потокобезопасность.
- **`int` — это `struct`.** Все значимые типы наследуются от `System.ValueType` и **запечатаны неявно**: у структуры нет указателя на MethodTable в самом значении, значит нет и механизма виртуальной диспетчеризации по подтипу. Подтипизация значимых типов физически невозможна при их раскладке. См. [[Value types vs Reference types]].

Отдельная группа — типы, наследоваться от которых запрещает **компилятор**, даже если формально они не запечатаны: `System.ValueType`, `System.Enum`, `System.Array`, `System.Delegate`, `System.MulticastDelegate`. Их производит только сам рантайм.

Что делать вместо: расширяющие методы, обёртка-композиция, `record` со свойством нужного типа. Для строк почти всегда нужен именно extension-метод или отдельный value object.

## Fragile base class problem

Самая дорогая проблема наследования: изменение базового класса, корректное само по себе, тихо ломает наследников.

```csharp
// ── Версия 1 базового класса ─────────────────────────────
public class Bag<T>
{
    private readonly List<T> _items = [];

    public virtual void Add(T item) => _items.Add(item);

    public virtual void AddRange(IEnumerable<T> items)
    {
        foreach (var item in items)
            Add(item);              // ← ВНУТРЕННИЙ вызов виртуального Add
    }

    public int Count => _items.Count;
}

// Наследник в другой сборке. Хочет считать, сколько всего добавили.
public class CountingBag<T> : Bag<T>
{
    public int AddedCount { get; private set; }

    public override void Add(T item)
    {
        AddedCount++;
        base.Add(item);
    }
}

var bag = new CountingBag<int>();
bag.AddRange([1, 2, 3]);
Console.WriteLine(bag.AddedCount);   // Вывод: 3 — работает
```

Пока всё хорошо. Автор `CountingBag` даже не переопределял `AddRange` — и правильно, счётчик и так растёт.

Теперь автор `Bag<T>` делает безобидную оптимизацию:

```csharp
// ── Версия 2 базового класса: -1 аллокация энумератора, +скорость ─────
public virtual void AddRange(IEnumerable<T> items)
{
    _items.AddRange(items);         // больше НЕ вызываем Add
}
```

Публичный контракт не изменился ни на байт. Тесты `Bag<T>` зелёные. А наследник:

```csharp
var bag = new CountingBag<int>();
bag.AddRange([1, 2, 3]);
Console.WriteLine(bag.AddedCount);   // Вывод: 0  ← тихо сломалось
Console.WriteLine(bag.Count);        // Вывод: 3
```

Ничего не упало, исключения нет, компилятор молчит. Просто метрика в проде показывает ноль.

Зеркальная версия той же беды: если бы `CountingBag` на всякий случай переопределил и `AddRange` со своим счётчиком, то на версии 1 он считал бы **вдвое** (`AddRange` увеличил счётчик и позвал `base.AddRange`, который вызвал переопределённый `Add`).

Суть: **наследник зависит не от контракта базы, а от того, какие свои методы база вызывает внутри себя (self-call pattern).** Это деталь реализации, её никто не документирует и никто не считает частью совместимости. Обёртка через композицию такой зависимости не имеет — она видит только публичный API.

```csharp
// Композиция: та же задача, никакой хрупкости
public sealed class CountingBag<T>
{
    private readonly Bag<T> _inner = new();
    public int AddedCount { get; private set; }

    public void Add(T item)   { AddedCount++; _inner.Add(item); }
    public void AddRange(IEnumerable<T> items)
    {
        var list = items as IReadOnlyCollection<T> ?? [.. items];
        AddedCount += list.Count;
        _inner.AddRange(list);
    }
    public int Count => _inner.Count;
}
```

Как жить с наследованием, если оно всё-таки нужно: документируй self-calls («`AddRange` вызывает `Add` для каждого элемента, это часть контракта») и считай эту документацию таким же обязательством, как сигнатуры. Именно так поступает BCL для классов, спроектированных под наследование, — например, `Collection<T>` явно обещает, что все мутации проходят через `InsertItem`/`SetItem`/`RemoveItem`/`ClearItems`.

## Нарушение LSP: Rectangle и Square

Принцип подстановки Лисков (Liskov Substitution Principle) требует: объект подтипа должен подставляться вместо объекта базового типа, не ломая корректность программы. Классический контрпример:

```csharp
public class Rectangle
{
    public virtual int Width  { get; set; }
    public virtual int Height { get; set; }
    public int Area => Width * Height;
}

public class Square : Rectangle
{
    public override int Width
    {
        get => base.Width;
        set { base.Width = value; base.Height = value; }   // квадрат обязан остаться квадратом
    }
    public override int Height
    {
        get => base.Height;
        set { base.Width = value; base.Height = value; }
    }
}

// Код, написанный против Rectangle и ничего не знающий про Square:
static void Stretch(Rectangle r)
{
    r.Width  = 4;
    r.Height = 5;
    Console.WriteLine(r.Area);
}

Stretch(new Rectangle());   // Вывод: 20 — ожидаемо
Stretch(new Square());      // Вывод: 25 — Width уже не 4
```

Здесь важно понять, **где именно** ошибка. Геометрия ни при чём: квадрат действительно является прямоугольником. Ошибка в том, что тип `Rectangle` — **изменяемый**, и его неявный контракт включает постусловие: «после `Width = w` высота не изменилась». `Square` это постусловие нарушает.

Правило: LSP — про **поведение** (пред- и постусловия, инварианты, исключения), а не про то, как объекты соотносятся в реальном мире. Наследник может ослаблять предусловия и усиливать постусловия, но не наоборот.

Как чинится:

```csharp
// Иммутабельные типы: постусловия про мутацию не существует, проблема исчезает
public record Rectangle(int Width, int Height)
{
    public int Area => Width * Height;
}
public static class Shapes
{
    public static Rectangle Square(int side) => new(side, side);   // фабрика, не подтип
}
```

Квадрат перестаёт быть подтипом и становится **способом создать** прямоугольник. Ничего не потеряно, ловушки нет. См. [[SOLID]] и [[Иммутабельность как приём проектирования]].

## Антипаттерн: наследование ради переиспользования кода

```csharp
// ПЛОХО: наследуемся, потому что в базе лежат удобные методы
public class HttpHelpers
{
    protected static HttpClient Client = new();
    protected string BuildUrl(string path) => $"https://api.example.com/{path}";
    protected T Deserialize<T>(string json) => JsonSerializer.Deserialize<T>(json)!;
}

public class OrderService : HttpHelpers { /* ... */ }
public class UserService  : HttpHelpers { /* ... */ }
```

Что здесь не так:

- `OrderService` **не является** `HttpHelpers` — подтипизация тут бессмысленна, никто не будет писать `HttpHelpers h = orderService`.
- Единственный слот наследования сожжён на утилиты. Если завтра понадобится общий базовый класс по делу — его некуда воткнуть.
- Все наследники связаны друг с другом через базу: правка `BuildUrl` для одного ломает остальных.
- `protected static` поле — общее изменяемое состояние на всю иерархию.

```csharp
// ХОРОШО: зависимость передаётся, а не наследуется
public sealed class ApiClient(HttpClient http, IOptions<ApiOptions> options)
{
    public async Task<T> GetAsync<T>(string path, CancellationToken ct)
    {
        var url = new Uri(options.Value.BaseUrl, path);
        return await http.GetFromJsonAsync<T>(url, ct) ?? throw new InvalidOperationException("Пустой ответ");
    }
}

public sealed class OrderService(ApiClient api) { /* использует api */ }
public sealed class UserService(ApiClient api)  { /* использует api */ }
```

Проверка одним вопросом: **«Захочу ли я подставить наследника туда, где ожидается база?»** Нет — значит наследование не нужно, нужна композиция или обычный сервис. Развёрнуто — в [[Композиция vs наследование]] и [[Связанность и связность (coupling, cohesion)]].

> [!warning] Подводные камни
> **1. Виртуальный вызов из конструктора базы попадает в неинициализированный наследник.** Конструктор базы отрабатывает раньше инициализаторов полей и тела конструктора производного класса. Если база вызовет `virtual`-метод, выполнится переопределение наследника, где все поля ещё в значениях по умолчанию (`null`, `0`), включая `readonly`. Компилятор молчит, анализатор CA2214 предупреждает. Никогда не вызывай виртуальные члены из конструктора; если нужна точка расширения на старте — вынеси её в отдельный `Initialize()` или в фабрику. Порядок инициализации разобран в [[Конструкторы и инициализация]].
>
> **2. `new` вместо `override` возвращает разные ответы для одного объекта.** `Base b = derived; b.Log();` вызовет метод базы, потому что выбор делается по статическому типу переменной. Это регулярно происходит случайно: кто-то убрал `virtual` из базы, компилятор потребовал `new`, разработчик дописал `new` вместо того, чтобы разобраться. Симптом — «метод не вызывается, хотя я его переопределил».
>
> **3. Расширяющие методы (extension methods) не участвуют в полиморфизме.** Они разрешаются по статическому типу выражения на этапе компиляции. Метод расширения для `Animal` не «переопределяется» методом расширения для `Dog`, если переменная объявлена как `Animal`.
>
> **4. `protected` — это часть публичного API.** Всё, что помечено `protected`, обязано поддерживаться так же строго, как `public`: любой наследник в чужой сборке на это опирается. Каждое `protected`-поле — это дыра в инкапсуляции на всю глубину иерархии. Предпочитай `protected` метод, а не `protected` поле, и `private protected`, если наследники ожидаются только внутри своей сборки.
>
> **5. Наследование ломает бинарную совместимость сильнее, чем кажется.** Добавление в базовый класс метода `Save()` тихо сделает существующий метод `Save()` наследника скрывающим, а не переопределяющим (и при перекомпиляции всплывёт предупреждение CS0108). Для библиотек, распространяемых как NuGet-пакеты, это реальный источник поломок.

> [!example] Как делают в бою
> - **Иерархия в проде почти всегда мельче двух-трёх уровней.** Иерархия на пять уровней — это код, который никто не может отладить, потому что для понимания одного вызова надо держать в голове пять файлов.
> - **`sealed` по умолчанию на все классы, кроме явно спроектированных под наследование.** Многие команды включают это правилом анализатора. Открыть класс потом можно всегда, закрыть уже используемый — нельзя.
> - **Исключения — законное место для наследования.** `class OrderNotFoundException : DomainException` — здесь подтипизация ровно то, что нужно: `catch (DomainException)` ловит всё семейство. См. [[Свои типы исключений]].
> - **Базовые классы во фреймворках** (`ControllerBase`, `DbContext`, `BackgroundService`, `Middleware`-подобные) — это Template Method: фреймворк вызывает твои переопределения. Наследоваться от них нормально, потому что они спроектированы под это и их self-calls задокументированы. См. [[Абстрактные классы]].
> - **В доменной модели** предпочитают закрытую иерархию: абстрактный базовый тип с приватным конструктором и несколько `sealed`-наследников, разбираемых через `switch` по паттернам. Это даёт полиморфизм там, где он нужен, и запрещает неконтролируемое расширение снаружи.

## Вопросы с собеседований

> [!question]- Почему в C# нет множественного наследования классов, но есть множественная реализация интерфейсов?
> Три причины. Первая — проблема ромба: при двух базовых классах с разными реализациями одного метода рантайм не может однозначно выбрать реализацию. Вторая — раскладка памяти: при единственном наследовании поля базы всегда лежат в начале объекта, поэтому приведение вверх не меняет адрес; при множественном пришлось бы сдвигать указатель, что несовместимо с тем, как GC отслеживает ссылки. Третья — таблица методов: она получается простой копией родительской с перезаписанными слотами, индекс слота стабилен по всей ветке иерархии, и виртуальный вызов стоит две загрузки из памяти. Интерфейсы до C# 8 не несли реализации, конфликтовать было нечему — конфликтовали только сигнатуры, а они схлопываются в один слот. С появлением default interface methods ромб вернулся, и язык требует явно разрешать конфликт переопределением в производном интерфейсе или классе.

> [!question]- Что произойдёт при вызове виртуального метода из конструктора базового класса?
> Вызовется переопределение производного класса — потому что указатель на MethodTable в объекте выставлен на точный тип ещё до запуска любого конструктора. Но к этому моменту инициализаторы полей и тело конструктора производного класса ещё не выполнялись, поэтому все его поля содержат значения по умолчанию: `null` у ссылок, `0` у чисел, причём даже `readonly`-поля. Классический результат — `NullReferenceException` при создании объекта или тихо неверное поведение. Правильно — не вызывать виртуальные члены из конструкторов вообще; если нужна точка расширения при создании, использовать фабричный метод, который сначала полностью конструирует объект, а потом вызывает `Initialize()`.

> [!question]- Что такое fragile base class problem? Приведи пример.
> Ситуация, когда изменение базового класса, полностью корректное с точки зрения его публичного контракта, ломает наследников. Классика: базовая коллекция, у которой `AddRange` внутри в цикле вызывает виртуальный `Add`. Наследник переопределяет только `Add`, чтобы вести счётчик, и всё работает. Автор базы оптимизирует `AddRange`, заменив цикл на прямую вставку во внутренний список, — контракт не изменился, тесты базы зелёные, а счётчик наследника молча перестаёт расти. Причина в том, что наследник зависит от **внутреннего** паттерна самовызовов базы, который не является частью документированного API. Лечится либо композицией (обёртка видит только публичный API), либо явной документацией самовызовов как части контракта — так делает `Collection<T>` в BCL, обещая, что все мутации проходят через `InsertItem`/`SetItem`/`RemoveItem`/`ClearItems`.

> [!question]- Почему нельзя унаследоваться от `string`? А от `int`?
> `System.String` объявлен `sealed`. У строки специальная раскладка в памяти: поле длины и сразу за ним символы переменной длиной; рантайм, JIT и сборщик мусора знают эту раскладку и генерируют для неё особый код — литералы, интернирование, быстрые операции. Наследник со своими полями сломал бы всё это. Плюс иммутабельность строки — фундамент её потокобезопасности и семантики значения. С `int` причина иная: это структура, а все значимые типы неявно запечатаны, потому что значение структуры не содержит указателя на MethodTable — механизма для виртуальной диспетчеризации по подтипу физически нет. Отдельно есть типы, наследование от которых запрещает компилятор: `ValueType`, `Enum`, `Array`, `Delegate`, `MulticastDelegate` — их порождает только рантайм. Заменители: расширяющие методы, обёртка через композицию, value object на `record struct`.

> [!question]- Пример с Rectangle и Square — это про геометрию?
> Нет. Геометрически квадрат — прямоугольник, спорить не с чем. Проблема в том, что тип `Rectangle` сделан изменяемым, и его неявный контракт содержит постусловие: после присваивания `Width` значение `Height` не изменилось. `Square`, синхронизирующий стороны, это постусловие нарушает — и любой код, написанный против `Rectangle`, начинает получать неожиданные результаты. LSP говорит именно о поведении: наследник может ослаблять предусловия и усиливать постусловия, но не наоборот. Если сделать `Rectangle` иммутабельным `record`, постусловия про мутацию просто нет, и квадрат превращается из подтипа в фабричный метод `Shapes.Square(side)` — проблема исчезает вместе с сеттерами.

> [!question]- Чем `as` отличается от прямого приведения `(T)x`, и что использовать?
> `(T)x` компилируется в `castclass`: при несоответствии типа бросает `InvalidCastException`. `x as T` компилируется в `isinst`: при несоответствии возвращает `null`, поэтому применим только к ссылочным и nullable-типам. Выбор по семантике: если промах — это баг, нужен `castclass`, чтобы упасть громко и близко к причине. Если промах — нормальный сценарий, нужен `as` или, что лучше в современном коде, `if (x is T t)`. Последний вариант компилируется в тот же `isinst` плюс переход, то есть по стоимости идентичен `as` с проверкой на null, но короче и не оставляет в области видимости переменную, которая может быть null.

> [!question]- Зачем помечать класс `sealed`, если наследоваться от него всё равно никто не собирается?
> Три причины. Дизайн: наследование — часть публичного контракта, и открытый класс обязывает поддерживать совместимость для наследников, включая порядок внутренних вызовов. Производительность: JIT знает точный тип, девиртуализирует вызовы и может их встроить, а проверка приведения к запечатанному типу сводится к сравнению указателей на MethodTable вместо прохода вверх по иерархии. Инварианты: иммутабельность, потокобезопасность, корректность `Equals`/`GetHashCode` легко ломаются наследником, добавившим состояние. Практическое правило — запечатывать по умолчанию: открыть класс потом можно, закрыть уже используемый нельзя, это ломающее изменение.

## Задачи

### Задача 1. Предсказать вывод

```csharp
public class A
{
    public A() { Init(); }
    protected virtual void Init() => Console.WriteLine("A.Init");
}

public class B : A
{
    private readonly List<int> _items = [1, 2, 3];
    protected override void Init() => Console.WriteLine($"B.Init, items = {_items?.Count.ToString() ?? "null"}");
}

_ = new B();
```

Что напечатает и почему?

> [!success]- Решение
> ```
> B.Init, items = null
> ```
> Порядок такой: сначала выполняются инициализаторы полей `B`? Нет — наоборот. Для производного класса CLR выполняет: инициализаторы полей `B` → конструктор `A` (через `base()`) → тело конструктора `B`. Но инициализаторы полей `B` выполняются **после** вызова `base()`, если конструктор `B` неявный... На самом деле правило в C# такое: инициализаторы полей производного класса выполняются **перед** вызовом конструктора базового класса — но только у того класса, чей конструктор сейчас работает. Здесь у `B` конструктора нет, компилятор сгенерировал `public B() : base() { _items = [1,2,3]; }` — и инициализатор поля идёт **до** `base()`... нет.
>
> Правильный порядок в C# (спецификация, раздел про создание экземпляра): инициализаторы полей класса `B` выполняются, затем вызывается конструктор базового класса, затем тело конструктора `B`. То есть `_items` должен быть уже заполнен?
>
> Нет: инициализаторы полей выполняются перед вызовом `base()` только для того класса, который их объявил, и порядок при создании `B` такой: инициализаторы `B` → `A()` → тело `B()`. Значит вывод был бы `items = 3`.
>
> Проверь сам — и запомни правильный ответ: **`B.Init, items = 3`**. C# отличается здесь от Java и C++: в C# инициализаторы полей производного класса выполняются **до** вызова конструктора базы, поэтому ловушка «поля наследника ещё null» в C# срабатывает не на инициализаторах полей, а на **присваиваниях в теле конструктора**:
> ```csharp
> public class B : A
> {
>     private readonly List<int> _items;
>     public B() { _items = [1, 2, 3]; }              // тело — ПОСЛЕ base()
>     protected override void Init() => Console.WriteLine($"items = {_items?.Count.ToString() ?? "null"}");
> }
> _ = new B();   // Вывод: items = null
> ```
> Вывод: вызывать виртуальные методы из конструктора всё равно нельзя — в общем случае ты не контролируешь, чем наследник инициализирует поля.

### Задача 2. Починить хрупкую базу

Дан класс, наследники которого регулярно ломаются при рефакторинге:

```csharp
public class Notifier
{
    public virtual void Notify(string message)  { Send(Format(message)); }
    public virtual void NotifyAll(IEnumerable<string> messages)
    {
        foreach (var m in messages) Notify(m);
    }
    protected virtual string Format(string m) => m;
    protected virtual void Send(string m) => Console.WriteLine(m);
}
```

Перепроектируй так, чтобы точки расширения были явными и минимальными, а внутренние вызовы не были частью контракта.

> [!success]- Решение
> ```csharp
> public abstract class Notifier
> {
>     // Шаблонные методы: НЕ виртуальные, их поведение фиксировано.
>     public void Notify(string message) => Send(Format(message));
>
>     public void NotifyAll(IEnumerable<string> messages)
>     {
>         foreach (var m in messages)
>             Send(Format(m));      // не через Notify: самовызова больше нет
>     }
>
>     // Ровно две точки расширения, обе обязательны или явно опциональны.
>     protected abstract void Send(string formatted);
>     protected virtual string Format(string raw) => raw;
> }
>
> public sealed class SlackNotifier(ISlackApi api) : Notifier
> {
>     protected override void Send(string formatted) => api.Post(formatted);
>     protected override string Format(string raw) => $"*{raw}*";
> }
> ```
> Что изменилось и почему это работает:
> - `Notify`/`NotifyAll` больше не виртуальные — наследник не может подменить скелет алгоритма, значит база вправе менять его реализацию без риска.
> - `NotifyAll` не вызывает `Notify`: внутренний самовызов, от которого зависели наследники, устранён.
> - Точек расширения две, они `protected` и явно названы. `Send` абстрактный — компилятор заставит реализовать.
> - Класс абстрактный: он бесполезен сам по себе, создавать его экземпляр незачем.
>
> Это Template Method в чистом виде, разбор — в [[Абстрактные классы]].

### Задача 3. Убрать наследование

```csharp
public class CsvExporter
{
    protected string Escape(string value) => value.Contains(',') ? $"\"{value}\"" : value;
    protected string Join(IEnumerable<string> cells) => string.Join(',', cells.Select(Escape));
}

public class OrderExporter : CsvExporter
{
    public string Export(IEnumerable<Order> orders) =>
        string.Join('\n', orders.Select(o => Join([o.Id.ToString(), o.Customer, o.Total.ToString()])));
}
```

`OrderExporter` явно не «является» `CsvExporter`. Перепиши без наследования.

> [!success]- Решение
> ```csharp
> public static class Csv
> {
>     public static string Escape(string value) =>
>         value.AsSpan().ContainsAny(',', '"', '\n') ? $"\"{value.Replace("\"", "\"\"")}\"" : value;
>
>     public static string Row(params ReadOnlySpan<string> cells)
>     {
>         var sb = new StringBuilder();
>         for (var i = 0; i < cells.Length; i++)
>         {
>             if (i > 0) sb.Append(',');
>             sb.Append(Escape(cells[i]));
>         }
>         return sb.ToString();
>     }
> }
>
> public sealed class OrderExporter
> {
>     public string Export(IEnumerable<Order> orders) =>
>         string.Join('\n', orders.Select(o => Csv.Row(o.Id.ToString(), o.Customer, o.Total.ToString())));
> }
> ```
> Почему так лучше: `Csv` — набор чистых функций без состояния, его можно тестировать отдельно и переиспользовать где угодно; слот наследования у `OrderExporter` свободен; изменение экранирования не может сломать наследников, потому что их нет. Проверочный вопрос «подставлю ли я `OrderExporter` туда, где ждут `CsvExporter`?» даёт «нет» — значит подтипизация была лишней с самого начала. См. [[Композиция vs наследование]].

### Задача 4. Найти нарушение LSP

```csharp
public class FileStorage
{
    public virtual void Save(string path, byte[] data) => File.WriteAllBytes(path, data);
}

public class ReadOnlyStorage : FileStorage
{
    public override void Save(string path, byte[] data) =>
        throw new NotSupportedException("Хранилище только для чтения");
}
```

В чём нарушение и как переделать?

> [!success]- Решение
> Нарушение: наследник **усиливает предусловие** до невыполнимого — он не работает ни при каких аргументах. Любой код `void Backup(FileStorage s) => s.Save(path, bytes);` корректен против базы и падает на подтипе. LSP запрещает подтипу бросать исключения, не предусмотренные контрактом базы.
>
> Правильно — разделить контракты (Interface Segregation из [[SOLID]]):
> ```csharp
> public interface IReadableStorage
> {
>     byte[] Read(string path);
> }
>
> public interface IWritableStorage : IReadableStorage
> {
>     void Save(string path, byte[] data);
> }
>
> public sealed class FileStorage : IWritableStorage { /* Read + Save */ }
> public sealed class ArchiveStorage : IReadableStorage { /* только Read */ }
> ```
> Теперь `void Backup(IWritableStorage s)` физически не примет хранилище только для чтения — ошибка ловится компилятором, а не в проде. Это же объясняет, почему у `IReadOnlyList<T>` в BCL нет `Add`, а не есть-но-кидает.

## Итог

- Наследование даёт три вещи разом: подтипизацию, переиспользование реализации и дифференциальное программирование. Нужна почти всегда только первая — остальное берётся композицией.
- Единственное наследование классов — следствие раскладки памяти (поля базы первыми, адрес не меняется при приведении), простоты таблицы методов и проблемы ромба. Интерфейсы конфликтов не создавали, пока не появились реализации по умолчанию.
- `base` даёт невиртуальный вызов реализации родителя; `new` не переопределяет, а создаёт второй метод, и выбор делается по статическому типу переменной.
- Upcast бесплатен и неявен, downcast явный: `castclass` для «промах = баг», `is`-паттерн для «промах — норма». Частые downcast'ы в бизнес-логике означают неверную абстракцию.
- Fragile base class: наследник зависит от недокументированных самовызовов базы. Любое изменение базы становится потенциально ломающим. Композиция такой зависимости не имеет.
- LSP — про поведение (пред-/постусловия, инварианты, исключения), а не про предметную область. Изменяемость типа — главный источник нарушений; иммутабельность их убирает.
- Практическое правило: `sealed` по умолчанию, наследование только там, где реально нужен полиморфный подтип и база спроектирована под расширение.
