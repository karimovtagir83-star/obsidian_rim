# Явная реализация интерфейсов

> [!abstract] Коротко
> Обычно интерфейс реализуют неявно: публичный член класса одновременно закрывает контракт. Явная реализация (`void IFoo.Bar() { }`) привязывает член именно к интерфейсу: у него нет модификатора доступа, он не виден через ссылку на класс и вызывается только после приведения к интерфейсу. Три реальных применения: разрешить конфликт одинаковых членов двух интерфейсов, убрать из публичного API типа служебные члены (классика — не-обобщённый `IEnumerable.GetEnumerator`) и дать интерфейсной версии другое поведение или другой возвращаемый тип, чем у публичного метода.

## Зачем это нужно

```csharp
public sealed class Repository : IDisposable
{
    public void Dispose() { }         // неявно: метод торчит в публичном API класса
}

public sealed class Repository2 : IDisposable
{
    void IDisposable.Dispose() { }    // явно: виден только через IDisposable
}

var r = new Repository2();
// r.Dispose();                        // не компилируется
((IDisposable)r).Dispose();            // так — да
using (var x = new Repository2()) { }  // using работает: он приводит к IDisposable
```

Смысл — контроль над тем, что видно в подсказках IDE и в контракте типа. Чем меньше публичных членов, тем понятнее, как типом пользоваться.

## Синтаксис и правила

```csharp
public interface IJsonSerializer { string Serialize(object value); }

public sealed class Serializer : IJsonSerializer
{
    // Явная реализация: имя члена квалифицировано интерфейсом
    string IJsonSerializer.Serialize(object value) => System.Text.Json.JsonSerializer.Serialize(value);
}
```

- **Нет модификатора доступа.** Ни `public`, ни `private` писать нельзя: доступность определяется интерфейсом.
- **Не виден через тип класса** — только через ссылку на интерфейс.
- **Нельзя объявить `virtual`, `abstract`, `override`.** Явно реализованный член не переопределяется наследником напрямую; наследник может лишь заново реализовать интерфейс (`class D : C, IFoo`), что меняет привязку.
- **Нельзя вызвать изнутри класса без приведения**: `((IJsonSerializer)this).Serialize(x)`.
- Работает для методов, свойств, индексаторов и событий.

```csharp
public sealed class Cache : IReadOnlyDictionary<string, string>
{
    // Явно реализованные члены не засоряют API класса
    IEnumerable<string> IReadOnlyDictionary<string, string>.Keys => _map.Keys;
    IEnumerable<string> IReadOnlyDictionary<string, string>.Values => _map.Values;
    int IReadOnlyCollection<KeyValuePair<string, string>>.Count => _map.Count;
    // ...
    private readonly Dictionary<string, string> _map = [];
}
```

## Три сценария, где это действительно нужно

### 1. Конфликт членов двух интерфейсов

```csharp
public interface IFileWriter { void Write(string text); }
public interface IConsoleWriter { void Write(string text); }

public sealed class DualWriter : IFileWriter, IConsoleWriter
{
    void IFileWriter.Write(string text) => File.AppendAllText("out.txt", text);
    void IConsoleWriter.Write(string text) => Console.WriteLine(text);
}

var w = new DualWriter();
((IFileWriter)w).Write("в файл");
((IConsoleWriter)w).Write("в консоль");
```

Без явной реализации одна публичная `Write` закрыла бы оба контракта, и разного поведения добиться было бы невозможно.

### 2. Служебные члены, которые не нужны потребителю

Классика — реализация `IEnumerable<T>`, которая требует ещё и не-обобщённую версию из `IEnumerable`:

```csharp
public sealed class OrderCollection : IEnumerable<Order>
{
    private readonly List<Order> _items = [];

    public List<Order>.Enumerator GetEnumerator() => _items.GetEnumerator();   // структура, без аллокации

    IEnumerator<Order> IEnumerable<Order>.GetEnumerator() => _items.GetEnumerator();
    System.Collections.IEnumerator System.Collections.IEnumerable.GetEnumerator() => _items.GetEnumerator();
}
```

Здесь сразу три приёма: публичный `GetEnumerator` возвращает **структурный** перечислитель (поэтому `foreach` по конкретному типу не аллоцирует — компилятор ищет метод по форме, а не по интерфейсу, см. [[Циклы и итерация]]); обе интерфейсные версии реализованы явно и не мешают в подсказках; устаревшая не-обобщённая версия спрятана полностью.

### 3. Другой тип результата или другое поведение

```csharp
public sealed class Money : IComparable<Money>, IComparable
{
    public decimal Amount { get; init; }

    public int CompareTo(Money? other) => Amount.CompareTo(other?.Amount ?? 0);

    // Не-обобщённая версия с object — только для старых API, прячем её
    int IComparable.CompareTo(object? obj) => obj is Money m
        ? CompareTo(m)
        : throw new ArgumentException("Ожидался Money", nameof(obj));
}
```

Публичным остаётся типобезопасный метод, а вариант с `object` доступен только тем, кто работает через `IComparable` (например, `Array.Sort` для не-обобщённых коллекций).

## Явная плюс публичная: комбинированный приём

Часто нужны обе формы: удобная публичная и интерфейсная, делегирующая к ней.

```csharp
public sealed class Temperature : IFormattable
{
    public double Celsius { get; init; }

    public string ToString(string? format) => format switch
    {
        "F" => $"{Celsius * 9 / 5 + 32:F1}°F",
        _ => $"{Celsius:F1}°C"
    };

    // Интерфейсная версия с лишним параметром — явно, чтобы не мешала
    string IFormattable.ToString(string? format, IFormatProvider? provider) => ToString(format);
}
```

Так публичный API остаётся чистым (`ToString("F")`), а совместимость с платформой сохраняется: интерполяция строк и `string.Format` вызывают `IFormattable.ToString` через интерфейс.

## Явная реализация и структуры

```csharp
public interface ICounter { void Increment(); }

public struct Counter : ICounter
{
    public int Value;
    void ICounter.Increment() => Value++;      // ЯВНО
}

var c = new Counter();
// c.Increment();                 // недоступно: нужен интерфейс
((ICounter)c).Increment();        // упаковка! инкрементируется копия в куче
Console.WriteLine(c.Value);        // Вывод: 0
```

Для структур явная реализация особенно коварна: единственный способ вызвать член — привести к интерфейсу, а это упаковка, и изменения уходят в копию. Правило: у структур интерфейсы реализуют **неявно**, а вызовы делают через дженерик с ограничением (`where T : ICounter`), где упаковки нет ([[Boxing и unboxing]], [[Интерфейсы]]).

## Разрешение неоднозначности с реализациями по умолчанию

```csharp
public interface IA { void Do() => Console.WriteLine("A"); }
public interface IB { void Do() => Console.WriteLine("B"); }

public sealed class C : IA, IB
{
    // Без явной реализации вызов ((IA)c).Do() и ((IB)c).Do() дал бы разное поведение,
    // а c.Do() не существовал бы вовсе. Явно фиксируем:
    void IA.Do() => Console.WriteLine("выбрали поведение A");
    void IB.Do() => Console.WriteLine("выбрали поведение B");
}
```

Это единственный способ развести конфликтующие члены по умолчанию из разных интерфейсов — аналог решения «ромбовидной проблемы» из языков с множественным наследованием.

> [!warning] Подводные камни
> - **Явная реализация «для красоты».** Скрытый член неудобно вызывать и легко не заметить; применяй только по одному из трёх сценариев выше.
> - **Структуры.** Вызов возможен только через интерфейс, значит через упаковку, значит изменения теряются.
> - **Нельзя пометить `virtual`.** Наследник не переопределит явно реализованный член обычным способом; если поведение должно быть расширяемым, делай публичный виртуальный метод и делегируй в него из явной реализации.
> - **Вызов изнутри класса.** Требует `((IFoo)this).Member()` — легко забыть и написать бесконечную рекурсию, вызвав публичный одноимённый метод.
> - **Тесты и моки.** Мок-фреймворки настраивают интерфейс, и это работает, но при тестировании конкретного класса скрытые члены придётся вызывать через приведение.
> - **Сериализация.** `System.Text.Json` сериализует публичные свойства; явно реализованные свойства он не увидит.

> [!example] Как делают в бою
> В прикладном коде явная реализация встречается редко и в основном в двух местах: собственные коллекции (обе версии `GetEnumerator`) и типы, реализующие пары «обобщённый + не-обобщённый» интерфейсов из BCL (`IComparable<T>`/`IComparable`, `IFormattable`, `IEquatable<T>`/`IStructuralEquatable`).
> В библиотечном коде добавляется третий сценарий — сокрытие членов, обязательных по контракту, но не предназначенных для повседневного использования: инфраструктурные методы, устаревшие перегрузки, внутренние точки расширения.
> Отдельная практика — не путать явную реализацию с ограничением доступа: спрятать член из подсказок IDE она помогает, но защиты не даёт — любой код может привести объект к интерфейсу и вызвать что угодно. Реальные границы задаются `internal` и сборками ([[Инкапсуляция и модификаторы доступа]]).

## Вопросы с собеседований

> [!question]- Чем явная реализация интерфейса отличается от неявной?
> При неявной реализации член объявляется как обычный публичный член класса и одновременно закрывает контракт: он доступен и через тип класса, и через интерфейс. При явной имя квалифицируется интерфейсом (`void IFoo.Bar()`), модификатор доступа не указывается, и член доступен **только** через ссылку на интерфейс — через тип класса его не видно, даже изнутри самого класса нужно приведение `((IFoo)this).Bar()`. Явно реализованный член нельзя объявить `virtual` или `abstract`. Применяют её в трёх случаях: конфликт одинаковых членов из разных интерфейсов, необходимость скрыть служебные члены контракта из публичного API (не-обобщённые версии `GetEnumerator`, `CompareTo(object)`), и потребность дать интерфейсной версии другое поведение или сигнатуру, чем у публичного метода.

> [!question]- Зачем при реализации `IEnumerable<T>` пишут три метода `GetEnumerator`?
> Потому что `IEnumerable<T>` наследует не-обобщённый `IEnumerable`, и его версия тоже обязательна. Обе интерфейсные версии реализуют явно, чтобы они не засоряли API типа, а третий, публичный `GetEnumerator` объявляют с конкретным типом перечислителя — обычно структурой. Это даёт заметный выигрыш: `foreach` ищет метод `GetEnumerator` по форме, а не через интерфейс, поэтому по конкретному типу он использует структурный перечислитель без упаковки и без аллокации, а через `IEnumerable<T>` работает обычный интерфейсный путь. Так устроены `List<T>`, `Dictionary<K,V>` и большинство коллекций BCL.

> [!question]- Почему явная реализация опасна для структур?
> Потому что вызвать явно реализованный член можно только через ссылку на интерфейс, а приведение структуры к интерфейсу выполняет упаковку: значение копируется в объект в куче. Все изменения состояния уходят в эту копию, исходная переменная остаётся прежней — код компилируется, выполняется и молча ничего не делает. Плюс появляется аллокация на каждый вызов. Поэтому у структур интерфейсы реализуют неявно, а если нужен вызов через абстракцию в горячем коде — используют обобщённый метод с ограничением `where T : IInterface`: там JIT генерирует специализацию под конкретный значимый тип и вызывает член напрямую, без упаковки.

## Задачи

### Задача 1. Развести конфликт

Класс должен реализовать `ILogger` с методом `Write(string)` и `IReportWriter` с таким же `Write(string)`, но поведение должно быть разным.

> [!success]- Решение
> ```csharp
> public sealed class DualOutput(ILogger<DualOutput> logger, Stream reportStream) : ILogSink, IReportWriter
> {
>     void ILogSink.Write(string text) => logger.LogInformation("{Message}", text);
>
>     void IReportWriter.Write(string text)
>     {
>         var bytes = System.Text.Encoding.UTF8.GetBytes(text + Environment.NewLine);
>         reportStream.Write(bytes);
>     }
> }
>
> ILogSink asLog = new DualOutput(logger, stream);
> asLog.Write("в лог");
> ```
> Обе реализации явные, поэтому каждая привязана к своему контракту, а у самого класса публичного `Write` нет вовсе — это правильно: без указания, куда писать, вызов был бы неоднозначен для читателя. Если бы одно из поведений считалось «основным», его стоило бы сделать публичным методом с говорящим именем (`WriteToReport`), а явную реализацию свести к делегированию в него.

### Задача 2. Найти ошибку

```csharp
public struct Position : IResettable
{
    public int X;
    void IResettable.Reset() => X = 0;
}

Position p = new() { X = 5 };
IResettable r = p;
r.Reset();
Console.WriteLine(p.X);
```

> [!success]- Решение
> Выведет `5`. Присваивание `IResettable r = p;` упаковало структуру: в куче создалась копия, и `Reset` обнулил её, а исходная переменная `p` осталась нетронутой. Ошибка усугубляется явной реализацией: другого способа вызвать `Reset` просто нет, поэтому упаковка неизбежна.
> ```csharp
> public struct Position : IResettable
> {
>     public int X;
>     public void Reset() => X = 0;          // неявная реализация: вызывается напрямую
> }
>
> Position p = new() { X = 5 };
> p.Reset();                                  // без упаковки, меняется сама переменная
> Console.WriteLine(p.X);                      // 0
>
> // Если нужен вызов через абстракцию — дженерик с ограничением, тоже без упаковки:
> static void ResetAll<T>(Span<T> items) where T : IResettable
> {
>     for (int i = 0; i < items.Length; i++) items[i].Reset();
> }
> ```
> Более глубокий вывод: изменяемые структуры сами по себе источник таких сюрпризов. Обычно правильнее сделать структуру `readonly` и возвращать новое значение (`Position WithReset()`), а не мутировать существующее — см. [[Записи (record) и структуры]].

## Итог

- Явная реализация привязывает член к интерфейсу: без модификатора доступа, невидим через тип класса, вызывается после приведения.
- Три оправданных сценария: конфликт членов разных интерфейсов, сокрытие служебных членов контракта, отдельное поведение или сигнатура для интерфейсной версии.
- Классический пример — пара `GetEnumerator` при реализации `IEnumerable<T>` плюс публичный структурный перечислитель.
- Явный член нельзя сделать `virtual`/`abstract`; расширяемость даёт делегирование в публичный виртуальный метод.
- Для структур явная реализация вынуждает приводить к интерфейсу, а значит упаковывать — изменения теряются.
- Это средство оформления API, а не защиты: любой код может привести объект к интерфейсу.
