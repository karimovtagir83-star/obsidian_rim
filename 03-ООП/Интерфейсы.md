# Интерфейсы

> [!abstract] Коротко
> Интерфейс — контракт: список членов, которые обязан предоставить реализующий тип, без состояния и без конструктора. Он отвечает на вопрос «что умеет», не говоря «как устроен», и потому является основным инструментом развязки в .NET: код зависит от `IOrderRepository`, а конкретную реализацию подставляет DI-контейнер. С C# 8 интерфейсы умеют содержать реализации по умолчанию, с C# 11 — статические абстрактные члены (на них построена обобщённая математика). Реализовать можно сколько угодно интерфейсов, в том числе структурами — но обращение к структуре через интерфейс вызывает упаковку, и это надо помнить.

## Зачем это нужно

Три задачи, которые решает интерфейс.

**Развязка.** Класс зависит от контракта, а не от конкретного типа: реализацию можно заменить, не трогая потребителя. Это база для внедрения зависимостей и для принципа инверсии зависимостей ([[Инверсия зависимостей на практике]]).

**Тестируемость.** Подставить фейк или мок вместо базы данных и HTTP-клиента можно только через абстракцию.

**Множественность контрактов.** Наследоваться можно от одного класса, а реализовать — сколько угодно интерфейсов; тип может быть одновременно `IDisposable`, `IEquatable<T>` и `IComparable<T>`.

```csharp
public interface IOrderRepository
{
    Task<Order?> FindAsync(long id, CancellationToken ct);
    Task AddAsync(Order order, CancellationToken ct);
}

public sealed class OrderService(IOrderRepository repository)     // зависимость от контракта
{
    public Task<Order?> GetAsync(long id, CancellationToken ct) => repository.FindAsync(id, ct);
}

// В проде — EF Core, в тестах — список в памяти. Сервис не меняется.
```

## Объявление и реализация

```csharp
public interface IReportBuilder
{
    string Name { get; }                                     // свойство
    Task<byte[]> BuildAsync(ReportRequest request, CancellationToken ct);   // метод
    event EventHandler<ReportBuiltEventArgs>? Built;         // событие
    byte[] this[int index] { get; }                          // индексатор
}

public sealed class PdfReportBuilder : IReportBuilder
{
    public string Name => "PDF";
    public Task<byte[]> BuildAsync(ReportRequest request, CancellationToken ct) => ...;
    public event EventHandler<ReportBuiltEventArgs>? Built;
    public byte[] this[int index] => ...;
}
```

Правила:

- члены интерфейса по умолчанию `public`; полей нет (только `static`-члены и константы);
- реализация обязана быть `public` (при неявной реализации) и точно соответствовать сигнатуре;
- интерфейс может наследовать другие интерфейсы, в том числе несколько;
- реализовывать интерфейсы могут классы, структуры, записи и (с C# 13) `ref struct`.

```csharp
public interface IEntity { long Id { get; } }
public interface IAuditable { DateTimeOffset CreatedAt { get; } }
public interface IAuditableEntity : IEntity, IAuditable { }      // объединение контрактов

public sealed record Order(long Id, DateTimeOffset CreatedAt) : IAuditableEntity;
```

Если два интерфейса объявляют член с одинаковой сигнатурой, одна реализация закрывает оба. Если поведение должно различаться — нужна явная реализация ([[Явная реализация интерфейсов]]).

## Реализация по умолчанию (C# 8)

```csharp
public interface INotificationChannel
{
    Task SendAsync(string to, string text, CancellationToken ct);

    // Реализация по умолчанию: наследники могут не писать её
    Task SendManyAsync(IEnumerable<string> recipients, string text, CancellationToken ct)
        => Task.WhenAll(recipients.Select(r => SendAsync(r, text, ct)));
}
```

Зачем добавили: чтобы можно было **расширить интерфейс, не сломав существующие реализации** — важная вещь для библиотек, где реализации живут в чужом коде.

Ограничения, из-за которых это не «интерфейс с кодом»:

```csharp
public sealed class Sms : INotificationChannel
{
    public Task SendAsync(string to, string text, CancellationToken ct) => Task.CompletedTask;
}

var sms = new Sms();
// sms.SendManyAsync(...);                     // Ошибка: член не виден через тип класса
((INotificationChannel)sms).SendManyAsync(...); // работает только через интерфейс
```

Плюс у интерфейса нет полей и конструктора, поэтому состояние в реализации по умолчанию хранить негде. Практический вывод: реализации по умолчанию — инструмент версионирования библиотек и удобных «надстроек» над основными членами, а не замена абстрактным классам ([[Абстрактные классы]]).

Альтернатива, которая чаще уместнее в прикладном коде, — методы расширения над интерфейсом: они видны через конкретный тип и не требуют приведения.

```csharp
public static class NotificationChannelExtensions
{
    public static Task SendManyAsync(this INotificationChannel channel,
        IEnumerable<string> recipients, string text, CancellationToken ct)
        => Task.WhenAll(recipients.Select(r => channel.SendAsync(r, text, ct)));
}
```

## Статические абстрактные члены (C# 11)

```csharp
public interface IParsableEntity<TSelf> where TSelf : IParsableEntity<TSelf>
{
    static abstract TSelf Parse(string text);
    static abstract string Prefix { get; }
}

public sealed record OrderId(long Value) : IParsableEntity<OrderId>
{
    public static OrderId Parse(string text) => new(long.Parse(text.AsSpan(4)));
    public static string Prefix => "ORD-";
}

// Обобщённый код может вызывать статические члены типа-параметра
static T ParseAll<T>(string text) where T : IParsableEntity<T> => T.Parse(text);
```

На этом механизме построена **обобщённая математика** в .NET 7+: интерфейсы `INumber<T>`, `IAdditionOperators<,,>`, `IParsable<T>`, `ISpanFormattable`. Благодаря им можно написать один алгоритм для всех числовых типов:

```csharp
static T Sum<T>(IEnumerable<T> values) where T : INumber<T>
{
    T total = T.Zero;
    foreach (var v in values) total += v;
    return total;
}
Console.WriteLine(Sum([1, 2, 3]));          // int
Console.WriteLine(Sum([1.5m, 2.5m]));       // decimal
```

Раньше такое требовало либо дублирования кода на каждый тип, либо `dynamic`. Подробнее — [[Дженерики: ограничения и вариантность]].

## Проектирование интерфейсов

### Размер: чем меньше, тем лучше

Принцип разделения интерфейсов (буква I в [[SOLID]]) говорит: клиент не должен зависеть от методов, которыми не пользуется.

```csharp
// Плохо: реализация обязана поддержать всё, даже если нужно только чтение
public interface IRepository<T>
{
    Task<T?> FindAsync(long id, CancellationToken ct);
    Task AddAsync(T item, CancellationToken ct);
    Task UpdateAsync(T item, CancellationToken ct);
    Task DeleteAsync(long id, CancellationToken ct);
    Task<IReadOnlyList<T>> QueryAsync(string sql, CancellationToken ct);
}

// Лучше: разные потребители зависят от разного
public interface IOrderReader { Task<Order?> FindAsync(long id, CancellationToken ct); }
public interface IOrderWriter { Task AddAsync(Order order, CancellationToken ct); }
```

Хороший ориентир: интерфейс на 1–5 членов, объединённых одной ответственностью. Интерфейс на 20 методов почти всегда означает, что за ним прячется класс, который делает слишком много.

### Именование и семантика

- Имя начинается с `I` и описывает **роль или способность**: `IOrderRepository`, `IClock`, `IDisposable`, `IValidator<T>`.
- Суффикс `-able` для способностей: `IEnumerable`, `IComparable`, `IParsable`.
- Плохое имя — `IOrderServiceInterface`, `IManager`, `IHelper`: они не говорят о роли.
- Интерфейс, дословно повторяющий один класс (`IOrderService` для единственного `OrderService` с теми же членами), полезен только для тестов и DI — и это допустимо, но не считается «абстракцией».

### Когда интерфейс не нужен

- У типа одна реализация и не предвидится другой, а тестировать его можно напрямую (чистая функция, value object, DTO).
- Абстракция «на всякий случай»: каждый лишний интерфейс — ещё один файл и ещё один переход при чтении кода.
- Для подмены времени, файловой системы и HTTP в тестах в .NET уже есть готовые абстракции: `TimeProvider`, `IFileSystem` из библиотек, `HttpMessageHandler`.

Обратная сторона: интерфейс почти обязателен для всего, что уходит за границу процесса (база, сеть, брокер, файлы) и для того, что подменяется по конфигурации.

## Интерфейсы и структуры: упаковка

```csharp
public interface IShape { double Area { get; } }
public readonly record struct Square(double Side) : IShape
{
    public double Area => Side * Side;
}

Square s = new(2);
IShape boxed = s;                 // УПАКОВКА: структура копируется в кучу
Console.WriteLine(boxed.Area);    // виртуальный вызов через интерфейс

// Дженерик с ограничением упаковки НЕ делает:
static double AreaOf<T>(T shape) where T : IShape => shape.Area;   // constrained-вызов, без упаковки
Console.WriteLine(AreaOf(s));
```

Это важное практическое различие: приведение структуры к интерфейсу упаковывает её (аллокация в куче), а вызов через дженерик с ограничением — нет, потому что JIT генерирует специализированный код для каждого значимого типа. Отсюда правило для горячего кода: принимать `T where T : IShape`, а не `IShape` ([[Boxing и unboxing]], [[Дженерики в CLR: как устроены]]).

## Интерфейсы BCL, которые надо знать

| Интерфейс | Зачем |
|---|---|
| `IEnumerable<T>` / `IAsyncEnumerable<T>` | перечисление, `foreach`, LINQ |
| `IDisposable` / `IAsyncDisposable` | освобождение ресурсов, `using` |
| `IEquatable<T>` | равенство без упаковки |
| `IComparable<T>` / `IComparer<T>` | сортировка |
| `IFormattable` / `ISpanFormattable` | форматирование в строку и в буфер |
| `IParsable<T>` / `ISpanParsable<T>` | обобщённый разбор (C# 11) |
| `INotifyPropertyChanged` | уведомления об изменениях (UI) |
| `IReadOnlyList<T>` / `IReadOnlyDictionary<K,V>` | контракт «только чтение» |

Реализация правильных интерфейсов встраивает тип в платформу: `IEquatable<T>` ускоряет словари, `IComparable<T>` включает `Sort`, `IFormattable` — интерполяцию с форматами ([[Сравнение объектов: IEquatable, IComparable, компараторы]]).

> [!warning] Подводные камни
> - **Интерфейс-копия класса.** `IOrderService` с теми же 12 методами, что и `OrderService`, не является абстракцией: он меняется вместе с классом и ничего не развязывает.
> - **Толстые интерфейсы.** Реализации вынуждены писать `NotSupportedException` для ненужных членов — прямое нарушение принципа подстановки.
> - **Добавление члена в опубликованный интерфейс.** Ломает все внешние реализации; для библиотек — только через реализацию по умолчанию или новый интерфейс.
> - **Реализация по умолчанию как «код в интерфейсе».** Не видна через конкретный тип, не имеет состояния, вызывает путаницу при множественном наследовании интерфейсов.
> - **Приведение структуры к интерфейсу.** Упаковка и аллокация; в дженериках с ограничением её нет.
> - **Интерфейс ради тестов там, где тесты не нужны.** Каждая абстракция — стоимость чтения; для чистой логики достаточно прямых тестов.
> - **Маркерные интерфейсы без членов.** Иногда оправданы (сканирование сборки в DI), но обычно лучше атрибут или явная регистрация.

> [!example] Как делают в бою
> Устойчивая практика в .NET-сервисах: интерфейсы объявляются на границах — репозитории, клиенты внешних API, шина сообщений, поставщик времени, хранилище файлов. Внутри доменного слоя интерфейсов мало: доменная логика тестируется напрямую, и абстракции там только мешают.
> Интерфейс живёт рядом с **потребителем**, а не с реализацией: `IOrderRepository` объявлен в слое приложения, а реализован в инфраструктуре. Это и есть инверсия зависимостей — направление ссылок между сборками разворачивается, и домен перестаёт зависеть от EF Core.
> Размер держат небольшим: один-пять членов. Когда интерфейс разрастается, его делят по ролям (`IOrderReader`/`IOrderWriter`) — это заодно упрощает моки в тестах, потому что подменять приходится меньше.
> Для сквозного поведения (логирование, кеш, повторы) вместо наследования применяют декораторы поверх интерфейса: тот же контракт, обёрнутая реализация, регистрация в DI одной строкой.

## Вопросы с собеседований

> [!question]- Чем интерфейс отличается от абстрактного класса и что выбрать?
> Интерфейс — только контракт: без полей, без конструктора, без состояния; реализовать можно сколько угодно интерфейсов, в том числе структурами. Абстрактный класс может иметь состояние, конструктор, невиртуальные члены и члены с любым доступом, но наследование от него единственное. С C# 8 интерфейсы поддерживают реализации по умолчанию, однако состояние туда всё равно не переносится, а такие члены не видны через ссылку на конкретный класс. Выбор: интерфейс — когда нужен контракт, реализации не связаны, тип подставляется через DI или подменяется в тестах, требуется несколько контрактов; абстрактный класс — когда есть общее состояние и общий код, являющийся частью алгоритма (шаблонный метод), и нужно контролировать, что наследник не может переопределить. Часто применяют оба: интерфейс наружу, абстрактный класс как удобная база.

> [!question]- Зачем нужны реализации по умолчанию в интерфейсах?
> Главная причина — версионирование: добавление члена в опубликованный интерфейс ломает все существующие реализации, в том числе в чужом коде, а член с реализацией по умолчанию позволяет расширить контракт безопасно. Вторая — удобные надстройки над основными членами (перегрузки, комбинации), чтобы каждый реализующий тип не переписывал их. Ограничения существенны: у интерфейса нет полей и конструктора, поэтому состояния в такой реализации быть не может; член по умолчанию доступен только через ссылку на интерфейс, а не через конкретный класс; при реализации нескольких интерфейсов с одинаковыми членами по умолчанию возникает неоднозначность, которую приходится разрешать явно. Поэтому в прикладном коде часто предпочитают методы расширения над интерфейсом: они видны через конкретный тип и не требуют приведения.

> [!question]- Что происходит при приведении структуры к интерфейсу?
> Происходит упаковка: значение копируется в новый объект в управляемой куче, и дальше вызовы идут через таблицу методов этого объекта. Это аллокация и дополнительная косвенность, а также источник неожиданностей с изменяемыми структурами — изменения через интерфейсную ссылку затрагивают упакованную копию, а не исходное значение. Избежать упаковки позволяет обобщённый код с ограничением: `void M<T>(T value) where T : IShape` вызывает члены через constrained-вызов, а JIT генерирует отдельную специализацию для каждого значимого типа, поэтому упаковки нет. Это же объясняет, почему `IEquatable<T>` важен для структур: сравнение через него не упаковывает операнды, в отличие от унаследованного `object.Equals`.

> [!question]- Нужен ли интерфейс, если реализация одна?
> Зависит от того, что за реализацией. Если это выход за границу процесса — база данных, HTTP-клиент, брокер, файловая система, часы, — интерфейс нужен: он даёт возможность подменить реализацию в тестах и изолировать домен от инфраструктуры, даже если в проде вариант единственный. Если это чистая логика без внешних зависимостей (расчёт, валидатор, value object), интерфейс обычно лишний: такой код тестируется напрямую, а лишняя абстракция добавляет файл и переход при чтении. Отдельно стоит различать интерфейс-абстракцию и интерфейс-копию: контракт, повторяющий все члены единственного класса и меняющийся вместе с ним, ничего не развязывает — он полезен только как точка подмены в DI, и это допустимая, но скромная цель.

## Задачи

### Задача 1. Разделить толстый интерфейс

```csharp
public interface IUserService
{
    Task<User?> FindAsync(long id, CancellationToken ct);
    Task<IReadOnlyList<User>> SearchAsync(string query, CancellationToken ct);
    Task CreateAsync(User user, CancellationToken ct);
    Task DeleteAsync(long id, CancellationToken ct);
    Task SendWelcomeEmailAsync(long id, CancellationToken ct);
    Task<byte[]> ExportToCsvAsync(CancellationToken ct);
}
```

> [!success]- Решение
> Интерфейс объединяет четыре разные ответственности: чтение, изменение, уведомления и экспорт. Потребитель, которому нужен только поиск, вынужден зависеть от отправки писем; мок в тесте приходится настраивать целиком; реализация обязана поддерживать всё.
> ```csharp
> public interface IUserReader
> {
>     Task<User?> FindAsync(long id, CancellationToken ct);
>     Task<IReadOnlyList<User>> SearchAsync(string query, CancellationToken ct);
> }
>
> public interface IUserWriter
> {
>     Task CreateAsync(User user, CancellationToken ct);
>     Task DeleteAsync(long id, CancellationToken ct);
> }
>
> public interface IUserNotifier { Task SendWelcomeAsync(long userId, CancellationToken ct); }
> public interface IUserExporter { Task<byte[]> ExportToCsvAsync(CancellationToken ct); }
> ```
> Реализовать их может по-прежнему один класс — разделение нужно **потребителям**, а не реализации. Контроллер поиска зависит от `IUserReader`, фоновая рассылка — от `IUserNotifier`, и каждый видит ровно то, чем пользуется. Заодно становится видно, что отправка писем и экспорт, скорее всего, вообще не принадлежат сервису пользователей.

### Задача 2. Убрать упаковку

Метод считает сумму площадей и вызывается миллионы раз. Найди проблему и исправь.

```csharp
public interface IShape { double Area { get; } }
public readonly record struct Circle(double R) : IShape { public double Area => Math.PI * R * R; }

static double TotalArea(IEnumerable<IShape> shapes)
{
    double total = 0;
    foreach (var s in shapes) total += s.Area;
    return total;
}
```

> [!success]- Решение
> Каждый `Circle`, попадающий в `IEnumerable<IShape>`, упаковывается: миллион структур — миллион объектов в куче и работа для GC, плюс виртуальные вызовы через интерфейс.
> ```csharp
> static double TotalArea<T>(IEnumerable<T> shapes) where T : IShape
> {
>     double total = 0;
>     foreach (var s in shapes) total += s.Area;
>     return total;
> }
>
> // Ещё лучше для горячего пути — без перечислителя-интерфейса:
> static double TotalArea<T>(ReadOnlySpan<T> shapes) where T : IShape
> {
>     double total = 0;
>     foreach (ref readonly var s in shapes) total += s.Area;
>     return total;
> }
> ```
> В обобщённой версии JIT создаёт отдельную специализацию для каждого значимого типа, вызов `Area` разрешается статически (constrained call) и обычно встраивается — упаковки нет вовсе. Вариант со `Span<T>` дополнительно убирает аллокацию перечислителя и обходит данные последовательно в памяти. Оговорка: такая оптимизация оправданна только при подтверждённой бенчмарком нагрузке; для смешанной коллекции разных фигур интерфейсная версия остаётся единственно возможной.

## Итог

- Интерфейс — контракт без состояния и конструктора; реализовать можно сколько угодно, в том числе структурами.
- Основные роли: развязка через DI, тестируемость, множественные контракты.
- Реализации по умолчанию (C# 8) нужны для версионирования библиотек; состояния в них нет, и через конкретный тип они не видны.
- Статические абстрактные члены (C# 11) сделали возможной обобщённую математику: `INumber<T>`, `IParsable<T>`.
- Интерфейс должен быть маленьким и выражать роль; толстые интерфейсы ломают принцип разделения интерфейсов.
- Интерфейс объявляют рядом с потребителем, а реализуют в инфраструктуре — это и есть инверсия зависимостей.
- Приведение структуры к интерфейсу упаковывает её; дженерик с ограничением — нет.
- Абстракция нужна там, где есть граница (БД, сеть, время, файлы); для чистой логики она чаще лишняя.
