# Интерфейсы

> [!abstract] Коротко
> Интерфейс — контракт: список членов, которые обязан предоставить реализующий тип, без состояния и без конструктора. Абстрактный класс — незавершённый тип: часть реализации и состояние он отдаёт наследникам, а остальное требует доопределить. С C# 8 интерфейсы умеют содержать реализации по умолчанию, но это не делает их заменой абстрактного класса: полей и конструктора там всё равно нет. Явная реализация (`void IFoo.Bar()`) — способ привязать член строго к интерфейсу, когда нужно развести конфликт имён или спрятать служебный член из публичного API.

## Зачем это знать

Выбор между интерфейсом и абстрактным классом — решение до написания кода: от него зависит, можно ли будет унаследоваться ещё от чего-то, можно ли тип подставить через DI, как будут выглядеть тесты. Ошибка здесь не ловится компилятором — она проявляется через полгода, когда нужно добавить второй вариант поведения, а наследование уже занято. Явная реализация в диффе агента — почти всегда сигнал: либо решают реальный конфликт контрактов, либо просто маскируют плохо спроектированный публичный API.

## Модель

### Интерфейс — контракт, не реализация

```csharp
public interface IOrderRepository
{
    Task<Order?> FindAsync(long id, CancellationToken ct);
    Task AddAsync(Order order, CancellationToken ct);
}

public sealed class OrderService(IOrderRepository repository)   // зависимость от контракта
{
    public Task<Order?> GetAsync(long id, CancellationToken ct) => repository.FindAsync(id, ct);
}
// В проде — EF Core, в тестах — список в памяти. Сервис не меняется.
```

Правила: члены по умолчанию `public`, полей нет (только `static`); интерфейс может наследовать несколько интерфейсов; реализовать можно классами, структурами, записями. Если два интерфейса объявляют член с одинаковой сигнатурой, одна неявная реализация закрывает оба сразу — если поведение должно различаться, нужна явная реализация (ниже).

### Реализация по умолчанию (C# 8) — не «интерфейс с кодом»

```csharp
public interface INotificationChannel
{
    Task SendAsync(string to, string text, CancellationToken ct);

    Task SendManyAsync(IEnumerable<string> recipients, string text, CancellationToken ct)   // умолчание
        => Task.WhenAll(recipients.Select(r => SendAsync(r, text, ct)));
}

public sealed class Sms : INotificationChannel
{
    public Task SendAsync(string to, string text, CancellationToken ct) => Task.CompletedTask;
}

var sms = new Sms();
// sms.SendManyAsync(...);                        // Ошибка: не виден через тип класса
((INotificationChannel)sms).SendManyAsync(...);    // работает только через интерфейс
```

Задача этой возможности — версионирование библиотек: добавить член в опубликованный интерфейс, не сломав чужие реализации. У интерфейса по-прежнему нет полей и конструктора, поэтому состояние туда не переносится, а член виден только через ссылку на интерфейс. Для прикладного кода чаще уместнее метод расширения — он виден через конкретный тип и не требует приведения.

### Абстрактный класс — общий код плюс состояние

```csharp
public abstract class ImportJob(ILogger logger)
{
    public async Task<ImportResult> RunAsync(Stream source, CancellationToken ct)   // шаблонный метод
    {
        var rows = await ParseAsync(source, ct);           // деталь наследника
        var valid = rows.Where(IsValid).ToList();
        await SaveAsync(valid, ct);                         // деталь наследника
        logger.LogInformation("Импорт {Job}: {Count}", Name, valid.Count);
        return new ImportResult(rows.Count, valid.Count);
    }

    protected abstract string Name { get; }
    protected abstract Task<IReadOnlyList<ImportRow>> ParseAsync(Stream source, CancellationToken ct);
    protected abstract Task SaveAsync(IReadOnlyList<ImportRow> rows, CancellationToken ct);
    protected virtual bool IsValid(ImportRow row) => true;
}
```

Правила: создать нельзя (`new ImportJob(...)` — CS0144), но переменную и параметр такого типа объявлять можно и нужно. Конструктор есть и вызывается только из наследника, модификатор — `protected`. Абстрактный член неявно виртуальный, не может быть `private`. Наследник, не реализовавший всё, сам обязан быть `abstract`. Виртуальный вызов из конструктора базы опасен: метод наследника выполнится до инициализации его полей.

### Множественное наследование интерфейсов и явная реализация

Класс может реализовать сколько угодно интерфейсов, но унаследоваться — только от одного класса. Когда два интерфейса конфликтуют по имени или нужно другое поведение для каждого — явная реализация:

```csharp
public interface IFileWriter { void Write(string text); }
public interface IConsoleWriter { void Write(string text); }

public sealed class DualWriter : IFileWriter, IConsoleWriter
{
    void IFileWriter.Write(string text) => File.AppendAllText("out.txt", text);
    void IConsoleWriter.Write(string text) => Console.WriteLine(text);
}

((IFileWriter)new DualWriter()).Write("в файл");   // без приведения не вызвать
```

У явно реализованного члена нет модификатора доступа, он не виден через тип класса (даже изнутри — нужен `((IFoo)this).Bar()`), его нельзя пометить `virtual`/`abstract`/`override`. Три оправданных сценария: конфликт членов двух интерфейсов (пример выше); сокрытие служебных членов контракта — классика: `IEnumerable<T>` наследует не-обобщённый `IEnumerable`, и обе версии `GetEnumerator` прячут явно, оставляя публичной структурную версию без аллокации; другой тип результата — `IComparable<Money>.CompareTo(Money?)` публичный и типобезопасный, `IComparable.CompareTo(object?)` явный и только для старых API.

Тот же приём разводит неоднозначность двух default-реализаций:

```csharp
public interface IA { void Do() => Console.WriteLine("A"); }
public interface IB { void Do() => Console.WriteLine("B"); }

public sealed class C : IA, IB
{
    void IA.Do() => Console.WriteLine("A");   // без этого c.Do() не существовал бы вовсе
    void IB.Do() => Console.WriteLine("B");
}
```

Для структур явная реализация особенно опасна: единственный способ вызвать член — привести к интерфейсу, а это упаковка (копия в куче), и изменения уходят в копию, а не в исходную переменную.

### Интерфейсы и структуры: упаковка

```csharp
public interface IShape { double Area { get; } }
public readonly record struct Square(double Side) : IShape { public double Area => Side * Side; }

Square s = new(2);
IShape boxed = s;                  // УПАКОВКА: копия в куче
static double AreaOf<T>(T shape) where T : IShape => shape.Area;   // constrained-вызов, БЕЗ упаковки
```

Приведение структуры к интерфейсу упаковывает её; дженерик с ограничением — нет, потому что JIT генерирует специализацию под каждый значимый тип ([[Value types vs Reference types]]).

## Решения

| Критерий | Интерфейс | Абстрактный класс |
|---|---|---|
| Состояние (поля) | нет (только `static`) | да |
| Конструктор | нет | да, `protected` |
| Множественное наследование | да, сколько угодно | нет, только один базовый класс |
| Реализация по умолчанию | да (C# 8+, без состояния) | да (любые члены) |
| Контроль «наследник не может переопределить» | нет | да (невиртуальные члены) |
| Реализация значимыми типами | да (`struct`) | нет |
| Отношение | «умеет» (can-do) | «является» (is-a) |
| Когда выбрать | контракт для DI/тестов; реализации не связаны; нужно несколько контрактов; тип — структура | общее состояние и код, часть алгоритма (шаблонный метод); нужно запретить переопределение |
| Оба вместе | интерфейс — публичный контракт для потребителя, абстрактный класс — необязательная база с общим кодом (частая правильная комбинация) | |

```csharp
public interface INotificationChannel { Task SendAsync(string to, string text, CancellationToken ct); }

public abstract class NotificationChannelBase(ILogger logger) : INotificationChannel   // общая обвязка
{
    public async Task SendAsync(string to, string text, CancellationToken ct)
    {
        logger.LogInformation("Отправка через {Channel}", GetType().Name);
        await DeliverAsync(to, text, ct);
    }
    protected abstract Task DeliverAsync(string to, string text, CancellationToken ct);
}
```

Потребители зависят от `INotificationChannel`, а `NotificationChannelBase` — деталь реализации, которую можно и не использовать.

> [!example] В ServiceShop
> `BuildingBlocks.Domain/IBusinessRule.cs` — контракт бизнес-правила: новое ограничение домена оформляется отдельным классом в `Order/BusinessRules/`, реализующим `IBusinessRule` (метод проверки плюс сообщение об ошибке). Интерфейс маленький и живёт рядом с потребителем — `Entity.CheckRule(...)`.
> `Configuration/Commands/ICommandHandler.cs` задаёт `ICommandHandler<TCommand, TResult>` — каждый `*CommandHandler` реализует его, MediatR резолвит нужный обработчик по типу команды. Здесь интерфейс — точка расширения: новый юзкейс добавляет новый класс, ничего в инфраструктуре не меняя.
> `Entity` из `BuildingBlocks.Domain` — абстрактный класс, а не интерфейс: у сущностей общее состояние (идентификатор, список доменных событий) и общий код (`Equals`/`GetHashCode` по идентификатору, `Raise`/`ClearEvents`). Разное соотношение точное: контракты, которые подставляет DI или которые различаются между модулями (`IBusinessRule`, `ICommandHandler<,>`), — интерфейсы; общий каркас доменной модели одного понятия — абстрактный класс.

> [!warning] Где ошибаются
> - **Абстрактный класс вместо интерфейса в публичном API.** Потребитель тратит единственное наследование и не может унаследоваться от чего-то ещё.
> - **Реализация по умолчанию как «код в интерфейсе».** Не видна через конкретный тип, не имеет состояния, при множественном наследовании интерфейсов вызывает неоднозначность.
> - **Явная реализация «для красоты».** Скрытый член неудобно вызвать и легко забыть; уместна только для трёх сценариев выше.
> - **Публичный конструктор у абстрактного класса.** Создать объект всё равно нельзя, но контракт выглядит обманчиво; нужен `protected`.
> - **`protected`-поля в базе.** Наследники получают прямой доступ к состоянию, любой рефакторинг базы их ломает.
> - **Приведение структуры к интерфейсу (особенно с явной реализацией).** Упаковка, копия в куче, изменения теряются молча.
> - **Агент часто:** предлагает базовый абстрактный класс с одним наследником «на будущее» — вместо интерфейса плюс композиции.
> - **Агент часто:** генерирует явную реализацию там, где конфликта или скрытия нет, — просто чтобы «выглядело как в BCL».
> - **Агент часто:** добавляет член в существующий интерфейс без реализации по умолчанию, ломая все внешние реализации, вместо нового интерфейса или default-метода.

## Проверка на ревью

- Новый интерфейс — 1–5 членов одной ответственности, а не `IRepository<T>` на все случаи жизни.
- Явная реализация в диффе — есть ли реальный конфликт контрактов или скрываемый служебный член; если нет — почему не публичный метод.
- Абстрактный класс с одним наследником — задан ли вопрос «а нужен ли он вообще» вместо композиции с интерфейсом.
- Приведение `struct` к интерфейсу в горячем пути — нет ли способа заменить на `where T : IInterface`.
- Публичный конструктор у `abstract class` — должен быть `protected`.
- Добавление члена в существующий интерфейс — есть ли default-реализация или это новый интерфейс.

## Проверь себя

> [!question]- Чем интерфейс отличается от абстрактного класса и что выбрать?
> Интерфейс — только контракт: без полей, без конструктора, реализовать можно сколько угодно интерфейсов, в том числе структурами. Абстрактный класс может иметь состояние, конструктор и невиртуальные члены, но наследование от него единственное. Выбор: интерфейс — когда реализации не связаны, тип подставляется через DI или подменяется в тестах, нужно несколько контрактов; абстрактный класс — когда есть общее состояние и общий код, являющийся частью алгоритма. Часто применяют оба: интерфейс наружу, абстрактный класс как удобная база.

> [!question]- Зачем нужны реализации по умолчанию в интерфейсах и чем они не заменяют абстрактный класс?
> Главная причина — версионирование: член с реализацией по умолчанию позволяет расширить опубликованный интерфейс, не сломав существующие реализации. Но состояния там всё равно нет — полей и конструктора у интерфейса не появилось; член виден только через ссылку на интерфейс, а не через конкретный класс; при конфликте одинаковых default-членов из разных интерфейсов нужна явная реализация. Поэтому «общий код с состоянием» по-прежнему живёт в абстрактных классах.

> [!question]- Когда явная реализация интерфейса оправдана?
> В трёх случаях: конфликт одинаковых членов из разных интерфейсов, которым нужно разное поведение; сокрытие служебных членов контракта, не предназначенных для повседневного использования (не-обобщённый `IEnumerable.GetEnumerator`); другой тип результата или сигнатура у интерфейсной версии по сравнению с публичным методом (`IComparable.CompareTo(object?)` рядом с типобезопасным `CompareTo(Money?)`). Во всех остальных случаях явная реализация просто прячет член без причины и усложняет чтение.

> [!question]- Почему явная реализация особенно опасна для структур?
> Вызвать явно реализованный член можно только через ссылку на интерфейс, а приведение структуры к интерфейсу выполняет упаковку — значение копируется в объект в куче. Изменения состояния уходят в эту копию, исходная переменная остаётся прежней: код компилируется и молча ничего не делает. Поэтому у структур интерфейсы реализуют неявно, а для вызова через абстракцию в горячем коде используют дженерик с ограничением `where T : IInterface`, где JIT генерирует специализацию и упаковки нет.

> [!question]- Нужен ли интерфейс, если реализация одна?
> Зависит от того, что за реализацией. Для выхода за границу процесса (база, сеть, брокер, часы) интерфейс нужен — он даёт точку подмены в тестах, даже если в проде вариант единственный. Для чистой логики без внешних зависимостей интерфейс обычно лишний: такой код тестируется напрямую, а лишняя абстракция добавляет файл и переход при чтении.

## Разбор

**Дан фрагмент — найди проблему.**

```csharp
public abstract class RepositoryBase
{
    protected readonly AppDbContext Db;
    protected RepositoryBase(AppDbContext db) => Db = db;
}

public sealed class OrderRepository : RepositoryBase
{
    public OrderRepository(AppDbContext db) : base(db) { }
    public Task<Order?> FindAsync(long id, CancellationToken ct) => Db.Orders.FindAsync([id], ct).AsTask();
}
```

> [!success]- Решение
> База не даёт ни общего алгоритма, ни поведения — только хранит зависимость, которую наследник и так мог бы получить через конструктор. Взамен она забирает у `OrderRepository` возможность унаследоваться от чего-то ещё и делает `Db` частью контракта для всех будущих наследников.
> ```csharp
> public sealed class OrderRepository(AppDbContext db) : IOrderRepository
> {
>     public Task<Order?> FindAsync(long id, CancellationToken ct) => db.Orders.FindAsync([id], ct).AsTask();
> }
> ```
> Интерфейс `IOrderRepository` нужен для DI и тестов; общий код (пагинация, спецификации) лучше вынести в статический класс расширений над `IQueryable<T>`, доступный всем репозиториям без наследования.

**Дан PR агента — что вернёшь на доработку.**

```csharp
public interface ICounter { void Increment(); }

public struct Counter : ICounter
{
    public int Value;
    void ICounter.Increment() => Value++;   // явная реализация
}
```

> [!success]- Решение
> Верну с комментарием: единственный способ вызвать `Increment` — привести `Counter` к `ICounter`, а это упаковка; инкремент уйдёт в копию в куче, исходная переменная не изменится. Для структуры интерфейс нужно реализовать неявно (`public void Increment() => Value++;`), а если требуется вызов через абстракцию — дженерик с ограничением `where T : ICounter`, где упаковки нет.

## Итог

- Интерфейс — контракт без состояния и конструктора; абстрактный класс — незавершённый тип с общим состоянием и кодом.
- Реализации по умолчанию (C# 8) решают версионирование библиотек, а не заменяют абстрактный класс: состояния в них нет.
- Явная реализация привязывает член к интерфейсу; оправдана для конфликта имён, сокрытия служебных членов и другой сигнатуры — не «для порядка».
- Множественное наследование доступно только интерфейсам; абстрактный класс — единственный.
- Приведение структуры к интерфейсу (тем более с явной реализацией) — упаковка; в горячем коде и дженериках с ограничением её нет.
- Частая правильная комбинация — интерфейс наружу для потребителя, абстрактный класс как необязательная общая база.
