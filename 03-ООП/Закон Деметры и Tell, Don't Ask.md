# Закон Деметры и Tell, Don't Ask

> [!abstract] Коротко
> Закон Деметры («не разговаривай с незнакомцами») требует, чтобы метод обращался только к ближайшему окружению: к своим полям, к своим параметрам, к объектам, которые сам создал. Цепочка `order.Customer.Address.City.Name` нарушает его: вызывающий знает устройство четырёх чужих типов, и изменение любого из них его сломает. «Tell, Don't Ask» — та же идея с другой стороны: не вытаскивай данные из объекта, чтобы принять решение снаружи, а попроси объект сделать работу. Обе рекомендации служат одному — снижению связанности и переносу поведения туда, где живут данные.

## Зачем это нужно

```csharp
// Спрашиваем: вытащили данные и решили снаружи
if (order.Customer.Subscription.Level == SubscriptionLevel.Gold
    && order.Items.Sum(i => i.Price * i.Quantity) > 1_000_000
    && order.Customer.Address.Country == "UZ")
{
    order.Discount = order.Items.Sum(i => i.Price * i.Quantity) * 0.1m;
}

// Говорим: попросили объект сделать то, что он умеет
order.ApplyLoyaltyDiscount();
```

Первый вариант знает про пять чужих типов и их устройство. Переименование `SubscriptionLevel`, перенос страны из адреса в профиль, изменение способа расчёта суммы — каждое изменение потребует править этот код и все похожие места. Второй вариант знает только про `Order`.

---

## Закон Деметры формально

Метод объекта может вызывать методы только у:

1. **самого себя** (`this`);
2. **своих полей**;
3. **своих параметров**;
4. **объектов, которые он создал** в этом методе;
5. **глобально доступных объектов** (в разумных пределах).

Всё остальное — «незнакомцы». Правило иногда формулируют проще: **одна точка** (не считая обращений к результату собственных вызовов).

```csharp
public sealed class OrderProcessor(IPaymentGateway gateway)
{
    public void Process(Order order)
    {
        gateway.Charge(order);                     // ок: поле
        order.MarkPaid();                          // ок: параметр
        var log = new StringBuilder();
        log.AppendLine("готово");                  // ок: создали сами

        var city = order.Customer.Address.City;    // нарушение: два «прыжка» вглубь
    }
}
```

### Что нарушением не является

Правило часто понимают буквально и начинают бороться с любыми точками — это ошибка. Не нарушают закон Деметры:

```csharp
// 1. Fluent-интерфейсы: каждый вызов возвращает тот же объект (или билдер), это одна сущность
services.AddControllers().AddJsonOptions(o => { }).AddXmlSerializerFormatters();
builder.Configuration.GetSection("Payment").Bind(options);

// 2. LINQ: цепочка операторов над одной последовательностью
var top = orders.Where(o => o.IsPaid).OrderByDescending(o => o.Total).Take(10).ToList();

// 3. Обращение к данным DTO: у него нет поведения, прятать нечего
var city = request.Address.City;
```

Ключевое различие: закон Деметры про **поведение**, а не про доступ к данным. Цепочка нарушает его тогда, когда вызывающий на основании чужих внутренностей принимает решение, которое должен принимать владелец данных.

## Tell, Don't Ask

Формулировка: **не запрашивай состояние объекта, чтобы решить, что с ним делать, — скажи ему, что сделать**. Объект, у которого есть данные, должен иметь и поведение над ними.

```csharp
// Ask: снаружи проверяем и снаружи меняем
if (account.Balance >= amount && !account.IsBlocked && account.Currency == "UZS")
{
    account.Balance -= amount;
    account.LastOperationAt = DateTimeOffset.UtcNow;
}

// Tell: правило внутри объекта, снаружи — намерение
account.Withdraw(new Money(amount, "UZS"));
```

Выигрыш не в краткости, а в том, что правило существует **в одном месте**. В первом варианте такая же проверка будет продублирована в переводах, возвратах, комиссиях — и однажды где-то забудут условие `IsBlocked`.

### Анемичная модель

Систематическое нарушение «tell, don't ask» приводит к анемичной модели: классы с одними свойствами, вся логика — в сервисах.

```csharp
// Анемично
public class Order { public decimal Total { get; set; } public OrderStatus Status { get; set; } }

public class OrderService
{
    public void Pay(Order order)
    {
        if (order.Status != OrderStatus.New) throw new InvalidOperationException();
        order.Status = OrderStatus.Paid;
    }
}

// Богатая модель
public sealed class Order
{
    public OrderStatus Status { get; private set; } = OrderStatus.New;

    public void MarkPaid()
    {
        if (Status != OrderStatus.New)
            throw new InvalidOperationException($"Нельзя оплатить заказ в статусе {Status}");
        Status = OrderStatus.Paid;
    }
}
```

Оговорка, которую важно сделать честно: анемичная модель — не всегда зло. Для CRUD-приложения, где «бизнес-логика» сводится к валидации и сохранению, богатая модель избыточна и только добавляет слоёв. Проблемой она становится там, где правил много и они начинают дублироваться по сервисам ([[Антипаттерны и code smells]], [[DDD: тактические паттерны]]).

## Как убирать цепочки

### Перенести поведение к данным

```csharp
// Было
if (order.Customer.Address.Country == "UZ") { }

// Стало
if (order.IsDomestic) { }        // свойство Order, которое само спрашивает у клиента
// внутри: public bool IsDomestic => Customer.IsFromCountry("UZ");
```

Каждый объект спрашивает только своего непосредственного соседа — знание не «прыгает» через уровни.

### Делегирующие члены

```csharp
public sealed class Order
{
    private readonly Customer _customer;

    public string CustomerDisplayName => _customer.DisplayName;   // делегирование
    public bool IsVipCustomer => _customer.IsVip;
}
```

Дешёвый приём, но им легко злоупотребить: если делегирующих свойств становится десяток, значит вызывающему на самом деле нужен сам `Customer`, и правильнее передать его явно.

### Передавать то, что нужно

```csharp
// Метод принимает объект, а использует одно поле — лишняя связанность
public decimal CalculateFee(Order order) => order.Total * 0.02m;

// Принимает ровно то, что нужно: проще тестировать, меньше зависимостей
public decimal CalculateFee(decimal amount) => amount * 0.02m;
```

Это движение от связанности «по структуре» к связанности «по данным» ([[Связанность и связность (coupling, cohesion)]]).

## Признак в тестах

Нарушения видно по мокам:

```csharp
// Чтобы протестировать метод, приходится собрать четыре уровня заглушек
var address = Substitute.For<IAddress>();
address.City.Returns("Ташкент");
var customer = Substitute.For<ICustomer>();
customer.Address.Returns(address);
var order = Substitute.For<IOrder>();
order.Customer.Returns(customer);
```

Такая настройка («мок возвращает мок, который возвращает мок») — прямой сигнал нарушения закона Деметры: тестируемый класс знает про устройство трёх чужих типов. После переноса поведения тест сводится к одной строке.

## Когда правило не применяют

- **DTO, ответы API, конфигурация.** У них нет поведения и нет инвариантов; `request.Address.City` — нормальный доступ к данным.
- **Билдеры и fluent-конфигурация.** `builder.Services.AddX().AddY()` — цепочка по одному объекту.
- **LINQ и функциональные конвейеры.** Цепочка операторов не раскрывает внутренностей.
- **Слой отображения.** Шаблон или маппер, который собирает вьюмодель из графа объектов, по определению обходит структуру — прятать её там незачем.
- **Цена делегирования выше выгоды.** Если ради устранения одной цепочки в базовый тип придётся добавить пять сквозных свойств, лекарство хуже болезни.

Правило — эвристика, а не закон физики: его цель снизить связанность, и если применение увеличивает сложность, применять не надо.

> [!warning] Подводные камни
> - **Буквальный счёт точек.** `a.B.C` в DTO — не нарушение; нарушение — принятие решения на основе чужих внутренностей.
> - **Обвязка делегирующих свойств.** Десяток сквозных `CustomerName`, `CustomerCity`, `CustomerPhone` — тот же граф, только размазанный по фасаду.
> - **Tell, Don't Ask доведённый до абсурда.** Не всякий геттер — зло: объекту нужно уметь отдавать данные для отображения и сериализации.
> - **Богатая модель ради принципа.** В CRUD-сервисе доменная логика может просто отсутствовать; тогда сервис плюс DTO — честнее.
> - **Перенос инфраструктуры в модель.** «Пусть заказ сам себя сохранит» превращает доменный тип в зависимого от базы; сохранение — не его ответственность.
> - **Цепочки через `?.`.** `a?.B?.C?.D` не исправляют проблему связанности, а только маскируют `null`.

> [!example] Как делают в бою
> В доменном слое правило соблюдают строго: сущность инкапсулирует состояние, публикует поведение (`MarkPaid`, `AddItem`, `Cancel`) и не отдаёт наружу изменяемые внутренности. Сервис приложения не считает и не проверяет — он оркеструет: загрузил агрегат, вызвал метод, сохранил.
> В слое представления правило ослабляют осознанно: мапперы и вьюмодели обходят граф объектов, потому что их задача — именно преобразование структуры. Чтобы это не протекало обратно в домен, для отображения используют отдельные модели, а не доменные типы.
> На ревью два надёжных маркера: цепочка из трёх и более обращений с последующим решением (`if (a.B.C.D == ...)`) и тест, в котором мок возвращает мок. Оба почти всегда означают, что поведение написано не в том классе.
> И обратная сторона, о которой стоит помнить: в проекте, где бизнес-правил мало, богатая модель не окупается. Тогда честнее оставить анемичные модели и держать правила в небольшом числе сервисов — главное, чтобы одно правило жило в одном месте.

## Вопросы с собеседований

> [!question]- Что такое закон Деметры и что считается его нарушением?
> Это правило ограничения знаний: метод должен обращаться только к самому себе, своим полям, своим параметрам и объектам, которые сам создал. Нарушение — обращение к «незнакомцам», то есть к объектам, полученным через чужие объекты: `order.Customer.Address.City`. Проблема не в количестве точек, а в том, что вызывающий начинает зависеть от внутренней структуры нескольких чужих типов: любое изменение этой структуры ломает его, хотя контракт непосредственного соседа не менялся. Важно, что цепочки над одним объектом (fluent-билдеры, LINQ) нарушением не являются, как и доступ к полям DTO, у которых нет ни поведения, ни инвариантов. Признак настоящего нарушения — решение, принимаемое снаружи на основании чужих внутренностей: такое решение почти всегда должно принимать сам владелец данных.

> [!question]- Что означает «Tell, Don't Ask» и как это связано с инкапсуляцией?
> Принцип говорит: вместо того чтобы запрашивать состояние объекта и принимать решение снаружи, следует передать объекту намерение и позволить ему решить самому. Связь с инкапсуляцией прямая: если данные закрыты, а поведение опубликовано, то принять решение снаружи попросту нечем — правило неизбежно оказывается внутри. Практическая выгода в том, что правило живёт в одном месте: при подходе «ask» одна и та же проверка дублируется во всех сценариях, и рано или поздно в каком-то из них забывают условие. Обратная сторона — принцип не запрещает геттеры вовсе: данные нужны для отображения, сериализации и отчётов. Граница проходит по тому, кто принимает решение об изменении состояния.

> [!question]- Всегда ли анемичная модель — это плохо?
> Нет. Анемичная модель (классы-структуры данных плюс сервисы с логикой) плоха тогда, когда правил много и они начинают дублироваться: одно и то же условие появляется в нескольких сервисах, и они расходятся. В такой ситуации перенос поведения к данным (богатая модель) окупается — правило становится единственным и проверяется тестами на уровне домена. Но в приложениях, где логика сводится к валидации и сохранению (типичный CRUD, административные панели, интеграционные шлюзы), богатая модель добавляет слои без пользы: сущность, у которой единственный метод — присвоить поля, ничем не лучше DTO. Практический критерий — количество и связность бизнес-правил, а не идеология: если правила есть и они нетривиальны, им место в модели; если их нет, честнее признать это и не строить домен ради формы.

## Задачи

### Задача 1. Убрать цепочку

```csharp
public sealed class ShippingCalculator
{
    public decimal Calculate(Order order)
    {
        if (order.Customer.Address.Country == "UZ" && order.Customer.Address.City == "Ташкент")
            return 0;
        if (order.Customer.Subscription.Level == SubscriptionLevel.Gold)
            return 0;
        return order.Items.Sum(i => i.Weight) * 1500;
    }
}
```

> [!success]- Решение
> Калькулятор знает про устройство четырёх чужих типов. Переносим решения туда, где данные, оставляя каждому объекту знание только о непосредственном соседе.
> ```csharp
> public sealed class Address
> {
>     public bool IsInCity(string country, string city) => Country == country && City == city;
> }
>
> public sealed class Customer
> {
>     public bool HasFreeShipping => _address.IsInCity("UZ", "Ташкент") || _subscription.IsGold;
> }
>
> public sealed class Order
> {
>     public bool QualifiesForFreeShipping => _customer.HasFreeShipping;
>     public decimal TotalWeight => _items.Sum(i => i.Weight);
> }
>
> public sealed class ShippingCalculator(decimal ratePerKg)
> {
>     public decimal Calculate(Order order)
>         => order.QualifiesForFreeShipping ? 0 : order.TotalWeight * ratePerKg;
> }
> ```
> Теперь `Order` спрашивает только `Customer`, `Customer` — только `Address` и `Subscription`, а калькулятор не знает ни о ком, кроме заказа. Побочные выигрыши: правило «бесплатная доставка» перестало дублироваться (его наверняка проверяли ещё в отображении корзины), тариф стал параметром вместо магического числа, а тест калькулятора теперь требует одного объекта с двумя свойствами вместо графа из четырёх моков.
> Честная оговорка: такой перенос оправдан, когда правило действительно принадлежит домену. Если условия бесплатной доставки — это конфигурируемая маркетинговая акция, им место в отдельной политике (`IShippingPolicy`), а не внутри `Customer`.

### Задача 2. Оценить, нарушение ли это

Для каждого фрагмента реши, есть ли проблема.
1. `services.AddAuthentication().AddJwtBearer();`
2. `if (user.Profile.Settings.Notifications.EmailEnabled) SendEmail(user.Profile.Email);`
3. `var names = orders.Select(o => o.Customer.Name).ToList();` в мапперe для отчёта.
4. `order.Items.Add(new OrderItem(...));`

> [!success]- Решение
> 1. **Нет.** Fluent-конфигурация: каждый вызов возвращает тот же билдер, это цепочка по одному объекту, а не обход чужих внутренностей.
> 2. **Да.** Решение об отправке принимается снаружи на основании четырёх уровней чужой структуры, и такая же проверка наверняка есть в других местах рассылки. Правильно — `user.WantsEmailNotifications` или, ещё лучше, метод `user.NotifyByEmail(message)`, скрывающий и проверку, и адрес.
> 3. **Нет** (с оговоркой). Задача маппера — преобразование структуры, и обход графа для него естественен. Оговорка касается производительности: если `Customer` — навигационное свойство EF Core без `Include`, это проблема N+1 ([[EF Core: производительность и типичные грабли]]).
> 4. **Да.** Внешний код добавляет позицию напрямую в коллекцию заказа, минуя его правила: нет проверки статуса, не пересчитывается итог, не публикуется событие. Правильно — `order.AddItem(...)`, а коллекция наружу отдаётся как `IReadOnlyList<T>` ([[Инкапсуляция и модификаторы доступа]]).

## Итог

- Закон Деметры: обращайся только к своим полям, параметрам, созданным объектам и себе; остальное — «незнакомцы».
- Нарушение — не количество точек, а решение, принятое снаружи на основе чужих внутренностей.
- Fluent-API, LINQ и доступ к полям DTO закон не нарушают.
- «Tell, Don't Ask»: передавай намерение, а не вытаскивай состояние для решения снаружи.
- Оба принципа снижают связанность и переносят поведение туда, где живут данные.
- Признак нарушения в тестах — мок, возвращающий мок, возвращающий мок.
- Анемичная модель плоха, когда правил много и они дублируются; в CRUD она уместна.
- Лечение: поведение к данным, делегирующие члены в меру, передача значений вместо объектов.
