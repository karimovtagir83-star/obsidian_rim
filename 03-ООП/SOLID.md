# SOLID

> [!abstract] Коротко
> SOLID — пять эвристик Роберта Мартина против роста стоимости изменения кода, а не законы для код-ревью. DRY, KISS и YAGNI — тот же список целей другими словами, и у каждого есть своя ложь: DRY, доведённый до абсурда, склеивает два разных правила в одно и создаёт неверную абстракцию; YAGNI работает только на обратимых решениях. DIP — принцип о том, кому принадлежит интерфейс; DI-контейнер (в проекте — Autofac) — просто механизм, который его реализует и сам по себе ничего не инвертирует.

## Зачем это знать

На ревью «нарушен SOLID» без объяснения последствия — не аргумент, а ритуал. Все восемь принципов этой заметки существуют, чтобы отвечать на один вопрос: **что конкретно сломается, если оставить как есть**. Нужно это для трёх вещей: заметить в диффе абстракцию, которая появилась раньше вариации (YAGNI/OCP); заметить дублирование, которое на самом деле два разных правила под одной маской (ложный DRY); и отличить «завели интерфейс» от «инвертировали зависимость» (DIP).

## Модель

### SRP — Single Responsibility Principle

Модуль отвечает перед одним **актором** — человеком или ролью, которая заказывает правку. Не «одна ответственность» (это неоперационально), а «один заказчик изменений».

```diff
 public sealed class OrderService
 {
     public async Task<Guid> CreateAsync(CreateOrderCommand cmd, CancellationToken ct)
     {
         var order = Order.Create(cmd.CustomerId, cmd.Items);
         await _repository.AddAsync(order, ct);
+        // добавили прямо в хендлере, чтобы "не плодить файлы"
+        await _smtp.SendAsync(cmd.CustomerEmail, "Заказ создан", $"№{order.Id}", ct);
         return order.Id;
     }
 }
```

Правка формата письма теперь тянет перекомпиляцию и ревью того же файла, что и бизнес-правила заказа — два разных заказчика в одном месте. Правильно: письмо — в обработчик доменного события ([[Иммутабельность как приём проектирования]] сюда не относится, но структура события — да).

### OCP — Open/Closed Principle

Новое поведение — новым кодом, старый не трогаем. Работает только на оси, где вариация уже доказана.

```diff
 public Task<Receipt> PayAsync(Payment p) => p.Method switch
 {
     "card" => ChargeCardAsync(p),
     "sbp"  => ChargeSbpAsync(p),
+    "crypto" => ChargeCryptoAsync(p),   // ещё одна ветка в работающем switch
     _ => throw new NotSupportedException(p.Method)
 };
```

Симптом на ревью: диффом правится файл, покрытый тестами и работающий в проде, ради добавления однотипного варианта. Правильно — новая реализация `IPaymentMethod` и строка регистрации в DI, старый `switch` не трогается вовсе.

### LSP — Liskov Substitution Principle

Наследник обязан соблюдать контракт предка, а не только сигнатуры. Компилятор это не проверяет — нарушение всплывает в рантайме.

```diff
 public class FileStorage
 {
     public virtual void Save(string name, byte[] content) => File.WriteAllBytes(name, content);
 }

 public class S3Storage : FileStorage
 {
     public override void Save(string name, byte[] content)
     {
+        if (content.Length > 5 * 1024 * 1024)
+            throw new ArgumentException("S3 не принимает больше 5 МБ");   // новое предусловие
         // ...
     }
 }
```

Код, написанный против `FileStorage`, падает, когда в него подставили `S3Storage`, хотя всё скомпилировалось. Ограничение размера должно быть частью контракта (`long MaxObjectSize { get; }`), а не сюрпризом в реализации.

### ISP — Interface Segregation Principle

Интерфейс определяется потребителем, а не реализацией. Число методов стремится к 1–3.

```diff
 public interface IUserService
 {
     Task<User?> GetByIdAsync(Guid id, CancellationToken ct);
     Task<Guid> CreateAsync(CreateUserDto dto, CancellationToken ct);
+    Task<byte[]> ExportToCsvAsync(CancellationToken ct);   // ещё один метод в общем интерфейсе
 }
```

Каждый клиент, которому нужен только `GetByIdAsync`, теперь зависит и от экспорта: правка сигнатуры `ExportToCsvAsync` перекомпилирует чужой контроллер, а его тест мокает метод, которым не пользуется. Правильно — отдельный `IUserExporter`.

### DIP — Dependency Inversion Principle

Модули верхнего уровня и модули нижнего уровня зависят от абстракций; абстракция принадлежит потребителю, а не реализации.

```diff
 public sealed class SubscriptionService(ISubscriptionRepository repository)
 {
     public async Task RenewAsync(Guid userId, CancellationToken ct)
     {
         var sub = await repository.GetAsync(userId, ct);
+        using var conn = new NpgsqlConnection("Host=prod-db;...");   // прямая зависимость от драйвера
+        // ... точечный SQL-запрос "просто чтобы проверить дубликат" ...
         sub.RenewUntil(DateTime.UtcNow.AddMonths(1));
     }
 }
```

Один прямой вызов инфраструктуры внутри домена — уже утечка: тест требует поднятую БД, а сборка домена ссылается на `Npgsql`. Разбор DIP как практики — в отдельном разделе ниже.

### DRY, KISS, YAGNI: когда врут

Это не третий и четвёртый принцип «после SOLID», а тот же список целей — низкая стоимость изменения — сформулированный иначе, с собственными ловушками.

**DRY врёт, когда «похоже» путают со «одно и то же знание».** Тест: *эти два места изменятся вместе и обязательно?* Если нет — это совпадение, а не дублирование.

```diff
 public static void Validate(UserInput input, bool isImport)
 {
     if (!isImport && !EmailIsUnique(input.Email))
         throw new ValidationException("Email уже занят");
+    if (isImport) input.Password ??= GenerateTemporaryPassword();
+    // при третьем сценарии (приглашение) появится isInvite, и матрица веток удвоится
 }
```

`bool isImport` — управляющая связанность: вызывающий код обязан знать внутреннее устройство метода. Асимметрия важнее самого DRY: дублирование чинится за час локально, неправильная абстракция — нет, потому что к моменту, когда её признали плохой, у неё уже десяток клиентов и три флага «не трогать, ломает биллинг». Rule of Three (третье вхождение — повод обобщить) и AHA-принцип («дублирование дешевле неправильной абстракции», Сэнди Метц) — рабочий компромисс.

**KISS врёт, когда простоту меряют строками, а не концепциями.** `GenericRepository<T>` с рефлексией и деревом выражений короче трёх явных LINQ-методов, но требует держать в голове семь понятий вместо одного. И наоборот: `double` для денег — «просто» сегодня и невоспроизводимый баг округления завтра.

**YAGNI врёт на необратимых решениях.** Обратимость определяется не кодом, а тем, кто ещё зависит от решения:

| Решение | Дверь | YAGNI применим? |
|---|---|---|
| Имя приватного метода, структура класса | two-way | да, откладывай |
| Схема БД, первичные ключи | one-way | нет, миграция живых данных |
| Публичный контракт REST/gRPC | one-way | нет, внешние клиенты |
| Ключ идемпотентности в контракте | one-way | нет, ретраи начнутся при первом сбое |

Вопрос для планирования: «если через полгода окажется, что мы ошиблись, — что придётся сделать?» «Переименовать класс» — не думай. «Мигрировать 300 млн строк» — думай сейчас.

### DIP на практике: принцип vs механизм

DIP, IoC и DI — три разных уровня, их путают систематически.

| Термин | Что это |
|---|---|
| **DIP** | принцип: интерфейс принадлежит верхнему уровню, направление компиляционной зависимости развёрнуто |
| **IoC** | общая идея: управление потоком передаётся фреймворку, а не пишется в коде |
| **DI** | техника: зависимости передаются извне, обычно через конструктор |
| **DI-контейнер** (Autofac) | инструмент автоматизации DI; сам по себе DIP не гарантирует |

Ключевая ошибка: завести интерфейс и решить, что зависимость инвертирована. Инверсия происходит, только если интерфейс объявлен там, где живёт потребитель:

```
БЕЗ инверсии:                         С инверсией:

Application ──► Infrastructure        Application  ◄── Infrastructure
                ├── IOrderRepository       ├── IOrderRepository
                └── EfOrderRepository      └── SubscriptionService
Ссылка всё равно вниз — интерфейс     Стрелка компиляции развёрнута
не меняет направления.                против направления вызова.
```

Autofac регистрирует пары интерфейс → реализация в `*Startup.cs` модуля так же, как это делал бы встроенный контейнер ASP.NET Core — разницы для DIP никакой, потому что контейнер — это композиционный корень, а не место, где решается, кому принадлежит интерфейс. Правило проще принципа: инвертируй **волатильные** зависимости (сеть, БД, часы, файлы, генератор случайных чисел), остальное вызывай напрямую.

## Решения

| Принцип | Типичное нарушение | Как исправить |
|---|---|---|
| SRP | Правило одного актора правится в файле, который читают три команды | Разнести по акторам: данные отдельно, поведение — по обработчикам одного сценария |
| OCP | Новый вариант — ветка в существующем `switch`/`if` | Новая реализация интерфейса + строка регистрации в DI, старый код не трогать |
| LSP | Наследник ужесточает предусловие или бросает `NotSupportedException` | Вынести способность в отдельный интерфейс либо в контракт (ограничение как явное свойство) |
| ISP | Один интерфейс на 6–8 методов ради всех клиентов сразу | Разрезать по потребителю: интерфейс на 1–3 метода рядом с тем, кто его использует |
| DIP | Интерфейс объявлен рядом с реализацией, домен вызывает конкретный тип напрямую | Перенести интерфейс в слой-потребитель, реализацию — в инфраструктуру |
| DRY (ложный) | Два похожих, но независимо меняющихся правила склеены флагом | Развести на два метода/типа, оставить общим только реально общее знание |
| KISS (ложная простота) | Короткое решение с неявным поведением (рефлексия, `double` для денег) | Явное решение с предсказуемым типом ошибок, пусть и длиннее |
| YAGNI (не туда) | Абстракция с одной реализацией «на будущее» для необратимого решения | Абстракция только при доказанной вариации; для one-way door — решать заранее, не откладывать |

> [!example] В ServiceShop
> DI — только Autofac, не встроенный контейнер: каждый модуль публикует один `<Модуль>Startup.cs` в `Infrastructure/Configuration/`, где регистрирует пары интерфейс → реализация (`AddOrdersModule`-подобный метод-расширение). Интерфейсы вроде `IOrderRepository` объявлены в `<Модуль>.Application`, реализации (`EfOrderRepository`) — в `<Модуль>.Infrastructure`, которая ссылается на `Application`, а не наоборот — это и есть DIP, а Autofac лишь исполняет разводку декларативно. Проверить, кто зарегистрировал сервис, — значит открыть `<M>Startup.cs`, а не искать `new` по всему модулю. OCP в бою — стратегии платежей и правила скидок регистрируются как `IEnumerable<T>` через тот же Autofac-модуль; ISP — читающие и пишущие контракты разнесены между CQRS-путями команд и запросов. Подробнее про структуру модуля — [[93 — Рабочий проект: Alif ServiceShop (обзор раздела)]].

> [!warning] Где ошибаются
> - **Интерфейс с одной реализацией «для теста» — не DIP.** Если интерфейс лежит в той же сборке, что и единственная реализация, и ничего не собирается менять, — это лишний файл, а не инверсия.
> - **DRY через наследование.** Увидели общий код в двух методах, подняли в базовый класс — через год там `protected virtual bool ShouldSkip => false;` и три хука, которые никто не решается убрать.
> - **YAGNI как оправдание отсутствия дизайна.** «Мы по YAGNI не делали идемпотентность» — это не YAGNI, а пропущенное необратимое решение: YAGNI про функциональность, не про корректность.
> - **SRP путают с «один метод — один класс».** Итог — двенадцать файлов ради одного сценария и полная потеря контекста при чтении диффа.
> - **Агент часто:** генерирует интерфейс сразу под новую зависимость «на всякий случай», даже если вторая реализация не планируется и решение полностью обратимо — это нарушение YAGNI, а не следование DIP. Та же логика подсказывает агенту делать интерфейсы-обёртки над `List<T>` или `DateTime` — заворачивать нужно границу (сеть, БД, часы), а не всё подряд.
> - **Агент часто:** добавляет новый вариант веткой в существующий `switch`, потому что так короче диффа — формально работает, но нарушает OCP и обычно такой `switch` не один: рядом есть парный для комиссии или отображения, который остаётся не синхронизированным.

## Проверка на ревью

- Новый вариант поведения в диффе оформлен как новый файл/класс, а не веткой в существующем `switch`/`if`.
- Новый интерфейс в диффе объявлен в слое, который его потребляет, а не рядом с единственной реализацией.
- Переопределение в диффе не ужесточает предусловие базового типа и не бросает `NotSupportedException` вместо реализации метода.
- Новый метод не добавлен в общий интерфейс, которым пользуются клиенты, которым он не нужен.
- Похожий на существующий код в диффе — это одно знание с одним источником правды, а не два похожих, но независимо меняющихся правила под общим флагом.
- Абстракция в диффе появилась под доказанную вариацию (вторая реализация есть или анонсирована), а не «про запас» для обратимого решения.

## Проверь себя

> [!question]- Чем «завести интерфейс в диффе» отличается от настоящей инверсии зависимостей?
> Инверсия — это про то, где объявлен интерфейс, а не про факт его существования. Если `IOrderRepository` лежит в той же сборке, что `EfOrderRepository`, а домен по-прежнему ссылается на инфраструктуру ради этого файла, — ничего не инвертировано, добавился только уровень косвенности. DIP выполнен, только когда владелец контракта — потребитель (домен/приложение), а реализация ссылается на него, а не наоборот.

> [!question]- Как на ревью отличить «настоящий DRY» от ложного?
> Спросить: «эти два места изменятся вместе и обязательно, по одной и той же причине?» Если да — это одно знание, объединяй. Если правки приходят от разных заказчиков (например, продуктовое ограничение и юридическое — оба «18 лет», но по разным причинам), это совпадение, и объединение через общую константу или флаг создаст управляющую связанность там, где её не было.

> [!question]- Почему `bool`-параметр, добавленный в диффе, — повод для замечания?
> Потому что он превращает метод в два метода, склеенных условием, и вызывающий код обязан знать, какую ветку он выбирает. Это management-связанность — читать `Process(order, true)` по месту вызова невозможно, а при третьем сценарии число комбинаций флагов растёт быстрее, чем польза от «единого» метода.

> [!question]- Почему YAGNI не работает для схемы БД или контрактов API?
> Потому что обратимость определяется не сложностью кода, а числом внешних зависимых. Схему БД откатывать — значит мигрировать уже записанные данные; контракт API — значит ломать чужих клиентов, которых не видно в репозитории. YAGNI рассчитан на дешёвый откат; там, где отката нет или он стоит недель, решение принимают заранее, а не «когда понадобится».

> [!question]- Autofac в проекте гарантирует соблюдение DIP?
> Нет. Autofac — механизм внедрения зависимостей (DI) и композиционный корень для проводки; он одинаково охотно зарегистрирует и правильно инвертированные интерфейсы, и интерфейсы, объявленные рядом с реализацией без всякой инверсии. DIP проверяется расположением файла интерфейса (в каком слое он лежит) и архитектурным тестом («Application не ссылается на EF Core»), а не выбором контейнера.

## Разбор

### Разбор 1. PR агента: что вернёшь на доработку

Агент реализовал фичу «добавить оплату криптовалютой» и прислал такой диф:

```diff
 public Task<Receipt> PayAsync(Payment p) => p.Method switch
 {
     "card" => ChargeCardAsync(p),
     "sbp"  => ChargeSbpAsync(p),
+    "crypto" => await ChargeCryptoAsync(p, new HttpClient(), ct),
     _ => throw new NotSupportedException(p.Method)
 };

+public async Task<Receipt> ChargeCryptoAsync(Payment p, HttpClient http, CancellationToken ct)
+{
+    var resp = await http.PostAsJsonAsync("https://crypto-gateway/charge", p, ct);
+    return await resp.Content.ReadFromJsonAsync<Receipt>(ct);
+}
```

> [!success]- Решение
> Что вернуть на доработку: (1) OCP — новая ветка в рабочем `switch`, вместо этого нужен новый `IPaymentMethod` и регистрация в DI; (2) DIP — `new HttpClient()` внутри метода вместо `IHttpClientFactory`/выделенного `ICryptoGateway`, зависимость от конкретной технологии прямо в бизнес-логике; (3) утечка контракта — метод возвращает `HttpResponseMessage`-логику наружу (`ReadFromJsonAsync` прямо тут), а не абстрактный `Receipt`. Правильный вид — `CryptoPayment : IPaymentMethod`, зависящий от `ICryptoGateway`, зарегистрированный рядом с остальными методами оплаты, без единой правки существующего `switch`.

### Разбор 2. Дано два решения — обоснуй выбор

Нужно тестировать три сценария импорта пользователей. Вариант А: один метод `Validate(UserInput input, ImportMode mode)` с `if` по `mode` внутри. Вариант Б: три отдельных валидатора (`RegistrationValidator`, `CsvImportValidator`, `InviteValidator`) с общим `EmailRules.IsWellFormed`.

> [!success]- Решение
> Вариант Б. Формальное различие — `enum` вместо `bool`, но проблема не в типе флага, а в том, что три сценария меняются по трём разным причинам (продуктовые правила регистрации, формат CSV, политика приглашений). В варианте А правка формата импорта рискует задеть регистрацию, а тест обязан покрывать все три ветки одного метода. В варианте Б общее — только реально общее знание (`EmailRules`), и это ровно тест DRY «изменятся ли вместе» — часть про формат письма не изменится вместе с частью про уникальность email при импорте.

## Итог

- SOLID — пять эвристик снижения стоимости изменения, а все пять сводятся к «низкая связанность, высокая связность».
- DRY — про единственность знания, а не про похожий текст; неправильная абстракция дороже дублирования, потому что асимметрична стоимость выхода.
- KISS меряется числом концепций в голове, а не строками; YAGNI работает только на обратимых решениях.
- DIP — про то, кому принадлежит интерфейс; DI и IoC-контейнер (Autofac) — механизм, который сам по себе инверсию не гарантирует.
- На ревью и в диффе принцип без названного последствия — карго-культ; называй, что конкретно сломается.
