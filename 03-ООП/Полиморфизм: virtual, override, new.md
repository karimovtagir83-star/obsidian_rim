# Полиморфизм: virtual, override, new

> [!abstract] Коротко
> Полиморфизм подтипов — способность обращаться к объектам разных типов через общий контракт и получать поведение конкретного типа. В C# это делается через `virtual`/`abstract` + `override`: вызов разрешается в рантайме по фактическому типу объекта, через таблицу виртуальных методов. Ключевое противопоставление — `override` против `new`: первый **заменяет** реализацию в таблице, второй лишь **прячет** член базового типа, и вызов через ссылку базового типа пойдёт в базовую реализацию. Отсюда правило: `new` в реальном коде почти всегда ошибка, а не приём.

## Зачем это нужно

Полиморфизм — механизм, благодаря которому код работает с абстракцией, не зная конкретных типов:

```csharp
abstract class Notification
{
    public abstract Task SendAsync(string to, string text, CancellationToken ct);
}

sealed class EmailNotification : Notification { public override Task SendAsync(...) => ...; }
sealed class SmsNotification : Notification { public override Task SendAsync(...) => ...; }

// Этот метод не изменится при добавлении Telegram, push и чего угодно ещё
async Task NotifyAllAsync(IEnumerable<Notification> channels, string to, string text, CancellationToken ct)
{
    foreach (var channel in channels)
        await channel.SendAsync(to, text, ct);
}
```

Альтернатива без полиморфизма — `switch` по типу, который приходится править при каждом новом варианте (нарушение принципа открытости/закрытости из [[SOLID]]).

## Механика: таблица виртуальных методов

У каждого объекта в куче есть указатель на таблицу методов его типа (method table, аналог vtable). Для **невиртуального** метода компилятор знает адрес на этапе компиляции и генерирует прямой вызов (`call`). Для **виртуального** он генерирует косвенный вызов (`callvirt`): адрес берётся из таблицы того типа, которым объект является на самом деле.

```
Notification n = new SmsNotification();
n.SendAsync(...)   →  взять указатель на таблицу методов объекта
                   →  найти слот SendAsync
                   →  вызвать SmsNotification.SendAsync
```

Отсюда всё остальное поведение:

```csharp
class Base
{
    public virtual string Who() => "Base";
    public string NonVirtual() => "Base";
}

sealed class Derived : Base
{
    public override string Who() => "Derived";       // ЗАМЕНЯЕТ слот в таблице
    public new string NonVirtual() => "Derived";      // ПРЯЧЕТ, отдельный метод
}

Base asBase = new Derived();
Derived asDerived = new Derived();

Console.WriteLine(asBase.Who());          // Derived — вызов по таблице
Console.WriteLine(asDerived.Who());       // Derived

Console.WriteLine(asBase.NonVirtual());   // Base    — тип переменной решает всё
Console.WriteLine(asDerived.NonVirtual());// Derived
```

Строка `asBase.NonVirtual()` возвращает `"Base"`, хотя объект — `Derived`. Именно это делает `new` опасным: поведение зависит от того, через переменную какого типа обратились, а не от того, чем объект является.

## Ключевые слова

| Слово | Где | Что делает |
|---|---|---|
| `virtual` | базовый класс | разрешает переопределение, даёт реализацию по умолчанию |
| `abstract` | базовый класс | требует переопределения, реализации нет |
| `override` | наследник | заменяет реализацию в таблице методов |
| `sealed override` | наследник | переопределяет и запрещает дальнейшее переопределение |
| `new` | наследник | скрывает член базового типа (создаёт независимый член) |
| `base.X()` | наследник | явный вызов базовой реализации |

```csharp
abstract class Report
{
    public abstract string Title { get; }                      // обязателен к реализации
    public virtual string Format() => $"=== {Title} ===";       // можно переопределить
    protected virtual void OnRendered() { }                     // хук для наследников
}

class SalesReport : Report
{
    public override string Title => "Продажи";
    public override string Format() => base.Format() + "\nданные...";   // расширение, не замена
}

sealed class MonthlySalesReport : SalesReport
{
    public sealed override string Title => "Продажи за месяц";   // дальше переопределять нельзя
}
```

Переопределять можно методы, свойства, индексаторы и события. Сигнатура должна совпадать, включая уровень доступа (нельзя сузить `public` до `protected`).

### Ковариантный возвращаемый тип (C# 9)

```csharp
abstract class Animal { public abstract Animal Reproduce(); }
sealed class Cat : Animal { public override Cat Reproduce() => new Cat(); }   // Cat вместо Animal
```

Раньше пришлось бы возвращать `Animal` и приводить у вызывающего. Ковариантность допустима только «сужающая» — возвращаемый тип наследника должен быть подтипом исходного.

## Почему `new` — почти всегда ошибка

```csharp
class Repository
{
    public void Save(Order order) => Console.WriteLine("базовое сохранение");
}

class AuditingRepository : Repository
{
    public new void Save(Order order)                 // забыли virtual/override
    {
        Console.WriteLine("аудит");
        base.Save(order);
    }
}

Repository repo = new AuditingRepository();
repo.Save(order);                                     // "базовое сохранение" — аудита НЕТ
```

Код компилируется, тесты, написанные на `AuditingRepository`, проходят, а в проде через DI объект приходит как `Repository`, и аудит молча не работает. Это одна из самых неприятных категорий багов: ошибки нет, поведение просто другое.

Компилятор предупреждает (CS0108), если член скрывает базовый без `new`, — и это предупреждение нельзя игнорировать. Появление `new` обычно означает одно из трёх: забыли `virtual` в базовом классе, наследование выбрано вместо композиции, либо иерархия спроектирована неверно.

Редкие законные применения: сужение типа в возвращаемом значении до C# 9 (сейчас есть ковариантность), адаптация к чужой библиотеке, которую нельзя изменить, и «переопределение» статических или невиртуальных членов при работе с генерируемым кодом. Во всех случаях это должно быть прокомментировано.

## Перегрузка против переопределения

Разрешение **перегрузок** (несколько методов с одним именем и разными параметрами) происходит на этапе компиляции по статическим типам аргументов. Разрешение **переопределений** — в рантайме по фактическому типу объекта. Их смешение даёт неочевидные результаты:

```csharp
class Handler
{
    public virtual void Handle(object value) => Console.WriteLine("object");
    public virtual void Handle(string value) => Console.WriteLine("string");
}

object arg = "текст";
new Handler().Handle(arg);        // "object" — статический тип переменной object
new Handler().Handle("текст");    // "string"
```

Это же объясняет, почему «двойная диспетчеризация» (выбор поведения по двум типам сразу) в C# из коробки не работает и требует паттерна Visitor или сопоставления с образцом ([[Паттерны GoF: поведенческие]]).

## Виртуальный вызов из конструктора

```csharp
class Base
{
    public Base() => Initialize();                 // вызов виртуального метода из конструктора
    protected virtual void Initialize() { }
}

sealed class Derived : Base
{
    private readonly List<int> _items = [];         // инициализируется ПОСЛЕ конструктора базы

    protected override void Initialize() => _items.Add(1);   // NullReferenceException!
}
```

Порядок такой: сначала инициализаторы полей наследника? Нет — сначала выполняется конструктор базового класса (после инициализаторов полей наследника в C#? нет). Точный порядок в C#: инициализаторы полей **наследника**, затем конструктор базового класса, затем тело конструктора наследника. Но при вызове виртуального метода из конструктора базы объект уже имеет тип `Derived`, а вот `readonly`-поля, присваиваемые в конструкторе наследника, ещё не заполнены — и метод работает с полуинициализированным объектом.

Правило: **не вызывать виртуальные методы из конструкторов**. Если нужна инициализация с участием наследника — фабричный метод или отдельный `InitializeAsync`, вызываемый после создания. Анализаторы это правило проверяют.

## Стоимость и девиртуализация

Виртуальный вызов дороже прямого: нужно прочитать указатель на таблицу и сделать косвенный переход, плюс он мешает встраиванию (inlining). В цифрах это единицы наносекунд — незаметно в прикладном коде и заметно в горячем цикле на миллионы итераций.

JIT умеет **девиртуализировать** вызов, когда может доказать фактический тип: если класс `sealed`, если переменная только что создана через `new`, или если профиль исполнения (PGO, включён по умолчанию с .NET 8) показывает, что в 99 % случаев приходит один и тот же тип — тогда генерируется прямой вызов с проверкой (guarded devirtualization) и метод может быть встроен.

Практический вывод: помечать классы `sealed` по умолчанию полезно не только для дизайна, но и для производительности — это даёт JIT больше возможностей. Про измерения — [[Как измерять: BenchmarkDotNet]].

## Полиморфизм без наследования

Наследование — не единственный способ. В современном C# чаще используют интерфейсы:

```csharp
public interface INotificationChannel
{
    Task SendAsync(string to, string text, CancellationToken ct);
}
```

Интерфейс даёт полиморфизм без привязки к иерархии: реализация может наследоваться от чего угодно, может быть структурой, может реализовать несколько контрактов. Именно так работает DI в ASP.NET Core: регистрируется интерфейс, подставляется реализация ([[Интерфейсы]], [[Композиция vs наследование]]).

Другие формы полиморфизма в C#:

- **параметрический** — дженерики: один код для разных типов с проверкой на этапе компиляции ([[Дженерики: ограничения и вариантность]]);
- **ad-hoc** — перегрузка методов и операторов;
- **структурный** — сопоставление с образцом по типу, когда набор вариантов закрыт и поведение принадлежит потребителю, а не типу ([[Pattern matching]]).

> [!warning] Подводные камни
> - **`new` вместо `override`.** Поведение зависит от типа переменной; через базовый тип вызывается базовая реализация. Предупреждение CS0108 игнорировать нельзя.
> - **Виртуальный вызов из конструктора.** Метод наследника выполняется до инициализации его полей.
> - **Переопределение с сужением доступа.** Нельзя сделать `protected override` для `public virtual` — компилятор не позволит, и это правильно: контракт базового типа обязан соблюдаться.
> - **Забытый `base.Method()`.** Переопределение, которое должно расширять поведение, но не вызывает базовую реализацию, тихо теряет её. Обратная ошибка — вызвать `base` там, где поведение должно быть заменено.
> - **Виртуальные члены в `public`-классе библиотеки.** Каждый — часть контракта: наследники в чужом коде рассчитывают на текущее поведение, и его изменение ломает их.
> - **Глубокие иерархии с переопределением на каждом уровне.** Чтобы понять, что выполнится, нужно пройти пять классов. Композиция читается лучше.
> - **`sealed` забыт по умолчанию.** Класс, не рассчитанный на наследование, но открытый, будет унаследован — и это станет чьей-то зависимостью.

> [!example] Как делают в бою
> В прикладном коде на .NET полиморфизм чаще всего приходит через интерфейсы и DI, а не через иерархии классов: `IPaymentProvider`, `INotificationChannel`, `IOrderValidator`. Классы при этом `sealed`, потому что расширение делается композицией и регистрацией другой реализации, а не наследованием.
> Абстрактные базовые классы остаются там, где у вариантов есть общий обязательный код: шаблонный метод (`ProcessAsync` в базе вызывает абстрактные `ValidateAsync` и `ExecuteAsync`), базовый обработчик сообщений с логированием и повторами, базовый контроллер. Это оправданно, когда общего кода много и он не сводится к вспомогательному сервису.
> Ключевая привычка на ревью: увидел `new` перед членом — это либо забытый `virtual`, либо неверная иерархия. Второй маркер — виртуальный метод, вызываемый из конструктора: он почти всегда означает будущий `NullReferenceException` у наследника.

## Вопросы с собеседований

> [!question]- В чём разница между `override` и `new`?
> `override` заменяет реализацию виртуального члена в таблице методов типа: вызов разрешается в рантайме по фактическому типу объекта, поэтому через ссылку любого базового типа выполнится переопределённая версия. `new` не участвует в виртуальной диспетчеризации — он объявляет **новый** член, скрывающий одноимённый член базового типа; какой из двух вызовется, определяется на этапе компиляции по статическому типу выражения. Практическое следствие: если объект `Derived` присвоен переменной типа `Base`, то `override`-версия сработает, а `new`-версия — нет, и это источник багов, при которых код «работает» в тестах и молча не работает в проде через DI. `new` требуется только когда базовый член невиртуальный, а его нужно скрыть, — что почти всегда указывает на ошибку проектирования.

> [!question]- Почему нельзя вызывать виртуальные методы из конструктора?
> Потому что при выполнении конструктора базового класса объект уже имеет фактический тип наследника, и виртуальный вызов уйдёт в переопределение — но конструктор наследника ещё не отработал, значит его поля (в том числе `readonly`, присваиваемые в конструкторе) не инициализированы. Метод получит объект в промежуточном состоянии: ссылочные поля равны `null`, числовые — нулю, и типичный итог — `NullReferenceException` или тихо некорректная инициализация. Порядок выполнения в C#: инициализаторы полей наследника, затем конструктор базового класса (включая его инициализаторы полей и тело), затем тело конструктора наследника. Правильные альтернативы: передавать нужные данные через параметры конструктора, использовать фабричный метод, который создаёт объект и затем вызывает инициализацию, или инициализировать лениво при первом обращении.

> [!question]- Как работает виртуальный вызов и сколько он стоит?
> У каждого объекта есть указатель на таблицу методов его типа. Для виртуального члена компилятор генерирует инструкцию `callvirt`: адрес метода берётся из таблицы, соответствующей фактическому типу, поэтому выполняется реализация наследника. Стоимость — дополнительное чтение из памяти и косвенный переход, единицы наносекунд; главный минус не в этом, а в том, что виртуальный вызов мешает встраиванию метода и связанным с ним оптимизациям. JIT это частично компенсирует девиртуализацией: если тип точно известен (класс `sealed`, объект только что создан) или профиль исполнения показывает доминирующий тип, генерируется прямой вызов, иногда с проверкой типа и запасной веткой. Отсюда практическая рекомендация помечать классы `sealed` по умолчанию — это помогает и дизайну, и оптимизатору. В прикладном коде разница незаметна; она проявляется в горячих циклах на миллионы итераций.

> [!question]- Что выведет код с перегрузками, если переменная объявлена как `object`?
> Выберется перегрузка для `object`, потому что разрешение перегрузок происходит на этапе компиляции по **статическому** типу выражения, а не по фактическому типу значения. Это принципиально отличается от переопределения, которое разрешается в рантайме. Из-за этого различия в C# не работает «двойная диспетчеризация»: нельзя выбрать реализацию сразу по двум фактическим типам, для этого нужен паттерн «Посетитель» или явное сопоставление с образцом. Если поведение должно зависеть от фактического типа аргумента, есть три пути: сделать метод виртуальным на самом аргументе (то есть перенести поведение в тип), использовать `switch` с типовыми паттернами или, в крайнем случае, `dynamic`, который переносит разрешение перегрузки в рантайм ценой производительности и потери проверок компилятора.

## Задачи

### Задача 1. Что выведет

```csharp
class A
{
    public virtual string Name => "A";
    public string Describe() => $"Я {Name}";
}

class B : A
{
    public override string Name => "B";
}

class C : B
{
    public new string Name => "C";
}

A a = new C();
B b = new C();
C c = new C();
Console.WriteLine($"{a.Name} {b.Name} {c.Name} {c.Describe()}");
```

> [!success]- Решение
> Вывод: `B B C Я B`.
> `a.Name` и `b.Name` — статические типы `A` и `B`, у обоих `Name` виртуальный, поэтому идёт вызов по таблице: последнее **переопределение** — в `B` (класс `C` не переопределяет, а скрывает). `c.Name` — статический тип `C`, и там виден скрывающий член, поэтому «C». `Describe()` объявлен в `A` и обращается к `Name` через `this`: это виртуальный вызов, который снова приводит к `B`.
> Практический вывод: метод `Describe`, написанный в базовом классе, никогда не увидит скрытый через `new` член — сокрытие не участвует в полиморфизме. Если в `C` действительно нужно другое имя, там должен быть `override`, а не `new`.

### Задача 2. Спроектировать иерархию

Нужно три вида уведомлений (email, SMS, push). Общее: проверка получателя, логирование, ограничение длины текста. Разное: способ отправки и максимальная длина. Спроектируй базовый класс.

> [!success]- Решение
> ```csharp
> public abstract class NotificationChannel(ILogger logger)
> {
>     protected abstract int MaxLength { get; }
>     protected abstract Task DeliverAsync(string to, string text, CancellationToken ct);
>
>     // Шаблонный метод: общий алгоритм здесь, различия — в абстрактных членах
>     public async Task SendAsync(string to, string text, CancellationToken ct)
>     {
>         ArgumentException.ThrowIfNullOrWhiteSpace(to);
>         ArgumentException.ThrowIfNullOrWhiteSpace(text);
>
>         var payload = text.Length <= MaxLength ? text : text[..MaxLength];
>         logger.LogInformation("Отправка через {Channel} на {Recipient}", GetType().Name, to);
>
>         await DeliverAsync(to, payload, ct);
>     }
> }
>
> public sealed class SmsChannel(ILogger<SmsChannel> logger, ISmsGateway gateway)
>     : NotificationChannel(logger)
> {
>     protected override int MaxLength => 160;
>     protected override Task DeliverAsync(string to, string text, CancellationToken ct)
>         => gateway.SendAsync(to, text, ct);
> }
> ```
> Разбор решения: публичным сделан только `SendAsync` — общий алгоритм, который наследники **не могут** переопределить (он невиртуальный), а точки расширения объявлены `abstract` и `protected`. Это паттерн «Шаблонный метод»; он гарантирует, что валидация и логирование выполнятся всегда, чего не было бы, будь `SendAsync` виртуальным. Классы-наследники `sealed` — расширяться дальше они не должны. Урезание текста вынесено в базу, а лимит — в наследника, потому что различается только значение, а не логика.
> Альтернатива без наследования: интерфейс `INotificationChannel` плюс декоратор с логированием и валидацией. Она лучше, если общий код сводится к «обвязке»; вариант с базовым классом уместен, когда общего кода много и он неотделим от алгоритма.

## Итог

- Полиморфизм подтипов: вызов виртуального члена разрешается в рантайме по фактическому типу через таблицу методов.
- `virtual` разрешает переопределение, `abstract` требует, `override` заменяет, `sealed override` закрывает дальнейшее.
- `new` не переопределяет, а скрывает: результат зависит от статического типа переменной — почти всегда это ошибка.
- Перегрузки разрешаются на этапе компиляции, переопределения — в рантайме; смешение даёт неожиданный выбор метода.
- Виртуальные вызовы из конструктора попадают в наследника до инициализации его полей.
- `sealed` по умолчанию: помогает и дизайну, и девиртуализации в JIT.
- В современном C# полиморфизм чаще получают через интерфейсы и DI, а абстрактные классы оставляют для общего кода (шаблонный метод).
