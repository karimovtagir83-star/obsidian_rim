# Иммутабельность как приём проектирования

> [!abstract] Коротко
> Иммутабельный объект после создания не меняется: «изменение» — это новый объект с другими значениями. Это не идеология, а способ убрать целый класс проблем — гонки в многопоточном коде, «потерянные» ключи в словарях, неожиданные изменения через сохранённую ссылку, необходимость гадать, в каком состоянии объект сейчас. В C# для этого есть `readonly`, `init`, `required`, `record`, `readonly struct` и иммутабельные коллекции. Цена — аллокации при копировании, поэтому иммутабельность применяют там, где выигрыш в предсказуемости важнее: значения, DTO, конфигурация, события, ключи. Сущности с жизненным циклом обычно остаются изменяемыми, но с контролируемыми переходами.

## Зачем это нужно

```csharp
// Изменяемый объект: кто угодно и когда угодно
public class Money { public decimal Amount { get; set; } public string Currency { get; set; } = ""; }

var price = new Money { Amount = 100, Currency = "UZS" };
var discounted = price;
discounted.Amount = 50;
Console.WriteLine(price.Amount);          // 50 — исходная цена изменилась

var cache = new Dictionary<Money, string>();
cache[price] = "товар";
price.Amount = 999;                        // ключ мутировал — значение больше не найти
```

```csharp
// Иммутабельный: «изменение» создаёт новое значение
public readonly record struct Money(decimal Amount, string Currency);

var price = new Money(100, "UZS");
var discounted = price with { Amount = 50 };
Console.WriteLine(price.Amount);          // 100 — исходник цел
```

Четыре конкретных выигрыша: объект безопасно передавать куда угодно; его можно читать из любого числа потоков без блокировок; он пригоден как ключ словаря; рассуждать о нём проще — значение не зависит от того, что происходило между строками.

## Средства C#

```csharp
public sealed class Order
{
    private readonly List<OrderItem> _items;      // ссылку сменить нельзя (содержимое — можно!)

    public Order(long id, IEnumerable<OrderItem> items)
    {
        Id = id;
        _items = [..items];                        // защитная копия
    }

    public long Id { get; }                        // только чтение, задаётся в конструкторе
    public required string Number { get; init; }    // задаётся при создании, дальше неизменно
    public IReadOnlyList<OrderItem> Items => _items;
}
```

| Средство | Что даёт | Когда |
|---|---|---|
| `readonly` поле | нельзя переприсвоить после конструктора | зависимости, внутренние коллекции |
| `{ get; }` | нет сеттера, задаётся в конструкторе | обязательные значения |
| `{ get; init; }` | задаётся в инициализаторе и в `with` | DTO, конфигурация |
| `required` | компилятор требует задать | обязательные `init`-свойства |
| `record` / `record struct` | равенство по значению плюс `with` | значения, события, DTO |
| `readonly struct` | все поля неизменяемы, нет защитных копий | мелкие значения |
| `ImmutableArray<T>`, `FrozenDictionary<K,V>` | неизменяемые коллекции | содержимое, которое не должно меняться |
| `const` | значение впаивается при компиляции | настоящие константы |

Разница `readonly` и `const` разобрана в [[Переменные, const и readonly]], `init`/`required` — в [[Свойства и field-backed properties]].

### Иммутабельность бывает поверхностной

```csharp
public sealed record Order(long Id, List<string> Tags);      // ловушка

var a = new Order(1, ["новый"]);
var b = a with { Id = 2 };
b.Tags.Add("важный");
Console.WriteLine(a.Tags.Count);        // 2 — список общий, «копия» связана с оригиналом
```

`with` и `readonly` защищают **ссылку**, а не то, на что она указывает. Настоящая (глубокая) иммутабельность требует, чтобы все поля тоже были иммутабельными:

```csharp
public sealed record Order(long Id, ImmutableArray<string> Tags)
{
    public Order AddTag(string tag) => this with { Tags = Tags.Add(tag) };
}
```

## Иммутабельные коллекции

```csharp
using System.Collections.Immutable;
using System.Collections.Frozen;

// Immutable*: каждая операция возвращает новую коллекцию, разделяя внутреннюю структуру
ImmutableArray<int> a = [1, 2, 3];
ImmutableArray<int> b = a.Add(4);          // a не изменилась
ImmutableList<string> list = [.. names];
ImmutableDictionary<string, int> map = ImmutableDictionary<string, int>.Empty.Add("a", 1);

// Frozen*: строится один раз, дальше только чтение — но читает быстрее обычного Dictionary
FrozenDictionary<string, int> lookup = source.ToFrozenDictionary();
FrozenSet<string> allowed = codes.ToFrozenSet(StringComparer.OrdinalIgnoreCase);
```

Три семейства с разным назначением:

| Тип | Изменение | Скорость чтения | Когда |
|---|---|---|---|
| `List<T>`, `Dictionary<K,V>` | на месте | быстро | обычная работа |
| `ImmutableArray<T>`, `ImmutableList<T>` | новая коллекция | `ImmutableArray` — как массив, `ImmutableList` — медленнее (дерево) | публикуемое наружу состояние, снапшоты |
| `FrozenDictionary/FrozenSet` (.NET 8) | невозможно | быстрее обычного словаря | справочники, построенные при старте и читаемые миллионы раз |
| `IReadOnlyList<T>` | — | как у обёрнутой | контракт «только чтение», без гарантии неизменности |

Важное различие: `IReadOnlyList<T>` — это **вид** на коллекцию, а не гарантия. Владелец может изменить исходный список, и изменение будет видно; приведением обратно к `List<T>` можно и записать. `ImmutableArray<T>` гарантирует неизменность физически.

Отдельно про стоимость: `ImmutableList<T>.Add` — `O(log n)` и создаёт узлы дерева, но переиспользует большую часть структуры (structural sharing); `ImmutableArray<T>.Add` копирует весь массив, зато чтение и обход у него как у обычного массива. Отсюда практика: `ImmutableArray` для того, что читают часто, а меняют редко; `ImmutableList` для частых модификаций больших коллекций.

## Что даёт иммутабельность

**Потокобезопасность даром.** Неизменяемое состояние можно читать из любого числа потоков без блокировок — гонок нет по построению. Это единственный вид потокобезопасности, который не стоит производительности ([[Примитивы синхронизации: lock, Monitor]]).

**Стабильные ключи.** Хеш неизменяемого объекта не меняется, поэтому он не «теряется» в `Dictionary` и `HashSet` ([[Object: Equals, GetHashCode, ToString]]).

**Отсутствие защитных копий.** Иммутабельный объект можно отдать наружу как есть: испортить его невозможно. С изменяемым приходится копировать при каждой передаче.

**Простота рассуждений.** Значение переменной не зависит от того, что произошло между строками, — не нужно держать в голове историю изменений. Это же упрощает отладку: объект в дампе такой же, каким был при создании.

**Кеширование и мемоизация.** Результат, зависящий только от неизменяемого входа, можно кешировать без риска устаревания.

## Что она стоит

**Аллокации.** Каждое «изменение» — новый объект. В горячем цикле на миллионы итераций это заметно; в обработчике HTTP-запроса — нет.

**Копирование больших графов.** Изменение одного поля в глубоко вложенной структуре требует пересоздать всю цепочку владельцев. Частично решается structural sharing в иммутабельных коллекциях, но остаётся многословным.

**Неудобство для естественно изменяемых сущностей.** Заказ, который живёт неделю и проходит пять состояний, естественнее моделировать изменяемым объектом с контролируемыми переходами, чем цепочкой из пяти копий.

## Где применять, а где нет

| Применять | Оставлять изменяемым |
|---|---|
| Value objects: `Money`, `Email`, `DateRange` | Сущности с жизненным циклом (`Order`, `Account`) |
| DTO, команды, запросы, ответы API | Буферы и накопители в горячем коде |
| Доменные события и сообщения | Большие коллекции, изменяемые в цикле |
| Конфигурация (`IOptions<T>`) | Локальные переменные внутри метода |
| Ключи словарей и множеств | Билдеры (`StringBuilder`, `ImmutableArray<T>.Builder`) |
| Состояние, разделяемое между потоками | ORM-сущности, материализуемые фреймворком |

Компромисс, который работает в прикладном коде, — **иммутабельность значений, контролируемая изменяемость сущностей**: `Order` меняется, но только через методы, проверяющие правила, а всё, что он содержит (`Money`, `Address`, позиции), — неизменяемо ([[Инкапсуляция и модификаторы доступа]]).

Второй полезный паттерн — **билдер**: собираем изменяемо, публикуем неизменяемо.

```csharp
var builder = ImmutableArray.CreateBuilder<OrderItem>();
foreach (var row in rows) builder.Add(Map(row));         // дёшево, без копий
ImmutableArray<OrderItem> items = builder.ToImmutable();  // дальше только чтение
```

Тот же принцип в архитектуре называют «функциональное ядро, императивная оболочка»: чистые неизменяемые вычисления внутри, изменения состояния и ввод-вывод — по краям.

> [!warning] Подводные камни
> - **Поверхностная иммутабельность.** `record` с `List<T>` внутри изменяем; `with` копирует ссылку на тот же список.
> - **`readonly` для поля-коллекции.** Запрещает заменить список, но не мешает его очистить.
> - **`IReadOnlyList<T>` как гарантия.** Это вид, а не копия: владелец меняет — изменения видны; приведение к `List<T>` возвращает запись.
> - **`readonly struct` забыт.** Обычная структура с `in`-параметрами и `readonly`-полями порождает защитные копии при каждом обращении к члену ([[Записи (record) и структуры]]).
> - **Иммутабельность в горячем цикле.** Пересоздание объекта на каждой итерации даёт мусор; там нужны буферы, `Span<T>` и билдеры.
> - **`ImmutableList` вместо `ImmutableArray` по умолчанию.** Обход дерева заметно медленнее массива; для «часто читаем, редко меняем» нужен массив.
> - **Иммутабельные сущности EF Core.** ORM материализует объекты через сеттеры и отслеживает изменения; полностью неизменяемая сущность требует обходных путей.
> - **Копирование графа ради одного поля.** Если приходится писать пять вложенных `with`, стоит пересмотреть модель или ограничить иммутабельность листьями.

> [!example] Как делают в бою
> Устойчивое разделение: всё, что является **значением**, — иммутабельно (`readonly record struct Money`, `record Address`, `record CreateOrderCommand`, доменные события); всё, что имеет **идентичность и жизненный цикл**, — изменяемо, но с закрытыми сеттерами и переходами через методы.
> Конфигурация приложения читается один раз при старте в `record`-модель через `IOptions<T>` — так исключается ситуация, когда часть кода видит старые настройки, а часть новые.
> Справочники, которые строятся при старте и потом только читаются (коды валют, тарифы, карта маршрутов), переводят на `FrozenDictionary`: он строится дороже обычного словаря, но читает быстрее, а именно чтение здесь миллионократно.
> В многопоточном коде иммутабельность используют как замену блокировкам: разделяемое состояние публикуется целиком новым экземпляром (`Interlocked.Exchange` ссылки), читатели работают со снимком без синхронизации.
> Чего не делают: не переводят на иммутабельность ORM-сущности и не пересоздают большие объекты в циклах ради принципа — там выигрыш в предсказуемости не окупает аллокаций.

## Вопросы с собеседований

> [!question]- Что даёт иммутабельность и чего она стоит?
> Даёт четыре вещи. Потокобезопасность без блокировок: неизменяемое состояние можно читать из любого числа потоков, гонок не возникает по построению. Стабильность в хеш-коллекциях: хеш не меняется, объект не «теряется» в словаре. Отсутствие защитных копий: неизменяемый объект безопасно передавать наружу, испортить его нельзя. И простоту рассуждений: значение не зависит от истории вызовов, отладка и тестирование становятся предсказуемыми. Стоит аллокаций — каждое «изменение» создаёт новый объект, — и многословности при работе с глубоко вложенными структурами, где изменение одного поля требует пересоздать цепочку владельцев. Поэтому иммутабельность применяют к значениям, DTO, событиям и конфигурации, а сущности с жизненным циклом обычно оставляют изменяемыми, но с контролируемыми переходами.

> [!question]- Чем `IReadOnlyList<T>` отличается от `ImmutableArray<T>`?
> `IReadOnlyList<T>` — интерфейс-вид: он лишь не предоставляет методов изменения. Под ним может лежать обычный `List<T>`, который владелец продолжает менять, и все изменения будут видны через этот вид; более того, приведение обратно к `List<T>` вернёт возможность записи. Это контракт намерения, а не гарантия. `ImmutableArray<T>` — структура, оборачивающая массив, который физически никто не меняет: любая операция вроде `Add` возвращает новый экземпляр, а исходный остаётся прежним. Практический выбор: `IReadOnlyList<T>` достаточно для параметров и свойств внутри своего кода, где владелец дисциплинирован; `ImmutableArray<T>` нужен там, где значение публикуется наружу, кешируется, разделяется между потоками или используется как часть ключа. Из соседних вариантов стоит помнить `FrozenDictionary`/`FrozenSet` — они строятся один раз и оптимизированы под очень частое чтение.

> [!question]- Почему изменяемые объекты опасны как ключи словаря?
> Потому что `Dictionary` и `HashSet` размещают элемент в корзине по хешу, вычисленному **в момент добавления**. Если после этого изменить поле, участвующее в вычислении хеша, объект окажется в «неправильной» корзине: поиск по нему пойдёт в другую корзину и ничего не найдёт, хотя элемент физически лежит в коллекции — он становится недостижимым, а перечисление его по-прежнему показывает. То же происходит с `SortedSet`, где позиция определяется сравнением. Отсюда правило: ключи должны быть иммутабельными, а хеш нужно считать только по неизменяемым полям. Это одна из главных практических причин делать value objects как `readonly record struct` — они не могут измениться после создания, и класс проблем исчезает.

## Задачи

### Задача 1. Сделать тип действительно неизменяемым

```csharp
public record Basket(long CustomerId, List<BasketItem> Items)
{
    public decimal Total => Items.Sum(i => i.Price);
}
```

> [!success]- Решение
> Запись иммутабельна только на поверхности: `Items` — изменяемый список, и `with` копирует ссылку на него, поэтому «копия» корзины делит содержимое с оригиналом.
> ```csharp
> public sealed record Basket(long CustomerId, ImmutableArray<BasketItem> Items)
> {
>     public decimal Total => Items.Sum(i => i.Price);
>
>     public Basket Add(BasketItem item) => this with { Items = Items.Add(item) };
>     public Basket Remove(long productId)
>         => this with { Items = Items.RemoveAll(i => i.ProductId == productId) };
>
>     public static Basket Empty(long customerId) => new(customerId, []);
> }
>
> var basket = Basket.Empty(1).Add(item1).Add(item2);
> ```
> Теперь любое изменение возвращает новую корзину, а старая остаётся валидной — её можно безопасно закешировать, передать в другой поток или сравнить со следующей версией. `BasketItem` тоже должен быть `readonly record struct` или `record`, иначе неизменяемость снова окажется поверхностной.
> Оговорка по стоимости: `ImmutableArray.Add` копирует массив целиком, поэтому наполнять корзину из тысячи позиций в цикле так не стоит — для этого есть `ImmutableArray.CreateBuilder<T>()` с финальным `ToImmutable()`.

### Задача 2. Выбрать модель изменяемости

Спроектируй `Order` для системы, где заказ живёт несколько дней, проходит статусы, к нему добавляются позиции и платежи. Полностью иммутабельным его делать или нет?

> [!success]- Решение
> Полная иммутабельность здесь неудобна: заказ имеет идентичность и длинный жизненный цикл, его состояние действительно меняется, а пересоздание всего агрегата на каждое изменение усложнит и код, и работу ORM. Правильный компромисс — изменяемая сущность с закрытым состоянием и неизменяемыми значениями внутри.
> ```csharp
> public sealed class Order                      // сущность: идентичность и жизненный цикл
> {
>     private readonly List<OrderItem> _items = [];
>
>     public long Id { get; private init; }
>     public OrderStatus Status { get; private set; } = OrderStatus.New;
>     public Money Total => _items.Aggregate(Money.Zero("UZS"), (sum, i) => sum + i.Total);
>     public IReadOnlyList<OrderItem> Items => _items;
>
>     public void AddItem(OrderItem item)        // переход, а не сеттер
>     {
>         if (Status != OrderStatus.New)
>             throw new InvalidOperationException("Состав оплаченного заказа менять нельзя");
>         _items.Add(item);
>     }
>
>     public void MarkPaid() { /* проверка правил и смена статуса */ }
> }
>
> public readonly record struct Money(decimal Amount, string Currency);     // значение — иммутабельно
> public readonly record struct OrderItem(long ProductId, int Quantity, Money Price)
> {
>     public Money Total => Price with { Amount = Price.Amount * Quantity };
> }
> ```
> Логика решения: сущность отличается от значения именно наличием идентичности — два заказа с одинаковыми полями это разные заказы, и «новая версия при каждом изменении» противоречит этой природе. Зато всё, из чего заказ состоит, — значения, и они неизменяемы: их нельзя испортить, они безопасны как ключи и в многопоточном чтении. Изменяемость сущности при этом строго контролируется: сеттеров нет, коллекция закрыта, переходы проверяют правила. Если позже понадобится история изменений, её добавляют событиями, а не превращением заказа в цепочку копий ([[Доменные события]]).

## Итог

- Иммутабельный объект не меняется после создания; «изменение» — это новый объект.
- Средства C#: `readonly`, `{ get; }`, `init`, `required`, `record`, `readonly struct`, `Immutable*`, `Frozen*`.
- Иммутабельность бывает поверхностной: изменяемая коллекция внутри записи разрушает гарантию.
- `IReadOnlyList<T>` — вид, а не гарантия; `ImmutableArray<T>` — настоящая неизменяемость.
- Выигрыш: потокобезопасность без блокировок, стабильные ключи, отсутствие защитных копий, предсказуемость.
- Цена: аллокации и многословность при глубоких структурах; в горячем коде нужны билдеры и буферы.
- Практическое разделение: значения иммутабельны, сущности изменяемы, но только через контролируемые переходы.
- `FrozenDictionary`/`FrozenSet` — для справочников, которые строятся один раз и читаются постоянно.
