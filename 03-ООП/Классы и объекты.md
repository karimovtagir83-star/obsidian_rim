# Классы и объекты

> [!abstract] Коротко
> Класс — описание типа (поля и члены), объект — его экземпляр в куче, адресуемый по ссылке. Конструктор — единственное место, где язык гарантирует переход объекта из «не существует» в «инварианты выполняются»; порядок инициализации при наследовании и primary constructors C# 12 — источник половины ловушек ревью. Статические члены принадлежат типу, а не экземпляру, и инициализируются рантаймом лениво и потокобезопасно. Свойства — это методы, замаскированные под поля: они решают, что можно менять снаружи, а что нет, не жертвуя удобным синтаксисом.

## Зачем это знать

Всё это — база, без которой нельзя читать доменный код проекта. Агент, не знающий правил ревью, сгенерирует класс с публичным конструктором и публичными сеттерами — рабочий, но ломающий инварианты. Порядок инициализации при наследовании и запрет виртуальных вызовов из конструктора — классические баги генерации: агент вызовет `virtual`-метод из базового конструктора, потому что это компилируется без предупреждений и выглядит логично. Static-конструктор, упавший на проде, «отравляет» тип навсегда до рестарта — если не знать этого, инцидент расследуется часами. А выбор `auto-property` vs backing field — не стиль, а вопрос: где будет жить валидация.

## Модель

### Анатомия класса

Класс — ссылочный тип: переменная хранит адрес объекта в куче, а не сами данные. Основные члены: поля (состояние, почти всегда `private`), свойства (контролируемый доступ к состоянию), методы (поведение), конструкторы (инициализация). Публичное изменяемое поле — дыра в инкапсуляции и ломающее изменение при замене на свойство (другая раскладка в IL), поэтому наружу выставляют свойства, см. [[Инкапсуляция и модификаторы доступа]].

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];   // состояние, скрыто
    public Guid Id { get; }                          // состояние, доступно на чтение
    public OrderStatus Status { get; private set; }   // меняется только изнутри

    private Order(Guid id) => Id = id;                // конструктор private — см. ServiceShop

    public static Order Create() => new(Guid.NewGuid());

    public void Pay()
    {
        if (Status != OrderStatus.New)
            throw new InvalidOperationException($"Нельзя оплатить заказ в статусе {Status}.");
        Status = OrderStatus.Paid;
    }
}
```

`class` vs `struct`: по умолчанию пиши `class`. `struct` — когда тип маленький, логически неизменяемый и создаётся массово в горячем коде. Подробности — [[Value types vs Reference types]] и [[Записи (record) и структуры]].

### Конструкторы и порядок инициализации

Конструктор не «заполняет поля», а устанавливает инварианты: после выхода из него объект должен быть корректным. Он не переопределяется, не возвращает `null`, не бывает `async` — как только нужно что-то из этого, берут статическую фабрику (`static Create(...)`, `static Task<T> LoadAsync(...)`).

Точный порядок для `new Derived()`:

```
1. Память выделяется и обнуляется (все поля = default)
2. Инициализаторы полей ПРОИЗВОДНОГО класса
3. base(...):  инициализаторы полей БАЗОВОГО → тело конструктора БАЗОВОГО
4. Тело конструктора ПРОИЗВОДНОГО класса
```

Контринтуитивный момент: инициализаторы производного класса выполняются **до** конструктора базового (в Java/C++ наоборот). Отсюда ловушка — виртуальный вызов из конструктора базового класса уходит в переопределение наследника, чьи поля, присваиваемые в *теле* его конструктора, ещё `default`:

```csharp
// ПЛОХО: метод виртуальный, вызван до того, как Derived успел проинициализироваться
public abstract class Repository
{
    protected Repository() => Cache = BuildCache();      // виртуальный вызов из ctor
    protected abstract Dictionary<string, string> BuildCache();
}
```

Лечится передачей готовых данных через `base(...)` статическим методом, а не переопределением. Конструктор, делегирующий через `: this(...)`, инициализаторы полей повторно не запускает — они выполняются один раз, там, где вызывается `base(...)`.

**Primary constructors (C# 12)** — параметры прямо у типа: `public class OrderService(IRepo repo, ILogger<OrderService> log)`. Компилятор создаёт скрытое поле под параметр только если он реально читается из члена типа; это поле **не** `readonly` — иммутабельности сама по себе фича не даёт:

```csharp
public class Counter(int value)
{
    public int Value => value;
    public void Increment() => value++;   // компилируется — мутирует скрытое поле
}
```

Хороши для DI-сервисов и тонких обёрток; плохи там, где нужна валидация (телу писать негде) или несколько способов создания.

Object initializer (`new Order { Id = 1 }`) выполняется **после** конструктора: временная переменная создаётся, затем идут присваивания в порядке записи, и только потом ссылка попадает в целевую переменную. Валидировать комбинацию значений из initializer в конструкторе невозможно — их там ещё нет; для этого нужны `required` + `init` или обычный конструктор с параметрами.

### Статические члены

Статика принадлежит типу: один блок памяти на тип (и отдельный на каждую конкретизацию дженерика), не в теле объекта. Экземплярный код видит статику, статический — не видит `this` и экземплярные члены.

Статический конструктор (`.cctor`) CLR вызывает ровно один раз, потокобезопасно, до первого обращения к типу. Если у типа нет явного `static Ctor()`, но есть инициализаторы статических полей, компилятор ставит флаг `beforefieldinit` — момент инициализации становится «когда-нибудь до первого чтения поля», а не «точно перед обращением». Для наблюдаемых побочных эффектов (лог, регистрация) нужен явный статический конструктор.

Если `.cctor` бросает исключение, CLR оборачивает его в `TypeInitializationException` и помечает тип **непригодным навсегда** в этом процессе — повторное обращение вернёт то же закэшированное исключение, а не перезапустит инициализацию. Поэтому в `.cctor` нельзя ничего блокирующего (`.Result`, `.Wait()`) и ничего, что может упасть от внешних условий (сеть, парсинг env-переменных).

`const` вшивается литералом в потребителя на этапе компиляции и не подхватывает пересборку только зависимой сборки — версионный баг. `static readonly` читается в рантайме и безопасен. Правило: `const` только для значений, которые не изменятся никогда по определению; всё остальное — `static readonly` или конфигурация.

### Свойства

Свойство — пара методов `get_X`/`set_X`, синтаксически похожая на поле. Формы: `{ get; set; }` (изменяемое), `{ get; private set; }` (меняется только изнутри), `{ get; init; }` (только при создании), `required` (обязательно задать), вычисляемое `=> выражение` (состояние не хранится — не рассинхронится). Тривиальные аксессоры JIT встраивает — свойство не медленнее поля.

```csharp
public sealed class Product
{
    public string Name { get; private set; } = "";
    public long Id { get; init; }
    public required string Sku { get; init; }
    public bool IsFree => Price == 0;
    public decimal Price { get; private set; }
}
```

Когда логике нужен явный доступ к backing-полю (нормализация, валидация в сеттере), в `net8.0`/C# 12 заводят приватное поле руками:

```csharp
private string _email = "";
public string Email
{
    get => _email;
    set => _email = string.IsNullOrWhiteSpace(value)
        ? throw new ArgumentException("Email обязателен", nameof(value))
        : value.Trim().ToLowerInvariant();
}
```

> [!info] Куда идёт индустрия
> В C# 14 (.NET 10) это пишут короче — ключевое слово `field` внутри аксессора ссылается на автоматически созданное backing-поле, и явное поле заводить не нужно: `set => field = value?.Trim() ?? "";` при автоматическом `get;`. В `net8.0`/C# 12 `field` **недоступен** — писать backing-поле руками, но знать конструкцию стоит: она встретится в статьях, свежих примерах и в ответах агента, обученного на актуальном C#.

Правило «свойство или метод»: если за обращением стоит работа (I/O, заметная стоимость, побочный эффект, возможное исключение, асинхронность) — это метод, а не свойство. `LatestReport => _db....First()` или `Logo => File.ReadAllBytes(...)` в геттере обманывают читателя и отладчик, вычисляющий свойства в watch.

## Решения

| Вопрос | Выбор A | Выбор B | Когда что |
|---|---|---|---|
| Конструктор | Primary constructor | Обычный конструктор | Primary — для DI-сервисов, тонких обёрток, record; обычный — где нужна валидация, нормализация или несколько путей создания |
| Создание объекта | Публичный `new` | `private` ctor + `static Create(...)`/`LoadAsync(...)` | Публичный — для DTO без инвариантов; фабрика — для доменных агрегатов, асинхронного или условного создания, возврата кеша/подтипа |
| Доступ к состоянию | Auto-property `{ get; set; }` | Backing field вручную (`_x` + `get`/`set`) | Auto — когда логики в аксессоре нет вовсе; backing field — как только нужна валидация/нормализация в net8.0 (в C# 14 — `field`) |
| Изменяемость свойства | `{ get; set; }` | `{ get; private set; }` / `{ get; init; }` | Set — для DTO, EF-моделей, конфигов; private set/init — для доменных сущностей, где состояние меняют только методы-команды |
| Константа | `const` | `static readonly` | `const` — для значений, неизменных по определению (`Math.PI`); всё, что может поменяться в другой версии сборки, — `static readonly` |
| Ленивая инициализация | `static readonly` | `Lazy<T>` | `static readonly` — бесплатно и достаточно почти всегда; `Lazy<T>` — когда нужен контроль над политикой (`PublicationOnly` и т. п.) |

> [!example] В ServiceShop
> Правило проекта (см. [[93 — Рабочий проект: Alif ServiceShop (обзор раздела)]]): **конструкторы агрегатов — только `private`, создание идёт через `static Create(...)`**. Это не стилистика, а защита инварианта на этапе рождения объекта: `Create` может провалидировать входные данные, поднять доменное событие (`AddDomainEvent(...)`) и вернуть `Order` только в согласованном состоянии — то, чего публичный конструктор с набором параметров не гарантирует при расширении списка правил. Правило частично проверяется автотестами в `ArchTests`: публичный конструктор агрегата не доедет до ревью, упадёт сборка.
> Приватный конструктор без параметров (`private Order() { }`) отдельно нужен для EF Core — ORM пишет прямо в backing field, `public set` ради маппинга не требуется.

> [!warning] Где ошибаются
> - **Агент часто:** делает конструктор агрегата публичным по умолчанию, не зная про правило `static Create(...)` — код компилируется и работает, пока кто-то не создаст объект в обход бизнес-правил.
> - **Агент часто:** вызывает виртуальный/абстрактный метод из тела конструктора базового класса — компилятор молчит, а поля наследника на этот момент ещё не проинициализированы телом его конструктора.
> - **Агент часто:** добавляет валидацию в конструктор доменного типа, который создаётся через object initializer — проверка стоит раньше присваиваний из `{ ... }` и падает на любом вызове.
> - Публичный `set` на доменной сущности вместо метода-команды: инвариант ломается одной строкой снаружи класса.
> - Логика в `.cctor` с сетевым вызовом или `.Result`: одна недоступность внешнего сервиса «отравляет» тип до рестарта процесса (`TypeInitializationException`).
> - `readonly`-поле или `init`-свойство создают иллюзию иммутабельности, но не защищают содержимое вложенной изменяемой коллекции.

## Проверка на ревью

- У доменной сущности конструктор `private`/`protected`, создание — через именованный `static Create(...)`/`LoadAsync(...)`.
- Нет виртуальных/абстрактных вызовов и публикации `this` в теле конструктора (в т.ч. базового).
- Поля `private`, наружу — свойства; коллекции отдаются как `IReadOnlyList<T>`/`IReadOnlyCollection<T>`, не как изменяемый тип.
- Сеттеры доменных свойств — `private set`/`init`, а не публичный `set`, если только это не DTO или EF-модель.
- В `.cctor` и в инициализаторах статических полей нет I/O, `.Result`/`.Wait()`, блокирующих вызовов.
- Геттер свойства не делает I/O, не бросает исключение в норме и не создаёт новый объект на каждое обращение (`Data => _buf.ToArray()`).
- `const` не используется для значений, которые может изменить бизнес (тарифы, ставки, лимиты) — там `static readonly` или конфигурация.

## Проверь себя

> [!question]- Почему инициализаторы полей производного класса выполняются раньше конструктора базового, и чем это опасно?
> Порядок в C# такой: инициализаторы производного → инициализаторы базового → тело базового → тело производного. Опасность — если тело базового конструктора вызывает виртуальный метод, диспетчеризация уйдёт в переопределение наследника (method table стоит с момента аллокации), а поля, присваиваемые в *теле* конструктора наследника, ещё не выполнялись и содержат `default`. Лечится запретом виртуальных вызовов из конструкторов — нужные данные передают вверх через `base(...)`, вычисляя их статическим методом.

> [!question]- Чем primary constructor класса отличается от primary constructor record?
> В `record` на каждый параметр генерируется публичное `init`-свойство плюс `Equals`/`GetHashCode`/`ToString`/`Deconstruct`/`with`. В обычном `class` ничего публичного не создаётся: параметр захватывается в скрытое приватное поле, и только если реально читается из какого-то члена, — а это поле изменяемое, не `readonly`, поэтому иммутабельности primary constructor класса сам по себе не даёт.

> [!question]- Почему `beforefieldinit` делает момент инициализации типа непредсказуемым?
> Флаг ставится компилятором автоматически, если у типа нет явного статического конструктора, но есть инициализаторы статических полей. Он разрешает CLR инициализировать тип в любой момент до первого чтения статического поля, а не строго перед первым обращением к типу — рантайм может сделать это раньше, при JIT-компиляции обращающегося метода. Если побочный эффект инициализации важен по времени (лог, регистрация, открытие соединения), нужен явный `static` конструктор — тогда флага нет и момент строго определён.

> [!question]- Когда стоит выбрать auto-property, а когда — backing field вручную?
> Auto-property (`{ get; set; }`), пока аксессору нечего делать кроме чтения/записи значения. Как только нужна нормализация, валидация или побочный эффект хотя бы в одном аксессоре — в `net8.0`/C# 12 заводится приватное поле и оба аксессора пишутся явно. В C# 14 то же самое делает ключевое слово `field` без отдельного поля — но эта возможность недоступна в проектном стеке.

> [!question]- Почему конструкторы агрегатов в ServiceShop сделаны `private`?
> Публичный конструктор с набором параметров не может гарантировать выполнение бизнес-правил при их усложнении — новый инвариант легко забыть проверить в одном из мест создания. `private` конструктор плюс `static Create(...)` централизуют создание в одном месте: там же валидация и поднятие доменных событий. Дополнительный приватный конструктор без параметров нужен отдельно — под EF Core, который заполняет объект напрямую через backing field.

## Разбор

### Упражнение 1. Ревью PR

Агент прислал такой класс агрегата:

```csharp
public class Subscription
{
    public Subscription(Guid customerId, DateOnly startsAt)
    {
        CustomerId = customerId;
        StartsAt = startsAt;
        Status = SubscriptionStatus.Active;
    }

    public Guid CustomerId { get; set; }
    public DateOnly StartsAt { get; set; }
    public SubscriptionStatus Status { get; set; }

    public void Cancel() => Status = SubscriptionStatus.Cancelled;
}
```

Что вернёшь на доработку?

> [!success]- Решение
> Три замечания. Во-первых, конструктор публичный — по правилу проекта агрегаты создаются приватным конструктором через `static Create(...)`, здесь же любой код может создать `Subscription` в обход будущих правил валидации. Во-вторых, все свойства с публичным `set` — `Status` можно выставить в любое значение снаружи, минуя `Cancel()`, а `CustomerId`/`StartsAt` вообще не должны меняться после создания. В-третьих, нет валидации: пустой `customerId` или `startsAt` из прошлого пройдут молча.
> ```csharp
> public sealed class Subscription
> {
>     public Guid CustomerId { get; }
>     public DateOnly StartsAt { get; }
>     public SubscriptionStatus Status { get; private set; }
>
>     private Subscription(Guid customerId, DateOnly startsAt)
>     {
>         CustomerId = customerId;
>         StartsAt = startsAt;
>         Status = SubscriptionStatus.Active;
>     }
>
>     public static Subscription Create(Guid customerId, DateOnly startsAt)
>     {
>         if (customerId == Guid.Empty) throw new ArgumentException("Пустой customerId.", nameof(customerId));
>         return new Subscription(customerId, startsAt);
>     }
>
>     public void Cancel() => Status = SubscriptionStatus.Cancelled;
> }
> ```

### Упражнение 2. Найди баг

```csharp
public abstract class Handler
{
    protected Handler() => Route = BuildRoute();
    public string Route { get; }
    protected abstract string BuildRoute();
}

public sealed class OrdersHandler : Handler
{
    private readonly string _prefix = "/orders";
    protected override string BuildRoute() => $"{_prefix}/v1";
}

var h = new OrdersHandler();
Console.WriteLine(h.Route);
```

> [!success]- Решение
> Печатает `/v1`, а не `/orders/v1`. `_prefix` — поле, инициализируемое инициализатором, а не в теле конструктора, поэтому по правилам порядка инициализации оно **уже** установлено к моменту вызова `BuildRoute()` из конструктора `Handler` — тут бы сработало. Проблема глубже: `Route` — `get`-only свойство без сеттера, присваиваемое прямо в конструкторе базового класса через виртуальный вызов `BuildRoute()`. Если бы `_prefix` присваивался в *теле* конструктора `OrdersHandler` (а не в инициализаторе), результат был бы `/v1` из-за `default` на строке. Правильная защита — не звать виртуальные методы из конструктора вовсе: передавать префикс через `base(prefix)` и собирать `Route` в производном конструкторе, либо сделать `Handler` не абстрактным по конструктору, а фабричным.

## Итог

- Класс — описание, объект — экземпляр в куче; конструктор гарантирует, что до его завершения объекта не существует.
- Порядок при наследовании: инициализаторы производного → инициализаторы базового → тело базового → тело производного. Виртуальные вызовы из конструктора — запрещённый приём, а не стиль.
- Primary constructor (C# 12) сокращает бойлерплейс DI-сервисов, но не даёт иммутабельности сам по себе и не подходит типам с валидацией.
- Статика живёт на уровне типа, инициализируется лениво и один раз; исключение в `.cctor` отравляет тип до рестарта процесса.
- Свойство — метод под видом поля: выбор между auto-property и ручным backing field — это вопрос, куда пойдёт валидация, а не вкусовщина.
- В ServiceShop агрегаты создаются только через `private`-конструктор + `static Create(...)` — это архитектурное правило, защищённое автотестами.
