# Классы и объекты

> [!abstract] Коротко
> Класс — это описание типа: набор полей (состояние) и членов (поведение). Объект — конкретный экземпляр этого описания, живущий в управляемой куче и адресуемый по ссылке. Класс — ссылочный тип: переменная хранит не объект, а адрес объекта, и именно это порождает большинство типичных ошибок новичков. Хороший класс прячет состояние и выставляет наружу поведение, а не мешок публичных полей.

## Зачем это нужно

Программа без классов — это набор функций и глобальных данных. Пока данных мало, это работает. Как только состояний становится десятки, а инвариантов («сумма заказа не может быть отрицательной», «отменённый заказ нельзя оплатить») — сотни, возникает вопрос: кто отвечает за то, чтобы данные оставались корректными?

Класс отвечает на этот вопрос так: состояние и правила его изменения лежат рядом, за одной границей. Снаружи видно только то, что автор класса решил показать. Это и есть смысл — не «сгруппировать переменные», а **защитить инварианты**. Подробнее про границы — в [[Инкапсуляция и модификаторы доступа]].

Второй смысл — полиморфизм. Класс задаёт контракт, который можно реализовать по-разному, см. [[Полиморфизм: virtual, override, new]] и [[Интерфейсы]].

## Класс — это описание, объект — это экземпляр

```csharp
// Класс: описание. Существует в метаданных сборки, памяти под объекты не занимает.
public class Order
{
    private readonly List<OrderLine> _lines = [];   // состояние
    public Guid Id { get; }                          // состояние (через свойство)

    public Order(Guid id) => Id = id;

    public void AddLine(OrderLine line) => _lines.Add(line);  // поведение
    public decimal Total => _lines.Sum(l => l.Amount);        // производное состояние
}

// Объект: экземпляр. Живёт в куче, у него есть адрес и время жизни.
var a = new Order(Guid.NewGuid());
var b = new Order(Guid.NewGuid());
// a и b — два разных объекта одного класса. У каждого свои _lines и Id.
```

Проведём аналогию точнее: класс — это форма для отливки, но также и запись в таблице типов рантайма (method table). Каждый объект хранит указатель на эту таблицу — так рантайм в любой момент знает, какого он типа. Это то, что делает возможными `GetType()`, `is`, приведения и виртуальные вызовы.

## class vs struct — кратко

| Критерий | `class` | `struct` |
|---|---|---|
| Категория | ссылочный тип | значимый тип |
| Где живёт | в куче (или в стеке при escape-анализе) | inline: в стеке, в поле объекта, в массиве |
| Переменная хранит | ссылку (8 байт на x64) | сами данные |
| Присваивание | копируется ссылка, объект один | копируется всё содержимое |
| Значение по умолчанию | `null` | все поля обнулены |
| Наследование | да | нет (только реализация интерфейсов) |
| Заголовок объекта | 16 байт на x64 | нет |
| Равенство по умолчанию | по ссылке | по полям (медленно, через рефлексию для не-примитивных) |

Правило выбора на практике: **по умолчанию пиши `class`**. `struct` бери, когда тип маленький (до 16–24 байт), логически неизменяемый, и его создают в больших количествах в горячем коде. Всё остальное — в [[Value types vs Reference types]], [[Стек и куча: что где лежит]] и [[Записи (record) и структуры]].

## Что бывает внутри класса

| Член | Что это | Пример |
|---|---|---|
| Поле (field) | переменная экземпляра или типа | `private int _count;` |
| Свойство (property) | пара методов `get_X`/`set_X` | `public int Count { get; private set; }` |
| Метод | поведение | `public void Add(int x)` |
| Конструктор | инициализация | `public Foo(int x)` |
| Финализатор | последний шанс освободить неуправляемый ресурс | `~Foo()` |
| Событие | точка подписки на уведомление | `public event EventHandler? Changed;` |
| Индексатор | доступ по `[...]` | `public T this[int i]` |
| Оператор | перегруженная операция | `public static Money operator +(Money a, Money b)` |
| Вложенный тип | тип внутри типа | `private sealed class Node { }` |
| Константа | значение времени компиляции | `public const int Max = 100;` |

Поля должны быть `private` (или `protected` в редких случаях) практически всегда. Публичное поле — это дыра в инкапсуляции и вдобавок бинарно несовместимо со свойством: заменить `public int X;` на `public int X { get; set; }` — это ломающее изменение для уже скомпилированных сборок. Подробнее — в [[Свойства и field-backed properties]].

## Что происходит в памяти при `new`

Выражение `new Order(id)` компилируется в IL-инструкцию `newobj`, которая выполняет примерно следующее:

1. Рантайм узнаёт из method table точный размер экземпляра.
2. Аллокатор двигает указатель в allocation context текущего потока (bump pointer allocation) — это буквально несколько инструкций, аллокация в .NET дешёвая. Если контекст исчерпан — берётся новый кусок, при нехватке места запускается сборка мусора.
3. Память уже занулена (GC отдаёт занулённые страницы), поэтому все поля получают `default`.
4. В объект записывается указатель на method table.
5. Sync block index устанавливается в нейтральное значение.
6. Вызывается конструктор.
7. На стек кладётся ссылка на объект.

### Раскладка объекта на x64

```
       ↓ сюда указывает ссылка (переменная типа Order)
       |
[-8]   [0]    [8]        [16]
+------+------+----------+----------+
| SBI  |  MT  | поле1    | поле2    | ...
+------+------+----------+----------+
 8 байт 8 байт

SBI (sync block index / object header word) — 8 байт ПЕРЕД адресом объекта.
MT  (method table pointer, он же TypeHandle) — 8 байт, лежит по адресу объекта.
```

- **Sync block index** хранит несколько вещей упакованно: индекс синхронизационного блока (когда объект использован в `lock`), хеш-код от `Object.GetHashCode()` (если его запросили), биты GC и состояние thin lock. Именно поэтому «`lock` на любом объекте» вообще возможен: место под это зарезервировано в каждом объекте.
- **Method table pointer** — по нему рантайм определяет тип, находит таблицу виртуальных методов, интерфейсные мапы, размер экземпляра, информацию для GC о том, где внутри объекта лежат ссылки.

Итого накладные расходы: **16 байт на объект** на x64 (8 на x86).

### Выравнивание и минимальный размер

Размер объекта округляется вверх до кратного 8 байт на x64 (это и есть выравнивание). Кроме того, GC требует, чтобы любой объект был **не меньше 24 байт на x64** — освобождённый объект должен уметь превратиться в элемент свободного списка, а тому нужно место под служебные данные.

```csharp
public class Empty { }              // 24 байта: 16 заголовок + 0 полей → округление до 24
public class OneInt { int _a; }     // 24 байта: 16 + 4 = 20 → округление до 24
public class TwoInts { int _a, _b; }// 24 байта: 16 + 8 = 24, ровно
public class ThreeInts { int _a, _b, _c; } // 16 + 12 = 28 → 32 байта
public class OneRef { object? _o; } // 16 + 8 = 24 байта
```

Измерить можно так (обязательно в Release, иначе JIT может выкинуть аллокацию):

```csharp
long before = GC.GetAllocatedBytesForCurrentThread();
object o = new object();
long after = GC.GetAllocatedBytesForCurrentThread();
GC.KeepAlive(o);                 // не дать оптимизатору удалить аллокацию
Console.WriteLine(after - before);  // Вывод: 24
```

> [!info] Порядок полей
> Для `class` рантайм использует auto-layout и **волен переупорядочивать поля**, чтобы уменьшить паддинг. Не рассчитывай на порядок объявления и не читай память по смещениям. Для `struct` компилятор C# по умолчанию проставляет sequential-раскладку, но и там для не-blittable типов рантайм может решить иначе. Если раскладка критична (interop) — ставь `[StructLayout(LayoutKind.Explicit)]` явно.

Как это связано с временем жизни объекта и поколениями — см. [[Сборка мусора (GC): как работает]].

## Ссылка на объект vs сам объект

Самая частая путаница. Переменная типа класса — это не объект. Это 8-байтная ячейка, в которой лежит адрес.

```csharp
var a = new StringBuilder("привет");
var b = a;                 // скопировали ССЫЛКУ, объект по-прежнему один
b.Append(", мир");
Console.WriteLine(a);      // Вывод: привет, мир   ← a и b смотрят на один объект

b = new StringBuilder("другой");  // b теперь смотрит на ДРУГОЙ объект
Console.WriteLine(a);      // Вывод: привет, мир   ← a не изменилась
```

```
    Стек                      Куча
  a  [0x1A00] ──────────►  ┌──────────────────┐
  b  [0x1A00] ──────────►  │ StringBuilder    │
                           │ "привет, мир"    │
                           └──────────────────┘
```

## Передача объекта в метод: ссылка передаётся по значению

Это классический вопрос на собеседовании и классическая ошибка в коде. В C# **всё передаётся по значению по умолчанию** — включая ссылки. Копируется адрес, а не объект.

```csharp
public class User { public string Name { get; set; } = ""; }

static void Mutate(User u)      => u.Name = "изменён";       // меняем ОБЪЕКТ по адресу
static void Reassign(User u)    => u = new User { Name = "новый" };  // меняем локальную КОПИЮ адреса
static void ReassignRef(ref User u) => u = new User { Name = "новый" }; // меняем саму переменную вызывающего

var user = new User { Name = "исходный" };

Mutate(user);
Console.WriteLine(user.Name);   // Вывод: изменён      ← объект тот же, поле поменяли

Reassign(user);
Console.WriteLine(user.Name);   // Вывод: изменён      ← присваивание внутри метода не видно снаружи

ReassignRef(ref user);
Console.WriteLine(user.Name);   // Вывод: новый        ← ref передаёт ссылку НА ПЕРЕМЕННУЮ
```

Формулировка, которую хотят услышать: «объекты не передаются по ссылке; передаётся значение ссылки. Чтобы передать саму переменную, нужен `ref` или `out`».

## `this`

`this` — неявный первый аргумент любого метода экземпляра. В IL он лежит в слоте аргумента 0. Три реальных применения:

```csharp
public class Point
{
    private readonly int x, y;

    public Point(int x, int y)
    {
        this.x = x;          // 1) снять затенение имени параметром
        this.y = y;
    }

    public Point WithX(int newX) => new Point(newX, y);

    public void Register(IRegistry registry) => registry.Add(this); // 2) передать себя наружу
}

public class Money
{
    public Money(decimal amount) : this(amount, "UZS") { }   // 3) цепочка конструкторов
    public Money(decimal amount, string currency) { /* ... */ }
}
```

> [!danger] Не раздавай `this` из конструктора
> `registry.Add(this)` внутри конструктора публикует ссылку на **недостроенный** объект. Другой поток (или тот же код чуть позже) может увидеть его с неинициализированными полями. Правило: не выпускай `this` наружу, пока конструктор не отработал.

В структурах `this` — это `ref`-подобная ссылка на сам экземпляр, и ей можно присваивать целиком: `this = default;`. В классах так нельзя.

## Жизненный цикл объекта

```
new  →  конструктор  →  использование  →  недостижим  →  GC-сборка
                                              │
                                              ├─ есть финализатор? → очередь финализации
                                              │                     → следующий цикл GC
                                              └─ нет → память освобождена сразу
```

Ключевые моменты:

- В .NET нет детерминированного разрушения. Объект собирается, когда GC решит, а не когда исчезла последняя ссылка (это не подсчёт ссылок).
- «Недостижим» = нет пути от корней (статические поля, стеки потоков, регистры, GC handles).
- Финализатор **удлиняет** жизнь объекта минимум на один цикл GC. Поэтому финализаторы — крайняя мера, см. [[Финализаторы и SafeHandle]].
- Освобождение ресурсов (файлы, сокеты, соединения) делается детерминированно через `IDisposable`/`using`, а не через GC.

## partial-классы

`partial` разрешает разложить один тип по нескольким файлам. Компилятор склеивает их в один тип.

```csharp
// Order.cs — написано человеком
public partial class Order
{
    public void Cancel() => Status = OrderStatus.Cancelled;
}

// Order.Generated.cs — сгенерировано
public partial class Order
{
    public OrderStatus Status { get; private set; }
}
```

Зачем это реально нужно:

- Генераторы кода: EF Core scaffolding, gRPC, [[Source Generators]], сериализаторы. Генератор пишет свою половину, человек — свою, и регенерация не затирает ручной код.
- Разбить действительно большой тип (но это чаще признак нарушения SRP, см. [[SOLID]]).

С C# 14 `partial` можно ставить не только на методы и свойства, но и на **конструкторы и события**: объявление в одном файле, реализация в другом. Это сделано ровно для генераторов.

Все части должны быть в одной сборке и одном неймспейсе, модификатор доступа должен совпадать (или отсутствовать во всех частях кроме одной).

## `sealed`

`sealed class` запрещает наследование. `sealed override` запрещает дальнейшее переопределение конкретного члена.

```csharp
public sealed class OrderId { /* ... */ }

public class Base { public virtual void M() { } }
public class Middle : Base { public sealed override void M() { } }  // дальше не переопределить
```

Зачем:

- **Проектирование.** Наследование — это публичный контракт. Если ты не продумал, как класс наследовать, честнее его запечатать. См. [[Композиция vs наследование]].
- **Производительность.** JIT может девиртуализировать вызовы у `sealed`-типов: вместо косвенного вызова через таблицу — прямой, а часто ещё и inline. Выигрыш заметен только в горячем коде, но он бесплатный.
- **Корректность.** Запечатанный тип нельзя сломать переопределением `Equals`/`GetHashCode` в наследнике, см. [[Object: Equals, GetHashCode, ToString]].

Практика: **`sealed` по умолчанию для конкретных классов**, открывай наследование осознанно. Многие команды включают это правилом анализатора.

## Вложенные и локальные типы

```csharp
public sealed class LruCache<TKey, TValue> where TKey : notnull
{
    // Вложенный тип: деталь реализации, никому снаружи не нужен.
    // Имеет доступ к приватным членам внешнего класса.
    private sealed class Node
    {
        public TKey Key = default!;
        public TValue Value = default!;
        public Node? Prev, Next;
    }

    private readonly Dictionary<TKey, Node> _map = [];
}
```

Важно: вложенный класс **не** содержит неявной ссылки на экземпляр внешнего класса (в отличие от нестатических внутренних классов Java). Это просто тип с именем `Outer.Inner` и с правом видеть приватные члены `Outer`.

Локальные типы объявляются прямо в теле метода (C# 12+ для локальных структур/классов через `file`-подобный сценарий редок; чаще используют локальные функции). На практике вместо локальных типов берут кортежи, `record`-типы уровня файла или локальные функции — см. [[Локальные функции и замыкания]] и [[Кортежи и деконструкция]].

## Деконструкторы

`Deconstruct` — это **не** деструктор. Это метод, позволяющий разложить объект на части через синтаксис кортежа.

```csharp
public sealed class Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(decimal amount, string currency) => (Amount, Currency) = (amount, currency);

    // Правила: имя Deconstruct, void, все параметры out, минимум два.
    public void Deconstruct(out decimal amount, out string currency)
        => (amount, currency) = (Amount, Currency);
}

var money = new Money(120.50m, "UZS");
var (amount, currency) = money;
Console.WriteLine($"{amount} {currency}");   // Вывод: 120,50 UZS

// Работает и в pattern matching:
if (money is (> 100m, "UZS")) Console.WriteLine("крупный платёж в сумах");
```

Перегрузок `Deconstruct` может быть несколько — они различаются по числу параметров. `record`-типы получают `Deconstruct` автоматически, см. [[Записи (record) и структуры]].

## Плохо → хорошо: анемичный класс против класса с поведением

### Плохо

```csharp
// Мешок публичных данных. Класс ничего не гарантирует.
public class Order
{
    public Guid Id;
    public List<OrderLine> Lines = new();
    public decimal Total;
    public string Status = "New";
}

// Логика размазана по вызывающему коду и дублируется в пяти местах
order.Lines.Add(new OrderLine(productId, 2, 500m));
order.Total += 1000m;                       // забыл — рассинхрон
order.Status = "Paid";                      // а он вообще был "New"? а если "Cancelled"?
order.Lines.Clear();                        // кто угодно и когда угодно
```

### Хорошо

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];

    public Guid Id { get; }
    public OrderStatus Status { get; private set; }
    public IReadOnlyList<OrderLine> Lines => _lines;      // наружу — только чтение
    public decimal Total => _lines.Sum(l => l.Amount);    // не хранится, значит не рассинхронится

    public Order(Guid id) => Id = id;

    public void AddLine(OrderLine line)
    {
        if (Status != OrderStatus.New)
            throw new InvalidOperationException("Позиции можно менять только у нового заказа.");
        _lines.Add(line);
    }

    public void Pay()
    {
        if (Status != OrderStatus.New)
            throw new InvalidOperationException($"Нельзя оплатить заказ в статусе {Status}.");
        if (_lines.Count == 0)
            throw new InvalidOperationException("Нельзя оплатить пустой заказ.");
        Status = OrderStatus.Paid;
    }
}

public enum OrderStatus { New, Paid, Cancelled }
```

### Почему

- `Total` перестал быть полем — исчез целый класс багов «сумма не совпадает с позициями».
- Переход статусов проверяется в одном месте, а не в каждом вызывающем.
- `_lines` недоступен на запись снаружи: `IReadOnlyList<T>` не даёт `Add`/`Clear` (нюансы см. в [[Инкапсуляция и модификаторы доступа]]).
- Класс теперь можно протестировать целиком: подал команды — проверил инварианты. Вызывающему коду нечего мокать.

Это не «правильный ООП ради ООП» — это [[Закон Деметры и Tell, Don't Ask]] на практике: говори объекту, что сделать, а не вытаскивай из него кишки и не делай за него.

> [!warning] Подводные камни
> **1. Присваивание копирует ссылку, не объект.** `var copy = original;` для класса не создаёт копию. Если нужна копия — пиши её руками, через `record` с `with`, или явный метод `Clone`. `MemberwiseClone` даёт поверхностную (shallow) копию: вложенные объекты останутся общими.
>
> **2. `==` для класса по умолчанию сравнивает ссылки, а не содержимое.** `new Money(100, "UZS") == new Money(100, "UZS")` даёт `false`, пока ты не переопределил `Equals`/`GetHashCode`/`operator ==`. Особенно больно, когда объект кладут в `Dictionary` или `HashSet` — см. [[Object: Equals, GetHashCode, ToString]] и [[Сравнение объектов: IEquatable, IComparable, компараторы]].
>
> **3. Мутабельный объект в качестве ключа словаря.** Положили, потом изменили поле, участвующее в хеше — объект «потерялся» в словаре навсегда: он лежит не в той корзине. Ключи должны быть иммутабельными, см. [[Иммутабельность как приём проектирования]].
>
> **4. Публикация `this` из конструктора.** Регистрация в статическом реестре, подписка на событие, запуск таска — всё это из конструктора выпускает недостроенный объект. Делай отдельным методом `Initialize()` или фабрикой.
>
> **5. Публичное изменяемое поле.** Кроме дыры в инкапсуляции это ещё и бинарная несовместимость: замена поля на свойство требует перекомпиляции всех зависимых сборок. Плюс поле нельзя объявить в интерфейсе и нельзя перехватить в отладчике.
>
> **6. Огромный класс на 2000 строк.** Симптом: в нём три группы полей, и каждый метод трогает только одну из них. Значит, там сидят три класса — см. [[Связанность и связность (coupling, cohesion)]].

> [!example] Как делают в бою
> - Доменные сущности пишут с приватными сеттерами и публичными методами-командами (`Pay()`, `Cancel()`, `AddLine()`). Публичный `set` в доменной модели — повод для вопроса на код-ревью.
> - DTO — наоборот, плоские и открытые: `public sealed record OrderDto(Guid Id, decimal Total, string Status);`. У DTO нет инвариантов, у него задача пересечь границу процесса. Не смешивай DTO и доменную модель.
> - Конкретные классы помечают `sealed` по умолчанию. В шаблонах многих команд стоит анализатор, требующий явного решения.
> - EF Core требует конструктор (может быть приватным) и умеет писать напрямую в backing field — поэтому доменную модель с приватными сеттерами он мапит нормально, `public set` ради ORM добавлять не нужно.
> - Приватный конструктор без параметров под ORM/сериализатор — стандартная практика: `private Order() { }`.

## Вопросы с собеседований

> [!question]- В чём разница между классом и объектом?
> Класс — описание типа: набор членов и правил, существует в метаданных сборки. Объект — экземпляр класса во время выполнения: конкретный блок памяти в управляемой куче со своим состоянием, заголовком и временем жизни. Классов в программе фиксированное число (известно при компиляции), объектов может быть сколько угодно. Обращаемся к объекту всегда через ссылку.

> [!question]- Объекты в C# передаются по ссылке или по значению?
> По значению — но передаётся значение *ссылки*, то есть копия адреса. Поэтому изменение полей объекта внутри метода видно вызывающему (адрес тот же, объект тот же), а переприсваивание параметра (`u = new User()`) — не видно, оно меняет только локальную копию адреса. Чтобы метод мог заменить саму переменную вызывающего, нужен `ref` или `out`. Формула, которую хотят услышать: «ссылка передаётся по значению».

> [!question]- Сколько байт занимает пустой объект `new object()` на x64 и почему?
> 24 байта. Из них 8 — sync block index (лежит по отрицательному смещению, перед адресом объекта), 8 — указатель на method table, итого 16 байт заголовка и 0 байт полей. Оставшиеся 8 байт — добивка до минимального размера объекта, который GC требует равным 24 байтам на x64: освобождённый объект должен уметь стать элементом свободного списка, а тому нужно место под служебные данные. На x86 те же величины вдвое меньше: 12 байт.

> [!question]- Зачем нужен sync block index, если я не использую `lock`?
> Он универсальный слот под несколько вещей: thin lock (состояние блокировки без выделения полноценного объекта синхронизации), индекс в таблице sync blocks (когда thin lock перерастает в fat lock или объекту нужен, например, `Monitor.Wait`), кешированный хеш-код от `Object.GetHashCode()`, а также служебные биты GC (в частности, для перемещения объектов). Именно из-за него `lock` работает на *любом* ссылочном объекте, а не только на специальном типе, — и именно поэтому `lock(this)` и `lock(typeof(T))` считаются плохой практикой: этот слот виден всем и его может занять чужой код.

> [!question]- Что даёт `sealed` и стоит ли ставить его по умолчанию?
> `sealed` запрещает наследование от класса (или дальнейшее переопределение члена). Три эффекта: во-первых, ты не обязан продумывать и поддерживать контракт наследования — это реальная экономия; во-вторых, JIT может девиртуализировать и заинлайнить вызовы, поскольку точный тип известен статически; в-третьих, наследник не сломает поведение переопределением `Equals`/`GetHashCode`. Да, ставить по умолчанию стоит: открыть класс для наследования можно всегда, закрыть уже используемый — ломающее изменение.

> [!question]- Чем вложенный класс в C# отличается от внутреннего класса в Java?
> В Java нестатический inner class хранит неявную ссылку на экземпляр внешнего класса и создаётся как `outer.new Inner()`. В C# вложенный класс — это просто тип с квалифицированным именем `Outer.Inner`; неявной ссылки на экземпляр внешнего типа у него нет, и создаётся он как `new Outer.Inner()`. Единственная привилегия: вложенный тип видит приватные члены внешнего типа (обратное тоже верно, если внешний тип держит экземпляр вложенного). По умолчанию доступ вложенного типа — `private`.

> [!question]- Что такое `Deconstruct` и чем он отличается от финализатора?
> `Deconstruct` — обычный метод с `out`-параметрами, включающий синтаксис `var (a, b) = obj;` и позиционные паттерны `obj is (1, "x")`. Никакого отношения к освобождению памяти он не имеет. Финализатор пишется как `~ClassName()`, компилируется в переопределение `Object.Finalize()` и вызывается сборщиком мусора недетерминированно. Путаница возникает из-за похожего перевода «деконструктор» / «деструктор» — на собеседовании стоит проговорить разницу явно.

## Задачи

### Задача 1. Объясни вывод

Не запуская код, скажи, что напечатается и почему.

```csharp
public class Box { public int Value; }

static void A(Box b) { b.Value = 1; }
static void B(Box b) { b = new Box { Value = 2 }; }
static void C(ref Box b) { b = new Box { Value = 3 }; }

var box = new Box { Value = 0 };
A(box); Console.WriteLine(box.Value);
B(box); Console.WriteLine(box.Value);
C(ref box); Console.WriteLine(box.Value);
```

> [!success]- Решение
> ```
> 1
> 1
> 3
> ```
> `A` получает копию ссылки, но по этой ссылке лежит тот же объект — запись в поле видна снаружи.
> `B` тоже получает копию ссылки и переприсваивает её. Меняется только локальная переменная параметра; объект вызывающего не тронут, поэтому по-прежнему `1`.
> `C` получает ссылку на саму переменную `box` вызывающего, поэтому присваивание внутри метода меняет переменную вызывающего — `3`.

### Задача 2. Почини инкапсуляцию

Класс позволяет извне сломать свои инварианты. Найди все дыры и перепиши.

```csharp
public class Basket
{
    public List<string> Items = new();
    public int MaxItems = 10;
    public decimal Total;
}
```

> [!success]- Решение
> ```csharp
> public sealed class Basket
> {
>     private readonly List<BasketItem> _items = [];
>     private readonly int _maxItems;
>
>     public Basket(int maxItems = 10)
>     {
>         if (maxItems <= 0)
>             throw new ArgumentOutOfRangeException(nameof(maxItems));
>         _maxItems = maxItems;
>     }
>
>     public IReadOnlyList<BasketItem> Items => _items;
>     public decimal Total => _items.Sum(i => i.Price);   // вычисляем, а не храним
>
>     public void Add(BasketItem item)
>     {
>         ArgumentNullException.ThrowIfNull(item);
>         if (_items.Count >= _maxItems)
>             throw new InvalidOperationException($"В корзину помещается не более {_maxItems} товаров.");
>         _items.Add(item);
>     }
>
>     public bool Remove(BasketItem item) => _items.Remove(item);
> }
>
> public sealed record BasketItem(string Name, decimal Price);
> ```
> Дыры в исходном коде: список отдавался наружу на запись (`basket.Items.Clear()` работал), лимит можно было изменить в любой момент (`basket.MaxItems = 0` при уже полной корзине), `Total` хранился отдельно от позиций и гарантированно рассинхронизировался. После правки инварианты «не больше N позиций» и «Total == сумме позиций» держит сам класс.

### Задача 3. Посчитай размер

Сколько байт займут экземпляры этих классов на x64? Ответ обоснуй.

```csharp
class A { }
class B { byte _x; }
class C { long _a; long _b; }
class D { object _o; int _i; byte _b; }
```

> [!success]- Решение
> - `A`: 16 байт заголовка + 0 полей = 16, но минимум объекта 24 → **24 байта**.
> - `B`: 16 + 1 = 17 → округление до 24 (и минимум тот же) → **24 байта**.
> - `C`: 16 + 8 + 8 = 32, кратно 8 → **32 байта**.
> - `D`: 16 + 8 (ссылка) + 4 (int) + 1 (byte) = 29 → округление вверх до 32 → **32 байта**. Реальный порядок полей выберет рантайм (auto-layout), он же схлопнет `int` и `byte` в один 8-байтный слот, так что паддинг здесь минимальный.
>
> Проверить: `GC.GetAllocatedBytesForCurrentThread()` до и после аллокации в Release-сборке, либо `!objsize` в SOS/WinDbg.

## Итог

- Класс — описание типа, объект — его экземпляр в куче. Переменная класса хранит ссылку, а не объект.
- На x64 объект несёт 16 байт заголовка (sync block index + method table pointer), выравнивается по 8 байт и не бывает меньше 24 байт.
- Ссылка передаётся в метод по значению: мутация объекта видна снаружи, переприсваивание параметра — нет. Для замены самой переменной нужен `ref`.
- Хороший класс прячет поля и выставляет поведение. Публичные изменяемые поля и «мешок данных» — источник рассинхрона и дублирования логики.
- `sealed` по умолчанию, наследование — по осознанному решению. `partial` — в первую очередь для генераторов кода.
- `Deconstruct` — про разложение на кортеж, финализатор — про GC. Это разные вещи.
