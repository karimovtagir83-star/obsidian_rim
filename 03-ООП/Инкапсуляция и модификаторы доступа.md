# Инкапсуляция и модификаторы доступа

> [!abstract] Коротко
> Инкапсуляция — это не «сделать поля приватными и написать геттеры», а сокрытие того, **как** объект устроен, за тем, **что** он умеет. Модификаторы доступа — инструмент, которым это сокрытие обеспечивается: `public` (всем), `private` (только своему типу), `protected` (наследникам), `internal` (своей сборке) и две комбинации — `protected internal` и `private protected`. Практический критерий хорошей инкапсуляции один: **невозможно перевести объект в некорректное состояние снаружи**. Класс с публичными сеттерами на все поля инкапсуляции не имеет, даже если формально «поля приватные».

## Зачем это нужно

Каждый публичный член — это обещание, которое придётся поддерживать. Чем меньше поверхность типа, тем меньше способов им злоупотребить и тем свободнее его менять внутри.

```csharp
// Инкапсуляции нет: любой код может нарушить инвариант «сумма = сумме позиций»
public class Order
{
    public List<OrderItem> Items { get; set; } = [];
    public decimal Total { get; set; }
    public OrderStatus Status { get; set; }
}

order.Total = -1000;                  // никто не мешает
order.Items.Clear();                  // Total остался прежним — данные разъехались
order.Status = OrderStatus.Delivered; // из New сразу в Delivered, минуя оплату

// Инкапсуляция есть: состояние меняется только через методы, которые следят за инвариантами
public class Order
{
    private readonly List<OrderItem> _items = [];

    public IReadOnlyList<OrderItem> Items => _items;
    public decimal Total => _items.Sum(i => i.Price * i.Quantity);
    public OrderStatus Status { get; private set; } = OrderStatus.New;

    public void AddItem(OrderItem item)
    {
        if (Status != OrderStatus.New)
            throw new InvalidOperationException("Нельзя менять состав оплаченного заказа");
        _items.Add(item);
    }

    public void MarkPaid()
    {
        if (Status != OrderStatus.New)
            throw new InvalidOperationException($"Нельзя оплатить заказ в статусе {Status}");
        if (_items.Count == 0)
            throw new InvalidOperationException("Пустой заказ нельзя оплатить");
        Status = OrderStatus.Paid;
    }
}
```

Второй вариант отличается не количеством строк, а тем, что у него **нет способа сломать** правила снаружи. Это и есть цель.

## Модификаторы доступа

| Модификатор | Кто видит |
|---|---|
| `public` | все, включая другие сборки |
| `internal` | только своя сборка |
| `protected` | свой тип и наследники (в том числе в других сборках) |
| `private` | только свой тип (и вложенные в него типы) |
| `protected internal` | своя сборка **или** наследники где угодно (объединение) |
| `private protected` | наследники **внутри своей сборки** (пересечение, C# 7.2) |
| `file` | только этот файл (C# 11, в основном для генераторов кода) |

Значения по умолчанию (когда модификатор не написан):

```csharp
class Foo { }                    // internal — типы верхнего уровня по умолчанию internal
class Bar
{
    int _x;                      // private — члены класса по умолчанию private
    void Method() { }            // private
}
interface IService
{
    void Do();                   // public — члены интерфейса по умолчанию public
}
struct Point { int X; }          // private
enum Status { A }                // члены enum всегда public
```

Правило запоминания: **всё максимально закрыто по умолчанию, кроме членов интерфейсов и enum**. Явно писать `private` у полей не обязательно, но принято — так виден намеренный выбор ([[Стиль кода, соглашения и .editorconfig]]).

### `internal` и граница сборки

`internal` — единственный настоящий архитектурный барьер в C#: пространство имён ничего не ограничивает, а сборка ограничивает.

```csharp
// Модуль заказов: наружу торчит только контракт
public interface IOrderService { Task<Order> CreateAsync(CreateOrderRequest request, CancellationToken ct); }

internal sealed class OrderService : IOrderService { }        // реализация не видна снаружи
internal sealed class OrderPricingCalculator { }               // внутренняя деталь
```

Так строят модульные монолиты: каждый модуль — сборка, публичны только контракты и DTO, всё остальное `internal`. Попытка обратиться к чужой внутренности не компилируется, а не «осуждается на ревью» ([[ServiceShop: модульный монолит и изоляция модулей]]).

Для тестов доступ открывают точечно:

```xml
<ItemGroup>
  <InternalsVisibleTo Include="Alif.ServiceShop.Orders.Tests" />
</ItemGroup>
```

Тестировать `internal`-типы напрямую — компромисс: удобно, но привязывает тесты к реализации. Лучше тестировать через публичный контракт, а `InternalsVisibleTo` оставлять для сложных внутренних алгоритмов.

### `protected` — тоже публичный API

Часто забывают: `protected`-член видят **все наследники, в том числе в чужих сборках**. Изменение его сигнатуры ломает их так же, как изменение `public`. Поэтому `protected` — часть публичного контракта класса, и открывать через него внутренности нужно так же осторожно.

`private protected` (наследники только внутри своей сборки) обычно ближе к тому, что на самом деле имели в виду.

## Свойства вместо публичных полей

```csharp
public class Bad  { public decimal Total; }              // публичное поле
public class Good { public decimal Total { get; private set; } }
```

Причины предпочитать свойства даже там, где логики нет:

1. **Можно добавить логику потом**, не ломая вызывающих: валидацию, ленивое вычисление, уведомление.
2. **Бинарная совместимость**: замена поля на свойство — ломающее изменение на уровне IL, пересборка потребителей обязательна.
3. **Интерфейсы, привязка данных, сериализация, ORM** работают со свойствами, а не с полями.
4. **`ref`-семантика**: поле можно передать по `ref` и изменить в обход владельца.

Подробно про формы свойств, `init`, `required` и ключевое слово `field` — [[Свойства и field-backed properties]].

### Коллекции: самая частая дыра

```csharp
public class Leaky
{
    public List<OrderItem> Items { get; } = [];      // сеттера нет, но...
}
leaky.Items.Clear();                                  // ...содержимое меняется свободно

public class Sealed
{
    private readonly List<OrderItem> _items = [];
    public IReadOnlyList<OrderItem> Items => _items;   // наружу — только чтение
    public void AddItem(OrderItem item) => _items.Add(item);
}
```

`IReadOnlyList<T>` не даёт **скомпилировать** изменение, хотя приведением обратно к `List<T>` его формально можно обойти — от злого умысла это не защита, но от случайности защищает полностью. Полная гарантия — `ImmutableArray<T>` или копия в геттере (дорого).

То же с массивами в конструкторе: принятый снаружи массив нужно копировать (`[..items]`), иначе вызывающий сохранит ссылку и изменит состояние объекта в обход методов ([[Защитное программирование и guard clauses]]).

## Что именно скрывать

Инкапсуляция — про **сокрытие решений, которые могут измениться**:

| Скрывать | Открывать |
|---|---|
| структуру хранения (список, словарь, массив) | операции над данными |
| алгоритм расчёта | результат расчёта |
| промежуточные состояния | завершённые переходы состояний |
| зависимости и способ их получения | контракт того, что объект умеет |
| порядок инициализации | готовый к использованию объект |

Ошибка новичка — «инкапсуляция = приватное поле плюс `get`/`set` на него». Такой класс полностью открыт: разница с публичным полем только синтаксическая.

```csharp
// Это НЕ инкапсуляция — просто поле, обёрнутое в свойство
public class Account
{
    private decimal _balance;
    public decimal Balance { get => _balance; set => _balance = value; }
}

// Это инкапсуляция: снаружи доступны только осмысленные операции
public class Account
{
    public decimal Balance { get; private set; }

    public void Deposit(decimal amount)
    {
        ArgumentOutOfRangeException.ThrowIfNegativeOrZero(amount);
        Balance += amount;
    }

    public void Withdraw(decimal amount)
    {
        ArgumentOutOfRangeException.ThrowIfNegativeOrZero(amount);
        if (amount > Balance) throw new InsufficientFundsException(amount, Balance);
        Balance -= amount;
    }
}
```

Смысловая разница: в первом случае вызывающий сам считает новый баланс (и правила размазаны по всему коду), во втором правило живёт в одном месте. Это же основа принципа «говори, а не спрашивай» — [[Закон Деметры и Tell, Don't Ask]].

## Границы применимости

Не всё должно быть закрыто. Есть типы, у которых **нет** поведения и нет инвариантов, — данные в чистом виде:

```csharp
// DTO, команда, событие, конфигурация: открытые свойства — это нормально
public sealed record CreateOrderRequest(long CustomerId, string Address, decimal Total);
public sealed class PaymentOptions
{
    public string ApiKey { get; init; } = "";
    public int TimeoutSeconds { get; init; } = 30;
}
```

Пытаться «инкапсулировать» DTO бессмысленно: его задача — переносить данные, инвариантов у него нет, а лишние методы только мешают сериализации. Признак, по которому отличают: если у типа есть правила, связывающие поля между собой, — это модель с поведением, и её нужно закрывать; если полей просто набор — это данные.

Второй тип границы — `sealed`. Закрытый от наследования класс проще менять: не нужно думать, что сломается у наследников. Разумное умолчание — делать классы `sealed`, кроме тех, которые специально проектируются под расширение ([[Наследование]]).

> [!warning] Подводные камни
> - **Публичные автосвойства с сеттерами на доменной модели.** Инвариант можно нарушить одной строкой из любого места кода.
> - **Возврат внутренней коллекции.** `public List<T> Items { get; }` — состояние объекта доступно на запись всем.
> - **`protected`-поля.** Наследники получают прямой доступ к состоянию базового класса, и рефакторинг базы ломает их. Лучше `protected`-метод или `private protected`.
> - **Геттер с побочными эффектами.** Свойство должно вести себя как чтение значения: без запросов в базу, без мутаций, без исключений в обычном случае.
> - **`internal` вместо `public` «на всякий случай» в библиотеке.** Потребитель не сможет расширить тип; но и обратное хуже — сделать `public` то, что не готов поддерживать годами.
> - **Тестирование через `InternalsVisibleTo` всего подряд.** Тесты привязываются к реализации и ломаются на каждом рефакторинге.
> - **Приватный сеттер как иллюзия защиты.** Если внутри класса состояние всё равно меняется хаотично, инвариант не защищён; нужны методы-переходы, а не сеттер.

> [!example] Как делают в бою
> В доменном слое сущности почти не имеют публичных сеттеров: состояние меняется методами (`MarkPaid`, `AddItem`, `Cancel`), коллекции наружу отдаются как `IReadOnlyList<T>`, а конструктор либо приватный (создание через фабричный метод), либо требует всё необходимое сразу. Такой тип невозможно создать или перевести в некорректное состояние — и половина проверок в сервисах исчезает.
> В прикладном слое (DTO, команды, ответы API) наоборот: `record` с `init`-свойствами, никакого поведения, всё открыто. Смешивать эти два стиля в одном типе — типичная ошибка, из-за которой доменная модель превращается в набор структур данных, а бизнес-правила растекаются по сервисам ([[Антипаттерны и code smells]], анемичная модель).
> В модульном монолите публичны только контракты модуля: интерфейсы, DTO, события. Реализации, репозитории и хелперы — `internal`. Это единственный способ, которым компилятор реально удержит границы между модулями.

## Вопросы с собеседований

> [!question]- Что такое инкапсуляция и чем она отличается от «private-полей с геттерами»?
> Инкапсуляция — сокрытие внутреннего устройства объекта за интерфейсом его поведения, так чтобы снаружи было невозможно нарушить его инварианты и чтобы реализацию можно было менять, не затрагивая потребителей. Приватное поле с публичными `get`/`set` не даёт ни того, ни другого: состояние по-прежнему меняется произвольно, а тип хранения фактически зафиксирован в контракте. Настоящая инкапсуляция выражается в том, что снаружи доступны осмысленные операции (`Withdraw`, `MarkPaid`), а не отдельные поля, и что правила изменения состояния живут внутри объекта. Проверочный вопрос: можно ли из внешнего кода привести объект в состояние, которое запрещено бизнес-правилами? Если да, инкапсуляции нет независимо от того, как объявлены поля.

> [!question]- Чем `protected internal` отличается от `private protected`?
> `protected internal` — это **объединение**: член доступен всему коду в своей сборке и, кроме того, наследникам в любых других сборках. `private protected` (C# 7.2) — **пересечение**: только наследникам и только внутри своей сборки. То есть первый шире `internal`, второй уже `protected`. Практически `private protected` обычно и есть то, что имеют в виду, когда пишут `protected`: дать доступ подклассам, но не превращать член в часть публичного контракта для внешних потребителей. Важно помнить, что обычный `protected` виден наследникам из чужих сборок, поэтому его изменение — ломающее изменение API.

> [!question]- Почему нельзя возвращать внутреннюю коллекцию через публичное свойство?
> Потому что `public List<T> Items { get; }` защищает только саму ссылку: заменить список нельзя, а изменить его содержимое (`Add`, `Clear`, `RemoveAt`) может любой внешний код. Все инварианты, связанные с составом коллекции, оказываются незащищёнными, и объект узнаёт об изменениях последним — например, кешированная сумма перестаёт соответствовать позициям. Правильные варианты: хранить приватное поле и отдавать `IReadOnlyList<T>` (изменение не скомпилируется), использовать `ImmutableArray<T>`, если нужна полная гарантия, или возвращать копию, если данных мало. Симметричное правило действует на входе: коллекцию, принятую в конструкторе, надо копировать, иначе вызывающий сохранит ссылку и продолжит менять состояние объекта извне.

> [!question]- Какая видимость по умолчанию у типов и членов в C#?
> Типы верхнего уровня — `internal`; вложенные типы — `private`. Члены классов и структур (поля, методы, свойства, события, конструкторы) — `private`. Члены интерфейсов — `public` (в C# 8+ у интерфейсов появились и другие модификаторы, но умолчание осталось `public`). Члены перечислений — всегда `public`, изменить нельзя. Общий принцип: по умолчанию всё максимально закрыто, и открывать нужно осознанно. Отдельно стоит помнить про `file`-типы из C# 11 — они видны только в пределах одного файла и предназначены в первую очередь для генераторов исходного кода, чтобы сгенерированные вспомогательные типы не конфликтовали по именам.

## Задачи

### Задача 1. Закрыть модель

```csharp
public class ShoppingCart
{
    public List<CartItem> Items { get; set; } = [];
    public decimal Total { get; set; }
    public bool IsCheckedOut { get; set; }
}
```

Инвариант: `Total` всегда равен сумме позиций; после оформления состав менять нельзя.

> [!success]- Решение
> ```csharp
> public sealed class ShoppingCart
> {
>     private readonly List<CartItem> _items = [];
>
>     public IReadOnlyList<CartItem> Items => _items;
>     public decimal Total => _items.Sum(i => i.Price * i.Quantity);   // вычисляется, а не хранится
>     public bool IsCheckedOut { get; private set; }
>
>     public void Add(CartItem item)
>     {
>         ArgumentNullException.ThrowIfNull(item);
>         EnsureEditable();
>         _items.Add(item);
>     }
>
>     public void Remove(long productId)
>     {
>         EnsureEditable();
>         _items.RemoveAll(i => i.ProductId == productId);
>     }
>
>     public void Checkout()
>     {
>         EnsureEditable();
>         if (_items.Count == 0) throw new InvalidOperationException("Корзина пуста");
>         IsCheckedOut = true;
>     }
>
>     private void EnsureEditable()
>     {
>         if (IsCheckedOut) throw new InvalidOperationException("Корзина уже оформлена");
>     }
> }
> ```
> Ключевые решения: `Total` стал вычисляемым — так рассинхронизация с составом физически невозможна (если бы пересчёт был дорогим, значение кешировали бы **внутри**, инвалидируя при изменениях); коллекция приватная, наружу `IReadOnlyList<T>`; все изменения проходят через методы с проверкой состояния; `IsCheckedOut` меняется только изнутри. Внешний код теперь не может нарушить ни одно правило.

### Задача 2. Выбрать модификаторы

Модуль платежей: интерфейс `IPaymentService`, его реализация, класс расчёта комиссии, DTO запроса, базовый класс для провайдеров с общим кодом для наследников внутри модуля. Расставь модификаторы.

> [!success]- Решение
> ```csharp
> // Контракт — единственное, что видно другим модулям
> public interface IPaymentService { Task<PaymentResult> PayAsync(PaymentRequest request, CancellationToken ct); }
>
> // DTO контракта — тоже public, иначе интерфейсом нельзя пользоваться
> public sealed record PaymentRequest(long OrderId, decimal Amount, string Currency);
> public sealed record PaymentResult(bool Success, string? ExternalId);
>
> // Реализация и внутренние детали наружу не торчат
> internal sealed class PaymentService : IPaymentService { /* ... */ }
> internal sealed class FeeCalculator { /* ... */ }
>
> // База для провайдеров: наследники есть только внутри модуля
> internal abstract class PaymentProviderBase
> {
>     private protected abstract Task<PaymentResult> SendAsync(PaymentRequest request, CancellationToken ct);
>     private protected ILogger Logger { get; }              // доступно наследникам только в этой сборке
> }
> ```
> Логика: публично ровно то, что нужно вызывающему — интерфейс и типы, которые в нём фигурируют. Всё остальное `internal`, поэтому чужой модуль физически не может обратиться к `PaymentService` напрямую в обход контракта. Для членов базового класса выбран `private protected`, а не `protected`: наследники предполагаются только внутри модуля, и превращать эти члены в публичный контракт для внешних сборок незачем. Регистрация `internal`-реализации в DI работает штатно: `services.AddScoped<IPaymentService, PaymentService>()` вызывается из того же модуля, обычно из его метода-расширения `AddPaymentsModule`.

## Итог

- Инкапсуляция — сокрытие устройства, а не механическое оборачивание полей в свойства.
- Критерий: невозможно ли снаружи привести объект в некорректное состояние.
- Умолчания: типы верхнего уровня `internal`, члены `private`, члены интерфейсов `public`.
- `internal` — единственная реальная архитектурная граница в C#; пространство имён ничего не ограничивает.
- `protected` — часть публичного контракта: его видят наследники из чужих сборок. Часто нужен `private protected`.
- Свойства вместо публичных полей — ради совместимости, интерфейсов, ORM и возможности добавить логику.
- Коллекции наружу — только `IReadOnlyList<T>`/иммутабельные; принятые снаружи — копировать.
- У DTO и конфигурации инвариантов нет: там открытые `init`-свойства уместны.
