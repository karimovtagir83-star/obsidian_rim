# DRY, KISS, YAGNI и когда они врут

> [!abstract] Коротко
> DRY, KISS и YAGNI — три эвристики, которые чаще всего цитируют и чаще всего понимают неправильно. DRY — про единственность **знания**, а не про отсутствие похожих символов. KISS — про количество концепций в голове, а не про количество строк. YAGNI — про гипотетические требования, а не про необратимые решения. Все три перестают работать ровно там, где стоимость ошибки становится асимметричной: из дублирования выход дешёвый, из неправильной абстракции — нет; «простое» решение может стоить переписывания системы; «сделаем потом» для схемы БД стоит на порядок дороже, чем «сделаем сейчас».

## Зачем это нужно

Эти принципы — не законы, а компрессия опыта. Они полезны как **вопросы**, которые ты задаёшь коду, и вредны как **ответы**, которыми ты закрываешь обсуждение. На код-ревью «это же нарушает DRY» без объяснения, какое именно знание задублировано, — это не аргумент, а ритуал.

Практическая цель заметки: научиться отличать случай, когда принцип реально указывает на проблему, от случая, когда он подталкивает к решению хуже исходного. Плюс дать словарь, которым можно об этом разговаривать: «ложный DRY», «преждевременная абстракция», «необратимое решение».

Смежное — [[SOLID]] (те же грабли, только формализованные), [[Связанность и связность (coupling, cohesion)]] (метрики, на которые эти принципы влияют), [[Антипаттерны и code smells]].

## DRY: Don't Repeat Yourself

Оригинальная формулировка Энди Ханта и Дэйва Томаса («The Pragmatic Programmer», 1999):

> [!quote] Формулировка
> Every piece of **knowledge** must have a single, unambiguous, authoritative representation within a system.
> Каждая единица **знания** должна иметь единственное, однозначное, авторитетное представление в системе.

Ключевое слово — **knowledge** (знание). Не «строка кода», не «фрагмент», не «похожий метод». Знание — это правило, которое кто-то однажды принял и может однажды поменять: ставка НДС, формула комиссии, порядок полей в файле выгрузки для банка, список стран, где сервис работает.

Правильный тест на DRY звучит так: **если это правило изменится, сколько мест мне придётся править и все ли я найду?** Если ответ «одно место» — DRY соблюдён, даже если код в двух местах выглядит похоже.

### Ложный DRY: одинаково выглядит, меняется по-разному

Классика. Есть регистрация пользователя и есть импорт пользователей из CSV. Валидация выглядит похоже, кто-то «убрал дублирование».

```csharp
// ПЛОХО. Один метод на два разных сценария, потому что они «одинаковые».
public static class UserValidator
{
    public static void Validate(UserInput input, bool isImport)
    {
        if (string.IsNullOrWhiteSpace(input.Email))
            throw new ValidationException("Email обязателен");

        // При импорте дубликаты допустимы — их сливают с существующими записями.
        if (!isImport && !EmailIsUnique(input.Email))
            throw new ValidationException("Email уже занят");

        if (isImport)
        {
            // При импорте пароля нет, генерируем временный.
            input.Password ??= GenerateTemporaryPassword();
        }
        else
        {
            if (input.Password!.Length < 12)
                throw new ValidationException("Пароль короче 12 символов");
            SendConfirmationEmail(input.Email);   // при импорте письма не шлём
        }
    }
}
```

Через три месяца сюда прилетает третий сценарий — регистрация через приглашение админа. Появляется второй флаг:

```csharp
// Ещё хуже. Флаги размножаются, тело метода становится матрицей ветвлений.
public static void Validate(UserInput input, bool isImport, bool isInvite) { /* ... */ }
```

Что здесь произошло:

1. Два куска кода совпадали **случайно** (coincidental duplication). Их совпадение отражало не общее правило, а сегодняшнее состояние двух независимых правил.
2. Флаг-параметр `bool isImport` — это признак того, что абстракция неверна. **Если вызывающий обязан знать, какой режим включить, значит, он знает, что внутри два разных метода.**
3. Читать метод стало дороже: чтобы понять поведение при импорте, нужно мысленно выполнить всё тело, вычёркивая ветки.

> [!tip] Эвристика флага
> Булев параметр, который управляет **логикой** метода (а не данными), почти всегда означает, что метода должно быть два. Проверка: попробуй прочитать вызов вслух. `Validate(input, true)` — что такое `true`? Если по месту вызова непонятно, абстракция протекла.

Как правильно:

```csharp
// ХОРОШО. Два сценария — два входа. Общее — только то, что действительно общее.

// Общее знание: что считается синтаксически корректным email в нашей системе.
public static class EmailRules
{
    public static bool IsWellFormed(string? value) =>
        !string.IsNullOrWhiteSpace(value) && value.Contains('@') && value.Length <= 254;
}

public sealed class RegistrationValidator
{
    private readonly IUserRepository _users;

    public RegistrationValidator(IUserRepository users) => _users = users;

    public async Task ValidateAsync(RegistrationRequest request, CancellationToken ct)
    {
        if (!EmailRules.IsWellFormed(request.Email))
            throw new ValidationException("Некорректный email");

        if (await _users.ExistsByEmailAsync(request.Email, ct))
            throw new ValidationException("Email уже занят");

        if (request.Password.Length < 12)
            throw new ValidationException("Пароль короче 12 символов");
    }
}

public sealed class CsvImportValidator
{
    public void Validate(CsvUserRow row, int lineNumber)
    {
        // При импорте у нас другой контракт ошибок: нужен номер строки файла.
        if (!EmailRules.IsWellFormed(row.Email))
            throw new ImportException(lineNumber, "Некорректный email");

        // Дубликаты здесь не ошибка — их разрешает стратегия слияния выше по стеку.
    }
}
```

**Почему так лучше:** осталась ровно одна единица знания — «что такое корректный email» — и она живёт в одном месте. Всё остальное было двумя разными знаниями, которые просто похоже выглядели. Теперь изменение правил импорта физически не может сломать регистрацию.

### Настоящий DRY: одно знание в трёх местах

А вот случай, где DRY обязателен. Формула комиссии.

```csharp
// ПЛОХО. Одно бизнес-правило продублировано в трёх слоях.

// Слой API — показываем пользователю предварительную сумму
decimal preview = amount * 0.015m + 10m;

// Слой обработки платежа
var fee = payment.Amount * 0.015m + 10m;

// Отчёт для бухгалтерии
var totalFees = payments.Sum(p => p.Amount * 0.015m + 10m);
```

Ставка меняется с 1.5 % на 1.8 %. Правят два места из трёх, отчёт начинает расходиться с реальными списаниями на копейки, бухгалтерия ловит это через квартал.

```csharp
// ХОРОШО. Одно знание — один авторитетный источник.
public sealed record CommissionPolicy(decimal Rate, decimal FixedFee)
{
    public Money Calculate(Money amount) =>
        new(decimal.Round(amount.Value * Rate + FixedFee, 2, MidpointRounding.ToEven), amount.Currency);
}
```

**Почему так лучше:** правило стало объектом. Его можно версионировать (комиссия по договору от такой-то даты), протестировать один раз, залогировать применённую политику. И главное — изменение физически невозможно применить частично.

> [!info] Как отличить за 10 секунд
> Спроси: «эти два куска кода изменятся вместе или по отдельности?» Вместе — это дублирование знания, объединяй. По отдельности — это совпадение, не трогай.

### AHA и Rule of Three

**Rule of Three** (Дон Робертс, популяризован Мартином Фаулером): первое вхождение — пишешь. Второе — **дублируешь** и морщишься. Третье — вот теперь у тебя есть три точки данных, чтобы увидеть настоящую форму абстракции.

Смысл в том, что по двум примерам ты не отличишь общее от частного. По трём — обычно уже видно, что реально варьируется.

**AHA — Avoid Hasty Abstractions** (Кент Доддс): «предпочитай дублирование неправильной абстракции; оптимизируй под изменение в первую очередь».

Это развитие тезиса Сэнди Метц:

> [!quote] Сэнди Метц
> Duplication is far cheaper than the wrong abstraction.
> Дублирование намного дешевле неправильной абстракции.

Почему асимметрия? Сравни стоимость выхода:

| | Дублирование | Неправильная абстракция |
|---|---|---|
| Кто страдает | Автор изменения | Все текущие и будущие клиенты абстракции |
| Как чинится | Правишь 2–3 места | Нужно расплести 20 вызовов, каждый со своим набором флагов |
| Видно ли проблему | Да, сразу и локально | Нет, она размазана: каждый вызывающий добавил «маленькое» условие |
| Риск при исправлении | Низкий, изменения локальны | Высокий, регресс в несвязанных модулях |
| Кто заплатит | Ты сегодня | Кто-то другой через год |

Из дублирования выход всегда есть: ты видишь оба куска, объединяешь. Из плохой абстракции выхода почти нет: к моменту, когда она признана плохой, у неё уже 20 клиентов, шесть параметров и один `bool` с комментарием «не трогать, ломает биллинг».

## KISS: Keep It Simple

Расшифровка «Keep It Simple, Stupid» — из авиационной инженерии (Келли Джонсон, Lockheed). Смысл в оригинале: систему должен уметь чинить средний механик, а не автор конструкции.

**Ключевое непонимание:** простота — это не мало строк. Простота — это **мало концепций, которые нужно держать в голове одновременно**, чтобы понять и изменить код. Рич Хикки называл это разницей между *simple* (не переплетено с другим) и *easy* (привычно, близко).

### Пример: «умный» репозиторий против трёх методов

```csharp
// ПЛОХО. Строк меньше, концепций — сильно больше.
public class GenericRepository<TEntity> where TEntity : class
{
    private readonly DbContext _db;
    public GenericRepository(DbContext db) => _db = db;

    public async Task<IReadOnlyList<TEntity>> FindAsync(
        ISpecification<TEntity> spec,
        string[]? includes = null,
        string? orderByProperty = null,
        bool descending = false,
        int? skip = null,
        int? take = null,
        CancellationToken ct = default)
    {
        IQueryable<TEntity> query = _db.Set<TEntity>().Where(spec.ToExpression());

        foreach (var include in includes ?? [])
            query = query.Include(include);          // строка вместо выражения — опечатка ловится в рантайме

        if (orderByProperty is not null)
        {
            // Сортировка через рефлексию: ошибка в имени свойства = падение на проде
            var parameter = Expression.Parameter(typeof(TEntity), "x");
            var property = Expression.Property(parameter, orderByProperty);
            var lambda = Expression.Lambda(property, parameter);
            var method = descending ? "OrderByDescending" : "OrderBy";
            var call = Expression.Call(typeof(Queryable), method,
                [typeof(TEntity), property.Type], query.Expression, Expression.Quote(lambda));
            query = query.Provider.CreateQuery<TEntity>(call);
        }

        if (skip is not null) query = query.Skip(skip.Value);
        if (take is not null) query = query.Take(take.Value);

        return await query.ToListAsync(ct);
    }
}
```

Чтобы прочитать один вызов этого репозитория, нужно понимать: дженерики, `ISpecification`, деревья выражений, рефлексию, семантику `Include` по строке, порядок применения `Skip`/`Take`, и как всё это транслируется в SQL. Семь концепций ради выборки заказов.

```csharp
// ХОРОШО. Строк больше, концепций — одна: LINQ поверх DbSet.
public sealed class OrderQueries(ShopDbContext db)
{
    public Task<List<OrderListItem>> GetRecentForCustomerAsync(
        Guid customerId, int take, CancellationToken ct) =>
        db.Orders
          .Where(o => o.CustomerId == customerId)
          .OrderByDescending(o => o.CreatedAt)
          .Take(take)
          .Select(o => new OrderListItem(o.Id, o.Number, o.Total, o.Status))  // проекция: тянем только нужное
          .ToListAsync(ct);

    public Task<Order?> GetWithLinesAsync(Guid orderId, CancellationToken ct) =>
        db.Orders
          .Include(o => o.Lines)
          .FirstOrDefaultAsync(o => o.Id == orderId, ct);

    public Task<bool> HasUnpaidAsync(Guid customerId, CancellationToken ct) =>
        db.Orders.AnyAsync(o => o.CustomerId == customerId && o.Status == OrderStatus.Unpaid, ct);
}
```

**Почему так лучше:** каждый метод читается за пять секунд, его SQL предсказуем, опечатка в имени свойства — ошибка компиляции, а не 500-я на проде. Добавить четвёртый запрос стоит четыре строки. Подробнее о том, стоит ли вообще заворачивать EF Core в репозиторий — [[Repository и Unit of Work: нужны ли поверх EF Core]] и [[Specification pattern]].

### Когда KISS врёт

Простое сегодня решение, которое требует переписать всё завтра, — это не простота, а отложенный счёт.

| «Простое» решение | Что ломается | Правильное простое решение |
|---|---|---|
| `double` для денег | Копеечные расхождения в отчётах, невоспроизводимые баги округления | `decimal` или value object `Money` |
| Синхронный `List<T>` там, где будет 10 млн строк | OOM, таймауты, LOH-фрагментация | `IAsyncEnumerable<T>` и стриминг с самого начала |
| `DateTime.Now` везде | Ломается при переезде сервера в другой часовой пояс и при переходе на летнее время | `DateTimeOffset` + `TimeProvider` |
| Строковый статус `"paid"` | Опечатки, невозможность рефакторинга, нет исчерпывающей проверки | `enum` или закрытая иерархия |
| Один общий `AppDbContext` на всё, без транзакционных границ | Частичные сохранения, гонки | Явные границы Unit of Work |

Общее у всех строк: цена перехода к правильному варианту растёт **нелинейно** со временем, потому что данные уже записаны в неправильном формате, а API уже опубликован.

> [!tip] Формулировка, которая работает
> KISS — это «выбери минимальное решение, из которого есть дешёвый выход», а не «выбери решение, которое пишется быстрее всего».

## YAGNI: You Aren't Gonna Need It

Из практик экстремального программирования: не реализуй функциональность, пока она реально не понадобилась. Не «пока не появилось предчувствие», а «пока не появилось требование».

Логика простая: гипотетическое требование в 80 % случаев не приходит, а в оставшихся 20 % приходит в форме, которую ты не угадал. При этом за преждевременную функциональность ты платишь четырежды: пишешь, тестируешь, документируешь, тащишь при каждом рефакторинге.

### Пример: абстракция над БД «на всякий случай»

```csharp
// ПЛОХО. «А вдруг мы уйдём с Postgres на Mongo».
public interface IDataStore
{
    Task<T?> GetAsync<T>(string id, CancellationToken ct) where T : class, IEntity;
    Task SaveAsync<T>(T entity, CancellationToken ct) where T : class, IEntity;
    Task<IReadOnlyList<T>> QueryAsync<T>(Expression<Func<T, bool>> predicate, CancellationToken ct)
        where T : class, IEntity;
    Task DeleteAsync<T>(string id, CancellationToken ct) where T : class, IEntity;
}
```

Что с этим не так:

1. Интерфейс — это **пересечение** возможностей всех гипотетических реализаций. Из него выпали транзакции, джойны, оконные функции, `ON CONFLICT DO UPDATE`, частичные индексы. То есть примерно всё, ради чего берут реляционную БД.
2. Реализация ровно одна, и она навсегда останется одна. Абстракция без второй реализации — это не абстракция, это лишний слой пересылки.
3. Когда действительно понадобится специфичный запрос, его протащат мимо интерфейса. Через полгода будет и `IDataStore`, и прямой `DbContext`, и никто не знает, где что.
4. Смена Postgres → Mongo — это не смена драйвера. Это смена модели консистентности, транзакционности и способа моделировать связи. Ни один интерфейс тебя от этого не спасёт.

```csharp
// ХОРОШО. Абстрагируем не «хранилище вообще», а конкретную операцию,
// которая реально имеет две реализации (боевая + тестовая или две стратегии).
public interface IPaymentGateway
{
    Task<PaymentResult> ChargeAsync(ChargeRequest request, CancellationToken ct);
}
```

**Почему так лучше:** абстракция появилась там, где есть настоящая вариативность (два платёжных провайдера, sandbox и прод) и настоящая граница (внешняя система, сетевые сбои, необходимость подменять в тестах). См. [[Инверсия зависимостей на практике]].

### Когда YAGNI врёт: обратимые и необратимые решения

Джефф Безос сформулировал это как **двери в одну и в две стороны** (one-way / two-way doors).

- **Two-way door (обратимое)** — если решение окажется плохим, ты вернёшься назад за часы или дни. Здесь YAGNI работает в полную силу: решай быстро, ошибись дёшево.
- **One-way door (необратимое)** — откат стоит недели, миграции данных, координации с клиентами. Здесь «сделаем потом» — самая дорогая фраза в проекте.

Почему разница такая резкая: обратимость определяется не кодом, а тем, **кто ещё зависит от решения**. Код ты меняешь один. Схему БД — вместе с данными за два года. Публичный API — вместе с чужими клиентами, которых ты не контролируешь. Формат сообщений в очереди — вместе с сообщениями, которые уже лежат в топике.

| Решение | Тип двери | Почему |
|---|---|---|
| Имя приватного метода, структура класса | Two-way | Меняется рефакторингом за минуту |
| Выбор библиотеки логирования | Two-way | Обёртка `ILogger` уже есть в BCL |
| Слоистая или вертикальная нарезка модуля | Two-way (в пределах модуля) | Больно, но локально |
| **Схема БД и первичные ключи** | **One-way** | Миграция живых данных, простой, риск потери |
| **Публичный контракт REST/gRPC API** | **One-way** | Внешние клиенты, версионирование, депрекация на кварталы |
| **Формат сообщений в очереди** | **One-way** | В топике лежат старые сообщения; нужны обратно совместимые схемы |
| **Идемпотентность операций** | **One-way** | Ретраи начнутся в первый же сбой; без ключа идемпотентности их некуда прицепить |
| **Мультиарендность (tenant_id)** | **One-way** | Добавить арендатора в существующие таблицы и во все запросы — это переписывание доступа к данным |
| **Часовой пояс и точность времени в хранилище** | **One-way** | Данные уже записаны неправильно, восстановить нечем |
| **Единица хранения денег (тип и валюта)** | **One-way** | Пересчёт истории с потерей точности |

```csharp
// Пример необратимого решения, которое стоит принять сразу.
// Ключ идемпотентности в контракте — три строки сейчас, недели миграции потом.
public sealed record CreatePaymentRequest
{

    /// обязан вернуть результат первой операции, а не создать вторую.</summary>
    public required string IdempotencyKey { get; init; }

    public required Guid AccountId { get; init; }
    public required decimal Amount { get; init; }
    public required string Currency { get; init; }   // ISO-4217, хранится всегда
```

### Практическая эвристика

| Стоимость ошибки | Что делать | Пример |
|---|---|---|
| Низкая, откат за часы | **YAGNI.** Простейшее рабочее решение, не проектируй впрок | Структура папок, имена, выбор между `switch` и словарём стратегий |
| Средняя, откат за дни | Простое решение + **место для шва**: один интерфейс на границе | Отправка email: интерфейс есть, реализация одна |
| Высокая, откат за недели | **Продумай заранее.** Потрать день на ADR, обсуди с командой | Схема БД, ключи, контракты, транзакционные границы |
| Катастрофическая, отката нет | Продумай + **заложи миграционный путь** с первого дня | Формат хранения денег, персональные данные, схема событий |

Формулируй это на планировании одним вопросом: **«если через полгода окажется, что мы ошиблись, что придётся сделать?»** Если ответ «переименовать класс» — не думай, делай. Если «остановить сервис и мигрировать 300 млн строк» — думай сейчас. См. [[Оценка задач и декомпозиция]] и [[Технический долг: как говорить о нём с бизнесом]].

## Карго-культ принципов на код-ревью

Карго-культ — это когда воспроизводят форму, потеряв причину. В ревью это выглядит как ссылка на аббревиатуру вместо описания последствий.

| Догма | Что говорят | Почему это карго-культ | Как звучит полезное замечание |
|---|---|---|---|
| DRY | «Тут повтор, вынеси в метод» | Не сказано, какое знание задублировано | «Ставка комиссии здесь и в `ReportService` — при изменении разъедутся. Вынести в `CommissionPolicy`?» |
| SOLID/SRP | «Класс делает больше одного» | «Одно» не определено; любой класс можно нарезать до бессмысленности | «Этот класс меняется и при смене формата выгрузки, и при смене правил скидок. Два разных заказчика изменений — предлагаю разделить» |
| KISS | «Слишком сложно» | Нет критерия | «Чтобы понять этот метод, надо знать про деревья выражений и рефлексию. Три явных метода читаются без этого» |
| YAGNI | «Это не нужно» | Не отличили обратимое от необратимого | «Мы не используем этот параметр. Но если это часть публичного контракта — убрать потом будет breaking change, давай решим сейчас» |
| Паттерны | «Здесь нужна фабрика» | Паттерн ради паттерна | «У нас три способа создать `Notification` и выбор зависит от конфига — фабрика уберёт `switch` из четырёх мест» |

Рабочее правило ревьюера: **называй последствие, а не принцип.** Принцип — это ярлык на последствии; если ты не можешь назвать последствие, то и замечания нет. И наоборот, как автор: если тебе прилетело «нарушает X», спрашивай «что конкретно сломается» — это не пререкание, это уточнение. Подробнее — [[Code review: как давать и получать]].

> [!warning] Подводные камни
> **1. DRY на уровне слоёв.** Соблазн переиспользовать доменную сущность как DTO API «чтобы не дублировать поля». Это разное знание: сущность отражает бизнес-инварианты, DTO — контракт с внешним миром. Как только API нужно переименовать поле, а домен — нет, ты либо ломаешь клиентов, либо ломаешь домен. Дублируй структуру, это не дублирование знания.
>
> **2. DRY через наследование.** Самый частый способ получить неправильную абстракцию: увидели общий код, подняли в базовый класс. Через год базовый класс содержит `protected virtual bool ShouldSkipValidation => false;` и три хука. Наследование фиксирует связь навсегда и на все члены сразу — см. [[Композиция vs наследование]].
>
> **3. YAGNI как оправдание отсутствия дизайна.** «Мы по YAGNI не делали транзакции» — это не YAGNI, это пропущенное необратимое решение. YAGNI про *функциональность*, а не про *корректность*: обработку ошибок, отмену ([[CancellationToken и отмена операций]]), идемпотентность и границы транзакций нельзя «добавить потом», их отсутствие уже породило данные в неконсистентном состоянии.
>
> **4. KISS против явности.** «Простое» решение с неявным поведением сложнее сложного с явным. Магия через рефлексию, конвенции по имени, автоматическая регистрация «всего, что заканчивается на Service» — короче в написании и дороже в отладке: переход к определению не работает, компилятор не помогает, ошибка вылезает в рантайме.
>
> **5. Правило трёх, применённое к необратимым вещам.** «Подождём третьего случая» отлично работает для внутреннего кода и катастрофически — для публичных контрактов: третий случай уже будет у трёх разных клиентов с тремя несовместимыми ожиданиями.

> [!example] Как делают в бою
> **Дублирование помечают, а не немедленно устраняют.** В команде заводят соглашение: при втором вхождении ставится комментарий-маркер вида `// dup: расчёт комиссии, см. CommissionPolicy` и заводится задача в бэклог. Третье вхождение — триггер к рефакторингу. Это даёт данные вместо интуиции.
>
> **Необратимые решения оформляют ADR.** Короткий документ на страницу: контекст, варианты, решение, последствия. Схема БД, формат событий, стратегия идемпотентности, мультиарендность — сюда. Через год это единственный способ узнать, почему `tenant_id` стоит первым в составном ключе. См. [[Документация: ADR и RFC]].
>
> **Архитектурные тесты вместо устных договорённостей.** Правило «домен не ссылается на инфраструктуру» проверяется тестом, а не ревьюером. Разбор — в [[Связанность и связность (coupling, cohesion)]].
>
> **Флаг-параметры ловят анализатором.** В командах, где это болит, включают правило на публичные методы с `bool`-параметрами и обсуждают каждое исключение. Не догма, но заставляет назвать причину.

## Вопросы с собеседований

> [!question]- Что именно означает «единица знания» в формулировке DRY?
> Знание — это решение или правило, у которого есть владелец и причина меняться: ставка налога, формула расчёта, формат интеграции, список допустимых статусов. DRY требует, чтобы у такого правила был ровно один авторитетный источник в системе. Два фрагмента кода, которые сегодня выглядят одинаково, но изменятся по разным причинам и от разных заказчиков, — это два разных знания, и объединять их вредно. Практический тест: «если это правило изменится, все ли места я обязан поправить одновременно?» Если да — это одно знание. Если можно поправить одно и не трогать другое — разные.

> [!question]- Почему `bool`-параметр в методе считается признаком плохой абстракции?
> Потому что вызывающий код вынужден знать про внутреннее устройство метода: он выбирает ветку исполнения. Это управляющая связанность (control coupling) — худший вид связанности после общего состояния. Практические следствия: метод нельзя прочитать локально (надо мысленно вычёркивать половину тела), в точке вызова `Process(order, true)` невозможно понять смысл, флаги имеют свойство размножаться и перемножаться (`true, false, true` — восемь комбинаций, из которых валидны три). Обычно правильный рефакторинг — два метода с говорящими именами и общая приватная часть, если она реально общая. Исключение: `bool` как *данные*, а не как переключатель логики, — например, `user.SetActive(true)`.

> [!question]- Дублирование или неправильная абстракция — что дороже и почему?
> Неправильная абстракция дороже, и разница асимметричная. Из дублирования выход дешёвый и локальный: оба фрагмента перед глазами, объединяешь за час, риск ограничен. Из плохой абстракции выход дорогой: к моменту осознания у неё уже десятки клиентов, каждый добавил свой параметр или флаг, поведение переплетено, а рефакторинг задевает несвязанные модули и требует регрессионного прогона всего. Плюс психология: абстракцию неохотно ломают, её проще «немного расширить» — так она и деградирует. Отсюда AHA-принцип Кента Доддса и правило трёх: сначала продублируй, дождись трёх примеров, потом абстрагируй по реальной, а не угаданной форме.

> [!question]- Где проходит граница YAGNI? Приведите пример, когда откладывать нельзя.
> Граница — обратимость решения. YAGNI применим к тому, что можно переделать дёшево: внутренняя структура кода, конкретные реализации, дополнительные фичи. Он неприменим к решениям с высокой стоимостью отката: схема БД и первичные ключи, публичный контракт API, формат сообщений в очереди, идемпотентность, мультиарендность, единица и точность хранения денег и времени. Пример: не заложить ключ идемпотентности в контракт создания платежа — это три поля сегодня и недели работы завтра, потому что придётся менять контракт (breaking change для клиентов), добавлять таблицу дедупликации и разбираться с уже созданными дублями. Формулировка для планирования: «если через полгода мы ошиблись — что придётся сделать?»

> [!question]- KISS — это про меньше кода?
> Нет. Простота меряется числом концепций, которые нужно удерживать в голове, чтобы понять и безопасно изменить код, а не числом строк. Метод на 15 строк с рефлексией, деревьями выражений и строковыми именами свойств сложнее трёх явных методов по 6 строк, хотя короче суммарно. Полезно различать simple (мало переплетений с другими понятиями) и easy (знакомо лично мне): фреймворк с «магией» может быть easy для того, кто его знает, и при этом крайне not simple. Второй критерий простоты — насколько рано ошибка обнаруживается: явный код ловится компилятором, магический — в рантайме на проде.

> [!question]- Как ответить на замечание «это нарушает DRY» на код-ревью, если ты не согласен?
> Спросить, какое конкретно знание задублировано и когда эти два места изменятся вместе. Если ревьюер может назвать правило («ставка комиссии») — он прав, надо объединять. Если ответ звучит как «ну это же одинаковый код» — стоит показать, что фрагменты меняются по разным причинам и от разных заказчиков, и что объединение потребует флага-переключателя, то есть создаст управляющую связанность. Полезно предложить компромисс: оставить дублирование, поставить маркер и договориться объединить на третьем вхождении. Общее правило дискуссии: обсуждаем последствия, а не аббревиатуры.

> [!question]- Что такое «обратимые и необратимые решения» и как это меняет процесс разработки?
> Метафора дверей в одну и две стороны. Обратимое решение можно откатить за часы-дни, его принимает один человек быстро и без церемоний. Необратимое требует миграции данных, координации с внешними клиентами или простоя — его обсуждают заранее и фиксируют в ADR. Практический эффект: команда перестаёт тратить одинаковое количество обсуждения на всё подряд. Спор про имя класса закрывается за минуту («это two-way door, назови как хочешь»), а обсуждение формата событий в Kafka получает столько времени, сколько нужно. Ошибка в обе стороны одинаково вредна: бюрократия на обратимых решениях замедляет, спешка на необратимых оставляет шрам на годы.

### Задача 1. Убрать флаг-параметр

Дан метод. Требуется переделать так, чтобы вызывающий код не передавал переключатель логики, а общее знание не задублировалось.

```csharp
public sealed class ReportService
{
    public byte[] Build(IReadOnlyList<Sale> sales, bool forAccounting)
    {
        var rows = sales.Where(s => forAccounting ? s.IsConfirmed : true)
                        .OrderBy(s => forAccounting ? s.DocumentNumber : s.Date.Ticks.ToString())
                        .ToList();

        var total = rows.Sum(s => s.Amount * (forAccounting ? 1m : 1.2m)); // для менеджеров — с НДС

        return forAccounting ? Csv(rows, total) : Xlsx(rows, total);
    }
}
```

> [!success]- Решение
> ```csharp
> // Общее знание вынесено в явные, самостоятельные понятия.
> public static class VatPolicy
> {
>     public const decimal Rate = 0.20m;
>     public static decimal WithVat(decimal net) => decimal.Round(net * (1 + Rate), 2, MidpointRounding.ToEven);
> }
>
> public sealed class AccountingReportBuilder
> {
>     // Бухгалтерии нужны только подтверждённые продажи, суммы без НДС, порядок по номеру документа.
>     public byte[] Build(IReadOnlyList<Sale> sales)
>     {
>         var rows = sales.Where(s => s.IsConfirmed)
>                         .OrderBy(s => s.DocumentNumber)
>                         .ToList();
>         return CsvWriter.Write(rows, rows.Sum(s => s.Amount));
>     }
> }
>
> public sealed class ManagerReportBuilder
> {
>     // Менеджерам — всё подряд, по дате, с НДС.
>     public byte[] Build(IReadOnlyList<Sale> sales)
>     {
>         var rows = sales.OrderBy(s => s.Date).ToList();
>         return XlsxWriter.Write(rows, VatPolicy.WithVat(rows.Sum(s => s.Amount)));
>     }
> }
> ```
> Что изменилось: исчезла управляющая связанность — вызывающий больше не выбирает ветку внутри чужого метода. Каждый билдер читается целиком и меняется независимо. Единственное реально общее знание — ставка НДС — живёт в одном месте. Побочный выигрыш: исчезла скрытая ошибка исходника — сортировка по `Ticks.ToString()` даёт лексикографический порядок, то есть неверный.

### Задача 2. Отличить настоящее дублирование от совпадения

Ниже три фрагмента из разных мест проекта. Определи, где DRY обязателен, а где объединение навредит.

```csharp
// A. Валидация в контроллере регистрации
if (dto.Age < 18) return BadRequest("Только для совершеннолетних");

// B. Валидация в контроллере оформления заказа алкоголя
if (customer.Age < 18) throw new DomainException("Товар 18+");

// C. Расчёт возраста в двух местах
var age = (DateTime.UtcNow - birthDate).Days / 365;
var years = (DateTime.UtcNow - user.BirthDate).Days / 365;
```

> [!success]- Решение
> **A и B — совпадение, не дублируй.** Оба используют число 18, но это два разных правила с разными владельцами: «минимальный возраст регистрации в сервисе» (продуктовое решение, завтра станет 16 или 21) и «возрастное ограничение на категорию товара» (законодательное, зависит от страны и категории). Общий `const int MinAge = 18` склеит их так, что изменение продуктового правила молча поменяет юридическое. Правильно — два явных, названных правила:
> ```csharp
> public static class RegistrationRules { public const int MinAge = 18; }
> public sealed record AgeRestriction(int MinAge)          // атрибут категории товара
> {
>     public bool IsSatisfiedBy(int customerAge) => customerAge >= MinAge;
> }
> ```
>
> **C — настоящее дублирование знания, объединяй.** «Как в нашей системе считается возраст» — одно правило. Плюс обе реализации неверны: деление на 365 игнорирует високосные годы и даёт ошибку в день рождения.
> ```csharp
> public static class AgeCalculator
> {
>     // TimeProvider вместо DateTime.UtcNow — чтобы возраст можно было тестировать.
>     public static int YearsOld(DateOnly birthDate, TimeProvider clock)
>     {
>         var today = DateOnly.FromDateTime(clock.GetUtcNow().UtcDateTime);
>         var age = today.Year - birthDate.Year;
>         if (birthDate > today.AddYears(-age)) age--;   // день рождения ещё не наступил
>         return age;
>     }
> }
> ```
> Мораль: одинаковые константы — почти всегда совпадение; одинаковые *формулы* — почти всегда знание.

### Задача 3. Классифицировать решения по обратимости

Для каждого пункта укажи тип двери и что делать по YAGNI. Проект — API интернет-магазина, MVP на три месяца.

1. Хранить корзину в БД или в Redis.
2. Использовать `int` или `Guid` как первичный ключ заказа.
3. Возвращать ошибки как `ProblemDetails` или как свой JSON-формат.
4. Разделить проект на слои или писать одним проектом.
5. Логировать в консоль или сразу настроить Serilog с отправкой в централизованное хранилище.

> [!success]- Решение
> **1. Корзина в БД или Redis — two-way, но с оговоркой.** Реализация меняется за день, если доступ к корзине изолирован за одним классом. Оговорка: если корзина уже наполнена данными пользователей, нужен перенос. По YAGNI — начинай с БД (одно хранилище, транзакции, ничего не теряется), переезжай в Redis, когда появятся замеры.
>
> **2. `int` против `Guid` — one-way.** Это ключ, на него ссылаются внешние системы, он попадает в URL и в интеграции. Смена типа ключа — миграция всех таблиц со всеми внешними ключами плюс breaking change в API. Решать сейчас. Практический выбор: `Guid` (лучше — упорядоченный, `Guid.CreateVersion7()`) для сущностей, чьи идентификаторы уходят наружу или генерируются на клиенте; `int`/`long` для внутренних справочников.
>
> **3. Формат ошибок — one-way.** Это публичный контракт: клиенты напишут парсинг. Смена формата ломает всех потребителей. Решать сейчас, брать стандартный `ProblemDetails` (RFC 9457) — он уже поддержан в ASP.NET Core и в клиентских библиотеках. См. [[Обработка ошибок и ProblemDetails]].
>
> **4. Слои против одного проекта — two-way.** Разрезать один проект на три — механический рефакторинг на полдня, компилятор ведёт за руку. По YAGNI: начинай одним проектом с чёткими папками, разделяй, когда границы станут видны. См. [[Как выбрать архитектуру под задачу]].
>
> **5. Логирование — two-way по реализации, one-way по содержанию.** Заменить провайдер легко: код пишет в `ILogger`. А вот *что* именно логируется — какие поля попадают в структурные логи, есть ли correlation id — восстановить задним числом нельзя: инцидент уже случился, данных о нём нет. По YAGNI: провайдер простой, но correlation id и ключевые поля закладывай сразу. См. [[Логирование и структурные логи]].

## Итог

- DRY — про единственность **знания**, а не про отсутствие похожего текста. Тест: «изменятся ли эти места одновременно и обязательно?»
- Флаг-параметр, управляющий логикой, — надёжный признак того, что абстракция склеила два разных сценария. Разделяй.
- Дублирование дешевле неправильной абстракции, потому что асимметричны стоимости выхода. Правило трёх и AHA — способ не платить эту разницу.
- KISS меряется числом концепций, которые нужно держать в голове, а не строками. «Простое» решение с неявным поведением — не простое.
- YAGNI работает на обратимых решениях и вреден на необратимых. Схема БД, публичные контракты, формат событий, идемпотентность, мультиарендность — думай заранее.
- На ревью называй последствие, а не аббревиатуру. Принцип без последствия — карго-культ.
