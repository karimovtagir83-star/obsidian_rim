# Композиция vs наследование

> [!abstract] Коротко
> Наследование выражает «является» (is-a) и связывает типы жёстко: наследник зависит от внутреннего устройства базы, а изменение базы ломает всех потомков. Композиция выражает «содержит» (has-a): объект хранит другой объект и делегирует ему работу, поэтому связь остаётся на уровне контракта и меняется в рантайме. Индустриальное правило «предпочитай композицию наследованию» (сформулировано ещё в книге GoF) не запрещает наследование — оно ставит его на второе место: сначала спроси, нельзя ли обойтись композицией. В .NET это заметно и в самой платформе: DI, декораторы, middleware и `IOptions` — всё это композиция.

## Зачем это нужно

Классический пример неудачного наследования:

```csharp
// «Стек — это же список с ограничениями»
public class Stack<T> : List<T>
{
    public void Push(T item) => Add(item);
    public T Pop() { var last = this[^1]; RemoveAt(Count - 1); return last; }
}

var stack = new Stack<int>();
stack.Push(1);
stack.Insert(0, 42);      // и вот это тоже доступно
stack.Clear();
stack[5] = 7;             // инвариант «доступ только с вершины» разрушен
```

Наследуясь от `List<T>`, стек получил весь его API, включая операции, которые противоречат его смыслу. Композиция решает это в две строки:

```csharp
public sealed class Stack<T>
{
    private readonly List<T> _items = [];          // содержит список, а не является им

    public int Count => _items.Count;
    public void Push(T item) => _items.Add(item);
    public T Pop()
    {
        if (_items.Count == 0) throw new InvalidOperationException("Стек пуст");
        var last = _items[^1];
        _items.RemoveAt(_items.Count - 1);
        return last;
    }
}
```

Наружу торчит ровно то, что имеет смысл, а внутреннее устройство (список, массив, связный список) можно поменять, не затрагивая никого.

## Чем именно плохо наследование

### 1. Проблема хрупкого базового класса

Наследник зависит не только от контракта базы, но и от того, **как** база реализована:

```csharp
public class CountingList<T> : List<T>
{
    public int AddCount { get; private set; }

    public new void Add(T item) { AddCount++; base.Add(item); }
    public new void AddRange(IEnumerable<T> items) { AddCount += items.Count(); base.AddRange(items); }
}
```

Если в новой версии базового класса `AddRange` начнёт вызывать `Add` внутри — счётчик станет считать вдвое. Если наоборот, перестанет — перестанет считать. Наследник сломается от изменения, которое для базы было деталью реализации и не меняло её контракт. Это и называется fragile base class: **база не может свободно меняться, потому что от её внутренностей зависят потомки**.

### 2. Нарушение принципа подстановки

Наследование обязывает: объект наследника должен подходить везде, где ожидается база ([[SOLID]], буква L). На практике это нарушают постоянно:

```csharp
public class Rectangle
{
    public virtual int Width { get; set; }
    public virtual int Height { get; set; }
}

public class Square : Rectangle       // «квадрат — это же прямоугольник»
{
    public override int Width { set => base.Width = base.Height = value; }
    public override int Height { set => base.Width = base.Height = value; }
}

static void Resize(Rectangle r) { r.Width = 4; r.Height = 5; }
// Для Rectangle площадь 20, для Square — 25. Код, работающий с базой, ломается.
```

Отношение «является» из предметной области не обязано выполняться для **изменяемых** объектов: квадрат является прямоугольником в геометрии, но не в модели с сеттерами.

### 3. Жёсткость и одно наследование

Иерархия фиксируется на этапе компиляции: поведение нельзя поменять в рантайме и нельзя скомбинировать. Нужны логирование, кеш и повторы — при наследовании получаются `CachingRepository`, `LoggingRepository`, `LoggingCachingRepository`, `RetryingLoggingCachingRepository`. Комбинаторный взрыв. Композиция решает это декораторами: три независимых класса, любой порядок применения.

### 4. Наследование ломает инкапсуляцию

`protected`-члены — часть контракта, доступная всем потомкам, в том числе в чужих сборках. Чем больше `protected`, тем меньше свободы у базы; чем меньше — тем неудобнее наследоваться. Композиция такой дилеммы не создаёт: у зависимости есть только публичный интерфейс ([[Инкапсуляция и модификаторы доступа]]).

## Как выглядит композиция

```csharp
// Вместо наследования от базового «сервиса с логированием» — внедрение зависимостей
public sealed class OrderService(IOrderRepository repository, ILogger<OrderService> logger, TimeProvider clock)
{
    public async Task<Order> CreateAsync(CreateOrderRequest request, CancellationToken ct)
    {
        logger.LogInformation("Создание заказа для {CustomerId}", request.CustomerId);
        var order = new Order(request.CustomerId, clock.GetUtcNow());
        await repository.AddAsync(order, ct);
        return order;
    }
}
```

Здесь три зависимости внедрены, а не унаследованы. Каждую можно подменить в тестах, каждая имеет собственную жизнь, и класс не занимает своё единственное наследование.

### Декоратор: поведение слоями

```csharp
public interface IOrderRepository { Task<Order?> FindAsync(long id, CancellationToken ct); }

public sealed class CachingOrderRepository(IOrderRepository inner, IMemoryCache cache) : IOrderRepository
{
    public async Task<Order?> FindAsync(long id, CancellationToken ct)
    {
        if (cache.TryGetValue(id, out Order? cached)) return cached;
        var order = await inner.FindAsync(id, ct);
        if (order is not null) cache.Set(id, order, TimeSpan.FromMinutes(5));
        return order;
    }
}

public sealed class LoggingOrderRepository(IOrderRepository inner, ILogger<LoggingOrderRepository> logger)
    : IOrderRepository
{
    public async Task<Order?> FindAsync(long id, CancellationToken ct)
    {
        logger.LogDebug("Поиск заказа {OrderId}", id);
        return await inner.FindAsync(id, ct);
    }
}

// Сборка цепочки — в одном месте, порядок явный
IOrderRepository repo = new LoggingOrderRepository(
    new CachingOrderRepository(new EfOrderRepository(db), cache), logger);
```

Каждый слой знает только про интерфейс, тестируется отдельно и комбинируется в любом порядке. Наследованием такой набор не выражается.

### Стратегия: поведение параметром

```csharp
public sealed class PriceCalculator(IDiscountPolicy policy)
{
    public decimal Calculate(Order order) => order.Total - policy.GetDiscount(order);
}

public interface IDiscountPolicy { decimal GetDiscount(Order order); }
public sealed class NoDiscount : IDiscountPolicy { public decimal GetDiscount(Order o) => 0; }
public sealed class VipDiscount : IDiscountPolicy { public decimal GetDiscount(Order o) => o.Total * 0.1m; }
```

Вместо `VipPriceCalculator : PriceCalculator` — одна реализация калькулятора и подменяемая политика, в том числе выбираемая в рантайме по данным заказа.

## Когда наследование уместно

Правило «предпочитай композицию» не означает «никогда не наследуй». Наследование оправдано, когда выполняются все три условия: отношение действительно «является», иерархия **закрыта и контролируется тобой**, и общий код неотделим от алгоритма.

Конкретные ситуации:

- **Шаблонный метод.** Базовый класс задаёт последовательность шагов, наследники реализуют шаги ([[Абстрактные классы]]).
- **Закрытый набор вариантов.** `abstract record Result` с наследниками `Success`/`NotFound`/`Invalid` — иерархия существует ради сопоставления с образцом.
- **Требование фреймворка.** `ControllerBase`, `DbContext`, `BackgroundService`, `Exception` — тут выбора нет.
- **Базовый тип доменной модели.** `Entity<TId>` с равенством по идентификатору: состояние и поведение общие для всех сущностей.
- **Расширение своего типа внутри своей сборки**, когда база и наследники меняются вместе.

Признаки, что наследование выбрано ошибочно: наследник переопределяет почти всё; используется `new` вместо `override`; в базе появился `switch` по типу наследника; иерархия глубже трёх уровней; наследуются ради переиспользования пары вспомогательных методов; наследник не проходит проверку «его можно подставить везде вместо базы».

## Цена композиции

Композиция не бесплатна, и честно назвать её минусы полезно:

- **Больше кода делегирования.** Обёртка над интерфейсом с десятью методами требует написать десять методов-переходников. Частично снимается тем, что интерфейсы должны быть маленькими ([[Интерфейсы]]).
- **Больше типов.** Три декоратора вместо одного класса — больше файлов и переходов при чтении.
- **Сложнее увидеть итоговое поведение.** Что именно выполняется, определяется сборкой цепочки в DI, а не иерархией в коде. Лечится тем, что регистрация собрана в одном месте и покрыта тестом.
- **Косвенность в горячем коде.** Лишние виртуальные вызовы через интерфейсы; в 99 % прикладного кода незаметно, в горячем цикле измеримо ([[Полиморфизм: virtual, override, new]]).

Практический вывод: композиция — умолчание, наследование — осознанное исключение с обоснованием.

> [!warning] Подводные камни
> - **Наследование ради переиспользования кода.** Самая частая причина плохих иерархий; общий код выносится в отдельный сервис или статический класс.
> - **Наследование от коллекций BCL.** `class Basket : List<Item>` отдаёт наружу весь API списка и делает невозможной смену внутреннего хранения.
> - **Наследник, ломающий подстановку.** Метод, бросающий `NotSupportedException`, — сигнал, что иерархия неверна.
> - **Глубина больше трёх уровней.** Понять поведение можно, только прочитав всю цепочку; отладка становится дорогой.
> - **`protected`-поля.** Прямой доступ потомков к состоянию базы фиксирует её реализацию навсегда.
> - **Классы без `sealed` по умолчанию.** Незапланированное наследование превращается в чью-то зависимость, а вместе с ней — в обязательство.
> - **Композиция без интерфейса.** Хранить конкретный тип внутри — уже лучше наследования, но подменить его в тестах по-прежнему нельзя.

> [!example] Как делают в бою
> В типичном .NET-сервисе наследование встречается в трёх местах: обязательные базовые классы фреймворка, базовые типы доменной модели (`Entity`, `ValueObject`, `AggregateRoot`) и шаблонный метод для семейства однотипных операций (импортёры, обработчики сообщений). Всё остальное — композиция через DI.
> Сквозное поведение оформляют декораторами или конвейерами: логирование, кеш, повторы, транзакции, валидация. В ASP.NET Core весь конвейер обработки запроса — это композиция middleware; в MediatR те же роли выполняют behaviors ([[MediatR и альтернативы]]).
> Классы по умолчанию `sealed`: если кому-то потребуется расширение, он попросит — и тогда точка расширения проектируется осознанно, а не появляется случайно. Заодно `sealed` помогает JIT девиртуализировать вызовы.
> Правило на ревью, которое ловит большинство ошибок: увидел новый базовый класс — спроси, что мешает сделать это зависимостью. Если ответа нет, значит наследование лишнее.

## Вопросы с собеседований

> [!question]- Почему рекомендуют предпочитать композицию наследованию?
> Потому что наследование создаёт самую жёсткую связь из возможных: наследник зависит не только от публичного контракта базы, но и от её внутреннего поведения — какой метод какой вызывает, в каком порядке, что защищено. Изменение базы, не меняющее её контракт, способно сломать потомков (проблема хрупкого базового класса). Кроме того, наследование фиксируется на этапе компиляции, не комбинируется (нужны логирование и кеш — получаем комбинаторный взрыв классов), расходует единственное наследование C# и ослабляет инкапсуляцию через `protected`-члены. Композиция связывает объекты через интерфейс: реализацию можно подменить, в том числе в рантайме, поведение собирается слоями (декораторы), а тестировать каждый элемент можно отдельно. Наследование остаётся правильным выбором там, где есть настоящее отношение «является», закрытая иерархия и общий алгоритм — типичный пример шаблонный метод.

> [!question]- Что такое проблема хрупкого базового класса?
> Ситуация, когда изменение реализации базового класса ломает наследников, хотя его публичный контракт не менялся. Классический пример: наследник переопределяет `Add` и `AddRange`, чтобы считать добавления; если в новой версии базы `AddRange` начинает вызывать `Add`, счётчик удваивается. Корень проблемы в том, что наследование раскрывает потомкам детали реализации: порядок внутренних вызовов, `protected`-члены, момент выполнения виртуальных методов. Из этого следуют практические правила: документировать, какие виртуальные члены и как вызываются внутри базы (именно это делает документация .NET для классов, рассчитанных на наследование); минимизировать число виртуальных и `protected`-членов; помечать классы `sealed` по умолчанию; предпочитать композицию, где связь ограничена публичным контрактом.

> [!question]- Приведи пример, когда наследование нарушает принцип подстановки Лисков.
> Классический — квадрат и прямоугольник. Кажется естественным сделать `Square : Rectangle`, но у прямоугольника ширина и высота независимы, а у квадрата нет: переопределённые сеттеры вынуждены менять оба поля. Код, написанный против `Rectangle` («установлю ширину 4 и высоту 5, ожидаю площадь 20»), с объектом `Square` получит 25 — подстановка нарушена. Причина не в геометрии, а в изменяемости: для иммутабельных типов проблема исчезает, потому что нет сеттеров, способных нарушить инвариант. Другие частые примеры: наследник, у которого часть методов бросает `NotSupportedException` (коллекция только для чтения, унаследованная от изменяемой), и наследник, ужесточающий предусловия — например, требующий не-null там, где база допускала null. Общий признак нарушения: клиентский код вынужден проверять фактический тип, чтобы работать правильно.

## Задачи

### Задача 1. Переписать иерархию

Есть базовый класс отправки уведомлений и три наследника, которые различаются только транспортом, но `EmailNotifier` дополнительно шифрует, а `SmsNotifier` — сокращает текст. Сейчас в базе появился `switch` по типу. Что делать?

> [!success]- Решение
> `switch` по типу наследника в базовом классе — верный признак того, что иерархия неверна: база знает о потомках, значит зависимость направлена в обе стороны. Разбираем на композицию.
> ```csharp
> public interface INotificationTransport
> {
>     Task SendAsync(string to, string text, CancellationToken ct);
> }
>
> public interface IMessagePreprocessor { string Process(string text); }
>
> public sealed class Truncate(int maxLength) : IMessagePreprocessor
> {
>     public string Process(string text) => text.Length <= maxLength ? text : text[..maxLength];
> }
>
> public sealed class Encrypt(IEncryptor encryptor) : IMessagePreprocessor
> {
>     public string Process(string text) => encryptor.Encrypt(text);
> }
>
> public sealed class NotificationSender(INotificationTransport transport,
>                                        IReadOnlyList<IMessagePreprocessor> preprocessors)
> {
>     public Task SendAsync(string to, string text, CancellationToken ct)
>     {
>         foreach (var p in preprocessors) text = p.Process(text);
>         return transport.SendAsync(to, text, ct);
>     }
> }
> ```
> Что изменилось: транспорт и обработка текста стали независимыми осями, и их можно комбинировать (SMS с сокращением, email с шифрованием, push без обработки) без создания класса на каждое сочетание. База больше не знает о вариантах, а добавление нового транспорта не требует правок в существующем коде — это и есть принцип открытости/закрытости. Набор препроцессоров задаётся при регистрации в DI, то есть меняется конфигурацией.

### Задача 2. Выбрать подход

Для каждого случая реши: наследование или композиция.
1. `AdminUser` и `RegularUser` с разными правами.
2. Репозиторий с кешированием поверх обычного.
3. Набор импортёров данных (CSV, XML, JSON) с общим алгоритмом «разобрать → проверить → сохранить».
4. Контроллер ASP.NET Core.
5. Класс, которому нужны методы форматирования дат из другого класса.

> [!success]- Решение
> 1. **Композиция.** «Админ» и «обычный» — это не разные типы пользователя, а разные наборы прав: одно поле `Roles` или объект `Permissions` внутри `User`. Наследование здесь фиксирует роль на этапе создания объекта, а роли меняются в рантайме — пользователя пришлось бы пересоздавать.
> 2. **Композиция (декоратор).** Кеширующий репозиторий реализует тот же интерфейс и хранит внутри «настоящий». Наследование связало бы его с конкретной реализацией, а декоратор работает с любой и включается регистрацией в DI.
> 3. **Наследование (шаблонный метод).** Общий алгоритм неотделим от процесса, набор шагов фиксирован, иерархия закрыта и своя. Абстрактный базовый класс с `abstract ParseAsync/ValidateAsync/SaveAsync` — правильная форма. Альтернатива на композиции (три интерфейса и оркестратор) тоже рабочая и даже гибче, если шаги нужно комбинировать.
> 4. **Наследование.** Выбора нет: этого требует фреймворк (`ControllerBase`). Собственную логику при этом всё равно выносят в сервисы, а не в базовый контроллер — иначе появляется `BaseController` с растущим набором утилит, от которого зависят все контроллеры.
> 5. **Ни то ни другое.** Наследоваться ради пары методов — худший вариант; композиция с хранением объекта-форматтера избыточна. Правильно — статический класс с методами расширения или отдельный сервис `IDateFormatter`, если форматирование зависит от культуры и настроек.

## Итог

- Наследование — «является», композиция — «содержит»; вторая связь слабее и меняется в рантайме.
- Хрупкий базовый класс: наследник зависит от внутреннего поведения базы, и её изменение ломает потомков.
- Наследование не комбинируется — отсюда комбинаторный взрыв классов; декораторы решают ту же задачу слоями.
- Наследование уместно при настоящем «является», закрытой иерархии и неотделимом общем алгоритме (шаблонный метод).
- Требование фреймворка (`ControllerBase`, `DbContext`) — законная причина наследоваться.
- Признаки ошибки: `new` вместо `override`, `NotSupportedException` в наследнике, `switch` по типу в базе, глубина больше трёх.
- Цена композиции — делегирование и больше типов; она окупается тестируемостью и свободой изменений.
- Классы по умолчанию `sealed`: расширение проектируется, а не случается.
