# Композиция vs наследование

> [!abstract] Коротко
> Наследование даёт подтип и вместе с ним виртуальную диспетчеризацию (`virtual`/`override`): вызов через ссылку базового типа уходит к реализации фактического типа. Но та же связь жёстко привязывает наследника к внутреннему устройству базы — изменение реализации базы, не трогающее её публичный контракт, тихо ломает потомков. Композиция даёт то же поведение через интерфейс и делегирование, без этой хрупкости. Отсюда правило индустрии «предпочитай композицию наследованию»: не запрет, а порядок вопросов — сначала спроси, можно ли обойтись зависимостью.

## Зачем это знать

Выбор между наследованием и композицией — решение до кода: от него зависит, можно ли комбинировать поведения (логирование + кеш + повтор), можно ли подменить часть системы в тестах и переживёт ли код рефакторинг базового класса без падения в проде. Ошибка не ловится компилятором: иерархия компилируется и работает до тех пор, пока кто-то не поменяет деталь реализации базы. Отдельно — `new` вместо `override`: код компилируется, тесты через переменную точного типа зелёные, а через переменную базового типа (а DI почти всегда так и делает) вызывается не то поведение.

## Модель

### Наследование даёт три вещи разом

Под одним двоеточием в C# скрыты три разные задачи:

1. **Подтипизация** — «`Dog` можно подставить, где ожидают `Animal`». Единственное, что реально нужно в большинстве случаев.
2. **Переиспользование реализации** — «не писать эти сорок строк снова».
3. **Дифференциальное программирование** — «взять и поменять одну деталь».

Наследование выдаёт все три сразу, вместе с зависимостью от внутренностей базы, которую пункт 1 сам по себе не требует. Композиция даёт ровно пункт 2 (через делегирование) и пункт 1 (через интерфейс) — без цены пункта 3.

### Виртуальная диспетчеризация: как решается вызов

У каждого объекта в куче есть указатель на таблицу методов (method table) его **фактического** типа. Невиртуальный член компилятор разрешает статически и вызывает напрямую (`call`). Виртуальный — косвенно (`callvirt`): адрес метода читается из таблицы фактического типа объекта, а не из типа переменной.

```csharp
public class Animal
{
    public virtual string Speak() => "...";
    public string Kind() => "Animal";          // невиртуальный
}
public sealed class Dog : Animal
{
    public override string Speak() => "Гав";   // ЗАМЕНЯЕТ слот в таблице
    public new string Kind() => "Dog";         // ПРЯЧЕТ, отдельный метод
}

Animal a = new Dog();
Console.WriteLine(a.Speak());   // Гав  — вызов идёт по таблице фактического типа
Console.WriteLine(a.Kind());    // Animal — решает СТАТИЧЕСКИЙ тип переменной
```

### `override` против `new` — разница, которая стоит багов

| | `override` | `new` |
|---|---|---|
| Требует | `virtual`/`abstract` в базе | ничего, работает и для невиртуальных |
| Что делает | заменяет слот в таблице методов | создаёт независимый член с тем же именем |
| Кто решает вызов | фактический тип объекта, в рантайме | статический тип переменной, на компиляции |
| Через `Base b = derived; b.M()` | вызовется версия `derived` | вызовется версия `Base` |

`new` без явного намерения — почти всегда следствие забытого `virtual` в базе: компилятор выдаёт предупреждение CS0108 («член скрывает унаследованный, добавьте `new`, если это намеренно»), кто-то дописывает `new`, не разобравшись, и получает метод, который «есть, но не вызывается».

```csharp
public class Repository
{
    public void Save(Order order) { /* базовое сохранение */ }
}
public class AuditingRepository : Repository
{
    public new void Save(Order order)          // забыли virtual в Repository
    {
        _log.Information("Аудит {Id}", order.Id);
        base.Save(order);
    }
}

Repository repo = new AuditingRepository();    // так приходит из DI почти всегда
repo.Save(order);                              // аудита НЕТ — вызвалась версия Repository
```

Ничего не падает, компилятор молчит после `new`, юнит-тест, написанный через `new AuditingRepository().Save(...)`, зелёный. Ломается только прод, где объект приходит через интерфейс или базовый тип. Здесь и теряется полиморфизм: `new` — не «переопределение для невиртуальных членов», а два разных метода с одним именем, и выбор между ними не зависит от того, чем объект является на самом деле.

### Где кончается полиморфизм: перегрузки, extension-методы, конструктор

Ещё три места, где ожидание «сработает как виртуальный вызов» ломается:

- **Перегрузки** (`Handle(object)` / `Handle(string)`) разрешаются на компиляции по статическому типу аргумента, не по рантайм-типу значения — это не про наследование, но путают часто.
- **Extension-методы** не участвуют в диспетчеризации вообще: они разрешаются по статическому типу выражения, метод расширения для `Dog` не «переопределяет» метод расширения для `Animal`.
- **Виртуальный вызов из конструктора базы** уходит в переопределение наследника, но поля наследника (включая `readonly`) на этот момент ещё не инициализированы — типичный итог `NullReferenceException` или тихо неверная инициализация. Правило: не вызывать виртуальные члены из конструкторов, точку расширения при создании выносить в фабрику.

### Fragile base class problem

Наследник зависит не только от контракта базы, но и от того, какие свои методы база вызывает внутри себя:

```csharp
public class Bag<T>
{
    private readonly List<T> _items = [];
    public virtual void Add(T item) => _items.Add(item);
    public virtual void AddRange(IEnumerable<T> items)
    {
        foreach (var item in items) Add(item);      // самовызов — не часть контракта
    }
}
public class CountingBag<T> : Bag<T>
{
    public int AddedCount { get; private set; }
    public override void Add(T item) { AddedCount++; base.Add(item); }
}
```

Работает, пока `AddRange` вызывает `Add`. Стоит автору `Bag<T>` заменить цикл на `_items.AddRange(items)` — оптимизация, не меняющая публичный контракт, — счётчик наследника молча перестаёт расти. Тесты `Bag<T>` зелёные, компилятор молчит, метрика в проде показывает ноль. Композиция (обёртка, хранящая `Bag<T>` полем и видящая только его публичный API) такой зависимости не имеет в принципе.

### Нарушение LSP: почему это про поведение, а не про предметную область

```csharp
public class Rectangle { public virtual int Width { get; set; } public virtual int Height { get; set; } }
public class Square : Rectangle       // «квадрат — это прямоугольник»
{
    public override int Width  { set { base.Width = base.Height = value; } }
    public override int Height { set { base.Width = base.Height = value; } }
}
static void Resize(Rectangle r) { r.Width = 4; r.Height = 5; }
// Rectangle → площадь 20. Square → площадь 25: код, написанный против базы, ломается.
```

Геометрически квадрат — прямоугольник, спорить не с чем. Проблема в том, что `Rectangle` изменяемый, и его неявный контракт включает постусловие «после `Width = w` высота не меняется» — `Square` его нарушает. Для иммутабельных типов (`record`, фабрика `Shapes.Square(side)`) проблема исчезает: квадрат становится способом создать прямоугольник, а не подтипом.

## Решения

| Ситуация | Выбор | Почему |
|---|---|---|
| Нужно комбинировать поведения (лог + кеш + повтор) | Композиция (декораторы) | Наследование даёт `LoggingCachingRetryingRepository` — комбинаторный взрыв классов; декораторы — три независимых слоя в любом порядке |
| Наследник переопределяет почти всё, база часто меняется | Композиция | Каждое изменение базы рискует задеть самовызовы — fragile base class |
| Отношение реально «является», иерархия закрыта, общий код неотделим от алгоритма | Наследование (шаблонный метод) | Общий каркас плюс абстрактные точки расширения — ровно то, для чего наследование хорошо подходит |
| Требование фреймворка (`ControllerBase`, `DbContext`, `BackgroundService`, `Exception`) | Наследование | Выбора нет; собственную логику всё равно выносят в сервисы, а не в базовый класс |
| Закрытый набор вариантов для `switch`/pattern matching (`Result`: `Success`/`NotFound`/`Invalid`) | Наследование (`abstract record`) | Иерархия существует ради сопоставления с образцом, не ради переиспользования кода |
| Нужны методы форматирования/утилиты из другого класса | Ни то ни другое | Статический класс или отдельный сервис — наследование ради пары методов и композиция ради них же одинаково избыточны |
| Реализации меняются в рантайме или подменяются в тестах | Композиция (интерфейс) | Наследование фиксирует поведение на этапе компиляции |

Признаки, что наследование выбрано ошибочно: `new` вместо `override`; в базе появился `switch` по типу наследника; наследник бросает `NotSupportedException` на части методов; иерархия глубже трёх уровней; наследование ради пары вспомогательных методов.

> [!example] В ServiceShop
> `BuildingBlocks.Domain/Entity.cs` — абстрактный базовый класс, а не интерфейс: у всех сущностей общее состояние (идентификатор, список доменных событий) и общий код (`Equals`/`GetHashCode` по идентификатору, `Raise`/`ClearEvents`). Это законный случай наследования: отношение «является сущностью» настоящее, иерархия закрыта в `BuildingBlocks`, общий код неотделим от понятия идентификатора.
> Командные хендлеры, наоборот, идут через композицию и интерфейс: `*CommandHandler` реализует `ICommandHandler<TCommand, TResult>` из `Configuration/Commands/ICommandHandler.cs`, а не наследует общий базовый класс с утилитами — MediatR резолвит нужный обработчик по типу команды, и добавление нового хендлера не требует правок в существующих.
> Конструкторы агрегатов — правило проекта: только `private`, создание через `static Create(...)`. Это защищает инварианты в момент создания и не даёт наследникам обойти бизнес-правила через `base(...)` — ещё одна причина, по которой агрегаты в модулях не образуют глубоких иерархий.

> [!warning] Где ошибаются
> - **`new` вместо `override`.** Компилятор предупредил (CS0108), предупреждение проигнорировали. Метод «есть», но не вызывается через переменную базового типа — а DI почти всегда работает именно через базовый тип или интерфейс.
> - **Наследование от коллекций BCL.** `class Basket : List<Item>` тащит наружу весь API списка, включая операции, ломающие инвариант («доступ только с вершины», «нельзя вставить в середину»).
> - **Fragile base class без документированных самовызовов.** Если наследование всё же нужно, самовызовы — часть контракта наравне с сигнатурами (так `Collection<T>` в BCL обещает, что все мутации идут через `InsertItem`/`SetItem`/`RemoveItem`/`ClearItems`).
> - **Виртуальный вызов из конструктора.** Наследник получает объект в промежуточном состоянии — поля ещё не инициализированы.
> - **Классы без `sealed` по умолчанию.** Незапланированное наследование становится чьей-то зависимостью и обязательством поддерживать порядок внутренних вызовов.
> - **Агент часто:** предлагает базовый класс с общими методами по привычке из учебных примеров («три сервиса делают похожее — вынесем в `BaseService`») там, где нужна композиция или интерфейс с внедрённой зависимостью.
> - **Агент часто:** генерирует `new` для «исправления» предупреждения о скрытии члена, вместо того чтобы добавить `virtual` в базу или спросить, нужен ли вообще этот метод в наследнике.
> - **Агент часто:** наследует от `List<T>`/`Dictionary<TKey,TValue>` для доменного типа, потому что это «быстрее, чем описывать нужные методы», — и выдаёт наружу весь API коллекции.

## Проверка на ревью

- Новый `class X : Y` — задан ли вопрос «подставлю ли я `X` там, где ожидается `Y`»; если ответ «нет», это композиция, а не наследование.
- `new` перед членом в диффе — забытый `virtual` в базе или намеренное скрытие с комментарием; без комментария — на доработку.
- Базовый класс с одним наследником «на будущее» — есть ли общее состояние и общий алгоритм или это просто утилиты, которые проще вынести в сервис.
- Виртуальный член, вызываемый из конструктора, — прямой кандидат на `NullReferenceException` у наследника.
- Глубина иерархии больше трёх уровней — сигнал искать композицию.
- `protected`-поле в базе — доступ к состоянию, который любой рефакторинг базы способен сломать; предпочтителен `protected` метод.

## Проверь себя

> [!question]- Чем `override` отличается от `new` и почему вторая половина отличия важна на практике?
> `override` заменяет слот в таблице виртуальных методов: вызов разрешается в рантайме по фактическому типу объекта, поэтому через ссылку любого базового типа выполнится версия наследника. `new` создаёт независимый метод, который не участвует в диспетчеризации — какой из двух вызовется, решается на компиляции по статическому типу переменной. Практическое следствие: `Base b = new Derived(); b.M();` вызовет `Derived.M()` при `override` и `Base.M()` при `new`, хотя объект один и тот же. Поскольку DI почти всегда передаёт зависимость через базовый тип или интерфейс, ошибочный `new` означает, что переопределение молча не работает именно в проде, а не в тесте, написанном через точный тип.

> [!question]- Что такое fragile base class problem и как композиция её снимает?
> Ситуация, когда изменение реализации базового класса, не меняющее его публичный контракт, ломает наследников, потому что они зависели от того, какие свои методы база вызывает внутри себя (self-call pattern). Классика — `AddRange`, вызывающий `Add` в цикле: наследник переопределяет `Add`, чтобы считать вставки, а после безобидной оптимизации базы счётчик молча перестаёт расти. Композиция снимает проблему структурно: обёртка, хранящая объект базы полем, видит только его публичный API и не может зависеть от внутренних самовызовов, которых у неё просто нет в поле зрения.

> [!question]- Пример с Rectangle и Square — про геометрию или про что-то другое?
> Не про геометрию — квадрат действительно является прямоугольником, спорить не с чем. Проблема в том, что `Rectangle` сделан изменяемым, и его неявный контракт содержит постусловие: после присваивания `Width` значение `Height` не меняется. `Square`, синхронизирующий стороны, это постусловие нарушает, и код, написанный против `Rectangle`, получает неожиданный результат. LSP — про поведение (пред-/постусловия, инварианты, исключения), а не про то, как объекты соотносятся в реальном мире. Для иммутабельных типов проблема исчезает: без сеттеров нет постусловия, которое можно нарушить, и квадрат превращается в фабричный метод, а не в подтип.

> [!question]- Когда наследование всё-таки оправдано, а не запрещено правилом «предпочитай композицию»?
> Когда одновременно верны три условия: отношение действительно «является», иерархия закрыта и контролируется тобой, а общий код неотделим от алгоритма — типичный случай шаблонный метод. Отдельно легитимны требования фреймворка (`ControllerBase`, `DbContext`, `Exception`) и закрытые наборы вариантов для сопоставления с образцом (`abstract record Result` с наследниками `Success`/`NotFound`). Правило «предпочитай композицию» не запрещает наследование, оно меняет порядок вопросов: сначала проверить, не решается ли задача зависимостью, и только при явном «нет» наследоваться осознанно.

> [!question]- Почему extension-методы и перегрузки — тоже места, где ломаются ожидания от полиморфизма?
> Оба разрешаются на этапе компиляции по статическому типу, а не в рантайме по фактическому типу объекта, как виртуальные вызовы. Extension-метод для `Animal`, вызванный на переменной типа `Animal`, отработает, даже если объект на самом деле `Dog` и для `Dog` есть свой extension-метод — выбор делает тип выражения, а не значение. Перегрузки `Handle(object)`/`Handle(string)` ведут себя так же: вызов на `object arg = "текст"` выберет `Handle(object)`, потому что компилятор смотрит на объявленный тип переменной. Смешение этой статической логики с рантайм-диспетчеризацией виртуальных членов — частый источник «метод не вызвался, хотя я его написал».

## Разбор

**Дан фрагмент — найди проблему.**

```csharp
public class Notifier
{
    public virtual void Notify(string message) => Send(Format(message));
    public virtual void NotifyAll(IEnumerable<string> messages)
    {
        foreach (var m in messages) Notify(m);
    }
    protected virtual string Format(string m) => m;
    protected virtual void Send(string m) => Console.WriteLine(m);
}
```

Наследники регулярно ломаются при рефакторинге `Notifier`. Почему, и как перепроектировать точки расширения?

> [!success]- Решение
> `NotifyAll` вызывает публичный виртуальный `Notify`, а не внутренний `Send`/`Format` напрямую — значит наследник, переопределивший `Notify` (например, добавивший логирование), незаметно меняет и поведение `NotifyAll`, хотя не трогал его. Это тот же класс проблем, что и fragile base class: контракт для наследника фактически включает «какой метод кого вызывает».
> ```csharp
> public abstract class Notifier
> {
>     public void Notify(string message) => Send(Format(message));         // не виртуальный
>     public void NotifyAll(IEnumerable<string> messages)
>     {
>         foreach (var m in messages) Send(Format(m));                     // не через Notify
>     }
>     protected abstract void Send(string formatted);
>     protected virtual string Format(string raw) => raw;
> }
> ```
> Скелет алгоритма (`Notify`/`NotifyAll`) больше не виртуальный — наследник не может его подменить, значит база вправе менять реализацию без риска. Точек расширения ровно две, они `protected` и не участвуют в самовызовах друг друга. Это шаблонный метод в правильной форме.

**Дано два решения — обоснуй выбор.**

Нужны три канала уведомлений (email, SMS, push) с общей проверкой получателя и логированием, но разной отправкой. Решение A — абстрактный `NotificationChannel` с шаблонным методом `SendAsync`. Решение B — интерфейс `INotificationChannel` плюс декоратор `LoggingNotificationChannel`.

> [!success]- Решение
> Оба рабочие, выбор зависит от объёма и связности общего кода. Решение A уместно, если проверка и логирование неотделимы от алгоритма отправки и не будут комбинироваться в других сочетаниях — общий код фиксирован, наследники `sealed`, слот наследования не нужен ни для чего другого. Решение B лучше, если логирование — сквозное поведение, которое захочется применить и к другим типам (репозитории, HTTP-клиенты), или если позже понадобится добавить ещё слой (метрики, повтор) — декораторы комбинируются, наследование добавляет только новый уровень иерархии на каждый слой. На практике в ServiceShop сквозные вещи (логирование, повтор, кеш) собираются композицией через DI-регистрацию, а наследование остаётся для доменных базовых типов вроде `Entity`.

## Итог

- Наследование = подтипизация + переиспользование реализации + дифференциальное программирование одним двоеточием; в подавляющем большинстве случаев нужна только первая часть.
- Виртуальная диспетчеризация решает вызов по фактическому типу объекта в рантайме (`callvirt`); `override` встраивается в этот механизм, `new` — нет, он создаёт второй метод, разрешаемый статически.
- `new` без явного намерения — почти всегда забытый `virtual` в базе; DI передаёт объект через базовый тип, и там теряется именно та реализация, которую ожидали вызвать.
- Fragile base class: наследник зависит от недокументированных самовызовов базы, а не только от её публичного контракта — композиция такой зависимости не создаёт.
- LSP нарушается не предметной областью, а изменяемостью типа: иммутабельность убирает постусловия, которые можно нарушить.
- Наследование остаётся правильным выбором при настоящем «является», закрытой иерархии, неотделимом общем алгоритме и требованиях фреймворка — во всех остальных случаях по умолчанию берут композицию.
