# Абстрактные классы

> [!abstract] Коротко
> Абстрактный класс — незавершённый тип: его нельзя создать через `new`, он существует только как база для наследников. Смысл в том, чтобы отдать наследникам **часть** реализации (общий код, состояние, конструктор) и потребовать реализовать остальное — члены, помеченные `abstract`. Это отличает его от интерфейса, который задаёт контракт без состояния. Практический выбор: абстрактный класс — когда у вариантов есть общий код и общее состояние; интерфейс — когда нужен только контракт, а реализации ничем не связаны.

## Зачем это нужно

Ситуация, из которой вырастает абстрактный класс: у нескольких типов один алгоритм и разные детали.

```csharp
public abstract class ImportJob(ILogger logger)
{
    // Общий алгоритм — здесь, и он одинаков для всех наследников
    public async Task<ImportResult> RunAsync(Stream source, CancellationToken ct)
    {
        var started = DateTimeOffset.UtcNow;
        logger.LogInformation("Импорт {Job} начат", Name);

        var rows = await ParseAsync(source, ct);          // деталь наследника
        var valid = rows.Where(IsValid).ToList();          // деталь наследника
        await SaveAsync(valid, ct);                        // деталь наследника

        logger.LogInformation("Импорт {Job} завершён за {Elapsed}", Name, DateTimeOffset.UtcNow - started);
        return new ImportResult(rows.Count, valid.Count);
    }

    protected abstract string Name { get; }
    protected abstract Task<IReadOnlyList<ImportRow>> ParseAsync(Stream source, CancellationToken ct);
    protected abstract Task SaveAsync(IReadOnlyList<ImportRow> rows, CancellationToken ct);
    protected virtual bool IsValid(ImportRow row) => true;    // разумное умолчание
}
```

Наследнику остаётся написать три метода — порядок шагов, логирование и замер времени он не может ни забыть, ни испортить. Это паттерн «Шаблонный метод» (Template Method), и абстрактный класс — его естественная форма.

## Механика

```csharp
public abstract class Shape
{
    protected Shape(string name) => Name = name;    // конструктор есть, но вызывается только наследником

    public string Name { get; }                      // обычный член с реализацией
    public abstract double Area { get; }             // абстрактное свойство — обязательно к реализации
    public abstract double Perimeter();              // абстрактный метод — тела нет
    public virtual string Describe() => $"{Name}: площадь {Area:F2}";   // можно переопределить
}

public sealed class Circle(double radius) : Shape("круг")
{
    public override double Area => Math.PI * radius * radius;
    public override double Perimeter() => 2 * Math.PI * radius;
}

// var s = new Shape("что-то");     // Ошибка CS0144: нельзя создать экземпляр абстрактного класса
Shape shape = new Circle(2);         // но переменная абстрактного типа — норма
Console.WriteLine(shape.Describe());
```

Правила:

- **Создать нельзя**, но можно объявить переменную и параметр такого типа — в этом весь смысл.
- **Конструктор нужен и работает**: он вызывается из конструктора наследника. Модификатор — `protected` (публичный конструктор у абстрактного класса бессмысленен, компилятор его допускает, но анализаторы ругаются).
- **Абстрактный член неявно виртуальный**, `virtual` писать нельзя. Он не может быть `private` — реализовать его было бы некому.
- **Абстрактные члены** бывают у методов, свойств, индексаторов и событий; полей и конструкторов — нет.
- Абстрактный класс **может не иметь абстрактных членов вовсе** — тогда он просто запрещает создание экземпляров базового типа.
- Наследник, не реализовавший все абстрактные члены, сам обязан быть `abstract`.

```csharp
public abstract class Middle : Shape          // промежуточный класс может отложить реализацию
{
    protected Middle() : base("промежуточный") { }
    public override double Area => 0;          // часть реализовал
    // Perimeter() остался абстрактным — поэтому класс тоже abstract
}
```

### `abstract override` и `sealed override`

```csharp
public abstract class Base { public virtual string Format() => "база"; }

public abstract class Middle2 : Base
{
    public abstract override string Format();     // сделали обязательным для дальнейших наследников
}

public sealed class Leaf : Middle2
{
    public sealed override string Format() => "лист";   // sealed здесь избыточен: класс и так sealed
}
```

`abstract override` — приём, которым промежуточный класс «отменяет» реализацию по умолчанию и заставляет каждого конкретного наследника определиться.

## Абстрактный класс или интерфейс

Начиная с C# 8 у интерфейсов появились реализации по умолчанию, и граница размылась. Актуальное сравнение:

| | Абстрактный класс | Интерфейс |
|---|---|---|
| Состояние (поля) | да | нет (только статические) |
| Конструктор | да | нет |
| Множественное наследование | нет, только один базовый класс | да, сколько угодно |
| Реализация по умолчанию | да | да (C# 8+, с оговорками) |
| Модификаторы доступа у членов | любые | по умолчанию `public`, есть и другие |
| Реализация значимыми типами | нет | да (`struct`, `record struct`) |
| Добавить член без ломки наследников | да (невиртуальный или виртуальный) | да, если с реализацией по умолчанию |
| Отношение | «является» (is-a) | «умеет» (can-do) |

Практические критерии выбора:

**Абстрактный класс**, если: есть общее **состояние** (поля, зависимости через конструктор); общего кода много и он неотделим от алгоритма; нужен контроль над тем, что наследник **не может** переопределить (невиртуальные члены); варианты действительно являются разновидностями одного понятия.

**Интерфейс**, если: нужен только контракт; реализации не связаны между собой и могут иметь свои иерархии; тип должен реализовать несколько контрактов; контракт нужен структурам; тип будет подставляться через DI и подменяться в тестах.

**Оба сразу** — частая и правильная комбинация: интерфейс как публичный контракт, абстрактный класс как удобная база для типовых реализаций.

```csharp
public interface INotificationChannel                     // контракт для потребителей и DI
{
    Task SendAsync(string to, string text, CancellationToken ct);
}

public abstract class NotificationChannelBase(ILogger logger) : INotificationChannel   // общая обвязка
{
    public async Task SendAsync(string to, string text, CancellationToken ct)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(to);
        logger.LogInformation("Отправка через {Channel}", GetType().Name);
        await DeliverAsync(to, text, ct);
    }

    protected abstract Task DeliverAsync(string to, string text, CancellationToken ct);
}
```

Потребители зависят от интерфейса, а базовый класс остаётся деталью реализации, которую можно и не использовать.

### Почему реализации по умолчанию в интерфейсах не заменяют абстрактные классы

Реализация по умолчанию (`default interface member`, C# 8) добавлялась ради версионирования библиотек: она позволяет расширить интерфейс, не сломав существующие реализации. Но:

- у интерфейса нет полей, значит нет и состояния — только статические члены;
- метод по умолчанию не виден через ссылку на конкретный класс, только через интерфейс (это неявная реализация, вызывающая путаницу);
- нет конструктора, значит нет и контролируемой инициализации.

Поэтому «общий код с состоянием» по-прежнему живёт в абстрактных классах, а реализации по умолчанию используют точечно — для расширения контрактов и адаптеров ([[Интерфейсы]]).

## Когда абстрактный класс не нужен

Соблазн «сделаю базовый класс, вдруг пригодится» приводит к иерархиям, которые мешают. Признаки, что абстрактный класс лишний:

- у него один наследник (и не планируется второй) — это лишний уровень косвенности;
- «общий код» — это набор вспомогательных методов без состояния: их место в статическом классе или отдельном сервисе;
- наследники переопределяют почти всё, включая то, что задумывалось общим, — значит, общего у них нет;
- базовый класс знает о наследниках (например, `switch` по `GetType()` внутри) — иерархия построена неверно;
- нужен только контракт для DI и тестов — достаточно интерфейса.

Альтернатива почти всегда одна и та же: композиция плюс интерфейс. Вместо наследования от `RepositoryBase` — внедрение `IDbConnectionFactory`; вместо `ServiceBase` с логированием — декоратор ([[Композиция vs наследование]]).

> [!warning] Подводные камни
> - **Виртуальный вызов из конструктора базы.** Метод наследника выполнится до инициализации его полей — см. [[Полиморфизм: virtual, override, new]].
> - **Публичный конструктор у абстрактного класса.** Создать объект всё равно нельзя, но контракт выглядит обманчиво; нужен `protected`.
> - **Глубокая иерархия (3+ уровня).** Чтобы понять поведение, приходится читать всю цепочку; тестировать промежуточные уровни неудобно.
> - **`protected`-поля.** Наследники получают прямой доступ к состоянию базы, и любой рефакторинг базы ломает их. Лучше `private` поле плюс `protected`-метод.
> - **Абстрактный класс вместо интерфейса в публичном API.** Потребитель тратит своё единственное наследование и уже не может унаследоваться от чего-то ещё.
> - **Общий код «на всякий случай».** База, у которой один наследник, — почти всегда преждевременное обобщение.
> - **Абстрактный класс как замена DI.** Наследование ради доступа к сервисам (`protected ILogger Logger`) связывает типы жёстче, чем внедрение зависимостей.

> [!example] Как делают в бою
> В типичном .NET-сервисе абстрактных классов немного, и они выполняют одну из трёх ролей. Первая — шаблонный метод для семейства однотипных операций: импортёры, обработчики сообщений, экспортёры отчётов, где общий алгоритм с логированием, замером времени и обработкой ошибок вынесен в базу. Вторая — базовый тип доменной модели: `Entity` с идентификатором и равенством по нему, `ValueObject` с равенством по компонентам, `AggregateRoot` со списком доменных событий. Третья — базовый класс из фреймворка, который приходится наследовать: `ControllerBase`, `DbContext`, `BackgroundService`.
> Всё остальное строится на интерфейсах и композиции: так проще подменять реализации в тестах, регистрировать в DI и оборачивать декораторами. Правило, которое стоит держать: наследование добавляется, когда общий код **уже** продублирован дважды и его нельзя вынести в отдельный сервис, — а не заранее.

## Вопросы с собеседований

> [!question]- Чем абстрактный класс отличается от интерфейса?
> Абстрактный класс может иметь состояние (поля), конструктор, члены с любыми модификаторами доступа и невиртуальные члены, которые наследник не может переопределить; наследоваться от него можно только от одного. Интерфейс задаёт контракт, не имеет полей и конструктора, реализовать его можно сколько угодно раз и в том числе структурами. С C# 8 интерфейс умеет содержать реализации по умолчанию, но это не делает его заменой абстрактного класса: без состояния и конструктора общий код с инициализацией туда не переносится, а члены по умолчанию доступны только через ссылку на интерфейс. Смысловая разница: наследование от абстрактного класса выражает «является разновидностью», реализация интерфейса — «умеет делать». На практике часто применяют оба сразу: интерфейс как публичный контракт для DI и тестов, абстрактный класс как необязательная база с общим кодом.

> [!question]- Можно ли создать экземпляр абстрактного класса и зачем ему конструктор?
> Напрямую нельзя — `new AbstractType()` не компилируется, потому что часть реализации отсутствует. Но переменные, параметры и поля такого типа объявлять можно и нужно, и через них работают с объектами наследников — в этом и состоит смысл. Конструктор абстрактному классу необходим: он инициализирует состояние базовой части объекта и вызывается из конструктора наследника явным или неявным `base(...)`. Объявляют его `protected`, потому что вызывать его может только наследник; публичный конструктор компилируется, но вводит в заблуждение. Отдельная тонкость — порядок выполнения: инициализаторы полей наследника, затем конструктор базы, затем тело конструктора наследника, поэтому вызывать виртуальные методы из конструктора базы опасно.

> [!question]- Когда стоит выбрать абстрактный класс, а не интерфейс?
> Когда у вариантов есть общее состояние и общий код, который является частью алгоритма, а не просто набором утилит. Типичный признак — шаблонный метод: публичный невиртуальный метод в базе задаёт последовательность шагов и гарантирует обязательные действия (валидацию, логирование, замер), а наследники реализуют только абстрактные шаги. Второй признак — необходимость контролировать, что наследник **не может** переопределить: у интерфейса такой возможности нет. Третий — общая инициализация через конструктор. Если же нужен только контракт, если реализации не связаны между собой, если тип должен реализовать несколько контрактов или быть структурой, или если он подставляется через DI и подменяется в тестах, — правильный выбор интерфейс. И стоит помнить об ограничении: наследование одно, и абстрактный класс в публичном API забирает его у потребителя.

## Задачи

### Задача 1. Найти лишнюю абстракцию

```csharp
public abstract class RepositoryBase
{
    protected readonly AppDbContext Db;
    protected RepositoryBase(AppDbContext db) => Db = db;
    protected string ConnectionInfo => Db.Database.GetConnectionString() ?? "";
}

public sealed class OrderRepository : RepositoryBase
{
    public OrderRepository(AppDbContext db) : base(db) { }
    public Task<Order?> FindAsync(long id, CancellationToken ct) => Db.Orders.FindAsync([id], ct).AsTask();
}
```

Стоит ли здесь базовый класс?

> [!success]- Решение
> Нет. База не даёт ни общего алгоритма, ни поведения — только хранит зависимость, которую наследник и так мог бы получить через конструктор. Взамен она забирает у `OrderRepository` возможность наследоваться от чего-то ещё, делает `Db` доступным всем будущим наследникам как `protected`-поле (то есть частью контракта) и добавляет уровень, который придётся читать при разборе кода.
> ```csharp
> public sealed class OrderRepository(AppDbContext db) : IOrderRepository
> {
>     public Task<Order?> FindAsync(long id, CancellationToken ct) => db.Orders.FindAsync([id], ct).AsTask();
> }
> ```
> Первичный конструктор из C# 12 убирает даже поле. Интерфейс `IOrderRepository` нужен для DI и тестов; общий код, если он появится (например, применение спецификаций или пагинация), лучше вынести в статический класс расширений над `IQueryable<T>` — им смогут пользоваться все репозитории без наследования.

### Задача 2. Спроектировать базу для доменных сущностей

Нужен базовый тип для сущностей: идентификатор, равенство по идентификатору, список доменных событий.

> [!success]- Решение
> ```csharp
> public abstract class Entity<TId> : IEquatable<Entity<TId>> where TId : notnull
> {
>     private readonly List<IDomainEvent> _events = [];
>
>     protected Entity(TId id) => Id = id;
>     protected Entity() { }                        // для материализации ORM
>
>     public TId Id { get; protected init; } = default!;
>
>     public IReadOnlyList<IDomainEvent> DomainEvents => _events;
>     protected void Raise(IDomainEvent e) => _events.Add(e);
>     public void ClearEvents() => _events.Clear();
>
>     public bool Equals(Entity<TId>? other)
>         => other is not null && GetType() == other.GetType() && Id.Equals(other.Id);
>
>     public override bool Equals(object? obj) => Equals(obj as Entity<TId>);
>     public override int GetHashCode() => HashCode.Combine(GetType(), Id);
> }
> ```
> Здесь абстрактный класс оправдан: есть состояние (идентификатор и список событий), общий код (равенство, накопление событий) и точки контроля — `Raise` доступен только наследникам, `_events` наружу отдаётся как `IReadOnlyList<T>`.
> Важные детали: сравнение типов через `GetType()` не даёт считать равными сущности разных классов с одинаковым идентификатором; `GetHashCode` согласован с `Equals` и включает тип; параметр `TId` ограничен `notnull`, чтобы идентификатор нельзя было забыть. Конструктор без параметров нужен ORM для материализации и потому `protected`. Подробнее о правилах равенства — [[Object: Equals, GetHashCode, ToString]] и [[DDD: тактические паттерны]].

## Итог

- Абстрактный класс нельзя создать; он существует, чтобы отдать наследникам часть реализации и потребовать остальное.
- Абстрактный член неявно виртуальный, не может быть `private`; наследник обязан реализовать все или сам быть абстрактным.
- Конструктор нужен и объявляется `protected`; виртуальные вызовы из него опасны.
- Основной сценарий — шаблонный метод: алгоритм в базе, детали в наследниках, обязательные шаги неотключаемы.
- Абстрактный класс — при наличии общего состояния и кода; интерфейс — когда нужен контракт; часто применяют оба.
- Реализации по умолчанию в интерфейсах не заменяют абстрактные классы: нет полей и конструктора.
- База с одним наследником, `protected`-поля и глубокие иерархии — признаки лишней абстракции.
