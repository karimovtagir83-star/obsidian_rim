# Компиляция, интерпретация и виртуальные машины

> [!abstract] Коротко
> Процессор понимает только машинный код. Компилятор — программа, которая переводит текст на языке в что-то исполнимое: либо сразу в машинный код (C, Rust, Go), либо в промежуточное представление, которое потом доводит до машинного кода рантайм (C#, Java, Kotlin). C# идёт вторым путём: `csc` (Roslyn) переводит исходники в IL и кладёт его в `.dll`, а при запуске JIT-компилятор превращает IL в машинный код того процессора, на котором мы оказались. Отсюда и переносимость, и «первый запрос медленный», и возможность рефлексии.

## Зачем это нужно

Без этой модели непонятны вещи, с которыми сталкиваешься на первой же неделе:

- почему собранная программа — это `.dll`, а не `.exe`, и почему её запускают командой `dotnet myapp.dll`;
- почему первый HTTP-запрос к свежеподнятому сервису отвечает за 300 мс, а следующие — за 3 мс;
- почему на машине нужен «SDK», а на сервере хватает «runtime», и в чём разница;
- почему в C# можно узнать типы во время выполнения (рефлексия), а в C++ — почти нет;
- почему код на C# в тесном цикле бывает так же быстр, как C++, но при этом «медленно стартует»;
- что вообще значит Native AOT и почему его вспоминают рядом со словом «серверлесс».

## Что делает компилятор

Компилятор — не «переводчик слово в слово», а конвейер из нескольких фаз:

```
исходный текст
   │
   ├─ 1. Лексический анализ  →  поток токенов
   │      "int x = 5;"  →  [KeywordInt][IdentifierX][Equals][Number5][Semicolon]
   │
   ├─ 2. Синтаксический анализ  →  дерево разбора (AST)
   │      проверка: конструкции сложены по правилам грамматики
   │
   ├─ 3. Семантический анализ  →  типизированное дерево + таблица символов
   │      проверка: типы совпадают, имена существуют, нет обращения
   │      к неинициализированной переменной
   │
   ├─ 4. Промежуточное представление и оптимизации
   │      constant folding, устранение мёртвого кода, inlining
   │
   └─ 5. Генерация кода  →  машинный код или байт-код
```

Ошибки, которые ты видишь в IDE, приходят с разных фаз, и это подсказка, где искать причину: «; expected» — фаза 2, «cannot convert int to string» — фаза 3, «unreachable code» — фаза 4 (предупреждение оптимизатора).

В C# фазы 1–3 выполняет **Roslyn** — компилятор C# и VB, сам написанный на C# и доступный как библиотека. Именно поэтому IDE подсвечивает ошибки на лету, а рефакторинги и анализаторы работают на настоящем дереве кода, а не на регулярных выражениях (см. [[Roslyn-анализаторы и свои правила]] и [[Source Generators]]).

## Три способа исполнить программу

### Компиляция в машинный код (ahead-of-time, AOT)

C, C++, Rust, Go. Компилятор сразу выдаёт машинный код под конкретную архитектуру и ОС.

- **Плюсы:** максимальная скорость старта, нет рантайма в поставке, полный контроль над памятью.
- **Минусы:** отдельная сборка под каждую платформу; нет информации о типах во время выполнения; ошибка адресации памяти — падение процесса или уязвимость.

### Интерпретация

Python, Ruby, PHP (в классическом виде), Bash. Интерпретатор читает программу и выполняет её по шагам, каждый раз заново разбирая конструкции.

- **Плюсы:** ничего не собирать, мгновенный цикл «поправил — запустил», переносимость.
- **Минусы:** в 10–100 раз медленнее машинного кода; ошибки типов и опечатки в редкой ветке всплывают только в рантайме.

### Гибрид: байт-код + виртуальная машина

C#, Java, Kotlin, Scala, и в другой форме — современные JavaScript-движки. Компилятор переводит код не в машинные инструкции, а в **байт-код** для абстрактной («виртуальной») машины. Виртуальная машина при запуске превращает байт-код в машинный код — это и есть JIT (just-in-time compilation).

```
   C#                     Java                     Python
   ──                     ────                     ──────
 исходник                исходник                 исходник
    │ Roslyn (csc)          │ javac                   │
   IL (.dll)              байт-код (.class)        байт-код (.pyc)
    │ JIT в CLR             │ JIT в JVM               │ интерпретатор CPython
 машинный код            машинный код              выполнение по шагам
```

Виртуальная машина — это не эмулятор компьютера (не VirtualBox). Это спецификация набора инструкций плюс рантайм, который эти инструкции исполняет: управляет памятью, проверяет типы, обрабатывает исключения. В .NET роль ВМ играет **CLR** (Common Language Runtime), подробно — [[Устройство .NET: CLR, BCL, SDK, рантаймы]].

| | AOT в машинный код | Байт-код + JIT | Интерпретация |
|---|---|---|---|
| Старт | мгновенный | заметная задержка на прогрев | мгновенный |
| Пиковая скорость | высокая | сравнимая, иногда выше | низкая |
| Переносимость | сборка на платформу | одна сборка на все | одна на все |
| Знание о типах в рантайме | нет | полное (метаданные) | полное |
| Оптимизация под конкретный CPU | по флагам сборки | автоматически, по факту запуска | нет |

Ключевой и неочевидный пункт — последний. AOT-компилятор не знает, на каком процессоре запустят программу, и вынужден целиться в общий знаменатель. JIT компилирует на месте и видит: есть AVX-512 — использует AVX-512; в .NET 10 JIT задействует AVX-512/AVX10.2 и ARM SVE2, и на подходящем железе это даёт 15–30 % выигрыша. Плюс JIT видит **фактическое поведение** программы: какие ветки исполняются, какие типы реально приходят в виртуальные вызовы — и оптимизирует под них (profile-guided optimization, PGO, включена по умолчанию с .NET 8).

## Путь C#-кода до процессора

```
 Program.cs
    │  dotnet build   →   Roslyn
    ▼
 MyApp.dll  =  IL (инструкции) + метаданные (описание типов) + ресурсы
    │
    │  dotnet MyApp.dll  →  хост загружает CLR, CLR загружает сборку
    ▼
 первый вызов метода  →  JIT компилирует ЭТОТ метод в машинный код
    │                        (не всю программу — только вызванное)
    ▼
 машинный код в памяти  →  адрес подставляется в таблицу вызовов
    │
    ▼
 повторные вызовы идут напрямую в скомпилированный код
```

### Что лежит в сборке

`.dll` (assembly) — это не машинный код. Внутри:

- **IL** (Intermediate Language, он же CIL/MSIL) — стековый байт-код: `ldloc.0`, `ldc.i4.5`, `add`, `stloc.1`, `call`, `ret`;
- **метаданные** — полное описание типов, методов, полей, атрибутов. Именно на них работают рефлексия, сериализаторы, DI-контейнеры и отладчик;
- ресурсы (строки, картинки) и, при желании, встроенный PDB.

Посмотреть IL можно `ildasm`, ILSpy, dnSpy или на sharplab.io. Это стоит сделать хотя бы раз: многие вопросы («во что превращается `foreach`», «что делает `async`», «сколько на самом деле аллокаций») отвечаются одним взглядом в IL. Подробно — [[Устройство .NET: CLR, BCL, SDK, рантаймы]].

```csharp
int Sum(int a, int b) => a + b;

// IL примерно такой:
//   ldarg.1     // положить a на стек вычислений
//   ldarg.2     // положить b
//   add         // сложить, результат на стеке
//   ret         // вернуть верх стека
```

Обрати внимание: в IL нет регистров и нет типов процессора — есть абстрактный стек вычислений. Отображением на регистры конкретного CPU занимается JIT.

### Почему `.dll`, а не `.exe`

Результат сборки — библиотека с IL, ей нужен рантайм. Запустить можно двумя способами:

```bash
dotnet MyApp.dll        # хост dotnet находит рантайм и запускает сборку
./MyApp                 # apphost — маленький нативный запускатель,
                        # который делает то же самое
```

`MyApp` (или `MyApp.exe` на Windows) рядом с `.dll` — это **apphost**: несколько килобайт нативного кода, чья единственная работа — найти рантайм и передать ему `MyApp.dll`. Поэтому «exe» в .NET не содержит программу, программа — в dll.

Два режима публикации:

| | framework-dependent | self-contained |
|---|---|---|
| Что в поставке | только твой код | код + весь рантайм (~60–70 МБ) |
| Требование к серверу | установленный .NET 10 runtime | ничего |
| Обновление рантайма | централизованно, патчи ОС/образа | пересобрать и переразвернуть |
| Типичное применение | docker-образ `aspnet:10.0`, серверы под контролем | утилиты «скачал и запустил» |

### Tiered compilation: почему первый запрос медленный

JIT стоит времени, и оптимизирующая компиляция стоит его много. Компромисс в .NET — **многоуровневая компиляция**:

- **Tier 0** — при первом вызове метод компилируется быстро и без оптимизаций. Старт быстрый, код так себе.
- **Tier 1** — если метод вызван много раз (порядка 30) или содержит горячий цикл, он перекомпилируется с полными оптимизациями и подставляется на место старого. Для долгих циклов работает **OSR** (on-stack replacement) — замена кода метода, который уже выполняется.
- **PGO** — при переходе в tier 1 используется статистика, собранная в tier 0: какие типы реально приходили, какие ветки брались.

Практические следствия:

- Первый запрос к свежему инстансу — это JIT всего конвейера ASP.NET Core, отсюда 100–500 мс. Дальше — миллисекунды.
- Замер производительности без прогрева бессмысленен: ты меряешь tier 0. Поэтому существует [[Как измерять: BenchmarkDotNet]], который прогревает код перед замером.
- В Kubernetes при частом рестарте пода прогрев платится каждый раз; отсюда практика readiness-проб с прогревочными запросами.

**ReadyToRun (R2R)** — компромисс: при публикации в сборку кладётся заранее сгенерированный машинный код в дополнение к IL. Старт быстрее (не надо JIT-ить с нуля), а горячие методы всё равно перекомпилируются в tier 1 под конкретный процессор. Размер сборки при этом растёт.

**Native AOT** — другой полюс: всё компилируется в нативный исполняемый файл заранее, JIT в поставку не входит вообще. Старт — единицы миллисекунд, потребление памяти ниже, размер файла меньше self-contained. Цена: нет динамической генерации кода, рефлексия ограничена, `Assembly.Load` для плагинов недоступен, часть библиотек не работает. Подходит для CLI-утилит, serverless и микросервисов с жёсткими требованиями к старту. Детально — [[JIT, Tiered Compilation, ReadyToRun, Native AOT]].

### Управляемый код

Код, исполняемый под CLR, называют **управляемым** (managed): рантайм отвечает за выделение и освобождение памяти (GC), проверку границ массивов, приведение типов, обработку исключений и безопасность типов. Обратная сторона — вызовы в нативные библиотеки требуют перехода границы (marshalling, P/Invoke), а поведение по памяти менее предсказуемо (пауза GC вместо детерминированного `free`).

«Ошибка сегментации» в C# практически невозможна: обращение по нулевой ссылке даёт `NullReferenceException`, выход за границу массива — `IndexOutOfRangeException`. Это не бесплатно: проверка границ — сравнение и переход на каждом обращении, но JIT умеет её устранять, когда доказал, что индекс безопасен (bounds check elimination) — например, в цикле `for (int i = 0; i < array.Length; i++)`. Отсюда практический совет: писать цикл именно так, а не кешировать длину в переменную — иначе JIT теряет возможность доказать безопасность.

> [!warning] Подводные камни
> - **«C# компилируется в машинный код» и «C# интерпретируется» — оба утверждения неверны.** Компилируется в IL при сборке, в машинный код — при выполнении. Интерпретатор в .NET есть только в специальных сценариях (например, WebAssembly без AOT).
> - **Компиляция в Release ≠ работающий код в Release.** Оптимизации JIT меняют порядок чтения и записи полей. Многопоточный код, «работающий» в Debug, может ломаться в Release — не потому, что оптимизатор сломался, а потому что код изначально некорректен без барьеров памяти. См. [[Примитивы синхронизации: lock, Monitor]].
> - **Замер в `Main` через `Stopwatch`.** Первый прогон включает JIT метода и всего, что он вызывает. Разница с прогретым кодом — десятки раз.
> - **`#if DEBUG` и `Debug.Assert`.** Это вырезается компилятором в Release-сборке, а не «просто выключается». Логика, спрятанная в `#if DEBUG`, на проде отсутствует физически.
> - **Отладка Release-сборки.** Без PDB и с оптимизациями значения локальных переменных «пропадают», а стек вызовов схлопывается из-за inlining. Это не баг отладчика.

> [!example] Как делают в бою
> Продовый Docker-образ .NET-сервиса собирают в два этапа: первый на образе SDK (`mcr.microsoft.com/dotnet/sdk:10.0`) делает `dotnet publish`, второй — на образе рантайма (`mcr.microsoft.com/dotnet/aspnet:10.0`) содержит только результат. SDK — это компилятор, шаблоны и инструменты, десятки мегабайт, на проде он не нужен и является лишней поверхностью атаки.
> Для serverless-функций и CLI-утилит выбирают Native AOT: холодный старт с 200 мс падает до единиц миллисекунд, а образ — до десятков мегабайт.
> Для обычных веб-сервисов оставляют JIT: он даёт лучшую пиковую производительность и полную совместимость с библиотеками, а холодный старт лечится тем, что инстанс живёт долго.

## Вопросы с собеседований

> [!question]- Что происходит при сборке и запуске C#-приложения?
> При сборке Roslyn проводит лексический, синтаксический и семантический анализ, применяет часть оптимизаций и генерирует IL — стековый байт-код — вместе с метаданными о типах; результат — сборка `.dll`. При запуске хост (`dotnet` или apphost рядом с dll) находит рантайм, CLR загружает сборку, читает метаданные и передаёт управление точке входа. Каждый метод компилируется JIT-ом в машинный код при первом вызове: сначала быстро и без оптимизаций (tier 0), затем, если метод оказался горячим, повторно с полными оптимизациями и с учётом собранного профиля (tier 1 + PGO). Ничего не компилируется заранее целиком — только то, что реально вызвано.

> [!question]- Чем JIT лучше и хуже AOT?
> JIT компилирует во время выполнения, поэтому знает точную модель процессора (использует доступные векторные расширения) и фактическое поведение программы (какие типы приходят в виртуальные вызовы, какие ветки горячие) — за счёт этого пиковая производительность может превосходить AOT. Плюс одна сборка работает на всех платформах, а рефлексия и динамическая генерация кода доступны полностью. Минусы: задержка на старте (JIT-компиляция первых вызовов), дополнительное потребление памяти самим компилятором и непредсказуемость первых миллисекунд. AOT наоборот: мгновенный старт, меньше памяти, но код собран под общий знаменатель железа, нет динамики, нужна отдельная сборка под платформу. Поэтому веб-сервисы обычно на JIT, а CLI и serverless — на Native AOT.

> [!question]- Что такое IL и зачем он нужен, если всё равно потом компилируется в машинный код?
> IL — платформенно-независимый байт-код со стековой моделью вычислений, без регистров и без привязки к архитектуре. Он решает три задачи. Переносимость: одна сборка исполняется на x86-64 и ARM64, под Windows, Linux и macOS. Многоязычность: C#, F#, VB компилируются в один и тот же IL, поэтому библиотека на F# используется из C# без обёрток. Отложенная оптимизация: решение о машинном коде принимается на целевой машине, где известны и процессор, и профиль исполнения. Дополнительно IL вместе с метаданными делает возможными рефлексию, декомпиляцию, инструментирование и анализаторы.

> [!question]- Почему первый запрос к только что запущенному ASP.NET Core сервису медленнее остальных?
> Работает сумма факторов: JIT компилирует в tier 0 весь путь запроса (Kestrel, middleware-конвейер, роутинг, сериализацию, EF Core), первый запрос к БД устанавливает физическое соединение и заполняет пул, EF Core компилирует и кеширует модель и планы запросов, кеши приложения пусты, а страницы памяти ещё не тронуты. Дальше горячие методы переходят в tier 1, соединения переиспользуются, кеши прогреты — и время падает на порядок. Стандартные лекарства: ReadyToRun для ускорения старта, прогревочные запросы в readiness-пробе, не гонять частые перезапуски инстансов.

> [!question]- В чём разница между SDK и runtime?
> Runtime — то, что нужно, чтобы **исполнить** уже собранное приложение: CLR (загрузчик, JIT, GC) плюс библиотеки BCL. SDK — то, что нужно, чтобы **собрать**: компиляторы Roslyn, MSBuild, шаблоны проектов, инструменты (`dotnet new`, `dotnet publish`, `dotnet ef`), и внутри него уже лежит runtime. На машине разработчика ставят SDK, в продовый образ кладут только runtime — меньше размер, меньше поверхность атаки. Отсюда двухэтапная сборка Docker-образов.

## Задачи

### Задача 1. Прочитать IL

Что выведет программа и почему в IL не окажется сложения?

```csharp
const int a = 2;
const int b = 3;
Console.WriteLine(a + b);
```

> [!success]- Решение
> Выведет `5`. Оба операнда — константы времени компиляции, поэтому Roslyn выполняет свёртку константы (constant folding) на этапе компиляции: в IL попадает `ldc.i4.5` — «положить литерал 5», инструкции `add` нет вообще. Это одна из причин, по которой `const` отличается от `readonly` не только «когда можно присвоить»: значение `const` физически впаивается в место использования, в том числе в другие сборки, — и потому его изменение требует перекомпиляции всех потребителей. Подробнее — [[Синтаксис и структура программы]].

### Задача 2. Объяснить замер

Разработчик мерит два способа конкатенации и получает, что в первом прогоне `string +` быстрее `StringBuilder`, а при повторе в том же процессе — наоборот. Что происходит?

> [!success]- Решение
> В первом прогоне значительная доля времени — это JIT-компиляция самих методов `StringBuilder` (конструктор, `Append`, `ToString`, рост внутреннего буфера) в tier 0, плюс первое обращение к ним подтягивает страницы памяти и заполняет кеши. Простая конкатенация задействует меньше кода, поэтому «выигрывает» — измерена стоимость прогрева, а не алгоритма. При повторных прогонах горячие методы уже в tier 1, и проявляется настоящая разница: конкатенация в цикле создаёт новую строку на каждой итерации (O(n²) по копированию), `StringBuilder` пишет в буфер. Правильный вывод: замеры делаются в BenchmarkDotNet с прогревом и множеством итераций, а не в `Main` со `Stopwatch`.

### Задача 3. Выбрать способ публикации

Нужно раздать коллегам утилиту-однофайловик, которая читает CSV и печатает отчёт. На машинах коллег .NET не установлен, антивирус запрещает «непонятные инсталляторы», старт должен быть быстрым. Что публиковать?

> [!success]- Решение
> Self-contained публикация с Native AOT:
> ```bash
> dotnet publish -c Release -r osx-arm64 -p:PublishAot=true
> ```
> Аргументы: без установленного рантайма framework-dependent не запустится, значит нужен self-contained; AOT убирает JIT, даёт старт в единицы миллисекунд и один файл заметно меньшего размера, чем self-contained с рантаймом; для утилиты, которая не грузит плагины и не строит типы в рантайме, ограничения AOT по рефлексии не мешают. Идентификатор среды выполнения (RID) указывается под целевую платформу — `osx-arm64`, `linux-x64`, `win-x64`, и на каждую нужна отдельная сборка: это плата за отказ от IL. Если бы у коллег стоял .NET 10, дешевле был бы framework-dependent — сборка в считанные сотни килобайт.

## Итог

- Компилятор — конвейер: лексер, парсер, семантика, оптимизации, генерация кода. Разные ошибки приходят с разных фаз.
- Три модели исполнения: AOT в машинный код, интерпретация, байт-код + виртуальная машина. C# — третья.
- `dotnet build` даёт `.dll` с IL и метаданными; машинный код появляется в рантайме силами JIT.
- IL нужен для переносимости, многоязычности и оптимизации на целевой машине; метаданные — основа рефлексии и инструментов.
- Tiered compilation обменивает скорость старта на пиковую производительность; отсюда «медленный первый запрос» и требование прогрева в бенчмарках.
- ReadyToRun ускоряет старт, Native AOT убирает JIT совсем — за счёт динамики и отдельной сборки под платформу.
- Управляемый код даёт безопасность типов и памяти ценой GC-пауз и границы при вызове нативного кода.
