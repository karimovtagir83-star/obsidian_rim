# Сети для бэкендера: TCP, DNS, порты

> [!abstract] Коротко
> Бэкенд — это программа, которая ждёт на порту. Чтобы понимать, что происходит, нужно немного: IP-адрес находит машину, порт — процесс на ней, TCP обеспечивает надёжную доставку байтов, DNS переводит имена в адреса, TLS шифрует, HTTP — уже смысл поверх всего этого. Эта заметка даёт минимум, после которого `localhost:5000`, `0.0.0.0`, «connection refused», «таймаут» и «socket exhaustion» перестают быть загадками.

## Зачем это нужно

Первые же практические вопросы упираются в сеть:

- запустил приложение, оно пишет `Now listening on: http://localhost:5000` — что это значит и почему коллега по сети не может открыть эту ссылку;
- приложение в Docker слушает 5000, а браузер на хосте не видит — почему нужен `-p 8080:5000`;
- `Connection refused` и `Timeout` — это одна ошибка или разные, и что искать в каждом случае;
- сервис перестал отвечать под нагрузкой с `SocketException: Address already in use` — при том что «код не менялся»;
- запрос к соседнему сервису идёт 300 мс вместо 5 мс, хотя оба в одном дата-центре.

Полный разбор HTTP — отдельная тема ([[HTTP: методы, коды, заголовки, кеширование]]). Здесь — то, что ниже HTTP.

## Модель: слои

Сеть устроена слоями, каждый следующий пользуется предыдущим и не знает его деталей. Практичная версия (стек TCP/IP, четыре слоя вместо академических семи OSI):

```
 ┌─────────────────────────────────────────────────────────┐
 │ Прикладной:  HTTP, gRPC, AMQP (RabbitMQ), PostgreSQL    │  ← твой код
 │              +  TLS как «полуслой» шифрования           │
 ├─────────────────────────────────────────────────────────┤
 │ Транспортный: TCP (надёжно, поток) · UDP (быстро, без   │  ← порты
 │               гарантий) · QUIC (поверх UDP, для HTTP/3) │
 ├─────────────────────────────────────────────────────────┤
 │ Сетевой:      IP — адресация и маршрутизация пакетов    │  ← IP-адреса
 ├─────────────────────────────────────────────────────────┤
 │ Канальный:    Ethernet, Wi-Fi — доставка внутри сегмента│  ← MAC-адреса
 └─────────────────────────────────────────────────────────┘
```

Практический смысл слоёв — в диагностике: если `ping` до хоста идёт, а `curl` не соединяется, то IP работает, а проблема на уровне TCP или выше (процесс не слушает, файрвол режет порт). Это первое разветвление в любом разборе сетевой проблемы.

## IP-адрес: где машина

IPv4 — 4 байта, записываются как `192.168.1.10`. Всего 4,3 млрд адресов, что кончилось ещё в 2011 году; отсюда NAT и IPv6 (16 байт, `2001:db8::1`).

Адреса, которые надо узнавать с ходу:

| Адрес | Что это |
|---|---|
| `127.0.0.1`, `::1` | loopback — «эта же машина». Трафик не выходит на сетевую карту |
| `localhost` | имя, которое разрешается в loopback (через `/etc/hosts`) |
| `10.x.x.x`, `172.16–31.x.x`, `192.168.x.x` | приватные диапазоны: локальные сети, Docker, Kubernetes |
| `0.0.0.0` | «все интерфейсы» — как адрес прослушивания, а не назначения |
| `169.254.x.x` | link-local: адрес не выдан DHCP, признак проблемы с сетью |

`localhost` vs `0.0.0.0` — источник половины вопросов новичка. Это про то, **на каких интерфейсах** процесс принимает соединения:

```
Kestrel слушает 127.0.0.1:5000  →  доступен только с этой же машины
Kestrel слушает 0.0.0.0:5000    →  доступен со всех интерфейсов,
                                   в том числе из локальной сети и из Docker
```

Поэтому в контейнере ASP.NET Core обязательно слушает `0.0.0.0` (в образах Microsoft это настроено переменной `ASPNETCORE_URLS=http://+:8080`): если бы он слушал `127.0.0.1`, то был бы доступен только внутри контейнера, и `-p 8080:8080` не помог бы.

## Порт: какой процесс на машине

Порт — 16-битное число (1–65535), которое ОС использует, чтобы понять, какому процессу отдать пришедший пакет. Соединение однозначно определяется **четвёркой**: `(IP источника, порт источника, IP получателя, порт получателя)`.

| Диапазон | Название | Смысл |
|---|---|---|
| 1–1023 | well-known | требуют прав root на Unix: 80 (HTTP), 443 (HTTPS), 22 (SSH), 53 (DNS) |
| 1024–49151 | registered | 5432 (PostgreSQL), 6379 (Redis), 5672 (RabbitMQ), 9092 (Kafka), 5000/8080 (dev-серверы) |
| 49152–65535 | ephemeral | ОС выдаёт их исходящим соединениям автоматически |

Ключевое: **исходящее соединение тоже занимает порт**. Когда приложение делает запрос к базе, ОС выделяет ему свободный эфемерный порт как порт источника. Их конечное число (~16–28 тысяч на интерфейс) — отсюда возможность «исчерпать порты», о чём ниже.

Команды, которые надо знать (macOS и Linux):

```bash
# Кто слушает порты (macOS и Linux)
lsof -nP -iTCP -sTCP:LISTEN

# Кто занял конкретный порт — типичная ситуация «Address already in use»
lsof -nP -i :5000

# Linux: то же современными средствами
ss -tulpn

# Проверить, отвечает ли порт (без отправки данных)
nc -vz localhost 5432

# Полный HTTP-запрос с диагностикой
curl -v http://localhost:5000/health
```

## TCP: надёжный поток байтов

IP доставляет пакеты «как получится»: пакет может потеряться, продублироваться, прийти не в том порядке. TCP надстраивает над этим надёжный упорядоченный поток и добавляет:

- **установление соединения** (three-way handshake): `SYN` → `SYN-ACK` → `ACK`. Одна полная задержка туда-обратно (RTT) до передачи первого байта данных;
- **подтверждения и повторы**: не пришло `ACK` — отправитель повторяет;
- **упорядочивание** по номерам последовательности;
- **контроль потока** (окно приёма) и **контроль перегрузки** (не заливать сеть);
- **корректное закрытие**: `FIN`/`ACK` с обеих сторон и состояние `TIME_WAIT` на закрывающей стороне.

```
   Клиент                                  Сервер
     │ ── SYN ─────────────────────────────► │   0,5 RTT
     │ ◄──────────────────────── SYN+ACK ─── │   1,0 RTT
     │ ── ACK ─────────────────────────────► │   1,5 RTT — соединение готово
     │ ── (TLS handshake: ещё 1–2 RTT) ────► │
     │ ── HTTP GET ────────────────────────► │
     │ ◄──────────────────────── 200 OK ──── │
```

Из этой картинки следует практика, которая объясняет реальные цифры: **установление соединения стоит дороже, чем передача данных**. Внутри дата-центра RTT ~0,5 мс, значит TCP+TLS handshake — 1,5–3 мс до первого байта. Между континентами RTT 150 мс — и те же три обмена дают почти полсекунды. Поэтому соединения **переиспользуют**: keep-alive в HTTP, пул соединений к БД ([[Пулинг соединений]]), пул в `SocketsHttpHandler` за `HttpClient`.

### TCP vs UDP

| | TCP | UDP |
|---|---|---|
| Доставка | гарантированная, в порядке | без гарантий |
| Соединение | есть (handshake) | нет, просто отправка датаграмм |
| Накладные расходы | заголовок 20+ байт, подтверждения | заголовок 8 байт |
| Кому нужно | HTTP/1.1 и 2, БД, брокеры, gRPC | DNS, метрики (StatsD), видео, игры, QUIC/HTTP/3 |

«UDP быстрее TCP» — упрощение: он не быстрее по пропускной способности, он просто не тратит время на восстановление порядка и повторы. Если данные нужны целиком и в порядке — надёжность придётся реализовать самому, что и делает QUIC поверх UDP.

## DNS: имена вместо адресов

Код обращается к `db.internal.company` или `api.stripe.com`, а не к IP. Перевод имени в адрес делает DNS:

```
приложение → системный резолвер (кеш ОС)
                    │ промах
                    ▼
             DNS-сервер провайдера / кластера (кеш)
                    │ промах
                    ▼
         корневые серверы → .com → stripe.com → ответ + TTL
```

Что важно знать практически:

- **TTL и кеширование.** Ответ кешируется на время TTL. Поэтому после переезда сервиса на новый IP часть клиентов ещё какое-то время идёт на старый адрес.
- **.NET кеширует DNS на уровне соединений.** `SocketsHttpHandler` держит пул соединений и по умолчанию не перепроверяет DNS для уже открытых. Если адрес сервиса меняется (типично для облаков и Kubernetes), выставляют `PooledConnectionLifetime` (обычно 2–5 минут), чтобы соединения периодически пересоздавались — это стандартная настройка `IHttpClientFactory` ([[HttpClient и IHttpClientFactory]]).
- **Типы записей:** `A` (IPv4), `AAAA` (IPv6), `CNAME` (псевдоним), `MX` (почта), `TXT` (произвольный текст, часто для верификации домена), `SRV` (сервис и порт — используется в service discovery).
- **`/etc/hosts` сильнее DNS.** Локальные подмены для отладки делают там; там же живёт `127.0.0.1 localhost`.
- **В Docker и Kubernetes DNS — часть платформы.** Имя контейнера или сервиса резолвится внутренним DNS, поэтому в `docker-compose` можно писать `Host=postgres` вместо IP.

```bash
dig +short api.github.com          # какие A-записи и с каким TTL
dig api.github.com | tail -5
host -t MX company.uz
```

## TLS: та самая буква S в HTTPS

TLS даёт три вещи: шифрование (никто по пути не прочитал), целостность (никто не подменил) и аутентификацию сервера (это действительно тот домен, сертификат подписан доверенным центром).

Механика в одном абзаце: клиент и сервер договариваются о версии и наборе шифров, сервер присылает сертификат с публичным ключом, клиент проверяет цепочку подписей до доверенного корневого центра, стороны вырабатывают общий сеансовый ключ (обмен по Диффи — Хеллману), дальше трафик шифруется быстрой симметричной криптографией. TLS 1.3 укладывает это в один RTT, TLS 1.2 — в два.

Что из этого вылезает в работе:

- **Проверка сертификата валится в dev-окружении** — самоподписанный сертификат не в доверенных. Правильно: `dotnet dev-certs https --trust`. Неправильно и опасно: отключать проверку в коде — такой «временный» костыль регулярно доезжает до прода и превращается в уязвимость.
- **Истёкший сертификат** — классическая авария с самым простым root cause. Мониторинг срока действия обязателен.
- **TLS-терминация** обычно происходит на reverse proxy (nginx, ingress, ALB), а до приложения идёт HTTP. Отсюда потребность в заголовках `X-Forwarded-Proto`/`X-Forwarded-For` и middleware `ForwardedHeaders` — без него приложение считает, что запрос пришёл по HTTP от прокси, и генерирует неправильные абсолютные ссылки.

## Сокеты в .NET: где это видно в коде

Прямой работы с сокетами в бэкенде почти не бывает — обычно достаточно `HttpClient`, драйвера БД или клиента брокера. Но полезно видеть, что под ними:

```csharp
using System.Net.Sockets;

// Клиент: подключиться и проверить, что порт отвечает
using var client = new TcpClient();
await client.ConnectAsync("localhost", 5432);       // TCP handshake
Console.WriteLine($"Подключено: {client.Connected}");

// Разрешение имени в адреса — то же, что делает браузер перед запросом
var addresses = await System.Net.Dns.GetHostAddressesAsync("api.github.com");
foreach (var a in addresses) Console.WriteLine(a);
```

```csharp
// Типичный правильный клиент HTTP: один экземпляр на приложение,
// ограниченное время жизни соединений, явный таймаут.
var handler = new SocketsHttpHandler
{
    PooledConnectionLifetime = TimeSpan.FromMinutes(2),   // пересоздавать соединения:
                                                          // подхватывает смену DNS
    MaxConnectionsPerServer = 50
};
using var http = new HttpClient(handler) { Timeout = TimeSpan.FromSeconds(10) };
```

> [!warning] Подводные камни
> - **`new HttpClient()` в цикле или в каждом запросе.** Каждый экземпляр со своим handler открывает новые TCP-соединения; закрытые соединения ещё минуты висят в состоянии `TIME_WAIT` и держат эфемерные порты. Результат под нагрузкой — `SocketException: Address already in use`, при том что «код не менялся, просто выросла нагрузка». Лечение: один `HttpClient` на приложение или `IHttpClientFactory`.
> - **`HttpClient` как singleton без `PooledConnectionLifetime`.** Обратная крайность: соединения живут вечно и не замечают смену IP за DNS-именем. В облаке это выглядит как «сервис ходит на удалённый инстанс, которого уже нет».
> - **Connection refused ≠ timeout.** `Connection refused` — машина ответила «на этом порту никто не слушает»: процесс не запущен, слушает другой порт или только `127.0.0.1`. Timeout — ответа нет вообще: файрвол, security group, неверный хост, сеть. Это два разных класса причин, и путать их — терять часы.
> - **Запросы без таймаута.** По умолчанию у `HttpClient` таймаут 100 секунд; для внутреннего вызова это вечность. Один залипший внешний сервис без таймаута выстраивает очередь запросов и роняет твой сервис — так каскадные отказы и работают. Таймаут и повторы — [[Устойчивость: retry, circuit breaker, Polly]].
> - **`localhost` в контейнере — это сам контейнер.** Строка подключения `Host=localhost` внутри контейнера ищет базу в этом же контейнере. Нужен либо hostname сервиса из compose, либо `host.docker.internal` для доступа к хосту.
> - **Один медленный DNS-резолв блокирует запрос целиком.** Если DNS отвечает за 5 секунд, запрос идёт 5 секунд, и в трейсе это выглядит как «медленный сервис». Смотреть надо на этап установления соединения, а не на обработку.

> [!example] Как делают в бою
> Проверка «жив ли сосед» делается сверху вниз, слой за слоем: `dig` — резолвится ли имя; `nc -vz host port` — открыт ли порт; `curl -v` — отвечает ли приложение и что в заголовках; и только потом смотрят логи и трейсы приложения. Такой порядок за минуту отделяет проблему сети от проблемы кода.
> В продовой конфигурации внутренние вызовы всегда имеют таймаут (единицы секунд, не 100), ограниченное число повторов с экспоненциальной задержкой и разрыватель цепи. Соединения переиспользуются: пул к БД, keep-alive для HTTP, долгоживущие каналы для gRPC.
> Ошибка «Address already in use» при локальном запуске почти всегда означает, что предыдущий процесс не завершился: `lsof -nP -i :5000`, затем `kill`.

## Вопросы с собеседований

> [!question]- Что происходит, когда браузер открывает `https://example.com/api/users`?
> Разбор URL, затем DNS-резолв `example.com` в IP (кеш браузера → кеш ОС → DNS-сервер, ответ с TTL). Затем TCP-соединение на порт 443: three-way handshake, одна RTT. Затем TLS-рукопожатие: согласование версии и шифров, сертификат сервера, проверка цепочки доверия, выработка сеансового ключа — ещё 1–2 RTT. По установленному защищённому соединению уходит HTTP-запрос с методом, путём и заголовками; сервер (обычно reverse proxy, который терминирует TLS и проксирует в приложение по HTTP) обрабатывает и возвращает ответ. Соединение остаётся открытым по keep-alive для следующих запросов. Итого до первого байта — минимум 3–4 сетевых обмена, поэтому переиспользование соединений даёт больше, чем оптимизация кода обработчика.

> [!question]- Чем отличаются `127.0.0.1`, `0.0.0.0` и `localhost` в настройке прослушивания?
> `127.0.0.1` — loopback-интерфейс: сервер принимает соединения только с той же машины, трафик не выходит на сетевую карту. `0.0.0.0` (или `http://+:port` в ASP.NET Core) — все интерфейсы: соединения принимаются и с loopback, и из локальной сети, и из других контейнеров. `localhost` — не адрес, а имя, которое резолвится в `127.0.0.1` и `::1`; при прослушивании ведёт себя как loopback. Практическое следствие: приложение в контейнере обязано слушать `0.0.0.0`, иначе проброс порта не поможет — снаружи соединение просто не примут. Обратная сторона: слушать `0.0.0.0` на машине в публичной сети без файрвола — значит открыть сервис всем.

> [!question]- Что такое socket exhaustion в .NET и как его избежать?
> Каждое исходящее TCP-соединение занимает эфемерный порт, а после закрытия порт ещё держится в состоянии `TIME_WAIT` (порядка минуты-двух). Число эфемерных портов ограничено — десятки тысяч. Если создавать `new HttpClient()` на каждый запрос, соединения не переиспользуются: под нагрузкой порты кончаются, и появляется `SocketException` с «Address already in use» либо резкий рост задержек. Решение — один `HttpClient` (или `IHttpClientFactory`) на приложение, потому что внутренний `SocketsHttpHandler` держит пул соединений. При этом бесконечно живущий singleton тоже плох: он не видит смену DNS, поэтому задают `PooledConnectionLifetime` в 2–5 минут. Тот же принцип у драйверов БД — там пул встроен, и его нельзя обходить, создавая соединения руками.

> [!question]- Чем TCP отличается от UDP и что выбирают в бэкенде?
> TCP устанавливает соединение (three-way handshake), гарантирует доставку и порядок, управляет перегрузкой; цена — минимум одна RTT до передачи данных, заголовок больше, задержка при потерях из-за повторов. UDP просто отправляет датаграммы: без соединения, без гарантий, без порядка, зато без накладных расходов. В бэкенде почти всё поверх TCP: HTTP/1.1 и HTTP/2, соединения к БД, AMQP, Kafka, gRPC. UDP берут там, где потеря отдельного сообщения не критична, а задержка важна: DNS-запросы, отправка метрик, видео и голос. Отдельный случай — QUIC: он поверх UDP, но реализует надёжность сам, и на нём работает HTTP/3.

> [!question]- В логах «connection timeout» при обращении к соседнему сервису. Как искать причину?
> По слоям снизу вверх. Резолвится ли имя (`dig`) — если нет, проблема в DNS или в конфигурации хоста. Отвечает ли порт (`nc -vz host port`) — если соединение отклоняется, значит процесс не слушает или слушает не тот интерфейс; если висит без ответа, значит пакеты дропаются файрволом, security group или сетевой политикой. Дальше `curl -v` покажет, доходит ли до приложения и на каком этапе останавливается. Со стороны приложения смотрят, не исчерпан ли пул соединений (тогда таймаут наступает ещё до отправки запроса), не залипли ли запросы без таймаута и не деградировал ли сам сосед — в этом случае у него в трейсах видно рост времени обработки. Разница между «отказано в соединении» и «таймаут» — первое, что нужно установить: это разные ветви поиска.

## Задачи

### Задача 1. Разобрать «не работает»

Приложение локально запускается и отвечает на `http://localhost:5000/health`. Тот же образ в Docker с `docker run -p 8080:5000 myapp` отвечает `Empty reply from server` на `http://localhost:8080/health`. Что не так?

> [!success]- Решение
> Скорее всего приложение внутри контейнера слушает `127.0.0.1:5000`, а не `0.0.0.0:5000`. Проброс порта доставляет пакеты на сетевой интерфейс контейнера, а на loopback-интерфейсе процесс их не ждёт, поэтому соединение обрывается. Проверка — логи старта Kestrel: там печатается фактический адрес прослушивания.
> Лечение: указать `ASPNETCORE_URLS=http://+:5000` (в официальных образах .NET это значение уже настроено на 8080) или `http://0.0.0.0:5000`. Второй частый вариант той же ошибки — приложение слушает 8080, а `-p 8080:5000` пробрасывает на 5000: порт справа должен совпадать с портом внутри контейнера.

### Задача 2. Проверить порт из кода

Напиши метод, который проверяет доступность TCP-порта с таймаутом 2 секунды и отличает «отказано в соединении» от «нет ответа».

> [!success]- Решение
> ```csharp
> using System.Net.Sockets;
>
> static async Task<string> ProbeAsync(string host, int port)
> {
>     using var client = new TcpClient();
>     using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(2));
>     try
>     {
>         await client.ConnectAsync(host, port, cts.Token);
>         return "открыт";
>     }
>     catch (OperationCanceledException)
>     {
>         return "нет ответа (таймаут): пакеты дропаются или хост недоступен";
>     }
>     catch (SocketException ex) when (ex.SocketErrorCode == SocketError.ConnectionRefused)
>     {
>         return "отказано: хост есть, на порту никто не слушает";
>     }
>     catch (SocketException ex) when (ex.SocketErrorCode == SocketError.HostNotFound)
>     {
>         return "имя не разрешается: проблема DNS";
>     }
> }
>
> Console.WriteLine(await ProbeAsync("localhost", 5432));
> ```
> Три разных ветви `catch` — это ровно те три разных диагноза, которые надо различать: DNS, отсутствие слушателя и блокировка трафика. `ConnectAsync` с токеном отмены нужен потому, что собственного таймаута у него нет, а системный может составлять десятки секунд. Обрати внимание на фильтры `when` — они позволяют разбирать `SocketException` по коду, не вкладывая `if` внутрь блока (см. [[Обработка исключений]]).

### Задача 3. Посчитать бюджет запроса

Сервис на обработку одного HTTP-запроса делает: 1 запрос в PostgreSQL (в том же дата-центре, RTT 0,5 мс, запрос 3 мс), 2 обращения к внешнему API (RTT 80 мс, обработка на их стороне 50 мс) и 1 обращение в Redis (RTT 0,3 мс). Оцени минимальное время ответа и что оптимизировать.

> [!success]- Решение
> Внешний API доминирует полностью. Одно обращение: RTT на установление TCP уже не платится, если соединения переиспользуются, но остаётся один RTT на обмен (80 мс) плюс 50 мс обработки — итого ~130 мс. Два последовательных обращения — 260 мс. База и Redis добавляют около 4 мс.
> Оптимизации по эффективности: сделать два внешних вызова параллельно (`Task.WhenAll`) — 260 мс превращаются в ~130; закешировать ответы внешнего API в Redis, если данные допускают устаревание — тогда типичный запрос вообще не выходит наружу; проверить, что HTTP-соединения переиспользуются, иначе на каждый вызов добавляются ещё 1–2 RTT на TCP и TLS (то есть 80–240 мс сверху). Оптимизировать SQL-запрос на 3 мс или код сериализации бессмысленно, пока в бюджете есть 260 мс сетевых ожиданий. Заодно отсюда видно, зачем нужны таймауты: без них залипший внешний API держит запрос все 100 секунд.

## Итог

- IP находит машину, порт — процесс; соединение задаётся четвёркой адрес-порт с обеих сторон.
- `127.0.0.1` — только своя машина, `0.0.0.0` — все интерфейсы. В контейнере надо слушать `0.0.0.0`.
- TCP даёт надёжный упорядоченный поток ценой рукопожатия: соединение дороже передачи, поэтому его переиспользуют.
- DNS переводит имена в адреса и кешируется; в .NET за это отвечает время жизни соединений в пуле, а не только TTL.
- TLS даёт шифрование, целостность и аутентификацию сервера; в проде обычно терминируется на прокси.
- `Connection refused` и `timeout` — разные диагнозы: первый про отсутствие слушателя, второй про блокировку или недоступность.
- Исходящие соединения занимают эфемерные порты: `new HttpClient()` на запрос приводит к их исчерпанию.
- Каждый внешний вызов без таймаута — заготовка каскадного отказа.
