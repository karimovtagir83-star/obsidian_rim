# Как работает компьютер: процессор, память, ОС

> [!abstract] Коротко
> Процессор умеет только читать байты из памяти, складывать их и переходить по адресам — всё остальное надстроено сверху. Память не одна: это пирамида от регистров (0 тактов) до диска (миллионы тактов), и почти вся производительность современного кода определяется тем, попал ты в кеш или нет. Операционная система — прослойка, которая создаёт иллюзию: у каждого процесса «своя» память и «свой» процессор, хотя физически они общие. Понимать эти три вещи нужно не для эрудиции: без них `struct` vs `class`, GC, async и «почему запрос тормозит» останутся заклинаниями.

## Зачем это нужно

C# — язык с высоким уровнем абстракции. Ты пишешь `list.Add(item)` и не думаешь, что происходит физически. Ровно до того момента, когда:

- код работает правильно, но в 30 раз медленнее ожидаемого;
- приложение съедает 4 ГБ памяти и падает с `OutOfMemoryException`;
- на собеседовании спрашивают, чем `struct` отличается от `class` — а разница вся про память;
- нагрузочный тест показывает 200 RPS вместо 5000, и профилировщик показывает «cache miss».

Абстракции текут (leaky abstractions). Каждая абстракция рано или поздно протекает, и в этот момент нужно знать, что под ней. Этот конспект — минимальная модель железа, достаточная для всего дальнейшего пути. Он сознательно упрощает: цель — рабочая интуиция, а не курс по архитектуре ЭВМ.

## Три части и одна шина

```
        ┌──────────────────────────────────────────────┐
        │                  ПРОЦЕССОР                   │
        │   регистры · ALU · кеши L1/L2 · декодер       │
        └───────────────┬──────────────────────────────┘
                        │ шина памяти (десятки ГБ/с)
        ┌───────────────┴──────────────────────────────┐
        │            ОПЕРАТИВНАЯ ПАМЯТЬ (RAM)          │
        │   код программ · данные · стеки · кучи       │
        └───────────────┬──────────────────────────────┘
                        │ PCIe / SATA (гигабайты/с)
        ┌───────────────┴──────────────────────────────┐
        │   ДИСК · СЕТЬ · КЛАВИАТУРА · ЭКРАН (I/O)     │
        └──────────────────────────────────────────────┘
```

Ключевое, что стоит запомнить с самого начала: **чем дальше от процессора, тем медленнее — не на проценты, а на порядки**. Разница между регистром и диском такая же, как между «взять книгу с полки» и «заказать её из другого города».

## Процессор: он глупее, чем кажется

Физически процессор выполняет цикл, который не менялся с 1945 года (машина фон Неймана):

1. **Fetch** — прочитать инструкцию по адресу из регистра `RIP`/`PC` (instruction pointer).
2. **Decode** — понять, что это за инструкция.
3. **Execute** — выполнить: сложить два регистра, сравнить, прочитать из памяти, перейти.
4. Увеличить `RIP` и повторить.

Набор инструкций (ISA — instruction set architecture) примитивен: `mov` (переложить), `add`/`sub`/`mul`, `cmp` (сравнить), `jmp`/`je`/`jne` (переход, условный переход), `call`/`ret` (вызов и возврат), `push`/`pop` (стек). Всё, что ты пишешь на C#, в конечном счёте превращается в такие инструкции — см. [[Компиляция, интерпретация и виртуальные машины]].

Две архитектуры, которые встречаются сегодня:

| | x86-64 (AMD64) | ARM64 (AArch64) |
|---|---|---|
| Где | Intel, AMD: серверы, ПК | Apple Silicon (M1–M4), AWS Graviton, телефоны |
| Стиль | CISC: много сложных инструкций | RISC: мало простых, фиксированная длина |
| Инструкций | тысячи, длина 1–15 байт | сотни, длина 4 байта |
| .NET | поддержан полностью | поддержан полностью, native ARM64 SDK |

Практический вывод: код на C# переносится между ними без изменений (за это отвечает JIT — [[JIT, Tiered Compilation, ReadyToRun, Native AOT]]), но нативные зависимости, Docker-образы и бенчмарки — нет. Образ `linux/amd64` на Apple Silicon запустится через эмуляцию и будет медленнее в разы.

### Регистры

Регистр — ячейка внутри процессора, обращение к ней бесплатно (0–1 такт). На x86-64 их 16 общего назначения по 64 бита (`rax`, `rbx`, `rcx`, …) плюс векторные (`xmm`/`ymm`/`zmm` на 128/256/512 бит). Это вся «быстрая память» процессора — суммарно около 100–200 байт.

Отсюда следует то, что потом объяснит половину советов по производительности: **работа идёт только в регистрах**. Чтобы сложить два числа из памяти, их надо сначала туда загрузить. Оптимизирующий компилятор в первую очередь занят тем, чтобы держать горячие переменные в регистрах и не гонять их в память (register allocation).

### Тактовая частота и конвейер

3 ГГц = 3 миллиарда тактов в секунду, один такт ≈ 0,33 наносекунды. Но «одна инструкция за такт» — неправда в обе стороны:

- **Конвейер (pipeline).** Инструкция проходит 10–20 стадий, и стадии разных инструкций выполняются одновременно, как на заводском конвейере. Пока одна декодируется, следующая читается, предыдущая пишет результат.
- **Суперскалярность.** Современное ядро запускает 4–8 инструкций за такт, если они независимы.
- **Out-of-order execution.** Процессор переставляет инструкции местами, чтобы не простаивать в ожидании памяти. Программист этого не видит, но это причина, по которой существуют `volatile` и барьеры памяти — см. [[Interlocked, volatile и модель памяти]].

### Предсказание переходов

Конвейер требует знать заранее, какая инструкция следующая. На `if` это неизвестно до вычисления условия. Процессор **угадывает** (branch predictor) и спекулятивно выполняет предсказанную ветку. Угадал (а угадывает он в 95–99 % случаев на предсказуемых данных) — выигрыш. Промахнулся — весь конвейер сбрасывается, потеря 15–20 тактов.

```csharp
// Классический эксперимент. Массив тот же, разница — в порядке данных.
int[] data = new int[100_000];
var rnd = new Random(42);
for (int i = 0; i < data.Length; i++)
    data[i] = rnd.Next(256);

long Sum(int[] a)
{
    long s = 0;
    for (int i = 0; i < a.Length; i++)
        if (a[i] >= 128)      // непредсказуемое условие на случайных данных
            s += a[i];
    return s;
}

Array.Sort(data);             // после сортировки условие предсказуемо:
                              // сначала всегда false, потом всегда true
// Sum(data) на отсортированном массиве быстрее в 2–6 раз при том же
// количестве операций. Меняется только точность предсказателя переходов.
```

Мерить такое надо через [[Как измерять: BenchmarkDotNet]], а не `Stopwatch` в `Main`: без прогрева JIT цифры врут.

## Память: пирамида, а не ящик

Главная причина, по которой «правильный» алгоритм бывает медленным, — разрыв между скоростью процессора и скоростью RAM. Процессор с 1990-х ускорился в ~100 раз, память по задержке — в ~3 раза. Этот разрыв («memory wall») закрывают кешами.

Порядки величин (для интуиции; на конкретной машине отличаются в разы):

| Уровень | Задержка | В «человеческих» единицах | Объём |
|---|---|---|---|
| Регистр | 0–1 такт | сейчас | ~200 байт |
| L1 cache | ~4 такта (≈1 нс) | 1 секунда | 32–192 КБ на ядро |
| L2 cache | ~12 тактов | 3 секунды | 0,5–16 МБ |
| L3 cache | ~40 тактов | 10 секунд | 8–256 МБ, общий на ядра |
| RAM | ~200 тактов (60–100 нс) | 1 минута | гигабайты |
| NVMe SSD | 50–100 мкс | 1 день | терабайты |
| Сеть в дата-центре | 0,5–1 мс | 1–2 недели | — |
| Сеть между континентами | 100–200 мс | 5 лет | — |

> [!info] Проверить свою машину
> На macOS: `sysctl -a | grep hw.*cache` покажет размеры кешей и длину строки кеша (`hw.cachelinesize`). На Linux — `lscpu` и `/sys/devices/system/cpu/cpu0/cache/`. Разница между x86-64 и Apple Silicon тут существенная, поэтому лучше посмотреть, а не запоминать чужие цифры.

### Строка кеша и локальность

Память подтягивается в кеш не байтами, а **строками кеша** (cache line) — блоками по 64 байта (на Apple Silicon — 128). Прочитал один `int` — в L1 приехали соседние 16 `int`. Отсюда два правила, которые объясняют больше, чем любые микрооптимизации:

- **Пространственная локальность:** данные, лежащие рядом, обрабатывать дешевле. Массив быстрее связного списка не потому, что «списки плохие», а потому что элементы массива физически рядом.
- **Временная локальность:** данные, которые только что использовал, ещё в кеше.

```csharp
const int N = 4096;
var m = new int[N, N];       // ~64 МБ, в кеш целиком не влезает

// Обход по строкам: идём по памяти последовательно.
long SumByRows()
{
    long s = 0;
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++)
            s += m[i, j];
    return s;
}

// Обход по столбцам: каждый шаг — прыжок на 16 КБ вперёд.
long SumByColumns()
{
    long s = 0;
    for (int j = 0; j < N; j++)
        for (int i = 0; i < N; i++)
            s += m[i, j];
    return s;
}

// Одинаковое количество сложений. Разница на практике — 5–10 раз.
// Причина одна: в первом случае почти все обращения попадают в кеш,
// во втором почти каждое — промах и поход в RAM.
```

В .NET многомерный массив `int[N, N]` хранится по строкам (row-major): `m[0,0], m[0,1], … m[0,N-1], m[1,0], …`. Поэтому «внутренний цикл по последнему индексу» — правило, а не вкусовщина.

### Стек и куча — откуда они берутся

ОС даёт процессу непрерывное виртуальное адресное пространство. Как его использовать, решает рантайм. .NET использует:

- **Стек (stack)** — на поток, обычно 1 МБ (в .NET по умолчанию 1 МБ для основного потока). Растёт вниз, работает как LIFO: вызов метода кладёт кадр (stack frame) с параметрами, локальными переменными и адресом возврата, выход — снимает. Выделение стоит одну инструкцию — сдвиг регистра указателя стека. Освобождение бесплатно.
- **Куча (heap)** — общая на процесс, произвольный порядок выделения и освобождения. В .NET освобождением занимается сборщик мусора — [[Сборка мусора (GC): как работает]].

```
Виртуальное адресное пространство процесса (упрощённо)

0x0000...  ┌────────────────────┐
           │ код (text)         │  инструкции, только чтение
           ├────────────────────┤
           │ статические данные │
           ├────────────────────┤
           │        КУЧА        │  растёт вверх ↓ (new)
           │          ↓         │
           │                    │
           │          ↑         │
           │        СТЕК        │  растёт вниз ↑ (вызовы методов)
0xFFFF...  └────────────────────┘
```

Бесконечная рекурсия упирается в границу стека → `StackOverflowException`, которую в .NET **нельзя поймать**: процесс убивается немедленно, потому что перехватчику негде выполняться. Утечка объектов в куче → `OutOfMemoryException`, её поймать можно, но обычно бессмысленно.

Подробный разбор, что именно из C# попадает на стек, а что в кучу (и почему «структуры живут на стеке» — неточность), — [[Value types vs Reference types]] и [[Стек и куча: что где лежит]].

### Виртуальная память

Программа никогда не видит физических адресов. ОС и блок MMU в процессоре переводят виртуальные адреса в физические по таблицам страниц (page tables). Страница — 4 КБ на x86-64 Linux/Windows, 16 КБ на macOS/Apple Silicon.

Это даёт три вещи:

1. **Изоляцию.** Процесс не может прочитать память другого процесса: его адреса просто не отображены. Обращение по неотображённому адресу → page fault → на уровне .NET это `NullReferenceException`/`AccessViolationException`.
2. **Иллюзию большой памяти.** Неиспользуемые страницы вытесняются на диск (swap). Приложение продолжает работать, но с задержками диска вместо RAM — отсюда «сервер живой, но всё висит».
3. **Ленивое выделение.** `new byte[1_000_000_000]` резервирует адреса; физические страницы выделяются при первом обращении. Поэтому «выделенная» и «использованная» память в мониторинге — разные числа.

> [!warning] Подводные камни
> - **«У меня 32 ГБ RAM, память не проблема».** Проблема не в объёме, а в задержке. Код, который обходит 200 МБ данных случайным порядком, будет медленным на любом объёме памяти.
> - **Считать, что `Stopwatch` в консольном приложении измеряет код.** Первый вызов метода включает JIT-компиляцию, первый обход массива — прогрев кеша, ОС может переселить поток на другое ядро. Без BenchmarkDotNet цифры отличаются от реальных в разы.
> - **Путать выделение и освобождение.** Выделение в куче .NET почти так же дешёво, как в стеке (сдвиг указателя). Дорого — последующая сборка мусора и промахи кеша из-за фрагментации. Поэтому совет «меньше аллокаций» — про GC и кеш, а не про сам `new`.
> - **Swap на сервере.** Если продовый сервис начал свапиться, latency вырастает на порядки, а метрики CPU выглядят нормально. Это одна из самых неочевидных production-проблем.

## Операционная система: кто на самом деле хозяин

Процессор один (точнее, несколько ядер), программ — сотни. Разделением занимается ОС.

### Процесс и поток

- **Процесс** — программа со своим адресным пространством, дескрипторами файлов, правами. `dotnet myapp.dll` — один процесс.
- **Поток (thread)** — единица планирования внутри процесса: свой стек и свои регистры, но общая куча со всеми потоками процесса. Отсюда весь класс проблем многопоточности: два потока видят один и тот же объект.

Планировщик ОС выдаёт потоку квант времени (обычно 10–30 мс) и по истечении переключает контекст: сохраняет регистры, загружает регистры другого потока. Переключение стоит 1–10 микросекунд плюс потеря разогретого кеша. Поэтому «создать поток на каждый запрос» — плохая идея: 1000 потоков будут заняты в основном переключением друг между другом. Как .NET решает это через пул потоков и `async` — [[Процессы, потоки и планировщик ОС]] и [[Thread и ThreadPool]].

### Режим ядра и системные вызовы

Инструкции делятся на пользовательские и привилегированные. Прямого доступа к диску, сети или чужой памяти у приложения нет — оно делает **системный вызов** (syscall): `read`, `write`, `mmap`, `socket`. Переход в режим ядра и обратно стоит порядка 1 микросекунды.

```csharp
// Каждая строка ниже — как минимум один системный вызов.
File.WriteAllText("out.txt", "hello");          // open + write + close
using var client = new HttpClient();
var body = await client.GetStringAsync("http://localhost:5000/ping"); // socket + connect + send + recv
Console.WriteLine(body);                        // write в дескриптор stdout
```

Отсюда правило, которое потом объяснит асинхронность: **I/O медленный не потому, что процессор занят, а потому что процессор ждёт**. Поток, зависший на `read` с диска или из сети, не потребляет CPU — он спит. Задача `async`/`await` — не ускорить I/O, а не держать поток в ожидании. См. [[async и await: как это работает на самом деле]].

### Что из этого нужно знать про macOS, Linux и Windows

.NET кроссплатформенный, но различия протекают в код:

| | Windows | Linux (в т.ч. контейнеры) | macOS |
|---|---|---|---|
| Разделитель путей | `\` | `/` | `/` |
| Регистр в именах файлов | не важен | важен | по умолчанию не важен (APFS case-insensitive) |
| Перевод строки | `\r\n` | `\n` | `\n` |
| Where прод | реже | почти всегда | никогда |

Практический вывод: писать `Path.Combine(a, b)` вместо `a + "\\" + b` и `Environment.NewLine` вместо `"\r\n"`. И помнить: код, который работает на macOS локально, может упасть в Linux-контейнере из-за регистра в имени файла — это одна из самых частых «мистических» ошибок при первом деплое. Про терминал и файловую систему — [[Командная строка Linux для .NET-разработчика]].

> [!example] Как делают в бою
> Знание железа применяется на трёх типовых задачах.
> **Первая:** выбрать структуру данных. «Список из 10 000 элементов, часто ищем по ключу» → `Dictionary`, потому что O(1) вместо O(n). «Список из 20 элементов, только перебор» → массив, потому что O(n) по кешу быстрее хеширования. См. [[Обзор коллекций .NET и как выбирать]].
> **Вторая:** объяснить деградацию под нагрузкой. RPS растёт линейно, потом резко падает — почти всегда это либо исчерпание пула потоков из-за блокирующего I/O, либо GC, либо промахи кеша при разрастании рабочего набора данных.
> **Третья:** оценить, где вообще смысл оптимизировать. Если запрос идёт в базу на другом хосте (1 мс) и обрабатывает 100 объектов в памяти (микросекунды), микрооптимизация кода бессмысленна — вся стоимость в сетевом обращении и SQL. Порядки величин из таблицы выше нужны именно для этого.

## Вопросы с собеседований

> [!question]- Что такое стек и куча, и чем они отличаются?
> Стек — область памяти на каждый поток, работающая как LIFO: кадр вызова метода кладётся при входе и снимается при выходе. Размер фиксирован (~1 МБ по умолчанию), выделение стоит одну инструкцию, освобождение автоматическое и бесплатное, память всегда «горячая» в кеше. Куча — общая на процесс область, объекты живут произвольное время, освобождением занимается GC. В стеке лежат кадры вызовов, ссылки и значимые типы, не захваченные замыканиями и не упакованные; в куче — экземпляры классов, массивы и всё, что переживает вызов метода. Переполнение стека фатально и неперехватываемо, исчерпание кучи даёт `OutOfMemoryException`.

> [!question]- Почему обход двумерного массива по столбцам медленнее, чем по строкам?
> Потому что .NET хранит `int[N,N]` по строкам, а память подтягивается в кеш блоками по 64/128 байт. При обходе по строкам одна загрузка строки кеша обслуживает 16 следующих обращений — почти все попадания в L1. При обходе по столбцам каждый шаг прыгает на длину строки массива вперёд, и каждая загрузка кеша используется на один элемент из шестнадцати, остальное — промахи и обращения в RAM (~200 тактов вместо 4). Число арифметических операций при этом одинаково: разница целиком в подсистеме памяти.

> [!question]- Что происходит при переключении контекста и почему много потоков — это плохо?
> ОС сохраняет регистры и указатель стека текущего потока, загружает состояние другого и передаёт ему управление; прямая стоимость — единицы микросекунд, косвенная — потеря разогретых L1/L2 (новый поток работает с другими данными) и возможная миграция на другое ядро. Пока потоков примерно столько, сколько ядер, это незаметно. При тысяче потоков процессор значительную часть времени тратит на переключения и промахи кеша, а каждый поток дополнительно занимает ~1 МБ виртуальной памяти под стек. Правильный ответ на «много одновременных операций» — не много потоков, а асинхронный I/O: ожидание сети не требует потока вообще.

> [!question]- Зачем нужна виртуальная память, если физической и так хватает?
> Три причины помимо объёма. Изоляция: процессы физически не могут обратиться к чужой памяти, потому что их виртуальные адреса не отображены в чужие физические страницы — это база безопасности ОС. Гибкость размещения: программа видит непрерывное адресное пространство, хотя физические страницы разбросаны по RAM; это позволяет ОС выделять память кусками и не заниматься дефрагментацией физической памяти. Ленивое выделение: страницы отдаются при первом обращении, поэтому резервирование больших буферов дешёво, а «выделенная» память в метриках отличается от фактически занятой (RSS).

> [!question]- Почему одна и та же программа на Apple Silicon и на сервере Intel может вести себя по-разному?
> Разный набор инструкций (ARM64 против x86-64) — JIT генерирует разный машинный код, разные векторные расширения (NEON/SVE против AVX2/AVX-512), поэтому векторизованный код ускоряется неодинаково. Разная модель памяти: ARM64 слабее упорядочивает обращения к памяти, и код с состоянием гонки, который «работал» на x86, на ARM ломается — это классический источник плавающих багов в многопоточном коде. Разный размер страницы (16 КБ против 4 КБ) и длина строки кеша влияют на потребление памяти и на бенчмарки. Плюс контейнеры: `linux/amd64`-образ на ARM-хосте пойдёт через эмуляцию и будет заметно медленнее.

## Задачи

### Задача 1. Измерить длину строки кеша

Не заглядывая в документацию, покажи существование строки кеша: пройди по массиву с разным шагом и найди шаг, после которого время перестаёт расти.

> [!success]- Решение
> ```csharp
> using System.Diagnostics;
>
> const int size = 64 * 1024 * 1024;           // 64 МБ, заведомо больше L3
> var data = new byte[size];
>
> for (int step = 1; step <= 512; step *= 2)
> {
>     var sw = Stopwatch.StartNew();
>     // Одинаковое количество итераций при любом шаге —
>     // меняется только «плотность» обращений к памяти.
>     for (int rep = 0; rep < 4; rep++)
>         for (int i = 0; i < size; i += step)
>             data[i]++;
>     sw.Stop();
>     Console.WriteLine($"шаг {step,4}: {sw.ElapsedMilliseconds,5} мс");
> }
> ```
> Пока шаг меньше длины строки кеша, число обращений падает вдвое с каждым удвоением шага, но количество загруженных строк кеша не меняется — время держится примерно на одном уровне. Начиная с шага, равного длине строки (64 или 128 байт), каждое обращение требует своей строки, и время начинает падать пропорционально числу итераций. Точка перелома и есть длина строки кеша. Для аккуратных цифр этот эксперимент надо переносить в BenchmarkDotNet, но эффект виден и так.

### Задача 2. Оценить стоимость по порядкам

Эндпоинт делает: один запрос в PostgreSQL на соседнем хосте, десериализацию 200 КБ JSON, сортировку 1000 объектов в памяти и запись строки в лог-файл. Расставь операции по вкладу в общее время и скажи, что оптимизировать первым.

> [!success]- Решение
> Порядок примерно такой: сетевое обращение к БД (0,5–2 мс, плюс время самого запроса — часто 1–50 мс) → десериализация JSON (десятки–сотни микросекунд, плюс аллокации и последующая работа GC) → запись в лог (микросекунды, если буферизована; миллисекунды, если каждый вызов делает `flush` на диск) → сортировка 1000 объектов (единицы микросекунд).
> Оптимизировать надо запрос к БД: индексы, объём выбираемых данных, число обращений (проблема N+1). Сортировка 1000 элементов не имеет значения — это шум на фоне сети. Общее правило: сначала убрать походы по сети и на диск, потом аллокации, и только потом арифметику.

### Задача 3. Почему это падает и как это поймать

```csharp
static int Depth(int n) => 1 + Depth(n + 1);
Console.WriteLine(Depth(0));
```

Что произойдёт при запуске и можно ли обработать это `try/catch`?

> [!success]- Решение
> Каждый вызов кладёт на стек кадр (адрес возврата, параметр, служебные данные). Стек основного потока ограничен ~1 МБ, кадр занимает десятки байт — через несколько сотен тысяч вызовов свободное место кончается, поток обращается к странице за границей стека, и процесс завершается с `StackOverflowException`. Поймать её нельзя: начиная с .NET Framework 2.0 рантайм не даёт перехватить это исключение и убивает процесс, потому что для выполнения блока `catch` тоже нужен стек, а его нет. Правильный подход — не полагаться на `catch`, а ограничивать глубину: переписать рекурсию в цикл или явно передавать и проверять глубину. Кстати, здесь JIT не может применить хвостовую оптимизацию: результат вызова участвует в сложении, значит кадр нужен.

## Итог

- Процессор умеет мало: перекладывать байты, считать и переходить. Всё остальное — абстракции компилятора и рантайма.
- Производительность современного кода определяется памятью, а не арифметикой: разница между попаданием в L1 и походом в RAM — 50 раз.
- Данные, лежащие рядом, обрабатываются кратно быстрее. Это причина, по которой массив обычно быстрее списка, а обход по строкам — быстрее обхода по столбцам.
- Стек — быстрый, маленький, на поток, освобождается сам. Куча — большая, общая, требует GC.
- Виртуальная память даёт изоляцию, ленивое выделение и swap; последний — тихий убийца latency на проде.
- ОС переключает потоки за микросекунды, но с потерей кеша: масштабироваться надо асинхронностью, а не количеством потоков.
- Держи в голове таблицу порядков величин — она отвечает на вопрос «что вообще имеет смысл оптимизировать».
