# Системы счисления и представление данных

> [!abstract] Коротко
> В памяти нет ни чисел, ни букв — только байты. Смысл байтам придаёт тип: одни и те же четыре байта могут быть числом 1 065 353 216, числом с плавающей точкой 1.0f или четырьмя символами. Отсюда растут вещи, которые иначе выглядят мистикой: почему `0.1 + 0.2 != 0.3`, почему `Math.Abs(int.MinValue)` бросает исключение, почему `"👍".Length == 2` и почему кириллица в файле иногда превращается в «Ð¿Ñ€Ð¸Ð²ÐµÑ‚». Эта заметка — про то, как именно значения лежат в байтах.

## Зачем это нужно

Три ситуации, в которых незнание этого стоит денег:

1. **Финансовые расчёты.** Сумма в `double` через год расчётов расходится с бухгалтерией на копейки, потом на рубли. Правильный тип — `decimal`, и надо понимать, почему.
2. **Границы типов.** Счётчик в `int` доходит до 2 147 483 647 и молча становится отрицательным. Идентификатор в `int` заканчивается на 2 миллиардах записей — реальная авария в проектах, где `id` не сделали `long`.
3. **Кодировки.** Файл, выгруженный на macOS, читается сервисом в Linux-контейнере как мусор. Или наоборот: JSON с эмодзи ломает выравнивание строк и обрезку по длине.

Плюс это стандартный блок вопросов на собеседовании: «сколько байт в `int`», «что такое дополнительный код», «чем `char` отличается от `byte`», «почему сравнение `double` через `==` — плохая идея».

## Позиционные системы счисления

Число в позиционной системе — сумма цифр, умноженных на степень основания:

```
     Десятичное 205  = 2·10² + 0·10¹ + 5·10⁰
     Двоичное 11001101 = 1·2⁷ + 1·2⁶ + 0·2⁵ + 0·2⁴ + 1·2³ + 1·2² + 0·2¹ + 1·2⁰ = 205
     Шестнадцатеричное CD = 12·16¹ + 13·16⁰ = 205
```

Компьютер использует двоичную, потому что транзистор различает два состояния надёжно, а десять — нет. Программист использует шестнадцатеричную, потому что она — компактная запись двоичной: **одна hex-цифра = ровно 4 бита**, две hex-цифры = один байт.

| Двоичное | Hex | Десятичное | | Двоичное | Hex | Десятичное |
|---|---|---|---|---|---|---|
| 0000 | 0 | 0 | | 1000 | 8 | 8 |
| 0001 | 1 | 1 | | 1001 | 9 | 9 |
| 0010 | 2 | 2 | | 1010 | A | 10 |
| 0011 | 3 | 3 | | 1011 | B | 11 |
| 0100 | 4 | 4 | | 1100 | C | 12 |
| 0101 | 5 | 5 | | 1101 | D | 13 |
| 0110 | 6 | 6 | | 1110 | E | 14 |
| 0111 | 7 | 7 | | 1111 | F | 15 |

Эту таблицу стоит выучить: она нужна при чтении дампов памяти, хешей, цветов (`#FF6600`), флагов и масок.

### Запись в C#

```csharp
int dec = 205;              // десятичный
int hex = 0xCD;             // шестнадцатеричный
int bin = 0b1100_1101;      // двоичный (C# 7.0), _ — разделитель разрядов (C# 7.0)
long big = 1_000_000_000;   // разделители читаются глазами, компилятором игнорируются

Console.WriteLine(dec == hex && hex == bin);   // Вывод: True

// Обратно в строку:
Console.WriteLine(Convert.ToString(205, 2));   // Вывод: 11001101
Console.WriteLine(205.ToString("X"));          // Вывод: CD
Console.WriteLine(205.ToString("X4"));         // Вывод: 00CD
Console.WriteLine($"{205:b8}");                // Вывод: 11001101  (формат "b" — .NET 8+)
```

## Целые числа

### Размеры и границы

| Тип C# | Тип .NET | Байт | Диапазон |
|---|---|---:|---|
| `sbyte` | `SByte` | 1 | −128 … 127 |
| `byte` | `Byte` | 1 | 0 … 255 |
| `short` | `Int16` | 2 | −32 768 … 32 767 |
| `ushort` | `UInt16` | 2 | 0 … 65 535 |
| `int` | `Int32` | 4 | −2 147 483 648 … 2 147 483 647 |
| `uint` | `UInt32` | 4 | 0 … 4 294 967 295 |
| `long` | `Int64` | 8 | ±9,22·10¹⁸ |
| `ulong` | `UInt64` | 8 | 0 … 1,8·10¹⁹ |
| `nint`/`nuint` | `IntPtr`/`UIntPtr` | 4 или 8 | размер указателя платформы |
| `Int128`/`UInt128` | — | 16 | ±1,7·10³⁸ (.NET 7+) |
| `BigInteger` | — | сколько нужно | без ограничений, из `System.Numerics` |

Числа в диапазоне до 2 миллиардов — `int`, это дефолт по умолчанию и в API .NET (`Length`, `Count`, индексы). Всё, что может расти без предела (идентификаторы в БД, счётчики событий, размеры в байтах у больших файлов), — `long` сразу, менять потом дорого.

### Дополнительный код: как хранится минус

Отрицательные числа хранятся в **дополнительном коде** (two's complement). Правило: чтобы получить `-x`, инвертируй все биты `x` и прибавь 1.

```
  5  = 0000_0101
 ~5  = 1111_1010    (инверсия)
 +1  = 1111_1011    = -5 в дополнительном коде (для sbyte)
```

Почему так, а не «отдельный бит знака»: при таком представлении вычитание — это обычное сложение, и процессору не нужна отдельная схема. Плюс нет двух нулей (`+0` и `−0`).

Два следствия, которые попадаются на практике:

```csharp
// 1. Диапазон асимметричен: отрицательных значений на одно больше.
Console.WriteLine(int.MinValue);            // -2147483648
Console.WriteLine(int.MaxValue);            //  2147483647
// Console.WriteLine(Math.Abs(int.MinValue));  // OverflowException:
//    +2147483648 не существует в int, представить результат невозможно

// 2. Старший бит — знак, поэтому сдвиги вправо для знаковых типов
//    «дотягивают» знак (арифметический сдвиг).
int negative = -8;
Console.WriteLine(negative >> 1);           // Вывод: -4   (заполняется единицами)
Console.WriteLine(negative >>> 1);          // Вывод: 2147483644 — беззнаковый сдвиг (C# 11)
```

### Переполнение: тихое по умолчанию

```csharp
int max = int.MaxValue;
Console.WriteLine(max + 1);        // Вывод: -2147483648 — без исключения!

// Биты: 0111...1111 + 1 = 1000...0000, а это минимальное отрицательное.
```

По умолчанию арифметика в C# **unchecked**: переполнение молча заворачивается по кругу. Это осознанный выбор в пользу скорости — проверка на каждой операции стоит такты. Как включать проверки локально (`checked`) и глобально (`<CheckForOverflowUnderflow>`), разобрано в [[Числа, деньги и округление]].

### Битовые операции

```csharp
int a = 0b1100;   // 12
int b = 0b1010;   // 10

Console.WriteLine(Convert.ToString(a & b, 2));   // 1000  — AND, оба бита
Console.WriteLine(Convert.ToString(a | b, 2));   // 1110  — OR, хотя бы один
Console.WriteLine(Convert.ToString(a ^ b, 2));   // 110   — XOR, ровно один
Console.WriteLine(Convert.ToString(~a, 2));      // ...11110011 — NOT, инверсия
Console.WriteLine(a << 2);                       // 48 — сдвиг влево = умножение на 4
Console.WriteLine(a >> 2);                       // 3  — сдвиг вправо = деление на 4
```

Где это реально встречается в бэкенде:

- **Флаги.** Набор булевых признаков одним числом — см. [[Записи (record) и структуры]] и `[Flags]`.
- **Хеши и идентификаторы.** `GetHashCode` почти всегда комбинирует поля через сдвиги и XOR — см. [[Object: Equals, GetHashCode, ToString]].
- **Битовые маски прав** в моделях доступа, где ролей мало и они не меняются.
- **Готовые помощники** вместо ручных велосипедов: `BitOperations.PopCount`, `LeadingZeroCount`, `IsPow2`, `RoundUpToPowerOf2` из `System.Numerics`.

```csharp
using System.Numerics;
Console.WriteLine(BitOperations.PopCount(0b1011u));   // Вывод: 3 — сколько единичных бит
Console.WriteLine(BitOperations.IsPow2(64));          // Вывод: True
```

## Числа с плавающей точкой: почему 0.1 + 0.2 != 0.3

`float` и `double` устроены по стандарту IEEE 754: знак, показатель (экспонента) и мантисса.

```
double (64 бита):
 ┌─┬───────────┬────────────────────────────────────────────────────┐
 │S│  exponent │                   mantissa                         │
 │1│    11     │                     52                             │
 └─┴───────────┴────────────────────────────────────────────────────┘

значение = (−1)^S · 1.mantissa · 2^(exponent − 1023)
```

Мантисса двоичная. Это значит, что точно представимы только дроби, которые раскладываются в конечную сумму степеней двойки: 0,5, 0,25, 0,75, 0,125. А `0.1` в двоичной системе — бесконечная периодическая дробь, ровно как 1/3 в десятичной. Она обрезается по 52 битам, и появляется ошибка.

```csharp
Console.WriteLine(0.1 + 0.2);                 // Вывод: 0,30000000000000004
Console.WriteLine(0.1 + 0.2 == 0.3);          // Вывод: False
Console.WriteLine((0.1).ToString("R"));       // Вывод: 0,1  — round-trip формат скрывает погрешность
Console.WriteLine((0.1 + 0.2).ToString("G17"));// Вывод: 0,30000000000000004

// Накопление ошибки:
double sum = 0;
for (int i = 0; i < 1000; i++) sum += 0.1;
Console.WriteLine(sum);                        // Вывод: 99,9999999999986
```

### decimal: другой компромисс

`decimal` — 128 бит: 96-битная целая мантисса, знак и десятичный масштаб (0…28). Он хранит **степени десятки**, а не двойки, поэтому 0,1 представим точно.

```csharp
Console.WriteLine(0.1m + 0.2m == 0.3m);       // Вывод: True

decimal dsum = 0;
for (int i = 0; i < 1000; i++) dsum += 0.1m;
Console.WriteLine(dsum);                       // Вывод: 100,0
```

| | `double` | `decimal` |
|---|---|---|
| Размер | 8 байт | 16 байт |
| Значащих цифр | ~15–17 | 28–29 |
| Основание мантиссы | 2 | 10 |
| Диапазон | ±1,7·10³⁰⁸ | ±7,9·10²⁸ |
| Скорость | аппаратная, быстро | программная, в 10–20 раз медленнее |
| Для чего | физика, метрики, статистика, графика | деньги, финансы, всё, что сверяют с бухгалтерией |

Правило: **деньги — только `decimal`** (в БД — `numeric`/`decimal`, не `float`). Альтернатива для высоконагруженных систем — хранить целое количество минимальных единиц (копеек, тийинов) в `long`, но тогда округление и деление придётся писать руками.

### Особые значения

```csharp
Console.WriteLine(1.0 / 0);                   // Вывод: ∞          (double.PositiveInfinity)
Console.WriteLine(-1.0 / 0);                  // Вывод: -∞
Console.WriteLine(0.0 / 0);                   // Вывод: NaN
Console.WriteLine(double.NaN == double.NaN);   // Вывод: False — по стандарту NaN не равен ничему,
                                              // включая себя. Проверять через double.IsNaN().
Console.WriteLine(1 / 0);                     // DivideByZeroException — у целых деление на ноль
                                              // это исключение, у плавающих — бесконечность
```

`NaN`, ломающий сравнение, — источник настоящих багов: `Array.Sort` на массиве с `NaN` даёт неожиданный порядок, `Max`/`Min` возвращают `NaN`, а `dictionary[double.NaN]` не находит значение, положенное по этому же ключу.

> [!warning] Подводные камни
> - **`double.Epsilon` — не допуск для сравнения.** Это наименьшее положительное денормализованное число (≈5·10⁻³²⁴), сравнение с ним бессмысленно. Сравнивать надо с относительным допуском: `Math.Abs(a - b) <= tolerance * Math.Max(Math.Abs(a), Math.Abs(b))`, где `tolerance` подобран под задачу.
> - **`float` для денег «потому что памяти меньше»** — 7 значащих цифр. Сумма 1 234 567,89 уже не влезает без потерь.
> - **Целочисленное деление там, где ждали дробь.** `1 / 2` — это `0`, потому что оба операнда `int`. Надо `1 / 2.0` или `1m / 2`.
> - **Сложение чисел разного масштаба.** `1e16 + 1 == 1e16` даёт `True`: единица теряется, мантиссы не хватает. При суммировании больших наборов данных порядок слагаемых меняет результат — отсюда алгоритмы вроде компенсированного суммирования Кэхэна.
> - **`decimal` хранит масштаб.** `1.0m` и `1.00m` равны по `==`, но `ToString()` даёт разные строки, а `GetHashCode` одинаковый. Округление задаётся явно: `Math.Round(x, 2, MidpointRounding.AwayFromZero)` — иначе по умолчанию работает «банковское» округление к чётному, и `Math.Round(2.5)` даст 2.

## Символы, строки и кодировки

### Как дошли до Unicode

- **ASCII (1963)** — 7 бит, 128 символов: латиница, цифры, знаки, управляющие. Кириллицы нет.
- **Однобайтовые кодировки** — вторая половина таблицы (128–255) под национальный алфавит: `windows-1251` и `KOI8-R` для кириллицы, `ISO-8859-1` для западной Европы. Проблема очевидна: один и тот же байт 0xC0 — это «А» в 1251 и «ю» в KOI8-R. Отсюда легендарная «кракозябра».
- **Unicode** — единая таблица для всех письменностей. Присваивает каждому символу номер (code point) от U+0000 до U+10FFFF (1,1 млн позиций, занято ~150 тысяч). Unicode — это **таблица номеров, а не способ хранения**. Способов хранения несколько:

| Кодировка | Байт на символ | Где применяется |
|---|---|---|
| UTF-8 | 1 (ASCII) … 4 | файлы, HTTP, JSON, всё в Linux и в интернете — де-факто стандарт |
| UTF-16 | 2 или 4 | внутреннее представление `string` в .NET и Java, Windows API |
| UTF-32 | всегда 4 | почти не используется, расточительно |

UTF-8 устроен так, что ASCII-текст в нём совпадает байт в байт с ASCII, а не-ASCII символы занимают 2–4 байта. Кириллица — 2 байта на букву, эмодзи — 4.

### Как это выглядит в .NET

`string` в .NET — последовательность `char`, а `char` — это **16 бит, одна UTF-16 code unit**, а не «один символ».

```csharp
string s = "Привет";
Console.WriteLine(s.Length);                                  // Вывод: 6 символов
Console.WriteLine(System.Text.Encoding.UTF8.GetByteCount(s));  // Вывод: 12 байт в UTF-8
Console.WriteLine(System.Text.Encoding.Unicode.GetByteCount(s));// Вывод: 12 байт в UTF-16

string emoji = "👍";
Console.WriteLine(emoji.Length);                               // Вывод: 2 (!) — surrogate pair
Console.WriteLine(char.IsSurrogate(emoji[0]));                 // Вывод: True
Console.WriteLine(System.Text.Encoding.UTF8.GetByteCount(emoji));// Вывод: 4

// Правильный способ работать с «символами как их видит человек»:
foreach (var rune in emoji.EnumerateRunes())
    Console.WriteLine(rune.Value.ToString("X"));                // Вывод: 1F44D — один code point

var enumerator = System.Globalization.StringInfo.GetTextElementEnumerator("é👨‍👩‍👦");
// текстовые элементы — «графемы», то, что человек считает одним знаком
```

Символы вне BMP (Basic Multilingual Plane, U+0000–U+FFFF) — эмодзи, редкие иероглифы, часть математических знаков — кодируются **суррогатной парой**: двумя `char`. Поэтому `s.Length` — это число UTF-16 единиц, а не букв, и `s.Substring(0, 10)` может разрезать эмодзи пополам, выдав повреждённую строку.

### Чтение и запись файлов

```csharp
// .NET по умолчанию пишет и читает UTF-8 БЕЗ BOM. Это правильное поведение.
File.WriteAllText("out.txt", "Привет");

// Чтение файла в кодировке windows-1251 (легаси-выгрузки, экспорт из 1С):
// нужен пакет System.Text.Encoding.CodePages — в .NET Core однобайтовых
// кодировок в базовой поставке нет.
System.Text.Encoding.RegisterProvider(System.Text.CodePagesEncodingProvider.Instance);
var legacy = File.ReadAllText("export.csv", System.Text.Encoding.GetEncoding(1251));
```

BOM (byte order mark, `EF BB BF` для UTF-8) — три байта в начале файла, которыми Windows-редакторы помечают кодировку. В UTF-8 он бессмысленен (порядок байтов там не варьируется) и вреден: парсеры CSV и JSON видят его как часть первого поля. Если первое поле CSV «не находится» по имени — почти всегда это BOM.

### Порядок байтов (endianness)

Как разложить `int 0x12345678` по четырём байтам:

```
little-endian (x86-64, ARM64 в обычном режиме):  78 56 34 12   — младший байт первым
big-endian    (сетевой порядок, старые SPARC):   12 34 56 78   — старший байт первым
```

Все актуальные платформы .NET — little-endian, но в сетевых протоколах и бинарных форматах принят big-endian. Поэтому руками байты не переставляют, а берут явные API:

```csharp
using System.Buffers.Binary;

var buffer = new byte[4];
BinaryPrimitives.WriteInt32BigEndian(buffer, 0x12345678);
Console.WriteLine(Convert.ToHexString(buffer));              // Вывод: 12345678
Console.WriteLine(BitConverter.IsLittleEndian);              // Вывод: True на x86-64 и ARM64
```

> [!example] Как делают в бою
> **Деньги.** `decimal` в C#, `numeric(19,4)` в PostgreSQL, никогда не `double`. Округление — только явное и в одном месте кода, с зафиксированным `MidpointRounding`.
> **Идентификаторы.** `long` (`bigint`) для всего, что может вырасти, либо `Guid`/UUIDv7. `int` для справочников из десятка строк.
> **Кодировки.** Везде UTF-8 без BOM: в файлах, в `Content-Type: application/json; charset=utf-8`, в БД (`ENCODING 'UTF8'`). Точка конвертации из легаси-кодировок — одна, на границе системы, а не по всему коду.
> **Обрезка строк.** `title.Length > 50 ? title[..50] : title` — мина: разрежет суррогатную пару или комбинированный символ. Для отображаемого текста обрезать надо по графемам (`StringInfo`), для лимитов БД — считать байты в UTF-8, потому что `varchar(50)` в PostgreSQL — это 50 символов, а в некоторых движках 50 байт.

## Вопросы с собеседований

> [!question]- Почему `0.1 + 0.2 != 0.3` и как с этим жить?
> `double` хранит число как двоичную дробь: знак, 11 бит экспоненты, 52 бита мантиссы. Точно представимы только дроби, разложимые в конечную сумму степеней двойки; 0,1 в двоичной записи — бесконечная периодическая дробь, поэтому она обрезается, и результат сложения отличается от 0,3 на ~5,5·10⁻¹⁷. Для денег и любых сверяемых расчётов используют `decimal` (мантисса целая, масштаб десятичный — 0,1 представима точно). Для физики и статистики `double` оставляют, но сравнивают не через `==`, а по относительному допуску. `double.Epsilon` в роли допуска использовать нельзя — это наименьшее денормализованное число, а не «маленькая погрешность».

> [!question]- Что такое дополнительный код и почему `Math.Abs(int.MinValue)` бросает исключение?
> Дополнительный код — представление отрицательных чисел, при котором `-x` получается инверсией битов `x` плюс единица. Оно позволяет процессору выполнять вычитание тем же сумматором, что и сложение, и убирает «минус ноль». Побочный эффект — асимметрия диапазона: для `int` это −2 147 483 648 … 2 147 483 647, отрицательных значений на одно больше. Модуль `int.MinValue` равен 2 147 483 648, а такого значения в `int` нет, представить результат невозможно — поэтому `Math.Abs` бросает `OverflowException` вместо тихого возврата отрицательного числа. Тот же корень у `-int.MinValue == int.MinValue` в unchecked-контексте.

> [!question]- Чем `char` отличается от `byte`, и почему `"👍".Length` равно 2?
> `byte` — 8 бит, беззнаковое целое 0…255. `char` — 16 бит, одна code unit UTF-16, то есть кусок кодировки, а не «символ». Символы из BMP (U+0000–U+FFFF) занимают один `char`, символы за её пределами (эмодзи, редкие письменности) кодируются суррогатной парой из двух `char`. Поэтому `string.Length` возвращает число UTF-16 единиц: у «👍» их две. Для работы с настоящими code point'ами есть `Rune` и `EnumerateRunes()`, для «того, что человек видит одним знаком» — `StringInfo` и текстовые элементы (графемы), потому что даже один code point не всегда равен одному видимому символу — «é» может быть как U+00E9, так и «e» + комбинирующий акцент.

> [!question]- Чем Unicode отличается от UTF-8?
> Unicode — это стандарт-таблица: он присваивает каждому символу номер (code point) вида U+0041. Он не говорит, как этот номер хранить в байтах. UTF-8, UTF-16, UTF-32 — способы кодирования этих номеров в байты. UTF-8 переменной длины (1–4 байта), обратно совместим с ASCII и потому стал стандартом файлов и сети. UTF-16 — 2 или 4 байта, используется как внутреннее представление строк в .NET. Формально неверная, но частая фраза «файл в кодировке Unicode» на практике означает UTF-16 LE — так этот вариант подписан в блокноте Windows.

> [!question]- Целочисленное переполнение в C#: что происходит по умолчанию?
> По умолчанию контекст `unchecked`: результат заворачивается по модулю 2ⁿ без всяких сигналов, `int.MaxValue + 1` даёт `int.MinValue`. Это сделано ради скорости — проверка на каждой арифметической операции стоит такты. Включить проверки можно выражением `checked(a + b)`, блоком `checked { }` или свойством проекта `<CheckForOverflowUnderflow>true</CheckForOverflowUnderflow>` (обычно включают только для Debug). Исключения: `decimal` всегда бросает `OverflowException` независимо от контекста, а константные выражения проверяются на этапе компиляции — `int x = int.MaxValue + 1;` не соберётся.

## Задачи

### Задача 1. Перевод без Convert

Напиши метод, который переводит неотрицательное целое в двоичную строку, не используя `Convert.ToString` и `ToString("b")`.

> [!success]- Решение
> ```csharp
> static string ToBinary(uint value)
> {
>     if (value == 0) return "0";
>
>     var buffer = new char[32];
>     int pos = 32;
>     while (value > 0)
>     {
>         buffer[--pos] = (char)('0' + (value & 1));  // младший бит
>         value >>= 1;                                // сдвиг вправо = деление на 2
>     }
>     return new string(buffer, pos, 32 - pos);
> }
>
> Console.WriteLine(ToBinary(205));   // Вывод: 11001101
> ```
> Алгоритм — деление на основание с сбором остатков, только вместо `% 2` и `/ 2` используются битовые операции: они выражают то же самое, но точнее передают смысл. Собираем с конца буфера, чтобы не переворачивать строку. `uint` в параметре избавляет от возни со знаком.

### Задача 2. Сколько денег потерялось

```csharp
double price = 0.7;
int count = 100;
Console.WriteLine(price * count);
```

Что выведет и как посчитать правильно?

> [!success]- Решение
> Выведет `69,99999999999999`. Ни 0,7, ни результат умножения не представимы в двоичной плавающей точке точно; погрешность вылезает при выводе, потому что стандартное форматирование `double` в .NET Core 3.0+ печатает кратчайшую строку, которая round-trip'ится в то же значение — и здесь она отличается от «70».
> Правильно:
> ```csharp
> decimal price = 0.7m;
> int count = 100;
> Console.WriteLine(price * count);      // Вывод: 70,0
> ```
> Отдельно опасен вариант с «почти правильным» выводом: `Math.Round(0.7 * 100, 2)` даст ровно 70, и ошибка спрячется — до момента, когда таких умножений в отчёте станет миллион и расхождение с бухгалтерией станет заметным. Тип надо менять, а не округлять симптом.

### Задача 3. Безопасная обрезка строки

Напиши метод, обрезающий строку до `maxLength` символов так, чтобы не разрезать суррогатную пару.

> [!success]- Решение
> ```csharp
> static string SafeTruncate(string value, int maxLength)
> {
>     if (value.Length <= maxLength) return value;
>
>     int end = maxLength;
>     // Если попали на верхний суррогат — его пара осталась за границей,
>     // отступаем на один char назад.
>     if (char.IsHighSurrogate(value[end - 1])) end--;
>
>     return value[..end];
> }
>
> Console.WriteLine(SafeTruncate("ok👍", 3).Length);   // Вывод: 2 — эмодзи не разрезан
> ```
> Проверка `IsHighSurrogate` на последнем оставляемом `char` ловит случай, когда граница пришлась на середину пары: такая строка формально валидна как `string`, но при записи в UTF-8 даст символ-замену U+FFFD, а в JSON — невалидную escape-последовательность. Для текста, показываемого пользователю, надёжнее резать по графемам через `StringInfo.GetTextElementEnumerator`, иначе можно отрезать комбинирующий акцент от буквы или разбить составной эмодзи семьи.

## Итог

- Байт сам по себе не имеет смысла: значение задаёт тип. Hex — просто компактная запись битов, 1 цифра = 4 бита.
- Целые хранятся в дополнительном коде: отсюда асимметричный диапазон, `Math.Abs(int.MinValue)` с исключением и арифметический сдвиг вправо.
- Переполнение целых по умолчанию тихое (`unchecked`); `decimal` — единственный числовой тип, который всегда сигналит.
- `double` — двоичные дроби, поэтому 0,1 неточна. Для денег `decimal` или целые минимальные единицы, и никогда `==` для `double`.
- `NaN` не равен ничему, включая себя; проверять через `double.IsNaN`.
- Unicode — таблица номеров, UTF-8/16 — способы хранения. `string` в .NET — UTF-16, `char` — code unit, а не символ.
- Везде UTF-8 без BOM. Обрезка строк по `Length` — потенциальная порча текста.
