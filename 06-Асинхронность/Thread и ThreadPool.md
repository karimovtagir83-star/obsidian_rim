# Thread и ThreadPool

> [!abstract] Коротко
> Поток ОС — единица планирования: свой стек (резерв 1 МБ на Windows) и регистры, но память процесса общая для всех его потоков. Переключение между потоками стоит 1–10 мкс, а реальная цена выше из-за холодных кешей после переключения — именно поэтому поток нельзя создавать на каждую единицу работы. `Thread` в .NET — тонкая обёртка над потоком ОС, руками её создают почти никогда. `ThreadPool` — статический пул переиспользуемых потоков с work-stealing и алгоритмом hill-climbing; на нём по умолчанию исполняется вся асинхронность — `Task`, `async`/`await`, таймеры, продолжения. Главная беда серверных приложений — thread pool starvation: блокирующий код съедает потоки быстрее, чем пул успевает добавлять новые.

## Зачем это знать

Без этого фундамента `async`/`await` выглядит магией, а тюнинг прода — гаданием. Все решения в дизайне `ThreadPool` и `Task` — прямые следствия того, что потоки ОС дорогие: создание — 50–200 мкс, переключение контекста — единицы-десятки микросекунд с учётом промахов кеша. Большинство проблем производительности .NET-бэкенда в итоге упирается в пул: либо в него насовали блокирующий код, либо от него ждут числа потоков, которого он никогда не даст быстро.

## Модель

### Поток ОС: минимум, который нужен знать

Процесс — изолированное адресное пространство и ресурсы (дескрипторы, токен безопасности). Поток — единица, которую планировщик ставит на ядро: свой стек, свои регистры, свой TLS. Все потоки одного процесса делят кучу, код и дескрипторы — отсюда необходимость синхронизации.

| Что | Порядок величины |
|---|---|
| Резерв стека потока | 1 МБ (Windows, по умолчанию); реально закоммичено 8–64 КБ |
| Создание потока | 50–200 мкс |
| Контекстное переключение | 1–10 мкс + десятки мкс на «прогрев» кешей после |
| Неконтендованный `lock` для сравнения | ~20 нс |

Планировщик ОС вытесняет потоки по истечении кванта (обычно единицы-десятки миллисекунд) — это **вытесняющая многозадачность**, она не спрашивает разрешения у кода. `async`/`await` внутри одного потока — противоположность, **кооперативная модель**: точки `await` и есть точки добровольной уступки. Заблокированный поток (`Waiting`) не грузит CPU, но продолжает держать стек и место в структурах ядра — тысяча заблокированных потоков не про CPU, а про память и планировщик.

`Environment.ProcessorCount` возвращает число логических процессоров с учётом cgroup-лимитов контейнера (с .NET Core 3.0) — от него зависит `MinThreads` пула, число куч Server GC и `MaxDegreeOfParallelism` по умолчанию, см. [[Parallel, PLINQ и параллелизм данных]].

Отсюда правило: **потоки — ресурс уровня десятков, а не тысяч**. Приложению с тысячами одновременных операций асинхронный I/O нужен не из вкуса, а потому что альтернатива физически не масштабируется.

### `Thread` в .NET

```csharp
var thread = new Thread(() => Console.WriteLine(Environment.CurrentManagedThreadId))
{
    IsBackground = true,   // false по умолчанию — держит процесс живым
    Name = "MyWorker",     // видно в дампах и отладчике
};
thread.Start();
thread.Join();
```

`Thread.Abort()` в .NET Core бросает `PlatformNotSupportedException` — метод принципиально небезопасен (исключение могло прилететь в середине `finally`, оставив состояние повреждённым). Единственный способ остановить работу — кооперативная отмена, см. [[CancellationToken и отмена операций]].

Оправданные случаи `new Thread` в серверном коде: вечный цикл, который нельзя отдавать пулу (и то лучше через `BackgroundService`, см. [[Background services и IHostedService]]); нестандартный размер стека (`maxStackSize`) под глубокую рекурсию; STA-поток для COM-интеропа; поток, который должен держать процесс живым (foreground). Всё остальное — `Task`.

### `ThreadPool`: устройство

Статический пул на процесс, из двух категорий потоков: worker threads (пользовательские делегаты — `Task.Run`, продолжения `await`) и I/O completion threads (завершения асинхронного ввода-вывода). У каждого рабочего потока — своя локальная очередь плюс общая глобальная.

```
        глобальная очередь (для работы, поставленной НЕ из потока пула)
                          │
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
   Worker 1 [local]  Worker 2 [local]  Worker 3 [local]
   LIFO для своих  ◄──кража с FIFO-конца──►
```

Работа, поставленная из потока пула (`Task.Run` изнутри задачи, продолжение `await`), уходит в локальную очередь и обрабатывается **LIFO** — последняя добавленная задача горячая в кеше своего ядра, её выгодно взять первой. Когда своя очередь и глобальная пусты, поток «ворует» задачу из чужой локальной очереди — но с противоположного конца, **FIFO**: там лежат самые старые и обычно самые крупные задачи, поэтому кража случается реже и не конкурирует с владельцем за одну и ту же ячейку.

Число потоков подбирает **hill-climbing**: пул измеряет пропускную способность за интервал (порядка 500 мс), вносит небольшое возмущение в число потоков и смотрит на корреляцию с эффектом — расти дальше или откатить. `MinThreads` (по умолчанию `Environment.ProcessorCount`, с учётом cgroups в контейнере) — граница, до которой поток создаётся немедленно, без участия hill-climbing. Сверх неё — прирост примерно на один-два потока в секунду, плюс отдельный детектор голодания, который форсирует добавление, если очередь не пустеет за интервал ни на один элемент. `MaxThreads` — жёсткий потолок в тысячи, практически недостижим и не является инструментом тюнинга.

### Голодание пула (thread pool starvation)

Если код массово блокирует потоки пула (`.Result`, `.Wait()`, синхронный I/O), а MinThreads мал, пул не успевает нарастить число потоков быстрее, чем требуется — очередь растёт, латентность p99 улетает, а **CPU при этом простаивает**. Это ключевой диагностический признак: очередь не пуста + число потоков растёт + низкий CPU. Смотреть через `dotnet-counters monitor System.Runtime` (`ThreadPool Queue Length`, `ThreadPool Thread Count`) или в дампе `dotnet-dump analyze` по стекам с `Task.SpinThenBlockingWait` — см. [[Диагностика в проде: дампы и dotnet-tools]].

Пример масштаба проблемы: на 8 ядрах `MinThreads = 8`. Если разом приходят 200 запросов, каждый блокирует поток на 2 секунды, — первые 8 обслужатся сразу, а чтобы догнать до 200 потоков хватающим по одному-два в секунду пулом, нужны минуты. Всё это время очередь растёт, клиенты ловят таймауты и ретраят, делая нагрузку только хуже.

```csharp
// КАК НЕПРАВИЛЬНО: sync-over-async съедает поток пула на всё время запроса
var data = _httpClient.GetStringAsync(url).Result;

// КАК ПРАВИЛЬНО: поток свободен на время ожидания
var data = await _httpClient.GetStringAsync(url, ct);
```

`ThreadPool.SetMinThreads(n, n)` убирает симптом (потоки создаются сразу), но не лечит причину — каждая блокировка всё равно жрёт стек и место в планировщике. Приемлемо как временная мера на легаси без асинхронной альтернативы, не приемлемо как «настройка производительности» нового кода.

## Решения

| Нужно | Инструмент | Почему |
|---|---|---|
| Короткая единица CPU- или I/O-bound работы | `Task.Run` / `await` | Переиспользует поток пула, не платит за создание |
| Вечный фоновый цикл (читает из очереди, пока не отменят) | `BackgroundService` (`IHostedService`) | Асинхронный цикл не держит поток на ожидании |
| Вечный цикл, который обязан быть отдельным потоком | `Task.Factory.StartNew(..., TaskCreationOptions.LongRunning)` | Планировщик создаёт выделенный поток вне пула |
| Нестандартный размер стека / STA-интероп / foreground-поток | `new Thread(...)` | Единственный способ задать эти параметры |
| Блокирующая чужая библиотека без async-версии | `Task.Run` + `SemaphoreSlim` на ограничение параллелизма | Ограничивает число одновременно съеденных потоков пула |
| Нужен порядок выполнения нескольких задач | `Channel<T>` или явная цепочка `await` | Порядок в пуле — деталь реализации, полагаться нельзя |

> [!example] В ServiceShop
> Прикладной код `ServiceShop` не создаёт `Thread` напрямую — Kestrel держит цикл событий, обработчики MediatR и контроллеры исполняются на потоках пула через `Task`/`async`. Фоновая обработка Outbox идёт через Quartz-джобы, а не через самодельные вечные циклы на `Thread`, поэтому пул не забивается долгоживущей работой. Вызовы внешних HTTP-сервисов и Kafka — асинхронные до конца цепочки; синхронного `.Result` в хендлерах быть не должно — это первое, что проверяют на ревью при жалобах на латентность.

> [!warning] Где ошибаются
> - **Агент часто:** создаёт `new Thread(...)` там, где достаточно `Task.Run` — по привычке к книжным примерам или из желания «явно управлять потоком». В серверном коде это лишний мегабайт резерва стека и потерянные преимущества пула без единой причины из списка выше.
> - **Агент часто:** синхронно блокирует поток из пула — `.Result`, `.Wait()`, `Thread.Sleep` внутри асинхронного метода, синхронный `Read` там, где есть `ReadAsync`. Каждый такой вызов приближает голодание пула под нагрузкой, хотя локально код «просто работает».
> - Полагаются на порядок выполнения задач, поставленных в `ThreadPool` — LIFO для локальной очереди и work-stealing делают порядок недетерминированным между запусками.
> - Лечат симптом голодания через `SetMinThreads`, не убирая блокирующие вызовы — латентность на старте уходит, но каждая заблокированная операция продолжает жечь память и слот планировщика.

## Проверка на ревью

- В хендлерах и контроллерах нет `.Result`, `.Wait()`, `GetAwaiter().GetResult()` на асинхронных вызовах.
- Нет `new Thread(...)` без одной из четырёх оправданных причин (вечный цикл вне пула, нестандартный стек, STA, foreground) — иначе это `Task.Run`.
- Вечный цикл оформлен как `BackgroundService`, а не как `Thread` с `while(true)` в конструкторе.
- Вызов синхронной сторонней библиотеки без async-версии обёрнут в `Task.Run` и ограничен `SemaphoreSlim`, а не запущен без лимита.
- Код не полагается на порядок выполнения нескольких `Task.Run`/`QueueUserWorkItem`.
- `ThreadPool.SetMinThreads` в конфиге объяснён комментарием, а не подобран наугад.

## Проверь себя

> [!question]- Чем `Thread` отличается от `ThreadPool` и когда нужен именно `Thread`?
> `Thread` — конкретный поток ОС, который создаётся под одну задачу и умирает после неё; стоимость создания 50–200 мкс плюс резерв стека. `ThreadPool` — набор потоков, живущих всё время процесса: единица работы ставится в очередь, свободный поток берёт её и возвращается за следующей, число потоков регулирует hill-climbing. `Thread` оправдан для вечного цикла вне пула, нестандартного стека, STA-интеропа и foreground-потока — во всех остальных случаях это `Task`.

> [!question]- Что такое work-stealing и почему кража идёт с другого конца очереди?
> У каждого рабочего потока пула своя локальная очередь, обрабатываемая LIFO — последняя поставленная задача горячая в кеше, её выгодно взять самому. Когда поток простаивает, а глобальная и его локальная очереди пусты, он ворует у другого потока, но с противоположного конца — FIFO. Там лежат самые старые и обычно самые крупные задачи, поэтому вор получает больше работы за одну кражу и не конкурирует с владельцем за одну и ту же ячейку.

> [!question]- Что такое thread pool starvation и по каким признакам её отличить от обычной перегрузки CPU?
> Ситуация, когда потоки пула массово заблокированы, а пул добавляет новые медленно (единицы в секунду сверх MinThreads): очередь растёт, латентность p99 улетает. Ключевой признак — CPU при этом **низкий**: работа не делается, потоки просто ждут. Если CPU 100% — это не starvation, а нехватка вычислительной мощности, и добавление потоков только ухудшит ситуацию лишними переключениями.

> [!question]- Почему `ThreadPool` добавляет потоки так медленно?
> Потому что в подавляющем большинстве случаев больше потоков — не решение, а проблема: для коротких неблокирующихся задач `ProcessorCount` потоков уже полностью загружает машину, а лишние только добавляют контекстные переключения. Hill-climbing проверяет, действительно ли прирост потоков увеличивает пропускную способность, и откатывается, если нет. Быстрый прирост нужен только когда потоки блокируются — а это само по себе признак кода, который стоило написать иначе.

> [!question]- Почему `SetMinThreads` не считается решением проблемы голодания пула?
> Он убирает задержку нарастания пула — новые потоки создаются сразу до заданного порога, симптом (растущая очередь) исчезает. Но каждая заблокированная операция по-прежнему держит поток, резерв стека и слот в планировщике; при достаточной нагрузке голодание вернётся на новом пороге. Настоящее лечение — убрать блокирующие вызовы (`.Result`, `.Wait()`, синхронный I/O) и перейти на `await` до конца цепочки.

> [!question]- Что делает `TaskCreationOptions.LongRunning` и почему это не то же самое, что асинхронный вечный цикл?
> Это подсказка `TaskScheduler`, что делегат будет работать долго; стандартный `ThreadPoolTaskScheduler` реагирует на неё выделенным потоком вне пула, а не постановкой в очередь. Это нужно для по-настоящему синхронного вечного цикла, который иначе навсегда занял бы один из немногих потоков пула. Но если цикл асинхронный (`while (!ct.IsCancellationRequested) await ...`), он и так не держит поток на время ожидания — `LongRunning` в этом случае не нужен, правильный инструмент — `BackgroundService`.

## Разбор

**Дан фрагмент из PR агента:**

```csharp
public async Task<IActionResult> GetReportAsync(int id)
{
    var report = new Thread(() =>
    {
        var data = _client.GetStringAsync($"/reports/{id}").Result;
        _cache[id] = data;
    });
    report.Start();
    report.Join();
    return Ok(_cache[id]);
}
```

Что вернёшь на доработку и почему?

> [!success]- Разбор
> Две независимые проблемы, и обе типично агентные. Первая: `new Thread` создан ради одной короткой операции — это лишний мегабайт резерва стека и 50–200 мкс на создание там, где `Task.Run` или прямой `await` справятся без накладных расходов. Вторая, серьёзнее: внутри этого потока `.Result` блокирует его в ожидании HTTP-ответа — а поскольку это не поток пула, эффект на starvation пула нет, но метод контроллера полностью теряет смысл асинхронности: `report.Join()` синхронно блокирует уже поток пула ASP.NET Core, на котором исполняется сам `GetReportAsync`. Итог — два заблокированных потока вместо нуля. Правильно: убрать `Thread` целиком, `var data = await _client.GetStringAsync($"/reports/{id}");`, `return Ok(data)` — весь смысл ухода от синхронной модели в том, чтобы не блокировать ничего.

**Дано два решения** для вызова синхронной легаси-библиотеки `LegacyReport.Generate(int id)` (2 секунды, без async-версии) для 1000 идентификаторов. Какое обосновать в ревью?

```csharp
// Вариант А
var results = await Task.WhenAll(
    ids.Select(id => Task.Run(() => LegacyReport.Generate(id))));

// Вариант Б
var gate = new SemaphoreSlim(Environment.ProcessorCount * 2);
async Task<Report> GenerateAsync(int id, CancellationToken ct)
{
    await gate.WaitAsync(ct);
    try { return await Task.Run(() => LegacyReport.Generate(id), ct); }
    finally { gate.Release(); }
}
var results = await Task.WhenAll(ids.Select(id => GenerateAsync(id, ct)));
```

> [!success]- Разбор
> Вариант А выглядит проще, но ставит в пул 1000 блокирующих задач одновременно — это гарантированное голодание пула на время выполнения, потому что каждая занимает поток пула на все 2 секунды, а остальная работа приложения в это время встанет в очередь. Вариант Б ограничивает число одновременно занятых потоков семафором (`ProcessorCount * 2` — разумная отправная точка), а `SemaphoreSlim.WaitAsync` не блокирует поток на ожидании своей очереди, так что 1000 «ждущих» вызовов стоят почти ничего. В ревью верный ответ — Б, а число в семафоре должно быть обосновано (профилированием или явным SLA), а не взято произвольно.

## Итог

- Поток ОС дорог (стек, создание, переключение с потерей кешей) — это причина существования пула, а не деталь для галочки.
- `Thread` в серверном коде оправдан только в четырёх случаях: вечный цикл вне пула, нестандартный стек, STA, foreground. Остальное — `Task`.
- `ThreadPool` — локальные очереди LIFO + work-stealing FIFO + hill-climbing, который наращивает потоки медленно, потому что для короткой неблокирующейся работы больше потоков почти всегда хуже.
- Thread pool starvation = растущая очередь + растущее число потоков + низкий CPU; лечится устранением блокировок, `SetMinThreads` только маскирует симптом.
- Блокирующую стороннюю библиотеку без async-версии заворачивай в `Task.Run` с `SemaphoreSlim`, а не вызывай без ограничения.
