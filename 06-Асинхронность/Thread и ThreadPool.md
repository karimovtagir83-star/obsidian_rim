# Thread и ThreadPool

> [!abstract] Коротко
> `Thread` — обёртка над потоком ОС; создавать его руками в серверном коде почти никогда не нужно. `ThreadPool` — статический пул переиспользуемых потоков с глобальной очередью, локальными очередями рабочих потоков и алгоритмом work-stealing; количество потоков в нём подстраивается алгоритмом hill-climbing, который добавляет потоки медленно — примерно по одному-двум в секунду сверх минимума. Отсюда главная беда серверных приложений: **thread pool starvation**, когда блокирующий код съедает потоки быстрее, чем пул успевает их добавлять.

## Зачем это нужно

Создание потока стоит 50–200 мкс и мегабайт резерва стека ([[Процессы, потоки и планировщик ОС]]). Если задача выполняется 100 мкс, накладные расходы на поток больше самой задачи. Пул решает это переиспользованием: поток создаётся один раз и потом бесконечно берёт задачи из очереди.

Всё, что построено выше — `Task`, `async`/`await`, `Parallel`, PLINQ, таймеры, продолжения — по умолчанию исполняется на потоках `ThreadPool`. Понимать его поведение обязательно: большинство проблем производительности в .NET-бэкенде упирается именно в пул.

## Thread: когда он всё-таки нужен

```csharp
var thread = new Thread(() =>
{
    Console.WriteLine($"Работаю в потоке {Environment.CurrentManagedThreadId}");
})
{
    IsBackground = true,     // не удерживает процесс от завершения
    Name = "MyWorker",       // видно в отладчике и дампах
    Priority = ThreadPriority.Normal
};
thread.Start();
thread.Join();               // блокирующее ожидание завершения
```

Ключевые свойства:

| Член | Смысл |
|---|---|
| `IsBackground` | `false` (по умолчанию для `new Thread`) — foreground-поток удерживает процесс живым. `true` — процесс завершится, не дожидаясь потока. Потоки пула **всегда** background |
| `Name` | Не влияет на работу, но критично для отладки: в дампе видно `MyWorker` вместо `Thread 0x1a3c` |
| `Join()` / `Join(timeout)` | Блокирующее ожидание |
| `Interrupt()` | Бросает `ThreadInterruptedException` в потоке, если он в состоянии ожидания. Ненадёжный механизм |
| `Abort()` | **Удалён в .NET Core.** Бросает `PlatformNotSupportedException`. Оставлен только для совместимости исходников |
| `maxStackSize` (в конструкторе) | Размер стека. Единственный способ дать потоку не 1 МБ |

### Оправданные случаи для `new Thread`

1. **Долгоживущий цикл, который никогда не завершится** — например, поток, который читает из именованного pipe весь срок жизни приложения. Отдавать его пулу — значит навсегда занять поток пула. Но и здесь в ASP.NET Core правильнее `BackgroundService` (см. [[Background services и IHostedService]]) с `Task.Factory.StartNew(..., TaskCreationOptions.LongRunning)`.
2. **Нужен нестандартный размер стека** — глубокая рекурсия (парсер, обход дерева):
   ```csharp
   var t = new Thread(ParseDeeplyNested, maxStackSize: 16 * 1024 * 1024);
   ```
3. **Нужна STA-модель** для COM/WinForms-интеропа: `t.SetApartmentState(ApartmentState.STA)`. Потоки пула всегда MTA.
4. **Нужен foreground-поток**, который не даст процессу умереть.

Во всех остальных случаях — `Task.Run` или асинхронный код. `#устарело`: паттерн «создать поток на единицу работы» ушёл вместе с .NET 1.x.

> [!danger] Thread.Abort больше нет
> В .NET Framework можно было убить поток через `Thread.Abort()`. Это было принципиально сломано: `ThreadAbortException` мог прилететь в любой инструкции, включая середину обновления структуры данных или `finally`-блока, оставив состояние приложения повреждённым. В .NET Core метод бросает `PlatformNotSupportedException`. **Единственный способ остановить работу — кооперативная отмена**, см. [[CancellationToken и отмена операций]].

## ThreadPool: устройство

`ThreadPool` — статический класс, единый на процесс. Внутри два разных пула:

1. **Worker threads** — исполняют пользовательские делегаты (`ThreadPool.QueueUserWorkItem`, `Task.Run`, продолжения `await`).
2. **I/O completion threads** — обрабатывают завершения асинхронного ввода-вывода. На Windows это потоки, привязанные к I/O Completion Port. На Linux начиная с .NET 6 в CoreCLR используется собственный `PortableThreadPool` и epoll-цикл; понятие «IOCP threads» там во многом номинально.

### Структура очередей

```
                     ┌────────────────────────────────────────┐
                     │   ГЛОБАЛЬНАЯ очередь (ConcurrentQueue)  │
                     │  сюда попадает работа, поставленная     │
                     │  НЕ из потока пула: Task.Run из Main,   │
                     │  QueueUserWorkItem извне               │
                     └───────────────┬────────────────────────┘
                                     │ (берут, когда своя очередь пуста)
        ┌────────────────────────────┼────────────────────────────┐
        ▼                            ▼                            ▼
  ┌───────────┐               ┌───────────┐                ┌───────────┐
  │ Worker 1  │               │ Worker 2  │                │ Worker 3  │
  │ local q   │◄──кража──────►│ local q   │◄──кража───────►│ local q   │
  │ [A][B][C] │               │  []       │                │ [X][Y]    │
  └───────────┘               └───────────┘                └───────────┘
   LIFO для своих              пусто → идёт                 FIFO при краже
   (горячий кеш)               воровать                     (берёт с хвоста)
```

**Локальная очередь (local queue)** есть у каждого рабочего потока. Если поток пула сам ставит новую работу (типичный случай: `Task.Run` изнутри `Task`, или продолжение `await`), она попадает в его локальную очередь, а не в глобальную. Это даёт две вещи:
- нет конкуренции за глобальную очередь (масштабируемость);
- локальная очередь обрабатывается в порядке **LIFO** — последняя поставленная задача берётся первой, потому что её данные, скорее всего, ещё в кеше L1/L2 этого ядра.

**Work-stealing.** Когда поток исчерпал свою локальную очередь и глобальная тоже пуста, он «ворует» задачу из локальной очереди другого потока — но **с противоположного конца** (FIFO). Это не случайность: с хвоста лежат самые старые и, как правило, самые «крупные» задачи (в дерево-подобных разбиениях), а их владелец в это время работает с головой очереди. Так минимизируется конкуренция за одну и ту же ячейку.

> [!info] Почему LIFO для своих и FIFO для воров
> В рекурсивном разбиении задачи (`Parallel.For` делит диапазон пополам, потом ещё пополам) последняя поставленная подзадача самая мелкая и самая горячая по кешу — её выгодно взять самому. Самая первая поставленная подзадача — самая крупная, её выгодно отдать вору: он получит много работы за одну кражу, и красть придётся реже.

### Сколько потоков в пуле

```csharp
ThreadPool.GetMinThreads(out int minWorker, out int minIo);
ThreadPool.GetMaxThreads(out int maxWorker, out int maxIo);
ThreadPool.GetAvailableThreads(out int availWorker, out int availIo);

Console.WriteLine($"Min: {minWorker} worker / {minIo} io");
// .NET 6+: Min worker = Environment.ProcessorCount
Console.WriteLine($"Max: {maxWorker} worker / {maxIo} io");
// Max — очень большое число (порядка тысяч), фактически не ограничение
```

- **MinThreads** — сколько потоков пул держит «даром»: если запросов работы меньше этого числа, потоки создаются **немедленно, без задержки**. По умолчанию равно `Environment.ProcessorCount`.
- **MaxThreads** — жёсткий потолок, обычно тысячи. Практически недостижим и не является инструментом тюнинга.
- Между Min и Max новые потоки добавляются алгоритмом hill-climbing с задержкой.

### Hill-climbing: как пул подбирает число потоков

Алгоритм (реализация в `PortableThreadPool.HillClimbing.cs`) работает так:

1. Пул измеряет **пропускную способность** — сколько рабочих элементов завершено за интервал (по умолчанию около 500 мс).
2. Он вносит в число потоков небольшое периодическое возмущение (изменяет их количество вверх/вниз) и смотрит, как коррелирует пропускная способность с этим возмущением.
3. Используется дискретное преобразование Фурье, чтобы отделить полезный сигнал от шума.
4. Если рост числа потоков повышает пропускную способность — пул продолжает добавлять; если нет — убирает лишние.

Плюс к этому есть **starvation detection**: если очередь не пуста и за интервал ни один элемент не завершился, пул добавляет поток принудительно. Именно этот механизм и даёт наблюдаемое «примерно один-два потока в секунду».

**Практическое следствие.** Если у тебя 8 ядер (значит MinThreads = 8) и внезапно приходят 200 запросов, каждый из которых блокирует поток на 2 секунды:
- первые 8 обслуживаются сразу;
- остальные ждут, пока пул медленно нарастит потоки;
- чтобы дойти до 200 потоков, нужны минуты;
- всё это время очередь растёт, латентность p99 улетает в небо, срабатывают таймауты, клиенты ретраят и делают хуже.

Это и есть **thread pool starvation** — «голодание пула потоков».

## Thread pool starvation: как выглядит и как лечится

### Как воспроизвести

```csharp
// КАК НЕПРАВИЛЬНО: sync-over-async в контроллере
[HttpGet("/bad")]
public IActionResult Bad()
{
    // .Result блокирует поток пула на всё время сетевого запроса
    var data = _httpClient.GetStringAsync("https://slow-api.example/data").Result;
    return Ok(data);
}
```

При 100 RPS и задержке внешнего API в 1 секунду нужно 100 одновременно заблокированных потоков. Пул нарастит их за полторы-две минуты, к тому времени очередь распухнет, и приложение будет отвечать за 30+ секунд при том, что CPU почти простаивает.

### Как диагностировать

```bash
# Счётчики рантайма
dotnet-counters monitor --process-id <pid> System.Runtime

# Смотрим:
#   ThreadPool Thread Count       — растёт монотонно, много больше числа ядер
#   ThreadPool Queue Length       — стабильно > 0, не разгружается
#   ThreadPool Completed Work Item Count / sec — низкая при высокой очереди
#   CPU Usage                     — НИЗКАЯ. Вот это главный признак:
#                                   очередь есть, потоков много, а CPU простаивает
```

Признак starvation: **очередь не пуста + число потоков растёт + CPU низкий**. Если CPU 100 % — это не starvation, это просто нехватка вычислительной мощности.

В дампе (`dotnet-dump analyze`, команда `clrstack -all`) видно десятки потоков со стеком вида:
```
System.Threading.Monitor.Wait
System.Threading.ManualResetEventSlim.Wait
System.Threading.Tasks.Task.SpinThenBlockingWait     ← вот он, .Result / .Wait()
System.Threading.Tasks.Task`1.get_Result
MyApp.Controllers.BadController.Bad
```

### Как лечится

```csharp
// КАК ПРАВИЛЬНО
[HttpGet("/good")]
public async Task<IActionResult> GoodAsync(CancellationToken ct)
{
    var data = await _httpClient.GetStringAsync("https://slow-api.example/data", ct);
    return Ok(data);
}
```

Настоящее лечение — убрать блокировки. Никакой тюнинг пула не спасёт код, который блокирует потоки.

### Костыль: увеличить MinThreads

```csharp
// В Program.cs, до старта хоста
ThreadPool.SetMinThreads(workerThreads: 200, completionPortThreads: 200);
```

Или через `runtimeconfig.json` / `.csproj`:
```xml
<PropertyGroup>
  <ThreadPoolMinThreads>200</ThreadPoolMinThreads>
  <ThreadPoolMaxThreads>1000</ThreadPoolMaxThreads>
</PropertyGroup>
```

> [!warning] SetMinThreads — это анестезия, а не лечение
> Повышение MinThreads убирает задержку нарастания пула, и симптом уходит. Но ты продолжаешь тратить мегабайт стека и слот планировщика на каждую заблокированную операцию. Приемлемо как временная мера при миграции легаси или когда упираешься в чужую синхронную библиотеку без асинхронной альтернативы. Не приемлемо как «настройка производительности» в новом коде. Слишком большое значение MinThreads вредно само по себе: пул перестаёт саморегулироваться и создаёт потоки без нужды.

## API постановки работы в пул

```csharp
// 1. Самый низкоуровневый (редко нужен напрямую)
ThreadPool.QueueUserWorkItem(state => Console.WriteLine("работаю"), null);

// 2. Без аллокации замыкания — обобщённая версия (.NET Core 3.0+)
ThreadPool.QueueUserWorkItem(
    static (string s) => Console.WriteLine(s),
    "привет",
    preferLocal: false);      // false = в глобальную очередь

// 3. Самый частый способ: Task.Run
await Task.Run(() => HeavyComputation());

// 4. Прямая постановка объекта, реализующего IThreadPoolWorkItem — без аллокаций
//    Используется внутри рантайма и в высокопроизводительных библиотеках
sealed class MyWorkItem : IThreadPoolWorkItem
{
    public void Execute() => Console.WriteLine("выполняюсь без делегата");
}
ThreadPool.UnsafeQueueUserWorkItem(new MyWorkItem(), preferLocal: true);
```

`preferLocal: true` кладёт работу в локальную очередь текущего потока пула (если вызов из потока пула). Полезно, когда работа продолжает текущую цепочку и данные горячие в кеше. `false` — в глобальную, чтобы работу мог подхватить любой свободный поток.

`Unsafe*`-варианты не захватывают `ExecutionContext` (в частности, не переносят `AsyncLocal<T>` и текущего пользователя). Быстрее, но требуют понимания последствий.

## Особые задачи: LongRunning

```csharp
// Долгоживущий цикл. НЕ отдаём поток пула навсегда.
var loop = Task.Factory.StartNew(
    () =>
    {
        while (!token.IsCancellationRequested)
        {
            ProcessBatch();
        }
    },
    token,
    TaskCreationOptions.LongRunning,      // подсказка планировщику
    TaskScheduler.Default);
```

`TaskCreationOptions.LongRunning` — подсказка `TaskScheduler`. Стандартный `ThreadPoolTaskScheduler` реагирует на неё созданием **выделенного потока вне пула**. Это ровно то, что нужно для вечного цикла.

Но в современном ASP.NET Core вечный цикл делают иначе — через `BackgroundService`, где `ExecuteAsync` асинхронный и не занимает поток на ожидании. См. [[Background services и IHostedService]].

> [!warning] Подводные камни
> - **Потоки пула — всегда background.** Если `Main` завершился, а `Task.Run` ещё работает — процесс просто умрёт, задача не доработает. Всегда `await`-ай или `Wait()`-ай задачи, результат которых важен.
> - **Никогда не блокируй поток пула.** `Thread.Sleep`, `.Result`, `.Wait()`, `WaitOne()`, синхронный `Read` из сокета — всё это выводит поток из оборота. Пул рассчитан на то, что элементы работы короткие и не блокируются.
> - **`Task.Run` внутри `Task.Run` не создаёт «больше параллелизма».** Это просто ещё один элемент в локальной очереди того же потока.
> - **Локальная очередь обрабатывается LIFO** — это иногда даёт неожиданный порядок выполнения. Никогда не полагайся на порядок выполнения задач в пуле.
> - **`ThreadPool.SetMaxThreads` нельзя опустить ниже `ProcessorCount`** — вызов вернёт `false` и ничего не сделает.
> - **В контейнере с лимитом CPU MinThreads считается от cgroup-лимита.** При `--cpus=1` MinThreads = 1, и старт даже двух параллельных задач попадёт под hill-climbing. Часто именно это делает холодный старт в Kubernetes медленным.
> - **`ThreadPool` один на процесс.** Библиотека, которая гадит в пул (например, вызывает `.Result`), портит жизнь всему приложению, включая ASP.NET Core и GC-фоновые операции.

> [!example] Как делают в бою
> Типичный сервис на .NET 10 вообще не трогает `ThreadPool` API. Настройки, которые иногда встречаются в проде:
> ```xml
> <PropertyGroup>
>   <!-- Только если есть неустранимый синхронный legacy-код -->
>   <ThreadPoolMinThreads>64</ThreadPoolMinThreads>
>   <!-- Отключить приоритет локальной очереди, если задачи неоднородны -->
>   <!-- (редко, но бывает в системах с жёсткими требованиями к латентности хвоста) -->
> </PropertyGroup>
> ```
> Гораздо чаще в проде мониторят `ThreadPool Queue Length` и алертят, если он держится выше нуля дольше 10 секунд. Это ранний сигнал будущего инцидента.
>
> Отдельная практика — «блокирующий адаптер» для чужой синхронной библиотеки: её вызывают через `Task.Run` **с ограничением по `SemaphoreSlim`**, чтобы даже в худшем случае она не съела больше N потоков.

## Вопросы с собеседований

> [!question]- Чем `Thread` отличается от `ThreadPool`?
> `Thread` — это конкретный поток ОС, который ты создаёшь, запускаешь и который умирает после выполнения делегата. Стоимость создания — 50–200 мкс плюс мегабайт резерва стека. `ThreadPool` — набор переиспользуемых потоков, живущих всё время работы процесса: ты ставишь в очередь единицу работы, свободный поток её забирает и после выполнения возвращается за следующей. Пул сам управляет количеством потоков через hill-climbing, имеет локальные очереди и work-stealing. Практическое правило: короткая единица работы — в пул; вечный цикл, нестандартный стек или STA — свой `Thread`.

> [!question]- Что такое work-stealing и зачем он нужен?
> У каждого рабочего потока пула есть своя локальная очередь. Когда поток пула сам порождает новую работу (например, `Task.Run` изнутри задачи или продолжение после `await`), она кладётся в локальную очередь этого потока — так избегается конкуренция за общую структуру данных. Своя очередь обрабатывается в порядке LIFO, потому что последняя поставленная задача горячая по кешу. Когда у потока работа кончилась и глобальная очередь пуста, он «ворует» задачу из чужой локальной очереди, но с противоположного конца (FIFO). Обратный конец выбран, чтобы вор и владелец не конкурировали за одну ячейку и чтобы вор получал самую крупную подзадачу.

> [!question]- Что такое thread pool starvation и как его диагностировать?
> Ситуация, когда все потоки пула заблокированы (обычно на `.Result`, `.Wait()`, `lock` или синхронном I/O), очередь работы растёт, а пул добавляет новые потоки очень медленно — примерно по одному-два в секунду сверх MinThreads. Симптомы: латентность p99 растёт в десятки раз, при этом **загрузка CPU низкая**. Диагностика: `dotnet-counters monitor System.Runtime` — смотрим `ThreadPool Queue Length` (стабильно больше нуля) и `ThreadPool Thread Count` (монотонно растёт). В дампе через `dotnet-dump analyze` + `clrstack -all` видно множество потоков в `Task.SpinThenBlockingWait`. Лечение — убрать блокирующие вызовы; `ThreadPool.SetMinThreads` только маскирует симптом.

> [!question]- Почему пул добавляет потоки так медленно?
> Потому что в 99 % случаев большое число потоков — это не решение, а проблема. Если элементы работы короткие и не блокируются, `ProcessorCount` потоков полностью загружает машину, и добавление лишних только увеличивает число контекстных переключений, ухудшая пропускную способность. Медленное нарастание — защита от переоптимизации: пул через hill-climbing проверяет, действительно ли добавление потока увеличивает пропускную способность, и откатывается, если нет. Быстрое нарастание оправдано только когда потоки блокируются — а это по определению неправильный код, который пул не обязан обслуживать хорошо.

> [!question]- Чему равно `ThreadPool.GetMinThreads` по умолчанию и что это значит?
> В современном .NET количество worker-потоков по умолчанию равно `Environment.ProcessorCount` (с учётом cgroups в контейнере). Смысл MinThreads: пока число активных потоков пула меньше этого значения, новый поток создаётся **немедленно** при появлении работы, без участия hill-climbing. Сверх MinThreads включается медленный алгоритм. MaxThreads — жёсткий потолок в тысячи потоков, практически недостижимый и не являющийся инструментом настройки. Важная тонкость: `SetMaxThreads` со значением меньше `ProcessorCount` не сработает и вернёт `false`.

> [!question]- Что делает `TaskCreationOptions.LongRunning`?
> Это подсказка планировщику задач о том, что делегат будет выполняться долго. Стандартный `ThreadPoolTaskScheduler` реагирует на неё созданием отдельного потока **вне пула**, а не постановкой в очередь. Смысл: длительная задача, поставленная в пул, надолго выводит из оборота один из немногих потоков и провоцирует hill-climbing на создание лишних. Применяется для вечных циклов вроде «читать из очереди, пока не отменят». Важно: это именно подсказка, кастомный `TaskScheduler` вправе её игнорировать. И важно понимать, что в асинхронном коде это обычно не нужно — асинхронный вечный цикл через `await` вообще не удерживает поток.

> [!question]- Почему `Thread.Abort` убрали из .NET Core?
> Потому что он принципиально не может быть безопасным. `ThreadAbortException` инжектировался в поток в произвольной точке — например, между двумя записями, обновляющими связанные поля, или внутри кода библиотеки, который не рассчитан на прерывание. Результат — повреждённое состояние: полузаписанные структуры данных, неотпущенные блокировки, недописанные файлы. Более того, в .NET Framework прерывание могло случиться внутри `finally`-блока, из-за чего очистка не выполнялась. В .NET Core метод оставлен ради компиляции старого кода, но бросает `PlatformNotSupportedException`. Единственный правильный механизм остановки — кооперативная отмена через `CancellationToken`.

## Задачи

### Задача 1. Показать starvation

Напиши консольное приложение, которое демонстрирует голодание пула и измеряет скорость нарастания числа потоков.

> [!success]- Решение
> ```csharp
> using System.Diagnostics;
>
> ThreadPool.GetMinThreads(out int minW, out _);
> Console.WriteLine($"MinThreads = {minW}, ProcessorCount = {Environment.ProcessorCount}");
>
> var sw = Stopwatch.StartNew();
> int completed = 0;
>
> // 100 задач, каждая блокирует поток на 3 секунды
> var tasks = Enumerable.Range(0, 100).Select(i => Task.Run(() =>
> {
>     Thread.Sleep(3000);                  // имитация блокирующего I/O
>     int done = Interlocked.Increment(ref completed);
>     Console.WriteLine($"[{sw.Elapsed.TotalSeconds,6:F1}s] завершено {done,3}, " +
>                       $"потоков в пуле: {ThreadPool.ThreadCount}");
> })).ToArray();
>
> await Task.WhenAll(tasks);
> Console.WriteLine($"Итого: {sw.Elapsed.TotalSeconds:F1} с вместо ожидаемых 3 с");
> ```
> Ожидаемый результат: если бы потоков хватало, все 100 задач заняли бы 3 секунды. Реально — десятки секунд, и в логе видно, как `ThreadPool.ThreadCount` растёт по одному-двум в секунду.
>
> Теперь добавь в самое начало `ThreadPool.SetMinThreads(100, 100);` и запусти снова — время упадёт почти до 3 секунд. Это наглядно показывает и проблему, и что «лечение» через MinThreads работает, но ценой 100 заблокированных потоков.

### Задача 2. Ограничить блокирующую библиотеку

Есть чужая синхронная библиотека `LegacyReport.Generate(int id)`, которая работает 2 секунды и не имеет асинхронной версии. Нужно вызвать её для 1000 идентификаторов, не убив пул потоков.

> [!success]- Решение
> ```csharp
> // Ограничиваем число одновременных блокирующих вызовов.
> // Число подбирается так, чтобы не съесть пул: обычно 2–4 × ProcessorCount.
> var gate = new SemaphoreSlim(Environment.ProcessorCount * 2);
>
> async Task<Report> GenerateAsync(int id, CancellationToken ct)
> {
>     await gate.WaitAsync(ct);                     // асинхронное ожидание — поток не блокируется
>     try
>     {
>         // Task.Run здесь оправдан: оборачиваем СИНХРОННЫЙ блокирующий вызов
>         return await Task.Run(() => LegacyReport.Generate(id), ct);
>     }
>     finally
>     {
>         gate.Release();
>     }
> }
>
> var results = await Task.WhenAll(
>     Enumerable.Range(1, 1000).Select(id => GenerateAsync(id, ct)));
> ```
> Разбор: `SemaphoreSlim.WaitAsync` не занимает поток на ожидании, поэтому 1000 «ожидающих очереди» вызовов стоят почти ничего. Одновременно блокируется не более `ProcessorCount * 2` потоков пула — пулу этого хватает, чтобы обслуживать остальную работу приложения.
>
> Ещё лучше — `Parallel.ForEachAsync` с `MaxDegreeOfParallelism`, см. [[Parallel, PLINQ и параллелизм данных]]. Про семафоры — [[Semaphore, Mutex, ReaderWriterLockSlim]].

### Задача 3. Локальные очереди и LIFO

Предскажи порядок вывода и объясни его.

```csharp
await Task.Run(() =>
{
    for (int i = 0; i < 5; i++)
    {
        int captured = i;
        ThreadPool.QueueUserWorkItem(_ => Console.WriteLine(captured), preferLocal: true);
    }
    Thread.Sleep(500);   // даём отработать
});
```

> [!success]- Решение
> Порядок **не гарантирован**, но с высокой вероятностью будет ближе к `4 3 2 1 0`, чем к `0 1 2 3 4`. Причина: `preferLocal: true` кладёт работу в локальную очередь текущего потока пула, а локальная очередь обрабатывается в порядке LIFO. Пока внешний делегат спит, другие потоки пула начнут воровать элементы с противоположного конца (FIFO), поэтому порядок будет смешанным и нестабильным от запуска к запуску.
>
> Практический вывод, который проверяют на собеседовании: **порядок выполнения задач в пуле — это деталь реализации**. Любой код, который на него полагается, сломается. Если порядок нужен — используй `Channel` ([[System.Threading.Channels]]) или явную цепочку `await`.

## Итог

- `Thread` в серверном коде оправдан в четырёх случаях: вечный цикл, нестандартный размер стека, STA-интероп, foreground-поток. Всё остальное — `Task` и пул.
- `Thread.Abort` удалён и не вернётся. Останавливать работу можно только кооперативно, через `CancellationToken`.
- Пул состоит из глобальной очереди и локальных очередей рабочих потоков; локальная обрабатывается LIFO, кража идёт с другого конца (FIFO).
- Число потоков подбирается hill-climbing по пропускной способности плюс детектор голодания. Сверх MinThreads (= `ProcessorCount`) потоки добавляются примерно по одному-двум в секунду.
- Thread pool starvation = растущая очередь + растущее число потоков + **низкий CPU**. Смотреть через `dotnet-counters`.
- `SetMinThreads` — обезболивающее, а не лекарство. Лекарство — убрать блокирующие вызовы.
- Блокирующую чужую библиотеку заворачивай в `Task.Run` **с семафором**, чтобы ограничить ущерб пулу.
