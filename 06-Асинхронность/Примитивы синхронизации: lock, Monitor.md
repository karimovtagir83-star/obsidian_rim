# Примитивы синхронизации: lock, Monitor

> [!abstract] Коротко
> Когда несколько потоков меняют общее состояние, результат непредсказуем: даже `count++` — это чтение, изменение и запись, между которыми может вклиниться другой поток. `lock` (он же `Monitor`) — базовый способ защиты: критическая секция, в которой одновременно находится только один поток. Вокруг него — три расширения под конкретные сценарии: `SemaphoreSlim` для асинхронного кода и ограничения параллелизма, `Mutex` для межпроцессной блокировки, `ReaderWriterLockSlim` для «много читателей, редкие писатели». И отдельный класс решений — обойтись без блокировки вовсе: `Interlocked` для атомарных операций, `volatile` для видимости флага. Модель памяти объясняет, почему без этих инструментов один поток может не увидеть запись другого.

## Зачем это знать

Гонки данных — самый неприятный класс ошибок: не воспроизводятся стабильно, проявляются под нагрузкой и молча портят данные. На ревью нужно узнавать пять сигналов: незащищённое общее поле, `lock` вокруг `await`-подобного кода (не компилируется, но агент такое пишет и потом чинит неправильно), блокировку на `this`/типе/строке, забытый `Release`/`Dispose`, и `volatile`-флаг там, где нужна атомарность. При инциденте — отличать дедлок (два потока стоят навсегда) от гонки (данные тихо испорчены) и знать, с чего начинать в дампе.

## Модель

### Базовый механизм: lock / Monitor

```csharp
private readonly System.Threading.Lock _gate = new();   // C# 13 / .NET 9+
private int _counter;

public void Increment()
{
    lock (_gate) { _counter++; }        // одновременно только один поток
}
```

До .NET 9 блокировались произвольным объектом (`private readonly object _gate = new();`) — вариант всё ещё повсеместен в существующем коде. Компилятор разворачивает `lock` в `Monitor.Enter(obj, ref taken)` / `Monitor.Exit(obj)` внутри `try/finally` — освобождение гарантировано даже при исключении. Для `System.Threading.Lock` вместо этого вызывается `EnterScope()`: реализация без служебного слова в заголовке объекта, поэтому быстрее классического монитора и явно показывает по объявлению поля, что это примитив синхронизации.

Свойства монитора:

- **Реентерабельность.** Поток, уже владеющий блокировкой, может войти в неё повторно; счётчик увеличивается, выход — после стольких же `Exit`. Удобно, но маскирует ошибки проектирования: если метод вызывают и с блокировкой, и без, стоит разделить его на публичный и внутренний.
- **Привязка к потоку.** Освободить блокировку обязан тот же поток, который её взял. Поэтому `await` внутри `lock` запрещён компилятором — после возобновления может выполняться другой поток ([[Дедлоки, async void и типичные ошибки]]).
- **`Monitor.TryEnter` с таймаутом** — вместо бесконечного ожидания получаем отказ, что часто лучше под нагрузкой.

Блокироваться можно только на приватном `readonly`-объекте:

```csharp
lock (this)                 // ⛔ внешний код может заблокироваться на том же объекте
lock (typeof(MyClass))      // ⛔ тип общий для всего процесса
lock ("ключ")                // ⛔ строковые литералы интернируются
lock (_someValueType)        // ⛔ упаковка: каждый раз новый объект — синхронизации нет
```

Дорога не сама блокировка (~10–20 нс без конкуренции), а **конкуренция за неё**: короткая секция, без ввода-вывода и без вызова чужого кода внутри — обратный вызов может захватить другую блокировку и создать дедлок. Разный порядок захвата двух блокировок в разных потоках — классический дедлок; лечится единым порядком захвата и `TryEnter` с таймаутом.

### Расширения под конкретный сценарий

**`SemaphoreSlim`** — счётчик разрешений вместо взаимного исключения одного потока. Единственный штатный способ сделать асинхронную критическую секцию, потому что `WaitAsync` не блокирует поток и не привязан к нему:

```csharp
private readonly SemaphoreSlim _mutex = new(1, 1);

private async Task RefreshTokenAsync(CancellationToken ct)
{
    await _mutex.WaitAsync(ct);
    try
    {
        if (_token is { IsValid: true }) return;
        _token = await _auth.GetTokenAsync(ct);
    }
    finally { _mutex.Release(); }        // ОБЯЗАТЕЛЬНО в finally
}
```

При `N > 1` тот же тип ограничивает степень параллелизма — не более N одновременных обращений к внешнему API ([[Task и Task Parallel Library]]). Семафор **не реентерабелен**: повторный `WaitAsync` из той же логической операции — самодедлок.

**`Mutex`** — блокировка уровня ОС, видимая **между процессами** («запустить только один экземпляр приложения»). Привязан к потоку (как классический `Monitor`), поэтому в асинхронном коде практически непригоден: после `await` поток может смениться, и освобождение из другого потока — исключение. Медленнее `lock` на порядок — каждая операция идёт через ядро. Заброшенный мьютекс (владелец умер, не освободив) даёт `AbandonedMutexException` — сигнал, что данные могли остаться в несогласованном состоянии. В серверном .NET встречается редко: задачу «обработчик один в системе» решает не `Mutex` (он в пределах машины), а распределённая блокировка через Redis или БД, либо партиционирование очереди.

**`ReaderWriterLockSlim`** — читателей много, писатель один:

```csharp
_rw.EnterReadLock();
try { return _configs.GetValueOrDefault(key); }
finally { _rw.ExitReadLock(); }
```

Выгоден, когда чтений намного больше записей и операции достаточно длинные, чтобы окупить более дорогой захват. При коротких операциях обычный `lock` часто быстрее — внутренняя реализация сложнее монитора. Почти всегда это вытесняет `ConcurrentDictionary` или иммутабельный снимок ([[Конкурентные коллекции]]).

### Без блокировки вовсе: Interlocked и volatile

Процессор и JIT вправе переставлять операции с памятью и держать значения в регистрах, пока это не меняет результат **однопоточного** выполнения. В многопоточном коде это значит: один поток может не увидеть запись другого или увидеть их в другом порядке.

```csharp
private bool _stop;                 // без volatile
void Worker() { while (!_stop) DoWork(); }   // JIT вправе прочитать поле один раз и закешировать
void Stop() => _stop = true;                  // поток может никогда не увидеть изменение
```

Это регулярно воспроизводится в Release-сборке (JIT включает оптимизации) и на ARM64 (Apple Silicon, AWS Graviton) — там модель памяти слабее, чем на x86-64, и переупорядочивание записей происходит на практике, а не только теоретически.

`Interlocked` — атомарные операции инструкциями процессора, каждая ещё и полный барьер памяти:

```csharp
Interlocked.Increment(ref _counter);
Config? previous = Interlocked.CompareExchange(ref _current, newConfig, expected);
```

`CompareExchange` — основа неблокирующих алгоритмов: прочитать текущее значение, вычислить новое, попытаться заменить при условии, что текущее не изменилось; если кто-то вмешался — повторить. Так устроены `ConcurrentDictionary` и пул потоков изнутри.

`volatile` (и точечная альтернатива `Volatile.Read/Write`) даёт **видимость и порядок** для одного поля, но не атомарность: `volatile int x; x++;` по-прежнему теряет обновления. Практическое правило: **под `lock` volatile не нужен** — вход в блокировку это acquire, выход — release, барьеры уже есть.

```csharp
private Config _config = Config.Default;                    // иммутабельный снимок
public Config Current => Volatile.Read(ref _config);         // читатели без блокировок вовсе
public void Update(Config c) => Volatile.Write(ref _config, c);
```

Присваивание ссылки атомарно, а объект после публикации не меняется — читатель видит либо старую версию целиком, либо новую, промежуточных состояний не бывает. Лучший способ хранить конфигурацию и справочники, читаемые из многих потоков ([[Иммутабельность как приём проектирования]]).

## Решения

| Сценарий | Примитив |
|---|---|
| Изменить общее состояние в синхронном коде | `lock` / `System.Threading.Lock` |
| Критическая секция с `await` внутри | `SemaphoreSlim(1, 1)` |
| Не больше N одновременных операций | `SemaphoreSlim(N)` или `Parallel.ForEachAsync` |
| Один экземпляр процесса на машине | `Mutex` с именем |
| Один обработчик в кластере | распределённая блокировка (Redis, БД), не `Mutex` |
| Много читателей, редкие записи, длинные операции | `ReaderWriterLockSlim` (после замеров) |
| Много читателей, редкие записи, короткие операции | `ConcurrentDictionary` или иммутабельный снимок |
| Атомарный счётчик или замена ссылки | `Interlocked` |
| Флаг остановки/готовности | `volatile`, `Volatile.Read/Write`, лучше `CancellationToken` |
| Атомарное обновление по условию | `Interlocked.CompareExchange` |
| Очередь между потоками | `ConcurrentQueue`, конкурентные коллекции |
| Ленивая инициализация | `Lazy<T>` |

Лучшая синхронизация — отсутствие разделяемого изменяемого состояния: иммутабельный объект читают без блокировок вовсе.

> [!example] В ServiceShop
> В типичном модуле ServiceShop явных блокировок мало: состояние живёт в БД, в Redis-кеше или в scoped-сервисах на запрос, а не в статических полях. Там, где общее состояние в памяти всё же есть — реестр активных подключений, счётчики обработанных сообщений в консьюмере Kafka, кеш конфигурации модуля — используют готовые потокобезопасные типы (`ConcurrentDictionary`, `Interlocked`) вместо ручной синхронизации. Ограничение параллелизма при вызове внешних API (например, у поставщика услуг) делают через `SemaphoreSlim` или `Parallel.ForEachAsync`, а не через `lock`, потому что вызов асинхронный. Задачу «этот job должен выполняться только одним экземпляром сервиса» решает не `Mutex` (под Kubernetes процессов несколько и на разных подах), а блокировка в Redis или уникальный ключ в БД с обработкой конфликта.

> [!warning] Где ошибаются
> - **Агент часто:** использует `lock` там, где нужен `SemaphoreSlim`, для кода с `await` внутри — компилятор такой `lock` не пропустит, и агент, чинясь, оборачивает `await` в `.Result`/`.Wait()` внутри секции вместо замены примитива. Это не чинит проблему, а добавляет риск дедлока поверх старого.
> - **Агент часто:** добавляет `volatile` к полю, которое уже меняется под `lock`, «на всякий случай» — это признак непонимания модели памяти, а не дополнительная надёжность.
> - `lock (this)`, `lock (typeof(T))`, `lock ("строка")` — объект виден снаружи, дедлок может прийти из чужого кода.
> - `Release()` семафора не в `finally` — при раннем `return` или исключении разрешение теряется навсегда, и все следующие вызовы зависают на `WaitAsync`.
> - Долгая работа или сетевой вызов внутри `lock`/семафора — пока один поток ждёт, остальные стоят; `.Result` внутри секции вдобавок рискует дедлоком пула потоков.
> - `Mutex` в асинхронном коде — привязка к потоку ломается после `await`.
> - Проверка «работает на x86» — на ARM64 модель памяти слабее, скрытая гонка проявится там.
> - `ReaderWriterLockSlim` без замеров — на коротких операциях он часто медленнее обычного `lock`.

## Проверка на ревью

- Есть ли общее изменяемое поле (не `readonly`, не через DI-скоуп), к которому обращаются из нескольких потоков или консьюмеров.
- Блокировка (`lock`, семафор, мьютекс) держится строго вокруг изменения состояния, а не вокруг сетевого вызова или логирования.
- Объект блокировки — приватный `readonly`, не `this`, не тип, не строка.
- У каждого `SemaphoreSlim.Wait`/`WaitAsync` есть парный `Release` в `finally`.
- Там, где внутри секции есть `await`, использован `SemaphoreSlim`, а не `lock` с обходом через `.Result`.
- Флаг, который проверяет фоновый цикл (`while (!_stop)`), либо `volatile`, либо (лучше) заменён на `CancellationToken`.

## Проверь себя

> [!question]- Почему `await` нельзя использовать внутри `lock`?
> Монитор привязан к потоку: освободить блокировку обязан тот же поток, который её взял. После `await` продолжение может выполняться в другом потоке (особенно без `ConfigureAwait(false)` и синхронизационного контекста), и `Monitor.Exit` из чужого потока — либо исключение, либо неопределённое поведение. Компилятор поэтому запрещает `await` внутри `lock` на уровне синтаксиса. Решение — `SemaphoreSlim`, у которого `WaitAsync`/`Release` не привязаны к потоку.

> [!question]- Чем `SemaphoreSlim` отличается от `Mutex`, если оба ограничивают доступ?
> `SemaphoreSlim` — управляемый счётчик разрешений внутри процесса, с асинхронным ожиданием и токеном отмены; он быстрый и не привязан к потоку. `Mutex` — примитив уровня ОС, видимый **между процессами** по имени, привязанный к потоку и на порядок дороже (каждая операция идёт через ядро). Задачи разные: `SemaphoreSlim` — асинхронная критическая секция и ограничение параллелизма внутри сервиса; `Mutex` — «не запускать второй экземпляр приложения» или синхронизация с другим процессом на той же машине. В кластере ни то, ни другое не решает задачу «один обработчик на все инстансы» — там нужна распределённая блокировка.

> [!question]- Почему `volatile` не решает гонку при `counter++`?
> `volatile` управляет только видимостью и порядком: он гарантирует, что значение читается из памяти, а не из регистра, и что соседние операции не переставляются через него. Но `counter++` — это три отдельных шага (чтение, увеличение, запись), и `volatile` не делает их одной атомарной операцией. Два потока по-прежнему могут прочитать одно и то же значение и потерять одно из увеличений. Для атомарного счётчика нужен `Interlocked.Increment`, который выполняется одной инструкцией процессора.

> [!question]- Когда `ReaderWriterLockSlim` действительно выгоднее `lock`?
> Когда чтений заметно больше записей и сами операции достаточно длинные, чтобы окупить более дорогой захват — он позволяет читателям работать параллельно, блокируя только на время записи. При коротких операциях (получить значение из словаря) он часто проигрывает обычному `lock`, потому что его внутренняя реализация сложнее монитора. На практике его почти всегда вытесняет `ConcurrentDictionary` или иммутабельный снимок, публикуемый через `Volatile.Write`, — там читатели работают вообще без синхронизации.

> [!question]- Как возникает дедлок с двумя блокировками и как его избежать?
> Когда два потока захватывают одни и те же блокировки в разном порядке: первый держит A и ждёт B, второй держит B и ждёт A — оба ждут вечно. Избегают единым порядком захвата для всех блокировок системы, отказом от второй блокировки без необходимости, `TryEnter` с таймаутом вместо бесконечного ожидания и запретом на вызов чужого кода внутри секции (обратный вызов может захватить другую блокировку). В дампе `syncblk` показывает владельцев мониторов, `clrthreads` — состояния потоков ([[Диагностика в проде: дампы и dotnet-tools]]).

## Разбор

### Задача 1. Найти ошибки

```csharp
public class TokenProvider
{
    private readonly SemaphoreSlim _gate = new(1, 1);
    private Token? _token;

    public async Task<Token> GetTokenAsync(CancellationToken ct)
    {
        await _gate.WaitAsync(ct);
        if (_token is { IsValid: true }) return _token;
        _token = await _auth.RequestAsync(ct);
        _gate.Release();
        return _token;
    }
}
```

> [!success]- Решение
> Две ошибки, обе про `Release` не в `finally`. При раннем `return` (токен уже валиден) `Release` не вызывается — разрешение теряется навсегда, и все следующие вызовы зависают на `WaitAsync`. Если `RequestAsync` бросит исключение — тот же результат.
> ```csharp
> public async Task<Token> GetTokenAsync(CancellationToken ct)
> {
>     if (_token is { IsValid: true }) return _token;       // быстрый путь без блокировки
>
>     await _gate.WaitAsync(ct);
>     try
>     {
>         if (_token is { IsValid: true }) return _token;   // повторная проверка под блокировкой
>         _token = await _auth.RequestAsync(ct);
>         return _token;
>     }
>     finally { _gate.Release(); }
> }
> ```
> Добавлена проверка до захвата — в типичном случае (токен валиден) не платим за синхронизацию вовсе; повторная проверка под блокировкой нужна, потому что между быстрым путём и захватом другой поток мог уже обновить токен. Это асинхронный вариант двойной проверки.

### Задача 2. Выбрать инструмент

Нужно защитить: (а) счётчик обработанных Kafka-сообщений; (б) кеш справочника, читаемый тысячами запросов и обновляемый раз в час; (в) обновление двух связанных полей (баланс и дата последней операции); (г) вызов внешнего API с ограничением в 20 одновременных запросов из асинхронного кода.

> [!success]- Решение
> **(а) `Interlocked.Increment`.** Одна ячейка, атомарная операция; `lock` был бы дороже и не даёт ничего сверх.
> **(б) Иммутабельный снимок с `Volatile.Write`.** Справочник публикуется целиком новым объектом, читатели работают без синхронизации вообще — идеальный профиль «много чтений, редкие записи». `ReaderWriterLockSlim` тоже сработает, но проиграет; `lock` сериализует всех читателей без нужды.
> **(в) `lock`.** Два поля должны меняться согласованно — другой поток не должен увидеть новый баланс со старой датой. Ни `Interlocked`, ни `volatile` этого не дают. Альтернатива — иммутабельная запись с обоими полями и подмена ссылки через `Interlocked.Exchange`.
> **(г) `SemaphoreSlim(20, 20)` или `Parallel.ForEachAsync`.** Код асинхронный, `lock` не пропустит `await`. Семафор даёт больше контроля (индивидуальная обработка ошибок), `Parallel.ForEachAsync` — короче и сам управляет отменой.

## Итог

- Гонка возникает, когда несколько потоков меняют общее состояние; даже `i++` не атомарен.
- `lock`/`Monitor` — базовый механизм: взаимное исключение плюс барьеры памяти, но не работает с `await` внутри секции.
- `SemaphoreSlim` — асинхронная критическая секция и ограничение параллелизма; `Release` строго в `finally`, семафор не реентерабелен.
- `Mutex` — межпроцессная блокировка, привязан к потоку, в кластере не решает задачу «один обработчик».
- `ReaderWriterLockSlim` оправдан только при большом перевесе чтений и длинных операциях — иначе `lock` быстрее.
- `Interlocked` — атомарные операции без блокировки; `volatile` — видимость без атомарности; под `lock` `volatile` не нужен.
- На ARM64 модель памяти слабее, чем на x86-64: гонки, невидимые на x86, там проявляются регулярно.
- Часто лучшее решение — вообще без блокировки: конкурентные коллекции, `Interlocked`, иммутабельный снимок.
