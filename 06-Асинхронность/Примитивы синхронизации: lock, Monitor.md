# Примитивы синхронизации: lock, Monitor

> [!abstract] Коротко
> Когда два потока изменяют общее состояние, результат непредсказуем: даже `count++` — это чтение, увеличение и запись, между которыми может вклиниться другой поток. `lock` создаёт критическую секцию: одновременно в ней находится только один поток. Под капотом это `Monitor.Enter`/`Monitor.Exit` в `try/finally`, а с C# 13 появился специальный тип `System.Threading.Lock`, который быстрее и понятнее объекта-заглушки. Ключевые правила: блокировать приватный объект (никогда `this`, строку или тип), держать секцию короткой, никогда не вызывать внутри чужой код и не пытаться использовать `await` — для асинхронного кода нужен `SemaphoreSlim`.

## Зачем это нужно

Гонки — самый неприятный класс ошибок: они не воспроизводятся, проявляются под нагрузкой и портят данные тихо.

```csharp
private int _counter;

// Три потока по 100 000 инкрементов → ожидаем 300 000
void Increment() { for (int i = 0; i < 100_000; i++) _counter++; }
// Фактически: 217 483 или другое случайное число
```

Причина в том, что `_counter++` не атомарен: это загрузка значения, увеличение и запись. Два потока могут прочитать одно и то же значение и записать одинаковый результат — одно увеличение потеряется.

## lock

```csharp
private readonly System.Threading.Lock _gate = new();   // C# 13 / .NET 9+
private int _counter;

public void Increment()
{
    lock (_gate)
    {
        _counter++;          // критическая секция: одновременно только один поток
    }
}
```

До .NET 9 блокировались произвольным объектом:

```csharp
private readonly object _gate = new();     // классический вариант, всё ещё повсеместен
lock (_gate) { _counter++; }
```

Компилятор разворачивает `lock` в вызовы монитора:

```csharp
// Для object (классический вариант)
bool taken = false;
try
{
    Monitor.Enter(_gate, ref taken);
    _counter++;
}
finally
{
    if (taken) Monitor.Exit(_gate);        // освобождение гарантировано даже при исключении
}

// Для System.Threading.Lock компилятор вызывает _gate.EnterScope()
```

Тип `Lock` из .NET 9 быстрее классического монитора (оптимизированная реализация без служебного слова в заголовке объекта) и выразительнее: по объявлению поля сразу видно, что это примитив синхронизации, а не случайный объект. В новом коде используют его.

### На чём нельзя блокироваться

```csharp
lock (this) { }                 // ⛔ внешний код может заблокироваться на том же объекте
lock (typeof(MyClass)) { }      // ⛔ тип общий для всего процесса и домена
lock ("ключ") { }               // ⛔ строковые литералы интернируются — объект общий
lock (_publicField) { }         // ⛔ доступен снаружи
lock (_someValueType) { }       // ⛔ упаковка: каждый раз новый объект, блокировки нет вовсе
```

Правило: объект блокировки — **приватный, только для чтения, ссылочный и созданный специально для этого**. Иначе появляется риск, что кто-то извне захватит ту же блокировку и создаст дедлок, который невозможно предвидеть по коду класса.

## Свойства монитора

**Реентерабельность.** Поток, уже владеющий блокировкой, может войти в неё снова: счётчик увеличивается, выход происходит после стольких же `Exit`.

```csharp
lock (_gate)
{
    Helper();                 // внутри тоже lock (_gate) — не заблокируется
}
```

Это удобно, но маскирует ошибки проектирования: если метод рассчитан на вызов и с блокировкой, и без неё, обычно стоит разделить его на публичный (берущий блокировку) и приватный (предполагающий, что она уже взята).

**Привязка к потоку.** Освободить блокировку должен тот же поток, который её взял. Поэтому `await` внутри `lock` запрещён компилятором — после возобновления может работать другой поток ([[Дедлоки, async void и типичные ошибки]]).

**Ожидание с таймаутом.**

```csharp
if (Monitor.TryEnter(_gate, TimeSpan.FromSeconds(1)))
{
    try { DoWork(); }
    finally { Monitor.Exit(_gate); }
}
else
{
    logger.LogWarning("Не удалось получить блокировку за секунду");
}
```

Полезно там, где долгое ожидание хуже отказа: под нагрузкой лучше вернуть 503, чем накапливать очередь потоков.

**Wait/Pulse** — низкоуровневые сигналы для реализации очередей и барьеров:

```csharp
lock (_gate)
{
    while (_queue.Count == 0) Monitor.Wait(_gate);    // освобождает блокировку и ждёт
    var item = _queue.Dequeue();
}
// в другом потоке
lock (_gate) { _queue.Enqueue(item); Monitor.Pulse(_gate); }
```

В прикладном коде это писать почти никогда не нужно: готовые `BlockingCollection`, `Channel` и конкурентные коллекции делают то же самое и корректно ([[System.Threading.Channels]], [[Конкурентные коллекции]]).

## Сколько стоит блокировка

| Ситуация | Порядок стоимости |
|---|---|
| Захват без конкуренции | ~10–20 наносекунд |
| Захват при конкуренции (короткое ожидание) | спин, десятки–сотни наносекунд |
| Захват с переходом в ядро (долгое ожидание) | микросекунды плюс переключение контекста |
| `Interlocked` вместо блокировки | единицы наносекунд |

Отсюда практические выводы: блокировка сама по себе дёшева, дорога **конкуренция за неё**. Уменьшать конкуренцию можно тремя способами: сокращать критическую секцию, дробить блокировки (например, по сегментам данных), либо вообще обходиться без них — атомарными операциями, конкурентными коллекциями или иммутабельностью ([[Interlocked, volatile и модель памяти]], [[Иммутабельность как приём проектирования]]).

```csharp
// Плохо: в секции дорогая работа и, что хуже, вызов чужого кода
lock (_gate)
{
    var data = _http.GetStringAsync(url).Result;   // ⛔ блокировка + сеть + риск дедлока
    _cache[key] = Parse(data);
}

// Лучше: снаружи — работа, внутри — только обновление состояния
var data = await _http.GetStringAsync(url, ct);
var parsed = Parse(data);
lock (_gate) { _cache[key] = parsed; }
```

## Дедлок из-за порядка захвата

```csharp
// Поток 1                       // Поток 2
lock (_a)                        lock (_b)
{                                {
    lock (_b) { }                    lock (_a) { }     // ⛔ взаимная блокировка
}                                }
```

Классический дедлок: каждый держит то, что нужно другому. Средства борьбы:

- **Единый порядок захвата** для всех блокировок в системе (например, по идентификатору объекта).
- **Не брать вторую блокировку** без крайней необходимости; при возможности — разделить операцию.
- **`TryEnter` с таймаутом** вместо бесконечного ожидания: получаем отказ вместо зависания.
- **Не вызывать чужой код** внутри секции: обратный вызов может захватить другую блокировку и замкнуть цикл.

Диагностика: в дампе команда `syncblk` показывает, кто владеет мониторами, а `clrthreads` — состояния потоков ([[Диагностика в проде: дампы и dotnet-tools]]).

## Двойная проверка и Lazy

```csharp
// Классический double-checked locking — исторический приём
private static MyService? _instance;
private static readonly Lock Gate = new();

public static MyService Instance
{
    get
    {
        if (_instance is null)                  // быстрая проверка без блокировки
        {
            lock (Gate)
            {
                _instance ??= new MyService();  // повторная проверка под блокировкой
            }
        }
        return _instance;
    }
}

// Современный вариант: Lazy<T> делает то же самое корректно
private static readonly Lazy<MyService> Lazy = new(() => new MyService());
public static MyService Instance => Lazy.Value;
```

`Lazy<T>` с режимом по умолчанию (`ExecutionAndPublication`) гарантирует, что фабрика выполнится один раз, и корректно обрабатывает исключения. Писать двойную проверку руками сегодня не нужно — и в подавляющем большинстве серверных приложений singleton создаёт DI-контейнер, где эта задача уже решена ([[Жизненные циклы сервисов: Singleton, Scoped, Transient]]).

## Когда блокировка не нужна

| Задача | Решение без lock |
|---|---|
| Счётчик | `Interlocked.Increment` |
| Замена ссылки | `Interlocked.Exchange`, `CompareExchange` |
| Общий словарь | `ConcurrentDictionary` |
| Очередь между потоками | `Channel<T>`, `ConcurrentQueue` |
| Ленивая инициализация | `Lazy<T>` |
| Разделяемые данные только для чтения | иммутабельный снимок, публикуемый целиком |
| Асинхронная критическая секция | `SemaphoreSlim` |

Лучшая синхронизация — отсутствие разделяемого изменяемого состояния. Иммутабельный объект можно читать из любого числа потоков без блокировок вовсе.

> [!warning] Подводные камни
> - **`lock (this)`, `lock (typeof(T))`, `lock ("строка")`.** Объект виден снаружи, дедлок может прийти из чужого кода.
> - **Блокировка значимого типа.** Упаковка создаёт новый объект на каждый вход — синхронизации нет вообще.
> - **Долгая работа в секции.** Особенно ввод-вывод: пока один поток ждёт сеть, остальные стоят.
> - **Вызов чужого кода под блокировкой.** Обратный вызов может захватить другую блокировку и создать цикл.
> - **Разный порядок захвата двух блокировок.** Классический дедлок.
> - **Попытка `await` внутри `lock`.** Компилятор запретит; нужен `SemaphoreSlim`.
> - **`Monitor.Exit` вне `finally`.** При исключении блокировка не освободится — используй `lock`, а не ручные вызовы.
> - **Блокировка там, где хватило бы `Interlocked` или конкурентной коллекции.** Лишняя конкуренция и потеря производительности.

> [!example] Как делают в бою
> В типичном веб-приложении явных блокировок мало: состояние живёт в базе, в кеше или в scoped-сервисах, а не в разделяемых полях. Там, где общее состояние всё же есть (кеш в памяти, счётчики, реестр подключений), используют готовые потокобезопасные типы — `ConcurrentDictionary`, `Channel`, `Interlocked` — вместо ручной синхронизации.
> Когда блокировка нужна, придерживаются трёх правил: приватный объект (в новом коде — `System.Threading.Lock`), максимально короткая секция, никакого ввода-вывода и вызовов чужого кода внутри. Асинхронная критическая секция — только `SemaphoreSlim` с `Release` в `finally`.
> При расследовании зависаний смотрят дамп: `clrthreads` показывает состояния потоков, `syncblk` — владельцев мониторов, `pstacks` — где именно все стоят. Дедлок из-за порядка захвата виден там сразу.
> Отдельная привычка на ревью: блокировка вокруг `await`-подобной или сетевой операции — сигнал остановиться и переписать; она означает, что вся система будет ждать самого медленного вызова.

## Вопросы с собеседований

> [!question]- Что делает `lock` и во что он разворачивается?
> `lock (obj) { ... }` — синтаксический сахар над монитором: компилятор генерирует `Monitor.Enter(obj, ref taken)` перед блоком и `Monitor.Exit(obj)` в `finally`, что гарантирует освобождение даже при исключении. Монитор реентерабелен (поток, уже владеющий блокировкой, может войти повторно, счётчик увеличивается) и привязан к потоку: освободить блокировку обязан тот же поток, который её взял. Именно из-за этой привязки компилятор запрещает `await` внутри `lock` — после возобновления код может выполняться в другом потоке. Начиная с C# 13 и .NET 9 появился специальный тип `System.Threading.Lock`: если поле объявлено им, компилятор вызывает `EnterScope()` вместо монитора, что быстрее и делает намерение явным. Для объектов типа `object` поведение осталось прежним.

> [!question]- Почему нельзя блокироваться на `this`, типе или строке?
> Потому что эти объекты доступны извне, и посторонний код может захватить ту же блокировку, создав дедлок, который невозможно предвидеть, читая класс. `lock (this)` позволяет любому потребителю объекта заблокировать его изнутри; `lock (typeof(MyClass))` берёт блокировку на объект типа, общий для всего процесса, — её может захватить совершенно другая библиотека; строковые литералы интернируются, поэтому `lock ("key")` в двух не связанных местах кода блокируется на одном и том же объекте. Отдельный случай — блокировка на значимом типе: он упаковывается при каждом входе, создавая новый объект, поэтому синхронизации не происходит вовсе, хотя код компилируется. Правильный выбор — приватное поле `readonly`, созданное специально для синхронизации: в новом коде это `System.Threading.Lock`, в существующем — `new object()`.

> [!question]- Как возникает дедлок с двумя блокировками и как его избежать?
> Когда два потока захватывают одни и те же блокировки в разном порядке: первый держит A и ждёт B, второй держит B и ждёт A. Ни один не может продолжить, и оба ждут вечно. Основные способы избежать: установить глобальный порядок захвата (например, всегда по возрастанию идентификатора объекта) и соблюдать его везде; по возможности не брать две блокировки одновременно, разделив операцию; использовать `Monitor.TryEnter` с таймаутом, чтобы вместо зависания получить отказ и залогировать проблему; не вызывать внутри критической секции чужой код, потому что обратный вызов может захватить другую блокировку и замкнуть цикл. Диагностика по дампу: `clrthreads` показывает состояние потоков, `syncblk` — какие мониторы кем удерживаются, и цикл ожиданий виден непосредственно.

## Задачи

### Задача 1. Найти ошибки

```csharp
public class Cache
{
    private readonly Dictionary<string, string> _items = new();

    public string GetOrLoad(string key)
    {
        lock (this)
        {
            if (_items.TryGetValue(key, out var value)) return value;
            var loaded = _http.GetStringAsync(key).Result;
            _items[key] = loaded;
            return loaded;
        }
    }
}
```

> [!success]- Решение
> Три ошибки. Блокировка на `this` — внешний код может захватить тот же объект. Внутри секции выполняется сетевой запрос: пока один поток ждёт ответа (сотни миллисекунд), все остальные стоят, а `.Result` вдобавок блокирует поток пула и рискует дедлоком. И конструкция в целом сериализует весь кеш, хотя разные ключи независимы.
> ```csharp
> public sealed class Cache(HttpClient http)
> {
>     private readonly ConcurrentDictionary<string, Lazy<Task<string>>> _items = new();
>
>     public Task<string> GetOrLoadAsync(string key, CancellationToken ct)
>         => _items.GetOrAdd(key, k =>
>                new Lazy<Task<string>>(() => http.GetStringAsync(k, ct))).Value;
> }
> ```
> Что изменилось: `ConcurrentDictionary` снимает необходимость в блокировке; `Lazy<Task<string>>` гарантирует, что для одного ключа запрос будет выполнен ровно один раз, даже если десять потоков обратились одновременно (без него `GetOrAdd` мог бы запустить фабрику несколько раз); метод стал асинхронным, поэтому потоки не блокируются вовсе.
> Оговорка: в такой схеме неудачный запрос закешируется как упавшая задача — в реальном коде добавляют удаление ключа при ошибке или используют `HybridCache`/`IMemoryCache`, где эта проблема уже решена.

### Задача 2. Устранить гонку

Счётчик обработанных сообщений обновляется из десяти потоков и показывает заниженное значение. Три варианта решения — какой выбрать?

> [!success]- Решение
> ```csharp
> // 1. lock — работает, но избыточен для одной операции
> lock (_gate) { _processed++; }
>
> // 2. Interlocked — атомарная операция без блокировки
> Interlocked.Increment(ref _processed);
>
> // 3. Отдельный счётчик на поток с итоговым суммированием
> // (для очень горячих путей, где даже Interlocked создаёт конкуренцию за кеш-линию)
> ```
> Правильный выбор для большинства случаев — **`Interlocked.Increment`**: он выполняется атомарной инструкцией процессора, стоит единицы наносекунд, не требует блокировки и не может привести к дедлоку. `lock` здесь избыточен: он дороже и защищает больше, чем нужно.
> Третий вариант (счётчики по потокам или разделение по сегментам) применяют, когда конкуренция за одну и ту же ячейку становится узким местом — миллионы обновлений в секунду с разных ядер вызывают «пинг-понг» кеш-линии между процессорами. Это уже оптимизация по результатам замеров, а не умолчание.
> И общий принцип: если операция сводится к одному атомарному действию над числом или ссылкой, блокировка не нужна — есть `Interlocked` ([[Interlocked, volatile и модель памяти]]).

## Итог

- Гонка возникает, когда несколько потоков изменяют общее состояние; даже `i++` не атомарен.
- `lock` разворачивается в `Monitor.Enter`/`Exit` в `try/finally`; монитор реентерабелен и привязан к потоку.
- С C# 13 есть тип `System.Threading.Lock` — быстрее и выразительнее объекта-заглушки.
- Блокироваться можно только на приватном `readonly`-объекте: не `this`, не тип, не строку, не значимый тип.
- Дорога не блокировка, а конкуренция: секция должна быть короткой, без ввода-вывода и вызовов чужого кода.
- Разный порядок захвата двух блокировок даёт дедлок; лечится единым порядком и `TryEnter` с таймаутом.
- `await` внутри `lock` невозможен — для асинхронной секции нужен `SemaphoreSlim`.
- Часто блокировка не нужна вовсе: `Interlocked`, конкурентные коллекции, `Lazy<T>`, иммутабельность.
