# Task и Task Parallel Library

> [!abstract] Коротко
> `Task` — обещание результата: объект, который представляет операцию, ещё не завершившуюся. Он не равен потоку: задача может выполняться в потоке пула (`Task.Run`), а может не занимать поток вовсе, пока ждёт ввода-вывода. У задачи есть состояние, результат или исключение и список продолжений, которые запускаются по завершении. TPL добавляет к этому комбинаторы (`WhenAll`, `WhenAny`, `WhenEach`), фабрики (`Task.FromResult`, `TaskCompletionSource`) и облегчённую версию `ValueTask` для случаев, когда результат чаще всего готов синхронно.

## Зачем это нужно

`Task` — базовый кирпич всей асинхронности: `async`/`await` работает поверх него, HTTP-клиенты и драйверы БД возвращают его, фоновые службы им управляют. Не понимая, что это объект с состоянием, а не «поток», невозможно объяснить ни `Task.Run` в ASP.NET Core (обычно вредный), ни «горячие» и «холодные» задачи, ни почему `WhenAll` показывает только первое исключение.

## Что такое Task

```csharp
Task<int> task = ComputeAsync();      // операция уже запущена («горячая» задача)

Console.WriteLine(task.Status);       // WaitingForActivation / Running / RanToCompletion / Faulted / Canceled
Console.WriteLine(task.IsCompleted);  // завершена (успешно, с ошибкой или отменена)

int result = await task;              // дождаться и получить результат
```

Ключевые свойства модели:

- **Задача — объект в куче**, а не поток. Одновременно могут существовать миллионы задач при десятке потоков.
- **Задачи в .NET «горячие»**: метод, возвращающий `Task`, уже начал работу к моменту возврата. Это отличается от «холодных» абстракций вроде `IObservable` или `Func<Task>`.
- **Результат сохраняется**: повторный `await` одной и той же задачи не выполняет операцию заново, а сразу отдаёт готовое значение.
- **Исключение хранится внутри** и выбрасывается при `await` ([[Исключения в асинхронном коде]]).

```csharp
var t = ComputeAsync();
int a = await t;      // выполнение
int b = await t;      // мгновенно: результат уже есть
```

### Task против потока

| | `Thread` | `Task` |
|---|---|---|
| Что это | поток ОС | объект-обещание результата |
| Стоимость | ~1 МБ стека, миллисекунды на создание | объект в куче, десятки байт |
| Кто планирует | планировщик ОС | `TaskScheduler` поверх пула потоков |
| Нужен ли поток | всегда | только для вычислений; ожидание I/O потока не занимает |
| Результат и ошибки | вручную | встроены |
| Отмена | нет штатной | `CancellationToken` |

Главное: **`Task` не означает «новый поток»**. Асинхронная операция ввода-вывода (`ReadAsync`, `SendAsync`) не занимает поток на время ожидания вовсе — за это отвечают механизмы ОС и порты завершения ([[Thread и ThreadPool]]).

## Как создать задачу

```csharp
// 1. Асинхронный метод — основной способ
async Task<int> LoadAsync() { await Task.Delay(10); return 42; }

// 2. Task.Run — вынести CPU-работу в поток пула
Task<int> cpu = Task.Run(() => HeavyCalculation());

// 3. Готовый результат — без аллокаций и планирования
Task<int> ready = Task.FromResult(42);
Task completed = Task.CompletedTask;
Task failed = Task.FromException(new InvalidOperationException());
Task canceled = Task.FromCanceled(token);

// 4. Мост к колбэкам и событиям
static Task<string> WaitForMessageAsync(IBus bus, CancellationToken ct)
{
    var tcs = new TaskCompletionSource<string>(TaskCreationOptions.RunContinuationsAsynchronously);
    void Handler(object? s, MessageEventArgs e) => tcs.TrySetResult(e.Text);

    bus.MessageReceived += Handler;
    ct.Register(() => tcs.TrySetCanceled(ct));

    return tcs.Task.ContinueWith(t => { bus.MessageReceived -= Handler; return t.Result; }, ct);
}
```

`TaskCompletionSource` — способ превратить в задачу что угодно: колбэк, событие, сигнал из другого потока. Флаг `RunContinuationsAsynchronously` важен: без него продолжение выполнится **синхронно в потоке, вызвавшем `TrySetResult`**, что может неожиданно заблокировать чужой поток или привести к дедлоку.

> [!warning] `Task.Run` в ASP.NET Core почти всегда лишний
> Запрос уже выполняется в потоке пула. Обёртка `Task.Run(() => ...)` вокруг асинхронного вызова не ускоряет ничего: она забирает **ещё один** поток из того же пула и добавляет накладные расходы на планирование. Оправдано это только для действительно вычислительной работы, которая иначе заблокировала бы поток запроса надолго, — и то лучше вынести её в фоновую службу или очередь.

## Комбинаторы

```csharp
// Все параллельно, ждать всех
Task<Order>[] tasks = ids.Select(id => LoadOrderAsync(id, ct)).ToArray();
Order[] orders = await Task.WhenAll(tasks);

// Первая завершившаяся (например, гонка с таймаутом)
Task done = await Task.WhenAny(work, Task.Delay(timeout, ct));
if (done != work) throw new TimeoutException();

// Обрабатывать по мере готовности (.NET 9)
await foreach (Task<Order> finished in Task.WhenEach(tasks))
    Process(await finished);

// Задержка и уступка кванта
await Task.Delay(TimeSpan.FromSeconds(1), ct);
await Task.Yield();          // вернуть управление и продолжить асинхронно
```

Практическая разница между последовательным и параллельным выполнением:

```csharp
// 3 × 100 мс = 300 мс
var a = await LoadAsync(1, ct);
var b = await LoadAsync(2, ct);
var c = await LoadAsync(3, ct);

// ~100 мс: операции стартуют одновременно
var results = await Task.WhenAll(LoadAsync(1, ct), LoadAsync(2, ct), LoadAsync(3, ct));
```

Это самая частая упускаемая оптимизация в прикладном коде: независимые вызовы пишут в цикле с `await`, хотя они могли бы идти параллельно. Обратная сторона — нагрузка на внешнюю систему: сотня одновременных запросов может её положить, поэтому параллелизм ограничивают семафором ([[Semaphore, Mutex, ReaderWriterLockSlim]]).

### `WhenAll` и исключения

```csharp
var all = Task.WhenAll(t1, t2, t3);
try { await all; }
catch (Exception)
{
    // await бросает ПЕРВОЕ исключение; все остальные — здесь
    foreach (var ex in all.Exception!.InnerExceptions) Log(ex);
}
```

Важно: `WhenAll` **дожидается всех задач**, даже если одна упала сразу. Если нужно прекратить остальные при первой ошибке, используют общий `CancellationTokenSource` и отменяют его в обработчике.

## ValueTask

```csharp
public ValueTask<int> GetAsync(string key)
{
    if (_cache.TryGetValue(key, out var cached))
        return new ValueTask<int>(cached);       // синхронный путь: без аллокации Task

    return new ValueTask<int>(LoadFromDbAsync(key));
}
```

`ValueTask<T>` — структура: она не создаёт объект в куче, когда результат уже готов. Это выгодно в горячих API, где кеш попадает в 90 % случаев (`Stream.ReadAsync`, `Channel.ReadAsync`, `IMemoryCache`-обёртки).

Ограничения жёсткие:

- **`await` только один раз.** Повторный `await` того же `ValueTask` — неопределённое поведение.
- **Нельзя хранить и передавать** между вызовами; чтобы сохранить, надо вызвать `.AsTask()`.
- **Нельзя ждать параллельно** (`Task.WhenAll` над `ValueTask` требует преобразования).

Правило: возвращать `ValueTask` в библиотечных API, где синхронное завершение — норма; в прикладном коде по умолчанию `Task`, он проще и безопаснее ([[Асинхронность и производительность: ValueTask, пулинг]]).

## Чего не делать

```csharp
// Блокирующее ожидание: съедает поток и может дать дедлок
var result = LoadAsync().Result;
LoadAsync().Wait();
LoadAsync().GetAwaiter().GetResult();

// Забытая задача: исключение потеряно, завершение не дождано
_ = ProcessAsync();                       // «fire and forget» без обработки

// Task.Factory.StartNew без флагов — устаревший способ
Task.Factory.StartNew(() => Work());      // не разворачивает вложенные задачи
```

Про `.Result` и дедлоки — [[Дедлоки, async void и типичные ошибки]]. Про правильный «запустить и забыть» — с логированием исключений и учётом времени жизни приложения ([[Background services и IHostedService]]).

`Task.Factory.StartNew` нужен только для экзотических случаев (свой планировщик, `TaskCreationOptions.LongRunning`); во всех остальных используют `Task.Run`.

## Продолжения

```csharp
// Явное продолжение — сегодня почти не нужно, его заменил await
task.ContinueWith(t => Console.WriteLine(t.Result), TaskContinuationOptions.OnlyOnRanToCompletion);

// То же самое читаемее
try { Console.WriteLine(await task); }
catch (Exception ex) { Log(ex); }
```

`ContinueWith` остался в коде, написанном до C# 5, и в библиотечных сценариях. У него неочевидное поведение по умолчанию: он не наследует контекст синхронизации, требует явных флагов для обработки ошибок и легко приводит к проглоченным исключениям. В прикладном коде его заменяет `await`.

> [!warning] Подводные камни
> - **`Task.Run` вокруг асинхронного вызова.** Забирает лишний поток и ничего не ускоряет.
> - **Последовательные `await` вместо `WhenAll`.** Самая частая потеря производительности в прикладном коде.
> - **`WhenAll` без ограничения параллелизма.** Тысяча одновременных запросов кладёт внешнюю систему или исчерпывает пул соединений.
> - **`.Result`/`.Wait()`.** Блокируют поток; в контексте с синхронизацией дают дедлок.
> - **Повторный `await` над `ValueTask`.** Неопределённое поведение; для хранения нужен `.AsTask()`.
> - **`TaskCompletionSource` без `RunContinuationsAsynchronously`.** Продолжения выполняются в потоке, установившем результат.
> - **Забытая задача без обработки исключений.** Ошибка теряется, приложение может завершиться раньше её окончания.
> - **`WhenAll` не отменяет остальные задачи при первой ошибке.** Нужен общий `CancellationTokenSource`.

> [!example] Как делают в бою
> В прикладном коде явных `Task`-манипуляций мало: методы объявляются `async Task`, вызываются через `await`, а независимые операции объединяются `Task.WhenAll` с ограничением параллелизма через `SemaphoreSlim` или `Parallel.ForEachAsync` с `MaxDegreeOfParallelism`.
> `Task.Run` встречается ровно в одном сценарии — вынести настоящую вычислительную работу (обработка изображения, разбор большого файла) из потока запроса. Всё остальное «ускорение через `Task.Run`» — миф, забирающий потоки у того же пула.
> `TaskCompletionSource` применяют в интеграционном коде: обёртки над колбэками старых библиотек, ожидание ответа по идентификатору корреляции в брокере, тестовые заглушки, где нужно вручную управлять завершением.
> `ValueTask` появляется в библиотеках и горячих путях с кешем; в обычных сервисах его сознательно не используют — ограничения на повторный `await` и хранение легко нарушить, а выигрыш там незаметен.

## Вопросы с собеседований

> [!question]- Чем `Task` отличается от `Thread`?
> `Thread` — поток операционной системы: около мегабайта стека, миллисекунды на создание, планируется ядром. `Task` — объект в управляемой куче, представляющий операцию и её будущий результат; он не создаёт поток сам по себе. Для вычислительной задачи (`Task.Run`) исполнение действительно займёт поток пула, но для операции ввода-вывода поток не нужен вовсе: пока идёт ожидание, ни один поток не занят, а продолжение будет запланировано по завершении операции. Отсюда практическая разница в масштабировании: тысяча одновременных HTTP-запросов — это тысяча задач и десяток потоков, тогда как модель «поток на запрос» упёрлась бы в память и переключения контекста. Дополнительно `Task` даёт встроенные результат, исключения, отмену и комбинаторы, чего у `Thread` нет.

> [!question]- Что делает `Task.WhenAll` и как он ведёт себя при исключениях?
> Он возвращает задачу, завершающуюся, когда завершены **все** переданные задачи, и позволяет выполнять независимые операции параллельно вместо последовательного ожидания. При исключениях есть две тонкости. Первая: `WhenAll` дожидается всех задач, даже если одна упала сразу — остальные не отменяются автоматически, для этого нужен общий `CancellationTokenSource`. Вторая: `await` над результатом бросает только **первое** исключение, тогда как все ошибки собраны в `AggregateException` в свойстве `Exception` итоговой задачи. Поэтому при обработке ошибок нескольких задач принято ловить исключение и дополнительно перебирать `all.Exception.InnerExceptions`, иначе часть ошибок останется незамеченной. Ещё одна практическая деталь: `WhenAll` без ограничения степени параллелизма может создать сотни одновременных обращений к внешней системе, поэтому его сочетают с семафором.

> [!question]- Когда использовать `ValueTask` вместо `Task`?
> Когда метод в большинстве вызовов завершается **синхронно** и вызывается очень часто: чтение из кеша, чтение из буферизованного потока, попытка получить элемент из канала. `ValueTask<T>` — структура, поэтому при синхронном завершении объект в куче не создаётся, и на горячем пути это заметно снижает нагрузку на GC. Цена — жёсткие правила: результат можно ожидать только один раз, нельзя хранить, передавать между вызовами и ожидать параллельно; для этих случаев требуется преобразование `.AsTask()`, которое сводит выгоду на нет. Поэтому `ValueTask` уместен в библиотечных API и в измеренных горячих участках, а в обычном прикладном коде по умолчанию используют `Task`: он проще, безопаснее и разница незаметна на фоне сетевых задержек.

## Задачи

### Задача 1. Ускорить метод

```csharp
async Task<Dashboard> LoadAsync(long userId, CancellationToken ct)
{
    var profile = await _users.GetAsync(userId, ct);        // 80 мс
    var orders = await _orders.GetRecentAsync(userId, ct);   // 120 мс
    var balance = await _billing.GetBalanceAsync(userId, ct); // 90 мс
    return new Dashboard(profile, orders, balance);
}
```

> [!success]- Решение
> Три независимых вызова выполняются последовательно: 290 мс вместо 120.
> ```csharp
> async Task<Dashboard> LoadAsync(long userId, CancellationToken ct)
> {
>     var profileTask = _users.GetAsync(userId, ct);          // все три стартуют сразу
>     var ordersTask = _orders.GetRecentAsync(userId, ct);
>     var balanceTask = _billing.GetBalanceAsync(userId, ct);
>
>     await Task.WhenAll(profileTask, ordersTask, balanceTask);
>
>     return new Dashboard(await profileTask, await ordersTask, await balanceTask);
> }
> ```
> Задачи «горячие»: они начинают работу в момент вызова метода, поэтому достаточно не ставить `await` сразу. Повторный `await` после `WhenAll` мгновенен и нужен только чтобы получить типизированные результаты (и корректно пробросить исключение).
> Оговорки: все три вызова должны использовать **разные** экземпляры зависимостей или быть потокобезопасными — например, один `DbContext` так использовать нельзя, он не поддерживает параллельные операции. И при большом числе задач параллелизм ограничивают семафором, чтобы не перегрузить внешние сервисы.

### Задача 2. Ограничить параллелизм

Нужно обработать 10 000 идентификаторов, обращаясь к внешнему API, но не более 10 одновременных запросов.

> [!success]- Решение
> ```csharp
> // Вариант 1: штатный API (.NET 6+) — предпочтительный
> await Parallel.ForEachAsync(ids,
>     new ParallelOptions { MaxDegreeOfParallelism = 10, CancellationToken = ct },
>     async (id, token) => await ProcessAsync(id, token));
>
> // Вариант 2: семафор — когда нужен контроль над результатами
> using var gate = new SemaphoreSlim(10);
> var tasks = ids.Select(async id =>
> {
>     await gate.WaitAsync(ct);
>     try { return await ProcessAsync(id, ct); }
>     finally { gate.Release(); }
> });
> var results = await Task.WhenAll(tasks);
> ```
> Почему нельзя просто `Task.WhenAll` без ограничения: 10 000 одновременных запросов исчерпают пул соединений `HttpClient`, вызовут ошибки 429 у внешнего сервиса и, вероятно, таймауты. Первый вариант проще и сам управляет очередью; второй нужен, когда важно собрать результаты или обработать ошибки индивидуально. Важная деталь второго варианта: `Release` обязательно в `finally`, иначе одна ошибка навсегда «съест» слот семафора.

## Итог

- `Task` — объект-обещание результата, а не поток; ожидание I/O не занимает поток вовсе.
- Задачи в .NET горячие: операция стартует до возврата из метода; результат кешируется в задаче.
- `Task.Run` нужен только для вычислительной работы; в ASP.NET Core он обычно лишний.
- `WhenAll` даёт параллельность, но дожидается всех и показывает при `await` только первое исключение.
- Параллелизм ограничивают `Parallel.ForEachAsync` или семафором — иначе страдает внешняя система.
- `TaskCompletionSource` превращает колбэки и события в задачи; нужен `RunContinuationsAsynchronously`.
- `ValueTask` экономит аллокации при частом синхронном завершении, но его нельзя ждать дважды и хранить.
- `.Result`, `.Wait()` и `ContinueWith` — наследие: первое опасно, второе заменено `await`.
