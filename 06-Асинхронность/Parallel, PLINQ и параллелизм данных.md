# Parallel, PLINQ и параллелизм данных

> [!abstract] Коротко
> Параллелизм данных — разложить одинаковую работу над множеством элементов по ядрам процессора. В .NET для этого есть `Parallel.For`/`Parallel.ForEach` (императивно), `Parallel.ForEachAsync` (для асинхронных операций) и PLINQ (`AsParallel()`, декларативно). Ключевое различие с асинхронностью: **параллелизм ускоряет вычисления, асинхронность освобождает потоки во время ожидания**. Отсюда главное правило: `Parallel` и PLINQ — для работы, нагружающей процессор; для ввода-вывода нужен `async` и, при необходимости ограничить нагрузку, `Parallel.ForEachAsync` с явной степенью параллелизма.

## Зачем это нужно

```csharp
// 10 млн элементов, чистые вычисления
var results = new double[data.Length];
for (int i = 0; i < data.Length; i++) results[i] = Compute(data[i]);      // 8 секунд, одно ядро

Parallel.For(0, data.Length, i => results[i] = Compute(data[i]));          // 1,1 секунды на 8 ядрах
```

Но тот же приём, применённый к сетевым вызовам, не ускорит ничего и создаст проблемы: потоки будут стоять в ожидании, а внешний сервис получит шквал запросов.

## Parallel

```csharp
// Цикл по индексам
Parallel.For(0, items.Length, i => Process(items[i]));

// Цикл по коллекции
Parallel.ForEach(items, item => Process(item));

// Несколько независимых действий
Parallel.Invoke(() => TaskA(), () => TaskB(), () => TaskC());

// С настройками
Parallel.ForEach(items,
    new ParallelOptions { MaxDegreeOfParallelism = 4, CancellationToken = ct },
    item => Process(item));

// Досрочный выход
Parallel.For(0, items.Length, (i, state) =>
{
    if (items[i].IsInvalid) { state.Break(); return; }   // остановить после текущих итераций
    Process(items[i]);
});
```

`Parallel` сам разбивает диапазон на части (партиционирование), распределяет их по потокам пула и балансирует нагрузку — если одни элементы обрабатываются дольше других, свободные потоки заберут оставшуюся работу.

### Локальное состояние потока

Агрегация без общего изменяемого состояния — важный приём: вместо одной переменной под блокировкой каждый поток копит свой результат, и только в конце они складываются.

```csharp
long total = 0;

Parallel.For(0, data.Length,
    localInit: () => 0L,                                   // начальное значение для потока
    body: (i, state, local) => local + data[i],            // накопление без синхронизации
    localFinally: local => Interlocked.Add(ref total, local));  // одно объединение на поток
```

Наивный вариант с `lock` вокруг `total += data[i]` был бы медленнее последовательного цикла: конкуренция за одну ячейку сводит параллелизм на нет ([[Interlocked, volatile и модель памяти]]).

### Parallel.ForEachAsync

Для асинхронных операций с ограничением параллелизма (.NET 6+):

```csharp
await Parallel.ForEachAsync(ids,
    new ParallelOptions { MaxDegreeOfParallelism = 10, CancellationToken = ct },
    async (id, token) => await _api.LoadAsync(id, token));
```

Это правильный инструмент для «сделать N сетевых вызовов, но не больше 10 одновременно»: потоки не блокируются, нагрузка на внешнюю систему ограничена, отмена поддержана ([[Task и Task Parallel Library]]).

## PLINQ

```csharp
var result = data
    .AsParallel()
    .WithDegreeOfParallelism(4)
    .WithCancellation(ct)
    .Where(x => IsInteresting(x))
    .Select(x => Transform(x))
    .ToArray();

// Порядок не гарантирован по умолчанию — за него надо платить
var ordered = data.AsParallel().AsOrdered().Select(Transform).ToArray();

// Побочные действия без сборки результата
data.AsParallel().ForAll(item => Handle(item));

// Вернуться к последовательному выполнению
var mixed = data.AsParallel().Where(Filter).AsSequential().Take(10).ToList();
```

PLINQ хорош декларативностью, но у него есть особенности, из-за которых он применяется реже, чем `Parallel`:

- **Порядок теряется** без `AsOrdered`, а с ним часть выигрыша исчезает.
- **Накладные расходы на партиционирование** заметны на малых коллекциях: до нескольких тысяч элементов с лёгкой обработкой последовательный LINQ обычно быстрее.
- **Исключения собираются в `AggregateException`**.
- **Не для ввода-вывода**: `AsParallel()` над асинхронными операциями не даст ничего хорошего.

## Когда параллелизм окупается

Ориентир — три условия одновременно:

1. **Работа нагружает процессор**, а не ждёт ввода-вывода.
2. **Элементов много** (обычно от тысяч) или обработка одного элемента дорогая.
3. **Элементы независимы**: нет общего изменяемого состояния и порядок не важен.

Что мешает ускорению:

| Причина | Эффект |
|---|---|
| Общая блокировка внутри цикла | сериализация, может быть медленнее последовательного |
| Слишком мелкие элементы | накладные расходы на планирование превышают работу |
| Ложное разделение (false sharing) | потоки пишут в соседние ячейки одной кеш-линии, кеш «прыгает» между ядрами |
| Ввод-вывод внутри | потоки стоят, ядра простаивают |
| Сервер уже под нагрузкой | параллелизм внутри запроса отбирает ядра у других запросов |

Последний пункт часто упускают: в веб-приложении параллелизм **уже есть** — сотни одновременных запросов занимают все ядра. Дополнительное распараллеливание внутри одного запроса ускоряет его, но снижает общую пропускную способность. Оправдано оно там, где запросов мало, а работа тяжёлая (отчёты, импорт, обработка изображений).

```csharp
// Ложное разделение: потоки пишут в соседние элементы массива
var counters = new int[Environment.ProcessorCount];
Parallel.For(0, 1_000_000, i => counters[i % counters.Length]++);   // медленно из-за кеш-линий

// Лечение: локальное состояние потока и объединение в конце
```

## Обработка ошибок и отмена

```csharp
try
{
    Parallel.ForEach(items, new ParallelOptions { CancellationToken = ct }, Process);
}
catch (AggregateException ex)
{
    foreach (var inner in ex.Flatten().InnerExceptions) Log(inner);
}
catch (OperationCanceledException)
{
    // отмена — штатный исход
}
```

`Parallel` собирает все исключения в `AggregateException` и, обнаружив первое, прекращает запуск новых итераций (уже выполняющиеся дорабатывают). `Flatten()` разворачивает вложенные агрегаты в плоский список ([[Исключения в асинхронном коде]]).

## Что выбрать

| Задача | Инструмент |
|---|---|
| Вычисления над большим массивом | `Parallel.For` с локальным состоянием |
| Декларативная обработка коллекции (CPU) | PLINQ `AsParallel()` |
| N сетевых вызовов с ограничением | `Parallel.ForEachAsync` |
| Несколько независимых асинхронных операций | `Task.WhenAll` |
| Конвейер с разными этапами | `Channel<T>` |
| Обработка потока данных | `IAsyncEnumerable<T>` + `Parallel.ForEachAsync` |
| Векторизуемые вычисления | SIMD (`Vector<T>`), часто быстрее многопоточности |

Перед распараллеливанием стоит проверить, нельзя ли ускорить алгоритмически: замена `O(n²)` на `O(n log n)` даёт больше, чем восемь ядер, и не приносит проблем синхронизации ([[Введение в алгоритмы: сложность и Big-O]]).

> [!warning] Подводные камни
> - **`Parallel` для ввода-вывода.** Потоки блокируются, ядра простаивают; нужен `async` или `Parallel.ForEachAsync`.
> - **Асинхронная лямбда в `Parallel.ForEach`.** Превращается в `async void`: операции не дожидаются, ошибки теряются.
> - **Общее изменяемое состояние.** Список, словарь или счётчик без синхронизации — гонка; с блокировкой — потеря выигрыша.
> - **Непотокобезопасные объекты внутри цикла.** `DbContext`, `Random` (до .NET 6), `HttpContext` — источники «плавающих» ошибок.
> - **Ложное разделение.** Запись в соседние элементы массива из разных потоков резко замедляет работу.
> - **`MaxDegreeOfParallelism` по умолчанию на сервере.** Один запрос может занять все ядра и просадить остальные.
> - **PLINQ на маленьких коллекциях.** Накладные расходы превышают выигрыш.
> - **Отсутствие замеров.** Параллелизм часто оказывается медленнее; без бенчмарка это не видно ([[Как измерять: BenchmarkDotNet]]).

> [!example] Как делают в бою
> В типичном веб-сервисе `Parallel` и PLINQ почти не встречаются: параллелизм обеспечивается самими запросами, а работа в основном связана с вводом-выводом. Там, где они появляются, это фоновые задачи — обработка загруженных файлов, генерация отчётов, пересчёт агрегатов, обработка изображений, — и всегда с явным `MaxDegreeOfParallelism`, чтобы не съесть все ядра.
> `Parallel.ForEachAsync` используется куда чаще: это стандартный способ выполнить много сетевых вызовов с ограничением, заменивший ручные конструкции с семафором.
> Обязательная практика — измерять до и после. Регулярно оказывается, что параллельная версия медленнее из-за синхронизации, мелких элементов или ложного разделения; или что настоящее узкое место было в базе, а не в вычислениях.
> Для по-настоящему тяжёлых числовых задач перед многопоточностью рассматривают векторизацию: `Vector<T>` и SIMD дают ускорение в разы на одном ядре и без проблем синхронизации ([[Vectorization и SIMD в .NET]]).

## Вопросы с собеседований

> [!question]- Чем параллелизм отличается от асинхронности?
> Асинхронность — про то, чтобы **не занимать поток** во время ожидания: операция ввода-вывода выполняется вне процессора, и на это время поток возвращается в пул. Она повышает пропускную способность и имеет смысл даже на одном ядре. Параллелизм — про то, чтобы **задействовать несколько ядер** для одновременного выполнения вычислений: он уменьшает время одной операции и бессмысленен на одном ядре. Инструменты разные: `async`/`await`, `Task.WhenAll` — для асинхронности; `Parallel.For`, PLINQ — для параллелизма. Самая частая ошибка — применить `Parallel.ForEach` к сетевым вызовам: потоки будут просто стоять в ожидании, ядра простаивать, а внешний сервис получит неограниченный шквал запросов. Для такого случая существует `Parallel.ForEachAsync`, который сочетает асинхронное ожидание с ограничением числа одновременных операций.

> [!question]- Почему параллельная версия может оказаться медленнее последовательной?
> Несколько причин. Накладные расходы на разбиение работы, планирование и объединение результатов: если элементов мало или обработка каждого дешёвая, они превышают выигрыш. Синхронизация: общая блокировка или атомарные операции над одной ячейкой сводят параллелизм к последовательному выполнению плюс расходы на конкуренцию. Ложное разделение — потоки пишут в разные переменные, попадающие в одну строку кеша, и она «прыгает» между ядрами, что может замедлить код в разы. Ввод-вывод внутри цикла: потоки блокируются, ядра простаивают. Наконец, контекст: на загруженном сервере ядра уже заняты другими запросами, и распараллеливание внутри одного запроса отбирает ресурсы у остальных. Правильный подход — измерять бенчмарком, а перед распараллеливанием проверить алгоритмическую сложность и возможность векторизации.

> [!question]- Как правильно агрегировать результат в `Parallel.For`?
> Через локальное состояние потока: перегрузка с `localInit`, `body` и `localFinally` даёт каждому потоку собственный накопитель, в который он пишет без всякой синхронизации, а объединение происходит один раз на поток в `localFinally` — обычно через `Interlocked` или короткую блокировку. Наивный вариант с общей переменной под `lock` внутри тела цикла обычно **медленнее последовательного кода**: все потоки конкурируют за одну блокировку на каждой итерации. Тот же принцип действует и вне `Parallel`: счётчики и агрегаты в многопоточном коде выгоднее считать по потокам или по сегментам и складывать в конце. Для коллекций-результатов используют потокобезопасные типы (`ConcurrentBag`, `ConcurrentQueue`) либо запись в заранее выделенный массив по индексу — тогда синхронизация не нужна вовсе.

## Задачи

### Задача 1. Найти ошибки

```csharp
var results = new List<Result>();
Parallel.ForEach(orders, async order =>
{
    var data = await _api.LoadAsync(order.Id);
    results.Add(new Result(order.Id, data));
});
return results;
```

> [!success]- Решение
> Три ошибки. Асинхронная лямбда в `Parallel.ForEach` становится `async void`: метод завершится мгновенно, не дождавшись ни одной операции, а исключения потеряются — `results` вернётся пустым или частично заполненным. `List<T>` не потокобезопасен: параллельные `Add` портят внутреннее состояние и могут дать исключение или потерю элементов. И сама задача связана с вводом-выводом, для которого `Parallel.ForEach` не предназначен.
> ```csharp
> var results = new ConcurrentBag<Result>();
>
> await Parallel.ForEachAsync(orders,
>     new ParallelOptions { MaxDegreeOfParallelism = 10, CancellationToken = ct },
>     async (order, token) =>
>     {
>         var data = await _api.LoadAsync(order.Id, token);
>         results.Add(new Result(order.Id, data));
>     });
>
> return results.ToArray();
> ```
> `Parallel.ForEachAsync` дожидается всех операций, не блокирует потоки и ограничивает нагрузку на API. `ConcurrentBag` безопасен для параллельного добавления; если порядок важен, вместо него используют заранее выделенный массив с записью по индексу.

### Задача 2. Решить, стоит ли распараллеливать

Для каждого случая: применять `Parallel`/PLINQ или нет? (а) Сжатие 5 000 изображений в фоновой задаче. (б) Загрузка 200 записей из БД и маппинг в DTO в обработчике HTTP. (в) Подсчёт суммы по массиву из 1 000 чисел. (г) Отправка 10 000 HTTP-запросов.

> [!success]- Решение
> **(а) Да.** Классический случай: работа нагружает процессор, элементы независимы, их много, и это фоновая задача, а не обработчик запроса. Нужен `Parallel.ForEach` с `MaxDegreeOfParallelism`, чтобы не занять все ядра целиком, если сервис одновременно обслуживает запросы.
> **(б) Нет.** Узкое место — запрос к базе, а маппинг 200 объектов занимает микросекунды. Параллелизм здесь ничего не ускорит, зато отберёт ядра у других запросов. Оптимизировать надо сам запрос — проекцию, индексы, отсутствие лишних включений.
> **(в) Нет.** Тысяча простых операций выполняется за микросекунды; накладные расходы на разбиение и планирование превысят выигрыш многократно. Если такой цикл действительно горячий, выигрыш даст векторизация (`Vector<T>`), а не потоки.
> **(г) Нет для `Parallel`, да для `Parallel.ForEachAsync`.** Это ввод-вывод: `Parallel.ForEach` заблокирует потоки в ожидании. Нужен `Parallel.ForEachAsync` с ограничением параллелизма (и, вероятно, политикой повторов), чтобы не перегрузить внешний сервис и не исчерпать пул соединений.

## Итог

- Параллелизм ускоряет вычисления, асинхронность освобождает потоки при ожидании — это разные задачи.
- `Parallel.For`/`ForEach` — императивный параллелизм данных с автоматическим партиционированием и балансировкой.
- `Parallel.ForEachAsync` — правильный инструмент для многих асинхронных операций с ограничением параллелизма.
- PLINQ декларативен, но теряет порядок без `AsOrdered` и проигрывает на малых коллекциях.
- Агрегировать надо через локальное состояние потока, а не через общую переменную под блокировкой.
- Асинхронная лямбда в `Parallel.ForEach` превращается в `async void` — операции не дожидаются.
- Общее изменяемое состояние, ложное разделение и ввод-вывод внутри цикла убивают выигрыш.
- На сервере параллелизм уже обеспечен запросами: распараллеливание внутри запроса снижает пропускную способность.
