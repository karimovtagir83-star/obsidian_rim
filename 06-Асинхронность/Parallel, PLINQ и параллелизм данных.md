# Parallel, PLINQ и параллелизм данных

> [!abstract] Коротко
> Есть две соседние, но разные модели параллельной обработки. **Параллелизм данных** — одна и та же операция выполняется над множеством элементов сразу на нескольких ядрах: `Parallel.For`/`Parallel.ForEach` (императивно) и PLINQ (`AsParallel()`, декларативно). **Конвейер (pipeline)** — данные проходят через несколько разных этапов обработки, каждый в своём темпе, и связываются асинхронной очередью `Channel<T>`. Первое ускоряет один этап за счёт ядер, второе разводит разные этапы во времени и не даёт быстрому этапу задавить медленный. Путать их — переусложнить код: конвейер ради одного однородного цикла не нужен, а параллельный цикл не решает задачу «читаем из одного источника, пишем в другой с иной скоростью».

## Зачем это знать

Агент почти всегда предлагает `Parallel.ForEach` там, где на самом деле нужен `Task.WhenAll` или `Channel<T>` — потому что в обучающих примерах эти три вещи выглядят взаимозаменяемо. Разница проявляется в проде: `Parallel.ForEach` над сетевыми вызовами блокирует пул потоков, а забытый `Complete()` у `Channel` вешает фоновую службу навсегда. Оба случая не ловятся компилятором и почти никогда — тестами на CI, только нагрузкой.

## Модель

### Parallel: императивный параллелизм данных

```csharp
Parallel.For(0, items.Length, i => Process(items[i]));

Parallel.ForEach(items,
    new ParallelOptions { MaxDegreeOfParallelism = 4, CancellationToken = ct },
    item => Process(item));

// Локальное состояние потока — агрегация без общей блокировки
long total = 0;
Parallel.For(0, data.Length,
    localInit: () => 0L,
    body: (i, _, local) => local + data[i],
    localFinally: local => Interlocked.Add(ref total, local));
```

`Parallel` сам разбивает диапазон на части и распределяет по потокам пула, балансируя нагрузку. Работает только тогда, когда элементы независимы и обработка — чистый CPU: она забирает ядро на всё время своей работы, поток не освобождается для другой задачи.

### Parallel.ForEachAsync: параллелизм данных для I/O

```csharp
await Parallel.ForEachAsync(ids,
    new ParallelOptions { MaxDegreeOfParallelism = 10, CancellationToken = ct },
    async (id, token) => await _api.LoadAsync(id, token));
```

Это мост между двумя мирами: те же «много однородных операций», но с ограничением параллелизма без блокировки потоков — заменяет ручные конструкции с семафором вокруг `Task.WhenAll`.

### PLINQ: декларативный параллелизм данных

```csharp
var result = data.AsParallel()
    .WithDegreeOfParallelism(4)
    .Where(IsInteresting)
    .Select(Transform)
    .ToArray();
```

Та же модель, что `Parallel`, но в LINQ-синтаксисе. Порядок теряется без `AsOrdered()`, накладные расходы на партиционирование заметны на малых коллекциях, исключения собираются в `AggregateException`. Не для ввода-вывода — `AsParallel()` над асинхронными операциями не даёт ничего хорошего.

### Channel: асинхронная очередь между этапами

```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(1000)
{
    FullMode = BoundedChannelFullMode.Wait
});

// Производитель
await channel.Writer.WriteAsync(job, ct);
channel.Writer.Complete();                     // сигнал: записей больше не будет

// Потребитель
await foreach (var job in channel.Reader.ReadAllAsync(ct))
    await ProcessAsync(job, ct);
```

Это другая задача: не «ускорить один этап», а **развязать разные этапы**, работающие с разной скоростью — чтение файла, разбор, запись в базу, каждый в своём `Task`, связанные каналами. Ограниченная ёмкость даёт обратное давление: если потребитель отстаёт, `WriteAsync` заставляет производителя подождать, вместо того чтобы копить очередь до `OutOfMemoryException`. Явное завершение (`Complete`/`Completion`) — ключевое отличие от «просто очереди»: потребитель узнаёт о конце данных сам, без внешнего сигнала.

```csharp
// Конвейер из трёх этапов, каждый со своей ёмкостью
var raw = Channel.CreateBounded<string>(100);
var parsed = Channel.CreateBounded<Order>(100);

var reading = Task.Run(async () => { await foreach (var l in ReadLinesAsync(ct)) await raw.Writer.WriteAsync(l, ct); raw.Writer.Complete(); });
var parsing = Task.Run(async () => { await foreach (var l in raw.Reader.ReadAllAsync(ct)) await parsed.Writer.WriteAsync(Parse(l), ct); parsed.Writer.Complete(); });
var writing = Task.Run(async () => { await foreach (var o in parsed.Reader.ReadAllAsync(ct)) await SaveAsync(o, ct); });

await Task.WhenAll(reading, parsing, writing);
```

Канал живёт **в памяти процесса**: при перезапуске содержимое теряется, гарантий доставки нет. Для данных, которые нельзя терять (платежи, документы), нужна персистентная очередь или таблица-outbox; канал уместен там, где потерю можно пережить или легко повторить ([[Паттерн Transactional Outbox]]).

## Решения

| Задача | Модель | Инструмент |
|---|---|---|
| Одинаковая CPU-операция над множеством элементов | параллелизм данных | `Parallel.For`/`ForEach`, локальное состояние потока |
| То же самое, декларативно | параллелизм данных | PLINQ `AsParallel()` |
| N сетевых вызовов с ограничением | параллелизм данных (I/O) | `Parallel.ForEachAsync` |
| Несколько независимых асинхронных операций | асинхронность, не параллелизм | `Task.WhenAll` |
| Данные проходят разные этапы обработки с разной скоростью | конвейер | `Channel<T>` между этапами |
| Разгрузить HTTP-запрос: принять и ответить сразу | конвейер | `Channel<T>` + `BackgroundService` |
| Пакетирование записей перед вставкой в БД | конвейер | `Channel<T>` + накопление по размеру/таймеру |
| Векторизуемые числовые вычисления | ни то, ни другое | SIMD (`Vector<T>`), часто быстрее многопоточности |

Правило выбора: если после разбиения на части их можно обработать **одинаковой функцией независимо друг от друга** — это параллелизм данных. Если у задачи есть стадии, каждая со своей логикой и своим темпом, — это конвейер, и связывать стадии параллельным циклом бессмысленно: он не умеет ждать, пока следующий этап освободится.

> [!example] В ServiceShop
> Пакетная обработка заказов (закрытие смены, пересчёт отчётов) — кандидат на `Parallel.ForEachAsync` с ограничением параллелизма: десятки тысяч заказов, для каждого независимый вызов к БД или внешнему сервису, но нельзя открывать тысячи соединений одновременно.
> Конвейер обработки входящих событий — другая модель: событие из Kafka разбирается, обогащается справочными данными, затем пишется в БД, и эти три шага логично развести `Channel<T>` между собой, чтобы медленная запись в БД не блокировала чтение из топика. Раскладку по конкретным модулям и файлам стоит уточнить в коде — здесь она может отличаться от общей схемы.

> [!warning] Где ошибаются
> - **Агент часто:** предлагает `Parallel.ForEach` для сетевых вызовов вместо `Task.WhenAll` или `Parallel.ForEachAsync` — потоки блокируются в ожидании, ядра простаивают, а внешний сервис получает неограниченный шквал запросов.
> - **Агент часто:** пишет `Channel<T>` для producer-consumer, но забывает вызвать `Writer.Complete()` — `ReadAllAsync` не завершается никогда, фоновая служба не останавливается при `SIGTERM`.
> - Асинхронная лямбда внутри `Parallel.ForEach` превращается в `async void`: метод продолжает без ожидания, исключения теряются.
> - Общее изменяемое состояние (список, счётчик) без синхронизации в параллельном цикле — гонка; с `lock` на каждой итерации — итог медленнее последовательного кода.
> - Неограниченный `Channel` (`CreateUnbounded`) в проде: при отставании потребителя память растёт до OOM — ёмкость нужна почти всегда.
> - Исключение внутри цикла потребителя канала без `try/catch` останавливает всю дальнейшую обработку молча.
> - PLINQ и `Parallel` применяют к маленьким коллекциям (сотни элементов) — накладные расходы на партиционирование превышают выигрыш.

## Проверка на ревью

- В `Parallel.ForEach`/`AsParallel()` внутри тела нет `await` и сетевых или файловых вызовов — только CPU-работа.
- У `Parallel.ForEach`/`Parallel.For` задан `MaxDegreeOfParallelism`, если код исполняется в сервисе, который параллельно обслуживает запросы.
- Агрегация результата идёт через `localInit`/`localFinally` или потокобезопасную коллекцию, а не через `lock` вокруг общей переменной.
- Каждый `Channel.CreateBounded`/`CreateUnbounded` — осознанный выбор ёмкости, а не `CreateUnbounded` по умолчанию.
- На стороне производителя канала явно вызывается `Writer.Complete()` (в том числе в `finally`/`catch`), иначе потребитель зависает.
- Цикл потребителя канала (`ReadAllAsync`/`while (TryRead)`) ловит исключения по элементу, а не даёт им остановить весь `foreach`.

## Проверь себя

> [!question]- Чем параллелизм данных отличается от конвейера на каналах?
> Параллелизм данных — это одна и та же операция, выполняемая параллельно над множеством независимых элементов: цель — использовать несколько ядер и сократить время одного этапа. Конвейер — это несколько разных операций (этапов), выстроенных последовательно, где каждый этап работает в своём темпе; цель — развязать этапы друг от друга, а не ускорить один из них. `Parallel`/PLINQ хороши для первого: они распараллеливают одну функцию. `Channel<T>` создан для второго: он передаёт данные между разными кусками кода, каждый из которых может быть однопоточным. Смешение моделей — например, попытка сделать конвейер через `Parallel.ForEach` с общей коллекцией — обычно приводит к гонкам и потере обратного давления.

> [!question]- Почему `Parallel.ForEach` с асинхронной лямбдой — ошибка?
> Тело `Parallel.ForEach` ожидает делегат `Action<T>`, а не `Func<T, Task>`. Если передать `async` лямбду, компилятор молча превращает её в `async void`: `Parallel.ForEach` считает итерацию завершённой сразу после первого `await`, не дожидаясь фактического выполнения операции. В результате цикл заканчивается почти мгновенно, ни одна асинхронная операция может не успеть выполниться, а исключения из `async void` некому перехватить — они улетают в необработанный поток и в лучшем случае валят процесс. Правильная замена — `Parallel.ForEachAsync`, у которого делегат явно асинхронный и который дожидается каждой операции.

> [!question]- Зачем каналу ограниченная ёмкость, если можно использовать `CreateUnbounded`?
> Ограниченная ёмкость — это единственный встроенный механизм обратного давления: пока очередь заполнена, `WriteAsync` не завершается, и производитель ждёт вместо того, чтобы копить работу впрок. Без ограничения при отставании потребителя очередь растёт, пока хватает памяти, и процесс падает по `OutOfMemoryException` — обычно не сразу, а через часы работы под нагрузкой, когда причину уже трудно связать с изменением в коде. `CreateUnbounded` оправдан только тогда, когда производитель гарантированно медленнее потребителя или объём данных заранее ограничен.

> [!question]- Почему параллельная версия цикла иногда оказывается медленнее последовательной?
> Несколько причин, каждая проверяется бенчмарком, а не интуицией. Накладные расходы на разбиение работы и объединение результатов превышают выигрыш, если элементов мало или обработка каждого дешёвая. Общая блокировка внутри тела цикла сериализует работу и добавляет расходы на конкуренцию за блокировку. Ложное разделение (false sharing) — запись из разных потоков в соседние ячейки одного массива — заставляет кеш-линию «прыгать» между ядрами. И контекст: на сервере, уже занятом другими запросами, параллелизм внутри одного запроса отбирает ядра у остальных, ускоряя один запрос ценой общей пропускной способности.

## Разбор

### Задача 1. Найти проблему

```csharp
var results = new List<Result>();
Parallel.ForEach(orders, async order =>
{
    var data = await _api.LoadAsync(order.Id);
    results.Add(new Result(order.Id, data));
});
return results;
```

> [!success]- Решение
> Три ошибки сразу. Асинхронная лямбда в `Parallel.ForEach` превращается в `async void`: метод возвращает `results` до того, как завершится хотя бы один вызов `LoadAsync`, а исключения теряются. `List<T>` не потокобезопасен — параллельные `Add` портят внутреннее состояние. И сама задача — сетевой вызов, для которого `Parallel.ForEach` не подходит в принципе.
> ```csharp
> var results = new ConcurrentBag<Result>();
> await Parallel.ForEachAsync(orders,
>     new ParallelOptions { MaxDegreeOfParallelism = 10, CancellationToken = ct },
>     async (order, token) =>
>     {
>         var data = await _api.LoadAsync(order.Id, token);
>         results.Add(new Result(order.Id, data));
>     });
> return results.ToArray();
> ```

### Задача 2. Ревью PR агента

Агент реализовал фоновую отправку писем через канал:

```csharp
public sealed class EmailWorker(Channel<EmailJob> channel, IEmailSender sender) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var job in channel.Reader.ReadAllAsync(stoppingToken))
            await sender.SendAsync(job, stoppingToken);
    }
}
// В контроллере: await channel.Writer.WriteAsync(job, ct); — и всё
```

> [!success]- Решение
> Что вернуть на доработку: (1) нигде не вызывается `Writer.Complete()` — при штатной остановке сервиса `ReadAllAsync` не завершится, `ExecuteAsync` зависнет, graceful shutdown не сработает; (2) ошибка `SendAsync` для одного письма не поймана внутри цикла — упадёт весь `foreach`, и обработчик перестанет читать канал навсегда; (3) канал создаётся, скорее всего, `CreateUnbounded` — нужно проверить и заменить на ограниченный с явным `FullMode`. Верное решение оборачивает `SendAsync` в `try/catch` внутри `foreach` и вызывает `Complete()` там, где известно, что писем больше не будет (или подписывается на остановку хоста).

## Итог

- Параллелизм данных (`Parallel`, PLINQ) ускоряет один однородный этап за счёт нескольких ядер; конвейер (`Channel<T>`) развязывает разные этапы, работающие с разной скоростью. Это разные задачи, и путать их — источник лишней сложности или гонок.
- `Parallel`/PLINQ — только для CPU-bound работы с независимыми элементами; для I/O — `Parallel.ForEachAsync` или `Task.WhenAll`.
- Агрегировать в параллельном цикле нужно через локальное состояние потока, а не общую переменную под блокировкой.
- Ограниченная ёмкость канала — это обратное давление: без неё отставший потребитель приводит к OOM.
- `Writer.Complete()` — обязательная часть контракта канала: без него потребитель не узнает о конце данных и зависнет.
- Канал живёт в памяти процесса; для данных, которые нельзя терять, нужен брокер или outbox, а не `Channel<T>`.
- Перед распараллеливанием стоит измерить и проверить алгоритмическую сложность — параллелизм часто оказывается медленнее из-за накладных расходов или синхронизации.
