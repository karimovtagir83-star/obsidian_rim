# async и await: как это работает на самом деле

> [!abstract] Коротко
> `async`/`await` — не «магия многопоточности», а преобразование кода компилятором: метод превращается в **конечный автомат**, где каждый `await` становится точкой возможной приостановки. При достижении `await` проверяется, завершена ли уже операция; если да — выполнение продолжается синхронно без всяких переключений, если нет — метод возвращает управление вызывающему, а продолжение будет запущено по завершении операции. Ключевая мысль, которую надо унести: **`async` не создаёт потоков**. Он позволяет не занимать поток на время ожидания, и именно поэтому веб-сервер держит десятки тысяч соединений на десятке потоков.

## Зачем это нужно

Без понимания механики невозможно объяснить ни одну из типичных проблем: почему `.Result` даёт дедлок, почему `async void` роняет процесс, почему после `await` код может выполняться в другом потоке, почему асинхронный метод «дороже» синхронного и зачем нужен `ConfigureAwait(false)`.

Плюс это один из самых частых вопросов на собеседовании уровня middle — и отвечать на него надо не «await ждёт задачу», а через автомат состояний.

## Что делает компилятор

```csharp
public async Task<int> LoadAsync(long id)
{
    var order = await _repository.GetAsync(id);      // точка приостановки 1
    var user = await _users.GetAsync(order.UserId);  // точка приостановки 2
    return order.Total + user.Bonus;
}
```

Компилятор порождает примерно такую структуру (упрощённо):

```csharp
public Task<int> LoadAsync(long id)
{
    var machine = new <LoadAsync>d__0
    {
        _this = this,
        id = id,
        builder = AsyncTaskMethodBuilder<int>.Create(),
        state = -1
    };
    machine.builder.Start(ref machine);      // синхронно выполняет код до первого «неготового» await
    return machine.builder.Task;             // возвращает Task вызывающему
}

private struct <LoadAsync>d__0 : IAsyncStateMachine
{
    public int state;
    public AsyncTaskMethodBuilder<int> builder;
    public long id;
    private Order order;                     // ЛОКАЛЬНЫЕ переменные стали полями
    private TaskAwaiter<Order> awaiter1;

    public void MoveNext()
    {
        switch (state)
        {
            case -1:                          // первый вход
                awaiter1 = _repository.GetAsync(id).GetAwaiter();
                if (!awaiter1.IsCompleted)    // операция не готова — приостанавливаемся
                {
                    state = 0;
                    builder.AwaitUnsafeOnCompleted(ref awaiter1, ref this);   // здесь структура УПАКУЕТСЯ в кучу
                    return;                    // управление возвращается вызывающему
                }
                goto case 0;                   // готова — продолжаем синхронно

            case 0:
                order = awaiter1.GetResult();
                // ... второй await аналогично ...
                builder.SetResult(order.Total + user.Bonus);
                return;
        }
    }
}
```

Из этого разворачивания следует всё остальное поведение.

### Следствие 1: до первого «неготового» await всё синхронно

Тело `async`-метода выполняется в вызывающем потоке до первого `await`, операция под которым ещё не завершена. Это значит:

```csharp
async Task<int> Compute()
{
    HeavyCpuWork();                 // выполнится СИНХРОННО в потоке вызывающего
    await Task.Delay(10);
    return 42;
}
var task = Compute();               // здесь уже потрачено время на HeavyCpuWork
```

Асинхронный метод не «уходит в фон» автоматически — он работает до первой реальной приостановки.

### Следствие 2: быстрый путь для готовых задач

Если операция завершилась синхронно (кеш попал, буфер уже заполнен), `IsCompleted` вернёт `true`, и `await` **не создаёт продолжение и не переключает контекст** — код идёт дальше в том же потоке. Именно поэтому асинхронные API, часто завершающиеся синхронно, стоят почти столько же, сколько синхронные.

### Следствие 3: цена

Первое приостанавливающее `await` упаковывает структуру-автомат в кучу (она должна пережить возврат из метода) и создаёт объект `Task`. Отсюда: асинхронный метод, который **никогда** не приостанавливается, почти бесплатен; метод с реальной приостановкой стоит две-три небольшие аллокации. В горячих путях это лечат `ValueTask` и пулингом ([[Асинхронность и производительность: ValueTask, пулинг]]).

Локальные переменные, живущие через `await`, становятся полями автомата и переезжают в кучу — поэтому асинхронный метод с десятком локальных дороже синхронного ([[Стек и куча: что где лежит]]).

## Awaiter: что можно ожидать

`await` не привязан к `Task`. Компилятор требует лишь, чтобы у выражения был метод `GetAwaiter()`, возвращающий тип с тремя членами:

```csharp
public struct MyAwaiter : INotifyCompletion
{
    public bool IsCompleted { get; }          // готово ли уже
    public void OnCompleted(Action continuation);   // как запланировать продолжение
    public TResult GetResult();               // забрать результат или бросить исключение
}
```

Поэтому ждать можно `Task`, `ValueTask`, `Task.Yield()`, `ValueTuple` из задач (в некоторых библиотеках), таймеры, каналы и любые свои типы. Метод `GetAwaiter` можно добавить и extension-методом — так реализованы, например, ожидание `TimeSpan` в учебных примерах.

## Где выполняется продолжение

При приостановке фиксируются два контекста:

- **`ExecutionContext`** — переносится всегда: `AsyncLocal`, культура потока, идентификация пользователя. Это делает `HttpContext.User` доступным после `await`.
- **`SynchronizationContext`** (или текущий `TaskScheduler`) — определяет, **куда** отправить продолжение.

```csharp
// ASP.NET Core: контекста синхронизации нет — продолжение идёт в любой поток пула
await LoadAsync();
// здесь другой поток, но HttpContext доступен (это ExecutionContext, а не поток)

// WPF/WinForms: продолжение вернётся в UI-поток
await LoadAsync();
label.Text = "готово";       // безопасно: снова UI-поток

// Отказ от возврата в контекст
await LoadAsync().ConfigureAwait(false);
```

Подробно — [[Контекст синхронизации и ConfigureAwait]].

## Типы возврата

| Тип | Когда |
|---|---|
| `Task` | нет результата — основной вариант |
| `Task<T>` | есть результат — основной вариант |
| `ValueTask`/`ValueTask<T>` | горячий путь, часто синхронное завершение |
| `void` | **только** обработчики событий; в остальных случаях ошибка |
| `IAsyncEnumerable<T>` | асинхронный поток значений (`await foreach`) |
| свой тип с `[AsyncMethodBuilder]` | библиотеки со специальной семантикой |

```csharp
// async void: исключение НЕ попадает в Task и обычно роняет процесс
private async void Button_Click(object sender, EventArgs e)
{
    try { await LoadAsync(); }        // обработка обязательна внутри
    catch (Exception ex) { Show(ex); }
}
```

Разбор опасностей — [[Дедлоки, async void и типичные ошибки]].

## Правила, которые следуют из механики

**Асинхронность «до самого верха».** Смешивание синхронного и асинхронного кода (`.Result`, `.Wait()`) уничтожает выигрыш и создаёт риск дедлока: поток блокируется, ожидая продолжение, которое, возможно, планируется в тот же поток.

```csharp
// Плохо: sync-over-async
public int GetTotal() => LoadAsync().Result;

// Хорошо: асинхронность проходит через весь стек вызовов
public Task<int> GetTotalAsync(CancellationToken ct) => LoadAsync(ct);
```

**`async` без `await` бессмыслен.** Компилятор предупредит (CS1998): метод выполняется полностью синхронно, но платит за автомат.

```csharp
// Лишний автомат
public async Task<int> GetAsync() { return 42; }
// Правильно
public Task<int> GetAsync() => Task.FromResult(42);

// Но: убирать async ради «оптимизации» из метода с try/catch или using нельзя —
// без await ресурс освободится до завершения задачи
public async Task<string> ReadAsync(string path)
{
    using var reader = new StreamReader(path);
    return await reader.ReadToEndAsync();     // без await using закроется раньше времени
}
```

**Токен отмены передаётся всегда.** Это часть контракта асинхронного метода ([[CancellationToken и отмена операций]]).

**Суффикс `Async` в имени** — соглашение платформы, помогающее не забыть `await`.

## Отладка и диагностика

Стек вызовов асинхронного метода не соответствует физическому стеку: продолжение выполняется в другом кадре, возможно, в другом потоке. Отладчик восстанавливает логическую цепочку по продолжениям, но при исключениях видны внутренние кадры `MoveNext` и инфраструктуры.

Полезное:

- окно Tasks / Parallel Stacks вместо обычного стека;
- `[AsyncMethodBuilder]`-инфраструктура видна в трассировке — это нормально;
- структурные логи с идентификатором корреляции восстанавливают последовательность лучше стека ([[Отладка: точки останова, watch, immediate]]).

> [!info] Что изменится в будущем
> В .NET 11 ожидается **Runtime Async**: машина состояний переезжает с уровня компилятора на уровень рантайма. Прикладной код не изменится, но аллокаций станет меньше, а стеки — понятнее. Пока это preview ([[Что впереди: .NET 11 и C# 15]]).

> [!warning] Подводные камни
> - **«`async` создаёт поток».** Не создаёт. Он позволяет не занимать поток на время ожидания.
> - **`.Result`/`.Wait()`.** Блокировка потока плюс возможный дедлок в контексте с синхронизацией.
> - **`async void`.** Исключение не попадает в задачу и обычно завершает процесс.
> - **Забытый `await`.** Задача не дождана, исключения теряются; компилятор предупреждает (CS4014).
> - **`async` без `await`.** Лишний автомат и предупреждение CS1998.
> - **Тяжёлая синхронная работа в начале `async`-метода.** Выполняется в потоке вызывающего до первого `await`.
> - **Ожидание, что после `await` тот же поток.** В ASP.NET Core — обычно другой; состояние надо держать в переменных, а не в `ThreadLocal`.
> - **`async` поверх синхронного API через `Task.Run`.** Не делает код асинхронным — просто перекладывает блокировку на другой поток пула.

> [!example] Как делают в бою
> Правило простое: асинхронность идёт сквозь весь стек — от контроллера до драйвера БД, без единого `.Result`. Каждый асинхронный метод принимает `CancellationToken` и передаёт его дальше, имя заканчивается на `Async`.
> `ConfigureAwait(false)` ставят в библиотеках; в приложениях на ASP.NET Core он не нужен, потому что контекста синхронизации там нет ([[Контекст синхронизации и ConfigureAwait]]).
> Анализаторы включают обязательно: они ловят забытый `await`, `async void`, синхронные вызовы поверх асинхронных API и отсутствие токена отмены — это самые дорогие ошибки в проде.
> Оптимизация асинхронного кода начинается не с `ValueTask`, а с устранения лишних приостановок: если метод только пробрасывает вызов, `async`/`await` можно убрать и вернуть задачу напрямую — но лишь когда в методе нет `using`, `try/catch` и ничего не зависит от завершения.

## Вопросы с собеседований

> [!question]- Во что компилятор разворачивает `async`-метод?
> В конечный автомат: генерируется структура, реализующая `IAsyncStateMachine`, в которой поля соответствуют параметрам и локальным переменным метода, а поле состояния указывает, на каком `await` выполнение было приостановлено. Тело метода превращается в метод `MoveNext` с переключателем по состоянию. Сам метод при вызове создаёт автомат и построитель (`AsyncTaskMethodBuilder`), запускает `MoveNext` синхронно и возвращает вызывающему `Task` из построителя. На каждом `await` проверяется `IsCompleted` у awaiter'а: если операция уже завершена, выполнение продолжается синхронно без переключений; если нет — регистрируется продолжение, структура автомата упаковывается в кучу (она должна пережить возврат), и управление возвращается вызывающему. По завершении операции продолжение вызывает `MoveNext` снова, и выполнение возобновляется с сохранённого состояния.

> [!question]- Создаёт ли `async` новый поток?
> Нет. `async`/`await` — механизм, позволяющий **не занимать** поток на время ожидания, а не создавать новые. При асинхронной операции ввода-вывода работа выполняется вне управляемого кода — на уровне ОС и драйверов, — и на время ожидания ни один поток не блокируется; продолжение будет запланировано в пул потоков по завершении операции. Поток появляется только в двух случаях: явное `Task.Run`, которое отправляет вычислительную работу в пул, и продолжения, которые выполняются в потоке пула. Именно поэтому асинхронность повышает **пропускную способность** сервера (тысячи одновременных запросов на десятке потоков), но не ускоряет одну конкретную операцию: сетевой запрос не станет быстрее оттого, что его ждут асинхронно.

> [!question]- Почему после `await` код может выполняться в другом потоке и что при этом сохраняется?
> Потому что продолжение планируется заново: если есть контекст синхронизации (UI-приложения), оно вернётся в его поток; если нет (ASP.NET Core, консоль), оно будет выполнено любым свободным потоком пула. Физически тот же поток к этому моменту уже занят другой работой. При этом переносится `ExecutionContext` — в нём живут `AsyncLocal`, культура и данные идентификации, поэтому `HttpContext.User` и идентификатор корреляции остаются доступны после `await`. Не переносится привязка к конкретному потоку: `ThreadLocal`, `Thread.CurrentThread.ManagedThreadId` и блокировки, захваченные `Monitor`, после возобновления могут вести себя неожиданно — в частности, поэтому нельзя удерживать `lock` через `await`.

> [!question]- Что произойдёт, если вызвать `.Result` на незавершённой задаче?
> Текущий поток заблокируется до завершения задачи. В приложении без контекста синхронизации (ASP.NET Core) это «всего лишь» потеря потока пула: под нагрузкой такие блокировки быстро исчерпывают пул, запросы начинают ждать свободных потоков, и латентность растёт лавинообразно — классическое thread pool starvation. В приложении с контекстом синхронизации (WPF, WinForms, старый ASP.NET) это ещё и **дедлок**: продолжение асинхронного метода должно выполниться в захваченном контексте, а его единственный поток заблокирован ожиданием этой же задачи. Дополнительно `.Result` оборачивает исключения в `AggregateException`, что усложняет обработку. Правильное решение — асинхронность через весь стек вызовов; если синхронный API неизбежен (например, интерфейс библиотеки), лучше выполнять работу синхронно, чем блокировать поток на асинхронной операции.

## Задачи

### Задача 1. Предсказать порядок вывода

```csharp
async Task Main()
{
    Console.Write("1");
    var t = WorkAsync();
    Console.Write("3");
    await t;
    Console.Write("5");
}

async Task WorkAsync()
{
    Console.Write("2");
    await Task.Delay(100);
    Console.Write("4");
}
```

> [!success]- Решение
> Вывод: `12345`.
> Разбор: `WorkAsync` начинает выполняться **синхронно** в вызывающем потоке и печатает «2» ещё до возврата — асинхронный метод не «уходит в фон» сам по себе. На `await Task.Delay(100)` операция не готова, поэтому метод возвращает незавершённую задачу вызывающему, и печатается «3». Затем `await t` приостанавливает `Main`, через 100 мс продолжение `WorkAsync` печатает «4», задача завершается, и продолжение `Main` печатает «5».
> Полезное следствие: если бы вместо `Task.Delay` стоял уже завершённый `Task.CompletedTask`, весь метод выполнился бы синхронно, и вывод был бы `12435`... нет — `1`, затем «2» и «4» подряд (быстрый путь без приостановки), затем «3», затем «5»: то есть `12435`. Это хорошая иллюстрация того, что поведение зависит от того, завершена ли операция на момент `await`.

### Задача 2. Найти проблемы

```csharp
public class OrderService
{
    public async void ProcessAll(List<long> ids)
    {
        foreach (var id in ids)
        {
            var order = _repo.GetAsync(id).Result;
            await SendEmailAsync(order);
        }
    }
}
```

> [!success]- Решение
> Четыре проблемы, каждая серьёзная.
> `async void` — исключение из метода не попадает в задачу: его нельзя перехватить у вызывающего, и в большинстве хостов оно завершает процесс. Вызывающий также не может дождаться завершения.
> `.Result` блокирует поток пула на время запроса к БД и в контексте с синхронизацией даёт дедлок; под нагрузкой это исчерпание пула.
> Последовательная обработка в цикле: тысяча идентификаторов — тысяча последовательных обращений, хотя они независимы.
> Нет `CancellationToken`: остановить обработку невозможно, при остановке приложения метод продолжит работу.
> ```csharp
> public async Task ProcessAllAsync(IReadOnlyList<long> ids, CancellationToken ct)
> {
>     await Parallel.ForEachAsync(ids,
>         new ParallelOptions { MaxDegreeOfParallelism = 8, CancellationToken = ct },
>         async (id, token) =>
>         {
>             var order = await _repo.GetAsync(id, token);
>             await SendEmailAsync(order, token);
>         });
> }
> ```
> Метод стал `async Task` (можно дождаться и поймать ошибки), блокировок нет, обработка идёт с ограниченным параллелизмом, токен пробрасывается до самых нижних вызовов. Если порядок обработки важен, вместо `Parallel.ForEachAsync` остаётся цикл с `await`, но уже без `.Result`.

## Итог

- `async`/`await` — преобразование метода в конечный автомат; каждый `await` — точка возможной приостановки.
- До первого «неготового» `await` код выполняется синхронно в потоке вызывающего.
- Если операция уже завершена, `await` не приостанавливает и не переключает контекст (быстрый путь).
- `async` не создаёт потоков: он позволяет не занимать поток во время ожидания.
- Локальные переменные, живущие через `await`, переезжают в объект автомата в куче.
- `await` работает с любым типом, у которого есть `GetAwaiter()` с `IsCompleted`/`OnCompleted`/`GetResult`.
- После `await` поток может быть другим; `ExecutionContext` (и `AsyncLocal`) при этом переносится.
- Асинхронность должна проходить через весь стек: `.Result` и `.Wait()` — блокировка и риск дедлока.
