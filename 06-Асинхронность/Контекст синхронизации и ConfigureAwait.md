# Контекст синхронизации и ConfigureAwait

> [!abstract] Коротко
> Контекст синхронизации (`SynchronizationContext`) — абстракция «куда отправить продолжение». В UI-приложениях он возвращает выполнение в поток интерфейса, в старом ASP.NET — в контекст запроса, а в **ASP.NET Core и консоли его нет вообще** (`null`), поэтому продолжения выполняются в любом свободном потоке пула. По умолчанию `await` захватывает текущий контекст и возвращается в него; `ConfigureAwait(false)` отключает это поведение. Отсюда практическое правило: в библиотеках `ConfigureAwait(false)` нужен, в приложениях на ASP.NET Core — нет, потому что захватывать нечего.

## Зачем это нужно

Три вопроса, ответы на которые прячутся здесь: почему `.Result` в WPF даёт дедлок, а в ASP.NET Core «всего лишь» тратит поток; зачем в чужих библиотеках повсюду `ConfigureAwait(false)`; почему после `await` в веб-приложении другой поток, но `HttpContext` всё ещё доступен.

---

## Что такое контекст синхронизации

Это объект с методом `Post(callback, state)`, который умеет выполнить делегат «в правильном месте». Реализация зависит от среды:

| Среда | Контекст | Куда отправляет продолжение |
|---|---|---|
| WPF | `DispatcherSynchronizationContext` | в UI-поток через очередь диспетчера |
| WinForms | `WindowsFormsSynchronizationContext` | в UI-поток через цикл сообщений |
| ASP.NET (Framework) | `AspNetSynchronizationContext` | в контекст запроса, по одному потоку за раз |
| **ASP.NET Core** | **`null`** | в любой поток пула |
| Консоль, фоновые службы | `null` | в любой поток пула |
| xUnit (по умолчанию) | свой контекст | сериализует выполнение теста |

```csharp
Console.WriteLine(SynchronizationContext.Current?.GetType().Name ?? "нет контекста");
```

Когда выполнение доходит до `await` над незавершённой задачей, компилятор (точнее, `TaskAwaiter`) запоминает текущий контекст, и по завершении операции продолжение отправляется через него. Если контекста нет, используется текущий `TaskScheduler`, а по умолчанию — пул потоков.

```csharp
// WPF: продолжение вернётся в UI-поток, поэтому обращение к элементу безопасно
private async void Load_Click(object sender, RoutedEventArgs e)
{
    var data = await _service.LoadAsync();
    ResultLabel.Text = data.Title;      // тот же UI-поток
}
```

## ConfigureAwait

```csharp
await SomeAsync();                       // = ConfigureAwait(true): вернуться в контекст
await SomeAsync().ConfigureAwait(false); // продолжить в любом потоке пула
```

`ConfigureAwait(false)` говорит: «мне неважно, где продолжится выполнение». Это даёт два эффекта — снимает риск дедлока при блокирующем ожидании выше по стеку и убирает лишнее переключение (в UI-приложениях оно стоит постановки в очередь диспетчера).

### Где он нужен

| Код | Нужен ли `ConfigureAwait(false)` |
|---|---|
| Библиотека общего назначения (NuGet-пакет) | **да**, на каждом `await` |
| Общий код, используемый и в UI, и на сервере | **да** |
| Приложение ASP.NET Core | нет — контекста нет |
| Консольное приложение, фоновая служба | нет |
| UI-обработчик, где нужен доступ к элементам | нет — контекст нужен |
| Метод библиотеки, который обязан вернуться в UI-поток | нет (редкий случай, документируется) |

Причина различия: библиотека не знает, в какой среде её вызовут. Если она вызывается из WPF без `ConfigureAwait(false)`, каждое её внутреннее `await` будет гонять продолжение через очередь UI-потока — это и медленно, и создаёт условия для дедлока, если вызывающий заблокировался на `.Result`.

```csharp
// Библиотечный код
public async Task<Order> GetAsync(long id, CancellationToken ct)
{
    var response = await _http.GetAsync($"/orders/{id}", ct).ConfigureAwait(false);
    var json = await response.Content.ReadAsStringAsync(ct).ConfigureAwait(false);
    return Parse(json);
}
```

Анализатор CA2007 подсказывает пропущенные вызовы; в приложениях его обычно отключают в `.editorconfig`, в библиотеках — включают как ошибку ([[Стиль кода, соглашения и .editorconfig]]).

## Механика дедлока

```csharp
// WPF / WinForms / старый ASP.NET
public void OnClick()
{
    var data = LoadAsync().Result;      // ① UI-поток блокируется
}

async Task<string> LoadAsync()
{
    await _http.GetStringAsync(url);    // ② контекст захвачен: продолжение → UI-поток
    return "готово";                     // ③ никогда не выполнится
}
```

Шаг за шагом: UI-поток вызывает `LoadAsync`, доходит до `await`, метод возвращает незавершённую задачу; UI-поток блокируется на `.Result`; HTTP-запрос завершается, и продолжение ставится в очередь UI-потока — но он занят ожиданием той самой задачи. Взаимная блокировка.

Что разрывает цикл:

```csharp
// 1. Правильно: асинхронность через весь стек
public async Task OnClickAsync() => _data = await LoadAsync();

// 2. Если менять вызывающий код нельзя — ConfigureAwait(false) в библиотеке
await _http.GetStringAsync(url).ConfigureAwait(false);   // продолжение не требует UI-потока

// 3. Крайняя мера (в проде не применять): выполнение без контекста
var data = Task.Run(() => LoadAsync()).GetAwaiter().GetResult();
```

В ASP.NET Core этого дедлока нет — контекста нет, продолжение выполнится в потоке пула. Но `.Result` там всё равно вреден: он занимает поток пула на время ожидания, и под нагрузкой это приводит к исчерпанию пула ([[Дедлоки, async void и типичные ошибки]]).

---

## Почему в ASP.NET Core контекста нет

В старом ASP.NET контекст обеспечивал две вещи: доступ к `HttpContext.Current` через статическое свойство и сериализацию продолжений в рамках запроса. Оба решения стоили дорого — переключения, накладные расходы на каждый `await`, риск дедлоков.

В ASP.NET Core от них отказались: `HttpContext` передаётся явно (или через `IHttpContextAccessor`, использующий `AsyncLocal`), а продолжения выполняются в любом потоке пула. Выигрыш — заметно выше пропускная способность и меньше подводных камней.

Важно не путать две вещи:

- **`SynchronizationContext`** — куда планировать продолжение. В ASP.NET Core его нет.
- **`ExecutionContext`** — какие данные переносить (`AsyncLocal`, культура, идентификация). Он переносится **всегда**, и именно поэтому `HttpContext`, идентификатор корреляции и `User` доступны после `await`, хотя поток другой.

```csharp
private static readonly AsyncLocal<string> CorrelationId = new();

CorrelationId.Value = "abc";
await Task.Delay(10);
Console.WriteLine(CorrelationId.Value);    // "abc" — ExecutionContext перенёсся
```

## ConfigureAwaitOptions (.NET 8)

```csharp
using System.Threading.Tasks;

await task.ConfigureAwait(ConfigureAwaitOptions.None);                  // = ConfigureAwait(false)
await task.ConfigureAwait(ConfigureAwaitOptions.ContinueOnCapturedContext); // = ConfigureAwait(true)

// Дождаться завершения, не бросая исключение (например, при остановке службы)
await task.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing);

// Гарантированно уступить поток, даже если задача уже завершена
await task.ConfigureAwait(ConfigureAwaitOptions.ForceYielding);
```

`SuppressThrowing` полезен там, где нужно дождаться завершения фоновой задачи при остановке, а её ошибка уже обработана и логирована. `ForceYielding` — способ гарантированно разорвать синхронное выполнение, например чтобы не переполнить стек при глубокой цепочке синхронно завершающихся задач.

> [!warning] Подводные камни
> - **`ConfigureAwait(false)` в UI-обработчике перед обращением к элементам.** Продолжение окажется в потоке пула, и обращение к интерфейсу бросит исключение.
> - **Пропущенный `ConfigureAwait(false)` в библиотеке.** Дедлок у потребителя, вызывающего её из UI с блокировкой.
> - **Вера, что `ConfigureAwait(false)` лечит `.Result`.** Он снимает только один сценарий дедлока; блокировка потока остаётся.
> - **Попытка «оптимизировать» ASP.NET Core через `ConfigureAwait(false)`.** Контекста нет, эффекта тоже; только шум в коде.
> - **`ConfigureAwait` на первом `await` и забытый на остальных.** Достаточно одного захвата, чтобы вернуть проблему.
> - **Путаница `SynchronizationContext` и `ExecutionContext`.** Первый — куда планировать, второй — что переносить; `AsyncLocal` работает всегда.
> - **`ConfigureAwait` над `Task.Yield()`.** Он влияет только на способ возобновления и почти никогда не нужен.
> - **Тесты в xUnit со своим контекстом.** Код, «работающий в тестах», может вести себя иначе в проде — и наоборот.

> [!example] Как делают в бою
> В приложениях на ASP.NET Core `ConfigureAwait(false)` не пишут: контекста нет, и добавление вызовов только засоряет код. Анализатор CA2007 при этом отключают в `.editorconfig` — осознанно, а не «потому что ругается».
> В библиотеках, которые публикуются как пакеты, `ConfigureAwait(false)` ставят на каждом `await` и включают CA2007 как предупреждение-ошибку. Это дисциплина, которая один раз настраивается в `Directory.Build.props` для проектов-библиотек.
> В десктопных приложениях правило другое: `ConfigureAwait(false)` во внутренних сервисах и никогда — в коде, который после `await` трогает элементы интерфейса.
> Отдельно — про диагностику: когда «зависает» страница или запрос, первым делом ищут блокирующее ожидание (`.Result`, `.Wait()`, `GetAwaiter().GetResult()`) по всему стеку. В ASP.NET Core это выглядит не как зависание, а как рост латентности и исчерпание пула потоков, что видно по счётчику `threadpool-queue-length`.

## Вопросы с собеседований

> [!question]- Что такое контекст синхронизации и где он есть?
> Это абстракция над «местом», куда нужно отправлять продолжения асинхронных операций: объект с методом `Post`, который умеет выполнить делегат в нужной среде. В WPF и WinForms он возвращает выполнение в поток интерфейса, потому что обращаться к элементам можно только оттуда; в старом ASP.NET он обеспечивал доступ к `HttpContext.Current` и сериализовал продолжения в рамках запроса. В ASP.NET Core, консольных приложениях и фоновых службах контекста нет (`SynchronizationContext.Current` равен `null`), и продолжения выполняются в любом свободном потоке пула — это дало заметный выигрыш в пропускной способности и убрало целый класс дедлоков. При `await` над незавершённой задачей текущий контекст захватывается, и по завершении операции продолжение отправляется через него; `ConfigureAwait(false)` отключает захват.

> [!question]- Зачем нужен `ConfigureAwait(false)` и где его писать?
> Он сообщает, что продолжение не обязано выполняться в захваченном контексте: его можно выполнить в любом потоке пула. Это даёт два эффекта — устраняет один из сценариев дедлока (когда вызывающий блокируется на `.Result`, а продолжение планируется в его же единственный поток) и убирает лишнее переключение через очередь диспетчера. Писать его нужно в библиотечном коде, который может быть вызван из любой среды: библиотека не знает, есть ли у потребителя контекст. В приложениях на ASP.NET Core он бессмыслен, потому что захватывать нечего; в UI-коде, который после `await` обращается к элементам, он вреден — продолжение окажется в чужом потоке. Важная оговорка: `ConfigureAwait(false)` не делает блокирующее ожидание безопасным — он лишь снимает часть проблемы, а сама блокировка потока остаётся.

> [!question]- Почему в ASP.NET Core после `await` другой поток, но `HttpContext` доступен?
> Потому что это два разных механизма. Планирование продолжения определяется контекстом синхронизации, которого в ASP.NET Core нет, — поэтому продолжение выполняется любым свободным потоком пула. А данные, привязанные к логическому потоку выполнения, переносятся `ExecutionContext`: он копируется при каждой приостановке и восстанавливается при возобновлении, независимо от потока. В нём живут значения `AsyncLocal`, культура и данные идентификации; `IHttpContextAccessor` реализован именно через `AsyncLocal`, поэтому `HttpContext` остаётся доступным. Практический вывод: полагаться на конкретный поток (например, хранить состояние в `ThreadLocal` или удерживать `lock` через `await`) нельзя, а на `AsyncLocal` — можно.

## Задачи

### Задача 1. Объяснить зависание

Приложение WPF зависает при нажатии кнопки. Код:

```csharp
private void Button_Click(object sender, RoutedEventArgs e)
{
    var text = _api.GetTextAsync().Result;
    TextBlock.Text = text;
}
```

> [!success]- Решение
> Классический дедлок с захватом контекста. UI-поток вызывает `GetTextAsync`, тот доходит до `await` над сетевой операцией и возвращает незавершённую задачу; UI-поток блокируется на `.Result`. Когда сетевая операция завершается, продолжение `GetTextAsync` ставится в очередь диспетчера — то есть требует UI-поток, который занят ожиданием. Ни одна из сторон не сдвинется.
> ```csharp
> private async void Button_Click(object sender, RoutedEventArgs e)
> {
>     try
>     {
>         TextBlock.Text = await _api.GetTextAsync();   // продолжение вернётся в UI-поток штатно
>     }
>     catch (Exception ex) { MessageBox.Show(ex.Message); }
> }
> ```
> `async void` здесь допустим — это обработчик события, единственный законный случай; обязательным становится `try/catch`, потому что исключение из `async void` иначе уронит приложение. Дополнительно в библиотеке `_api` стоит проставить `ConfigureAwait(false)` — тогда даже неправильный вызывающий код не заблокируется намертво.

### Задача 2. Решить, где нужен ConfigureAwait

Для каждого места скажи, нужен ли `ConfigureAwait(false)`: (а) метод контроллера ASP.NET Core; (б) метод NuGet-библиотеки; (в) обработчик кнопки WPF, обновляющий метку; (г) внутренний сервис в WPF-приложении, не трогающий интерфейс; (д) `IHostedService` в фоновой службе.

> [!success]- Решение
> **(а) Нет.** В ASP.NET Core контекста синхронизации нет — захватывать нечего, вызов ничего не меняет и только добавляет шум.
> **(б) Да**, на каждом `await`. Библиотека не знает среду вызова: из WPF без него внутренние продолжения будут гоняться через очередь UI-потока, а при блокирующем ожидании у потребителя получится дедлок.
> **(в) Нет.** После `await` нужно вернуться в UI-поток, иначе обращение к метке бросит исключение о доступе из чужого потока.
> **(г) Да.** Сервис не работает с интерфейсом, возврат в UI-поток ему не нужен и стоит лишнего переключения; заодно это защищает от дедлока, если кто-то наверху заблокируется.
> **(д) Нет.** У фоновой службы контекста нет, как и в консольном приложении. Но если код службы вынесен в библиотеку, там правило (б) снова действует.

## Итог

- Контекст синхронизации определяет, куда планировать продолжение; в ASP.NET Core и консоли его нет.
- `await` по умолчанию захватывает контекст; `ConfigureAwait(false)` отключает захват.
- Дедлок возникает, когда единственный поток контекста блокируется ожиданием задачи, чьё продолжение планируется в него же.
- `ConfigureAwait(false)` обязателен в библиотеках, бессмыслен в ASP.NET Core, вреден в UI-коде перед обращением к элементам.
- `SynchronizationContext` — куда планировать; `ExecutionContext` — что переносить: `AsyncLocal` работает всегда.
- В ASP.NET Core от контекста отказались ради производительности; `HttpContext` живёт в `AsyncLocal`.
- `ConfigureAwaitOptions` (.NET 8) добавил `SuppressThrowing` и `ForceYielding` для узких сценариев.
- Блокирующее ожидание вредно и без дедлока: оно занимает поток пула и роняет пропускную способность.
