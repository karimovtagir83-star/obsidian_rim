# Interlocked, volatile и модель памяти

> [!abstract] Коротко
> Процессор и компилятор имеют право переставлять операции с памятью и держать значения в регистрах — пока это не меняет результат **однопоточного** выполнения. В многопоточном коде это приводит к тому, что один поток не видит записи другого или видит их в другом порядке. Модель памяти описывает, какие гарантии всё-таки есть, а `volatile`, `Volatile.Read/Write` и `Interlocked` — инструменты, чтобы их получить. Практическое правило: `Interlocked` для атомарных операций над числом или ссылкой, `volatile` для флагов, `lock` для всего остального — он даёт и взаимное исключение, и полный барьер памяти.

## Зачем это нужно

Ошибки этого класса самые коварные: код работает годами на x86, а на ARM (Apple Silicon, AWS Graviton) начинает вести себя странно, потому что там модель памяти слабее. Или работает в Debug и ломается в Release, когда JIT включает оптимизации.

```csharp
private bool _stop;                    // без volatile

void Worker()
{
    while (!_stop) { DoWork(); }        // JIT вправе прочитать _stop ОДИН раз и закешировать в регистре
}

void Stop() => _stop = true;            // поток может никогда не увидеть изменение
```

Цикл может крутиться вечно: это не гипотетическая, а регулярно воспроизводимая в Release-сборке ситуация.

## Что атомарно само по себе

Атомарная операция — та, которую другой поток не может увидеть «наполовину выполненной».

| Операция | Атомарна |
|---|---|
| Чтение/запись выровненного `int`, `bool`, `char`, ссылки | да |
| Чтение/запись `long`/`double` на 64-битной платформе | да |
| Чтение/запись `long`/`double` на 32-битной платформе | **нет** |
| Чтение/запись структуры больше слова (`decimal`, `DateTime`, свои структуры) | **нет** |
| `i++`, `i += 5` | **нет** (чтение + изменение + запись) |
| Присваивание ссылки | да |

Два вывода. Первый: `counter++` из нескольких потоков теряет инкременты — нужна атомарная операция. Второй: структура из двух полей, записанная одним потоком, может быть прочитана другим в промежуточном состоянии («разорванное чтение»), поэтому большие структуры не публикуют без синхронизации.

Атомарность **не означает видимости**: даже атомарная запись может быть не замечена другим потоком, если нет барьера.

## Interlocked

Атомарные операции, реализованные инструкциями процессора. Каждая из них является ещё и полным барьером памяти.

```csharp
private int _counter;
private long _total;
private Config? _current;

Interlocked.Increment(ref _counter);              // атомарный ++
Interlocked.Decrement(ref _counter);
Interlocked.Add(ref _total, 100);
int value = Interlocked.Exchange(ref _counter, 0); // записать и вернуть старое
long read = Interlocked.Read(ref _total);          // атомарное чтение long на 32-битной платформе

// Сравнить и обменять — основа всех неблокирующих алгоритмов
Config? previous = Interlocked.CompareExchange(ref _current, newConfig, comparand: expected);

// .NET 5+: побитовые операции
Interlocked.Or(ref _flags, 0b100);
Interlocked.And(ref _flags, ~0b010);
```

### Цикл CAS

`CompareExchange` позволяет реализовать любое атомарное обновление без блокировки:

```csharp
// Атомарно применить произвольную функцию к значению
static void Max(ref int location, int value)
{
    int current = Volatile.Read(ref location);
    while (value > current)
    {
        int original = Interlocked.CompareExchange(ref location, value, current);
        if (original == current) return;      // успех: никто не вмешался
        current = original;                    // кто-то опередил — повторяем с новым значением
    }
}
```

Схема универсальна: прочитать текущее значение, вычислить новое, попытаться заменить при условии, что текущее не изменилось; если изменилось — повторить. Так устроены внутри `ConcurrentDictionary`, пул потоков и большинство неблокирующих структур данных.

Стоимость: `Interlocked` — единицы наносекунд, в разы дешевле блокировки. Но при высокой конкуренции за одну ячейку памяти начинается «пинг-понг» кеш-линии между ядрами, и выигрыш падает; тогда данные разносят по ядрам (счётчик на поток с итоговым суммированием).

## Модель памяти и переупорядочивание

Три уровня, на которых операции могут поменяться местами:

1. **Компилятор C#** — минимально, но может.
2. **JIT** — держит значения в регистрах, устраняет «лишние» чтения, переставляет независимые операции.
3. **Процессор** — выполняет вне порядка и буферизует записи.

```csharp
// Поток 1                 // Поток 2
_data = 42;                if (_ready)
_ready = true;                 Console.WriteLine(_data);   // может напечатать 0!
```

Без барьеров поток 2 может увидеть `_ready == true` раньше, чем `_data == 42`: записи могли быть переставлены или не дойти до его кеша.

Насколько это вероятно, зависит от архитектуры:

| | x86-64 | ARM64 |
|---|---|---|
| Модель памяти | сильная (TSO) | слабая |
| Переупорядочивание записей | почти нет | возможно |
| Насколько заметны ошибки | редко проявляются | проявляются регулярно |

Это практическая проблема сегодня: код, годами работавший на серверах Intel, может начать сбоить на Apple Silicon и AWS Graviton. Ошибка при этом была всегда — просто не проявлялась.

## volatile

```csharp
private volatile bool _stop;

void Worker() { while (!_stop) DoWork(); }     // чтение не будет закешировано
void Stop() => _stop = true;                    // запись станет видимой
```

Семантика: чтение `volatile`-поля имеет семантику **acquire** (последующие операции не могут быть перемещены до него), запись — **release** (предыдущие операции не могут быть перемещены после неё). Практически это означает: значение не кешируется в регистре и порядок относительно соседних операций сохраняется.

Ограничения, из-за которых `volatile` часто применяют неверно:

- **Не делает операцию атомарной.** `volatile int counter; counter++;` по-прежнему теряет инкременты.
- **Нельзя применять к `long`/`double`** (на 32-битных платформах их чтение не атомарно) и к структурам.
- **Не заменяет блокировку** при изменении нескольких связанных полей.
- **Не гарантирует мгновенности**: он про порядок и видимость, а не про «сразу же».

Явная альтернатива, которую предпочитают в новом коде, — `Volatile.Read`/`Volatile.Write`: они выражают намерение в конкретной точке, а не для всех обращений к полю.

```csharp
private bool _stop;                                  // обычное поле

void Worker() { while (!Volatile.Read(ref _stop)) DoWork(); }
void Stop() => Volatile.Write(ref _stop, true);
```

Полный барьер (запрет перестановки в обе стороны) — `Thread.MemoryBarrier()`, но в прикладном коде он почти не нужен.

## Что даёт lock

`lock` решает обе задачи сразу: взаимное исключение и барьеры памяти. Вход в блокировку — acquire, выход — release, поэтому всё, что записал поток внутри секции, будет видно следующему потоку, вошедшему в ту же секцию.

```csharp
lock (_gate) { _data = 42; _ready = true; }     // оба поля станут видимы согласованно
```

Отсюда практическое правило: **если данные защищены блокировкой, `volatile` не нужен**. Добавление `volatile` «на всякий случай» к полю под `lock` — признак непонимания модели, а не дополнительная надёжность.

## Публикация иммутабельного снимка

Приём, который снимает вопрос синхронизации в самом частом сценарии — «редко пишем, часто читаем»:

```csharp
private Config _config = Config.Default;      // ссылочный тип, иммутабельный

// Читатели: без блокировок вообще
public Config Current => Volatile.Read(ref _config);

// Писатель: подменяет ссылку целиком, атомарно
public void Update(Config newConfig) => Volatile.Write(ref _config, newConfig);
```

Работает потому, что присваивание ссылки атомарно, а сам объект после публикации не изменяется. Читатель видит либо старую версию целиком, либо новую целиком — промежуточных состояний не бывает. Это лучший способ хранить конфигурацию, справочники и кешированные вычисления, читаемые из многих потоков ([[Иммутабельность как приём проектирования]]).

## Что выбрать

| Задача | Инструмент |
|---|---|
| Счётчик из нескольких потоков | `Interlocked.Increment` |
| Флаг остановки | `volatile` или `Volatile.Read/Write` |
| Замена ссылки на новое значение | `Interlocked.Exchange` / `Volatile.Write` |
| Атомарное обновление по условию | `Interlocked.CompareExchange` (цикл CAS) |
| Изменение нескольких связанных полей | `lock` |
| Общий словарь | `ConcurrentDictionary` |
| Публикация редко меняющихся данных | иммутабельный снимок + `Volatile.Write` |

> [!warning] Подводные камни
> - **`volatile` вместо атомарности.** `volatile int x; x++;` — по-прежнему гонка.
> - **Отсутствие `volatile` у флага остановки.** JIT кеширует значение в регистре, цикл не завершается.
> - **`volatile` у поля под `lock`.** Избыточно и вводит в заблуждение.
> - **Разорванное чтение структуры.** `decimal`, `DateTime`, свои структуры читаются не атомарно; публикуй их через ссылку на иммутабельный объект.
> - **Проверка «работает на x86».** На ARM64 модель слабее, и та же ошибка проявится.
> - **Двойная проверка без барьера.** Классический double-checked locking требует `volatile`; в .NET проще использовать `Lazy<T>`.
> - **Высокая конкуренция за одну ячейку.** `Interlocked` дёшев, но «пинг-понг» кеш-линии между ядрами убивает масштабирование.
> - **Самодельные неблокирующие структуры.** Написать корректный lock-free алгоритм сложнее, чем кажется; в BCL уже есть проверенные.

> [!example] Как делают в бою
> В прикладном коде из этой темы применяются ровно две вещи: `Interlocked` для счётчиков (обработано сообщений, активных соединений, попыток) и публикация иммутабельного снимка через `Volatile.Write` для конфигурации и справочников. Всё остальное закрывают готовые типы — `ConcurrentDictionary`, `Channel`, `Lazy<T>`, — где синхронизация уже реализована корректно.
> `volatile` встречается в основном на флагах остановки фоновых циклов, и даже там его вытесняет `CancellationToken`, который решает задачу лучше: он даёт и видимость, и отмену ожиданий ([[CancellationToken и отмена операций]]).
> Ручные барьеры (`Thread.MemoryBarrier`) в прикладном коде не пишут вовсе — это уровень авторов библиотек и рантайма.
> Отдельная практика последних лет — тестирование на ARM: если продовые узлы на Graviton или разработка идёт на Apple Silicon, скрытые ошибки модели памяти проявляются именно там. Гонки ловят стресс-тестами с большим числом потоков и повторов, а не единичным прогоном.

## Вопросы с собеседований

> [!question]- Что такое модель памяти и зачем нужен `volatile`?
> Модель памяти — набор гарантий о том, в каком порядке один поток видит операции другого. Без неё компилятор, JIT и процессор вправе переставлять чтения и записи и держать значения в регистрах, потому что для однопоточного выполнения результат не меняется. В многопоточном коде это приводит к тому, что поток не видит чужую запись вовсе (значение закешировано в регистре) или видит записи в другом порядке. `volatile` запрещает такие оптимизации для конкретного поля: чтение получает семантику acquire, запись — release, поэтому значение всегда читается из памяти, а порядок относительно соседних операций сохраняется. Типичный пример необходимости — флаг остановки цикла: без `volatile` (или `Volatile.Read`) поток может крутиться бесконечно. Важно понимать границы: `volatile` не делает операцию атомарной и не заменяет блокировку при изменении нескольких связанных полей.

> [!question]- Чем `Interlocked` отличается от `volatile` и от `lock`?
> `volatile` управляет **видимостью и порядком** одиночных чтений и записей, но не делает операцию атомарной: `volatile int x; x++;` по-прежнему теряет обновления, потому что инкремент состоит из трёх шагов. `Interlocked` выполняет операцию **атомарно** одной инструкцией процессора (инкремент, обмен, сравнение с обменом) и одновременно является полным барьером памяти — то есть решает обе задачи для одной ячейки. `lock` даёт взаимное исключение для произвольного участка кода плюс барьеры на входе и выходе, поэтому подходит, когда нужно согласованно изменить несколько полей или выполнить составную операцию. По стоимости: `Interlocked` — единицы наносекунд, незанятый `lock` — десятки, занятый — на порядки больше. Практический выбор: одна переменная — `Interlocked`, флаг — `volatile`, несколько связанных изменений — `lock`.

> [!question]- Как работает `CompareExchange` и зачем он нужен?
> Он атомарно сравнивает значение в ячейке с ожидаемым и, если они совпали, записывает новое; в любом случае возвращает **исходное** значение. Это единственная инструкция, на которой можно построить любое атомарное обновление без блокировок: читаем текущее значение, вычисляем новое, пытаемся заменить с условием «текущее не изменилось»; если между чтением и заменой кто-то вмешался, возвращённое значение не совпадёт с ожидаемым, и попытку повторяют с новым исходным. Такой цикл CAS лежит в основе неблокирующих алгоритмов, `ConcurrentDictionary`, пула потоков, и позволяет, например, атомарно вычислить максимум или обновить ссылку по условию. Ограничение: при высокой конкуренции число повторов растёт, а кеш-линия «прыгает» между ядрами, поэтому на очень горячих счётчиках выгоднее разносить данные по потокам и суммировать в конце.

## Задачи

### Задача 1. Объяснить зависание

В Release-сборке фоновый поток не останавливается, в Debug — работает. Код:

```csharp
private bool _running = true;
public void Stop() => _running = false;
private void Loop() { while (_running) { Process(); } }
```

> [!success]- Решение
> В Release включены оптимизации JIT: он видит, что внутри цикла `_running` не изменяется, и вправе прочитать поле один раз, поместив значение в регистр. Дальнейшие изменения из другого потока цикл просто не увидит. В Debug оптимизация не применяется, поэтому поле читается на каждой итерации, и код «работает» — классическая ситуация, когда ошибка есть всегда, а проявляется только в Release и чаще на ARM.
> ```csharp
> // Минимальное исправление
> private volatile bool _running = true;
>
> // Или явно в точках использования
> private bool _running = true;
> public void Stop() => Volatile.Write(ref _running, false);
> private void Loop() { while (Volatile.Read(ref _running)) Process(); }
>
> // Правильное решение для фоновой работы
> protected override async Task ExecuteAsync(CancellationToken stoppingToken)
> {
>     while (!stoppingToken.IsCancellationRequested)
>     {
>         Process();
>         await Task.Delay(100, stoppingToken);
>     }
> }
> ```
> Третий вариант лучше двух первых: `CancellationToken` даёт не только корректную видимость, но и прерывание ожиданий, интеграцию с остановкой приложения и единый механизм отмены по всему стеку.

### Задача 2. Выбрать инструмент

Для каждой задачи выбери минимально достаточное средство: (а) счётчик обработанных сообщений; (б) кеш конфигурации, читаемый тысячами запросов и обновляемый раз в час; (в) обновление двух связанных полей (баланс и дата последней операции); (г) флаг «сервис прогрет».

> [!success]- Решение
> **(а) `Interlocked.Increment`.** Одна ячейка, одна атомарная операция; блокировка была бы избыточной и в разы дороже. Если счётчик обновляется миллионы раз в секунду с разных ядер, следующий шаг — счётчики по потокам с суммированием при чтении.
> **(б) Иммутабельный снимок с `Volatile.Write`.** Конфигурация публикуется целиком новым объектом, читатели работают вообще без синхронизации — идеальный профиль «много чтений, редкие записи». `ReaderWriterLockSlim` здесь тоже сработает, но проиграет, а `lock` сериализует всех читателей.
> **(в) `lock`.** Два поля должны меняться согласованно: другой поток не должен увидеть новый баланс со старой датой. Ни `Interlocked`, ни `volatile` этого не обеспечивают. Альтернатива — сделать состояние иммутабельным (`record` с двумя полями) и подменять ссылку целиком через `Interlocked.Exchange`.
> **(г) `volatile bool` или `Volatile.Read/Write`.** Одно булево значение, важна только видимость. Но если флаг используется для ожидания, лучше `ManualResetEventSlim` или `TaskCompletionSource` — они не заставляют крутить цикл.

## Итог

- Компилятор, JIT и процессор вправе переставлять операции с памятью и кешировать значения в регистрах.
- Атомарны чтение/запись ссылки и выровненных значений до размера слова; `i++` и большие структуры — нет.
- Атомарность не равна видимости: нужна ещё и правильная упорядоченность (барьеры).
- `volatile` даёт видимость и порядок для одного поля, но не атомарность и не заменяет блокировку.
- `Volatile.Read/Write` выражает то же намерение точечно и предпочтительнее в новом коде.
- `Interlocked` — атомарные операции плюс полный барьер; `CompareExchange` — основа неблокирующих алгоритмов.
- `lock` даёт и взаимное исключение, и барьеры: под ним `volatile` не нужен.
- На ARM64 модель памяти слабее, чем на x86-64: скрытые ошибки проявляются именно там.
