# Дедлоки, async void и типичные ошибки

> [!abstract] Коротко
> Почти все проблемы с асинхронностью сводятся к четырём ошибкам: блокирующее ожидание асинхронной операции (`.Result`, `.Wait()`), `async void` вне обработчика события, забытый `await` и удержание блокировки через `await`. В приложении с контекстом синхронизации первая даёт мгновенный дедлок; в ASP.NET Core — исчерпание пула потоков, которое выглядит как внезапный рост латентности под нагрузкой при нормальной загрузке процессора. Эта заметка — каталог ошибок с механикой, симптомами и способом починки.

## Зачем это нужно

Асинхронные баги плохи тем, что не проявляются в разработке: на одном запросе всё работает, а под нагрузкой сервис «встаёт». Знание конкретного набора антипаттернов позволяет находить их на ревью, а не в проде.

---

## 1. Блокирующее ожидание (sync-over-async)

```csharp
var data = LoadAsync().Result;          // ⛔
LoadAsync().Wait();                      // ⛔
LoadAsync().GetAwaiter().GetResult();    // ⛔ (чуть лучше по исключениям, так же плохо по потокам)
```

**В UI и старом ASP.NET — дедлок.** Поток контекста блокируется, ожидая задачу, продолжение которой должно выполниться в этом же потоке ([[Контекст синхронизации и ConfigureAwait]]).

**В ASP.NET Core — исчерпание пула.** Дедлока нет, но каждый заблокированный запрос удерживает поток пула на время ожидания. Пул добавляет новые потоки медленно (порядка одного-двух в секунду после исчерпания минимума), поэтому при всплеске нагрузки очередь работы растёт быстрее, чем появляются потоки:

```
Нормально:   1000 запросов → ~десяток потоков (ожидание I/O потока не занимает)
С .Result:   1000 запросов → 1000 заблокированных потоков → очередь, таймауты, рост latency
```

Симптом: латентность растёт лавинообразно, процессор при этом почти простаивает, счётчик `threadpool-queue-length` большой. Лечение — асинхронность через весь стек:

```csharp
// Было
public Order Get(long id) => _repo.GetAsync(id).Result;

// Стало
public Task<Order> GetAsync(long id, CancellationToken ct) => _repo.GetAsync(id, ct);
```

Если синхронный интерфейс навязан снаружи и изменить его нельзя, честнее выполнить работу синхронным API (если он есть), чем блокировать поток на асинхронном.

## 2. async void

```csharp
public async void ProcessAsync() { ... }        // ⛔ вне обработчика события
```

Проблемы: исключение не попадает в задачу и обычно роняет процесс; вызывающий не может дождаться завершения; невозможно протестировать. Единственное законное применение — обработчики событий, и там обязателен `try/catch` внутри ([[Исключения в асинхронном коде]]).

```csharp
// Правильно: async Task, даже если результат не нужен
public async Task ProcessAsync(CancellationToken ct) { ... }
```

Ловушка того же рода — асинхронная лямбда, переданная туда, где ожидается `Action`:

```csharp
// Компилируется! Лямбда становится async void
Parallel.ForEach(items, async item => await ProcessAsync(item));   // ⛔
list.ForEach(async item => await ProcessAsync(item));               // ⛔
timer.Elapsed += async (s, e) => await TickAsync();                  // ⛔ без try/catch внутри

// Правильно
await Parallel.ForEachAsync(items, ct, async (item, token) => await ProcessAsync(item, token));
```

`Parallel.ForEach` с асинхронной лямбдой не ждёт завершения операций: он мгновенно «обработает» все элементы, а работа продолжится в фоне без учёта и без обработки ошибок.

## 3. Забытый await

```csharp
async Task SaveAsync()
{
    _repo.AddAsync(order);          // ⛔ нет await: не дождались, исключения потеряны
    await _repo.SaveChangesAsync();
}
```

Компилятор предупреждает (CS4014), и это предупреждение нужно возводить в ошибку. Если задача действительно не нужна, намерение выражают явно:

```csharp
_ = FireAndForgetAsync();      // видно, что задача осознанно не ожидается
```

Но в серверном коде осознанный «запусти и забудь» почти всегда неверен: нет ни логирования ошибок, ни ожидания при остановке приложения ([[Background services и IHostedService]]).

## 4. Блокировка через await

```csharp
private readonly object _gate = new();

lock (_gate)                       // ⛔ не компилируется с await внутри — и это хорошо
{
    // await SomethingAsync();
}
```

`Monitor` привязан к потоку: захвативший поток должен и освободить. После `await` продолжение может выполняться в другом потоке, поэтому компилятор запрещает `await` внутри `lock`. Асинхронный аналог — `SemaphoreSlim`:

```csharp
private readonly SemaphoreSlim _gate = new(1, 1);

await _gate.WaitAsync(ct);
try
{
    await DoWorkAsync(ct);          // теперь ожидание внутри «блокировки» допустимо
}
finally
{
    _gate.Release();                 // ОБЯЗАТЕЛЬНО в finally
}
```

Подробнее — [[Semaphore, Mutex, ReaderWriterLockSlim]] и [[Примитивы синхронизации: lock, Monitor]].

## 5. Асинхронность поверх синхронного API

```csharp
// ⛔ Не делает работу асинхронной: просто перекладывает блокировку на другой поток пула
public Task<Data> GetAsync() => Task.Run(() => GetSync());
```

Такой метод выглядит асинхронным, но поток по-прежнему занят на всё время операции — только уже другой, из того же пула. В библиотеке это особенно вредно: потребитель считает вызов дешёвым и делает сотню параллельных обращений.

Правильно: либо предоставить честно синхронный API и позволить вызывающему решать, либо использовать асинхронные примитивы ввода-вывода внутри.

Исключение — вычислительная работа в UI-приложении: там `Task.Run` действительно нужен, чтобы не блокировать интерфейс.

## 6. Task.Run в ASP.NET Core

```csharp
// ⛔ Запрос уже в потоке пула; Task.Run забирает ещё один
var result = await Task.Run(async () => await _service.LoadAsync(ct));

// Правильно
var result = await _service.LoadAsync(ct);
```

Пропускная способность от этого только падает: добавляется планирование и удваивается расход потоков. Оправдано лишь для длительной чисто вычислительной работы, и то обычно её выносят в фоновую службу или очередь.

## 7. Параллельное использование непотокобезопасных объектов

```csharp
// ⛔ DbContext не поддерживает параллельные операции
var t1 = _db.Orders.ToListAsync(ct);
var t2 = _db.Users.ToListAsync(ct);
await Task.WhenAll(t1, t2);          // InvalidOperationException: second operation started
```

Правильно — последовательно на одном контексте либо по отдельному контексту на операцию через фабрику (`IDbContextFactory<T>`). То же относится к `HttpClient`-обработчикам с состоянием, `MemoryStream`, к любым типам, чья потокобезопасность не заявлена явно ([[EF Core: производительность и типичные грабли]]).

---

## 8. Неограниченный параллелизм

```csharp
// ⛔ 10 000 одновременных запросов: пул соединений, лимиты внешнего API, память
await Task.WhenAll(ids.Select(id => CallApiAsync(id, ct)));

// Правильно: ограничить степень параллелизма
await Parallel.ForEachAsync(ids,
    new ParallelOptions { MaxDegreeOfParallelism = 10, CancellationToken = ct },
    async (id, token) => await CallApiAsync(id, token));
```

## 9. Прочее из практики

```csharp
// ⛔ Асинхронность в конструкторе — невозможна; получается блокировка
public MyService() { _data = LoadAsync().Result; }
// Правильно: фабричный метод
public static async Task<MyService> CreateAsync(CancellationToken ct) => new(await LoadAsync(ct));

// ⛔ Асинхронная работа в геттере свойства
public Task<int> Count => _db.Orders.CountAsync();     // вызывается при каждом обращении, в том числе отладчиком
// Правильно: метод с говорящим именем и токеном
public Task<int> GetCountAsync(CancellationToken ct) => _db.Orders.CountAsync(ct);

// ⛔ Игнорирование токена отмены
public async Task ProcessAsync(CancellationToken ct) { await Task.Delay(5000); }   // токен не передан

// ⛔ async-метод без await и с лишним автоматом
public async Task<int> GetAsync() => 42;               // предупреждение CS1998
public Task<int> GetAsync() => Task.FromResult(42);     // правильно
```

## Как диагностировать

```bash
# Пул потоков: очередь и число потоков
dotnet-counters monitor -p <pid> --counters System.Runtime
# threadpool-thread-count, threadpool-queue-length, threadpool-completed-items-count
```

Признаки исчерпания пула: `threadpool-queue-length` растёт, число потоков увеличивается медленно и линейно, загрузка процессора низкая, латентность растёт. Это почти всегда означает блокирующие вызовы.

```bash
dotnet-dump collect -p <pid>
dotnet-dump analyze core.dmp
> clrthreads                 # список потоков и их состояние
> syncblk                    # кто держит блокировки Monitor
> dumpasync                  # ⭐ незавершённые async-операции и их цепочки
> pstacks                    # агрегированные стеки: видно, где стоят потоки
```

Команда `dumpasync` — главный инструмент для асинхронных зависаний: она показывает «висящие» автоматы состояний и то, чего они ждут ([[Диагностика в проде: дампы и dotnet-tools]]).

> [!example] Как делают в бою
> Профилактика дешевле диагностики, поэтому в проектах включают анализаторы, ловящие эти ошибки: предупреждение CS4014 (забытый `await`) и CS1998 (`async` без `await`) возводят в ошибки, добавляют `Microsoft.VisualStudio.Threading.Analyzers` или `Meziantou.Analyzer`, которые находят `.Result`, `.Wait()`, `async void`, отсутствие токена отмены и блокирующие вызовы в асинхронных методах.
> Правило команды формулируют коротко: «асинхронность до самого верха, никаких `.Result`, `async void` только в обработчиках событий, параллелизм всегда ограничен». Эти четыре пункта закрывают подавляющее большинство инцидентов.
> При разборе инцидента «сервис перестал отвечать под нагрузкой» первым делом смотрят не на код, а на `threadpool-queue-length`: если очередь растёт при простаивающем процессоре, дальше ищут блокирующие вызовы по дампу через `pstacks` и `dumpasync`.
> Отдельная практика — нагрузочное тестирование перед релизом: sync-over-async почти невозможно заметить на одном запросе, но он мгновенно проявляется при сотне одновременных.

## Вопросы с собеседований

> [!question]- Почему `.Result` вызывает дедлок и всегда ли?
> Не всегда — это зависит от наличия контекста синхронизации. В UI-приложении (WPF, WinForms) и в старом ASP.NET продолжение асинхронного метода планируется обратно в захваченный контекст: в единственный поток интерфейса или в контекст запроса. Если этот же поток заблокирован на `.Result`, он не может выполнить продолжение, а задача не может завершиться без продолжения — получается взаимная блокировка. В ASP.NET Core, консольных приложениях и фоновых службах контекста нет, продолжение выполнит любой свободный поток пула, и дедлока не будет. Но проблема остаётся другой: заблокированный поток пула не обслуживает другие запросы, а пул расширяется медленно, поэтому под нагрузкой возникает исчерпание пула — латентность растёт лавинообразно при почти простаивающем процессоре. Правильное решение в обоих случаях одно: асинхронность через весь стек вызовов, без блокирующих ожиданий.

> [!question]- Чем плох `async void` и где он допустим?
> У него нет задачи, в которую можно положить результат или исключение. Исключение из такого метода отправляется в контекст синхронизации (или в пул потоков) как необработанное и обычно завершает процесс; перехватить его снаружи невозможно, потому что метод возвращает управление на первом `await`. Вызывающий не может дождаться завершения, а значит нельзя ни корректно остановить приложение, ни написать тест. Допустим он только там, где сигнатуру навязывает фреймворк, — в обработчиках событий, и внутри такого метода обработка исключений обязательна. Отдельная ловушка того же рода: асинхронная лямбда, переданная в параметр типа `Action` (например, в `Parallel.ForEach` или `List.ForEach`), молча становится `async void` — код компилируется, но операции не дожидаются и ошибки теряются.

> [!question]- Что такое исчерпание пула потоков и как его распознать?
> Ситуация, когда все потоки пула заняты блокирующими ожиданиями, а новая работа накапливается в очереди. Пул добавляет потоки постепенно (порядка одного-двух в секунду после исчерпания начального количества, равного числу ядер), поэтому при всплеске нагрузки очередь растёт быстрее, чем появляются исполнители. Характерные признаки: латентность растёт лавинообразно, процессор при этом слабо загружен, счётчик `threadpool-queue-length` большой, а `threadpool-thread-count` медленно ползёт вверх. Причина почти всегда одна — блокирующие вызовы в асинхронном коде: `.Result`, `.Wait()`, `GetAwaiter().GetResult()`, синхронный ввод-вывод, `lock` вокруг долгой операции. Диагностика по дампу: `pstacks` показывает, где стоят потоки, `dumpasync` — какие асинхронные операции зависли. Лечение — убрать блокировки, а не увеличивать минимальное число потоков: последнее лишь маскирует проблему.

## Задачи

### Задача 1. Найти все ошибки

```csharp
public class NotificationService
{
    private readonly object _lock = new();

    public async void SendAll(List<User> users)
    {
        Parallel.ForEach(users, async user =>
        {
            var template = _templates.GetAsync(user.Language).Result;
            await SendAsync(user, template);
        });
    }
}
```

> [!success]- Решение
> Пять ошибок.
> `async void` в публичном методе: исключения уронят процесс, вызывающий не может дождаться завершения.
> `Parallel.ForEach` с асинхронной лямбдой: лямбда становится `async void`, метод завершится мгновенно, не дождавшись отправок, а ошибки потеряются.
> `.Result` внутри: блокирует поток пула, а поскольку `Parallel.ForEach` уже занял потоки, это прямой путь к исчерпанию пула.
> Нет ограничения параллелизма: при большом списке пользователей внешний сервис получит шквал запросов.
> Нет токена отмены: остановить рассылку невозможно.
> ```csharp
> public async Task SendAllAsync(IReadOnlyList<User> users, CancellationToken ct)
> {
>     await Parallel.ForEachAsync(users,
>         new ParallelOptions { MaxDegreeOfParallelism = 10, CancellationToken = ct },
>         async (user, token) =>
>         {
>             var template = await _templates.GetAsync(user.Language, token);
>             await SendAsync(user, template, token);
>         });
> }
> ```
> Поле `_lock` не понадобилось: если бы синхронизация была нужна, вместо `lock` использовался бы `SemaphoreSlim` — удерживать `Monitor` через `await` невозможно.

### Задача 2. Диагностировать инцидент

Сервис работает нормально при 50 запросах в секунду, но при 200 латентность вырастает с 50 мс до 20 секунд, при этом CPU 15 %, память в норме. Что проверять?

> [!success]- Решение
> Картина «латентность выросла, процессор простаивает» почти однозначно указывает на исчерпание пула потоков из-за блокирующих вызовов.
> Порядок действий:
> 1. `dotnet-counters monitor -p <pid> --counters System.Runtime` — смотреть `threadpool-queue-length` (растёт), `threadpool-thread-count` (медленно увеличивается) и `threadpool-completed-items-count` (стагнирует). Это подтверждает гипотезу.
> 2. `dotnet-dump collect` и в анализе `pstacks` — агрегированные стеки покажут, что десятки потоков стоят в одном и том же месте, обычно на `Monitor.Wait`, `Task.Result` или синхронном вводе-выводе.
> 3. `dumpasync` — незавершённые асинхронные цепочки: видно, чего ждут «повисшие» операции.
> 4. По найденному месту искать в коде `.Result`, `.Wait()`, `GetAwaiter().GetResult()`, синхронные вызовы `File.ReadAllText`, `HttpClient.Send`, `lock` вокруг долгих операций.
> Чего делать не стоит: увеличивать `ThreadPool.SetMinThreads` как «решение». Это маскирует проблему и помогает лишь до следующего роста нагрузки; корректное лечение — убрать блокирующие вызовы. Профилактика — анализаторы, запрещающие блокирующие ожидания, и нагрузочный тест в конвейере: на одном запросе такая проблема невидима.

## Итог

- Блокирующее ожидание асинхронной операции даёт дедлок при наличии контекста и исчерпание пула — без него.
- Признак исчерпания пула: растущая очередь и латентность при низкой загрузке процессора.
- `async void` допустим только в обработчиках событий; асинхронная лямбда в параметре `Action` — скрытый `async void`.
- Забытый `await` теряет исключения; CS4014 и CS1998 стоит возводить в ошибки.
- `lock` нельзя удерживать через `await`; асинхронный аналог — `SemaphoreSlim`.
- `Task.Run` вокруг синхронного API не делает его асинхронным, а в ASP.NET Core просто забирает лишний поток.
- Непотокобезопасные объекты (`DbContext`) нельзя использовать в параллельных задачах.
- Параллелизм всегда ограничивают; диагностика — `dotnet-counters`, `pstacks`, `dumpasync`.
