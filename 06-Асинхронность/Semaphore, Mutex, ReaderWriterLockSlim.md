# Semaphore, Mutex, ReaderWriterLockSlim

> [!abstract] Коротко
> `lock` решает задачу «одновременно только один поток». Для остальных случаев есть специализированные примитивы: `SemaphoreSlim` — «одновременно не больше N» и единственный способ сделать асинхронную критическую секцию (`WaitAsync`); `Mutex` — блокировка **между процессами** (например, «запустить только один экземпляр приложения»); `ReaderWriterLockSlim` — много читателей или один писатель, что выгодно при преобладании чтения. В прикладном коде из этого списка реально нужен почти только `SemaphoreSlim`, остальные встречаются в специфических сценариях.

## Зачем это нужно

Три задачи, которые `lock` не решает: ограничить число одновременных обращений к внешнему сервису; синхронизировать асинхронный код, где нужен `await` внутри секции; договориться между разными процессами на одной машине.

## SemaphoreSlim

Счётчик разрешений: `Wait` уменьшает, `Release` увеличивает; когда разрешений нет, ожидающие стоят в очереди.

```csharp
// Ограничение параллелизма: не больше 10 одновременных вызовов
private readonly SemaphoreSlim _gate = new(initialCount: 10, maxCount: 10);

public async Task<Order> LoadAsync(long id, CancellationToken ct)
{
    await _gate.WaitAsync(ct);          // асинхронное ожидание: поток не блокируется
    try
    {
        return await _api.GetAsync(id, ct);
    }
    finally
    {
        _gate.Release();                 // ОБЯЗАТЕЛЬНО в finally
    }
}
```

Два главных применения:

**1. Асинхронная критическая секция.** `lock` не допускает `await` внутри, поэтому там, где секция содержит асинхронные вызовы, используют семафор с одним разрешением:

```csharp
private readonly SemaphoreSlim _mutex = new(1, 1);

private async Task RefreshTokenAsync(CancellationToken ct)
{
    await _mutex.WaitAsync(ct);
    try
    {
        if (_token is { IsValid: true }) return;    // повторная проверка под «блокировкой»
        _token = await _auth.GetTokenAsync(ct);
    }
    finally { _mutex.Release(); }
}
```

**2. Ограничение степени параллелизма.** Без него `Task.WhenAll` над тысячей элементов создаёт тысячу одновременных обращений ([[Task и Task Parallel Library]]).

Отличия от классического `Semaphore`: `SemaphoreSlim` полностью в управляемом коде (быстрее, но только внутри процесса), поддерживает `WaitAsync` и `CancellationToken`. Классический `Semaphore` умеет работать между процессами по имени, но не имеет асинхронного ожидания.

> [!warning] Семафор не реентерабелен
> В отличие от `lock`, повторный `WaitAsync` из того же потока (или той же логической операции) заблокируется навсегда. Рекурсивные вызовы под семафором приводят к самодедлоку — это самая частая ошибка при его использовании.

Отдельная тонкость: `Release()` можно вызвать больше раз, чем `Wait`, и счётчик разрешений вырастет сверх ожидаемого — если задан `maxCount`, будет исключение. Поэтому `Release` всегда в `finally` и ровно один раз на каждый успешный `Wait`.

## Mutex

Блокировка уровня операционной системы, доступная **между процессами**:

```csharp
// Запустить только один экземпляр приложения на машине
using var mutex = new Mutex(initiallyOwned: true, name: "Global\\MyApp.Single", out bool created);
if (!created)
{
    Console.WriteLine("Приложение уже запущено");
    return;
}
// ... работа ...
```

Свойства и ограничения:

- **Именованный мьютекс виден всем процессам** (префикс `Global\` — на всю машину, `Local\` — на сессию).
- **Привязан к потоку**: освободить обязан тот же поток, который захватил. С асинхронным кодом это делает его практически непригодным — после `await` поток может смениться.
- **Медленнее `lock`** на порядок: каждая операция идёт через ядро ОС.
- **Заброшенный мьютекс**: если владеющий процесс умер, не освободив его, следующий ожидающий получит `AbandonedMutexException` — это сигнал, что данные под защитой могут быть в несогласованном состоянии.
- **Кроссплатформенность**: именованные мьютексы работают на Linux и macOS, но с оговорками по времени жизни и правам; в контейнерах на них лучше не полагаться.

Практически в серверном .NET `Mutex` встречается редко. Задачу «только один экземпляр обработчика» в распределённой системе решают не мьютексом, а распределённой блокировкой (Redis, база данных, лидер-выборы), потому что процессов несколько и они на разных машинах ([[Redis и стратегии кеширования]]).

## ReaderWriterLockSlim

Разделяет доступ на чтение и запись: читателей может быть много одновременно, писатель — один и в одиночку.

```csharp
private readonly ReaderWriterLockSlim _rw = new(LockRecursionPolicy.NoRecursion);
private readonly Dictionary<string, Config> _configs = new();

public Config? Get(string key)
{
    _rw.EnterReadLock();
    try { return _configs.GetValueOrDefault(key); }
    finally { _rw.ExitReadLock(); }
}

public void Set(string key, Config value)
{
    _rw.EnterWriteLock();
    try { _configs[key] = value; }
    finally { _rw.ExitWriteLock(); }
}

// Обновляемая блокировка: читаем, и только при необходимости повышаем до записи
public Config GetOrCreate(string key, Func<Config> factory)
{
    _rw.EnterUpgradeableReadLock();
    try
    {
        if (_configs.TryGetValue(key, out var existing)) return existing;

        _rw.EnterWriteLock();
        try
        {
            var created = factory();
            _configs[key] = created;
            return created;
        }
        finally { _rw.ExitWriteLock(); }
    }
    finally { _rw.ExitUpgradeableReadLock(); }
}
```

Когда это выгодно: **чтений намного больше, чем записей**, и сами операции достаточно длинные, чтобы окупить более дорогой захват. При коротких операциях обычный `lock` часто быстрее, потому что `ReaderWriterLockSlim` сложнее внутри.

Практическая альтернатива, которая почти всегда лучше: `ConcurrentDictionary` (для словарей) или иммутабельный снимок, публикуемый целиком через `Interlocked.Exchange` — читатели работают вообще без синхронизации ([[Конкурентные коллекции]], [[Иммутабельность как приём проектирования]]).

## Прочие примитивы

```csharp
// Сигнал: один поток ждёт, другой разрешает
private readonly ManualResetEventSlim _ready = new(false);
_ready.Wait(ct);                    // ждать
_ready.Set();                       // разрешить всем ждущим
_ready.Reset();                     // снова закрыть

// AutoResetEvent: пропускает по одному ждущему за раз
private readonly AutoResetEvent _signal = new(false);

// Дождаться завершения N операций
using var countdown = new CountdownEvent(initialCount: 5);
countdown.Signal();                  // из каждой операции
countdown.Wait(ct);

// Синхронизация фаз между потоками
using var barrier = new Barrier(participantCount: 3, b => Console.WriteLine($"Фаза {b.CurrentPhaseNumber}"));
barrier.SignalAndWait(ct);
```

В асинхронном коде вместо событий обычно используют `TaskCompletionSource` (сигнал как задача) и `Channel<T>` (очередь с ожиданием), потому что они не блокируют потоки ([[System.Threading.Channels]]).

## Как выбрать

| Задача | Инструмент |
|---|---|
| Критическая секция в синхронном коде | `lock` / `System.Threading.Lock` |
| Критическая секция с `await` внутри | `SemaphoreSlim(1, 1)` |
| Не больше N одновременных операций | `SemaphoreSlim(N)` или `Parallel.ForEachAsync` |
| Много читателей, редкие записи | `ConcurrentDictionary`, иммутабельный снимок, в крайнем случае `ReaderWriterLockSlim` |
| Атомарный счётчик или замена ссылки | `Interlocked` |
| Очередь между потоками | `Channel<T>` |
| Один экземпляр процесса на машине | `Mutex` с именем |
| Один обработчик в кластере | распределённая блокировка (Redis, БД), не `Mutex` |
| Ожидание сигнала в асинхронном коде | `TaskCompletionSource` |

> [!warning] Подводные камни
> - **`Release` не в `finally`.** Одно исключение — и разрешение потеряно навсегда; со временем семафор «схлопывается» до нуля.
> - **Семафор не реентерабелен.** Повторный вход из той же операции — самодедлок.
> - **Лишний `Release`.** Счётчик разрешений растёт сверх задуманного или бросается `SemaphoreFullException`.
> - **`Mutex` в асинхронном коде.** Привязка к потоку ломается после `await`; освобождение из другого потока — исключение.
> - **`ReaderWriterLockSlim` без замеров.** При коротких операциях он проигрывает обычному `lock`.
> - **Рекурсия с `LockRecursionPolicy.NoRecursion`.** Повторный вход бросает исключение — это умолчание и оно правильное.
> - **`Mutex` как распределённая блокировка.** Он работает в пределах машины; в кластере нужен внешний координатор.
> - **Забытый `Dispose`.** `SemaphoreSlim`, `ReaderWriterLockSlim`, события удерживают дескрипторы ОС.

> [!example] Как делают в бою
> Из всего списка в прикладном коде регулярно встречается только `SemaphoreSlim`, и в двух ролях: ограничение числа одновременных обращений к внешнему API или базе и защита асинхронной критической секции (например, обновление токена доступа — чтобы десять параллельных запросов не пошли за ним одновременно).
> Второй по частоте приём — вообще обойтись без примитивов: `ConcurrentDictionary` для разделяемых словарей, `Channel` для передачи работы между частями приложения, `Interlocked` для счётчиков, иммутабельный снимок для конфигурации, читаемой из многих потоков.
> `Mutex` появляется в десктопных приложениях («не запускать второй экземпляр») и в утилитах, работающих с общим файлом. В серверных сервисах его заменяет распределённая блокировка или, чаще, пересмотр архитектуры: задачу «обработчик должен быть один» решают партиционированием очереди или лидер-выборами, а не блокировкой.
> `ReaderWriterLockSlim` в новом коде встречается редко: его вытеснили конкурентные коллекции. Он остаётся оправданным для больших структур данных с длинными операциями чтения, где замеры показали выигрыш.

## Вопросы с собеседований

> [!question]- Чем `SemaphoreSlim` отличается от `lock` и когда он нужен?
> `lock` даёт взаимное исключение для одного потока и работает только в синхронном коде: удерживать его через `await` нельзя, потому что монитор привязан к потоку. `SemaphoreSlim` — счётчик разрешений: он допускает N одновременных владельцев (при N = 1 получается аналог критической секции) и, главное, поддерживает асинхронное ожидание `WaitAsync` с токеном отмены, поэтому позволяет делать `await` внутри защищённого участка. Второе применение — ограничение степени параллелизма: не более N одновременных обращений к внешнему сервису. Важные отличия в поведении: семафор **не реентерабелен** (повторный вход из той же операции — самодедлок) и не привязан к потоку — освободить его может другой поток, что как раз и требуется после `await`. `Release` всегда пишут в `finally`, иначе разрешение теряется безвозвратно.

> [!question]- Зачем нужен `Mutex`, если есть `lock`?
> `Mutex` — примитив уровня операционной системы, и его именованный вариант виден **всем процессам** на машине. Это единственный из перечисленных примитивов, решающий задачу межпроцессной синхронизации: «запустить только один экземпляр приложения», «не дать двум утилитам одновременно писать в один файл». Платой являются существенно большая стоимость (каждая операция идёт через ядро), привязка к потоку (освободить обязан захвативший поток, что делает его непригодным для асинхронного кода) и особая ситуация с заброшенной блокировкой: если владеющий процесс завершился аварийно, следующий ожидающий получает `AbandonedMutexException` — сигнал, что защищённые данные могут быть повреждены. В серверных приложениях `Mutex` почти не используется: там процессов несколько и на разных машинах, поэтому нужна распределённая блокировка через Redis или базу данных.

> [!question]- Когда `ReaderWriterLockSlim` выгоднее обычной блокировки?
> Когда чтений существенно больше, чем записей, и операции достаточно длинные. Он позволяет нескольким читателям работать одновременно, блокируя их только на время записи, тогда как `lock` сериализует всех. Но у него есть цена: захват сложнее и дороже обычного монитора, поэтому при коротких операциях (получить значение из словаря) он часто проигрывает — накладные расходы съедают выигрыш от параллельного чтения. Дополнительно нужно помнить про политику рекурсии (по умолчанию `NoRecursion`, повторный вход бросает исключение) и про обновляемую блокировку `EnterUpgradeableReadLock`, которая позволяет прочитать, а затем при необходимости повысить до записи без гонки. На практике его почти всегда вытесняют конкурентные коллекции и приём с иммутабельным снимком, который публикуется целиком: читатели тогда работают вообще без синхронизации.

## Задачи

### Задача 1. Ограничить нагрузку на внешний сервис

Нужно обработать список из 5 000 элементов, обращаясь к API, который выдерживает не более 20 одновременных запросов. Два варианта решения — с чем их сравнить?

> [!success]- Решение
> ```csharp
> // Вариант 1: штатный API — предпочтительный
> await Parallel.ForEachAsync(items,
>     new ParallelOptions { MaxDegreeOfParallelism = 20, CancellationToken = ct },
>     async (item, token) => await CallApiAsync(item, token));
>
> // Вариант 2: семафор — когда нужны результаты или индивидуальная обработка ошибок
> using var gate = new SemaphoreSlim(20, 20);
> var tasks = items.Select(async item =>
> {
>     await gate.WaitAsync(ct);
>     try { return await CallApiAsync(item, ct); }
>     finally { gate.Release(); }
> });
> var results = await Task.WhenAll(tasks);
> ```
> Сравнение: первый вариант короче, сам управляет очередью и корректно обрабатывает отмену; второй даёт больше контроля — можно собрать результаты, обработать ошибки по элементам, объединить с повторами. Общее в обоих: `Release` (или выход из лямбды) гарантирован даже при исключении.
> Что важно не забыть: `using` у семафора (он держит дескрипторы), одна и та же `gate` на всё приложение, если лимит относится к сервису в целом, а не к одной операции, и сочетание с политикой повторов — при 429 от API ограничение параллелизма само по себе не спасёт ([[Устойчивость: retry, circuit breaker, Polly]]).

### Задача 2. Найти ошибку

```csharp
private readonly SemaphoreSlim _gate = new(1, 1);

public async Task<Token> GetTokenAsync(CancellationToken ct)
{
    await _gate.WaitAsync(ct);
    if (_token is { IsValid: true }) return _token;
    _token = await _auth.RequestAsync(ct);
    _gate.Release();
    return _token;
}
```

> [!success]- Решение
> Две ошибки. Первая и критическая: при раннем `return` (когда токен уже валиден) `Release` не вызывается — разрешение теряется навсегда, и **все последующие вызовы зависнут** на `WaitAsync`. Вторая: если `RequestAsync` бросит исключение, `Release` тоже не выполнится — тот же результат.
> ```csharp
> public async Task<Token> GetTokenAsync(CancellationToken ct)
> {
>     if (_token is { IsValid: true }) return _token;      // быстрый путь без блокировки
>
>     await _gate.WaitAsync(ct);
>     try
>     {
>         if (_token is { IsValid: true }) return _token;  // повторная проверка под блокировкой
>         _token = await _auth.RequestAsync(ct);
>         return _token;
>     }
>     finally
>     {
>         _gate.Release();
>     }
> }
> ```
> Изменения: `Release` в `finally` — единственный надёжный способ; добавлена проверка до захвата, чтобы в типичном случае (токен валиден) не платить за синхронизацию вовсе; повторная проверка под блокировкой нужна, потому что между быстрым путём и захватом другой поток мог уже обновить токен. Это тот же шаблон двойной проверки, что и в ленивой инициализации, только в асинхронном виде.

## Итог

- `SemaphoreSlim` — счётчик разрешений: асинхронная критическая секция (N = 1) и ограничение параллелизма (N > 1).
- `Release` всегда в `finally`; семафор не реентерабелен, повторный вход — самодедлок.
- `Mutex` — межпроцессная блокировка, привязан к потоку и потому не подходит для асинхронного кода.
- В кластере вместо `Mutex` нужна распределённая блокировка или пересмотр архитектуры.
- `ReaderWriterLockSlim` выгоден при большом перевесе чтений и длинных операциях; иначе `lock` быстрее.
- Конкурентные коллекции, `Interlocked`, `Channel` и иммутабельные снимки чаще лучше любых блокировок.
- Все эти примитивы освобождаются (`Dispose`): они держат дескрипторы ОС.
