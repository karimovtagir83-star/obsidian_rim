# Исключения в асинхронном коде

> [!abstract] Коротко
> Исключение из `async`-метода не выбрасывается сразу: оно сохраняется **внутри задачи** и выбрасывается заново в момент `await`. Отсюда три следствия, которые надо помнить. Первое: `await` разворачивает исключение и бросает исходный тип, а блокирующие `.Result`/`.Wait()` бросают `AggregateException`. Второе: `Task.WhenAll` при `await` показывает только **первое** исключение, остальные лежат в `task.Exception`. Третье: `async void` не имеет задачи, куда положить исключение, поэтому оно уходит в контекст синхронизации и обычно завершает процесс. Отдельно стоит отмена: `OperationCanceledException` — штатный исход, а не ошибка.

## Зачем это нужно

Асинхронный код ломает привычную интуицию про `try/catch`: исключение может «повиснуть» в задаче, которую никто не ждёт, потеряться в `WhenAll` или уронить приложение из обработчика события. Диагностика таких случаев без понимания механики превращается в гадание, потому что в логах либо ничего нет, либо стек обрывается.

## Где живёт исключение

```csharp
async Task<int> FailAsync()
{
    await Task.Delay(10);
    throw new InvalidOperationException("сломалось");
}

Task<int> task = FailAsync();      // исключения ЕЩЁ НЕТ: метод вернул задачу
Console.WriteLine(task.Status);     // WaitingForActivation

try
{
    int result = await task;        // ЗДЕСЬ исключение выбрасывается
}
catch (InvalidOperationException ex)
{
    Console.WriteLine(ex.Message);  // обычный catch работает как ожидается
}

Console.WriteLine(task.Status);     // Faulted
Console.WriteLine(task.Exception);  // AggregateException с исходным внутри
```

Механика: построитель автомата (`AsyncTaskMethodBuilder`) перехватывает исключение из тела метода и вызывает `SetException`, помещая его в задачу. При `await` awaiter вызывает `GetResult`, который **перебрасывает** исключение с сохранением исходного стека через `ExceptionDispatchInfo` — поэтому в логе видно место возникновения, а не место `await` ([[async и await: как это работает на самом деле]]).

### await против .Result

```csharp
try { await FailAsync(); }
catch (InvalidOperationException ex) { }        // исходный тип

try { FailAsync().Wait(); }
catch (AggregateException ex)                    // обёртка!
{
    var inner = ex.InnerException;               // здесь исходное
}

try { FailAsync().GetAwaiter().GetResult(); }
catch (InvalidOperationException ex) { }         // тоже разворачивает, но всё равно блокирует поток
```

`await` разворачивает `AggregateException` и бросает первое внутреннее исключение — это сделано ради читаемости кода. Ещё одна причина не использовать `.Result`: помимо блокировки потока он ломает привычную обработку ошибок ([[Дедлоки, async void и типичные ошибки]]).

## Несколько задач

```csharp
var t1 = FailAsync("первая");
var t2 = FailAsync("вторая");
var t3 = OkAsync();

var all = Task.WhenAll(t1, t2, t3);
try
{
    await all;
}
catch (Exception ex)
{
    Console.WriteLine(ex.Message);                   // ТОЛЬКО первое исключение
    foreach (var inner in all.Exception!.InnerExceptions)
        Console.WriteLine(inner.Message);            // все: первая, вторая
}
```

Два важных момента:

- **`WhenAll` дожидается всех задач**, даже если одна упала сразу. Чтобы прервать остальные, нужен общий `CancellationTokenSource`, отменяемый в обработчике.
- **Потерянные исключения.** Если ошибок несколько, а разработчик смотрит только на пойманное, часть проблем останется незамеченной — типичный источник «загадочных» частичных сбоев.

```csharp
// Сбор всех результатов и ошибок явно
var results = await Task.WhenAll(ids.Select(async id =>
{
    try { return (Id: id, Order: await LoadAsync(id, ct), Error: (Exception?)null); }
    catch (Exception ex) { return (Id: id, Order: null, Error: ex); }
}));

foreach (var failed in results.Where(r => r.Error is not null))
    logger.LogError(failed.Error, "Не удалось загрузить {OrderId}", failed.Id);
```

Такой приём часто честнее: он не прерывает обработку на первой ошибке и даёт полную картину.

## async void: исключение некуда положить

```csharp
async void FireAndForget()
{
    await Task.Delay(10);
    throw new InvalidOperationException("это уронит процесс");
}

try
{
    FireAndForget();          // catch НЕ поможет: метод вернул управление на первом await
    await Task.Delay(1000);
}
catch (Exception) { /* никогда не сработает */ }
```

У `async void` нет задачи, куда сохранить исключение. Построитель `AsyncVoidMethodBuilder` отправляет его в текущий контекст синхронизации (`SynchronizationContext.Post`), а при отсутствии контекста — в пул потоков, где оно становится необработанным и завершает процесс.

Единственное законное применение — обработчики событий, и там обработка обязана быть внутри:

```csharp
private async void Button_Click(object sender, EventArgs e)
{
    try { await LoadAsync(); }
    catch (Exception ex) { ShowError(ex); }     // ловим ЗДЕСЬ, снаружи невозможно
}
```

## Незамеченные исключения задач

```csharp
_ = ProcessAsync();          // задача не дождана: исключение никто не увидит
```

С .NET Framework 4.5 необработанное исключение в задаче **не завершает процесс** — оно тихо теряется, когда задача собирается сборщиком мусора. Это удобно, но опасно: ошибка исчезает бесследно.

Поймать такие случаи глобально можно:

```csharp
TaskScheduler.UnobservedTaskException += (sender, e) =>
{
    logger.LogError(e.Exception, "Незамеченное исключение задачи");
    e.SetObserved();          // пометить обработанным
};
```

Но это диагностика, а не решение. Правильный «запусти и забудь» выглядит так:

```csharp
static void FireAndForget(Func<Task> work, ILogger logger)
{
    _ = Task.Run(async () =>
    {
        try { await work(); }
        catch (OperationCanceledException) { /* штатно */ }
        catch (Exception ex) { logger.LogError(ex, "Фоновая задача упала"); }
    });
}
```

А в серверном приложении фоновую работу вообще не запускают «в никуда»: для этого есть `IHostedService`, очередь или `Channel`, где есть учёт, отмена и корректная остановка ([[Background services и IHostedService]]).

## Отмена — не ошибка

```csharp
try { await ProcessAsync(ct); }
catch (OperationCanceledException) when (ct.IsCancellationRequested)
{
    logger.LogInformation("Операция отменена");     // Information, не Error
    throw;
}
catch (Exception ex)
{
    logger.LogError(ex, "Сбой обработки");
    throw;
}
```

Порядок блоков важен: `OperationCanceledException` должен обрабатываться **до** общего `catch (Exception)`, иначе штатная отмена попадёт в лог как сбой и зашумит мониторинг ([[CancellationToken и отмена операций]]).

## Стек вызовов

```
System.InvalidOperationException: сломалось
   at OrderService.ValidateAsync(Order order)          ← место возникновения сохранено
   at OrderService.<ProcessAsync>d__5.MoveNext()       ← кадр автомата
--- End of stack trace from previous location ---
   at OrderController.<Post>d__3.MoveNext()
```

Разделитель «End of stack trace from previous location» показывает границу между кадрами до и после приостановки: физически это разные стеки, склеенные рантаймом. Кадры `MoveNext` — внутренности автомата, их наличие нормально.

Полезные приёмы:

- в свои вспомогательные методы, которые только пробрасывают вызовы, добавляют `[StackTraceHidden]` — они исчезают из стека;
- при перебросе исключения из другого контекста используют `ExceptionDispatchInfo.Capture(ex).Throw()`, а не `throw ex` ([[Обработка исключений]]);
- для восстановления последовательности между сервисами полагаются на идентификатор корреляции в структурных логах, а не на стек ([[Наблюдаемость: логи, метрики, трейсы]]).

> [!warning] Подводные камни
> - **`async void` вне обработчика события.** Исключение не перехватывается снаружи и роняет процесс.
> - **Забытый `await`.** Задача не дождана, исключение теряется; компилятор предупреждает (CS4014).
> - **`WhenAll` и только первое исключение.** Остальные ошибки останутся невидимыми, если не заглянуть в `task.Exception`.
> - **`.Result`/`.Wait()`.** Оборачивают исключение в `AggregateException` и блокируют поток.
> - **`catch (Exception)` раньше `catch (OperationCanceledException)`.** Отмена логируется как сбой.
> - **Исключение в `finally` асинхронного метода.** Затирает исходное — то же правило, что и в синхронном коде.
> - **Проглоченное исключение в фоновой задаче.** Работа не выполнена, но никто не знает.
> - **`throw ex` в `catch`.** Обрезает стек; нужен `throw;`.

> [!example] Как делают в бою
> Обработка ошибок в асинхронном коде подчиняется тем же правилам, что и в синхронном: ловить там, где есть решение, и не ловить в остальных местах ([[Обработка исключений]]). Специфика асинхронности сводится к четырём вещам.
> Первое: никаких `async void` вне обработчиков событий — это проверяется анализаторами и на ревью. Второе: никаких «забытых» задач — любая фоновая работа проходит через `IHostedService` или очередь, где есть логирование и отмена. Третье: при использовании `WhenAll` ошибки собирают явно, а не полагаются на одно пойманное исключение. Четвёртое: отмена обрабатывается отдельным `catch` до общего и логируется на уровне Information.
> На границе приложения работает один глобальный обработчик (`IExceptionHandler` в ASP.NET Core), который превращает исключение в ответ и структурный лог; в фоновых службах его роль выполняет try/catch внутри цикла обработки.
> Дополнительно в проде подписываются на `TaskScheduler.UnobservedTaskException` — не как на способ обработки, а как на детектор: срабатывание означает, что где-то есть задача без `await`, и это надо чинить.

## Вопросы с собеседований

> [!question]- Где хранится исключение из `async`-метода и когда оно выбрасывается?
> Построитель автомата перехватывает исключение из тела метода и сохраняет его в задаче через `SetException`, переводя её в состояние `Faulted`; вызывающий в этот момент ничего не замечает — он просто получил незавершённую или уже завершённую с ошибкой задачу. Исключение выбрасывается заново в момент `await`: awaiter вызывает `GetResult`, который перебрасывает сохранённое исключение с сохранением исходного стека (используется `ExceptionDispatchInfo`), поэтому в логе видно место возникновения, а не место ожидания. Из этого следует, что `try/catch` вокруг вызова без `await` бесполезен, а задача, которую никто не ждёт, унесёт своё исключение в небытие: с .NET 4.5 необработанные исключения задач не завершают процесс, они просто теряются при сборке мусора.

> [!question]- Почему `await` бросает исходное исключение, а `.Result` — `AggregateException`?
> Потому что задача в принципе может завершиться несколькими исключениями (например, `WhenAll` над несколькими упавшими задачами), и её свойство `Exception` всегда имеет тип `AggregateException`. Блокирующие `Wait()` и `Result` отдают его как есть, что технически честно, но неудобно: обработка ошибок обрастает разворачиванием `InnerException`. Компилятор при `await` делает это разворачивание сам и бросает первое внутреннее исключение, чтобы код с `try/catch` выглядел так же, как синхронный. Обратная сторона — при `await Task.WhenAll(...)` видно только первое исключение, а остальные надо доставать из `task.Exception.InnerExceptions` вручную. Отдельно стоит помнить, что `GetAwaiter().GetResult()` тоже разворачивает исключение, но по-прежнему блокирует поток, поэтому не является безопасной альтернативой.

> [!question]- Что произойдёт с исключением в `async void`-методе?
> Оно не попадёт в задачу — задачи просто нет. Построитель `AsyncVoidMethodBuilder` отправляет исключение в контекст синхронизации, захваченный при старте метода, а если контекста нет — в пул потоков. В обоих случаях оно становится необработанным исключением уровня приложения и обычно завершает процесс. Перехватить его снаружи невозможно: к моменту первого `await` метод уже вернул управление вызывающему, и `try/catch` вокруг вызова не сработает. Поэтому `async void` допустим только для обработчиков событий, где сигнатура навязана фреймворком, и внутри такого метода обработка исключений обязательна. Во всех остальных случаях используют `async Task`, даже если результат не нужен: тогда вызывающий может дождаться завершения и обработать ошибку.

## Задачи

### Задача 1. Найти потерянные ошибки

```csharp
public async Task ProcessAllAsync(IEnumerable<long> ids, CancellationToken ct)
{
    var tasks = ids.Select(id => ProcessAsync(id, ct));
    try { await Task.WhenAll(tasks); }
    catch (Exception ex) { _logger.LogError(ex, "Ошибка обработки"); }
}
```

Что не так и как исправить?

> [!success]- Решение
> Две проблемы. Первая: в лог попадёт только **одно** исключение, хотя упасть могли десятки задач, — остальные останутся невидимыми. Вторая: отмена (`OperationCanceledException`) будет залогирована как ошибка, засоряя мониторинг при каждом деплое.
> ```csharp
> public async Task ProcessAllAsync(IReadOnlyList<long> ids, CancellationToken ct)
> {
>     var tasks = ids.Select(id => ProcessAsync(id, ct)).ToArray();
>     var all = Task.WhenAll(tasks);
>
>     try
>     {
>         await all;
>     }
>     catch (OperationCanceledException) when (ct.IsCancellationRequested)
>     {
>         _logger.LogInformation("Обработка отменена");
>         throw;
>     }
>     catch (Exception)
>     {
>         foreach (var (id, task) in ids.Zip(tasks))
>             if (task.IsFaulted)
>                 _logger.LogError(task.Exception!.InnerException, "Не удалось обработать {Id}", id);
>         throw;
>     }
> }
> ```
> Материализация `ToArray()` обязательна: без неё `Select` создаст задачи заново при повторном перечислении. Перебор задач с их идентификаторами даёт полную картину — какие именно элементы упали и почему. Отмена обрабатывается отдельно и до общего блока.

### Задача 2. Исправить фоновую задачу

```csharp
public void StartBackgroundSync()
{
    Task.Run(async () =>
    {
        while (true)
        {
            await SyncAsync();
            await Task.Delay(TimeSpan.FromMinutes(5));
        }
    });
}
```

> [!success]- Решение
> Проблемы: результат `Task.Run` не сохранён и не наблюдается — любое исключение из `SyncAsync` тихо потеряет задачу и остановит синхронизацию навсегда, причём без единой записи в логе; нет токена отмены, поэтому приложение не сможет корректно остановиться; бесконечный цикл без обработки ошибок означает, что одна ошибка убивает всю фоновую работу.
> ```csharp
> public sealed class SyncService(ILogger<SyncService> logger, ISyncJob job) : BackgroundService
> {
>     protected override async Task ExecuteAsync(CancellationToken stoppingToken)
>     {
>         while (!stoppingToken.IsCancellationRequested)
>         {
>             try
>             {
>                 await job.SyncAsync(stoppingToken);
>                 await Task.Delay(TimeSpan.FromMinutes(5), stoppingToken);
>             }
>             catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
>             {
>                 break;
>             }
>             catch (Exception ex)
>             {
>                 logger.LogError(ex, "Ошибка синхронизации, повтор через минуту");
>                 await Task.Delay(TimeSpan.FromMinutes(1), stoppingToken);
>             }
>         }
>     }
> }
> ```
> Ключевое изменение — переход от «запустил и забыл» к `BackgroundService`: хост знает о задаче, дожидается её при остановке и перезапускает приложение корректно. Ошибка одной итерации логируется и не останавливает цикл, отмена обрабатывается штатно.

## Итог

- Исключение из `async`-метода сохраняется в задаче и выбрасывается при `await` с исходным стеком.
- `await` разворачивает `AggregateException` и бросает исходный тип; `.Result`/`.Wait()` — нет.
- `Task.WhenAll` при `await` показывает только первое исключение; остальные — в `task.Exception.InnerExceptions`.
- `async void` не имеет задачи для исключения: оно уходит в контекст и обычно роняет процесс.
- Незамеченные исключения задач тихо теряются; `TaskScheduler.UnobservedTaskException` — детектор, а не решение.
- Отмена обрабатывается отдельным `catch` до общего и логируется как информация.
- Кадры `MoveNext` и разделитель в стеке — нормальная часть асинхронной трассировки.
- Фоновую работу запускают через `IHostedService` или очередь, а не «в никуда».
