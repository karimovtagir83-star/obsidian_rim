# Процессы, потоки и планировщик ОС

> [!abstract] Коротко
> Процесс — это изолированное адресное пространство и набор ресурсов ОС. Поток — единица планирования внутри процесса: свой стек и свои регистры, но общая память с остальными потоками процесса. Планировщик ОС вытесняет потоки по кванту времени, и каждое такое переключение стоит от единиц до десятков микросекунд плюс потеря кешей процессора. Поток в Windows/.NET по умолчанию резервирует 1 МБ виртуальной памяти под стек — поэтому «поток на запрос» не масштабируется, и вся асинхронность в .NET существует ради того, чтобы не создавать и не блокировать потоки.

## Зачем это нужно

Без этого фундамента `async`/`await` выглядит магией. Все решения в дизайне `ThreadPool`, `Task` и `async` — прямые следствия того, что потоки ОС дорогие, а переключение между ними ещё дороже. Когда на собеседовании спрашивают «почему нельзя просто создать поток на каждый запрос», ждут не «потому что так не принято», а конкретные числа: 1 МБ стека, ~1–10 мкс на переключение, деградация кеша L1/L2.

## Процесс

Процесс — это то, что ОС создаёт, когда ты запускаешь программу. Что в него входит:

- **Виртуальное адресное пространство.** Отдельная таблица страниц. Указатель `0x00007FF8_12340000` в процессе A и в процессе B указывает на разную физическую память. Именно это даёт изоляцию: упавший процесс не портит чужую память.
- **Таблица дескрипторов (handles):** открытые файлы, сокеты, семафоры, окна.
- **Токен безопасности:** от чьего имени работает процесс.
- **Как минимум один поток.** Процесс без потоков — мёртвый процесс.
- В .NET дополнительно: загруженный CLR, кучи GC, домен приложения (в .NET Core — `AssemblyLoadContext`).

Стоимость создания процесса на Linux — порядка сотен микросекунд, на Windows — единицы миллисекунд (Windows создаёт процессы существенно дороже, потому что нет `fork`). Межпроцессное взаимодействие требует явных механизмов: pipe, сокет, разделяемая память, `Mutex` с именем.

## Поток

Поток (thread) — единица, которую планировщик ОС ставит на ядро. У потока своё:

- **Стек.** В Windows по умолчанию **резервируется 1 МБ виртуального адресного пространства**, физическая память выделяется страницами по мере роста (commit on demand). На Linux по умолчанию 8 МБ резерва в pthread, но .NET задаёт свой размер. Управляется через `<ThreadStackSize>` или конструктор `new Thread(action, maxStackSize)`.
- **Контекст регистров:** RIP (счётчик команд), RSP (указатель стека), общие регистры, флаги, состояние FPU/SIMD.
- **Thread Local Storage (TLS)** и в .NET — `[ThreadStatic]`, `ThreadLocal<T>`.
- **Приоритет** и маска сродства к ядрам (affinity).

Общее с остальными потоками процесса: **вся куча, весь код, все дескрипторы**. Отсюда все проблемы синхронизации — см. [[Interlocked, volatile и модель памяти]].

```
Процесс
├── Виртуальное адресное пространство (общее для всех потоков)
│   ├── Код (только чтение)
│   ├── Куча GC ─────────── общая ─────────────┐
│   └── Загруженные сборки                     │
├── Дескрипторы (общие)                        │  ← отсюда гонки
├── Поток 1: стек 1 МБ, регистры, TLS ─────────┤
├── Поток 2: стек 1 МБ, регистры, TLS ─────────┤
└── Поток 3: стек 1 МБ, регистры, TLS ─────────┘
```

### Стоимость потока: конкретные числа

| Что | Порядок величины | Комментарий |
|---|---|---|
| Резерв стека | 1 МБ (Windows, по умолчанию) | Виртуальная память. 10 000 потоков = 10 ГБ адресного пространства |
| Реально закоммиченная память нового потока | 8–64 КБ | Растёт по страницам |
| Структуры ядра на поток | ~10–20 КБ | KTHREAD, ETHREAD, стек ядра |
| Создание потока | 50–200 мкс | Плюс регистрация в CLR |
| Контекстное переключение | 1–10 мкс | Из них ~0.5–2 мкс — само переключение, остальное — промахи кеша после |
| Стоимость промаха L1/L2/TLB после переключения | десятки мкс на «прогрев» | Часто больше самого переключения |

Отсюда правило: **потоки — это ресурс уровня десятков, а не тысяч**. Приложение, которому нужны десятки тысяч одновременных операций, обязано делать их асинхронно, а не по потоку на операцию.

## Планировщик ОС и вытесняющая многозадачность

Планировщик — часть ядра, которая решает, какой поток выполняется на каком ядре и как долго.

**Вытесняющая многозадачность (preemptive multitasking)** означает: ОС может отнять процессор у потока в любой момент, независимо от желания потока. Механизм — прерывание от системного таймера. По его срабатыванию ядро проверяет, не истёк ли квант времени текущего потока, и при необходимости делает переключение.

Квант времени (time slice / quantum):
- Windows, клиентская редакция: ~20–30 мс для фонового потока, короче для потока активного окна.
- Windows Server: ~120 мс (длиннее, чтобы меньше переключаться).
- Linux CFS: квант рассчитывается динамически из `sched_latency_ns` (по умолчанию ~6–24 мс) делённого на число готовых задач, с нижней границей `sched_min_granularity_ns`.

Противоположность — **кооперативная многозадачность**: поток сам отдаёт управление. Так работали Windows 3.x и так работают корутины/`async` внутри одного потока. Один «жадный» участник вешает всех.

### Что именно происходит при контекстном переключении

1. Прерывание таймера → процессор переходит в режим ядра, сохраняет минимальный контекст.
2. Ядро сохраняет регистры текущего потока в его KTHREAD.
3. Планировщик выбирает следующий поток из очередей готовности.
4. **Смена таблицы страниц**, если переключение между процессами (запись в CR3 на x86) — это сбрасывает TLB, самая дорогая часть.
5. Загрузка регистров нового потока, возврат в пользовательский режим.
6. Дальше поток работает с холодными кешами: его данные вытеснены данными предыдущего потока. Это невидимая, но часто основная часть стоимости.

> [!info] Почему переключение между потоками одного процесса дешевле
> Адресное пространство общее, значит CR3 не меняется, TLB не сбрасывается полностью. Именно поэтому многопоточность внутри процесса предпочтительнее многопроцессности, когда изоляция не нужна.

### Состояния потока

```
   Created ──Start()──► Ready ◄──────────────┐
                          │                  │
                    планировщик              │ квант истёк / вытеснен
                     выбрал                  │ более приоритетным
                          ▼                  │
                       Running ──────────────┘
                          │
             блокирующий вызов (WaitOne, Monitor.Enter,
             Read из сокета, Sleep)
                          ▼
                       Waiting ──событие произошло──► Ready
                          │
                          ▼
                    Terminated
```

Ключевое: поток в состоянии `Waiting` **не потребляет процессор**, но продолжает потреблять память (стек!) и место в структурах ядра. Тысяча заблокированных потоков не грузит CPU, но занимает гигабайт адресного пространства и заставляет планировщик перебирать длинные списки.

## Ядра, гиперпоточность и `Environment.ProcessorCount`

- **Физическое ядро** — реальный исполнительный блок.
- **Логический процессор (hardware thread)** — то, что видит ОС. При включённом SMT/Hyper-Threading одно физическое ядро даёт два логических: они делят исполнительные блоки и кеши, но имеют свои наборы регистров.

`Environment.ProcessorCount` возвращает число **логических** процессоров, доступных процессу (с учётом affinity и, начиная с .NET Core 3.0, с учётом cgroups-лимитов в контейнере).

> [!danger] Контейнеры и ProcessorCount
> До .NET Core 3.0 приложение в Docker с лимитом `--cpus=1` на 64-ядерной машине видело 64 процессора и создавало пул под 64 ядра. Результат — постоянное вытеснение и деградация. Начиная с .NET Core 3.0 рантайм читает cgroup-лимиты. Но `--cpus=1.5` округляется вверх до 2. Если нужно точно, задавай `DOTNET_PROCESSOR_COUNT`.

Гиперпоточность даёт прирост 10–30 % на смешанных нагрузках и **отрицательный** прирост на плотных вычислениях, которые упираются в исполнительные блоки (например, SIMD — см. [[Vectorization и SIMD в .NET]]).

```csharp
Console.WriteLine(Environment.ProcessorCount);            // например, 16
Console.WriteLine(Environment.CurrentManagedThreadId);    // ID управляемого потока
Console.WriteLine(Thread.CurrentThread.IsThreadPoolThread); // из пула или нет
```

## Управляемый поток vs поток ОС

В .NET Core / .NET 5+ каждый управляемый поток (`Thread`) соответствует ровно одному потоку ОС. Один к одному.

Историческая деталь: в .NET Framework существовало понятие «логического потока» и теоретическая возможность хостить CLR так, чтобы управляемые потоки были волокнами (fibers) — SQL Server так делал. В современном .NET этого нет. `Thread.ManagedThreadId` не равен ID потока ОС, но соответствие один к одному.

```csharp
// ID потока ОС (Windows / Linux)
// В .NET нет кроссплатформенного API; на Windows — устаревший AppDomain.GetCurrentThreadId
// В Linux можно прочитать через syscall gettid. Практически: используй ManagedThreadId.
Console.WriteLine($"Managed: {Environment.CurrentManagedThreadId}");
```

## Как это выглядит в коде

```csharp
using System.Diagnostics;

var current = Process.GetCurrentProcess();
Console.WriteLine($"PID: {current.Id}");
Console.WriteLine($"Потоков в процессе: {current.Threads.Count}");
Console.WriteLine($"Рабочее множество: {current.WorkingSet64 / 1024 / 1024} МБ");

// Даже «однопоточное» консольное приложение имеет несколько потоков:
// основной, потоки GC (в Server GC — по одному на ядро),
// финализатор, поток таймеров, потоки диагностики.
```

### Демонстрация цены переключения

```csharp
using System.Diagnostics;

// Два потока пинают друг друга через AutoResetEvent — каждый цикл = 2 переключения.
var a = new AutoResetEvent(false);
var b = new AutoResetEvent(false);
const int Iterations = 100_000;

var t = new Thread(() =>
{
    for (int i = 0; i < Iterations; i++)
    {
        a.WaitOne();
        b.Set();
    }
});
t.Start();

var sw = Stopwatch.StartNew();
for (int i = 0; i < Iterations; i++)
{
    a.Set();
    b.WaitOne();
}
sw.Stop();
t.Join();

Console.WriteLine($"{sw.Elapsed.TotalMicroseconds / Iterations:F2} мкс на цикл");
// Типично: 3–15 мкс на цикл (2 переключения + работа планировщика).
// Для сравнения: неконтендованный lock — около 20 наносекунд.
// Разница в ~500 раз.
```

## Блокирующий ввод-вывод: где теряется всё

```csharp
// КАК НЕПРАВИЛЬНО: поток на запрос, блокирующий I/O
var listener = new TcpListener(IPAddress.Any, 5000);
listener.Start();
while (true)
{
    var client = listener.AcceptTcpClient();   // блокирует поток
    new Thread(() =>                            // 1 МБ стека на каждое соединение
    {
        using var stream = client.GetStream();
        var buffer = new byte[4096];
        int read = stream.Read(buffer);         // поток спит в ядре всё время ожидания
        // ...
    }).Start();
}
// 10 000 соединений = 10 000 потоков = 10 ГБ адресного пространства
// + планировщик перебирает 10 000 записей.
```

```csharp
// КАК ПРАВИЛЬНО: асинхронный I/O, потоки не блокируются
var listener = new TcpListener(IPAddress.Any, 5000);
listener.Start();
while (true)
{
    var client = await listener.AcceptTcpClientAsync();
    _ = HandleAsync(client);   // fire-and-forget; про правильный вариант см. заметку про антипаттерны

    static async Task HandleAsync(TcpClient client)
    {
        using (client)
        await using (var stream = client.GetStream())
        {
            var buffer = new byte[4096];
            int read = await stream.ReadAsync(buffer);  // поток свободен на время ожидания
            // ...
        }
    }
}
// 10 000 соединений обслуживаются десятком потоков пула.
```

Механика внизу: асинхронный `ReadAsync` не блокирует поток, потому что регистрирует операцию в порту завершения ввода-вывода (I/O Completion Port на Windows, epoll на Linux). Когда данные пришли, ядро сообщает об этом, и продолжение ставится в очередь пула. Подробнее — [[async и await: как это работает на самом деле]].

> [!warning] Подводные камни
> - **1 МБ стека — это резерв, а не потребление.** Люди спорят «поток не занимает мегабайт». Верно: физически коммитится порядка 8–64 КБ. Но виртуальное адресное пространство резервируется целиком, и на 32-битном процессе (2 ГБ пользовательского пространства) это жёсткий потолок в ~1800 потоков. На 64 битах адресного пространства хватает, но структуры ядра и работа планировщика никуда не деваются.
> - **`Thread.Sleep(0)` и `Thread.Sleep(1)` — разные вещи.** `Sleep(0)` отдаёт остаток кванта только потоку **того же приоритета**, готовому к выполнению; если такого нет — возвращается немедленно. `Sleep(1)` реально уходит в планировщик минимум на один тик таймера (обычно 15.6 мс на Windows по умолчанию!). `Thread.Yield()` отдаёт квант любому готовому потоку **на том же ядре**. Ни один из них не является инструментом синхронизации.
> - **Приоритеты потоков почти всегда вредны.** Повышение приоритета одного потока в .NET-приложении легко приводит к инверсии приоритетов и голоданию GC-потоков. `ThreadPriority` в бэкенде трогать не надо.
> - **Промахи кеша дороже самого переключения.** Микробенчмарк, который меряет только `SwitchToThread`, покажет 1 мкс и обманет тебя. Реальная цена в приложении с рабочим множеством в мегабайты — существенно выше, потому что после переключения L1/L2 забиты чужими данными.
> - **`Process.Threads.Count` в .NET-приложении никогда не равен числу «твоих» потоков.** Там же потоки GC (в Server GC — по числу ядер), финализатор, таймер, EventPipe, потоки библиотек.

> [!example] Как делают в бою
> В типичном ASP.NET Core-сервисе никто не создаёт потоки руками. Kestrel держит небольшой набор потоков цикла событий, работа идёт через порты завершения, а прикладной код исполняется на потоках пула. Единственные оправданные `new Thread(...)` в проде: (1) долгоживущий фоновый цикл, который нельзя отдавать пулу (но и его лучше делать через `BackgroundService`, см. [[Background services и IHostedService]]); (2) поток с нестандартным размером стека под глубокую рекурсию; (3) STA-поток для COM-интеропа. Всё остальное — `Task`.

## Вопросы с собеседований

> [!question]- Чем процесс отличается от потока?
> Процесс — контейнер ресурсов: своё виртуальное адресное пространство, таблица дескрипторов, токен безопасности. Поток — единица планирования внутри процесса: свой стек, свои регистры, свой TLS, но общая с другими потоками процесса память и общие дескрипторы. Из этого следует главное практическое различие: потоки одного процесса могут портить данные друг друга (отсюда нужна синхронизация), а процессы изолированы и общаются только через явные механизмы IPC. Переключение между потоками одного процесса дешевле, чем между процессами, потому что не меняется таблица страниц и не сбрасывается TLB.

> [!question]- Что такое контекстное переключение и сколько оно стоит?
> Это сохранение состояния текущего потока (регистры, счётчик команд, указатель стека) и загрузка состояния другого потока, выполняемое ядром ОС. Прямая стоимость — примерно 1–10 микросекунд. Но реальная цена выше: после переключения новый поток работает с холодными кешами L1/L2 и частично сброшенным TLB, и «прогрев» может стоить дороже самого переключения. При переключении между процессами дополнительно меняется CR3 и TLB сбрасывается почти полностью. Для сравнения: захват неконтендованного `lock` — порядка 20 наносекунд, то есть в сотни раз дешевле.

> [!question]- Почему нельзя создавать поток на каждый входящий запрос?
> Три причины. Первая: память — 1 МБ резерва виртуального адресного пространства на поток плюс 10–20 КБ структур ядра; при 10 000 соединений это 10 ГБ резерва. Вторая: время создания — 50–200 мкс на поток, что сопоставимо со временем обработки лёгкого запроса. Третья и главная: планировщик. Когда готовых потоков в разы больше, чем ядер, система входит в режим постоянного вытеснения (thrashing): CPU тратится не на работу, а на переключения и промахи кеша, латентность растёт нелинейно. Решение — пул потоков плюс асинхронный ввод-вывод: небольшое фиксированное число потоков обслуживает тысячи логических операций.

> [!question]- Что такое вытесняющая многозадачность и чем она отличается от кооперативной?
> При вытесняющей многозадачности ОС по прерыванию таймера может отобрать процессор у потока в любой момент, независимо от кода потока. Это даёт устойчивость: зациклившийся поток не вешает систему. При кооперативной многозадачности поток сам должен отдать управление явным вызовом; один невежливый участник блокирует всех. Все современные ОС используют вытесняющую модель для потоков. При этом `async`/`await` внутри одного потока — это кооперативная модель: точки `await` и есть точки, где код добровольно отдаёт управление. Поэтому CPU-bound цикл без `await` внутри асинхронного метода блокирует поток пула так же, как обычный синхронный код.

> [!question]- Сколько потоков имеет смысл для CPU-bound и для I/O-bound работы?
> Для чистой CPU-bound работы оптимум — примерно `Environment.ProcessorCount` потоков. Больше — только лишние переключения, меньше — недогруженные ядра. Для I/O-bound работы понятия «оптимального числа потоков» вообще не должно возникать: правильный ответ — не блокировать потоки, а использовать асинхронный ввод-вывод, тогда десяток потоков обслужит тысячи операций. Если приходится работать с блокирующим API без асинхронной альтернативы, число потоков считают по формуле Литтла: `потоки ≈ пропускная_способность × время_ожидания`, и обязательно ограничивают его семафором, чтобы не выесть пул.

> [!question]- Что делает `Environment.ProcessorCount` в контейнере?
> Начиная с .NET Core 3.0 рантайм учитывает cgroup-ограничения: при `--cpus=4` вернётся 4, а не число ядер хоста. Дробные значения округляются вверх (`--cpus=1.5` даст 2). Это важно, потому что от `ProcessorCount` зависят: размер пула потоков по умолчанию, число куч Server GC, `MaxDegreeOfParallelism` по умолчанию в `Parallel`/PLINQ. Если автоопределение работает не так, как нужно, значение переопределяется переменной окружения `DOTNET_PROCESSOR_COUNT`. Ошибка «приложение видит 64 ядра при лимите в 1» была массовой на .NET Core 2.x и приводила к сотням лишних потоков в контейнере.

## Задачи

### Задача 1. Измерить стоимость переключения

Напиши бенчмарк, который измеряет среднее время одного контекстного переключения между двумя потоками, и сравни с временем вызова простого метода.

> [!success]- Решение
> ```csharp
> using System.Diagnostics;
>
> const int N = 200_000;
> var ping = new AutoResetEvent(false);
> var pong = new AutoResetEvent(false);
>
> var worker = new Thread(() =>
> {
>     for (int i = 0; i < N; i++) { ping.WaitOne(); pong.Set(); }
> }) { IsBackground = true };
> worker.Start();
>
> var sw = Stopwatch.StartNew();
> for (int i = 0; i < N; i++) { ping.Set(); pong.WaitOne(); }
> sw.Stop();
> double switchNs = sw.Elapsed.TotalNanoseconds / (N * 2);   // 2 переключения на цикл
>
> // Базовая линия: пустой вызов
> sw.Restart();
> long acc = 0;
> for (int i = 0; i < N; i++) acc += Work(i);
> sw.Stop();
> double callNs = sw.Elapsed.TotalNanoseconds / N;
>
> Console.WriteLine($"Переключение: {switchNs:F0} нс");   // ~2000–8000 нс
> Console.WriteLine($"Вызов метода: {callNs:F2} нс");     // ~0.3–2 нс
> Console.WriteLine($"Отношение: {switchNs / callNs:F0}x");
>
> [MethodImpl(MethodImplOptions.NoInlining)]
> static long Work(int i) => i * 2L;
> ```
> Отношение получается в тысячи раз. Это и есть причина, по которой пул потоков переиспользует потоки вместо создания новых, и по которой асинхронный I/O выгоднее блокирующего.
>
> Для честного измерения лучше использовать BenchmarkDotNet — см. [[Как измерять: BenchmarkDotNet]]. Приведённый код даёт правильный порядок величины, но не учитывает прогрев JIT и шум планировщика.

### Задача 2. Найти предел по потокам

Напиши программу, которая создаёт потоки, пока не упрётся в лимит, и выведи, сколько получилось. Объясни, во что именно упёрлась.

> [!success]- Решение
> ```csharp
> int created = 0;
> var stop = new ManualResetEventSlim(false);
> try
> {
>     while (true)
>     {
>         var t = new Thread(() => stop.Wait(), maxStackSize: 256 * 1024)
>         {
>             IsBackground = true
>         };
>         t.Start();
>         created++;
>         if (created % 500 == 0)
>             Console.WriteLine($"{created} потоков, RSS {Environment.WorkingSet / 1024 / 1024} МБ");
>     }
> }
> catch (OutOfMemoryException)
> {
>     Console.WriteLine($"Упёрлись на {created} потоках");
> }
> finally { stop.Set(); }
> ```
> На 64-битной системе с 256 КБ стека получаются десятки тысяч потоков, и упрёшься скорее в лимит ОС (`/proc/sys/kernel/threads-max`, `ulimit -u` на Linux) или в физическую память под стеки ядра, чем в адресное пространство. Уменьши `maxStackSize` — предел вырастет; убери его (1 МБ по умолчанию) — упадёт. Отдельно обрати внимание, как растёт время создания потока по мере роста их числа: планировщику всё тяжелее.
>
> Практический вывод: даже если технически можно создать 30 000 потоков, работать они будут отвратительно. Техническая возможность не равна работоспособности.

### Задача 3. Sleep(0) vs Yield vs SpinWait

Объясни разницу и покажи, когда какой применяется.

> [!success]- Решение
> ```csharp
> // Thread.Sleep(0): отдаёт остаток кванта потоку ТОГО ЖЕ приоритета, готовому к запуску,
> //   на любом ядре. Если такого нет — возврат немедленно, переключения нет.
> // Thread.Yield(): отдаёт квант любому готовому потоку НА ТОМ ЖЕ ядре (Windows: SwitchToThread).
> //   Возвращает bool — было ли переключение.
> // Thread.Sleep(1): гарантированно уходит в планировщик минимум на тик таймера.
> //   На Windows по умолчанию ~15.6 мс — катастрофа для горячего цикла.
> // SpinWait: адаптивная стратегия — сначала крутится в цикле с инструкцией PAUSE,
> //   затем Yield, затем Sleep(0), затем Sleep(1).
>
> // Правильное применение — короткое ожидание изменения флага другим ядром:
> var spinner = new SpinWait();
> while (Volatile.Read(ref _flag) == 0)
>     spinner.SpinOnce();     // сам подберёт стратегию
> ```
> `SpinWait` полезен, когда ожидание заведомо короче стоимости переключения (единицы микросекунд) — типично в lock-free структурах. Если ожидание может быть длинным, крутиться нельзя: сожжёшь ядро. Тогда нужен настоящий примитив ожидания из [[Semaphore, Mutex, ReaderWriterLockSlim]].

## Итог

- Процесс = изолированное адресное пространство + ресурсы; поток = стек + регистры + место в очереди планировщика. Потоки одного процесса делят всю память.
- Поток стоит ~1 МБ резерва стека, 10–20 КБ ядерных структур и 50–200 мкс на создание. Это ресурс масштаба десятков, а не тысяч.
- Контекстное переключение — 1–10 мкс прямых затрат плюс потеря кешей, что часто дороже. Именно поэтому пул потоков переиспользует потоки.
- Вытесняющая многозадачность: ОС может отнять процессор в любой момент. `async`/`await` внутри потока — наоборот, кооперативная модель, где точки `await` и есть точки уступки.
- Заблокированный поток не жрёт CPU, но жрёт память и место в планировщике. Задача асинхронного I/O — вообще не иметь заблокированных потоков.
- `Environment.ProcessorCount` учитывает cgroups с .NET Core 3.0; от него зависят пул, GC и `MaxDegreeOfParallelism`.
