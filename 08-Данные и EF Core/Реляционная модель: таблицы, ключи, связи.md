# Реляционная модель: таблицы, ключи, связи

> [!abstract] Коротко
> Реляционная модель — это математика на множествах: отношение (relation) есть множество кортежей, каждый кортеж — набор значений из доменов. SQL реализовал эту модель приблизительно: таблица допускает дубликаты строк, имеет порядок колонок и знает NULL, чего в исходной теории не было. Практическая работа с БД сводится к тому, чтобы средствами ключей, внешних ключей и ограничений вернуть таблице свойства настоящего отношения — и не дать данным разъехаться. В финтехе это не академический вопрос: строка-дубликат в проводках — это реально потерянные или созданные из воздуха деньги.

## Зачем это нужно

Схема БД живёт дольше, чем код вокруг неё. Приложение перепишут на новом фреймворке, микросервис распилят, ORM поменяют — а таблица `accounts` с кривым ключом останется и будет тянуть за собой костыли годами. Ошибка в C#-коде правится деплоем; ошибка в модели данных правится миграцией, разбором накопившегося мусора и объяснительной перед комплаенсом.

Реляционная модель даёт язык, на котором можно рассуждать о корректности схемы до того, как в неё зальют миллион строк. Она отвечает на вопросы: как гарантировать, что у клиента не будет двух счетов с одним номером; что проводка не сошлётся на несуществующий счёт; что удаление клиента не сотрёт историю его платежей. Всё это выражается декларативно — ограничениями, которые проверяет сама СУБД, а не «мы же в сервисе проверяем».

Ключевая мысль: **любую проверку, которую можно переложить на СУБД, надо переложить на СУБД**. Код с проверкой обходят кривой миграцией, скриптом поддержки, вторым сервисом, который пишет в ту же базу. Ограничение в схеме не обойдёт никто.

## Отношение, кортеж, атрибут, домен

Формально отношение `R` над множеством атрибутов `{A1, ..., An}` — это подмножество декартова произведения доменов:

```
R ⊆ D1 × D2 × ... × Dn
```

Термины и их SQL-соответствия:

| Теория | SQL | Пример |
|---|---|---|
| Отношение (relation) | Таблица (table) | `accounts` |
| Кортеж (tuple) | Строка (row) | одна запись о счёте |
| Атрибут (attribute) | Столбец (column) | `currency_code` |
| Домен (domain) | Тип данных + ограничения | `char(3)` + CHECK на ISO 4217 |
| Кардинальность отношения | Число строк | `COUNT(*)` |
| Степень (арность) отношения | Число столбцов | 8 |

Домен — это не просто тип. Домен `currency_code` — не «строка», а «трёхбуквенный код валюты из ISO 4217 в верхнем регистре». Тип `char(3)` покрывает лишь часть этого определения, остальное дописывают `CHECK` и внешний ключ на справочник. В PostgreSQL домен можно объявить буквально:

```sql
CREATE DOMAIN money_amount AS numeric(20, 4)
    CHECK (VALUE IS NOT NULL);

CREATE DOMAIN iso_currency AS char(3)
    CHECK (VALUE ~ '^[A-Z]{3}$');
```

> [!danger] Деньги — только numeric/decimal
> Домен денежной суммы — это `numeric(p, s)` в PostgreSQL и `decimal(p, s)` в SQL Server, ничего больше. `real`/`double precision`/`float` — двоичная плавающая точка: `0.1 + 0.2 <> 0.3`, накопленная ошибка в отчёте за месяц даёт расхождение баланса. Тип PostgreSQL `money` тоже не годится: его масштаб задан глобальным параметром `lc_monetary` и меняется вместе с локалью сервера. В C# соответствие — `decimal`, а не `double`.

### Отношение — это множество

Из определения «подмножество декартова произведения» следуют три свойства, которых у SQL-таблицы нет:

1. **Нет дубликатов.** Множество не содержит одинаковых элементов. Значит, у любого отношения есть ключ — как минимум весь набор атрибутов целиком.
2. **Нет порядка кортежей.** Множество неупорядочено. Понятия «первая строка» не существует.
3. **Нет порядка атрибутов.** Кортеж адресуется по имени атрибута, а не по позиции.

### Где SQL отступил от теории

SQL работает не с множествами, а с мультимножествами (bag, мешок) — и с упорядоченными кортежами.

```sql
CREATE TABLE demo (a int, b int);
INSERT INTO demo VALUES (1, 1), (1, 1), (1, 1);

SELECT count(*) FROM demo;
-- 3   -- в отношении такого быть не может, тут три одинаковых кортежа
```

| Свойство отношения | Что в SQL | Чем лечить |
|---|---|---|
| Нет дубликатов строк | Дубликаты разрешены | `PRIMARY KEY` / `UNIQUE` на каждой таблице |
| Нет порядка строк | Порядка тоже нет, но `SELECT` без `ORDER BY` создаёт иллюзию порядка | Явный `ORDER BY` всегда, когда порядок важен |
| Нет порядка колонок | Колонки позиционные: `SELECT *`, `INSERT` без списка колонок | Всегда перечислять колонки явно |
| Каждое значение из домена | Есть NULL — «значение вне домена» | `NOT NULL` по умолчанию, NULL — осознанное решение |

Порядок колонок в SQL — источник целого класса аварий:

```sql
-- Плохо: молчаливо сломается после ALTER TABLE ... ADD COLUMN в середине
INSERT INTO accounts VALUES (1, 42, 'USD', '20208840100000000001');

-- Хорошо: не зависит от физического порядка колонок
INSERT INTO accounts (client_id, currency_code, number)
VALUES (42, 'USD', '20208840100000000001');
```

## NULL и трёхзначная логика

NULL — не значение, а маркер «значения нет». Он не принадлежит домену, поэтому любое сравнение с ним даёт не «истина/ложь», а третье состояние — UNKNOWN.

```sql
SELECT NULL = NULL;      -- NULL (не true!)
SELECT NULL <> NULL;     -- NULL
SELECT 1 > NULL;         -- NULL
SELECT NULL IS NULL;     -- true   -- единственный корректный способ проверки
```

Логика становится трёхзначной: `TRUE`, `FALSE`, `UNKNOWN`. `WHERE` пропускает строку только при `TRUE` — `UNKNOWN` отбрасывается наравне с `FALSE`. А вот `CHECK`-ограничение, наоборот, считает `UNKNOWN` допустимым и строку пропускает: `CHECK (amount > 0)` не защитит от `amount = NULL`.

```sql
CREATE TABLE t (amount numeric(20,4) CHECK (amount > 0));
INSERT INTO t VALUES (NULL);   -- проходит! CHECK вернул UNKNOWN, а не FALSE
INSERT INTO t VALUES (-1);     -- ERROR: new row violates check constraint
```

Отсюда правило: **`NOT NULL` — умолчание при проектировании**. Nullable-колонка допустима только там, где «значения нет» — часть бизнес-смысла (`closed_at` у открытого счёта, `deleted_at` у живой записи). Развёрнутые таблицы истинности и ловушку `NOT IN (... NULL ...)` разбирает [[SQL: SELECT, фильтрация, сортировка]].

В C# аналог этого решения — nullable reference types и `decimal?` против `decimal`; см. [[Nullable reference types]].

## Ключи

### Суперключ

Суперключ (superkey) — любой набор атрибутов, который уникально определяет кортеж. Весь набор атрибутов отношения — всегда суперключ (дубликатов-то в отношении нет). Суперключей у отношения обычно много, и большинство из них избыточны.

### Потенциальный ключ (candidate key)

Потенциальный ключ — минимальный суперключ: убери любой атрибут, и уникальность потеряется. У таблицы `accounts` потенциальных ключей два: `{id}` и `{number}`. Набор `{id, number}` — суперключ, но не потенциальный ключ, потому что не минимален.

### Первичный и альтернативный

Из потенциальных ключей один выбирают первичным (`PRIMARY KEY`), остальные объявляют альтернативными (`UNIQUE`). Технически различий немного:

| | PRIMARY KEY | UNIQUE |
|---|---|---|
| Сколько на таблицу | Ровно один | Сколько угодно |
| NULL в колонках | Запрещён | Разрешён |
| Дубликаты NULL | — | По умолчанию считаются различными: несколько NULL допустимы |
| Цель по умолчанию для FK | Да, `REFERENCES t` без списка колонок берёт PK | Нет, надо перечислять колонки |
| Кластеризация | В PostgreSQL — нет (heap-таблицы). В SQL Server PK по умолчанию кластерный | — |

Поведение UNIQUE с NULL настраивается начиная с PostgreSQL 15:

```sql
-- Классика: два NULL считаются разными, обе строки пройдут
CREATE TABLE a (tax_id char(9) UNIQUE);
INSERT INTO a VALUES (NULL), (NULL);   -- OK

-- PostgreSQL 15+: NULL считаются одинаковыми
CREATE TABLE b (tax_id char(9) UNIQUE NULLS NOT DISTINCT);
INSERT INTO b VALUES (NULL);
INSERT INTO b VALUES (NULL);   -- ERROR: duplicate key value
```

> [!info] SQL Server
> Уникальный индекс в SQL Server допускает **ровно один** NULL в колонке — поведение посередине между двумя режимами PostgreSQL. Обойти можно фильтрованным индексом `WHERE tax_id IS NOT NULL`.

### Составной ключ

Составной (composite) ключ — из двух и более колонок. Каноническое применение — таблица связи M:N, где PK составлен из двух внешних ключей. Порядок колонок в составном ключе важен: он определяет порядок в B-tree индексе и, значит, какие запросы этот индекс ускорит (см. [[Индексы: как работают и когда помогают]]).

### Естественный vs суррогатный

Естественный ключ (natural key) — атрибут, который существует в предметной области: ИНН, номер счёта, код валюты. Суррогатный (surrogate) — искусственный идентификатор без бизнес-смысла: `bigint identity`, `uuid`.

| Критерий | Естественный | Суррогатный |
|---|---|---|
| Стабильность | Меняется: человек сменил паспорт, регулятор перевыпустил код | Никогда не меняется |
| Размер | Часто широкий (`char(20)`, текст) — раздувает все FK и индексы | 8 байт (`bigint`) или 16 (`uuid`) |
| Читаемость в логах | Сразу понятно, о ком речь | Ничего не говорит без JOIN |
| Утечка данных наружу | ИНН в URL — это уже персональные данные | Безопаснее, особенно UUID |
| Дополнительный индекс | Не нужен | Нужен UNIQUE на бизнес-ключ, иначе дубликаты |
| Каскадное обновление | Требует `ON UPDATE CASCADE` по всей схеме | Не требуется |
| Слияние баз / шардирование | Коллизии маловероятны | `bigint identity` коллизирует, `uuid` — нет |

**Что выбрать в финтехе.** Практика, к которой сходятся почти все: суррогатный PK плюс обязательный UNIQUE на естественный бизнес-ключ. Первый держит связи внутри схемы, второй защищает от дубликатов из внешнего мира.

Исключение — маленькие стабильные справочники: у `currencies` первичным ключом разумно взять сам код ISO 4217. Он короткий, стабильный, и `accounts.currency_code = 'USD'` читается в дампе без единого JOIN.

Для идентификатора, который уходит наружу (в API, в чек, в вебхук), берут UUID версии 7 — он сортируется по времени создания, поэтому не фрагментирует B-tree, в отличие от UUIDv4.

```sql
-- PostgreSQL 18: uuidv7() встроен, расширения не нужны
CREATE TABLE clients (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- внутренний
    public_id uuid   NOT NULL DEFAULT uuidv7() UNIQUE           -- наружный
);
```

```csharp
// В .NET 9+ есть парная фабрика; в EF Core её удобно ставить генератором значений
var publicId = Guid.CreateVersion7();   // монотонно возрастающий GUID
```

> [!warning] serial устарел
> `serial`/`bigserial` — устаревший синтаксис PostgreSQL `#устарело`. Он создаёт отдельный объект sequence, права на который надо выдавать отдельно, и не входит в стандарт SQL. Пиши `GENERATED ALWAYS AS IDENTITY` — сиквенс становится зависимым объектом таблицы и удаляется вместе с ней.

## Внешние ключи и ссылочная целостность

Внешний ключ (foreign key, FK) — набор атрибутов дочерней таблицы, значения которого обязаны присутствовать в потенциальном ключе родительской. Это и есть ссылочная целостность (referential integrity): в базе не бывает проводки, указывающей на несуществующий счёт.

```sql
ALTER TABLE accounts
    ADD CONSTRAINT fk_accounts_client
    FOREIGN KEY (client_id) REFERENCES clients (id)
    ON DELETE RESTRICT
    ON UPDATE CASCADE;
```

Важная деталь для составных FK: если хотя бы одна колонка NULL, поведение задаёт `MATCH`.

| Режим | Когда проверка пропускается |
|---|---|
| `MATCH SIMPLE` (по умолчанию) | Достаточно одной NULL-колонки — FK не проверяется вообще |
| `MATCH FULL` | Либо все колонки NULL, либо все не-NULL; смесь запрещена |
| `MATCH PARTIAL` | В стандарте есть, в PostgreSQL не реализован |

`MATCH SIMPLE` на составном FK — тихая дыра: строка со значениями `(NULL, 12345)` пройдёт, даже если пары такой в родителе нет.

### ON DELETE / ON UPDATE

| Действие | Что происходит при удалении/обновлении родителя |
|---|---|
| `NO ACTION` (по умолчанию) | Ошибка. Проверка **в конце оператора**, поэтому можно объявить `DEFERRABLE` и отложить до конца транзакции |
| `RESTRICT` | Ошибка. Проверка немедленная, отложить нельзя |
| `CASCADE` | Дочерние строки удаляются / их ключ обновляется следом |
| `SET NULL` | FK-колонки дочерних строк становятся NULL (требует их nullable) |
| `SET DEFAULT` | FK-колонки получают `DEFAULT`, который сам обязан существовать в родителе |

PostgreSQL 15+ умеет ограничивать список колонок: `ON DELETE SET NULL (manager_id)` — обнулить только часть составного FK.

### Что выбрать в финансовой схеме

Правило простое: **по умолчанию `RESTRICT` (или `NO ACTION`), `CASCADE` — только для строго подчинённых сущностей, которые не имеют смысла без родителя и не являются деньгами**.

| Связь | Действие | Почему |
|---|---|---|
| `accounts.client_id -> clients.id` | `ON DELETE RESTRICT` | Клиента со счетами удалять нельзя вообще; закрывают статусом |
| `entries.account_id -> accounts.id` | `ON DELETE RESTRICT` | Проводка — юридический факт, живёт дольше счёта |
| `entries.transaction_id -> transactions.id` | `ON DELETE RESTRICT` | См. ниже про опасность CASCADE |
| `account_limits.account_id -> accounts.id` | `ON DELETE CASCADE` | Лимит без счёта бессмысленен, деньгами не является |
| `accounts.currency_code -> currencies.code` | `ON UPDATE CASCADE` | Естественный ключ теоретически может смениться |
| `client_documents.client_id` | `ON DELETE CASCADE` | Вложения без клиента — мусор |

### Почему CASCADE опасен для проводок

`ON DELETE CASCADE` превращает безобидный на вид `DELETE` в неограниченную рекурсивную операцию. Три конкретных механизма отказа:

1. **Невидимый радиус поражения.** Разработчик пишет `DELETE FROM transactions WHERE id = 100500`, а СУБД молча уносит все `entries` этой проводки. Дебет и кредит исчезают вместе — баланс сойдётся, аудиторский след пропадёт. Финансовая история в принципе не должна удаляться: отмену оформляют сторнирующей проводкой, а не `DELETE`.
2. **Цепная реакция.** CASCADE транзитивен. Удаление одного клиента может пройти по цепочке `clients -> accounts -> entries -> ...` и вычистить пол-базы. Проверить радиус заранее по коду нельзя — только по схеме.
3. **Блокировки и дедлоки.** Каскад берёт row-level блокировки на все затронутые строки в порядке, который определяет планировщик, а не приложение. На горячих таблицах это надёжный способ получить взаимоблокировку (см. [[Блокировки и взаимоблокировки в БД]]) и долгую транзакцию, удерживающую тысячи строк.

Правильный паттерн для финансовых данных — soft delete плюс запрет физического удаления:

```sql
ALTER TABLE clients ADD COLUMN deleted_at timestamptz;

-- Отзыв прав на DELETE у прикладной роли: страховка от «ой, забыл WHERE»
REVOKE DELETE ON transactions, entries FROM app_user;
```

## Кардинальность связей

### 1:1

Обе стороны ссылаются друг на друга не более чем одной строкой. Реализация: PK дочерней таблицы одновременно является FK на родителя.

```sql
CREATE TABLE client_kyc (
    client_id     bigint PRIMARY KEY
                  REFERENCES clients (id) ON DELETE RESTRICT,
    passport_hash bytea       NOT NULL,
    verified_at   timestamptz NOT NULL,
    risk_level    smallint    NOT NULL CHECK (risk_level BETWEEN 1 AND 5)
);
```

`PRIMARY KEY` на `client_id` — это и есть гарантия «не более одной анкеты на клиента». Если бы там был обычный FK, получилась бы 1:N.

Когда выделять 1:1 в отдельную таблицу: колонки редко читаются и широкие (сканы основной таблицы дешевеют), у них другой профиль доступа или другие требования по шифрованию/правам. Иначе — держи в одной таблице.

### 1:N

Самая частая связь. FK живёт на стороне «многих».

```sql
-- Один клиент - много счетов. FK в accounts, а не в clients.
ALTER TABLE accounts
    ADD CONSTRAINT fk_accounts_client
    FOREIGN KEY (client_id) REFERENCES clients (id) ON DELETE RESTRICT;
```

Обязательность стороны «один» задаётся `NOT NULL` на FK: `client_id bigint NOT NULL` означает «счёт не бывает ничей».

> [!tip] Индекс на FK не создаётся автоматически
> PostgreSQL строит индекс под `PRIMARY KEY` и `UNIQUE`, но **не** под внешний ключ. Без индекса на `accounts.client_id` каждый `DELETE`/`UPDATE` родителя вызывает seq scan дочерней таблицы для проверки ссылок, а `JOIN` по связи идёт полным перебором. То же в SQL Server. Индекс на FK — почти всегда нужен.

### M:N

Прямой связи M:N в реляционной модели не существует. Её разбивают на две связи 1:N через таблицу связи (junction, ассоциативная таблица). Классический банковский случай — совместные счета: у счёта может быть несколько владельцев, у клиента — несколько счетов в совместном владении.

```sql
CREATE TABLE account_holders (
    account_id bigint NOT NULL REFERENCES accounts (id) ON DELETE RESTRICT,
    client_id  bigint NOT NULL REFERENCES clients  (id) ON DELETE RESTRICT,
    role       text   NOT NULL,
    added_at   timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT pk_account_holders PRIMARY KEY (account_id, client_id),
    CONSTRAINT ck_account_holders_role CHECK (role IN ('primary', 'joint', 'viewer'))
);

-- Обратный индекс: PK покрывает поиск «владельцы счёта»,
-- а для «счета клиента» нужен индекс с client_id впереди
CREATE INDEX ix_account_holders_client ON account_holders (client_id, account_id);

-- Ровно один основной владелец на счёт
CREATE UNIQUE INDEX ux_account_holders_primary
    ON account_holders (account_id)
    WHERE role = 'primary';
```

Составной PK `(account_id, client_id)` даёт бесплатно две вещи: запрет дублирования пары и покрывающий индекс для навигации в одну сторону. Суррогатный `id` в таблице связи заводят только тогда, когда на неё саму нужно ссылаться из третьей таблицы.

## ER-модель и «воронья лапка»

Нотация crow's foot описывает кардинальность и обязательность на обоих концах связи:

```
  ||   ровно один            o|   ноль или один
 -|<   один или много       o|<   ноль или много
```

Схема сквозного примера:

```
      currencies                         clients
   +----------------+              +------------------+
   | PK code char(3)|              | PK id            |
   |    minor_unit  |              | UQ public_id     |
   |    name        |              | UQ tax_id (part) |
   +--------+-------+              | UQ full_name     |
            |                      |    deleted_at    |
            || 1                   +---------+--------+
            |                                || 1
            |                                |
            |                                o<  0..N
            |                      +---------+--------+
            |         1 ||         |     accounts     |
            +-----------------o<---| PK id            |
                                   | FK client_id     |
                                   | FK currency_code |
                                   | UQ number        |
                                   |    balance       |
                                   |    closed_at     |
                                   +---------+--------+
                                             || 1
                                             |
                                             o<  0..N
    transactions                   +---------+--------+
 +------------------+   1 ||       |      entries     |
 | PK id            |-------o<-----| PK transaction_id|
 | UQ external_ref  |              | PK seq           |
 |    booked_at     |              | FK account_id    |
 +------------------+              |    amount        |
                                   +------------------+

      clients  ||---o<  account_holders  >o---||  accounts     (M:N)
      clients  ||---o|  client_kyc                             (1:1)
```

Читается так: у счёта ровно один клиент-держатель по колонке `client_id`, у клиента — ноль или больше счетов; у проводки (`entries`) ровно одна транзакция, у транзакции — ноль или больше проводок (на практике минимум две, но это уже не выражается ER-нотацией и уходит в триггер или `DEFERRABLE`-проверку).

## Ограничения как часть модели

Ограничение — это часть определения домена и отношения, а не «дополнительная опция». Пять инструментов:

| Ограничение | Что гарантирует | Проверяется |
|---|---|---|
| `NOT NULL` | Значение принадлежит домену | При записи, немедленно |
| `CHECK` | Предикат над одной строкой | При записи; UNKNOWN считается пройденным |
| `UNIQUE` | Нет двух строк с одинаковым набором значений | При записи (может быть `DEFERRABLE`) |
| `PRIMARY KEY` | `UNIQUE` + `NOT NULL` | При записи |
| `FOREIGN KEY` | Ссылка разрешима | Триггером после оператора |
| `EXCLUDE` (PostgreSQL) | Нет двух строк, для которых указанные операторы дают true | При записи, через индекс GiST/B-tree |

`CHECK` видит только одну строку — он не может обратиться к другой таблице или к агрегату. Попытка обойти это подзапросом внутри функции с `IMMUTABLE` — известная дыра: PostgreSQL не перепроверит ограничение при изменении другой таблицы, и данные разъедутся.

### EXCLUDE — то, чего нет в SQL Server

`EXCLUDE` обобщает `UNIQUE`: вместо жёсткого равенства он берёт произвольный оператор. Главное применение — запрет пересечения интервалов.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;   -- нужен для = по скалярным типам в gist

CREATE TABLE account_limits (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    account_id bigint        NOT NULL REFERENCES accounts (id) ON DELETE CASCADE,
    daily_cap  numeric(20,4) NOT NULL CHECK (daily_cap > 0),
    period     daterange     NOT NULL,
    CONSTRAINT ex_account_limits_no_overlap
        EXCLUDE USING gist (account_id WITH =, period WITH &&)
);

INSERT INTO account_limits (account_id, daily_cap, period)
VALUES (1, 5000.0000, daterange('2026-01-01', '2026-07-01'));   -- OK

INSERT INTO account_limits (account_id, daily_cap, period)
VALUES (1, 9000.0000, daterange('2026-06-01', '2027-01-01'));
-- ERROR: conflicting key value violates exclusion constraint
--        "ex_account_limits_no_overlap"
```

Без `EXCLUDE` это пришлось бы проверять в коде под `SERIALIZABLE` или явной блокировкой — и всё равно ловить гонки.

> [!info] SQL Server
> Аналога `EXCLUDE` нет. Пересечение периодов проверяют триггером, `SERIALIZABLE`-транзакцией с диапазонной блокировкой либо темпоральными таблицами (`SYSTEM_VERSIONING`) там, где задача сводится к истории версий.

### Частичный UNIQUE-индекс для soft delete

Классическая проблема: `UNIQUE (tax_id)` не даёт завести клиента с тем же ИНН повторно, даже если предыдущая запись помечена удалённой. Решение — частичный (partial) уникальный индекс:

```sql
CREATE UNIQUE INDEX ux_clients_tax_id_alive
    ON clients (tax_id)
    WHERE deleted_at IS NULL AND tax_id IS NOT NULL;

INSERT INTO clients (tax_id, full_name, birth_date)
VALUES ('123456789', 'Иванов И. И.', DATE '1990-05-01');

INSERT INTO clients (tax_id, full_name, birth_date)
VALUES ('123456789', 'Иванов И. И.', DATE '1990-05-01');
-- ERROR: duplicate key value violates unique index "ux_clients_tax_id_alive"

UPDATE clients SET deleted_at = now() WHERE tax_id = '123456789';

INSERT INTO clients (tax_id, full_name, birth_date)
VALUES ('123456789', 'Иванов И. И.', DATE '1990-05-01');   -- теперь OK
```

Тот же приём — «ровно один активный текущий счёт клиента в валюте»:

```sql
CREATE UNIQUE INDEX ux_accounts_one_open_current
    ON accounts (client_id, currency_code)
    WHERE kind = 'current' AND closed_at IS NULL;
```

Альтернатива без частичного индекса — колонка `deleted_marker` со значением `0` для живых и `id` для удалённых, входящая в обычный UNIQUE. Некрасиво, но работает в СУБД без partial-индексов.

> [!info] SQL Server
> То же самое называется filtered index: `CREATE UNIQUE INDEX ... ON clients (tax_id) WHERE deleted_at IS NULL;`. Синтаксис совпадает, но фильтр в SQL Server поддерживает только простые предикаты сравнения — выражения вроде `WHERE lower(x) = 'y'` не пройдут.

## Сквозной пример: схема банковского сервиса

```sql
-- 1. Справочник валют. Естественный PK - код ISO 4217.
CREATE TABLE currencies (
    code         char(3)  PRIMARY KEY,
    numeric_code smallint NOT NULL,
    minor_unit   smallint NOT NULL DEFAULT 2,
    name         text     NOT NULL,
    CONSTRAINT uq_currencies_numeric UNIQUE (numeric_code),
    CONSTRAINT ck_currencies_code  CHECK (code ~ '^[A-Z]{3}$'),
    CONSTRAINT ck_currencies_minor CHECK (minor_unit BETWEEN 0 AND 4)
);

INSERT INTO currencies (code, numeric_code, minor_unit, name) VALUES
    ('UZS', 860, 2, 'Узбекский сум'),
    ('USD', 840, 2, 'Доллар США'),
    ('EUR', 978, 2, 'Евро'),
    ('JPY', 392, 0, 'Иена');

-- 2. Клиенты. Суррогатный PK + наружный UUIDv7 + бизнес-ключ под partial UNIQUE.
CREATE TABLE clients (
    id         bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    public_id  uuid        NOT NULL DEFAULT uuidv7(),
    tax_id     char(9),
    full_name  text        NOT NULL,
    birth_date date        NOT NULL,
    status     text        NOT NULL DEFAULT 'pending',
    created_at timestamptz NOT NULL DEFAULT now(),
    deleted_at timestamptz,
    CONSTRAINT uq_clients_public_id UNIQUE (public_id),
    CONSTRAINT ck_clients_status CHECK (status IN ('pending','active','blocked','closed')),
    CONSTRAINT ck_clients_name   CHECK (length(btrim(full_name)) > 0),
    CONSTRAINT ck_clients_birth  CHECK (birth_date BETWEEN DATE '1900-01-01' AND CURRENT_DATE)
);

CREATE UNIQUE INDEX ux_clients_tax_id_alive
    ON clients (tax_id) WHERE deleted_at IS NULL AND tax_id IS NOT NULL;

INSERT INTO clients (tax_id, full_name, birth_date, status) VALUES
    ('100000001', 'Иванов Иван Иванович',   DATE '1988-03-12', 'active'),
    ('100000002', 'Петрова Мария Сергеевна', DATE '1995-11-02', 'active');

-- 3. Счета. Деньги - numeric(20,4). Номер счёта - альтернативный ключ.
CREATE TABLE accounts (
    id            bigint        GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    client_id     bigint        NOT NULL,
    currency_code char(3)       NOT NULL,
    number        char(20)      NOT NULL,
    kind          text          NOT NULL,
    balance       numeric(20,4) NOT NULL DEFAULT 0,
    opened_at     timestamptz   NOT NULL DEFAULT now(),
    closed_at     timestamptz,
    CONSTRAINT fk_accounts_client
        FOREIGN KEY (client_id) REFERENCES clients (id)
        ON DELETE RESTRICT ON UPDATE CASCADE,
    CONSTRAINT fk_accounts_currency
        FOREIGN KEY (currency_code) REFERENCES currencies (code)
        ON DELETE RESTRICT ON UPDATE CASCADE,
    CONSTRAINT uq_accounts_number UNIQUE (number),
    CONSTRAINT ck_accounts_kind   CHECK (kind IN ('current','savings','card','nostro')),
    CONSTRAINT ck_accounts_closed CHECK (closed_at IS NULL OR closed_at >= opened_at),
    CONSTRAINT ck_accounts_balance_scale CHECK (balance = round(balance, 4))
);

CREATE INDEX ix_accounts_client ON accounts (client_id);   -- FK-индекс вручную

INSERT INTO accounts (client_id, currency_code, number, kind, balance) VALUES
    (1, 'UZS', '20208860100000000001', 'current', 15000000.0000),
    (1, 'USD', '20208840100000000002', 'current',      1250.5000),
    (2, 'UZS', '20208860100000000003', 'current',    340000.0000);

-- 4. Транзакции и проводки: двойная запись.
CREATE TABLE transactions (
    id           bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    external_ref text        NOT NULL,
    kind         text        NOT NULL,
    booked_at    timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT uq_transactions_ref UNIQUE (external_ref),   -- идемпотентность
    CONSTRAINT ck_transactions_kind CHECK (kind IN ('transfer','fee','interest','reversal'))
);

CREATE TABLE entries (
    transaction_id bigint        NOT NULL,
    seq            smallint      NOT NULL,
    account_id     bigint        NOT NULL,
    amount         numeric(20,4) NOT NULL,
    CONSTRAINT pk_entries PRIMARY KEY (transaction_id, seq),
    CONSTRAINT fk_entries_tx
        FOREIGN KEY (transaction_id) REFERENCES transactions (id) ON DELETE RESTRICT,
    CONSTRAINT fk_entries_account
        FOREIGN KEY (account_id) REFERENCES accounts (id) ON DELETE RESTRICT,
    CONSTRAINT ck_entries_nonzero CHECK (amount <> 0)
);

CREATE INDEX ix_entries_account ON entries (account_id, transaction_id);

-- Перевод 100 USD со счёта 2 на счёт 1 (условно, одна валюта).
INSERT INTO transactions (external_ref, kind) VALUES ('ext-2026-08-05-0001', 'transfer');

INSERT INTO entries (transaction_id, seq, account_id, amount) VALUES
    (1, 1, 2, -100.0000),   -- дебет
    (1, 2, 1,  100.0000);   -- кредит

-- Проверка двойной записи: сумма проводок каждой транзакции равна нулю
SELECT transaction_id, sum(amount) AS delta
FROM entries
GROUP BY transaction_id
HAVING sum(amount) <> 0;
-- Ожидаемый результат: 0 строк
```

Балансировку двойной записи `CHECK` выразить не может — он однострочный. В продакшене её обеспечивают либо constraint trigger с `DEFERRABLE INITIALLY DEFERRED` (проверка в момент COMMIT, когда обе строки уже вставлены), либо тем, что все проводки создаёт единственная хранимая процедура. Детали — в [[Транзакции и уровни изоляции]] и [[EF Core: сырой SQL и хранимые процедуры]].

## Как это ложится на классы C#

Каждое отношение становится классом-сущностью, внешние ключи — парой «FK-свойство + навигационное свойство», связи 1:N — коллекцией на стороне «один».

```csharp
public sealed class Client
{
    public long Id { get; init; }                       // суррогатный PK
    public Guid PublicId { get; init; }                 // альтернативный ключ наружу
    public string? TaxId { get; set; }                  // nullable = колонка допускает NULL
    public required string FullName { get; set; }
    public DateOnly BirthDate { get; init; }
    public ClientStatus Status { get; set; }
    public DateTimeOffset CreatedAt { get; init; }
    public DateTimeOffset? DeletedAt { get; set; }      // soft delete

    // Навигация 1:N. Инициализируем, чтобы не ловить NRE до Include.
    public ICollection<Account> Accounts { get; } = new List<Account>();

    // Навигация 1:1
    public ClientKyc? Kyc { get; set; }
}

public sealed class Account
{
    public long Id { get; init; }
    public long ClientId { get; set; }                  // явный FK - удобнее в запросах
    public Client Client { get; set; } = null!;         // обратная навигация

    public required string CurrencyCode { get; set; }
    public Currency Currency { get; set; } = null!;

    public required string Number { get; init; }
    public AccountKind Kind { get; set; }

    public decimal Balance { get; set; }                // именно decimal, не double
    public DateTimeOffset OpenedAt { get; init; }
    public DateTimeOffset? ClosedAt { get; set; }
}
```

Связь M:N в EF Core 10 можно объявить двумя коллекциями без явного класса связи, но как только у связи появляются собственные атрибуты (`role`, `added_at`), таблицу связи описывают отдельной сущностью с составным ключом:

```csharp
public sealed class AccountHolder
{
    public long AccountId { get; init; }
    public Account Account { get; init; } = null!;

    public long ClientId { get; init; }
    public Client Client { get; init; } = null!;

    public required string Role { get; set; }
    public DateTimeOffset AddedAt { get; init; }
}

// Конфигурация составного ключа
modelBuilder.Entity<AccountHolder>()
    .HasKey(x => new { x.AccountId, x.ClientId });
```

Подробности маппинга — в [[EF Core: конфигурация модели и Fluent API]] и [[EF Core: связи и навигационные свойства]]; выбор типа для денег и точность `decimal` разбирает [[PostgreSQL и Npgsql]].

> [!warning] Подводные камни
> - **`CHECK` не ловит NULL.** `CHECK (amount > 0)` пропустит `NULL`, потому что предикат вернёт UNKNOWN, а ограничение считает нарушением только явный FALSE. Всегда пара: `amount numeric(20,4) NOT NULL CHECK (amount > 0)`.
> - **FK не индексируется автоматически.** Ни PostgreSQL, ни SQL Server не создают индекс под внешний ключ. Без него удаление родителя сканирует всю дочернюю таблицу, а JOIN по связи деградирует на росте данных.
> - **`ON DELETE CASCADE` на финансовых сущностях.** Один `DELETE` без `WHERE` в скрипте поддержки уносит историю проводок вместе с транзакциями. Для денег — только `RESTRICT` плюс отобранное право `DELETE` у прикладной роли.
> - **Естественный PK, который «точно не меняется».** Меняется всё: номера счетов при миграции АБС, коды подразделений при реорганизации, ИНН при смене юрлица. Без `ON UPDATE CASCADE` обновление такого ключа падает, с ним — переписывает половину базы под блокировками.
> - **`UNIQUE` и несколько NULL.** `UNIQUE (tax_id)` в PostgreSQL по умолчанию пропустит сколько угодно строк с `tax_id IS NULL`, в SQL Server — ровно одну. Если по бизнесу NULL должен быть один, пиши `NULLS NOT DISTINCT` (PostgreSQL 15+) или фильтрованный индекс.
> - **`MATCH SIMPLE` на составном FK.** Частично заполненный ключ проходит проверку целиком. Для составных FK, где допустимы NULL, явно пиши `MATCH FULL`.
> - **`SELECT *` и порядок колонок.** Позиционная зависимость в `INSERT ... VALUES` без списка колонок и в чтении по индексу ломается после любого `ALTER TABLE`. Перечисляй колонки всегда.

> [!example] Как делают в бою
> - **Именование ограничений — обязательно.** Автогенерируемое `accounts_client_id_fkey` неудобно ловить в коде. Явные `fk_`, `uq_`, `ck_`, `ix_`, `pk_` префиксы позволяют в обработчике исключения различить, какое именно ограничение нарушено: Npgsql кладёт имя в `PostgresException.ConstraintName`, и по нему возвращают конкретную ошибку API вместо «500 Internal Server Error».
> - **Идемпотентность через UNIQUE.** `uq_transactions_ref` на внешнем идентификаторе платежа — самый дешёвый способ не провести один платёж дважды при ретрае вебхука. Повторная вставка падает с кодом `23505`, обработчик отвечает «уже проведено». Подробнее — [[Идемпотентность]].
> - **Деньги как `numeric`, а не как «минорные единицы в bigint».** Оба подхода живут. `bigint` в копейках исключает вопросы округления, но требует хранить `minor_unit` валюты и умножать/делить в каждом месте, а на валютах с 0 и 3 знаками (JPY, KWD) регулярно даёт ошибки. `numeric(20,4)` с явным `CHECK (round(x, 4) = x)` в большинстве финтех-схем удобнее и точен по определению.
> - **Миграции пишут вручную поверх сгенерированных.** EF Core сгенерирует таблицы и FK, но не создаст `EXCLUDE`, частичные индексы и большинство `CHECK`. Их дописывают в миграцию через `migrationBuilder.Sql(...)` — см. [[EF Core: миграции]].
> - **Схему проверяют тестом.** Интеграционный тест на Testcontainers, который поднимает чистый PostgreSQL, накатывает миграции и пробует нарушить каждое ограничение, ловит регрессии схемы раньше прода. См. [[EF Core: тестирование доступа к данным]].

## Вопросы с собеседований

> [!question]- Чем отношение из реляционной модели отличается от таблицы в SQL?
> Отношение — математическое множество кортежей: в нём нет одинаковых элементов, нет порядка элементов и нет порядка атрибутов. Таблица SQL — мультимножество: допускает полные дубликаты строк, имеет фиксированный порядок колонок (поэтому работают `SELECT *` и `INSERT` без списка колонок) и позволяет NULL — маркер, которого в исходной модели нет вовсе. Практический вывод: свойство «нет дубликатов» надо возвращать вручную, объявляя `PRIMARY KEY` на каждой таблице; порядок строк никогда не гарантирован без `ORDER BY`, даже если запрос стабильно возвращает их «как надо» на тестовых данных.

> [!question]- Что такое потенциальный ключ и чем он отличается от первичного? Может ли быть несколько первичных ключей?
> Потенциальный ключ (candidate key) — минимальный набор атрибутов, уникально определяющий строку: убрать хоть один атрибут нельзя без потери уникальности. Потенциальных ключей у таблицы может быть несколько: у `accounts` это `{id}` и `{number}`. Первичный ключ — один из потенциальных, выбранный проектировщиком в качестве основного; он может быть только один на таблицу, и его колонки автоматически `NOT NULL`. Остальные потенциальные ключи объявляют как `UNIQUE` (альтернативные ключи) — они выполняют ту же защитную функцию, но допускают NULL и не служат целью FK по умолчанию.

> [!question]- Естественный или суррогатный ключ — что выбрать и почему?
> Практика для финтеха: суррогатный первичный ключ плюс обязательный `UNIQUE` на естественный бизнес-ключ. Суррогатный (`bigint identity` или `uuid`) стабилен, узкий, не утекает наружу и не требует `ON UPDATE CASCADE` по всей схеме. Естественный ключ (ИНН, номер счёта) рано или поздно меняется, часто широкий и раздувает все индексы, где он встречается как FK. Но выкидывать его нельзя: без `UNIQUE` на бизнес-ключе таблица немедленно набирает дубликаты, потому что суррогатный PK разрешит вставить того же клиента второй раз. Исключение — маленькие стабильные справочники вроде валют: там естественный код ISO лучше суррогата, потому что избавляет от лишнего JOIN.

> [!question]- Почему `ON DELETE CASCADE` считается опасным в финансовой схеме?
> Три причины. Первая — невидимый радиус: разработчик пишет `DELETE FROM transactions WHERE id = 1`, а СУБД молча уносит все связанные проводки, и аудиторский след исчезает без единой записи в логе приложения. Вторая — транзитивность: каскады выстраиваются в цепочку через несколько таблиц, и удаление одной строки может вычистить пол-базы; предсказать это по коду невозможно, только по схеме. Третья — блокировки: каскад захватывает строки в порядке, который выбирает планировщик, что даёт долгие транзакции и дедлоки на горячих таблицах. Для финансовых данных правильно `ON DELETE RESTRICT` плюс soft delete плюс отозванное право `DELETE` у прикладной роли; отмена операции оформляется сторнирующей проводкой.

> [!question]- Как реализовать связь M:N и почему у таблицы связи составной первичный ключ?
> Прямой M:N в реляционной модели нет, её разбивают на две связи 1:N через таблицу связи с двумя внешними ключами. Первичный ключ из этих двух FK даёт сразу две гарантии: пара «счёт-владелец» не продублируется, и появляется B-tree индекс, покрывающий навигацию в одну сторону. Для обратной навигации нужен второй индекс с колонками в противоположном порядке. Суррогатный `id` в таблицу связи добавляют только когда на неё саму нужно ссылаться из третьей таблицы; в остальных случаях он лишний и вдобавок снимает защиту от дублей, если забыть отдельный `UNIQUE`.

> [!question]- В чём разница между `RESTRICT` и `NO ACTION`?
> Обе опции запрещают удаление родителя при наличии ссылок, но отличаются моментом проверки. `RESTRICT` проверяет немедленно, при обработке строки, и не может быть отложен. `NO ACTION` (умолчание по стандарту) проверяет в конце оператора и, если ограничение объявлено `DEFERRABLE INITIALLY DEFERRED`, — в момент `COMMIT`. Это критично для сценариев, где строки временно нарушают целостность внутри транзакции: например, при перестановке ссылок или взаимных FK между двумя таблицами. По умолчанию разница незаметна, поэтому в большинстве схем `NO ACTION` предпочтительнее — он оставляет возможность отложить.

> [!question]- Зачем нужен EXCLUDE, если есть UNIQUE?
> `UNIQUE` — частный случай: он запрещает две строки, у которых указанные колонки *равны*. `EXCLUDE` обобщает это до произвольного оператора: `EXCLUDE USING gist (account_id WITH =, period WITH &&)` запрещает две строки, у которых счёт совпадает и периоды *пересекаются*. Такая проверка невыразима через `UNIQUE` или `CHECK` (последний видит только одну строку), а в приложении корректно реализуется лишь под `SERIALIZABLE` или явной блокировкой — и всё равно даёт гонки при конкурентной вставке. Реализуется через GiST-индекс; для операторов `=` по скалярным типам нужно расширение `btree_gist`. В SQL Server прямого аналога нет.

> [!question]- Почему `CHECK (amount > 0)` не спасает от отрицательного баланса при конкурентных списаниях?
> `CHECK` проверяет одну строку в момент записи, и он действительно не даст записать отрицательное значение — но не решает проблему потерянного обновления. Если два запроса читают баланс 100, каждый вычитает 80 и пишет результат, при `READ COMMITTED` второй перезапишет первый, и итог будет 20 вместо ошибки. `CHECK` тут ни при чём: записываемое значение положительное. Нужна либо атомарная запись `UPDATE accounts SET balance = balance - 80 WHERE id = ? AND balance >= 80` с проверкой числа затронутых строк, либо явная блокировка `SELECT ... FOR UPDATE`, либо оптимистичная блокировка по версии. Подробности — в [[Транзакции и уровни изоляции]] и [[EF Core: транзакции и конкурентность]].

## Задачи

### Задача 1. Один основной владелец на счёт

Дана таблица `account_holders (account_id, client_id, role)` с составным PK. Нужно гарантировать: у счёта может быть сколько угодно владельцев с ролями `joint` и `viewer`, но ровно один с ролью `primary`. Обычный `UNIQUE (account_id)` не подходит — он запретит совместное владение.

> [!success]- Решение
> ```sql
> CREATE UNIQUE INDEX ux_account_holders_primary
>     ON account_holders (account_id)
>     WHERE role = 'primary';
>
> INSERT INTO account_holders (account_id, client_id, role) VALUES (1, 1, 'primary'); -- OK
> INSERT INTO account_holders (account_id, client_id, role) VALUES (1, 2, 'joint');   -- OK
> INSERT INTO account_holders (account_id, client_id, role) VALUES (1, 3, 'viewer');  -- OK
> INSERT INTO account_holders (account_id, client_id, role) VALUES (1, 4, 'primary');
> -- ERROR: duplicate key value violates unique index "ux_account_holders_primary"
> ```
> Частичный уникальный индекс индексирует только те строки, которые удовлетворяют условию `WHERE`. Строки с ролями `joint` и `viewer` в индекс не попадают вовсе, поэтому не конфликтуют между собой. Индекс заодно компактнее полного и быстрее отвечает на запрос «кто основной владелец счёта». Обеспечить «ровно один, а не максимум один» на уровне схемы нельзя — минимальное количество строк ограничением не выражается, это задача транзакционной логики создания счёта.

### Задача 2. Найти висячие ссылки в схеме без FK

Досталась легаси-таблица `entries`, в которой FK на `accounts` никогда не объявляли. Нужно понять масштаб проблемы до того, как добавлять ограничение, а затем добавить его, не блокируя запись надолго.

> [!success]- Решение
> ```sql
> -- 1. Сколько строк ссылаются в никуда
> SELECT count(*)
> FROM entries e
> WHERE NOT EXISTS (SELECT 1 FROM accounts a WHERE a.id = e.account_id);
>
> -- 2. Какие именно идентификаторы битые (для разбора с бизнесом)
> SELECT DISTINCT e.account_id
> FROM entries e
> LEFT JOIN accounts a ON a.id = e.account_id
> WHERE a.id IS NULL
> ORDER BY e.account_id;
>
> -- 3. Добавляем FK в два шага, без долгой блокировки на валидацию
> ALTER TABLE entries
>     ADD CONSTRAINT fk_entries_account
>     FOREIGN KEY (account_id) REFERENCES accounts (id)
>     ON DELETE RESTRICT
>     NOT VALID;                     -- мгновенно: проверяются только новые строки
>
> ALTER TABLE entries VALIDATE CONSTRAINT fk_entries_account;
> -- берёт SHARE UPDATE EXCLUSIVE, не мешает SELECT/INSERT/UPDATE
> ```
> Ключевой приём — `NOT VALID`. Обычный `ADD CONSTRAINT ... FOREIGN KEY` берёт блокировку и сканирует всю таблицу целиком; на таблице проводок в сотни миллионов строк это часы простоя. `NOT VALID` объявляет ограничение сразу — оно начинает работать для новых и изменяемых строк, — а отдельный `VALIDATE CONSTRAINT` проверяет старые данные под гораздо более слабой блокировкой. Обратите внимание на `NOT EXISTS` вместо `NOT IN`: с `NOT IN` и NULL в подзапросе результат был бы пустым (см. [[SQL: SELECT, фильтрация, сортировка]]).

### Задача 3. Спроектировать связь 1:1 с обязательностью на одной стороне

Нужна таблица KYC-анкеты: у клиента может не быть анкеты (до прохождения проверки), но анкета не существует без клиента. Одна анкета на клиента. Удаление клиента запрещено.

> [!success]- Решение
> ```sql
> CREATE TABLE client_kyc (
>     client_id     bigint      PRIMARY KEY
>                   REFERENCES clients (id) ON DELETE RESTRICT,
>     passport_hash bytea       NOT NULL,
>     verified_at   timestamptz NOT NULL,
>     verified_by   text        NOT NULL,
>     risk_level    smallint    NOT NULL,
>     CONSTRAINT ck_client_kyc_risk CHECK (risk_level BETWEEN 1 AND 5),
>     CONSTRAINT ck_client_kyc_hash CHECK (octet_length(passport_hash) = 32)
> );
> ```
> `PRIMARY KEY` и `FOREIGN KEY` совмещены в одной колонке — это и есть каноническая реализация 1:1. PK даёт уникальность («не более одной анкеты»), FK со стороны `NOT NULL` даёт обязательность («анкета не бывает ничья»). Кардинальность получается `clients ||---o| client_kyc`: ноль или одна анкета на клиента. Обратное направление — «клиент обязан иметь анкету» — на уровне схемы выразить нельзя без взаимных отложенных FK, поэтому его контролируют статусом: `clients.status = 'active'` выставляется только после успешной верификации.

### Задача 4. Найти дубликаты по бизнес-ключу и почистить перед добавлением UNIQUE

В `clients` исторически нет ограничения на `tax_id`, и дубликаты уже накопились. Надо оставить самую раннюю запись, остальные пометить удалёнными, затем повесить частичный UNIQUE.

> [!success]- Решение
> ```sql
> -- Помечаем удалёнными все, кроме самой ранней записи в каждой группе
> WITH ranked AS (
>     SELECT id,
>            row_number() OVER (PARTITION BY tax_id ORDER BY created_at, id) AS rn
>     FROM clients
>     WHERE tax_id IS NOT NULL AND deleted_at IS NULL
> )
> UPDATE clients c
> SET deleted_at = now()
> FROM ranked r
> WHERE c.id = r.id AND r.rn > 1;
>
> -- Теперь ограничение накатится
> CREATE UNIQUE INDEX CONCURRENTLY ux_clients_tax_id_alive
>     ON clients (tax_id)
>     WHERE deleted_at IS NULL AND tax_id IS NOT NULL;
>
> -- Контроль: дубликатов среди живых больше нет
> SELECT tax_id, count(*)
> FROM clients
> WHERE deleted_at IS NULL AND tax_id IS NOT NULL
> GROUP BY tax_id HAVING count(*) > 1;
> -- Ожидаемый результат: 0 строк
> ```
> `row_number()` с `PARTITION BY tax_id` нумерует строки внутри каждой группы дубликатов, `ORDER BY created_at, id` делает выбор «первой» детерминированным даже при одинаковых меткам времени (см. [[SQL: оконные функции]]). `CREATE INDEX CONCURRENTLY` строит индекс без блокировки записи — обязателен на живой таблице, но не может выполняться внутри транзакции, поэтому в миграции EF Core его выносят в отдельный шаг с отключённым транзакционным оборачиванием.

## Итог

- Отношение — множество кортежей: без дубликатов и без порядка. SQL-таблица этих свойств не имеет, их возвращают ключами и ограничениями.
- NULL — не значение, а маркер отсутствия; сравнение с ним даёт UNKNOWN. `CHECK` пропускает UNKNOWN, поэтому `NOT NULL` — умолчание при проектировании.
- Ключи: суперключ (любой уникальный набор) → потенциальный (минимальный) → первичный (выбранный) + альтернативные (`UNIQUE`). В финтехе — суррогатный PK плюс `UNIQUE` на бизнес-ключ.
- Внешний ключ обеспечивает ссылочную целостность, но индекс под него нужно создавать вручную. `ON DELETE` для денег — `RESTRICT`, `CASCADE` — только для строго подчинённых несущественных сущностей.
- 1:1 — общий PK/FK; 1:N — FK на стороне «многих»; M:N — таблица связи с составным PK из двух FK.
- `CHECK`, `UNIQUE`, `NOT NULL`, `EXCLUDE` и частичные уникальные индексы — часть модели, а не украшение: проверка в СУБД не обходится ни скриптом поддержки, ни вторым сервисом.
