# Свои типы исключений

> [!abstract] Коротко
> Свой тип исключения нужен ровно тогда, когда вызывающий должен **отличить** эту ситуацию от других и отреагировать на неё иначе. Если реакция одинаковая, хватает существующих типов из BCL. Правила проектирования просты: имя заканчивается на `Exception`, тип `sealed` (если не планируется иерархия), наследование напрямую от `Exception`, три стандартных конструктора, а данные о проблеме — в **свойствах**, а не в тексте сообщения. В новом коде не нужно ни `[Serializable]`, ни конструктор сериализации: этот механизм объявлен устаревшим в .NET 8.

## Зачем это нужно

Разница между «что-то пошло не так» и работающей диагностикой:

```csharp
// Плохо: тип не говорит ничего, данные спрятаны в строке
throw new Exception($"Недостаточно средств: нужно {amount}, есть {balance}");
// Вызывающий вынужден разбирать текст, чтобы понять, что случилось,
// а обработчик на границе не может отличить это от падения базы

// Хорошо: тип различим, данные доступны кодом
throw new InsufficientFundsException(accountId, requested: amount, available: balance);
```

Во втором случае обработчик на границе превращает исключение в 409 с внятным телом, ретрай-политика понимает, что повторять бессмысленно, а тест проверяет конкретные значения, а не подстроку.

---

## Когда свой тип нужен, а когда нет

| Ситуация | Что бросать |
|---|---|
| Аргумент `null` | `ArgumentNullException` |
| Аргумент вне диапазона | `ArgumentOutOfRangeException` |
| Объект в неподходящем состоянии | `InvalidOperationException` |
| Операция не поддерживается | `NotSupportedException` |
| Строка неверного формата | `FormatException` |
| Нарушено доменное правило, и вызывающий реагирует особым образом | **свой тип** |
| Ошибка интеграции, которую надо отличать от прочих | **свой тип** |
| «Просто ошибка», реакция такая же, как у всех | ничего своего — существующий тип |

Проверочный вопрос перед созданием нового типа: **напишет ли кто-нибудь `catch` именно на него?** Если нет — тип не нужен, достаточно подходящего существующего с хорошим сообщением.

Обратная крайность тоже вредна: заводить по типу исключения на каждый код ошибки. Десять почти одинаковых классов, отличающихся только сообщением, никто не различает в `catch`; лучше один тип со свойством-кодом.

## Канонический шаблон

```csharp
public sealed class InsufficientFundsException : Exception
{
    public InsufficientFundsException(long accountId, decimal requested, decimal available)
        : base($"На счёте {accountId} недостаточно средств: запрошено {requested}, доступно {available}")
    {
        AccountId = accountId;
        Requested = requested;
        Available = available;
    }

    // Данные — свойствами: их можно использовать в коде и в логах
    public long AccountId { get; }
    public decimal Requested { get; }
    public decimal Available { get; }
    public decimal Shortfall => Requested - Available;
}
```

Что здесь важно:

- **`sealed`** — если наследование не планируется. Это и подсказка читателю, и мелкая оптимизация проверки типа.
- **Наследование от `Exception`**, а не от `ApplicationException` (устарело) и не от `SystemException` (зарезервировано для рантайма).
- **Данные в свойствах.** Сообщение — для человека, свойства — для кода. Разбирать `Message` регулярным выражением недопустимо.
- **Осмысленное сообщение** с контекстом: идентификаторы, значения, но **без секретов и персональных данных** — сообщение попадёт в логи и, возможно, в трассировку.

Для типов общего назначения полезны стандартные конструкторы — их ожидают инструменты и тесты:

```csharp
public class OrderProcessingException : Exception
{
    public OrderProcessingException() { }
    public OrderProcessingException(string message) : base(message) { }
    public OrderProcessingException(string message, Exception innerException)
        : base(message, innerException) { }
}
```

> [!warning] Сериализация исключений устарела
> В коде и статьях старше .NET 8 встречается такое:
> ```csharp
> [Serializable]
> public class MyException : Exception
> {
>     protected MyException(SerializationInfo info, StreamingContext context) : base(info, context) { }
> }
> ```
> Это наследие `BinaryFormatter`, который удалён из .NET по соображениям безопасности; соответствующие члены `Exception` помечены устаревшими (SYSLIB0051). В новом коде ни атрибут, ни конструктор сериализации не нужны — исключения не пересекают границы процессов в бинарном виде, а между сервисами передаются как данные ответа (`ProblemDetails`), а не как объекты.

## Иерархия исключений модуля

Для крупного модуля полезен один базовый тип: он позволяет поймать «всё наше» одним `catch`, не хватая при этом чужие ошибки.

```csharp
// Базовый — abstract, чтобы его нельзя было бросить напрямую
public abstract class OrdersException(string message, Exception? inner = null)
    : Exception(message, inner);

public sealed class OrderNotFoundException(long orderId)
    : OrdersException($"Заказ {orderId} не найден")
{
    public long OrderId { get; } = orderId;
}

public sealed class OrderAlreadyPaidException(long orderId)
    : OrdersException($"Заказ {orderId} уже оплачен")
{
    public long OrderId { get; } = orderId;
}

// Использование на границе
catch (OrdersException ex)      // все ошибки модуля заказов
{
    logger.LogWarning(ex, "Бизнес-ошибка модуля заказов");
    return Results.BadRequest(ex.Message);
}
```

Правило глубины: два уровня (базовый модуля + конкретные) достаточно почти всегда. Глубокие иерархии исключений никто не использует в `catch`, зато их дорого поддерживать.

Полезная разновидность базового типа — исключение с кодом ошибки, когда вариантов много, а реакция одинаковая:

```csharp
public sealed class DomainException(string code, string message) : Exception(message)
{
    public string Code { get; } = code;      // "order.already_paid", "payment.limit_exceeded"
}
```

Код удобно отдавать клиенту: он стабилен (в отличие от текста), пригоден для локализации на стороне интерфейса и для группировки в мониторинге.

## Бросать удобно: throw-помощники

```csharp
public sealed class OrderNotFoundException(long orderId)
    : Exception($"Заказ {orderId} не найден")
{
    public long OrderId { get; } = orderId;

    // Статический помощник в стиле ArgumentNullException.ThrowIfNull
    public static void ThrowIfNull(Order? order, long orderId)
    {
        if (order is null) throw new OrderNotFoundException(orderId);
    }
}

// В коде это выглядит как одна строка без ветвления
OrderNotFoundException.ThrowIfNull(order, id);
```

Приём полезен ещё и для производительности: метод с `throw` внутри мешает JIT встраивать вызывающий метод, поэтому в горячем коде бросок выносят в отдельный метод, помеченный `[DoesNotReturn]`:

```csharp
[System.Diagnostics.CodeAnalysis.DoesNotReturn]
private static void ThrowClosed(long id) => throw new InvalidOperationException($"Счёт {id} закрыт");
```

Атрибут `[DoesNotReturn]` сообщает компилятору, что после вызова управление не вернётся — это помогает анализу потока для nullable-типов и определённого присваивания.

## Проверка в тестах

```csharp
[Fact]
public void Withdraw_WhenNotEnoughMoney_ThrowsWithDetails()
{
    var account = new Account(id: 1, balance: 100m);

    var ex = Assert.Throws<InsufficientFundsException>(() => account.Withdraw(150m));

    Assert.Equal(1, ex.AccountId);
    Assert.Equal(150m, ex.Requested);
    Assert.Equal(100m, ex.Available);
    Assert.Equal(50m, ex.Shortfall);
}
```

Тест проверяет **свойства**, а не текст сообщения — именно ради этого данные и выносятся в свойства. Тест на подстроку в `Message` ломается при первой же правке формулировки и не проверяет ничего полезного.

> [!warning] Подводные камни
> - **Свой тип «на всякий случай».** Если никто не пишет `catch` на него, он лишь добавляет классов. Проверочный вопрос — будет ли отдельная реакция.
> - **Данные только в сообщении.** Вызывающий вынужден парсить строку; локализация или правка текста ломает логику.
> - **Персональные данные и секреты в сообщении.** Сообщение уходит в логи и трассировку, а иногда и в ответ клиенту.
> - **Наследование от `ApplicationException`.** Устаревшая практика без пользы.
> - **`[Serializable]` и конструктор сериализации.** Механизм объявлен устаревшим в .NET 8, копировать его из старых примеров не нужно.
> - **Исключение вместо результата.** Если «не найдено» — обычный исход поиска, лучше вернуть `null` или Result, а не бросать. См. [[Когда исключение — плохой выбор]].
> - **Потеря `innerException`.** При оборачивании внешней ошибки обязательно передавай исходное исключение вторым аргументом, иначе первопричина исчезнет.
> - **Глубокие иерархии.** Пять уровней наследования исключений не используются в `catch` и только усложняют код.

> [!example] Как делают в бою
> В доменном слое обычно есть один абстрактный базовый тип (`DomainException`) и несколько конкретных для правил, на которые реагируют по-разному. На границе HTTP они раскладываются в коды: `NotFoundException` → 404, конфликт состояния → 409, нарушение правила → 400 с кодом ошибки в теле `ProblemDetails`. Клиент получает стабильный машинный код (`order.already_paid`) и человекочитаемое сообщение, а стек остаётся в логах.
> В инфраструктурном слое исключения внешних библиотек оборачивают в свои: `NpgsqlException` → `OrderStorageException` с исходным исключением внутри. Это не декорация: так домен и прикладной слой не зависят от типов конкретного драйвера, и замена хранилища не требует правок в обработчиках.
> Чего избегают: исключений как способа вернуть результат в ожидаемых сценариях, «универсальных» исключений с кодом на все случаи жизни в домене (там как раз нужны различимые типы) и десятка одинаковых типов там, где хватило бы одного с кодом.

## Вопросы с собеседований

> [!question]- Когда стоит создавать свой тип исключения?
> Когда вызывающий код должен отличить эту ситуацию от остальных и отреагировать на неё иначе: повторить операцию, вернуть конкретный HTTP-код, показать пользователю особое сообщение, откатить бизнес-процесс. Проверочный вопрос — напишет ли кто-нибудь `catch` именно на этот тип; если реакция такая же, как на прочие ошибки, хватает существующего типа из BCL с хорошим сообщением. Второй повод — необходимость передать структурированные данные о проблеме (идентификаторы, суммы, коды), чтобы обработчик и тесты не разбирали текст сообщения. Обратная крайность — заводить класс на каждый код ошибки: если реакция одинаковая, лучше один тип со свойством `Code`. Правило по иерархии: один абстрактный базовый тип на модуль и конкретные под ним — двух уровней достаточно.

> [!question]- Как правильно оформить свой класс исключения?
> Имя с суффиксом `Exception`, наследование напрямую от `System.Exception` (не от `ApplicationException` — она устарела и бесполезна, и не от `SystemException` — она зарезервирована рантаймом), тип `sealed`, если наследование не планируется. Стандартные конструкторы: без параметров, с сообщением и с сообщением плюс `innerException` — последний обязателен, если исключение когда-либо оборачивает чужое. Данные о проблеме выносятся в свойства только для чтения, а сообщение формируется из них и предназначено человеку; секретов и персональных данных в нём быть не должно. `[Serializable]` и конструктор `(SerializationInfo, StreamingContext)` в новом коде не нужны: этот механизм привязан к удалённому `BinaryFormatter` и помечен устаревшим в .NET 8. Полезное дополнение — статический throw-помощник и атрибут `[DoesNotReturn]` на методах, которые всегда бросают.

## Задачи

### Задача 1. Спроектировать исключение

Сервис оплаты должен сообщать о превышении дневного лимита так, чтобы API мог вернуть 409 с указанием оставшейся суммы и времени сброса лимита.

> [!success]- Решение
> ```csharp
> public sealed class DailyLimitExceededException : Exception
> {
>     public DailyLimitExceededException(long customerId, decimal requested, decimal remaining,
>                                        DateTimeOffset resetsAt)
>         : base($"Дневной лимит исчерпан: запрошено {requested}, доступно {remaining}")
>     {
>         CustomerId = customerId;
>         Requested = requested;
>         Remaining = remaining;
>         ResetsAt = resetsAt;
>     }
>
>     public long CustomerId { get; }
>     public decimal Requested { get; }
>     public decimal Remaining { get; }
>     public DateTimeOffset ResetsAt { get; }
> }
>
> // На границе HTTP
> catch (DailyLimitExceededException ex)
> {
>     return Results.Conflict(new ProblemDetails
>     {
>         Status = StatusCodes.Status409Conflict,
>         Title = "Дневной лимит исчерпан",
>         Extensions =
>         {
>             ["code"] = "payment.daily_limit_exceeded",
>             ["remaining"] = ex.Remaining,
>             ["resetsAt"] = ex.ResetsAt
>         }
>     });
> }
> ```
> Все данные, нужные клиенту, лежат в свойствах — обработчику не приходится ничего вычислять или разбирать. Машинный код ошибки (`payment.daily_limit_exceeded`) добавлен в ответ, а не в тип: он стабилен для клиента и не зависит от переименования класса. Идентификатор клиента в ответ **не** попадает — он есть в исключении для логов, но наружу отдаётся только то, что клиент и так знает.

### Задача 2. Найти проблемы

```csharp
[Serializable]
public class MyAppException : ApplicationException
{
    public MyAppException(string msg) : base(msg) { }
}

// использование
throw new MyAppException($"Ошибка обработки заказа {order.Id} клиента {order.Customer.Email}");
```

> [!success]- Решение
> Проблем четыре. `[Serializable]` для исключения — наследие `BinaryFormatter`, механизм объявлен устаревшим в .NET 8 и не нужен. Наследование от `ApplicationException` — устаревшая практика, наследовать надо от `Exception`. Нет конструктора с `innerException`, значит при оборачивании внешней ошибки первопричина потеряется. И самое серьёзное: в сообщение попал email клиента — персональные данные, которые уедут в логи, в трассировку и потенциально в ответ API.
> ```csharp
> public sealed class OrderProcessingException : Exception
> {
>     public OrderProcessingException(long orderId, string message, Exception? inner = null)
>         : base(message, inner) => OrderId = orderId;
>
>     public long OrderId { get; }
> }
>
> throw new OrderProcessingException(order.Id, $"Не удалось обработать заказ {order.Id}", inner);
> ```
> Идентификатор заказа достаточен для диагностики: по нему в базе находится всё остальное, включая клиента, — и при этом персональные данные не размазываются по логам.

## Итог

- Свой тип нужен, только если кто-то напишет `catch` именно на него или потребуются структурированные данные об ошибке.
- Наследование от `Exception`, суффикс `Exception` в имени, `sealed` по умолчанию.
- Три стандартных конструктора; конструктор с `innerException` обязателен при оборачивании.
- Данные — в свойствах, сообщение — для человека; разбор `Message` кодом недопустим.
- Ни секретов, ни персональных данных в сообщении: оно попадает в логи и трассировку.
- `[Serializable]` и конструктор сериализации устарели в .NET 8 — в новом коде не нужны.
- Иерархия: один абстрактный базовый тип на модуль плюс конкретные; глубже не нужно.
- Тесты проверяют свойства исключения, а не текст сообщения.
