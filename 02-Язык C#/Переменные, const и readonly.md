# Переменные, const и readonly

> [!abstract] Коротко
> Переменная — это именованная ячейка (в стеке, в объекте на куче или в статической области), у которой есть тип, область видимости и время жизни. C# требует, чтобы локальная переменная была *определённо присвоена* до первого чтения, а поля класса компилятор обнуляет сам. `const` — это compile-time значение, которое физически инлайнится в IL вызывающего кода со всеми вытекающими проблемами версионирования; `readonly` — runtime-константа, которая живёт как настоящее поле и читается через `ldfld`/`ldsfld`.
> Понимание разницы между этими двумя словами — граница между «знаю синтаксис» и «понимаю, что происходит в сборке».

## Зачем это нужно

Переменные кажутся темой первого дня, но именно на них строятся три вещи, которые ломают прод у мидлов:

1. **Версионирование библиотек.** `public const` в публичном API NuGet-пакета — это скрытая бомба: значение вшивается в сборку потребителя и не меняется при обновлении пакета.
2. **Иммутабельность.** `readonly` не делает объект неизменяемым — он замораживает только ссылку. Половина «иммутабельных» доменных моделей в реальных проектах иммутабельны только на бумаге.
3. **Производительность структур.** `readonly` на поле-структуре без `readonly struct` заставляет компилятор делать защитные копии на каждом вызове метода. Это тихая, невидимая в коде потеря, которую находят только профайлером.

Плюс к этому — правила определённого присваивания (definite assignment), которые отличают C# от C: там чтение мусора из неинициализированной переменной легально, здесь это ошибка компиляции.

## Объявление, категории и область видимости

Переменная в C# — это место хранения (storage location) с типом. Категорий пять, и они различаются тем, *где* лежат и *кто* их инициализирует.

| Категория | Где хранится | Автоинициализация нулём | Время жизни |
|---|---|---|---|
| Локальная переменная | стек (или регистр после JIT) | нет — CS0165 | до конца блока |
| Параметр метода | стек / регистр | приходит извне | до конца метода |
| Поле экземпляра | внутри объекта на куче | да | пока жив объект |
| Статическое поле | Loader Heap (статическая область типа) | да | пока жив AssemblyLoadContext |
| Элемент массива | внутри объекта-массива на куче | да | пока жив массив |

Подробнее о том, что реально попадает на стек, а что на кучу — [[Стек и куча: что где лежит]] и [[Value types vs Reference types]].

```csharp
public class Basket
{
    private int _count;                    // поле экземпляра: 0 без явного присваивания
    private static int _totalBaskets;      // статическое поле: 0
    private readonly int[] _slots = new int[4]; // элементы массива: 0, 0, 0, 0

    public void Add(int amount)            // amount — параметр
    {
        int newCount = _count + amount;    // локальная переменная
        _count = newCount;
        Console.WriteLine($"{_count} {_slots[0]} {_totalBaskets}");
        // Вывод при первом Add(5): 5 0 0
    }
}
```

### Scope и затенение (shadowing)

Область видимости локальной переменной — блок, в котором она объявлена, начиная с точки объявления. Но C# использует более строгое понятие: **local variable declaration space**. Внутри одного пространства объявлений имя должно быть уникальным, и вложенный блок наследует пространство внешнего.

```csharp
void Demo()
{
    int x = 1;
    {
        // int x = 2;  // CS0136: имя x уже используется в объемлющей области
        x = 2;         // а это нормально — то же самое x
    }
    Console.WriteLine(x); // Вывод: 2
}
```

Что важно: **порядок строк не имеет значения**. Конфликт возникает по пространству объявлений, а не «сверху вниз».

```csharp
void Reverse()
{
    {
        int y = 2;     // CS0136 будет здесь
        Console.WriteLine(y);
    }
    int y = 1;         // объявление ниже, но конфликт всё равно есть
    Console.WriteLine(y);
}
```

Причина запрета — читаемость и защита от опечаток. В C++ и Java внутреннее объявление легально затеняет внешнее, и это классический источник багов. Авторы C# решили, что «два разных `x` в соседних строках» — не та выразительность, за которую стоит платить.

А вот **поле** локальная переменная или параметр затеняют совершенно спокойно — для этого и существует `this`:

```csharp
public class Order
{
    private decimal _total;

    public void SetTotal(decimal _total)   // параметр затеняет поле
    {
        this._total = _total;              // без this присвоили бы параметр сам себе
    }
}
```

## Definite assignment: определённое присваивание

Компилятор C# проводит анализ потока данных (data flow analysis) и на каждой точке программы знает, находится ли локальная переменная в состоянии «определённо присвоена» или «не присвоена». Читать «не присвоенную» — ошибка CS0165.

```csharp
int a;
Console.WriteLine(a);   // CS0165: использование локальной переменной "a", которой не присвоено значение
```

**Почему поля так не проверяются?** Потому что CLR гарантирует, что вся память под объект обнуляется при аллокации (`newobj` выдаёт зачищенный блок), а под статические поля — при инициализации типа. Компилятору нечего доказывать: значение всегда есть, просто оно `default`. Для локальных такой гарантии нет: JIT имеет право не эмитить `.locals init` (при `[SkipLocalsInit]`), и в стековом слоте окажется мусор от предыдущего кадра. Проверка компилятора — единственное, что стоит между вами и чтением мусора.

### Ветвления и анализ потока

```csharp
int x;
if (DateTime.Now.Second % 2 == 0)
    x = 1;
Console.WriteLine(x);   // CS0165: есть путь исполнения, где x не присвоен
```

Компилятор рассуждает по путям: переменная определённо присвоена после `if` только если она присвоена **и** в then-ветке, **и** в else-ветке. Нет else — есть путь без присваивания. Исправляется либо `else x = 0;`, либо инициализацией при объявлении.

А вот это компилируется:

```csharp
int x;
if (true)
    x = 1;
Console.WriteLine(x);   // Вывод: 1
```

Спецификация отдельно оговаривает случай константного условия: если выражение — константа `true`, то состояние после `if` равно состоянию после then-ветки, потому что else-ветка недостижима. Тот же механизм работает для `while (true)` без `break` — код после цикла считается недостижимым, и всё, что там объявлено, компилятор не проверяет.

> [!info] Практическое следствие
> `#if DEBUG` и `const bool EnableFeature = false;` дают компилятору константное условие. Тело такого `if` не попадёт в IL вообще (dead code elimination на уровне компилятора), но проверяется на синтаксис и типы. Это способ держать отладочный код скомпилированным, но не оплаченным.

### out-параметры

`out` — это обещание: метод обязан присвоить параметр на **каждом** пути выхода, включая ветку с `return false`.

```csharp
static bool TryParseAge(string? s, out int age)
{
    if (int.TryParse(s, out age) && age is >= 0 and < 150)
        return true;

    age = 0;      // обязательно: без этой строки CS0177 на пути return false
    return false;
}

// В вызывающем коде переменная считается присвоенной сразу после вызова:
if (TryParseAge("42", out int parsed))
    Console.WriteLine(parsed);   // Вывод: 42
```

Тонкость: `out` не обязан быть присвоен *до* чтения внутри метода — читать `age` до присваивания нельзя, это та же CS0165. `int.TryParse(s, out age)` работает потому, что передача по `out` — это запись, а не чтение.

## var и вывод типа

`var` — это **статическая типизация**. Компилятор выводит тип из инициализатора и подставляет его; в IL нет никакого следа от `var`. Это не `dynamic` и не «переменная любого типа».

```csharp
var count = 42;               // int
var name = "Alif";            // string
var items = new List<int>();  // List<int>
// count = "нет";             // CS0029: нельзя преобразовать string в int
```

Где `var` использовать нельзя и почему:

| Ситуация | Почему запрещено |
|---|---|
| `var x;` | нечего выводить — нет инициализатора |
| `var x = null;` | у `null` нет типа (CS0815) |
| поле класса | вывод типа поля создал бы циклические зависимости при разрешении типов |
| параметр метода | сигнатура должна быть известна до анализа тел методов |
| возвращаемый тип метода | то же — сигнатура часть публичного контракта |
| `var x = (a, b) => a + b;` | лямбда без контекста не имеет естественного типа |

С C# 10 у лямбд и групп методов появился естественный тип, поэтому `var f = () => 42;` (это `Func<int>`) работает, если перегрузка однозначна.

### Target-typed new — зеркало var

C# 9 добавил `new()` без указания типа: тип берётся из целевого. Это ровно противоположная `var` операция — там тип «слева выводится из справа», здесь «справа выводится из слева».

```csharp
// Раньше (C# 8 и ниже) — дублирование имени типа:
private readonly Dictionary<string, List<int>> _map = new Dictionary<string, List<int>>();

// Сейчас (C# 9+) — единственное упоминание типа:
private readonly Dictionary<string, List<int>> _map2 = new();

// var здесь не помог бы: для полей var запрещён.
```

| Приём | Тип пишется | Работает для полей | Когда предпочесть |
|---|---|---|---|
| `var x = new Foo();` | справа | нет | локальные, тип очевиден из правой части |
| `Foo x = new Foo();` | дважды | да | почти никогда — шум |
| `Foo x = new();` | слева | да | поля, свойства, параметры по умолчанию, длинные дженерики |

Практическое правило команды: `var` — когда тип виден в той же строке (`new`, каст, литерал); явный тип — когда правая часть это вызов метода с неочевидным возвратом (`var result = _repo.Find(id);` — что это, `Order`, `Order?`, `Task<Order>`?).

## const: compile-time константа

`const` — это не «поле, которое нельзя менять». Это именованный литерал. Он:

- обязан быть инициализирован выражением, вычислимым во время компиляции;
- **неявно `static`** (написать `static const` — CS0504);
- не имеет адреса — к нему нельзя применить `ref`, `out`, `in`;
- **инлайнится в IL каждого места использования**.

Допустимые типы: все встроенные числовые, `char`, `bool`, `string`, любой `enum`, а также любой ссылочный тип со значением `null`.

```csharp
public static class Limits
{
    public const int MaxRetries = 3;
    public const string DefaultCulture = "ru-RU";
    public const double GoldenRatio = 1.618033988749895;
    public const FileMode Mode = FileMode.Open;      // enum можно
    public const string? Nothing = null;             // null для ссылочного типа можно

    // public const DateTime Epoch = new DateTime(1970, 1, 1);  // CS0133: не compile-time
    // public const int[] Empty = [];                           // CS0134: только null
}

// Локальные const тоже бывают — они вообще не занимают места:
void Work()
{
    const int BatchSize = 500;
    Console.WriteLine(BatchSize);   // Вывод: 500
}
```

> [!info] Исключение — decimal
> `const decimal` формально разрешён, но `decimal` не является примитивом CLR и не может быть IL-литералом. Компилятор эмитит `initonly`-поле, помеченное `[DecimalConstantAttribute]`, а Roslyn при чтении атрибута всё равно инлайнит значение у потребителя. То есть с точки зрения версионирования `const decimal` ведёт себя как обычный `const` — со всеми его проблемами.

### Что реально попадает в IL

```csharp
// Библиотека LibA
public static class Config
{
    public const int MaxRetries = 3;
    public static readonly int MaxRetriesSafe = 3;
}

// Приложение AppB
Console.WriteLine(Config.MaxRetries);
Console.WriteLine(Config.MaxRetriesSafe);
```

IL приложения `AppB`:

```
// Console.WriteLine(Config.MaxRetries);
IL_0000:  ldc.i4.3                                            // тройка ВШИТА в AppB.dll
IL_0001:  call       void [System.Console]System.Console::WriteLine(int32)

// Console.WriteLine(Config.MaxRetriesSafe);
IL_0006:  ldsfld     int32 LibA.Config::MaxRetriesSafe         // читаем поле из LibA во время выполнения
IL_000b:  call       void [System.Console]System.Console::WriteLine(int32)
```

Разница в одну инструкцию — и в целый класс багов. Подробнее об устройстве IL — [[Сборки, метаданные и IL]].

## readonly: runtime-константа

`readonly` поле можно присвоить только в двух местах: в инициализаторе объявления и в конструкторе того же типа (для `static readonly` — в статическом конструкторе). Во всём остальном коде оно только для чтения.

```csharp
public sealed class HttpRetryPolicy
{
    public static readonly HttpRetryPolicy Default = new(3, TimeSpan.FromSeconds(2));

    private readonly int _maxAttempts;
    private readonly TimeSpan _delay;
    private readonly List<string> _log = new();      // ссылка заморожена, содержимое — нет

    public HttpRetryPolicy(int maxAttempts, TimeSpan delay)
    {
        _maxAttempts = maxAttempts;                  // можно: конструктор
        _delay = delay;
    }

    public void Record(string message)
    {
        _log.Add(message);                           // РАБОТАЕТ: мутируем объект, не ссылку
        // _log = new List<string>();                // CS0191: нельзя присвоить readonly вне конструктора
        Console.WriteLine($"{_log.Count} {_maxAttempts} {_delay.TotalSeconds}");
        // Вывод после первого Record: 1 3 2
    }
}
```

В IL `readonly`-поле помечается флагом `initonly`. Читается как обычное поле — `ldfld` для экземплярного, `ldsfld` для статического. CLR проверяет `initonly` только при верификации: присвоить его через рефлексию (`FieldInfo.SetValue`) на .NET Core/.NET 5+ уже нельзя — бросается `FieldAccessException`.

## Сводная таблица: const, static readonly, readonly, init

| Признак | `const` | `static readonly` | `readonly` (экземпляр) | `init`-свойство |
|---|---|---|---|---|
| Когда вычисляется | компиляция | статический конструктор / первое обращение | конструктор экземпляра | инициализатор объекта или конструктор |
| Инлайнится у потребителя | **да** | нет | нет | нет |
| Допустимые типы | примитивы, `string`, `enum`, `null` | любые | любые | любые |
| Неявно static | да | — | нет | нет |
| Устойчиво к обновлению библиотеки | **нет** | да | да | да |
| Доступ через экземпляр | нет (CS0176) | нет | да | да |
| Можно взять `ref`/`in` | нет | да | да | нет (это свойство) |
| Стоимость чтения | ноль (литерал) | `ldsfld` + проверка init типа | `ldfld` | вызов геттера (обычно инлайнится JIT) |
| Типичное применение | вечные значения, атрибуты, `case`-метки, размеры массивов | конфиг библиотеки, синглтоны, кешированные объекты | зависимости класса, поля-состояние | DTO, доменные объекты, `record` |

Мелочь, о которой спрашивают: `const` и `static readonly` можно использовать в `case`-метках `switch`? Только `const` — `case` требует константного паттерна. Так же и с параметрами по умолчанию (`void F(int n = Limits.MaxRetries)`) и с аргументами атрибутов. Про `init` и `record` — [[Записи (record) и структуры]] и [[Иммутабельность как приём проектирования]].

## readonly struct и readonly-члены

Структура, помеченная `readonly struct` (C# 7.2), обязана иметь все поля `readonly` (и автосвойства без сеттеров). Это контракт, который компилятор использует для оптимизации.

```csharp
public readonly struct Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(decimal amount, string currency) => (Amount, Currency) = (amount, currency);

    public Money Add(in Money other)
    {
        if (Currency != other.Currency) throw new InvalidOperationException("разные валюты");
        return new Money(Amount + other.Amount, Currency);
    }
}
```

C# 8 добавил `readonly` на **отдельные члены** — для случаев, когда сделать всю структуру readonly нельзя (например, есть кешируемое поле):

```csharp
public struct Segment
{
    public int Start;
    public int End;

    public readonly int Length => End - Start;                       // readonly-свойство
    public readonly override string ToString() => $"[{Start}, {End})"; // readonly-метод
    public void Shift(int delta) { Start += delta; End += delta; }   // мутирующий — без readonly
}
```

Зачем помечать `ToString`? Потому что `object.ToString()` не readonly, и без явного модификатора компилятор при вызове на readonly-контексте сделает копию.

### Defensive copy: механика тихой потери

Когда компилятор видит вызов **не-readonly** метода структуры на readonly-месте (readonly-поле, `in`-параметр, `ref readonly` локальная, статическое readonly поле), он не имеет права передать адрес: метод потенциально изменит поля и нарушит readonly. Вместо `ldflda` (адрес поля) он эмитит `ldfld` (копию значения), кладёт копию во временную локальную и вызывает метод на ней.

```csharp
public struct Counter
{
    private int _value;
    public int Value => _value;
    public void Increment() => _value++;   // НЕ readonly
}

public class Service
{
    private readonly Counter _counter = new();

    public void Run()
    {
        _counter.Increment();
        _counter.Increment();
        Console.WriteLine(_counter.Value);   // Вывод: 0  (мутации ушли во временные копии)
    }
}
```

Компилируется без единого предупреждения от компилятора. Два эффекта:

1. **Логическая ошибка**: инкременты потерялись. В отладчике всё выглядит нормально, пока не посмотришь итог.
2. **Производительность**: на каждый вызов — копирование `sizeof(T)` байт. Для `Money` (16 + 8 = 24 байта) это ещё терпимо, для структуры на 128 байт в горячем цикле это уже заметно в профайлере.

Как ловить: включить анализатор — `<EnableNETAnalyzers>true</EnableNETAnalyzers>` и правило **CA1067/IDE0250** («сделать структуру readonly»), плюс явный ручной аудит структур больше 16 байт. Как чинить: `readonly struct`, либо `readonly` на конкретных членах, либо не делать поле-структуру readonly, если она обязана мутировать.

## in, ref readonly и scoped

Большие структуры дорого копировать при передаче в метод. `in` (C# 7.2) передаёт по ссылке, но запрещает запись.

```csharp
public readonly struct Matrix4 { /* 16 float = 64 байта */ public readonly float M00; }

static float Trace(in Matrix4 m) => m.M00;   // передаётся адрес, не 64 байта

var matrix = new Matrix4();
Console.WriteLine(Trace(matrix));      // модификатор в точке вызова не нужен
Console.WriteLine(Trace(in matrix));   // но можно написать явно
Console.WriteLine(Trace(new Matrix4())); // rvalue разрешён — компилятор создаст временную
```

C# 12 добавил `ref readonly` параметры. Семантика на стороне вызываемого та же (читать можно, писать нельзя), но требования к вызову строже.

| Признак | `in T p` | `ref readonly T p` | `ref T p` |
|---|---|---|---|
| Модификатор обязателен в точке вызова | нет | да (`ref` или `in`), иначе предупреждение CS9192 | да |
| Можно передать rvalue / литерал | да | предупреждение CS9193 | нет, ошибка |
| Можно писать внутри метода | нет | нет | да |
| Смысл, который выражает | «мне хватит копии, но не копируй ради скорости» | «мне нужна именно эта переменная, я её не трогаю» | «я её изменю» |

`ref readonly` появился как раз для того, чтобы можно было мигрировать старые `ref`-API на «только чтение», не ломая вызывающий код: `ref` в точке вызова остаётся валидным. Замена `ref` на `in` этого не даёт — `in`-параметр в существующих API читается как «а вдруг тут временная копия».

Локальные и возвраты тоже бывают `ref readonly`:

```csharp
int[] data = [10, 20, 30];
ref readonly int first = ref data[0];
Console.WriteLine(first);   // Вывод: 10
// first = 99;              // CS8331: нельзя присвоить через ref readonly
```

`scoped` (C# 11) ограничивает время жизни ссылки: `scoped ref` обещает, что ссылка не «убежит» за пределы метода. Это позволяет компилятору разрешить конструкции со `stackalloc` и `Span<T>`, которые иначе были бы отвергнуты анализом ref safety — см. [[Span, ReadOnlySpan и Memory]]. В C# 14 модификаторы `ref`, `out`, `in`, `scoped` и `ref readonly` разрешены у параметров лямбд **без указания типа**:

```csharp
var read = (ref readonly int x) => x * 2;   // C# 14: тип у x можно было бы опустить в контексте делегата
```

## ref-локальные и ref-возвраты

`ref`-локальная — это псевдоним для чужой ячейки, а не копия значения.

```csharp
int[] arr = [1, 2, 3, 4, 5];
ref int slot = ref arr[3];
slot = 42;
Console.WriteLine(arr[3]);   // Вывод: 42
```

`ref`-возврат позволяет отдать наружу ссылку на элемент коллекции без копирования:

```csharp
static ref int FindFirst(int[] data, Func<int, bool> predicate)
{
    for (int i = 0; i < data.Length; i++)
        if (predicate(data[i]))
            return ref data[i];
    throw new InvalidOperationException("не найдено");
}

int[] scores = [5, 12, 7];
ref int found = ref FindFirst(scores, v => v > 10);
found *= 2;
Console.WriteLine(scores[1]);   // Вывод: 24
```

На этом механизме построены `CollectionsMarshal.GetValueRefOrAddDefault` и `Span<T>.this[int]` — способ обновить значение в словаре за один поиск вместо двух. Подробности про аллокации и обходы — [[Аллокации и как их избегать]].

## Инициализаторы полей против конструктора

Порядок инициализации при наследовании — классический вопрос собеседования, и он неинтуитивен: **инициализаторы полей производного класса выполняются ДО конструктора базового**.

```csharp
class Base
{
    protected string _fromBase = Log("1. Инициализатор поля Base");
    public Base() => Log("2. Тело конструктора Base");
    protected static string Log(string msg) { Console.WriteLine(msg); return msg; }
}

class Derived : Base
{
    private string _fromDerived = Log("0. Инициализатор поля Derived");
    public Derived() => Log("3. Тело конструктора Derived");
}

_ = new Derived();
// Вывод:
// 0. Инициализатор поля Derived
// 1. Инициализатор поля Base
// 2. Тело конструктора Base
// 3. Тело конструктора Derived
```

Механика простая: компилятор вставляет код инициализаторов полей в начало каждого конструктора класса — **до** вызова `base(...)`. Поэтому цепочка выглядит так: инициализаторы Derived, затем `base()`, внутри которого инициализаторы Base, затем тело Base, и только потом тело Derived.

Практическое следствие — **инициализатор поля не может обращаться к `this`**:

```csharp
class Broken
{
    private int _a = 5;
    // private int _b = _a + 1;              // CS0236: инициализатор поля ссылается на нестатическое поле
    // private int _c = Compute();           // CS0236: и на нестатический метод тоже
    private int _d = StaticCompute();        // а статический метод можно

    private int Compute() => 1;
    private static int StaticCompute() => 1;
}
```

Запрет логичен: на момент выполнения инициализатора объект ещё не сконструирован, базовый конструктор не отработал, инварианты не установлены. Если нужно вычислять поле от другого поля — делайте это в конструкторе, там порядок под вашим контролем. Разбор конструкторов целиком — [[Конструкторы и инициализация]].

## Статические поля и beforefieldinit

Статические поля инициализируются при инициализации типа. Момент этой инициализации зависит от одного флага в метаданных.

- **Есть только инициализаторы статических полей, нет явного `static` конструктора** → компилятор помечает тип флагом `beforefieldinit`. CLR обещает лишь «до первого обращения к статическому полю», но вправе сделать это сильно раньше — например, при JIT-компиляции метода. Проверок при каждом обращении нет, доступ максимально быстрый.
- **Есть явный `static Foo() { }`** → флага нет. CLR обязана инициализировать тип **точно** перед первым обращением к любому статическому члену или созданием экземпляра. Это добавляет проверку инициализации (обычно JIT её выносит из горячего пути, но не всегда) и делает момент детерминированным.

```csharp
static class Fast   // beforefieldinit: может инициализироваться раньше, чем вы думаете
{
    public static readonly int Value = Compute("Fast");
    private static int Compute(string who) { Console.WriteLine($"init {who}"); return 1; }
}

static class Precise  // без beforefieldinit из-за явного статического конструктора
{
    public static readonly int Value;
    static Precise() { Console.WriteLine("init Precise"); Value = 1; }
}
```

Практика: если статическая инициализация имеет побочные эффекты (чтение конфигурации, открытие соединения, регистрация в реестре), пишите явный статический конструктор — иначе порядок непредсказуем. Если это просто кеш значений — не пишите, оставьте `beforefieldinit` и его нулевую стоимость. CLR гарантирует потокобезопасность инициализации типа в обоих случаях, но при `beforefieldinit` порядок между разными типами не определён. Полный разбор — [[Статические члены, классы и конструкторы]].

## Ключевое слово field (C# 14)

C# 14 позволяет обратиться к автогенерируемому backing field прямо из аксессора — раньше ради одной строчки валидации приходилось писать поле руками.

```csharp
public class Customer
{
    // Раньше (C# 13 и ниже):
    // private string _name = "";
    // public string Name { get => _name; set => _name = value?.Trim() ?? ""; }

    // Сейчас (C# 14):
    public string Name { get => field; set => field = value?.Trim() ?? ""; }
}
```

Компилятор создаёт скрытое поле, доступное только внутри аксессоров. Обратите внимание: `field` — контекстное ключевое слово, и если у вас в классе есть переменная с именем `field`, приоритет у неё (с предупреждением). Подробнее — [[Свойства и field-backed properties]] и [[Новое в C# 12, 13, 14]].

> [!warning] Подводные камни
>
> **1. `public const` в публичном API библиотеки — бомба замедленного действия.**
> Разберём по шагам. Библиотека `Alif.Http` версии 1.0 объявляет:
> ```csharp
> namespace Alif.Http;
> public static class RetryDefaults { public const int MaxRetries = 3; }
> ```
> Приложение `PaymentGateway` использует `RetryDefaults.MaxRetries` и компилируется. В его IL стоит `ldc.i4.3` — тройка физически скопирована в `PaymentGateway.dll`. Ссылки на `RetryDefaults` в этом месте вообще нет.
> Выходит `Alif.Http` 1.1 с `MaxRetries = 5`. DevOps подкладывает новую dll рядом (или NuGet подтягивает её транзитивно как зависимость другого пакета) — **без перекомпиляции `PaymentGateway`**. Приложение продолжает ретраить 3 раза. В логах библиотеки написано «политика: 5 попыток», в поведении — 3. Такие расследования занимают дни.
> Хуже всего с транзитивными зависимостями: NuGet поднимает версию пакета автоматически по правилам разрешения (см. [[NuGet: пакеты, версии, транзитивные зависимости]]), а ваш код при этом никто не пересобирает.
> **Решение:** в публичном API библиотек используйте `public static readonly` — тогда потребитель эмитит `ldsfld` и читает актуальное значение из новой сборки. `const` оставляйте для: (а) `private`/`internal` значений внутри одной сборки, (б) по-настоящему вечных величин (`Math.PI`, `int.MaxValue`, `"\r\n"`), (в) мест, где `const` синтаксически обязателен — метки `case`, значения по умолчанию у параметров, аргументы атрибутов, размеры буферов в `stackalloc`.
> Цена решения: одно обращение к памяти вместо литерала. В 99,9 % кода это не измеримо; в оставшихся 0,1 % JIT всё равно часто промоутит `static readonly` в константу после инициализации типа.
>
> **2. `readonly` на ссылочном поле не делает объект неизменяемым.**
> `readonly List<int> _items` защищает только слот со ссылкой. `_items.Add(5)`, `_items.Clear()`, `_items[0] = 7` — всё это компилируется и работает. Ваш «иммутабельный» класс, который отдаёт `_items` наружу через свойство, позволяет любому вызывающему коду переписать состояние.
> **Решение:** тип-обёртка, а не модификатор. `ImmutableArray<T>`, `FrozenSet<T>`, `ReadOnlyCollection<T>` через `_items.AsReadOnly()` или хотя бы возврат `IReadOnlyList<T>` (последнее — не защита, а соглашение: приведение обратно к `List<T>` никто не запретит).
>
> **3. Defensive copy у структур.**
> Не-readonly структура в `readonly`-поле, в `in`-параметре или в `ref readonly` локальной копируется целиком при каждом вызове любого не-readonly члена — включая унаследованные `ToString()`, `Equals()`, `GetHashCode()`, если они не переопределены с модификатором `readonly`. Ни ошибки, ни предупреждения от компилятора нет. Мутации теряются молча, а профайлер показывает необъяснимые `memcpy` в горячем пути.
> **Решение:** делайте структуры `readonly struct` по умолчанию; если нельзя — помечайте `readonly` все немутирующие члены, включая `override`-ы.
>
> **4. `const string` в атрибутах и `switch` — единственный вариант, но помните про пункт 1.**
> `[Obsolete(Messages.Deprecated)]` требует `const`. Значит, изменение текста в библиотеке не долетит до уже скомпилированных потребителей. Это обычно приемлемо — но знайте, что происходит.

> [!example] Как делают в бою
>
> **Публичные константы библиотеки.** Всё, что торчит наружу из NuGet-пакета и теоретически может измениться, объявляется как `public static readonly`. `const` в публичном API проходит code review только с обоснованием «это значение не изменится никогда» (номер версии протокола, магическое число формата файла).
>
> **Поля-зависимости — всегда `readonly`.** Инъекция через конструктор пишется как `private readonly IOrderRepository _repo;`. Это не микрооптимизация, а защита: невозможно случайно переприсвоить зависимость в середине метода. Анализатор IDE0044 («сделать поле readonly») включают в CI как error — он находит поля, которые де-факто присваиваются только в конструкторе.
> ```csharp
> public sealed class OrderService(IOrderRepository repo, TimeProvider clock)
> {
>     // Primary constructor (C# 12) захватывает параметры в скрытые поля,
>     // но они НЕ readonly. Если нужна гарантия — объявите поля явно:
>     private readonly IOrderRepository _repo = repo;
>     private readonly TimeProvider _clock = clock;
> }
> ```
>
> **Кеш через `static readonly`.** Скомпилированные регулярки, `JsonSerializerOptions`, `HttpClient`, массивы-справочники — всё это `static readonly`, инициализируется один раз, переиспользуется. Ключевой момент: такие объекты обязаны быть потокобезопасными на чтение, потому что к ним обращаются из всех потоков.
> ```csharp
> private static readonly JsonSerializerOptions JsonOptions = new()
> {
>     PropertyNamingPolicy = JsonNamingPolicy.CamelCase,
>     DefaultIgnoreCondition = System.Text.Json.Serialization.JsonIgnoreCondition.WhenWritingNull
> };
> ```
> Обратите внимание: `JsonSerializerOptions` становится неизменяемым после первого использования — попытка изменить его свойства после сериализации бросит `InvalidOperationException`. Это пример «иммутабельности по контракту», которую `readonly` не обеспечивает.
>
> **`readonly struct` по умолчанию.** В командах, где есть value-объекты (`Money`, `OrderId`, `Percentage`), правило простое: любая новая структура пишется как `readonly struct` или `readonly record struct`. Мутабельные структуры допускаются только в узких перформанс-сценариях с явным комментарием.
>
> **`var` — по соглашению команды.** Самый распространённый компромисс: `var` разрешён, когда тип очевиден из правой части (`new`, явный каст, литерал, `as`), и запрещён для результатов вызовов методов. Соглашение прописывается в `.editorconfig` правилами `csharp_style_var_when_type_is_apparent = true` и `csharp_style_var_elsewhere = false`, чтобы спор решался анализатором, а не на ревью.

## Вопросы с собеседований

> [!question]- В чём разница между `const` и `static readonly`? Когда `const` опасен?
> `const` вычисляется на этапе компиляции и физически инлайнится в IL каждого места использования: в сборке потребителя стоит `ldc.i4.3`, а не ссылка на поле. `static readonly` — обычное поле с флагом `initonly`, читается во время выполнения через `ldsfld`. Отсюда главная опасность: если библиотека объявила `public const int MaxRetries = 3`, а приложение скомпилировалось с ней, то обновление библиотеки до `= 5` без перекомпиляции приложения ничего не изменит — приложение продолжит видеть тройку, вшитую в собственный IL. Поэтому в публичном API библиотек используют `static readonly`, а `const` оставляют для internal-значений, вечных величин и мест, где константа синтаксически обязательна (метки `case`, значения параметров по умолчанию, аргументы атрибутов).

> [!question]- Почему компилятор требует инициализировать локальную переменную, но не поле класса?
> CLR гарантирует, что память под объект и под статическую область типа обнуляется при выделении, поэтому у поля всегда есть корректное значение `default(T)` — доказывать нечего. Для локальных переменных такой гарантии нет: стековый слот может содержать мусор от предыдущего кадра, а с атрибутом `[SkipLocalsInit]` рантайм официально перестаёт зачищать стек. Компилятор проводит анализ потока данных и на каждой точке знает, «определённо присвоена» переменная или нет; чтение неприсвоенной даёт CS0165. Анализ консервативный: `if (cond) x = 1;` без `else` не считается присваиванием, потому что существует путь исполнения без него. Исключение — константное условие: `if (true) x = 1;` компилируется, так как else-ветка недостижима по спецификации.

> [!question]- Делает ли `readonly` объект неизменяемым?
> Нет. `readonly` замораживает только сам слот поля — то есть ссылку, а не то, на что она указывает. `private readonly List<int> _items = new();` запрещает `_items = new List<int>()` вне конструктора, но полностью разрешает `_items.Add(1)`, `_items.Clear()` и `_items[0] = 7`. Для реальной неизменяемости нужен неизменяемый тип: `ImmutableArray<T>`, `FrozenDictionary<K,V>`, `ReadOnlyCollection<T>`, `record` с `init`-свойствами. Возврат `IReadOnlyList<T>` — не защита, а соглашение: вызывающий код может привести результат обратно к `List<T>`.

> [!question]- Что такое defensive copy и когда она возникает?
> Когда компилятор видит вызов не-readonly члена структуры на readonly-месте — readonly-поле, `in`-параметр, `ref readonly` локальная, `static readonly` поле — он не может передать адрес переменной, потому что метод потенциально изменит поля. Вместо `ldflda` он эмитит `ldfld`, копирует структуру во временную локальную и вызывает метод на копии. Последствий два: мутация теряется (`_counter.Increment()` на readonly-поле не увеличивает счётчик, и компилятор об этом молчит) и на каждый вызов тратится копирование `sizeof(T)` байт, что заметно для больших структур в горячем цикле. Лечится модификатором `readonly struct` (C# 7.2) или пометкой `readonly` на конкретных членах, включая `override string ToString()` (C# 8).

> [!question]- В каком порядке выполняются инициализаторы полей и конструкторы при наследовании?
> Сначала инициализаторы полей самого производного класса, затем — вверх по цепочке — инициализаторы полей базового, потом тело конструктора базового, и последним тело конструктора производного. Причина в том, что компилятор вставляет код инициализаторов полей в начало каждого конструктора класса, **до** вызова `base(...)`. Отсюда практическое ограничение: инициализатор поля не может ссылаться на `this` (CS0236) — ни на другое нестатическое поле, ни на нестатический метод, потому что объект в этот момент ещё не сконструирован и базовый конструктор не отработал. Если нужно вычислить поле от другого поля, делайте это в теле конструктора, где порядок под контролем.

> [!question]- Чем `in`-параметр отличается от `ref readonly`-параметра?
> Внутри метода семантика одинаковая: обе формы передают ссылку и запрещают запись. Разница в требованиях к точке вызова. `in` не требует модификатора при вызове (`Trace(matrix)` компилируется молча) и принимает rvalue — литералы, результаты выражений, для них создаётся временная переменная. `ref readonly` (C# 12) требует `ref` или `in` при вызове, иначе предупреждение CS9192, и предупреждает CS9193 на rvalue. Смысл этой строгости — миграция: существующий `ref`-API можно переписать на `ref readonly`, не сломав вызывающий код, который пишет `ref`. С `in` так не получится, потому что `in` в сигнатуре читается как «возможно, тут временная копия, адрес ничего не значит».

> [!question]- Что такое `beforefieldinit` и как на него влияет статический конструктор?
> Это флаг в метаданных типа. Если у типа есть только инициализаторы статических полей и нет явного статического конструктора, компилятор ставит `beforefieldinit`, и CLR получает право инициализировать тип в любой момент до первого обращения к статическому полю — например, прямо при JIT-компиляции метода, который на него ссылается. Проверок инициализации в коде доступа нет, чтение максимально дешёвое, но порядок инициализации разных типов не определён. Явный `static Foo() { }` снимает флаг: CLR обязана инициализировать тип точно перед первым обращением к любому статическому члену или созданием экземпляра. Это дороже (появляется проверка, которую JIT не всегда выносит из горячего пути), но детерминированно. Вывод: побочные эффекты в статической инициализации — пишите статический конструктор; просто кеш значений — не пишите.

## Задачи

### Задача 1. Найдите потерянные инкременты

Дан код. Он должен печатать `2`, но печатает другое. Объясните почему и предложите два способа починки, не меняя логику вызовов.

```csharp
public struct Hits
{
    private int _n;
    public int Count => _n;
    public void Hit() => _n++;
}

public class Page
{
    private readonly Hits _hits = new();
    public void Render() { _hits.Hit(); _hits.Hit(); Console.WriteLine(_hits.Count); }
}
```

> [!success]- Решение
> Печатает `0`. `_hits` — readonly-поле структурного типа, а `Hit()` не помечен `readonly`. Компилятор не может передать адрес поля (`ldflda`), потому что метод потенциально мутирует структуру и нарушит `initonly`. Вместо этого он копирует значение поля во временную локальную (`ldfld` + `stloc`) и вызывает `Hit()` на копии. Копия умирает, поле остаётся нулём.
>
> Способ 1 — убрать `readonly` с поля. Тогда компилятор эмитит `ldflda` и мутация попадёт в поле:
> ```csharp
> private Hits _hits = new();   // Вывод: 2
> ```
>
> Способ 2 — сделать структуру честно иммутабельной, чтобы мутации вообще не было:
> ```csharp
> public readonly struct Hits
> {
>     private readonly int _n;
>     private Hits(int n) => _n = n;
>     public int Count => _n;
>     public Hits Hit() => new(_n + 1);
> }
> // Но тогда меняются вызовы: _hits = _hits.Hit(); — а поле не может быть readonly.
> ```
> На практике для счётчика внутри класса правильнее первый вариант: структура мутабельная по природе, и `readonly` на поле здесь просто ошибка. Общее правило: `readonly`-поле структурного типа безопасно только если тип объявлен `readonly struct`.

### Задача 2. Константа, которая не обновилась

Библиотека `Billing.Core` версии 1.0 содержит:

```csharp
namespace Billing.Core;
public static class Fees
{
    public const decimal ServiceFeePercent = 1.5m;
    public static decimal Apply(decimal amount) => amount * (1 + ServiceFeePercent / 100);
}
```

Приложение вызывает и `Fees.Apply(1000)`, и считает комиссию само: `1000 * Fees.ServiceFeePercent / 100`. Вышла версия 1.1 с `ServiceFeePercent = 2.0m`, dll заменили без пересборки приложения. Что покажут оба расчёта и как переписать `Fees`?

> [!success]- Решение
> `Fees.Apply(1000)` вернёт `1020` — правильно, потому что тело метода живёт внутри новой библиотеки и было перекомпилировано вместе с ней. Собственный расчёт приложения даст `15` вместо `20`: значение `1.5m` инлайнилось в IL приложения при его компиляции.
>
> Отдельно: `const decimal` не является IL-литералом (decimal не примитив CLR). Компилятор эмитит `initonly`-поле с атрибутом `[DecimalConstantAttribute(1, 0, 0, 0, 15)]`, а Roslyn у потребителя читает этот атрибут и всё равно инлайнит значение. То есть проблема ровно та же, что у `const int`, просто механизм другой.
>
> Правильная версия:
> ```csharp
> namespace Billing.Core;
> public static class Fees
> {
>     public static readonly decimal ServiceFeePercent = 2.0m;   // ldsfld у потребителя
>     public static decimal Apply(decimal amount) => amount * (1 + ServiceFeePercent / 100);
> }
> ```
> Ещё лучше — вообще не отдавать ставку как поле, а сделать её частью конфигурации, которую приложение получает через DI. Тогда изменение ставки не требует ни перекомпиляции, ни деплоя библиотеки.

### Задача 3. Предскажите вывод

Не запуская, напишите, что выведет программа, и объясните порядок.

```csharp
class A
{
    protected int _x = Log(1, "поле A");
    public A() { Log(2, "ctor A"); Init(); }
    protected virtual void Init() => Log(3, "Init из A");
    protected static int Log(int n, string s) { Console.WriteLine($"{n} {s}"); return n; }
}

class B : A
{
    private readonly string _name = (string)(object)"готово";
    private int _y = Log(0, "поле B");
    public B() { Log(4, "ctor B"); }
    protected override void Init() => Console.WriteLine($"Init из B, _name = '{_name}'");
}

_ = new B();
```

> [!success]- Решение
> ```
> 0 поле B
> 1 поле A
> 2 ctor A
> Init из B, _name = 'готово'
> 4 ctor B
> ```
> Порядок: инициализаторы полей `B` (в порядке объявления: `_name`, затем `_y`), потом неявный `base()` — внутри него инициализаторы полей `A`, потом тело конструктора `A`.
>
> Ключевой момент — вызов виртуального `Init()` из конструктора базового класса. Диспетчеризация идёт по фактическому типу объекта (`B`), поэтому выполняется `B.Init()`. И тут повезло: `_name` уже проинициализирован, потому что инициализаторы полей производного класса отрабатывают до `base()`. Но `_y` был бы виден корректно по той же причине, а вот всё, что `B` присваивает **в теле** своего конструктора, на момент вызова `Init()` ещё не выполнено — там были бы нули.
>
> Отсюда правило: **никогда не вызывайте виртуальные методы из конструктора**. Здесь пример «работает случайно»; в реальном коде производный класс обычно инициализирует зависимости в теле конструктора, и виртуальный метод получит `null`. Анализатор CA2214 («Do not call overridable methods in constructors») именно об этом.

## Итог

- Локальная переменная требует определённого присваивания (CS0165), поле — нет, потому что CLR обнуляет память объекта и статическую область типа; анализ потока консервативен и не считает `if` без `else` присваиванием, но понимает константное условие `if (true)`.
- `var` — статическая типизация с выводом типа из правой части, `new()` — вывод из левой; в IL ни того, ни другого не остаётся, различие чисто синтаксическое.
- `const` — литерал, который инлайнится в IL потребителя (`ldc.i4.3`), неявно `static`, только для примитивов, `string`, `enum` и `null`. В публичном API библиотеки это ломает версионирование: обновление сборки без пересборки потребителя не меняет значение.
- `static readonly` читается через `ldsfld` во время выполнения — это правильный выбор для любых публичных настраиваемых величин; `const` оставляйте для internal-значений, вечных констант и мест, где он обязателен синтаксически.
- `readonly` защищает слот, а не объект: `readonly List<T>` спокойно мутируется через `Add`. Реальная неизменяемость — только через неизменяемые типы.
- Структуры: `readonly struct` и `readonly`-члены существуют, чтобы компилятор не делал защитных копий. Без них readonly-поле, `in`-параметр и `ref readonly` локальная порождают тихое копирование и теряют мутации без единого предупреждения.
- Порядок инициализации: инициализаторы полей производного, затем базовый конструктор целиком, затем тело конструктора производного; `beforefieldinit` у статики отключается явным статическим конструктором.
