# Иерархия исключений в .NET

> [!abstract] Коротко
> Все исключения наследуются от `System.Exception`. Исторически они делились на `SystemException` (от рантайма) и `ApplicationException` (от приложения), но это разделение признано неудачным и не используется — свои исключения наследуют прямо от `Exception`. Практически полезнее другая классификация: **ошибки программиста** (`NullReferenceException`, `ArgumentException`, `InvalidOperationException`) — их не ловят, их чинят; **ошибки окружения** (`IOException`, `HttpRequestException`, `TimeoutException`) — их ловят и обрабатывают; **фатальные** (`OutOfMemoryException`, `StackOverflowException`) — их ловить бессмысленно или невозможно.

## Зачем это нужно

Чтобы отвечать на два вопроса, которые возникают каждый день: «какой тип исключения бросить» и «какой тип поймать». Ответ «поймаю `Exception`» неверен почти всегда, а бросить неправильный тип означает, что вызывающий не сможет отличить свою ошибку от чужой.

Кроме того, по типу исключения можно быстро понять причину: `InvalidOperationException` означает «объект не в том состоянии», `ArgumentException` — «тебе передали не то», `TypeInitializationException` — «упал статический конструктор, смотри внутрь».

```
System.Object
└── System.Exception
    ├── SystemException                        ← базовый для исключений рантайма

    │   │   ├── ArgumentNullException
    │   │   └── ArgumentOutOfRangeException
    │   ├── InvalidOperationException
    │   │   └── ObjectDisposedException
    │   ├── NullReferenceException
    │   ├── IndexOutOfRangeException
    │   ├── InvalidCastException
    │   ├── FormatException
    │   ├── ArithmeticException
    │   │   ├── OverflowException
    │   │   └── DivideByZeroException
    │   ├── NotSupportedException
    │   │   └── PlatformNotSupportedException
    │   ├── NotImplementedException
    │   ├── TimeoutException
    │   ├── OperationCanceledException
    │   │   └── TaskCanceledException
    │   ├── IOException
    │   │   ├── FileNotFoundException
    │   │   ├── DirectoryNotFoundException
    │   │   └── EndOfStreamException
    │   ├── OutOfMemoryException
    │   ├── StackOverflowException             ← неперехватываемое
    │   ├── TypeInitializationException
    │   └── TargetInvocationException
    ├── AggregateException
    ├── ApplicationException                    ← не использовать
    └── (твои исключения — наследуй от Exception)
```

Плюс типы из отдельных библиотек: `HttpRequestException`, `JsonException`, `DbException` (и его наследник `NpgsqlException`), `DbUpdateException`/`DbUpdateConcurrencyException` из EF Core, `ValidationException` из аннотаций данных, `KeyNotFoundException` из коллекций.

## Три категории по способу реакции

### 1. Ошибки программиста — не ловить, а чинить

| Исключение | Что означает |
|---|---|
| `NullReferenceException` | обращение по нулевой ссылке — пропущена проверка или не инициализировано поле |
| `IndexOutOfRangeException` | выход за границы массива |
| `ArgumentException`, `ArgumentNullException`, `ArgumentOutOfRangeException` | метод получил недопустимый аргумент |
| `InvalidCastException` | приведение к несовместимому типу |
| `InvalidOperationException` | объект не в том состоянии для этой операции |
| `ObjectDisposedException` | использование освобождённого объекта |
| `NotImplementedException` | заглушка, оставшаяся в коде |

Перехват таких исключений маскирует дефект: `catch (NullReferenceException) { }` не чинит `null`, а прячет его до следующего места, где он проявится в непонятной форме. Правильная реакция — исправить код или добавить проверку на входе ([[Защитное программирование и guard clauses]]).

Единственное место, где эти исключения перехватываются законно, — глобальный обработчик на границе приложения, чтобы один сбойный запрос не уронил процесс и попал в логи.

### 2. Ошибки окружения — ловить и обрабатывать

| Исключение | Типичная причина | Что делать |
|---|---|---|
| `IOException` и наследники | файл занят, диск недоступен, обрыв потока | повтор, запасной путь, понятная ошибка пользователю |
| `HttpRequestException` | сеть, DNS, недоступный сервис | повтор с задержкой, разрыватель цепи |
| `TimeoutException`, `TaskCanceledException` (по таймауту) | сервис не ответил вовремя | повтор или деградация функциональности |
| `SocketException` | нет соединения, порт закрыт | то же, что для HTTP |
| `DbException`/`NpgsqlException` | БД недоступна, нарушено ограничение | различать по коду ошибки: повтор или бизнес-ответ |
| `DbUpdateConcurrencyException` | кто-то изменил запись параллельно | перечитать и применить заново |
| `JsonException` | битые данные от внешней системы | 400 или отбраковка сообщения |
| `FormatException`, `OverflowException` | некорректный ввод | валидация и ответ 400 |

Это и есть та зона, ради которой существует `try/catch` в прикладном коде.

### 3. Фатальные — ловить нельзя или бессмысленно

- `StackOverflowException` — начиная с .NET Framework 2.0 **невозможно перехватить**: процесс завершается немедленно, потому что для выполнения `catch` нужен стек.
- `OutOfMemoryException` — формально перехватывается, но осмысленно обработать почти невозможно: любая попытка что-то сделать требует памяти. Исключение — сценарии, где заранее известно, что аллокация была большой и её можно не делать.
- `AccessViolationException` — повреждение памяти в нативном коде; по умолчанию не перехватывается управляемым кодом.
- `Environment.FailFast` вообще не бросает исключение: он завершает процесс, минуя `finally` и обработчики, и пишет дамп. Применяется, когда состояние процесса нельзя считать корректным.

## Особые случаи, о которых надо знать

### `AggregateException`

```csharp
var task = Task.WhenAll(t1, t2, t3);
try
{
    await task;                 // await бросает ПЕРВОЕ исключение
}
catch (Exception)
{
    foreach (var inner in task.Exception!.InnerExceptions)   // а здесь — все
        logger.LogError(inner, "Одна из задач упала");
}

// Синхронное ожидание (.Wait()/.Result) бросает именно AggregateException —
// ещё одна причина не смешивать синхронный и асинхронный код
```

`AggregateException` — контейнер: он появляется там, где ошибок может быть несколько (`Task.WhenAll`, `Parallel.For`, `TPL Dataflow`). Полезный метод — `Flatten()`, разворачивающий вложенные агрегаты.

### Исключения-обёртки: смотри внутрь

```csharp
try { /* обращение к статическому классу */ }
catch (TypeInitializationException ex)
{
    // Реальная причина — в ex.InnerException: упал статический конструктор.
    // Само сообщение TypeInitializationException бесполезно.
}
```

Тот же принцип у `TargetInvocationException` (исключение из метода, вызванного рефлексией) и у `DbUpdateException` (внутри — исключение драйвера БД с кодом ограничения). Первое действие при виде такого исключения в логе — раскрыть `InnerException`.

### `OperationCanceledException` — не ошибка

```csharp
try { await ProcessAsync(ct); }
catch (OperationCanceledException) when (ct.IsCancellationRequested)
{
    logger.LogInformation("Операция отменена");     // Information, не Error
    throw;                                           // обычно пробрасываем дальше
}
```

Отмена — штатный исход: клиент разорвал соединение, приложение останавливается, истёк таймаут. Логировать её как ошибку значит зашумлять мониторинг ложными сбоями. `TaskCanceledException` — наследник `OperationCanceledException`, ловить достаточно базовый тип.

### `ApplicationException` — не использовать

Задумывался как база для пользовательских исключений, но разделение «системные против прикладных» не давало ничего полезного: ловить по нему всё равно никто не мог, потому что исключения BCL от него не наследуются. Официальная рекомендация Microsoft — наследовать свои исключения напрямую от `Exception`. В легаси-коде `ApplicationException` встречается, и это не повод его менять, но новый код так не пишут.

## Полезные члены `Exception`

```csharp
catch (Exception ex)
{
    ex.Message;             // текст для человека (не для разбора кодом!)
    ex.StackTrace;          // стек на момент броска
    ex.InnerException;      // причина, если исключение обёрнуто
    ex.Data["orderId"] = 42; // произвольный словарь контекста
    ex.Source;              // имя сборки, где возникло
    ex.HResult;             // числовой код — по нему различают IO-ошибки и коды драйверов
    ex.TargetSite;          // метод, где произошло (дорого, использует рефлексию)
    ex.ToString();          // тип + сообщение + стек + все внутренние — то, что нужно в логе
}
```

Правило: **не разбирать `Message` кодом**. Текст локализуется и меняется между версиями; логика строится на типе исключения, `HResult` или собственных свойствах своего типа исключения.

> [!warning] Подводные камни
> - **`catch (Exception)` в середине стека.** Ловит и фатальные, и отмену, и ошибки программиста. Если такой перехват нужен (граница приложения, цикл фоновой службы), он должен быть осознанным и одним.
> - **Разбор `ex.Message` строкой.** Ломается при смене локали или версии библиотеки. Различай по типу и коду.
> - **Игнорирование `InnerException`.** `TypeInitializationException`, `TargetInvocationException`, `DbUpdateException` без внутреннего исключения не говорят ничего.
> - **Ловить `OperationCanceledException` как сбой.** Отмена штатна; отдельный `catch` с уровнем Information и пробросом дальше.
> - **Наследование от `ApplicationException`.** Устаревшая практика без пользы.
> - **`KeyNotFoundException` как часть нормального потока.** Означает, что вместо индексатора нужен `TryGetValue`.
> - **Попытка «восстановиться» после `OutOfMemoryException`.** Обычно приводит к каскаду новых сбоев; корректнее упасть и перезапуститься.

> [!example] Как делают в бою
> На границе приложения исключения раскладываются в HTTP-коды по типу: `ArgumentException` и `ValidationException` → 400, своё `NotFoundException` или `KeyNotFoundException` → 404, `DbUpdateConcurrencyException` → 409, `OperationCanceledException` → 499 или просто без ответа, всё остальное → 500 с идентификатором корреляции в теле и полным стеком в логе.
> Для интеграций различают повторяемые и неповторяемые ошибки: таймаут, 5xx и обрыв сети — повторять с экспоненциальной задержкой; 4xx и `JsonException` — не повторять, это не пройдёт и со второго раза. Именно эта классификация, а не «поймать всё», отличает устойчивый сервис.
> При работе с PostgreSQL в `NpgsqlException` смотрят `SqlState`: `23505` (нарушение уникальности) обычно означает бизнес-конфликт и превращается в 409, а не в 500; коды класса `08` (сбой соединения) — повторяемая ошибка.

## Вопросы с собеседований

> [!question]- Какие исключения нельзя перехватывать и почему?
> `StackOverflowException` перехватить физически невозможно начиная с .NET Framework 2.0: стек исчерпан, выполнять код обработчика негде, поэтому рантайм немедленно завершает процесс. `OutOfMemoryException` формально ловится, но осмысленной обработки почти не существует — любое действие в обработчике требует памяти, а система уже в деградировавшем состоянии; правильнее дать процессу упасть и перезапуститься. `AccessViolationException` сигнализирует о повреждении памяти, обычно в нативном коде, и по умолчанию не перехватывается управляемым кодом. Ещё две категории, которые не стоит ловить по другим причинам: ошибки программиста (`NullReferenceException`, `InvalidCastException`, `ArgumentException`) — их надо чинить, а не прятать, и `OperationCanceledException` — это штатная отмена, её пробрасывают дальше.

> [!question]- Чем `ArgumentException` отличается от `InvalidOperationException`?
> `ArgumentException` (и его наследники `ArgumentNullException`, `ArgumentOutOfRangeException`) означает, что проблема в **переданных аргументах**: значение `null`, выход за диапазон, недопустимый формат. Виноват вызывающий, и исправление — передать другие данные. `InvalidOperationException` означает, что аргументы допустимы, но **объект находится в состоянии**, при котором операция невозможна: чтение из закрытого соединения, `MoveNext` после изменения коллекции, попытка отменить уже завершённую транзакцию. Виноват порядок вызовов. Наследник `ObjectDisposedException` уточняет частный случай — объект уже освобождён. Разделение важно для вызывающего: в первом случае надо исправить данные, во втором — последовательность действий. Своё исключение стоит наследовать от того из них, которое ближе по смыслу, либо прямо от `Exception`, если ситуация доменная.

> [!question]- Что такое `AggregateException` и когда он возникает?
> Это контейнер для нескольких исключений, возникающий там, где параллельно выполняется много операций и упасть может любая: `Task.WhenAll`, `Parallel.For`/`Parallel.ForEach`, `TPL Dataflow`, а также при синхронном ожидании задачи через `.Wait()` или `.Result`. Все ошибки лежат в `InnerExceptions`, а метод `Flatten()` разворачивает вложенные агрегаты в один плоский список. Важная тонкость: `await` над задачей бросает **первое** исключение, а не `AggregateException` — это сделано ради читаемости кода, но означает, что при `await Task.WhenAll(...)` остальные ошибки не видны, пока не заглянуть в `task.Exception`. Поэтому при ожидании набора задач исключения обычно собирают явно, а не полагаются на то, что `catch` покажет всё.

## Задачи

### Задача 1. Выбрать типы исключений

Метод `Withdraw(Account account, decimal amount)` должен реагировать на: `account == null`, `amount <= 0`, недостаток средств, закрытый счёт. Какие исключения бросать?

> [!success]- Решение
> ```csharp
> public void Withdraw(Account account, decimal amount)
> {
>     ArgumentNullException.ThrowIfNull(account);
>     ArgumentOutOfRangeException.ThrowIfLessThanOrEqual(amount, 0);
>
>     if (account.IsClosed)
>         throw new InvalidOperationException($"Счёт {account.Id} закрыт");
>
>     if (account.Balance < amount)
>         throw new InsufficientFundsException(account.Id, requested: amount, available: account.Balance);
>
>     account.Balance -= amount;
> }
> ```
> Логика выбора: `null` и неположительная сумма — ошибки вызывающего, значит семейство `ArgumentException` (готовые статические `ThrowIfNull`/`ThrowIfLessThanOrEqual` из .NET 8 короче и сами подставляют имя параметра). Закрытый счёт — корректные аргументы, но неподходящее состояние объекта, значит `InvalidOperationException`. Недостаток средств — доменная ситуация, о которой вызывающий захочет узнать отдельно и показать пользователю: здесь оправдан свой тип с данными (сколько запрошено, сколько доступно), чтобы обработчик мог сформировать внятный ответ, не разбирая текст сообщения. Проектирование таких типов — [[Свои типы исключений]].

### Задача 2. Разобрать лог

В логе видно `TypeInitializationException: The type initializer for 'App.Config' threw an exception`. Что это значит и куда смотреть?

> [!success]- Решение
> Это означает, что упал **статический конструктор** (или инициализатор статического поля) типа `App.Config`. Рантайм оборачивает любое исключение из статической инициализации в `TypeInitializationException`, и само по себе оно не сообщает ничего — реальная причина лежит в `InnerException`: обычно это отсутствующий файл конфигурации, `null` в переменной окружения, неверная строка подключения или деление на ноль в вычисляемой константе.
> Практические детали, которые важны при разборе: статический конструктор выполняется один раз, и если он упал, тип помечается как непригодный — **все последующие обращения** будут бросать то же `TypeInitializationException` с тем же внутренним исключением, даже если причина уже устранена; перезапуск процесса обязателен. Отсюда правило: в статических конструкторах не делают ничего, что может упасть, — ни чтения файлов, ни обращений к сети, ни разбора конфигурации. Подробно — [[Статические члены, классы и конструкторы]].

## Итог

- Всё наследуется от `Exception`; деление на `SystemException`/`ApplicationException` устарело — свои исключения наследуют от `Exception`.
- Практическая классификация: ошибки программиста (чинить), ошибки окружения (обрабатывать), фатальные (не ловить).
- `StackOverflowException` не перехватывается вообще; `OutOfMemoryException` перехватывается, но обрабатывать почти нечем.
- `OperationCanceledException` — штатная отмена, а не сбой.
- `TypeInitializationException`, `TargetInvocationException`, `DbUpdateException` бесполезны без `InnerException`.
- `AggregateException` собирает несколько ошибок; `await` показывает только первую.
- Логика строится на типе исключения и кодах, а не на разборе текста `Message`.
