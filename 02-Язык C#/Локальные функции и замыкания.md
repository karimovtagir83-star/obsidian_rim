# Локальные функции и замыкания

> [!abstract] Коротко
> Локальная функция (local function) — метод, объявленный внутри тела другого метода. Она видит локальные переменные окружающего метода, но, в отличие от лямбды, имеет имя, поддерживает рекурсию и дженерики и в подавляющем большинстве случаев не создаёт мусора в куче.
> Замыкание (closure) — механизм, которым компилятор «продлевает жизнь» захваченным переменным: он переносит их в сгенерированный объект (display class), и переменная перестаёт быть переменной стека. Понимание того, где именно возникает этот объект, отделяет код, который аллоцирует ноль байт, от кода, который в горячем цикле создаёт миллионы объектов.

## Зачем это нужно

До C# 7 (2017) единственным способом определить «хелпер только для этого метода» была лямбда, положенная в `Func<...>`/`Action<...>`:

```csharp
// Как писали до C# 7
public int Sum(int[] data)
{
    Func<int, bool> isValid = x => x > 0 && x < 1000;   // аллокация делегата
    var total = 0;
    foreach (var x in data)
        if (isValid(x)) total += x;                      // вызов через делегат: невиртуальный callvirt по Invoke
    return total;
}
```

Проблем три:
1. Аллокация объекта делегата (и display class, если есть захват).
2. Вызов через `Invoke` — JIT почти никогда не инлайнит его.
3. Лямбда не может быть рекурсивной без танцев и не может быть дженериком.

Локальные функции решают всё это. Плюс — они дают приём, без которого невозможно корректно написать итератор или `async`-метод с валидацией аргументов.

## Синтаксис локальной функции

```csharp
public static int Fibonacci(int n)
{
    ArgumentOutOfRangeException.ThrowIfNegative(n);
    return Fib(n);

    // Локальная функция может быть объявлена ПОСЛЕ места использования.
    // Компилятор видит всё тело метода целиком, порядок не важен.
    static int Fib(int k) => k < 2 ? k : Fib(k - 1) + Fib(k - 2);
}

Console.WriteLine(Fibonacci(10));
// Вывод: 55
```

Локальная функция может быть:

```csharp
void Demo()
{
    // обычная
    int Twice(int x) => x * 2;

    // дженерик — лямбда так не умеет до сих пор (C# 14)
    T First<T>(IReadOnlyList<T> items) => items[0];

    // с ref/out/in/ref readonly параметрами
    static void Swap(ref int a, ref int b) => (a, b) = (b, a);

    // итератор
    IEnumerable<int> Range(int n) { for (var i = 0; i < n; i++) yield return i; }

    // асинхронная
    async Task<int> LoadAsync() { await Task.Yield(); return 1; }

    // с ref struct — лямбде понадобился бы собственный тип делегата
    static int Count(ReadOnlySpan<char> s) => s.Length;

    // с атрибутами (разрешено с C# 9)
    [System.Diagnostics.Conditional("DEBUG")]
    static void Trace(string m) => Console.WriteLine(m);

    Console.WriteLine($"{Twice(21)} {First(new[] { 7, 8 })} {Count("abc")}");
    // Вывод: 42 7 3
}
```

Чего локальная функция **не** может: иметь модификатор доступа (`public`/`private`), быть `virtual`/`override`/`abstract`/`partial`, быть объявленной на уровне типа. Она невидима снаружи метода — это и есть смысл.

## Локальная функция против лямбды

| Признак | Локальная функция | Лямбда |
|---|---|---|
| Имя | Есть, вызов по имени | Только через переменную-делегат |
| Рекурсия | Естественная | Нужно сначала объявить `Func`, потом присвоить |
| Дженерики | Да | Нет (и в C# 14 тоже) |
| Использование до объявления | Да | Нет |
| Definite assignment | Проверяется в точке **вызова** | Проверяется в точке **создания** лямбды |
| Аллокация делегата | Нет, если не преобразуется в делегат | Есть (кроме кешированных случаев) |
| Display class при захвате | `struct`, передаётся по `ref` | `class` в куче |
| Инлайнинг JIT | Возможен | Практически никогда |
| `ref`/`out`/`ref struct` | Свободно | Ограниченно, нужен свой тип делегата |
| `yield return` | Да | Нет |
| Передать как значение | Через явное преобразование в делегат | Это и есть значение |

### Отложенная проверка definite assignment

```csharp
void Deferred()
{
    int x;                                    // ещё не присвоена

    void Print() => Console.WriteLine(x);     // ОК: тело проверят в точке вызова

    x = 42;
    Print();                                  // Вывод: 42
}

void Broken()
{
    int y;
    Action a = () => Console.WriteLine(y);    // CS0165: использование неприсвоенной y
    y = 1;
    a();
}
```

Компилятор анализирует тело локальной функции в каждом месте её вызова: если бы `Print()` стоял до `x = 42`, была бы ошибка CS0165. Лямбда же — выражение, её значение создаётся немедленно, поэтому и захват проверяется немедленно.

## Во что компилируется локальная функция

Возьмём метод с захватом:

```csharp
public int Process(int[] data, int threshold)
{
    var total = 0;

    void Accumulate(int value)
    {
        if (value > threshold) total += value;   // захвачены threshold и total
    }

    foreach (var v in data) Accumulate(v);
    return total;
}
```

Roslyn генерирует примерно такое (декомпиляция, имена с `<>` невыразимы в C#):

```csharp
// Сгенерированный компилятором код
[CompilerGenerated]
private struct <Process>g__DisplayClass0_0     // ЗАМЕТЬТЕ: struct, не class
{
    public int threshold;
    public int total;
}

public int Process(int[] data, int threshold)
{
    <Process>g__DisplayClass0_0 cls = default;
    cls.threshold = threshold;
    cls.total = 0;

    foreach (var v in data)
        <Process>g__Accumulate|0_0(v, ref cls);   // передача по ссылке

    return cls.total;
}

[CompilerGenerated]
private static void <Process>g__Accumulate|0_0(int value, ref <Process>g__DisplayClass0_0 cls)
{
    if (value > cls.threshold) cls.total += value;
}
```

Ключевые выводы:
- Локальная функция стала **private static** методом типа. Статическим — потому что `this` она не использует. Вызов обычный `call`, не через делегат.
- Захваченные переменные упакованы в **структуру**, которая лежит на стеке. Она передаётся по `ref`, поэтому изменение `total` внутри видно снаружи, а боксинга и аллокации в куче нет. Ноль байт мусора.
- Если бы `Accumulate` использовала `this`, компилятор сгенерировал бы **instance**-метод, и `this` не попал бы в display class.

В IL вызов выглядит так:

```
ldloc.1                      // v
ldloca.s   cls               // адрес структуры-замыкания
call       void C::'<Process>g__Accumulate|0_0'(int32, valuetype C/'<Process>g__DisplayClass0_0'&)
```

`ldloca` вместо `ldloc` — это и есть «по ссылке, без копии».

> [!info] Когда struct превращается в class
> Как только локальная функция **преобразуется в делегат** (`Action a = Accumulate;`), передаётся куда-то как значение или захватывается лямбдой, компилятор обязан сделать display class обычным `class` в куче: делегат может пережить кадр стека, а структура на стеке — нет. То же произойдёт, если локальная функция — итератор или `async`: их состояние живёт дольше кадра.

## static локальные функции (C# 8)

Модификатор `static` у локальной функции запрещает захватывать что-либо из окружающего метода, включая `this`:

```csharp
public sealed class Report
{
    private readonly decimal _rate = 0.2m;

    public decimal Total(decimal[] lines)
    {
        decimal sum = 0;

        // static: захват запрещён компилятором
        static decimal WithVat(decimal amount, decimal rate) => amount * (1 + rate);

        foreach (var l in lines) sum += WithVat(l, _rate);
        return sum;
    }
}
```

Зачем это нужно:
1. **Гарантия отсутствия display class.** Компилятор физически не создаст ни структуру-замыкание, ни класс. Это контракт, который проверяет компилятор, а не «я вроде ничего не захватил».
2. **Защита от случайного захвата `this`.** Самая частая невидимая аллокация — когда рефакторинг добавляет в тело обращение к полю, и метод внезапно перестаёт быть статическим.
3. **Инлайнинг.** Статический метод с явными параметрами инлайнится JIT намного охотнее.

Правило для горячего пути: **пиши `static` по умолчанию, снимай только когда компилятор заставит**. Анализаторы Roslyn IDE0062 («make local function static») подсказывают это автоматически.

## Замыкание: что происходит с переменными

Замыкание — это не «лямбда», а *связка кода и захваченного окружения*. С момента захвата переменная перестаёт быть слотом на стеке и становится **полем объекта**:

```
До захвата                          После захвата
------------------                  --------------------------------
Стек:                               Стек:                Куча:
 +---------+                         +---------+          +-------------------+
 | counter |  int, 4 байта           | cls ref |--------->| <>c__DisplayClass |
 +---------+                         +---------+          |   int counter     |
                                                          +-------------------+
                                                          живёт, пока жив делегат
```

```csharp
Func<int> MakeCounter()
{
    var counter = 0;                 // выглядит как локальная переменная
    return () => ++counter;          // на деле — поле объекта в куче
}

var c1 = MakeCounter();
var c2 = MakeCounter();
Console.WriteLine($"{c1()} {c1()} {c1()} {c2()}");
// Вывод: 1 2 3 1
```

`c1` и `c2` имеют **разные** display class'ы — каждый вызов `MakeCounter` создаёт новый экземпляр. Захватывается **переменная**, а не её значение: если после создания лямбды изменить переменную, лямбда увидит новое значение.

```csharp
var x = 1;
Func<int> f = () => x;
x = 99;
Console.WriteLine(f());
// Вывод: 99
```

## Кеширование делегата компилятором

Лямбда **без захвата** не зависит от контекста, поэтому её делегат можно создать один раз:

```csharp
static void Run(Action a) => a();

for (var i = 0; i < 3; i++)
    Run(() => Console.WriteLine("hi"));
```

Сгенерированный код:

```csharp
// Сгенерированный компилятором код
[CompilerGenerated]
private sealed class <>c
{
    public static readonly <>c <>9 = new <>c();
    public static Action <>9__0_0;                    // кеш делегата

    internal void <Main>b__0_0() => Console.WriteLine("hi");
}

for (var i = 0; i < 3; i++)
    Run(<>c.<>9__0_0 ??= new Action(<>c.<>9.<Main>b__0_0));   // аллокация один раз за всё время
```

Три случая, которые надо различать:

| Что захватывает лямбда | Что генерируется | Аллокаций на вызов |
|---|---|---|
| Ничего | Метод в синглтоне `<>c`, делегат в статическом поле `<>9__X` | 0 (после первого раза) |
| Только `this` | Приватный instance-метод самого класса, display class не нужен | 1 (делегат, **не** кешируется) |
| Локальные переменные | `<>c__DisplayClassN_0` (class) + метод в нём | 2 и больше: display class + делегат |
| Переменные из нескольких уровней вложенности | Цепочка display class'ов со ссылками друг на друга | По одному объекту на уровень + делегат |

Случай «только `this`» коварен: аллокация display class'а нет, но новый делегат создаётся при **каждом** проходе, потому что кешировать его в статике нельзя — он привязан к конкретному экземпляру.

> [!info] Группы методов
> С C# 11 компилятор кеширует и преобразование группы методов: `Func<string, int> f = int.Parse;` создаёт делегат один раз и кладёт в статический кеш. До C# 11 это была аллокация на каждое преобразование — типичный источник мусора в LINQ-цепочках вида `.Select(Convert.ToInt32)`.

## static лямбды (C# 9) и опциональные параметры (C# 12)

`static` перед лямбдой работает так же, как перед локальной функцией: запрещает любой захват, включая `this`.

```csharp
public sealed class Prices
{
    private decimal _vat = 0.2m;

    public decimal[] Apply(decimal[] input)
    {
        var vat = _vat;
        // static гарантирует: ни this, ни vat не попадут внутрь
        return input.Select(static x => Math.Round(x, 2)).ToArray();

        // Это НЕ скомпилируется: CS8820
        // return input.Select(static x => x * (1 + vat)).ToArray();
    }
}
```

`static`-лямбда без захвата кешируется в `<>c.<>9__X` — то есть даёт нулевые аллокации в цикле.

C# 12 добавил лямбдам значения параметров по умолчанию и `params`:

```csharp
var increment = (int value, int by = 1) => value + by;
Console.WriteLine($"{increment(10)} {increment(10, 5)}");
// Вывод: 11 15

var join = (params string[] parts) => string.Join('-', parts);
Console.WriteLine(join("a", "b", "c"));
// Вывод: a-b-c
```

Важная тонкость: значение по умолчанию **не является захватом**. Оно обязано быть константой времени компиляции и уезжает в метаданные синтезированного типа делегата (`<>f__AnonymousDelegate0`), а не в display class. Поэтому `var f = (int x = someLocal) => x;` не скомпилируется, и `Func<int, int>` такую лямбду принять не сможет — у `Func` нет опциональных параметров, тип выводится только через `var`.

C# 14 разрешил модификаторы параметров без указания типа: `var tryGet = (ref int slot, out bool ok) => { ok = true; return slot; };` — раньше пришлось бы писать полные типы.

## Захват переменной цикла

Классический вопрос собеседования:

```csharp
var actions = new List<Action>();

for (var i = 0; i < 3; i++)
    actions.Add(() => Console.Write(i));

foreach (var a in actions) a();
// Вывод: 333
```

Переменная `i` в `for` объявлена **один раз на весь цикл** — значит, display class тоже один, и все три лямбды смотрят в одно поле. К моменту выполнения там уже `3` (условие выхода).

С `foreach` поведение другое:

```csharp
var actions = new List<Action>();

foreach (var i in new[] { 0, 1, 2 })
    actions.Add(() => Console.Write(i));

foreach (var a in actions) a();
// Вывод: 012
```

Здесь переменная итерации логически **новая на каждой итерации**, поэтому создаётся три display class'а.

> [!warning] Историческая ловушка
> До C# 5 (2012) `foreach` вёл себя как `for`: переменная итерации была одна на весь цикл, и код выше печатал `222`. Это признали ошибкой дизайна и поменяли — единственное breaking change такого масштаба в истории языка. В легаси-коде на C# 4 и старше вы встретите обходной приём `foreach (var x in src) { var copy = x; list.Add(() => copy); }`. В `for` этот приём нужен до сих пор:

```csharp
for (var i = 0; i < 3; i++)
{
    var copy = i;                       // новая переменная на итерацию
    actions.Add(() => Console.Write(copy));
}
// Вывод: 012
```

## Разделяемый display class: неочевидное продление жизни

Компилятор создаёт **один** display class на область видимости, а не на лямбду. Все захваченные из этой области переменные — его поля. Отсюда — утечка, которую невозможно увидеть глазами:

```csharp
public static class Leak
{
    public static Func<int>? Retained;

    public static void Setup()
    {
        var huge = new byte[100_000_000];   // 100 МБ
        var small = 42;

        Action useHuge = () => Console.WriteLine(huge.Length);
        useHuge();                          // делегат больше не нужен

        Retained = () => small;             // захватывает ТОЛЬКО small
    }
}

Leak.Setup();
GC.Collect();
GC.WaitForPendingFinalizers();
Console.WriteLine(GC.GetTotalMemory(true) / 1_000_000 + " МБ");
// Вывод: около 100 МБ — массив жив
```

`huge` и `small` попали в один `<>c__DisplayClass0_0`. Долгоживущий делегат `Retained` держит ссылку на весь объект целиком, а значит и на массив. Лечится изоляцией области видимости:

```csharp
public static void SetupFixed()
{
    {
        var huge = new byte[100_000_000];
        Action useHuge = () => Console.WriteLine(huge.Length);
        useHuge();
    }                                        // отдельный блок -> отдельный display class

    var small = 42;
    Retained = () => small;
}
```

Подробнее про то, что удерживает объекты живыми, — в [[Слабые ссылки и утечки памяти в .NET]] и [[Сборка мусора (GC): как работает]].

## Захват this и утечка через события

Обращение к любому полю или методу экземпляра внутри лямбды захватывает **весь `this`**, а не поле:

```csharp
public sealed class Bus
{
    public event Action<string>? Message;
    public void Publish(string m) => Message?.Invoke(m);
}

public sealed class Widget
{
    private readonly string _name;

    public Widget(string name, Bus bus)
    {
        _name = name;
        bus.Message += m => Console.WriteLine($"{_name}: {m}");  // захвачен this
    }
}
```

`Bus` держит делегат, делегат держит `Widget`. Пока жива шина — жив каждый когда-либо созданный виджет. Правильный вариант — хранить делегат и отписываться:

```csharp
public sealed class Widget : IDisposable
{
    private readonly Bus _bus;
    private readonly Action<string> _handler;
    private readonly string _name;

    public Widget(string name, Bus bus)
    {
        _name = name;
        _bus = bus;
        _handler = OnMessage;                 // ссылка на метод, её можно отписать
        _bus.Message += _handler;
    }

    private void OnMessage(string m) => Console.WriteLine($"{_name}: {m}");

    public void Dispose() => _bus.Message -= _handler;
}
```

Отписаться от лямбды напрямую нельзя: `bus.Message -= m => ...` создаст **новый** делегат, который не равен подписанному, и `-=` молча ничего не сделает. См. [[Делегаты, события и лямбды]] и [[IDisposable, using и паттерн Dispose]].

## Главный паттерн: валидация аргументов в итераторах и async

Тело метода с `yield return` не выполняется до первого `MoveNext`. Тело `async`-метода выполняется, но исключение не летит наружу, а оседает в `Task`. Значит, наивная проверка аргументов срабатывает не там, где ожидает вызывающий:

```csharp
// ПЛОХО: исключение вылетит только при первом foreach, а не при вызове Where
public static IEnumerable<T> WhereBad<T>(IEnumerable<T> source, Func<T, bool> predicate)
{
    ArgumentNullException.ThrowIfNull(source);
    foreach (var item in source)
        if (predicate(item)) yield return item;
}

var query = WhereBad<int>(null!, x => true);   // исключения НЕТ
Console.WriteLine("дошли сюда");
foreach (var _ in query) { }                   // вот здесь ArgumentNullException
```

Решение — разделить метод на «жадную» обёртку и «ленивую» локальную функцию:

```csharp
public static IEnumerable<T> Where<T>(IEnumerable<T> source, Func<T, bool> predicate)
{
    ArgumentNullException.ThrowIfNull(source);
    ArgumentNullException.ThrowIfNull(predicate);

    return Iterator();                         // сам метод НЕ итератор -> проверки жадные

    IEnumerable<T> Iterator()
    {
        foreach (var item in source)
            if (predicate(item)) yield return item;
    }
}

try { Where<int>(null!, x => true); }
catch (ArgumentNullException e) { Console.WriteLine(e.ParamName); }
// Вывод: source
```

Тот же приём для `async` — чтобы `ArgumentException` летел синхронно, а не через `await`:

```csharp
public static Task<string> FetchAsync(HttpClient client, string url, CancellationToken ct)
{
    ArgumentNullException.ThrowIfNull(client);
    ArgumentException.ThrowIfNullOrWhiteSpace(url);

    return Core();

    async Task<string> Core()
    {
        using var response = await client.GetAsync(url, ct);
        response.EnsureSuccessStatusCode();
        return await response.Content.ReadAsStringAsync(ct);
    }
}
```

Именно так устроены реальные LINQ-операторы в `System.Linq` и методы BCL. Это самый практичный повод знать локальные функции. Про проверки аргументов — [[Защитное программирование и guard clauses]], про отложенность — [[Отложенное и немедленное выполнение]].

## Рекурсия и стек

Локальная функция рекурсивна из коробки, но стек у неё общий с методом-хозяином — примерно 1 МБ на поток по умолчанию:

```csharp
static int Depth(int n) => n == 0 ? 0 : 1 + Depth(n - 1);
// Depth(200_000) -> StackOverflowException, процесс падает без шанса поймать
```

`StackOverflowException` в .NET **нельзя перехватить** — рантайм убивает процесс. Поэтому глубокую рекурсию переписывают в цикл с явным стеком:

```csharp
static int CountNodes(TreeNode root)
{
    var stack = new Stack<TreeNode>();
    stack.Push(root);
    var count = 0;

    while (stack.TryPop(out var node))
    {
        count++;
        foreach (var child in node.Children) stack.Push(child);   // куча вместо стека
    }
    return count;
}

sealed record TreeNode(IReadOnlyList<TreeNode> Children);
```

C# не делает хвостовую оптимизацию (tail call) автоматически: IL-инструкция `tail.` существует, но Roslyn её не эмитит. См. [[Стек и куча: что где лежит]].

> [!warning] Подводные камни
> **1. Захват переменной цикла `for`.** Одна переменная на весь цикл — все делегаты видят финальное значение. В `foreach` с C# 5 переменная своя на итерацию, в `for` — нет. Копируйте в локальную переменную внутри тела.
>
> **2. Общий display class продлевает жизнь чужим объектам.** Все захваты из одной области видимости живут в одном объекте. Долгоживущий делегат, захвативший `int`, может удерживать 100-мегабайтный массив, захваченный соседней короткоживущей лямбдой. Изолируйте тяжёлые захваты отдельным блоком `{ }` или отдельным методом.
>
> **3. Утечка через `event` + лямбда с `this`.** Обращение к полю захватывает весь объект. Отписаться от лямбды невозможно — `-=` сравнивает делегаты по цели и методу, а новая лямбда создаёт новый экземпляр. Храните делегат в поле либо используйте метод-обработчик.
>
> **4. «Внезапная» аллокация в горячем пути.** Метод был без захвата и не аллоцировал; кто-то добавил в лямбду обращение к полю — появились display class и некешируемый делегат на каждый вызов. В цикле на миллион итераций это гигабайты мусора. Лечение: `static` на лямбдах и локальных функциях везде, где возможно, плюс бенчмарк с `[MemoryDiagnoser]`.
>
> **5. Локальная функция, преобразованная в делегат, теряет главное преимущество.** `Action a = Local;` превращает struct-замыкание в class-замыкание и добавляет аллокацию делегата. Если функция всё равно уезжает в делегат, разницы с лямбдой почти нет.
>
> **6. Валидация в теле итератора/async молчит.** Без разделения на обёртку и локальную функцию `ArgumentNullException` вылетит не в точке вызова, а при первом `MoveNext` или `await` — иногда через минуты и в чужом стеке.
>
> **7. Захват в `struct`-методе.** Лямбда внутри метода структуры не может захватить `this` (CS1673) — структура копируется, ссылку на неё в кучу положить нельзя. Приходится копировать нужные поля в локальные переменные.

> [!example] Как делают в бою
> **Валидация + ленивое тело.** Любой публичный метод, возвращающий `IEnumerable<T>` или `Task<T>`, оформляется как жадная обёртка с guard clauses плюс локальная функция с реальной логикой. Так написан весь `System.Linq`.
>
> **`static` по умолчанию.** В командах, где важна производительность, включают в `.editorconfig` `csharp_prefer_static_local_function = true:warning` и `dotnet_diagnostic.IDE0062.severity = warning`, чтобы компилятор ловил случайный захват.
>
> **Локальные функции вместо приватных методов-однодневок.** Если хелпер нужен ровно одному методу и оперирует его переменными — он локальная функция. Это уменьшает публичную поверхность типа и не тащит параметры через сигнатуру. Как только хелпер понадобился второму методу — выносим в приватный статический метод.
>
> **Проверка аллокаций.** В `BenchmarkDotNet` атрибут `[MemoryDiagnoser]` показывает колонку `Allocated`. Норма для горячего пути с локальными функциями — `0 B`. Любое ненулевое значение означает, что где-то родился display class или делегат. См. [[Как измерять: BenchmarkDotNet]] и [[Аллокации и как их избегать]].
>
> **Кеширование предикатов.** Вместо `list.Where(x => x.Id == id)` в цикле, где `id` меняется, в горячих местах пишут либо цикл руками, либо `static` лямбду с передачей состояния: `list.Where(static (x, state) => x.Id == state, id)` — такой перегрузки в LINQ нет, но паттерн «состояние параметром» повсеместен в `Task.Run`, `Parallel.For` и `ConcurrentDictionary.GetOrAdd`, чтобы избежать замыкания.

## Вопросы с собеседований

> [!question]- Чем локальная функция отличается от лямбды?
> Локальная функция — это метод, а лямбда — выражение, создающее объект-делегат. Отсюда все различия: у локальной функции есть имя, её можно вызвать до объявления, она поддерживает рекурсию, дженерики, `ref`/`out`/`ref struct` параметры, `yield return` и атрибуты. Definite assignment у локальной функции проверяется в точке вызова, у лямбды — в точке создания. Главное практическое отличие — стоимость: если локальная функция не преобразуется в делегат, она компилируется в приватный статический метод, а захваченные переменные попадают в **структуру**, передаваемую по `ref`. Аллокаций в куче нет. Лямбда с захватом всегда создаёт класс в куче плюс объект делегата.

> [!question]- Что напечатает цикл `for` с лямбдами, добавляющими `i` в список, и почему?
> Напечатает финальное значение счётчика столько раз, сколько было итераций (`333` для `i < 3`). Переменная `i` в `for` объявлена один раз на весь цикл, поэтому компилятор создаёт один display class, поле `i` в нём общее для всех делегатов, и к моменту выполнения там уже значение, при котором цикл завершился. В `foreach` начиная с C# 5 переменная итерации логически создаётся заново каждую итерацию, поэтому display class'ов будет три и вывод станет `012`. До C# 5 `foreach` вёл себя как `for` — это одно из немногих намеренных breaking changes языка.

> [!question]- Зачем нужен модификатор `static` у локальной функции и лямбды?
> Он запрещает захват чего-либо из окружающего контекста, включая `this`. Это превращает намерение «здесь ничего не захватывается» в проверяемый компилятором контракт (ошибка CS8421/CS8820 при попытке захвата). Практическая польза: гарантия отсутствия display class и, для лямбды, гарантия кеширования делегата в статическом поле — то есть ноль аллокаций в цикле. Плюс защита от регрессии: если при рефакторинге кто-то обратится к полю экземпляра, код просто не соберётся вместо того, чтобы тихо начать аллоцировать.

> [!question]- Почему валидацию аргументов в итераторе выносят в отдельный метод?
> Потому что тело метода с `yield return` компилируется в конечный автомат и не выполняется до первого `MoveNext()`. Вызов `Foo(null)` вернёт объект-перечислитель без единой проверки, а `ArgumentNullException` вылетит позже — при `foreach`, часто в совсем другом месте стека и через заметное время. Решение: сделать сам метод обычным (не итератором), выполнить проверки жадно и вернуть результат вложенной локальной функции-итератора. Для `async` то же самое: без разделения исключение попадёт в возвращаемый `Task` и всплывёт только при `await`.

> [!question]- Может ли лямбда, захватившая маленькую переменную, удерживать в памяти большой объект?
> Да, и это классический источник утечек. Компилятор создаёт один display class на область видимости, а не на каждую лямбду. Если в одном методе первая лямбда захватила гигантский массив, а вторая — только `int`, оба значения станут полями одного объекта. Пока жив делегат второй лямбды, жив весь display class, а значит и массив. Диагностируется дампом памяти: в пути удержания видно тип с именем вида `<Method>c__DisplayClass0_0`. Лечится изоляцией тяжёлого захвата в отдельный блок или метод.

> [!question]- Что происходит с делегатом лямбды, которая ничего не захватывает?
> Компилятор помещает её тело в метод синглтон-класса `<>c` и кеширует созданный делегат в статическом поле `<>9__N`. Код `Run(() => ...)` превращается в `Run(<>c.<>9__0_0 ??= new Action(<>c.<>9.<M>b__0_0))` — аллокация происходит один раз за жизнь приложения. Если лямбда захватывает только `this`, кеширование невозможно (делегат привязан к экземпляру), и новый объект делегата создаётся при каждом преобразовании, хотя display class не нужен. С C# 11 такое же кеширование появилось у преобразования групп методов.

> [!question]- Захватывается переменная или её значение?
> Переменная. После захвата она физически становится полем сгенерированного объекта, и все, кто её видит — и внешний код, и все замыкания, — работают с одним и тем же полем. Поэтому изменение переменной после создания лямбды видно внутри лямбды, и наоборот. Единственное исключение по ощущению — значимые типы, захваченные локальной функцией без преобразования в делегат: они лежат в структуре на стеке, но семантика та же (передача по `ref`).

> [!question]- Почему нельзя отписаться от события, подписавшись лямбдой?
> `-=` удаляет из списка вызова делегат, равный переданному. Равенство делегатов определяется парой «целевой объект + метод». Каждое вычисление лямбда-выражения с захватом создаёт новый display class и новый делегат с новой целью, поэтому `bus.Event -= m => Handle(m)` сравнивает несовпадающие цели и молча не делает ничего — исключения не будет, подписка останется. Правильно: сохранить делегат в поле при подписке и передать его же в `-=`, либо подписываться методом.

## Задачи

### Задача 1. Ноль аллокаций

Дан метод, который в цикле фильтрует массив и аллоцирует в куче на каждом вызове. Перепишите его так, чтобы `[MemoryDiagnoser]` показывал `0 B`, сохранив выделение логики фильтра в отдельную функцию.

```csharp
public int SumAbove(int[] data, int threshold)
{
    Func<int, bool> ok = x => x > threshold;   // display class + делегат на каждый вызов
    var total = 0;
    foreach (var x in data) if (ok(x)) total += x;
    return total;
}
```

> [!success]- Решение
> ```csharp
> public int SumAbove(int[] data, int threshold)
> {
>     var total = 0;
>     foreach (var x in data)
>         if (IsOk(x, threshold)) total += x;
>     return total;
>
>     // static: компилятор гарантирует отсутствие захвата и display class
>     static bool IsOk(int value, int threshold) => value > threshold;
> }
> ```
> Порог передан параметром, а не захвачен, поэтому нет ни структуры-замыкания, ни делегата. Вызов компилируется в обычный `call` приватного статического метода и почти наверняка будет заинлайнен JIT. Если оставить `bool IsOk(int value) => value > threshold;` без `static`, аллокаций в куче всё равно не будет (замыкание станет структурой на стеке), но исчезнет гарантия и шанс на инлайнинг снизится.

### Задача 2. Итератор с честной валидацией

Напишите метод `Chunk<T>(IEnumerable<T> source, int size)`, который лениво разбивает последовательность на списки по `size` элементов. Требование: `ArgumentNullException` и `ArgumentOutOfRangeException` должны бросаться **в момент вызова**, а не при первом переборе.

> [!success]- Решение
> ```csharp
> public static IEnumerable<List<T>> Chunk<T>(IEnumerable<T> source, int size)
> {
>     ArgumentNullException.ThrowIfNull(source);
>     ArgumentOutOfRangeException.ThrowIfLessThan(size, 1);
>
>     return Iterator();
>
>     IEnumerable<List<T>> Iterator()
>     {
>         var buffer = new List<T>(size);
>         foreach (var item in source)
>         {
>             buffer.Add(item);
>             if (buffer.Count == size)
>             {
>                 yield return buffer;
>                 buffer = new List<T>(size);   // новый буфер: отданный список у вызывающего
>             }
>         }
>         if (buffer.Count > 0) yield return buffer;
>     }
> }
>
> foreach (var c in Chunk(Enumerable.Range(1, 7), 3))
>     Console.Write($"[{string.Join(',', c)}]");
> // Вывод: [1,2,3][4,5,6][7]
>
> try { Chunk<int>(null!, 3); }
> catch (ArgumentNullException e) { Console.WriteLine(e.ParamName); }
> // Вывод: source
> ```
> Внешний метод не содержит `yield`, поэтому он обычный и выполняется жадно. Ленивая часть спрятана в локальную функцию-итератор, которая захватывает `source` и `size` из внешнего метода. Обратите внимание на новый буфер после каждого `yield return`: переиспользование одного списка — типичная ошибка, вызывающий получил бы одну и ту же ссылку.

### Задача 3. Найти утечку

Приложение съедает память. Дамп показывает живые массивы по 50 МБ, путь удержания идёт через `Cache.Formatter` -> `<Configure>c__DisplayClass2_0`. Найдите причину и исправьте.

```csharp
public static class Cache
{
    public static Func<int, string>? Formatter;

    public static void Configure(int width)
    {
        var scratch = new byte[50_000_000];   // временный буфер для прогрева
        Warmup(scratch);

        Formatter = n => n.ToString().PadLeft(width, '0');
    }

    private static void Warmup(byte[] buffer) { /* ... */ }
}
```

> [!success]- Решение
> ```csharp
> public static void Configure(int width)
> {
>     Prepare();                    // тяжёлый буфер живёт в чужой области видимости
>
>     Formatter = n => n.ToString().PadLeft(width, '0');
>
>     static void Prepare()
>     {
>         var scratch = new byte[50_000_000];
>         Warmup(scratch);
>     }
> }
> ```
> Причина: `scratch` и `width` объявлены в одной области видимости. Хотя лямбда обращается только к `width`, компилятор кладёт **обе** переменные в один `<>c__DisplayClass2_0`, а долгоживущий `Formatter` держит на него ссылку. Массив никогда не собирается. Вынос тяжёлой части в отдельную (`static`) локальную функцию или просто в блок `{ }` даёт `scratch` собственную область и собственное время жизни. Проверить исправление можно так же, как искали проблему: `GC.Collect()` плюс `GC.GetTotalMemory(true)`.

### Задача 4. Рекурсия без стека

Напишите локальную функцию, обходящую дерево каталогов и считающую суммарный размер файлов. Условие: глубина дерева может быть 100 000 уровней, `StackOverflowException` недопустим.

> [!success]- Решение
> ```csharp
> public static long TotalSize(string root)
> {
>     ArgumentException.ThrowIfNullOrWhiteSpace(root);
>
>     var pending = new Stack<string>();
>     pending.Push(root);
>     long total = 0;
>
>     while (pending.TryPop(out var dir))
>     {
>         total += SizeOfFiles(dir);
>         foreach (var sub in Directory.EnumerateDirectories(dir))
>             pending.Push(sub);
>     }
>
>     return total;
>
>     static long SizeOfFiles(string dir)
>     {
>         long sum = 0;
>         foreach (var file in Directory.EnumerateFiles(dir))
>             sum += new FileInfo(file).Length;
>         return sum;
>     }
> }
> ```
> Явный `Stack<string>` в куче заменяет стек вызовов: его размер ограничен доступной памятью, а не мегабайтом на поток. `StackOverflowException` в .NET перехватить нельзя — рантайм завершает процесс, поэтому «попробуем рекурсию и поймаем» не вариант. Локальная функция `SizeOfFiles` сделана `static`: она не нуждается в захвате и не создаёт замыкания в цикле.

## Итог

- Локальная функция — это метод, а не делегат. Без преобразования в делегат она не аллоцирует ничего: захват уезжает в **структуру** на стеке, передаваемую по `ref`.
- Лямбда с захватом локальных переменных всегда даёт минимум два объекта в куче: display class и делегат. Лямбда без захвата кешируется в статическом поле, лямбда с захватом только `this` не кешируется.
- Пишите `static` у лямбд и локальных функций везде, где можно: это проверяемая компилятором гарантия отсутствия захвата.
- Захватывается переменная, а не значение. Display class один на область видимости, поэтому долгоживущий делегат может удерживать чужие тяжёлые объекты.
- `for` захватывает одну переменную на весь цикл (`333`), `foreach` с C# 5 — новую на итерацию (`012`).
- Валидация аргументов в итераторах и `async`-методах обязана жить в жадной обёртке, а логика — в локальной функции. Иначе исключение прилетит не туда и не тогда.
- Отписаться от события, подписанного лямбдой, невозможно: храните делегат в поле.
