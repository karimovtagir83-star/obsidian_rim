# Pattern matching

> [!abstract] Коротко
> Паттерн — это проверка «подходит ли значение под форму» плюс попутное извлечение частей. С C# 7 паттерны выросли из `is Type x` в отдельный мини-язык: константные, реляционные (`> 100`), логические (`and`/`or`/`not`), свойственные (`{ Status: Paid }`), позиционные (через `Deconstruct`) и списочные (`[_, .., last]`). Работают они в трёх местах: `is`-выражение, `switch`-инструкция и `switch`-выражение. Практическая выгода — код, где условие читается как утверждение на естественном языке, а компилятор проверяет полноту разбора.

## Зачем это нужно

Три типовых куска кода, которые паттерны сокращают радикально.

```csharp
// Было: проверка типа, приведение, проверка на null — три шага
if (value != null && value is string)
{
    var s = (string)value;
    if (s.Length > 3) Use(s);
}
// Стало: одно выражение
if (value is string { Length: > 3 } s) Use(s);

// Было: лестница if-else по диапазонам
// Стало:
var category = age switch
{
    < 0 => throw new ArgumentOutOfRangeException(nameof(age)),
    < 18 => "несовершеннолетний",
    < 65 => "взрослый",
    _ => "пенсионер"
};

// Было: проверки на null в четыре строки
// Стало:
if (order is { Customer.Address.City: "Ташкент" }) { }
```

И главное: `switch`-выражение заставляет обработать все случаи. Если добавить новое значение в enum и забыть про него, компилятор предупредит — с цепочкой `if` этого не бывает.

## Виды паттернов

### Константный и тип

```csharp
// Константный: сравнение с литералом, константой или enum-значением
if (code is 404) { }
if (status is OrderStatus.Paid) { }
if (name is null) { }              // предпочтительнее == null: не вызывает
                                   // переопределённый оператор ==

// Типовой: проверка типа с объявлением переменной
object value = "текст";
if (value is string s) Console.WriteLine(s.Length);
if (value is not string) Console.WriteLine("не строка");    // C# 9
```

`is null` и `is not null` — рекомендуемая форма проверки: она не зависит от перегрузки `==`, работает для дженериков и не создаёт неожиданностей с `Nullable<T>`.

### Реляционный и логический (C# 9)

```csharp
bool IsValidPercent(int x) => x is >= 0 and <= 100;
bool IsSpecialCode(int c) => c is 400 or 404 or 409;
bool IsNotEmpty(string? s) => s is not (null or "");

// Читается как утверждение и не даёт опечататься в имени переменной:
// сравни с (x >= 0 && y <= 100) — здесь опечатку не видно
```

Порядок приоритета внутри паттернов: `not` → `and` → `or`. Скобки разрешены и часто нужны для читаемости.

### Свойственный (C# 8, расширенный в C# 10)

```csharp
record Address(string City, string Street);
record Customer(string Name, Address Address, bool IsVip);
record Order(long Id, decimal Total, Customer Customer, OrderStatus Status);

// Проверка нескольких свойств сразу
if (order is { Status: OrderStatus.Paid, Total: > 1000 }) { }

// Вложенность через точку — C# 10; до этого нужны были вложенные фигурные скобки
if (order is { Customer.Address.City: "Ташкент", Customer.IsVip: true }) { }

// Пустой паттерн { } означает «не null»
if (order is { }) { }                     // эквивалент order is not null

// Извлечение значений по ходу проверки
if (order is { Total: > 1000 and < 5000, Customer.Name: { Length: > 0 } name })
    Console.WriteLine($"Крупный заказ клиента {name}");
```

Ключевое свойство: **проверка свойства через паттерн безопасна к null**. `order is { Customer.Address.City: "X" }` не бросит `NullReferenceException`, если `Customer` или `Address` равны null — паттерн просто не совпадёт. Это заменяет цепочку `?.` с последующей проверкой.

### Позиционный

Работает для кортежей и для типов с методом `Deconstruct` (у `record` он есть автоматически):

```csharp
var point = (X: 3, Y: 0);
string where = point switch
{
    (0, 0) => "начало координат",
    (_, 0) => "на оси X",
    (0, _) => "на оси Y",
    var (x, y) when x == y => "на диагонали",
    _ => "где-то ещё"
};

// Свой тип с деконструкцией
record Money(decimal Amount, string Currency);
static string Describe(Money m) => m switch
{
    (0, _) => "ноль",
    (< 0, var cur) => $"долг в {cur}",
    (var a, "UZS") when a > 1_000_000 => "крупная сумма в сумах",
    _ => "обычная сумма"
};
```

Сопоставление кортежей особенно полезно для разбора комбинаций состояний — вместо вложенных `if`:

```csharp
static string Decide(bool isPaid, bool isShipped) => (isPaid, isShipped) switch
{
    (true, true) => "завершён",
    (true, false) => "готов к отправке",
    (false, true) => "ошибка данных",       // невозможное состояние явно названо
    (false, false) => "ожидает оплаты"
};
```

### Списочный (C# 11)

```csharp
int[] data = [1, 2, 3, 4, 5];

Console.WriteLine(data is [1, .., 5]);          // True: начинается с 1, кончается 5
Console.WriteLine(data is [_, _, _, _, _]);      // True: ровно 5 элементов
Console.WriteLine(data is []);                   // False: пустой?

// Извлечение с срезом
if (data is [var first, .. var middle, var last])
    Console.WriteLine($"{first} {middle.Length} {last}");   // Вывод: 1 3 5

// Разбор команды — типичное применение
static string Run(string[] args) => args switch
{
    [] => "укажите команду",
    ["help"] => "справка",
    ["add", var item] => $"добавляю {item}",
    ["remove", var item, "--force"] => $"удаляю {item} принудительно",
    [var unknown, ..] => $"неизвестная команда {unknown}"
};
```

Списочные паттерны работают для массивов, `List<T>`, `Span<T>` и любого типа со счётчиком и индексатором — то есть по той же логике «по форме», что и `foreach`.

### `var` и отбрасывание

```csharp
// var-паттерн совпадает ВСЕГДА и просто присваивает — полезен для промежуточных вычислений
if (GetOrder() is var order && order.Total > 0) { }

// _ — отбрасывание: значение неважно
if (tuple is (_, > 0)) { }

// В switch _ означает «всё остальное» (не то же, что default в switch-инструкции,
// но роль похожа)
```

## Три места применения

```csharp
// 1. is-выражение — булев результат
if (value is int i and > 0) { }

// 2. switch-инструкция — ветвление без результата
switch (order.Status)
{
    case OrderStatus.New or OrderStatus.Pending:
        await ReserveAsync(order);
        break;
    case OrderStatus.Paid when order.Total > 1_000_000:
        await NotifyManagerAsync(order);
        break;
    case OrderStatus.Paid:
        await ShipAsync(order);
        break;
    default:
        throw new InvalidOperationException($"Неожиданный статус {order.Status}");
}

// 3. switch-выражение — возвращает значение
decimal fee = order switch
{
    { Total: <= 0 } => throw new ArgumentException("Некорректная сумма"),
    { Customer.IsVip: true } => 0m,
    { Total: > 1_000_000 } => order.Total * 0.005m,
    _ => order.Total * 0.02m
};
```

### `when`-фильтры

`when` добавляет произвольное условие к паттерну — то, что нельзя выразить формой:

```csharp
static string Check(Order o) => o switch
{
    { Status: OrderStatus.Paid } when DateTimeOffset.UtcNow - o.PaidAt > TimeSpan.FromDays(30)
        => "оплата давно, возврат невозможен",
    { Status: OrderStatus.Paid } => "оплачен",
    _ => "не оплачен"
};
```

Порядок ветвей важен: проверяются сверху вниз, срабатывает первая подходящая. Компилятор предупредит о ветви, которая недостижима (полностью перекрыта предыдущей), но не о ветви, которая перекрыта частично.

### Полнота разбора

```csharp
enum Level { Low, Medium, High }

// Предупреждение CS8509: не все значения обработаны
string Describe(Level level) => level switch
{
    Level.Low => "низкий",
    Level.Medium => "средний"
    // High не обработан → при передаче High будет UnreachableException/SwitchExpressionException
};
```

`switch`-выражение обязано вернуть значение, поэтому компилятор проверяет полноту: если совпадений нет, в рантайме бросается `SwitchExpressionException`. Это лучше, чем тихое `default`, потому что превращает пропущенный случай в громкую ошибку.

Практика: для enum и закрытых иерархий **не писать `_ => ...` вслепую**. Без него компилятор предупреждает при добавлении нового значения — это самая полезная страховка от «забыли обработать новый статус». Если ветвь по умолчанию всё же нужна, пусть она бросает исключение с внятным сообщением, а не возвращает «пустое» значение.

## Паттерны и полиморфизм

Соблазн: `switch` по типу вместо виртуального метода.

```csharp
// Так делать в доменной модели не надо
decimal CalculateArea(Shape shape) => shape switch
{
    Circle c => Math.PI * c.Radius * c.Radius,
    Rectangle r => r.Width * r.Height,
    Triangle t => t.Base * t.Height / 2,
    _ => throw new NotSupportedException()
};
```

Проблема в том, что добавление новой фигуры требует правки этого метода — и всех похожих `switch` в других местах. Виртуальный метод `Shape.Area()` решает это в одном месте (принцип открытости/закрытости, [[SOLID]]).

Когда `switch` по типу всё-таки правильный выбор:

- иерархия **закрыта** и контролируется тобой (например, набор результатов `Success`/`NotFound`/`Conflict`);
- логика принадлежит не типу, а внешнему потребителю (отображение в HTTP-код, форматирование, маппинг в DTO) — тогда добавлять её в доменный тип было бы нарушением разделения ответственностей;
- нужен разбор внешних данных, где типы приходят «сырыми».

Именно поэтому `switch` по типу естественно смотрится в слое API (Result → `IResult`) и подозрительно — в доменной логике.

## Как это работает под капотом

Компилятор не превращает `switch` в цепочку `if` подряд. Он строит **дерево решений**: группирует проверки, вычисляет каждое подвыражение один раз, для константных `int`-паттернов может построить таблицу переходов, для строк — хеш-таблицу. Поэтому `switch`-выражение на 20 ветвей не медленнее, чем несколько `if`, а часто быстрее.

Что стоит знать про производительность:

- проверка типа (`is Circle`) — это одна инструкция `isinst` плюс проверка на null, дёшево;
- сопоставление кортежей не создаёт объектов: кортежи — структуры (`ValueTuple`), и компилятор их обычно раскладывает по регистрам;
- `when` с вызовом метода — обычный вызов, и он выполняется столько раз, сколько ветвей его содержат: тяжёлое условие в `when` нескольких ветвей лучше вычислить заранее;
- паттерны над значимыми типами через `object` вызывают распаковку — но это цена не паттернов, а самой упаковки ([[Value types vs Reference types]]).

> [!warning] Подводные камни
> - **Порядок ветвей.** Более общий паттерн, поставленный выше, «съедает» частные случаи. Компилятор предупредит только о полностью недостижимой ветви.
> - **`_ => ...` в switch по enum.** Убивает проверку полноты: при добавлении значения в enum компилятор промолчит, а поведение станет неверным. Лучше не писать `_` вовсе или бросать в нём исключение.
> - **`is` с обратной логикой.** `if (!(x is string s))` — переменная `s` внутри блока недоступна (она не определена на этом пути), и код не скомпилируется как ожидалось. Правильно: `if (x is not string s) return;` — после этого `s` доступна ниже.
> - **`when` с побочными эффектами.** Условия вычисляются в процессе сопоставления, порядок и число вызовов неочевидны. В `when` — только чистые проверки.
> - **Сопоставление `double` с константами.** `x is 0.1` наследует все проблемы сравнения плавающей точки; для дробных используются реляционные паттерны с допуском.
> - **Слишком умный паттерн.** Вложенность из свойств, срезов и `when` на пять строк читается хуже, чем три отдельных `if`. Паттерны существуют ради читаемости — если она пропала, надо остановиться.

> [!example] Как делают в бою
> Самое частое применение — отображение результата операции в HTTP-ответ на границе API:
> ```csharp
> return result switch
> {
>     { IsSuccess: true, Value: var order } => TypedResults.Ok(order),
>     { Error: NotFoundError } => TypedResults.NotFound(),
>     { Error: ValidationError v } => TypedResults.ValidationProblem(v.Errors),
>     { Error: ConflictError c } => TypedResults.Conflict(c.Message),
>     _ => TypedResults.Problem()
> };
> ```
> Второе — замена лестниц условий в бизнес-правилах: расчёт скидок, тарифов, приоритетов. Правило в виде `{ Total: > 1_000_000, Customer.IsVip: true } => 0.05m` читается почти как формулировка из требований, и его легко сверить с постановкой.
> Третье — разбор входных данных: аргументов командной строки списочными паттернами, сообщений брокера по типу события, ответов внешних API по коду и телу.
> Чего в бою не делают: `switch` по типу внутри доменной модели там, где должен быть виртуальный метод, и «умные» многострочные паттерны в горячем коде без бенчмарка.

## Вопросы с собеседований

> [!question]- Чем `switch`-выражение отличается от `switch`-инструкции?
> Инструкция — управляющая конструкция: она выполняет ветви, требует `break`, допускает несколько инструкций в секции и не обязана быть полной. Выражение возвращает значение, поэтому синтаксис другой (`=>` вместо `case:`, запятые вместо `break`), в ветви допускается только выражение, и компилятор проверяет полноту разбора: если ни один паттерн не подошёл, в рантайме бросается `SwitchExpressionException`. Практическая разница в применении: выражение — когда нужно получить значение (маппинг, расчёт, выбор стратегии), инструкция — когда нужно выполнить разные действия, особенно асинхронные или многострочные. Ещё одно отличие: в выражении нет провала между ветвями (fall-through) и нет `goto case`, что убирает целый класс ошибок.

> [!question]- Как паттерны помогают с null?
> Несколькими способами. `is null` и `is not null` — проверки, не зависящие от перегрузки оператора `==`, поэтому они надёжнее для типов, где `==` переопределён (и обязательны в дженерик-коде). Пустой свойственный паттерн `{ }` означает «не null». Свойственные паттерны с вложенностью безопасны к null на любом уровне: `order is { Customer.Address.City: "X" }` не бросит исключение, если промежуточные ссылки пусты — паттерн просто не совпадёт, что заменяет цепочку `?.` с последующей проверкой результата. И в `switch`-выражении ветвь `null => ...` позволяет обработать отсутствие значения наравне с остальными случаями, вместо отдельного `if` сверху. При включённых nullable reference types компилятор ещё и учитывает паттерны в анализе потока: после `if (x is not null)` он знает, что дальше `x` не null.

> [!question]- Когда `switch` по типу — плохая идея?
> Когда логика принадлежит самим типам и иерархия открыта для расширения. Тогда каждое добавление наследника требует правки всех `switch` по этой иерархии — это прямое нарушение принципа открытости/закрытости, и компилятор о пропущенном месте не скажет (особенно если есть ветвь `_`). Правильное решение — виртуальный метод или интерфейс: поведение живёт рядом с данными и добавляется вместе с новым типом. `switch` по типу оправдан, когда иерархия закрыта и известна целиком (результаты операции, узлы разобранного дерева, набор событий), и особенно когда логика принадлежит потребителю, а не типу: перевод результата в HTTP-код, форматирование для конкретного канала, маппинг в DTO — помещать это в доменный тип было бы хуже.

> [!question]- Что даёт проверка полноты в `switch`-выражении?
> Компилятор анализирует, покрывают ли паттерны все возможные значения, и выдаёт предупреждение CS8509, если нет. Для `bool`, кортежей из `bool`, enum и закрытых иерархий это означает, что при добавлении нового варианта код перестанет компилироваться чисто — и ты узнаешь обо всех местах, которые нужно обновить, во время сборки, а не от пользователя. Это одна из немногих в C# форм «алгебраических типов данных» на практике. Важная оговорка: ветвь `_ => ...` отключает эту проверку, потому что формально покрывает всё, поэтому её не стоит добавлять машинально. Для enum есть дополнительная тонкость: значение можно привести из любого целого (`(Level)999`), поэтому полностью «полным» разбор enum не бывает — компилятор предупреждает об этом, и разумный компромисс — ветвь по умолчанию, бросающая исключение с самим значением в сообщении.

## Задачи

### Задача 1. Переписать лестницу условий

```csharp
static string GetShippingCost(Order order)
{
    if (order == null) throw new ArgumentNullException(nameof(order));
    if (order.Customer != null && order.Customer.IsVip) return "бесплатно";
    if (order.Total > 500_000) return "бесплатно";
    if (order.Customer != null && order.Customer.Address != null
        && order.Customer.Address.City == "Ташкент") return "10000";
    return "25000";
}
```

> [!success]- Решение
> ```csharp
> static string GetShippingCost(Order? order) => order switch
> {
>     null => throw new ArgumentNullException(nameof(order)),
>     { Customer.IsVip: true } or { Total: > 500_000 } => "бесплатно",
>     { Customer.Address.City: "Ташкент" } => "10000",
>     _ => "25000"
> };
> ```
> Что изменилось: проверки на null промежуточных объектов исчезли — вложенный свойственный паттерн не совпадает, если по пути встретился null, вместо того чтобы бросать исключение; два независимых условия «бесплатно» объединены через `or` в одну ветвь; порядок ветвей задаёт приоритет правил явно и сверху вниз, как в постановке задачи. Обрати внимание, что параметр стал `Order?` — это честно отражает, что метод принимает null и сам бросает исключение.

### Задача 2. Разобрать команду

Реализуй разбор аргументов CLI: `list`, `add <текст>`, `done <номер>`, `remove <номер> [--force]`, всё остальное — ошибка.

> [!success]- Решение
> ```csharp
> static string Handle(string[] args) => args switch
> {
>     [] or ["list"] => "показать список",
>     ["add", .. var rest] when rest.Length > 0 => $"добавить: {string.Join(' ', rest)}",
>     ["done", var n] when int.TryParse(n, out var num) => $"отметить {num}",
>     ["remove", var n, "--force"] when int.TryParse(n, out var num) => $"удалить {num} без подтверждения",
>     ["remove", var n] when int.TryParse(n, out var num) => $"удалить {num}",
>     [var cmd, ..] => $"неизвестная команда: {cmd}",
>     _ => "ошибка"
> };
>
> Console.WriteLine(Handle(["add", "купить", "хлеб"]));   // добавить: купить хлеб
> Console.WriteLine(Handle(["remove", "3", "--force"]));   // удалить 3 без подтверждения
> ```
> Ключевые приёмы: срез `.. var rest` собирает «всё остальное» — так `add` принимает многословный текст; `when int.TryParse(...)` проверяет то, что нельзя выразить формой; более специфичная ветвь `remove` с флагом стоит **выше** общей, иначе она была бы недостижима. Последняя ветвь `_` формально нужна компилятору для полноты, хотя `[var cmd, ..]` покрывает все непустые массивы — предыдущая ветвь `[]` покрывает пустой, но компилятор не всегда доказывает это самостоятельно.

### Задача 3. Найти ошибку

```csharp
enum PaymentStatus { Created, Authorized, Captured, Refunded }

static bool CanRefund(PaymentStatus status) => status switch
{
    PaymentStatus.Captured => true,
    _ => false
};
```

Через полгода в enum добавили `PartiallyCaptured`, и возвраты по таким платежам перестали работать. Что было сделано неправильно и как надо?

> [!success]- Решение
> Ошибка не в логике, а в ветви `_ => false`: она отключает проверку полноты, поэтому при добавлении нового значения компилятор ничего не сказал, и новый статус тихо попал в «нельзя вернуть».
> ```csharp
> static bool CanRefund(PaymentStatus status) => status switch
> {
>     PaymentStatus.Captured or PaymentStatus.PartiallyCaptured => true,
>     PaymentStatus.Created or PaymentStatus.Authorized or PaymentStatus.Refunded => false,
>     _ => throw new ArgumentOutOfRangeException(nameof(status), status, "Неизвестный статус платежа")
> };
> ```
> Теперь все известные значения перечислены явно, и добавление нового даёт предупреждение CS8509 при сборке (а с `TreatWarningsAsErrors` — ошибку), то есть заставляет принять решение осознанно. Ветвь `_` оставлена, но бросает исключение с самим значением — это нужно потому, что enum в C# может содержать значение, отсутствующее в объявлении: `(PaymentStatus)999` компилируется и приходит, например, из базы данных или из десериализации. Подробнее об этом — [[Записи (record) и структуры]].

## Итог

- Паттерн — проверка формы значения плюс извлечение частей; работает в `is`, `switch`-инструкции и `switch`-выражении.
- Виды: константный, типовой, реляционный (`> 100`), логический (`and`/`or`/`not`), свойственный (`{ A.B: x }`), позиционный (через `Deconstruct`), списочный (`[first, .., last]`), `var` и `_`.
- Вложенные свойственные паттерны безопасны к null: при null по пути паттерн просто не совпадает.
- `is null`/`is not null` надёжнее `== null`: не зависят от перегрузки оператора.
- `switch`-выражение проверяет полноту разбора — не добавляй `_` машинально, это отключает страховку.
- Порядок ветвей = приоритет правил; более общий паттерн выше перекрывает частные.
- `switch` по типу уместен для закрытых иерархий и логики потребителя; в доменной модели вместо него — виртуальный метод.
