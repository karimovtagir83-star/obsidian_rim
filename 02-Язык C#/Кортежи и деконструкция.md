# Кортежи и деконструкция

> [!abstract] Коротко
> Кортеж (tuple) — это лёгкий составной тип «несколько значений в одном», который не требует объявления класса. С C# 7 в языке используется `System.ValueTuple` — структура с изменяемыми полями `Item1..Item8`, а имена элементов (`(int Code, string Text)`) существуют только на этапе компиляции. Деконструкция — обратная операция: разложить объект на переменные, `var (a, b) = point`. Кортежи отлично работают внутри метода и в приватном API и плохо — в публичном контракте, где лучше `record`.

## Зачем это нужно

До C# 7 «вернуть из метода два значения» означало один из трёх плохих вариантов:

```csharp
// 1. out-параметры: метод нельзя использовать в LINQ, порядок аргументов неочевиден
public bool TryParseRange(string s, out int from, out int to) { /* ... */ }

// 2. System.Tuple: аллокация в куче и нечитаемые Item1/Item2
public Tuple<int, int> ParseRange(string s) => Tuple.Create(1, 10);
var r = ParseRange("1-10");
Console.WriteLine(r.Item1);  // что такое Item1? непонятно без документации

// 3. одноразовый класс на 5 строк ради одного метода
private sealed class RangeResult { public int From; public int To; }
```

C# 7 добавил кортежи в *синтаксис языка*: тип `(int From, int To)`, литерал `(1, 10)` и деконструкцию. Итог — читаемый код без аллокаций:

```csharp
public (int From, int To) ParseRange(string s)
{
    var parts = s.Split('-');
    return (int.Parse(parts[0]), int.Parse(parts[1]));
}

var (from, to) = ParseRange("1-10");
Console.WriteLine($"{from}..{to}");   // Вывод: 1..10
```

## ValueTuple против System.Tuple

`System.Tuple<...>` появился в .NET 4.0 и остался в BCL, но новый код его не использует.

| Признак | `System.ValueTuple<...>` | `System.Tuple<...>` |
|---|---|---|
| Категория типа | `struct` (value type) | `class` (reference type) |
| Аллокация | на стеке / инлайн в объекте-владельце | всегда в куче, плюс работа GC |
| Изменяемость | **mutable** — публичные поля | immutable — только `get`-свойства |
| Члены | публичные **поля** `Item1..Item7`, `Rest` | публичные **свойства** `Item1..Item7`, `Rest` |
| Именованные элементы | да, но только на уровне компилятора | нет, всегда `Item1` |
| Синтаксис языка | `(int, string)`, литерал `(1, "a")` | только `new Tuple<...>` / `Tuple.Create` |
| Деконструкция | встроенная | есть `Deconstruct` (с .NET Core 2.0) |
| Сравнение `==` | да, с C# 7.3 | нет, только `Equals` |
| Максимум элементов | 7 + `TRest` (вложенность) | 7 + `TRest` (вложенность) |
| Где встречается | весь новый код | легаси, .NET 4.x, старые API |

`ValueTuple` — это буквально:

```csharp
// Упрощённо, как в исходниках BCL
public struct ValueTuple<T1, T2> : IEquatable<ValueTuple<T1, T2>>, IComparable, ITuple
{
    public T1 Item1;   // именно поле, а не свойство
    public T2 Item2;
}
```

Отсюда сразу два следствия: кортеж не аллоцирует (см. [[Value types vs Reference types]]) и кортеж **изменяем** — `t.Item1 = 5` компилируется.

## Синтаксис

```csharp
// Тип без имён
(int, string) a = (1, "one");
Console.WriteLine(a.Item1);           // Вывод: 1

// Тип с именами
(int Code, string Text) b = (404, "Not Found");
Console.WriteLine(b.Code);            // Вывод: 404
Console.WriteLine(b.Item1);           // Вывод: 404 — Item1 доступен всегда

// Имена в литерале
var c = (Code: 500, Text: "Server Error");
Console.WriteLine(c.Text);            // Вывод: Server Error

// ToString переопределён
Console.WriteLine(c);                 // Вывод: (500, Server Error)

// Кортеж как поле, параметр, элемент коллекции
var list = new List<(string Name, int Age)> { ("Аня", 30), ("Борис", 41) };
```

### Вывод имён элементов (C# 7.1)

Если элемент кортежа инициализируется переменной, полем или свойством, компилятор берёт имя оттуда:

```csharp
int code = 200;
string text = "OK";

var t = (code, text);                 // выведен тип (int code, string text)
Console.WriteLine(t.code);            // Вывод: 200

var user = new { Id = 7, Login = "root" };
var u = (user.Id, user.Login);        // (int Id, string Login)
Console.WriteLine(u.Login);           // Вывод: root
```

Правило не срабатывает, если имя «зарезервировано» (`Item3` не на третьей позиции, `Rest`, `ToString`) — тогда имени просто не будет.

## Имена элементов — компиляторная фикция

Это ключевое место, которое любят спрашивать на собеседовании. В рантайме **нет** типа `(int Code, string Text)`. Есть `ValueTuple<int, string>`, а имена компилятор:

1. подставляет как синтаксический сахар вместо `Item1`/`Item2` внутри метода;
2. для *сигнатур* (параметры, возвращаемые типы, поля, свойства) записывает в метаданные атрибутом `TupleElementNamesAttribute`.

```csharp
using System.Reflection;
using System.Runtime.CompilerServices;

(int Code, string Text) Get() => (200, "OK");

var t = Get();
Console.WriteLine(t.GetType().Name);            // Вывод: ValueTuple`2
Console.WriteLine(t.GetType().FullName);
// Вывод: System.ValueTuple`2[[System.Int32, ...],[System.String, ...]]

// Имена лежат в атрибуте на сигнатуре метода, а не в типе
var mi = typeof(Program).GetMethod(nameof(Get),
    BindingFlags.NonPublic | BindingFlags.Static)!;
var attr = mi.ReturnParameter.GetCustomAttribute<TupleElementNamesAttribute>()!;
Console.WriteLine(string.Join(", ", attr.TransformNames));   // Вывод: Code, Text
```

Практические следствия:

```csharp
object boxed = (Code: 200, Text: "OK");
// Приведение обратно — имена придумываешь заново, компилятор не проверит
var back = ((int Status, string Message))boxed;   // легально!
Console.WriteLine(back.Status);                    // Вывод: 200
```

Для локальных переменных имена вообще нигде не хранятся, кроме отладочной информации.

## Присваивание и совместимость

Совместимость кортежей определяется **позициями и типами**, а не именами:

```csharp
(int Code, string Text) a = (200, "OK");
(int Status, string Message) b = a;    // ОК, типы совпадают
(int, string) c = a;                   // ОК, имена отбрасываются

// Работают и неявные преобразования элементов
(long, object) d = (1, "x");           // int -> long, string -> object
```

Если имена расходятся, компилятор даёт предупреждение **CS8123** («имя элемента кортежа игнорируется») только там, где имена явно указаны в литерале и отбрасываются целевым типом:

```csharp
(int Code, string Text) e = (Status: 200, Message: "OK");  // CS8123 x2
```

## Сравнение `==` и `!=` (C# 7.3)

C# 7.3 разрешил `==`/`!=` для кортежей. Компилятор **не вызывает** `ValueTuple.Equals`, а разворачивает сравнение поэлементно, применяя обычный оператор `==` к каждой паре:

```csharp
var x = (1, "a");
var y = (1, "a");
Console.WriteLine(x == y);            // Вывод: True
// компилируется примерно в: x.Item1 == y.Item1 && x.Item2 == y.Item2

// Имена не участвуют
Console.WriteLine((Code: 1, Text: "a") == (Status: 1, Message: "a"));  // Вывод: True

// Работает лифтинг nullable
(int?, int?) n1 = (1, null);
(int?, int?) n2 = (1, null);
Console.WriteLine(n1 == n2);          // Вывод: True — null == null даёт true
(int?, int?) n3 = (1, 2);
Console.WriteLine(n1 == n3);          // Вывод: False

// Nullable сам кортеж
(int, int)? maybe = null;
Console.WriteLine(maybe == (1, 2));   // Вывод: False
```

Из «разворачивается в `==` по элементам» следует важное расхождение с `Equals`:

```csharp
var a = (double.NaN, 1);
var b = (double.NaN, 1);

Console.WriteLine(a == b);        // Вывод: False — потому что NaN == NaN даёт false
Console.WriteLine(a.Equals(b));   // Вывод: True  — EqualityComparer<double>.Default
                                  //                считает NaN равным NaN
```

Ещё следствие: сравнение через `==` требует, чтобы **у каждого элемента** был оператор `==`. Для произвольного пользовательского класса без оператора код не скомпилируется, а `Equals` отработает.

## Equals и GetHashCode

`ValueTuple` реализует `IEquatable<T>` и переопределяет `Equals`/`GetHashCode`, используя `EqualityComparer<T>.Default` для каждого элемента — то есть уважает пользовательские `IEquatable<T>`. Хеш комбинируется через тот же алгоритм, что и `HashCode.Combine`.

```csharp
var set = new HashSet<(string City, int Year)>
{
    ("Ташкент", 2026),
    ("Ташкент", 2026),   // дубликат
    ("Самарканд", 2026)
};
Console.WriteLine(set.Count);         // Вывод: 2

var cache = new Dictionary<(int UserId, string Perm), bool>
{
    [(1, "read")] = true,
    [(1, "write")] = false
};
Console.WriteLine(cache[(1, "read")]);   // Вывод: True
```

Кортеж как составной ключ словаря — идиоматичный приём, он заменяет `Dictionary<int, Dictionary<string, bool>>`. Подробнее о хешировании — в [[Object: Equals, GetHashCode, ToString]] и [[Dictionary и HashSet изнутри]].

Также `ValueTuple` реализует `IComparable`/`IComparable<T>` — сравнение лексикографическое, поэлементно слева направо:

```csharp
var items = new List<(int Priority, string Name)>
{
    (2, "b"), (1, "z"), (1, "a")
};
items.Sort();
Console.WriteLine(string.Join(" ", items));   // Вывод: (1, a) (1, z) (2, b)
```

## Кортежи вместо out-параметров

```csharp
// Было
public static bool TryGetSize(string path, out long bytes, out DateTime modified)
{
    bytes = 0; modified = default;
    var fi = new FileInfo(path);
    if (!fi.Exists) return false;
    bytes = fi.Length; modified = fi.LastWriteTimeUtc;
    return true;
}

// Стало — работает в LINQ, не требует объявлять переменные заранее
public static (bool Found, long Bytes, DateTime Modified) GetSize(string path)
{
    var fi = new FileInfo(path);
    return fi.Exists
        ? (true, fi.Length, fi.LastWriteTimeUtc)
        : (false, 0L, default);
}

var sizes = paths.Select(GetSize).Where(r => r.Found).Sum(r => r.Bytes);
```

Исключение — паттерн `Try*`, который используется вместе с `is`-паттерном и `out var`: там `out` остаётся идиоматичнее. См. [[Методы и параметры]].

## Деконструкция

```csharp
var point = (X: 3, Y: 4);

// 1. Все переменные объявляются сразу
var (x, y) = point;

// 2. С явными типами
(int px, int py) = point;

// 3. Смешанный режим запрещён: нельзя (var a, int b) = ...
//    Но можно присвоить в уже существующие
int a2, b2;
(a2, b2) = point;

// 4. Discard — «мне это значение не нужно»
var (_, onlyY) = point;
Console.WriteLine(onlyY);             // Вывод: 4
```

### Swap и порядок вычисления

```csharp
int p = 1, q = 2;
(p, q) = (q, p);
Console.WriteLine($"{p} {q}");        // Вывод: 2 1
```

Работает потому, что при деконструирующем присваивании порядок строго такой:

1. вычисляются «адреса» целей слева направо (получатели, индексы);
2. **полностью** вычисляется правая часть во временные переменные;
3. применяются преобразования;
4. выполняются присваивания слева направо.

Проверим на индексаторе:

```csharp
int[] arr = [0, 1, 2];
int i = 0;

(arr[i], i) = (i + 10, 2);

// Шаг 1: цель arr[i] зафиксирована при i == 0, то есть arr[0]
// Шаг 2: правая часть = (10, 2)
// Шаг 4: arr[0] = 10; i = 2
Console.WriteLine($"[{string.Join(",", arr)}] i={i}");   // Вывод: [10,1,2] i=2
```

### Метод Deconstruct

Деконструировать можно любой тип, у которого есть доступный метод `Deconstruct` со всеми параметрами `out` и возвращаемым `void`. Компилятор ищет его по количеству параметров.

```csharp
public sealed class Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(decimal amount, string currency) => (Amount, Currency) = (amount, currency);

    // Перегрузки различаются числом out-параметров
    public void Deconstruct(out decimal amount, out string currency)
        => (amount, currency) = (Amount, Currency);

    public void Deconstruct(out decimal amount, out string currency, out bool isZero)
    {
        (amount, currency) = (Amount, Currency);
        isZero = Amount == 0m;
    }
}

var (amount, currency) = new Money(19.99m, "USD");
Console.WriteLine($"{amount} {currency}");            // Вывод: 19,99 USD

var (_, _, isZero) = new Money(0m, "UZS");
Console.WriteLine(isZero);                            // Вывод: True
```

`record` и позиционные `record struct` получают `Deconstruct` автоматически — см. [[Записи (record) и структуры]].

### Extension-деконструктор

Если тип чужой, деконструктор можно добавить снаружи:

```csharp
public static class DateTimeExtensions
{
    // Классический синтаксис расширяющего метода
    public static void Deconstruct(this DateTime dt, out int year, out int month, out int day)
        => (year, month, day) = (dt.Year, dt.Month, dt.Day);
}

var (yy, mm, dd) = new DateTime(2026, 8, 5);
Console.WriteLine($"{dd:00}.{mm:00}.{yy}");           // Вывод: 05.08.2026
```

В C# 14 то же самое можно записать через extension-блок (подробности — в [[Расширяющие методы и extension members]]):

```csharp
public static class DateTimeExtensions14
{
    extension(DateTime dt)
    {
        public void Deconstruct(out int year, out int month, out int day)
            => (year, month, day) = (dt.Year, dt.Month, dt.Day);
    }
}
```

> [!info] Приоритет
> Если у типа есть собственный `Deconstruct` и подходящий extension-вариант, выигрывает собственный: расширяющие методы всегда рассматриваются последними.

### Деконструкция в foreach по Dictionary

`KeyValuePair<TKey, TValue>` имеет `Deconstruct`, поэтому цикл читается как человеческий текст:

```csharp
var rates = new Dictionary<string, decimal>
{
    ["USD"] = 12550m,
    ["EUR"] = 13700m
};

foreach (var (code, rate) in rates)
    Console.WriteLine($"{code}: {rate}");
// Вывод:
// USD: 12550
// EUR: 13700

// Работает и для любого IEnumerable<кортеж>
foreach (var (index, value) in rates.Select((kv, i) => (i, kv.Key)))
    Console.WriteLine($"{index} -> {value}");
```

### Деконструкция в паттернах

Позиционный паттерн (positional pattern) использует тот же `Deconstruct`. Подробно — в [[Pattern matching]].

```csharp
static string Describe(Money m) => m switch
{
    (0m, _)            => "ноль",
    ( < 0m, var cur)   => $"долг в {cur}",
    (var a, "USD")     => $"{a} долларов",
    _                  => "прочее"
};

Console.WriteLine(Describe(new Money(0m, "UZS")));     // Вывод: ноль
Console.WriteLine(Describe(new Money(-5m, "EUR")));    // Вывод: долг в EUR
Console.WriteLine(Describe(new Money(20m, "USD")));    // Вывод: 20 долларов
```

Кортежи в `switch` — самый частый способ сравнить сразу несколько условий:

```csharp
static string Quadrant(int x, int y) => (x, y) switch
{
    (0, 0)         => "начало координат",
    ( > 0, > 0)    => "I",
    ( < 0, > 0)    => "II",
    ( < 0, < 0)    => "III",
    ( > 0, < 0)    => "IV",
    _              => "на оси"
};
Console.WriteLine(Quadrant(-1, 5));   // Вывод: II
Console.WriteLine(Quadrant(0, 3));    // Вывод: на оси
```

## Больше семи элементов: TRest

В BCL объявлены `ValueTuple<T1>` … `ValueTuple<T1..T7, TRest>`. Восьмой параметр — это вложенный кортеж. Компилятор прячет вложенность:

```csharp
var big = (1, 2, 3, 4, 5, 6, 7, 8, 9);
Console.WriteLine(big.Item8);                 // Вывод: 8 — синтаксический сахар
Console.WriteLine(big.Rest.Item1);            // Вывод: 8 — реальное расположение
Console.WriteLine(big.GetType().Name);        // Вывод: ValueTuple`8
Console.WriteLine(big.Rest.GetType().Name);   // Вывод: ValueTuple`2
```

Практически: если элементов больше пяти-шести — это уже не кортеж, а тип с именем. Заводите `record`.

## Производительность

```csharp
// Аллокаций нет: кортеж живёт на стеке вызывающего
static (int, int) MinMax(ReadOnlySpan<int> data)
{
    int min = int.MaxValue, max = int.MinValue;
    foreach (var v in data)
    {
        if (v < min) min = v;
        if (v > max) max = v;
    }
    return (min, max);
}
```

Нюансы:

- Кортеж копируется целиком при передаче и возврате. Кортеж из десяти `decimal` — это 160 байт копирования на каждый вызов.
- Кортеж в поле класса живёт в куче внутри объекта-владельца, но отдельной аллокации не делает.
- Приведение к `object`, `ITuple` или `IEquatable<...>` **боксирует** — см. [[Boxing и unboxing]].
- В `async`-методах кортеж уезжает в поле state machine, как и любая локальная переменная.

## Кортежи в публичном API

Технически можно. Практически — спорно:

| Проблема | Почему больно |
|---|---|
| Имена элементов не документируются | XML-комментарий `<returns>` описывает кортеж целиком, IntelliSense показывает `Item1`, если имя потерялось при приведении |
| Нет инвариантов | Нельзя проверить в конструкторе, что `From <= To` |
| Нет поведения | Нельзя добавить метод, свойство, `ToString` под задачу |
| Ломающие изменения | Добавить восьмое поле = поменять тип = сломать всех потребителей |
| Ковариантность | Кортеж не участвует в вариантности интерфейсов |
| Сериализация | `System.Text.Json` по умолчанию **не** сериализует поля, а у `ValueTuple` именно поля — на выходе `{}` |

Последний пункт стоит запомнить отдельно:

```csharp
using System.Text.Json;

Console.WriteLine(JsonSerializer.Serialize((Code: 200, Text: "OK")));
// Вывод: {}   — потому что Item1/Item2 это поля, а не свойства

var opts = new JsonSerializerOptions { IncludeFields = true };
Console.WriteLine(JsonSerializer.Serialize((Code: 200, Text: "OK"), opts));
// Вывод: {"Item1":200,"Item2":"OK"}   — имена всё равно потеряны
```

Правило: кортеж — внутри метода, между приватными методами, как ключ словаря, как промежуточный результат LINQ. Публичный контракт — `record` (см. [[Записи (record) и структуры]]) или `readonly record struct`.

> [!warning] Подводные камни
> - **Имена исчезают при переходе через `object`, `dynamic` и рефлексию.** `t.GetType()` вернёт `ValueTuple\`2` — никаких `Code`/`Text`. Обратное приведение позволяет придумать любые имена, и компилятор промолчит.
> - **Кортеж изменяем.** `readonly` поле-кортеж защищает от `_t.Item1 = 5`, но локальная переменная-кортеж меняется свободно. Ещё хуже: `list[0].Item1 = 5` для `List<(int, int)>` не скомпилируется (индексатор возвращает копию), а для массива `arr[0].Item1 = 5` — скомпилируется и сработает. Разное поведение одинакового на вид кода.
> - **`==` и `Equals` дают разные ответы на `NaN` и на типах с перегруженным `==`.** `==` разворачивается в поэлементные операторы, `Equals` идёт через `EqualityComparer<T>.Default`. Если у вашего класса перегружен `==`, но не переопределён `Equals` (или наоборот) — кортежи из таких элементов начнут вести себя непредсказуемо.
> - **`==` с nullable-элементами лифтится.** `(1, (int?)null) == (1, (int?)null)` даёт `True`, что противоречит привычному `null == null` для ссылок... но совпадает с ним. А вот `((int, int)?)null == (1, 2)` даёт `False`, а не исключение — легко пропустить логическую ошибку.
> - **Кортеж в `Dictionary` со ссылочными элементами наследует их `GetHashCode`.** Если элемент — класс без переопределённого `GetHashCode`, ключ будет сравниваться по ссылке, и поиск «такого же» кортежа не найдёт ничего.
> - **`Sort()` кортежей с элементом-классом без `IComparable` бросит `InvalidOperationException`** в рантайме, компилятор об этом не предупредит.

> [!example] Как делают в бою
> - **Составной ключ кеша.** `ConcurrentDictionary<(int TenantId, string Key), byte[]>` вместо конкатенации строк `$"{tenant}:{key}"` — быстрее (нет аллокации строки) и типобезопаснее.
> - **Промежуточные шаги LINQ.** `items.Select(x => (x, Score: Score(x))).OrderByDescending(t => t.Score).Select(t => t.x)` — не нужен анонимный тип, не нужна аллокация на элемент.
> - **Групповое присваивание в конструкторе.** `(Amount, Currency) = (amount, currency);` — компактнее, чем два оператора, и компилируется в то же самое.
> - **Возврат «результат + метаданные»** из приватных helper-методов: `private (bool Ok, string? Error) Validate(...)`. Как только этот метод становится публичным — заменяют на `Result`-тип.
> - **Деконструкция в `foreach` по словарям и по `Zip`** — стандартный стиль в современных кодовых базах, `kv.Key`/`kv.Value` считается устаревшим шумом.
> - **Ограничение в code review:** кортеж с более чем тремя элементами или пересекающий границу сборки — повод попросить `record`.

## Вопросы с собеседований

> [!question]- Чем `ValueTuple` отличается от `Tuple`?
> `Tuple<...>` — класс из .NET 4.0: аллоцируется в куче, иммутабелен, элементы — свойства `Item1..Item7`, имён нет. `ValueTuple<...>` — структура из .NET 4.7/.NET Core 2.0: не аллоцируется, изменяема, элементы — публичные поля, поддерживает именованные элементы, деконструкцию и оператор `==`. Синтаксис языка `(int, string)` разворачивается именно в `ValueTuple`. `Tuple` в новом коде не используют; он встречается в легаси и в старых сигнатурах BCL вроде `Task<Tuple<...>>`.

> [!question]- Где хранятся имена элементов кортежа?
> Нигде в самом типе — в рантайме существует только `ValueTuple<int, string>`. Внутри метода компилятор просто заменяет `t.Code` на `t.Item1`. Для членов, видимых снаружи (возвращаемые типы, параметры, поля, свойства), компилятор дополнительно навешивает `[TupleElementNames({"Code","Text"})]` на сигнатуру, чтобы другой компилятор при ссылке на сборку восстановил имена. Поэтому имена теряются при боксинге в `object`, при работе через рефлексию и при приведении к другому набору имён — последнее компилятор даже не считает ошибкой.

> [!question]- Как работает `==` для кортежей и чем отличается от `Equals`?
> С C# 7.3 компилятор разворачивает `t1 == t2` в цепочку `t1.Item1 == t2.Item1 && t1.Item2 == t2.Item2`, применяя оператор `==` каждого типа элемента, с обычным лифтингом для `Nullable<T>`. Имена элементов игнорируются. `ValueTuple.Equals` работает иначе — он использует `EqualityComparer<T>.Default`, то есть `IEquatable<T>.Equals`. Отсюда классическое расхождение: `(double.NaN, 1) == (double.NaN, 1)` даёт `False`, а `.Equals` — `True`. Ещё разница: `==` требует наличия оператора у каждого элемента, `Equals` работает всегда.

> [!question]- Почему `(a, b) = (b, a)` корректно меняет значения местами?
> Деконструирующее присваивание — не последовательность двух присваиваний. Сначала фиксируются цели слева (для простых переменных это ничего не значит, для `arr[i]` — вычисляется индекс), затем **целиком** вычисляется правая часть во временные значения, и только потом выполняются присваивания слева направо. Правая часть читает старые значения `b` и `a` до того, как что-либо изменилось, поэтому обмен работает без временной переменной. Обратите внимание, что порядок «цели, затем источники» заметен на индексаторах: в `(arr[i], i) = (i + 10, 2)` индекс `i` берётся старый.

> [!question]- Как деконструировать чужой тип, у которого нет `Deconstruct`?
> Написать расширяющий метод `public static void Deconstruct(this T value, out T1 a, out T2 b)`. Компилятор ищет `Deconstruct` сначала как инстанс-метод (включая унаследованные), затем среди расширяющих методов в области видимости. Требования: возвращаемый тип `void`, все параметры `out`, разрешены перегрузки с разным количеством параметров (по числу параметров и идёт разрешение). В C# 14 тот же метод можно объявить внутри `extension(T value) { ... }`-блока. Работает это и для позиционных паттернов: `obj is (var a, var b)` использует тот же самый `Deconstruct`.

> [!question]- Кортеж как ключ `Dictionary` — хорошая идея?
> Да, для составных ключей это идиоматично: `ValueTuple` переопределяет `GetHashCode` (комбинирует хеши элементов через тот же алгоритм, что `HashCode.Combine`) и `Equals` (через `EqualityComparer<T>.Default` по элементам), реализует `IEquatable<T>`, поэтому `Dictionary` пойдёт по быстрому пути без боксинга. Ограничение одно: качество ключа определяется элементами. Если один из элементов — класс без переопределённого `Equals`/`GetHashCode`, сравнение выродится в сравнение по ссылке. И не кладите в ключ изменяемые объекты — как и для любого ключа словаря.

> [!question]- Почему `JsonSerializer.Serialize` возвращает `{}` для кортежа?
> Потому что элементы `ValueTuple` — это публичные **поля**, а `System.Text.Json` по умолчанию сериализует только публичные свойства. Включение `IncludeFields = true` вернёт `{"Item1":...,"Item2":...}` — имена всё равно потеряны, поскольку в рантайме их нет. Вывод: кортеж нельзя использовать как DTO. Для контрактов берут `record` с нормальными свойствами и `[JsonPropertyName]`.

## Задачи

### Задача 1. Частотный словарь по паре признаков

Есть список заказов `IEnumerable<(string City, string Status, decimal Sum)>`. Посчитайте суммы по паре (город, статус) и выведите тройки, отсортированные по убыванию суммы.

> [!success]- Решение
> ```csharp
> var orders = new List<(string City, string Status, decimal Sum)>
> {
>     ("Ташкент", "paid", 100m),
>     ("Ташкент", "paid", 50m),
>     ("Ташкент", "new",  30m),
>     ("Бухара",  "paid", 70m)
> };
>
> var totals = new Dictionary<(string City, string Status), decimal>();
> foreach (var (city, status, sum) in orders)
> {
>     var key = (city, status);
>     // CollectionsMarshal.GetValueRefOrAddDefault был бы ещё быстрее
>     totals[key] = totals.GetValueOrDefault(key) + sum;
> }
>
> foreach (var ((city, status), total) in totals.OrderByDescending(kv => kv.Value))
>     Console.WriteLine($"{city}/{status}: {total}");
> // Вывод:
> // Ташкент/paid: 150
> // Бухара/paid: 70
> // Ташкент/new: 30
> ```
> Кортеж-ключ избавляет от вложенного словаря и от конкатенации строк. Обратите внимание на двойную деконструкцию в `foreach`: сначала `KeyValuePair` раскладывается на ключ и значение, затем ключ-кортеж — на два поля.

### Задача 2. Свой деконструктор и позиционный паттерн

Напишите структуру `Version3` (Major, Minor, Patch) с `Deconstruct`, и метод `Kind`, который через позиционный паттерн возвращает `"pre-release"` для `Major == 0`, `"patch"` если `Patch > 0`, иначе `"minor/major"`.

> [!success]- Решение
> ```csharp
> public readonly struct Version3
> {
>     public int Major { get; }
>     public int Minor { get; }
>     public int Patch { get; }
>
>     public Version3(int major, int minor, int patch)
>         => (Major, Minor, Patch) = (major, minor, patch);
>
>     public void Deconstruct(out int major, out int minor, out int patch)
>         => (major, minor, patch) = (Major, Minor, Patch);
>
>     public override string ToString() => $"{Major}.{Minor}.{Patch}";
> }
>
> static string Kind(Version3 v) => v switch
> {
>     (0, _, _)        => "pre-release",
>     (_, _, > 0)      => "patch",
>     _                => "minor/major"
> };
>
> Console.WriteLine(Kind(new Version3(0, 9, 1)));   // Вывод: pre-release
> Console.WriteLine(Kind(new Version3(1, 2, 3)));   // Вывод: patch
> Console.WriteLine(Kind(new Version3(2, 0, 0)));   // Вывод: minor/major
> ```
> Позиционный паттерн вызывает `Deconstruct` ровно один раз на входе в `switch`. Порядок веток важен: первая подходящая выигрывает, поэтому `(0, _, _)` стоит выше.

### Задача 3. Найти расхождение `==` и `Equals`

Приведите пример двух кортежей, для которых `t1 == t2` и `t1.Equals(t2)` дают разный результат, и объясните механику.

> [!success]- Решение
> ```csharp
> var t1 = (Value: double.NaN, Tag: "x");
> var t2 = (Value: double.NaN, Tag: "x");
>
> Console.WriteLine(t1 == t2);        // Вывод: False
> Console.WriteLine(t1.Equals(t2));   // Вывод: True
>
> // Второй пример: строки, сравниваемые оператором vs компаратором
> // (здесь совпадёт, но полезно понимать, что пути разные)
> Console.WriteLine(double.NaN == double.NaN);                        // Вывод: False
> Console.WriteLine(EqualityComparer<double>.Default.Equals(
>     double.NaN, double.NaN));                                       // Вывод: True
> ```
> `==` для кортежа — чистый синтаксический сахар: компилятор пишет `t1.Item1 == t2.Item1 && t1.Item2 == t2.Item2`. Оператор `==` для `double` реализует стандарт IEEE 754, по которому `NaN` не равен ничему, включая себя. `ValueTuple.Equals` идёт через `EqualityComparer<double>.Default` → `Double.Equals(double)`, а он специально сделан рефлексивным, чтобы `NaN` можно было положить в `HashSet` и найти. Тот же эффект даёт `+0.0` и `-0.0`, но в обратную сторону: `==` даёт `True`, `Equals` — `False`.

## Итог

- Синтаксис `(int, string)` разворачивается в структуру `System.ValueTuple` — без аллокаций, но с изменяемыми полями и копированием при передаче.
- Имена элементов существуют только на этапе компиляции; для сигнатур они сохраняются в `TupleElementNamesAttribute`, для локальных переменных — нигде.
- Совместимость кортежей определяется позициями и типами, имена при присваивании отбрасываются с предупреждением CS8123.
- `==` (C# 7.3) разворачивается поэлементно и может расходиться с `Equals`, который идёт через `EqualityComparer<T>.Default`.
- Деконструкция работает для любого типа с методом `Deconstruct` (в том числе расширяющим) и лежит в основе позиционных паттернов.
- Кортеж — отличный внутренний инструмент и составной ключ словаря; в публичном контракте вместо него берут `record`.
