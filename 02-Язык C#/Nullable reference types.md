# Nullable reference types

> [!abstract] Коротко
> Nullable reference types (NRT) — режим компилятора, в котором `string` означает «здесь не должно быть null», а `string?` — «здесь null допустим». Компилятор анализирует поток данных и предупреждает, когда возможный null разыменовывают или присваивают в ненулевую переменную. Важно понимать границу: это **проверка на этапе компиляции**, в рантайме ничего не меняется — `string?` и `string` — один и тот же `System.String`, никакой обёртки нет. Поэтому NRT не отменяет проверку данных, приходящих извне, но убирает целый класс ошибок внутри собственного кода.

## Зачем это нужно

`NullReferenceException` — самая частая ошибка в .NET за всю его историю. Тони Хоар, автор идеи null-ссылок, называл её своей «ошибкой на миллиард долларов»: тип `string` до C# 8 не позволял выразить, обязателен параметр или нет, и это приходилось описывать в комментариях и проверять в рантайме.

NRT переносит эту информацию в систему типов:

```csharp
// До: из подписи неясно, можно ли передать null и может ли вернуться null
string FindName(int id);

// После: контракт очевиден и проверяется компилятором
string? FindName(int id);            // может вернуть null — проверь результат
string FindName(int id);             // не вернёт null — можно использовать сразу
void Save(string name);              // null передавать нельзя
void Save(string? comment);          // null допустим
```

В шаблонах .NET 6 и новее режим включён по умолчанию, поэтому это не «новая фича для энтузиастов», а поведение по умолчанию, с которым придётся работать.

## Включение и режимы

```xml
<PropertyGroup>
  <Nullable>enable</Nullable>          <!-- аннотации + предупреждения: правильный выбор -->
</PropertyGroup>
```

| Значение | Аннотации (`?` имеет смысл) | Предупреждения |
|---|---|---|
| `enable` | да | да |
| `warnings` | нет | да (по анализу потока) |
| `annotations` | да | нет |
| `disable` | нет | нет |

Локальное управление в коде — для постепенной миграции:

```csharp
#nullable enable                   // включить в этом файле с этого места
#nullable disable warnings         // отключить только предупреждения
#nullable restore                  // вернуться к настройке проекта
```

Практика для нового кода: `enable` на весь проект плюс `<TreatWarningsAsErrors>true</TreatWarningsAsErrors>` — иначе предупреждения накопятся и перестанут читаться ([[Стиль кода, соглашения и .editorconfig]]).

## Анализ потока

Компилятор отслеживает состояние каждой переменной («может быть null» / «точно не null») по ветвям кода:

```csharp
void Process(string? input)
{
    // Console.WriteLine(input.Length);      // CS8602: разыменование возможного null

    if (input is null) return;
    Console.WriteLine(input.Length);          // ок: после проверки компилятор знает, что не null

    input = null;
    // Console.WriteLine(input.Length);       // снова предупреждение: состояние изменилось
}

void Process2(string? a, string? b)
{
    if (a is not null && b is not null)
        Console.WriteLine(a.Length + b.Length);      // ок для обеих

    var length = a?.Length ?? 0;                      // ок: безопасный доступ
    var name = a ?? "по умолчанию";                    // тип результата — string, не string?
    ArgumentNullException.ThrowIfNull(b);              // после этого b считается не-null
    Console.WriteLine(b.Length);                       // ок
}
```

Анализ учитывает `if`, паттерны, `??`, `?.`, `throw`, `return`, `Debug.Assert`, атрибуты BCL и даже `TryGetValue`. Он не всесилен: состояние теряется после присваивания, вызова метода, который мог изменить поле, и на границе лямбд.

```csharp
class Service
{
    private string? _cache;

    void Use()
    {
        if (_cache is not null)
        {
            Refresh();                            // метод мог обнулить поле
            // Console.WriteLine(_cache.Length);   // CS8602 — и компилятор прав
        }

        // Правильно: скопировать в локальную переменную
        var local = _cache;
        if (local is not null)
            Console.WriteLine(local.Length);        // ок, локальную никто не изменит
    }

    void Refresh() => _cache = null;
}
```

Это не придирка компилятора, а реальная защита: тот же код в многопоточной среде — классическая гонка, когда поле обнуляется между проверкой и использованием.

## Оператор `!` — обещание под личную ответственность

```csharp
string? maybe = GetName();
string definitely = maybe!;               // «я знаю, что здесь не null»
Console.WriteLine(maybe!.Length);          // подавляет предупреждение
```

`!` (null-forgiving operator) ничего не проверяет и ничего не делает в рантайме — он только заставляет компилятор замолчать. Если предположение неверно, получишь `NullReferenceException` там же, где и без NRT.

Когда `!` оправдан:

```csharp
// 1. Компилятор не видит инварианта, который гарантирован логикой
if (dict.ContainsKey(key))
    Use(dict[key]!);                   // хотя лучше TryGetValue — тогда ! не нужен

// 2. Тесты: намеренная передача null для проверки поведения
Assert.Throws<ArgumentNullException>(() => service.Save(null!));

// 3. Поля, инициализируемые фреймворком (EF Core, DI, десериализация)
public class Order
{
    public string Number { get; set; } = null!;   // EF Core заполнит при материализации
}
```

Каждое `!` — место, где ты берёшь ответственность на себя. Если их в файле десятки, режим NRT перестаёт работать: он превращается в раздражитель, который глушат, вместо инструмента. Правильная реакция на предупреждение — исправить модель (сделать поле `required`, добавить проверку, изменить подпись), и только в крайнем случае — `!` с комментарием почему.

Более честная альтернатива для обязательных свойств — `required` (C# 11):

```csharp
public class Order
{
    public required string Number { get; init; }   // компилятор потребует задать при создании
    public string? Comment { get; init; }
}

// var o = new Order();                            // Ошибка: Number не инициализирован
var o = new Order { Number = "ORD-1" };            // ок
```

## Атрибуты для тонких контрактов

Иногда «nullable или нет» зависит от результата или от других параметров. Для этого в `System.Diagnostics.CodeAnalysis` есть атрибуты, которыми аннотирована и вся BCL:

```csharp
using System.Diagnostics.CodeAnalysis;

// Результат не null, если метод вернул true — так аннотирован int.TryParse
static bool TryFind(string key, [NotNullWhen(true)] out string? value)
{
    value = key.Length > 0 ? key.ToUpperInvariant() : null;
    return value is not null;
}

if (TryFind("abc", out var found))
    Console.WriteLine(found.Length);        // ок: компилятор знает, что не null

// Возврат не null, если аргумент не null — так аннотирован Path.GetDirectoryName
[return: NotNullIfNotNull(nameof(path))]
static string? Normalize(string? path) => path?.Trim();

// Метод гарантирует, что поле инициализировано после его вызова
class Repo
{
    private List<string>? _items;

    [MemberNotNull(nameof(_items))]
    private void EnsureLoaded() => _items ??= new List<string>();

    public int Count()
    {
        EnsureLoaded();
        return _items.Count;               // ок без ! — атрибут это гарантирует
    }
}
```

Полезный набор:

| Атрибут | Смысл |
|---|---|
| `[NotNullWhen(true/false)]` | параметр `out` не null при таком результате метода |
| `[MaybeNullWhen(true/false)]` | наоборот, может быть null |
| `[NotNullIfNotNull("param")]` | результат не null, если указанный параметр не null |
| `[MemberNotNull(...)]` | после вызова метода поле точно инициализировано |
| `[MemberNotNullWhen(true, ...)]` | то же, но при определённом результате |
| `[AllowNull]` | сеттер принимает null, геттер не отдаёт |
| `[DisallowNull]` | наоборот: присваивать null нельзя, но прочитать можно |
| `[DoesNotReturn]` | метод всегда бросает — код после него недостижим |

Эти атрибуты не влияют на рантайм: они лишь передают компилятору знание, которое он не может выяснить сам.

## Дженерики и NRT

```csharp
// T? для несвязанного T означает «может быть null», но обёртки Nullable<T> не создаёт:
// для ссылочных типов это аннотация, для значимых — просто T (default)
static T? FirstOrDefault<T>(IEnumerable<T> source)
{
    foreach (var item in source) return item;
    return default;                                 // null для class, 0 для int
}

// Ограничения меняют смысл
static void RequireClass<T>(T value) where T : class { }        // T не может быть nullable
static void AllowNullClass<T>(T? value) where T : class { }      // T? = «ссылка, возможно null»
static void RequireStruct<T>(T? value) where T : struct { }      // T? = Nullable<T>
static void RequireNotNull<T>(T value) where T : notnull { }     // ни null-ссылка, ни Nullable
```

Ограничение `notnull` — способ сказать «этот параметр типа не должен допускать null»; именно так объявлен ключ в `Dictionary<TKey, TValue>` начиная с .NET 5.

## Где NRT не спасает: данные извне

Это самое важное практическое ограничение. Аннотации существуют только в метаданных сборки, рантайм их не проверяет:

```csharp
public record CreateOrderRequest(string CustomerName, string Address);

// JSON без полей десериализуется успешно, и в НЕнулевых свойствах окажется null:
var request = System.Text.Json.JsonSerializer.Deserialize<CreateOrderRequest>("{}");
Console.WriteLine(request!.CustomerName is null);   // Вывод: True (!)
```

Источники «невозможного» null:

- десериализация JSON, XML, конфигурации;
- материализация из базы данных (EF Core заполняет свойства напрямую);
- вызовы из кода без NRT — старых библиотек и проектов с `<Nullable>disable</Nullable>`;
- рефлексия, `Activator.CreateInstance`, мокинг в тестах;
- interop с нативным кодом.

Вывод: **NRT заменяет проверки внутри своего кода, но не валидацию на границах системы**. На входе в приложение данные проверяются явно — атрибутами валидации, FluentValidation или guard-выражениями ([[Защитное программирование и guard clauses]], [[Model binding и валидация]]). Хорошая новость: в ASP.NET Core 10 не-nullable свойства модели по умолчанию считаются обязательными при валидации, то есть аннотация становится и правилом валидации тоже.

## Миграция существующего проекта

Порядок, который работает на большом коде:

1. `<Nullable>annotations</Nullable>` — включить смысл `?` без потока предупреждений; расставить аннотации в публичном API.
2. Затем `enable` для новых файлов через `#nullable enable` в шапке; так новый код сразу корректен.
3. Разбирать по одному файлу или сборке за коммит, поднимая до `enable` на уровне проекта.
4. В конце — `TreatWarningsAsErrors`, чтобы не откатиться назад.

Чего делать не стоит: включить `enable` на всё решение и «починить» пять тысяч предупреждений расстановкой `!`. Формально предупреждений не станет, а информации о контрактах не появится — только ложное чувство защищённости.

> [!warning] Подводные камни
> - **`!` вместо исправления.** Подавляет предупреждение, не меняя поведение. Каждое `!` — обещание, за которое отвечаешь ты, а не компилятор.
> - **Вера в то, что не-nullable значит «не будет null».** Десериализация, EF Core, старые библиотеки и рефлексия спокойно положат null в `string`. Валидация на границе обязательна.
> - **Состояние поля не сохраняется между вызовами.** После любого вызова метода компилятор снова считает поле возможно-null. Копируй в локальную переменную — это ещё и защита от гонки.
> - **`string?` не создаёт обёртку.** В отличие от `int?` (это `Nullable<int>`, 8 байт), `string?` — та же ссылка. Ни размера, ни поведения в рантайме это не меняет.
> - **`default!` в поле как привычка.** `public string Name { get; set; } = null!;` уместен для сущностей EF Core, но в остальных случаях лучше `required` или конструктор с параметром.
> - **Разные настройки в разных проектах решения.** Вызов из проекта с `disable` в проект с `enable` не проверяется, и предупреждения не появляются. Настройку задают централизованно в `Directory.Build.props`.
> - **`?` у типа-значения путают с NRT.** `int?` — это `Nullable<int>` с полем `HasValue`, реально существующий тип; `string?` — только аннотация. Одинаковый синтаксис, разная природа.

> [!example] Как делают в бою
> В новом сервисе `<Nullable>enable</Nullable>` и `<TreatWarningsAsErrors>true</TreatWarningsAsErrors>` стоят в `Directory.Build.props` с первого коммита. Дальше действует простое правило: предупреждение NRT — это не шум, а сообщение о том, что модель описана неточно. Обычно лечится одним из четырёх способов: сделать свойство `required`, изменить подпись на `?`, добавить `ArgumentNullException.ThrowIfNull` в начало метода или переставить порядок инициализации.
> Сущности EF Core — единственное место, где массово встречается `= null!;`: навигационные свойства и строковые колонки заполняет рантайм ORM. Это допустимое исключение, и оно локализовано в слое данных.
> На границах (контроллеры, обработчики сообщений, парсеры конфигурации) NRT дополняется валидацией: аннотации данных или FluentValidation, ответ 400 с деталями вместо `NullReferenceException` в середине бизнес-логики. Дальше внутри приложения проверок на null почти нет — это и есть выигрыш.

## Вопросы с собеседований

> [!question]- Что происходит в рантайме с `string?`?
> Ничего. `string?` и `string` компилируются в один и тот же тип `System.String`; разница существует только в метаданных: компилятор помечает члены атрибутом `NullableAttribute`/`NullableContextAttribute`, чтобы другие сборки видели аннотации. Проверок в рантайме не добавляется, размер и поведение объектов не меняются. Отсюда два практических следствия. Первое: производительность NRT нулевая, включать его безопасно. Второе: гарантии тоже нулевые в рантайме — если данные приходят из десериализации, из базы через ORM, через рефлексию или из сборки, скомпилированной без NRT, в не-nullable свойстве вполне может оказаться null. Поэтому NRT убирает проверки внутри своего кода, но не заменяет валидацию на границах системы. Это принципиально отличается от `int?`, который является настоящим типом `Nullable<int>` с полем-флагом.

> [!question]- Что делает оператор `!` и когда его применение оправдано?
> `!` (null-forgiving) подавляет предупреждение компилятора о возможном null и больше ничего: он не вставляет проверок, не бросает исключений, в IL от него не остаётся следа. Оправдан в трёх случаях: когда инвариант гарантирован логикой, которую компилятор не может вывести (хотя чаще это признак, что код лучше переписать — например, заменить `ContainsKey` + индексатор на `TryGetValue`); в тестах, где null передаётся намеренно (`service.Save(null!)`); и для свойств, которые заполняет фреймворк — сущности EF Core, модели десериализации (`= null!`), хотя для них лучше `required`. Признак злоупотребления — десятки `!` в файле: тогда режим NRT не работает, а лишь создаёт видимость. Правильная реакция на предупреждение — уточнить модель, а не заглушить сообщение.

> [!question]- Почему после проверки поля на null компилятор всё равно предупреждает?
> Потому что анализ потока сбрасывает знание о состоянии поля после любого вызова метода: вызванный метод мог присвоить полю null, и компилятор не отслеживает это через границы вызовов (а для многопоточного кода поле вообще может измениться в другом потоке в любой момент). Проверка `if (_field is not null)` действует только до первого вызова, который потенциально может изменить состояние. Правильный приём — скопировать поле в локальную переменную и работать с ней: локальную переменную никто извне не изменит, поэтому анализ потока сохраняет знание, и заодно устраняется настоящая гонка «проверил — обнулилось — использовал». Это одна из немногих ситуаций, где предупреждение компилятора указывает не на формальность, а на реальный дефект.

> [!question]- Как аннотировать метод `TryGetValue`, чтобы компилятор понимал контракт?
> Через атрибут `[NotNullWhen(true)]` на `out`-параметре: он сообщает, что при возврате `true` параметр гарантированно не null. Именно так аннотированы `int.TryParse`, `Dictionary.TryGetValue` и подобные методы в BCL, поэтому после `if (dict.TryGetValue(key, out var value))` компилятор разрешает использовать `value` без проверки и без `!`. Родственные атрибуты: `[MaybeNullWhen(false)]` для обратного случая, `[NotNullIfNotNull(nameof(param))]` для методов, чей результат не null при не-null аргументе (`Path.GetDirectoryName`), `[MemberNotNull(nameof(_field))]` для методов инициализации, гарантирующих заполнение поля. Все эти атрибуты влияют только на анализ компилятора, никакой проверки в рантайме не добавляется.

## Задачи

### Задача 1. Убрать предупреждения правильно

```csharp
#nullable enable
public class UserService
{
    private Dictionary<int, string> _names;

    public UserService(Dictionary<int, string> names) => _names = names;

    public string GetName(int id)
    {
        if (_names.ContainsKey(id))
            return _names[id];
        return null;
    }

    public int GetLength(int id) => GetName(id).Length;
}
```

> [!success]- Решение
> ```csharp
> #nullable enable
> public class UserService
> {
>     private readonly Dictionary<int, string> _names;
>
>     public UserService(Dictionary<int, string> names)
>         => _names = names ?? throw new ArgumentNullException(nameof(names));
>
>     public string? GetName(int id)                       // контракт стал честным
>         => _names.TryGetValue(id, out var name) ? name : null;
>
>     public int GetLength(int id) => GetName(id)?.Length ?? 0;
> }
> ```
> Что исправлено: `return null` из метода с типом `string` — это предупреждение CS8603, лечится изменением подписи на `string?`, потому что метод действительно может не найти значение. `ContainsKey` + индексатор заменены на `TryGetValue`: два поиска превратились в один, а благодаря атрибуту `[NotNullWhen(true)]` в BCL компилятор понимает контракт без `!`. Вызов `GetName(id).Length` стал безопасным через `?.` и `??`. Поле помечено `readonly`, а аргумент конструктора проверен — при вызове из кода без NRT туда всё ещё может прийти null.

### Задача 2. Спроектировать модель запроса

Опиши DTO для создания заказа: обязательные `customerId` и `address`, необязательные `comment` и `promoCode`. Учти, что объект приходит из JSON.

> [!success]- Решение
> ```csharp
> public sealed record CreateOrderRequest
> {
>     public required long CustomerId { get; init; }
>     public required string Address { get; init; }
>     public string? Comment { get; init; }
>     public string? PromoCode { get; init; }
> }
> ```
> `required` заставляет заполнить свойства при создании объекта в коде — это защита от забытого поля при рефакторинге. Но и её недостаточно: `System.Text.Json` умеет учитывать `required` и бросит `JsonException`, если поле отсутствует в JSON, а вот старые сериализаторы и биндинг из формы могут положить null молча. Поэтому аннотации дополняются валидацией на входе:
> ```csharp
> public sealed record CreateOrderRequest
> {
>     [Required, Range(1, long.MaxValue)]
>     public required long CustomerId { get; init; }
>
>     [Required, StringLength(500, MinimumLength = 5)]
>     public required string Address { get; init; }
>
>     [StringLength(1000)] public string? Comment { get; init; }
>     [StringLength(32)]   public string? PromoCode { get; init; }
> }
> ```
> В ASP.NET Core 10 валидация Minimal API включается через `AddValidation()` и учитывает как атрибуты, так и то, что свойство не-nullable. Итог: тип описывает контракт для компилятора, атрибуты — для рантайма, и оба уровня согласованы.

## Итог

- NRT — проверка компилятора: `string` значит «не должно быть null», `string?` — «может быть». В рантайме не меняется ничего.
- Включается `<Nullable>enable</Nullable>`; в шаблонах .NET 6+ включено по умолчанию.
- Компилятор ведёт анализ потока: учитывает проверки, паттерны, `??`, `?.`, `ThrowIfNull` и атрибуты BCL.
- Состояние поля сбрасывается после вызова метода — копируй в локальную переменную (это ещё и защита от гонки).
- `!` ничего не проверяет, только глушит предупреждение; массовое применение обесценивает режим.
- `required` — способ выразить обязательность свойства без конструктора и без `null!`.
- Атрибуты `[NotNullWhen]`, `[NotNullIfNotNull]`, `[MemberNotNull]` описывают контракты, которые компилятор не может вывести сам.
- На границах системы аннотации не гарантируют ничего: десериализация и ORM положат null в не-nullable поле. Валидация обязательна.
