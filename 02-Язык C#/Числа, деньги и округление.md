# Числа, деньги и округление

> [!abstract] Коротко
> `decimal`, `double` и `float` выглядят взаимозаменяемо, но решают разные задачи: `decimal` хранит десятичные дроби точно и создан для денег, `double`/`float` — двоичное приближение, созданное для научных вычислений, где скорость важнее точности до копейки. Для сумм заказа, комиссий и графиков рассрочки выбор типа — не стиль, а вопрос «сойдётся ли баланс».

## Зачем это знать

Ошибка в денежном типе не падает с исключением — она копится молча и всплывает через месяцы как расхождение в сверке. В рассрочке (Nasiya, BML и аналогичные кредитные продукты) один платёж входит в график десятки раз: график считается, пересчитывается при досрочном погашении, округляется на каждом шаге. Если сумма платежа хранится в `double`, ошибка на 15-м знаке после запятой на одном платеже незаметна, а после суммирования графика на 24 месяца — это уже расхождение в копейках, которое находит бухгалтерия, а не тесты. Тема попадает в ревью-фильтр напрямую: тип поля в контракте или в EF-модели — то, что нужно поймать до мержа, а не после инцидента.

## Модель

### decimal, double, float: разное представление

```
double, float  → двоичная мантисса (IEEE 754): точно представляют степени двойки,
                 но 0.1 в двоичном виде — бесконечная дробь, как 1/3 в десятичном
decimal        → десятичная мантисса (96 бит) + знак + масштаб:
                 точно представляет любое число с ≤28-29 значащими цифрами,
                 записанное как конечная десятичная дробь
```

```csharp
Console.WriteLine(0.1 + 0.2 == 0.3);        // False — двоичное приближение
Console.WriteLine(0.1m + 0.2m == 0.3m);     // True  — decimal хранит десятичные дроби точно

double d = 1_000_000.1;
for (int i = 0; i < 10; i++) d += 0.1;
Console.WriteLine(d);                        // 1000001.0999999999 — накопленная погрешность

decimal m = 1_000_000.1m;
for (int i = 0; i < 10; i++) m += 0.1m;
Console.WriteLine(m);                        // 1000001.1 — точно
```

Разница не в «количестве знаков после запятой» — оба типа могут хранить много цифр. Разница в том, какие дроби представимы без потерь: `double` точен для сумм степеней двойки, `decimal` точен для сумм степеней десяти. Деньги десятичны по определению (100 копеек в рубле), поэтому `decimal` для них не «более точный», а единственно верный по смыслу представления.

Плата за точность — размер и скорость: `decimal` занимает 16 байт против 8 у `double`, а арифметика реализована программно, а не инструкциями процессора, и потому в 10-20 раз медленнее. Для денежных сумм в бизнес-логике эта разница не имеет значения — счётчик операций там на порядки меньше, чем в численных расчётах.

### checked и unchecked: переполнение целых

Отдельно от плавающей точки стоит целочисленное переполнение — оно касается `int`/`long`-счётчиков, которые тоже нередко участвуют в денежной логике (число товаров, число платежей, ID).

```csharp
int max = int.MaxValue;
Console.WriteLine(max + 1);            // -2147483648, молча, без исключения
Console.WriteLine(checked(max + 1));    // OverflowException
```

По умолчанию арифметика `int`/`long` — `unchecked`: переполнение заворачивается по модулю, без сигнала. `checked` (выражением, блоком или глобально через `<CheckForOverflowUnderflow>` в `.csproj`) включает проверку. Три частных случая, которые определяют, где вообще искать переполнение:

- **`decimal` бросает `OverflowException` всегда**, вне зависимости от `checked`/`unchecked` — арифметика decimal реализована в библиотеке, а не набором инструкций процессора.
- **`float`/`double` никогда не переполняются** — при выходе за диапазон получается `Infinity`, проверяется через `double.IsFinite`.
- **Константные выражения проверяются компилятором всегда**, обойти можно только через `unchecked(...)`.

Практика для проекта: `CheckForOverflowUnderflow` включён в Debug/тестовой конфигурации (переполнение находится на этапе разработки), в Release — точечный `checked` вокруг мест, где переполнение реально возможно по смыслу данных: суммирование по большому набору строк заказа, расчёт итоговой суммы рассрочки в минимальных единицах (копейках/тийинах).

### Культура при парсинге и форматировании

```csharp
// В ru-RU и uz-UZ десятичный разделитель — запятая, точка — разделитель разрядов
// double.Parse("19.99") без культуры на сервере с локалью ru-RU даст 1999, а не 19.99

using System.Globalization;

decimal price = decimal.Parse("19.99", NumberStyles.Number, CultureInfo.InvariantCulture);
string display = price.ToString("N2", new CultureInfo("ru-RU"));   // "19,99"
```

Правило простое и не имеет исключений: **машинные данные (JSON, CSV, интеграции, значения в БД, сообщения Kafka) — только `CultureInfo.InvariantCulture`**, при разборе и при форматировании. Культура пользователя применяется исключительно на границе с интерфейсом — там, где сумму видит человек. Перепутанная сторона обычно не ловится локально: на машине разработчика и в CI культура одна, на проде — другая, и сумма превращается из «19.99» в «1999» без единого исключения на этапе сборки.

## Решения

| Тип | Когда выбирать | Чего не делать |
|---|---|---|
| `decimal` | Любые денежные суммы: цена, комиссия, платёж, остаток по рассрочке | Не парсить через `double`, не хранить как `float` в БД ради экономии места |
| `double`/`float` | Научные и инженерные расчёты, где важна скорость, а погрешность в 15-й цифре не имеет бизнес-смысла: координаты, физика, ML-признаки | Не использовать «потому что быстрее» там, где результат сравнивается или суммируется как деньги |
| `int`/`long` | Счётчики, количество, ID, суммы в минимальных неделимых единицах (копейки/тийины), если проект сознательно выбрал целочисленное денежное представление | Не использовать `int` для промежуточных сумм без расширения типа — переполнение на большом заказе тихое |
| `decimal` в минимальных единицах | Когда единственная операция — сложение/сравнение без деления с остатком (кэш, лимиты) | Не путать с плавающей точкой «для скорости»: выигрыш не окупает риск округления |

Общий критерий: если число когда-либо сравнивается на равенство, суммируется много раз или показывается пользователю как сумма к оплате — это `decimal`. Если число участвует в вычислениях, где сам предмет измерения непрерывен (расстояние, вес, вероятность), и точность до последней цифры не входит в контракт — `double` уместен.

> [!example] В ServiceShop
> В денежной логике проекта — расчёте суммы заказа, комиссии маркетплейса и графика платежей по рассрочке — все суммы проходят через `decimal` от чтения из БД (MySQL хранит их как `DECIMAL(p,s)`, что соответствует представлению один в один) до сериализации в ответ API. Промежуточные приведения к `double` не встречаются: как только сумма попадает в `decimal`, она в нём и остаётся до конца расчёта, а округление до копеек выполняется один раз — в конце цепочки вычислений графика, явной стратегией (`MidpointRounding.AwayFromZero` для сумм, показываемых клиенту), а не там, где это исторически получилось. Это тот случай, когда «модель не доделана», если `decimal` парсится из строки в нескольких разных хендлерах вместо одной точки на границе.

> [!warning] Где ошибаются
> - **Агент часто:** предлагает `double` для денег, потому что в обучающих примерах и туториалах it's the default numeric type — `double price = 19.99` компилируется без предупреждений и выглядит невинно, а расхождение проявляется только при суммировании большого количества операций.
> - **Агент часто:** ставит `Math.Round(x, 2)` без `MidpointRounding` и не проверяет, что банковское округление (к чётному, по умолчанию) — это не то, что ожидает бизнес-требование «округлять 0.5 всегда вверх».
> - **`(int)` или `(long)` вместо `Math.Round` при переводе суммы в минимальные единицы.** Приведение отбрасывает дробную часть, а не округляет — итог систематически занижен, и ошибка одного знака в приведении незаметна на code review, потому что синтаксически всё верно.
> - **Смешение `decimal` и `double` в одном выражении.** Компилятор не разрешит неявно (`CS0664`), но явное приведение `(double)someDecimal` в середине денежного расчёта проходит ревью незамеченным, а погрешность появляется именно в точке приведения.
> - **`checked` вокруг всего выражения, когда переполнение происходит в промежуточном типе.** Если сумма считается как `int * int`, оборачивание итогового `long` в `checked` ничего не даст — переполнение уже случилось до расширения типа.

## Проверка на ревью

- Все денежные поля (цена, комиссия, сумма платежа, остаток) объявлены как `decimal`, не `double`/`float`.
- Нет явных приведений `(double)` или `(float)` для значений, которые участвуют в денежном расчёте.
- Округление денежных сумм выполняется явным `Math.Round(value, digits, MidpointRounding.X)` в одном месте расчёта, а не через `(int)`/`(long)`.
- Парсинг и форматирование сумм передают `CultureInfo.InvariantCulture`, если данные идут не напрямую в интерфейс пользователя.
- Счётчики и суммы, которые могут расти без ограничения (агрегация по большому набору строк заказа), используют тип шире исходных слагаемых или явный `checked`.
- В `.csproj` для Debug/Test включён `<CheckForOverflowUnderflow>`, если раньше в проекте были инциденты с переполнением.

## Проверь себя

> [!question]- Почему `decimal` подходит для денег лучше, чем `double`, если оба хранят дробные числа?
> `double` — это двоичное приближение: он точно представляет только суммы степеней двойки, а десятичные дроби вроде 0.1 хранятся с бесконечным повторяющимся остатком, как 1/3 в десятичной записи. `decimal` использует десятичную мантиссу и точно представляет любое число, записанное как конечная десятичная дробь — то есть ровно то, чем являются деньги (копейки, центы). При многократном суммировании `double` накапливает погрешность, которая в денежном контексте означает расхождение баланса; `decimal` при тех же операциях остаётся точным. Плата — размер (16 байт против 8) и более медленная программная арифметика, что для объёма операций в бизнес-логике несущественно.

> [!question]- Что произойдёт при `int.MaxValue + 1` в обычном коде и что изменится внутри `checked`?
> По умолчанию арифметика `int` — `unchecked`: результат вычисляется по модулю 2³² и заворачивается без сигнала, `int.MaxValue + 1` даст `int.MinValue`. Обёртка `checked` (выражением, блоком или глобальной настройкой проекта) заставляет ту же операцию бросить `OverflowException`. Есть отдельные случаи вне этого правила: константные выражения компилятор проверяет всегда, `decimal` бросает исключение при переполнении независимо от контекста, а `float`/`double` вместо исключения дают `Infinity`.

> [!question]- Почему `Math.Round(2.5)` даёт 2, а не 3, и как это влияет на денежные расчёты?
> По умолчанию `Math.Round` использует `MidpointRounding.ToEven` — округление к ближайшему чётному числу, а не «школьное» округление 0.5 вверх. Это соответствует IEEE 754 и уменьшает систематическое смещение при массовом суммировании округлённых значений. Для денежных сумм, где бизнес-правило часто требует конкретную стратегию (например, всегда округлять в пользу продавца или клиента), нельзя полагаться на поведение по умолчанию — стратегию нужно указывать явно вторым аргументом (`MidpointRounding.AwayFromZero` и т.д.) и фиксировать её в одном месте расчёта, а не в каждом вызове по отдельности.

> [!question]- Почему сумма, распарсенная как `double.Parse("19.99")`, может вдруг стать 1999 на проде?
> Без явно указанной культуры `Parse` использует текущую культуру потока выполнения. В `ru-RU` и `uz-UZ` десятичный разделитель — запятая, а точка воспринимается как разделитель групп разрядов — поэтому строка "19.99" разбирается как "1999". Локально и в CI культура часто английская или инвариантная, а на сервере в проде — региональная, поэтому ошибка не ловится тестами и проявляется только в проде. Решение — всегда передавать `CultureInfo.InvariantCulture` явно для машинных форматов (JSON, интеграции, конфиги) и культуру пользователя — только на границе с интерфейсом.

> [!question]- Почему `checked` вокруг итогового сложения не спасает от переполнения, если промежуточный расчёт был в `int`?
> `checked` проверяет переполнение только той операции, которую непосредственно оборачивает. Если промежуточное значение уже посчитано и переполнилось в более узком типе (например, `int * int`) до того, как результат присвоен переменной более широкого типа, то к моменту, когда `checked` окружает финальное сложение, искажённое значение уже существует — проверять поздно. Правильно — заранее расширять тип операндов там, где промежуточный результат может выйти за диапазон: `(long)a * b`, а не `(long)(a * b)`.

## Разбор

### Упражнение 1. Найти проблему

```csharp
public decimal CalculateInstallmentPayment(double totalAmount, int months)
{
    double monthly = totalAmount / months;
    return (decimal)monthly;
}
```

> [!success]- Решение
> Расчёт денежной суммы целиком идёт через `double`, хотя на входе и на выходе — деньги: `totalAmount` должен быть `decimal` с самого начала, деление тоже должно выполняться в `decimal`. Приведение `(decimal)monthly` в конце не восстанавливает точность, которая уже была потеряна в двоичном представлении на предыдущем шаге, а лишь придаёт результату вид денежного типа. Кроме того, нет округления и нет обработки `months == 0`. Исправленная сигнатура: `decimal CalculateInstallmentPayment(decimal totalAmount, int months)` с явным `Math.Round(totalAmount / months, 2, MidpointRounding.AwayFromZero)` и проверкой `months > 0` до деления.

### Упражнение 2. Обосновать выбор

Ревьюер видит в PR два варианта хранения суммы комиссии маркетплейса: `decimal CommissionAmount` или `int CommissionCents` (сумма в минимальных единицах). Оба варианта используются в разных частях кодовой базы. Что спросить у автора PR, прежде чем одобрять?

> [!success]- Решение
> Оба варианта корректны с точки зрения точности — `decimal` точен для десятичных дробей, целое число в минимальных единицах по определению не имеет дробной части и потому не может накопить погрешность округления. Вопрос не «что точнее», а «что согласовано с остальной моделью»: если соседние поля в той же агрегатной сущности уже хранятся как `decimal` (обычная практика для сумм, приходящих из EF Core с колонкой `DECIMAL`), смешение с `int`-центами внутри одной модели создаёт постоянную необходимость конвертации на границах и удваивает число мест, где можно ошибиться в масштабе (перепутать копейки с рублями). Проверить стоит: есть ли уже принятый в модуле стандарт представления денег, и не разойдётся ли новое поле с ним без веской причины (производительность, интеграция с внешней системой, которая требует целых копеек).

## Итог

- `decimal` точно представляет десятичные дроби и создан для денег; `double`/`float` — двоичное приближение для научных расчётов, где потеря 15-го знака не имеет значения.
- Округление денежных сумм всегда явное: `Math.Round` с указанной `MidpointRounding`, а не приведение `(int)`/`(long)`, которое отбрасывает дробную часть, а не округляет.
- Целочисленное переполнение по умолчанию тихое (`unchecked`); `decimal` переполняется с исключением всегда, `double`/`float` не переполняются вовсе, а дают `Infinity`.
- Культура при разборе и форматировании сумм задаётся явно: `InvariantCulture` для машинных данных, культура пользователя — только в интерфейсе.
- Признак недоделанной денежной модели — многократный парсинг суммы из строки в разных местах вместо одной точки на границе системы.
