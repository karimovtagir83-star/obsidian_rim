# Стиль кода, соглашения и .editorconfig

> [!abstract] Коротко
> Стиль кода — не вкусовщина, а способ не тратить внимание на форму. В .NET есть общепринятые соглашения (PascalCase для типов и членов, camelCase для локальных, `_camelCase` для приватных полей, суффикс `Async`), и они не обсуждаются в каждой команде заново. Формальную часть автоматизируют: `.editorconfig` описывает правила, анализаторы находят нарушения, `<TreatWarningsAsErrors>` превращает их в ошибки сборки, а `dotnet format` исправляет. Настроить это стоит в первый же день — переучиваться потом дороже.

## Зачем это нужно

Три конкретных выгоды, а не «красиво».

**Чтение.** Код читают в 10 раз чаще, чем пишут. Единый стиль означает, что взгляд не спотыкается: увидел `_orders` — понял, что это приватное поле, увидел `SaveAsync` — понял, что нужно `await`.

**Чистые диффы.** Если у двоих разные настройки форматирования, каждый коммит переформатирует полфайла. Ревью тонет в шуме, `git blame` перестаёт отвечать на вопрос «кто и зачем это написал», конфликты слияния возникают на пустом месте.

**Ошибки, найденные компилятором.** Анализаторы .NET ловят не стиль, а баги: сравнение строк без `StringComparison`, `IDisposable` без `using`, `async void`, пустой `catch`, неиспользуемый результат. Это тот же класс проблем, что позже ищут на код-ревью, только бесплатно и мгновенно.

## Соглашения об именовании .NET

| Что | Стиль | Пример |
|---|---|---|
| Классы, структуры, record, enum, делегаты | `PascalCase` | `OrderService`, `PaymentStatus` |
| Интерфейсы | `I` + `PascalCase` | `IOrderRepository` |
| Методы, свойства, события | `PascalCase` | `CalculateTotal`, `IsActive` |
| Публичные и protected поля | `PascalCase` (но лучше свойства) | `MaxRetries` |
| Приватные поля | `_camelCase` | `_logger`, `_orders` |
| Статические приватные поля | `_camelCase` или `s_camelCase` | `_cache`, `s_instance` |
| Константы | `PascalCase` (**не** UPPER_CASE) | `DefaultTimeout` |
| Локальные переменные, параметры | `camelCase` | `orderId`, `total` |
| Параметры типа (generic) | `T` + описание | `T`, `TKey`, `TResult` |
| Асинхронные методы | суффикс `Async` | `LoadAsync`, `SaveAsync` |
| Пространства имён | `Company.Product.Feature` | `Alif.ServiceShop.Orders` |
| Файл | по имени основного типа | `OrderService.cs` |

Отдельные правила, которые часто нарушают:

```csharp
// Аббревиатуры: две буквы — обе заглавные, три и больше — как слово
public string Id { get; }            // не ID
public IPAddress Address { get; }     // две буквы — IP
public string HtmlContent { get; }    // не HTMLContent
public Guid CustomerId { get; }        // не CustomerID, не customerID

// Никакой венгерской нотации и префиксов типов
string strName;      // плохо
int iCount;          // плохо
string name;         // хорошо

// Булевы — вопросительная форма
bool IsActive, HasItems, CanRefund, ShouldRetry;   // хорошо
bool Active, Items;                                 // хуже: непонятно, что это флаг

// Асинхронность видна в имени
Task<Order> GetOrderAsync(long id);       // хорошо
Task<Order> GetOrder(long id);            // плохо: на вызове забудут await

// Единственное/множественное число отражает кардинальность
List<Order> orders;      // коллекция
Order order;             // один элемент
```

Про имена важнее любых правил: **имя должно объяснять смысл, а не тип**. `var d = 30;` — плохо; `var timeoutSeconds = 30;` — хорошо; `var timeout = TimeSpan.FromSeconds(30);` — ещё лучше, потому что единица измерения ушла в тип.

## Форматирование

Стандарт .NET (он же по умолчанию в Visual Studio, Rider и `dotnet format`):

```csharp
// Отступ — 4 пробела, не табы. Фигурные скобки — на новой строке (стиль Allman).
namespace Alif.ServiceShop.Orders;          // file-scoped namespace (C# 10) — без лишнего уровня

using System.Text;                           // System.* первыми, затем остальные,
using Microsoft.Extensions.Logging;          // внутри групп — по алфавиту

public sealed class OrderService
{
    private readonly IOrderRepository _repository;
    private readonly ILogger<OrderService> _logger;

    public OrderService(IOrderRepository repository, ILogger<OrderService> logger)
    {
        _repository = repository;
        _logger = logger;
    }

    public async Task<Order?> FindAsync(long id, CancellationToken ct)
    {
        if (id <= 0)
        {
            return null;                      // скобки даже для однострочного блока
        }

        return await _repository.GetAsync(id, ct);
    }
}
```

Порядок членов внутри типа (соглашение, а не требование компилятора): константы → статические поля → поля экземпляра → конструкторы → свойства → методы → вложенные типы. Внутри каждой группы — от `public` к `private`.

Ещё несколько правил, которые экономят споры:

- один публичный тип на файл, имя файла = имя типа;
- длина строки — 120 символов (число условно, но должно быть согласовано и проверяться);
- `var` там, где тип очевиден из правой части; явный тип, когда он приходит из вызова метода;
- фигурные скобки всегда, кроме, возможно, `using`-объявлений и `return` в guard-выражениях — единый выбор фиксируется в `.editorconfig`;
- `this.` не используется, кроме случаев неоднозначности (для этого и нужен префикс `_` у полей).

## .editorconfig: правила как код

`.editorconfig` — текстовый файл в корне репозитория, который читают все современные IDE и компилятор. Он делает стиль частью проекта, а не настроек человека.

```ini
# .editorconfig в корне решения
root = true

[*]
charset = utf-8
end_of_line = lf
insert_final_newline = true
trim_trailing_whitespace = true
indent_style = space
indent_size = 4

[*.{json,yml,yaml,xml,csproj,props}]
indent_size = 2

[*.cs]
# --- Форматирование ---
csharp_new_line_before_open_brace = all
csharp_new_line_before_else = true
csharp_indent_case_contents = true
csharp_space_after_keywords_in_control_flow_statements = true
dotnet_sort_system_directives_first = true
csharp_using_directive_placement = outside_namespace:warning
csharp_style_namespace_declarations = file_scoped:warning

# --- Предпочтения языка (уровень = severity диагностики) ---
csharp_style_var_when_type_is_apparent = true:suggestion
csharp_style_var_elsewhere = false:suggestion
csharp_prefer_braces = true:warning
csharp_style_prefer_pattern_matching = true:suggestion
csharp_style_throw_expression = true:suggestion
csharp_style_expression_bodied_methods = when_on_single_line:suggestion
dotnet_style_prefer_conditional_expression_over_assignment = true:suggestion
dotnet_style_readonly_field = true:warning
dotnet_style_require_accessibility_modifiers = for_non_interface_members:warning

# --- Именование: приватные поля с подчёркиванием ---
dotnet_naming_rule.private_fields_underscore.severity = warning
dotnet_naming_rule.private_fields_underscore.symbols = private_fields
dotnet_naming_rule.private_fields_underscore.style = underscore_camel

dotnet_naming_symbols.private_fields.applicable_kinds = field
dotnet_naming_symbols.private_fields.applicable_accessibilities = private

dotnet_naming_style.underscore_camel.required_prefix = _
dotnet_naming_style.underscore_camel.capitalization = camel_case

# --- Диагностики анализаторов ---
dotnet_diagnostic.CA1305.severity = warning   # указывать IFormatProvider
dotnet_diagnostic.CA1307.severity = warning   # указывать StringComparison
dotnet_diagnostic.CA1310.severity = warning   # StartsWith/EndsWith без StringComparison
dotnet_diagnostic.CA2007.severity = none      # ConfigureAwait — не нужен в ASP.NET Core
dotnet_diagnostic.CA1848.severity = suggestion# LoggerMessage вместо LogInformation
dotnet_diagnostic.IDE0055.severity = warning  # нарушение форматирования

# Сгенерированный код исключаем из правил
[**/Migrations/*.cs]
generated_code = true
```

Как это работает: файлы применяются от корня к текущему каталогу, `root = true` останавливает подъём выше. Значит, для сгенерированного кода или тестов можно положить свой `.editorconfig` в подкаталог и ослабить там часть правил (например, разрешить длинные имена методов-тестов с подчёркиваниями — правило CA1707).

Суффикс `:warning`/`:suggestion`/`:error`/`:none` задаёт, насколько громко IDE и сборка реагируют. Правила без суффикса, заданные через `dotnet_diagnostic.*.severity`, работают так же.

## Анализаторы и сборка

```xml
<!-- Directory.Build.props в корне решения: применяется ко всем проектам -->
<Project>
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <LangVersion>latest</LangVersion>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>

    <!-- Предупреждения — это ошибки. Единственный способ, чтобы их не игнорировали -->
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <!-- Кроме отдельных, если это осознанное решение -->
    <WarningsNotAsErrors>CS1591</WarningsNotAsErrors>

    <!-- Анализаторы .NET включены по умолчанию для net5.0+; поднимаем строгость -->
    <AnalysisLevel>latest-recommended</AnalysisLevel>
    <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>

    <!-- XML-документация: нужна для библиотек и для OpenAPI-описаний -->
    <GenerateDocumentationFile>true</GenerateDocumentationFile>
  </PropertyGroup>
</Project>
```

`EnforceCodeStyleInBuild` — ключевая строка: без неё правила `IDE*` из `.editorconfig` работают только в IDE, и сборка их не проверяет. С ней стиль ломает CI, а значит, соблюдается.

Дополнительные наборы анализаторов, которые обычно добавляют:

| Пакет | Что даёт |
|---|---|
| встроенные .NET analyzers | корректность и API-практики (CA*), стиль (IDE*) |
| `StyleCop.Analyzers` | детальные правила оформления и порядка членов (SA*) |
| `Roslynator.Analyzers` | упрощения и рефакторинги, много полезных подсказок |
| `SonarAnalyzer.CSharp` | поиск дефектов и «запахов», близко к промышленному SAST |
| `Meziantou.Analyzer` | практичный набор про async, culture, DI |

Не нужно включать всё сразу: набор правил с включённым `TreatWarningsAsErrors` на существующем проекте даст тысячи ошибок. Порядок внедрения: включить встроенные анализаторы → зафиксировать текущее состояние (нарушения как `suggestion`) → чинить по одному правилу за коммит → поднимать до `warning`/`error`.

### Команды

```bash
dotnet format                          # исправить форматирование и стиль по .editorconfig
dotnet format --verify-no-changes      # проверить без изменений — то, что ставят в CI
dotnet build -warnaserror              # разово собрать со строгими предупреждениями
```

Шаг в CI, который экономит все споры о стиле:

```yaml
- run: dotnet format --verify-no-changes --severity warn
- run: dotnet build --configuration Release   # с TreatWarningsAsErrors из props
```

## Комментарии и XML-документация

```csharp
/// <summary>
/// Рассчитывает итог заказа с учётом скидок и налога.
/// </summary>
/// <param name="order">Заказ; должен содержать хотя бы одну позицию.</param>
/// <param name="ct">Токен отмены.</param>
/// <returns>Итоговая сумма в валюте заказа.</returns>
/// <exception cref="ArgumentException">Заказ не содержит позиций.</exception>
public async Task<decimal> CalculateTotalAsync(Order order, CancellationToken ct) { }
```

XML-комментарии обязательны для публичного API библиотек: они попадают в IntelliSense потребителя, в NuGet-пакет и, начиная с .NET 10, в описание OpenAPI через генератор исходного кода. Для внутреннего кода — по потребности.

Правило про обычные комментарии: **комментарий объясняет «почему», а не «что»**.

```csharp
// Плохо: пересказ кода
// увеличиваем счётчик на 1
count++;

// Хорошо: объясняет решение, которого не видно в коде
// Платёжный шлюз возвращает 429 при более чем 5 запросах в секунду,
// поэтому здесь намеренная задержка, а не Task.WhenAll.
await Task.Delay(200, ct);

// Хорошо: помечает известный компромисс с адресом
// TODO(SHOP-1423): убрать после миграции клиентов на v2 API. Срок — Q4.
```

`TODO` без тикета и срока — это мусор: он не будет сделан и не будет удалён. Анализаторы умеют такие комментарии подсвечивать, а CI — запрещать новые.

> [!warning] Подводные камни
> - **`.editorconfig` без `root = true` в корне.** IDE продолжит подниматься выше по дереву каталогов и может подхватить чужие настройки, а поведение станет зависеть от того, где лежит репозиторий.
> - **Правила стиля без `EnforceCodeStyleInBuild`.** В IDE подсветка есть, в CI — нет; через месяц половина кода не соответствует конфигу.
> - **`TreatWarningsAsErrors` на старом проекте без подготовки.** Сборка перестанет собираться, и правило отключат целиком. Внедрять по шагам.
> - **Обновление SDK ломает сборку.** Новая версия добавляет новые предупреждения, а они у тебя ошибки. Лечится закреплением `AnalysisLevel` на конкретной версии (`latest` → `9.0`, `10.0`) и осознанным обновлением.
> - **Коммит «переформатировал весь проект».** Смешивать форматирование с логикой нельзя: ревью становится невозможным. Форматирование — отдельным коммитом, а его хеш добавляют в `.git-blame-ignore-revs` (`git config blame.ignoreRevsFile .git-blame-ignore-revs`), чтобы `git blame` его пропускал.
> - **`#pragma warning disable` без комментария.** Через полгода никто не помнит, почему правило отключено, и оно остаётся навсегда. Отключение всегда с причиной и, по возможности, локальное.
> - **Стиль вместо смысла на ревью.** Если люди спорят о скобках, значит автоматизация не настроена. Настроенная автоматизация освобождает ревью для обсуждения логики.

> [!example] Как делают в бою
> В зрелом .NET-репозитории есть три файла, задающих правила для всех: `.editorconfig` (стиль и severity), `Directory.Build.props` (TFM, `Nullable`, `TreatWarningsAsErrors`, анализаторы), `Directory.Packages.props` (централизованные версии пакетов). Плюс `.gitattributes` с `*.cs text eol=lf`, чтобы переводы строк не создавали фантомных диффов между macOS и Linux.
> CI прогоняет `dotnet format --verify-no-changes` и сборку с предупреждениями-ошибками до тестов: дешёвые проверки — первыми.
> При внедрении на существующий проект правила не включают разом. Сначала `dotnet format` одним коммитом (и его хеш — в `.git-blame-ignore-revs`), затем анализаторы на уровне `suggestion`, затем поочерёдный подъём до `warning` с чисткой. Так стиль становится фоном, а не поводом для конфликтов.

## Вопросы с собеседований

> [!question]- Зачем нужен `.editorconfig`, если у каждого своя IDE?
> Потому что его читают все основные IDE (Visual Studio, Rider, VS Code) и сам компилятор Roslyn: правила становятся частью репозитория, а не настроек человека. Это даёт три вещи. Единый формат — коммиты не содержат случайного переформатирования, `git blame` остаётся полезным, конфликты слияния не возникают из-за отступов. Единая строгость диагностик — через `dotnet_diagnostic.*.severity` можно поднять правило до предупреждения или ошибки, и это применится в сборке при `EnforceCodeStyleInBuild`. И иерархичность — правила можно ослабить в подкаталоге (например, разрешить имена тестов с подчёркиваниями) без глобальных исключений. Без `.editorconfig` соблюдение стиля превращается в ручной труд на код-ревью.

> [!question]- Почему приватные поля называют с подчёркиванием, а константы — PascalCase?
> Подчёркивание у приватных полей решает практическую задачу: сразу видно, что это состояние объекта, а не локальная переменная или параметр, и не нужен префикс `this.` для устранения неоднозначности в конструкторе (`_name = name;`). Это соглашение самого .NET-рантайма и большинства команд, хотя формально компилятор к нему безразличен. Константы в .NET пишут в `PascalCase`, а не в `UPPER_SNAKE_CASE`, потому что для потребителя `const`, `static readonly` и обычное свойство — одна и та же вещь: значение, доступное только для чтения. Способ реализации не должен просачиваться в имя; если завтра `const` станет `static readonly` (а это регулярно происходит из-за версионирования), имя менять не придётся.

> [!question]- Что даёт `<TreatWarningsAsErrors>` и в чём его риск?
> Он превращает все предупреждения компилятора и анализаторов в ошибки сборки. Смысл в том, что предупреждения, которые «просто есть», накапливаются и перестают читаться: через год их триста, и новое важное теряется в шуме. С этим свойством нельзя влить код, который снижает качество, — и это самый дешёвый механизм контроля из существующих. Риски два. Первый: обновление SDK или версии анализаторов добавляет новые правила, и сборка ломается на коде, который не менялся; лечится закреплением `AnalysisLevel` на конкретной версии и осознанным обновлением. Второй: на большом существующем проекте включение сразу даёт тысячи ошибок, и правило отключают целиком; поэтому внедряют поэтапно, а отдельные правила выводят через `WarningsNotAsErrors`.

> [!question]- Когда комментарий полезен, а когда вреден?
> Полезен, когда объясняет то, чего в коде нет: причину неочевидного решения, ограничение внешней системы, ссылку на тикет или спецификацию, сознательный компромисс. Вреден, когда пересказывает код (`// увеличиваем счётчик`) — такой комментарий не добавляет информации и рассинхронизируется при первом же изменении, после чего активно вводит в заблуждение. Отдельный случай — комментарий, компенсирующий плохое имя: вместо пояснения, что такое `d`, надо переименовать в `delayBeforeRetry`. Для публичного API комментарии обязательны в форме XML-документации: они попадают в IntelliSense потребителя, в NuGet-пакет и в описание OpenAPI. И правило про `TODO`: без номера тикета и владельца это не задача, а декорация.

## Задачи

### Задача 1. Исправить именование

```csharp
public class OrderService
{
    public IOrderRepository Repository;
    private const int MAX_RETRY_COUNT = 3;
    public Task<Order> getOrder(long ID) { }
    public bool active;
}
```

> [!success]- Решение
> ```csharp
> public sealed class OrderService                      // PascalCase, sealed по умолчанию
> {
>     private const int MaxRetryCount = 3;               // константы — PascalCase, и они приватные
>     private readonly IOrderRepository _repository;      // приватное поле, readonly, _camelCase
>
>     public OrderService(IOrderRepository repository) => _repository = repository;
>
>     public bool IsActive { get; private set; }          // свойство, а не публичное поле; вопросительная форма
>
>     public Task<Order?> GetOrderAsync(long id, CancellationToken ct) => _repository.GetAsync(id, ct);
> }
> ```
> Изменения по пунктам: имя типа в `PascalCase`; публичное изменяемое поле `Repository` заменено на приватное `readonly` поле, потому что зависимость не должна быть доступна снаружи; константа в `PascalCase` вместо стиля C; метод в `PascalCase` с суффиксом `Async`, потому что он возвращает `Task`; параметр `ID` → `id` (аббревиатура из двух букв, но это параметр, значит camelCase); публичное поле `active` → свойство `IsActive`. Добавлены `CancellationToken` и `Order?` — асинхронный метод, который может не найти заказ, должен и то и другое отражать в подписи.

### Задача 2. Собрать минимальный набор настроек для нового проекта

Какие файлы и свойства ты добавишь в новый репозиторий на .NET 10 в первый день?

> [!success]- Решение
> Четыре файла.
> `.editorconfig` с `root = true`: кодировка UTF-8, `end_of_line = lf`, отступ 4 пробела, `csharp_style_namespace_declarations = file_scoped`, правило `_camelCase` для приватных полей, `dotnet_diagnostic.CA1307/CA1310.severity = warning` (сравнение строк), `IDE0055 = warning` (форматирование).
> `Directory.Build.props`: `TargetFramework net10.0`, `Nullable enable`, `ImplicitUsings enable`, `TreatWarningsAsErrors true`, `AnalysisLevel latest-recommended`, `EnforceCodeStyleInBuild true`, `GenerateDocumentationFile true` для библиотек.
> `Directory.Packages.props` с `ManagePackageVersionsCentrally` — чтобы версии пакетов не разъезжались между проектами решения.
> `.gitattributes` с `* text=auto` и `*.cs text eol=lf` — иначе переводы строк между macOS и Linux-контейнерами дадут фантомные диффы и падающие shell-скрипты.
> Плюс шаг в CI: `dotnet format --verify-no-changes` и сборка в Release. Всё это занимает полчаса в начале и экономит недели спорах и «переформатировал весь файл» коммитах потом.

## Итог

- Соглашения .NET: `PascalCase` для типов и членов, `camelCase` для локальных, `_camelCase` для приватных полей, `I` для интерфейсов, суффикс `Async`, константы в `PascalCase`.
- Имя объясняет смысл, а не тип; единицы измерения лучше выражать типом, а не именем.
- `.editorconfig` делает стиль частью репозитория; иерархия файлов позволяет ослаблять правила локально.
- `EnforceCodeStyleInBuild` и `TreatWarningsAsErrors` — то, что превращает договорённость в проверяемое требование.
- Анализаторы ловят не стиль, а дефекты: культура, `StringComparison`, `IDisposable`, `async void`.
- Внедрять на существующем проекте по шагам: форматирование одним коммитом, правила через `suggestion`, затем подъём строгости.
