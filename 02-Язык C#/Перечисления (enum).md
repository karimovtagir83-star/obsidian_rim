# Перечисления (enum)

> [!abstract] Коротко
> `enum` — набор именованных констант поверх целочисленного типа (по умолчанию `int`). Это значимый тип, и он **не гарантирует валидность**: `(OrderStatus)999` компилируется, работает и спокойно доезжает до базы данных, потому что в рантайме enum — это просто число. Отсюда два практических вывода: значения, попавшие в хранилище или в API, нельзя перенумеровывать, а данные, пришедшие извне, надо проверять. Отдельная разновидность — `[Flags]`-перечисления, где значения являются степенями двойки и комбинируются битовыми операциями.

## Зачем это нужно

`enum` заменяет магические значения понятными именами и превращает часть ошибок в ошибки компиляции:

```csharp
// Было
if (order.Status == 3) { }              // что такое 3?
order.Status = 7;                        // а 7 вообще существует?

// Стало
if (order.Status == OrderStatus.Shipped) { }
```

Плюс подсказки IDE, полнота разбора в `switch`-выражении и осмысленное имя в логах. Это самый дешёвый способ сделать код самодокументируемым — и одновременно тип, вокруг которого больше всего заблуждений.

## Основы

```csharp
public enum OrderStatus
{
    New,           // 0 — значение по умолчанию
    Paid,          // 1 — нумерация продолжается автоматически
    Shipped = 10,  // можно задать явно
    Delivered,     // 11
    Cancelled = 99
}

OrderStatus status = OrderStatus.Paid;
Console.WriteLine(status);              // Вывод: Paid
Console.WriteLine((int)status);         // Вывод: 1
Console.WriteLine(status.ToString());   // Вывод: Paid — но это дорого, см. ниже

// Базовый тип можно изменить: экономия памяти в больших массивах или соответствие протоколу
public enum SmallStatus : byte { A, B, C }
public enum BigCode : long { X = 10_000_000_000 }
```

Обязательное правило проектирования: **значение 0 должно быть осмысленным**. Поле структуры или необнулённая память дают `default(T)`, то есть 0, и если под нулём числится `Deleted`, объект по умолчанию окажется удалённым. Поэтому под нулём держат `None`/`Unknown`/`New`.

### Что даёт статический класс `Enum`

```csharp
// Перебор значений — generic-версии без упаковки, .NET 5+
foreach (var value in Enum.GetValues<OrderStatus>())
    Console.WriteLine($"{value} = {(int)value}");

Console.WriteLine(string.Join(", ", Enum.GetNames<OrderStatus>()));

// Разбор строки: только TryParse и только с явным игнорированием регистра при необходимости
if (Enum.TryParse<OrderStatus>("paid", ignoreCase: true, out var parsed))
    Console.WriteLine(parsed);                     // Вывод: Paid

// Проверка, что число соответствует объявленному значению
Console.WriteLine(Enum.IsDefined(OrderStatus.Cancelled));    // True
Console.WriteLine(Enum.IsDefined((OrderStatus)999));         // False
```

> [!danger] `Enum.TryParse` принимает числа
> ```csharp
> Enum.TryParse<OrderStatus>("999", out var weird);   // true! weird == (OrderStatus)999
> ```
> `TryParse` разбирает не только имена, но и числовые строки, и результат не проверяется на принадлежность перечислению. Поэтому для внешнего ввода нужна пара: `TryParse` + `Enum.IsDefined`.

## Enum не является гарантией

```csharp
OrderStatus fromDb = (OrderStatus)ReadIntFromDatabase();   // может быть что угодно
Console.WriteLine(fromDb);                                  // Вывод: 42 — просто число

// Значит, разбор должен учитывать невозможное:
string label = fromDb switch
{
    OrderStatus.New => "новый",
    OrderStatus.Paid => "оплачен",
    OrderStatus.Shipped => "отправлен",
    OrderStatus.Delivered => "доставлен",
    OrderStatus.Cancelled => "отменён",
    _ => throw new ArgumentOutOfRangeException(nameof(fromDb), fromDb, "Неизвестный статус")
};
```

Причина в устройстве CLR: enum — это `int` с именами на этапе компиляции, приведение из числа не проверяется, а арифметика над enum разрешена. Отсюда три источника «невозможных» значений: приведение из числа, десериализация (JSON с числом `42` или неизвестной строкой при определённых настройках) и чтение из БД, где данные записал старый код или миграция.

Поэтому граница системы валидирует enum так же, как любые другие данные. Внутри — уже можно доверять.

## Флаги

Когда нужен **набор** значений, а не одно, применяют битовые флаги:

```csharp
[Flags]
public enum Permissions
{
    None    = 0,
    Read    = 1 << 0,      // 1
    Write   = 1 << 1,      // 2
    Delete  = 1 << 2,      // 4
    Manage  = 1 << 3,      // 8
    All     = Read | Write | Delete | Manage    // 15 — составное значение
}

var rights = Permissions.Read | Permissions.Write;
Console.WriteLine(rights);                              // Вывод: Read, Write — работа [Flags]

// Проверка
bool canWrite = (rights & Permissions.Write) != 0;      // быстрый способ
bool canWrite2 = rights.HasFlag(Permissions.Write);     // читаемый способ

// Изменение
rights |= Permissions.Delete;                            // добавить
rights &= ~Permissions.Write;                            // снять
rights ^= Permissions.Read;                              // переключить

// Проверка «есть все указанные»
bool hasBoth = (rights & (Permissions.Read | Permissions.Delete))
               == (Permissions.Read | Permissions.Delete);
```

Правила флагов: значения — степени двойки (`1 << n`), обязательный `None = 0`, имя перечисления во множественном числе, комбинированные значения допустимы. Атрибут `[Flags]` не меняет поведение операторов (битовые операции работают и без него) — он влияет на `ToString()` и на `Enum.IsDefined`/`Parse`.

`HasFlag` до .NET Core упаковывал оба операнда и был заметно медленнее битовой проверки; сейчас JIT его разворачивает в ту же операцию `&`, поэтому в прикладном коде читаемость важнее. В горячем цикле битовый тест всё же предпочтительнее.

> [!warning] `Enum.IsDefined` не работает для комбинаций флагов
> `Enum.IsDefined(Permissions.Read | Permissions.Write)` вернёт `false`, потому что значения 3 в объявлении нет. Для флагов проверяют иначе: `(value & ~Permissions.All) == 0` — «нет посторонних битов».

## Enum и внешний мир

### JSON

```csharp
using System.Text.Json;
using System.Text.Json.Serialization;

// По умолчанию System.Text.Json пишет enum ЧИСЛОМ
Console.WriteLine(JsonSerializer.Serialize(OrderStatus.Paid));     // Вывод: 1

// Строкой — через конвертер (на типе или глобально в options)
[JsonConverter(typeof(JsonStringEnumConverter<OrderStatus>))]
public enum OrderStatusApi { New, Paid }

var options = new JsonSerializerOptions { Converters = { new JsonStringEnumConverter() } };
Console.WriteLine(JsonSerializer.Serialize(OrderStatus.Paid, options));   // Вывод: "Paid"
```

Числа в API — плохой выбор: клиент видит `3` вместо `Shipped`, и любое изменение нумерации ломает контракт молча. Строки читаемы и устойчивы к переупорядочиванию, но тогда нельзя переименовывать члены. Выбор фиксируется один раз на весь сервис.

### База данных

EF Core по умолчанию хранит enum как число. Хранение строкой (`HasConversion<string>()`) делает данные читаемыми в SQL и устойчивыми к перенумерации, но занимает больше места и требует индексов по строке.

```csharp
modelBuilder.Entity<Order>()
    .Property(o => o.Status)
    .HasConversion<string>()
    .HasMaxLength(32);
```

> [!danger] Никогда не меняй числовые значения, которые уже в хранилище
> Если в базе лежит `Status = 2` как `Shipped`, а кто-то вставил новый член в середину перечисления, все существующие записи меняют смысл. Правило: новые члены добавляются только в конец с явным числом, старые не удаляются и не перенумеровываются, а неиспользуемые помечаются `[Obsolete]`. Явная нумерация всех членов (`New = 1, Paid = 2, ...`) делает это правило видимым в коде.

### Отображение для человека

```csharp
public enum DeliveryType
{
    [System.ComponentModel.Description("Самовывоз")] Pickup,
    [System.ComponentModel.Description("Курьером")] Courier
}
```

Читать такие атрибуты приходится рефлексией, и это медленно, если делать на каждый вызов. Для UI лучше отдельный словарь или ресурсы локализации, а не атрибуты плюс рефлексия в горячем пути.

## Когда enum — неправильный выбор

Enum не может нести поведение и данные. Если к значению начинает прилипать логика («у этого статуса такой процент комиссии, а этот разрешает возврат»), появляются `switch` по всему коду, и каждое новое значение требует правок в десяти местах.

Варианты замены:

```csharp
// 1. Enum + расширения — если логики немного и она принадлежит потребителю
public static class OrderStatusExtensions
{
    public static bool CanRefund(this OrderStatus s) => s is OrderStatus.Paid or OrderStatus.Delivered;
}

// 2. «Умное перечисление» — если логика и данные принадлежат значению
public sealed record DeliveryOption(string Code, string Title, decimal Price)
{
    public static readonly DeliveryOption Pickup  = new("pickup", "Самовывоз", 0);
    public static readonly DeliveryOption Courier = new("courier", "Курьером", 25_000);

    public static IReadOnlyList<DeliveryOption> All => [Pickup, Courier];
    public static DeliveryOption FromCode(string code) =>
        All.FirstOrDefault(o => o.Code == code) ?? throw new ArgumentException($"Нет опции {code}");
}

// 3. Иерархия типов — если поведение действительно разное (и тогда работает полиморфизм)
```

Признаки, что enum пора заменить: `switch` по нему больше чем в двух-трёх местах; рядом лежит таблица соответствий значение → данные; значения приходят из конфигурации или из базы и могут добавляться без релиза.

> [!warning] Подводные камни
> - **Значение 0 без смысла.** `default(MyEnum)` всегда равен 0; если под нулём числится `Deleted` или `Error`, объекты «по умолчанию» получают неверное состояние.
> - **Перенумерация сохранённых значений.** Вставка члена в середину меняет смысл данных в БД и в старых сообщениях брокера. Только явная нумерация и только в конец.
> - **`Enum.TryParse` принимает числа.** `"999"` разберётся успешно. Нужна дополнительная проверка `Enum.IsDefined`.
> - **`Enum.IsDefined` для флагов.** Для комбинаций возвращает `false`; проверять надо маской.
> - **`ToString()` в горячем коде.** Работает через метаданные и заметно дороже целочисленных операций; для логов это нормально, для миллиона итераций — нет.
> - **`_ => ...` в `switch` по enum.** Отключает предупреждение о неполноте разбора, и добавление нового члена проходит незамеченным. Лучше перечислить все значения и бросать исключение в ветви по умолчанию ([[Pattern matching]]).
> - **Enum в публичном API как число.** Клиенты начинают зависеть от конкретных чисел; в API безопаснее строки.

> [!example] Как делают в бою
> Устойчивый набор правил: все члены enum нумеруются явно; под 0 — `None`/`Unknown`; в API enum сериализуется строкой (`JsonStringEnumConverter` глобально); в БД — числом при жёстких требованиях к размеру и строкой, когда важнее читаемость данных и устойчивость к изменениям; в `switch`-выражениях перечисляются все значения без «ловящего» `_`.
> На границе enum валидируется: значение из запроса проверяется биндингом и `Enum.IsDefined`, значение из БД — при материализации или на входе в домен. Внутри домена enum считается валидным.
> Когда к статусу начинает прилипать логика переходов («из New можно в Paid и Cancelled, из Paid только в Shipped»), заводят явную машину состояний с таблицей допустимых переходов — enum остаётся представлением состояния, а правила живут отдельно и покрываются тестами.

## Вопросы с собеседований

> [!question]- Почему `(OrderStatus)999` компилируется и что с этим делать?
> Потому что enum в CLR — это значимый тип поверх целого (по умолчанию `int`), а имена существуют только в метаданных для компилятора и для `ToString`. Приведение из числа к enum не проверяется ни компилятором, ни рантаймом — это обычное преобразование чисел, и результатом может быть любое значение базового типа. Отсюда следует, что enum не является гарантией корректности: «невозможные» значения приходят из приведения, из десериализации и из базы данных, где их записал старый код. Практические меры: проверять внешние значения через `Enum.IsDefined` (для флагов — маской допустимых битов), в `switch`-выражениях всегда иметь ветвь по умолчанию, бросающую исключение с самим значением, и никогда не перенумеровывать члены, значения которых уже сохранены.

> [!question]- Как устроены `[Flags]`-перечисления и зачем нужен атрибут?
> Значения объявляются степенями двойки, чтобы каждое занимало свой бит, и комбинируются побитовым ИЛИ; проверка принадлежности делается побитовым И, снятие — И с инверсией маски. Сам атрибут `[Flags]` не влияет ни на операторы (битовые операции работают с любым enum), ни на компиляцию: он меняет поведение `ToString()`, который начинает раскладывать составное значение на имена через запятую, и учитывается `Enum.Parse`. Обязательные элементы правильного флагового перечисления: `None = 0`, значения-степени двойки, имя во множественном числе; допустимы составные константы вроде `All = Read | Write`. Важная тонкость: `Enum.IsDefined` для комбинации вернёт `false`, потому что такого объявленного значения нет — валидность флагов проверяют выражением `(value & ~All) == 0`.

> [!question]- Enum или отдельный тип: как выбрать?
> Enum подходит, когда это закрытый набор простых состояний без собственных данных и поведения: статус, уровень логирования, вид сортировки. Как только к значению привязываются дополнительные атрибуты (цена, название для UI, правило доступа) или поведение (можно ли из этого состояния перейти в то), enum начинает разъезжаться по коду в виде `switch` и словарей соответствий, и каждое новое значение требует правок в нескольких местах. Тогда лучше «умное перечисление» — sealed-тип со статическими экземплярами, где данные и поведение лежат рядом со значением, — либо полноценная иерархия типов, если поведение действительно различается. Дополнительный признак в пользу отдельного типа: набор значений пополняется без релиза, то есть приходит из конфигурации или из справочника в базе — enum для такого не годится по определению, потому что он фиксируется при компиляции.

## Задачи

### Задача 1. Спроектировать перечисление статусов

Опиши enum для статусов платежа, который будет храниться в PostgreSQL и отдаваться в публичном API. Учти будущие изменения.

> [!success]- Решение
> ```csharp
> public enum PaymentStatus
> {
>     Unknown = 0,        // защита от default и от неизвестных значений из БД
>     Created = 1,
>     Authorized = 2,
>     Captured = 3,
>     Failed = 4,
>     Refunded = 5
> }
> ```
> Решения и почему: явная нумерация всех членов — чтобы вставка нового значения не могла случайно сдвинуть существующие; `Unknown = 0` — потому что `default(PaymentStatus)` неизбежен (несохранённая сущность, десериализация без поля, поле структуры), и лучше получить явно «неизвестно», чем ошибочно «создан»; новые члены добавляются только в конец с новым числом, устаревшие не удаляются, а помечаются `[Obsolete]`, потому что в базе остаются старые записи.
> В API сериализуется строкой (`JsonStringEnumConverter` в настройках сериализатора), чтобы клиент видел `"Captured"`, а не `3`, и не зависел от нумерации. В БД — на выбор: число при больших объёмах, строка через `HasConversion<string>()` при приоритете читаемости данных; главное — решение принимается один раз для всего проекта и фиксируется в правилах.

### Задача 2. Флаги прав

Реализуй перечисление прав (чтение, запись, удаление, администрирование) и методы: проверить право, добавить, снять, проверить корректность значения, полученного из БД.

> [!success]- Решение
> ```csharp
> [Flags]
> public enum Permissions
> {
>     None = 0,
>     Read = 1 << 0,
>     Write = 1 << 1,
>     Delete = 1 << 2,
>     Admin = 1 << 3,
>     All = Read | Write | Delete | Admin
> }
>
> public static class PermissionsExtensions
> {
>     public static bool Has(this Permissions value, Permissions flag) => (value & flag) == flag;
>     public static Permissions Add(this Permissions value, Permissions flag) => value | flag;
>     public static Permissions Remove(this Permissions value, Permissions flag) => value & ~flag;
>     public static bool IsValid(this Permissions value) => (value & ~Permissions.All) == 0;
> }
>
> var rights = Permissions.Read.Add(Permissions.Write);
> Console.WriteLine(rights.Has(Permissions.Write));                 // True
> Console.WriteLine(((Permissions)64).IsValid());                    // False — посторонний бит
> ```
> Ключевые детали: `Has` сравнивает `(value & flag) == flag`, а не `!= 0` — это корректно работает и для составных флагов (`rights.Has(Read | Write)` означает «есть оба»); `Remove` использует инверсию маски; `IsValid` проверяет отсутствие битов вне `All`, потому что `Enum.IsDefined` для комбинаций не годится. Расширяющие методы дают читаемый вызов без потери производительности — компилятор их инлайнит в те же битовые операции.

## Итог

- `enum` — именованные константы поверх целого; в рантайме это просто число, и валидность не гарантируется.
- Значение 0 обязано быть осмысленным (`None`/`Unknown`): `default` неизбежен.
- Нумеруй члены явно и добавляй только в конец: сохранённые значения нельзя перенумеровывать.
- `Enum.TryParse` разбирает и числа, поэтому внешний ввод дополнительно проверяется `Enum.IsDefined`.
- `[Flags]`: степени двойки, `None = 0`, проверка через `&`, снятие через `& ~`, валидация маской `~All`.
- В API enum лучше отдавать строкой; в БД — число или строка, но решение единое на проект.
- Как только к значению прилипают данные или поведение, enum пора заменить умным перечислением или иерархией типов.
