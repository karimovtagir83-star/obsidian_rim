# Записи (record) и структуры

> [!abstract] Коротко
> `class` — ссылочный тип, сравнение по ссылке. `struct` — значимый тип, сравнение по значению и копирование при передаче. `record` — не третья категория, а модификатор: компилятор генерирует `Equals`, `GetHashCode`, `ToString`, `Deconstruct` и `with` для типа-значения. Рядом с этой тройкой — два соседних инструмента с той же идеей «данные без поведения»: кортеж (временная структура на несколько значений без объявления типа) и `enum` (закрытый набор именованных констант). Разница между ними — то, что определяет выбор структуры перед написанием кода и то, что чаще всего ломается в проде и на ревью.

## Зачем это знать

Неверный выбор здесь не ловится компилятором и стоит дорого по-разному: `record` вместо класса для сущности EF Core ломает материализацию и идентичность; изменяемый `record struct` создаёт баг «изменили копию»; кортеж, просочившийся в публичный API, делает контракт нечитаемым и хрупким к рефлексии; enum, перенумерованный после того как значения легли в MySQL-колонку, молча меняет смысл старых записей. Все четыре ошибки — из тех, что агент вставляет уверенно и без предупреждений: код компилируется и даже работает на тестовых данных.

## Модель

### Значимые и ссылочные типы

```csharp
struct PointS { public int X; }
class PointC { public int X; }

var s1 = new PointS { X = 1 };
var s2 = s1;                    // копия значения
s2.X = 99;
Console.WriteLine(s1.X);        // Вывод: 1

var c1 = new PointC { X = 1 };
var c2 = c1;                    // копия ссылки
c2.X = 99;
Console.WriteLine(c1.X);        // Вывод: 99
```

| | `class` | `struct` |
|---|---|---|
| Категория | ссылочный | значимый |
| Присваивание | копия ссылки | копия всех полей |
| Равенство по умолчанию | по ссылке | по значению (полям) |
| Наследование | да | нет (только интерфейсы) |
| `null` | допустим | только `Nullable<T>` |

Точная формулировка (не «структуры на стеке»): **структура живёт там, где объявлена** — в стеке метода, в поле класса, в элементе массива. Подробно — [[Value types vs Reference types]].

### `record`: что генерирует компилятор

```csharp
public record Person(string FirstName, string LastName);

var p1 = new Person("Иван", "Петров");
var p2 = p1 with { LastName = "Иванов" };   // копия с изменением
Console.WriteLine(p1 == p2);                 // False — сравнение по значению
Console.WriteLine(p2);                       // Person { FirstName = Иван, LastName = Иванов }
var (first, last) = p1;                       // деконструкция генерируется сама
```

Из одной строки: `init`-only свойства, первичный конструктор, `Equals`/`GetHashCode`/`==` по всем полям, `ToString`, `Deconstruct`, конструктор копирования и `EqualityContract` (из-за него `record`-наследник не равен базовому `record` даже при одинаковых полях).

`with` копирует **поверхностно** — вложенный `List<T>` остаётся общим объектом для оригинала и копии. Иммутабельность записи не наследуется её полями.

### `record struct`

| Объявление | Категория | Позиционные свойства |
|---|---|---|
| `record class X(...)` (он же `record`) | ссылочный | `get; init;` |
| `record struct X(...)` | значимый | `get; set;` — **изменяемые** |
| `readonly record struct X(...)` | значимый | `get; init;` |

Практический вывод: для value object почти всегда нужен `readonly record struct` — иначе получаешь именно то, чего надо избегать. У `record struct` компилятор генерирует `Equals`/`GetHashCode` по полям напрямую; у обычной `struct` без переопределения работает `ValueType.Equals` через рефлексию — в разы медленнее и годится в ключ словаря только после ручного переопределения.

```csharp
struct Counter { public int Value; public void Increment() => Value++; }

var list = new List<Counter> { new() };
var copy = list[0];
copy.Increment();
Console.WriteLine(list[0].Value);   // Вывод: 0 — индексатор List<T> вернул копию

var array = new Counter[1];
array[0].Increment();
Console.WriteLine(array[0].Value);  // Вывод: 1 — индексатор массива даёт ссылку
```

Одинаковый на вид код ведёт себя по-разному в зависимости от того, возвращает индексатор ссылку или копию. Отсюда правило без исключений: **структура — `readonly`**.

### Кортежи: временная структура вместо record

Кортеж — это `System.ValueTuple`, структура с публичными полями `Item1..Item8`; имена элементов (`(int Code, string Text)`) существуют только на этапе компиляции, в рантайме есть только `ValueTuple<int, string>`.

```csharp
public (bool Found, long Bytes) GetSize(string path)
{
    var fi = new FileInfo(path);
    return fi.Exists ? (true, fi.Length) : (false, 0L);
}

var (found, bytes) = GetSize("a.txt");
var big = (Code: 200, Text: "OK");
Console.WriteLine(big.GetType().Name);   // Вывод: ValueTuple`2 — имён здесь нет
```

Кортеж не аллоцирует, но изменяем (`t.Item1 = 5` компилируется) и копируется целиком при каждой передаче. `==` (C# 7.3) разворачивается поэлементно и может расходиться с `.Equals()` (через `EqualityComparer<T>.Default`) на `NaN`. Уместен внутри метода, между приватными методами, как составной ключ словаря; неуместен в публичном контракте — там нет валидации, поведения, а `System.Text.Json` сериализует пустой объект `{}`, потому что элементы — поля, а не свойства.

### Enum: закрытый набор констант поверх числа

`enum` — значимый тип поверх `int` (по умолчанию), и он **не гарантирует валидность**: приведение из числа не проверяется ни компилятором, ни рантаймом.

```csharp
public enum OrderStatus { New, Paid, Shipped = 10, Delivered, Cancelled = 99 }

OrderStatus fromDb = (OrderStatus)999;   // компилируется и работает
Console.WriteLine(fromDb);                // Вывод: 999 — просто число с именем, которого нет

Console.WriteLine(Enum.IsDefined(fromDb));            // False
Enum.TryParse<OrderStatus>("999", out var weird);      // true! TryParse принимает и числа
```

Обязательное правило: **значение 0 должно быть осмысленным** (`None`/`Unknown`), потому что `default(T)` неизбежен — несохранённая сущность, поле структуры, десериализация без поля. `[Flags]`-перечисления — отдельный режим: значения — степени двойки, комбинируются `|`, проверяются `&`, валидность — маской `(value & ~All) == 0`, а не `IsDefined`.

**Представление в БД.** EF Core по умолчанию хранит enum числом. Число компактнее и быстрее по индексу, но **перенумерация уже сохранённых значений меняет смысл существующих строк** — вставка нового члена в середину сдвигает все следующие. Строка (`HasConversion<string>()`) читаема в SQL и устойчива к переупорядочиванию ценой размера и индекса по строке. Правило одно на проект: члены нумеруются явно, новые добавляются только в конец, старые не удаляются — только `[Obsolete]`.

Когда к значению начинает прилипать логика («у этого статуса такой процент комиссии»), enum пора заменить: расширяющими методами (если логики немного), «умным перечислением» на `record` (данные и поведение при значении) или иерархией типов (если поведение действительно разное).

```csharp
public sealed record DeliveryOption(string Code, string Title, decimal Price)
{
    public static readonly DeliveryOption Pickup = new("pickup", "Самовывоз", 0);
    public static readonly DeliveryOption Courier = new("courier", "Курьером", 25_000);
    public static IReadOnlyList<DeliveryOption> All => [Pickup, Courier];
}
```

## Решения

| Задача | Выбор | Почему |
|---|---|---|
| DTO запроса/ответа API, событие домена | `record` (`sealed record`) | равенство и `with` готовы, контракт документируем |
| Value object (деньги, идентификатор, диапазон) | `readonly record struct` | одно значение, малый размер, нет аллокации |
| Сущность домена с идентичностью и поведением | `class` | равенство по ссылке/ключу, изменяемое состояние |
| Результат операции внутри метода/приватного API | кортеж | нет смысла заводить тип ради одного вызова |
| Результат, пересекающий границу сборки или API | `record` | имена не теряются, можно добавить инвариант |
| Составной ключ словаря | кортеж или `readonly record struct` | равенство и хеш уже реализованы |
| Закрытый набор простых состояний без данных | `enum` | компактно, полнота разбора в `switch` |
| Состояние с данными или переходами по правилам | `record`-иерархия / «умное перечисление» | enum не несёт поведение |

> [!example] В ServiceShop
> Идентификаторы и деньги — `readonly record struct OrderId(long Value)`, `readonly record struct Money(decimal Amount, string Currency)`: типобезопасность против «передал customerId туда, где ждали orderId», которую компилятор при `long` не поймает.
> Статус заказа — `enum OrderStatus { New = 1, Paid = 2, Shipped = 3, Delivered = 4, Cancelled = 5 }`, хранится в MySQL-колонке `status` числом. Типичный сценарий инцидента: правка на ревью добавляет `Refunded` между `Paid` и `Shipped` без явного числа — все значения после сдвигаются, и старые заказы в проде мгновенно «переезжают» в другой статус без единой ошибки компиляции или миграции. Правильная правка — новый член в конец с явным числом (`Refunded = 6`), либо переход на `HasConversion<string>()`, если колонка это позволяет.
> Промежуточный шаг в CQRS-обработчике — кортеж `(bool Ok, string? Error)` из приватного `Validate(...)`; как только такой метод становится публичным контрактом хендлера, его меняют на `record`-результат.

> [!warning] Где ошибаются
> - **`record` для сущности EF Core.** Равенство по значению конфликтует с идентичностью (две разные записи с одинаковыми полями — «один и тот же» объект по `Equals`), `init` мешает материализации. Сущности — классы, `record` — для DTO и value objects.
> - **`record struct` без `readonly`.** Позиционные свойства получаются `get; set;` — то есть по умолчанию получаешь изменяемую структуру, а это отдельная категория багов «поменяли копию, а не оригинал».
> - **Перенумерация enum, уже сохранённого в БД или ушедшего в Kafka-сообщение.** Вставка члена в середину без явного числа меняет смысл старых данных молча — ни компилятор, ни миграция не предупредят.
> - **Кортеж в публичном контракте.** Имена теряются при переходе через `object`/рефлексию, `System.Text.Json` сериализует `{}` (элементы — поля, не свойства), нельзя добавить инвариант или метод.
> - **`_ => ...` в `switch` по enum.** Отключает предупреждение компилятора о неполноте разбора — новый член пройдёт незамеченным. Лучше явная ветка по умолчанию с исключением.
> - **Агент часто:** генерирует enum без явной нумерации членов («пусть компилятор сам пронумерует») — при следующей правке кто-то вставит член в середину, и это не будет выглядеть как проблема ни в диффе, ни в тестах.
> - **Агент часто:** сериализует enum в API числом по умолчанию `System.Text.Json`, не добавляя `JsonStringEnumConverter` — контракт ломается молча при следующей вставке члена.
> - **Агент часто:** возвращает кортеж из публичного метода хендлера или контроллера вместо `record`, потому что кортеж короче писать — а через полгода к результату добавляется третье поле, и это уже breaking change для всех потребителей.

## Проверка на ревью

- Enum, идущий в БД или в сообщение брокера, имеет явную нумерацию всех членов, новые добавлены в конец.
- В `switch`-выражении по enum нет `_ => ...`, скрывающего неполноту разбора, либо ветка по умолчанию явно бросает исключение.
- `record struct` в диффе объявлен как `readonly record struct`, если не задумана изменяемость.
- Кортеж не пересекает границу контроллера/хендлера наружу — на этой границе `record`.
- `record`, используемый как сущность EF Core, — намеренное решение, а не копипаста из соседнего DTO.
- Enum, уходящий в JSON публичного API, сериализуется строкой, а не голым числом.

## Проверь себя

> [!question]- Чем `record` отличается от `class` по сути, а не по синтаксису?
> `record` — не отдельная категория типов, а модификатор объявления: `record` (`record class`) остаётся ссылочным типом. Разница в том, что компилятор генерирует члены, характерные для типа-значения: `Equals`/`GetHashCode` по всем полям, `==`/`!=`, `ToString`, `Deconstruct`, конструктор копирования и `with`, а также `EqualityContract`, из-за которого экземпляры разных типов в иерархии не равны даже при одинаковых полях. Всё это можно написать руками в обычном классе — `record` избавляет от шаблонного кода и типичных ошибок в `GetHashCode`.

> [!question]- Почему `(OrderStatus)999` компилируется и чем это опасно для проекта на MySQL?
> Enum в CLR — это целое число с именами только в метаданных компилятора; приведение из числа к enum не проверяется рантаймом. Отсюда «невозможные» значения приходят из приведения, десериализации и из БД, где их мог записать старый код или миграция. Опасность для хранения в MySQL: если колонка хранит числовое значение enum, а кто-то вставил новый член в середину объявления без явного числа, все существующие строки задним числом получают другой статус — без единой ошибки на этапе компиляции или деплоя.

> [!question]- Когда кортеж стоит заменить на `record`?
> Как только результат пересекает границу метода наружу — становится частью публичного API, контроллера, обработчика сообщений. Причины: имена элементов кортежа существуют только в метаданных сигнатуры и теряются при рефлексии/боксинге; нет места для инварианта («`From <= To`»); добавление восьмого поля меняет тип и ломает всех потребителей; `System.Text.Json` по умолчанию не видит поля `ValueTuple`. Внутри метода или между приватными методами кортеж остаётся уместным и не создаёт этих проблем.

> [!question]- Почему `readonly record struct`, а не просто `record struct`?
> Без `readonly` позиционные свойства `record struct` получаются `get; set;` — то есть значимый тип получается изменяемым по умолчанию, хотя весь смысл value object в неизменности. Изменяемая структура даёт классический баг «список вернул копию по индексатору, изменили копию» и заставляет компилятор делать защитные копии при обращении через `in`-параметры. `readonly record struct` фиксирует `init`-семантику и убирает оба источника ошибок.

> [!question]- Как правильно валидировать enum, пришедший из внешнего источника?
> `Enum.TryParse` разбирает не только имена, но и числовые строки, и не проверяет принадлежность объявленным значениям — поэтому одного `TryParse` недостаточно. Правильная пара: `TryParse` + `Enum.IsDefined` для обычного enum. Для `[Flags]`-перечислений `IsDefined` не годится в принципе (комбинация значений не объявлена как отдельный член) — валидность проверяют маской `(value & ~All) == 0`.

## Разбор

**Дан фрагмент — найди проблему.**

```csharp
public enum PaymentStatus { Created, Authorized, Refunded, Captured, Failed }
// PaymentStatus сохраняется в MySQL как int
```

> [!success]- Решение
> Членам не заданы явные числа: `Created = 0, Authorized = 1, Refunded = 2, Captured = 3, Failed = 4`. `Refunded` стоит перед `Captured`, хотя по бизнес-смыслу возврат происходит после захвата платежа — очевидный кандидат на то, что кто-то вставит между ними ещё один статус в будущем PR, случайно сдвинув `Captured` и `Failed` на единицу для всех уже сохранённых заказов. Исправление: явная нумерация всех членов плюс `Unknown = 0` под default, новые статусы — только в конец с новым числом:
> ```csharp
> public enum PaymentStatus
> {
>     Unknown = 0, Created = 1, Authorized = 2,
>     Captured = 3, Refunded = 4, Failed = 5
> }
> ```

**Дан PR агента — что вернёшь на доработку.**

Агент реализовал метод хендлера так:

```csharp
public async Task<(bool Success, string? Error, long? OrderId)> Handle(CreateOrderCommand cmd, CancellationToken ct)
{
    // ...
    return (true, null, order.Id);
}
```

> [!success]- Решение
> Вернуть на доработку с формулировкой: результат хендлера — это публичный контракт между слоями (MediatR-запрос), а не внутренний helper, поэтому кортеж здесь неуместен — при следующем изменении (например, добавлении кода ошибки) придётся менять сигнатуру и все точки вызова, а IntelliSense у вызывающей стороны покажет `Item1/Item2/Item3`, если результат хоть раз пройдёт через интерфейс или сериализацию. Замена — `record CreateOrderResult(bool Success, string? Error, long? OrderId)` или, если в проекте уже есть слой Result pattern, использование его типа.

## Итог

- `record` — модификатор, добавляющий семантику значения (`Equals`, `with`, `Deconstruct`) к классу или структуре; не отдельная категория типов.
- `readonly record struct` — стандартный выбор для value objects; без `readonly` получаешь изменяемую структуру и связанные с этим баги.
- Кортеж — временная структура для внутреннего использования; на границе метода/API его место занимает `record`.
- `enum` — число с именами, валидность не гарантирована рантаймом: внешние значения проверяются `IsDefined` (для флагов — маской).
- Перенумерация enum, уже сохранённого в БД или ушедшего в брокер, — необратимая ошибка данных, а не стилистическая мелочь.
- Как только к enum или к кортежу прилипают данные и поведение, это сигнал переходить на `record`-иерархию.
