# Записи (record) и структуры

> [!abstract] Коротко
> `class` — ссылочный тип со сравнением по ссылке, `struct` — значимый тип со сравнением по значению. `record` — не третья категория, а модификатор: он просит компилятор сгенерировать всё, что нужно типу-значению по смыслу — `Equals`, `GetHashCode`, `ToString`, `Deconstruct` и поддержку `with`. Отсюда простая карта выбора: `record` для данных без поведения (DTO, события, результаты), `record struct` для маленьких иммутабельных величин (деньги, координаты, идентификаторы), `class` для объектов с поведением и жизненным циклом, `struct` вручную — почти никогда.

## Зачем это нужно

До C# 9 честный тип-значение писался руками: конструктор, свойства только для чтения, `Equals`, `GetHashCode`, `IEquatable<T>`, `ToString`, оператор `==`, метод копирования с изменением. Сто строк шаблонного кода на каждый тип, и в каждой второй реализации `GetHashCode` была ошибка.

```csharp
// Всё это теперь одна строка
public record Money(decimal Amount, string Currency);

var a = new Money(100, "UZS");
var b = new Money(100, "UZS");
Console.WriteLine(a == b);              // True — сравнение по значению
Console.WriteLine(a);                    // Money { Amount = 100, Currency = UZS }
var c = a with { Amount = 200 };         // копия с изменением
var (amount, currency) = a;              // деконструкция
```

Второй мотив — производительность. Понимание разницы между `struct` и `class` определяет, сколько мусора создаёт горячий код: массив из миллиона структур — это один объект в куче, массив из миллиона классов — миллион и один.

## Значимые и ссылочные типы: короткое повторение

```csharp
struct PointS { public int X; public int Y; }
class PointC { public int X; public int Y; }

var s1 = new PointS { X = 1 };
var s2 = s1;                  // копируется значение
s2.X = 99;
Console.WriteLine(s1.X);       // Вывод: 1

var c1 = new PointC { X = 1 };
var c2 = c1;                  // копируется ссылка
c2.X = 99;
Console.WriteLine(c1.X);       // Вывод: 99
```

| | `class` | `struct` |
|---|---|---|
| Категория | ссылочный | значимый |
| Где значение | в куче, переменная хранит ссылку | там, где объявлено (стек, поле, элемент массива) |
| Присваивание | копия ссылки | копия всех полей |
| Равенство по умолчанию | по ссылке | по значению (полям) |
| `null` | допустим | только через `Nullable<T>` |
| Наследование | да | нет (только реализация интерфейсов) |
| Значение по умолчанию | `null` | все поля обнулены, конструктор не вызывается |
| Стоимость передачи | размер ссылки (8 байт) | размер всех полей |

Утверждение «структуры лежат на стеке» — неточность: структура-поле класса лежит в куче внутри объекта, элемент `Point[]` — в куче внутри массива. Точная формулировка: **структура живёт там, где объявлена**. Подробно — [[Value types vs Reference types]] и [[Стек и куча: что где лежит]].

## record: что генерирует компилятор

```csharp
public record Person(string FirstName, string LastName);
```

Из одной строки компилятор создаёт:

- **свойства** `FirstName`, `LastName` — публичные, `init`-only (задать можно только при создании);
- **конструктор** `Person(string, string)` — первичный (primary constructor);
- **`Equals`/`GetHashCode`** по всем полям плюс реализацию `IEquatable<Person>`;
- **операторы `==` и `!=`**, работающие по значению;
- **`ToString()`** — `Person { FirstName = Иван, LastName = Петров }`;
- **`Deconstruct`** для позиционной деконструкции и позиционных паттернов;
- **защищённый конструктор копирования** и метод `<Clone>$` — на них работает `with`;
- **`EqualityContract`** — свойство с типом, из-за которого `record` наследника не равен `record` базового типа даже при одинаковых полях.

```csharp
// То же самое, но с телом — можно добавлять члены и валидацию
public record Person(string FirstName, string LastName)
{
    public string FullName => $"{FirstName} {LastName}";

    public int Age { get; init; }                        // дополнительное необязательное свойство

    // Валидация в первичном конструкторе
    public string FirstName { get; init; } = FirstName is { Length: > 0 }
        ? FirstName
        : throw new ArgumentException("Имя обязательно", nameof(FirstName));
}
```

### `with`

```csharp
var p1 = new Person("Иван", "Петров") { Age = 30 };
var p2 = p1 with { LastName = "Иванов" };      // новая запись, остальные поля скопированы
Console.WriteLine(p2);                          // Person { FirstName = Иван, LastName = Иванов, Age = 30 }
Console.WriteLine(ReferenceEquals(p1, p2));      // False — это разные объекты
```

`with` делает **поверхностную** копию: вложенные ссылочные поля общие для оригинала и копии. Для иммутабельных вложенных типов это нормально, для изменяемых (например, `List<T>`) — источник неожиданных связей между «независимыми» объектами.

### Равенство и наследование

```csharp
public record Animal(string Name);
public record Dog(string Name, string Breed) : Animal(Name);

Animal a = new Dog("Рекс", "овчарка");
Animal b = new Animal("Рекс");
Console.WriteLine(a.Equals(b));         // False — разные EqualityContract (типы не совпадают)
```

Это отличает `record` от рукописного `Equals`, где такую проверку часто забывают, получая несимметричное равенство. Наследование записей поддерживается, но применяется редко: иерархии данных обычно лучше выражать как набор независимых типов или через интерфейс.

## record struct

```csharp
public readonly record struct Money(decimal Amount, string Currency);

var m1 = new Money(100, "UZS");
var m2 = m1 with { Amount = 200 };
Console.WriteLine(m1 == m2);            // False, сравнение по значению
Console.WriteLine(m1.GetHashCode() == new Money(100, "UZS").GetHashCode());  // True
```

Различия по формам объявления:

| Объявление | Категория | Свойства из позиционных параметров |
|---|---|---|
| `record class X(...)` (или просто `record`) | ссылочный | `get; init;` |
| `record struct X(...)` | значимый | `get; set;` — **изменяемые!** |
| `readonly record struct X(...)` | значимый | `get; init;` |

Практический вывод: для значимого типа почти всегда нужен `readonly record struct` — иначе получится изменяемая структура, а это отдельная категория проблем (см. ниже).

Важное отличие от обычной `struct`: у `record struct` компилятор генерирует `Equals`/`GetHashCode`, сравнивающие поля напрямую. У обычной структуры без переопределения работает `ValueType.Equals`, который в общем случае использует рефлексию и в разы медленнее (быстрый путь применяется только к структурам без ссылочных полей и без «дырок» выравнивания). Поэтому обычная `struct`, используемая как ключ словаря или в сравнениях, обязана переопределять `Equals`/`GetHashCode` — или быть `record struct`.

## Когда `struct`, а когда `class`

Официальные рекомендации .NET сводятся к четырём условиям, при которых уместна структура:

1. логически представляет **одно значение** (точка, деньги, диапазон дат, идентификатор);
2. размер до **16 байт** (примерно два-три поля);
3. **иммутабельна**;
4. не будет часто упаковываться.

Каждое нарушение имеет цену: большая структура дорого копируется при каждой передаче; изменяемая ведёт себя неинтуитивно; часто упаковываемая создаёт мусора больше, чем сэкономила.

```csharp
// Хорошие кандидаты в структуры (все — из BCL)
// int, DateTime, TimeSpan, Guid, DateOnly, ValueTuple, Span<T>, Nullable<T>

// Хороший прикладной пример: value object
public readonly record struct OrderId(long Value)
{
    public override string ToString() => $"ORD-{Value}";
}

// Плохой кандидат: сущность с поведением и жизненным циклом
public class Order            // класс: изменяемое состояние, много полей, идентичность
{
    public OrderId Id { get; }
    public List<OrderItem> Items { get; } = [];
    public void AddItem(OrderItem item) { }
}
```

Отдельный сильный сценарий для структур — **массивы данных в горячем коде**:

```csharp
readonly record struct Candle(double Open, double High, double Low, double Close);

var candles = new Candle[1_000_000];    // ОДИН объект в куче, 32 МБ подряд
// Массив классов был бы 1 000 001 объект и обход по разбросанным адресам:
// в 5–10 раз медленнее из-за промахов кеша
```

### Почему изменяемые структуры опасны

```csharp
struct Counter { public int Value; public void Increment() => Value++; }

var list = new List<Counter> { new() };
// list[0].Increment();               // Ошибка компиляции: индексатор возвращает КОПИЮ
var copy = list[0];
copy.Increment();
Console.WriteLine(list[0].Value);      // Вывод: 0 — изменили копию

var array = new Counter[1];
array[0].Increment();                  // а здесь работает: индексатор массива даёт ссылку
Console.WriteLine(array[0].Value);      // Вывод: 1
```

Одинаковый по виду код ведёт себя по-разному в зависимости от того, возвращает ли индексатор ссылку или копию. Плюс `readonly` поля и `in`-параметры создают защитные копии при каждом вызове метода не-`readonly` структуры ([[Методы и параметры]]). Отсюда правило без исключений в прикладном коде: **структура — `readonly`**.

## Первичные конструкторы у классов (C# 12)

С C# 12 позиционный синтаксис доступен не только записям:

```csharp
// Первичный конструктор класса: параметры доступны во всём теле
public class OrderService(IOrderRepository repository, ILogger<OrderService> logger)
{
    public async Task<Order?> FindAsync(long id, CancellationToken ct)
    {
        logger.LogInformation("Поиск заказа {OrderId}", id);
        return await repository.GetAsync(id, ct);
    }
}
```

Это заметно сокращает классы с внедрением зависимостей: нет ни полей, ни присваиваний в конструкторе. Отличия от `record`: свойства **не создаются**, `Equals`/`ToString` не генерируются, параметры остаются захваченными переменными (компилятор создаёт скрытые поля только для тех, что реально используются). Ограничение, о котором надо помнить: параметры первичного конструктора класса не `readonly`, их можно случайно переприсвоить внутри — анализаторы это подсвечивают.

## Что выбрать: карта решений

| Задача | Выбор |
|---|---|
| DTO запроса/ответа API | `record` (`sealed record`) |
| Событие домена, сообщение брокера | `record` |
| Результат операции (`Success`/`Error`) | `record` + иерархия или `readonly record struct` |
| Value object (деньги, идентификатор, диапазон) | `readonly record struct`, если мал; иначе `record` |
| Сущность домена с поведением и идентичностью | `class` |
| Сервис, репозиторий, обработчик | `class` (обычно с первичным конструктором) |
| Элемент большого массива в горячем коде | `readonly record struct` |
| Ключ словаря | `readonly record struct` или `record` (равенство уже готово) |
| Буфер/срез памяти | `ref struct` (`Span<T>`), см. [[Span, ReadOnlySpan и Memory]] |

> [!warning] Подводные камни
> - **`record struct` без `readonly`.** Позиционные свойства получаются изменяемыми (`get; set;`) — то есть по умолчанию ты получаешь именно то, чего следует избегать.
> - **`with` копирует поверхностно.** Список внутри копии — тот же самый объект. Иммутабельность записи не делает иммутабельным её содержимое.
> - **`record` не значит «иммутабельный».** `record` с `{ get; set; }` или с изменяемой коллекцией внутри полностью изменяем; `init` — только на позиционных свойствах.
> - **Обычная `struct` как ключ словаря.** Без переопределения `Equals`/`GetHashCode` работает медленный путь `ValueType.Equals` через рефлексию.
> - **Большая структура в параметрах.** Копируется целиком при каждом вызове; для 64-байтной структуры в горячем цикле это заметно. Лечится `in` (только для `readonly struct`) или переходом на класс.
> - **`record` для сущностей EF Core.** Технически работает, но равенство по значению конфликтует с идентичностью сущности (две разные записи с одинаковыми полями — один объект по `Equals`), а `init`-свойства мешают материализации. Сущности — обычные классы; `record` — для DTO и value objects.
> - **`ToString()` записи в логах.** Он печатает все свойства, включая персональные данные и секреты. Для чувствительных типов `ToString` переопределяют явно.

> [!example] Как делают в бою
> Устойчивое распределение в современном .NET-проекте: `record` — для всего, что является данными (команды и запросы CQRS, DTO контроллеров, доменные события, сообщения брокера, конфигурационные модели), `readonly record struct` — для мелких величин с семантикой значения (идентификаторы, деньги, периоды), `class` — для сервисов и доменных сущностей.
> Типизированные идентификаторы — самая частая практическая победа: `readonly record struct OrderId(long Value)` делает невозможной ошибку «передал customerId туда, где ждали orderId», которую компилятор при `long` не поймает никогда. Цена — немного шума при маппинге в БД (конвертер значений в EF Core).
> Деньги оформляют как `readonly record struct Money(decimal Amount, string Currency)` с проверкой валюты в операторах: попытка сложить сумы с долларами превращается из тихой ошибки округления в исключение.
> Чего не делают: не превращают всё в структуры «ради производительности» и не пишут `Equals` руками там, где достаточно `record`.

## Вопросы с собеседований

> [!question]- Чем `record` отличается от `class`?
> `record` — не отдельная категория типов, а модификатор объявления: `record` (то есть `record class`) остаётся ссылочным типом, `record struct` — значимым. Разница в том, что компилятор генерирует набор членов, характерных для типа-значения: `Equals` и `GetHashCode` по всем полям, реализацию `IEquatable<T>`, операторы `==`/`!=` по значению, `ToString` с перечислением свойств, `Deconstruct`, конструктор копирования и поддержку выражения `with`, а также свойство `EqualityContract`, из-за которого экземпляры разных типов в иерархии не равны даже при одинаковых полях. Позиционные параметры превращаются в `init`-only свойства. Всё это можно написать руками в обычном классе — `record` лишь избавляет от шаблонного кода и от типичных ошибок в `GetHashCode`. Практическое разделение: `record` для данных, `class` для объектов с поведением и идентичностью.

> [!question]- Когда стоит использовать `struct`?
> Когда тип логически представляет одно значение, невелик (ориентир — до 16 байт), иммутабелен и не будет часто упаковываться. Выигрыш в двух вещах: отсутствие аллокации в куче (значит, меньше работы для GC) и локальность данных — массив структур лежит непрерывно, и его обход в разы быстрее массива объектов из-за попаданий в кеш. Цена: копирование при каждой передаче и присваивании, невозможность наследования, `default`-значение без вызова конструктора, а также упаковка при приведении к `object` или интерфейсу, которая сводит выигрыш на ноль. Дополнительное требование — `readonly`: изменяемая структура ведёт себя неинтуитивно (изменение копии вместо оригинала) и заставляет компилятор создавать защитные копии при обращении через `in`-параметры и `readonly`-поля. Для большинства прикладных типов правильный ответ — класс или `record`.

> [!question]- Почему обычная структура без переопределения `Equals` работает медленно?
> Потому что унаследованный `ValueType.Equals` не знает состав полей на этапе компиляции. Рантайм применяет быстрый путь — побитовое сравнение памяти — только если структура не содержит ссылочных полей и в её раскладке нет «дырок» от выравнивания; в остальных случаях он обходит поля через рефлексию, что в десятки раз медленнее и вдобавок упаковывает значения. `GetHashCode` у `ValueType` тоже реализован консервативно и может учитывать только первое поле, что даёт плохое распределение в хеш-таблицах. Поэтому структура, попадающая в `Dictionary`, `HashSet` или в сравнения, обязана либо переопределять `Equals`/`GetHashCode` и реализовывать `IEquatable<T>` (чтобы не было упаковки при вызове), либо объявляться как `record struct` — тогда компилятор сгенерирует эти члены с прямым сравнением полей.

> [!question]- Что делает выражение `with` и в чём его ограничение?
> `with` создаёт копию объекта с изменёнными указанными свойствами: компилятор вызывает сгенерированный конструктор копирования, а затем присваивает перечисленные `init`-свойства. Работает для `record`, `record struct`, обычных структур (C# 10) и анонимных типов. Главное ограничение — копия **поверхностная**: значения ссылочных полей копируются как ссылки, поэтому список или словарь внутри останутся общими для оригинала и копии, и изменение через один объект будет видно через другой. Для настоящей независимости вложенные структуры данных тоже должны быть иммутабельными (`ImmutableArray<T>`) или копироваться явно. Второе ограничение практическое: `with` работает только с `init`/`set`-свойствами, поэтому изменить значение, вычисляемое в теле записи, через него нельзя.

## Задачи

### Задача 1. Заменить рукописный код записью

```csharp
public class Money : IEquatable<Money>
{
    public decimal Amount { get; }
    public string Currency { get; }
    public Money(decimal amount, string currency) { Amount = amount; Currency = currency; }
    public bool Equals(Money? other) => other is not null && Amount == other.Amount && Currency == other.Currency;
    public override bool Equals(object? obj) => Equals(obj as Money);
    public override int GetHashCode() => HashCode.Combine(Amount, Currency);
    public override string ToString() => $"{Amount} {Currency}";
    public Money WithAmount(decimal amount) => new(amount, Currency);
}
```

> [!success]- Решение
> ```csharp
> public readonly record struct Money(decimal Amount, string Currency)
> {
>     public override string ToString() => $"{Amount} {Currency}";
>
>     public static Money operator +(Money a, Money b) => a.Currency == b.Currency
>         ? new(a.Amount + b.Amount, a.Currency)
>         : throw new InvalidOperationException($"Нельзя складывать {a.Currency} и {b.Currency}");
> }
>
> var total = new Money(100, "UZS") + new Money(50, "UZS");
> var changed = total with { Amount = 500 };     // вместо WithAmount
> ```
> Что ушло: конструктор, свойства, три метода равенства, `GetHashCode`, метод копирования — всё генерируется. Что осталось: `ToString` переопределён, потому что нужен свой формат вместо `Money { Amount = 100, Currency = UZS }`. Что добавилось по делу: оператор `+` с проверкой валюты — это то, ради чего value object и создаётся. Выбран `readonly record struct`, а не `record`: тип маленький (16 + 8 байт), представляет одно значение и создаётся часто, поэтому отсутствие аллокаций важно. Если бы тип использовался как ключ словаря — равенство и хеш уже готовы.

### Задача 2. Найти проблему

```csharp
public record Order(long Id, List<string> Tags);

var original = new Order(1, ["новый"]);
var copy = original with { Id = 2 };
copy.Tags.Add("важный");
Console.WriteLine(original.Tags.Count);
```

> [!success]- Решение
> Выведет `2`. `with` копирует поля поверхностно: свойство `Tags` в копии ссылается на **тот же самый** список. Запись формально иммутабельна (свойства `init`-only), но её содержимое — нет, и «независимые» объекты оказались связаны.
> ```csharp
> public sealed record Order(long Id, System.Collections.Immutable.ImmutableArray<string> Tags)
> {
>     public Order AddTag(string tag) => this with { Tags = Tags.Add(tag) };
> }
>
> var original = new Order(1, ["новый"]);
> var copy = original.AddTag("важный");       // новый массив, оригинал не тронут
> Console.WriteLine(original.Tags.Length);     // Вывод: 1
> ```
> Общее правило: иммутабельность типа не наследуется его полями. Чтобы `record` действительно был значением, все его поля должны быть либо значимыми типами, либо иммутабельными ссылочными (`string`, другой `record`, `ImmutableArray<T>`). Если хранение изменяемой коллекции неизбежно, её нельзя выставлять наружу — только копию или `IReadOnlyList<T>`.

## Итог

- `class` — ссылка и идентичность, `struct` — значение и копирование. `record` — модификатор, добавляющий семантику значения к любому из них.
- `record` генерирует `Equals`, `GetHashCode`, `==`, `ToString`, `Deconstruct`, конструктор копирования и `with`.
- `record struct` по умолчанию изменяем: почти всегда нужен `readonly record struct`.
- Структура уместна, если это одно значение до ~16 байт, иммутабельное и редко упаковываемое.
- Изменяемые структуры ведут себя неинтуитивно (копия вместо оригинала) и вызывают защитные копии.
- `with` — поверхностная копия: вложенные изменяемые объекты остаются общими.
- Первичные конструкторы (C# 12) сокращают классы с внедрением зависимостей, но не генерируют свойства и равенство.
- Данные — `record`, мелкие величины — `readonly record struct`, поведение и идентичность — `class`.
