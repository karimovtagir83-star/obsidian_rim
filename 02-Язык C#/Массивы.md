# Массивы

> [!abstract] Коротко
> Массив — непрерывный блок памяти в куче с фиксированной длиной, известной при создании. Это единственная структура данных, встроенная в саму платформу: у неё есть поддержка в IL, в JIT и в GC, поэтому она быстрее любой коллекции — и одновременно менее удобна, потому что размер изменить нельзя. Все `List<T>`, `Dictionary<K,V>`, `StringBuilder` внутри — это массивы плюс логика роста. Уметь надо три вещи: работать с индексами и срезами, отличать многомерный массив от ступенчатого и знать методы класса `Array`.

## Зачем это нужно

Массивы в прикладном коде встречаются реже, чем `List<T>`, но зато в самых важных местах:

- любой байтовый ввод-вывод — `byte[]`: файлы, сеть, шифрование, сериализация;
- `Span<T>`/`Memory<T>` и вся работа без аллокаций строятся поверх массивов;
- параметры `params`, `Main(string[] args)`, `string.Split()` возвращают массивы;
- в собеседовании live coding почти всегда про массив и строку — потому что там негде спрятаться за библиотечным методом.

И главное: понимая массив, понимаешь, как устроены остальные коллекции.

## Объявление и инициализация

```csharp
// Все способы задать массив
int[] a1 = new int[5];                     // 5 элементов, заполненных 0
int[] a2 = new int[] { 1, 2, 3 };
int[] a3 = { 1, 2, 3 };                    // только при объявлении
int[] a4 = [1, 2, 3];                      // коллекционное выражение (C# 12) — предпочтительный стиль
var a5 = new[] { 1, 2, 3 };                // тип выводится из элементов
int[] a6 = [];                             // пустой; компилятор использует Array.Empty<int>()

// Значения по умолчанию: 0 для чисел, false для bool, null для ссылок
string[] names = new string[3];
Console.WriteLine(names[0] is null);       // Вывод: True

// Spread — склейка массивов (C# 12)
int[] head = [1, 2];
int[] tail = [4, 5];
int[] all = [..head, 3, ..tail];           // [1, 2, 3, 4, 5]
```

Коллекционные выражения `[...]` — новый универсальный синтаксис: та же запись работает для массива, `List<T>`, `Span<T>`, `ImmutableArray<T>`, и компилятор выбирает эффективный способ создания. Для пустого массива он подставит кешированный `Array.Empty<T>()` вместо новой аллокации — это правильная привычка и в старом коде: `Array.Empty<T>()` вместо `new T[0]`.

### Массив — ссылочный тип

```csharp
int[] source = [1, 2, 3];
int[] alias = source;          // копируется ССЫЛКА, не данные
alias[0] = 99;
Console.WriteLine(source[0]);   // Вывод: 99

int[] copy = [..source];        // настоящая копия (или source.ToArray(), Array.Copy)
copy[0] = 1;
Console.WriteLine(source[0]);   // Вывод: 99 — исходник не тронут

// Сравнение по умолчанию — по ссылке:
Console.WriteLine([1, 2] == (int[])[1, 2]);              // False — разные объекты
Console.WriteLine(new[] {1,2}.SequenceEqual(new[] {1,2}));// True — сравнение содержимого
```

Сам массив всегда живёт в куче, даже если элементы — значимые типы. Массив на 1000 `int` — это один объект в куче с непрерывным блоком 4000 байт; массив на 1000 ссылок на объекты — это 1001 объект. Отсюда практический вывод про производительность: массив структур обходится кратно быстрее массива классов, потому что данные лежат рядом. Разбор — [[Value types vs Reference types]] и [[Как работает компьютер: процессор, память, ОС]].

## Индексы, диапазоны, срезы

```csharp
int[] data = [10, 20, 30, 40, 50];

Console.WriteLine(data[0]);        // 10 — индексация с нуля
Console.WriteLine(data[^1]);       // 50 — индекс с конца (C# 8): ^1 это последний
Console.WriteLine(data[^2]);       // 40

int[] middle = data[1..4];         // [20, 30, 40] — от 1 включительно до 4 исключительно
int[] head   = data[..2];          // [10, 20]
int[] tail   = data[3..];          // [40, 50]
int[] whole  = data[..];           // копия целиком

// Диапазон и индекс — обычные типы, их можно хранить в переменных
Range r = 1..^1;
Console.WriteLine(string.Join(",", data[r]));   // 20,30,40
```

> [!warning] Срез массива копирует данные, срез Span — нет
> ```csharp
> int[] slice = data[1..4];              // НОВЫЙ массив: аллокация + копирование
> Span<int> view = data.AsSpan()[1..4];  // окно в тот же массив: 0 аллокаций
> view[0] = 999;
> Console.WriteLine(data[1]);            // Вывод: 999 — Span смотрит в исходные данные
> ```
> Для больших массивов в горячем коде это разница между работой и деградацией. Подробно — [[Span, ReadOnlySpan и Memory]].

Подробнее про `Index`, `Range` и то, как их поддержать в своих типах, — [[Индексаторы, Index и Range]].

## Класс Array: что есть готового

```csharp
int[] numbers = [5, 3, 9, 1, 7];

Array.Sort(numbers);                          // на месте: [1, 3, 5, 7, 9]; introsort, O(n log n)
Array.Reverse(numbers);                       // на месте
Array.IndexOf(numbers, 5);                    // индекс или -1
Array.BinarySearch(numbers, 5);               // O(log n), но ТОЛЬКО для отсортированного
Array.Clear(numbers);                         // заполнить значениями по умолчанию
Array.Fill(numbers, 42);                      // заполнить конкретным значением
Array.Copy(source, dest, count);              // копировать элементы
Array.Exists(numbers, x => x > 5);            // как Any
Array.Find(numbers, x => x > 5);              // первый подходящий или default
Array.TrueForAll(numbers, x => x > 0);        // как All
Array.ConvertAll(numbers, x => x.ToString()); // как Select + ToArray

var empty = Array.Empty<int>();               // кешированный пустой массив, без аллокации

// «Изменение размера», которого не существует
int[] small = [1, 2, 3];
Array.Resize(ref small, 5);                   // создаёт НОВЫЙ массив и копирует; ref обязателен
Console.WriteLine(small.Length);              // Вывод: 5
```

`Array.Resize` — самый обманчивый метод в BCL: он не увеличивает массив, а создаёт другой и копирует данные, поэтому в цикле это `O(n²)`. Нужен растущий контейнер — это `List<T>`, который делает то же самое, но с амортизированным удвоением ёмкости.

Свойства и «размерность»:

```csharp
int[] one = [1, 2, 3];
Console.WriteLine(one.Length);        // 3 — общее число элементов
Console.WriteLine(one.Rank);          // 1 — число размерностей

int[,] grid = new int[3, 4];
Console.WriteLine(grid.Length);        // 12 — ВСЕГО элементов, не 3 и не 4
Console.WriteLine(grid.Rank);          // 2
Console.WriteLine(grid.GetLength(0));  // 3 — по первой размерности
Console.WriteLine(grid.GetLength(1));  // 4
```

## Многомерные и ступенчатые массивы

Две разные вещи с похожим синтаксисом.

```csharp
// Многомерный (rectangular): ОДИН объект, непрерывный блок 3×4
int[,] rect = new int[3, 4];
rect[1, 2] = 5;
int[,] initialized = { { 1, 2 }, { 3, 4 } };

// Ступенчатый (jagged): массив массивов, 1 + 3 объекта, строки могут быть разной длины
int[][] jagged = new int[3][];
jagged[0] = [1, 2];
jagged[1] = [3, 4, 5, 6];
jagged[2] = [];
jagged[1][2] = 5;
```

```
int[3,4] в памяти — один объект:
[ хедер | 3 | 4 | 00 01 02 03 10 11 12 13 20 21 22 23 ]

int[3][] в памяти — четыре объекта:
[ хедер | 3 | ref → [1,2] ]
                 ref → [3,4,5,6]
                 ref → []
```

| | `int[,]` многомерный | `int[][]` ступенчатый |
|---|---|---|
| Объектов в куче | 1 | 1 + число строк |
| Строки разной длины | нельзя | можно |
| Доступ по элементу | вычисление адреса (умножение) | два разыменования |
| Скорость обхода | обычно медленнее в .NET | обычно быстрее |
| LINQ | нужен `Cast<int>()` | работает естественно |
| `foreach` | обходит все элементы подряд | обходит строки |

Неожиданный, но многократно измеренный факт: в .NET **ступенчатые массивы обычно быстрее многомерных**, потому что JIT хорошо оптимизирует одномерный доступ и устраняет проверки границ, а для `int[i, j]` вынужден считать смещение и проверять две границы. Поэтому в вычислительном коде на .NET чаще используют `int[][]` или одномерный массив с ручным индексом:

```csharp
// Самый быстрый вариант для матрицы: одномерный массив + ручной индекс
int width = 4;
var flat = new int[3 * width];
flat[1 * width + 2] = 5;         // эквивалент rect[1, 2]
```

Обход двумерных данных всегда по строкам (последний индекс во внутреннем цикле) — иначе теряется локальность кеша, и разница достигает 5–10 раз.

## Ковариантность массивов: скрытая мина

```csharp
string[] strings = ["a", "b"];
object[] objects = strings;       // компилируется! Массивы ковариантны
objects[0] = 42;                  // ArrayTypeMismatchException в РАНТАЙМЕ
```

Ковариантность массивов ссылочных типов — решение из C# 1.0, принятое до появления дженериков ради совместимости с Java. Сегодня это считается ошибкой дизайна: типобезопасность нарушена, и цена — проверка типа при каждой записи в массив ссылок (её нет только там, где JIT доказал точный тип).

Практический вывод: не передавать `T[]` туда, где ждут `object[]` или базовый тип. Для чтения безопасно использовать `IReadOnlyList<T>`, который ковариантен корректно, потому что записи в нём нет — см. [[Дженерики: ограничения и вариантность]].

## Массивы и интерфейсы

`T[]` реализует `IList<T>`, `ICollection<T>`, `IEnumerable<T>`, `IReadOnlyList<T>`:

```csharp
IList<int> asList = new[] { 1, 2, 3 };
Console.WriteLine(asList.Count);        // 3
// asList.Add(4);                        // NotSupportedException: размер фиксирован
Console.WriteLine(asList.IsReadOnly);    // False (!) — но Add всё равно упадёт
```

Это «протекающая» абстракция: массив выдаёт себя за изменяемый список, но половина операций бросает `NotSupportedException`. Отсюда правило API: если метод принимает данные только для чтения, объявляй параметр как `IReadOnlyList<T>` или `ReadOnlySpan<T>`, а не `IList<T>` — семантика будет честной.

Что возвращать из публичного метода: `T[]` — если вызывающий вправе менять результат и данные уже в массиве; `IReadOnlyList<T>` — если менять нельзя; `IEnumerable<T>` — если результат вычисляется лениво. Возвращать внутренний массив напрямую — типичная утечка инкапсуляции: вызывающий получит право менять состояние объекта в обход его методов.

## Производительность и память

```csharp
// Проверка границ есть при каждом обращении, но JIT её устраняет
// для канонического цикла — не «оптимизируй» его вручную:
for (int i = 0; i < data.Length; i++)      // проверка устранена
    data[i] *= 2;

// Большие массивы попадают в Large Object Heap (LOH) — от 85 000 байт.
// Для int это ~21 250 элементов, для ссылок на 64-битной платформе ~10 600.
var big = new byte[100_000];               // сразу в LOH: не сжимается по умолчанию,
                                           // собирается только при полной сборке

// Частые большие буферы берут из пула, а не создают заново:
var pool = System.Buffers.ArrayPool<byte>.Shared;
byte[] buffer = pool.Rent(4096);           // может вернуть БОЛЬШИЙ массив, чем просили
try
{
    // работать только с buffer.AsSpan(0, 4096)
}
finally
{
    pool.Return(buffer);                   // обязательно, иначе смысла нет
}

// Маленькие буферы можно вообще не аллоцировать:
Span<byte> onStack = stackalloc byte[128];
```

Про LOH и фрагментацию — [[Поколения GC, LOH и режимы сборщика]], про пул и `stackalloc` — [[Span, Memory и ArrayPool на практике]] и [[stackalloc и работа без аллокаций]].

> [!warning] Подводные камни
> - **`Array.Resize` не меняет размер.** Создаёт новый массив и копирует; в цикле это квадратичная сложность. Растущие данные — `List<T>`.
> - **`Length` у многомерного массива — общее число элементов.** `new int[3,4].Length` равно 12; размеры по осям — через `GetLength(i)`.
> - **Ковариантность массивов.** `object[] o = new string[1]; o[0] = 42;` компилируется и падает в рантайме.
> - **`==` для массивов сравнивает ссылки.** Содержимое — `SequenceEqual` или `MemoryExtensions.SequenceEqual` для спанов.
> - **`Clone()` — поверхностная копия.** Массив объектов клонируется как массив тех же ссылок; изменение объекта видно через оба массива.
> - **Возврат внутреннего массива из свойства.** Вызывающий получает право изменить состояние объекта напрямую. Возвращай копию, `IReadOnlyList<T>` или `ReadOnlySpan<T>`.
> - **Массив как ключ словаря.** Хеш и равенство — по ссылке, поэтому найти значение по «такому же» массиву невозможно. Нужен `StructuralComparisons.StructuralEqualityComparer` или иной ключ.
> - **`new T[0]` в горячем коде.** Каждый вызов — аллокация; `Array.Empty<T>()` возвращает один общий экземпляр.

> [!example] Как делают в бою
> В прикладном коде массивы применяют там, где размер известен и не меняется: результат запроса, конфигурация, байтовый буфер. Всё, что растёт, — `List<T>`. Всё, что отдаётся наружу и не должно меняться, — `IReadOnlyList<T>` или `ImmutableArray<T>`.
> В инфраструктурном коде (парсеры, сериализация, сетевые протоколы) массивы центральны, но работают с ними через `Span<T>`: срезы без копирования, `ArrayPool` для буферов, `stackalloc` для мелочи. Именно так написаны `System.Text.Json` и Kestrel — и именно поэтому они не создают мусор на каждый запрос.
> Отдельная практика — не превращать массив в LINQ-цепочку в горячем пути. `data.Where(...).Select(...).ToArray()` создаёт делегаты, перечислители и промежуточный буфер; в коде, вызываемом миллионы раз в секунду, это заметно, а в обычном обработчике HTTP-запроса — нет. Разница между этими двумя случаями и есть содержание разговора об оптимизации.

## Вопросы с собеседований

> [!question]- Чем `int[,]` отличается от `int[][]`?
> `int[,]` — многомерный (прямоугольный) массив: один объект в куче, непрерывный блок, все строки одинаковой длины, адрес элемента вычисляется умножением. `int[][]` — ступенчатый: массив ссылок на отдельные одномерные массивы, строки могут быть разной длины и даже `null`, доступ требует двух разыменований. По памяти многомерный экономнее (нет заголовков вложенных объектов и ссылок), по скорости в .NET обычно проигрывает: JIT хорошо оптимизирует одномерный доступ и устраняет проверки границ, а для двумерного индексирования вынужден считать смещение. Ещё практические различия: LINQ по `int[,]` требует `Cast<int>()`, `foreach` по нему обходит все элементы подряд, а по `int[][]` — строки. В вычислительном коде на .NET часто используют одномерный массив с ручным вычислением индекса — это самый быстрый вариант.

> [!question]- Что такое ковариантность массивов и почему это проблема?
> Массивы ссылочных типов в C# ковариантны: `string[]` можно присвоить переменной типа `object[]`. Для чтения это безопасно, но для записи — нет: через `object[]` можно попытаться положить `int` или `StringBuilder` в массив, который физически хранит строки. Компилятор это разрешает, а рантайм при каждой записи проверяет фактический тип элемента и бросает `ArrayTypeMismatchException`. Получается двойной проигрыш: типобезопасность не гарантирована на этапе компиляции, и есть цена проверки в рантайме. Решение было принято в C# 1.0 до появления дженериков; сегодня правильный способ безопасной ковариантности — `IEnumerable<out T>`/`IReadOnlyList<out T>`, где вариантность корректна именно потому, что запись отсутствует.

> [!question]- Почему `Array.Resize` не рекомендуется в цикле?
> Потому что он не изменяет существующий массив (в CLR это невозможно: длина — часть объекта), а выделяет новый нужного размера, копирует элементы и переприсваивает ссылку — отсюда и параметр `ref`. Одна такая операция стоит `O(n)`; вызов на каждой итерации даёт `O(n²)` и порождает мусор для GC: каждый промежуточный массив становится недостижимым сразу после копирования. `List<T>` решает ту же задачу правильно: он держит внутренний массив с запасом и при заполнении удваивает ёмкость, что даёт амортизированную `O(1)` на добавление. Если конечный размер известен заранее, лучше всего сразу создать массив нужной длины или задать `List<T>` начальную ёмкость.

> [!question]- Что такое LOH и при чём тут массивы?
> Large Object Heap — отдельная область управляемой кучи для объектов от 85 000 байт. Почти всегда туда попадают именно массивы: `byte[]` больше ~85 КБ, `int[]` больше ~21 250 элементов, массив ссылок больше ~10 600 элементов на 64-битной платформе. Особенности LOH: объекты в нём по умолчанию не перемещаются (сжатие можно запросить вручную), а сборка происходит только при полной сборке второго поколения — то есть редко и дорого. Практические последствия: частое выделение больших буферов ведёт к фрагментации LOH и росту потребления памяти при формально небольшом объёме живых данных, а также к длинным паузам. Лечение — `ArrayPool<T>` для переиспользования буферов, потоковая обработка вместо чтения файла целиком и `Span<T>` вместо срезов-копий.

> [!question]- Как сравнить два массива на равенство содержимого?
> Оператор `==` и `Equals` по умолчанию сравнивают ссылки, потому что массив не переопределяет равенство. Варианты по содержимому: `a.SequenceEqual(b)` из LINQ (универсально, но с накладными расходами на перечислители); `a.AsSpan().SequenceEqual(b)` (для примитивов работает через векторизованное сравнение памяти и заметно быстрее); `StructuralComparisons.StructuralEqualityComparer.Equals(a, b)` (умеет вложенные структуры); для байтовых массивов также `MemoryExtensions.SequenceCompareTo` при необходимости порядка. Отдельный момент: массив нельзя использовать как ключ словаря по содержимому — хеш считается по ссылке, поэтому нужен либо специальный компаратор, либо другой ключ (строка, кортеж, `ReadOnlyMemory<T>` с самодельным компаратором).

## Задачи

### Задача 1. Развернуть массив на месте

Напиши метод, разворачивающий массив без создания второго массива и без `Array.Reverse`.

> [!success]- Решение
> ```csharp
> static void Reverse<T>(T[] array)
> {
>     for (int i = 0, j = array.Length - 1; i < j; i++, j--)
>         (array[i], array[j]) = (array[j], array[i]);   // обмен через кортеж, без temp
> }
> ```
> Два указателя идут навстречу, условие `i < j` останавливает их в середине — при нечётной длине центральный элемент остаётся на месте, и это правильно. Кортежное присваивание (C# 7) компилируется в те же три операции, что и обмен через временную переменную, но читается лучше. Сложность `O(n)` по времени, `O(1)` по памяти. Если бы массив нужно было развернуть как срез, правильнее было бы принимать `Span<T>`: тогда метод работал бы и по части массива, и по `stackalloc`-буферу без изменений.

### Задача 2. Найти второй максимум

Дан массив `int[]` длиной не меньше двух. Найди второе по величине **различное** значение за один проход.

> [!success]- Решение
> ```csharp
> static int SecondMax(int[] data)
> {
>     if (data.Length < 2) throw new ArgumentException("Нужно минимум два элемента", nameof(data));
>
>     long max = long.MinValue, second = long.MinValue;
>     foreach (var x in data)
>     {
>         if (x > max) { second = max; max = x; }
>         else if (x > second && x != max) second = x;
>     }
>
>     if (second == long.MinValue)
>         throw new InvalidOperationException("Все элементы одинаковы");
>     return (int)second;
> }
> ```
> Ключевые детали: один проход `O(n)` вместо сортировки `O(n log n)`; накопители объявлены как `long`, чтобы `long.MinValue` был заведомо меньше любого `int` и не пришлось вводить флаги «значение ещё не найдено»; условие `x != max` обеспечивает требование «различное», иначе на массиве `[5, 5, 3]` ответом было бы 5. Отдельно стоит обработать случай, когда второго различного значения нет — иначе метод молча вернёт мусор.

### Задача 3. Найти ошибку с памятью

Метод читает файл и возвращает его строки. Что здесь не так для файла на 2 ГБ?

```csharp
static string[] ReadLines(string path)
{
    var content = File.ReadAllText(path);
    return content.Split('\n');
}
```

> [!success]- Решение
> Проблем несколько, и все про память. `ReadAllText` создаёт одну строку на весь файл: для 2 ГБ текста в UTF-8 это ~4 ГБ в UTF-16, и она сразу попадает в LOH (а при превышении лимита длины строки — `OutOfMemoryException`). Затем `Split` создаёт ещё и массив всех строк — то есть в памяти одновременно оказываются и монолит, и его разбор, удваивая пик. Плюс `Split('\n')` оставляет `\r` в конце строк для файлов с CRLF.
> ```csharp
> static IEnumerable<string> ReadLines(string path) => File.ReadLines(path);
> ```
> `File.ReadLines` возвращает ленивую последовательность и читает файл построчно через буфер: потребление памяти постоянно и не зависит от размера файла, обработка начинается сразу, а перевод строки распознаётся корректно для обоих вариантов. Разница между `ReadAllLines` (массив целиком) и `ReadLines` (ленивое перечисление) — типовой вопрос про потоковую обработку; см. [[Файлы, потоки и System.IO]].

## Итог

- Массив — объект в куче с фиксированной длиной и непрерывным размещением элементов; на нём построены все коллекции .NET.
- Присваивание копирует ссылку; копия содержимого — `[..source]`, `ToArray()` или `Array.Copy`.
- Срез `array[1..4]` создаёт новый массив; `AsSpan()[1..4]` — окно без копирования.
- `Array.Resize` создаёт новый массив: для растущих данных нужен `List<T>`.
- Многомерный `int[,]` — один объект, ступенчатый `int[][]` — массив массивов; второй в .NET обычно быстрее.
- Массивы ковариантны, и это дыра в типобезопасности: запись через `object[]` падает в рантайме.
- `Length` многомерного массива — общее число элементов; размеры осей — `GetLength(i)`.
- От 85 000 байт массив уходит в LOH: большие буферы берут из `ArrayPool<T>`, мелкие — через `stackalloc`.
