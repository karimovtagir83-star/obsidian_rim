# Делегаты, события и лямбды

> [!abstract] Коротко
> Делегат — типизированная ссылка на метод: тип, который описывает подпись и хранит цель вызова (объект + метод). Лямбда — компактный способ создать такой метод на месте. Событие — обёртка над делегатом, ограничивающая доступ: подписчики могут только добавлять и удалять обработчики, а вызывать умеет только владелец. Практически важны три вещи: делегаты — это объекты (значит, аллокации), замыкания захватывают переменные (значит, продлевают им жизнь), а подписка на событие держит подписчика живым (значит, это самый частый способ получить утечку памяти в .NET).

## Зачем это нужно

Делегаты — механизм, на котором стоит половина платформы: LINQ (`Where(x => ...)`), обратные вызовы, регистрация обработчиков в DI, `Task.ContinueWith`, middleware в ASP.NET Core, фабрики, стратегии.

```csharp
// Без делегата приходится вводить интерфейс и класс на каждую операцию
interface IFilter { bool Match(Order o); }
class ExpensiveFilter : IFilter { public bool Match(Order o) => o.Total > 1000; }
var result = Filter(orders, new ExpensiveFilter());

// С делегатом — одна строка
var result2 = orders.Where(o => o.Total > 1000);
```

## Делегаты

```csharp
// Объявление типа делегата: описывает подпись
public delegate decimal DiscountRule(Order order);

// Создание: из метода, из лямбды, из группы методов
DiscountRule rule1 = o => o.Total * 0.1m;
DiscountRule rule2 = CalculateVipDiscount;
static decimal CalculateVipDiscount(Order o) => o.Customer.IsVip ? o.Total * 0.2m : 0;

decimal discount = rule1(order);           // вызов; эквивалент rule1.Invoke(order)
```

Делегат — полноценный класс, унаследованный от `System.MulticastDelegate`. Внутри у экземпляра два ключевых поля: `Target` (объект, на котором вызывать; `null` для статических методов) и `Method` (метаданные метода). Отсюда две вещи: создание делегата — это аллокация, а делегат на метод экземпляра **держит ссылку на объект**.

### Готовые типы: Func, Action, Predicate

Свои `delegate`-типы в новом коде объявляют редко — хватает встроенных:

```csharp
Action greet = () => Console.WriteLine("привет");             // ничего не возвращает
Action<string> log = msg => Console.WriteLine(msg);            // до 16 параметров
Func<int, int> square = x => x * x;                            // последний параметр — результат
Func<Order, decimal> total = o => o.Total;
Func<Order, bool> isPaid = o => o.Status == OrderStatus.Paid;
Predicate<Order> isPaid2 = o => o.Status == OrderStatus.Paid;   // то же, что Func<T,bool>
Comparison<Order> byTotal = (a, b) => a.Total.CompareTo(b.Total);
```

Когда всё же объявляют свой тип делегата: когда имя несёт смысл (`DiscountRule` понятнее, чем `Func<Order, decimal>`), когда нужны `ref`/`out`/`params` в подписи или когда тип участвует в публичном API и должен документироваться.

### Многоадресность

```csharp
Action pipeline = () => Console.Write("1");
pipeline += () => Console.Write("2");
pipeline += () => Console.Write("3");
pipeline();                              // Вывод: 123 — вызовы в порядке подписки

pipeline -= null;                        // безопасно
Console.WriteLine(pipeline.GetInvocationList().Length);   // 3
```

Свойства, о которых надо знать:

- **Возвращается результат последнего** вызванного обработчика, остальные теряются. Поэтому многоадресные делегаты с результатом — почти всегда ошибка.
- **Исключение в обработчике прерывает цепочку**: последующие не вызываются. Если нужна независимость, обходят `GetInvocationList()` вручную с `try/catch` вокруг каждого.
- **Делегаты иммутабельны**: `+=` создаёт новый экземпляр, а не изменяет существующий. Отсюда и потокобезопасность чтения, и необходимость аккуратности при подписке из разных потоков.

## Лямбды

```csharp
Func<int, int, int> add = (a, b) => a + b;                       // выражение
Func<int, int> factorial = n =>                                  // блок инструкций
{
    var result = 1;
    for (var i = 2; i <= n; i++) result *= i;
    return result;
};

// Типы параметров можно указывать явно, а с C# 12 задавать значения по умолчанию
var withDefault = (int x, int step = 1) => x + step;
Console.WriteLine(withDefault(5));            // Вывод: 6

// C# 10: у лямбды есть «естественный тип», её можно присвоить var
var parse = (string s) => int.Parse(s);        // Func<string,int>

// C# 14: модификаторы параметров без указания типа
var tryTake = (out int value) => { value = 42; return true; };
```

### Замыкания и их цена

```csharp
int multiplier = 3;
Func<int, int> multiply = x => x * multiplier;      // захват переменной multiplier
multiplier = 10;
Console.WriteLine(multiply(5));                     // Вывод: 50 — захвачена ПЕРЕМЕННАЯ, не значение
```

Компилятор создаёт скрытый класс («класс отображения», display class), переносит в его поле захваченную переменную и создаёт делегат на метод этого класса. Практические следствия:

- **аллокация**: класс замыкания и делегат — два объекта на каждое создание;
- **продление жизни**: захваченный объект не собирается GC, пока живёт делегат. Лямбда, захватившая `this`, держит весь объект;
- **общая переменная**: несколько лямбд, захвативших одну переменную, видят её изменения (отсюда классическая ловушка с циклом `for` — см. [[Циклы и итерация]]).

```csharp
// Лямбда без захвата кешируется компилятором: создаётся один раз на весь процесс
Func<int, int> pure = x => x * 2;

// static-лямбда (C# 9) запрещает захват — компилятор проверит
Func<int, int> guaranteed = static x => x * 2;
// Func<int,int> bad = static x => x * multiplier;    // Ошибка: захват запрещён

// Вместо захвата — параметр состояния (перегрузки BCL это поддерживают)
var found = list.Find(item => item.Id == targetId);          // захват targetId → аллокация
// В горячем коде используют перегрузки с state-параметром, например
// CollectionsMarshal, Task.Factory.StartNew(action, state), MemoryCache.GetOrCreate(key, factory)
```

`static` перед лямбдой — дешёвая страховка в горячем коде: если она компилируется, значит аллокации замыкания нет.

Подробный разбор механики захвата — [[Локальные функции и замыкания]]. Про то, как та же лямбда может превратиться не в делегат, а в дерево выражений (и почему это критично для EF Core), — [[Деревья выражений]] и [[IEnumerable vs IQueryable]].

## События

Событие — это делегат плюс ограничение доступа. Без него поле-делегат можно было бы перезаписать целиком или вызвать извне:

```csharp
public sealed class OrderService
{
    // Соглашение .NET: EventHandler<T>, где T — данные события
    public event EventHandler<OrderPaidEventArgs>? OrderPaid;

    public void Pay(Order order)
    {
        order.Status = OrderStatus.Paid;

        // Безопасный вызов: ?. защищает от null (нет подписчиков)
        // и от гонки, потому что читает ссылку один раз
        OrderPaid?.Invoke(this, new OrderPaidEventArgs(order.Id));
    }
}

public sealed class OrderPaidEventArgs(long orderId) : EventArgs
{
    public long OrderId { get; } = orderId;
}

// Подписка
var service = new OrderService();
void Handler(object? sender, OrderPaidEventArgs e) => Console.WriteLine($"Оплачен {e.OrderId}");
service.OrderPaid += Handler;
service.Pay(order);
service.OrderPaid -= Handler;         // отписка — обязательна, см. ниже
```

Что даёт ключевое слово `event`: извне доступны только `+=` и `-=`. Присвоить (`= null`), прочитать список подписчиков или вызвать событие может только код внутри объявляющего типа. Это инкапсуляция: издатель контролирует, когда событие происходит.

Соглашения .NET: тип `EventHandler<TArgs>`, первый параметр — `sender`, данные — в наследнике `EventArgs`, имя события — глагол в форме, отражающей момент (`Closing` — до, `Closed` — после), метод вызова — защищённый `OnXxx` в классах, рассчитанных на наследование.

### Утечки памяти через события

Самая частая утечка в .NET:

```csharp
public sealed class Subscriber
{
    public Subscriber(OrderService service) => service.OrderPaid += OnPaid;   // подписались
    private void OnPaid(object? sender, OrderPaidEventArgs e) { }
    // Отписки нет!
}
```

Событие хранит делегаты, а делегат на метод экземпляра хранит ссылку на `Target`. Значит, **издатель держит подписчика живым**. Если издатель живёт долго (синглтон, кеш, статическое событие), а подписчиков создаётся много, память растёт до конца процесса, а обработчики продолжают вызываться на объектах, которые логически уже уничтожены.

Правильные варианты:

```csharp
// 1. Отписка в Dispose — основной способ
public sealed class Subscriber : IDisposable
{
    private readonly OrderService _service;
    public Subscriber(OrderService service)
    {
        _service = service;
        _service.OrderPaid += OnPaid;
    }
    private void OnPaid(object? sender, OrderPaidEventArgs e) { }
    public void Dispose() => _service.OrderPaid -= OnPaid;
}

// 2. Возврат «токена» подписки — как в IObservable
IDisposable subscription = service.Subscribe(OnPaid);
subscription.Dispose();

// 3. В серверном коде — вообще не события, а очередь/шина сообщений
```

> [!danger] Отписаться лямбдой невозможно
> ```csharp
> service.OrderPaid += (s, e) => Console.WriteLine("!");
> service.OrderPaid -= (s, e) => Console.WriteLine("!");   // НЕ отпишет: это другой объект
> ```
> Удаление сравнивает `Target` и `Method`; две лямбды с одинаковым телом — разные экземпляры. Чтобы отписаться, лямбду надо сохранить в переменную и передавать её же.

### Асинхронные обработчики

```csharp
// Ловушка: подпись EventHandler возвращает void, поэтому async-обработчик становится async void
service.OrderPaid += async (s, e) => await SendEmailAsync(e.OrderId);
// Исключение внутри такого обработчика НЕ поймать: оно уходит в контекст синхронизации
// и обычно роняет процесс. См. [[Дедлоки, async void и типичные ошибки]]
```

Поэтому в серверном коде события с асинхронными обработчиками почти не используют. Вместо них: интерфейс с `Task`-методом, `IAsyncEnumerable`, `Channel` или шина сообщений с обработчиками, возвращающими `Task`.

## Что выбрать: делегат, событие или интерфейс

| Задача | Инструмент |
|---|---|
| Одна операция передаётся в метод (фильтр, проекция, компаратор) | `Func`/`Action` |
| Одна операция настраивается при регистрации в DI | делегат-фабрика |
| Уведомление многих слушателей внутри процесса, UI | `event` |
| Стратегия с несколькими связанными операциями | интерфейс |
| Поток событий с фильтрацией и композицией | `IObservable<T>`, `IAsyncEnumerable<T>` |
| Развязка между модулями и сервисами, асинхронность | шина сообщений, `Channel`, брокер |

В бэкенде `event` встречается заметно реже, чем в UI-приложениях: события синхронны, не имеют возвращаемого значения, не поддерживают `await` и создают связность через подписки. Их место обычно занимают доменные события с явным диспетчером ([[Доменные события]]) и очереди ([[System.Threading.Channels]]).

> [!warning] Подводные камни
> - **Подписка без отписки.** Издатель держит подписчика — утечка памяти, а обработчики срабатывают на «мёртвых» объектах.
> - **Отписка лямбдой.** Не работает: нужен тот же экземпляр делегата.
> - **Вызов события без `?.`.** При отсутствии подписчиков поле равно `null` → `NullReferenceException`. Плюс `?.Invoke` читает ссылку один раз и защищает от гонки «отписался между проверкой и вызовом».
> - **`async void` в обработчике.** Исключения не перехватываются и роняют процесс.
> - **Многоадресный делегат с результатом.** Возвращается значение последнего обработчика, остальные молча теряются.
> - **Захват `this` в долгоживущей лямбде.** Объект не собирается, пока делегат жив: типично для кеширования делегатов в статических полях и подписок на статические события.
> - **Аллокации в горячем цикле.** Лямбда с захватом создаёт класс замыкания и делегат на каждой итерации. `static`-лямбда или перегрузка с параметром состояния решают.
> - **Исключение в одном обработчике ломает остальные.** Если подписчики независимы, обходить `GetInvocationList()` с индивидуальным `try/catch`.

> [!example] Как делают в бою
> Делегаты в серверном .NET встречаются постоянно, но почти всегда как `Func`/`Action` в аргументах: предикаты LINQ, фабрики в DI (`services.AddSingleton<IClock>(sp => new SystemClock())`), конвейер middleware (`app.Use(next => async ctx => ...)`), политики устойчивости, `GetOrCreate` в кешах.
> События в бэкенде используются ограниченно — в основном внутри библиотек и там, где издатель и подписчик живут одинаково долго. Для уведомлений между частями приложения берут доменные события с диспетчером, для развязки между сервисами — брокер сообщений. Причина проста: событие синхронно, не умеет `await`, не переживает перезапуск и не даёт гарантий доставки.
> Если событие всё же нужно, подписка оформляется как ресурс: класс-подписчик реализует `IDisposable`/`IAsyncDisposable` и отписывается там, а его время жизни контролирует DI-контейнер. Подписки «на всякий случай» в конструкторах синглтонов — самая частая причина растущей памяти в долгоживущем сервисе.

## Вопросы с собеседований

> [!question]- Чем событие отличается от поля-делегата?
> `event` — это тот же делегат, но с ограниченным доступом извне: снаружи доступны только операции `+=` и `-=`, а присвоить событие целиком, прочитать список подписчиков или вызвать его может только код объявляющего типа. Технически компилятор генерирует приватное поле-делегат и пару методов `add_X`/`remove_X`. Зачем это нужно: без `event` любой внешний код мог бы сделать `service.OnPaid = null`, стерев чужие подписки, или вызвать событие от чужого имени, что нарушило бы инкапсуляцию — издатель должен сам решать, когда событие произошло. Дополнительно `event` даёт стандартную форму, которую понимают инструменты и конвенции .NET (`EventHandler<T>`, `sender`, `EventArgs`). Можно определить и собственные аксессоры `add`/`remove` — например, чтобы хранить подписки в словаре или реализовать слабые ссылки.

> [!question]- Почему подписка на событие приводит к утечке памяти?
> Потому что делегат на метод экземпляра хранит ссылку на этот экземпляр в поле `Target`, а событие хранит список делегатов. Значит, издатель ссылается на подписчика, и пока живёт издатель, GC не может собрать подписчика — даже если больше на него никто не ссылается. Если издатель — долгоживущий объект (синглтон, статическое событие, кеш), а подписчики создаются на каждый запрос или на каждое окно, память растёт монотонно, и вдобавок обработчики продолжают вызываться на логически уничтоженных объектах, что даёт странные баги. Лечение: отписываться (`-=`) в `Dispose` подписчика, использовать модель «подписка возвращает `IDisposable`» вместо `+=`, применять слабые ссылки для событий там, где отписку гарантировать нельзя, либо вообще заменять события на очередь или шину сообщений. Обратное направление (подписчик держит издателя) утечкой обычно не является.

> [!question]- Что такое замыкание и что происходит с захваченной переменной?
> Замыкание — лямбда или локальная функция, использующая переменные из внешней области. Компилятор создаёт скрытый класс, переносит захваченные переменные в его поля и заменяет обращения к ним обращениями к полям; делегат создаётся на метод этого класса. Отсюда три следствия. Захватывается **переменная, а не значение**: изменение снаружи видно внутри лямбды и наоборот, а несколько лямбд, захвативших одну переменную, разделяют состояние. Продлевается **время жизни**: пока жив делегат, живы захваченные объекты, включая `this`, если захвачено поле или метод экземпляра. Появляются **аллокации**: класс замыкания плюс сам делегат, на каждое вычисление лямбды. Лямбда без захвата кешируется компилятором и создаётся один раз; модификатор `static` перед лямбдой запрещает захват, и это удобный способ гарантировать отсутствие аллокаций в горячем коде.

> [!question]- Что произойдёт, если один из обработчиков многоадресного делегата бросит исключение?
> Вызов прервётся на нём: обработчики выполняются последовательно в порядке подписки, и исключение выйдет из вызова делегата, не дав выполниться остальным. Издатель при этом не знает, сколько подписчиков успело сработать. Если подписчики независимы и должны выполняться все, надо обходить список вручную: `foreach (var handler in myEvent.GetInvocationList().Cast<EventHandler<T>>())` с индивидуальным `try/catch` и, при необходимости, сбором исключений в `AggregateException`. Второй важный момент того же ряда: у многоадресного делегата с возвращаемым значением вызывающий получает результат только последнего обработчика, остальные молча теряются — поэтому события объявляют с `void`, а если результат нужен, используют не событие, а список стратегий.

## Задачи

### Задача 1. Найти утечку

```csharp
public sealed class NotificationHub
{
    public event Action<string>? MessageReceived;
    public void Publish(string message) => MessageReceived?.Invoke(message);
}

public sealed class RequestHandler
{
    private readonly List<string> _log = [];
    public RequestHandler(NotificationHub hub) => hub.MessageReceived += m => _log.Add(m);
}
```

`NotificationHub` зарегистрирован как singleton, `RequestHandler` — как scoped. Что произойдёт за сутки работы?

> [!success]- Решение
> Каждый HTTP-запрос создаёт новый `RequestHandler`, который подписывается на событие синглтона. Отписки нет, а лямбда захватывает `this` (через поле `_log`), поэтому хаб держит ссылку на каждый созданный обработчик и на его список строк. За сутки в списке подписчиков окажутся десятки тысяч мёртвых объектов: память растёт монотонно, а `Publish` начинает работать всё дольше, потому что вызывает всю накопленную цепочку. Отписаться этой лямбдой нельзя даже при желании — сохранённой ссылки на делегат нет.
> ```csharp
> public sealed class RequestHandler : IDisposable
> {
>     private readonly NotificationHub _hub;
>     private readonly Action<string> _handler;
>     private readonly List<string> _log = [];
>
>     public RequestHandler(NotificationHub hub)
>     {
>         _hub = hub;
>         _handler = m => _log.Add(m);       // сохраняем ТОТ ЖЕ экземпляр делегата
>         _hub.MessageReceived += _handler;
>     }
>
>     public void Dispose() => _hub.MessageReceived -= _handler;
> }
> ```
> DI-контейнер вызовет `Dispose` при завершении scope. Но в серверном приложении правильнее вообще не связывать компоненты разного времени жизни через события: для этого есть очередь (`Channel`) или шина сообщений, где подписчик не удерживается издателем.

### Задача 2. Вызвать всех подписчиков несмотря на ошибки

Реализуй метод публикации, который вызывает всех подписчиков, собирает исключения и бросает их одним `AggregateException`.

> [!success]- Решение
> ```csharp
> public sealed class SafeHub
> {
>     public event Action<string>? MessageReceived;
>
>     public void Publish(string message)
>     {
>         var handlers = MessageReceived;          // копия ссылки: защита от гонки при отписке
>         if (handlers is null) return;
>
>         List<Exception>? errors = null;
>         foreach (var handler in handlers.GetInvocationList())
>         {
>             try
>             {
>                 ((Action<string>)handler)(message);
>             }
>             catch (Exception ex)
>             {
>                 (errors ??= []).Add(ex);
>             }
>         }
>
>         if (errors is { Count: > 0 })
>             throw new AggregateException("Часть подписчиков завершилась с ошибкой", errors);
>     }
> }
> ```
> Ключевые моменты: `GetInvocationList()` даёт массив отдельных делегатов, и каждый вызывается в своём `try` — поэтому падение одного подписчика не мешает остальным; локальная копия `handlers` нужна, потому что между проверкой на `null` и вызовом кто-то может отписаться (делегаты иммутабельны, поэтому копия остаётся валидной); список исключений создаётся лениво, чтобы не платить аллокацией в нормальном случае. `AggregateException` сохраняет все ошибки — тот же подход использует TPL при выполнении нескольких задач.

## Итог

- Делегат — типизированная ссылка на метод: объект с полями `Target` и `Method`. Его создание — аллокация, а ссылка на `Target` продлевает жизнь объекту.
- Свои `delegate`-типы почти не нужны: `Func`, `Action`, `Predicate`, `Comparison` покрывают почти всё.
- Многоадресный делегат вызывает подписчиков по порядку; результат остаётся только от последнего, а исключение прерывает цепочку.
- Лямбда захватывает переменную, а не значение; захват создаёт класс замыкания и продлевает время жизни. `static`-лямбда запрещает захват.
- `event` ограничивает доступ: снаружи только `+=`/`-=`, вызов — только внутри типа.
- Подписка без отписки — самая частая утечка памяти в .NET; лямбдой отписаться невозможно.
- `async void`-обработчики событий проглатывают исключения и роняют процесс; в бэкенде вместо событий берут очереди и шину сообщений.
