# Делегаты, события и лямбды

> [!abstract] Коротко
> Делегат — типизированная ссылка на метод: объект с полями `Target` (на ком вызывать) и `Method`. Лямбда и локальная функция — два способа задать этот метод на месте, с разной ценой: лямбда почти всегда аллоцирует, локальная функция — почти никогда. Событие — тот же делегат, но со снятым публичным доступом: снаружи только `+=`/`-=`. Всё это объединяет один механизм — захват переменных (замыкание), который решает, появится ли мусор в куче и кто кого держит живым дольше, чем кажется.

## Зачем это знать

Делегаты стоят под LINQ, DI-фабриками, middleware и подпиской на доменные события — код с ними встречается в каждом PR. Три решения здесь стоят денег напрямую: лямбда с захватом в горячем цикле — это лишние аллокации на каждой итерации; подписка на событие без отписки — самая частая утечка памяти в .NET; переменная цикла, захваченная делегатом, — баг, который проходит компиляцию и падает только в рантайме. Разница между лямбдой и локальной функцией снаружи незаметна, а по цене — это разница между «аллоцирует» и «нет».

## Модель

### Делегат как тип

```csharp
public delegate decimal DiscountRule(Order order);   // описывает подпись, не реализацию

DiscountRule rule1 = o => o.Total * 0.1m;             // из лямбды
DiscountRule rule2 = CalculateVipDiscount;             // из группы методов
decimal d = rule1(order);                              // эквивалент rule1.Invoke(order)
```

Делегат — класс, унаследованный от `System.MulticastDelegate`, с полями `Target` и `Method`. Отсюда два следствия: создание делегата — аллокация, а делегат на метод экземпляра держит ссылку на `Target`. Свои `delegate`-типы объявляют редко: `Func<TArgs..., TResult>`, `Action<TArgs...>`, `Predicate<T>`, `Comparison<T>` покрывают почти всё. Многоадресность (`+=`) — список вызовов: возвращается результат только последнего обработчика, а исключение в одном обрывает цепочку для остальных. Делегаты иммутабельны — `+=` создаёт новый экземпляр, не мутирует старый.

### Лямбда и замыкание: почему это две аллокации

```csharp
int rate = 3;
Func<int, int> mul = x => x * rate;   // захват переменной rate
rate = 10;
Console.WriteLine(mul(5));            // Вывод: 50 — захвачена ПЕРЕМЕННАЯ, не значение
```

Как только тело лямбды обращается к переменной снаружи, компилятор переносит её в скрытый класс (display class) и создаёт делегат на метод этого класса. Захватывается переменная целиком: несколько лямбд из одной области видимости получают поля одного и того же объекта, и долгоживущий делегат может держать в памяти данные, которые захватила соседняя, уже отработавшая лямбда. Захват `this` (обращение к полю или методу экземпляра) продлевает жизнь всему объекту. Лямбда без захвата исключения не составляет только по цене: компилятор кеширует её в статическом поле и создаёт один делегат на весь процесс. `static`-лямбда (C# 9) запрещает захват на уровне компиляции — удобная проверяемая страховка в горячем коде.

### Локальная функция — тот же захват, другая цена

```csharp
public int Process(int[] data, int threshold)
{
    var total = 0;
    void Accumulate(int v) { if (v > threshold) total += v; }   // захват threshold и total
    foreach (var v in data) Accumulate(v);
    return total;
}
```

Локальная функция — это метод, а не выражение-делегат. Если она не преобразуется в делегат, компилятор делает её приватным статическим методом типа, а захваченные переменные упаковывает в **структуру**, которая живёт на стеке и передаётся по `ref`. Ноль аллокаций в куче — в отличие от лямбды, где то же самое дало бы class и делегат. `static` перед локальной функцией (C# 8) запрещает захват совсем, включая `this`, и превращает «я вроде ничего не захватил» в ошибку компиляции. Как только локальную функцию преобразуют в делегат (`Action a = Accumulate;`) или она становится итератором/`async`, структура вынужденно превращается в class — преимущество исчезает.

Практическое следствие для валидации: тело `yield return`- и `async`-методов не выполняется в момент вызова, поэтому проверки аргументов пишут в обычном (нежадном) методе-обёртке, а саму логику — во вложенной локальной функции:

```csharp
public static IEnumerable<T> Where<T>(IEnumerable<T> source, Func<T, bool> predicate)
{
    ArgumentNullException.ThrowIfNull(source);
    return Iterator();
    IEnumerable<T> Iterator() { foreach (var x in source) if (predicate(x)) yield return x; }
}
```

### Захват переменной цикла

```csharp
var actions = new List<Action>();
for (var i = 0; i < 3; i++) actions.Add(() => Console.Write(i));
foreach (var a in actions) a();
// Вывод: 333 — одна переменная i на весь цикл, один display class
```

В `for` переменная объявлена один раз на весь цикл — один display class на все итерации, все делегаты смотрят в одно и то же поле. В `foreach`, начиная с C# 5, переменная итерации логически новая на каждом шаге, поэтому вывод будет `012`. В `for` копию делают вручную: `var copy = i;` внутри тела.

### Событие — делегат с ограниченным доступом

```csharp
public sealed class OrderService
{
    public event EventHandler<OrderPaidEventArgs>? OrderPaid;
    public void Pay(Order o) { o.Status = OrderStatus.Paid; OrderPaid?.Invoke(this, new(o.Id)); }
}
```

`event` не добавляет новый механизм — это тот же делегат-поле, но снаружи типа доступны только `+=` и `-=`; присвоить целиком (`= null`), прочитать список подписчиков или вызвать событие может только код объявляющего типа. Это инкапсуляция: издатель решает, когда событие произошло. Ключевая механика, из-за которой события текут: подписка — это делегат на метод подписчика, а он хранит `Target`. Значит **издатель держит подписчика живым**, и если издатель долгоживущий (синглтон, кеш, статическое событие), а подписчиков создаётся много — память растёт до конца процесса.

## Решения

| Задача | Выбор | Почему |
|---|---|---|
| Хелпер нужен ровно одному методу, оперирует его переменными | локальная функция | не аллоцирует, не засоряет публичную поверхность типа |
| Callback передаётся как значение, аргумент LINQ/API | лямбда (`Func`/`Action`) | это и есть контракт таких API, локальная функция не подходит без преобразования |
| Нужна рекурсия, дженерик, `ref`/`out`, `yield return`, `async` внутри метода | локальная функция | лямбда этого не умеет вовсе или ограниченно |
| Один и тот же коллбэк вызывается в горячем цикле | `static` локальная функция или `static` лямбда | компилятор гарантирует отсутствие захвата и аллокации |
| Уведомление многих слушателей внутри процесса (UI, редкие внутрипроцессные хуки) | `event` | стандартный паттерн подписки с инкапсуляцией |
| Уведомление между модулями/сервисами, нужна асинхронность или доставка | доменное событие через диспетчер, брокер | `event` синхронен, не поддерживает `await`, не переживает подписчика |
| Стратегия с несколькими связанными операциями | интерфейс | делегат покрывает одну операцию, не набор |

## Проверь себя

> [!question]- Почему лямбда с захватом аллоцирует, а локальная функция — нет?
> Лямбда — выражение, создающее объект-делегат; захваченные переменные компилятор переносит в отдельный class в куче, и это плюс сам делегат — минимум два объекта. Локальная функция — метод; если она не преобразуется в делегат, компилятор делает её статическим методом, а захват упаковывает в структуру на стеке, передаваемую по `ref`. Как только локальную функцию превращают в делегат, эта структура становится class — разница с лямбдой исчезает.

> [!question]- Что напечатает `for`-цикл с лямбдами, захватывающими счётчик, и почему в `foreach` иначе?
> `for` объявляет переменную цикла один раз на весь цикл, поэтому все лямбды разделяют один display class и видят финальное значение (`333` для трёх итераций). В `foreach`, начиная с C# 5, переменная итерации логически создаётся заново на каждом шаге — три отдельных display class и вывод `012`. До C# 5 `foreach` вёл себя как `for` — одно из немногих намеренных breaking changes в истории языка.

> [!question]- Почему подписка на событие приводит к утечке памяти?
> Делегат на метод экземпляра хранит ссылку на этот экземпляр в поле `Target`, а событие хранит список делегатов подписчиков. Издатель ссылается на подписчика, и пока жив издатель, GC не может собрать подписчика, даже если больше никто на него не ссылается. Если издатель — синглтон, а подписчики создаются на каждый запрос, память растёт монотонно, а обработчики продолжают срабатывать на логически мёртвых объектах.

> [!question]- Почему нельзя отписаться от события лямбдой?
> `-=` сравнивает делегаты по паре «`Target` + `Method`». Каждое вычисление лямбда-выражения с захватом создаёт новый экземпляр display class и новый делегат, поэтому `service.Event -= m => Handle(m)` сравнивает с несовпадающим `Target` и молча ничего не делает — без исключения. Чтобы отписаться, делегат нужно сохранить в переменную или поле при подписке и передать ту же ссылку в `-=`.

> [!question]- Зачем оборачивать логику итератора или `async`-метода в локальную функцию, а не проверять аргументы прямо в нём?
> Тело метода с `yield return` компилируется в конечный автомат и не выполняется до первого `MoveNext()`; тело `async`-метода выполняется, но исключение оседает в возвращаемом `Task` вместо того, чтобы вылететь синхронно. Если проверки аргументов написать прямо в таком методе, `ArgumentNullException` прилетит не в момент вызова, а при первом переборе или `await` — часто в другом месте стека и позже по времени. Разделение на жадную обёртку с guard clauses и вложенную локальную функцию с реальной логикой возвращает проверкам ожидаемое поведение — так устроены операторы `System.Linq`.

## Разбор

Дан код подписки в конструкторе scoped-сервиса на событие singleton-хаба:

```csharp
public sealed class RequestHandler
{
    private readonly List<string> _log = [];
    public RequestHandler(NotificationHub hub) => hub.MessageReceived += m => _log.Add(m);
}
```

Что произойдёт за сутки работы и как это исправить?

> [!success]- Решение
> `NotificationHub` — singleton, `RequestHandler` — scoped, создаётся на каждый запрос. Лямбда захватывает `this` (через `_log`), поэтому хаб держит ссылку на каждый созданный `RequestHandler`. Отписки нет и подписаться заново, чтобы отписать именно эту лямбду, невозможно — сохранённого делегата нет. За сутки список подписчиков хаба разрастётся до десятков тысяч мёртвых объектов, и `Publish` будет линейно замедляться. Исправление: реализовать `IDisposable`, сохранить делегат в поле при подписке и отписаться в `Dispose`; в серверном коде для связи компонентов с разным временем жизни правильнее вообще не использовать `event`, а брать очередь (`Channel`) или доменное событие с диспетчером.

Дан фрагмент, который агент сгенерировал для фильтрации в цикле, вызываемом в бенчмарке миллионы раз:

```csharp
public int SumAbove(int[] data, int threshold)
{
    Func<int, bool> ok = x => x > threshold;   // захват threshold
    var total = 0;
    foreach (var x in data) if (ok(x)) total += x;
    return total;
}
```

`[MemoryDiagnoser]` показывает ненулевую колонку `Allocated`. Что переписать и почему это уберёт аллокации?

> [!success]- Решение
> ```csharp
> public int SumAbove(int[] data, int threshold)
> {
>     var total = 0;
>     foreach (var x in data) if (IsAbove(x, threshold)) total += x;
>     return total;
>
>     static bool IsAbove(int value, int threshold) => value > threshold;
> }
> ```
> Порог передан параметром, а не захвачен, и функция помечена `static` — компилятор гарантирует отсутствие display class. Локальная функция компилируется в приватный статический метод, вызов — обычный `call`, не через делегат, и JIT может его заинлайнить. Исходный вариант с `Func<int, bool>` создавал бы class замыкания и делегат — лишние два объекта там, где нужен ноль.

## Итог

- Делегат — объект с `Target` и `Method`; создание — аллокация, ссылка на `Target` продлевает жизнь объекту.
- Лямбда с захватом — минимум два объекта в куче (class замыкания + делегат); без захвата кешируется компилятором.
- Локальная функция без преобразования в делегат не аллоцирует: захват уезжает в структуру на стеке, передаваемую по `ref`. `static` у обеих запрещает захват на уровне компиляции.
- `for` захватывает одну переменную на весь цикл, `foreach` с C# 5 — новую на итерацию.
- `event` — делегат с ограниченным доступом снаружи (`+=`/`-=`); подписка без отписки — самая частая утечка памяти в .NET, а отписаться лямбдой нельзя в принципе.
- В серверном коде `event` уместен реже, чем в UI: он синхронен и не пересекает границы времени жизни компонентов — там правильнее доменное событие с диспетчером или брокер.

> [!example] В ServiceShop
> Делегаты в коде — почти всегда `Func`/`Action`: предикаты в LINQ-запросах чтения, фабрики в Autofac (`builder.Register<IClock>(c => new SystemClock())`), делегаты продолжений в цепочках MediatR pipeline behaviors. Обычного C# `event` в бизнес-логике нет: уведомления между модулями идут как доменные события (`INotification` MediatR) с явным диспетчером, а между сервисами — через Kafka и Outbox, потому что `event` не переживает границу процесса и не даёт гарантий доставки. Локальные функции чаще всего встречаются как обёртки-валидаторы перед `async`-логикой в хендлерах команд — тот же приём, что и в BCL: публичный метод жадно проверяет аргументы, а вложенная локальная функция содержит `await`.

> [!warning] Где ошибаются
> - **Захват переменной цикла `for`.** Делегат внутри `for` без явной копии видит финальное значение счётчика у всех итераций разом. **Агент часто:** генерирует `for (var i = ...) list.Add(() => Use(i));` без копии — код компилируется и молча даёт неверный результат.
> - **Утечка через событие без отписки.** Подписка scoped- или transient-объекта на событие singleton-сервиса без `Dispose`/`-=` держит все созданные экземпляры живыми до конца процесса. **Агент часто:** подписывается лямбдой в конструкторе и не добавляет `IDisposable`, потому что явного сигнала «это ресурс» в коде нет.
> - **`async void` в обработчике события.** Сигнатура `EventHandler` не поддерживает `Task`, поэтому асинхронный обработчик становится `async void`, а исключение в нём валит процесс вместо того, чтобы попасть в `try/catch` вызывающего.
> - **Аллокация там, где ожидался ноль.** Рефакторинг добавил в лямбду или локальную функцию обращение к полю экземпляра — она перестала быть без-захватной, и в горячем цикле появился мусор на каждой итерации без единой видимой синтаксической причины.

## Проверка на ревью

- В `for`/`while` с делегатом внутри тела переменная цикла скопирована в локальную, если делегат переживает итерацию.
- На каждую подписку `+=` на не-локальное событие есть парная `-=` в `Dispose`/финализирующем коде, либо подписка оформлена как `IDisposable`-токен.
- Обработчики `event` не помечены `async void` — асинхронная работа вынесена за пределы обработчика или обработчик возвращает `Task` через не-`event` контракт.
- Многоадресный делегат не используется там, где нужен результат каждого подписчика, а не только последнего.
- Горячие пути (циклы, LINQ на больших коллекциях) используют `static` лямбды/локальные функции или явные параметры вместо захвата состояния.
- Локальная функция не превращена в делегат (`Action a = Local;`) без необходимости — это гасит её главное преимущество.
