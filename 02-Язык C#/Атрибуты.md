# Атрибуты

> [!abstract] Коротко
> Атрибут — метаданные, прикреплённые к элементу кода и сохранённые в сборке. Сам по себе он не делает ничего: `[Required]` не проверяет, `[Obsolete]` не запрещает — они лишь помечают, а действует тот, кто их читает (компилятор, анализатор, фреймворк валидации, сериализатор, DI-контейнер, тестовый раннер). Читаются атрибуты обычно рефлексией, а значит, дорого — поэтому в современном .NET их всё чаще обрабатывают генераторами исходного кода на этапе компиляции. Свои атрибуты пишутся в три строки, но полезны только вместе с кодом, который их учитывает.

## Зачем это нужно

Атрибуты — способ объявить намерение декларативно, вместо того чтобы писать императивный код в каждом месте:

```csharp
// Императивно: проверка в теле метода
if (string.IsNullOrEmpty(request.Email)) return BadRequest("Email обязателен");
if (request.Email.Length > 200) return BadRequest("Email слишком длинный");

// Декларативно: правило рядом с данными, проверку делает фреймворк
public sealed record CreateUserRequest
{
    [Required, EmailAddress, StringLength(200)]
    public required string Email { get; init; }
}
```

Половина .NET-фреймворков работает именно так: ASP.NET Core (маршруты, валидация, привязка модели), EF Core (`[Key]`, `[Table]`), сериализация (`[JsonPropertyName]`), тесты (`[Fact]`, `[Theory]`), OpenAPI. Не понимая атрибутов, невозможно понять, как эти библиотеки узнают о твоём коде.

## Синтаксис и цели

```csharp
[Obsolete("Используй CalculateTotalAsync", error: false)]
public decimal CalculateTotal() => 0;

// Несколько атрибутов: в отдельных скобках или через запятую
[Required]
[StringLength(200, MinimumLength = 3)]
public string Name { get; init; } = "";

[Required, StringLength(200)]
public string Title { get; init; } = "";

// Явное указание цели, когда она неоднозначна
[assembly: System.Reflection.AssemblyMetadata("build", "ci")]
[module: System.Diagnostics.CodeAnalysis.SuppressMessage("Category", "Rule")]
[method: Obsolete]                       // атрибут на метод, а не на его возвращаемое значение
[return: System.Diagnostics.CodeAnalysis.NotNullIfNotNull(nameof(input))]
public static string? Trim(string? input) => input?.Trim();
```

Аргументы атрибута делятся на позиционные (параметры конструктора) и именованные (публичные свойства и поля, задаются через `=`). Все они обязаны быть **константами времени компиляции**: числа, строки, `bool`, `enum`, `typeof(T)` и массивы из них. Поэтому `[Range(1, DateTime.Now.Year)]` не скомпилируется.

Цели атрибутов: сборка, модуль, тип, член (метод, свойство, поле, событие), параметр, возвращаемое значение, параметр типа-дженерика.

## Атрибуты, которые встречаются каждый день

| Атрибут | Кто читает | Что делает |
|---|---|---|
| `[Obsolete]` | компилятор | предупреждение или ошибка при использовании |
| `[Flags]` | `Enum.ToString`, `Parse` | побитовое представление перечисления |
| `[Required]`, `[StringLength]`, `[Range]` | валидация ASP.NET Core | проверка модели |
| `[JsonPropertyName]`, `[JsonIgnore]` | `System.Text.Json` | имя и наличие поля в JSON |
| `[Key]`, `[Table]`, `[Column]` | EF Core | отображение на схему БД |
| `[HttpGet]`, `[Route]`, `[FromBody]` | ASP.NET Core | маршрутизация и привязка |
| `[Fact]`, `[Theory]`, `[InlineData]` | xUnit | обнаружение и параметризация тестов |
| `[DebuggerDisplay]`, `[DebuggerStepThrough]` | отладчик | отображение и пропуск при отладке |
| `[MethodImpl(MethodImplOptions.AggressiveInlining)]` | JIT | подсказка по встраиванию |
| `[InternalsVisibleTo("Tests")]` | компилятор | доступ к `internal` из тестовой сборки |
| `[ThreadStatic]`, `[ModuleInitializer]` | рантайм | своё значение на поток; код при загрузке модуля |
| `[NotNullWhen]`, `[MemberNotNull]` | анализ компилятора | контракты по null ([[Nullable reference types]]) |
| `[StringSyntax("Json")]` | IDE | подсветка содержимого строки |

### Атрибуты вызывающего: бесплатная диагностика

Компилятор сам подставляет значения таких параметров в месте вызова:

```csharp
using System.Runtime.CompilerServices;

static void Trace(string message,
                  [CallerMemberName] string? member = null,
                  [CallerFilePath] string? file = null,
                  [CallerLineNumber] int line = 0)
    => Console.WriteLine($"{System.IO.Path.GetFileName(file)}:{line} ({member}) {message}");

static void DoWork() => Trace("начали");     // Вывод: Program.cs:14 (DoWork) начали

// CallerArgumentExpression — текст выражения аргумента (C# 10):
// именно так работает ArgumentNullException.ThrowIfNull
static void Require(bool condition, [CallerArgumentExpression(nameof(condition))] string? expr = null)
{
    if (!condition) throw new ArgumentException($"Нарушено условие: {expr}");
}

Require(1 > 2);       // ArgumentException: Нарушено условие: 1 > 2
```

Это не рефлексия: значения впаиваются при компиляции, стоимость нулевая. Приём широко используется в guard-выражениях ([[Защитное программирование и guard clauses]]) и в логировании.

## Свои атрибуты

```csharp
[AttributeUsage(AttributeTargets.Class | AttributeTargets.Method,
                AllowMultiple = false,
                Inherited = true)]
public sealed class AuditAttribute : Attribute
{
    public AuditAttribute(string action) => Action = action;    // позиционный параметр

    public string Action { get; }
    public bool IncludePayload { get; init; }                    // именованный параметр
}

[Audit("order.create", IncludePayload = true)]
public sealed class CreateOrderHandler { }
```

Соглашения: класс наследуется от `Attribute`, имя заканчивается на `Attribute` (при использовании суффикс опускается), тип `sealed` (быстрее поиск и нет путаницы с наследованием), `[AttributeUsage]` задаёт допустимые цели.

С C# 11 атрибуты могут быть дженериками — это удобнее, чем передавать `typeof`:

```csharp
public sealed class ValidatorAttribute<T> : Attribute where T : class;

[Validator<CreateOrderValidator>]
public sealed record CreateOrderRequest;
```

### Чтение атрибутов

```csharp
using System.Reflection;

var type = typeof(CreateOrderHandler);

// Один атрибут
var audit = type.GetCustomAttribute<AuditAttribute>();
if (audit is not null)
    Console.WriteLine($"{audit.Action}, payload={audit.IncludePayload}");

// Все атрибуты, включая унаследованные
foreach (var attr in type.GetCustomAttributes(inherit: true))
    Console.WriteLine(attr.GetType().Name);

// По всем свойствам типа
foreach (var prop in type.GetProperties())
{
    var required = prop.GetCustomAttribute<System.ComponentModel.DataAnnotations.RequiredAttribute>();
    if (required is not null) Console.WriteLine($"{prop.Name} обязательно");
}
```

Каждый вызов `GetCustomAttribute` — это работа с метаданными и создание экземпляра атрибута. В горячем коде результат обязательно кешируют:

```csharp
static class AuditCache
{
    private static readonly System.Collections.Concurrent.ConcurrentDictionary<Type, AuditAttribute?> Cache = new();

    public static AuditAttribute? Get(Type type)
        => Cache.GetOrAdd(type, static t => t.GetCustomAttribute<AuditAttribute>());
}
```

Именно так поступают все фреймворки: ASP.NET Core и EF Core читают атрибуты один раз при старте, строят модель и дальше работают с ней, а не с рефлексией на каждый запрос.

### Альтернатива рефлексии: генераторы

Современный подход — обработать атрибут **на этапе компиляции** генератором исходного кода: он видит помеченные элементы и порождает обычный C#-код без рефлексии. Так работают `[GeneratedRegex]`, `[LoggerMessage]`, `[JsonSerializable]` и валидация Minimal API в .NET 10. Выигрыш двойной: скорость и совместимость с Native AOT, где рефлексия ограничена. Детали — [[Source Generators]].

> [!warning] Подводные камни
> - **Атрибут сам ничего не делает.** Свой `[Audit]` без кода, который его читает, — просто комментарий, который выглядит как функциональность. Это регулярная ошибка: разработчик помечает метод и ждёт эффекта.
> - **Аргументы только константы.** `DateTime.Now`, `new List<int>()`, вычисляемые значения невозможны. Иногда обходят передачей строки и разбором её в момент чтения — плохой обмен.
> - **Рефлексия в горячем пути.** `GetCustomAttribute` на каждый вызов метода — заметная стоимость. Кешировать по `Type`/`MemberInfo`.
> - **`Inherited = true` не работает для интерфейсов.** Атрибуты, объявленные на интерфейсе, не наследуются реализующим классом — `GetCustomAttributes` их не увидит, придётся обходить интерфейсы вручную.
> - **`[Obsolete]` без сообщения.** Предупреждение без объяснения, что использовать вместо. Всегда указывай замену; `error: true` — когда пора запретить окончательно.
> - **Атрибуты и Native AOT / trimming.** Код, который ищет типы и атрибуты рефлексией, может «потерять» их после обрезки сборки. Требуются аннотации `[DynamicallyAccessedMembers]` или переход на генераторы.
> - **Валидация только атрибутами.** Атрибуты хороши для простых правил (обязательность, длина, диапазон). Правила, зависящие от нескольких полей или от базы, выражаются кодом — FluentValidation или проверка в домене.

> [!example] Как делают в бою
> Свои атрибуты в прикладном коде появляются в двух ролях. Первая — маркеры для инфраструктуры: `[Audit]`, `[RequiresFeature("newCheckout")]`, `[Idempotent]`, которые читает middleware или фильтр один раз при старте и дальше применяет по построенной карте. Вторая — метаданные для генерации: помеченные типы находит генератор исходного кода и создаёт регистрацию в DI, маппинг или валидатор.
> Того, чего избегают: рефлексии на каждый запрос, «магии», о которой не догадаться по коду (атрибут, меняющий поведение метода, но не упомянутый в его имени), и дублирования валидации атрибутами и кодом одновременно.
> Практическая деталь: атрибуты, влияющие на публичный контракт (`[JsonPropertyName]`, `[Required]`), живут на DTO, а не на доменных сущностях — иначе представление протекает в модель, и изменение формата API требует правки домена.

## Вопросы с собеседований

> [!question]- Что такое атрибут и что он делает сам по себе?
> Атрибут — это класс, унаследованный от `System.Attribute`, экземпляр которого описан в метаданных сборки рядом с помеченным элементом. Сам по себе он не делает ничего: это данные, а не поведение. Эффект появляется только тогда, когда его кто-то читает — компилятор (`[Obsolete]`, `[Conditional]`, атрибуты nullable-анализа), рантайм (`[ThreadStatic]`, `[ModuleInitializer]`), фреймворк через рефлексию (валидация, маршрутизация, сериализация, тестовый раннер) или генератор исходного кода на этапе компиляции. Отсюда типичная ошибка новичка: объявить свой атрибут и ждать, что он начнёт что-то проверять. Второе важное свойство — аргументы атрибута должны быть константами времени компиляции, потому что они физически записываются в метаданные.

> [!question]- Как работает `ArgumentNullException.ThrowIfNull` и почему в сообщении оказывается имя переменной?
> За счёт атрибута `[CallerArgumentExpression]`: параметр метода помечается им, и компилятор подставляет в этот параметр **текст выражения**, переданного в указанный аргумент, прямо в месте вызова. То есть при `ArgumentNullException.ThrowIfNull(order.Customer)` в строковый параметр попадёт литерал `"order.Customer"`. Это не рефлексия и не разбор стека — значение впаивается при компиляции, стоимость нулевая. Родственные атрибуты того же семейства: `[CallerMemberName]`, `[CallerFilePath]`, `[CallerLineNumber]`, которые подставляют имя вызывающего члена, путь к файлу и номер строки. Их применяют в логировании, диагностике, реализации `INotifyPropertyChanged` и в guard-выражениях, потому что они дают точный контекст без затрат.

> [!question]- Почему чтение атрибутов рефлексией считается дорогим и что с этим делают?
> Каждый вызов `GetCustomAttribute` требует обращения к метаданным сборки, разбора описания атрибута и создания его экземпляра; кроме того, поиск члена по имени и обход иерархии сам по себе не бесплатен. На один запрос это микросекунды, но в горячем пути (на каждый вызов метода, на каждый элемент коллекции) стоимость становится заметной, а под Native AOT рефлексия ещё и ограничена обрезкой сборок. Стандартные решения два. Первое — кешировать: прочитать атрибуты один раз при старте и построить структуру данных (именно так ASP.NET Core строит таблицу маршрутов, а EF Core — модель). Второе, современное — обрабатывать атрибуты генератором исходного кода: он видит помеченные элементы при компиляции и порождает обычный код, без рефлексии в рантайме; так работают `[GeneratedRegex]`, `[LoggerMessage]` и `[JsonSerializable]`.

## Задачи

### Задача 1. Свой атрибут и его обработка

Нужно помечать обработчики команд именем операции для аудита и один раз при старте построить карту «тип обработчика → имя операции».

> [!success]- Решение
> ```csharp
> [AttributeUsage(AttributeTargets.Class, AllowMultiple = false, Inherited = false)]
> public sealed class AuditAttribute(string action) : Attribute
> {
>     public string Action { get; } = action;
>     public bool IncludePayload { get; init; }
> }
>
> public static class AuditMap
> {
>     public static IReadOnlyDictionary<Type, AuditAttribute> Build(System.Reflection.Assembly assembly)
>         => assembly.GetTypes()
>             .Select(t => (Type: t, Attr: t.GetCustomAttribute<AuditAttribute>()))
>             .Where(x => x.Attr is not null)
>             .ToDictionary(x => x.Type, x => x.Attr!);
> }
>
> // При старте приложения — один раз:
> var map = AuditMap.Build(typeof(Program).Assembly);
> ```
> Ключевые решения: `sealed` и `[AttributeUsage]` с явными целями — чтобы атрибут нельзя было поставить куда попало; первичный конструктор для позиционного параметра и `init`-свойство для необязательного; сканирование сборки выполняется однократно на старте, а дальше работает готовый словарь — рефлексии на каждый запрос нет. Этот же подход масштабируется: если сканирование сборки на старте станет слишком медленным (или потребуется Native AOT), карту генерирует source generator.

### Задача 2. Найти проблему

```csharp
public interface ICommand
{
    [Audit("unknown")]
    void Execute();
}

public sealed class CreateOrder : ICommand
{
    public void Execute() { }
}

// Ожидается, что атрибут найдётся на реализации:
var attr = typeof(CreateOrder).GetMethod(nameof(ICommand.Execute))!
                              .GetCustomAttribute<AuditAttribute>();
Console.WriteLine(attr?.Action ?? "не найден");
```

> [!success]- Решение
> Выведет «не найден». Атрибуты, объявленные на членах интерфейса, **не наследуются** реализующим типом: `Inherited = true` работает только для наследования классов, а реализация интерфейса наследованием в этом смысле не является. Чтобы получить атрибут, надо явно обойти интерфейсы типа:
> ```csharp
> static AuditAttribute? FindAudit(Type type, string methodName)
> {
>     var own = type.GetMethod(methodName)?.GetCustomAttribute<AuditAttribute>();
>     if (own is not null) return own;
>
>     foreach (var iface in type.GetInterfaces())
>     {
>         var map = type.GetInterfaceMap(iface);
>         for (int i = 0; i < map.TargetMethods.Length; i++)
>             if (map.TargetMethods[i].Name == methodName)
>                 return map.InterfaceMethods[i].GetCustomAttribute<AuditAttribute>();
>     }
>     return null;
> }
> ```
> Практический вывод: метаданные для инфраструктуры лучше размещать на конкретных классах, а не на интерфейсах, — иначе обработка становится сложной и неочевидной. И это ещё один аргумент в пользу того, чтобы искать атрибуты один раз при старте, а не на каждом вызове: код с `GetInterfaceMap` в горячем пути недопустим.

## Итог

- Атрибут — метаданные в сборке; поведения в нём нет, действует тот, кто его читает.
- Аргументы атрибута — только константы времени компиляции.
- Цели указываются явно (`[method:]`, `[return:]`, `[assembly:]`), допустимые цели своего атрибута задаёт `[AttributeUsage]`.
- Атрибуты вызывающего (`[CallerMemberName]`, `[CallerArgumentExpression]`) подставляются компилятором и бесплатны.
- Чтение рефлексией дорого: кешировать по типу или, лучше, обрабатывать генератором исходного кода.
- Атрибуты на членах интерфейса не наследуются реализацией.
- Декларативная валидация атрибутами хороша для простых правил; сложные правила — код.
