# Когда исключение — плохой выбор

> [!abstract] Коротко
> Исключение предназначено для ситуации, которую вызывающий **не ожидал** и обычно не может обработать на месте. Всё, что происходит регулярно — пользователь ввёл не то, товара нет на складе, запись не найдена, лимит исчерпан, — это не исключение, а нормальный исход, который должен быть выражен в типе возвращаемого значения. Три альтернативы: `Try*`-метод с `bool` и `out`, nullable-результат и Result-тип с описанием ошибки. Практическая граница простая: **если ситуация встречается в требованиях, она не исключительная**.

## Зачем это нужно

Исключения как способ вернуть результат создают три проблемы сразу.

**Производительность.** Бросок и перехват — десятки микросекунд против наносекунд у обычного возврата. Эндпоинт, где каждый десятый запрос завершается «ожидаемым» исключением, теряет пропускную способность и заполняет мониторинг ложными сбоями.

**Читаемость подписи.** `Order GetOrder(long id)` не говорит ничего о том, что метод может бросить `OrderNotFoundException`. В C# нет проверяемых исключений (в отличие от Java), поэтому компилятор не подскажет, а вызывающий узнает о поведении только из документации — то есть обычно из инцидента.

**Логика через исключения.** Код, где ветвление организовано `try/catch`, невозможно читать: нормальный сценарий и обработка перемешаны, а `catch` перехватывает больше, чем предполагалось.

```csharp
// Так делать нельзя: «нет ключа» — обычный исход, а не сбой
try { var value = dictionary[key]; Use(value); }
catch (KeyNotFoundException) { UseDefault(); }

// Так правильно
if (dictionary.TryGetValue(key, out var value)) Use(value); else UseDefault();
```

## Как отличить ожидаемое от исключительного

| Вопрос | Ожидаемый исход | Исключение |
|---|---|---|
| Есть ли это в требованиях? | «если товара нет, показать…» | нет, это сбой |
| Как часто случается? | регулярно | редко, аварийно |
| Может ли вызывающий обработать? | да, и знает как | обычно нет |
| Виноват ли программист? | нет | часто да |
| Нужно ли будить дежурного? | нет | возможно |

Практические примеры распределения:

| Ситуация | Правильный механизм |
|---|---|
| Строка не разобралась в число | `TryParse` → `bool` |
| Записи с таким id нет | `null` или Result |
| Пользователь ввёл некорректные данные | результат валидации, ответ 400 |
| Товара не хватает на складе | Result с описанием, ответ 409 |
| Внешний сервис недоступен | исключение (и политика повтора) |
| Нарушен инвариант домена изнутри | исключение |
| Аргумент `null` там, где нельзя | исключение (ошибка программиста) |
| Битая конфигурация при старте | исключение — пусть приложение не поднимется |

Последний пункт важен: **бросать исключение правильно, когда продолжать нельзя**. Молча стартовать с неверной конфигурацией хуже, чем упасть.

## Три альтернативы

### 1. `Try*`-паттерн

```csharp
public bool TryGetDiscount(long customerId, out decimal discount)
{
    discount = 0;
    var customer = _cache.Get(customerId);
    if (customer is null) return false;

    discount = customer.IsVip ? 0.1m : 0m;
    return true;
}
```

Плюсы: узнаваемая идиома BCL, нулевая стоимость, отлично работает с анализом nullable через `[NotNullWhen(true)]`. Минусы: только один результат, не композируется (нельзя выстроить цепочку), не переносит причину неудачи. Годится, когда причина не важна: «получилось или нет».

### 2. Nullable-результат

```csharp
public async Task<Order?> FindAsync(long id, CancellationToken ct)
    => await _db.Orders.FirstOrDefaultAsync(o => o.Id == id, ct);
```

Плюсы: простейшая форма, при включённых nullable reference types компилятор заставит вызывающего проверить результат. Минусы: `null` не объясняет причину — «не найдено», «нет доступа» и «удалено» неразличимы.

Соглашение об именовании, принятое в .NET: `Find*`/`*OrDefault` возвращает `null`, `Get*` бросает, если не нашёл. Полезно следовать ему в своём коде — тогда поведение видно по имени.

### 3. Result-тип

```csharp
public abstract record Result<T>
{
    public sealed record Ok(T Value) : Result<T>;
    public sealed record NotFound(string Message) : Result<T>;
    public sealed record Invalid(IReadOnlyList<string> Errors) : Result<T>;
    public sealed record Conflict(string Code, string Message) : Result<T>;
}

public async Task<Result<Order>> PayAsync(long orderId, CancellationToken ct)
{
    var order = await _db.Orders.FindAsync([orderId], ct);
    if (order is null) return new Result<Order>.NotFound($"Заказ {orderId} не найден");
    if (order.Status == OrderStatus.Paid) return new Result<Order>.Conflict("order.already_paid", "Уже оплачен");

    order.Status = OrderStatus.Paid;
    await _db.SaveChangesAsync(ct);
    return new Result<Order>.Ok(order);
}

// На границе — разбор паттернами, компилятор проверит полноту
return result switch
{
    Result<Order>.Ok(var order) => Results.Ok(order),
    Result<Order>.NotFound(var msg) => Results.NotFound(msg),
    Result<Order>.Conflict(var code, var msg) => Results.Conflict(new { code, message = msg }),
    Result<Order>.Invalid(var errors) => Results.ValidationProblem(
        errors.ToDictionary(e => "error", e => new[] { e })),
    _ => Results.Problem()
};
```

Плюсы: все исходы видны в типе, вызывающий обязан их обработать, причина сохраняется, стоимость нулевая. Минусы: больше кода, чем при `throw`; результат нужно протаскивать через слои; в C# пока нет union-типов, поэтому конструкция получается многословной ([[Что впереди: .NET 11 и C# 15]]).

Готовые библиотеки: `ErrorOr`, `FluentResults`, `OneOf`, `LanguageExt`. Прежде чем брать зависимость, стоит написать свой минимальный Result на 30 строк — часто этого достаточно, а поведение полностью под контролем. Подробно — [[Result pattern вместо исключений]].

## Валидация — отдельный случай

Ошибки ввода почти никогда не должны быть исключениями: их много, они ожидаемы, и пользователю нужно показать **все сразу**, а исключение прерывает выполнение на первой.

```csharp
// Плохо: пользователь узнаёт об ошибках по одной, каждый раз через исключение
if (string.IsNullOrEmpty(request.Email)) throw new ValidationException("Email обязателен");
if (request.Age < 18) throw new ValidationException("Возраст меньше 18");

// Хорошо: собрать все и вернуть одним ответом
var errors = new List<string>();
if (string.IsNullOrWhiteSpace(request.Email)) errors.Add("Email обязателен");
if (request.Age < 18) errors.Add("Возраст меньше 18");
if (errors.Count > 0) return Results.ValidationProblem(...);
```

В ASP.NET Core это делает встроенная валидация модели или FluentValidation ([[Model binding и валидация]], [[FluentValidation]]).

## Где исключение — правильный выбор

Не стоит впадать в обратную крайность: Result-типы в каждом методе делают код многословным без пользы.

- **Нарушение инварианта внутри домена.** «Сумма заказа стала отрицательной» — не исход, о котором надо аккуратно сообщить, а признак бага. Бросать.
- **Ошибка программиста.** `null` там, где не должно, аргумент вне диапазона, вызов на освобождённом объекте. Бросать.
- **Невосстановимые сбои инфраструктуры.** База недоступна, диск не пишется, конфигурация битая. Бросать: обрабатывать это будет граница приложения или политика устойчивости.
- **Глубокий стек вызовов.** Если ошибка возникла на десять уровней ниже, а обрабатывается только на границе, протаскивание Result через все уровни — чистый шум. Исключение доставит её бесплатно.
- **Конструкторы и свойства.** Вернуть Result оттуда невозможно; остаётся исключение (или фабричный метод, возвращающий Result).

Практическое сочетание, которое работает: **Result для бизнес-исходов, исключения для сбоев и багов**. Тогда `catch` на границе означает именно «что-то сломалось», и его срабатывание можно считать сигналом для мониторинга.

> [!warning] Подводные камни
> - **Исключение в цикле.** Тысяча ожидаемых исключений в обработке пакета данных — это десятки миллисекунд накладных расходов и нечитаемые логи.
> - **`catch` как `if`.** `try { dict[key] } catch (KeyNotFoundException)` — самый частый пример; есть `TryGetValue`.
> - **Result везде, включая ошибки программиста.** `Result<Order>` с вариантом «аргумент был null» бессмысленен: это баг, его надо чинить, а не обрабатывать.
> - **`null` вместо причины.** Метод, возвращающий `null` и при «не найдено», и при «нет доступа», заставляет вызывающего гадать.
> - **Result, который никто не проверяет.** Если возвращаемое значение можно проигнорировать, толку от него мало; помогает `[MustUseReturnValue]`-подобные анализаторы или проверка на ревью.
> - **Смешение подходов в одном слое.** Половина методов бросает, половина возвращает Result — вызывающий не знает, чего ждать. Договорённость должна быть на уровне слоя.
> - **Исключения для передачи данных.** Использовать `Exception.Data` как канал возврата значений — злоупотребление, которое ломает диагностику.

> [!example] Как делают в бою
> Типичное разделение в сервисе на .NET: слой домена и приложения возвращает Result для всех бизнес-исходов («не найдено», «конфликт», «правило нарушено») и бросает исключения только при нарушении инвариантов; инфраструктурный слой пропускает исключения библиотек наверх, обернув их в свои типы; граница HTTP превращает Result в коды 200/400/404/409, а исключение — в 500 с идентификатором корреляции.
> Такое разделение даёт полезное свойство: **любое исключение, дошедшее до глобального обработчика, — это дефект**. По ним можно строить алерты, потому что там нет ожидаемых ситуаций. Пока «нет товара на складе» приходит исключением, отличить настоящую аварию от штатного отказа в мониторинге невозможно.
> Компромисс, который встречается чаще идеала: Result в новых модулях, исключения в старых. Это нормально, если граница между ними явная и каждый слой внутри себя последователен.

## Вопросы с собеседований

> [!question]- Почему исключения не стоит использовать для управления потоком?
> Три причины. Стоимость: бросок и обработка занимают десятки микросекунд против наносекунд у обычного возврата — создание объекта, захват стека, два прохода поиска обработчика; в цикле или на горячем пути это заметно. Читаемость: нормальный сценарий и обработка ошибок перемешиваются, а `catch` часто ловит шире, чем задумано, скрывая настоящие дефекты. Контракт: в C# нет проверяемых исключений, поэтому подпись метода не сообщает, что он может бросить, — вызывающий узнаёт об этом из документации или из инцидента, а компилятор не помогает. Практический критерий: если ситуация описана в требованиях («если товара нет — показать сообщение»), она ожидаема и должна быть выражена типом результата — `Try*`, nullable или Result. Исключения остаются для того, чего в требованиях нет: сбоев инфраструктуры и ошибок программиста.

> [!question]- Чем Result-подход лучше и хуже исключений?
> Лучше в четырёх вещах: все возможные исходы видны в сигнатуре метода, вызывающий не может о них не узнать; компилятор помогает при разборе через `switch`-выражение с проверкой полноты; нет накладных расходов на бросок и разворачивание стека; тесты пишутся проще, потому что проверяется возвращаемое значение, а не поведение с исключением. Хуже в трёх: больше кода (в C# нет union-типов, поэтому объявление вариантов многословно); результат нужно явно протаскивать через все уровни вызовов, что бессмысленно, если ошибка обрабатывается только на границе; и его можно молча проигнорировать, если нет анализатора, требующего использовать возвращаемое значение. Отсюда компромисс, принятый в большинстве команд: Result для бизнес-исходов, исключения для сбоев инфраструктуры и нарушений инвариантов.

> [!question]- Метод ищет запись по id. Что вернуть, если её нет?
> Зависит от того, что означает отсутствие. Если это ожидаемый исход поиска — вернуть `null` (при включённых nullable reference types компилятор заставит вызывающего проверить) и назвать метод по конвенции .NET: `Find*` или `*OrDefault` возвращает `null`, `Get*` бросает. Если у отсутствия могут быть разные причины — не найдено, нет доступа, удалено — `null` их не различает, и нужен Result с вариантами. Если запись обязана существовать по инварианту (например, ищем справочник, без которого система не работает), то это `Get*`, и бросить исключение правильно — продолжать всё равно нельзя. Чего делать не стоит: возвращать «пустой» объект-заглушку — он расползётся по системе и проявится позже в виде непонятных нулей и пустых строк.

## Задачи

### Задача 1. Переделать на ожидаемый исход

```csharp
public Order GetOrder(long id)
{
    var order = _db.Orders.Find(id);
    if (order is null) throw new Exception($"Заказ {id} не найден");
    if (order.IsDeleted) throw new Exception($"Заказ {id} удалён");
    return order;
}
```

Метод вызывается из эндпоинта, где «не найдено» — обычная ситуация (примерно 15 % запросов).

> [!success]- Решение
> ```csharp
> public enum OrderLookupError { NotFound, Deleted }
>
> public async Task<Result<Order, OrderLookupError>> FindOrderAsync(long id, CancellationToken ct)
> {
>     var order = await _db.Orders.FindAsync([id], ct);
>     if (order is null) return OrderLookupError.NotFound;
>     if (order.IsDeleted) return OrderLookupError.Deleted;
>     return order;
> }
>
> // На границе
> return await FindOrderAsync(id, ct) switch
> {
>     { IsSuccess: true, Value: var order } => Results.Ok(order),
>     { Error: OrderLookupError.NotFound } => Results.NotFound(),
>     { Error: OrderLookupError.Deleted } => Results.StatusCode(StatusCodes.Status410Gone),
>     _ => Results.Problem()
> };
> ```
> Что изменилось. Пятнадцать процентов запросов больше не бросают исключений — это и производительность, и чистый мониторинг: теперь исключение в логе означает настоящую аварию. Два разных исхода различимы и отображаются в разные HTTP-коды (404 и 410), тогда как раньше оба были `Exception` с текстом, который пришлось бы разбирать строкой. Метод переименован в `FindOrderAsync` по конвенции: `Find*` не бросает. Добавлен `CancellationToken`. Если бы отсутствие заказа было аварией (например, поиск идёт по идентификатору из только что созданной записи), исключение осталось бы правильным выбором.

### Задача 2. Решить, что использовать

Для каждого случая выбери механизм: исключение, `Try*`, `null` или Result.
1. Разбор даты из строки, введённой пользователем.
2. Списание со счёта при недостатке средств.
3. Получение обязательной настройки из конфигурации при старте.
4. Поиск товара в кеше.
5. Вызов внешнего платёжного шлюза, который вернул таймаут.

> [!success]- Решение
> 1. **`Try*`** — `DateTime.TryParse` с явной культурой и форматом. Ввод пользователя ожидаемо бывает некорректным, а причина неудачи не важна: нужен ответ 400 с понятным сообщением.
> 2. **Result** — недостаток средств это бизнес-исход, у него есть данные (сколько не хватает), и API должен вернуть 409 с деталями. Исключение здесь тоже встречается на практике (свой `InsufficientFundsException`) и допустимо, если правило нарушается редко и обрабатывается только на границе, — но Result честнее отражает, что это ожидаемый сценарий.
> 3. **Исключение** — при старте, без обязательной настройки продолжать нельзя. Приложение должно упасть громко и сразу, а не работать со значением по умолчанию, которое всплывёт через неделю.
> 4. **`null`** (или `TryGetValue`) — промах кеша это норма, а не ошибка; ни причина, ни диагностика не нужны, нужен просто путь «сходить в источник».
> 5. **Исключение** — сбой инфраструктуры, который обрабатывается политикой устойчивости: повтор с задержкой, затем разрыватель цепи, затем ответ 503. Заворачивать это в Result смысла нет: обработка происходит не в вызывающем методе, а в инфраструктурной обвязке.

## Итог

- Исключение — для неожиданного и необрабатываемого на месте; ожидаемое выражается типом результата.
- Критерий: если сценарий есть в требованиях, он не исключительный.
- Три альтернативы: `Try*` (нужен только факт успеха), nullable (одна причина), Result (несколько различимых исходов).
- Валидация никогда не делается исключениями: пользователю нужны все ошибки сразу.
- Исключения правильны для нарушенных инвариантов, ошибок программиста, сбоев инфраструктуры и битой конфигурации.
- Полезное свойство хорошего разделения: любое исключение на границе — это дефект, по нему можно строить алерты.
- Механизм должен быть единообразным внутри слоя, иначе вызывающий не знает, чего ждать.
