# Когда исключение — плохой выбор

> [!abstract] Коротко
> Исключение — для ситуации, которую вызывающий **не ожидал** и обычно не может обработать на месте. Всё, что происходит регулярно — товара нет, лимит исчерпан, запись не найдена, — нормальный исход, а не сбой, и должно быть выражено типом возвращаемого значения: `Try*`, nullable или Result. Guard clauses — отдельная техника: проверка предусловий в начале метода против ошибок программиста, а не против ожидаемого бизнес-ввода. Практическая граница простая: **если ситуация есть в требованиях, она не исключительная**.

## Зачем это знать

Исключение как способ вернуть ожидаемый результат создаёт три проблемы: бросок стоит десятки микросекунд против наносекунд у обычного `return`, подпись метода ничего не сообщает о возможном исключении (в C# нет проверяемых исключений), а код с логикой через `try/catch` тяжело читать — нормальный сценарий и обработка ошибок перемешаны. Отдельно нужно уметь отличать guard clause (защита от ошибки программиста) от валидации внешнего ввода (ожидаемый отказ) — их путают чаще всего, и рабочий проект показывает третий вариант: единый каталогизированный тип исключения вместо Result там, где книжный совет предлагает Result.

## Модель

### Ожидаемое или исключительное

| Вопрос | Ожидаемый исход | Исключение |
|---|---|---|
| Есть ли это в требованиях? | «если товара нет, показать…» | нет, это сбой |
| Как часто случается? | регулярно | редко, аварийно |
| Может ли вызывающий обработать? | да, и знает как | обычно нет |
| Виноват ли программист? | нет | часто да |

```csharp
// Так делать нельзя: «нет ключа» — обычный исход, а не сбой
try { var value = dictionary[key]; Use(value); }
catch (KeyNotFoundException) { UseDefault(); }

// Так правильно
if (dictionary.TryGetValue(key, out var value)) Use(value); else UseDefault();
```

### Guard clauses — техника, не альтернатива

Guard clause — проверка предусловия в начале метода с немедленным отказом. Смысл двойной: обнаружить проблему у источника (fail fast) и убрать вложенность — после серии проверок код идёт без отступов.

```csharp
public decimal Calculate(Order? order)
{
    ArgumentNullException.ThrowIfNull(order);
    if (order.Items.Count == 0) return 0;
    if (order.Status == OrderStatus.Cancelled) return 0;

    return order.Items.Sum(i => i.Price);
}
```

Готовые помощники .NET 6–8 (`ArgumentNullException.ThrowIfNull`, `ArgumentException.ThrowIfNullOrWhiteSpace`, `ArgumentOutOfRangeException.ThrowIfNegative`, `ObjectDisposedException.ThrowIf`) используют `[CallerArgumentExpression]` — имя параметра подставляется автоматически и не рассинхронизируется при переименовании.

Где проверять — работающее правило: **на границах**, а не везде.

| Граница | Что проверять | Чем |
|---|---|---|
| Публичный API, точка входа | все аргументы | guard-выражения → исключение |
| HTTP-эндпоинт | всю входящую модель | валидация → 400, не исключение |
| Конструктор доменного типа | инварианты типа | исключение при создании |
| Приватные методы модуля | ничего или `Debug.Assert` | доверяем вызывающему коду |

Тип, который невозможно создать в некорректном состоянии (обязательные поля в конструкторе, `Money`/`Email` как value object), убирает проверки из всех остальных методов — это и есть настоящая защита, а не разбросанные `if`.

Fail fast работает и на уровне приложения: конфигурация должна проверяться при старте (`ValidateOnStart`), а не при первом использовании — упасть на деплое лучше, чем через сутки в проде с половинчатым состоянием.

### Guard или валидация

| | Guard | Валидация |
|---|---|---|
| Против чего | ошибка программиста | некорректные данные пользователя |
| Кто виноват | вызывающий код | внешний ввод |
| Что делать | бросить исключение | вернуть список ошибок |
| Сколько ошибок | первая же прерывает | нужны все сразу |

### Три альтернативы исключению

**`Try*`** — узнаваемая идиома BCL, нулевая стоимость, но только «получилось или нет», причина не переносится:

```csharp
public bool TryGetDiscount(long customerId, out decimal discount)
{
    discount = 0;
    var customer = _cache.Get(customerId);
    if (customer is null) return false;
    discount = customer.IsVip ? 0.1m : 0m;
    return true;
}
```

**Nullable-результат** — простейшая форма, компилятор (при включённых NRT) заставит проверить, но `null` не объясняет причину:

```csharp
public async Task<Order?> FindAsync(long id, CancellationToken ct)
    => await _db.Orders.FirstOrDefaultAsync(o => o.Id == id, ct);
```

**Result-тип** — все исходы видны в сигнатуре, компилятор проверяет полноту `switch`, нулевая стоимость; минус — многословность без union-типов в C#:

```csharp
public abstract record Result<T>
{
    public sealed record Ok(T Value) : Result<T>;
    public sealed record NotFound(string Message) : Result<T>;
    public sealed record Conflict(string Code, string Message) : Result<T>;
}
```

Подробная реализация паттерна — [[Result pattern вместо исключений]]. Соглашение об именовании из .NET: `Find*`/`*OrDefault` возвращает `null`, `Get*` бросает, если не нашёл.

### Где исключение остаётся правильным выбором

- Нарушение инварианта внутри домена или ошибка программиста (`null` там, где не должно, аргумент вне диапазона) — признак бага, а не аккуратный исход.
- Невосстановимый сбой инфраструктуры — база недоступна, конфигурация битая.
- Глубокий стек вызовов, где ошибка обрабатывается только на границе, — протаскивать Result через десять уровней ради этого бессмысленно.
- Конструкторы и свойства — вернуть Result оттуда невозможно.

Рабочее сочетание: **Result для бизнес-исходов, исключения для сбоев и багов**. Тогда `catch` на границе означает именно «что-то сломалось».

## Решения

| Ситуация | Механизм | Почему |
|---|---|---|
| Строка не разобралась в число | `Try*` | причина не важна, нужен факт успеха |
| Записи с таким id нет, причина одна | `null` / `Find*` | простейшая форма, конвенция именования видна по сигнатуре |
| Товара не хватает на складе, есть данные об исходе | Result или единый доменный тип с кодом | нужен 409 с деталями, а не текст сообщения |
| Аргумент `null` там, где нельзя | guard → исключение | это ошибка вызывающего, а не бизнес-исход |
| Внешний сервис недоступен | исключение + политика повтора | обрабатывается не вызывающим методом, а инфраструктурной обвязкой |
| Битая конфигурация при старте | исключение | продолжать нельзя, лучше упасть на деплое |
| Пользовательский ввод с несколькими ошибками | валидация → список ошибок | нужны все ошибки сразу, а не по одной |

> [!example] В ServiceShop
> Домен не возвращает `Result<T>` для бизнес-правил — он бросает единственный каталогизированный тип `BusinessRuleValidationException`: `Entity.CheckRuleAsync` проверяет `IBusinessRule.IsBrokenAsync()` и при нарушении бросает именно его, а не произвольный `Exception` на каждое правило (~30 классов правил в `Orders.Domain/Order/BusinessRules/`, каждый со своим текстом и опциональным кодом через `IBusinessRuleWithCode`). В `Startup.cs` этот один тип маппится в предсказуемый `ProblemDetails`-ответ. Это компромисс между книжным Result и голыми исключениями: механизм технически бросает, но ведёт себя как Result на границе — единая точка перехвата, различимый код ошибки, предсказуемый HTTP-статус, а не поиск нужного `catch` среди тридцати типов. Guard clauses в конструкторах агрегатов используются как обычно — для инвариантов, которые не являются бизнес-правилом (например, `ArgumentNullException.ThrowIfNull`), а `IsBrokenAsync` — именно для нарушений, о которых должен узнать клиент API. Подробнее — [[ServiceShop: домен и тактический DDD]].

> [!warning] Где ошибаются
> - **`catch` как `if`.** `try { dict[key] } catch (KeyNotFoundException)` вместо `TryGetValue` — самый частый пример.
> - **Guard вместо валидации.** Исключение на каждое некорректное поле формы — дорого, и пользователь видит ошибки по одной вместо всех сразу.
> - **Проверки везде, а не на границах.** Дублирование guard-выражений на каждом уровне вызова не повышает надёжность, а прячет логику под шумом.
> - **Result, который никто не проверяет.** Если возвращаемое значение можно молча проигнорировать, толку от него не больше, чем от исключения без `catch`.
> - **Агент часто:** заворачивает бизнес-логику в `try/catch` с проглатыванием исключения «для надёжности» вместо того, чтобы явно смоделировать ожидаемый исход через Result или guard — метод тихо возвращает успех при непройденной проверке. Подробнее — [[Типовые ошибки агентов в .NET-коде]].

## Проверка на ревью

- Метод, где отказ ожидаем (не найдено, недостаточно средств), не бросает исключение — возвращает `null`/Result/`bool`.
- В `catch` нет условной логики вида `if (...) throw;` там, где мог бы стоять фильтр `when` или guard в начале метода.
- Guard-проверки — в начале публичных методов и конструкторов, а не разбросаны по приватным.
- Валидация внешнего ввода собирает все ошибки, а не бросает на первом же поле.
- В названии метода видна конвенция: `Find*`/`*OrDefault` не бросает, `Get*` может бросить.
- Единообразие внутри слоя: не половина методов бросает, а половина возвращает Result.

## Проверь себя

> [!question]- Почему исключения не стоит использовать для управления потоком?
> Три причины: стоимость (десятки микросекунд против наносекунд у `return`), читаемость (нормальный сценарий и обработка ошибок перемешиваются в `try/catch`) и контракт (в C# нет проверяемых исключений — подпись метода не сообщает, что он может бросить). Практический критерий: если ситуация описана в требованиях, она ожидаема и должна быть выражена типом результата.

> [!question]- В чём разница между guard clause и валидацией?
> Guard защищает от ошибки программиста — аргумент `null`, отрицательное количество; такое не должно случаться в корректной программе, и реакция — исключение на первой же проблеме. Валидация обрабатывает ожидаемо некорректные внешние данные — пользовательский ввод, тело запроса; реакция — собрать все ошибки и вернуть результат, а не бросить на первом поле. Guard живёт в начале методов и конструкторов, валидация — на границе системы.

> [!question]- Метод ищет запись по id. Что вернуть, если её нет?
> Зависит от смысла отсутствия. Если это обычный исход поиска — `null` (при NRT компилятор заставит проверить) и имя по конвенции `Find*`/`*OrDefault`. Если причин отсутствия несколько и их надо различать — Result с вариантами. Если запись обязана существовать по инварианту — это `Get*`, и бросить исключение правильно, потому что продолжать всё равно нельзя. Пустой объект-заглушка вместо явного отсутствия — худший вариант: он расползётся по системе и проявится позже непонятными нулями.

> [!question]- Почему в ServiceShop бизнес-правила бросают исключение, а не возвращают Result, хотя это ожидаемый бизнес-исход?
> Потому что механизм каталогизирован под один тип: `BusinessRuleValidationException` бросается всегда одним и тем же классом с кодом и сообщением, а не набором разных `Exception`. На границе HTTP это даёт то же свойство, что и Result, — предсказуемое отображение в `ProblemDetails` без разбора десятков типов в `catch`. Это не идеальный вариант с точки зрения сигнатуры метода (она не показывает возможность отказа), но на практике работает, потому что весь домен следует одному соглашению.

## Разбор

### Найди проблему

```csharp
public Order GetOrder(long id)
{
    var order = _db.Orders.Find(id);
    if (order is null) throw new Exception($"Заказ {id} не найден");
    if (order.IsDeleted) throw new Exception($"Заказ {id} удалён");
    return order;
}
```

Метод вызывается из эндпоинта, где «не найдено» — обычная ситуация (около 15% запросов).

> [!success]- Решение
> Пятнадцать процентов запросов не должны бросать исключение — это и производительность, и чистый мониторинг: исключение в логе перестаёт означать настоящую аварию. Нужен Result с различимыми исходами и переименование по конвенции (`Find*` не бросает):
> ```csharp
> public enum OrderLookupError { NotFound, Deleted }
>
> public async Task<Result<Order, OrderLookupError>> FindOrderAsync(long id, CancellationToken ct)
> {
>     var order = await _db.Orders.FindAsync([id], ct);
>     if (order is null) return OrderLookupError.NotFound;
>     if (order.IsDeleted) return OrderLookupError.Deleted;
>     return order;
> }
> ```
> На границе `NotFound` → 404, `Deleted` → 410 — раньше оба были голым `Exception` с текстом, который пришлось бы разбирать строкой.

### Ревью PR агента

Агент реализовал списание со счёта: guard-проверки на `null` и отрицательную сумму в начале метода — на месте, но при недостатке средств метод ловит собственное же исключение `InsufficientFundsException` внутри `try/catch` и возвращает `false`, логируя ошибку как `Error`.

> [!success]- Решение
> Вернуть на доработку по двум пунктам. Во-первых, `catch` собственного типа сразу после `throw` в том же методе — не обработка, а обфускация: проще сразу проверить условие `if (account.Balance < amount)` и вернуть Result/`false`, не создавая и не бросая исключение вовсе. Во-вторых, недостаток средств — ожидаемый бизнес-исход (пользователь регулярно пытается снять больше, чем есть), а не сбой: логировать его как `Error` зашумляет мониторинг, по которому потом ищут настоящие аварии. Guard-проверки на `null` и отрицательную сумму оставить как есть — это защита от ошибки программиста, и там исключение уместно.

## Итог

- Исключение — для неожиданного и необрабатываемого на месте; ожидаемое выражается типом результата (`Try*`, nullable, Result).
- Критерий: если сценарий есть в требованиях, он не исключительный.
- Guard clause — защита от ошибки программиста в начале метода; валидация — обработка ожидаемо некорректного внешнего ввода со сбором всех ошибок.
- Лучшая защита — тип, который невозможно создать в некорректном состоянии; тогда проверки исчезают из остальных методов.
- Исключения остаются правильным выбором для инвариантов, ошибок программиста, сбоев инфраструктуры и битой конфигурации при старте.
- ServiceShop показывает жизнеспособный средний вариант: не Result, а один каталогизированный тип исключения с кодом — если весь домен следует этому соглашению одинаково.
