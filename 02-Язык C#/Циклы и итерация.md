# Циклы и итерация

> [!abstract] Коротко
> В C# четыре цикла: `for` (когда важен индекс или счётчик), `foreach` (когда важны элементы), `while` (когда число итераций неизвестно) и `do-while` (когда тело обязано выполниться хотя бы раз). Главное, что стоит понять один раз, — во что компилятор разворачивает `foreach`: это не магия, а вызов `GetEnumerator()` и цикл по `MoveNext()`/`Current`, распознаваемый по форме, а не по интерфейсу. Отсюда следуют и производительность, и ограничения (нельзя менять коллекцию во время обхода), и то, почему `foreach` по `Span<T>` не делает аллокаций.

## Зачем это нужно

Цикл — самая горячая конструкция в любом коде: то, что внутри цикла, выполняется в тысячи раз чаще того, что снаружи. Три практических следствия:

- ошибка в границах (`<` вместо `<=`) — самый частый баг после `null`;
- лишняя работа внутри цикла — самый частый источник деградации производительности (запрос к БД, `Count()`, конкатенация строк);
- неверный выбор конструкции делает код нечитаемым: `for` там, где нужен `foreach`, или ручной цикл там, где нужен LINQ.

## Четыре формы

```csharp
// for — известное число итераций, нужен индекс
for (int i = 0; i < items.Length; i++)
    Console.WriteLine($"{i}: {items[i]}");

// foreach — обход элементов, индекс не нужен
foreach (var item in items)
    Console.WriteLine(item);

// while — условие проверяется перед итерацией, может не выполниться ни разу
while (queue.Count > 0)
    Process(queue.Dequeue());

// do-while — тело выполняется минимум один раз
string? input;
do
{
    Console.Write("Введите команду: ");
    input = Console.ReadLine();
} while (input is not "exit");
```

Правило выбора: **`foreach` по умолчанию**, `for` — когда нужен индекс, обратный порядок или изменение коллекции по позиции, `while` — когда условие не сводится к счётчику (чтение потока, опрос, обход дерева со стеком), `do-while` — редко, в основном для меню и повторного ввода.

### Составные части `for`

```csharp
// Все три секции опциональны
for (;;) { break; }                        // бесконечный цикл, эквивалент while(true)

// Несколько переменных и несколько изменений
for (int i = 0, j = items.Length - 1; i < j; i++, j--)
    (items[i], items[j]) = (items[j], items[i]);   // разворот массива на месте

// Обратный порядок — обязателен при удалении по индексу
for (int i = list.Count - 1; i >= 0; i--)
    if (list[i].IsExpired)
        list.RemoveAt(i);
```

### `break`, `continue` и `goto`

```csharp
foreach (var order in orders)
{
    if (order.IsCancelled) continue;    // к следующей итерации
    if (order.Total > limit) break;     // выйти из цикла
    Process(order);
}

// Выход из вложенного цикла: break выходит только из своего
foreach (var row in matrix)
{
    foreach (var cell in row)
        if (cell < 0) goto found;       // единственное оправданное применение goto
}
Console.WriteLine("не найдено");
return;
found:
Console.WriteLine("найдено отрицательное значение");
```

`goto` в C# существует, но в реальном коде его почти нет: вместо выхода из вложенных циклов метод выделяют отдельно и делают `return`, а в `switch` вместо `goto case` пишут паттерны. Единственное живое применение — `goto case` в разборе состояний и выход из глубокой вложенности в производительно-критичном коде.

## Во что разворачивается foreach

Это ключевое место темы. `foreach` — синтаксический сахар, и компилятор ищет **не интерфейс, а форму** (pattern-based): тип должен иметь публичный метод `GetEnumerator()`, возвращающий что-то с `MoveNext()` и `Current`.

```csharp
foreach (var item in collection)
    Use(item);

// Компилятор разворачивает примерно в это:
var enumerator = collection.GetEnumerator();
try
{
    while (enumerator.MoveNext())
    {
        var item = enumerator.Current;
        Use(item);
    }
}
finally
{
    // если перечислитель реализует IDisposable — освободить
    (enumerator as IDisposable)?.Dispose();
}
```

Из этого разворачивания следует всё остальное:

1. **`IEnumerable` не обязателен.** Можно сделать `foreach` по своему типу, просто добавив `GetEnumerator()`. Более того, `GetEnumerator()` можно добавить и extension-методом (C# 9) — так работает `foreach` по `Range` в некоторых библиотеках.
2. **Перечислитель может быть структурой.** У `List<T>`, массива, `Dictionary<K,V>` перечислители — структуры, поэтому обход не делает аллокации в куче. Но если тот же список обходить через `IEnumerable<T>`, перечислитель упакуется — вот почему `foreach` по `List<T>` быстрее, чем по `IEnumerable<T>`, содержащему тот же список.
3. **Есть `try/finally`.** Именно поэтому `foreach` корректно завершает итераторы с `yield return` и закрывает `SqlDataReader` — см. [[IEnumerable, IEnumerator и yield return]].
4. **`Span<T>` и `ref struct` тоже работают**, хотя они не могут реализовывать интерфейсы: pattern-based подход это позволяет.

```csharp
// Для массивов компилятор идёт дальше: разворачивает foreach в индексный цикл,
// потому что знает форму массива. Поэтому for и foreach по массиву
// дают почти одинаковый машинный код.
int[] numbers = [1, 2, 3];
foreach (var n in numbers) { }   // внутри — обычный i < numbers.Length
```

### Переменная цикла в `foreach` — только для чтения

```csharp
foreach (var item in list)
{
    // item = newValue;         // Ошибка CS1656: переменную итерации менять нельзя
    item.Property = 5;          // а вот менять СОСТОЯНИЕ объекта можно — если это класс
}

// Для структур в List<T> изменение не будет видно вообще:
// foreach отдаёт копию значения. Нужен индексный доступ:
for (int i = 0; i < points.Count; i++)
{
    var p = points[i];
    p.X = 10;
    points[i] = p;              // обратная запись обязательна
}

// Для массива структур можно взять ссылку (C# 7.3+ / Span):
foreach (ref var p in points.AsSpan())
    p.X = 10;                   // изменение на месте, без копий
```

## Модификация коллекции во время обхода

```csharp
var list = new List<int> { 1, 2, 3 };
foreach (var x in list)
{
    if (x == 2) list.Remove(x);   // InvalidOperationException:
                                  // Collection was modified; enumeration operation may not execute
}
```

Причина: перечислитель `List<T>` хранит счётчик версий коллекции и сверяет его на каждом `MoveNext()`. Это не вредность, а защита: без неё обход после сдвига элементов давал бы пропуски и дубликаты — то есть тихую порчу данных вместо исключения.

Правильные варианты:

```csharp
list.RemoveAll(x => x == 2);                    // лучший вариант: один проход
foreach (var x in list.ToList()) { }            // обход копии, если менять надо внутри
for (int i = list.Count - 1; i >= 0; i--) { }   // обратный индексный цикл
```

Отдельно про словари: `Dictionary<K,V>` с .NET Core 3.0 разрешает **удаление** по ключу во время обхода (перечислитель это переживает), но добавление по-прежнему бросает исключение. Полагаться на это в коде, который читают другие, всё равно не стоит: `ConcurrentDictionary` и полный проход по копии понятнее.

## Замыкание переменной цикла

Классическая ловушка, которая изменилась в C# 5:

```csharp
var actions = new List<Action>();

for (int i = 0; i < 3; i++)
    actions.Add(() => Console.Write(i));       // ОДНА переменная i, захвачена по ссылке
foreach (var a in actions) a();                // Вывод: 333

actions.Clear();
foreach (var i in Enumerable.Range(0, 3))
    actions.Add(() => Console.Write(i));       // переменная foreach — НОВАЯ на каждой итерации
foreach (var a in actions) a();                // Вывод: 012
```

В `for` переменная объявлена один раз на весь цикл, поэтому все лямбды видят её финальное значение. В `foreach` до C# 5 было то же поведение; его изменили именно потому, что оно ломало интуицию. Лечение для `for` — копия внутри тела:

```csharp
for (int i = 0; i < 3; i++)
{
    int captured = i;                          // своя переменная на итерацию
    actions.Add(() => Console.Write(captured));
}
```

Та же ошибка регулярно встречается с `Task.Run` в цикле — и там она проявляется как случайные значения из-за конкурентности. Подробно про захват — [[Локальные функции и замыкания]].

## Цикл или LINQ

```csharp
// Цикл: понятен, но многословен
var expensive = new List<Order>();
foreach (var o in orders)
    if (o.Total > 1000)
        expensive.Add(o);

// LINQ: короче и декларативнее
var expensive2 = orders.Where(o => o.Total > 1000).ToList();
```

Выбор не про «правильно/неправильно», а про контекст:

| | Цикл | LINQ |
|---|---|---|
| Читаемость фильтра/проекции | хуже | лучше |
| Сложная логика с несколькими условиями и состоянием | лучше | хуже |
| Аллокации | минимум | делегаты, промежуточные перечислители |
| Раннее прерывание | `break` | `First`, `Any`, `Take` |
| Горячий путь (миллионы итераций) | предпочтителен | заметны накладные расходы |
| Работа с БД | не применим | `IQueryable` транслируется в SQL |

Практика: LINQ по умолчанию для читаемости, ручной цикл — в горячем коде и там, где логика не выражается цепочкой. Что именно стоит LINQ в аллокациях — [[LINQ: производительность и аллокации]].

### Индекс при обходе

```csharp
// Классика
int index = 0;
foreach (var item in items) { Use(index++, item); }

// .NET 9+: Index() возвращает кортежи (Index, Item)
foreach (var (i, item) in items.Index())
    Console.WriteLine($"{i}: {item}");

// Для списка и массива проще обычный for
for (int i = 0; i < items.Count; i++)
    Console.WriteLine($"{i}: {items[i]}");
```

## Производительность циклов

Три факта, которые объясняют большинство замеров:

**1. Проверка границ и её устранение.** Каждое обращение `array[i]` в C# проверяет диапазон. Но JIT умеет доказывать безопасность и убирать проверку — в частности, для канонической формы `for (int i = 0; i < array.Length; i++)`. Поэтому кешировать длину в переменную (`int len = array.Length`) не только бесполезно, но иногда вредно: JIT теряет связь между условием и массивом.

**2. Локальность данных.** Обход подряд лежащих данных в разы быстрее обхода по ссылкам. Массив против `LinkedList`, обход двумерного массива по строкам против столбцов — всё это про кеш, см. [[Как работает компьютер: процессор, память, ОС]].

**3. Работа внутри цикла важнее самого цикла.** Вынести инвариант за пределы цикла — обычно единственная нужная оптимизация:

```csharp
// Плохо: Count() перечисляет источник на КАЖДОЙ итерации
for (int i = 0; i < source.Count(); i++) { }

// Плохо: запрос к БД внутри цикла (проблема N+1)
foreach (var id in ids)
    result.Add(await db.Orders.FirstAsync(o => o.Id == id));

// Плохо: компиляция регулярки на каждой итерации
foreach (var line in lines)
    if (Regex.IsMatch(line, @"^\d{4}-\d{2}-\d{2}")) { }

// Хорошо: инварианты вынесены
int count = source.Count;
var orders = await db.Orders.Where(o => ids.Contains(o.Id)).ToListAsync();
var dateRegex = MyRegexes.IsoDate;   // сгенерированная [GeneratedRegex]
```

> [!warning] Подводные камни
> - **Off-by-one.** `i <= array.Length` даёт `IndexOutOfRangeException` на последней итерации. Индексы — от 0 до `Length - 1`.
> - **Модификация коллекции внутри `foreach`.** Даёт `InvalidOperationException` — и это лучшее, что могло произойти; без проверки версии были бы пропущенные элементы.
> - **Захват переменной `for` в лямбде.** Все делегаты увидят финальное значение. Копия внутри тела решает.
> - **Двойное перечисление `IEnumerable`.** `if (source.Any()) foreach (var x in source)` перечисляет источник дважды; для отложенного запроса это два обращения к БД. Материализуй один раз через `ToList()`.
> - **Изменение структуры через переменную `foreach`.** Меняется копия, исходная коллекция не затронута, компилятор молчит — если это `List<T>`, поймёшь только по отсутствию эффекта.
> - **Бесконечный цикл без условия выхода по времени.** `while (!done)` в фоновой службе без `CancellationToken` не даёт приложению завершиться: `SIGTERM` придёт, а цикл продолжит работу до принудительного убийства.
> - **`for` по `double`.** `for (double d = 0; d != 1.0; d += 0.1)` не завершится: 0,1 не представима точно, равенства не случится. Считать надо целыми шагами.

> [!example] Как делают в бою
> В прикладном коде почти весь обход коллекций — `foreach` или LINQ. Ручные индексные циклы остаются в трёх местах: работа с `Span<T>`/буферами, обход с удалением по позиции и горячие участки, подтверждённые бенчмарком.
> Фоновые службы пишут циклом с токеном отмены, а не `while (true)`:
> ```csharp
> while (!stoppingToken.IsCancellationRequested)
> {
>     await ProcessBatchAsync(stoppingToken);
>     await Task.Delay(TimeSpan.FromSeconds(5), stoppingToken);
> }
> ```
> Так служба корректно останавливается по `SIGTERM` и не удерживает завершение приложения — см. [[Background services и IHostedService]].
> Отдельная привычка на ревью: увидел `await` внутри `foreach` — проверь, обязательна ли последовательность. Если операции независимы, это `Task.WhenAll` и десятикратное ускорение; если зависимы или нагружают внешнюю систему, последовательность оправдана и должна быть очевидна из кода.

## Вопросы с собеседований

> [!question]- Во что компилятор разворачивает `foreach`?
> В вызов `GetEnumerator()` и цикл `while (enumerator.MoveNext())` с чтением `enumerator.Current`, обёрнутый в `try/finally`, где в `finally` вызывается `Dispose()`, если перечислитель освобождаемый. Важная деталь: компилятор ищет не интерфейс `IEnumerable`, а **форму** — публичный `GetEnumerator()` с подходящими членами, поэтому `foreach` работает по `Span<T>` и `ref struct`, которые не могут реализовывать интерфейсы, а также по любому своему типу с одним методом. Для массивов и `string` компилятор идёт дальше и генерирует прямой индексный цикл. Практическое следствие: у `List<T>` перечислитель — структура, обход не аллоцирует; но при обходе через `IEnumerable<T>` он упаковывается, и появляется аллокация и виртуальные вызовы.

> [!question]- Почему нельзя изменять коллекцию во время `foreach`?
> Перечислитель `List<T>` (и большинства коллекций) хранит номер версии коллекции, снятый при создании, и сверяет его на каждом `MoveNext()`; любое изменение увеличивает версию, и обход падает с `InvalidOperationException`. Смысл в том, что при вставке или удалении элементы сдвигаются, и продолжение обхода по сохранённому индексу пропускало бы элементы или возвращало бы их дважды — то есть давало бы тихо неверный результат вместо явной ошибки. Обходные пути: собирать изменения и применять после цикла, обходить копию (`ToList()`), использовать `RemoveAll` с предикатом, идти индексным циклом в обратном порядке. Исключение: `Dictionary<K,V>` с .NET Core 3.0 допускает удаление по ключу во время обхода, добавление — по-прежнему нет.

> [!question]- В чём разница между `for` и `foreach` по производительности?
> Для массива разницы практически нет: компилятор разворачивает `foreach` в индексный цикл, а JIT в обоих случаях устраняет проверку границ. Для `List<T>` `foreach` немного дороже из-за вызовов `MoveNext`/`Current` (обычно они инлайнятся) и проверки версии; индексный доступ чуть быстрее, но разница видна только в микробенчмарках. Существенная разница появляется в двух случаях: обход через интерфейс `IEnumerable<T>` — там перечислитель упаковывается, добавляются аллокация и виртуальные вызовы; и обход `Span<T>` — там `foreach` работает по ссылкам и не копирует элементы. Общий вывод: выбирать между `for` и `foreach` надо по читаемости, а не по скорости, и оптимизировать содержимое цикла, а не его форму.

> [!question]- Почему все лямбды, созданные в цикле `for`, печатают одно значение?
> Потому что переменная цикла в `for` объявляется один раз на весь цикл, и лямбда захватывает **саму переменную**, а не её значение: компилятор поднимает её в поле класса замыкания, и все делегаты ссылаются на одно поле. К моменту вызова цикл завершён, и в поле лежит финальное значение. В `foreach` переменная итерации логически новая на каждой итерации (это изменили в C# 5 именно из-за постоянных ошибок), поэтому там каждая лямбда получает своё замыкание. Лечение для `for` — объявить локальную копию внутри тела цикла и захватывать её. Тот же баг особенно коварен с `Task.Run` в цикле, где к неверному значению добавляется недетерминированность.

## Задачи

### Задача 1. Найти три ошибки

```csharp
static List<string> GetActiveNames(List<User> users)
{
    var names = new List<string>();
    for (int i = 0; i <= users.Count; i++)
    {
        if (!users[i].IsActive)
            users.Remove(users[i]);
        else
            names.Add(users[i].Name);
    }
    return names;
}
```

> [!success]- Решение
> Ошибки: `i <= users.Count` выходит за границы; удаление элементов во время обхода по возрастающему индексу пропускает элементы (после `Remove` следующий сдвигается на место текущего, а `i` всё равно увеличивается); смешивание двух задач — фильтрации списка и сбора имён — в одном цикле.
> ```csharp
> static List<string> GetActiveNames(List<User> users)
> {
>     var names = users.Where(u => u.IsActive).Select(u => u.Name).ToList();
>     users.RemoveAll(u => !u.IsActive);     // если изменение исходного списка действительно нужно
>     return names;
> }
> ```
> Отдельно стоит спросить себя, нужна ли вообще мутация входного параметра: метод с именем `GetActiveNames`, который вдобавок вычищает переданный список, — сюрприз для вызывающего. Чаще правильнее не менять аргумент, а вернуть новую коллекцию.

### Задача 2. Отложенные действия

```csharp
var actions = new List<Action>();
for (int i = 0; i < 3; i++)
    actions.Add(() => Console.Write(i));
foreach (var a in actions) a();
```

Что выведет и как сделать, чтобы вывелось `012`?

> [!success]- Решение
> Выведет `333`. Переменная `i` одна на весь цикл, лямбды захватили её саму; после завершения цикла в ней 3.
> ```csharp
> for (int i = 0; i < 3; i++)
> {
>     int captured = i;                       // новая переменная на каждой итерации
>     actions.Add(() => Console.Write(captured));
> }
> // Или через foreach, где переменная итерации уже новая на каждом шаге:
> foreach (var i in Enumerable.Range(0, 3))
>     actions.Add(() => Console.Write(i));
> ```
> Механика: компилятор создаёт класс замыкания и поднимает захваченную переменную в его поле. Одна переменная — один экземпляр класса на весь цикл; переменная внутри тела — новый экземпляр на итерацию. Это же объясняет, почему захват в цикле создаёт аллокации: их столько же, сколько итераций.

### Задача 3. Ускорить обход

Метод ищет заказы, у которых есть хотя бы одна позиция из списка запрещённых товаров. Заказов 50 000, позиций в заказе до 20, запрещённых товаров 3 000.

```csharp
static List<Order> FindBlocked(List<Order> orders, List<int> blockedProductIds)
{
    var result = new List<Order>();
    foreach (var order in orders)
        foreach (var item in order.Items)
            if (blockedProductIds.Contains(item.ProductId))
            {
                result.Add(order);
                break;
            }
    return result;
}
```

> [!success]- Решение
> `blockedProductIds.Contains` для `List<int>` — линейный поиск, то есть до 3 000 сравнений на каждую позицию каждого заказа: 50 000 × 20 × 3 000 = 3 миллиарда операций в худшем случае.
> ```csharp
> static List<Order> FindBlocked(List<Order> orders, List<int> blockedProductIds)
> {
>     var blocked = new HashSet<int>(blockedProductIds);          // O(m), один раз
>     var result = new List<Order>();
>     foreach (var order in orders)
>         if (order.Items.Any(i => blocked.Contains(i.ProductId))) // O(1) на проверку
>             result.Add(order);
>     return result;
> }
> ```
> Стало 50 000 × 20 проверок по хеш-множеству — миллион дешёвых операций вместо трёх миллиардов. `Any` заодно убирает ручной `break`: он сам прекращает перечисление на первом совпадении. Ключевое — построить множество **до** цикла: та же строка внутри цикла вернула бы квадратичность обратно. Подробнее о выборе структуры — [[Введение в алгоритмы: сложность и Big-O]].

## Итог

- `foreach` по умолчанию, `for` — когда нужен индекс или обратный порядок, `while` — когда условие не счётчик.
- `foreach` разворачивается в `GetEnumerator()` + `MoveNext()`/`Current` в `try/finally`; компилятор ищет форму, а не интерфейс — поэтому работает и по `Span<T>`.
- Обход через `IEnumerable<T>` упаковывает перечислитель-структуру: в горячем коде это заметно.
- Менять коллекцию во время обхода нельзя: проверка версии превращает тихую порчу данных в исключение.
- Переменная `for`, захваченная в лямбду, одна на весь цикл; переменная `foreach` — новая на итерацию.
- Оптимизировать надо содержимое цикла: инварианты, запросы к БД, компиляцию регулярок, а не форму цикла.
- Фоновые циклы пишутся с `CancellationToken`, иначе приложение не завершится корректно.
