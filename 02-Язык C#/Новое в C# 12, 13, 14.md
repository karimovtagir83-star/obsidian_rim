# Новое в C# 12, 13, 14

> [!abstract] Коротко
> Язык обновляется ежегодно вместе с .NET. C# 12 (.NET 8) дал первичные конструкторы и коллекционные выражения `[...]`, C# 13 (.NET 9) — коллекции в `params`, отдельный тип `Lock` и `ref struct` в дженериках, C# 14 (.NET 10) — ключевое слово `field`, extension members нового вида, null-условное присваивание и пользовательские операторы составного присваивания. Практическая ценность этой заметки — не «список фич», а понимание, что именно изменилось в **привычках**: как теперь пишут коллекции, свойства, конструкторы классов с зависимостями и методы расширения.

## Зачем это нужно

Две причины. Первая: читать чужой код. Свежие проекты и исходники .NET написаны в новом стиле, и конструкции вроде `[.. items, last]` или `extension(string s) { }` без знакомства выглядят как другой язык.

Вторая: не писать по-старому. Половина шаблонного кода, который раньше был неизбежен (поле + конструктор + присваивание, приватное backing-поле, `new List<T> { ... }`), теперь не нужна.

Целевая версия базы — **C# 14 в составе .NET 10 LTS**. Ниже — по версиям, с пометкой, что стоит применять сразу, а что редко.

## C# 12 (.NET 8)

### Первичные конструкторы для классов и структур

```csharp
// Было
public sealed class OrderService
{
    private readonly IOrderRepository _repository;
    private readonly ILogger<OrderService> _logger;

    public OrderService(IOrderRepository repository, ILogger<OrderService> logger)
    {
        _repository = repository;
        _logger = logger;
    }
}

// Стало
public sealed class OrderService(IOrderRepository repository, ILogger<OrderService> logger)
{
    public async Task<Order?> FindAsync(long id, CancellationToken ct)
    {
        logger.LogInformation("Поиск заказа {OrderId}", id);
        return await repository.GetAsync(id, ct);
    }
}
```

Параметры доступны во всём теле типа; компилятор создаёт скрытые поля только для тех, что реально используются. Отличия от `record`: свойства **не создаются**, `Equals`/`ToString` не генерируются.

Важная тонкость: параметры первичного конструктора **не `readonly`**, их можно переприсвоить внутри типа. Анализаторы это подсвечивают; если нужна гарантия неизменности — обычное `readonly`-поле. Применять стоит везде, где класс просто принимает зависимости.

### Коллекционные выражения и spread

```csharp
int[] array = [1, 2, 3];
List<string> list = ["a", "b"];
Span<int> span = [1, 2, 3];
HashSet<int> set = [1, 2, 3];
ImmutableArray<int> immutable = [1, 2, 3];

int[] head = [1, 2];
int[] tail = [5, 6];
int[] all = [..head, 3, 4, ..tail];        // spread: [1,2,3,4,5,6]

int[] empty = [];                           // компилятор подставит Array.Empty<int>()
```

Один синтаксис для всех коллекций, а способ создания выбирает компилятор — часто эффективнее ручного (для `Span<T>` может разместить на стеке, для пустого массива взять кешированный). Это новый стиль по умолчанию.

### Псевдоним любого типа, значения по умолчанию у лямбд, `ref readonly`

```csharp
using Coordinates = (double Lat, double Lon);       // раньше алиас работал только для типов
using Matrix = double[,];

var increment = (int value, int step = 1) => value + step;   // значение по умолчанию в лямбде
Console.WriteLine(increment(5));                              // 6

static void Process(ref readonly LargeStruct data) { }        // как in, но требует ref/in у вызова
```

Ещё в C# 12 появились **inline arrays** — структура с фиксированным буфером для высокопроизводительного кода; в прикладном коде почти не встречается.

## C# 13 (.NET 9)

### params с любыми коллекциями

```csharp
// Раньше params работал только с массивом — значит, аллокация на каждый вызов
static int Sum(params ReadOnlySpan<int> numbers)      // теперь можно без кучи
{
    int total = 0;
    foreach (var n in numbers) total += n;
    return total;
}

static void Log(params IEnumerable<string> lines) { }  // и так тоже
Sum(1, 2, 3);                                          // значения могут лечь на стек
```

Именно поэтому в .NET 9/10 многие методы BCL получили перегрузки с `params ReadOnlySpan<T>`: вызовы вроде `string.Join` стали дешевле.

### Отдельный тип `Lock`

```csharp
// Было: блокировка по произвольному объекту
private readonly object _gate = new();
lock (_gate) { }

// Стало: специальный тип, оптимизированный рантаймом
private readonly System.Threading.Lock _gate = new();
lock (_gate) { }                       // компилятор вызывает _gate.EnterScope()
using (_gate.EnterScope()) { }         // эквивалентная явная форма
```

`Lock` быстрее классического монитора и делает намерение явным. Подробно — [[Примитивы синхронизации: lock, Monitor]].

### Прочее в C# 13

```csharp
char escape = '\e';                     // символ ESC (0x1B) — раньше писали ''

// Неявный доступ по индексу в инициализаторе объекта
var buffer = new Buffer { [^1] = 42 };

// ref struct теперь может реализовывать интерфейсы,
// а дженерик — объявить, что допускает ref struct:
static void Handle<T>(T value) where T : allows ref struct { }

// partial-свойства и partial-индексаторы: объявление в одном файле, реализация в другом
public partial class Model
{
    public partial string Name { get; set; }        // объявление — часто для генераторов
}

// [OverloadResolutionPriority] — способ подсказать компилятору предпочтительную перегрузку
```

Также в C# 13 разрешены `ref`-локальные переменные и `unsafe`-контексты в итераторах и `async`-методах (с ограничениями: их нельзя использовать через `await`/`yield`).

## C# 14 (.NET 10) — текущая версия

### Ключевое слово `field`

```csharp
// Было: ради одной проверки приходилось заводить поле руками
private string _name = "";
public string Name
{
    get => _name;
    set => _name = value?.Trim() ?? throw new ArgumentNullException(nameof(value));
}

// Стало: backing-поле доступно как field
public string Name
{
    get;
    set => field = value?.Trim() ?? throw new ArgumentNullException(nameof(value));
}

public int Count
{
    get => field;
    set => field = value < 0 ? 0 : value;     // нормализация без отдельного поля
}
```

`field` доступен внутри аксессора и ссылается на автоматически созданное поле. Убирает самый частый повод писать «полуавтоматическое» свойство. Осторожно: если в типе уже есть переменная с именем `field`, возникнет конфликт — компилятор предупредит.

### Extension members

```csharp
// Классические методы расширения (остаются и работают)
public static class OldExtensions
{
    public static bool IsBlank(this string? s) => string.IsNullOrWhiteSpace(s);
}

// C# 14: блок extension — можно объявлять свойства, статические члены и операторы
public static class StringExtensions
{
    extension(string source)
    {
        public bool IsBlank => string.IsNullOrWhiteSpace(source);      // extension-СВОЙСТВО
        public string Truncate(int max) => source.Length <= max ? source : source[..max];
    }

    extension(string)                                                   // статические члены
    {
        public static string Empty2 => "";
    }
}

Console.WriteLine("  ".IsBlank);              // True — обращение как к свойству
Console.WriteLine("длинный текст".Truncate(7));
```

Главное новшество — расширять можно не только методами: появились extension-свойства, статические extension-члены и extension-операторы. Подробно — [[Расширяющие методы и extension members]].

### Null-условное присваивание

```csharp
customer?.Order = newOrder;          // присвоить, только если customer не null
customer?.Total += 10;                // составные присваивания тоже работают
// customer?.Count++;                 // а инкремент и декремент НЕ поддерживаются

// Раньше это писалось так:
if (customer is not null) customer.Order = newOrder;
```

### Прочее в C# 14

```csharp
// nameof для несвязанных дженериков
Console.WriteLine(nameof(List<>));            // "List"
Console.WriteLine(nameof(Dictionary<,>));     // "Dictionary"

// Модификаторы у параметров лямбды без указания типа
var tryParse = (string s, out int value) => int.TryParse(s, out value);

// partial-конструкторы и partial-события (для генераторов исходного кода)

// Пользовательские операторы составного присваивания:
// раньше a += b всегда означало «вычислить a + b и присвоить»,
// теперь тип может определить += отдельно и изменять состояние на месте
public struct Accumulator
{
    private int _sum;
    public void operator +=(int value) => _sum += value;   // без создания нового значения
}
```

Плюс расширены неявные преобразования `Span<T>`/`ReadOnlySpan<T>`/`T[]`, что убирает часть явных `AsSpan()` в коде.

### Файловые приложения: `dotnet run app.cs`

.NET 10 SDK умеет запускать один файл `.cs` без проекта, а C# 14 добавил для этого директивы препроцессора:

```csharp
#!/usr/bin/env dotnet
#:package Humanizer@2.14.1
#:sdk Microsoft.NET.Sdk

Console.WriteLine("Скрипт на C# без csproj");
```

```bash
dotnet run script.cs
```

Полезно для утилит, экспериментов и обучения: пробовать конструкции языка теперь можно без создания проекта.

## Что применять сразу, а что редко

| Возможность | Версия | Насколько нужна в обычном коде |
|---|---|---|
| Коллекционные выражения `[...]`, spread | 12 | Всегда — новый стиль по умолчанию |
| Первичные конструкторы классов | 12 | Всегда для сервисов с зависимостями |
| `field` в свойстве | 14 | Часто — когда нужна нормализация или проверка |
| Extension-свойства и статические extension | 14 | По ситуации, но приятно для API |
| Null-условное присваивание | 14 | По ситуации |
| `Lock` вместо `object` | 13 | Всегда в новом многопоточном коде |
| `params ReadOnlySpan<T>` | 13 | В библиотеках и горячем коде |
| Псевдонимы любого типа | 12 | Редко, для читаемости |
| `allows ref struct`, inline arrays, `ref readonly` | 12–13 | Инфраструктурный и высокопроизводительный код |
| `partial`-свойства, конструкторы, события | 13–14 | Почти только для генераторов исходного кода |
| Пользовательские `+=` | 14 | Редко: буферы, аккумуляторы, математика |
| Файловые приложения `dotnet run app.cs` | 14 | Для скриптов и обучения |

> [!warning] Подводные камни
> - **Первичный конструктор не создаёт `readonly`-полей.** Параметр можно случайно переприсвоить внутри класса, и это не поймается компилятором.
> - **Первичный конструктор у `class` и у `record` — разные вещи.** У класса не будет ни свойств, ни равенства по значению; это регулярная путаница при чтении кода.
> - **Коллекционное выражение не всегда даёт ожидаемый тип.** `var x = [1,2,3];` не компилируется: у выражения нет собственного типа, он берётся из контекста.
> - **`field` конфликтует с переменной по имени `field`.** В старом коде такое встречается; лечится переименованием или `@field`.
> - **Смешение старого и нового стиля в одном проекте.** Читаемость страдает сильнее, чем выигрывает от новых конструкций. Стиль фиксируют в `.editorconfig` и мигрируют осознанно.
> - **Языковая версия зависит от TFM.** C# 14 доступен при `net10.0`; поднять `LangVersion` на старом таргете можно, но часть возможностей требует новых типов рантайма и не заработает.
> - **`Lock` — это тип из .NET 9+.** Если поле объявлено как `object`, `lock` работает по-старому: сначала меняется тип поля, потом появляется выигрыш.

> [!example] Как делают в бою
> Практическая линия миграции такая: новые файлы сразу пишутся в современном стиле (коллекционные выражения, первичные конструкторы, `field`, file-scoped namespace), старые не переписываются массово — только когда файл всё равно правится по задаче. Массовая «модернизация» одним коммитом ломает `git blame` и ревью, а пользы даёт мало.
> Из перечисленного реально меняет повседневный код три вещи: `[...]` вместо `new List<T> {...}`, первичные конструкторы в сервисах и `field` в свойствах с нормализацией. Остальное встречается точечно.
> Отдельно стоит следить за тем, чтобы новые возможности не превращались в загадки: `extension`-блоки и пользовательские `+=` мощны, но код с ними должен оставаться очевидным для того, кто увидит его впервые.

## Вопросы с собеседований

> [!question]- Чем первичный конструктор класса отличается от первичного конструктора record?
> Синтаксис одинаковый, семантика разная. У `record` позиционные параметры превращаются в публичные `init`-свойства, и вдобавок генерируются `Equals`, `GetHashCode`, `ToString`, `Deconstruct`, конструктор копирования и поддержка `with` — то есть получается полноценный тип-значение. У обычного `class` (и `struct`) первичный конструктор — это только параметры конструктора, доступные во всём теле типа: свойства не создаются, равенство остаётся по ссылке, `ToString` стандартный. Компилятор создаёт скрытые поля лишь для тех параметров, которые реально используются в теле. Ещё одно практическое отличие: параметры первичного конструктора класса не являются `readonly` — их можно переприсвоить внутри типа, поэтому там, где нужна гарантия неизменности, по-прежнему объявляют `readonly`-поле.

> [!question]- Что даёт ключевое слово `field` и зачем оно понадобилось?
> `field` внутри аксессора свойства ссылается на автоматически создаваемое backing-поле. До C# 14 добавление любой логики в сеттер (проверка, нормализация, обрезка пробелов) требовало вручную объявить приватное поле и написать оба аксессора целиком — то есть отказаться от автосвойства ради одной строки. С `field` можно оставить `get;` автоматическим и написать только нужный аксессор: `set => field = value?.Trim() ?? throw ...`. Это чисто синтаксическое удобство, никаких изменений в рантайме нет — генерируется то же самое поле. Единственная тонкость совместимости: если в области видимости уже есть идентификатор `field`, возникает конфликт, и его придётся переименовать или писать `@field`.

> [!question]- Что такое коллекционные выражения и почему они лучше инициализаторов?
> Коллекционное выражение — единый синтаксис `[a, b, c]` для создания массива, `List<T>`, `Span<T>`, `HashSet<T>`, `ImmutableArray<T>` и любого типа, поддерживающего построение коллекции; целевой тип берётся из контекста. Плюс оператор spread `..` для вставки содержимого другой коллекции. Преимущества перед `new List<T> { ... }` три: единообразие (одна форма записи вместо разных для каждого типа), краткость и то, что способ построения выбирает компилятор — он может использовать `Array.Empty<T>()` для пустой коллекции, разместить `Span<T>` на стеке или собрать `ImmutableArray<T>` через билдер без промежуточного списка. Ограничение: у выражения нет собственного типа, поэтому `var x = [1,2,3];` не компилируется — целевой тип должен быть известен из объявления, параметра или возвращаемого значения.

## Задачи

### Задача 1. Переписать в современном стиле

```csharp
public class ReportBuilder
{
    private readonly IClock _clock;
    private string _title;

    public ReportBuilder(IClock clock)
    {
        _clock = clock;
    }

    public string Title
    {
        get { return _title; }
        set { _title = value == null ? "" : value.Trim(); }
    }

    public List<string> GetDefaultSections()
    {
        var list = new List<string>();
        list.Add("Итоги");
        list.Add("Детали");
        return list;
    }
}
```

> [!success]- Решение
> ```csharp
> public sealed class ReportBuilder(IClock clock)
> {
>     public string Title
>     {
>         get;
>         set => field = value?.Trim() ?? "";
>     } = "";
>
>     public List<string> GetDefaultSections() => ["Итоги", "Детали"];
>
>     public DateTimeOffset Now => clock.UtcNow;
> }
> ```
> Что применено: первичный конструктор (C# 12) убрал поле и присваивание; `field` (C# 14) оставил геттер автоматическим и позволил написать только нужную логику сеттера; коллекционное выражение (C# 12) заменило создание списка и два `Add`; инициализатор `= ""` гарантирует непустое начальное значение при включённых nullable reference types. Класс помечен `sealed` — умолчание для типов, не рассчитанных на наследование.

### Задача 2. Что здесь не скомпилируется и почему

```csharp
var numbers = [1, 2, 3];
List<int> list = [1, 2, ..new[] { 3, 4 }];
customer?.Count++;
Console.WriteLine(nameof(Dictionary<,>));
```

> [!success]- Решение
> Первая строка не скомпилируется: у коллекционного выражения нет естественного типа, целевой тип должен быть известен из контекста. Нужно `int[] numbers = [1, 2, 3];` или `var numbers = new[] { 1, 2, 3 };`.
> Вторая строка корректна: spread работает с любой перечислимой коллекцией, результат — `List<int>` из четырёх элементов.
> Третья не скомпилируется: null-условное присваивание в C# 14 поддерживает `=` и составные операторы (`+=`, `-=` и другие), но не `++` и `--`. Писать надо `if (customer is not null) customer.Count++;`.
> Четвёртая корректна начиная с C# 14: `nameof` для несвязанного дженерика возвращает `"Dictionary"`.

## Итог

- C# 12: первичные конструкторы для классов, коллекционные выражения `[...]` со spread, псевдонимы любого типа, значения по умолчанию у лямбд.
- C# 13: `params` с любыми коллекциями (в том числе `ReadOnlySpan<T>`), тип `Lock`, `\e`, `ref struct` в дженериках и с интерфейсами, partial-свойства.
- C# 14: `field` в аксессорах, extension members нового вида, null-условное присваивание, `nameof` для несвязанных дженериков, пользовательские `+=`, файловые приложения.
- Меняют повседневный стиль в первую очередь три вещи: `[...]`, первичные конструкторы и `field`.
- Первичный конструктор класса не создаёт свойств и не даёт `readonly` — не путать с `record`.
- Мигрировать стоит по мере правки файлов, а не одним массовым коммитом.
