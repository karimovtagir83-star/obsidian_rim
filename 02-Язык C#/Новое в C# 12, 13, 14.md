# Новое в C# 12, 13, 14

> [!abstract] Коротко
> Три версии языка вышли подряд с тремя версиями .NET, но рабочий проект — `net8.0`, а это значит **только C# 12**. Первичные конструкторы и коллекционные выражения `[...]` — уже сегодняшний инструмент. `field`, extension members нового вида, null-условное присваивание `?.=`, `params` с `ReadOnlySpan<T>` и тип `Lock` — фичи C# 13/14, которые не скомпилируются на `net8.0` без явного риска. Агент, обученный на коде под .NET 9/10, эту границу не видит и путает версии постоянно.

## Зачем это знать

Обучающие данные агента смещены в сторону свежих статей и репозиториев на .NET 9/10, где C# 13/14 представлены гуще, чем в среднем `net8.0`-проекте — просто потому, что новые статьи пишут активнее старых. Итог предсказуем: агент предлагает `field`-аксессор или `customer?.Total += 10`, которые не существуют в проекте. Это первый по частоте паттерн из [[Типовые ошибки агентов в .NET-коде]] («версия вперёд репозитория»), и эта заметка — его разбор в деталях: что именно доступно, а что нет, и почему граница не всегда очевидна на глаз.

## Модель

### Что реально доступно в проекте: C# 12

`net8.0` собирается компилятором, который по умолчанию берёт `LangVersion 12`. Из нового в C# 12 в проекте можно и нужно применять уже сегодня:

```csharp
// Первичный конструктор — убирает поле + конструктор + присваивание
public sealed class OrderService(IOrderRepository repository, ILogger<OrderService> logger)
{
    public async Task<Order?> FindAsync(long id, CancellationToken ct)
    {
        logger.LogInformation("Поиск заказа {OrderId}", id);
        return await repository.GetAsync(id, ct);
    }
}
```

Важная тонкость: параметры первичного конструктора **не `readonly`** — их можно переприсвоить внутри типа, компилятор это не поймает. И у `class` первичный конструктор — не то же самое, что у `record`: свойства не создаются, `Equals`/`ToString` не генерируются.

```csharp
int[] head = [1, 2];
int[] tail = [5, 6];
int[] all = [..head, 3, 4, ..tail];   // spread: [1,2,3,4,5,6]
List<string> empty = [];              // компилятор выберет эффективный способ создания
```

Коллекционные выражения — единый синтаксис для массива, `List<T>`, `HashSet<T>`, `Span<T>`, `ImmutableArray<T>`; способ создания выбирает компилятор, а не программист.

Ещё в C# 12, но реже нужны в прикладном коде: алиас `using Coordinates = (double Lat, double Lon);` для любого типа (не только для классов), значения по умолчанию у параметров лямбд, `ref readonly` параметры, inline arrays для высокопроизводительных сценариев.

### Что НЕ доступно: C# 13 и C# 14

C# 13 идёт с .NET 9, C# 14 — с .NET 10. На `net8.0` ни то, ни другое не заработает без изменения TFM. Технически `<LangVersion>` можно поднять выше версии, которую подразумевает TFM, но часть возможностей опирается не только на компилятор, а на новые типы в BCL — например, `System.Threading.Lock` физически появился только в .NET 9, и его нет в референс-сборках `net8.0` независимо от `LangVersion`. Поднимать `LangVersion` вручную на боевом TFM — источник кода, который либо не соберётся у коллеги с другим SDK, либо тихо не даст обещанного эффекта. Правило простое: TFM проекта определяет доступный синтаксис, а не желаемая версия языка в статье, которую только что прочитал агент.

Если не уверены, доступна ли конкретная возможность на `net8.0` — самый быстрый способ проверить — открыть страницу возможности на learn.microsoft.com и посмотреть, с какой версии SDK она отмечена как рабочая, а не preview.

## Решения

| Фича | Версия C# | Доступна в `net8.0`? |
|---|---|---|
| Первичные конструкторы классов/структур | 12 | Да |
| Коллекционные выражения `[...]`, spread | 12 | Да |
| Алиас `using X = (...)` для любого типа | 12 | Да |
| Значения по умолчанию у параметров лямбд | 12 | Да |
| `ref readonly` параметры, inline arrays | 12 | Да, но редко нужны |
| `params` с `ReadOnlySpan<T>` / `IEnumerable<T>` | 13 | Нет |
| Тип `System.Threading.Lock` | 13 | Нет — типа нет в BCL `net8.0` |
| `ref struct` в дженериках и интерфейсах, partial-свойства | 13 | Нет |
| `field` в аксессоре свойства | 14 | Нет |
| Extension members нового вида (`extension(...)`) | 14 | Нет |
| Null-условное присваивание `?.=`, `?.+=` | 14 | Нет |
| `nameof` для несвязанного дженерика | 14 | Нет |
| Пользовательские операторы `+=` | 14 | Нет |
| Файловые приложения `dotnet run app.cs` | 14 / .NET 10 SDK | Нет — нужен SDK 10 |

> [!info] Куда идёт индустрия
> В .NET 9 (C# 13) добавили `params` с любыми коллекциями, отдельный тип `Lock` вместо блокировки по `object`, `ref struct` в дженериках. В .NET 10 (C# 14) — `field` в аксессорах, extension-свойства и статические extension-члены, null-условное присваивание, пользовательские `+=`, файловые приложения без `.csproj`. Ничего из этого не доступно на `net8.0`, но встретится в статьях, свежих open-source репозиториях и в ответах агента — знать стоит, чтобы отличить совет «для .NET 10» от применимого совета.
>
> Ещё дальше — .NET 11 / C# 15, релиз 10.11.2026, STS. Главная обсуждаемая возможность языка — union-типы (закрытые размеченные объединения с проверкой полноты `switch`); синтаксис пока не зафиксирован, приводить как готовый нельзя. Из рантайма — Runtime Async: перенос машины состояний `async` с уровня компилятора на уровень CLR, для прикладного кода изменение невидимо. Для нового продового кода это ничего не меняет — целевая версия остаётся .NET 10 LTS.

> [!warning] Где ошибаются
> - **Агент часто** предлагает `field`-аксессор или `customer?.Total += 10` в PR на `net8.0` — потому что в обучающих данных таких примеров больше, чем корректных для C# 12. На CI это упадёт с ошибкой компиляции, что хотя бы заметно сразу.
> - **Агент часто** предлагает поднять `<LangVersion>` в `.csproj`, чтобы «включить» нужную фичу, не проверив, что часть фич требует новых типов из BCL, которых на `net8.0` физически нет — сборка либо не пройдёт, либо даст рантайм-ошибку в неожиданном месте.
> - Путают первичный конструктор `class` и `record` — для `class` не создаются свойства и равенство по значению, это регулярная путаница при чтении кода, а не только при генерации.
> - Коллекционное выражение без контекста типа не компилируется: `var x = [1,2,3];` — ошибка, у выражения нет собственного типа.
> - На собеседовании путают версии: сказать, что union-типы «есть в C#», или что `field` работает в .NET 8 — теряет доверие к остальным ответам.

## Проверка на ревью

- В диффе на `net8.0` нет `field` в аксессоре, `extension(...)`, `?.=`/`?.+=`, `params ReadOnlySpan<T>`, `Lock` — если есть, это либо ошибка сборки, либо кто-то поднял `LangVersion` вручную.
- Если `LangVersion` в `.csproj` отличается от значения по умолчанию для TFM — это осознанное решение, а не случайная правка агента.
- Первичный конструктор `class` не используется вместо `record` там, где нужны равенство по значению и `with`-выражения.
- Коллекционные выражения и spread применены там, где раньше был явный `new List<T> { ... }` — стиль не смешан хаотично в одном файле.
- Параметры первичного конструктора не переприсваиваются там, где подразумевалась неизменность (нет теста/анализатора, который это ловит).

## Проверь себя

> [!question]- Почему код с `field` не соберётся на `net8.0`, даже если поднять `LangVersion`?
> `field` — контекстное ключевое слово компилятора C# 14, а C# 14 официально идёт с .NET 10 SDK. Формально `LangVersion` можно указать в `.csproj` отдельно от TFM, и в части случаев это сработает, но так делать не стоит: возможность становится незадокументированной для остальной команды, ломается в CI с другим SDK и не тестировалась авторами языка в связке именно с `net8.0`. Правильный путь — обновить TFM проекта до `net10.0`, а не подкручивать `LangVersion` точечно.

> [!question]- В чём разница между первичным конструктором `class` и `record`?
> Синтаксис одинаковый, семантика разная. У `record` позиционные параметры превращаются в публичные `init`-свойства, плюс генерируются `Equals`, `GetHashCode`, `ToString`, `Deconstruct`, конструктор копирования и `with`. У обычного `class` первичный конструктор — это только параметры, доступные в теле типа: свойств нет, равенство по ссылке, `ToString` стандартный. Параметры класса при этом не `readonly` — их можно переприсвоить внутри типа.

> [!question]- Почему агент вообще путает C# 12 и C# 14, если версии в документации указаны явно?
> Модель обучена на всём корпусе кода и статей, где .NET 9/10 и C# 13/14 представлены гуще C# 12 — новые статьи и примеры пишут активнее, чем старые устаревают. Без явного контекста «этот репозиторий на `net8.0`» агент опирается на статистически более частый паттерн в обучающих данных, а не на TFM конкретного проекта. Явный контекст (CLAUDE.md, `.csproj`, инструкция в задаче) снижает вероятность ошибки, но не убирает её полностью.

## Разбор

### Разбор 1. Ревью PR от агента

Агент прислал PR на `net8.0`-проект с такой правкой:

```csharp
public class DiscountPolicy
{
    public decimal Rate
    {
        get;
        set => field = value < 0 ? 0 : value;
    }

    public void Apply(Order order) => order.Total?.Discounted += Rate;
}
```

Что вернёшь на доработку?

> [!success]- Решение
> Оба места используют C# 14: `field` в аксессоре и null-условное составное присваивание `?.+=`. На `net8.0` (`LangVersion 12` по умолчанию) это не скомпилируется. Корректная замена — обычное приватное поле и явная проверка на `null`:
> ```csharp
> public class DiscountPolicy
> {
>     private decimal _rate;
>     public decimal Rate
>     {
>         get => _rate;
>         set => _rate = value < 0 ? 0 : value;
>     }
>
>     public void Apply(Order order)
>     {
>         if (order.Total is not null) order.Total.Discounted += Rate;
>     }
> }
> ```
> Возвращать нужно с пояснением «это C# 14, проект на `net8.0`/C# 12», а не просто «не компилируется» — иначе агент в следующей итерации предложит то же самое другими словами.

### Разбор 2. Что здесь реально работает в `net8.0`

```csharp
var numbers = [1, 2, 3];
public sealed class ReportBuilder(IClock clock)
{
    public List<string> GetDefaultSections() => ["Итоги", "Детали"];
}
static void Handle<T>(T value) where T : allows ref struct { }
```

> [!success]- Решение
> Первая строка не скомпилируется независимо от версии: у коллекционного выражения нет собственного типа, нужен явный целевой тип (`int[] numbers = [1, 2, 3];`). Класс `ReportBuilder` с первичным конструктором и коллекционным выражением в методе — корректный C# 12, работает на `net8.0` без изменений. Последняя строка — `allows ref struct`, возможность C# 13, на `net8.0` не соберётся.

## Итог

- Рабочий проект — `net8.0`, а значит доступен только C# 12: первичные конструкторы, коллекционные выражения `[...]` со spread, алиасы для любых типов, значения по умолчанию у лямбд.
- C# 13 (.NET 9) и C# 14 (.NET 10) на `net8.0` не работают — ни `params ReadOnlySpan<T>`, ни `Lock`, ни `field`, ни extension members нового вида, ни `?.=`.
- Поднимать `LangVersion` отдельно от TFM — не решение: часть возможностей требует новых типов из BCL, которых на `net8.0` физически нет.
- Агент путает версии системно, а не случайно: обучающие данные смещены в сторону свежих .NET 9/10 репозиториев — держать это в голове при ревью каждого PR с незнакомым синтаксисом.
- .NET 11 / C# 15 — только «что впереди»: union-типы без зафиксированного синтаксиса и невидимый для прикладного кода Runtime Async.
