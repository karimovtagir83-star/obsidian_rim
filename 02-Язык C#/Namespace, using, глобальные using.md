# Namespace, using, глобальные using

> [!abstract] Коротко
> Пространство имён — способ дать типам уникальные полные имена и сгруппировать их по смыслу: `Alif.ServiceShop.Orders.Order`. Директива `using` не «подключает библиотеку» (за это отвечает ссылка на сборку), а лишь позволяет писать короткие имена. С C# 10 появились `global using` — объявленные один раз на всю сборку, и `ImplicitUsings` — набор глобальных using, который SDK добавляет автоматически, поэтому в новых проектах `using System;` не видно. Пространство имён и сборка — разные вещи: в одной сборке может быть много пространств имён, а одно пространство имён может быть размазано по нескольким сборкам.

## Зачем это нужно

Две практические задачи. Первая — уникальность: `Order` в модуле заказов и `Order` в интеграции с платёжной системой должны сосуществовать, и полное имя это обеспечивает. Вторая — навигация: по имени `Alif.ServiceShop.Orders.Domain.Order` понятно, где искать файл и к какому слою он относится.

Плюс регулярные практические вопросы: почему `List<T>` доступен без `using`, откуда берётся ошибка «неоднозначная ссылка», как назвать свой класс `Path`, не сломав `System.IO.Path`, и почему extension-метод «не находится».

## Объявление пространств имён

```csharp
// File-scoped namespace (C# 10) — предпочтительный стиль: без лишнего уровня отступа
namespace Alif.ServiceShop.Orders;

public sealed class Order;

// Классический блочный стиль — нужен, только если в файле несколько пространств имён
namespace Alif.ServiceShop.Payments
{
    public sealed class Payment;
}
```

Соглашения именования: `Компания.Продукт.Модуль.Слой`, PascalCase, без подчёркиваний и множественного числа там, где оно не нужно. Структура папок должна повторять пространства имён (`Orders/Domain/Order.cs` → `...Orders.Domain`) — это не требование компилятора, а соглашение, которое проверяется анализаторами и делает навигацию предсказуемой.

Пространство имён никак не связано со сборкой: это чисто логическая группировка, разрешаемая на этапе компиляции. Полное имя типа в метаданных выглядит как `Alif.ServiceShop.Orders.Order`, а имя сборки хранится отдельно.

## Директива using

```csharp
using System.Text;                                 // импорт пространства имён
using static System.Math;                          // импорт статических членов типа
using Json = System.Text.Json.JsonSerializer;      // псевдоним типа
using Coordinates = (double Lat, double Lon);      // псевдоним чего угодно (C# 12)

var sb = new StringBuilder();
Console.WriteLine(Sqrt(16));                       // без Math. — благодаря using static
var text = Json.Serialize(new { ok = true });
Coordinates office = (41.2995, 69.2401);
```

`using` не влияет ни на размер сборки, ни на производительность: это указание компилятору, где искать короткие имена. Неиспользуемые `using` — только визуальный шум (и предупреждение IDE0005).

**Порядок размещения** имеет значение в редких, но неприятных случаях: `using` вне пространства имён (стандарт для file-scoped) и внутри него разрешают конфликты имён по-разному — при поиске компилятор сначала смотрит в текущем пространстве имён и его внешних уровнях, затем в импортированных. Смешивать оба варианта в проекте не стоит; правило фиксируют в `.editorconfig` (`csharp_using_directive_placement`).

### Псевдонимы для разрешения конфликтов

```csharp
using SystemTimer = System.Timers.Timer;
using ThreadingTimer = System.Threading.Timer;

var t1 = new SystemTimer();
var t2 = new ThreadingTimer(_ => { });

// Если имя типа совпадает с именем пространства имён или перекрыто локально,
// помогает квалификатор global::
global::System.Console.WriteLine("однозначно System.Console");
```

Псевдоним — самый прямой способ ужиться с двумя одноимёнными типами (классика: `Order` из домена и `Order` из сгенерированного клиента внешнего API).

## Глобальные using

```csharp
// Файл GlobalUsings.cs — обычно один на проект
global using System.Text.Json;
global using Alif.ServiceShop.Orders.Domain;
global using static System.Math;
global using OrderId = Alif.ServiceShop.Orders.Domain.OrderId;
```

`global using` действует на **всю сборку**: объявляется один раз, работает в каждом файле. Ограничения: должны идти до обычных `using` в своём файле и не могут находиться внутри пространства имён.

### ImplicitUsings

```xml
<PropertyGroup>
  <ImplicitUsings>enable</ImplicitUsings>
</PropertyGroup>
```

SDK сам генерирует файл с глобальными using — для консольного и библиотечного проекта это `System`, `System.Collections.Generic`, `System.IO`, `System.Linq`, `System.Net.Http`, `System.Threading`, `System.Threading.Tasks`; веб-SDK добавляет ещё `Microsoft.AspNetCore.*` и `Microsoft.Extensions.*`. Именно поэтому в новом шаблоне работает `Console.WriteLine` и `List<T>` без единого `using`.

Посмотреть фактический список можно в сгенерированном файле:

```
obj/Debug/net10.0/<Проект>.GlobalUsings.g.cs
```

Набор настраивается прямо в файле проекта:

```xml
<ItemGroup>
  <Using Include="System.Diagnostics" />              <!-- добавить -->
  <Using Include="System.Math" Static="true" />        <!-- как using static -->
  <Using Include="MyProject.Domain.OrderId" Alias="OrderId" />
  <Using Remove="System.Net.Http" />                   <!-- убрать из неявных -->
</ItemGroup>
```

Практика: в глобальные using выносят то, что нужно **почти в каждом файле** проекта, — базовые пространства имён, типы результата, общие абстракции. Всё остальное оставляют локальным: иначе теряется полезная информация о том, от чего файл реально зависит, а имена начинают конфликтовать неожиданно и в чужих файлах.

## Как компилятор разрешает имена

Порядок поиска типа `Foo` внутри `A.B.C`:

1. вложенные типы и члены текущего типа;
2. текущее пространство имён `A.B.C`, затем `A.B`, затем `A`, затем глобальное;
3. типы из `using`-директив (сначала файла, затем глобальных).

Если на каком-то уровне найдено ровно одно совпадение — оно и выбирается, поиск дальше не идёт. Если на одном уровне нашлось несколько — ошибка CS0104 «неоднозначная ссылка», и нужен псевдоним или полное имя.

```csharp
namespace MyApp.Utils;

public static class Console                        // свой Console!
{
    public static void Say(string s) { }
}

public static class Runner
{
    public static void Run()
    {
        // Console.WriteLine("...");                // Ошибка: локальный Console выигрывает —
                                                    // он найден раньше, чем System.Console
        global::System.Console.WriteLine("ok");     // однозначно
    }
}
```

Отсюда практическое правило: не называть свои типы именами часто используемых типов BCL (`Task`, `Path`, `Console`, `Timer`, `Environment`, `File`) — компилятор предпочтёт твой, и ошибки будут возникать в неожиданных местах.

### Extension-методы и using

```csharp
// Метод расширения виден, ТОЛЬКО если импортировано пространство имён,
// в котором объявлен его статический класс
using System.Linq;                    // без этого orders.Where(...) не найдётся
```

Это самая частая причина «метод не существует, хотя я вижу его в другом файле»: пропущен `using`. С неявными using это встречается реже, но остаётся актуальным для своих библиотек расширений. Подробно — [[Расширяющие методы и extension members]].

## Не путать: `using` как директива и как инструкция

```csharp
using System.IO;                                   // директива: импорт имён

// Инструкция using: освобождение ресурса
using (var stream = File.OpenRead("data.txt"))
{
    // ...
}                                                   // здесь вызывается Dispose()

// Объявление using (C# 8): освобождение в конце области видимости
using var reader = new StreamReader("data.txt");
var line = await reader.ReadLineAsync();
// Dispose() будет вызван при выходе из метода

await using var connection = new Npgsql.NpgsqlConnection(cs);   // асинхронное освобождение
```

Одинаковое ключевое слово, разные вещи: первое — про имена на этапе компиляции, второе — про детерминированное освобождение ресурсов в рантайме ([[IDisposable, using и паттерн Dispose]]).

## Как организовать пространства имён в проекте

Два устойчивых подхода:

```
По слоям (классическая многослойная архитектура)
  Alif.ServiceShop.Domain
  Alif.ServiceShop.Application
  Alif.ServiceShop.Infrastructure
  Alif.ServiceShop.Api

По функциям (vertical slice / модульный монолит)
  Alif.ServiceShop.Orders.Domain
  Alif.ServiceShop.Orders.Application
  Alif.ServiceShop.Payments.Domain
  Alif.ServiceShop.Payments.Application
```

Второй вариант лучше масштабируется: связанный код лежит рядом, модуль можно вынести в отдельную сборку или сервис, а границы видны в самих именах. Первый проще на старте и годится для небольших проектов. Подробнее — [[Vertical Slice Architecture]] и [[ServiceShop: модульный монолит и изоляция модулей]].

Ключевое различение, которое часто путают: **пространство имён не создаёт границы**. Ограничить доступ между модулями пространством имён невозможно — для этого нужны разные сборки и `internal`, либо архитектурные тесты, проверяющие зависимости.

> [!warning] Подводные камни
> - **Свои типы с именами из BCL.** Локальный `Console`, `Path` или `Task` выигрывает при разрешении имён и ломает код в том же пространстве имён.
> - **Слишком много глобальных using.** Файл перестаёт показывать свои зависимости, а конфликты имён всплывают в чужих файлах. Глобально — только то, что нужно почти везде.
> - **Пространство имён не совпадает с папкой.** Компилятор промолчит, а навигация и генерация кода сломаются. Проверяется анализатором IDE0130.
> - **`using` внутри и вне пространства имён вперемешку.** Разное разрешение конфликтов в разных файлах одного проекта; выбрать один стиль и зафиксировать в `.editorconfig`.
> - **Ожидание, что `using` что-то подключает.** Ссылки на сборки задаются в файле проекта (`PackageReference`/`ProjectReference`); `using` только сокращает имена.
> - **Псевдоним вместо честного типа.** `using Money = decimal;` не создаёт нового типа: сложить деньги с процентами компилятор по-прежнему разрешит. Нужен `readonly record struct`.

> [!example] Как делают в бою
> В решении заводят один `GlobalUsings.cs` на проект, и он короткий: базовые вещи, тип результата, общие абстракции модуля. Всё узкоспециальное (`System.Text.Json`, `Npgsql`, `Microsoft.EntityFrameworkCore`) остаётся локальным — так по шапке файла видно, с чем он работает.
> Имена пространств строятся от модуля, а не от технического слоя: `Alif.ServiceShop.Orders.Application` вместо `Alif.ServiceShop.Application.Orders`. При таком порядке всё, что относится к заказам, оказывается рядом и в дереве папок, и в списке типов.
> Конфликты имён с внешними библиотеками (особенно с сгенерированными клиентами и с типами вроде `Order`, `Customer`, `Status`) решают псевдонимами в том файле, где конфликт возник, а не переименованием доменных типов.

## Вопросы с собеседований

> [!question]- Чем пространство имён отличается от сборки?
> Пространство имён — логическая группировка имён, существующая только на уровне компиляции: оно делает полное имя типа уникальным и позволяет писать короткие имена через `using`. Сборка — единица развёртывания и версионирования: физический файл `.dll` с IL и метаданными, у которого есть имя, версия и границы доступа (`internal` действует внутри сборки). Одна сборка может содержать сколько угодно пространств имён, а одно пространство имён может быть распределено по нескольким сборкам — так устроена сама BCL, где `System.Collections.Generic` собран из нескольких сборок. Практическое следствие: пространством имён нельзя ограничить доступ или задать архитектурную границу — для этого нужны отдельные сборки с `internal` или архитектурные тесты.

> [!question]- Что такое `global using` и `ImplicitUsings`?
> `global using` (C# 10) — директива, действующая на всю сборку: объявляется в одном файле и работает в каждом. `ImplicitUsings` — свойство проекта, при котором SDK сам генерирует такие директивы для типового набора пространств имён: для консольного проекта это `System`, `System.Collections.Generic`, `System.IO`, `System.Linq`, `System.Net.Http`, `System.Threading`, `System.Threading.Tasks`, а веб-SDK добавляет пространства ASP.NET Core и `Microsoft.Extensions`. Сгенерированный файл лежит в `obj` и называется `<Проект>.GlobalUsings.g.cs`; набор настраивается элементами `<Using Include/Remove/Alias/Static>` в файле проекта. Выигрыш — меньше шума в шапке файлов; риск — файл перестаёт показывать свои реальные зависимости, поэтому глобально выносят только то, что нужно практически везде.

> [!question]- Почему компилятор не находит метод расширения, хотя он существует?
> Потому что методы расширения видны только при импорте пространства имён, в котором объявлен содержащий их статический класс. Наличие ссылки на сборку недостаточно: нужен именно `using` (обычный или глобальный) с этим пространством. Классические проявления: пропущен `using System.Linq` — и `Where`/`Select` «не существуют»; своя библиотека расширений лежит в `MyApp.Extensions`, а файл её не импортирует. Дополнительные причины того же класса: тип получателя не подходит по ограничениям дженерика; в области видимости есть метод экземпляра с тем же именем — он всегда выигрывает у расширения; расширение объявлено в другом проекте, на который нет ссылки. Разрешение методов расширения происходит на этапе компиляции по видимым `using`, поэтому все эти ошибки проявляются как «метод не найден», а не как ошибка времени выполнения.

## Задачи

### Задача 1. Разрешить конфликт имён

В проекте есть свой `Alif.ServiceShop.Orders.Order` и сгенерированный клиент внешнего API с типом `PaymentGateway.Client.Order`. В одном файле нужны оба.

> [!success]- Решение
> ```csharp
> using Alif.ServiceShop.Orders;
> using GatewayOrder = PaymentGateway.Client.Order;
>
> public sealed class OrderMapper
> {
>     public GatewayOrder ToGateway(Order order) => new()
>     {
>         ExternalId = order.Id.ToString(),
>         Amount = order.Total
>     };
> }
> ```
> Псевдоним лучше полного имени в каждом использовании (читаемее) и лучше переименования доменного типа (домен не должен подстраиваться под внешнюю интеграцию). Альтернатива, которая иногда удобнее: не импортировать ни одно из пространств имён и писать оба полных имени — оправдано, если каждое встречается один-два раза. Чего делать не стоит — выносить один из этих `using` в глобальные: конфликт тогда всплывёт в других файлах, где о нём никто не думает.

### Задача 2. Что не так с организацией

```csharp
// Файл: /Orders/Domain/Order.cs
namespace MyApp;

public class Order { }
public class Customer { }
public class Path { }        // утилита для построения путей доставки
```

> [!success]- Решение
> Три проблемы. Первая: пространство имён `MyApp` не соответствует пути `Orders/Domain` — навигация и генерация кода перестают работать предсказуемо (анализатор IDE0130 это подсвечивает); правильно `MyApp.Orders.Domain`. Вторая: три публичных типа в одном файле — соглашение .NET требует один публичный тип на файл с совпадающим именем, иначе типы невозможно найти по имени файла. Третья и самая опасная: класс `Path` перекрывает `System.IO.Path` для всего пространства имён `MyApp` — в любом файле этого пространства `Path.Combine` перестанет компилироваться, и причина будет неочевидна. Утилите нужно доменное имя — `DeliveryRoute` или `RouteBuilder`, — которое к тому же точнее описывает смысл.

## Итог

- Пространство имён делает полное имя типа уникальным и группирует код; со сборкой оно не связано.
- File-scoped `namespace X;` — современный стиль; структура папок должна повторять пространства имён.
- `using` только сокращает имена; ссылки на код задаются в файле проекта.
- `using static` импортирует статические члены, псевдоним — любое имя (с C# 12 в том числе кортежи и массивы).
- `global using` действует на всю сборку; `ImplicitUsings` — сгенерированный SDK набор, который можно менять элементами `<Using>`.
- Разрешение имён идёт от ближайшей области наружу; свой тип с именем из BCL выигрывает и ломает код.
- Методы расширения видны только при импорте их пространства имён.
- `using` как директива и `using` как инструкция освобождения ресурса — разные вещи с одинаковым словом.
