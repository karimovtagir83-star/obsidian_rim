# Обработка исключений

> [!abstract] Коротко
> Исключение — механизм передачи управления при нарушении нормального хода выполнения: рантайм разворачивает стек, пока не найдёт подходящий `catch`. Три практических правила покрывают почти всё: ловить только то, с чем можешь что-то сделать; никогда не терять исходное исключение (`throw;`, а не `throw ex;`); ставить обработчик там, где есть контекст для решения, — обычно на границе приложения, а не в каждом методе. Исключение стоит дорого (десятки микросекунд против наносекунд у обычного возврата), поэтому оно предназначено для исключительных ситуаций, а не для управления потоком.

## Зачем это нужно

Код без обработки ошибок работает только в демонстрациях. В реальности сеть отваливается, база отвечает таймаутом, файл занят, JSON приходит битым, а пользователь вводит буквы там, где ожидалось число.

Плохая обработка хуже её отсутствия:

```csharp
try { await ProcessAsync(order); }
catch (Exception) { }                       // проглотили: заказ не обработан, никто не знает
catch (Exception ex) { throw ex; }          // потеряли стек: где упало — неизвестно
catch (Exception ex) { return null; }       // превратили сбой в «нет данных»
```

Каждая из этих строк регулярно встречается в проде и каждая превращает диагностируемую ошибку в загадку.

## Механика

```csharp
try
{
    var content = File.ReadAllText(path);
    Process(content);
}
catch (FileNotFoundException ex)             // самый конкретный — первым
{
    logger.LogWarning(ex, "Файл {Path} не найден", path);
    throw;                                    // передать выше, сохранив стек
}
catch (IOException ex) when (ex.HResult == unchecked((int)0x80070020))
{
    logger.LogWarning(ex, "Файл {Path} заблокирован другим процессом", path);
}
finally
{
    // выполняется всегда: и при успехе, и при исключении, и при return из try
    stopwatch.Stop();
}
```

Что происходит в рантайме: при `throw` создаётся объект исключения, фиксируется стек вызовов, и CLR идёт вверх по стеку в поисках подходящего обработчика (**первый проход**), затем разворачивает стек, выполняя блоки `finally` (**второй проход**). Двухпроходность важна: она объясняет, почему фильтры `when` выполняются **до** разворачивания стека — об этом ниже.

Порядок блоков `catch` значим: они проверяются сверху вниз, и первый подходящий по типу выигрывает. Более общий тип, поставленный выше более конкретного, делает нижний недостижимым — компилятор на это ругается.

### finally и `using`

```csharp
// using — синтаксический сахар над try/finally
using var connection = new NpgsqlConnection(cs);
await connection.OpenAsync(ct);
// эквивалент: try { ... } finally { await connection.DisposeAsync(); }
```

`finally` не выполняется в трёх случаях: `StackOverflowException` (процесс убивается немедленно), `Environment.FailFast`, аварийное завершение процесса извне (`kill -9`, отключение питания). Всё остальное — включая `return` из `try` и исключение внутри `catch` — гарантирует выполнение `finally`.

## `throw;` против `throw ex;`

```csharp
try { Inner(); }
catch (Exception ex)
{
    throw;          // ПРАВИЛЬНО: исключение летит дальше, стек сохранён целиком
    // throw ex;    // НЕПРАВИЛЬНО: стек обрезается по текущему методу
}
```

`throw ex;` заново «бросает» тот же объект, и рантайм перезаписывает `StackTrace` начиная с этой строки. В результате в логах видно место перехвата, а не место возникновения — а именно оно и нужно. Это самая частая ошибка в обработке исключений.

Если исключение нужно перебросить из другого места (например, сохранённое из фонового кода), стек сохраняется через `ExceptionDispatchInfo`:

```csharp
System.Runtime.ExceptionServices.ExceptionDispatchInfo? captured = null;
try { Risky(); }
catch (Exception ex) { captured = System.Runtime.ExceptionServices.ExceptionDispatchInfo.Capture(ex); }

captured?.Throw();     // бросает позже, стек оригинала сохранён
```

### Оборачивание

Когда нужно добавить контекст, исходное исключение кладут внутрь, а не выбрасывают:

```csharp
catch (NpgsqlException ex)
{
    throw new OrderStorageException($"Не удалось сохранить заказ {orderId}", ex);
    //                                                             ^^ innerException
}
```

Тогда в логах будет и своё сообщение с бизнес-контекстом, и полная цепочка `InnerException` с первопричиной. Про проектирование своих типов — [[Свои типы исключений]].

## Фильтры исключений (`when`)

```csharp
try { await client.SendAsync(request, ct); }
catch (HttpRequestException ex) when (ex.StatusCode == System.Net.HttpStatusCode.TooManyRequests)
{
    await Task.Delay(retryDelay, ct);
}
catch (TaskCanceledException) when (!ct.IsCancellationRequested)
{
    // отмена по таймауту, а не по запросу пользователя — это разные ситуации
    logger.LogWarning("Таймаут запроса");
}
```

Фильтр — не просто «`catch` + `if` внутри». Разница принципиальная: **фильтр вычисляется до разворачивания стека**. Если он вернул `false`, стек остаётся нетронутым, и отладчик остановится в точке возникновения исключения с живыми локальными переменными. Вариант `catch { if (...) throw; }` стек уже развернул, и восстановить контекст невозможно.

Побочный полезный приём — логирование без перехвата:

```csharp
catch (Exception ex) when (Log(ex)) { }      // никогда не выполнится: Log всегда false
static bool Log(Exception ex) { Console.WriteLine(ex); return false; }
```

Фильтр вызывается, исключение логируется, но не перехватывается и летит дальше с сохранным стеком.

## Что ловить и где

Главный вопрос — не «как поймать», а «где». Ответ: там, где есть **достаточно контекста, чтобы принять решение**.

```csharp
// Плохо: перехват без решения — ошибка потеряна, вызывающий получит «пусто»
public async Task<Order?> GetAsync(long id)
{
    try { return await _db.Orders.FindAsync(id); }
    catch (Exception ex) { _logger.LogError(ex, "Ошибка"); return null; }
}

// Хорошо: метод не ловит ничего — он не знает, что делать с падением базы.
// Решение принимается выше: middleware вернёт 500, повторит запрос или включит fallback.
public Task<Order?> GetAsync(long id, CancellationToken ct) => _db.Orders.FindAsync([id], ct).AsTask();
```

Уровни, где перехват уместен:

1. **Граница приложения.** Глобальный обработчик превращает исключение в HTTP-ответ и структурный лог. В ASP.NET Core — `IExceptionHandler` и `UseExceptionHandler` с `ProblemDetails` ([[Обработка ошибок и ProblemDetails]]).
2. **Граница интеграции.** Вызов внешнего сервиса: перехват, чтобы применить повтор, разрыватель цепи, запасной вариант ([[Устойчивость: retry, circuit breaker, Polly]]).
3. **Фоновая задача.** Необработанное исключение в фоне может уронить процесс или тихо остановить обработку — цикл обязан ловить и продолжать.
4. **Точки, где ошибка ожидаема и обрабатываема.** Файл занят — подождать и повторить; конкурентное обновление — перечитать и применить заново.

Во всех остальных местах правильное поведение — **не ловить**. Метод, который не может исправить ситуацию, не должен притворяться, что справился.

### catch(Exception) в глобальном обработчике

```csharp
// ASP.NET Core 8+: типизированный обработчик вместо middleware с try/catch
public sealed class GlobalExceptionHandler(ILogger<GlobalExceptionHandler> logger) : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(HttpContext context, Exception exception, CancellationToken ct)
    {
        logger.LogError(exception, "Необработанное исключение при {Method} {Path}",
            context.Request.Method, context.Request.Path);

        var (status, title) = exception switch
        {
            ArgumentException or ValidationException => (StatusCodes.Status400BadRequest, "Некорректный запрос"),
            KeyNotFoundException => (StatusCodes.Status404NotFound, "Не найдено"),
            OperationCanceledException => (StatusCodes.Status499ClientClosedRequest, "Запрос отменён"),
            _ => (StatusCodes.Status500InternalServerError, "Внутренняя ошибка")
        };

        context.Response.StatusCode = status;
        await context.Response.WriteAsJsonAsync(new ProblemDetails { Status = status, Title = title }, ct);
        return true;
    }
}
```

Ключевые свойства такого обработчика: он один, он логирует **объект исключения** (а не `ex.Message`), и он не отдаёт наружу детали — стек и внутренние сообщения остаются в логах, клиент получает нейтральный текст. Утечка стека в ответ — это и подсказка атакующему, и мусор в интерфейсе.

## Стоимость исключений

Бросок и перехват исключения стоит порядка десятков микросекунд: создание объекта, захват стека, два прохода по кадрам, поиск обработчика. Обычный `return` — единицы наносекунд. Разница в тысячи раз.

Практические следствия:

- **Никогда — для управления потоком.** «Проверить наличие ключа через `catch (KeyNotFoundException)`» вместо `TryGetValue` превращает горячий путь в неработоспособный.
- **Валидация — не исключение.** Ожидаемо некорректный ввод обрабатывается проверкой и ответом 400, а не броском исключения на каждое поле.
- **`try` сам по себе бесплатен.** Пока исключение не брошено, блок `try` не стоит почти ничего — оборачивать код в `try/finally` не вредно.
- **Массовые исключения видны в метриках.** Счётчик исключений в секунду — хороший индикатор скрытых проблем: часто он показывает, что «работающий» сервис на самом деле обрабатывает половину запросов через сбой.

Когда исключений быть не должно по смыслу — [[Когда исключение — плохой выбор]].

## Асинхронный код

```csharp
// Исключение из async-метода сохраняется в Task и выбрасывается при await
try { await SendAsync(); }
catch (HttpRequestException ex) { /* обычный catch работает как ожидается */ }

// Несколько задач: WhenAll бросает ПЕРВОЕ исключение, но собирает все
var task = Task.WhenAll(t1, t2, t3);
try { await task; }
catch (Exception)
{
    foreach (var ex in task.Exception!.InnerExceptions)      // здесь все ошибки
        logger.LogError(ex, "Одна из задач упала");
}

// async void — исключение НЕ попадает в Task и обычно роняет процесс
```

Разбор — [[Исключения в асинхронном коде]] и [[Дедлоки, async void и типичные ошибки]].

Отдельно про отмену: `OperationCanceledException` — не ошибка, а штатный исход. Его не логируют как ошибку и не считают сбоем; в ASP.NET Core он обычно означает, что клиент разорвал соединение.

> [!warning] Подводные камни
> - **`throw ex;` вместо `throw;`.** Обрезает стек по месту перехвата — первопричина теряется.
> - **Пустой `catch`.** Ошибка исчезает бесследно; система продолжает работать в неопределённом состоянии. Если перехват действительно нужен без действий, это должно быть прокомментировано и залогировано.
> - **`catch (Exception)` в середине стека.** Ловит и то, что ловить нельзя: `OutOfMemoryException`, `OperationCanceledException`, ошибки программиста вроде `NullReferenceException`.
> - **Логирование `ex.Message` вместо `ex`.** Теряются тип, стек и внутренние исключения — в логе остаётся строка «Object reference not set», по которой ничего не найти. Правильно: `logger.LogError(ex, "...")`.
> - **Исключения для управления потоком.** Дорого и нечитаемо; для ожидаемых исходов есть `Try*`-методы и Result.
> - **`return` внутри `finally`.** Подавляет летящее исключение — компилятор это запрещает для `return` внутри `finally` в C#, но эквивалентный эффект достигается перехватом внутри `finally`; такого кода быть не должно.
> - **Детали исключения в ответе API.** Стек и текст внутреннего исключения не должны покидать сервер: в ответ идёт нейтральное сообщение и идентификатор корреляции, по которому ошибку находят в логах.
> - **Перехват `OperationCanceledException` как ошибки.** Отмена — норма; логировать её как сбой значит зашумлять мониторинг.

> [!example] Как делают в бою
> В зрелом сервисе `try/catch` встречается заметно реже, чем ожидают новички. Типичная структура: один глобальный обработчик на входе (`IExceptionHandler` + `ProblemDetails`), политики устойчивости вокруг внешних вызовов, `try/catch` в циклах фоновых служб — и почти ничего больше. Бизнес-логика исключений не ловит: она их бросает, когда нарушен инвариант, и позволяет им дойти до границы.
> Логирование делается один раз, на границе, с передачей объекта исключения и структурного контекста (идентификатор запроса, пользователя, заказа). Многократное логирование одного исключения на каждом уровне — распространённый антипаттерн: в логах появляется по пять записей об одной ошибке, и найти первопричину сложнее, а не легче.
> Отдельная практика — отличать ожидаемые исходы от сбоев уже в сигнатурах: «не найдено» и «не прошло валидацию» возвращаются как результат, а исключения остаются для того, что действительно сломалось.

## Вопросы с собеседований

> [!question]- Чем `throw;` отличается от `throw ex;`?
> `throw;` внутри блока `catch` продолжает распространение текущего исключения: объект тот же, стек вызовов сохраняется целиком, и в логе видно исходное место возникновения. `throw ex;` формально бросает исключение заново, и рантайм перезаписывает его `StackTrace`, начиная с текущей строки — вся история до места перехвата теряется, и по логу невозможно понять, где именно произошёл сбой. Если нужно добавить контекст, правильный вариант — обернуть: `throw new MyException("контекст", ex)`, тогда исходное исключение сохраняется в `InnerException`. Отдельный случай — переброс исключения, пойманного в другом месте или в другом потоке: там используют `ExceptionDispatchInfo.Capture(ex).Throw()`, который сохраняет оригинальный стек.

> [!question]- Зачем нужны фильтры исключений `when`, если можно проверить условие внутри `catch`?
> Из-за двухпроходной модели обработки в CLR. Фильтр вычисляется на **первом** проходе — когда рантайм ищет обработчик, но стек ещё не развёрнут. Если фильтр вернул `false`, этот `catch` просто не выбирается, кадры стека остаются нетронутыми, и исключение продолжает искать обработчик выше, сохраняя полный контекст: отладчик остановится в точке возникновения, локальные переменные живы, дампы информативны. Вариант «поймать, проверить условие, при несоответствии сделать `throw;`» разворачивает стек до перехвата и портит диагностику, а также запускает все `finally` по пути. Побочный полезный приём — фильтр, который всегда возвращает `false`, но по дороге логирует: так исключение записывается в лог без перехвата.

> [!question]- Где правильно ловить исключения?
> Там, где есть контекст и возможность принять решение. Практически это четыре места: граница приложения (глобальный обработчик, превращающий исключение в HTTP-ответ и структурный лог), граница интеграции с внешней системой (повтор, разрыватель цепи, запасной вариант), цикл фоновой службы (чтобы одна неудачная итерация не останавливала обработку) и точки, где ошибка ожидаема и обрабатываема — например, конфликт конкурентного обновления, который надо перечитать и применить заново. Во всех остальных местах ловить не нужно: метод, который не может исправить ситуацию, перехватом лишь скрывает её. Признак неправильного перехвата — `catch`, внутри которого только логирование и возврат `null` или значения по умолчанию: вызывающий получает «пусто» вместо ошибки и продолжает работать с неверными данными.

> [!question]- Сколько стоит исключение и почему это важно?
> Бросок и обработка исключения — десятки микросекунд: создаётся объект, захватывается стек вызовов, рантайм делает два прохода по кадрам, ищет обработчик и выполняет `finally`. Обычный возврат значения — единицы наносекунд, разница в тысячи раз. Сам блок `try` при этом почти бесплатен: пока исключения нет, он не влияет на исполнение (в основном мешает некоторым оптимизациям JIT, но не более). Отсюда правило: исключения — для исключительных ситуаций, а не для ожидаемых исходов и не для управления потоком. Валидация ввода, «ключ не найден», «строка не разобралась» должны обрабатываться проверками и `Try*`-методами. Практический индикатор — метрика исключений в секунду: если она заметно ненулевая при нормальной работе, значит какой-то ожидаемый сценарий реализован через исключения, и это стоит и производительности, и читаемости логов.

## Задачи

### Задача 1. Исправить обработку

```csharp
public async Task<Order?> LoadAsync(long id)
{
    try
    {
        var response = await _http.GetAsync($"/orders/{id}");
        var json = await response.Content.ReadAsStringAsync();
        return JsonSerializer.Deserialize<Order>(json);
    }
    catch (Exception ex)
    {
        _logger.LogError("Ошибка: " + ex.Message);
        throw ex;
    }
}
```

> [!success]- Решение
> ```csharp
> public async Task<Order?> LoadAsync(long id, CancellationToken ct)
> {
>     var response = await _http.GetAsync($"/orders/{id}", ct);
>
>     if (response.StatusCode == HttpStatusCode.NotFound)
>         return null;                                  // ожидаемый исход, не исключение
>
>     response.EnsureSuccessStatusCode();
>     return await response.Content.ReadFromJsonAsync<Order>(cancellationToken: ct);
> }
> ```
> Что исправлено. `throw ex;` обрезал стек — теперь исключение вообще не перехватывается, потому что метод не может ничего с ним сделать: решение примет вызывающий или глобальный обработчик. Логирование через конкатенацию `ex.Message` теряло тип, стек и внутренние исключения; логировать надо один раз на границе и передавать объект исключения. Добавлен `CancellationToken` — без него отмена не доходит до HTTP-клиента. Ответ 404 обрабатывается как обычный результат `null`, а не как ошибка. Ручная десериализация заменена на `ReadFromJsonAsync`, который читает поток и не создаёт промежуточную строку.

### Задача 2. Что выведет

```csharp
static int Test()
{
    try
    {
        return 1;
    }
    finally
    {
        Console.WriteLine("finally");
    }
}

Console.WriteLine(Test());
```

А если в `try` бросить исключение и поймать его снаружи — выполнится ли `finally`?

> [!success]- Решение
> Вывод: сначала `finally`, затем `1`. Значение возврата вычисляется и сохраняется до выполнения `finally`, но сам блок `finally` выполняется раньше фактического возврата управления вызывающему — отсюда такой порядок вывода.
> Да, при исключении `finally` тоже выполнится: рантайм разворачивает стек и по пути выполняет все блоки `finally` между точкой броска и найденным обработчиком. Не выполнится он только в трёх случаях: `StackOverflowException` (процесс завершается немедленно, выполнять код негде), `Environment.FailFast` (намеренное аварийное завершение без разворачивания стека) и внешнее убийство процесса (`kill -9`, отключение питания). Это, кстати, и причина, по которой `using`, построенный на `try/finally`, не гарантирует освобождение внешних ресурсов при жёстком завершении — надёжность в таких сценариях обеспечивают на стороне ресурса (таймауты соединений, аренда, транзакции).

## Итог

- Исключение разворачивает стек до ближайшего подходящего `catch`; `finally` выполняется в любом случае, кроме фатального завершения процесса.
- `throw;` сохраняет стек, `throw ex;` — обрезает. Контекст добавляют оборачиванием с `innerException`.
- Фильтры `when` вычисляются до разворачивания стека — это лучше, чем `catch` с проверкой внутри.
- Ловить надо там, где есть решение: граница приложения, граница интеграции, цикл фоновой службы, ожидаемо восстановимая ошибка.
- Пустой `catch` и `catch (Exception)` в середине стека — способ превратить сбой в загадку.
- Логировать объект исключения, а не `ex.Message`, и один раз — на границе.
- Исключение стоит десятки микросекунд: оно не для управления потоком и не для валидации.
- Отмена (`OperationCanceledException`) — штатный исход, а не ошибка.
