# Обработка исключений

> [!abstract] Коротко
> Исключение — механизм передачи управления при нарушении нормального хода выполнения: рантайм разворачивает стек, пока не найдёт подходящий `catch`. Все исключения наследуются от `System.Exception`; деление на `SystemException`/`ApplicationException` устарело. Три правила покрывают почти всё: ловить только то, с чем можешь что-то сделать; никогда не терять исходное исключение (`throw;`, а не `throw ex;`); ставить обработчик там, где есть контекст для решения. Свой тип исключения нужен, только когда вызывающий должен отличить эту ситуацию от других — иначе достаточно типа из BCL.

## Зачем это знать

Код без обработки ошибок работает только в демонстрациях: сеть отваливается, база отвечает таймаутом, файл занят. Плохая обработка хуже отсутствия — пустой `catch`, `throw ex;`, `catch (Exception) { return null; }` регулярно встречаются в проде и превращают диагностируемую ошибку в загадку. Отдельно нужно уметь читать тип исключения как диагноз (`InvalidOperationException` — «объект не в том состоянии», `ArgumentException` — «передали не то») и решать, когда завести свой тип, а когда это лишний класс, на который никто не напишет `catch`.

## Модель

### Механика try/catch/finally

```csharp
try
{
    var content = File.ReadAllText(path);
    Process(content);
}
catch (FileNotFoundException ex)             // самый конкретный — первым
{
    logger.LogWarning(ex, "Файл {Path} не найден", path);
    throw;                                    // передать выше, сохранив стек
}
catch (IOException ex) when (ex.HResult == unchecked((int)0x80070020))
{
    logger.LogWarning(ex, "Файл {Path} заблокирован другим процессом", path);
}
finally
{
    stopwatch.Stop();                         // выполняется всегда, кроме фатального завершения
}
```

При `throw` CLR фиксирует стек и идёт вверх в поисках обработчика (**первый проход**), затем разворачивает стек, выполняя `finally` (**второй проход**). Двухпроходность объясняет, почему фильтр `when` вычисляется **до** разворачивания стека: если он вернул `false`, кадры остаются нетронутыми и отладчик остановится в точке возникновения с живыми переменными. Вариант «поймать и внутри проверить условие» стек уже развернул — контекст потерян.

`finally` не выполняется в трёх случаях: `StackOverflowException` (процесс убивается немедленно), `Environment.FailFast`, аварийное завершение извне (`kill -9`). Всё остальное, включая `return` из `try`, гарантирует его выполнение. `using` — синтаксический сахар над `try/finally` с вызовом `Dispose`/`DisposeAsync`.

Порядок `catch`-блоков значим: проверяются сверху вниз, более общий тип выше конкретного делает нижний недостижимым — компилятор на это ругается.

**`throw;` против `throw ex;`**

```csharp
try { Inner(); }
catch (Exception ex)
{
    throw;          // ПРАВИЛЬНО: стек сохранён целиком
    // throw ex;    // НЕПРАВИЛЬНО: стек обрезается по текущему методу
}
```

`throw ex;` перезаписывает `StackTrace` начиная с этой строки — в логах видно место перехвата, а не возникновения. Самая частая ошибка в обработке исключений. Когда нужно добавить контекст — оборачивают, а не перебрасывают:

```csharp
catch (NpgsqlException ex)
{
    throw new OrderStorageException($"Не удалось сохранить заказ {orderId}", ex);   // ex — innerException
}
```

Для переброса из другого потока или отложенно — `ExceptionDispatchInfo.Capture(ex).Throw()`, сохраняющий оригинальный стек.

### Иерархия — компактно

```
System.Exception
├── ArgumentException, ArgumentNullException, ArgumentOutOfRangeException   ← ошибка вызывающего
├── InvalidOperationException, ObjectDisposedException                     ← неверное состояние объекта
├── NullReferenceException, IndexOutOfRangeException, InvalidCastException ← ошибка программиста
├── IOException, HttpRequestException, TimeoutException, DbException       ← ошибка окружения
├── OperationCanceledException → TaskCanceledException                    ← штатная отмена, не сбой
├── AggregateException                                                     ← контейнер нескольких ошибок
├── OutOfMemoryException, StackOverflowException                           ← фатальные, не ловить
└── ApplicationException                                                   ← #устарело, не использовать
```

Три категории по способу реакции — важнее конкретных имён:

1. **Ошибки программиста** (`NullReferenceException`, `ArgumentException`, `InvalidOperationException`) — не ловить, а чинить. Единственное законное место перехвата — граница приложения, чтобы один сбойный запрос не уронил процесс.
2. **Ошибки окружения** (`IOException`, `HttpRequestException`, `TimeoutException`, `DbException`) — ловить и обрабатывать: повтор, разрыватель цепи, понятный ответ. Это и есть зона, ради которой существует `try/catch` в прикладном коде.
3. **Фатальные** (`OutOfMemoryException`, `StackOverflowException`) — ловить нельзя (`StackOverflowException` физически не перехватывается с .NET Framework 2.0) или бессмысленно (`OutOfMemoryException` формально ловится, но обработать нечем).

Особые случаи: `AggregateException` — контейнер из `Task.WhenAll`/`Parallel.For`, `await` бросает только первое исключение, остальные видны через `task.Exception!.InnerExceptions`. Исключения-обёртки (`TypeInitializationException`, `TargetInvocationException`, `DbUpdateException`) сами по себе бесполезны — смотреть надо в `InnerException`. `OperationCanceledException` — не ошибка, а штатный исход отмены; логировать как Information, не Error. `ApplicationException` признана неудачной идеей (BCL от неё не наследуется) — новые типы наследуют прямо от `Exception`.

### Свои типы исключений

Свой тип нужен ровно тогда, когда вызывающий должен **отличить** ситуацию от других и отреагировать иначе. Проверочный вопрос: **напишет ли кто-нибудь `catch` именно на него?** Если реакция такая же, как у прочих ошибок, — не нужен, хватает типа из BCL с хорошим сообщением. Обратная крайность тоже вредна: класс на каждый код ошибки, который никто не различает в `catch`.

```csharp
public sealed class InsufficientFundsException : Exception
{
    public InsufficientFundsException(long accountId, decimal requested, decimal available)
        : base($"На счёте {accountId} недостаточно средств: запрошено {requested}, доступно {available}")
    {
        AccountId = accountId;
        Requested = requested;
        Available = available;
    }

    public long AccountId { get; }
    public decimal Requested { get; }
    public decimal Available { get; }
}
```

Правила: `sealed`, если наследование не планируется; наследование напрямую от `Exception`; данные — в **свойствах**, а не в тексте сообщения (тесты и обработчик читают свойства, а не парсят строку); сообщение без секретов и персональных данных — оно уходит в логи. Для модуля обычно достаточно одного `abstract`-типа сверху (`OrdersException`) и конкретных под ним — глубже двух уровней иерархию исключений никто не использует в `catch`.

> [!info] Куда идёт индустрия
> `[Serializable]` и конструктор `(SerializationInfo, StreamingContext)` — наследие `BinaryFormatter`, который удалён из .NET по соображениям безопасности; члены помечены устаревшими (SYSLIB0051). В новом коде не нужны: исключения не пересекают границы процессов в бинарном виде.

## Решения

| Ситуация | Что делать | Почему |
|---|---|---|
| Ошибка программиста (`null`, неверный аргумент) | не ловить, чинить код | перехват маскирует дефект |
| Внешний сервис недоступен | ловить на границе интеграции | нужен повтор или разрыватель цепи |
| Фоновая задача | ловить в цикле воркера | необработанное исключение может уронить процесс |
| Ожидаемый бизнес-исход | не бросать вовсе | см. [[Когда исключение — плохой выбор]] |
| Нужно отличить ситуацию для отдельной реакции | свой `sealed`-тип от `Exception` | иначе вызывающий не отличит от прочих ошибок |
| Много кодов ошибок с одинаковой реакцией | один тип со свойством `Code` | десяток одинаковых классов никто не различает |
| Оборачивание внешнего исключения | новый тип + `innerException` | сохраняет первопричину и не течёт наружу зависимость |

> [!example] В ServiceShop
> В домене нет разрозненных исключений на каждое бизнес-правило: `Entity.CheckRuleAsync` проверяет `IBusinessRule.IsBrokenAsync()` и при нарушении бросает единственный тип — `BusinessRuleValidationException`. Это осознанный выбор в духе «свой тип нужен, если на него будет `catch`»: в `Startup.cs` этот один тип маппится в предсказуемый `ProblemDetails`-ответ, и не нужно перечислять десятки конкретных исключений в обработчике. Вариант `IBusinessRuleWithCode` добавляет машинный код ошибки, который прогоняется через `ILocalizer<PurchaseResource>` — тот же приём, что и `DomainException.Code` из книжного варианта, но обёрнутый в единый тип, а не в Result. Подробнее — [[ServiceShop: домен и тактический DDD]].

> [!warning] Где ошибаются
> - **`throw ex;` вместо `throw;`.** Обрезает стек по месту перехвата — первопричина теряется.
> - **Пустой `catch`.** Ошибка исчезает бесследно, система продолжает работать в неопределённом состоянии.
> - **`catch (Exception)` в середине стека.** Ловит и `OutOfMemoryException`, и `OperationCanceledException`, и `NullReferenceException` — то, что ловить нельзя или не нужно.
> - **Логирование `ex.Message` вместо `ex`.** Теряются тип, стек и `InnerException`; правильно — `logger.LogError(ex, "...")`.
> - **Свой тип «на всякий случай».** Если никто не пишет `catch` именно на него, это лишний класс без пользы.
> - **`ApplicationException` и `[Serializable]` из старых примеров.** Копируются из статей и легаси без переосмысления.
> - **Агент часто:** заворачивает новый код в `try/catch` с логированием и проглатыванием исключения «для надёжности» — метод возвращает успех, хотя операция не выполнена. Разобрано в [[Типовые ошибки агентов в .NET-коде]].

## Проверка на ревью

- В `catch` нет `throw ex;` — только `throw;` или оборачивание с `innerException`.
- Нет пустых `catch` без комментария и лога.
- `catch (Exception)` встречается только на границе приложения или в цикле фоновой службы, и это осознанно, а не по умолчанию.
- Логирование передаёт объект исключения (`LogError(ex, ...)`), а не `ex.Message` строкой.
- Новый тип исключения оправдан: есть место, где на него написан отдельный `catch`, либо он используется для машинного кода ошибки.
- `OperationCanceledException` не логируется как ошибка и не путается со сбоем.

## Проверь себя

> [!question]- Чем `throw;` отличается от `throw ex;`?
> `throw;` продолжает распространение текущего исключения с сохранением полного стека. `throw ex;` формально бросает заново, и рантайм перезаписывает `StackTrace`, начиная с текущей строки — история до места перехвата теряется. Для добавления контекста оборачивают в новый тип с `innerException`, а для переброса из другого места или потока используют `ExceptionDispatchInfo.Capture(ex).Throw()`.

> [!question]- Зачем нужны фильтры `when`, если можно проверить условие внутри `catch`?
> Из-за двухпроходной модели CLR: фильтр вычисляется на первом проходе, до разворачивания стека. Если он вернул `false`, кадры остаются нетронутыми и исключение ищет обработчик выше с сохранённым контекстом — отладчик остановится в точке возникновения. Вариант «поймать, проверить условие, при несоответствии `throw;`» стек уже развернул, и диагностика потеряна.

> [!question]- Когда стоит создавать свой тип исключения?
> Когда вызывающий код должен отличить эту ситуацию от прочих и отреагировать иначе: другой HTTP-код, ретрай или его отсутствие, показ конкретного сообщения. Проверочный вопрос — напишет ли кто-нибудь `catch` именно на этот тип. Второй повод — структурированные данные о проблеме в свойствах, чтобы обработчик и тесты не разбирали текст сообщения. Правило по глубине: один `abstract` тип на модуль плюс конкретные под ним, глубже не нужно.

> [!question]- Почему `ApplicationException` не используют, хотя формально она существует?
> Замысел был разделить системные и прикладные исключения, но разделение не дало ничего полезного: типы BCL от `ApplicationException` не наследуются, поэтому перехватить по ней «всё прикладное» невозможно. Официальная рекомендация — наследовать свои исключения напрямую от `Exception`. В легаси встречается, но в новом коде так не пишут.

## Разбор

### Найди проблему

```csharp
public async Task<Order?> LoadAsync(long id)
{
    try
    {
        var response = await _http.GetAsync($"/orders/{id}");
        var json = await response.Content.ReadAsStringAsync();
        return JsonSerializer.Deserialize<Order>(json);
    }
    catch (Exception ex)
    {
        _logger.LogError("Ошибка: " + ex.Message);
        throw ex;
    }
}
```

> [!success]- Решение
> Две ошибки сразу. `throw ex;` обрезает стек — на самом деле метод вообще не должен ничего ловить: он не может исправить сбой сети или сериализации, решение примет вызывающий или глобальный обработчик. Логирование через конкатенацию `ex.Message` теряет тип, стек и `InnerException`. Дополнительно: 404 стоит обрабатывать как обычный `null`, а не как исключение (см. [[Когда исключение — плохой выбор]]), и нужен `CancellationToken`.
> ```csharp
> public async Task<Order?> LoadAsync(long id, CancellationToken ct)
> {
>     var response = await _http.GetAsync($"/orders/{id}", ct);
>     if (response.StatusCode == HttpStatusCode.NotFound) return null;
>     response.EnsureSuccessStatusCode();
>     return await response.Content.ReadFromJsonAsync<Order>(cancellationToken: ct);
> }
> ```

### Ревью PR агента

Агент добавил новый тип для каждого кода ошибки платежей: `PaymentDeclinedException`, `PaymentTimeoutException`, `PaymentLimitException` — десять классов, у каждого свой конструктор с одним `string message`, обработка на границе везде одинаковая (409 + текст).

> [!success]- Решение
> Вернуть на доработку. Ни один из десяти типов не проверяется отдельным `catch` — реакция одинакова для всех, значит различие не нужно на уровне типа. Правильно: один тип `PaymentException` со свойством `Code` (`"payment.declined"`, `"payment.timeout"`, `"payment.limit_exceeded"`) и данными в свойствах, а не в строке сообщения. Десять почти одинаковых классов увеличивают площадь кода без пользы для вызывающего.

## Итог

- Исключение разворачивает стек до ближайшего `catch`; `finally` выполняется всегда, кроме фатального завершения процесса.
- `throw;` сохраняет стек, `throw ex;` обрезает; контекст добавляют оборачиванием с `innerException`.
- Три категории по реакции: ошибки программиста — чинить, ошибки окружения — обрабатывать, фатальные — не ловить.
- `ApplicationException` и деление `SystemException`/`ApplicationException` устарели — свои типы наследуют от `Exception`.
- Свой тип оправдан, только если на него напишут отдельный `catch` или нужны структурированные данные в свойствах.
- Логировать объект исключения, а не `ex.Message`, и один раз — на границе.
