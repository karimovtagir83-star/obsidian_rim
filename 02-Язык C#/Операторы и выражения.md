# Операторы и выражения

> [!abstract] Коротко
> Выражение — это код, который вычисляется в значение; инструкция — код, который выполняет действие. В C# выражений становится всё больше: `switch`, `with`, лямбды, паттерны — всё это выражения, и именно поэтому современный C# короче старого. Знать нужно три вещи: приоритеты (чтобы не расставлять скобки наугад), порядок вычисления (слева направо, с короткими замыканиями у `&&`, `||`, `??`, `?.`) и то, что операторы работают с типами операндов, а не с типом результата.

## Зачем это нужно

Ошибки в этой теме не выглядят как ошибки — код компилируется и делает не то:

```csharp
if (user != null & user.IsActive)   // & вместо && → NullReferenceException
if (a == b == c)                    // компилируется для bool, но считает не то, что кажется
int avg = (a + b) / 2;              // переполнение при больших a и b
var name = user?.Name ?? "гость";    // а вот это правильно — и надо понимать, почему
```

Второй мотив — читаемость. Половина «умного» кода нечитаема ровно потому, что автор полагался на приоритеты, которые помнит он один.

## Выражение и инструкция

```csharp
int x = 2 + 3 * 4;         // 2 + 3 * 4 — выражение, вся строка — инструкция объявления
Console.WriteLine(x);       // вызов метода — выражение; со ; — инструкция-выражение
if (x > 10) { }             // инструкция; x > 10 внутри — выражение
```

Выражение имеет тип и значение. Инструкция — нет. Ключевая тенденция языка: конструкции переезжают из инструкций в выражения, потому что выражения композируются.

```csharp
// Инструкция switch (была всегда)
string label;
switch (code)
{
    case 200: label = "OK"; break;
    default:  label = "Прочее"; break;
}

// Выражение switch (C# 8) — то же самое, но возвращает значение
string label2 = code switch
{
    200 => "OK",
    404 => "Не найдено",
    _   => "Прочее"
};

// Выражение можно сразу передать, вернуть, положить в инициализатор
Log(code switch { >= 500 => LogLevel.Error, >= 400 => LogLevel.Warning, _ => LogLevel.Information });
```

Подробно про паттерны в этих выражениях — [[Pattern matching]] и [[Условия и ветвление]].

## Таблица приоритетов

От высшего к низшему. Внутри одной строки операторы равноприоритетны и вычисляются слева направо (кроме присваивания и `?:` — они правоассоциативны).

| Категория | Операторы |
|---|---|
| Первичные | `x.y` `x?.y` `x[i]` `f(x)` `x++` `x--` `new` `typeof` `nameof` `sizeof` `checked` `unchecked` `default` |
| Унарные | `+x` `-x` `!x` `~x` `++x` `--x` `(T)x` `await` `&x` `*x` |
| Мультипликативные | `*` `/` `%` |
| Аддитивные | `+` `-` |
| Сдвиги | `<<` `>>` `>>>` |
| Отношения и проверка типа | `<` `>` `<=` `>=` `is` `as` |
| Равенство | `==` `!=` |
| Побитовое AND | `&` |
| Побитовое XOR | `^` |
| Побитовое OR | `\|` |
| Логическое AND | `&&` |
| Логическое OR | `\|\|` |
| Null-объединение | `??` |
| Условный | `c ? a : b` |
| Присваивание и лямбда | `=` `+=` `-=` `*=` `/=` `%=` `&=` `\|=` `^=` `<<=` `>>=` `>>>=` `??=` `=>` |

Три места, где приоритеты обычно удивляют:

```csharp
// 1. Побитовые ниже сравнений — типичный источник ошибки при работе с флагами
if (flags & Flags.Admin != 0) { }        // Ошибка компиляции: сначала != , потом &
if ((flags & Flags.Admin) != 0) { }      // скобки обязательны

// 2. ?? ниже || — значит сначала логика, потом объединение
bool ok = a || b ?? false;               // читается как a || (b ?? false)

// 3. Сдвиг ниже сложения
int y = 1 << 2 + 3;                      // это 1 << 5 == 32, а не (1 << 2) + 3 == 7
```

Практическое правило: если приходится вспоминать приоритет — поставь скобки. Компилятор от них ничего не потеряет, а читатель выиграет.

## Арифметика

```csharp
Console.WriteLine(7 / 2);        // 3  — целочисленное деление, остаток отбрасывается
Console.WriteLine(7 % 2);        // 1  — остаток
Console.WriteLine(7 / 2.0);      // 3,5
Console.WriteLine(-7 / 2);       // -3 — округление к нулю, а не к минус бесконечности
Console.WriteLine(-7 % 2);       // -1 — знак остатка совпадает со знаком делимого
Console.WriteLine(7 % -2);       // 1
```

Знак остатка в C# берётся от делимого — это отличается от математического «остатка по модулю» и от поведения Python. Отсюда классический баг с индексами по кругу:

```csharp
int Next(int i, int n) => (i + 1) % n;            // работает
int Prev(int i, int n) => (i - 1) % n;            // при i == 0 даёт -1, а не n-1
int PrevOk(int i, int n) => (i - 1 + n) % n;      // правильный «модуль»
```

### Инкремент и декремент

```csharp
int a = 5;
Console.WriteLine(a++);   // 5, потом a == 6  — постфикс: сначала значение, потом изменение
Console.WriteLine(++a);   // 7                — префикс: сначала изменение, потом значение

// Выражения вроде этого читать невозможно, а поведение зависит от порядка вычисления:
int i = 1;
int r = i++ + ++i;        // 1 + 3 == 4. Компилируется, но в код такое писать нельзя.
```

`x++` и `++x` в отдельной инструкции идентичны — разница только в значении выражения. И отдельно: `i++` не является атомарной операцией, в многопоточном коде нужен `Interlocked.Increment` ([[Interlocked, volatile и модель памяти]]).

### Составное присваивание

```csharp
int x = 10;
x += 5;                   // x = x + 5

byte b = 200;
// b = b + 50;            // Ошибка: b + 50 имеет тип int
b += 50;                  // Компилируется! Составное присваивание содержит неявное приведение
Console.WriteLine(b);      // Вывод: 250
b += 50;                  // и молча переполняется: 250 + 50 = 300 → 44
Console.WriteLine(b);      // Вывод: 44
```

Это редкое место, где C# делает скрытое сужающее преобразование. С C# 14 составные операторы можно определять для своих типов явно (`operator +=`), что важно для изменяемых структур и буферов — раньше `+=` всегда разворачивался в «создать новое значение и присвоить».

## Логические операторы и короткое замыкание

```csharp
bool Both() => Check1() && Check2();   // Check2 не вызовется, если Check1 вернул false
bool Any()  => Check1() || Check2();   // Check2 не вызовется, если Check1 вернул true

bool BothStrict() => Check1() & Check2();  // ОБА вызовутся всегда
```

`&&`/`||` вычисляют правый операнд только если это нужно для результата (short-circuit). `&`/`|` для `bool` вычисляют оба. Из-за этого:

```csharp
if (user != null && user.IsActive) { }   // безопасно
if (user != null &  user.IsActive) { }   // NullReferenceException при user == null

if (index < array.Length && array[index] > 0) { }  // безопасно, порядок важен
```

Короткое замыкание — не оптимизация, а часть семантики: на неё опираются проверки на `null` и на границы. Обратная сторона — побочные эффекты в правом операнде могут не выполниться, поэтому вызовы, которые обязаны произойти, в условие не ставят.

## Работа с null

```csharp
string? name = GetName();

// ?? — вернуть левое, если не null, иначе правое
string display = name ?? "гость";

// ??= — присвоить, только если сейчас null
name ??= "гость";

// ?. — обратиться к члену, только если не null; иначе всё выражение null
int? length = name?.Length;
string? upper = customer?.Address?.City?.ToUpperInvariant();

// ?[] — то же для индексатора
var first = list?[0];

// Комбинация — самая частая идиома
int len = customer?.Name?.Length ?? 0;
```

Два важных свойства `?.`:

1. **Тип результата становится nullable.** `person?.Age` для `int Age` даёт `int?`, поэтому дальше нужен `?? 0` или проверка.
2. **Цепочка обрывается целиком.** В `a?.B.C.D` если `a` равно null, то `B.C.D` не вычисляется вовсе — второй `?.` не нужен для безопасности, но нужен, если сам `B` может быть null.

С C# 14 появилось **null-conditional assignment** — `?.` работает и слева от присваивания:

```csharp
customer?.Order = newOrder;         // присвоить, только если customer не null (C# 14)
customer?.Total += 10;               // составные присваивания тоже
// customer?.Count++;                // а вот ++ и -- не поддерживаются
```

Раньше это писали как `if (customer is not null) customer.Order = newOrder;`. Отдельно стоит помнить: `?.` для событий и делегатов — стандартный способ безопасного вызова: `Changed?.Invoke(this, args)`.

> [!warning] `??` не спасает от исключения внутри левой части
> ```csharp
> var value = dictionary["key"] ?? "default";   // KeyNotFoundException, если ключа нет:
>                                               // индексатор бросает исключение, а не возвращает null
> var ok = dictionary.TryGetValue("key", out var v) ? v : "default";
> var ok2 = dictionary.GetValueOrDefault("key", "default");
> ```

## Сравнение и равенство

```csharp
Console.WriteLine(5 == 5.0);          // True — int повышается до double
Console.WriteLine("a" == "a");        // True — у string переопределён ==, сравнение по содержимому

object o1 = "текст";
object o2 = string.Concat("те", "кст");
Console.WriteLine(o1 == o2);          // False! Операторы разрешаются статически:
                                      // для object это сравнение ссылок
Console.WriteLine(o1.Equals(o2));      // True — виртуальный вызов, у String он по содержимому
Console.WriteLine(ReferenceEquals(o1, o2));  // False
```

Это одно из самых частых непониманий в C#: **`==` разрешается на этапе компиляции по статическому типу операндов**, а `Equals` — виртуальный вызов, разрешаемый в рантайме по фактическому типу. Отсюда: сравнивая через `object` или через дженерик-параметр без ограничений, надо использовать `Equals`/`EqualityComparer<T>.Default`, а не `==`.

Про правила равенства для своих типов — [[Object: Equals, GetHashCode, ToString]] и [[Сравнение объектов: IEquatable, IComparable, компараторы]]. Для строк отдельная тема — сравнение с учётом культуры и регистра, см. [[Строки и работа с текстом]].

```csharp
// Цепочка сравнений не работает как в математике:
// if (0 <= x <= 10)          // Ошибка: результат (0 <= x) — bool, его нельзя сравнить с int
if (0 <= x && x <= 10) { }     // так
if (x is >= 0 and <= 10) { }   // или паттерном (C# 9) — читается лучше
```

## Проверка и преобразование типов

```csharp
object value = "текст";

// is — проверка с возможным объявлением переменной
if (value is string s && s.Length > 3)
    Console.WriteLine(s.ToUpperInvariant());

// as — попытка привести; при неудаче null (только для ссылочных и nullable)
string? maybe = value as string;

// приведение — при неудаче InvalidCastException
string forced = (string)value;

// typeof — Type по имени типа (этап компиляции)
Console.WriteLine(typeof(string).FullName);     // System.String
// GetType — фактический тип объекта (рантайм)
Console.WriteLine(value.GetType().Name);        // String

// nameof — имя символа строкой, проверяется компилятором
Console.WriteLine(nameof(value));               // "value"
Console.WriteLine(nameof(List<>));              // "List"  (C# 14: несвязанные дженерики)

// sizeof — размер значимого типа в байтах
Console.WriteLine(sizeof(decimal));             // 16
```

Выбор между `is`, `as` и приведением: `is` — когда решение зависит от типа (и особенно в паттернах); `as` + проверка на null — когда тип ожидаемо может не совпасть; жёсткое приведение — когда несовпадение типа это ошибка программиста, и падение с `InvalidCastException` предпочтительнее тихого `null`.

`nameof` — обязательная привычка вместо строковых литералов: имена аргументов в исключениях, ключи логов, имена свойств в `INotifyPropertyChanged`. При переименовании через рефакторинг обновится автоматически, а строка — нет.

## Тернарный оператор и `switch`-выражение

```csharp
string result = count > 0 ? "есть" : "нет";

// Правоассоциативен: вложенность справа
string grade = score >= 90 ? "A"
             : score >= 75 ? "B"
             : score >= 60 ? "C"
             : "F";
// Больше двух-трёх уровней — признак того, что нужен switch-выражение
```

Требование к тернарному оператору: обе ветви должны приводиться к общему типу. `cond ? 1 : "текст"` не скомпилируется; `cond ? 1 : null` — тоже (нет общего типа), нужно `(int?)1 : null`.

## Прочие операторы, которые встречаются каждый день

```csharp
// => — лямбда и определение члена через выражение
Func<int, int> square = x => x * x;
public string FullName => $"{First} {Last}";     // expression-bodied property

// with — копия record с изменением (C# 9)
var updated = order with { Status = OrderStatus.Paid };

// .. — диапазон, ^ — индекс с конца (C# 8)
int[] data = [1, 2, 3, 4, 5];
var tail = data[2..];            // [3, 4, 5]
var last = data[^1];             // 5

// [..] — коллекционные выражения и spread (C# 12)
int[] combined = [0, ..data, 6];  // [0, 1, 2, 3, 4, 5, 6]

// await — не оператор в привычном смысле, но участвует в выражениях
var content = await client.GetStringAsync(url);

// checked и unchecked — контекст переполнения
int safe = checked(a * b);        // OverflowException вместо тихого заворачивания
```

> [!warning] Подводные камни
> - **`&` вместо `&&` в проверках на null.** Компилируется, работает «через раз» — падает только когда левая часть ложна. Наоборот, `&` иногда пишут намеренно (чтобы выполнить оба побочных эффекта), и такой код обязательно надо комментировать, иначе его «исправят».
> - **Переполнение в середине выражения.** `(a + b) / 2` при `a = b = int.MaxValue` даёт отрицательное среднее. Правильно: `a + (b - a) / 2`.
> - **`==` через `object` или дженерик.** Сравнивает ссылки, а не значения. В дженерик-коде — `EqualityComparer<T>.Default.Equals(x, y)`.
> - **`==` для `float`/`double`.** Погрешность двоичного представления делает такое сравнение бессмысленным; `NaN != NaN` даже сам с собой.
> - **Порядок вычисления аргументов.** Гарантирован слева направо, но полагаться на побочные эффекты в аргументах (`Foo(i++, i)`) — путь к нечитаемому коду. Компилятор прав, читатель нет.
> - **`?.` в условии.** `if (customer?.IsActive)` не компилируется: тип `bool?`, а `if` требует `bool`. Нужно `== true` или `is true` — и это полезная строгость: она заставляет решить, чем считать null.
> - **Составное присваивание скрывает сужение.** `byte += int` компилируется и переполняется молча. То же с `short`, `sbyte`, `char`.

> [!example] Как делают в бою
> В продовом коде выигрывают три привычки. Первая — скобки вместо памяти о приоритетах: `(flags & Mask) != 0`, `(a + b) * c`. Ревьюеры не должны держать в голове таблицу из 14 строк.
> Вторая — паттерны вместо цепочек сравнений: `if (age is >= 18 and < 65)` вместо `if (age >= 18 && age < 65)`, `if (code is 400 or 404 or 409)` вместо трёх `||`. Читается как условие на естественном языке и не даёт опечататься в имени переменной.
> Третья — `nameof` вместо строк везде, где речь об именах кода: `ArgumentNullException.ThrowIfNull(order)` сам подставит имя параметра, `logger.LogInformation("Обработан {OrderId}", order.Id)` — структурные логи, а не конкатенация.
> Отдельно: длинное булево выражение в `if` почти всегда стоит вынести в именованную переменную или метод — `bool canRefund = order.IsPaid && !order.IsShipped && order.PaidAt > cutoff;`. Имя объясняет смысл, которого в операторах нет.

## Вопросы с собеседований

> [!question]- Чем `&&` отличается от `&`?
> `&&` — логическое И с коротким замыканием: правый операнд вычисляется только если левый истинен. `&` для `bool` — тоже логическое И, но оба операнда вычисляются всегда; для целочисленных типов это побитовое И. Практическая разница в двух вещах. Во-первых, безопасность: `if (x != null && x.IsActive)` работает, а с `&` бросит `NullReferenceException`. Во-вторых, побочные эффекты: если правая часть вызывает метод, который обязан выполниться, короткое замыкание его пропустит. Приоритет у `&` выше, чем у `&&` и `==`, поэтому в битовых проверках скобки обязательны: `(flags & Mask) != 0`.

> [!question]- Почему `o1 == o2` для двух одинаковых строк через `object` даёт False?
> Потому что операторы в C# — статические методы, и перегрузка выбирается компилятором по **статическим** типам операндов. Если переменные объявлены как `object`, компилятор выбирает `==` для `object`, то есть сравнение ссылок; перегрузка `String.op_Equality` при этом не рассматривается вообще. Метод `Equals` наоборот виртуальный: вызов разрешается в рантайме по фактическому типу, поэтому `o1.Equals(o2)` даёт True. Отсюда правило: в обобщённом коде и при работе через базовые типы сравнивать надо через `Equals` или `EqualityComparer<T>.Default`, а `==` использовать, когда статические типы конкретны.

> [!question]- Что такое короткое замыкание и где на него опираются?
> Это правило вычисления `&&`, `||`, `??`, `?.` и `?[]`: правая часть вычисляется только тогда, когда её результат может повлиять на итог. На этом построены самые распространённые защитные конструкции: проверка на null перед разыменованием, проверка индекса перед обращением к массиву, дешёвая проверка перед дорогой. Это часть семантики языка, а не оптимизация компилятора, поэтому на неё можно полагаться. Обратная сторона — в правую часть нельзя помещать обязательные побочные эффекты.

> [!question]- Чем `is`, `as` и приведение `(T)x` отличаются?
> `is` проверяет совместимость типа и возвращает `bool`, при этом умеет сразу объявить переменную (`x is string s`) и раскрывать паттерны — константные, реляционные, списочные. `as` пытается привести и возвращает `null` при неудаче; работает только для ссылочных типов и `Nullable<T>`, не выполняет пользовательских преобразований. Приведение `(T)x` бросает `InvalidCastException` при несовпадении и умеет вызывать определённые пользователем операторы преобразования. Выбор по смыслу: если несовпадение типа — нормальная ситуация, `is`/`as`; если это ошибка программиста, лучше жёсткое приведение, потому что падение сразу лучше, чем `null`, всплывающий десятью строками ниже.

> [!question]- Как вычислить среднее двух `int` без переполнения?
> `(a + b) / 2` переполняется, когда сумма выходит за границы `int`: при `a = b = int.MaxValue` результат отрицательный, и никакого исключения по умолчанию не будет — контекст `unchecked`. Варианты: `a + (b - a) / 2` (работает, если `a <= b`), приведение к более широкому типу `(int)(((long)a + b) / 2)`, или беззнаковый трюк `(int)(((uint)a + (uint)b) >> 1)` для неотрицательных значений. Именно эта ошибка была в реализации бинарного поиска в JDK и во множестве книг — то есть в реальном коде она живёт годами, потому что проявляется только на больших значениях.

## Задачи

### Задача 1. Что выведет

```csharp
int i = 5;
Console.WriteLine(i++ + i++);
Console.WriteLine(i);
Console.WriteLine(10 / 4 * 4);
Console.WriteLine(-9 % 4);
Console.WriteLine(1 << 3 + 1);
```

> [!success]- Решение
> `11`, `7`, `8`, `-1`, `16`.
> Первая строка: операнды вычисляются слева направо, первый `i++` даёт 5 (i становится 6), второй даёт 6 (i становится 7) — сумма 11. Вторая: i равно 7.
> Третья: приоритет `*` и `/` одинаков, вычисление слева направо: `10 / 4` — целочисленное деление, 2; `2 * 4` — 8. Здесь потеря точности случается до умножения.
> Четвёртая: знак остатка берётся от делимого, поэтому −1, а не 3.
> Пятая: `+` приоритетнее сдвига, поэтому это `1 << 4` = 16, а не `(1 << 3) + 1` = 9.
> Вывод по всем пяти: код, полагающийся на приоритеты и порядок вычисления, технически определён, но нечитаем. В рабочем коде такие выражения разбивают на строки со скобками.

### Задача 2. Починить проверку

Метод должен вернуть первый непустой элемент, приведённый к верхнему регистру, или «нет данных».

```csharp
static string FirstUpper(List<string?>? items)
{
    return items[0].ToUpperInvariant() ?? "нет данных";
}
```

> [!success]- Решение
> Проблем три: `items` может быть null, элемент может быть null, а `??` применяется к результату `ToUpperInvariant()`, который никогда не бывает null — то есть защита стоит не там, где нужно.
> ```csharp
> static string FirstUpper(List<string?>? items)
> {
>     var first = items?.FirstOrDefault(s => !string.IsNullOrWhiteSpace(s));
>     return first?.ToUpperInvariant() ?? "нет данных";
> }
> ```
> Ключевая идея: `?.` обрывает всю цепочку, поэтому `first?.ToUpperInvariant()` даёт `null` при отсутствии значения, и уже этот `null` перехватывается `??`. Порядок важен: `??` должен применяться к тому выражению, которое реально может быть null. Если включены nullable reference types, компилятор укажет на исходную версию предупреждением ещё до запуска — [[Nullable reference types]].

### Задача 3. Битовые флаги

Есть маска прав: 1 — чтение, 2 — запись, 4 — удаление. Напиши проверки «есть ли право на запись», «есть ли хотя бы одно из записи/удаления», «добавить право удаления», «снять право записи».

> [!success]- Решение
> ```csharp
> const int Read = 1, Write = 2, Delete = 4;
> int rights = Read | Write;                       // 3
>
> bool canWrite   = (rights & Write) != 0;          // скобки обязательны: & ниже !=
> bool canModify  = (rights & (Write | Delete)) != 0;
> rights |= Delete;                                 // добавить: 7
> rights &= ~Write;                                 // снять: инвертируем маску и накладываем → 5
>
> Console.WriteLine(Convert.ToString(rights, 2));    // Вывод: 101
> ```
> Три идиомы, которые стоит запомнить: `|` — установить бит, `& ~маска` — снять бит, `& маска != 0` — проверить. В реальном коде вместо констант используют `[Flags] enum` с методом `HasFlag` или тем же битовым тестом (он быстрее, потому что `HasFlag` до .NET Core делал упаковку); см. [[Перечисления (enum)]].

## Итог

- Выражение даёт значение, инструкция — нет. Современный C# двигает конструкции в сторону выражений: `switch`, `with`, лямбды.
- Приоритеты помнить целиком не нужно — нужно ставить скобки там, где приходится вспоминать. Отдельно опасны битовые операторы: они ниже сравнений.
- Целочисленное деление отбрасывает остаток, знак остатка берётся от делимого.
- `&&`, `||`, `??`, `?.` вычисляют правую часть только при необходимости — на этом держатся все проверки на null.
- `==` разрешается статически по типам операндов; `Equals` виртуален. Через `object` и дженерики сравнивать надо `Equals`.
- `?.` делает результат nullable и обрывает всю цепочку; с C# 14 работает и в левой части присваивания.
- `nameof` вместо строковых литералов — бесплатная защита от рассинхронизации при рефакторинге.
