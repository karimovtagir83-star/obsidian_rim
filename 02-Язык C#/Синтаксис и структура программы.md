# Синтаксис и структура программы

> [!abstract] Короток
> C# — язык со свободным форматом: компилятор видит не строки и отступы, а поток токенов, разделённых пунктуаторами и точками с запятой. Файл `.cs` имеет жёсткий порядок верхнеуровневых элементов (extern alias, using, глобальные атрибуты, namespace, типы), а всё остальное — блоки `{}`, объявления и выражения. Roslyn превращает этот текст в синтаксическое дерево, связывает имена с символами и генерирует IL. Стиль (Allman-скобки, PascalCase, `_camelCase`) на компиляцию не влияет, но фиксируется в `.editorconfig` и проверяется в CI.

## Зачем это нужно

Синтаксис — это контракт между тобой и компилятором. Пока не знаешь, где заканчивается токен и начинается пунктуатор, любая ошибка выглядит как магия: «почему `CS1002` показывает на строку ниже той, где я забыл точку с запятой?» Ответ прост — парсер читает поток токенов, а не строки, и ругается там, где встретил неожиданный токен.

Вторая причина — командная работа. В C# есть десятки способов написать одно и то же: блочный namespace или file-scoped, `var` или явный тип, скобки Allman или K&R. Без зафиксированного соглашения ревью превращается в спор о запятых. Поэтому индустрия договорилась: соглашения из `dotnet/runtime` + `.editorconfig` в корне репозитория + `dotnet format` в CI.

Третья — эволюция. Файл на C# 1.0 и файл на C# 14 выглядят по-разному настолько, что легаси читается с трудом. Знать, что `namespace X;` — это C# 10, а `dotnet run app.cs` — .NET 10, значит понимать, какой минимальный SDK нужен проекту.

## Лексика: из чего состоит текст программы

Компилятор сначала разбивает исходник на **лексемы (токены)**. Токены бывают пяти видов:

| Вид токена | Примеры | Комментарий |
|---|---|---|
| Идентификаторы | `userId`, `Order`, `_cache`, `@class` | имена, которые придумал ты |
| Ключевые слова | `class`, `if`, `return`, `static` | зарезервированы языком |
| Литералы | `42`, `3.14m`, `"текст"`, `true`, `null`, `'a'` | значения прямо в коде |
| Операторы | `+`, `=>`, `??=`, `?.` | подробнее — [[Операторы и выражения]] |
| Пунктуаторы | `{ } ( ) [ ] ; , . :` | структурируют код |

Всё, что между токенами, — **тривия (trivia)**: пробелы, табы, переводы строк, комментарии, директивы препроцессора. Roslyn не выбрасывает тривию, а привязывает её к соседним токенам — именно поэтому IDE умеет переформатировать код, не теряя комментарии.

### Идентификаторы и Unicode

Идентификатор начинается с буквы или `_` и продолжается буквами, цифрами и `_`. «Буква» здесь — по Unicode, а не по ASCII, поэтому это валидный C#:

```csharp
int счётчик = 0;      // кириллица в идентификаторе допустима
счётчик++;
Console.WriteLine(счётчик);   // Вывод: 1

int abc = 5;     // Unicode-escape в идентификаторе: это ровно "abc"
Console.WriteLine(abc);       // Вывод: 5
```

Работает — но в продакшене так не пишут: диффы, поиск по коду и стек-трейсы становятся нечитаемыми в смешанной раскладке. Единственное живое применение — учебные примеры и генерируемый код.

### `@`-экранирование ключевых слов

Если имя совпадает с ключевым словом, ставь `@`. Префикс — часть записи, а не часть имени: идентификатор `@class` — это идентификатор `class`.

```csharp
// Параметры называются "class" и "event" — иначе не скомпилируется
public static string Describe(string @class, int @event)
{
    return $"{@class}#{@event}";
}

Console.WriteLine(Describe("Order", 7));      // Вывод: Order#7
Console.WriteLine(nameof(@class) is "class"); // в теле метода вернуло бы True
```

Реальные случаи: маппинг JSON/HTML-полей (`@class`, `@for`, `@checked` в Razor), интероп с языками, где эти слова не зарезервированы, и генераторы кода, которые не хотят анализировать имена.

## Ключевые слова vs контекстные ключевые слова

Зарезервированных слов в C# порядка восьми десятков (`class`, `int`, `foreach`, `sealed`, …) — их нельзя использовать как идентификаторы никогда. Но язык растёт, а ломать чужой код нельзя, поэтому все новые слова добавляют **контекстными**: они специальные только в определённой позиции, а в остальных — обычные имена.

| Слово | С какой версии | Где имеет особый смысл | Можно ли назвать так переменную |
|---|---|---|---|
| `var` | C# 3 | тип локальной переменной | да, если нет типа с таким именем |
| `value` | C# 1 | внутри `set`/`init`-аксессора | да, вне аксессора |
| `yield` | C# 2 | `yield return` / `yield break` | да |
| `async` / `await` | C# 5 | `async` — модификатор, `await` — только в `async`-теле | да, вне async-метода |
| `record` | C# 9 | `record class` / `record struct` | да |
| `nameof` | C# 6 | оператор `nameof(x)` | да (тогда `nameof` перестанет работать как оператор) |
| `file` | C# 11 | модификатор типа верхнего уровня | да |
| `field` | **C# 14** | внутри аксессора свойства | да, но см. предупреждение ниже |

`field` — самый свежий и самый коварный из них. В C# 14 он даёт прямой доступ к автогенерируемому backing-полю, из-за чего свойство с логикой больше не требует ручного поля:

```csharp
public class Temperature
{
    // Раньше: приватное поле + свойство. Сейчас: только свойство.
    public int Celsius
    {
        get => field;
        set
        {
            if (value < -273)
            {
                throw new ArgumentOutOfRangeException(nameof(value), "Ниже абсолютного нуля");
            }

            field = value;
        }
    }
}

var t = new Temperature { Celsius = 20 };
Console.WriteLine(t.Celsius);   // Вывод: 20
```

Если в классе уже есть поле с именем `field`, внутри аксессора теперь выиграет новое ключевое слово. Пиши `this.field` или `@field`, чтобы обратиться к своему полю; компилятор в таких местах выдаёт предупреждение. Подробный разбор — в [[Новое в C# 12, 13, 14]].

## Разделители, блоки и точка с запятой

- `;` завершает **инструкцию (statement)**. Пустая инструкция `;` валидна и потому опасна: `if (x);` компилируется и не делает ничего.
- `{ }` образуют **блок** — он одновременно и группировка инструкций, и **область видимости**. Переменная, объявленная в блоке, вне его не существует.
- Whitespace не значим: перевод строки — такой же разделитель, как пробел. Всю программу можно записать в одну строку.

```csharp
// Валидно, но нечитаемо: whitespace не влияет на семантику
int a=1;int b=2;if(a<b){Console.WriteLine("меньше");}   // Вывод: меньше

{
    int scoped = 10;        // живёт только внутри этого блока
    Console.WriteLine(scoped);  // Вывод: 10
}
// Console.WriteLine(scoped); // CS0103: имя не существует в текущем контексте
```

Исключение из «whitespace незначим» одно: внутри строковых литералов и в raw string literals (`"""`), где отступ закрывающих кавычек задаёт срез общего отступа. Об этом — в [[Типы данных и литералы]].

## Комментарии и XML-документация

| Форма | Синтаксис | Назначение |
|---|---|---|
| Однострочный | `// текст` | пояснение по месту |
| Блочный | `/* текст */` | временное отключение куска, шапки файлов; не вкладывается |
| XML-doc | `/// <summary>…` | документация API, попадает в IntelliSense и в `.xml`-файл |

XML-doc — не декоративный: компилятор его парсит, проверяет `cref` и складывает в отдельный XML рядом со сборкой.

```csharp
/// <summary>
/// Переводит сумму между счетами. Операция атомарна на уровне БД.
/// </summary>
/// <param name="fromId">Идентификатор счёта-источника.</param>
/// <param name="amount">Сумма перевода, строго больше нуля.</param>
/// <returns>Новый баланс счёта-источника.</returns>
/// <exception cref="ArgumentOutOfRangeException">
/// Если <paramref name="amount"/> меньше или равна нулю.
/// </exception>
/// <seealso cref="Account"/>
public decimal Transfer(int fromId, decimal amount)
{
    if (amount <= 0)
    {
        throw new ArgumentOutOfRangeException(nameof(amount));
    }

    return 0m; // упрощённо
}
```

Полезные теги: `<summary>`, `<param>`, `<returns>`, `<exception cref="">`, `<remarks>`, `<example>`, `<see cref=""/>` (ссылка внутри текста), `<paramref name=""/>`, `<typeparam>`, и `<inheritdoc/>` — подтягивает документацию базового члена или реализуемого интерфейса, чтобы не копировать её в каждую реализацию.

```csharp
public interface IClock
{
    /// <summary>Текущее время в UTC.</summary>
    DateTimeOffset UtcNow { get; }
}

public sealed class SystemClock : IClock
{
    /// <inheritdoc/>
    public DateTimeOffset UtcNow => DateTimeOffset.UtcNow;
}
```

Генерация XML включается свойством проекта:

```xml
<PropertyGroup>
  <GenerateDocumentationFile>true</GenerateDocumentationFile>
  <!-- CS1591 — «нет XML-комментария у публичного члена». В библиотеке оставь,
       в приложении обычно глушат, иначе тонешь в предупреждениях. -->
  <NoWarn>$(NoWarn);CS1591</NoWarn>
</PropertyGroup>
```

Практический бонус .NET 10: если `GenerateDocumentationFile` включён, генератор OpenAPI берёт `<summary>`, `<param>` и `<returns>` прямо из XML-комментариев эндпоинтов и DTO — через source generator, без рефлексии и без чтения `.xml` в рантайме. Описания в Swagger UI появляются сами. Детали — [[OpenAPI и Swagger в .NET 10]].

## Анатомия файла .cs

Порядок верхнеуровневых элементов зафиксирован спецификацией и нарушать его нельзя — будет ошибка компиляции:

```
1. extern alias  — псевдоним для сборки при конфликте имён (редко)
2. using         — сначала global using, затем обычные
3. [assembly: …] — глобальные атрибуты сборки/модуля
4. namespace     — объявление пространства имён
5. типы          — class, struct, record, interface, enum, delegate
```

```csharp
extern alias LegacyJson;                    // 1) крайне редко, при конфликте версий сборок

global using System.Text.Json;              // 2a) global using — только до обычных
using System.Diagnostics.CodeAnalysis;      // 2b) обычные using
using Log = Serilog.Log;                    // 2c) алиас

[assembly: SuppressMessage("Design", "CA1050")]   // 3) атрибут уровня сборки

namespace Billing.Domain;                   // 4) file-scoped namespace (C# 10)

public sealed class Invoice                 // 5) тип
{
    public required int Number { get; init; }
}
```

Правила, о которые спотыкаются:
- `global using` обязан идти **раньше** любого не-global `using` в файле, иначе `CS8915`.
- Атрибуты сборки идут после `using`, но до объявлений типов.
- В файле может быть несколько namespace-блоков, но **file-scoped namespace — ровно один и на весь файл**.

Про сами директивы, алиасы и неявные using — [[Namespace, using, глобальные using]].

### file-scoped namespace vs блочный

```csharp
// Раньше (C# 1–9): блочный. Лишний уровень отступа на весь файл.
namespace Billing.Domain
{
    public sealed class Invoice { }
}

// Сейчас (C# 10+): file-scoped. Отступ на 4 пробела меньше, а смысл тот же.
namespace Billing.Domain;

public sealed class Invoice { }
```

| Критерий | Блочный `namespace X { }` | File-scoped `namespace X;` |
|---|---|---|
| Версия | C# 1.0 | C# 10 (.NET 6+) |
| Сколько в файле | несколько, можно вкладывать | ровно один |
| Отступ содержимого | +1 уровень | без отступа |
| Область действия | до закрывающей `}` | до конца файла |
| Совместим с `extern alias`/`using` сверху | да | да |
| Правило анализатора | — | IDE0161 переводит на file-scoped |
| Когда нужен старый | генераторы, два namespace в одном файле, `unsafe`-обёртки | — |

Почему перешли: один namespace на файл — норма в 99 % кода, а лишний уровень вложенности съедал ширину строки. `dotnet new` в .NET 10 генерирует file-scoped по умолчанию.

### Модификатор `file` (C# 11)

`file` ограничивает видимость типа **одним исходным файлом** — даже внутри одной сборки другой файл его не увидит.

```csharp
// Helpers.cs
file sealed class Buffer          // виден только в Helpers.cs
{
    public int Size => 4096;
}

public static class Helpers
{
    public static int GetSize() => new Buffer().Size;
}
```

Главный потребитель — [[Source Generators]]-подобные сценарии: генератор эмитит вспомогательные типы в каждый файл и не боится, что имена столкнутся с пользовательскими. В обычном коде используется редко, но встретить в сгенерированном — норма.

## Сборка и точка входа: коротко

Единица компиляции для CLR — **сборка (assembly)**: один `.dll` (или `.exe`) с IL-кодом и метаданными. Один проект `.csproj` = одна сборка; все `.cs`-файлы проекта компилируются вместе, поэтому `internal`-типы видны между файлами, а `partial class` может быть размазан по нескольким.

У исполняемой сборки есть ровно одна точка входа — метод `Main` (или сгенерированный компилятором `<Main>$` для top-level statements):

```csharp
// Классический вид
internal sealed class Program
{
    private static async Task<int> Main(string[] args)
    {
        Console.WriteLine(args.Length);   // Вывод: 0 при запуске без аргументов
        await Task.CompletedTask;
        return 0;
    }
}
```

```csharp
// Top-level statements (C# 9+) — то же самое, компилятор сам делает класс и Main
Console.WriteLine(args.Length);   // args доступен неявно
```

Разбор всех допустимых сигнатур `Main`, кода возврата и того, во что именно разворачиваются top-level statements, — [[Top-level statements и точка входа]]. Про формат сборки, метаданные и IL — [[Сборки, метаданные и IL]].

## Как Roslyn превращает текст в IL

```
   Program.cs (UTF-8 текст)
        |
        v  [Лексер]      разбивает на токены, whitespace/комментарии -> trivia
   поток SyntaxToken
        |
        v  [Парсер]      строит дерево по грамматике C#
   SyntaxTree            (синтаксис: правильно ли расставлены скобки и ;)
        |
        v  [Declaration table + Binder]   имена -> символы, разрешение перегрузок,
   BoundTree                              вывод типов, проверки nullable
        |
        v  [Lowering]    async/await -> конечный автомат, foreach -> while,
   упрощённое дерево      LINQ-запросы -> вызовы методов, using -> try/finally
        |
        v  [Emit]
   .dll = IL-код + метаданные (+ .pdb)
```

Ключевое понимание: **синтаксическая корректность и семантическая — разные стадии**. `int x = "строка";` парсится безупречно (дерево строится), а падает на биндинге — отсюда `CS0029` вместо синтаксической ошибки. И наоборот, забытая `}` рушит парсер, и он выдаёт каскад бессмысленных ошибок ниже по файлу — всегда чини самую первую.

Ещё следствие: анализаторы и рефакторинги IDE — это тот же Roslyn API поверх `SyntaxTree` и `SemanticModel`. Как писать свои правила — [[Roslyn-анализаторы и свои правила]]. Что происходит с IL дальше, в JIT, — [[Компиляция, интерпретация и виртуальные машины]] и [[Устройство .NET: CLR, BCL, SDK, рантаймы]].

## Соглашения именования

Официальных «правил языка» тут нет — есть соглашения Microsoft и стиль репозитория `dotnet/runtime`, который де-факто стал стандартом индустрии.

| Что | Стиль | Пример |
|---|---|---|
| Типы (class, struct, record, enum, delegate) | PascalCase | `OrderProcessor`, `PaymentStatus` |
| Методы, свойства, события | PascalCase | `CalculateTotal`, `IsActive` |
| Публичные и `const` поля | PascalCase | `public const int MaxRetries = 3;` |
| Приватные поля экземпляра | `_camelCase` | `private readonly IClock _clock;` |
| Приватные статические поля | `s_camelCase` | `private static readonly JsonSerializerOptions s_options;` |
| `[ThreadStatic]`-поля | `t_camelCase` | `private static t_buffer;` (стиль runtime) |
| Локальные переменные и параметры | camelCase | `var totalAmount = 0m;` |
| Интерфейсы | `I` + PascalCase | `IOrderRepository` |
| Параметры типа | `T` или `T` + смысл | `T`, `TKey`, `TItem`, `TResult` |
| Асинхронные методы | суффикс `Async` | `Task<Order> GetOrderAsync(int id)` |
| Пространства имён | `Компания.Продукт.Слой` | `Alif.Billing.Domain` |

Про `Async`: суффикс — часть Task-based Asynchronous Pattern, он нужен, чтобы отличать `Read()` от `ReadAsync()` в перегрузках. Если асинхронной пары нет и никогда не будет (например, у обработчиков ASP.NET Core), суффикс необязателен, но команды обычно ставят его везде ради единообразия.

Про `s_`: смысл в том, что статическое поле — это разделяемое состояние, и оно должно бросаться в глаза при чтении метода. `_` против `s_` мгновенно отвечает на вопрос «это состояние объекта или всего процесса».

## Скобки: почему .NET — это Allman

```csharp
// Allman (стандарт .NET): открывающая скобка на своей строке
if (order.IsPaid)
{
    Ship(order);
}
else
{
    Notify(order);
}

// K&R / Java-стиль: в .NET не принят
if (order.IsPaid) {
    Ship(order);
}
```

Почему так сложилось: C# вырос из мира Microsoft C++/Visual Studio, где форматтер по умолчанию всегда переносил скобку, и весь BCL с первого дня писался в этом стиле. Менять его задним числом означало бы переформатировать миллионы строк и порвать всю историю `git blame`. Плюс практический аргумент: при Allman открывающая и закрывающая скобки стоят в одной колонке, и вложенность видно вертикальным сканированием.

Второе правило, которое идёт в комплекте: **всегда ставь скобки**, даже для однострочного тела. Однострочники без скобок — классический источник багов при добавлении второй строки (вспомни goto fail в Apple).

## `var`: когда уместен

```csharp
// Уместно: тип очевиден из правой части
var order = new Order();
var items = new List<string>();
var count = orders.Count(o => o.IsPaid);          // int, видно по Count

// Обязательно: анонимный тип назвать нечем
var stats = orders.Select(o => new { o.Id, o.Total });
Console.WriteLine(stats.First().Total);

// Спорно: тип нечисловой природы неочевиден
var timeout = 30;              // int? TimeSpan? секунды? — читателю неясно
int timeoutSeconds = 30;       // лучше

// Плохо: тип скрыт за вызовом
var result = _service.Process(input);   // что это — bool, Result, Task?
```

Рабочее правило команды: **`var`, когда тип буквально написан справа (`new`, каст, литерал с очевидным типом); явный тип, когда справа вызов метода.** Ограничения языка: `var` нельзя для полей, параметров, возвращаемого типа; нельзя `var x = null;` и `var x = default;` — компилятору неоткуда вывести тип.

Отдельная позиция — примитивы. Часть команд требует `int i = 0` вместо `var i = 0`, чтобы в коде было видно `int` против `long` против `decimal` (см. [[Типы данных и литералы]] и [[Переменные, const и readonly]]).

`.editorconfig` в корне репозитория — единственный источник правды по стилю: его понимают Visual Studio, Rider, VS Code и компилятор. Он же задаёт severity диагностик, то есть напрямую влияет на сборку.

### File-based apps (.NET 10)

Раньше, чтобы запустить тридцать строк кода, нужен был проект целиком. В .NET 10 SDK умеет запускать одиночный `.cs`-файл без `.csproj`:

```csharp
#!/usr/bin/env -S dotnet --
#:sdk Microsoft.NET.Sdk
#:package Humanizer@2.14.1
#:property LangVersion=preview

using Humanizer;

var span = TimeSpan.FromMinutes(135);
Console.WriteLine(span.Humanize(2));   // Вывод: 2 hours, 15 minutes
```

```bash
dotnet run app.cs            # компилирует и запускает, зависимости тянет сам
chmod +x app.cs && ./app.cs  # благодаря shebang — как обычный скрипт
dotnet project convert app.cs  # вырос из скрипта -> получаешь нормальный .csproj
```

Директивы препроцессора для этого режима: `#:package Имя@Версия`, `#:sdk Microsoft.NET.Sdk.Web` (можно поднять Minimal API одним файлом), `#:property Свойство=Значение`, `#:project ../Lib` (ссылка на соседний проект). Это по-прежнему полноценная компиляция в IL, а не интерпретация — просто проект строится в памяти.

> [!warning] Подводные камни
>
> **Точка с запятой после `if`/`for`.** `if (x);` и `while (cond);` — валидные конструкции с пустой инструкцией в теле. Компилятор промолчит (в лучшем случае даст `CS0642`), а цикл повиснет навсегда. Отсюда правило «всегда фигурные скобки»: с ними такая опечатка невозможна.
>
> **Каскад ошибок от одной скобки.** Пропущенная `}` рушит парсер, и он выдаёт 40 ошибок в конце файла. Смотреть надо не на количество, а на **самую первую** ошибку по порядку в файле — остальные обычно её следствия.
>
> **`field` ломает существующий код.** Если у тебя есть поле `private int field;` и вы обновились на C# 14, внутри аксессоров свойств `field` теперь означает backing-поле, а не твоё. Компилятор предупредит, но код может незаметно поменять смысл. Лечение: `this.field` или `@field`, а лучше — переименовать.
>
> **`global using` не там, где надо.** Все `global using` обязаны стоять до обычных `using` в файле — иначе `CS8915`. И держи их в одном месте (`GlobalUsings.cs`), иначе через полгода никто не найдёт, откуда в проекте видно `System.Text.Json`.
>
> **XML-doc без `GenerateDocumentationFile`.** Написали сто комментариев `///` — а `.xml` не собирается, IntelliSense у потребителей библиотеки пустой, OpenAPI-описания не генерируются. Свойство надо включить явно (в шаблонах оно выключено).
>
> **`.editorconfig` без `EnforceCodeStyleInBuild`.** В IDE всё подсвечивается, а CI зелёный, потому что `IDExxxx` по умолчанию живут только в редакторе. Либо включай свойство, либо ставь в пайплайн `dotnet format --verify-no-changes`.
>
> **`var` с числовыми литералами.** `var x = 1;` — это `int`, а не `long` и не `decimal`. `var price = 0;` в денежном коде — прямая дорога к целочисленному делению и потере копеек.

> [!example] Как делают в бою
>
> **Один `.editorconfig` на солюшен, в корне репозитория, `root = true`.** Форматирование — `error`, стилевые предпочтения — `warning`, спорные вкусовые вещи — `suggestion`. Правило простое: если правило нельзя автоматически починить `dotnet format`, оно не должно быть `error`.
>
> **CI-шаг перед тестами:**
>
> ```yaml
> - name: Check formatting
>   run: dotnet format --verify-no-changes --verbosity diagnostic
> ```
>
> Это дешевле, чем спорить о скобках на ревью. Первый прогон на легаси даст тысячи нарушений — их закрывают одним коммитом «reformat», который потом добавляют в `.git-blame-ignore-revs`.
>
> **`Directory.Build.props` в корне** задаёт `TargetFramework`, `Nullable`, `TreatWarningsAsErrors`, `AnalysisLevel` сразу для всех проектов, чтобы новые проекты не заводились со старыми настройками.
>
> **XML-doc только на публичном API.** Для библиотек — `GenerateDocumentationFile=true` плюс `CS1591` как warning. Для внутренних сервисов — документируют контроллеры и DTO, чтобы .NET 10 сам собрал из них описания в OpenAPI, а внутренние классы оставляют без `///`.
>
> **File-based apps заменили `.csx` и bash-обвязку.** Одноразовые миграционные скрипты, дёргалки к прод-API, генераторы тестовых данных теперь живут как `tools/reindex.cs` с shebang прямо в репозитории — без проекта, но с типами, NuGet-пакетами и отладкой.

## Вопросы с собеседований

> [!question]- Чем контекстное ключевое слово отличается от зарезервированного? Приведи пример.
> Зарезервированное слово (`class`, `int`, `return`) нельзя использовать как идентификатор нигде и никогда — компилятор всегда трактует его как ключевое. Контекстное (`var`, `value`, `yield`, `async`, `await`, `record`, `nameof`, `field`) имеет специальный смысл только в определённой синтаксической позиции, а в остальных остаётся обычным именем. Так сделано ради обратной совместимости: когда в C# 3 добавляли `var`, миллионы строк уже содержали переменные с таким именем, и ломать их было нельзя. Обратная сторона — тонкие конфликты: если объявить класс с именем `var`, конструкция `var x = 5;` начнёт означать «переменная x типа var». Свежий пример — `field` в C# 14: внутри аксессора он теперь перекрывает одноимённое пользовательское поле.

> [!question]- Что делает символ `@` перед идентификатором и когда это нужно на практике?
> `@` превращает следующее слово в verbatim identifier — компилятор снимает с него статус ключевого слова. При этом сам `@` в имя не входит: `@class` и `class` — один и тот же идентификатор, поэтому `nameof(@class)` вернёт `"class"`. На практике это нужно, когда имя навязано извне: поле JSON или атрибут HTML с именем `class`, `for`, `event`; интероп с языком, где эти слова не зарезервированы; сгенерированный код, который не хочет анализировать входные имена. Внутри своего кода `@` — запашок: лучше переименовать. Не путать с `@` перед строкой — там это verbatim string literal, совсем другой механизм.

> [!question]- В каком порядке идут элементы в файле `.cs` и что будет при нарушении?
> Порядок жёсткий: `extern alias`, затем `using` (сначала все `global using`, потом обычные), затем глобальные атрибуты вида `[assembly: ...]`, затем объявления namespace и типов. Нарушение — ошибка компиляции, а не предупреждение: например, `using` после объявления класса даст `CS1529`, а `global using` после обычного — `CS8915`. Дополнительно: file-scoped namespace (`namespace X;`) может быть в файле только один и действует до конца файла, поэтому его нельзя смешивать с блочными объявлениями namespace. Порядок не случаен — он позволяет парсеру разрешать имена, не делая нескольких проходов по файлу.

> [!question]- Зачем нужен модификатор `file` и чем он отличается от `internal`?
> `internal` ограничивает видимость сборкой, `file` (C# 11) — одним исходным файлом: другой `.cs` в том же проекте тип не увидит. Применяется он только к типам верхнего уровня. Главный сценарий — генераторы кода: генератор вставляет вспомогательные типы в каждый сгенерированный файл, и без `file` их имена столкнулись бы друг с другом или с пользовательскими типами. В обычном прикладном коде `file` почти не встречается, но полезен, чтобы явно сказать «этот хелпер — деталь реализации ровно этого файла» и не засорять пространство имён проекта.

> [!question]- Как `.editorconfig` влияет на сборку и как заставить стиль ломать CI?
> `.editorconfig` задаёт не только форматирование, но и severity диагностик через ключи `dotnet_diagnostic.<ID>.severity`. Правила анализаторов (`CAxxxx`) по умолчанию работают на сборке, а IDE-правила (`IDExxxx`, включая форматирование IDE0055) — только в редакторе; чтобы они выполнялись при `dotnet build`, нужно свойство `EnforceCodeStyleInBuild=true`. Вторая опция — вынести проверку в отдельный шаг CI командой `dotnet format --verify-no-changes`, которая ничего не меняет и возвращает ненулевой код при нарушениях. Шкала severity: `none`, `silent`, `suggestion`, `warning`, `error`. Разумная настройка: автоисправимые правила — `error`, вкусовые — `suggestion`.

> [!question]- Опиши путь от текста `.cs` до `.dll`. На каком этапе ловится `int x = "abc";`?
> Лексер разбивает текст на токены, а пробелы и комментарии складывает в тривию. Парсер по грамматике строит синтаксическое дерево — на этом этапе проверяется только форма: скобки, точки с запятой, порядок конструкций. Дальше биндер строит таблицу символов и связывает каждое имя в дереве с конкретным типом, полем или методом, выполняет разрешение перегрузок, вывод типов и nullable-анализ — именно здесь ловится `int x = "abc";` с ошибкой `CS0029`, потому что синтаксически строка безупречна. Затем идёт lowering: `async/await` разворачивается в конечный автомат, `foreach` — в цикл с итератором, `using` — в `try/finally`. Финальный этап Emit пишет IL-инструкции и метаданные в PE-файл `.dll` плюс `.pdb` с символами.

> [!question]- Когда `var` уместен, а где он запрещён языком?
> Рабочее правило: `var` хорош, когда тип буквально написан в правой части (`new Order()`, приведение, коллекционное выражение с известным элементом), и когда тип назвать нельзя — для анонимных типов `var` обязателен. Он плох, когда справа стоит вызов метода и читателю приходится идти в определение, чтобы понять, `bool` там или `Task<Result>`. Для числовых примитивов вопрос спорный: `var x = 1;` даёт `int`, и в денежном коде это ведёт к целочисленному делению, поэтому многие команды ставят `csharp_style_var_for_built_in_types = false`. Языковые ограничения жёсткие: `var` работает только для локальных переменных (и переменных цикла), но не для полей, параметров и возвращаемых типов; нельзя `var x = null;` и `var x = default;` — выводить тип не из чего.

### Задача 2. Идентификаторы, конфликтующие с ключевыми словами

Напиши метод, который принимает три параметра с именами `class`, `event` и `params`, собирает из них HTML-атрибуты и возвращает строку. Покажи, что `nameof` от такого параметра возвращает имя без `@`.

> [!success]- Решение
>
> ```csharp
> /// <summary>Собирает строку HTML-атрибутов.</summary>
> static string BuildAttributes(string @class, string @event, string @params)
> {
>     // Внутри тела @ тоже обязателен: без него это ключевые слова
>     return $"class=\"{@class}\" on{@event}=\"{@params}\"";
> }
>
> Console.WriteLine(BuildAttributes("btn", "click", "save()"));
> // Вывод: class="btn" onclick="save()"
>
> // @ — часть записи, а не имени: сам идентификатор называется "class"
> Console.WriteLine(nameof(BuildAttributes));   // Вывод: BuildAttributes
>
> static string NameOfFirstParam(string @class) => nameof(@class);
> Console.WriteLine(NameOfFirstParam("x"));     // Вывод: class
> ```
>
> Ключевой момент: `@` — это лексическая экранировка на уровне токенизации. Лексер видит `@class`, снимает статус ключевого слова и отдаёт парсеру идентификатор `class`. Поэтому `nameof(@class)` даёт `"class"` без собаки, и в метаданных сборки параметр тоже называется `class` — вызывающий код на F# или VB увидит именно это имя.

### Задача 3. Одиночный файл вместо проекта

Напиши file-based app для .NET 10, который принимает путь к каталогу аргументом, считает суммарный размер `.cs`-файлов в нём и печатает результат. Файл должен запускаться и как `dotnet run stats.cs`, и как `./stats.cs`. Объясни, чем он отличается от `dotnet new console`.

> [!success]- Решение
>
> ```csharp
> #!/usr/bin/env -S dotnet --
> #:property LangVersion=preview
>
> // args доступен неявно: file-based app — это top-level statements
> var root = args.Length > 0 ? args[0] : Directory.GetCurrentDirectory();
>
> if (!Directory.Exists(root))
> {
>     Console.Error.WriteLine($"Каталог не найден: {root}");
>     return 1;
> }
>
> long total = 0;
> var count = 0;
>
> foreach (var file in Directory.EnumerateFiles(root, "*.cs", SearchOption.AllDirectories))
> {
>     total += new FileInfo(file).Length;
>     count++;
> }
>
> Console.WriteLine($"Файлов: {count}, суммарно: {total / 1024.0:F1} КБ");
> // Вывод (пример): Файлов: 12, суммарно: 48.3 КБ
>
> return 0;
> ```
>
> Запуск: `dotnet run stats.cs ./src` либо `chmod +x stats.cs && ./stats.cs ./src`. Shebang работает потому, что `#!` в первой строке file-based app компилятор .NET 10 воспринимает как комментарий-директиву, а не как синтаксическую ошибку.
>
> Отличия от `dotnet new console`: нет `.csproj`, нет `bin/`, нет `obj/` в рабочем каталоге — SDK строит проект в памяти и кеширует артефакты. Зависимости объявляются прямо в файле директивами `#:package Имя@Версия`, SDK — через `#:sdk`, MSBuild-свойства — через `#:property`. Компиляция полноценная: тот же Roslyn, тот же IL, та же отладка. Когда скрипт перерастает один файл — `dotnet project convert stats.cs` разворачивает его в обычный проект без потери кода.

## Итог

- C# — язык свободного формата: компилятор работает с потоком токенов, а пробелы и комментарии становятся тривией. Значимы `;` (конец инструкции) и `{}` (блок и область видимости), но не отступы.
- Новые слова языка добавляют контекстными, чтобы не ломать существующий код: `var`, `value`, `yield`, `async`, `await`, `record`, `nameof`, `file`, и с C# 14 — `field`. Конфликтующее имя всегда можно экранировать через `@`.
- Порядок в файле фиксирован: `extern alias` -> `using` (сначала `global using`) -> глобальные атрибуты -> namespace -> типы. File-scoped `namespace X;` (C# 10) — умолчание для нового кода, один на файл.
- Roslyn идёт по цепочке лексер -> парсер -> синтаксическое дерево -> биндер -> lowering -> emit IL. Синтаксические ошибки ловит парсер, ошибки типов — биндер; чинить всегда надо первую ошибку в файле.
- Стиль не влияет на IL, но влияет на скорость чтения кода: Allman-скобки, PascalCase для членов, `_camelCase` и `s_camelCase` для приватных полей, суффикс `Async`. Всё это фиксируется в `.editorconfig` и проверяется через `dotnet format --verify-no-changes` в CI.
- В .NET 10 порог входа снизился до одного файла: `dotnet run app.cs` с директивами `#:package`, `#:sdk`, `#:property` и shebang, а `dotnet project convert` превращает скрипт в полноценный проект.
