# Строки и работа с текстом

> [!abstract] Коротко
> `string` — ссылочный тип, но иммутабельный: любая «модификация» создаёт новую строку, а старая становится мусором. Из этого растут все практики: `StringBuilder` для сборки в цикле, `Span<char>` для разбора без копий, интернирование литералов, безопасность в многопоточном коде. Второй столп темы — сравнение: по умолчанию часть методов работает с учётом культуры, часть — побайтово, и это несовпадение регулярно даёт баги, которые проявляются только на другой машине или на другом языке.

## Зачем это нужно

Строки — самый частый тип в бэкенде: HTTP-заголовки, JSON, SQL, логи, идентификаторы, имена. И самая частая причина двух проблем.

**Производительность.** Конкатенация в цикле превращает линейную задачу в квадратичную. Формирование отчёта на 50 000 строк через `+=` занимает минуты вместо десятков миллисекунд.

**Корректность.** Сравнение строк по-разному ведёт себя в зависимости от культуры и регистра. Классика: логин `admin` и `ADMİN` (турецкая точка над I), сортировка, где `ё` оказывается не там, где ожидалось, и поиск подстроки, который «работает локально».

## Иммутабельность

```csharp
string s = "привет";
s = s + " мир";              // НЕ изменение: создана новая строка, ссылка перенаправлена
s.ToUpperInvariant();         // Возвращает новую строку. Сама s не изменилась!
Console.WriteLine(s);         // Вывод: привет мир

// Строка в памяти (упрощённо):
// [ хедер объекта | Length = 6 | п р и в е т ]
```

Строка неизменяема по решению дизайнеров платформы, и причины практические:

- **Безопасность.** Строку можно передать в метод, не опасаясь, что её изменят: пути, строки подключения, проверенные значения остаются такими, какими были.
- **Потокобезопасность бесплатно.** Иммутабельный объект можно читать из любого числа потоков без блокировок.
- **Кеширование хеша и интернирование.** Хеш строки не меняется, значит строки могут быть ключами словарей, а одинаковые литералы — переиспользоваться.

Цена — аллокация на каждое изменение. Отсюда все дальнейшие приёмы.

### Интернирование

Одинаковые строковые литералы в сборке — один объект. Это делает компилятор и загрузчик через таблицу интернирования (intern pool):

```csharp
string a = "текст";
string b = "текст";
Console.WriteLine(ReferenceEquals(a, b));        // True — один и тот же объект

string c = new string(['т','е','к','с','т']);
Console.WriteLine(ReferenceEquals(a, c));        // False — создана в рантайме
Console.WriteLine(a == c);                       // True — == сравнивает содержимое

Console.WriteLine(ReferenceEquals(a, string.Intern(c)));  // True — добавили в пул
```

Практически интернирование почти не нужно, но знать о нём важно по двум причинам: сравнение `==` для строк работает быстро, потому что часто попадает на один объект; и `string.Intern` — источник утечек, так как интернированные строки живут до конца жизни домена приложения и никогда не собираются GC.

## Сборка строк

### Конкатенация

```csharp
// Компилятор объединяет соседние + в один вызов string.Concat — это дешёво
string message = "Заказ " + id + " от " + date;     // один Concat, одна аллокация

// А вот это O(n²): каждая итерация создаёт новую строку и копирует всё накопленное
string report = "";
foreach (var line in lines)
    report += line + "\n";                          // n аллокаций, n²/2 скопированных символов
```

### StringBuilder

```csharp
var sb = new System.Text.StringBuilder(capacity: 1024);   // ёмкость с запасом, если известна
foreach (var line in lines)
    sb.Append(line).Append('\n');
string report = sb.ToString();

sb.AppendLine("строка с переводом");
sb.AppendFormat("{0:F2}", 19.999);
sb.Insert(0, "префикс: ");
sb.Replace("старое", "новое");
sb.Clear();                                   // переиспользование без новой аллокации
```

Внутри `StringBuilder` — связный список блоков `char[]` (chunks). При заполнении блока добавляется новый, а не копируется всё содержимое, поэтому `Append` амортизированно `O(1)`, а `ToString()` собирает результат один раз.

Когда `StringBuilder` **не** нужен: если конкатенаций фиксированное небольшое число (3–10) в одном выражении — компилятор и так сделает один `Concat`, а `StringBuilder` добавит лишний объект. Порог простой: **цикл — да, одна строка кода — нет**.

### Интерполяция

```csharp
var name = "Иван";
var total = 1234.5m;
string s1 = $"Клиент {name}, сумма {total:N2}";       // основной способ
string s2 = $"Сегодня {DateTime.UtcNow:yyyy-MM-dd}";

// Многострочная интерполяция с raw string
string json = $$"""
    { "client": "{{name}}", "total": {{total}} }
    """;
```

С C# 10 интерполяция компилируется не в `string.Format`, а в `DefaultInterpolatedStringHandler`: он пишет части во временный буфер (взятый из пула), форматирует значимые типы без упаковки и собирает результат один раз. Практический вывод: интерполяция теперь **не медленнее** `Concat` и заметно быстрее `string.Format`, поэтому выбирать надо по читаемости.

Два места, где интерполяцию использовать нельзя:

```csharp
// 1. Логирование: убивает структурные логи и форматирует даже когда уровень отключён
logger.LogInformation($"Обработан заказ {id}");        // плохо
logger.LogInformation("Обработан заказ {OrderId}", id); // правильно: шаблон + параметр

// 2. SQL: прямой путь к SQL-инъекции
var bad  = $"SELECT * FROM Orders WHERE Id = {userInput}";     // уязвимость
var good = "SELECT * FROM Orders WHERE Id = @id";              // параметр
// В EF Core интерполяция БЕЗОПАСНА только в FromSql/ExecuteSql —
// там она распознаётся как FormattableString и превращается в параметры:
// db.Orders.FromSql($"SELECT * FROM Orders WHERE Id = {id}")
```

Подробно — [[Логирование и структурные логи]] и [[SQL-инъекции и параметризация]].

## Сравнение строк: главная ловушка темы

```csharp
// == и Equals без параметров — ОРДИНАЛЬНОЕ сравнение (побайтово по code units)
Console.WriteLine("straße" == "strasse");                      // False

// Явное указание правил — единственный надёжный способ
Console.WriteLine(string.Equals("ADMIN", "admin", StringComparison.OrdinalIgnoreCase));  // True
Console.WriteLine(string.Equals("ADMIN", "admin", StringComparison.Ordinal));            // False
```

| `StringComparison` | Что делает | Когда применять |
|---|---|---|
| `Ordinal` | сравнение code units, максимально быстро | идентификаторы, ключи, пути, токены, всё машинное |
| `OrdinalIgnoreCase` | то же без учёта регистра (по инвариантным правилам) | логины, имена заголовков, расширения файлов |
| `CurrentCulture` | по правилам культуры пользователя | сортировка того, что видит человек |
| `CurrentCultureIgnoreCase` | то же без регистра | поиск в интерфейсе |
| `InvariantCulture` | по фиксированным «нейтральным» правилам | почти никогда: медленно и неочевидно |
| `InvariantCultureIgnoreCase` | то же без регистра | редко |

**Правило:** машинные данные — `Ordinal`/`OrdinalIgnoreCase`. Человеческий текст, который сортируется или ищется в интерфейсе, — культурные варианты. Всё остальное — ошибка.

> [!danger] Методы с разными значениями по умолчанию
> ```csharp
> "abc".Contains("b");                 // ORDINAL по умолчанию
> "abc".IndexOf("b");                  // КУЛЬТУРА по умолчанию (!)
> "abc".StartsWith("a");               // КУЛЬТУРА по умолчанию
> "abc".EndsWith("c");                 // КУЛЬТУРА по умолчанию
> "abc".Replace("b", "x");             // ORDINAL
> "abc" == "abc";                      // ORDINAL
> "abc".CompareTo("abd");              // КУЛЬТУРА
> ```
> Это историческая несогласованность, и она реально приводит к разному поведению на разных локалях. Правильная привычка — **всегда указывать `StringComparison` явно**. Анализаторы CA1307/CA1310 включаются в `.editorconfig` и находят такие места автоматически — см. [[Стиль кода, соглашения и .editorconfig]].

### Регистр: почему `ToUpper()` для сравнения — плохая идея

```csharp
// Плохо: две аллокации на каждое сравнение + зависимость от культуры
if (login.ToLower() == "admin") { }

// В турецкой культуре 'I'.ToLower() даёт 'ı' (без точки), и сравнение ломается.
// Классический баг: пользователь с турецкой локалью не может войти.

// Правильно: без аллокаций и без культурных сюрпризов
if (string.Equals(login, "admin", StringComparison.OrdinalIgnoreCase)) { }

// Если приведение регистра нужно именно для хранения — Invariant-версии
var normalized = login.ToUpperInvariant();   // предсказуемо, не зависит от локали сервера
```

### Строки как ключи

```csharp
// По умолчанию Dictionary<string,V> использует ординальное сравнение с учётом регистра
var caseInsensitive = new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase);
caseInsensitive["Token"] = 1;
Console.WriteLine(caseInsensitive["TOKEN"]);      // Вывод: 1

var sorted = names.OrderBy(n => n, StringComparer.CurrentCulture).ToList();   // для человека
var stable = keys.OrderBy(k => k, StringComparer.Ordinal).ToList();          // для машины
```

Сортировка человеческого текста без указания компаратора зависит от локали сервера: список, отсортированный на одном инстансе, может отличаться от другого. Для API-ответов и файлов используется `Ordinal`, для UI — культура.

## Частые операции

```csharp
string text = "  Иван,Пётр , Мария  ";

// Проверки на пустоту
string.IsNullOrEmpty(text);           // null или ""
string.IsNullOrWhiteSpace(text);      // null, "" или только пробелы — обычно нужен именно он

// Разбиение
var parts = text.Split(',', StringSplitOptions.RemoveEmptyEntries | StringSplitOptions.TrimEntries);
// ["Иван", "Пётр", "Мария"] — TrimEntries доступен с .NET 5

// Склейка
Console.WriteLine(string.Join(" | ", parts));       // Иван | Пётр | Мария

// Обрезка и замена
text.Trim();  text.TrimStart();  text.TrimEnd('.');
text.Replace(",", "; ");
text.Replace("иван", "Иван", StringComparison.OrdinalIgnoreCase);   // с .NET Core 2.0

// Поиск
text.Contains("Пётр", StringComparison.Ordinal);
text.IndexOf('М');                                  // char-перегрузка всегда ординальна и быстра
text.StartsWith("  ", StringComparison.Ordinal);

// Извлечение
text.Substring(2, 4);            // копия — аллокация
text[2..6];                       // то же самое, синтаксис диапазона
text.AsSpan(2, 4);                // окно без аллокации

// Дополнение и выравнивание
"7".PadLeft(3, '0');              // "007"
$"{7,5}";                          // "    7" — выравнивание в интерполяции
$"{7,-5}|";                        // "7    |"

// Форматирование чисел и дат
$"{1234.5678:N2}";                 // "1 234,57" — с учётом культуры
$"{0.153:P1}";                     // "15,3 %"
$"{DateTime.UtcNow:O}";            // ISO 8601 round-trip — для машин
$"{42:X}";                         // "2A"
```

## Строки без аллокаций: Span

Каждая `Substring`, `Trim`, `Split`, `ToUpper` создаёт новую строку. В горячем коде (парсеры, логи, сериализация) это основной источник мусора. Решение — `ReadOnlySpan<char>`: окно в существующую строку.

```csharp
static bool TryParseKeyValue(string line, out ReadOnlySpan<char> key, out ReadOnlySpan<char> value)
{
    var span = line.AsSpan();
    int sep = span.IndexOf('=');
    if (sep < 0) { key = default; value = default; return false; }

    key = span[..sep].Trim();          // Trim у Span возвращает Span — без аллокации
    value = span[(sep + 1)..].Trim();
    return true;
}

// Разбор числа прямо из среза, без промежуточной строки
if (int.TryParse("порт=8080".AsSpan()[5..], out int port))
    Console.WriteLine(port);           // Вывод: 8080

// Поиск любого из набора символов — .NET 8+, векторизованно
var separators = System.Buffers.SearchValues.Create([',', ';', '\t']);
int idx = "a;b,c".AsSpan().IndexOfAny(separators);
```

Ограничение: `Span<T>` — `ref struct`, его нельзя сохранить в поле класса, использовать в `async`-методе или в лямбде. Для этих случаев есть `ReadOnlyMemory<char>`. Подробно — [[Span, ReadOnlySpan и Memory]].

## Длина строки и Unicode

```csharp
Console.WriteLine("Привет".Length);      // 6
Console.WriteLine("👍".Length);           // 2 — суррогатная пара, не один символ
Console.WriteLine("é".Length);            // 1 или 2 — зависит от нормализации:
                                          // U+00E9 либо 'e' + U+0301
```

`Length` — число UTF-16 code units, а не «символов». Практические следствия: обрезка по `Length` может разрезать символ, а валидация «не длиннее 50 символов» на разных языках означает разное. Для аккуратной работы: `EnumerateRunes()` для code points, `StringInfo` для графем, `Normalize()` для приведения к единой форме. Подробно — [[Системы счисления и представление данных]].

> [!warning] Подводные камни
> - **`+=` в цикле.** Квадратичная сложность и мусор. Всегда `StringBuilder` (или `string.Join`, если элементы уже в коллекции).
> - **`ToLower()`/`ToUpper()` для сравнения.** Две лишние аллокации плюс зависимость от культуры (турецкая `I`). Нужно `string.Equals(..., StringComparison.OrdinalIgnoreCase)`.
> - **`IndexOf`, `StartsWith`, `EndsWith` без `StringComparison`.** Работают по культуре: результат зависит от локали процесса, а сравнение медленнее ординального в разы.
> - **`IsNullOrEmpty` там, где нужен `IsNullOrWhiteSpace`.** Строка из пробелов пройдёт валидацию и уедет в базу.
> - **Интерполяция в логах.** Строка форматируется всегда, даже если уровень логирования отключён, и структурные поля теряются.
> - **Интерполяция в SQL.** SQL-инъекция. Единственное исключение — методы EF Core, принимающие `FormattableString`.
> - **`string` для секретов.** Иммутабельная строка остаётся в памяти до сборки, её нельзя надёжно очистить; для паролей в чувствительных сценариях есть `SecureString` (с оговорками) и работа с `byte[]`/`Span<byte>`, который можно затереть.
> - **`Split` без `StringSplitOptions`.** «a,,b» даст пустой элемент, «a , b» — элементы с пробелами. Почти всегда нужны `RemoveEmptyEntries | TrimEntries`.

> [!example] Как делают в бою
> Три правила, которые встречаются в любом зрелом .NET-проекте.
> Первое: сравнение строк всегда с явным `StringComparison`, и это проверяется анализаторами в CI. Ординальное — по умолчанию, культурное — только для того, что видит человек.
> Второе: сборка текста — `StringBuilder` в циклах, `string.Join` для коллекций, интерполяция для коротких сообщений. `string.Format` в новом коде практически не используется.
> Третье: на границах системы строки нормализуются один раз (обрезка, приведение регистра для ключей, проверка длины), а дальше внутри системы считаются валидными. Валидация «на всякий случай» в каждом слое — признак того, что границы не определены.
> В инфраструктурном коде (парсинг больших файлов, разбор протоколов) переходят на `ReadOnlySpan<char>`: `IndexOf`, срезы и `TryParse` работают по спанам и не создают промежуточных строк. Именно так устроен `System.Text.Json` — и поэтому он в разы быстрее старых сериализаторов.

## Вопросы с собеседований

> [!question]- Почему `string` иммутабельна и чем это оборачивается?
> Иммутабельность даёт три вещи: безопасность передачи (метод не может изменить переданную строку у вызывающего), бесплатную потокобезопасность при чтении и возможность кешировать хеш и интернировать литералы — то есть переиспользовать один объект для одинаковых строк, что делает строки надёжными ключами словарей. Цена — каждая операция «изменения» выделяет новую строку и копирует символы. В цикле это даёт квадратичную сложность: сборка 10 000 строк через `+=` копирует десятки миллионов символов и создаёт 10 000 объектов для GC. Поэтому существует `StringBuilder` — изменяемый буфер, который дописывает в блоки `char[]` и собирает итог один раз, а для разбора без копирования существует `ReadOnlySpan<char>`, дающий окно в существующую строку.

> [!question]- Чем ординальное сравнение отличается от культурного?
> Ординальное сравнивает последовательности UTF-16 code units как числа: быстро, детерминированно, не зависит от локали. Культурное применяет правила языка: порядок символов национального алфавита, игнорируемые символы (например, дефис в некоторых культурах), эквивалентность составных символов. Для машинных данных нужно ординальное: идентификаторы, ключи, заголовки HTTP, имена файлов, токены — иначе поведение зависит от настроек сервера. Культурное нужно там, где результат читает человек: сортировка списка имён в интерфейсе, поиск по названию. Проблема в том, что значения по умолчанию у методов `string` несогласованны — `Contains` и `==` ординальны, а `IndexOf`, `StartsWith`, `CompareTo` культурны, — поэтому правильная привычка состоит в том, чтобы всегда указывать `StringComparison` явно.

> [!question]- Как устроен `StringBuilder` внутри?
> Это связный список блоков `char[]` (чанков). `Append` пишет в текущий блок; когда он заполнен, создаётся новый блок (обычно вдвое больше, с ограничением сверху), и старый не копируется — именно поэтому добавление амортизированно `O(1)`, а не `O(n)`, как в наивной реализации с одним растущим массивом. `ToString()` вычисляет итоговую длину, выделяет одну строку и копирует в неё все блоки. Практические следствия: задать `capacity` в конструкторе полезно, если размер известен (меньше блоков и меньше работы при сборке); `Clear()` позволяет переиспользовать экземпляр без новых аллокаций; частые обращения к `sb[i]` или `Insert` в начало относительно дороги, потому что требуют навигации по списку блоков.

> [!question]- Почему `logger.LogInformation($"...")` — плохая практика?
> По двум причинам. Первая — производительность: интерполированная строка формируется до вызова метода, поэтому форматирование и аллокации происходят даже если уровень `Information` отключён и сообщение будет выброшено. Вторая, более важная — структурные логи: провайдеры (Serilog, OpenTelemetry, ELK) сохраняют шаблон сообщения и параметры как отдельные поля, по которым потом можно искать и агрегировать (`OrderId = 42`). Интерполяция превращает всё в один плоский текст, и в логах остаётся только строка, по которой нельзя ни сгруппировать, ни отфильтровать. Правильная форма — `logger.LogInformation("Обработан заказ {OrderId}", id)`; порядок параметров сопоставляется с именами в шаблоне позиционно.

> [!question]- Как сравнить строки без учёта регистра правильно?
> `string.Equals(a, b, StringComparison.OrdinalIgnoreCase)` — для машинных данных, `StringComparison.CurrentCultureIgnoreCase` — для человеческого текста. Вариант `a.ToLower() == b.ToLower()` неправилен сразу по двум причинам: он создаёт две лишние строки на каждое сравнение и зависит от текущей культуры — в турецкой локали `'I'.ToLower()` даёт `'ı'` без точки, из-за чего строки «ADMIN» и «admin» перестают считаться равными. Это не теоретическая проблема: баг с турецкой `I` регулярно попадается в системах авторизации. Если приведение регистра нужно для хранения нормализованного значения, используют `ToUpperInvariant()`, а не `ToUpper()`. Для словарей с ключами-строками правильный способ — передать `StringComparer.OrdinalIgnoreCase` в конструктор.

## Задачи

### Задача 1. Ускорить сборку отчёта

```csharp
static string BuildReport(List<Order> orders)
{
    string result = "id;total;status\n";
    foreach (var o in orders)
        result += o.Id + ";" + o.Total + ";" + o.Status + "\n";
    return result;
}
```

Перепиши так, чтобы работало линейно, и объясни, что именно изменилось.

> [!success]- Решение
> ```csharp
> static string BuildReport(List<Order> orders)
> {
>     var sb = new System.Text.StringBuilder(orders.Count * 32);   // оценка ёмкости
>     sb.Append("id;total;status\n");
>     foreach (var o in orders)
>         sb.Append(o.Id).Append(';')
>           .Append(o.Total).Append(';')
>           .Append(o.Status).Append('\n');
>     return sb.ToString();
> }
> ```
> Что изменилось: было `n` аллокаций строк и копирование всего накопленного на каждой итерации — суммарно `O(n²)` скопированных символов; стало дописывание в блоки буфера и одна финальная сборка — `O(n)`. Дополнительно: `Append(o.Id)` для `int` не создаёт промежуточную строку (есть перегрузки под примитивы и форматирование напрямую в буфер), а `Append('\n')` с `char` дешевле, чем со строкой из одного символа. Начальная ёмкость убирает часть промежуточных блоков. На 50 000 заказах разница — секунды против единиц миллисекунд.

### Задача 2. Разобрать строку без аллокаций

Строка вида `"name=value"`. Верни значение как `ReadOnlySpan<char>`, не создавая новых строк, и обработай случай отсутствия `=`.

> [!success]- Решение
> ```csharp
> static bool TryGetValue(ReadOnlySpan<char> input, out ReadOnlySpan<char> value)
> {
>     int sep = input.IndexOf('=');
>     if (sep < 0)
>     {
>         value = default;
>         return false;
>     }
>     value = input[(sep + 1)..].Trim();
>     return true;
> }
>
> if (TryGetValue("timeout = 30".AsSpan(), out var v) && int.TryParse(v, out int timeout))
>     Console.WriteLine(timeout);      // Вывод: 30
> ```
> Ключевое: параметр объявлен как `ReadOnlySpan<char>`, а не `string` — тогда метод работает и по строке (`AsSpan()`), и по буферу из `stackalloc`, и по срезу большего текста без копирования. `IndexOf`, `Trim` и срез у спана не создают строк, а `int.TryParse` имеет перегрузку под спан. Итого разбор идёт с нулевыми аллокациями — именно так устроены парсеры в самом .NET. Ограничение, о котором надо помнить: возвращённый спан живёт, пока живёт исходная память, поэтому его нельзя сохранить в поле или использовать после `await`.

### Задача 3. Найти три проблемы в валидации

```csharp
static bool IsValidLogin(string login)
{
    if (string.IsNullOrEmpty(login)) return false;
    if (login.ToLower() == "admin") return false;
    if (login.Length > 20) return false;
    return login.IndexOf("@") == -1;
}
```

> [!success]- Решение
> Проблемы: `IsNullOrEmpty` пропускает строку из пробелов; `ToLower()` создаёт лишнюю строку и зависит от культуры (турецкая `I`); `IndexOf(string)` без `StringComparison` работает по правилам культуры — медленнее и потенциально с другим результатом, а искать один символ дешевле `char`-перегрузкой. Плюс проверка длины по `Length` считает UTF-16 единицы, поэтому лимит «20 символов» для строки с эмодзи означает меньше видимых знаков — здесь это скорее уточнение требования, чем баг.
> ```csharp
> static bool IsValidLogin(string? login)
> {
>     if (string.IsNullOrWhiteSpace(login)) return false;
>     if (login.Length > 20) return false;
>     if (string.Equals(login, "admin", StringComparison.OrdinalIgnoreCase)) return false;
>     return login.IndexOf('@') < 0;          // char-перегрузка: всегда ординальна
> }
> ```
> Порядок проверок тоже изменён: дешёвая проверка длины идёт раньше сравнения строк, а параметр объявлен как `string?`, что честно отражает возможность `null` при включённых nullable reference types.

## Итог

- `string` иммутабельна: каждая «модификация» — новая строка. Отсюда `StringBuilder` в циклах и `Span<char>` в горячем коде.
- Литералы интернируются; `string.Intern` для рантайм-строк почти никогда не нужен и держит память навсегда.
- Интерполяция с C# 10 компилируется в handler и не медленнее `Concat`; но в логах и SQL её использовать нельзя.
- `==` и `Contains` ординальны, `IndexOf`/`StartsWith`/`CompareTo` — культурны. Указывай `StringComparison` всегда.
- `ToLower()` для сравнения — две аллокации и баг с турецкой `I`; правильно `OrdinalIgnoreCase`.
- `IsNullOrWhiteSpace` вместо `IsNullOrEmpty` в валидации; `Split` с `RemoveEmptyEntries | TrimEntries`.
- `Length` — это UTF-16 единицы, а не символы: обрезка по длине может испортить текст.
- Разбор без аллокаций: `AsSpan()`, `IndexOf`, срезы, `TryParse` по спану, `SearchValues` для наборов символов.
