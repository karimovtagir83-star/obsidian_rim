# Условия и ветвление

> [!abstract] Коротко
> Ветвление — это способ выбрать одну из нескольких дорог исполнения. В C# есть три формы: `if`/`else` (последовательная проверка условий), `switch`-инструкция (выбор секции по значению или паттерну) и `switch`-выражение из C# 8 (та же логика, но возвращает значение). Ключевое отличие C# от C: условие обязано быть `bool`, неявного преобразования `int -> bool` нет, поэтому классическая опечатка `if (x = 5)` не компилируется. Под капотом `switch` — не всегда цепочка сравнений: компилятор умеет строить таблицу переходов (jump table) и хеш-таблицу для строк.

## Зачем это нужно

Программа без ветвления — это калькулятор, который всегда считает одно и то же. Любая бизнес-логика («если пользователь заблокирован — вернуть 403», «если сумма больше лимита — потребовать подтверждение») сводится к ветвлению.

Но у ветвления есть цена. Для процессора условный переход — это разрыв конвейера. Современный CPU угадывает, куда пойдёт исполнение (branch prediction), и заранее начинает выполнять инструкции. Промах предсказания стоит 15–20 тактов — это как 5–10 обычных арифметических операций, выкинутых в помойку. Поэтому важно не только «как написать условие», но и «как компилятор и процессор его исполнят». Про конвейер и предсказатель переходов — [[Как работает компьютер: процессор, память, ОС]].

Вторая цена — читаемость. Вложенные `if` на пять уровней («стрелка судьбы») — самый частый источник багов в бизнес-коде. Половина этой заметки про то, как ветвление сокращать, а не наращивать.

## if, else if, else

Базовая форма:

```csharp
int score = 87;

if (score >= 90)
    Console.WriteLine("Отлично");
else if (score >= 75)
    Console.WriteLine("Хорошо");
else if (score >= 60)
    Console.WriteLine("Удовлетворительно");
else
    Console.WriteLine("Неудовлетворительно");

// Вывод: Хорошо
```

`else if` — это не отдельная конструкция языка. Это `else`, за которым идёт вложенный `if`. Компилятор видит:

```csharp
if (score >= 90)
    ...
else
{
    if (score >= 75)
        ...
    else
    {
        if (score >= 60) ... else ...
    }
}
```

Отсюда важное следствие: цепочка `else if` проверяется **последовательно сверху вниз** и останавливается на первом истинном условии. Порядок условий значим. Если поставить `score >= 60` первым, ветки для 90 и 75 станут недостижимыми — и компилятор об этом не предупредит, потому что формально они достижимы.

### Условие обязано быть bool

В C и C++ условие — это «любое значение, отличное от нуля». В C# так нельзя:

```csharp
int x = 0;

// if (x)          // Ошибка CS0029: не удаётся преобразовать int в bool
// if (x = 5)      // Ошибка CS0029: результат присваивания — int, не bool

if (x != 0) { }    // Правильно
```

Это осознанное решение дизайнеров языка: классический баг C — `if (x = 5)` вместо `if (x == 5)` — в C# просто не компилируется. Единственное исключение, где присваивание выглядит как условие:

```csharp
bool flag = false;
if (flag = true) { }  // Компилируется! Тип присваивания — bool.
                      // Компилятор выдаст предупреждение CS0665.
```

Ещё одно место, где легко ошибиться, — пользовательский оператор `true`/`false` (см. [[Перегрузка операторов]]). Тип с таким оператором можно поставить в `if` напрямую. В реальном коде это встречается разве что в `System.Data.SqlTypes`.

### Висячий else (dangling else)

Классика из учебников по C, актуальная и для C#:

```csharp
int a = 1, b = 0;

if (a > 0)
    if (b > 0)
        Console.WriteLine("оба положительные");
else                                              // К какому if относится?
    Console.WriteLine("a не положительное?");     // Отступ врёт!
```

`else` всегда привязывается к **ближайшему незакрытому `if`** — то есть к `if (b > 0)`, а не к `if (a > 0)`, несмотря на отступы. Здесь при `a = 1, b = 0` выведется «a не положительное?», хотя `a` положительное.

Лечение простое и универсальное: **всегда ставить фигурные скобки**. Это правило есть в большинстве корпоративных styleguide и в анализаторах Roslyn (IDE0011). Один раз сэкономленные две строки не стоят получаса отладки.

```csharp
if (a > 0)
{
    if (b > 0)
    {
        Console.WriteLine("оба положительные");
    }
}
else
{
    Console.WriteLine("a не положительное");
}
```

## Тернарный оператор

`условие ? выражение1 : выражение2` — единственный тернарный (трёхоперандный) оператор в C#.

```csharp
int age = 20;
string status = age >= 18 ? "взрослый" : "несовершеннолетний";
Console.WriteLine(status);  // Вывод: взрослый
```

Ключевое отличие от `if`: это **выражение**, у него есть тип и значение. Значит, его можно подставить в аргумент метода, в инициализатор поля, в интерполяцию строки.

Обе ветви вычисляются лениво: выполняется только выбранная. Это важно, если в ветвях есть побочные эффекты или потенциальные исключения:

```csharp
int[] arr = [];
int first = arr.Length > 0 ? arr[0] : -1;  // arr[0] не вычисляется, исключения нет
Console.WriteLine(first);                   // Вывод: -1
```

### Target-typed conditional (C# 9)

До C# 9 компилятор искал **общий тип** двух ветвей самостоятельно, не глядя на то, куда результат присваивается. Если общего типа не находилось — ошибка:

```csharp
// До C# 9 это была ошибка CS0173: нет неявного преобразования между int и <null>
int? value = flag ? 1 : null;
```

Приходилось писать `flag ? (int?)1 : null`. С C# 9 компилятор, если общий тип не найден, пробует привести обе ветви к **целевому типу** (типу переменной слева):

```csharp
bool flag = true;

int? value = flag ? 1 : null;                  // C# 9+: ок, целевой тип int?
Console.WriteLine(value);                      // Вывод: 1

Stream s = flag ? new MemoryStream() : new FileStream("a.txt", FileMode.Create);
// C# 9+: ок, целевой тип Stream. Раньше — ошибка, у MemoryStream и FileStream
// нет наилучшего общего типа среди них самих.
s.Dispose();
```

Про то, как вообще работают преобразования и что бывает при явном приведении, — [[Приведение типов и checked-unchecked]].

### Когда тернарник вредит

Тернарный оператор — правоассоциативный, поэтому цепочки формально возможны:

```csharp
string Grade(int s) => s >= 90 ? "A" : s >= 75 ? "B" : s >= 60 ? "C" : "F";
```

Одна такая строка читается. Три вложенных уровня с длинными выражениями — уже нет. Для более чем двух-трёх веток берите `switch`-выражение: оно для этого и сделано.

## switch-инструкция

Классическая форма, унаследованная из C, но с существенными отличиями.

```csharp
int day = 3;

switch (day)
{
    case 1:
    case 2:
    case 3:
    case 4:
    case 5:
        Console.WriteLine("Будний день");
        break;
    case 6:
    case 7:
        Console.WriteLine("Выходной");
        break;
    default:
        Console.WriteLine("Некорректный номер дня");
        break;
}
// Вывод: Будний день
```

Разберём терминологию, она нужна для точных ответов на собеседовании:

| Термин | Что это |
|---|---|
| switch section (секция) | одна или несколько меток `case`/`default` плюс следующий за ними список инструкций |
| switch label (метка) | `case <константа или паттерн>:` либо `default:` |
| governing expression | выражение в скобках после `switch` |

### Fall-through запрещён

В C после выполнения тела `case` управление «проваливается» в следующий `case`, если не написать `break`. В C# это **ошибка компиляции** CS0163: «Управление не может передаваться от одной метки case к другой».

```csharp
switch (day)
{
    case 1:
        Console.WriteLine("Понедельник");
        // Ошибка CS0163, если раскомментировать case ниже без break
    case 2:
        Console.WriteLine("Вторник");
        break;
}
```

Каждая непустая секция обязана заканчиваться инструкцией, передающей управление наружу: `break`, `return`, `throw`, `goto case`, `goto default`, `continue` (если switch внутри цикла) или `yield break`.

Стакать пустые метки (`case 1: case 2:`) можно — это не fall-through, просто у одной секции несколько меток.

Почему так сделали: провалы в C — источник огромного количества багов (забытый `break`). Явный `goto case` требует осознанного действия.

### goto case

Если провал действительно нужен, есть явная форма:

```csharp
enum Tariff { Free, Basic, Pro, Enterprise }

static string Features(Tariff t)
{
    var sb = new System.Text.StringBuilder();
    switch (t)
    {
        case Tariff.Enterprise:
            sb.Append("SLA; ");
            goto case Tariff.Pro;      // Явный переход в другую секцию
        case Tariff.Pro:
            sb.Append("API; ");
            goto case Tariff.Basic;
        case Tariff.Basic:
            sb.Append("Экспорт; ");
            goto case Tariff.Free;
        case Tariff.Free:
            sb.Append("Базовый доступ");
            break;
    }
    return sb.ToString();
}

Console.WriteLine(Features(Tariff.Pro));
// Вывод: API; Экспорт; Базовый доступ
```

`goto case` требует константной метки — нельзя прыгнуть на `case` с паттерном или `when`. Есть ещё `goto default`.

В продакшене `goto case` встречается редко: обычно накопительную логику лучше выразить флаговым перечислением (см. [[Перечисления (enum)]]) или обычными вызовами методов. Но в парсерах и конечных автоматах он вполне уместен.

### Общая область видимости секций

Тонкость, которая ловит людей: все секции `switch` делят **одно** объявление переменных.

```csharp
switch (day)
{
    case 1:
        int temp = 10;      // Объявлена здесь
        Console.WriteLine(temp);
        break;
    case 2:
        // int temp = 20;   // Ошибка CS0128: переменная temp уже определена
        temp = 20;          // А так можно — но переменная не инициализирована
                            // при входе через case 2, компилятор это отследит
        Console.WriteLine(temp);
        break;
}
```

Лечится фигурными скобками вокруг тела секции — они создают отдельную область видимости.

## switch-выражение (C# 8)

`switch`-инструкция ничего не возвращает, поэтому классический код «выбрать значение по ключу» выглядел так:

```csharp
// Как писали до C# 8 #устарело
string name;
switch (day)
{
    case 1: name = "Пн"; break;
    case 2: name = "Вт"; break;
    default: name = "?"; break;
}
```

Шесть строк шума ради маппинга. C# 8 дал `switch`-выражение:

```csharp
string name = day switch
{
    1 => "Пн",
    2 => "Вт",
    3 => "Ср",
    4 => "Чт",
    5 => "Пт",
    6 or 7 => "Выходной",
    _ => "?"
};
Console.WriteLine(name);   // Вывод: Ср
```

Отличия от инструкции — в таблице:

| | `switch`-инструкция | `switch`-выражение |
|---|---|---|
| Синтаксис | `switch (x) { case ...: }` | `x switch { ... }` |
| Положение `switch` | перед выражением | после выражения |
| Возвращает значение | нет | да, у него есть тип |
| Разделитель ветвей | `case L:` + `break` | `паттерн => выражение,` |
| Тело ветви | список инструкций | ровно одно выражение |
| Ветвь «по умолчанию» | `default:` | `_ =>` (discard) |
| Что при отсутствии совпадения | молча ничего | `SwitchExpressionException` |
| Проверка полноты компилятором | нет | да, предупреждение CS8509 |
| Можно `goto case` | да | нет |
| Появилось | C# 1.0 | C# 8.0 |

### Гварды when

Паттерн можно уточнить произвольным булевым условием:

```csharp
static string Describe(int n) => n switch
{
    < 0 => "отрицательное",
    0 => "ноль",
    var x when x % 2 == 0 => "чётное положительное",
    _ => "нечётное положительное"
};

Console.WriteLine(Describe(-5));  // Вывод: отрицательное
Console.WriteLine(Describe(4));   // Вывод: чётное положительное
Console.WriteLine(Describe(7));   // Вывод: нечётное положительное
```

`when` работает и в `switch`-инструкции (`case int x when x > 0:`). Важно: ветви с `when` проверяются **по порядку**, компилятор не может построить по ним таблицу переходов — он вынужден генерировать последовательные проверки.

### Полнота (exhaustiveness) и SwitchExpressionException

Компилятор анализирует, покрывают ли ветви все возможные значения. Если нет — предупреждение CS8509 «выражение switch не обрабатывает все возможные значения».

```csharp
static string Bad(bool b) => b switch
{
    true => "да"
    // Предупреждение CS8509: не обработано значение false
};
```

Если во время выполнения ни один паттерн не подошёл, бросается `System.Runtime.CompilerServices.SwitchExpressionException`:

```csharp
try
{
    _ = Bad(false);
}
catch (System.Runtime.CompilerServices.SwitchExpressionException ex)
{
    Console.WriteLine(ex.GetType().Name);  // Вывод: SwitchExpressionException
}
```

Полнота для `enum` — отдельная история. Компилятор считает `switch` по enum полным, только если есть `_`, потому что в перечисление можно положить любое значение подлежащего типа: `(Tariff)999` — совершенно легальное значение типа `Tariff`. Подробнее — в [[Перечисления (enum)]].

### Паттерны в switch

Метки `case` и ветви `switch`-выражения принимают полноценные паттерны: типовые, свойств, позиционные, реляционные, логические, списочные. Это отдельная большая тема — [[Pattern matching]]. Здесь только вкус:

```csharp
abstract record Shape;
record Circle(double R) : Shape;
record Rect(double W, double H) : Shape;

static double Area(Shape s) => s switch
{
    Circle { R: <= 0 } => 0,                        // паттерн свойства + реляционный
    Circle c => Math.PI * c.R * c.R,                // типовой паттерн
    Rect (var w, var h) => w * h,                   // позиционный паттерн
    null => throw new ArgumentNullException(nameof(s)),
    _ => throw new NotSupportedException(s.GetType().Name)
};

Console.WriteLine(Area(new Rect(3, 4)));   // Вывод: 12
Console.WriteLine(Area(new Circle(0)));    // Вывод: 0
```

Обратите внимание на `null =>`: `switch`-выражение по ссылочному типу **не** бросает `NullReferenceException` само по себе, но типовые паттерны `null` не матчат, поэтому без явной ветви получите `SwitchExpressionException`.

## Во что компилируется switch

Это любимый вопрос собеседований, и ответ «в цепочку if» — неполный.

### switch по числам

Roslyn выбирает стратегию по **плотности** значений (отношение числа меток к диапазону).

Плотный набор (например, 1..7) компилируется в IL-инструкцию `switch` — это таблица переходов. JIT превращает её в машинный код вида «вычесть минимум, сравнить с длиной таблицы, прочитать адрес из массива, прыгнуть». Стоимость — O(1) независимо от числа веток.

```
switch (day) с метками 1..7  ->  IL:
    ldloc.0
    ldc.i4.1
    sub                 // нормализация: 1..7 превращается в 0..6
    switch (IL_0030, IL_0030, IL_0030, ..., IL_0050)
    br IL_0060          // default

Машинный код (упрощённо, x64):
    lea  eax, [rcx-1]
    cmp  eax, 6
    ja   default
    mov  rdx, [jumpTable + rax*8]
    jmp  rdx
```

Разреженный набор (`case 1: case 1000: case 1000000:`) в таблицу не превратить — она заняла бы мегабайты. Компилятор генерирует **бинарный поиск** по значениям: серию сравнений с медианой, глубиной log2(n). Для трёх-четырёх меток это просто цепочка `if`.

Проверить можно на sharplab.io или через `ildasm`/`dotnet-ildasm`. Про IL и то, как читать дизассемблер, — [[Сборки, метаданные и IL]].

### switch по строкам

Строку нельзя положить в jump table напрямую. Roslyn использует двухступенчатую схему:

1. Если меток мало (порог в Roslyn — 6, то есть до 6 включительно), генерируется просто цепочка `string.Equals(x, "a") ... string.Equals(x, "b")` — ординальных сравнений.
2. Если меток больше, компилятор генерирует в типе `<PrivateImplementationDetails>` метод `ComputeStringHash` (алгоритм FNV-1a, 32 бита), делает `switch` по хешу (уже как таблица переходов по числам), а внутри найденного бакета — контрольное `string.Equals` с настоящей строкой, чтобы отсеять коллизии.

```
switch (name) с 20 строковыми метками:

    hash = ComputeStringHash(name)      // FNV-1a, O(длина строки)
    switch (hash) { ... }               // jump table по числу
    if (name == "конкретная строка")    // проверка на коллизию
        -> тело секции
    else -> default
```

Итог: O(длина строки) на хеш плюс одно полное сравнение вместо N сравнений. Для больших `switch` по строкам это заметно быстрее наивной цепочки. Сравнение — всегда ординальное (побайтовое), культура не учитывается. Это важно: `switch` по строкам никогда не ведёт себя «по-турецки» (см. заметку [[Строки и работа с текстом]]).

> [!info] .NET 8+ и `FrozenDictionary`
> Если набор строк известен только в рантайме (например, читается из конфига), аналог хеш-switch — `FrozenDictionary<string, T>` из `System.Collections.Frozen`. Он строится дольше обычного словаря, но читается быстрее. См. [[Frozen и Immutable коллекции]].

## Операторы ?? и ??=

Оператор объединения с null (`??`) — сокращение частого ветвления «если null, то запасное значение»:

```csharp
string? input = null;
string result = input ?? "по умолчанию";
Console.WriteLine(result);   // Вывод: по умолчанию
```

Правая часть вычисляется лениво — только если левая оказалась `null`. Это принципиально: `GetFromCache() ?? LoadFromDatabase()` не пойдёт в базу при попадании в кеш.

`??=` (C# 8) присваивает, только если переменная сейчас `null`:

```csharp
List<string>? items = null;
items ??= new List<string>();     // Эквивалент: if (items is null) items = new();
items.Add("первый");
Console.WriteLine(items.Count);   // Вывод: 1
```

Классическое применение — ленивая инициализация поля:

```csharp
private HttpClient? _client;
private HttpClient Client => _client ??= new HttpClient();
```

Для многопоточного кода так делать нельзя: два потока могут одновременно увидеть `null` и создать два экземпляра. Там нужен `Lazy<T>` или `System.Threading.Lock` (C# 13).

`??` цепляется: `a ?? b ?? c ?? "fallback"`. И комбинируется с `?.`:

```csharp
string? name = null;
int length = name?.Length ?? 0;
Console.WriteLine(length);   // Вывод: 0
```

C# 14 добавил null-conditional присваивание — `?.` теперь можно писать и **слева** от `=`:

```csharp
// C# 14
public class Order { public string? Comment { get; set; } }

Order? order = null;
order?.Comment = "проверено";   // Ничего не делает, NRE нет.
                                // До C# 14 требовалось: if (order is not null) order.Comment = ...
```

Важное ограничение: `++`/`--` с null-conditional по-прежнему **не** разрешены — `order?.Count++` не компилируется.

## Ранний выход и guard clauses

Самое действенное лекарство от вложенности — не вкладывать, а выходить рано.

```csharp
// Плохо: пирамида судьбы
public decimal CalculateDiscount(Customer? customer, Order? order)
{
    if (customer is not null)
    {
        if (order is not null)
        {
            if (order.Total > 0)
            {
                if (customer.IsActive)
                {
                    return order.Total * customer.DiscountRate;
                }
            }
        }
    }
    return 0m;
}

// Хорошо: guard clauses, «счастливый путь» не отступает вправо
public decimal CalculateDiscountBetter(Customer? customer, Order? order)
{
    ArgumentNullException.ThrowIfNull(customer);
    ArgumentNullException.ThrowIfNull(order);

    if (order.Total <= 0) return 0m;
    if (!customer.IsActive) return 0m;

    return order.Total * customer.DiscountRate;
}
```

Второй вариант линеен: сверху отсекаются недопустимые состояния, дальше идёт основная логика без отступов. Подробно про то, что должно быть исключением, а что — возвратом значения, — в [[Защитное программирование и guard clauses]] и [[Когда исключение — плохой выбор]].

## Ветвление и производительность

Несколько практических наблюдений, которые стоит держать в голове (и не превращать в культ — сначала измерьте, см. [[Как измерять: BenchmarkDotNet]]):

| Приём | Эффект |
|---|---|
| Часто истинное условие — первым в цепочке `if` | предсказатель почти всегда угадывает, конвейер не рвётся |
| Хорошо предсказуемая ветвь (99 % в одну сторону) | практически бесплатна |
| Ветвь 50/50 в горячем цикле | до 15–20 тактов штрафа за промах |
| Замена ветви на арифметику без ветвления | иногда быстрее: `int max = a > b ? a : b` JIT может свернуть в `cmov` |
| `switch` по плотному диапазону | O(1) jump table, но косвенный переход — тоже плохо предсказывается |

Пример branchless-приёма, который JIT в .NET 10 умеет применять сам:

```csharp
// JIT для x64 может сгенерировать cmov вместо условного перехода
static int Max(int a, int b) => a > b ? a : b;

// Ветвление, зависящее от данных, — худший случай для предсказателя.
// Отсортированный массив здесь обрабатывается заметно быстрее случайного
// при абсолютно одинаковом коде.
static long SumAbove(int[] data, int threshold)
{
    long sum = 0;
    for (int i = 0; i < data.Length; i++)
    {
        if (data[i] >= threshold) sum += data[i];
    }
    return sum;
}
```

Это тот самый классический эффект «отсортированный массив обрабатывается быстрее»: код идентичен, но на отсортированных данных предсказатель после точки перехода угадывает всегда.

> [!warning] Подводные камни
> **1. Сравнение `double` через `==`.** Числа с плавающей точкой хранятся приближённо, поэтому `0.1 + 0.2 == 0.3` даёт `false` (реально получается 0.30000000000000004). Сравнивайте с допуском: `Math.Abs(a - b) < 1e-9`, а для денег вообще берите `decimal`. Отдельно: `double.NaN == double.NaN` — тоже `false` (так велит стандарт IEEE 754), проверяйте через `double.IsNaN(x)`. Подробности — в [[Типы данных и литералы]].
>
> **2. `==` для `string` сравнивает содержимое, а `ReferenceEquals` — нет.** `string` перегружает `==`, поэтому `s1 == s2` сравнивает символы. Но если переменные объявлены как `object`, перегрузка не выбирается (разрешение перегрузки статическое!) и сравниваются ссылки: `object a = "аб"; object b = new string(['а','б']); a == b` даёт `false`. Внутри `switch` по строкам всегда используется ординальное сравнение значений.
>
> **3. `switch` по `enum` без `default`.** Через полгода в перечисление добавят новое значение, и `switch` тихо не сработает (инструкция) или бросит `SwitchExpressionException` в проде (выражение). Всегда пишите `_ => throw new NotSupportedException(...)` — тогда ошибка проявится сразу и внятно, а не превратится в загадочный «пустой ответ». Плюс: перечисление может содержать значение, которого нет среди констант, — `(HttpStatusKind)42` компилируется и работает.
>
> **4. Побочные эффекты в условиях.** `if (list.Count > 0 && Process(list[0]))` — работает, `&&` короткозамкнутый. А `if (list.Count > 0 & Process(list[0]))` — с одним амперсандом обе стороны вычисляются всегда, и вы получите `ArgumentOutOfRangeException` на пустом списке. Разница между `&&`/`&` и `||`/`|` — в [[Операторы и выражения]].
>
> **5. Отступы врут, скобки — нет.** Висячий `else` и однострочные `if` без скобок регулярно порождают баги при последующем редактировании: кто-то добавляет вторую строку в тело `if`, и она внезапно выполняется всегда.
>
> **6. Ветви с `when` ломают оптимизацию.** Как только в `switch` появляется гвард, компилятор не может использовать jump table для затронутых меток и генерирует последовательные проверки. В горячем цикле на сотню веток это заметно.

> [!example] Как делают в бою
> **Маппинг доменной ошибки в HTTP-код** — типичный `switch`-выражение в веб-API:
>
> ```csharp
> public enum ErrorKind { NotFound, Conflict, Validation, Forbidden, Unexpected }
>
> static int ToStatusCode(ErrorKind kind) => kind switch
> {
>     ErrorKind.NotFound   => StatusCodes.Status404NotFound,
>     ErrorKind.Conflict   => StatusCodes.Status409Conflict,
>     ErrorKind.Validation => StatusCodes.Status400BadRequest,
>     ErrorKind.Forbidden  => StatusCodes.Status403Forbidden,
>     ErrorKind.Unexpected => StatusCodes.Status500InternalServerError,
>     _ => throw new ArgumentOutOfRangeException(nameof(kind), kind, "Неизвестный вид ошибки")
> };
> ```
>
> **Правило команды:** если `switch` по типу разросся больше 6–8 веток и повторяется в нескольких местах — это сигнал, что напрашивается полиморфизм или паттерн «Стратегия». Один `switch` по типу — нормально. Три одинаковых `switch` по тому же типу в разных файлах — уже проблема сопровождения: добавили новый тип, забыли обновить один из трёх.
>
> **Что включают в CI:** правила анализатора IDE0011 (обязательные скобки), IDE0066 (предпочитать `switch`-выражение), CS8509 как ошибку (`<WarningsAsErrors>CS8509</WarningsAsErrors>` в csproj) — последнее ловит неполные `switch`-выражения на этапе сборки, а не в проде.

## Вопросы с собеседований

> [!question]- Почему в C# нельзя написать `if (x)` для `int x`?
> Условие в `if` должно иметь тип `bool` (либо тип с пользовательским оператором `true`). Неявного преобразования `int -> bool` в C# нет — в отличие от C/C++, где ноль означает ложь. Это сделано ради безопасности: самая частая опечатка в C — `if (x = 5)` вместо `if (x == 5)` — в C# не компилируется, потому что результат присваивания `int` не приводится к `bool`. Цена: приходится писать `if (x != 0)`.

> [!question]- Чем `switch`-выражение отличается от `switch`-инструкции?
> Выражение возвращает значение и имеет тип, инструкция — нет. Синтаксис: `x switch { p => v, ... }` против `switch (x) { case c: ...; break; }`. В выражении тело ветви — одно выражение, `break` не нужен и невозможен, роль `default` играет discard `_`. Главное практическое отличие — компилятор проверяет полноту (CS8509), а при отсутствии совпадения в рантайме бросается `SwitchExpressionException`, тогда как инструкция без подходящего `case` просто ничего не делает. В выражении нет `goto case`, нельзя объявлять локальные переменные с инструкциями.

> [!question]- Во что компилируется `switch` по строкам?
> Зависит от количества меток. До шести включительно Roslyn генерирует цепочку ординальных `string.Equals`. Начиная с седьмой метки компилятор эмитит в скрытом типе `<PrivateImplementationDetails>` метод `ComputeStringHash` (FNV-1a, 32 бита), делает по хешу обычный целочисленный `switch` (то есть таблицу переходов), а внутри выбранной ветви — контрольное `string.Equals` с настоящей строкой, чтобы отсечь коллизию хешей. Итоговая сложность — O(длина строки) вместо O(N × длина). Сравнение всегда ординальное, культура не участвует.

> [!question]- Почему `switch` по `enum` желательно закрывать `default`, даже если все значения перечислены?
> Потому что перечисление в CLR — это просто обёртка над целочисленным типом, и значение вне списка констант абсолютно легально: `(Status)999` компилируется и работает. Плюс перечисление может пополниться после того, как ваш код написан (особенно если оно из чужой сборки), и тогда `switch` тихо промолчит. Ветка `_ => throw new ArgumentOutOfRangeException(...)` превращает «тихо неправильно» в «громко и сразу», что почти всегда лучше. Для флаговых перечислений `switch` вообще плохо подходит — там нужны битовые проверки.

> [!question]- Что делает `??=` и когда его нельзя использовать?
> `a ??= b` эквивалентно `if (a is null) a = b;`, причём `b` вычисляется лениво. Удобно для ленивой инициализации и подстановки значений по умолчанию. Нельзя использовать в многопоточном коде для кеширования: операция не атомарна, два потока могут одновременно увидеть `null` и создать два объекта. Там нужен `Lazy<T>`, `Interlocked.CompareExchange` или блокировка. Также `??=` не работает с типами, у которых нет `null` (не-nullable value types) — там компилятор просто скажет, что левая часть не может быть null.

> [!question]- Как порядок ветвей влияет на производительность и корректность?
> Корректность: цепочка `if/else if` проверяется сверху вниз и останавливается на первом истинном условии, поэтому более общее условие, поставленное раньше, делает последующие недостижимыми по смыслу (компилятор об этом не предупредит). То же для `switch`-выражения с гвардами `when` — они проверяются по порядку; для меток-констант порядок значения не имеет, компилятор их переупорядочивает и требует уникальности. Производительность: в цепочке `if` первым выгодно ставить самое частое условие — во-первых, меньше сравнений, во-вторых, предсказатель переходов процессора почти не промахивается. В `switch` с константами это неважно: там таблица переходов или бинарный поиск.

> [!question]- Что такое target-typed conditional и какую проблему он решил?
> До C# 9 тип тернарного выражения выводился только из самих ветвей: искался «наилучший общий тип». Если его не было (`int` и `null`, `MemoryStream` и `FileStream`), компилятор выдавал CS0173 и требовал явного приведения одной из ветвей. С C# 9 при неудаче поиска общего типа компилятор пробует преобразовать обе ветви к целевому типу — типу переменной, параметра или возвращаемого значения. Это убрало приведения вида `flag ? (int?)1 : null` и позволило писать `Stream s = flag ? new MemoryStream() : new FileStream(...)`.

## Задачи

### Задача 1. FizzBuzz через switch-выражение

Напишите метод `FizzBuzz(int n)`, возвращающий `"Fizz"` для кратных 3, `"Buzz"` для кратных 5, `"FizzBuzz"` для кратных 15 и строку с числом в остальных случаях. Используйте `switch`-выражение и кортежный паттерн, без цепочки `if`.

> [!success]- Решение
> ```csharp
> static string FizzBuzz(int n) => (n % 3, n % 5) switch
> {
>     (0, 0) => "FizzBuzz",
>     (0, _) => "Fizz",
>     (_, 0) => "Buzz",
>     _      => n.ToString()
> };
>
> for (int i = 1; i <= 15; i++)
>     Console.Write(FizzBuzz(i) + " ");
> // Вывод: 1 2 Fizz 4 Buzz Fizz 7 8 Fizz Buzz 11 Fizz 13 14 FizzBuzz
> ```
> Кортеж `(n % 3, n % 5)` вычисляется один раз, дальше идёт позиционный паттерн. Порядок ветвей значим: `(0, 0)` обязан идти первым, иначе кратные 15 поймает `(0, _)`. Discard `_` в паттерне означает «любое значение». Кортеж здесь не аллоцирует: `ValueTuple` — структура, см. [[Кортежи и деконструкция]].

### Задача 2. Классификатор HTTP-кода

Напишите метод, который по числовому HTTP-коду возвращает категорию: «информационный» (1xx), «успех» (2xx), «перенаправление» (3xx), «ошибка клиента» (4xx), «ошибка сервера» (5xx). Некорректный код (вне 100..599) должен приводить к исключению.

> [!success]- Решение
> ```csharp
> static string Category(int code) => code switch
> {
>     >= 100 and < 200 => "информационный",
>     >= 200 and < 300 => "успех",
>     >= 300 and < 400 => "перенаправление",
>     >= 400 and < 500 => "ошибка клиента",
>     >= 500 and < 600 => "ошибка сервера",
>     _ => throw new ArgumentOutOfRangeException(nameof(code), code, "Код вне диапазона 100..599")
> };
>
> Console.WriteLine(Category(204));  // Вывод: успех
> Console.WriteLine(Category(451));  // Вывод: ошибка клиента
> ```
> Здесь работают реляционные (`>=`, `<`) и логические (`and`) паттерны из C# 9. Такой `switch` не превращается в jump table — диапазоны компилируются в бинарный поиск по границам, что для пяти веток означает 2–3 сравнения. Альтернатива `code / 100 switch { 1 => ..., 2 => ... }` даёт настоящую таблицу переходов, но требует отдельной проверки диапазона.

### Задача 3. Убрать вложенность

Перепишите метод без вложенных `if`, используя ранний выход. Поведение должно остаться прежним.

```csharp
static string Process(string? input, bool trim, int maxLength)
{
    if (input != null)
    {
        if (input.Length > 0)
        {
            var s = trim ? input.Trim() : input;
            if (s.Length <= maxLength)
                return s;
            else
                return s.Substring(0, maxLength);
        }
        else
            return string.Empty;
    }
    else
        return string.Empty;
}
```

> [!success]- Решение
> ```csharp
> static string Process(string? input, bool trim, int maxLength)
> {
>     if (string.IsNullOrEmpty(input)) return string.Empty;
>
>     var s = trim ? input.Trim() : input;
>     return s.Length <= maxLength ? s : s[..maxLength];
> }
>
> Console.WriteLine(Process("  привет  ", trim: true, maxLength: 3));  // Вывод: при
> Console.WriteLine(Process(null, true, 10));                          // Вывод: (пусто)
> ```
> Два условия «null» и «пустая строка» схлопнулись в один `string.IsNullOrEmpty` (он ещё и помечен атрибутом `[NotNullWhen(false)]`, поэтому дальше компилятор знает, что `input` не null — см. [[Nullable reference types]]). Вложенность ушла с четырёх уровней до одного. `s[..maxLength]` — range-синтаксис из C# 8, эквивалент `Substring(0, maxLength)`, см. [[Индексаторы, Index и Range]].

### Задача 4. Найти ошибку

Что не так с этим кодом и как исправить?

```csharp
static bool IsAdmin(string role)
{
    switch (role.ToLower())
    {
        case "admin": return true;
        case "root": return true;
        default: return false;
    }
}
```

> [!success]- Решение
> Проблема — `ToLower()` без указания культуры. В турецкой локали (`tr-TR`) заглавная `I` переводится не в `i`, а в `ı` (без точки). Строка `"ADMIN"` превратится в `"admın"`, `case "admin"` не сработает, и администратор внезапно потеряет права на машине с турецкой культурой потока. Плюс `ToLower()` аллоцирует новую строку на каждый вызов.
>
> ```csharp
> static bool IsAdmin(string role) => role switch
> {
>     _ when role.Equals("admin", StringComparison.OrdinalIgnoreCase) => true,
>     _ when role.Equals("root",  StringComparison.OrdinalIgnoreCase) => true,
>     _ => false
> };
>
> // Или проще и быстрее, без switch:
> static bool IsAdminSimple(string role) =>
>     role.Equals("admin", StringComparison.OrdinalIgnoreCase) ||
>     role.Equals("root",  StringComparison.OrdinalIgnoreCase);
>
> Console.WriteLine(IsAdminSimple("ADMIN"));  // Вывод: True
> ```
> Общее правило: для сравнения технических идентификаторов (роли, коды, ключи конфигурации) всегда `StringComparison.Ordinal` или `OrdinalIgnoreCase`. Никогда `ToLower()`/`ToUpper()` ради сравнения — это и медленнее, и культурозависимо. Подробнее — в [[Строки и работа с текстом]].

## Итог

- Условие в C# обязано быть `bool`: неявного `int -> bool` нет, что убивает классическую опечатку `if (x = 5)`.
- `else` привязывается к ближайшему `if`; всегда ставьте фигурные скобки, это дешевле отладки.
- Тернарный оператор — выражение с ленивым вычислением ветвей; с C# 9 у него есть target typing, поэтому `int? x = flag ? 1 : null` компилируется.
- В `switch`-инструкции fall-through запрещён (CS0163), явный провал делается через `goto case`; все секции делят одну область видимости переменных.
- `switch`-выражение (C# 8) возвращает значение, использует `_` вместо `default`, проверяется на полноту компилятором (CS8509) и бросает `SwitchExpressionException`, если ничего не подошло.
- Числовой `switch` по плотному диапазону компилируется в IL-инструкцию `switch` (jump table, O(1)); разреженный — в бинарный поиск. Строковый от семи меток — в хеш FNV-1a плюс контрольное ординальное сравнение.
- Гварды `when` отключают табличную оптимизацию: ветви проверяются по порядку.
- Guard clauses и ранний выход — главное средство против вложенности; `??` и `??=` убирают половину проверок на null.
