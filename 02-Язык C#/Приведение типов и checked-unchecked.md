# Приведение типов и checked-unchecked

> [!abstract] Коротко
> Преобразования делятся на неявные (компилятор делает сам, потому что потерять данные невозможно) и явные (нужно приведение, потому что потеря возможна). Отдельная категория — разбор строк: `Parse`, `TryParse` и `Convert` ведут себя по-разному на пустых строках, мусоре и дробях, и путать их дорого. Целочисленное переполнение по умолчанию тихое: `int.MaxValue + 1` даёт отрицательное число без всяких сигналов, и включается проверка вручную — `checked`, блоком или свойством проекта.

## Зачем это нужно

Это тема с наибольшим числом тихих ошибок на строку кода:

```csharp
int total = (int)(price * quantity);        // отбросили копейки, а не округлили
int id = Convert.ToInt32(input);            // FormatException на пустой строке, но не на null
double rate = double.Parse(text);            // упало на проде, потому что там другая культура
int sum = a + b;                             // молча переполнилось и стало отрицательным
```

Ни одна из этих строк не вызывает подозрений на code review, и все четыре — реальные баги. Разобравшись раз, дальше пишешь правильно машинально.

## Неявные преобразования: когда данные заведомо не теряются

Компилятор разрешает без приведения только расширяющие (widening) преобразования.

```
sbyte → short → int → long → float → double
byte → short → ushort → int → uint → long → ulong → float → double
char  → ushort → int → ...
float → double
```

```csharp
int i = 42;
long l = i;             // ок: любой int влезает в long
double d = l;           // ок
decimal m = i;          // ок: любой целочисленный тип → decimal
char c = 'A';
int code = c;           // ок: 65
```

Исключения, которые надо знать:

```csharp
// float/double → decimal НЕЛЬЗЯ неявно, хотя decimal «точнее»:
// у них разные диапазоны и разные основания мантиссы
// decimal m2 = 1.5;         // Ошибка CS0664
decimal m2 = 1.5m;

// decimal → double тоже только явно: теряется точность
double d2 = (double)m2;

// long → float разрешено, хотя точность теряется (float даёт ~7 знаков):
float f = long.MaxValue;    // компилируется! Это узаконенная потеря точности
Console.WriteLine(f);        // Вывод: 9,223372E+18
```

Последний пункт — исторический компромисс: преобразования между целыми и плавающими считаются расширяющими по диапазону, хотя и теряют значащие цифры.

Для ссылочных типов неявное преобразование — это приведение к базовому типу или интерфейсу (upcast), оно всегда безопасно:

```csharp
string s = "текст";
object o = s;                    // upcast, неявно
IEnumerable<char> chars = s;      // к интерфейсу — тоже неявно
```

## Явные преобразования: приведение

```csharp
long big = 5_000_000_000;
int narrowed = (int)big;          // 705032704 — старшие биты отброшены, без предупреждения

double price = 19.99;
int rounded = (int)price;         // 19 — дробная часть ОТБРАСЫВАЕТСЯ, не округляется
int negative = (int)-19.99;       // -19 — округление к нулю, а не «вниз»

// Округление, если нужно именно оно:
Console.WriteLine(Math.Round(19.5));                                    // 20 (к чётному!)
Console.WriteLine(Math.Round(18.5));                                    // 18 (к чётному!)
Console.WriteLine(Math.Round(18.5, MidpointRounding.AwayFromZero));     // 19
Console.WriteLine(Math.Floor(19.99));                                   // 19
Console.WriteLine(Math.Ceiling(19.01));                                 // 20
Console.WriteLine(Math.Truncate(-19.99));                               // -19
```

`Math.Round` по умолчанию использует «банковское» округление к ближайшему чётному — это соответствует стандарту IEEE 754 и уменьшает систематическую ошибку при суммировании, но расходится с тем, что ожидает бухгалтерия. Для денег округление всегда задаётся явно.

### Плавающая точка в целое: особые случаи

```csharp
Console.WriteLine((int)double.NaN);              // 0
Console.WriteLine((int)double.PositiveInfinity); // 2147483647 (int.MaxValue)
Console.WriteLine((int)1e20);                    // 2147483647
```

Начиная с .NET 5 такие преобразования детерминированы и «насыщающие» (saturating): `NaN` даёт 0, выход за диапазон — граничное значение типа. До этого результат был платформозависимым — код, полагающийся на старое поведение, встречается в легаси. В `checked`-контексте те же выражения бросают `OverflowException`.

### Ссылочные типы: downcast

```csharp
object o = "текст";
string s1 = (string)o;              // ок
// int n = (int)o;                   // InvalidCastException в рантайме

// Безопасные варианты:
string? s2 = o as string;                        // null при несовпадении
if (o is string s3) Console.WriteLine(s3.Length); // проверка с объявлением
```

Приведение вниз по иерархии проверяется в рантайме, потому что компилятор не может знать фактический тип. Про выбор между `is`, `as` и приведением — [[Операторы и выражения]].

### Упаковка и распаковка

Особый случай преобразования между значимым типом и `object`:

```csharp
int value = 42;
object boxed = value;               // упаковка (boxing): аллокация в куче, копия значения
int unboxed = (int)boxed;           // распаковка (unboxing): копирование обратно
// long wrong = (long)boxed;         // InvalidCastException! Распаковать можно
                                    // ТОЛЬКО в исходный тип, даже если он «влезает»
long ok = (long)(int)boxed;          // сначала распаковать в int, потом расширить
```

Упаковка — это аллокация, то есть работа для GC. В горячем коде она незаметно съедает производительность: `object.Equals(a, b)` для структур, `string.Format` со значимыми типами, `List<object>`, интерфейсные вызовы на структурах. Подробно — [[Boxing и unboxing]].

### Свои преобразования

```csharp
public readonly record struct Celsius(double Degrees)
{
    // Неявное — только если потеря невозможна и операция очевидна
    public static implicit operator double(Celsius c) => c.Degrees;

    // Явное — если возможна потеря или неожиданный результат
    public static explicit operator Celsius(double d) => new(d);
}

Celsius t = (Celsius)36.6;
double raw = t;                     // неявно
```

Правило проектирования: неявное преобразование допустимо, только если оно не теряет данные и не может бросить исключение. Всё остальное — явное, а лучше — обычный метод с говорящим именем (`ToCelsius()`), потому что оператор преобразования не имеет имени и его легко применить случайно.

## Разбор строк: Parse, TryParse, Convert

Три семейства с разным поведением. Различия — не вкусовщина, они меняют поведение на плохих данных.

| | `int.Parse(s)` | `int.TryParse(s, out v)` | `Convert.ToInt32(s)` |
|---|---|---|---|
| `null` | `ArgumentNullException` | `false` | **0** |
| `""` | `FormatException` | `false` | `FormatException` |
| `"abc"` | `FormatException` | `false` | `FormatException` |
| `"2147483648"` | `OverflowException` | `false` | `OverflowException` |
| Стоимость на плохих данных | исключение | ноль | исключение |

```csharp
// Данные из внешнего мира (форма, файл, API) — только TryParse
if (!int.TryParse(input, out int quantity))
    return BadRequest("Количество должно быть целым числом");

// Внутренние данные, где нарушение — ошибка программиста: Parse уместен
int port = int.Parse(config["Port"]!);   // упадёт при старте, и это правильно

// Convert умеет ещё и числа→числа, и делает это с округлением, а не отбрасыванием:
Console.WriteLine(Convert.ToInt32(19.99));   // 20   — округление
Console.WriteLine((int)19.99);               // 19   — отбрасывание
Console.WriteLine(Convert.ToInt32(2.5));     // 2    — к ближайшему чётному
Console.WriteLine(Convert.ToInt32(3.5));     // 4
```

### Культура: главный источник «работает у меня»

```csharp
// В русской и узбекской культурах десятичный разделитель — запятая, в инвариантной — точка
Console.WriteLine(double.Parse("19.99", System.Globalization.CultureInfo.InvariantCulture)); // 19,99

// А так на машине с ru-RU получится 1999 (точка воспринята как разделитель групп!)
// Console.WriteLine(double.Parse("19.99"));

// Обратная сторона — форматирование:
double d = 19.99;
Console.WriteLine(d.ToString(System.Globalization.CultureInfo.InvariantCulture)); // 19.99
Console.WriteLine(d.ToString("F2", new System.Globalization.CultureInfo("ru-RU"))); // 19,99
```

Правило: **машинные данные — всегда `InvariantCulture`** (JSON, CSV, конфиги, интеграции, логи), **человеческий интерфейс — культура пользователя**. Ошибка в эту сторону обычно всплывает не сразу: локально и в CI культура одна, на сервере другая, и «внезапно» цена в 19.99 превращается в 1999. С .NET 5 приложения по умолчанию используют инвариантную культуру в контейнерах без ICU-данных, что снижает риск, но полагаться на это нельзя — правильный код передаёт культуру явно.

Обобщённый разбор через интерфейс `IParsable<T>` (.NET 7+) позволяет писать код, не привязанный к конкретному типу:

```csharp
static T ParseOrThrow<T>(string s) where T : IParsable<T>
    => T.Parse(s, System.Globalization.CultureInfo.InvariantCulture);

var a = ParseOrThrow<int>("42");
var b = ParseOrThrow<decimal>("19.99");
```

## checked и unchecked

По умолчанию арифметика целых в C# **не проверяет переполнение**. Причина — скорость: проверка на каждой операции стоит такты, а переполнение в большинстве кода невозможно по смыслу.

```csharp
int max = int.MaxValue;
Console.WriteLine(max + 1);              // -2147483648, без исключения

Console.WriteLine(checked(max + 1));      // OverflowException

checked
{
    int a = max;
    int b = a + 1;                        // OverflowException
}

unchecked
{
    // Иногда заворачивание нужно намеренно — например, при вычислении хешей
    int hash = unchecked(17 * 31 + value.GetHashCode());
}
```

Три важных уточнения:

1. **Константные выражения проверяются всегда.** `int x = int.MaxValue + 1;` не скомпилируется — компилятор считает константы сам и видит переполнение. Обойти можно только `unchecked(int.MaxValue + 1)`.
2. **`decimal` всегда бросает `OverflowException`**, независимо от контекста: его арифметика реализована в библиотеке, а не инструкциями процессора.
3. **`float`/`double` не переполняются вовсе** — они дают `Infinity`. Проверять надо через `double.IsFinite`.

Глобально проверки включаются в файле проекта:

```xml
<PropertyGroup Condition="'$(Configuration)' == 'Debug'">
  <CheckForOverflowUnderflow>true</CheckForOverflowUnderflow>
</PropertyGroup>
```

Практика: включать в Debug (чтобы ловить при разработке и в тестах), в Release оставлять выключенным ради производительности — либо расставлять `checked` точечно вокруг вычислений, где переполнение реально возможно (денежные суммы, счётчики, вычисление размеров).

Для своих типов с C# 11 можно определить отдельную проверяющую версию оператора:

```csharp
public readonly struct Money
{
    public long Cents { get; }
    public Money(long cents) => Cents = cents;

    public static Money operator +(Money a, Money b) => new(a.Cents + b.Cents);
    public static Money operator checked +(Money a, Money b) => new(checked(a.Cents + b.Cents));
}
```

Первый оператор вызывается в обычном контексте, второй — внутри `checked`. См. [[Перегрузка операторов]].

> [!warning] Подводные камни
> - **`(int)` вместо округления в денежных расчётах.** Приведение отбрасывает дробную часть, и итог систематически меньше — с ростом числа операций расхождение накапливается в одну сторону. Нужен `Math.Round` с явным `MidpointRounding`.
> - **`Convert.ToInt32(null)` возвращает 0.** Это тихое превращение «нет данных» в «ноль». Для внешних данных — только `TryParse`.
> - **`Parse` без культуры.** Работает локально, ломается на сервере с другой локалью. И наоборот: `ToString()` без культуры пишет в CSV запятую вместо точки, и файл перестаёт разбираться.
> - **Распаковка в «совместимый» тип.** `(long)boxedInt` бросает `InvalidCastException`: распаковывать можно только в исходный тип.
> - **`as` для значимых типов.** `o as int` не компилируется; работает только `o as int?`.
> - **Переполнение в промежуточном результате.** `checked` вокруг всего выражения не спасёт, если промежуточная величина считается в другом типе; иногда правильнее сразу считать в `long`: `(long)a * b`.
> - **`int.Parse` для идентификаторов из URL.** Пользователь пришлёт `/orders/abc` — и вместо 400 Bad Request получится 500 с исключением. Для входных данных парсинг всегда «пробующий»; в ASP.NET Core это делает model binding, и его результат надо проверять, а не парсить руками.

> [!example] Как делают в бою
> Границы системы (HTTP-запрос, файл, сообщение из брокера) — это единственное место, где данные разбираются из строк, и там используется `TryParse` с инвариантной культурой и явным ответом на невалидный ввод. Внутри системы значения уже типизированы, и никаких повторных парсингов нет — это признак хорошей архитектуры: если `decimal` парсится в трёх местах, значит модель не доделана.
> Денежные вычисления держат в `decimal` без промежуточных приведений, а округление делают один раз в конце, в явно названном методе, с зафиксированной стратегией. В коде это выглядит как `Money.Round(total)` — чтобы правило было в одном месте и покрыто тестом.
> `<CheckForOverflowUnderflow>` включают в Debug и в тестовой конфигурации: находить переполнение на этапе разработки дешевле, чем разбираться с отрицательной суммой заказа в проде.

## Вопросы с собеседований

> [!question]- Чем отличаются неявные и явные преобразования?
> Неявные компилятор выполняет сам, потому что потеря информации невозможна: расширение целочисленных типов (`int → long`), целое в плавающее, приведение к базовому типу или интерфейсу. Явные требуют оператора приведения, потому что данные могут быть потеряны или преобразование может не удаться: сужение (`long → int`), плавающее в целое (отбрасывание дробной части), downcast по иерархии (может бросить `InvalidCastException`), `double → decimal`. Отдельно стоит помнить исключение из логики: `long → float` разрешено неявно, хотя точность теряется — здесь критерием считается диапазон, а не число значащих цифр. Для своих типов правило проектирования такое же: неявный оператор преобразования допустим, только если он не теряет данные и не бросает исключений.

> [!question]- Чем `Parse` отличается от `TryParse` и от `Convert`?
> `Parse` бросает исключение на любых некорректных данных: `ArgumentNullException` на `null`, `FormatException` на мусоре, `OverflowException` на выходе за диапазон. `TryParse` не бросает ничего, возвращает `bool` и результат через `out` — это правильный выбор для любых данных из внешнего мира, потому что исключение на ожидаемо-плохом вводе и дорого, и семантически неверно. `Convert.ToInt32` ведёт себя как `Parse`, но с двумя отличиями: `null` превращает в 0 (тихая потеря информации) и умеет конвертировать между числовыми типами с округлением, а не отбрасыванием (`Convert.ToInt32(19.99)` — это 20, а `(int)19.99` — 19). Практика: `TryParse` на границах системы, `Parse` для внутренних данных, где нарушение формата — баг и падать надо громко, `Convert` — только когда нужно именно его поведение по округлению.

> [!question]- Что происходит при целочисленном переполнении в C#?
> По умолчанию действует контекст `unchecked`: результат вычисляется по модулю 2ⁿ и молча заворачивается — `int.MaxValue + 1` даёт `int.MinValue`. Это сделано ради производительности. Включить проверку можно выражением `checked(...)`, блоком `checked { }` или свойством проекта `CheckForOverflowUnderflow` — тогда бросается `OverflowException`. Есть три исключения из общего правила: константные выражения проверяются на этапе компиляции всегда; `decimal` бросает `OverflowException` независимо от контекста; `float` и `double` не переполняются, а дают `Infinity`, и проверяются через `double.IsFinite`. Практический подход — включать проверки в Debug и точечно оборачивать `checked` те вычисления, где переполнение возможно по смыслу данных.

> [!question]- Почему `(long)boxedInt` бросает исключение?
> Потому что распаковка (unboxing) — не преобразование, а извлечение значения из ранее упакованной копии. Рантайм проверяет, что запрашиваемый тип **точно совпадает** с типом, который был упакован, включая знаковость и размер; `int`, упакованный в `object`, можно распаковать только в `int`, хотя `long` его вмещает. Правильно писать `(long)(int)boxed`: сначала распаковка в исходный тип, затем обычное расширяющее преобразование. Побочно это объясняет, почему упаковка вредна для производительности: каждая упаковка — аллокация в куче с копированием значения, а каждая распаковка — проверка типа и ещё одно копирование.

> [!question]- Почему `double.Parse("19.99")` может вернуть 1999?
> Потому что без явной культуры используется текущая культура потока. В `ru-RU` и `uz-UZ` десятичный разделитель — запятая, а точка трактуется как разделитель групп разрядов, поэтому «19.99» разбирается как «1999». Локально и в CI культура часто инвариантная или английская, а на сервере — локальная, отсюда классическое «работает у меня». Правило: для машинных форматов (JSON, CSV, конфигурация, интеграции) всегда передавать `CultureInfo.InvariantCulture` и при разборе, и при форматировании; культуру пользователя применять только на границе с интерфейсом. То же касается дат: `DateTime.Parse` без культуры и без формата — источник ошибок с порядком дня и месяца.

## Задачи

### Задача 1. Найти четыре бага

```csharp
static decimal CalculateTotal(string priceText, string qtyText, string discountText)
{
    var price = decimal.Parse(priceText);
    var qty = Convert.ToInt32(qtyText);
    var discount = double.Parse(discountText);
    return (int)(price * qty * (decimal)(1 - discount));
}
```

> [!success]- Решение
> ```csharp
> static bool TryCalculateTotal(string priceText, string qtyText, string discountText, out decimal total)
> {
>     total = 0;
>     var ci = System.Globalization.CultureInfo.InvariantCulture;
>
>     if (!decimal.TryParse(priceText, System.Globalization.NumberStyles.Number, ci, out var price)
>         || !int.TryParse(qtyText, out var qty)
>         || !decimal.TryParse(discountText, System.Globalization.NumberStyles.Number, ci, out var discount))
>         return false;
>
>     total = Math.Round(price * qty * (1 - discount), 2, MidpointRounding.AwayFromZero);
>     return true;
> }
> ```
> Что было не так: `Parse` на внешних данных бросает исключение вместо валидируемого результата; `Convert.ToInt32(null)` вернул бы 0, тихо превратив отсутствие количества в нулевой заказ; отсутствие культуры делает разбор зависимым от локали сервера; `double` для скидки вносит двоичную погрешность в денежный расчёт, а `(int)` в конце отбрасывает копейки вместо округления — итог систематически занижен.

### Задача 2. Объяснить вывод

```csharp
Console.WriteLine(Math.Round(2.5));
Console.WriteLine(Math.Round(3.5));
Console.WriteLine(Math.Round(2.675, 2));
Console.WriteLine(Math.Round(2.675m, 2));
```

> [!success]- Решение
> Вывод: `2`, `4`, `2,67`, `2,68`.
> Первые две строки — банковское округление к ближайшему чётному (`MidpointRounding.ToEven` по умолчанию): 2,5 идёт к 2, 3,5 — к 4. Это соответствует IEEE 754 и не даёт систематического смещения при суммировании, но противоречит школьному правилу.
> Третья строка — не про округление, а про представление: 2,675 в `double` фактически равно 2,67499999999999982..., то есть до середины не доходит, и округление вниз формально верно.
> Четвёртая — `decimal` хранит 2,675 точно, попадает ровно на середину, и результат уже зависит от стратегии: по умолчанию к чётному, то есть 2,68.
> Практический вывод: для денег `decimal` плюс явный `MidpointRounding`, и никакого доверия «очевидному» результату округления `double`.

### Задача 3. Безопасное среднее и сумма

Напиши метод, вычисляющий сумму `int[]` так, чтобы переполнение было невозможно, и метод, возвращающий среднее как `decimal`.

> [!success]- Решение
> ```csharp
> static long Sum(int[] values)
> {
>     long sum = 0;                       // накопитель шире слагаемых — переполнение невозможно
>     foreach (var v in values) sum += v; // 2 млрд элементов по int.MaxValue всё ещё влезают в long
>     return sum;
> }
>
> static decimal Average(int[] values)
> {
>     if (values.Length == 0)
>         throw new ArgumentException("Массив пуст", nameof(values));
>     return (decimal)Sum(values) / values.Length;   // деление в decimal, а не целочисленное
> }
> ```
> Два приёма, которые надо запомнить. Первый — расширять тип накопителя, а не оборачивать всё в `checked`: `checked` сообщит о проблеме исключением, а `long` её просто не допустит. Второй — приводить к дробному типу **до** деления: `Sum(values) / values.Length` дало бы целочисленное деление, и `(decimal)` от результата уже не помог бы. Проверка на пустой массив нужна, потому что иначе получится `DivideByZeroException`, ничего не говорящий вызывающему; `nameof` подставит имя параметра в сообщение и не отстанет от кода при переименовании.

## Итог

- Неявно разрешены только преобразования, где данные заведомо не теряются; всё остальное — явно.
- Приведение плавающего к целому отбрасывает дробную часть; округление — это `Math.Round` с явной стратегией.
- С .NET 5 преобразование `double → int` детерминировано: `NaN` даёт 0, выход за диапазон — граничное значение; в `checked` — исключение.
- Распаковка возможна только в исходный тип; упаковка — аллокация, в горячем коде её избегают.
- `TryParse` на границах системы, `Parse` внутри, `Convert` — только за его особое поведение; `Convert.ToInt32(null)` даёт 0.
- Культуру при разборе и форматировании указывать всегда: `InvariantCulture` для машинных данных.
- Целочисленное переполнение по умолчанию тихое; `checked` включают точечно или глобально в Debug. `decimal` бросает всегда, `double` даёт `Infinity`.
