# Методы и параметры

> [!abstract] Коротко
> Метод — именованный блок кода с параметрами и возвращаемым значением; его подпись (имя, число и типы параметров с модификаторами) — то, по чему компилятор выбирает нужную перегрузку. Возвращаемый тип в подпись **не входит**, поэтому две перегрузки, отличающиеся только им, не скомпилируются. Модификаторы `ref`, `out`, `in` меняют способ передачи: аргумент передаётся не копией значения, а ссылкой на переменную вызывающего — и от этого зависит и семантика, и производительность. По умолчанию всё передаётся по значению, в том числе ссылки: это причина, по которой присваивание параметру внутри метода не видно снаружи.

## Зачем это нужно

Метод — единица декомпозиции. Всё, что делает код поддерживаемым (или нет), проявляется на уровне методов: сколько параметров, что они значат, можно ли вызвать метод неправильно.

Практические вопросы, на которые нужны ответы:

- почему `void Change(List<int> list)` меняет список у вызывающего, а `void Change(List<int> list)` с `list = new()` внутри — нет;
- когда `out` уместен (`TryParse`), а когда лучше кортеж или Result;
- почему добавление параметра со значением по умолчанию в библиотеку — потенциально ломающее изменение;
- зачем `in` для больших структур и почему он иногда делает код медленнее.

## Подпись и перегрузка

```csharp
int Add(int a, int b) => a + b;
double Add(double a, double b) => a + b;         // ок: другие типы параметров
int Add(int a, int b, int c) => a + b + c;       // ок: другое число параметров
// double Add(int a, int b) => a + b;             // Ошибка CS0111: подпись совпадает,
                                                 // возвращаемый тип в неё не входит
```

В подпись входят: имя, число параметров, их типы, модификаторы `ref`/`out`/`in` (частично) и число параметров типа для дженериков. Не входят: возвращаемый тип, имена параметров, значения по умолчанию, `params`.

```csharp
void Log(string message) { }
void Log(object value) { }
void Log(params string[] messages) { }

Log("текст");        // выбирается string — самый специфичный
Log(42);             // выбирается object — единственный подходящий
Log("a", "b");       // выбирается params-версия — она рассматривается ПОСЛЕДНЕЙ
```

Правила разрешения перегрузки, в порядке применения: сначала отбираются применимые кандидаты (по числу аргументов и возможности преобразования), затем выбирается наиболее специфичный (`string` предпочтительнее `object`, `int` предпочтительнее `long`), затем предпочитаются методы без опциональных параметров и без `params`. Если однозначного «лучшего» нет — ошибка CS0121 о неоднозначности.

> [!warning] Перегрузка + опциональные параметры = неоднозначность
> ```csharp
> void Send(string to, string subject = "") { }
> void Send(string to, string subject, bool urgent = false) { }
>
> // Send("a@b.c", "тема");     // Ошибка CS0121: подходят оба
> ```
> Смешивать перегрузки и значения по умолчанию — надёжный способ сломать вызывающий код. Выбирают одно: либо перегрузки, либо опциональные параметры.

## Передача по значению — что это значит на самом деле

По умолчанию аргумент **копируется**. Для значимых типов копируется значение, для ссылочных — ссылка (сам объект не копируется).

```csharp
static void ModifyValue(int x) => x = 99;
static void ModifyList(List<int> list) => list.Add(99);       // меняет ОБЪЕКТ
static void ReplaceList(List<int> list) => list = new() { 0 }; // меняет ЛОКАЛЬНУЮ копию ссылки

int number = 1;
var items = new List<int> { 1 };

ModifyValue(number);
Console.WriteLine(number);         // Вывод: 1  — копия значения изменена, исходник нет

ModifyList(items);
Console.WriteLine(items.Count);    // Вывод: 2  — тот же объект в куче

ReplaceList(items);
Console.WriteLine(items.Count);    // Вывод: 2  — присваивание затронуло копию ссылки
```

Это самый частый вопрос-ловушка про параметры. Формулировка, которую стоит запомнить: **ссылочные типы передаются по значению ссылки**. Через параметр можно менять состояние объекта, но нельзя заменить сам объект у вызывающего — для этого нужен `ref`.

## ref, out, in

```csharp
// ref — двусторонняя передача: переменная должна быть инициализирована до вызова
static void Swap(ref int a, ref int b) => (a, b) = (b, a);

int x = 1, y = 2;
Swap(ref x, ref y);
Console.WriteLine($"{x} {y}");     // Вывод: 2 1

// out — только «наружу»: метод ОБЯЗАН присвоить значение, до вызова оно не нужно
static bool TryDivide(int a, int b, out int result)
{
    if (b == 0) { result = 0; return false; }
    result = a / b;
    return true;
}

if (TryDivide(10, 3, out int q))    // out var — объявление прямо в вызове (C# 7)
    Console.WriteLine(q);            // Вывод: 3

// in — передача по ссылке только для чтения: избегает копирования больших структур
static double Distance(in Vector3 a, in Vector3 b)
{
    // a.X = 0;                      // Ошибка: in-параметр менять нельзя
    return Math.Sqrt((a.X - b.X) * (a.X - b.X) + (a.Y - b.Y) * (a.Y - b.Y));
}

// ref readonly параметр (C# 12) — как in, но требует явного ref/in у вызывающего
static double Length(ref readonly Vector3 v) => Math.Sqrt(v.X * v.X + v.Y * v.Y);
```

| Модификатор | Инициализация до вызова | Метод может читать | Метод может писать | Ключевое слово у вызывающего |
|---|---|---|---|---|
| (нет) | обязательна | да | только копию | нет |
| `ref` | обязательна | да | да | `ref` |
| `out` | не нужна | нет (до присваивания) | обязан | `out` |
| `in` | обязательна | да | нет | опционально |
| `ref readonly` | обязательна | да | нет | `ref` или `in` |

Практика применения:

- **`out`** — только для паттерна `Try*`: `TryParse`, `TryGetValue`, `TryDequeue`. Это устоявшаяся идиома, её узнают сразу.
- **`ref`** — редко: обмен значений, изменение элемента структуры на месте, работа с буферами. В прикладном коде почти всегда является признаком, что метод делает слишком много.
- **`in`** — оптимизация для больших `readonly struct` (16+ байт). Для маленьких структур и ссылочных типов вреден: добавляет разыменование без выгоды.

> [!danger] `in` с не-readonly структурой создаёт защитные копии
> Если структура не помечена `readonly`, компилятор не может доказать, что вызов её метода не изменит состояние, и на **каждое обращение** к члену через `in`-параметр создаёт защитную копию (defensive copy). Оптимизация превращается в пессимизацию: копий становится больше, чем было бы при обычной передаче. Правило: `in` применять только к `readonly struct`.

### Что нельзя с ref/out

```csharp
// async-методы не могут иметь ref/out параметров: они переживают возврат управления,
// а ссылка на стековую переменную вызывающего к тому моменту может стать невалидной
// static async Task<bool> TryLoadAsync(out int value) { }    // Ошибка

// Правильно — вернуть кортеж или Result-тип:
static async Task<(bool Success, int Value)> TryLoadAsync()
{
    await Task.Yield();
    return (true, 42);
}

// В лямбдах и итераторах ref/out тоже недоступны:
// Func<int> f = () => { TryDivide(1, 2, out int r); return r; };   // это можно
// но объявить лямбду С out-параметром, захватывающую ref-переменную — нет
```

С C# 14 модификаторы (`ref`, `out`, `in`, `scoped`, `ref readonly`) можно указывать у параметров лямбд **без указания типа**: `(ref x) => ...`. `params` по-прежнему требует явного типа.

## Опциональные и именованные аргументы

```csharp
static void Connect(string host, int port = 5432, bool useSsl = true, int timeoutSeconds = 30)
{
    Console.WriteLine($"{host}:{port} ssl={useSsl} timeout={timeoutSeconds}");
}

Connect("localhost");                                  // все значения по умолчанию
Connect("localhost", 5433);                            // позиционно
Connect("localhost", timeoutSeconds: 5);                // именованный аргумент — пропуск середины
Connect(host: "localhost", useSsl: false, port: 5433);  // порядок можно менять
```

Именованные аргументы — не только про пропуск: они делают вызов читаемым. `CreateUser("Иван", true, false, true)` не расшифровать без перехода к определению, а `CreateUser("Иван", isAdmin: true, isBlocked: false, sendEmail: true)` — можно.

> [!warning] Значение по умолчанию впаивается в место вызова
> Компилятор подставляет значение по умолчанию **в вызывающий код** на этапе компиляции. Если библиотека поменяет `int timeout = 30` на `int timeout = 60`, уже собранные приложения продолжат передавать 30, пока их не перекомпилируют. Отсюда два следствия: значение по умолчанию — часть публичного контракта, а не деталь реализации; для библиотечных API безопаснее перегрузки или объект параметров. Ровно та же механика у `const` — см. [[Переменные, const и readonly]].

Ограничения: значение по умолчанию должно быть константой времени компиляции (`null`, литерал, `default`, `new()` для значимых типов недоступен). Поэтому `List<int> items = new()` в качестве значения по умолчанию невозможно — вместо этого принимают `null` и подставляют внутри.

## params

```csharp
static int Sum(params int[] numbers)
{
    int total = 0;
    foreach (var n in numbers) total += n;
    return total;
}

Sum(1, 2, 3);              // компилятор создаёт массив [1,2,3]
Sum();                     // пустой массив (аллокация! для .NET 9+ — Array.Empty)
Sum([1, 2, 3]);            // можно передать коллекцию напрямую

// C# 13: params работает не только с массивом
static int SumSpan(params ReadOnlySpan<int> numbers)   // без аллокации в куче
{
    int total = 0;
    foreach (var n in numbers) total += n;
    return total;
}
static void Log(params IEnumerable<string> lines) { }   // тоже допустимо
```

`params ReadOnlySpan<T>` из C# 13 — важное улучшение: раньше каждый вызов `Sum(1,2,3)` создавал массив в куче, теперь компилятор может разместить значения на стеке. Именно поэтому в .NET 9/10 много методов BCL получили такие перегрузки (например, `string.Join`).

Ограничения: `params` — только последний параметр, только один, и вызывающий всегда может передать готовую коллекцию.

## Возврат нескольких значений

```csharp
// 1. Кортеж — современный способ по умолчанию
static (int Min, int Max) FindRange(int[] data)
{
    int min = int.MaxValue, max = int.MinValue;
    foreach (var x in data) { if (x < min) min = x; if (x > max) max = x; }
    return (min, max);
}
var (lo, hi) = FindRange([3, 7, 1]);

// 2. out — когда метод «пробует» и возвращает признак успеха
static bool TryFindRange(int[] data, out int min, out int max) { min = max = 0; return data.Length > 0; }

// 3. Свой тип — когда значений много или у них есть поведение
record OrderSummary(decimal Total, int ItemCount, bool HasDiscount);
```

Выбор: `out` — только для `Try*`-паттерна; кортеж — для двух-трёх значений без поведения; свой `record` — если значений больше трёх, если набор будет расширяться или если он появляется в нескольких местах. Кортеж с именами — не документация: имена не сохраняются в рантайме и легко теряются при передаче через `object`.

Про кортежи подробно — [[Кортежи и деконструкция]].

## Сколько параметров — слишком много

```csharp
// Плохо: понять вызов невозможно, порядок легко перепутать
Order CreateOrder(long customerId, string address, decimal total, decimal discount,
                  bool isExpress, string? comment, DateTimeOffset createdAt, string currency);

// Лучше: объект параметров, который заодно можно валидировать
record CreateOrderRequest(
    long CustomerId,
    string Address,
    decimal Total,
    string Currency)
{
    public decimal Discount { get; init; }
    public bool IsExpress { get; init; }
    public string? Comment { get; init; }
}

Order CreateOrder(CreateOrderRequest request);
```

Практическое правило: **больше четырёх параметров — повод остановиться**. Часто это признак, что метод делает несколько дел (нарушение SRP из [[SOLID]]) или что группа параметров образует понятие, которого не хватает в модели. Отдельный красный флаг — два-три подряд идущих `bool`: они превращают вызов в шифр и почти всегда означают, что нужны разные методы или enum.

## Прочее по методам

```csharp
// Тело-выражение (expression-bodied) для коротких методов
public decimal Total() => Items.Sum(i => i.Price);

// Статический локальный метод: гарантирует, что не захватывает внешнее состояние
static int Compute(int[] data)
{
    return Normalize(data.Sum());

    static int Normalize(int value) => value < 0 ? 0 : value;   // static — нет замыкания
}

// Возврат по ссылке: доступ к элементу без копирования (для больших структур)
static ref int First(int[] array) => ref array[0];
ref int slot = ref First(numbers);
slot = 42;                       // изменение попадает прямо в массив

// Рекурсия — там, где структура данных рекурсивна
static long Factorial(int n) => n <= 1 ? 1 : n * Factorial(n - 1);
// Осторожно: стек ограничен ~1 МБ, глубокая рекурсия даёт StackOverflowException,
// который нельзя поймать. Обход дерева большой глубины пишут со стеком в цикле.
```

Про локальные функции, захват переменных и их стоимость — [[Локальные функции и замыкания]]. Про методы расширения — [[Расширяющие методы и extension members]].

> [!warning] Подводные камни
> - **«Ссылочные типы передаются по ссылке».** Передаётся копия ссылки. Менять состояние объекта можно, заменить объект у вызывающего — нет.
> - **`out` вместо возврата значения.** Метод с тремя `out` невозможно скомпоновать в цепочку и нельзя использовать в LINQ. Кортеж или свой тип читаются лучше.
> - **Опциональные параметры в публичном API.** Значение по умолчанию впаивается в вызывающий код при компиляции; его изменение не долетает до уже собранных потребителей. В интерфейсах и виртуальных методах ещё хуже: реализация может объявить другое значение по умолчанию, и результат зависит от того, через какой тип вызвали.
> - **`in` с обычной (не `readonly`) структурой.** Компилятор вставляет защитные копии на каждое обращение — становится медленнее, чем без `in`.
> - **`params` в горячем пути.** Каждый вызов создаёт массив; для .NET 9+ используй перегрузку с `params ReadOnlySpan<T>`.
> - **Побитово идентичные перегрузки для `int`/`long`/`decimal`.** Литерал `1` — это `int`, и вызов может уйти не в ту перегрузку, что ожидалось. Особенно опасно, когда перегрузки различаются семантикой (миллисекунды против тиков).
> - **Мутация входных коллекций.** Метод `GetActiveUsers(List<User> users)`, который вдобавок вычищает список, — сюрприз для вызывающего. Метод либо возвращает новое, либо явно называется как изменяющий.

> [!example] Как делают в бою
> Подписи методов — это API, который читают чаще, чем реализацию, поэтому в зрелом коде видны устойчивые привычки. Метод возвращает результат, а не заполняет `out`-параметры; исключение — `Try*`-паттерн, который узнаётся с полувзгляда. Больше трёх-четырёх параметров сворачивается в `record`-запрос: заодно появляется место для валидации и для новых полей без ломающих изменений. Флаговые `bool` в параметрах заменяются enum'ами или отдельными методами: `Save(force: true)` — плохо, `SaveOrOverwrite()` — понятно.
> Асинхронные методы принимают `CancellationToken` последним параметром (по соглашению — с значением по умолчанию только в API-обёртках, во внутреннем коде без значения по умолчанию, чтобы его нельзя было забыть) и называются с суффиксом `Async`.
> `in`, `ref`, `ref readonly`, `params Span<T>` — инструменты инфраструктурного кода: сериализаторов, парсеров, математики. В прикладном коде их появление почти всегда означает, что оптимизацию делают там, где узкое место — сеть или база.

## Вопросы с собеседований

> [!question]- Чем отличаются `ref`, `out` и `in`?
> Все три передают аргумент по ссылке на переменную вызывающего, а не копией значения. `ref` — двунаправленный: переменная должна быть инициализирована до вызова, метод может и читать, и писать. `out` — только наружу: инициализация до вызова не требуется, метод **обязан** присвоить значение до возврата, читать его до присваивания нельзя; используется для `Try*`-паттерна. `in` — только для чтения: метод получает ссылку, но менять значение не может; смысл в том, чтобы не копировать большую структуру. Все три требуют ключевого слова в месте вызова (у `in` оно опционально), участвуют в подписи метода и запрещены в `async`-методах и итераторах, потому что те переживают возврат управления, а ссылка на стековую переменную к тому моменту может стать невалидной. Практически: `out` для `Try*`, `ref` редко, `in` — только для `readonly struct` от 16 байт.

> [!question]- Что произойдёт, если внутри метода присвоить параметру-списку новый список?
> Ничего у вызывающего не изменится. Ссылка передана по значению: параметр — это отдельная переменная, содержащая копию ссылки на тот же объект. Присваивание `list = new List<int>()` меняет только эту локальную копию, а переменная вызывающего продолжает указывать на исходный объект. При этом `list.Add(1)` изменение видно снаружи, потому что объект в куче один. Если нужно именно заменить объект у вызывающего, параметр объявляют как `ref List<int>`. Этот вопрос проверяет понимание разницы между «передача по ссылке» и «передача ссылки по значению» — вторая формулировка и есть правильная модель для C#.

> [!question]- Почему возвращаемый тип не входит в подпись метода?
> Потому что разрешение перегрузки происходит по аргументам вызова, а не по тому, куда результат присваивается. Если бы существовали `int Parse(string)` и `double Parse(string)`, то в выражении `var x = Parse("1")` компилятор не имел бы информации для выбора — контекст присваивания в общем случае недоступен (например, при `Parse("1").ToString()`). Поэтому CLR и C# требуют, чтобы методы различались именем, числом или типами параметров. Исключение, о котором иногда спрашивают: на уровне IL возвращаемый тип входит в сигнатуру метода, и рантайм может различать такие методы — но C# такой код породить не может, и обращаться к нему получится только через рефлексию.

> [!question]- Чем плохи опциональные параметры в публичной библиотеке?
> Значение по умолчанию не хранится в вызываемом методе — компилятор подставляет его в **вызывающий** код. Поэтому изменение значения по умолчанию в новой версии библиотеки не влияет на уже скомпилированные приложения: они продолжают передавать старое значение, и поведение расходится с документацией. Кроме того, добавление опционального параметра формально меняет подпись метода: код, использующий рефлексию, делегаты или реализующий интерфейс, может сломаться. В интерфейсах и виртуальных методах добавляется ещё одна ловушка: значения по умолчанию не наследуются, реализация может объявить другое значение, и результат зависит от статического типа, через который сделан вызов. Безопасная альтернатива — перегрузки или объект параметров с необязательными свойствами.

> [!question]- Когда `in` действительно ускоряет код?
> Только когда параметр — крупная структура (примерно от 16–24 байт) и она объявлена `readonly struct`. Тогда вместо копирования всех полей при каждом вызове передаётся один указатель, а компилятору не нужно защищаться от возможной мутации. Если структура не `readonly`, компилятор обязан предполагать, что вызов любого её метода или обращение к свойству может изменить состояние, и создаёт защитную копию на каждое такое обращение — в результате копий получается больше, чем при обычной передаче по значению. Для маленьких структур (`int`, `DateTime`, точка из двух полей) `in` тоже вреден: добавляется разыменование, а копирование 8 байт и так бесплатно. Для ссылочных типов `in` бессмысленен — ссылка и без него копируется как одно машинное слово.

## Задачи

### Задача 1. Что выведет

```csharp
static void Change(int[] array, List<int> list, string text)
{
    array[0] = 99;
    array = new int[] { -1 };
    list.Add(99);
    list = new List<int> { -1 };
    text += "!";
}

var a = new[] { 1 };
var l = new List<int> { 1 };
var s = "текст";
Change(a, l, s);
Console.WriteLine($"{a[0]} {l.Count} {s}");
```

> [!success]- Решение
> Вывод: `99 2 текст`.
> `array[0] = 99` меняет объект в куче — видно снаружи. `array = new int[]{-1}` заменяет только локальную копию ссылки — не видно. `list.Add(99)` меняет объект — видно, элементов стало 2. `list = new List<int>{-1}` — снова только локальная копия. `text += "!"` создаёт новую строку и присваивает её локальной копии ссылки; исходная строка иммутабельна, вызывающий видит «текст».
> Модель, которая объясняет все четыре случая одинаково: параметр — всегда новая переменная с копией переданного значения; для ссылочных типов значение — это ссылка. Менять то, на что ссылка указывает, можно; менять саму переменную вызывающего — нет, для этого нужен `ref`.

### Задача 2. Переписать API метода

Метод сложно вызвать правильно. Предложи лучшую подпись.

```csharp
static byte[]? Export(string path, bool compress, bool includeHeader, bool overwrite,
                      string? password, int retries, out string? error);
```

> [!success]- Решение
> ```csharp
> record ExportOptions
> {
>     public bool Compress { get; init; }
>     public bool IncludeHeader { get; init; } = true;
>     public bool Overwrite { get; init; }
>     public string? Password { get; init; }
>     public int Retries { get; init; } = 3;
> }
>
> // Успех/ошибка возвращаются типом результата, а не out-параметром
> static Task<Result<byte[]>> ExportAsync(string path, ExportOptions options, CancellationToken ct);
> ```
> Что улучшилось: три подряд `bool` в вызове больше не превращаются в загадку `Export(p, true, false, true, ...)`; новые опции добавляются без ломающего изменения подписи; значения по умолчанию живут в одном месте, а не впаиваются в каждый вызывающий код; ошибка стала возвращаемым значением, поэтому её невозможно проигнорировать так же незаметно, как `out string? error`; появился `CancellationToken`, потому что операция работает с файлами и сетью. Result-подход разобран в [[Result pattern вместо исключений]] и [[Когда исключение — плохой выбор]].

### Задача 3. Правильный Try-метод

Напиши метод, который разбирает строку вида `"ключ=значение"` по паттерну `Try*`, и объясни, почему здесь `out` уместен.

> [!success]- Решение
> ```csharp
> static bool TryParseSetting(string? line, out string key, out string value)
> {
>     key = value = string.Empty;                 // out-параметры обязаны быть присвоены
>                                                 // на ВСЕХ путях выхода, включая ранние return
>     if (string.IsNullOrWhiteSpace(line)) return false;
>
>     int sep = line.IndexOf('=');
>     if (sep <= 0 || sep == line.Length - 1) return false;
>
>     key = line[..sep].Trim();
>     value = line[(sep + 1)..].Trim();
>     return key.Length > 0;
> }
>
> if (TryParseSetting("timeout = 30", out var k, out var v))
>     Console.WriteLine($"{k} -> {v}");            // Вывод: timeout -> 30
> ```
> `out` уместен именно здесь по трём причинам: это узнаваемая идиома BCL (`int.TryParse`, `Dictionary.TryGetValue`), у метода ровно один «нормальный» результат плюс признак успеха, и отсутствие результата — ожидаемая ситуация, а не исключительная, поэтому бросать исключение было бы и семантически неверно, и дорого. Обязательное присваивание в самом начале избавляет от ошибки компиляции на ранних `return`. Если бы значений было три или требовалось сообщение об ошибке, правильнее был бы возврат `record`-результата.

## Итог

- Подпись — имя, число и типы параметров с модификаторами; возвращаемый тип в неё не входит.
- По умолчанию всё передаётся по значению; для ссылочных типов копируется ссылка — состояние менять можно, объект заменить нельзя.
- `out` — для `Try*`-паттерна, `ref` — редко и осознанно, `in` — только для `readonly struct` от 16 байт.
- `ref`/`out` невозможны в `async` и итераторах: там возвращают кортеж или Result.
- Значения по умолчанию впаиваются в вызывающий код: в публичном API это часть контракта, менять её небезопасно.
- `params` создаёт массив; с C# 13 есть `params ReadOnlySpan<T>` без аллокации.
- Больше четырёх параметров или два подряд `bool` — сигнал завести объект параметров или разделить метод.
- Имена параметров — часть читаемости: именованные аргументы делают вызов понятным без перехода к определению.
