# Отложенное и немедленное выполнение

> [!abstract] Коротко
> Большинство операторов LINQ (`Where`, `Select`, `OrderBy`) не выполняют запрос при вызове — они строят описание того, что нужно сделать, и выполняют его только при перечислении результата (`foreach`, `ToList()`, `First()`). Это отложенное выполнение, и оно — источник значительной доли реальных багов с LINQ: запрос выполняется не там и не тогда, где кажется по чтению кода.

## Зачем это знать

Код `var query = orders.Where(o => o.IsPaid);` не фильтрует ничего в момент выполнения этой строки. Если после неё изменить `orders` или зависимость внутри лямбды, следующий проход по `query` увидит уже другое состояние — не то, что было на момент объявления запроса. Незнание этого превращается в баги, которые не воспроизводятся стабильно и пропадают при добавлении отладочного `Console.WriteLine` (потому что он материализует запрос).

## Модель

Операторы делятся на две категории:

| Категория | Когда выполняется | Примеры |
|---|---|---|
| Отложенные (deferred) | при каждом перечислении результата | `Where`, `Select`, `OrderBy`, `GroupBy`, `Take`, `Skip`, `SelectMany` |
| Немедленные (immediate) | сразу при вызове | `ToList()`, `ToArray()`, `ToDictionary()`, `Count()`, `First()`, `Sum()`, `Any()` |

Механизм: `Where`/`Select` не проходят по коллекции сразу — они возвращают объект-итератор (`IEnumerable<T>`), реализующий `yield return` под капотом (см. [[IEnumerable, IEnumerator и yield return]]). Реальный проход происходит только тогда, когда что-то запрашивает следующий элемент — `foreach`, ручной вызов `MoveNext()`, или немедленный оператор, который сам делает `foreach` внутри.

```csharp
var numbers = new List<int> { 1, 2, 3 };
var query = numbers.Select(n => n * 2);   // ничего не выполнилось

numbers.Add(4);                            // список изменён ДО перечисления

foreach (var n in query)
    Console.WriteLine(n);
// Вывод: 2, 4, 6, 8 — включает добавленный элемент,
// потому что запрос выполнился только на этапе foreach
```

Второе следствие — повторное перечисление отложенного запроса выполняет его заново:

```csharp
var query = orders.Where(o => ExpensiveCheck(o));

var count = query.Count();      // ExpensiveCheck вызван для каждого заказа — раз
var list = query.ToList();      // ExpensiveCheck вызван для каждого заказа — ещё раз
```

Если `ExpensiveCheck` — запрос к БД или дорогая проверка, это удваивает (или умножает по числу использований) стоимость без единой видимой причины в коде — оба места выглядят безобидно.

## Решения

| Ситуация | Решение |
|---|---|
| Запрос используется больше одного раза | материализовать один раз через `.ToList()`/`.ToArray()` сразу после построения |
| Источник данных может измениться между построением запроса и его использованием | материализовать сразу же, если нужен снимок состояния на текущий момент |
| Запрос — это `IQueryable` к базе данных | не материализовывать раньше времени — отложенность здесь позволяет EF Core транслировать весь запрос в один SQL, см. [[IEnumerable vs IQueryable]] |
| Нужна лень намеренно (бесконечная последовательность, дорогой источник, который не всегда нужен целиком) | оставить отложенным, задокументировать это в имени переменной или комментарии |

## В ServiceShop

Для read-side через Dapper (см. [[ServiceShop: CQRS и путь запроса]]) вопрос отложенности не встаёт так остро — Dapper материализует результат сразу. Он актуален там, где `IEnumerable<T>` возвращается из доменного метода или сервиса и затем проходит через несколько LINQ-операторов в вызывающем коде: если этот `IEnumerable` обёрнут вокруг живого состояния (например, вычисляемое свойство агрегата), повторное перечисление может дать разные результаты при разных вызовах.

## Где ошибаются

> [!warning] Подводные камни
> - **Многократное перечисление дорогого запроса.** `query.Count()` и следом `query.ToList()` — источник данных проходится дважды, а если внутри есть побочный эффект или дорогой вызов — цена умножается незаметно для читающего код.
> - **Захват изменяемой переменной в лямбде отложенного запроса.** Если переменная, использованная в `Where`, меняется до момента перечисления, результат будет посчитан по значению на момент перечисления, а не на момент объявления запроса — см. также [[Делегаты, события и лямбды]].
> - **`IEnumerable`, возвращающий разные данные при каждом перечислении.** Метод вида `IEnumerable<T> GetItems() { foreach (...) yield return ...; }`, читающий изменяемое поле, — при двойном перечислении читателю кажется, что это «тот же список», хотя это два независимых прохода.
> - **Агент часто:** пишет `var result = query.Where(...).Select(...);` и затем использует `result` несколько раз в разных местах метода (например, для `Count` и для `ToList`) — не замечая, что каждое использование — отдельный проход по источнику.

## Проверка на ревью

- Запрос, используемый больше одного раза в методе, материализован (`.ToList()`/`.ToArray()`) один раз явно.
- Если отложенность нужна намеренно — это очевидно из контекста или подтверждено комментарием, а не побочный эффект невнимательности.
- В цепочке LINQ нет обращения к изменяемому внешнему состоянию, которое может отличаться между построением запроса и его выполнением.
- Запрос к `IQueryable` (EF Core) не материализован раньше времени — иначе фильтрация и сортировка уйдут в память вместо SQL.

## Проверь себя

> [!question]- Почему `orders.Where(o => o.IsPaid).Count()` и следующий за ним `.ToList()` на том же объекте запроса выполняют фильтрацию дважды?
> `Where` — отложенный оператор, он не проходит по коллекции сразу, а строит итератор. Каждый немедленный оператор (`Count()`, `ToList()`) сам инициирует новый проход `foreach` по этому итератору — источник данных и условие фильтрации выполняются заново при каждом таком вызове, потому что между вызовами ничего не сохранено.

> [!question]- В чём разница между отложенностью `IEnumerable` в LINQ to Objects и отложенностью `IQueryable` в EF Core, если механизм похож?
> В LINQ to Objects отложенность откладывает выполнение C#-кода (лямбд) до перечисления. В `IQueryable` отложенность откладывает не выполнение кода, а построение дерева выражений — и материализация (`ToList()`) — это момент, когда всё дерево целиком транслируется в один SQL-запрос и уходит в базу. Преждевременная материализация в `IQueryable`-сценарии не просто дублирует работу, а меняет то, где физически выполняется фильтрация — в базе или в памяти приложения.

## Разбор

### Разбор 1. Найди лишний проход

```csharp
IEnumerable<Order> GetUnpaidOrders(List<Order> orders) =>
    orders.Where(o => !o.IsPaid);

var unpaid = GetUnpaidOrders(orders);
if (unpaid.Any())
{
    Console.WriteLine($"Неоплаченных: {unpaid.Count()}");
    foreach (var o in unpaid)
        Notify(o);
}
```

Сколько раз в реальности выполняется фильтрация `!o.IsPaid` по коллекции `orders`? Почини, если считаешь нужным.

> [!success]- Разбор
> Три раза: `Any()`, `Count()` и `foreach` — каждый инициирует отдельный проход по отложенному запросу `unpaid`. Если `orders` большой или условие дорогое — это утроенная работа без единого явного признака в коде. Починка: `var unpaidList = GetUnpaidOrders(orders).ToList();` сразу после получения — дальше использовать список, а не отложенный запрос.

## Итог

- Отложенные операторы (`Where`, `Select`, `OrderBy`) строят описание запроса, а не выполняют его сразу; немедленные (`ToList`, `Count`, `First`) запускают проход
- Повторное перечисление отложенного запроса выполняет его заново — это может удвоить или умножить стоимость незаметно для чтения кода
- Материализуй запрос, если он используется больше одного раза или если источник может измениться до момента использования
- Для `IQueryable` (EF Core) отложенность — не баг, а механизм трансляции в один SQL; преждевременная материализация переносит работу из базы в память
