# SortedDictionary, SortedSet, SortedList

> [!abstract] Коротко
> Когда нужен не просто быстрый поиск по ключу, а ещё и **порядок**, `Dictionary`/`HashSet` бесполезны: они не дают никаких гарантий обхода. В BCL для этого есть три типа с разной внутренней механикой: `SortedDictionary<TKey,TValue>` и `SortedSet<T>` — красно-чёрное дерево (red-black tree) с O(log n) на всё, и `SortedList<TKey,TValue>` — два параллельных отсортированных массива с O(log n) на поиск и O(n) на вставку. Выбор между ними — это выбор между «часто меняю» и «часто читаю при минимуме памяти». Отдельно стоит `OrderedDictionary<TKey,TValue>` (.NET 9+), который хранит порядок **вставки**, а не сортировку.

## Зачем это нужно

`Dictionary<TKey,TValue>` отвечает на один вопрос: «есть ли такой ключ и что по нему лежит». Он не отвечает на вопросы, которые в бэкенде возникают постоянно:

1. **Диапазонные запросы (range queries).** «Все события с 10:00 до 11:00», «все цены от 100 до 200». В хеш-таблице для этого надо перебрать всё — O(n). В дереве или отсортированном массиве это O(log n) на поиск границы плюс O(k) на выдачу k результатов.
2. **Обход по порядку.** Отчёт, где строки идут по возрастанию ключа. С `Dictionary` порядок обхода — деталь реализации (он *похож* на порядок вставки, пока не было удалений, но опираться на это нельзя, см. [[Dictionary и HashSet изнутри]]).
3. **«Найти ближайший».** Ceiling/floor-запросы: «первая свободная дата не раньше указанной», «уровень тарифа для суммы X», «ближайший узел в consistent hashing». Классическая задача поиска предшественника/последователя.
4. **Min/Max за O(log n) без полного перебора.** В дереве это спуск по крайней левой/правой ветке. Если нужен только Min с приоритетом — смотри [[Очередь, стек, PriorityQueue]], `PriorityQueue<TElement,TPriority>` дешевле.

Раньше (до дженериков, .NET 1.x) существовал негенерик `System.Collections.SortedList` — та же идея, но с `object`-ключами, боксингом значимых типов и приведениями в каждом обращении. Он остался в BCL ради обратной совместимости и помечен как «не используйте в новом коде». `#устарело`

## Механика: почему дерево нужно балансировать

Начнём с обычного бинарного дерева поиска (binary search tree, BST). Инвариант: для любого узла всё в левом поддереве меньше него, всё в правом — больше. Поиск — спуск: сравнили, пошли влево или вправо. Стоимость поиска = высота дерева.

Проблема в том, что высота BST зависит от **порядка вставки**. Вставим 1, 2, 3, 4, 5 по возрастанию:

```
1
 \
  2
   \
    3
     \
      4
       \
        5        высота = 5, поиск = O(n) — это односвязный список
```

А это ровно тот случай, который в бэкенде встречается чаще всего: данные приходят из БД, уже отсортированные по `ORDER BY id`. Наивный BST деградировал бы именно на реальных данных, а не на искусственных.

Балансировка решает проблему: после каждой вставки/удаления структура локально перестраивается так, чтобы высота осталась логарифмической.

### Пять инвариантов красно-чёрного дерева

`SortedSet<T>` и `SortedDictionary<TKey,TValue>` в .NET используют красно-чёрное дерево. Каждый узел покрашен в красный или чёрный, и держатся правила:

1. Каждый узел — красный или чёрный.
2. **Корень чёрный.**
3. Все листья (условные NIL-узлы, «ничего») считаются чёрными.
4. **У красного узла оба ребёнка чёрные** — двух красных подряд по вертикали не бывает.
5. **Чёрная высота одинакова:** для любого узла число чёрных узлов на всех путях от него до листьев совпадает.

Из правил 4 и 5 математически выводится ограничение на высоту: `h ≤ 2·log2(n+1)`. Интуиция: правило 5 задаёт «идеально сбалансированный чёрный скелет», а правило 4 разрешает раздуть его красными узлами максимум вдвое — потому что красные не могут идти подряд. Отсюда гарантия O(log n) на поиск, вставку и удаление — не в среднем, а в **худшем случае**.

```
                 (13,B)
                /       \
           (8,R)         (17,R)
          /     \        /     \
      (1,B)   (11,B)  (15,B)  (25,B)
          \                   /    \
        (6,R)             (22,R)  (27,R)

B = чёрный, R = красный
Чёрная высота от корня вниз по любому пути = 3 (считая NIL)
Красных подряд нет. Корень чёрный. Инварианты соблюдены.
```

### Поворот (rotation)

Вставка идёт как в обычном BST, новый узел красится **красным** (чтобы не сломать правило 5), а затем, если появились два красных подряд, дерево лечится перекраской и/или поворотом. Поворот — локальная операция на трёх ссылках, которая меняет высоту поддеревьев, но сохраняет порядок BST.

```
Левый поворот вокруг X (X --> вниз-влево, Y --> вверх):

      X                            Y
     / \                          / \
    A   Y        ==>             X   C
       / \                      / \
      B   C                    A   B

Порядок сохранён: A < X < B < Y < C  --  в обоих вариантах.
Высота правой ветки уменьшилась на 1, левой — увеличилась на 1.
```

Ключевое свойство: поворот — это O(1) работы (переприсваивание ссылок), а лечение после вставки требует не больше O(log n) шагов вверх по дереву и **не больше двух поворотов**. Поэтому вставка суммарно O(log n).

> [!info] Почему именно красно-чёрное, а не AVL
> AVL-дерево держит баланс строже (высота ближе к log2 n), поэтому чуть быстрее на чтении, но требует больше поворотов на изменение. Красно-чёрное — компромисс в пользу записи. `ImmutableList<T>` из [[Frozen и Immutable коллекции]], наоборот, построен на AVL, потому что там важнее предсказуемая глубина и переиспользование узлов.

## SortedList: два массива вместо дерева

`SortedList<TKey,TValue>` не дерево. Внутри — ровно два массива одинаковой длины:

```
keys:    [ "aa", "bb", "cc", "dd", "ee", ---, ---, --- ]
values:  [   1 ,   7 ,   3 ,   9 ,   4 , ---, ---, --- ]
           ^-- отсортирован по компаратору        ^-- Count=5, Capacity=8
                                                     свободный хвост

Поиск ключа "cc": Array.BinarySearch по keys --> индекс 2 --> values[2] = 3.

Вставка "b0" (должен встать на индекс 1):
keys:    [ "aa", "b0", "bb", "cc", "dd", "ee", ---, --- ]
                  ^^^^  <-- всё правее сдвинуто на одну позицию (Array.Copy)
```

Отсюда все свойства:

- **Поиск — O(log n)**, бинарный поиск по плотному массиву. Данные лежат подряд, поэтому кеш процессора работает идеально: несколько последних шагов бинарного поиска попадают в одну-две кеш-линии. Дерево на тех же данных прыгает по случайным адресам в куче — почти каждый шаг это промах кеша.
- **Вставка/удаление в середину — O(n)**: `Array.Copy` сдвигает хвост. Зато вставка **в конец** (ключ больше всех имеющихся) — амортизированное O(1), как у `List<T>`.
- **Память минимальна**: два массива и всё. Никаких узлов, заголовков объектов и ссылок.
- **Доступ по индексу** — уникальная возможность среди отсортированных коллекций:

```csharp
var prices = new SortedList<string, decimal>
{
    ["BTC"] = 61000m,
    ["ETH"] = 3400m,
    ["SOL"] = 145m,
};

// Доступ по порядковому номеру в отсортированном порядке
Console.WriteLine(prices.GetKeyAtIndex(0));    // BTC
Console.WriteLine(prices.GetValueAtIndex(0));  // 61000
prices.SetValueAtIndex(0, 62000m);             // изменить значение по индексу

Console.WriteLine(prices.IndexOfKey("SOL"));   // 2
Console.WriteLine(prices.Keys[1]);             // ETH  (Keys — IList<TKey>)
prices.RemoveAt(2);                            // удалить третий по порядку

prices.Capacity = 16;   // предвыделить, если знаешь размер
prices.TrimExcess();    // отдать лишнюю память обратно
```

`GetKeyAtIndex`/`GetValueAtIndex`/`SetValueAtIndex` — методы, добавленные в .NET 6; в старом коде встретишь `sortedList.Keys[i]` и `sortedList.Values[i]`, которые делают то же самое, но через обёртки-коллекции.

## Таблица сравнения

| Тип | Структура | Поиск по ключу | Вставка | Удаление | Порядок обхода | Память на элемент | Индексный доступ |
|---|---|---|---|---|---|---|---|
| `Dictionary<K,V>` | хеш-таблица | O(1) | O(1)* | O(1) | не определён | ~1.3× массив | нет |
| `SortedDictionary<K,V>` | красно-чёрное дерево | O(log n) | O(log n) | O(log n) | по возрастанию ключа | высокая (узел ~48 Б) | нет |
| `SortedList<K,V>` | 2 массива | O(log n) | **O(n)** | **O(n)** | по возрастанию ключа | **минимальная** | да |
| `SortedSet<T>` | красно-чёрное дерево | O(log n) | O(log n) | O(log n) | по возрастанию | высокая (узел ~40 Б) | нет |
| `OrderedDictionary<K,V>` | хеш-таблица + массив записей | O(1) | O(1) в конец, O(n) в середину | O(n) | **по вставке** | средняя | да |
| `List<T>` + `Sort()` | массив | O(log n) после сортировки | O(1) в конец | O(n) | после сортировки | минимальная | да |

\* амортизированное, с редким O(n) на resize.

Главный практический вывод, который спрашивают на собеседовании:

| Сценарий | Победитель | Почему |
|---|---|---|
| Заполнить один раз, потом только читать | `SortedList` | быстрее на чтении (локальность кеша), меньше памяти в 2–3 раза |
| Много случайных вставок и удалений | `SortedDictionary` | O(log n) против O(n) — на 100 000 элементов разница на порядки |
| Заполнить отсортированными данными | `SortedList` | вставка в конец O(1), итого O(n) на всё заполнение |
| Заполнить неотсортированными данными | `List` + `Sort()`, затем в `SortedList`/поиск | O(n log n) один раз вместо O(n²) |
| Диапазон значений без ключей | `SortedSet` | `GetViewBetween` |
| Нужен только порядок вставки | `OrderedDictionary` | O(1) поиск + стабильный порядок |

## Дерево решений

```
Нужен ли порядок вообще?
├── Нет  --> Dictionary / HashSet (см. [[Dictionary и HashSet изнутри]])
│           если только читаешь после старта --> FrozenDictionary
└── Да
    ├── Порядок = порядок ВСТАВКИ (не сортировка)
    │       --> OrderedDictionary<K,V>  (.NET 9+)
    └── Порядок = СОРТИРОВКА по ключу
        ├── Нужны и ключи, и значения
        │   ├── Коллекция после заполнения не меняется --> SortedList<K,V>
        │   ├── Данные приходят уже отсортированными   --> SortedList<K,V>
        │   └── Частые вставки/удаления в середину     --> SortedDictionary<K,V>
        └── Нужны только элементы (множество)
            ├── Нужны диапазоны, Min/Max, операции множеств --> SortedSet<T>
            └── Нужен только минимум/максимум по приоритету --> PriorityQueue
```

Отдельная ветка: если сортировка нужна **только при выводе** (в API-ответе, в отчёте), не надо держать отсортированную структуру. Держи `Dictionary` и сортируй в момент вывода через `OrderBy` — один раз O(n log n) вместо log n на каждой из миллиона вставок.

## OrderedDictionary: порядок вставки, а не сортировка

Классическая задача: LRU-кеш, список полей формы, история операций — нужен быстрый поиск по ключу **и** стабильный порядок вставки. До .NET 9 это делали руками: `Dictionary<TKey, LinkedListNode<...>>` плюс `LinkedList<...>`. В .NET 9 появился `OrderedDictionary<TKey,TValue>` из `System.Collections.Generic`: внутри хеш-таблица для поиска плюс массив записей, задающий порядок.

```csharp
using System.Collections.Generic;

var steps = new OrderedDictionary<string, int>();
steps.Add("validate", 10);
steps.Add("charge", 20);
steps.Add("notify", 30);

// Обход строго в порядке вставки
foreach (var (name, ms) in steps)
    Console.WriteLine($"{name}: {ms}");
// validate: 10
// charge: 20
// notify: 30

// Индексный доступ
Console.WriteLine(steps.GetAt(1));        // [charge, 20]
steps.SetAt(1, 25);                       // изменить значение второй записи
steps.Insert(1, "authorize", 15);         // вставить на позицию 1
Console.WriteLine(steps.IndexOf("notify")); // 3
steps.RemoveAt(0);
```

### Новое в .NET 10: перегрузки с `out int index`

В .NET 10 добавлены перегрузки, которые сразу возвращают позицию записи. Это убирает лишний проход: раньше после `TryAdd` приходилось отдельно вызывать `IndexOf`, то есть искать ключ дважды.

```csharp
var counters = new OrderedDictionary<string, int>();

// .NET 10: узнать индекс сразу при добавлении
if (counters.TryAdd("errors", 1, out int index))
{
    // ключа не было, он добавлен на позицию index
    Console.WriteLine($"новая запись на {index}");
}
else
{
    // ключ уже был на позиции index — обновляем без повторного поиска
    counters.SetAt(index, counters.GetAt(index).Value + 1);
}

// .NET 10: получить значение и его индекс одним обращением
if (counters.TryGetValue("errors", out int value, out int idx))
    Console.WriteLine($"{value} на позиции {idx}");  // 1 на позиции 0
```

Пара `TryGetValue(..., out index)` + `SetAt(index, ...)` — это способ обновить значение по ключу за один поиск вместо двух (`ContainsKey` + индексатор). Подробнее о новинках версии — в [[Новое в C# 12, 13, 14]].

## SortedSet: диапазоны и множества

`SortedSet<T>` — единственная коллекция BCL, дающая честный range view:

```csharp
var events = new SortedSet<int> { 5, 12, 18, 23, 31, 42, 55, 67 };

Console.WriteLine(events.Min);   // 5   — спуск по левой ветке, O(log n)
Console.WriteLine(events.Max);   // 67

// Представление на диапазон [18, 42]. Это НЕ копия — это view на дерево.
SortedSet<int> window = events.GetViewBetween(18, 42);
Console.WriteLine(string.Join(", ", window));   // 18, 23, 31, 42
Console.WriteLine(window.Count);                // 4

// View живой: изменения видны в обе стороны
window.Add(25);
Console.WriteLine(events.Contains(25));         // True

// Обратный обход без копирования и сортировки
Console.WriteLine(string.Join(", ", events.Reverse()));
// 67, 55, 42, 31, 25, 23, 18, 12, 5

// Операции множеств выполняются на месте
var blocked = new SortedSet<int> { 23, 31, 99 };
var allowed = new SortedSet<int>(events);
allowed.ExceptWith(blocked);
Console.WriteLine(string.Join(", ", allowed));  // 5, 12, 18, 25, 42, 55, 67

// TryGetValue достаёт фактически хранимый экземпляр
// (полезно, когда компаратор считает равными разные объекты)
events.TryGetValue(42, out int actual);
```

> [!warning] Границы GetViewBetween
> Добавление в view элемента вне диапазона бросает `ArgumentOutOfRangeException` — view «знает» свои границы. Также `Count` у view — это O(log n) обход, а не поле, в отличие от `Count` у самого множества.

### Роль компаратора

Порядок задаётся `IComparer<T>`. Если не передать свой, берётся `Comparer<T>.Default`, который использует `IComparable<T>`/`IComparable` типа — подробно в [[Сравнение объектов: IEquatable, IComparable, компараторы]].

```csharp
// Обратный порядок и регистронезависимость через Comparer<T>.Create
var desc = new SortedSet<string>(
    Comparer<string>.Create((a, b) => string.Compare(b, a, StringComparison.OrdinalIgnoreCase)));

desc.Add("beta");
desc.Add("Alpha");
desc.Add("gamma");
Console.WriteLine(string.Join(", ", desc));   // gamma, beta, Alpha

// Составной ключ: сначала по приоритету (убывание), потом по имени
record Job(string Name, int Priority);

var queue = new SortedSet<Job>(Comparer<Job>.Create((x, y) =>
{
    int byPriority = y.Priority.CompareTo(x.Priority);
    return byPriority != 0 ? byPriority : string.CompareOrdinal(x.Name, y.Name);
}));
```

Обрати внимание на вторую часть компаратора: сравнение по имени добавлено не для красоты. Компаратор, возвращающий 0 для разных объектов, в множестве означает «это один и тот же элемент», и второй объект просто не добавится.

> [!info] Lookup<TKey,TElement>
> Результат `ToLookup()` — `Lookup<TKey,TElement>`, иммутабельная мультикарта «ключ → набор элементов». Это не отсортированная коллекция: порядок групп соответствует порядку первого появления ключа. Используется для группировки в памяти, разбор — в [[Группировка, соединения, агрегация]].

## Практический пример: поиск ближайшего значения

Задача «найти тарифную ставку для суммы» — это floor-запрос по отсортированным границам. На `SortedList` он решается бинарным поиском без аллокаций:

```csharp
sealed class TariffTable
{
    private readonly SortedList<decimal, decimal> _rates;

    public TariffTable(IEnumerable<(decimal From, decimal Rate)> rows)
    {
        // Заполняем отсортированными данными -> все вставки в конец, O(n) итого
        var ordered = rows.OrderBy(r => r.From).ToList();
        _rates = new SortedList<decimal, decimal>(ordered.Count);
        foreach (var (from, rate) in ordered)
            _rates.Add(from, rate);
    }

    // Ставка для суммы = ставка последней границы, не превышающей сумму
    public decimal RateFor(decimal amount)
    {
        var keys = _rates.Keys;          // IList<decimal>, доступ по индексу
        int lo = 0, hi = _rates.Count - 1, found = -1;

        while (lo <= hi)
        {
            int mid = lo + (hi - lo) / 2;
            if (keys[mid] <= amount) { found = mid; lo = mid + 1; }
            else hi = mid - 1;
        }

        if (found < 0)
            throw new ArgumentOutOfRangeException(nameof(amount), "Сумма ниже минимальной границы");

        return _rates.GetValueAtIndex(found);
    }
}

var table = new TariffTable([(0m, 0.02m), (10_000m, 0.015m), (100_000m, 0.01m)]);
Console.WriteLine(table.RateFor(50_000m));   // 0.015
Console.WriteLine(table.RateFor(9_999m));    // 0.02
```

С `SortedDictionary` так не получится: индексного доступа у дерева нет, и floor-запрос пришлось бы эмулировать через `GetViewBetween` на `SortedSet` ключей или через линейный проход.

> [!warning] Подводные камни
>
> **1. `SortedList` заполняют в случайном порядке и получают O(n²).** Каждая вставка в середину — `Array.Copy` хвоста. На 100 000 случайных ключей это порядка 2.5 миллиардов операций копирования вместо 1.7 миллиона у дерева. Симптом в проде: «стартовая инициализация справочника занимает 40 секунд». Лечение: отсортировать источник заранее (`OrderBy` + `Add` в порядке возрастания) или взять `SortedDictionary` на время наполнения.
>
> **2. Компаратор, возвращающий 0 для разных элементов, тихо теряет данные.** `SortedSet<T>`/`SortedDictionary<TKey,TValue>` определяют равенство **только** через компаратор, а не через `Equals`/`GetHashCode`. Если сравниваешь заказы по сумме, два разных заказа на 100 рублей — один элемент: `Add` вернёт `false` (у `SortedDictionary.Add` будет `ArgumentException` «duplicate key»). Данные не потеряны в кавычках — они реально не попали в коллекцию, и никакого исключения при `Add` у множества не будет. Правило: компаратор обязан быть **полным** — доводи сравнение до уникального поля (id).
>
> **3. Некорректный компаратор — исключение в рантайме, а не ошибка компиляции.** `new SortedDictionary<MyKey, int>()` компилируется для любого `MyKey`. Если `MyKey` не реализует `IComparable<MyKey>`/`IComparable` и компаратор не передан, `Comparer<MyKey>.Default` бросит исключение при **первом сравнении** — то есть при первом `Add` с уже непустой коллекцией: `ArgumentException` с текстом «At least one object must implement IComparable». Ошибка вылезет в проде на втором элементе, а тест с одним элементом пройдёт. Дополнительно: компаратор обязан быть согласованным (антисимметричным и транзитивным). Нарушение (`Compare` с плавающей логикой, `NaN`, побочные эффекты) ломает инварианты дерева и даёт «пропадающие» элементы без исключений.
>
> **4. Два разных `SortedList`.** `System.Collections.Generic.SortedList<TKey,TValue>` — современный дженерик. `System.Collections.SortedList` — негенерик из .NET 1.0 с `object`-ключами: боксинг значимых типов, приведения на каждом чтении, `Add(object, object)`. В легаси-коде под `using System.Collections;` можно случайно получить именно его. Проверяй, какой `using` в файле. `#устарело`
>
> **5. Память дерева заметно больше.** Узел `SortedSet<T>.Node` на x64 — заголовок объекта (16 байт) + две ссылки на детей (16) + элемент + флаг цвета с выравниванием: порядка 40 байт на элемент даже для `int`. У `SortedDictionary` в узле лежит `KeyValuePair<TKey,TValue>`, то есть ещё больше. `SortedList<int, int>` на те же данные — 8 байт на элемент в двух массивах. Разница в 5+ раз, плюс дерево создаёт n объектов для сборщика мусора, см. [[Поколения GC, LOH и режимы сборщика]].
>
> **6. `Count` у view от `GetViewBetween` — не O(1).** Это обход поддиапазона. В цикле `for (int i = 0; i < view.Count; i++)` получишь квадратичное поведение (и обращаться по индексу к view всё равно нельзя).

> [!example] Как делают в бою
> **Справочник тарифов/лимитов в памяти.** Загружается из БД при старте, дальше только читается. Берут `SortedList<decimal, Tariff>` (или сразу `FrozenDictionary`, если диапазоны не нужны), заполняют отсортированным источником, кладут в singleton. Ноль аллокаций на запрос, всё в кеше процессора.
>
> **Тайм-серия событий в окне.** `SortedSet<(DateTime, long)>` или `SortedDictionary<DateTime, Event>` с периодической очисткой «хвоста» старше N минут: `foreach (var k in dict.Keys.TakeWhile(k => k < cutoff).ToList()) dict.Remove(k);`. Удаление за O(log n) — то, чего нет у `SortedList`.
>
> **Что чаще встречается в реальном коде.** В прикладном бэкенде отсортированные коллекции нужны редко: обычно достаточно `Dictionary` + `OrderBy` при выводе, а диапазонные запросы делает БД по индексу ([[Индексы: как работают и когда помогают]]). Не тащи дерево в память там, где `ORDER BY` в SQL решает задачу дешевле.
>
> **Consistent hashing / шардирование.** Кольцо виртуальных узлов — это `SortedDictionary<uint, Node>` (или `SortedList`, если кольцо не меняется), поиск шарда — «первый ключ ≥ hash», с закольцовкой на `Min`. Здесь дерево оправдано: узлы добавляются и удаляются при масштабировании.

## Вопросы с собеседований

> [!question]- Чем `SortedDictionary` отличается от `SortedList`? Что быстрее?
> Это разные структуры данных с одинаковым интерфейсом. `SortedDictionary` — красно-чёрное дерево: все операции O(log n), но каждый элемент это отдельный объект-узел со ссылками, память высокая и обход прыгает по куче. `SortedList` — два параллельных отсортированных массива (keys и values): поиск O(log n) бинарным поиском, но вставка и удаление в середину O(n) из-за сдвига массива. Однозначного «быстрее» нет: `SortedList` быстрее на чтении и заметно экономнее по памяти за счёт плотной укладки и локальности кеша, `SortedDictionary` быстрее при частых изменениях в случайных позициях. Практическое правило: заполнил один раз и читаю — `SortedList`; коллекция постоянно меняется — `SortedDictionary`.

> [!question]- Почему красно-чёрное дерево даёт O(log n) в худшем случае?
> Из инвариантов. Правило «одинаковая чёрная высота на всех путях» задаёт сбалансированный чёрный каркас глубиной около log2(n). Правило «у красного узла нет красных детей» не даёт вставить между чёрными уровнями больше одного красного, то есть удлинить путь больше чем вдвое. Отсюда формальная граница высоты `h ≤ 2·log2(n+1)`. Поиск, вставка и удаление — это спуск на высоту плюс O(1) поворотов и O(log n) перекрасок, значит все они логарифмические не в среднем, а гарантированно. Без балансировки BST деградирует до списка: вставка отсортированных данных даёт высоту n и O(n) на поиск.

> [!question]- Зачем нужен `OrderedDictionary`, если есть `SortedDictionary`?
> Они решают разные задачи. `SortedDictionary` даёт порядок по **значению ключа** через компаратор, ценой O(log n) на все операции. `OrderedDictionary<TKey,TValue>` (.NET 9+) даёт порядок **вставки** и при этом сохраняет O(1) поиск по ключу, потому что внутри обычная хеш-таблица плюс массив записей для порядка. Он нужен там, где важна последовательность добавления: LRU-структуры, конвейеры шагов, поля формы, история. Раньше это собирали вручную из `Dictionary` + `LinkedList`. В .NET 10 у него появились перегрузки `TryAdd(key, value, out int index)` и `TryGetValue(key, out value, out int index)`, чтобы работать с `GetAt`/`SetAt` без повторного поиска ключа.

> [!question]- Что произойдёт, если компаратор для `SortedSet<T>` вернёт 0 для двух разных объектов?
> Второй объект не будет добавлен, а `Add` вернёт `false`. Для отсортированных коллекций компаратор — единственный источник истины о равенстве: `Equals` и `GetHashCode` не используются вообще. Это классический источник «пропадающих» данных: сравнили заказы только по сумме, и все заказы с одинаковой суммой слились в один. У `SortedDictionary.Add` ситуация заметнее — будет `ArgumentException` про дубликат ключа, но через индексатор `dict[key] = value` перезапись пройдёт молча. Правило: компаратор всегда доводи до уникального поля (id), даже если основная сортировка по другому полю.

> [!question]- Как в .NET найти в отсортированной коллекции все элементы в диапазоне?
> Через `SortedSet<T>.GetViewBetween(lowerValue, upperValue)` — он возвращает не копию, а живое представление на поддерево, поэтому получение view это O(log n), а перечисление O(k) по числу элементов в диапазоне. Изменения через view видны в исходном множестве и наоборот; добавление элемента вне границ бросает `ArgumentOutOfRangeException`. У `SortedDictionary` аналога нет — там либо линейный `Where` (что убивает смысл), либо приходится держать отдельный `SortedSet` ключей. У `SortedList` диапазон достаётся вручную: `Array.BinarySearch`-подобный поиск границы плюс проход по индексам через `GetKeyAtIndex`/`GetValueAtIndex`.

> [!question]- Почему у `SortedList` нет проблем с производительностью при заполнении отсортированными данными?
> Потому что вставка нового максимального ключа не требует сдвига: элемент дописывается в конец массива, и стоимость амортизированное O(1), как у `List<T>.Add`. Внутри `SortedList.Add` делает бинарный поиск позиции (O(log n)) и `Array.Copy` только для хвоста правее позиции — а при вставке в конец хвост пустой. Итого заполнение n отсортированных элементов это O(n log n) на поиски и O(n) на копирование, что практически линейно. Если же ключи приходят в случайном порядке, средний сдвиг — половина массива, и суммарная стоимость становится O(n²). Поэтому стандартный приём: отсортировать источник (`OrderBy`) перед заполнением.

> [!question]- Когда отсортированная коллекция — неправильный выбор?
> Когда порядок нужен только на выходе. Держать дерево, платя O(log n) за каждую из миллиона вставок, чтобы один раз вывести отчёт, — хуже, чем `Dictionary` плюс `OrderBy` при формировании ответа: одна сортировка O(n log n) дешевле миллиона логарифмов и не создаёт n узлов для GC. Также неправильно, если нужен только минимум или максимум — для этого есть `PriorityQueue<TElement,TPriority>` на бинарной куче, он дешевле и по памяти, и по константе. И совсем неправильно, если данные лежат в БД: диапазонный запрос по индексу выполнит СУБД, не надо вытаскивать таблицу в память ради `GetViewBetween`.

## Задачи

### Задача 1. Ближайшая свободная дата

Реализуй `BookingCalendar` с методом `DateOnly NextFree(DateOnly from)`: возвращает первую дату не раньше `from`, которая не занята. Занятые даты добавляются через `Book(DateOnly)`. Метод должен работать быстрее линейного перебора всех занятых дат.

> [!success]- Решение
> ```csharp
> using System.Collections.Generic;
>
> sealed class BookingCalendar
> {
>     private readonly SortedSet<DateOnly> _booked = [];
>
>     public bool Book(DateOnly date) => _booked.Add(date);
>
>     public DateOnly NextFree(DateOnly from)
>     {
>         // View на "всё, что >= from" — O(log n) на получение
>         var tail = _booked.GetViewBetween(from, DateOnly.MaxValue);
>
>         DateOnly candidate = from;
>         // Идём по занятым датам подряд: как только нашли разрыв — там и свободно
>         foreach (var busy in tail)
>         {
>             if (busy > candidate) break;      // разрыв найден
>             candidate = busy.AddDays(1);      // busy == candidate, сдвигаемся
>         }
>         return candidate;
>     }
> }
>
> var cal = new BookingCalendar();
> cal.Book(new DateOnly(2026, 8, 5));
> cal.Book(new DateOnly(2026, 8, 6));
> cal.Book(new DateOnly(2026, 8, 9));
>
> Console.WriteLine(cal.NextFree(new DateOnly(2026, 8, 5)));  // 2026-08-07
> Console.WriteLine(cal.NextFree(new DateOnly(2026, 8, 9)));  // 2026-08-10
> Console.WriteLine(cal.NextFree(new DateOnly(2026, 8, 1)));  // 2026-08-01
> ```
> Ключ решения — `GetViewBetween`: мы не перебираем все занятые даты, а начинаем сразу с первой, которая ≥ `from`, и идём только по непрерывной серии занятых дней. Стоимость — O(log n) на вход в диапазон плюс длина серии. `HashSet` тут не подошёл бы: он не даёт упорядоченного обхода начиная с нужной точки, пришлось бы проверять `Contains` для каждого дня подряд.

### Задача 2. Почему заполнение тормозит

Код грузит справочник из 200 000 строк и работает 30 секунд. Найди причину и исправь, сохранив тип коллекции.

```csharp
var dict = new SortedList<int, string>();
foreach (var row in ReadFromDbUnordered())   // порядок случайный
    dict.Add(row.Id, row.Name);
```

> [!success]- Решение
> ```csharp
> // Причина: SortedList вставляет в середину за O(n) (Array.Copy хвоста).
> // 200 000 случайных вставок ~ 200_000^2 / 2 = 2*10^10 операций копирования.
>
> // Вариант 1: отсортировать источник — тогда все вставки идут в конец, O(1) каждая
> var rows = ReadFromDbUnordered().OrderBy(r => r.Id).ToList();
> var dict = new SortedList<int, string>(rows.Count);   // сразу нужная Capacity
> foreach (var row in rows)
>     dict.Add(row.Id, row.Name);
>
> // Вариант 2 (ещё лучше): переложить сортировку на БД
> // SELECT id, name FROM refs ORDER BY id  --> вставки уже в конец
>
> // Вариант 3: если менять тип коллекции всё-таки можно и вставки будут дальше —
> // SortedDictionary: O(log n) на вставку в любую позицию.
> ```
> Дополнительно важен конструктор с capacity: без него внутренние массивы удваиваются с копированием, а на 200 000 элементов это ещё около 18 перевыделений. Проверить разницу удобно через [[Как измерять: BenchmarkDotNet]] — на этом кейсе она составляет три-четыре порядка.

### Задача 3. Счётчик с порядком вставки на .NET 10

Реализуй счётчик событий, который сохраняет порядок первого появления события и обновляет счётчик за **один** поиск ключа. Используй `OrderedDictionary<TKey,TValue>` и перегрузки .NET 10.

> [!success]- Решение
> ```csharp
> using System.Collections.Generic;
>
> sealed class EventCounter
> {
>     private readonly OrderedDictionary<string, int> _counts = new();
>
>     public void Hit(string name)
>     {
>         // .NET 10: TryAdd сразу отдаёт индекс записи —
>         // и при успешном добавлении, и когда ключ уже есть
>         if (!_counts.TryAdd(name, 1, out int index))
>         {
>             // Ключ был: обновляем по индексу, повторного хеширования нет
>             _counts.SetAt(index, _counts.GetAt(index).Value + 1);
>         }
>     }
>
>     public IEnumerable<(string Name, int Count)> InOrder()
>     {
>         for (int i = 0; i < _counts.Count; i++)
>         {
>             var kv = _counts.GetAt(i);
>             yield return (kv.Key, kv.Value);
>         }
>     }
> }
>
> var c = new EventCounter();
> c.Hit("login"); c.Hit("pay"); c.Hit("login"); c.Hit("logout"); c.Hit("pay");
>
> foreach (var (name, count) in c.InOrder())
>     Console.WriteLine($"{name} = {count}");
> // login = 2
> // pay = 2
> // logout = 1
> ```
> Наивная реализация `_counts[name] = _counts.GetValueOrDefault(name) + 1` делает **два** поиска по ключу: чтение и запись. Здесь `TryAdd(..., out index)` возвращает позицию записи, а `SetAt`/`GetAt` работают по индексу в массиве записей — это прямой доступ без хеширования. До .NET 10 пришлось бы вызывать `IndexOf(name)` отдельно, то есть искать ключ второй раз.

## Итог

- Отсортированный контейнер нужен для диапазонных запросов, обхода по порядку и поиска ближайшего значения — там, где `Dictionary` бессилен, потому что не даёт гарантий порядка.
- `SortedDictionary`/`SortedSet` — красно-чёрное дерево: пять инвариантов держат высоту в пределах `2·log2(n+1)`, поэтому O(log n) гарантировано в худшем случае, а не в среднем. Балансировка нужна потому, что без неё вставка отсортированных данных превращает BST в связный список.
- `SortedList` — два параллельных массива: поиск бинарный O(log n) с отличной локальностью кеша, минимум памяти и индексный доступ, но вставка/удаление в середину O(n). Заполнение случайными ключами даёт O(n²).
- Правило выбора: один раз заполнил и читаю — `SortedList`; часто меняю — `SortedDictionary`; нужен порядок вставки, а не сортировка — `OrderedDictionary` (.NET 9+, в .NET 10 — перегрузки с `out int index`); сортировка нужна только на выводе — `Dictionary` + `OrderBy`.
- Компаратор в отсортированных коллекциях определяет и порядок, и равенство. Неполный компаратор (0 для разных объектов) молча теряет элементы; отсутствие `IComparable` у ключа даёт исключение в рантайме, а не при компиляции.
- Дерево платит памятью: около 40–48 байт на узел против 8–16 байт на элемент в массивах, плюс n объектов для сборщика мусора.
