# Обзор коллекций .NET и как выбирать

> [!abstract] Коротко
> BCL даёт около тридцати готовых коллекций, разложенных по семи пространствам имён, и почти все они решают одну и ту же задачу — «хранить много объектов» — но с разной ценой операций, разными гарантиями порядка и разной потокобезопасностью. Выбор коллекции — это выбор структуры данных под профиль обращений: читаем мы или пишем, ищем по индексу или по ключу, нужен ли порядок, живёт ли она в одном потоке. Ошибка выбора не ломает код, она делает его в десятки раз медленнее и в разы жаднее к памяти, поэтому на собеседовании эту тему спрашивают почти всегда.

## Зачем это нужно

Первые версии .NET (Framework 1.0, 2002) не имели дженериков, и коллекции хранили `object`. Код выглядел так:

```csharp
// .NET Framework 1.0 — как жили до дженериков  #устарело
ArrayList numbers = new ArrayList();
numbers.Add(1);          // int -> object: boxing, аллокация в куче
numbers.Add("не число"); // компилятор молчит: типобезопасности нет
int sum = 0;
foreach (object o in numbers)
    sum += (int)o;       // unboxing + InvalidCastException на второй элемент
```

Проблем здесь три, и все три системные:

1. **Boxing.** Каждое значимое (value type) значение при добавлении упаковывается в объект на куче. Миллион `int` в `ArrayList` — это миллион мелких объектов вместо одного массива на 4 МБ. Подробнее в [[Boxing и unboxing]].
2. **Отсутствие типобезопасности.** `ArrayList` принимает всё, ошибка вылезает в рантайме при распаковке, а не при компиляции.
3. **Медленные сравнения.** `Contains`, `Sort`, `IndexOf` работали через `object.Equals` и `IComparable` с виртуальными вызовами и распаковкой на каждом шаге.

C# 2.0 и .NET Framework 2.0 (2005) принесли дженерики (generics), и `List<T>`/`Dictionary<TKey, TValue>` закрыли вопрос: типы проверяются компилятором, `List<int>` внутри держит настоящий `int[]`, никакого boxing. Дальше эволюция шла надстройками: неизменяемые коллекции (2013), конкурентные (2010, вместе с TPL), «замороженные» read-only коллекции с ускоренным поиском (.NET 8), `OrderedDictionary<TKey, TValue>` (.NET 9).

**Вывод для практики:** `System.Collections` (без `.Generic`) в новом коде не используется никогда. Он остался только ради обратной совместимости и встречается в легаси, в старых COM-интеропах и в API вроде `HttpContext.Items` (`IDictionary<object, object>` — уже дженерик, но с `object`).

| `System.Collections.Specialized` | System.Collections.Specialized | `NameValueCollection`, `StringDictionary`, `OrderedDictionary` (негенерик!), `HybridDictionary`, `BitVector32` | Легаси-конфиги, `HttpUtility.ParseQueryString`. `#устарело` |

> [!warning] Ловушка с именами
> `System.Collections.Specialized.OrderedDictionary` (негенерик, .NET Framework 2.0) и `System.Collections.Generic.OrderedDictionary<TKey, TValue>` (.NET 9) — разные типы. Первый хранит `object` и внутри держит и хеш-таблицу, и `ArrayList`. Второй — нормальная современная коллекция. Аналогично `System.Collections.SortedList` (негенерик) и `System.Collections.Generic.SortedList<TKey, TValue>`.
> `FrozenDictionary` лежит в пространстве `System.Collections.Frozen`, но физически — в сборке `System.Collections.Immutable.dll`. Ищете `using` — нужен именно `System.Collections.Frozen`.

## Иерархия интерфейсов

```
                        IEnumerable  (негенерик, object)
                             ^
                             |
                        IEnumerable<T>            <- ковариантен: out T
                        /          |         \
                       /           |          \
      IReadOnlyCollection<T>  ICollection<T>   IAsyncEnumerable<T> (отдельная ветка)
        |            |             |    \    \
        |            |             |     \    \
IReadOnlyList<T>  IReadOnlySet<T>  IList<T>  ISet<T>  IDictionary<TKey,TValue>
        |         (.NET 5+)                              |
IReadOnlyDictionary<TKey,TValue> ------------------------- (параллельная read-only ветка)
```

Что реально даёт каждый уровень:

| Интерфейс | Добавляет | Ключевая мысль |
|---|---|---|
| `IEnumerable<T>` | `GetEnumerator()` | Только «пройти один раз вперёд». Размер неизвестен, повторный проход может дать другой результат или бросить исключение |
| `IReadOnlyCollection<T>` | `Count` | Появился в .NET 4.5. Знаем размер, менять нельзя |
| `IReadOnlyList<T>` | `this[int]` | Индексируемый снимок |
| `IReadOnlySet<T>` | `Contains`, `IsSubsetOf`, ... | .NET 5. До него read-only множество приходилось отдавать как `IReadOnlyCollection<T>`, теряя быстрый `Contains` |
| `IReadOnlyDictionary<TKey,TValue>` | `this[TKey]`, `TryGetValue`, `ContainsKey` | Read-only словарь |
| `ICollection<T>` | `Add`, `Remove`, `Clear`, `Contains`, `Count`, `IsReadOnly` | Мутируемое множество без порядка |
| `IList<T>` | `this[int]` (get+set), `Insert`, `RemoveAt`, `IndexOf` | Позиционный доступ |
| `ISet<T>` | `UnionWith`, `IntersectWith`, `ExceptWith`, ... | Операции над множествами |
| `IDictionary<TKey,TValue>` | `this[TKey]`, `Add`, `Remove`, `TryGetValue`, `Keys`, `Values` | Ассоциативный доступ |

### Что принимать в параметре и что возвращать из метода

Правило: **принимай самый общий тип, который тебе достаточен; возвращай самый конкретный, который не обещает лишнего.**

```csharp
// Плохо: требуем List<T>, хотя нам нужен только проход
void Process(List<Order> orders) { foreach (var o in orders) { /* ... */ } }

// Хорошо: подойдёт массив, HashSet, результат LINQ, yield-итератор
void Process(IEnumerable<Order> orders) { foreach (var o in orders) { /* ... */ } }

// Если внутри нужен Count или два прохода — просите IReadOnlyCollection<T>/IReadOnlyList<T>:
// это честный контракт «мне нужен материализованный набор».
decimal Total(IReadOnlyCollection<Order> orders)
    => orders.Count == 0 ? 0m : orders.Sum(o => o.Amount);
```

Для возврата:

```csharp
public sealed class Cart
{
    private readonly List<Order> _orders = [];

    // Плохо: наружу утекает изменяемый список, любой может сделать cart.Orders.Clear()
    public List<Order> BadOrders => _orders;

    // Плохо: IEnumerable<T> честен по контракту, но вызывающий сделает .Count() и .ToList()
    public IEnumerable<Order> MehOrders => _orders;

    // Хорошо: контракт «читаемый список известного размера», без обещания изменяемости
    public IReadOnlyList<Order> Orders => _orders;

    public void Add(Order order) => _orders.Add(order); // изменение только через метод
}
```

> [!info] Почему не `IEnumerable<T>` для возврата коллекции
> `IEnumerable<T>` не говорит, материализована ли коллекция. Вызывающий вынужден защищаться: `.ToList()` «на всякий случай», а это лишняя копия. Если данные уже в памяти — скажите об этом типом: `IReadOnlyList<T>` или `IReadOnlyCollection<T>`. `IEnumerable<T>` возвращают, когда результат действительно ленивый (см. [[Отложенное и немедленное выполнение]]).

## Большая таблица: устройство и характеристики

| Тип | Устройство под капотом | Порядок перечисления | Потокобезопасность | Аллокации |
|---|---|---|---|---|
| `T[]` | Один объект в куче: заголовок + длина + элементы подряд | Позиционный, стабильный | Read-only — да; запись — нет | 1 объект, размер фиксирован |
| `List<T>` | `T[] _items` + `int _size` | Позиционный | Нет | Массив + рост удвоением, мусор от старых массивов |
| `LinkedList<T>` | Двусвязный список из `LinkedListNode<T>` | Порядок связей | Нет | 1 объект на элемент (~48 байт на x64) |
| `Dictionary<TKey,TValue>` | `int[] _buckets` + `Entry[] _entries`, цепочки через индексы | Не гарантирован (на практике — вставки, пока не было удалений) | Нет | 2 массива + рост |
| `HashSet<T>` | То же устройство, `Entry` без значения | Не гарантирован | Нет | 2 массива |
| `SortedDictionary<TKey,TValue>` | Красно-чёрное дерево (`TreeSet<KeyValuePair<,>>`) | По возрастанию ключа | Нет | 1 узел на элемент |
| `SortedSet<T>` | Красно-чёрное дерево | По возрастанию | Нет | 1 узел на элемент |
| `SortedList<TKey,TValue>` | Два параллельных массива: `TKey[] keys`, `TValue[] values` | По возрастанию ключа | Нет | 2 массива, минимум мусора |
| `Queue<T>` | Кольцевой буфер (`T[]` + head/tail) | FIFO | Нет | 1 массив + рост |
| `Stack<T>` | `T[]` + индекс вершины | LIFO | Нет | 1 массив + рост |
| `PriorityQueue<TElement,TPriority>` | Четверичная (4-арная) двоичная куча в массиве | Только «минимальный первым», внутри равных приоритетов — не стабилен | Нет | 1 массив пар |
| `OrderedDictionary<TKey,TValue>` (.NET 9+) | `int[] buckets` + упорядоченный `Entry[]` | Вставки, гарантированно | Нет | 2 массива |
| `ImmutableArray<T>` | `readonly struct`-обёртка над `T[]` | Позиционный | Да (не меняется) | Полная копия массива на каждое изменение |
| `ImmutableList<T>` | Сбалансированное AVL-дерево | Позиционный | Да | O(log n) новых узлов на изменение, остальное разделяется |
| `ImmutableDictionary<TKey,TValue>` | AVL-дерево хеш-корзин | Не гарантирован | Да | O(log n) узлов на изменение |
| `ImmutableHashSet<T>` | AVL-дерево хеш-корзин | Не гарантирован | Да | O(log n) узлов |
| `FrozenDictionary<TKey,TValue>` | Выбирается при построении: спец. реализации для `int`, для строк по длине/подстроке, идеальное хеширование | Не гарантирован | Да (только чтение) | Дорогое построение, компактный результат |
| `FrozenSet<T>` | То же | Не гарантирован | Да (только чтение) | Дорогое построение |
| `ConcurrentDictionary<TKey,TValue>` | Таблица корзин, чтение lock-free (`Volatile.Read`), запись — мелкогранулярные блокировки на корзину | Не гарантирован | Да | Узел на элемент + массив блокировок |
| `ConcurrentQueue<T>` | Связный список сегментов-массивов, CAS-операции | FIFO (для одного производителя) | Да | Сегменты по 32 и далее до 1024 элементов |
| `ConcurrentStack<T>` | Односвязный список, CAS на вершине | LIFO | Да | 1 узел на элемент |
| `ConcurrentBag<T>` | Локальная очередь на поток + work stealing | Не определён | Да | Узлы + структуры на поток |
| `BlockingCollection<T>` | Обёртка над `IProducerConsumerCollection<T>` (по умолчанию `ConcurrentQueue<T>`) + семафоры для границ и блокировок | Как у обёрнутой | Да | Обёртка + семафоры |
| `ReadOnlyCollection<T>` | Обёртка (`IList<T> list`), **делегирует** вызовы | Как у источника | Нет (источник может меняться!) | 1 маленький объект |
| `Collection<T>` | Обёртка над `IList<T>` с `virtual` методами `InsertItem`/`SetItem`/`RemoveItem` | Позиционный | Нет | Обёртка + внутренний `List<T>` |
| `ObservableCollection<T>` | `Collection<T>` + `INotifyCollectionChanged`/`INotifyPropertyChanged` | Позиционный | Нет (события в потоке-мутаторе) | Как `Collection<T>` + `EventArgs` на изменение |
| `Lookup<TKey,TElement>` | Хеш-таблица `TKey -> Grouping<TKey,TElement>` (список) | Порядок групп и элементов — как в источнике | Да после построения (менять нельзя) | Строится целиком в `ToLookup` |

## Дерево решений: какую коллекцию выбрать

```
Нужен доступ по ключу?
├─ ДА
│  ├─ Нужен порядок по ключу (обход по возрастанию, диапазоны)?
│  │  ├─ ДА → много вставок/удалений?  ── ДА → SortedDictionary<K,V>  (дерево, O(log n) вставка)
│  │  │                                └─ НЕТ, читаем и индексируем → SortedList<K,V>  (2 массива, память минимальна)
│  │  └─ НЕТ
│  │     ├─ Нужен порядок ВСТАВКИ + доступ по позиции? → OrderedDictionary<K,V>  (.NET 9+)
│  │     ├─ Многопоточный доступ?                      → ConcurrentDictionary<K,V>
│  │     ├─ Строится один раз, читается очень много?   → FrozenDictionary<K,V>
│  │     ├─ Нужен снапшот/разделяемое состояние?       → ImmutableDictionary<K,V>
│  │     ├─ Один ключ -> много значений, только чтение → ToLookup() -> ILookup<K,V>
│  │     └─ Иначе                                      → Dictionary<K,V>
│  └─ Значение не нужно, важен только факт наличия?    → HashSet<T> / FrozenSet<T> / SortedSet<T>
└─ НЕТ
   ├─ Дисциплина доступа?
   │  ├─ FIFO                 → Queue<T>  (многопоточно: ConcurrentQueue<T> / Channel)
   │  ├─ LIFO                 → Stack<T>  (многопоточно: ConcurrentStack<T>)
   │  ├─ По приоритету        → PriorityQueue<TElement,TPriority>
   │  └─ Producer/consumer с блокировкой и лимитом → BlockingCollection<T> или Channels
   ├─ Размер известен заранее и не меняется?  → T[] (или ArrayPool<T> для временных буферов)
   ├─ Нужна неизменяемость?
   │  ├─ Чаще читаем, редко копируем целиком → ImmutableArray<T>
   │  └─ Часто «изменяем» с сохранением истории → ImmutableList<T>
   └─ Иначе → List<T>
```

Разбор ветвей прозой.

**Доступ по ключу.** Как только в коде появляется `list.FirstOrDefault(x => x.Id == id)` внутри цикла — вы написали O(n·m) вместо O(n). Это самая частая ошибка в коде мидла. Ответ — `Dictionary<TKey, TValue>` или `ToDictionary`/`ToLookup` перед циклом. Механику см. в [[Dictionary и HashSet изнутри]].

**Сортировка.** «Мне нужен порядок» — вопрос-уточнение: порядок *вставки* или порядок *по ключу*? Порядок вставки до .NET 9 приходилось эмулировать парой `Dictionary<K, int> + List<V>`; теперь есть `OrderedDictionary<K, V>`. Порядок по ключу — дерево (`SortedDictionary`) или отсортированные массивы (`SortedList`). Разница: `SortedList` тратит меньше памяти и быстрее перечисляется и индексируется, но вставка в середину — O(n) со сдвигом. Детали в [[SortedDictionary, SortedSet, SortedList]].

**Потокобезопасность.** `Concurrent*` — не «быстрее», а «корректно без внешнего `lock`». Если запись редкая и вся под одним `lock`, обычный `Dictionary` под `lock` часто быстрее `ConcurrentDictionary`. Если словарь после инициализации только читается — вообще не нужен ни `lock`, ни `Concurrent`: обычный `Dictionary` (или лучше `FrozenDictionary`) безопасен для параллельного чтения, пока никто не пишет. См. [[Конкурентные коллекции]].

**Read-heavy.** Профиль «построили при старте, читаем на каждый запрос» — это `FrozenDictionary`/`FrozenSet`. Построение платит один раз за анализ ключей, зато поиск быстрее `Dictionary` (для строковых ключей выигрыш заметный, потому что реализация может сравнивать по длине или по одному различающему символу).

**Иммутабельность.** `Immutable*` нужны, когда объект живёт долго и его читают несколько потоков, а обновление должно быть атомарным «подменой ссылки». Классика — кеш конфигурации: `Interlocked.Exchange(ref _config, newImmutableDict)`. См. [[Frozen и Immutable коллекции]] и [[Иммутабельность как приём проектирования]].

**LIFO / FIFO / приоритет.** Если из коллекции всегда достают с одного конца, специализированный тип и понятнее, и быстрее (`Queue<T>` не сдвигает массив, в отличие от `list.RemoveAt(0)`). См. [[Очередь, стек, PriorityQueue]].

## Амортизированная сложность и почему O(1) не бесплатен

Записи `O(1)*` в таблице означают: *средняя* стоимость по длинной серии операций постоянна, но отдельные вызовы дороже. У `List<T>.Add` при переполнении происходит выделение нового массива и копирование:

```
Add #1..#4   : ёмкость 4   (первое добавление аллоцирует 4)
Add #5       : новый массив 8,  копируем 4 элемента
Add #9       : новый массив 16, копируем 8
Add #17      : новый массив 32, копируем 16
...
Суммарно скопировано при n вставках: 4 + 8 + ... + n/2 < n  =>  O(1) на вставку в среднем
```

Но «O(1)» — про количество операций, а не про время. Реальная стоимость `Dictionary` складывается из:

1. **Хеширование.** `GetHashCode()` для `string` длиной 200 символов читает все 200 символов (и по умолчанию использует рандомизированный хеш — см. ниже). Это не «одна операция», это десятки наносекунд.
2. **Промахи кеша.** Поиск в `Dictionary` — два случайных обращения: сначала `_buckets[hash % n]`, потом `_entries[i]`. Оба индекса непредсказуемы для префетчера процессора, поэтому каждое обращение с высокой вероятностью — промах L1/L2. Линейный проход по `T[]` таких промахов почти не даёт: одна cache line (64 байта) приносит сразу 16 `int`.
3. **Resize.** Расширение словаря — это полный rehash всех элементов в новый массив. На словаре в миллион записей это десятки миллисекунд и мгновенный скачок аллокаций (массивы уходят в LOH — см. [[Поколения GC, LOH и режимы сборщика]]).
4. **Сравнение ключей.** При коллизии сравниваются ключи через `EqualityComparer<T>.Default`. Для своего класса без `IEquatable<T>` это виртуальный `Equals(object)` с boxing для структур.

Практический вывод: **на маленьких наборах линейный поиск по массиву быстрее словаря.** Граница обычно в районе 8–30 элементов (зависит от типа ключа). Именно поэтому в горячем коде BCL встречаются линейные проверки по массиву вместо `HashSet`. Мерить — через [[Как измерять: BenchmarkDotNet]], а не «на глаз».

> [!info] Рандомизированное хеширование строк
> `string.GetHashCode()` в .NET Core возвращает разное значение для одной и той же строки в разных процессах: seed случайный. Это защита от Hash DoS-атак (когда злоумышленник подбирает ключи с одинаковым хешем и превращает O(1) в O(n)). Следствия: хеш строки нельзя сохранять в БД или файл, и `Dictionary<string, T>` дополнительно умеет переключаться на «недоверенный» рандомизированный компарер, если обнаружит слишком длинные цепочки коллизий.

## Ёмкость, предварительное выделение и низкоуровневый доступ

Все коллекции на массивах имеют две характеристики: `Count` (сколько элементов) и `Capacity` (сколько влезет без нового массива). Если размер известен — задайте его сразу:

```csharp
// Плохо: 1_000_000 добавлений вызовут ~18 расширений и скопируют ~2 млн элементов,
// оставив в куче цепочку мусорных массивов вплоть до 4 МБ
var bad = new List<int>();
for (int i = 0; i < 1_000_000; i++) bad.Add(i);

// Хорошо: один массив нужного размера
var good = new List<int>(capacity: 1_000_000);
for (int i = 0; i < 1_000_000; i++) good.Add(i);

// Если размер выяснился по ходу — EnsureCapacity (List<T>: .NET 6+, Dictionary/HashSet: .NET Core 2.1+)
var dict = new Dictionary<string, int>();
dict.EnsureCapacity(expectedCount);   // сразу выделит таблицу под expectedCount без rehash

// Обратная операция: отдать память назад. Сам по себе Capacity НИКОГДА не уменьшается.
good.TrimExcess();
```

`EnsureCapacity` есть у `List<T>`, `Dictionary<,>`, `HashSet<T>`, `Queue<T>`, `Stack<T>` (у последних двух — с .NET 6).

Для совсем горячего кода в `System.Runtime.InteropServices` живёт `CollectionsMarshal` — «легальный unsafe» для коллекций:

```csharp
using System.Runtime.InteropServices;
using System.Runtime.CompilerServices;

var list = new List<int> { 1, 2, 3, 4, 5 };

// 1. Span поверх внутреннего массива List<T>: ни копии, ни проверок индекса в цикле
Span<int> span = CollectionsMarshal.AsSpan(list);
for (int i = 0; i < span.Length; i++)
    span[i] *= 2;
Console.WriteLine(string.Join(',', list)); // Вывод: 2,4,6,8,10

// 2. Ссылка на значение в словаре без второго поиска.
//    Классика "прочитал -> изменил -> записал" делает ДВА поиска:
var counters = new Dictionary<string, int>();
// counters[key] = counters[key] + 1;  // поиск + поиск

ref int slot = ref CollectionsMarshal.GetValueRefOrNullRef(counters, "a");
if (!Unsafe.IsNullRef(ref slot))
    slot++;               // один поиск, изменение прямо в Entry[]

// 3. Ссылка со вставкой по умолчанию, если ключа нет
ref int c = ref CollectionsMarshal.GetValueRefOrAddDefault(counters, "a", out bool existed);
c++;                      // работает и для нового, и для существующего ключа: один поиск
Console.WriteLine(counters["a"]); // Вывод: 1
```

> [!danger] Правила игры с CollectionsMarshal
> Полученные `Span<T>` и `ref` действительны только до следующей структурной модификации коллекции. `list.Add(...)` может заменить внутренний массив — и ваш `Span` начнёт смотреть на осиротевший массив, а `ref` в словарь — на старый `Entry[]`. Никаких `Add`/`Remove`/`Clear`, пока ссылка живёт. Компилятор это не проверяет.
> Ещё: `CollectionsMarshal.SetCount(list, n)` (.NET 8+) выставляет `Count` напрямую, не инициализируя новые элементы — в них окажется мусор от предыдущего использования массива.

## Collection expressions: `[1, 2, 3]` и `..spread`

C# 12 (2023) ввёл единый синтаксис создания коллекций, C# 13 добавил `params`-коллекции. Раньше каждый тип требовал своего заклинания:

```csharp
// Раньше
int[] a1 = new int[] { 1, 2, 3 };
int[] a2 = { 1, 2, 3 };                            // только при объявлении переменной
List<int> l1 = new List<int> { 1, 2, 3 };
Span<int> s1 = stackalloc int[] { 1, 2, 3 };
ImmutableArray<int> i1 = ImmutableArray.Create(1, 2, 3);
int[] empty = Array.Empty<int>();

// Сейчас — одна форма для всех целевых типов
int[] a = [1, 2, 3];
List<int> l = [1, 2, 3];
Span<int> s = [1, 2, 3];
ReadOnlySpan<char> chars = ['a', 'b'];
ImmutableArray<int> im = [1, 2, 3];
HashSet<string> set = ["a", "b"];
int[] e = [];                                       // пустой массив
IEnumerable<int> seq = [1, 2, 3];

// spread-элемент: разворачивает другую коллекцию
int[] head = [1, 2];
int[] tail = [4, 5];
int[] all = [..head, 3, ..tail];                    // 1,2,3,4,5
List<int> mixed = [0, ..head, ..Enumerable.Range(10, 2)];  // 0,1,2,10,11
```

Что делает компилятор в зависимости от целевого типа:

| Целевой тип | Как реализуется |
|---|---|
| `T[]` | Обычное создание массива. Для `[]` — кешированный пустой массив (эквивалент `Array.Empty<T>()`) |
| `Span<T>` / `ReadOnlySpan<T>` | Может разместить данные на стеке (аналог `stackalloc`) или, для `ReadOnlySpan` из констант, указать прямо на данные в метаданных сборки — нулевые аллокации |
| `List<T>` | Создаёт список и заполняет его, зная итоговый размер (без лишних расширений) |
| Тип с `[CollectionBuilder]` | Вызывает указанный статический фабричный метод. Так работают `ImmutableArray<T>`, `ImmutableList<T>`, `FrozenSet<T>` в API-контрактах |
| Тип с публичным конструктором без параметров и `Add` | `new T()` + серия `Add` (тот же путь, что у collection initializer) |
| `IEnumerable<T>`, `IReadOnlyCollection<T>`, `IReadOnlyList<T>` | Компилятор создаёт внутренний неизменяемый тип-реализацию. Не полагайтесь на то, что это будет именно массив |

> [!tip] Ключевое отличие от collection initializer
> `new List<int> { 1, 2 }` работает только для типов с `Add`. `[1, 2]` — «целезависимая» (target-typed) конструкция: смысл выражения определяет тип, в который его присваивают. Поэтому `var x = [1, 2];` **не компилируется** — цели нет. Нужно `int[] x = [1, 2];`.

## Равенство и компараторы

Два разных механизма сравнения, их постоянно путают:

| | `IEqualityComparer<T>` | `IComparer<T>` |
|---|---|---|
| Методы | `bool Equals(T, T)`, `int GetHashCode(T)` | `int Compare(T, T)` |
| Отвечает на вопрос | «Это одно и то же?» | «Что раньше?» |
| Где нужен | `Dictionary`, `HashSet`, `ConcurrentDictionary`, `FrozenDictionary`, `GroupBy`, `Distinct`, `Union`, `ToLookup` | `SortedDictionary`, `SortedSet`, `SortedList`, `PriorityQueue`, `List.Sort`, `Array.Sort`, `OrderBy` |
| Значение по умолчанию | `EqualityComparer<T>.Default` (использует `IEquatable<T>`, иначе `object.Equals`) | `Comparer<T>.Default` (использует `IComparable<T>`) |

```csharp
// Регистронезависимый словарь: НЕ ToLower() на каждый ключ, а компарер
var headers = new Dictionary<string, string>(StringComparer.OrdinalIgnoreCase)
{
    ["Content-Type"] = "application/json"
};
Console.WriteLine(headers["CONTENT-TYPE"]); // Вывод: application/json

// StringComparer.Ordinal*        — побайтовое сравнение, быстро, детерминированно. Для идентификаторов, ключей, путей.
// StringComparer.CurrentCulture* — правила языка пользователя. Только для сортировки того, что видит человек.
// StringComparer.InvariantCulture* — стабильные культурные правила. Для хранения/протоколов почти не нужно.

// Свой компарер равенства
sealed class OrderByIdComparer : IEqualityComparer<Order>
{
    public bool Equals(Order? x, Order? y) => x?.Id == y?.Id;
    public int GetHashCode(Order o) => o.Id.GetHashCode();
}
var unique = orders.Distinct(new OrderByIdComparer()).ToList();

// Свой компарер порядка — часто короче через Comparer<T>.Create
var byAmountDesc = Comparer<Order>.Create((a, b) => b.Amount.CompareTo(a.Amount));
var queue = new PriorityQueue<Order, Order>(byAmountDesc);
```

> [!danger] Контракт GetHashCode
> Если `Equals(x, y) == true`, то `GetHashCode(x)` обязан равняться `GetHashCode(y)`. Нарушение — и элемент «теряется» в словаре: он там есть, но `ContainsKey` вернёт `false`, потому что поиск идёт не в ту корзину. Второе правило: **ключ не должен мутировать, пока лежит в словаре.** Изменили поле, участвующее в хеше, — элемент стал недостижим. Подробнее в [[Object: Equals, GetHashCode, ToString]] и [[Сравнение объектов: IEquatable, IComparable, компараторы]].

## Read-only обёртка против иммутабельной коллекции

Это разные гарантии, и путаница здесь регулярно приводит к багам.

```csharp
var source = new List<int> { 1, 2, 3 };

// 1. Обёртка: НОВЫЙ ФАСАД поверх ТОГО ЖЕ списка
IReadOnlyList<int> wrapper = new ReadOnlyCollection<int>(source);
Console.WriteLine(wrapper.Count);   // Вывод: 3
source.Add(4);                      // источник меняем — обёртка видит изменение!
Console.WriteLine(wrapper.Count);   // Вывод: 4

// 2. Иммутабельная коллекция: КОПИЯ, отвязанная от источника
ImmutableArray<int> snapshot = source.ToImmutableArray();
source.Add(5);
Console.WriteLine(snapshot.Length); // Вывод: 4 — снимок не изменился
```

| | `IReadOnlyList<T>` / `ReadOnlyCollection<T>` | `ImmutableArray<T>` / `ImmutableList<T>` |
|---|---|---|
| Что обещает | «Через эту ссылку менять нельзя» | «Эти данные не изменятся никогда» |
| Защищает от изменения источника | Нет | Да |
| Стоимость создания | O(1), один маленький объект | O(n), копия |
| Потокобезопасность чтения при живом источнике | Нет — `foreach` упадёт с `InvalidOperationException`, если источник изменили | Да |
| Типичное применение | Публичное свойство класса, который сам владеет данными | Разделяемый снимок, кеш, аргумент между потоками |

Отдельно: приведение типа обёртку не создаёт. `IReadOnlyList<int> x = myList;` — это тот же объект, и получатель может сделать `((List<int>)x).Clear()`. Реальная защита — либо `ReadOnlyCollection<T>` (`myList.AsReadOnly()`), либо копия, либо `Immutable*`.

> [!warning] Подводные камни
>
> **1. Негенерик-коллекции и boxing.** `ArrayList`, `Hashtable`, `Queue`, `Stack` из `System.Collections` хранят `object`. Каждый `int` в них — отдельный объект в куче (24 байта на x64 против 4 в `int[]`), плюс распаковка с проверкой типа на каждом чтении. `Hashtable` с ключами-структурами боксит ключ и при вставке, и **при каждом поиске**, потому что `GetHashCode`/`Equals` вызываются через `object`. Отсюда же отсутствие типобезопасности: ошибка типа обнаруживается в рантайме как `InvalidCastException`. Причина, по которой их нельзя было «просто исправить», — обратная совместимость: `ArrayList.Add(object)` уже был в публичном контракте, а дженериков в CLR 1.0 не существовало вовсе. `#устарело`
>
> **2. `List<T>` как поле, отданное наружу.** `public List<Item> Items { get; } = new();` выглядит безобидно, но это дырка в инкапсуляции: любой код может сделать `obj.Items.Clear()` или добавить элемент, минуя валидацию класса. Хуже, если внутри класса есть инварианты («сумма позиций равна `Total`») — они молча ломаются. Второй симптом: вы не можете поменять реализацию с `List<T>` на что-то другое, тип уже в публичном API. Лечение: приватное поле + `IReadOnlyList<T>` в свойстве + методы `Add`/`Remove` с проверками. Возврат `_items.AsReadOnly()` дороже (аллокация обёртки), зато исключает даже приведение типа обратно к `List<T>`.
>
> **3. Порядок перечисления `Dictionary` не определён.** Практически он совпадает с порядком вставки, **пока не было удалений**: `Entry[]` заполняется подряд, а `foreach` идёт по нему. Но `Remove` оставляет «дырку» и заносит её в список свободных слотов; следующая вставка переиспользует эту дырку, и новый элемент оказывается в перечислении в середине. Плюс `Resize` может перестроить порядок. Никогда не полагайтесь на порядок: если он нужен — `OrderedDictionary<K, V>` (.NET 9+), `SortedDictionary` (по ключу) или явный `OrderBy`. Тесты, зависящие от порядка словаря, — классический flaky-тест, который «внезапно» падает после обновления рантайма.
>
> **4. Ковариантность `IEnumerable<out T>` и её ловушки.** `IEnumerable<string>` присваивается в `IEnumerable<object>` — это безопасно, потому что читать `object` из последовательности `string` можно. Но: (а) ковариантность работает только для ссылочных типов — `IEnumerable<int>` в `IEnumerable<object>` не приводится (нужен boxing каждого элемента, а вариантность в CLR — приведение ссылок без изменения данных); (б) `IList<T>`, `ICollection<T>`, `IDictionary<,>` **инвариантны** — там есть `Add(T)`, и ковариантность позволила бы положить `object` в `List<string>`; (в) массивы ковариантны исторически и **небезопасно**, что вылезает как `ArrayTypeMismatchException` в рантайме (см. [[List, массивы, LinkedList]]). Практическая ловушка: `IEnumerable<object> x = listOfStrings; x is List<string>` вернёт `true`, и наивный `(List<object>)x` упадёт. Подробнее — [[Дженерики: ограничения и вариантность]].
>
> **5. `Count()` против `Count`.** `Count` — свойство коллекции, O(1). `Count()` — LINQ-метод. Он умеет быстрый путь: если объект реализует `ICollection<T>`, `ICollection` или (с .NET 6+) поддерживает `TryGetNonEnumeratedCount`, то это тоже O(1). Но если перед ним стоит `Where`, `Select` или свой `yield`-итератор — `Count()` **перечислит всю последовательность**, а для `IQueryable` уйдёт запросом в БД. Отсюда два реальных бага: `if (query.Count() > 0)` вместо `if (query.Any())` тянет из базы всё вместо `EXISTS`; и `for (int i = 0; i < seq.Count(); i++)` перечисляет коллекцию на каждой итерации, превращая цикл в O(n²). Для «есть ли хоть один» всегда `Any()`.

> [!example] Как делают в бою
> **Справочники — `FrozenDictionary` в singleton.** Список стран, коды валют, маппинг «код ошибки → сообщение» читаются на каждый запрос и никогда не меняются. Строим при старте один раз и регистрируем как singleton:
> ```csharp
> builder.Services.AddSingleton<IReadOnlyDictionary<string, Currency>>(_ =>
>     LoadCurrencies().ToFrozenDictionary(c => c.Code, StringComparer.OrdinalIgnoreCase));
> ```
> **Убийство N+1 в памяти.** Классика: два списка, для каждого элемента первого ищем во втором. `foreach (var o in orders) { var u = users.First(u => u.Id == o.UserId); }` — O(n·m). Заменяется на один словарь до цикла: `var byId = users.ToDictionary(u => u.Id);`. На 10 000 × 10 000 это разница между 40 секундами и 5 миллисекундами.
> **Публичные контракты — только read-only типы.** В DTO и доменных сущностях наружу отдаём `IReadOnlyList<T>`/`IReadOnlyDictionary<,>`. В параметрах методов сервисного слоя принимаем `IEnumerable<T>`, если внутри один проход, и `IReadOnlyCollection<T>`, если нужен `Count` или два прохода. Это документирует намерение лучше любого комментария.
> **Никогда не `IEnumerable<T>` из репозитория.** `IEnumerable<Order> GetOrders()` для EF Core означает, что запрос может выполниться у вызывающего, вне `using` для `DbContext`, и упасть с `ObjectDisposedException`. Возвращаем `List<T>`/`IReadOnlyList<T>` — материализованный результат. См. [[IEnumerable vs IQueryable]].
> **Ключи словарей — `StringComparer.Ordinal` по умолчанию.** Если ключ технический (id, код, имя заголовка), явно указывайте `StringComparer.Ordinal` или `OrdinalIgnoreCase`. Дефолт для `string` уже ordinal, но явность спасает от чужого рефакторинга и от случайного `CurrentCulture`, поведение которого зависит от локали сервера.
> **Анализаторы вместо ревью.** `CA1002` (не отдавать `List<T>` наружу), `CA1826` (не использовать LINQ там, где есть свойство), `CA1827`/`CA1829` (`Any()` вместо `Count() > 0`, `Length`/`Count` вместо `Count()`) включаются через `<AnalysisLevel>latest-recommended</AnalysisLevel>` и ловят эти ошибки в CI.

## Вопросы с собеседований

> [!question]- Чем `IEnumerable<T>` отличается от `ICollection<T>` и `IList<T>`? Что возвращать из метода?
> `IEnumerable<T>` даёт только однонаправленный проход и не гарантирует ни размера, ни повторяемости результата — за ним может стоять ленивый итератор или запрос к БД. `ICollection<T>` добавляет `Count`, `Add`, `Remove`, `Contains`, то есть материализованный изменяемый набор без понятия позиции. `IList<T>` добавляет позиционный доступ: индексатор, `Insert`, `RemoveAt`, `IndexOf`. В параметрах метода берут самый слабый достаточный тип (обычно `IEnumerable<T>`), чтобы принимать и массив, и результат LINQ. Из метода возвращают самый информативный, но не дающий лишних прав: `IReadOnlyList<T>` для материализованного списка, `IEnumerable<T>` — только если результат действительно ленивый.

> [!question]- Почему `ArrayList` и `Hashtable` считаются устаревшими?
> Они появились в .NET Framework 1.0, когда в CLR не было дженериков, и хранят элементы как `object`. Отсюда две системные проблемы. Первая — boxing: каждое значимое значение упаковывается в отдельный объект в куче, `int` вырастает с 4 байт до 24, а `Hashtable` боксит ключ-структуру даже при поиске, потому что `GetHashCode`/`Equals` вызываются через `object`. Вторая — отсутствие типобезопасности: компилятор не мешает положить строку в «коллекцию чисел», ошибка проявляется как `InvalidCastException` в рантайме. Исправить их на месте было нельзя из-за обратной совместимости публичного API, поэтому в .NET 2.0 добавили параллельную ветку `System.Collections.Generic`. В новом коде их не используют; встречаются только в легаси и старом COM-интеропе.

> [!question]- Когда `Dictionary` медленнее линейного поиска по массиву?
> На малых объёмах — обычно до нескольких десятков элементов. «O(1)» описывает число операций, но не их стоимость: поиск в словаре — это вычисление хеша (для длинной строки это проход по всей строке), затем два случайных обращения в память (`_buckets`, потом `_entries`), каждое из которых с большой вероятностью промах кеша, затем сравнение ключа. Линейный проход по массиву префетчер процессора предсказывает идеально: одна cache line 64 байта приносит сразу 16 значений `int`. Поэтому в горячем коде BCL и высокопроизводительных библиотеках для 4–16 элементов используют массив с линейной проверкой. Конкретную границу нужно измерять BenchmarkDotNet под свой тип ключа.

> [!question]- В чём разница между `ReadOnlyCollection<T>` и `ImmutableArray<T>`?
> `ReadOnlyCollection<T>` — обёртка: она держит ссылку на исходный `IList<T>` и просто не предоставляет методов изменения. Если источник изменят, обёртка это увидит, а идущий по ней `foreach` упадёт с `InvalidOperationException`. Создание — O(1). `ImmutableArray<T>` — независимая копия данных, которая не может измениться в принципе; создание O(n), зато коллекция безопасна для параллельного чтения и годится как снимок состояния. Правило: обёртку отдают из класса, который сам владеет данными и контролирует их изменение; иммутабельную коллекцию — когда данные уходят в другой поток или должны остаться неизменными во времени.

> [!question]- Что делает `[1, 2, 3]` для разных целевых типов?
> Collection expression из C# 12 — target-typed конструкция: компилятор смотрит на тип, в который её присваивают, и выбирает реализацию. Для `T[]` создаётся массив, для `[]` подставляется кешированный пустой массив. Для `Span<T>`/`ReadOnlySpan<T>` данные могут разместиться на стеке или, для констант, вообще указывать на блок в метаданных сборки — без аллокаций. Для `List<T>` создаётся список сразу нужной ёмкости. Для типов с атрибутом `[CollectionBuilder]` (`ImmutableArray<T>`, `FrozenSet<T>`) вызывается указанная фабрика. Для интерфейсов `IEnumerable<T>`/`IReadOnlyList<T>` компилятор синтезирует внутренний неизменяемый тип, и рассчитывать на то, что это массив, нельзя. Поскольку тип берётся из цели, `var x = [1, 2];` не компилируется.

> [!question]- Гарантирует ли `Dictionary<K,V>` порядок перечисления?
> Нет, документация прямо говорит, что порядок не определён. На практике при вставках без удалений он совпадает с порядком добавления, потому что записи кладутся подряд в `Entry[]`, а `foreach` идёт по этому массиву. Но `Remove` освобождает слот и добавляет его в список свободных, следующая вставка переиспользует дырку в середине — и порядок ломается; `Resize` тоже может его изменить. Опираться на этот порядок нельзя: тесты становятся хрупкими и падают при смене версии рантайма. Если порядок вставки нужен — с .NET 9 есть `OrderedDictionary<TKey, TValue>`, если порядок по ключу — `SortedDictionary`/`SortedList`, иначе явный `OrderBy`.

> [!question]- Чем `FrozenDictionary` отличается от `ImmutableDictionary` и обычного `Dictionary`?
> Все три неизменяемы или почти неизменяемы по-разному. `ImmutableDictionary` поддерживает «изменение» через возврат новой коллекции, устроен как AVL-дерево хеш-корзин, и потому и чтение, и запись — O(log n) с худшей константой, чем у `Dictionary`. `FrozenDictionary` (.NET 8, пространство `System.Collections.Frozen`, сборка System.Collections.Immutable.dll) изменять нельзя вообще: он строится один раз через `ToFrozenDictionary` или `FrozenDictionary.Create`, платит за это дорогим анализом ключей и выбирает специализированную реализацию под конкретный набор — например, для строк сравнивать по длине или по одному различающему символу. В обмен чтение быстрее, чем у `Dictionary`. Правильный сценарий: справочник, построенный при старте приложения и читаемый на каждый запрос.

> [!question]- Что не так с `if (collection.Count() > 0)`?
> `Count()` — метод LINQ, а не свойство. Он умеет быстрый путь через `ICollection<T>` и `TryGetNonEnumeratedCount`, но если перед ним `Where`, `Select` или `yield`-итератор, он перечислит всю последовательность целиком, только чтобы узнать, что элементов больше нуля. Для `IQueryable` это превращается в `SELECT COUNT(*)` (или, при неудачном коде, в материализацию всей таблицы) вместо дешёвого `EXISTS`. Правильно писать `Any()` — он останавливается на первом элементе. Отдельно ловушка `for (int i = 0; i < seq.Count(); i++)`: условие вычисляется на каждой итерации, и цикл становится O(n²). Анализаторы `CA1827`/`CA1829` ловят это автоматически.

## Задачи

### Задача 1. Выбрать коллекцию под требование

Для каждого требования назовите тип из BCL и обоснуйте одной фразой:
а) кеш «код валюты → курс», заполняется при старте, читается на каждый HTTP-запрос из многих потоков, не меняется;
б) очередь заданий, куда пишут 4 потока-производителя, а читает один потребитель, с ограничением на 1000 элементов;
в) набор посещённых URL в краулере, нужен только быстрый ответ «был ли уже»;
г) история операций, где нужно быстро отдать неизменяемый снимок другому потоку и при этом дописывать новые элементы;
д) LRU-подобная структура, где нужно и находить по ключу, и знать позицию элемента в порядке вставки.

> [!success]- Решение
> **а) `FrozenDictionary<string, decimal>`** с `StringComparer.OrdinalIgnoreCase`. Профиль «строим один раз, читаем очень много» — ровно его сценарий; неизменяемость снимает вопрос о блокировках.
> ```csharp
> private static readonly FrozenDictionary<string, decimal> Rates =
>     LoadRates().ToFrozenDictionary(x => x.Code, x => x.Rate, StringComparer.OrdinalIgnoreCase);
> ```
> **б) `BlockingCollection<T>`** с `boundedCapacity: 1000` (или `System.Threading.Channels.Channel<T>` — современнее и асинхронно). `BlockingCollection` даёт и блокировку при переполнении, и `CompleteAdding` для корректного завершения. Обычный `ConcurrentQueue` границы не поддерживает.
> ```csharp
> var queue = new BlockingCollection<Job>(new ConcurrentQueue<Job>(), boundedCapacity: 1000);
> ```
> **в) `HashSet<string>`** (или `ConcurrentDictionary<string, byte>` как множество, если краулер многопоточный — конкурентного `HashSet` в BCL нет). Значение не нужно, нужен O(1) `Contains`.
> **г) `ImmutableList<T>`** в поле, обновляемое через `Interlocked.CompareExchange`, — или `ImmutableArray<T>`, если дописываем редко, а читаем часто. `ImmutableList` даёт O(log n) на добавление с разделением структуры; `ImmutableArray` копирует весь массив, зато читается со скоростью обычного массива.
> **д) `OrderedDictionary<TKey, TValue>`** (.NET 9+). Он единственный в BCL сочетает O(1) поиск по ключу с гарантированным порядком вставки и доступом по индексу через `GetAt`/`SetAt`. До .NET 9 это собирали руками из `Dictionary<K, LinkedListNode<V>>` + `LinkedList<V>`.

### Задача 2. Убрать O(n·m)

Дан метод, который для каждого заказа находит пользователя и город пользователя. На 20 000 заказов, 20 000 пользователях и 500 городах он работает минуты. Переписать в линейное время.

```csharp
static List<string> Describe(List<Order> orders, List<User> users, List<City> cities)
{
    var result = new List<string>();
    foreach (var o in orders)
    {
        var user = users.First(u => u.Id == o.UserId);
        var city = cities.First(c => c.Id == user.CityId);
        result.Add($"{o.Id}: {user.Name}, {city.Name}");
    }
    return result;
}
```

> [!success]- Решение
> ```csharp
> static List<string> Describe(
>     IReadOnlyList<Order> orders,
>     IReadOnlyCollection<User> users,
>     IReadOnlyCollection<City> cities)
> {
>     // Индексы строим один раз: O(n + m)
>     var usersById  = users.ToDictionary(u => u.Id);
>     var citiesById = cities.ToDictionary(c => c.Id);
>
>     // Ёмкость известна заранее — ни одного расширения списка
>     var result = new List<string>(orders.Count);
>     foreach (var o in orders)
>     {
>         if (!usersById.TryGetValue(o.UserId, out var user)) continue;
>         if (!citiesById.TryGetValue(user.CityId, out var city)) continue;
>         result.Add($"{o.Id}: {user.Name}, {city.Name}");
>     }
>     return result;
> }
> ```
> Было `20 000 × (20 000 + 500)` сравнений — около 410 миллионов. Стало `20 000 + 500` вставок в словари плюс `20 000 × 2` поиска — примерно 60 тысяч операций. Дополнительно: `First` бросал исключение при отсутствии записи, `TryGetValue` делает поиск и проверку одним обращением (в отличие от пары `ContainsKey` + индексатор, которая ищет дважды). Параметры ослаблены до read-only интерфейсов — метод ничего не меняет и это видно по подписи.

### Задача 3. Инкапсулировать коллекцию

Класс `Invoice` держит позиции и поле `Total`, которое должно всегда равняться сумме позиций. Найдите проблему и исправьте.

```csharp
public class Invoice
{
    public List<InvoiceLine> Lines { get; } = new();
    public decimal Total { get; private set; }
    public void AddLine(InvoiceLine line)
    {
        Lines.Add(line);
        Total += line.Amount;
    }
}
```

> [!success]- Решение
> ```csharp
> public sealed class Invoice
> {
>     private readonly List<InvoiceLine> _lines = [];
>
>     // Наружу — только чтение. Count есть, индексатор есть, Add нет.
>     public IReadOnlyList<InvoiceLine> Lines => _lines;
>
>     public decimal Total { get; private set; }
>
>     public void AddLine(InvoiceLine line)
>     {
>         ArgumentNullException.ThrowIfNull(line);
>         _lines.Add(line);
>         Total += line.Amount;
>     }
>
>     public bool RemoveLine(InvoiceLine line)
>     {
>         if (!_lines.Remove(line)) return false;
>         Total -= line.Amount;
>         return true;
>     }
> }
> ```
> Проблема исходного кода: `Lines` — публичный `List<T>`, поэтому любой может сделать `invoice.Lines.Add(x)` или `invoice.Lines.Clear()`, и `Total` разойдётся с содержимым. `get`-only свойство защищает только *ссылку*, но не сам список — это частая ошибка. Замена типа свойства на `IReadOnlyList<T>` закрывает 99 % случаев (приведение обратно к `List<T>` возможно, но это уже явное вредительство; если нужна жёсткая гарантия — `_lines.AsReadOnly()`). Заодно исчезает зависимость публичного API от `List<T>`: реализацию можно менять свободно. Это же требует анализатор `CA1002`.

### Задача 4. Свой компарер для словаря

Нужен словарь путей к файлам, в котором `"/api/Users"` и `"/API/users/"` считаются одним ключом (регистр не важен, завершающий слэш не важен). Реализуйте компарер.

> [!success]- Решение
> ```csharp
> sealed class RoutePathComparer : IEqualityComparer<string>
> {
>     public static readonly RoutePathComparer Instance = new();
>
>     private static ReadOnlySpan<char> Normalize(string s) =>
>         s.AsSpan().TrimEnd('/');
>
>     public bool Equals(string? x, string? y)
>     {
>         if (ReferenceEquals(x, y)) return true;
>         if (x is null || y is null) return false;
>         return Normalize(x).Equals(Normalize(y), StringComparison.OrdinalIgnoreCase);
>     }
>
>     public int GetHashCode(string s) =>
>         string.GetHashCode(Normalize(s), StringComparison.OrdinalIgnoreCase);
> }
>
> var routes = new Dictionary<string, Handler>(RoutePathComparer.Instance);
> routes["/api/Users"] = handler;
> Console.WriteLine(routes.ContainsKey("/API/users/")); // Вывод: True
> ```
> Ключевой момент — согласованность: `GetHashCode` считается по той же нормализованной форме и с тем же `StringComparison`, что и `Equals`. Если бы `Equals` игнорировал регистр, а `GetHashCode` — нет, элементы попадали бы в разные корзины и словарь «терял» бы записи. Нормализация идёт через `ReadOnlySpan<char>` и `string.GetHashCode(ReadOnlySpan<char>, StringComparison)`, поэтому промежуточных строк не создаётся — важно, если компарер вызывается на горячем пути. Про `Span` см. [[Span, ReadOnlySpan и Memory]].

## Итог

- В `System.Collections.Generic` живёт 90 % рабочих коллекций; негенерик `System.Collections` — легаси из-за boxing и отсутствия типобезопасности, `System.Collections.Specialized` — тоже. `#устарело`
- Выбор коллекции определяется профилем обращений: ключ или индекс, порядок или его отсутствие, чтение или запись, один поток или много. Проходите по дереву решений, а не по привычке «везде `List<T>`».
- В параметрах метода принимайте самый общий тип (`IEnumerable<T>`, `IReadOnlyCollection<T>`), а возвращайте самый информативный без лишних прав (`IReadOnlyList<T>`). Публичный `List<T>` — дырка в инкапсуляции.
- «O(1)» не значит «бесплатно»: хеширование, промахи кеша и resize делают словарь медленнее линейного массива на десятках элементов. Задавайте `capacity`/`EnsureCapacity`, когда размер известен.
- Read-only обёртка не защищает от изменения источника, иммутабельная коллекция — защищает. Это разные гарантии, не взаимозаменяемые.
- Порядок перечисления `Dictionary`/`HashSet` не определён. Нужен порядок вставки — `OrderedDictionary<TKey, TValue>` (.NET 9+); нужен порядок по ключу — `SortedDictionary`/`SortedList`.
- Collection expressions `[...]` и spread `[..a, ..b]` — единый target-typed синтаксис для всех коллекций, но `var x = [1];` не компилируется: цели нет.
