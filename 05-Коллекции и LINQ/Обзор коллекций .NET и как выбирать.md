# Обзор коллекций .NET и как выбирать

> [!abstract] Коротко
> BCL даёт около тридцати готовых коллекций на семь пространств имён, но все они решают одну задачу — «хранить много объектов» — с разной ценой операций, разными гарантиями порядка и разной потокобезопасностью. Выбор коллекции — это выбор структуры данных под профиль обращений: по ключу или по индексу, нужен ли порядок (вставки или сортировка), меняется коллекция часто или один раз заполняется и читается. Ошибка выбора не ломает код — она делает его на порядки медленнее, поэтому это главный вопрос ревью в разделе коллекций.

## Зачем это знать

До дженериков (.NET Framework 1.0–1.1) коллекции хранили `object`: `ArrayList`, `Hashtable`. Каждое значимое значение боксилось в кучу, типобезопасности не было, ошибка вылезала в рантайме как `InvalidCastException`. C# 2.0 (2005) принёс `List<T>`/`Dictionary<TKey,TValue>` — это закрыло вопрос типов, но не вопрос выбора структуры: `Dictionary` не даёт порядка, `List` не даёт быстрого поиска по ключу, `SortedList` дёшев по памяти, но дорог на случайную вставку. Самая частая ошибка ревью — `list.FirstOrDefault(x => x.Id == id)` внутри цикла: O(n·m) там, где словарь даёт O(n). Вторая по частоте — не тот словарь для задачи «нужен порядок»: `Dictionary` не гарантирует порядок вообще, а `OrderedDictionary`/`SortedDictionary`/`SortedSet` дают разные виды порядка за разную цену.

## Модель

Все коллекции BCL раскладываются по **семантике**, а не по имени типа:

| Семантика | Вопрос, на который отвечает | Представители |
|---|---|---|
| **Список (последовательность)** | «Что на позиции i?» | `T[]`, `List<T>`, `LinkedList<T>`, `ImmutableArray<T>`, `ImmutableList<T>` |
| **Множество** | «Есть ли этот элемент?» | `HashSet<T>`, `SortedSet<T>`, `FrozenSet<T>`, `ImmutableHashSet<T>` |
| **Словарь** | «Что лежит под этим ключом?» | `Dictionary<K,V>`, `SortedDictionary<K,V>`, `SortedList<K,V>`, `OrderedDictionary<K,V>`, `FrozenDictionary<K,V>`, `ConcurrentDictionary<K,V>` |
| **Очередь/стек** | «Что забрать следующим?» | `Queue<T>`, `Stack<T>`, `PriorityQueue<TElement,TPriority>`, `ConcurrentQueue<T>`, `BlockingCollection<T>` |
| **Отсортированные** | «Дай по порядку / дай диапазон» | `SortedDictionary<K,V>`, `SortedSet<T>`, `SortedList<K,V>` — три реализации одной идеи с разной механикой |

Поверх этой сетки лежат две независимые оси: **потокобезопасность** (`Concurrent*` — lock-free или мелкогранулярные блокировки) и **неизменяемость** (`Immutable*` — структурное разделение при «изменении», `Frozen*` — построена один раз для максимально быстрого чтения).

Практическое следствие оси интерфейсов: в параметр метода стоит принимать самый общий тип, которого достаточно (`IEnumerable<T>` для одного прохода, `IReadOnlyCollection<T>`/`IReadOnlyList<T>`, если внутри нужен `Count` или индекс), а из метода возвращать самый информативный тип без лишних прав (`IReadOnlyList<T>`, а не голый `List<T>`). Публичное свойство `List<T> Items { get; }` — дырка в инкапсуляции: любой вызывающий код может сделать `obj.Items.Clear()` в обход инвариантов класса.

`System.Collections` (без `.Generic`) и `System.Collections.Specialized` — легаси-пространства с боксингом `object`-элементов (`ArrayList`, `Hashtable`, негенерик `SortedList`, негенерик `OrderedDictionary`). Они остались только ради обратной совместимости и встречаются в старом коде и COM-интеропе; в новом коде не используются. `#устарело`

Внутри «отсортированных» — два разных устройства, и путать их нельзя:

- **`SortedDictionary`/`SortedSet` — красно-чёрное дерево.** Пять инвариантов (корень чёрный, нет двух красных подряд, одинаковая чёрная высота на всех путях) держат высоту в пределах `2·log2(n+1)`, поэтому поиск/вставка/удаление — O(log n) **в худшем случае**, а не в среднем. Без балансировки обычное дерево поиска деградирует до списка на данных, отсортированных при вставке (`ORDER BY id` из БД — типичный такой случай).
- **`SortedList` — два параллельных массива** (`keys`, `values`), поиск бинарный по плотному массиву. Отсюда лучшая локальность кеша и в разы меньше памяти (8 байт на элемент против ~40 у узла дерева), но вставка в середину — `Array.Copy` хвоста, O(n). Вставка в конец (данные уже отсортированы) — амортизированное O(1), как у `List<T>.Add`.

Порядок — не одна вещь: `OrderedDictionary<K,V>` (.NET 9+) хранит порядок **вставки** при O(1) поиске (хеш-таблица + массив записей), `SortedDictionary`/`SortedSet`/`SortedList` — порядок **по значению ключа** через `IComparer<T>`, ценой O(log n) на операцию.

> [!info] Куда идёт индустрия
> В .NET 10 у `OrderedDictionary<K,V>` появились перегрузки `TryAdd(key, value, out int index)` и `TryGetValue(key, out value, out int index)` — обновление «прочитал → изменил» одним поиском вместо двух. В `net8.0` их нет, там `IndexOf` отдельным вызовом.

Разница механики видна на одинаковой задаче — «отдать ставку тарифа для суммы» (floor-запрос по границам):

```csharp
// SortedList: индексный доступ есть, диапазон эмулируется бинарным поиском вручную
var byArray = new SortedList<decimal, decimal> { [0m] = 0.02m, [10_000m] = 0.015m };
Console.WriteLine(byArray.GetValueAtIndex(0));      // 0.02 — доступ по позиции в порядке ключей

// SortedSet: диапазон — встроенная операция над деревом, но без индекса и без значений
var byTree = new SortedSet<decimal> { 0m, 10_000m, 100_000m };
var upTo50k = byTree.GetViewBetween(0m, 50_000m);   // живое представление, не копия
Console.WriteLine(upTo50k.Max);                     // 10_000
```

`SortedList` даёт индекс, но не диапазонные операции «из коробки»; `SortedSet`/`SortedDictionary` дают диапазон (`GetViewBetween`) и обход по возрастанию, но не индекс. Выбор между ними — это выбор, какая из двух возможностей нужна чаще.

## Решения

| Задача | Структура | Поиск | Вставка | Удаление | Порядок |
|---|---|---|---|---|---|
| Позиционный доступ, размер меняется | `List<T>` | O(n) | O(1)* в конец | O(n) | вставки |
| Доступ по ключу, порядок не важен | `Dictionary<K,V>` | O(1) | O(1)* | O(1) | не определён |
| Только факт наличия | `HashSet<T>` | O(1) | O(1)* | O(1) | не определён |
| Порядок вставки + быстрый поиск по ключу | `OrderedDictionary<K,V>` (.NET 9+) | O(1) | O(1)* в конец, O(n) в середину | O(n) | вставки |
| Порядок по ключу, частые правки в случайных позициях | `SortedDictionary<K,V>` | O(log n) | O(log n) | O(log n) | по ключу |
| Порядок по ключу, множество без значений, нужны диапазоны/Min/Max | `SortedSet<T>` | O(log n) | O(log n) | O(log n) | по ключу |
| Порядок по ключу, заполнили один раз, дальше читаем/индексируем | `SortedList<K,V>` | O(log n) | **O(n)** | **O(n)** | по ключу |
| Только минимум/максимум по приоритету | `PriorityQueue<TElement,TPriority>` | Peek O(1) | O(log n) | O(log n) Dequeue | по приоритету |
| FIFO / LIFO | `Queue<T>` / `Stack<T>` | O(n) | O(1)* | O(1) | FIFO/LIFO |
| Многопоточная запись без внешнего `lock` | `ConcurrentDictionary<K,V>` и `Concurrent*` | O(1) | O(1)* | O(1) | не определён |
| Построена один раз, читается очень много | `FrozenDictionary<K,V>` / `FrozenSet<T>` | O(1), лучшая константа | — | — | не определён |
| Разделяемый снимок между потоками | `ImmutableList<T>` / `ImmutableDictionary<K,V>` | O(log n) | O(log n) | O(log n) | как у источника |

\* амортизированная сложность: отдельная вставка может стоить O(n) из-за расширения внутреннего массива.

Разбор ключевых развилок:

- **«Нужен порядок» — это не один вопрос.** Уточняй: порядок *вставки* (`OrderedDictionary`) или порядок *по значению ключа* (`SortedDictionary`/`SortedSet`/`SortedList`). До .NET 9 порядок вставки эмулировали парой `Dictionary<K,int> + List<V>` вручную.
- **Внутри отсортированных: часто меняю → дерево, редко меняю → массивы.** `SortedDictionary`/`SortedSet` не деградируют при случайных вставках/удалениях, `SortedList` деградирует до O(n²) на заполнении в случайном порядке, но экономит память в разы и быстрее на чтении.
- **Сортировка только для вывода — не повод держать отсортированную структуру.** Если порядок нужен один раз в конце (отчёт, ответ API), дешевле `Dictionary` + `OrderBy` при выводе: одна сортировка O(n log n) вместо O(log n) на каждой из миллиона вставок.
- **Диапазонный запрос по данным в БД делает СУБД, не .NET.** Тащить таблицу в память ради `SortedSet.GetViewBetween` оправдано только для данных, которые и так живут в памяти процесса (кеш, тайм-серия последних N минут).

## Проверка на ревью

- В цикле нет `list.FirstOrDefault/First(x => x.Id == id)` там, где подошёл бы словарь.
- Если в коде появился `SortedList`/`SortedDictionary`/`SortedSet` — обоснован ли выбор именно порядка *по ключу*, а не порядка вставки (`OrderedDictionary`) или сортировки только на выводе (`Dictionary` + `OrderBy`).
- `SortedList` не заполняется в цикле случайными ключами без предварительной сортировки источника (`OrderBy` перед `Add`).
- Компаратор для `SortedSet`/`SortedDictionary` доведён до уникального поля (id), а не только до бизнес-поля, по которому возможны совпадения.
- Из репозитория/сервиса наружу не течёт голый `List<T>` или `Dictionary<K,V>` — только `IReadOnlyList<T>`/`IReadOnlyDictionary<K,V>`.
- `Count()` не вызывается вместо `Any()`, и не вызывается повторно в условии цикла.
- В параметрах метода нет требования конкретного типа коллекции (`List<T>`) там, где хватило бы `IEnumerable<T>`/`IReadOnlyCollection<T>`.
- Read-only коллекция, построенная один раз при старте (справочник, конфиг), не пересобирается на каждый запрос и не защищена избыточным `lock` там, где подошёл бы `FrozenDictionary`.

> [!example] В ServiceShop
> Справочники (курсы валют, коды ошибок, тарифные ставки) загружаются при старте и дальше только читаются — берут `FrozenDictionary<K,V>` или, если нужен floor-запрос по границам сумм, `SortedList<decimal, Tariff>`: заполняют уже отсортированным источником, кладут в singleton, поиск ставки — бинарным поиском без аллокаций на запрос. Consistent hashing для шардирования корзины использует `SortedDictionary<uint, Node>` — узлы добавляются и удаляются при масштабировании, здесь оправдано дерево, а не массивы. В прикладном коде модулей отсортированные коллекции нужны редко: обычно хватает `Dictionary` + `OrderBy` при формировании ответа, а диапазонные выборки (история заказов за период) делает MySQL по индексу.

> [!warning] Где ошибаются
>
> **Агент часто** генерирует `List<T>` и линейный `Where`/`FirstOrDefault` там, где по смыслу задачи нужен словарь — код компилируется и проходит тесты на маленьких наборах, а на проде деградирует до O(n·m).
>
> **Агент часто** предлагает `SortedList` для сценария с частыми случайными вставками — оно короче по имени и «звучит правильно», но даёт O(n²) на заполнении. Смотри, каким источником заполняется коллекция: отсортированным — `SortedList` уместен, случайным и часто меняющимся — нужен `SortedDictionary`.
>
> **Компаратор, возвращающий 0 для разных объектов, тихо теряет данные.** `SortedSet`/`SortedDictionary` определяют равенство только через компаратор, не через `Equals`/`GetHashCode`. Сравнили заказы только по сумме — два разных заказа на одну сумму станут одним элементом, `Add` в множестве вернёт `false` без исключения.
>
> **Ключ без `IComparable` роняет `SortedDictionary` не при компиляции, а в рантайме.** `new SortedDictionary<MyKey,int>()` компилируется для любого `MyKey`. Если `MyKey` не реализует `IComparable<MyKey>` и свой компаратор не передан, `Comparer<MyKey>.Default` бросит исключение только при первом сравнении — то есть при втором `Add`. Тест с одним элементом это не поймает.
>
> **Порядок `Dictionary`/`HashSet` не гарантирован**, хотя на практике совпадает с порядком вставки, пока не было `Remove`. Опираться на это нельзя — `Remove` освобождает слот, следующая вставка занимает дырку в середине, `Resize` тоже меняет порядок.

## Проверь себя

> [!question]- Чем `SortedDictionary` отличается от `SortedList` и когда что выбрать?
> Обе дают порядок по ключу через компаратор, но устроены по-разному. `SortedDictionary` — красно-чёрное дерево: O(log n) гарантированно на поиск, вставку и удаление в любую позицию, но узел — отдельный объект в куче (~40–48 байт) и обход прыгает по случайным адресам. `SortedList` — два параллельных массива: поиск бинарный O(log n) с отличной локальностью кеша и минимумом памяти, но вставка/удаление в середину — O(n) сдвиг хвоста. Правило: заполнил один раз и читаю — `SortedList`; коллекция часто меняется в случайных позициях — `SortedDictionary`.

> [!question]- Почему `SortedList`, заполненный случайными ключами, может работать на порядки медленнее ожидаемого?
> Каждая вставка не в конец — это `Array.Copy` хвоста массива. На случайных ключах средний сдвиг — половина массива, и суммарная стоимость n вставок становится O(n²): на 200 000 элементов — миллиарды операций копирования вместо линейных миллионов у дерева. Лечится сортировкой источника перед заполнением (`OrderBy` + `Add` по возрастанию — тогда все вставки идут в конец за O(1)) или временным использованием `SortedDictionary` на время наполнения.

> [!question]- Зачем нужен `OrderedDictionary`, если есть `Dictionary` и `SortedDictionary`?
> Он закрывает третий случай, который не покрывают ни `Dictionary` (порядка нет вообще), ни `SortedDictionary` (порядок по значению ключа). `OrderedDictionary<K,V>` (.NET 9+) даёт O(1) поиск по ключу и при этом гарантированный порядок **вставки** — то, что раньше собирали вручную из `Dictionary<K, LinkedListNode<V>>` плюс `LinkedList<V>`. Нужен для LRU-структур, конвейеров шагов, полей формы, истории операций.

> [!question]- Когда `Dictionary` окажется медленнее линейного поиска по массиву?
> На малых объёмах — обычно до нескольких десятков элементов, точная граница зависит от типа ключа. «O(1)» описывает число операций, а не их стоимость: вычисление хеша, затем два случайных обращения в память (`_buckets`, потом `_entries`) с высокой вероятностью промаха кеша, затем сравнение ключа при коллизии. Линейный проход по массиву процессор предсказывает почти идеально — одна cache line 64 байта приносит сразу 16 `int`. Проверять нужно [[Как измерять: BenchmarkDotNet]], а не «на глаз».

> [!question]- Почему нельзя опираться на порядок перечисления `Dictionary`?
> Документация прямо говорит, что порядок не определён. На практике при вставках без удалений он совпадает с порядком добавления, потому что записи кладутся подряд в `Entry[]`. Но `Remove` освобождает слот и заносит его в список свободных, следующая вставка переиспользует дырку в середине массива — и порядок ломается; `Resize` тоже может его изменить. Если порядок вставки нужен по контракту — `OrderedDictionary<K,V>`, если порядок по ключу — `SortedDictionary`/`SortedSet`.

> [!question]- Почему возврат `List<T>` из публичного свойства или метода — проблема, даже если снаружи его никто не должен менять?
> `get`-only свойство защищает только ссылку на объект, а не сам список: `public List<T> Items { get; }` всё равно отдаёт наружу изменяемый объект, и любой вызывающий код может сделать `obj.Items.Add(x)` или `.Clear()`, минуя проверки и инварианты класса. Если внутри есть зависимое состояние (например, кешированная сумма позиций), оно молча разойдётся с содержимым списка. Решение — приватное поле `List<T>` и публичное свойство типа `IReadOnlyList<T>`, а изменения только через явные методы класса с проверками.

## Разбор

**Дан фрагмент — найди проблему.** Справочник тарифов на 200 000 строк грузится из БД без `ORDER BY` и заполняет коллекцию 30 секунд:
```csharp
var rates = new SortedList<int, decimal>();
foreach (var row in ReadFromDbUnordered())   // порядок случайный
    rates.Add(row.Id, row.Rate);
```

> [!success]- Решение
> Причина — вставки в случайные позиции массива, каждая O(n) на сдвиг хвоста; суммарно на 200 000 строк это близко к O(n²). Два исправления, оба сохраняют тип коллекции: отсортировать источник перед заполнением (`ReadFromDbUnordered().OrderBy(r => r.Id)`, тогда все вставки идут в конец за O(1)) или переложить сортировку на СУБД (`ORDER BY id` в запросе). Дополнительно стоит сразу задать `Capacity` конструктором — без неё внутренние массивы несколько раз переудваиваются с копированием. Если вставки будут продолжаться после старта в произвольном порядке, правильный тип — не `SortedList`, а `SortedDictionary`.

**Дано два решения — обоснуй выбор.** Нужно хранить занятые даты бронирования и быстро находить первую свободную дату не раньше заданной. Кандидат А: `HashSet<DateOnly>` с циклом `while (booked.Contains(candidate)) candidate = candidate.AddDays(1);`. Кандидат Б: `SortedSet<DateOnly>` с `GetViewBetween(from, DateOnly.MaxValue)`.

> [!success]- Решение
> Кандидат А в худшем случае (длинная непрерывная серия занятых дат) выполняет `Contains` для каждого дня серии — O(1) на проверку, но столько проверок, сколько занятых дней подряд, без возможности сразу перейти к границе диапазона. Кандидат Б через `GetViewBetween` получает представление на поддерево «всё ≥ from» за O(log n) и дальше идёт только по реально занятым датам из этого представления, естественно останавливаясь на первом разрыве — та же асимптотика в худшем случае, но `SortedSet` дополнительно даёт `Min`/`Max` за O(log n) и диапазонные операции, которых у `HashSet` нет в принципе. Если из требований видно, что понадобятся диапазоны или обход по возрастанию — выбор `SortedSet` оправдан заранее, а не только по нынешнему методу.

**Дан PR агента — что вернёшь на доработку.** Агент реализовал кеш конфигурации фичей: словарь строится один раз при старте приложения и потом читается на каждый запрос из множества потоков.

```csharp
private static readonly SortedDictionary<string, bool> _features =
    LoadFeatures().ToDictionary(f => f.Name, f => f.Enabled)
                  is var dict ? new SortedDictionary<string, bool>(dict) : null!;

public static bool IsEnabled(string name) => _features.TryGetValue(name, out var v) && v;
```

> [!success]- Решение
> Вернуть на доработку с комментарием: выбор структуры не соответствует профилю обращений. Порядок по ключу здесь не используется вообще — `IsEnabled` только читает по имени, обход по алфавиту нигде не нужен. Значит, платить O(log n) и памятью узла дерева не за что. Если словарь read-only после старта и читается очень часто из многих потоков — правильный тип `FrozenDictionary<string, bool>` (`LoadFeatures().ToFrozenDictionary(f => f.Name, f => f.Enabled)`): быстрее на чтении, безопасен для параллельного доступа без единой блокировки, и не создаёт n узлов для GC. `SortedDictionary` в этом месте — типичный случай «выбрали коллекцию по названию, а не по операциям», которые она реально выполняет.

## Итог

- Коллекции делятся по семантике (список/множество/словарь/очередь/отсортированные), а потокобезопасность и неизменяемость — независимые оси поверх этого деления.
- Главный вопрос выбора — профиль обращений: ключ или индекс, порядок вставки или порядок по ключу или порядок не нужен, часто меняется или заполняется один раз.
- Отсортированные коллекции — не одна структура: дерево (`SortedDictionary`/`SortedSet`) держит O(log n) гарантированно при любых правках, массивы (`SortedList`) дешевле по памяти и быстрее на чтении, но деградируют на случайных вставках до O(n²).
- Порядок вставки и порядок по ключу — разные гарантии с разными типами (`OrderedDictionary` против `SortedDictionary`/`SortedSet`/`SortedList`); путать их — частая ошибка постановки задачи, а не только реализации.
- Компаратор в отсортированных и хеш-коллекциях — источник истины о равенстве, а не только о порядке; неполный компаратор молча теряет элементы.
- Типичная ловушка сгенерированного кода — `List` и линейный поиск там, где нужен словарь, и `SortedList` там, где данные меняются часто и в случайном порядке.
- Легаси-пространства `System.Collections` и `System.Collections.Specialized` (боксинг, `object`-ключи) в новом коде не используются; встречаются только в легаси и COM-интеропе.
