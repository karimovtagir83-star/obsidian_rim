# IEnumerable vs IQueryable

> [!abstract] Коротко
> `IEnumerable<T>` выполняет LINQ-операторы как обычный C#-код над коллекцией в памяти. `IQueryable<T>` строит **дерево выражений** и передаёт его провайдеру (например, EF Core), который транслирует дерево в SQL. Перепутать их — не ошибка компиляции: код скомпилируется и даже отработает корректно на маленьких данных, но на реальном объёме утащит в память то, что должно было отфильтроваться в базе.

## Зачем это знать

Это самая частая причина скрытого N+1 и полной материализации таблицы, которая не видна на code review без понимания разницы: `context.Orders.ToList().Where(o => o.IsPaid)` и `context.Orders.Where(o => o.IsPaid).ToList()` выглядят почти одинаково, но первый тянет в память всю таблицу `Orders`, а второй передаёт `WHERE` в SQL — и разница проявляется только под реальной нагрузкой, не на тестовой базе из десяти строк.

## Модель

`IQueryable<T>` наследует `IEnumerable<T>`, поэтому один и тот же LINQ-синтаксис компилируется в обоих случаях — сигнатуры операторов идентичны, но реализация принципиально разная:

```
IEnumerable<T>:  LINQ-оператор → делегат → выполняется как обычный C#-код,
                 сразу, элемент за элементом, в памяти процесса

IQueryable<T>:   LINQ-оператор → добавляется в Expression Tree →
                 ничего не выполняется, пока не вызван терминальный метод →
                 провайдер (EF Core) переводит дерево целиком в SQL →
                 SQL выполняется в СУБД → результат возвращается и материализуется
```

Граница между двумя мирами проходит **в момент вызова метода, который возвращает не `IQueryable`, а что-то другое** — чаще всего `.ToList()`/`.ToArray()`/`.AsEnumerable()`, или обращение к свойству/методу, которое EF Core не умеет транслировать в SQL. Любой LINQ-оператор, вызванный **после** этой границы, работает уже над данными в памяти.

```csharp
// Все фильтры до .ToList() уходят в один SQL-запрос — WHERE выполняет БД
var paid = context.Orders
    .Where(o => o.IsPaid)
    .OrderBy(o => o.CreatedAt)
    .ToList();

// Фильтр после .ToList() выполняется в памяти — вся таблица уже загружена
var paid = context.Orders
    .ToList()
    .Where(o => o.IsPaid);
```

## Решения

| Ситуация | Что использовать |
|---|---|
| Источник — `DbSet<T>`/EF-запрос, фильтрация по полям сущности | оставаться в `IQueryable` до последнего момента, материализовать одним `.ToList()` в конце |
| Нужна вызов C#-метода, который EF не умеет транслировать (сложная бизнес-функция) | материализовать раньше нужного места, явно это осознавая — и явно ограничить объём до материализации (`Where` по индексированному полю до `.ToList()`) |
| Работа полностью в памяти (уже загруженная коллекция, DTO) | `IEnumerable<T>` — как параметр метода это самый общий и достаточный тип |
| Публичный API репозитория/сервиса наружу модуля | возвращать `IEnumerable<T>`/`IReadOnlyList<T>`, а не `IQueryable<T>` — иначе вызывающий код может пристроить к запросу что угодно, включая непредсказуемо тяжёлые условия, без контроля со стороны репозитория |

## В ServiceShop

Read-side построен на CQRS: запросы идут через Dapper с явным SQL (см. [[ServiceShop: CQRS и путь запроса]]), а не через `IQueryable` — это осознанный выбор, который убирает саму возможность спутать `IEnumerable` и `IQueryable`, потому что SQL пишется руками и виден целиком. Там, где в проекте всё же используется EF Core напрямую (запись через команды), правило то же самое: `Where`/`Include`/сортировка — до материализации, а не после.

## Где ошибаются

> [!warning] Подводные камни
> - **Метод возвращает `IQueryable`, но подписан как `IEnumerable`.** Из-за наследования это компилируется, и вызывающий код может решить, что дальнейшие условия «просто LINQ», не понимая, что они всё ещё уйдут в SQL — или наоборот, что уже в памяти, хотя это не так.
> - **Вызов метода C#, не транслируемого в SQL, внутри `Where` до материализации.** EF Core либо выбросит исключение о невозможности перевести выражение в SQL, либо (для менее строгих провайдеров) незаметно выполнит клиентскую оценку — с непредсказуемой производительностью.
> - **Агент часто:** пишет `.ToList()` сразу после получения `DbSet`, а все фильтры и сортировки — цепочкой LINQ уже после, потому что это выглядит "более читаемым" линейным кодом — но именно так фильтрация переезжает из SQL в память, и на таблице с миллионом строк это заметно только в проде, не в тестах на десяти записях.

## Проверка на ревью

- Метод, возвращающий результат из EF Core, либо материализует результат до возврата (`.ToList()`), либо явно и осознанно возвращает `IQueryable` с документированной причиной (композиция запроса выше по стеку).
- Фильтрация, сортировка, проекция (`Select`) для EF-запроса стоят **до** `.ToList()`/`.ToArray()`, а не после.
- В цепочке `Where`/`OrderBy` над `IQueryable` нет вызовов пользовательских C#-методов, которые EF Core не умеет транслировать.
- Публичная сигнатура репозитория/сервиса не отдаёт `IQueryable<T>` наружу модуля без явной причины.

## Проверь себя

> [!question]- Почему `context.Orders.ToList().Where(o => o.IsPaid)` работает, но плохо, если он работает на любых данных?
> Он работает, потому что `IEnumerable<T>.Where` — валидный вызов после `ToList()`. Плохо — потому что `ToList()` уже выполнил SQL `SELECT * FROM Orders` без условия `WHERE`, загрузив в память всю таблицу, а фильтрация `IsPaid` произошла уже над данными в приложении. На маленькой тестовой таблице разницы не видно; на боевой таблице в миллионы строк это лишний сетевой трафик, память и время, которых не было бы при перестановке вызовов местами.

> [!question]- Почему нельзя просто «всегда использовать `IQueryable`» и не думать о разнице?
> `IQueryable` полезен только пока запрос строится над источником, который умеет транслировать выражения в SQL (`DbSet<T>`). Как только цепочка ушла в клиентский режим, `IQueryable` не имеет смысла — но переходы туда разные, и их стоит различать. `.ToList()` материализует: SQL выполнен, данные в памяти. `.AsEnumerable()` данные **не** материализует — он только меняет тип, из-за чего дальнейшие операторы становятся клиентскими, а чтение продолжает стримиться по открытому ридеру. То есть `AsEnumerable()` перед `Where` уносит фильтр в приложение, не загружая при этом таблицу целиком в список. После любого из этих переходов — дальнейшая работа идёт через `IEnumerable`. Кроме того, отдавать `IQueryable` наружу метода/модуля — это неявно передавать вызывающему коду возможность модифицировать сам SQL-запрос, что усложняет контроль над тем, какие запросы реально выполняются к базе.

## Разбор

### Разбор 1. Где переехала фильтрация

```csharp
public List<Order> GetRecentOrders(AppDbContext db, int customerId)
{
    var orders = db.Orders.ToList();
    return orders
        .Where(o => o.CustomerId == customerId)
        .OrderByDescending(o => o.CreatedAt)
        .Take(10)
        .ToList();
}
```

Опиши, что произойдёт при вызове этого метода на таблице `Orders` с 5 миллионами строк, и перепиши без проблемы.

> [!success]- Разбор
> `db.Orders.ToList()` загружает все 5 миллионов строк в память до какой-либо фильтрации — `Where`/`OrderByDescending`/`Take` выполняются уже над этим огромным списком в приложении. Правильная версия переносит все операторы до материализации: `return db.Orders.Where(o => o.CustomerId == customerId).OrderByDescending(o => o.CreatedAt).Take(10).ToList();` — тогда СУБД выполнит `WHERE customerId = ... ORDER BY ... LIMIT 10` и в приложение вернутся только 10 строк.

## Итог

- `IQueryable` строит дерево выражений и транслируется в SQL провайдером; `IEnumerable` выполняется как обычный C#-код в памяти
- Оба поддерживают один и тот же LINQ-синтаксис, поэтому спутать их не ловит компилятор — только внимательное чтение, где именно вызван материализующий метод
- Всё, что нужно передать в SQL (фильтр, сортировка, проекция), должно стоять до `.ToList()`/`.ToArray()`
- Возврат `IQueryable` наружу модуля — осознанное архитектурное решение, а не случайность сигнатуры
