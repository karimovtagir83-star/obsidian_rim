# Dictionary и HashSet изнутри

> [!abstract] Коротко
> `Dictionary<TKey,TValue>` — хеш-таблица (hash table) с разрешением коллизий методом цепочек, но сами цепочки живут внутри одного плоского массива `Entry[]` и связаны целочисленными индексами, а не ссылками. Это даёт амортизированный O(1) на поиск, вставку и удаление, отличную локальность кеша и почти нулевую нагрузку на сборщик мусора. `HashSet<T>` — та же структура без поля `value`. Вся корректность держится на контракте `GetHashCode`/`Equals`: нарушите его — и элемент физически останется в памяти, но станет недостижимым.

## Зачем это нужно

Базовая задача: по ключу быстро найти значение. Варианты без хеш-таблицы:

| Структура | Поиск | Вставка | Проблема |
|---|---|---|---|
| `List<T>` + линейный перебор | O(n) | O(1) | 100 000 элементов — 100 000 сравнений на каждый запрос |
| Отсортированный массив + бинарный поиск | O(log n) | O(n) | вставка сдвигает половину массива |
| Сбалансированное дерево (`SortedDictionary`) | O(log n) | O(log n) | указатели, аллокация узла на элемент, промахи кеша |
| **Хеш-таблица** | **O(1) сред.** | **O(1) аморт.** | нужен хороший `GetHashCode`, порядок не сохраняется |

Хеш-таблица переводит «где искать» из сравнения в арифметику: считаем от ключа число, делим по модулю на размер массива, попадаем сразу в нужную ячейку. Количество элементов почти не влияет на время.

### Что было до: Hashtable

До дженериков (.NET 1.x) существовал `System.Collections.Hashtable` — нетипизированная таблица `object → object`.

```csharp
// #устарело — так писали до .NET 2.0
var table = new Hashtable();
table["age"] = 42;                 // boxing int → object, аллокация в куче
int age = (int)table["age"];       // unboxing + приведение, может бросить в рантайме
```

Почему от него ушли:

1. **Boxing.** Любой значимый тип упаковывался при вставке и распаковывался при чтении. Словарь на миллион `int`-ключей — миллион лишних объектов в куче, см. [[Value types vs Reference types]].
2. **Нет типовой безопасности.** Можно положить `string` туда, где ожидается `int`, и узнать об этом в проде.
3. **Отдельный объект-bucket на элемент.** Внутри `Hashtable` цепочки коллизий были на объектах, что означало разбросанные по куче узлы и работу для GC.
4. **Странная семантика отсутствия ключа.** `table["нет"]` возвращает `null`, а не бросает — легко перепутать «нет ключа» и «значение null».

`Hashtable` до сих пор жив ради обратной совместимости и встречается в легаси. В новом коде — только `Dictionary<TKey,TValue>`.

> [!info] Мелкая, но важная деталь
> `Hashtable` использовал двойное хеширование (открытая адресация), а не цепочки. `Dictionary` с самого начала пошёл другим путём — и это одна из причин, почему у них разное поведение при плохих хешах.

## Внутреннее устройство Dictionary

В современном .NET (Core 2.1 и далее, включая .NET 10) поля выглядят так:

```csharp
public class Dictionary<TKey, TValue>
{
    private int[]? _buckets;          // индексы в _entries, сдвинутые на +1
    private Entry[]? _entries;        // сами данные, плотно, по порядку вставки
    private ulong _fastModMultiplier; // только на 64-битных: замена деления
    private int _count;               // сколько слотов _entries занято (вкл. освобождённые)
    private int _freeList;            // голова списка освобождённых слотов
    private int _freeCount;           // длина списка освобождённых слотов
    private int _version;             // счётчик структурных изменений для энумератора
    private IEqualityComparer<TKey>? _comparer;

    private struct Entry
    {
        public uint hashCode;  // сохранённый хеш ключа
        public int next;       // индекс следующего элемента цепочки, -1 = конец
        public TKey key;
        public TValue value;
    }
}
```

Обратите внимание: `Entry` — **структура**, лежит внутри массива. Значит на 1000 элементов приходится ровно два объекта в куче (`int[]` и `Entry[]`), а не 1001. Реальный размер `Count` = `_count - _freeCount`.

### Схема поиска ключа

```
                       Dictionary<string, int>
                       _buckets.Length = 7 (простое число)

   key = "cat"
     │
     │ 1. hash = _comparer.GetHashCode("cat")        →  0x9A3F21C4
     │ 2. bucket = hash % 7                          →  3
     ▼
  _buckets  index:  0    1    2    3    4    5    6
            ┌─────┬────┬────┬────┬────┬────┬────┐
            │  0  │ 5  │ 0  │ 2  │ 1  │ 0  │ 4  │   значения = index+1
            └─────┴────┴────┴──┬─┴────┴────┴────┘   0 означает «бакет пуст»
                               │
                    _buckets[3] = 2  →  реальный индекс в _entries = 2-1 = 1
                               │
                               ▼
  _entries  index:      0            1            2            3
            ┌──────────────┬──────────────┬──────────────┬──────────────┐
   hashCode │  0x1122AA01  │  0x77BC0055  │  0x9A3F21C4  │  0x0043FE10  │
   next     │      -1      │      2       │     -1       │     -1       │
   key      │    "dog"     │    "ant"     │    "cat"     │    "fox"     │
   value    │      7       │      3       │     42       │      9       │
            └──────────────┴──────┬───────┴──────────────┴──────────────┘
                                  │  next = 2
                                  └────────────▶ идём в _entries[2]

   3. _entries[1]: hashCode 0x77BC0055 != 0x9A3F21C4  → мимо, next = 2
   4. _entries[2]: hashCode совпал → сравниваем ключи Equals("cat","cat") → нашли
   5. возвращаем value = 42

   Цепочка бакета 3:  _entries[1] ("ant") → _entries[2] ("cat") → конец (-1)
```

Три вещи, которые надо унести из этой схемы.

**Почему `_buckets` хранит `index + 1`.** Массивы в .NET создаются занулёнными: `new int[7]` — это семь нулей. Если бы бакет хранил индекс как есть, ноль был бы валидным индексом (`_entries[0]`) и одновременно означал бы «пусто» — различить невозможно, пришлось бы отдельно инициализировать массив значением `-1` при каждом создании и каждом `Resize`. Сдвиг на единицу делает «пусто» бесплатным: `0` — пусто, `n` — элемент с индексом `n-1`. Внутри кода это выглядит как

```csharp
// упрощённо, из TryInsert
ref int bucket = ref GetBucket(hashCode);
int i = bucket - 1;              // распаковали индекс
// ...
bucket = index + 1;              // упаковали обратно
```

**`next` — это индекс, а не ссылка.** Цепочка коллизий — не связный список объектов, а связный список **позиций внутри массива**. Это критично: обход цепочки не разыменовывает указатели в разные места кучи, а прыгает по одному непрерывному блоку памяти. Процессор часто уже держит соседние `Entry` в строке кеша.

**Хеш хранится в `Entry`.** Сравнение начинается с целочисленного `hashCode` — дешёвая операция, отсекающая почти все несовпадения без вызова `Equals`. Вызов `Equals` (потенциально дорогой — сравнение строк, например) происходит только когда хеши уже равны.

### Разрешение коллизий: цепочки внутри массива

Коллизия — это когда два разных ключа попали в один бакет. Два ключа могут дать одинаковый бакет по двум причинам: одинаковый хеш (редко) или разные хеши, дающие одинаковый остаток по модулю (часто — бакетов всего несколько сотен, а хешей 4 миллиарда).

Есть два классических подхода:

| Подход | Как работает | Кто использует |
|---|---|---|
| Separate chaining (цепочки) | у бакета висит список всех элементов, попавших в него | `Dictionary`, `HashSet` |
| Open addressing (открытая адресация) | при занятости пробуем следующие ячейки по правилу | `Hashtable`, `FrozenDictionary` частично |

`Dictionary` использует цепочки, но реализует их **без отдельных объектов-узлов**. Сравнение с наивной реализацией:

```
Наивные цепочки (как в Hashtable / Java HashMap до оптимизаций):

  _buckets[3] ──▶ [Node] ──▶ [Node] ──▶ [Node] ──▶ null
                  куча       куча       куча
                  0x7F10     0x4A88     0xC301
                  ↑ три объекта, три промаха кеша, три корня для GC

Цепочки в массиве (Dictionary):

  _buckets[3] = 2 ──▶ _entries[1] ──next──▶ _entries[5] ──next──▶ _entries[9]
                      └──────────── один непрерывный блок памяти ───────────┘
                      ноль объектов на элемент, GC видит один массив
```

Что это даёт:

- **GC.** Для сборщика мусора `Entry[]` — один объект. При маркировке он обходит массив линейно; если `TKey` и `TValue` — значимые типы без ссылок, GC вообще не смотрит внутрь (массив помечен как не содержащий ссылок). Наивные цепочки означали бы n объектов, каждый из которых надо посетить, см. [[Сборка мусора (GC): как работает]].
- **Локальность.** Промах кеша стоит ~100 нс, попадание — ~1 нс. Обход цепочки из трёх элементов в массиве — это часто одна-две загрузки строк кеша вместо трёх случайных обращений в кучу.
- **Аллокации.** `Add` не аллоцирует ничего, пока не нужен `Resize`. Наивные цепочки аллоцируют узел на каждый `Add`, см. [[Аллокации и как их избегать]].

Обратная сторона: `Entry` содержит `key` и `value` по значению, поэтому большие структуры в качестве ключа/значения раздувают массив и делают `Resize` дороже.

### Как считается индекс бакета

```csharp
// упрощённая версия из System.Private.CoreLib
private ref int GetBucket(uint hashCode)
{
    int[] buckets = _buckets!;
#if TARGET_64BIT
    return ref buckets[HashHelpers.FastMod(hashCode, (uint)buckets.Length, _fastModMultiplier)];
#else
    return ref buckets[(uint)hashCode % (uint)buckets.Length];
#endif
}
```

**Размер `_buckets` — всегда простое число.** Оно берётся из зашитой таблицы `HashHelpers.primes`: `3, 7, 11, 17, 23, 29, 37, 47, 59, 71, 89, 107, 131, 163, 197, 239, 293, 353, 431, 521, 631, 761, 919, 1103, 1327, 1597, 1931, 2333, 2801, 3371, ...` — каждое следующее примерно в 1.2 раза больше предыдущего, а `ExpandPrime` при росте берёт первое простое, не меньшее `2 * _count`.

Почему именно простое? Потому что `hash % m` теряет информацию о старших битах хеша тем сильнее, чем больше у `m` делителей. Классический пример: пусть `m = 16` (степень двойки). Тогда `hash % 16` — это просто младшие 4 бита хеша. Если ключи — адреса объектов, выровненные по 16 байтам, или идентификаторы, кратные 16, все они лягут в один бакет:

```
Ключи: 16, 32, 48, 64, 80, ...   (все кратны 16)

m = 16 (степень двойки):     m = 17 (простое):
  16 % 16 = 0                  16 % 17 = 16
  32 % 16 = 0                  32 % 17 = 15
  48 % 16 = 0                  48 % 17 = 14
  64 % 16 = 0                  64 % 17 = 13
  80 % 16 = 0                  80 % 17 = 12
  ────────────────             ────────────────
  ВСЁ в бакет 0 → O(n)         равномерно → O(1)
```

Простое `m` не имеет общих делителей ни с одним «шагом» в данных, кроме самого себя, поэтому арифметические прогрессии в ключах рассыпаются по бакетам равномерно. Это страховка от посредственных `GetHashCode`, которых в реальном коде большинство.

**Fastmod.** Целочисленное деление — одна из самых дорогих инструкций (десятки тактов, `div` на x64). Раз `m` не степень двойки, битовым `and` не отделаться. Поэтому .NET Core 3.0 ввёл трюк: заранее вычислить «магический множитель» и заменить деление двумя умножениями и сдвигами.

```csharp
// HashHelpers, упрощённо
public static ulong GetFastModMultiplier(uint divisor) => ulong.MaxValue / divisor + 1;

public static uint FastMod(uint value, uint divisor, ulong multiplier)
{
    // Умножение 64×64 → берём старшие биты. Никакого div.
    uint highbits = (uint)(((((multiplier * value) >> 32) + 1) * divisor) >> 32);
    return highbits;
}
```

Множитель считается один раз в `Initialize`/`Resize` и живёт в поле `_fastModMultiplier`. Работает только на 64-битных платформах (нужно 64-битное умножение), поэтому обёрнуто в `#if TARGET_64BIT`. Выигрыш на горячем пути поиска — заметные проценты.

### GetHashCode: контракт и цена его нарушения

Контракт (см. [[Object: Equals, GetHashCode, ToString]]):

1. Если `a.Equals(b)`, то `a.GetHashCode() == b.GetHashCode()`. **Обязательно.**
2. Обратное неверно: равные хеши не означают равные объекты. Хеш — 32 бита, объектов бесконечно много, коллизии неизбежны и нормальны.
3. Хеш **не должен меняться**, пока объект используется как ключ. Формально: `GetHashCode` должен зависеть только от иммутабельного состояния.
4. Хеш должен быть дешёвым и равномерным.

Нарушение пункта 3 — самая коварная ошибка. Элемент не исчезает из памяти: он остаётся в `_entries`, `Count` его считает, `foreach` его находит. Но найти по ключу его невозможно, потому что поиск идёт в другой бакет.

```csharp
public sealed class MutablePoint
{
    public int X { get; set; }   // мутабельное поле — участвует в хеше. Мина.
    public int Y { get; set; }

    public override int GetHashCode() => HashCode.Combine(X, Y);
    public override bool Equals(object? o) => o is MutablePoint p && p.X == X && p.Y == Y;
    public override string ToString() => $"({X},{Y})";
}

var dict = new Dictionary<MutablePoint, string>();
var key = new MutablePoint { X = 1, Y = 1 };
dict[key] = "жив";

Console.WriteLine(dict.ContainsKey(key));   // True

key.X = 99;                                 // мутировали ключ, лежащий в словаре

Console.WriteLine(dict.ContainsKey(key));   // False — ищем в новом бакете
Console.WriteLine(dict.Count);              // 1 — элемент на месте
Console.WriteLine(dict.Keys.First());       // (99,1) — виден в перечислении
Console.WriteLine(dict.Remove(key));        // False — удалить тоже не получится

// Элемент недостижим по ключу. Это утечка: словарь растёт, память не освобождается.
```

Отсюда практическое правило: **ключом должен быть иммутабельный тип** — `string`, `int`, `Guid`, `enum`, `record` с `init`-свойствами, readonly struct. См. [[Иммутабельность как приём проектирования]].

### Рандомизация строковых хешей

`string.GetHashCode()` в .NET Core рандомизирован: в каждом процессе используется случайное «зерно» (seed), поэтому одна и та же строка даёт разные хеши в разных запусках.

```csharp
Console.WriteLine("hello".GetHashCode());
// Запуск 1: -1758410964
// Запуск 2:   837544235
// Запуск 3:  1204773119
```

Зачем: защита от **hash-flooding DoS**. Если хеш детерминирован, злоумышленник может заранее подобрать тысячу строк с одинаковым бакетом и отправить их в форму/JSON. Все они попадут в одну цепочку, каждая вставка станет O(n), обработка одного запроса займёт секунды CPU — и сервер лёг без всякого объёма трафика. Такие атаки массово применялись против веб-фреймворков в 2011–2012 годах.

Прямые следствия для вашего кода:

- **Нельзя персистить `GetHashCode()`** — ни в БД, ни в файл, ни в кеш, ни в HTTP-ответ. После рестарта значение изменится. Для стабильных хешей берите `SHA256`, `XxHash3`/`XxHash64` из `System.IO.Hashing` или `MD5` (для не-криптографических целей).
- Нельзя сравнивать хеши между процессами, узлами кластера, версиями приложения.
- Нельзя строить шардирование по `string.GetHashCode()`.

Но у рандомизации есть цена: она медленнее. Поэтому `Dictionary<string, TValue>` с компаратором по умолчанию хитрит.

```
Создание Dictionary<string, V> без явного компаратора:
        │
        ▼
  _comparer = NonRandomizedStringEqualityComparer   ← быстрый, НЕ рандомизированный
        │
        ├─ обычная работа: короткий быстрый хеш, максимум скорости
        │
        ▼
  при вставке считаем collisionCount в цепочке
        │
        ├─ collisionCount <= 100 → всё нормально, продолжаем
        │
        └─ collisionCount > 100 (HashHelpers.HashCollisionThreshold)
                   │
                   ▼
           Resize(entries.Length, forceNewHashCodes: true)
           _comparer = рандомизированный компаратор
           пересчитываем ВСЕ хеши заново
                   │
                   ▼
           атака нейтрализована, дальше работаем на рандомизированных хешах
```

То есть в обычной жизни вы получаете быстрый нерандомизированный хеш, а при признаках атаки (аномально длинная цепочка) словарь сам переключается на защищённый режим. Один раз на словарь, необратимо. Важно: этот механизм работает **только** для `Dictionary<string,V>`/`HashSet<string>` с компаратором по умолчанию или `StringComparer.Ordinal`/`OrdinalIgnoreCase`. Свой компаратор — своя ответственность.

### Resize: рост словаря

```csharp
// внутри TryInsert
if (_freeCount > 0)
{
    // берём слот из free-list, массив расти не должен
    index = _freeList;
    _freeList = StartOfFreeList - entries[_freeList].next;
    _freeCount--;
}
else
{
    if (_count == entries.Length)   // ← условие роста
    {
        Resize();
        bucket = ref GetBucket(hashCode);   // старая ссылка на бакет невалидна!
    }
    index = _count;
    _count++;
}
```

`Resize()` без параметров вызывает `Resize(HashHelpers.ExpandPrime(_count), forceNewHashCodes: false)`, где `ExpandPrime` возвращает первое простое число, не меньшее `2 * _count`.

Что происходит внутри:

1. Аллоцируется новый `Entry[]` нового размера и новый `int[] _buckets` нового размера.
2. Старые `Entry` **копируются целиком** через `Array.Copy` — включая уже сохранённые `hashCode`.
3. `_buckets` заполняется заново: для каждой записи считается `hashCode % newSize` и восстанавливается цепочка.
4. Пересчитывается `_fastModMultiplier`.

**Ключевой момент: `GetHashCode` при рехеше не вызывается.** Хеши уже лежат в `Entry.hashCode`. Пересчитывается только распределение по бакетам — это дешёвая арифметика. Единственное исключение — `forceNewHashCodes: true` при переключении на рандомизированный строковый компаратор.

Стоимость `Resize` — O(n), но так как размер удваивается, суммарная стоимость n вставок — O(n), то есть амортизированный O(1) на вставку. Разбор амортизации — в [[Введение в алгоритмы: сложность и Big-O]].

Как избежать роста, если размер известен заранее:

```csharp
// Вариант 1: конструктор с capacity. Округляется вверх до простого числа.
var d1 = new Dictionary<int, string>(capacity: 10_000);

// Вариант 2: EnsureCapacity — можно вызвать и на уже заполненном словаре
var d2 = new Dictionary<int, string>();
d2.EnsureCapacity(10_000);   // возвращает фактическую capacity (>= 10000)

// Вариант 3: копия существующего — capacity выставится сразу
var d3 = new Dictionary<int, string>(d1);

// Освободить лишнюю память после массовых удалений
d2.TrimExcess();             // или TrimExcess(capacity)
```

Для словаря на 10 000 элементов это экономит примерно 13 промежуточных `Resize` и 26 аллокаций массивов, часть из которых уйдёт в LOH (см. [[Сборка мусора (GC): как работает]]).

### Удаление и free-list

`Remove` не сдвигает элементы. Освободившийся слот попадает в односвязный список свободных слотов, голова которого — `_freeList`.

```csharp
// упрощённо, из Remove
entries[i].next = StartOfFreeList - _freeList;   // StartOfFreeList = -3
entries[i].key = default!;                       // обнуляем, чтобы GC отпустил ссылку
entries[i].value = default!;
_freeList = i;
_freeCount++;
_version++;
```

Почему `-3 - _freeList`, а не просто индекс? Потому что поле `next` перегружено двумя смыслами. Валидные значения цепочки — это `-1` (конец) и `>= 0` (индекс). Всё, что `<= -2`, гарантированно не встречается в живой цепочке, поэтому этот диапазон отдан под кодирование free-list. Смещение `-3` оставляет `-2` свободным как «дно» списка.

```
Было (Count = 4):
  _entries: [0]="dog" [1]="ant" [2]="cat" [3]="fox"    _count=4  _freeCount=0

Remove("ant") — слот 1 освободился:
  _entries: [0]="dog" [1]=СВОБОДЕН [2]="cat" [3]="fox"
  _freeList = 1,  _entries[1].next = -3 - (-1) = -2   (конец free-list)
  _count = 4 (не уменьшился!),  _freeCount = 1,  Count = 3

Remove("fox") — слот 3 освободился:
  _freeList = 3,  _entries[3].next = -3 - 1 = -4   → указывает на слот 1
  free-list:  3 → 1 → дно
  _freeCount = 2,  Count = 2

Add("owl") — берём голову free-list, слот 3:
  _entries: [0]="dog" [1]=СВОБОДЕН [2]="cat" [3]="owl"
                                                  ▲
                              новый элемент попал в СЕРЕДИНУ массива
```

Отсюда главное практическое следствие.

> [!danger] Порядок перечисления Dictionary не гарантирован
> Это не контракт, не документированное поведение и не деталь, на которую можно опираться. На практике, пока не было ни одного `Remove`, порядок перечисления совпадает с порядком вставки — потому что элементы кладутся подряд в `_entries`, а энумератор идёт по массиву. Но после первого удаления новые элементы занимают освободившиеся слоты в середине, и порядок ломается. Кроме того, реализация может измениться в любой версии .NET: так уже было при переходе с .NET Framework на .NET Core.

```csharp
var d = new Dictionary<string, int> { ["a"] = 1, ["b"] = 2, ["c"] = 3, ["d"] = 4 };
Console.WriteLine(string.Join(",", d.Keys));   // a,b,c,d — совпало с вставкой

d.Remove("b");
d["e"] = 5;                                    // занял слот от "b"

Console.WriteLine(string.Join(",", d.Keys));   // a,e,c,d — порядок вставки потерян
```

Если порядок нужен:

| Что нужно | Решение |
|---|---|
| Порядок вставки + O(1) поиск | `OrderedDictionary<TKey,TValue>` (System.Collections.Generic, .NET 9+) |
| Порядок вставки без индексации по ключу | `List<KeyValuePair<K,V>>` |
| Сортировка по ключу | `SortedDictionary<K,V>` / `SortedList<K,V>`, см. [[Обзор коллекций .NET и как выбирать]] |
| Разовый вывод в порядке | `dict.OrderBy(kv => kv.Key)` — O(n log n), но явно и читаемо |

### Devirtualization: почему кастомный компаратор дороже

В конструкторе `Dictionary` есть неочевидная асимметрия:

```csharp
// упрощённо, из конструктора Dictionary
if (!typeof(TKey).IsValueType)
{
    // Ссылочные типы: всегда храним экземпляр компаратора в поле.
    // Обращение к EqualityComparer<TKey>.Default через shared generics стоит денег.
    _comparer = comparer ?? EqualityComparer<TKey>.Default;
}
else if (comparer is not null && comparer != EqualityComparer<TKey>.Default)
{
    // Значимые типы: поле заполняем ТОЛЬКО если компаратор действительно кастомный.
    _comparer = comparer;
}
// Иначе _comparer остаётся null — и это специально.
```

Дальше на горячем пути `FindValue` есть две ветки:

```csharp
if (_comparer is null)
{
    // JIT видит конкретный TKey (для value-типов дженерик специализируется),
    // подставляет EqualityComparer<int>.Default, девиртуализует вызов
    // и инлайнит его в обычный int-сравнитель. Ни одного call.
    ...EqualityComparer<TKey>.Default.Equals(entry.key, key)...
}
else
{
    // Виртуальный вызов через интерфейс. Инлайна нет, есть косвенный переход.
    ..._comparer.Equals(entry.key, key)...
}
```

Практический вывод: для `Dictionary<int, V>` передача даже эквивалентного по смыслу компаратора выключает оптимизацию и делает поиск измеримо медленнее (в микробенчмарках разница на десятки процентов). Не передавайте компаратор, если он не нужен. Мерить — через [[Как измерять: BenchmarkDotNet]].

Для `Dictionary<string, V>` картина другая: компаратор в поле есть всегда, поэтому явный `StringComparer.Ordinal` не хуже дефолта (и даже лучше, чем `StringComparer.InvariantCulture`, который делает лингвистическое сравнение).

## HashSet: то же самое без значений

`HashSet<T>` — почти копипаста `Dictionary`, только `Entry` без `value`:

```csharp
private struct Entry
{
    public int HashCode;   // здесь int, а не uint — историческая мелочь
    public int Next;       // -1 = конец цепочки
    public T Value;
}
```

Всё остальное совпадает: `_buckets` с `+1`, free-list, простые числа, fastmod, рандомизация строковых хешей, `_version`. Поэтому `HashSet<T>` — это ровно «`Dictionary` без значения», а `Dictionary<T, bool>` как замена множества — лишняя память и лишний код.

### Операции над множествами

```csharp
var a = new HashSet<int> { 1, 2, 3, 4 };
var b = new HashSet<int> { 3, 4, 5 };

var u = new HashSet<int>(a); u.UnionWith(b);            // {1,2,3,4,5}
var i = new HashSet<int>(a); i.IntersectWith(b);        // {3,4}
var e = new HashSet<int>(a); e.ExceptWith(b);           // {1,2}
var s = new HashSet<int>(a); s.SymmetricExceptWith(b);  // {1,2,5}

Console.WriteLine(a.IsSubsetOf(u));          // True
Console.WriteLine(a.IsProperSubsetOf(u));    // True — строгое подмножество
Console.WriteLine(u.IsSupersetOf(b));        // True
Console.WriteLine(a.Overlaps(b));            // True — есть общий элемент
Console.WriteLine(a.SetEquals(new[] {4,3,2,1})); // True — порядок не важен
```

Асимптотика, где n — размер текущего множества, m — размер аргумента:

| Операция | Сложность | Комментарий |
|---|---|---|
| `Add` / `Remove` / `Contains` | O(1) сред. | как у `Dictionary` |
| `UnionWith(other)` | O(m) | просто `Add` каждого |
| `ExceptWith(other)` | O(m) | просто `Remove` каждого |
| `IntersectWith(other)` | O(n), если `other` — `HashSet` с тем же компаратором; иначе O(n + m) | во втором случае используется битовая маска на стеке/в пуле |
| `SymmetricExceptWith(other)` | O(m) при `HashSet` с тем же компаратором, иначе O(n + m) | |
| `IsSubsetOf` / `IsSupersetOf` | O(n) или O(n + m) | быстрый выход по сравнению `Count` |
| `Overlaps(other)` | O(m) | выходит на первом совпадении |
| `SetEquals(other)` | O(m) | |

> [!tip] Одинаковый компаратор — это важно
> Многие операции имеют быстрый путь только когда `other` — тоже `HashSet<T>` **с тем же компаратором**. `new HashSet<string>(StringComparer.OrdinalIgnoreCase).IntersectWith(new HashSet<string>())` пойдёт по медленному пути. Держите компараторы согласованными.

`HashSet` также поддерживает `TryGetValue(T equalValue, out T actualValue)` — способ получить именно тот экземпляр, который лежит в множестве. Полезно для интернирования объектов:

```csharp
var pool = new HashSet<string>(StringComparer.Ordinal);
string Intern(string s) => pool.TryGetValue(s, out var existing) ? existing : Add(s);
string Add(string s) { pool.Add(s); return s; }
```

## CollectionsMarshal: одно обращение вместо двух

Классический словарь-счётчик хеширует ключ дважды или трижды:

```csharp
// 2 хеширования: TryGetValue + индексатор
if (counts.TryGetValue(word, out int c)) counts[word] = c + 1;
else counts[word] = 1;

// Ещё хуже — 3 хеширования
if (counts.ContainsKey(word)) counts[word]++;   // ContainsKey + чтение + запись
else counts[word] = 1;
```

`CollectionsMarshal` даёт `ref` прямо на поле `value` внутри `Entry`, то есть один поиск и запись по ссылке:

```csharp
using System.Runtime.CompilerServices;
using System.Runtime.InteropServices;

var counts = new Dictionary<string, int>();

foreach (string word in words)
{
    // Один поиск: если ключа нет — добавляется со значением default(int) == 0
    ref int slot = ref CollectionsMarshal.GetValueRefOrAddDefault(counts, word, out bool existed);
    slot++;                       // пишем прямо в Entry.value, второго хеширования нет
    if (!existed) { /* можно отреагировать на первое появление */ }
}
```

Второй метод — для случая «обновить, только если есть»:

```csharp
ref int slot = ref CollectionsMarshal.GetValueRefOrNullRef(counts, "cat");
if (!Unsafe.IsNullRef(ref slot))
    slot += 10;      // ключ есть — обновили на месте
// иначе slot — null-ref, обращаться к нему нельзя (AccessViolation)
```

Особенно ценно, когда значение — большая структура: без `ref` пришлось бы читать копию, менять её и записывать обратно целиком.

> [!danger] Правила безопасности для ref-доступа
> Полученная ссылка указывает внутрь массива `_entries`. Любая операция, вызывающая `Resize` (`Add`, `TryAdd`, индексатор с новым ключом, `EnsureCapacity`), аллоцирует новый массив — и ваша ссылка начнёт указывать в старый, уже осиротевший. Аналогично `Remove` может отдать слот другому ключу. Правило: используйте `ref` немедленно и не держите его через модификации словаря. Класс называется `CollectionsMarshal` и лежит в `System.Runtime.InteropServices` не случайно — он помечен как unsafe API.

С .NET 9 есть ещё альтернативный поиск (alternate lookup), позволяющий искать в `Dictionary<string,V>` по `ReadOnlySpan<char>` без аллокации строки:

```csharp
var d = new Dictionary<string, int>(StringComparer.Ordinal) { ["cat"] = 1 };
var lookup = d.GetAlternateLookup<ReadOnlySpan<char>>();

ReadOnlySpan<char> span = "the cat sat".AsSpan(4, 3);   // "cat", без аллокации
Console.WriteLine(lookup[span]);                         // 1
Console.WriteLine(lookup.ContainsKey(span));             // True
```

Работает только с компараторами, реализующими `IAlternateEqualityComparer<,>` — все `StringComparer.Ordinal*` реализуют. См. [[Span, ReadOnlySpan и Memory]].

## Практические паттерны

```csharp
// 1. TryGetValue вместо ContainsKey + индексатор — одно хеширование вместо двух
if (dict.TryGetValue(key, out var value))
    Use(value);

// 2. TryAdd — добавить, если ещё нет, без исключения и без предварительной проверки
if (!dict.TryAdd(key, value))
    Log.Warning("Дубликат ключа {Key}", key);

// 3. GetValueOrDefault — читаемая замена «есть или дефолт»
int qty = inventory.GetValueOrDefault(sku);          // 0, если нет
int qty2 = inventory.GetValueOrDefault(sku, 1);      // своё значение по умолчанию

// 4. Словарь-счётчик (без CollectionsMarshal — читаемо и достаточно быстро)
var freq = new Dictionary<char, int>();
foreach (char ch in text)
    freq[ch] = freq.GetValueOrDefault(ch) + 1;

// 5. Словарь списков (bucketing) — без двойного поиска
var byLen = new Dictionary<int, List<string>>();
foreach (var w in words)
{
    if (!byLen.TryGetValue(w.Length, out var list))
        byLen[w.Length] = list = new List<string>();
    list.Add(w);
}

// 6. Регистронезависимые строковые ключи — задаётся ТОЛЬКО компаратором
var headers = new Dictionary<string, string>(StringComparer.OrdinalIgnoreCase)
{
    ["Content-Type"] = "application/json"
};
Console.WriteLine(headers["CONTENT-TYPE"]);   // application/json

// 7. Быстрая дедупликация с сохранением порядка первого появления
var seen = new HashSet<string>(StringComparer.Ordinal);
var unique = words.Where(seen.Add).ToList();  // Add возвращает false для дубля

// 8. Построение словаря из последовательности
var byId = users.ToDictionary(u => u.Id);              // бросит на дубле Id
var lookup = users.ToLookup(u => u.DepartmentId);      // допускает дубли, см. Группировка
```

> [!warning] ToDictionary и дубликаты
> `ToDictionary` бросает `ArgumentException` при повторном ключе. Если дубли возможны — используйте `ToLookup` (много значений на ключ) или `GroupBy(...).ToDictionary(g => g.Key, g => g.First())`. См. [[Группировка, соединения, агрегация]].

## Сравнение хеш-коллекций

| Тип | Порядок | Поиск | Вставка | Потокобезопасность | Когда |
|---|---|---|---|---|---|
| `Dictionary<K,V>` | не гарантирован | O(1) | O(1) аморт. | нет | рабочая лошадка, 95 % случаев |
| `HashSet<T>` | не гарантирован | O(1) | O(1) аморт. | нет | множество, дедупликация, операции над множествами |
| `OrderedDictionary<K,V>` (.NET 9+) | порядок вставки, есть индексация | O(1) | O(1) аморт. | нет | нужен и порядок, и поиск по ключу |
| `SortedDictionary<K,V>` | по ключу | O(log n) | O(log n) | нет | нужен обход по возрастанию, частые вставки |
| `SortedList<K,V>` | по ключу | O(log n) | O(n) | нет | много чтений, редкие вставки, экономия памяти |
| `FrozenDictionary<K,V>` (.NET 8+) | не гарантирован | O(1), быстрее `Dictionary` | построение O(n log n), потом read-only | да (иммутабельна) | построили раз при старте — читаем миллионы раз |
| `ImmutableDictionary<K,V>` | не гарантирован | O(log n) | O(log n), возвращает новый экземпляр | да | нужна персистентная структура с историей версий |
| `ConcurrentDictionary<K,V>` | не гарантирован | O(1) | O(1) аморт. | да | несколько потоков пишут одновременно |

Детали — в [[Frozen и Immutable коллекции]] и [[Конкурентные коллекции]]. Выбор по ситуации — [[Шпаргалка — выбор коллекции]].

> [!info] FrozenDictionary — не «Dictionary, но быстрее»
> `FrozenDictionary.ToFrozenDictionary()` тратит существенное время на анализ ключей и подбор оптимальной стратегии (для строк — например, сравнение только по длине или по одному различающему символу). Выигрыш только на чтении, и только если чтений много. Один-два поиска — и `Dictionary` окажется быстрее суммарно.

> [!warning] Подводные камни
>
> **1. Мутабельный ключ.** Изменили поле, участвующее в `GetHashCode`, у объекта, лежащего в словаре — элемент стал недостижим по ключу (пример выше). Он не удалится, не найдётся, но будет виден в `Count` и `foreach`. Это одновременно баг и утечка памяти. Почему: бакет вычисляется при вставке и больше не пересчитывается; после изменения хеша поиск идёт в другой бакет. Лечится только иммутабельностью ключа.
>
> **2. Переопределили `Equals`, забыли `GetHashCode`.** Классика. `Equals` говорит «равны», а базовый `Object.GetHashCode` (основанный на идентичности ссылки) даёт разные хеши — два «равных» объекта уезжают в разные бакеты, и словарь спокойно принимает оба как разные ключи. Компилятор предупреждает (CS0659), но это warning, а не error. Для `record` и `record struct` компилятор генерирует и `Equals`, и `GetHashCode` согласованно — это лучший способ сделать ключ, см. [[Записи (record) и структуры]].
>
> **3. Struct-ключ без `IEquatable<T>`.** Если структура не реализует `IEquatable<TSelf>`, `EqualityComparer<T>.Default` откатывается к `ObjectEqualityComparer<T>`, который вызывает `Object.Equals(object)` — а это **упаковка обоих операндов на каждое сравнение**. Плюс базовый `ValueType.Equals` для структур с ссылочными полями идёт через рефлексию, что катастрофически медленно. Всегда реализуйте `IEquatable<T>` и переопределяйте `GetHashCode` у struct-ключей, либо используйте `record struct` (компилятор сделает это сам). Разбор — в [[Object: Equals, GetHashCode, ToString]].
>
> **4. Опора на порядок перечисления.** «У нас в тестах ключи всегда идут в порядке вставки» — до первого `Remove` или до обновления .NET. Порядок не является контрактом. Особенно опасно, когда порядок влияет на бизнес-результат (например, первый найденный обработчик) или когда результат сериализуется и сравнивается в тесте побайтово.
>
> **5. `_version` и модификация в `foreach`.** Энумератор запоминает `_version` и бросает `InvalidOperationException`, если словарь изменился структурно. Но в .NET Core присваивание **существующему** ключу через индексатор `_version` не увеличивает — поэтому код ниже работает, хотя в .NET Framework бросал. `Remove`, `Add`, `Clear` версию увеличивают, и `foreach` падает.
> ```csharp
> var d = new Dictionary<string, int> { ["a"] = 1, ["b"] = 2 };
> foreach (var k in d.Keys) d[k] = 0;         // работает в .NET Core/.NET 5+
> foreach (var k in d.Keys) d.Remove(k);      // InvalidOperationException
> ```
> Опираться на первое не стоит: это деталь реализации, а не документированная гарантия. Безопасный способ — сначала материализовать ключи: `foreach (var k in d.Keys.ToList()) ...`.
>
> **6. Плохой `GetHashCode` деградирует словарь до списка.** `public override int GetHashCode() => 0;` формально корректен (равные объекты дают равные хеши), но все элементы попадут в один бакет. Поиск станет O(n), вставка n элементов — O(n²). Так же плохо: `GetHashCode() => Id % 100` (сто бакетов на миллион записей) или `GetHashCode() => Name.Length`. Используйте `HashCode.Combine(...)` — он реализует качественный алгоритм xxHash-подобного смешивания.
> ```csharp
> public override int GetHashCode() => HashCode.Combine(FirstName, LastName, BirthDate);
>
> // Для переменного числа полей:
> var hc = new HashCode();
> foreach (var item in Items) hc.Add(item);
> return hc.ToHashCode();
> ```
>
> **7. Строковые ключи чувствительны к регистру по умолчанию.** `dict["Id"]` и `dict["id"]` — разные ключи. Это правильный дефолт (ordinal-сравнение, быстрое и предсказуемое), но источник багов при работе с HTTP-заголовками, именами конфигурации, кодами валют. Регистронезависимость задаётся **только** через компаратор в конструкторе — `new Dictionary<string,V>(StringComparer.OrdinalIgnoreCase)`. Нельзя добавить её потом. И не используйте `StringComparer.CurrentCultureIgnoreCase` для технических ключей: результат зависит от локали сервера (классика — турецкая «i»), см. [[Культура, локализация и форматирование]].
>
> **8. `ConcurrentDictionary` не делает атомарным то, что вы делаете с ним.** Смена `Dictionary` на `ConcurrentDictionary` защищает от порчи внутренней структуры, но `if (!d.ContainsKey(k)) d[k] = v;` остаётся гонкой. Нужны `GetOrAdd`/`AddOrUpdate`/`TryUpdate`. И даже фабрика в `GetOrAdd` может быть вызвана несколько раз.

> [!example] Как делают в бою
>
> **Кеш в памяти.** Для конфигурации, справочников и словарей маппинга, читаемых на каждый запрос: заполнили `Dictionary` при старте, дальше только читаем. Если объём фиксирован — переводим в `FrozenDictionary` и получаем 20–50 % на чтении бесплатно. Если данные обновляются целиком — держим поле `private volatile FrozenDictionary<...> _snapshot` и подменяем ссылку атомарно (copy-on-write), это дешевле любых блокировок.
>
> **Дедупликация в конвейере обработки.** `HashSet<string>` идемпотентности сообщений: перед обработкой `if (!processed.Add(messageId)) return;`. Один вызов вместо `Contains` + `Add`. Для длительно живущих процессов — с ограничением по размеру или окном по времени, иначе множество растёт вечно. См. [[Идемпотентность]].
>
> **Индекс для in-memory join.** Вместо `list1.Where(a => list2.Any(b => b.Id == a.Id))` (O(n·m)) строим `var index = list2.ToDictionary(b => b.Id)` и делаем O(n + m). На списках по 10 000 это разница между 100 миллионами сравнений и 20 тысячами.
>
> **Явная capacity в горячем коде.** Парсер, который на каждый запрос создаёт словарь из ~50 полей: `new Dictionary<string, object>(64, StringComparer.Ordinal)` вместо `new()`. Убирает 5–6 `Resize` на каждый запрос — это заметно на профиле аллокаций.
>
> **Ключи-`record`.** Составной ключ (например, `(TenantId, EntityType, EntityId)`) удобно делать `readonly record struct CacheKey(Guid TenantId, string Type, long Id)`. Компилятор сгенерирует согласованные `Equals`/`GetHashCode`, боксинга не будет (у `record struct` есть `IEquatable<T>`), а тип-обёртка защищает от путаницы аргументов. Кортеж `(Guid, string, long)` тоже работает: `ValueTuple` реализует `IEquatable` и комбинирует хеши.
>
> **Чего не делают.** Не пишут свою хеш-таблицу. Реализация в BCL за 20 лет собрала оптимизации (fastmod, devirtualization, защита от hash-flooding, аккуратный free-list), которые в самописном варианте не воспроизводятся. Исключение — узкоспециальные структуры вроде open-addressing таблицы с `int`-ключами в жёстко горячем цикле, и то после замеров.

## Вопросы с собеседований

> [!question]- Как устроен `Dictionary<TKey,TValue>` внутри?
> Два массива: `int[] _buckets` и `Entry[] _entries`, где `Entry` — структура с полями `hashCode`, `next`, `key`, `value`. При вставке считается хеш ключа, из него по модулю длины `_buckets` получается номер бакета. В бакете лежит индекс первого элемента цепочки, сдвинутый на `+1` (чтобы ноль означал «пусто»). Элементы, попавшие в один бакет, связаны в цепочку через поле `next`, где хранится индекс следующего элемента внутри того же `_entries`, а не ссылка на объект. Поиск: считаем хеш, находим бакет, идём по цепочке, сначала сравнивая сохранённые `hashCode` (дёшево), и только при совпадении вызываем `Equals`. Удалённые слоты попадают в список свободных через `_freeList`/`_freeCount` и переиспользуются при следующей вставке.

> [!question]- Почему размер массива бакетов — простое число, и что такое fastmod?
> Индекс бакета — это `hash % length`. Если `length` — степень двойки, остаток равен младшим битам хеша, и вся информация из старших битов теряется: любая арифметическая прогрессия в ключах с шагом, кратным `length`, схлопывается в один бакет. Простое число не имеет общих делителей с шагами в данных, поэтому даже посредственный `GetHashCode` распределяется приемлемо. Обратная сторона: остаток от деления на непростое-не-степень-двойки нельзя посчитать битовой маской, а инструкция `div` дорогая (десятки тактов). Поэтому .NET Core 3.0 добавил fastmod: множитель `ulong.MaxValue / divisor + 1` вычисляется один раз при `Resize` и хранится в `_fastModMultiplier`, а сам остаток считается двумя умножениями и сдвигами. Работает только на 64-битных платформах.

> [!question]- Что произойдёт, если изменить объект-ключ после того, как он положен в словарь?
> Если изменённое поле участвует в `GetHashCode`, элемент станет недостижимым по ключу. Бакет вычисляется один раз при вставке и больше не пересчитывается, поэтому `ContainsKey`, индексатор, `TryGetValue` и `Remove` пойдут искать в новый бакет и ничего не найдут — вернут `false`/бросят `KeyNotFoundException`. При этом сам элемент останется в `_entries`, будет учитываться в `Count` и появится при `foreach`. Это одновременно логическая ошибка и утечка памяти: удалить его нормальным способом уже нельзя, только через `Clear` или пересборку словаря. Отсюда правило: ключом делают иммутабельные типы — `string`, `int`, `Guid`, `readonly record struct`.

> [!question]- Почему `string.GetHashCode()` возвращает разные значения в разных запусках?
> Хеш строк в .NET Core рандомизирован: при старте процесса генерируется случайное зерно, участвующее в вычислении. Это защита от hash-flooding DoS — атаки, при которой злоумышленник подбирает набор строк с одинаковым бакетом и заставляет сервер деградировать в O(n²) на разборе запроса. Следствие: значение `GetHashCode()` нельзя персистить, сравнивать между процессами или использовать для шардирования; для стабильного хеша нужны `SHA256` или `XxHash3` из `System.IO.Hashing`. При этом ради скорости `Dictionary<string,V>` с дефолтным компаратором стартует на быстром нерандомизированном компараторе и переключается на рандомизированный автоматически, если в какой-то цепочке накопилось больше 100 коллизий.

> [!question]- Гарантирован ли порядок перечисления `Dictionary`?
> Нет, и это не «на практике совпадает» — это отсутствие контракта. На практике до первого удаления порядок совпадает с порядком вставки, потому что элементы кладутся подряд в `_entries`, а энумератор идёт по этому массиву линейно. Но `Remove` помещает освободившийся слот в free-list, и следующий `Add` займёт слот в середине массива — порядок сломается. Плюс реализация может измениться между версиями .NET, как уже было при переходе с .NET Framework на .NET Core. Если порядок нужен: `OrderedDictionary<TKey,TValue>` из .NET 9, `List<KeyValuePair<K,V>>`, `SortedDictionary` для порядка по ключу или явный `OrderBy` на месте вывода.

> [!question]- Чем `TryGetValue` лучше `ContainsKey` + индексатор?
> Числом хеширований и обходов цепочки. `ContainsKey(k)` — это полный поиск, и следующий `dict[k]` — ещё один полный поиск: два вызова `GetHashCode` и два обхода цепочки со сравнениями. `TryGetValue` делает один поиск и отдаёт значение через `out`. Для дешёвых `int`-ключей разница небольшая, для строковых ключей и длинных цепочек — существенная. Аналогичные однопроходные варианты: `TryAdd` вместо `ContainsKey` + `Add`, `GetValueOrDefault` вместо `ContainsKey` + чтения, и `CollectionsMarshal.GetValueRefOrAddDefault` для паттерна «прочитать-изменить-записать» — он отдаёт `ref` прямо на поле `value` в `Entry`, то есть один поиск вместо трёх.

> [!question]- Что дороже: `Dictionary<int,V>` с кастомным компаратором или без него, и почему?
> С кастомным — дороже. Конструктор `Dictionary` для значимых типов заполняет поле `_comparer` только если компаратор действительно нестандартный; если он `null` или равен `EqualityComparer<TKey>.Default`, поле остаётся `null`. На горячем пути есть ветка `if (_comparer is null)`, внутри которой вызывается `EqualityComparer<TKey>.Default.Equals` — при специализации дженерика по значимому типу JIT девиртуализует и инлайнит этот вызов в обычное сравнение `int`-ов, без единого `call`. Передача любого компаратора уводит выполнение во вторую ветку с виртуальным вызовом через интерфейс: инлайна нет, есть косвенный переход. Для ссылочных типов такой асимметрии нет — там компаратор в поле хранится всегда, потому что доступ к `EqualityComparer<TKey>.Default` через shared generics сам стоит дороже виртуального вызова.

> [!question]- Чем `HashSet<T>` отличается от `Dictionary<T, bool>`?
> Устройством и стоимостью. `HashSet<T>` — та же хеш-таблица, но в `Entry` нет поля `value`: только `HashCode`, `Next` и `Value` (сам элемент). `Dictionary<T,bool>` тратит дополнительный байт плюс выравнивание на каждый элемент и требует писать бессмысленный `true` при каждой вставке. Кроме памяти, `HashSet` даёт нормальный API множеств: `UnionWith`, `IntersectWith`, `ExceptWith`, `SymmetricExceptWith`, `IsSubsetOf`, `Overlaps`, `SetEquals`, а также идиоматичный `Add`, возвращающий `false` для уже существующего элемента, — это делает дедупликацию однострочником `items.Where(seen.Add)`. Отдельно полезен `TryGetValue(equalValue, out actualValue)`, позволяющий достать именно тот экземпляр, который лежит в множестве.

## Задачи

### Задача 1. Найти пару чисел с заданной суммой

Дан массив `int[]` и целевое значение `target`. Верните индексы двух элементов, сумма которых равна `target`, или `null`. Решение должно работать за O(n), один проход.

> [!success]- Решение
> ```csharp
> static (int, int)? TwoSum(int[] nums, int target)
> {
>     // значение → его индекс. Capacity задаём заранее, чтобы избежать Resize.
>     var seen = new Dictionary<int, int>(nums.Length);
>
>     for (int i = 0; i < nums.Length; i++)
>     {
>         int need = target - nums[i];
>         if (seen.TryGetValue(need, out int j))
>             return (j, i);          // дополнение уже встречалось
>
>         seen[nums[i]] = i;          // TryAdd, если нужен первый индекс при дублях
>     }
>     return null;
> }
>
> Console.WriteLine(TwoSum([2, 7, 11, 15], 9));    // (0, 1)
> Console.WriteLine(TwoSum([3, 3], 6));            // (0, 1)
> Console.WriteLine(TwoSum([1, 2], 100));          // (пусто)
> ```
> Идея: вместо проверки всех пар (O(n²)) мы на каждом шаге спрашиваем словарь, встречалось ли уже нужное дополнение. Один проход, O(n) времени и O(n) памяти. Записываем элемент **после** проверки — иначе при `target = 2 * nums[i]` элемент найдёт сам себя. `TryGetValue` вместо `ContainsKey` + индексатора экономит второе хеширование.

### Задача 2. Группировка анаграмм

Дан массив строк. Сгруппируйте слова, являющиеся анаграммами друг друга (состоят из одних букв). Порядок групп не важен.

> [!success]- Решение
> ```csharp
> static List<List<string>> GroupAnagrams(string[] words)
> {
>     var groups = new Dictionary<string, List<string>>(words.Length, StringComparer.Ordinal);
>
>     foreach (string w in words)
>     {
>         // Канонический ключ: отсортированные символы.
>         // "eat" и "tea" дают одинаковый "aet".
>         char[] chars = w.ToCharArray();
>         Array.Sort(chars);
>         string key = new string(chars);
>
>         if (!groups.TryGetValue(key, out var bucket))
>             groups[key] = bucket = new List<string>();
>
>         bucket.Add(w);
>     }
>
>     return groups.Values.ToList();
> }
>
> var r = GroupAnagrams(["eat", "tea", "tan", "ate", "nat", "bat"]);
> foreach (var g in r) Console.WriteLine(string.Join(",", g));
> // eat,tea,ate
> // tan,nat
> // bat
> ```
> Суть приёма — **канонизация ключа**: свести все эквивалентные варианты к одному представлению, по которому хеш-таблица их склеит. Сложность O(n · k log k), где k — длина слова. Обратите внимание на `if (!TryGetValue(...)) groups[key] = bucket = new List<string>();` — это один поиск на проверку и один на вставку вместо трёх при наивном `ContainsKey`/индексатор/индексатор. Порядок групп в результате опирался бы на порядок перечисления `Values`, поэтому в условии он объявлен неважным.

### Задача 3. Сломанный ключ

Объясните, почему следующий код печатает `False`, и исправьте класс так, чтобы он был корректным ключом словаря.

```csharp
public class Money
{
    public decimal Amount { get; init; }
    public string Currency { get; init; } = "USD";
    public override bool Equals(object? o) =>
        o is Money m && m.Amount == Amount && m.Currency == Currency;
}

var d = new Dictionary<Money, string>();
d[new Money { Amount = 10m, Currency = "EUR" }] = "десять евро";
Console.WriteLine(d.ContainsKey(new Money { Amount = 10m, Currency = "EUR" }));
```

> [!success]- Решение
> Переопределён `Equals`, но не `GetHashCode`. Наследуется `Object.GetHashCode`, основанный на идентичности ссылки, поэтому два логически равных экземпляра дают разные хеши и попадают в разные бакеты. Поиск во втором бакете `Equals` даже не вызовет. Компилятор предупреждает (CS0659 «overrides Object.Equals but does not override Object.GetHashCode»), но это warning.
>
> ```csharp
> // Правильно: согласованные Equals/GetHashCode + IEquatable<T> против боксинга
> public sealed class Money : IEquatable<Money>
> {
>     public decimal Amount { get; init; }
>     public string Currency { get; init; } = "USD";
>
>     public bool Equals(Money? other) =>
>         other is not null && other.Amount == Amount &&
>         string.Equals(other.Currency, Currency, StringComparison.Ordinal);
>
>     public override bool Equals(object? o) => Equals(o as Money);
>
>     // Те же поля, что в Equals, — и только они
>     public override int GetHashCode() => HashCode.Combine(Amount, Currency);
> }
> ```
>
> Но в реальном коде это пишут короче — компилятор генерирует всё сам и согласованно:
>
> ```csharp
> public readonly record struct Money(decimal Amount, string Currency);
>
> var d = new Dictionary<Money, string>();
> d[new Money(10m, "EUR")] = "десять евро";
> Console.WriteLine(d.ContainsKey(new Money(10m, "EUR")));   // True
> ```
>
> `readonly record struct` даёт иммутабельность (ключ нельзя испортить), `IEquatable<Money>` (сравнение без боксинга и с devirtualization) и корректный `GetHashCode` из всех полей. Единственная тонкость: сгенерированное сравнение строк — ordinal через `EqualityComparer<string>.Default`, что для кода валюты именно то, что нужно.

### Задача 4. LRU-кеш на O(1)

Реализуйте кеш фиксированной ёмкости с операциями `Get(key)` и `Put(key, value)` за O(1). При переполнении вытесняется элемент, к которому дольше всего не обращались.

> [!success]- Решение
> ```csharp
> public sealed class LruCache<TKey, TValue> where TKey : notnull
> {
>     private readonly int _capacity;
>     // Список хранит порядок использования: голова — самый свежий, хвост — самый старый.
>     private readonly LinkedList<(TKey Key, TValue Value)> _order = new();
>     // Словарь даёт O(1) доступ к УЗЛУ списка, а не к значению.
>     private readonly Dictionary<TKey, LinkedListNode<(TKey, TValue)>> _map;
>
>     public LruCache(int capacity)
>     {
>         if (capacity <= 0) throw new ArgumentOutOfRangeException(nameof(capacity));
>         _capacity = capacity;
>         _map = new Dictionary<TKey, LinkedListNode<(TKey, TValue)>>(capacity);
>     }
>
>     public int Count => _map.Count;
>
>     public bool TryGet(TKey key, out TValue value)
>     {
>         if (!_map.TryGetValue(key, out var node))
>         {
>             value = default!;
>             return false;
>         }
>         _order.Remove(node);          // O(1): узел на руках, поиска нет
>         _order.AddFirst(node);        // O(1): переиспользуем тот же узел
>         value = node.Value.Value;
>         return true;
>     }
>
>     public void Put(TKey key, TValue value)
>     {
>         if (_map.TryGetValue(key, out var existing))
>         {
>             existing.Value = (key, value);   // Value узла — обычное поле, можно писать
>             _order.Remove(existing);
>             _order.AddFirst(existing);
>             return;
>         }
>
>         if (_map.Count == _capacity)
>         {
>             var oldest = _order.Last!;       // O(1): LinkedList двусвязный
>             _order.RemoveLast();
>             _map.Remove(oldest.Value.Key);   // поэтому ключ и лежит в узле
>         }
>
>         _map[key] = _order.AddFirst((key, value));
>     }
> }
>
> var cache = new LruCache<string, int>(2);
> cache.Put("a", 1);
> cache.Put("b", 2);
> cache.TryGet("a", out _);      // "a" стал свежим, вытеснится "b"
> cache.Put("c", 3);
> Console.WriteLine(cache.TryGet("b", out _));   // False — вытеснен
> Console.WriteLine(cache.TryGet("a", out _));   // True
> ```
> Ключевая идея: ни одна структура не даёт O(1) и на поиск по ключу, и на «переместить в начало». Комбинируем две. Словарь хранит не значение, а **ссылку на узел** `LinkedListNode`, потому что `LinkedList.Remove(node)` — O(1), а `LinkedList.Remove(value)` — O(n) с линейным поиском. Ключ дублируется внутри узла, чтобы при вытеснении хвоста знать, что удалять из словаря. Ёмкость словаря задана в конструкторе — `Resize` не случится никогда. Разбор `LinkedList<T>` — в [[List, массивы, LinkedList]]; в проде для этой задачи берут `MemoryCache` или `HybridCache`.

## Итог

- `Dictionary<TKey,TValue>` — хеш-таблица с цепочками, которые живут внутри массива `Entry[]` и связаны индексами (`next`), а не ссылками. Два объекта в куче на любое количество элементов: отличная локальность, минимум работы для GC.
- `_buckets` хранит `index + 1`, чтобы естественный ноль занулённого массива означал «пусто». `hashCode` кешируется в `Entry`, поэтому сравнение начинается с дешёвого целочисленного и `Resize` не вызывает `GetHashCode` заново.
- Размер `_buckets` — простое число из таблицы `HashHelpers.primes`: это гасит кластеризацию плохих хешей. Дорогое деление заменено fastmod-умножением на 64-битных платформах.
- Вся корректность держится на контракте `GetHashCode`/`Equals`. Мутабельный ключ, `Equals` без `GetHashCode`, struct без `IEquatable<T>` или константный хеш — четыре способа получить баг или деградацию до O(n).
- Порядок перечисления не гарантирован: `Remove` создаёт free-list, и следующая вставка садится в середину массива. Нужен порядок — `OrderedDictionary<K,V>` (.NET 9+) или `List<KeyValuePair<K,V>>`.
- `HashSet<T>` — тот же движок без `value`, плюс полноценные операции над множествами. `Dictionary<T,bool>` вместо него — лишняя память и лишний код.
- Однопроходные API: `TryGetValue`, `TryAdd`, `GetValueOrDefault`, `CollectionsMarshal.GetValueRefOrAddDefault`. Двойное хеширование через `ContainsKey` + индексатор — самая частая мелкая неэффективность в реальном коде.
