# Конкурентные коллекции

> [!abstract] Коротко
> Обычные коллекции (`List<T>`, `Dictionary<K,V>`) не потокобезопасны вообще — параллельная запись может не просто дать неверный результат, а физически повредить внутреннюю структуру и уронить процесс. `System.Collections.Concurrent` даёт набор коллекций, спроектированных для конкурентного доступа без внешней блокировки: `ConcurrentDictionary`, `ConcurrentQueue`, `ConcurrentBag`, `BlockingCollection`.

## Зачем это знать

Оборачивание обычного `Dictionary` в `lock` работает, но убивает параллелизм — весь доступ сериализуется через одну блокировку. Конкурентные коллекции используют более тонкую гранулярность (сегментированные блокировки, lock-free алгоритмы через `Interlocked`), поэтому дают реальный выигрыш там, где к структуре обращаются из нескольких потоков одновременно и часто.

## Модель

| Коллекция | Механизм | Для чего |
|---|---|---|
| `ConcurrentDictionary<K,V>` | сегментированные блокировки (несколько блокировок на разные части таблицы) | кеш, счётчики по ключу, разделяемая map |
| `ConcurrentQueue<T>` | lock-free (Interlocked-based) | FIFO-очередь между потоками |
| `ConcurrentStack<T>` | lock-free | LIFO-очередь между потоками |
| `ConcurrentBag<T>` | thread-local хранилище + кража работы | когда порядок не важен, а важна скорость добавления/извлечения из своего же потока |
| `BlockingCollection<T>` | обёртка над `IProducerConsumerCollection<T>` с блокирующим `Take` | классический producer-consumer до появления `Channel<T>` |

`ConcurrentDictionary` — самая частая в вебе. Ключевое отличие от `Dictionary` под `lock`: методы вроде `GetOrAdd`/`AddOrUpdate` атомарны как единая операция, но переданная в них лямбда может быть вызвана несколько раз при конкуренции — это не побочный эффект, а особенность реализации, и код внутри лямбды обязан быть чистым (без побочных эффектов), иначе будет выполнен лишний раз незаметно.

```csharp
// Ловушка: лямбда с побочным эффектом в GetOrAdd
var counter = _cache.GetOrAdd(key, _ =>
{
    _metrics.Increment("cache_miss"); // может вызваться дважды при гонке
    return LoadValue(key);
});
```

## Решения

| Задача | Что выбрать | Почему не альтернатива |
|---|---|---|
| Кеш в памяти с частым конкурентным чтением/записью | `ConcurrentDictionary` | `Dictionary` + `lock` сериализует весь доступ |
| Очередь задач между producer и consumer с ожиданием | `Channel<T>` (см. [[Parallel, PLINQ и параллелизм данных]]) | современнее `BlockingCollection`, поддерживает async нативно |
| Разовое построение словаря, потом только чтение из многих потоков | `FrozenDictionary` (упомянут в [[Обзор коллекций .NET и как выбирать]]) | конкурентная запись не нужна вообще — читай неизменяемую структуру |
| Редкая конкуренция, простая логика | обычная коллекция + `lock` | конкурентные коллекции сложнее в отладке, оправданы только при реальной нагрузке |

## В ServiceShop

Кеш соответствий или счётчики внутри одного процесса (не путать с распределённым кешем Redis, который отвечает за состояние между инстансами) — типичное место для `ConcurrentDictionary`: пока не подтверждено профилированием, что это горячий путь, простой `lock` вокруг `Dictionary` предпочтительнее — он проще для ревью и достаточен при низкой конкуренции.

## Где ошибаются

> [!warning] Подводные камни
> - **Совокупность операций не атомарна.** `if (!dict.ContainsKey(k)) dict[k] = v;` на `ConcurrentDictionary` — гонка: между проверкой и записью другой поток может вставить значение. Правильно — `TryAdd`/`GetOrAdd` как единая операция.
> - **Побочные эффекты в фабричной лямбде.** `GetOrAdd`/`AddOrUpdate` могут вызвать переданную функцию несколько раз при конкурентной вставке — лямбда не должна иметь наблюдаемых побочных эффектов.
> - **`Count` не бесплатен.** У `ConcurrentDictionary` подсчёт элементов сложнее, чем у обычного словаря — не вызывай в горячем цикле без необходимости.
> - **Агент часто:** оборачивает `ConcurrentDictionary` в дополнительный `lock` «на всякий случай» — это не ошибка компиляции, но сводит на нет смысл конкурентной коллекции и возвращает сериализованный доступ.

## Проверка на ревью

- Конкурентная коллекция выбрана осознанно — есть реальная многопоточная нагрузка, а не «на будущее».
- Составные операции (проверка + запись) выполнены атомарным методом (`GetOrAdd`, `TryAdd`, `AddOrUpdate`), а не последовательностью из двух вызовов.
- Фабричные лямбды в `GetOrAdd`/`AddOrUpdate` не содержат побочных эффектов.
- Нет лишней синхронизации (`lock`) поверх уже потокобезопасной коллекции.

## Проверь себя

> [!question]- Почему `if (!dict.ContainsKey(k)) dict[k] = v;` небезопасен на `ConcurrentDictionary`, если сама коллекция потокобезопасна?
> Потокобезопасность гарантирует целостность каждой отдельной операции (`ContainsKey`, индексатор), но не атомарность последовательности из двух операций. Между проверкой и записью другой поток может успеть вставить значение под тем же ключом — итоговая гонка данных ничем не отличается от гонки на обычном `Dictionary`, просто не роняет процесс.

> [!question]- Почему лямбда в `GetOrAdd` может выполниться больше одного раза?
> При конкурентном вызове `GetOrAdd` с одним и тем же отсутствующим ключом несколько потоков могут одновременно решить, что значения ещё нет, и начать вычислять его через переданную фабрику — побеждает только один результат, но фабрика могла быть вызвана у нескольких потоков. Поэтому фабрика обязана быть чистой функцией без побочных эффектов.

## Разбор

### Разбор 1. Найди гонку

```csharp
private readonly ConcurrentDictionary<string, int> _hits = new();

public void RegisterHit(string key)
{
    if (_hits.ContainsKey(key))
        _hits[key] = _hits[key] + 1;
    else
        _hits[key] = 1;
}
```

Найди гонку и перепиши без неё.

> [!success]- Разбор
> Между `ContainsKey`, чтением значения и записью — три отдельные неатомарные операции; при конкурентных вызовах инкременты могут потеряться. Правильная версия использует одну атомарную операцию: `_hits.AddOrUpdate(key, addValue: 1, updateValueFactory: (_, old) => old + 1);`.

## Итог

- Обычные коллекции не потокобезопасны вообще; конкурентные коллекции дают более тонкую гранулярность, чем `lock` вокруг всей структуры
- `ConcurrentDictionary` — основной рабочий инструмент для конкурентного кеша, `Channel<T>` — для producer-consumer с async
- Составные операции нужно выполнять атомарными методами, а не последовательностью из проверки и записи
- Фабричные лямбды в `GetOrAdd`/`AddOrUpdate` обязаны быть чистыми — могут быть вызваны несколько раз при конкуренции
