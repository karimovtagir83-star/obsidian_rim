# ServiceShop: данные, миграции и тесты

> [!abstract] Коротко
> Три вещи, которые отличают этот проект от типового ASP.NET Core-приложения. **Первая**: хранилищ несколько — MySQL у всех модулей (со своей схемой у каждого), MongoDB у корзины, Redis для кеша и сессий. **Вторая**: миграции делает FluentMigrator, а не EF Migrations, и таймстемп в имени файла критичен для команды — поэтому руками их не пишут. **Третья**: архитектурные правила проверяются автотестами через рефлексию, а не соглашениями — сборка падает раньше ревью.

## Зачем это нужно

Архитектура, описанная в остальных заметках раздела, держится не на дисциплине разработчиков. Дисциплина заканчивается на первом дедлайне. Держится она на трёх механизмах принуждения:

1. **Границы проектов** — компилятор не даёт увидеть чужой код.
2. **Отдельные контейнеры и строки подключения** — рантайм не даёт получить чужой сервис или чужую таблицу.
3. **ArchTests** — тесты не дают нарушить то, что первые два механизма не покрывают.

Плюс отдельная тема — миграции: там принуждение обеспечено не тестом, а инструментом, потому что сломанный порядок миграций тест не поймает, а команду остановит.

## Хранилища

| Что | Где | Зачем именно оно |
|---|---|---|
| **MySQL 8** | все модули, **своя схема у каждого** | основное хранилище; запись через EF Core, чтение через Dapper |
| **MongoDB** | **только Cart** | корзина — документ переменной формы, читается и пишется целиком |
| **Redis** | кеш, DataProtection keys, сессии корзины | [[Redis и стратегии кеширования]] |
| **MinIO** | изображения и файлы | S3-совместимое объектное хранилище |
| **Firebase** | пуш-уведомления | |

Строки подключения, объявленные в `Startup.cs`, показывают устройство целиком:

```csharp
CatalogConnectionString, ModerationConnectionString, OrdersConnectionString,
CartConnectionString, MarketingConnectionString,
CartMongoDbConnectionString,
CatalogRedisConnectionString, CatalogReadReplicaConnectionString,
MarketingRedisConnectionString
```

Три вывода из этого списка:

- **Схема на модуль** — модуль не может прочитать чужие таблицы даже SQL-запросом: у него нет соединения к их схеме. Изоляция держится на уровне БД, а не только кода.
- **`CatalogReadReplicaConnectionString`** — у каталога есть read-реплика: тяжёлые запросы витрины уходят на неё, не мешая записи. Плата — репликационное отставание: только что записанное может ещё не читаться из реплики.
- **Свой Redis у каталога и маркетинга** — разные профили нагрузки, чтобы вытеснение кеша в одном не било по другому.

### Почему у корзины MongoDB

Корзина — единственный агрегат в системе, который **всегда читается и пишется целиком**: показать корзину, добавить товар, пересчитать, очистить. Частичных обновлений отдельных позиций через сложные запросы почти нет.

Такой доступ идеально подходит документной БД: один документ = одна корзина, чтение — один запрос без джойнов, запись — замена документа. В реляционной схеме та же корзина — это `carts` + `cart_items` + `moderated_cart_items` + вложенные объекты (`Store`, `LoanCondition`, `PurchaseRestrictions`, `BnplDetails`, `ItemImage`), и каждое чтение — джойн на 5–6 таблиц.

Второй аргумент — **схема меняется часто**. У позиции корзины десятки полей, скопированных из каталога (цена, старая цена, картинки, условия рассрочки, ограничения покупки), и они добавляются под каждую новую фичу. В Mongo это не требует миграции. Про выбор — [[NoSQL: когда и зачем]].

Цена решения видна прямо в домене:

```csharp
public class Cart : Entity, IAggregateRoot
{
    [BsonId]
    [BsonRepresentation(BsonType.ObjectId)]
    public string? Id { get; private set; }

    [BsonElement("CartItems")]
    public IReadOnlyCollection<CartItem> CartItems => _cartItems;

    [BsonConstructor]
    public Cart(string id, Buyer buyer, ...) : this(buyer) { ... }
}
```

Инфраструктурные атрибуты в доменном классе и публичный конструктор ради драйвера — отступление от правила «домен не знает о хранилище». Пошли на это ради простоты маппинга; ArchTest на приватные конструкторы содержит для `Cart` явное исключение по атрибуту `BsonConstructorAttribute`.

> [!info] Служебные таблицы Cart всё равно в MySQL
> `outbox_messages`, `inbox_messages`, `internal_commands` у модуля Cart живут в MySQL, а не в Mongo. Причина принципиальная: Outbox требует **транзакционной** записи вместе с бизнес-данными, а транзакция здесь охватывает MySQL. Получается, что у модуля Cart сам агрегат и его Outbox лежат в разных базах — то есть атомарность «данные + событие», ради которой Outbox и существует, для Cart не гарантирована в полном объёме. Знать об этом стоит: это известная слабость, а не то, как надо делать.

### Запись и чтение

**Запись** — EF Core 8 + Pomelo.MySql через `<M>Context`. Change tracking, коммит через `UnitOfWork` ([[EF Core: change tracking и AsNoTracking]]).

**Чтение** — Dapper через `ISqlConnectionFactory`, сырой SQL прямо в ViewModel ([[Dapper: когда микро-ORM лучше]]).

Кастомные типы, которые Dapper сам не умеет, регистрируются в `Startup.cs` — около двадцати `SqlMapper.AddTypeHandler(...)`:

```csharp
SqlMapper.AddTypeHandler(new MultiLangTypeHandler());        // мультиязычная строка в JSON-колонке
SqlMapper.AddTypeHandler(new ImagePathsTypeHandler());       // пути к изображениям
SqlMapper.AddTypeHandler(new DiffTypeHandler<string>());     // diff-значение для аудита
SqlMapper.AddTypeHandler(new ListTypeHandler<Guid>());       // список в JSON-колонке
```

`MultiLang` — многоязычные тексты (названия товаров на трёх языках) в одной JSON-колонке вместо трёх колонок или таблицы переводов. Прагматично; цена — по такому полю нельзя нормально индексировать и фильтровать средствами SQL.

## Миграции

> [!danger] Никогда не создавай миграцию руками
> В проекте есть скилл `create-migration` — он ставит таймстемп по реальным часам и правильно именует файл и класс. Вручную написанная миграция получает выдуманный таймстемп, и порядок накатки у остальных разработчиков ломается: у них миграция с меньшим номером применится **после** уже накатанной с большим, или не применится вовсе.
> Правило действует на любое изменение схемы: новая таблица, новая колонка, удаление колонки, смена типа или nullability, переименование, индекс, уникальное ограничение, внешний ключ. Даже если это один шаг внутри большой задачи.

### FluentMigrator, а не EF Migrations

| | EF Migrations | FluentMigrator (здесь) |
|---|---|---|
| Кто создаёт | генерирует из модели (`dotnet ef migrations add`) | человек пишет явно |
| Порядок | по таймстемпу в имени | по числу в `[Migration(...)]` + имя файла |
| Связь с моделью | сравнивает модель и снапшот | связи нет вовсе |
| Откат | генерируется автоматически | пишется руками в `Down()` |

Почему выбран FluentMigrator при том, что EF Core в проекте есть:

- **Полный контроль над DDL.** Автогенерация EF на живой базе умеет предлагать деструктивные шаги (пересоздать таблицу, потерять данные). На проде с историей это неприемлемо.
- **Не вся схема описана моделями EF.** Служебные таблицы (`outbox_messages`, `inbox_messages`, `internal_commands`), индексы под конкретные запросы, схема модуля Cart в MySQL — EF-модели для них нет.
- **Модули имеют раздельные схемы** — снапшот модели EF на модуль работал бы, но FluentMigrator проще: миграции просто лежат в папке модуля.

Общий разбор темы — [[EF Core: миграции]].

### Формат

Эталон с подробным русским руководством прямо в комментариях — `Orders.Infrastructure/Migrations/2024_01_01_000001_create_examples_table.cs`. Его стоит прочитать до первой своей миграции целиком.

Имя файла: `YYYY_MM_DD_HHMMSS_описание_snake_case.cs`
Число в атрибуте: `[Migration(2024_01_01_000001)]` — **обязано совпадать** с таймстемпом в имени.

Конвенция имён класса: `[Глагол][Что][Предлог][Таблица]Table`

| Глагол | Когда | Пример |
|---|---|---|
| `Create` | новая таблица | `CreateUsersTable` |
| `Add` | колонка, индекс, FK | `AddDeletedAtColumnToUsersTable` |
| `Remove` | удаление | `RemoveLegacyStatusColumnFromOrdersTable` |
| `Alter` / `Change` | тип или свойства колонки | `AlterPriceColumnInProductsTable` |

Накатываются миграции при старте модуля — `FluentMigrationStartup.Initialize(...)` в `<M>Startup.Initialize`. То есть **деплой приложения = накатка миграций**, отдельного шага нет. Отсюда требование: миграция должна быть совместима с предыдущей версией кода, потому что во время rolling update в Kubernetes старые и новые поды работают одновременно на уже изменённой схеме.

> [!warning] Практическое следствие для несовместимых изменений
> Удалить колонку одной миграцией нельзя: старые поды, ещё живые в момент накатки, продолжат её читать и упадут. Такие изменения делаются в две-три стадии, разнесённые по релизам: сначала перестать писать, потом перестать читать, и только следующим релизом удалить. Это общее правило zero-downtime-миграций, и здесь оно обязательно, потому что миграции накатываются самим приложением.

## ArchTests: архитектура под автотестами

`ArchTests/` — обычные xUnit-тесты, которые через рефлексию и библиотеку **NetArchTest** проверяют структуру кода. Тринадцать проверок, и это самая недооценённая часть проекта.

### Правила домена

**`OnlyPrivateConstructorsTest`** — у агрегатов нет публичных конструкторов:

```csharp
var aggregateRoots = Types.InAssembly(domainAssembly)
    .That().ImplementInterface(typeof(IAggregateRoot))
    .GetTypes();

foreach (var aggregate in aggregateRoots)
{
    var constructors = aggregate.GetConstructors(BindingFlags.Public | BindingFlags.Instance);

    Assert.True(!constructors.Any(),
        $"Агрегат {aggregate.Name} должен иметь приватный конструктор");
}
```

Видно, зачем нужен пустой маркерный интерфейс `IAggregateRoot`: по нему находятся все агрегаты в сборке. Для `Cart` есть отдельная перегрузка теста с исключением по `BsonConstructorAttribute`.

**`CreatedThroughFactoryMethodOnlyTest`** — агрегат создаётся только фабричным методом.
**`NoApplicationLayerDependenciesTest`** — `Domain` не зависит от `Application`. Правило зависимостей ([[Clean Architecture]]) под тестом.
**`ConstructorParamsSameAsDomainEventTests`** — параметры конструктора доменного события совпадают с самим событием.

### Правила слоя приложения

**`CommandHandlersShouldImplementsICommandHandlerInterface`** — конвенция имён и интерфейсов.

**`QueryHandlersShouldNotInjectDomainRepositoriesTest`** — запросы читают через Dapper, не через доменные репозитории. Здесь самое интересное — как работают с унаследованными нарушениями:

```csharp
/// <summary>Query handlers must read via Dapper, not domain repositories.</summary>
public class QueryHandlersShouldNotInjectDomainRepositoriesTest : ApplicationTestBase
{
    // Pre-existing violations. Don't add new ones — migrate to Dapper and remove the entry.
    private static readonly HashSet<string> KnownExemptions = new(StringComparer.Ordinal)
    {
        "Alif.ServiceShop.Modules.Cart.Application.Queries.Cart.ViewCartQueryHandler",
        // ...около 20 записей
    };
```

Это **правильный способ вводить правило в живой проект**: включить сразу, зафиксировать существующие нарушения списком, запретить пополнять список. Новый код правило соблюдает с первого дня, старый чинится постепенно, и объём долга виден числом строк в `HashSet`. Альтернатива «сначала всё почистим, потом включим» не срабатывает никогда.

Про технический долг в такой форме — [[Технический долг: как говорить о нём с бизнесом]].

### Правила API

| Тест | Что проверяет |
|---|---|
| `MustExtendBaseControllerTest` | все контроллеры наследуют `BaseController` |
| `MustHaveApiControllerAttributesTest` | наличие `[ApiController]` и прочих атрибутов |
| `ShouldInjectOnlyInterfacesTest` | контроллер инжектит только интерфейсы, не конкретные классы |
| `IsolatedFromOtherControllersTest` | контроллер не зависит от другого контроллера |
| `AdminControllersShouldHaveHasPermissionAttributeTest` | админский эндпоинт не может остаться без проверки прав |
| `APILevelDependenciesTest` | API не ссылается на внутренности модулей |
| `ApiClientsMustInheritBaseApiClientTest` | HTTP-клиенты наследуют базовый |

`AdminControllersShouldHaveHasPermissionAttributeTest` — тест, закрывающий **уязвимость**, а не стиль. Забытый атрибут прав на админском эндпоинте — это открытая наружу админская функция. Человек на ревью такое пропускает легко, тест — никогда. Про класс проблемы — [[OWASP Top 10 для .NET]].

```bash
dotnet test ArchTests/
```

Запускать после любого структурного изменения.

> [!tip] Почему это ценнее ревью
> Ревью ловит нарушения выборочно, зависит от внимательности и загруженности ревьюера. Тест ловит все и всегда, а сообщение теста ещё и объясняет правило (`"Агрегат {Name} должен иметь приватный конструктор"`) — то есть работает как документация в момент, когда она нужна. Правило, зафиксированное только в вики, соблюдается ровно до первого срочного релиза; правило, зафиксированное тестом, не нарушается вообще.
> Это приём, который стоит унести в любой проект: одно архитектурное соглашение — один тест на 20 строк.

## Тесты остального

| Тип | Проект | Что покрывает |
|---|---|---|
| **Domain.UnitTests** | `<M>.Domain.UnitTests` | агрегаты и бизнес-правила, без БД, миллисекунды |
| **Application.UnitTests** | `<M>.Application.UnitTests` | хендлеры с замоканными зависимостями |
| **IntegrationTests** | только `Marketing.Application.IntegrationTests` | сценарии с реальной инфраструктурой |
| **ArchTests** | `ArchTests` | структура кода |

Инструменты: xUnit ([[xUnit: основы]]), FluentAssertions, NSubstitute и Moq ([[Моки: NSubstitute и Moq]]).

Основная масса тестов — доменные. Это прямое следствие DDD: правила изолированы в классах без зависимостей, поэтому тест на правило — три строки и никакого поднятия инфраструктуры. Именно за это платили сложностью архитектуры, и здесь возврат вложений виден лучше всего.

Структура тестовых папок повторяет структуру домена: `Orders.Domain.UnitTests/Order/`, `OrderItemTests/`, `Purchases/`, `PartnerCloneTests/`.

> [!info] Почему интеграционных тестов почти нет
> Модуль собирает контейнер в **статическом** поле (`<M>CompositionRoot._container`). Два теста, инициализирующих модуль по-разному в одном процессе, дерутся за это поле, а xUnit по умолчанию запускает коллекции параллельно. Отсюда и единственный проект интеграционных тестов.
> Правильное лечение — Testcontainers плюс отказ от статического контейнера в пользу инстанса на тест ([[Testcontainers]]). Это заметный рефакторинг инициализации модулей, поэтому пока живут с юнит-тестами. Знать причину полезно: это не «не написали тесты», а архитектурное ограничение, которое надо снимать осознанно.

### Фабрики тестовых объектов

В агрегатах встречаются публичные статические методы `Fake(...)`:

```csharp
public static Cart Fake(
    string? id = null,
    Buyer? buyer = null,
    List<CartItem>? cartItems = null,
    List<ModeratedCartItem>? moderatedCartItems = null,
    DateTime? updatedAt = null)
{
    return new Cart(id ?? string.Empty, buyer ?? null!, ...) { UpdatedAt = updatedAt ?? DateTime.Now };
}
```

Компромисс: приватные конструкторы и обязательные проверки правил делают сборку агрегата в нужном состоянии для теста трудоёмкой. `Fake` собирает объект в обход правил, все параметры опциональны — в тесте указываются только значимые.

Цена: **это публичный метод в продакшн-коде, обходящий инварианты**. Ничто не мешает вызвать `Cart.Fake(...)` в боевом хендлере и получить агрегат в невалидном состоянии. Чище был бы отдельный билдер в тестовой сборке (`internal` + `InternalsVisibleTo`), но `Fake` дешевле. Для `Order` вынесли хотя бы в отдельный файл `Order.Fake.cs` — видно, что о проблеме знают.

## Наблюдаемость и деплой

| Инструмент | Роль |
|---|---|
| **Serilog** | структурные логи; `LogContext.Push` для обогащения ([[Serilog]]) |
| **OpenTelemetry** | трейсы и метрики ([[OpenTelemetry в .NET]]) |
| **Prometheus** | метрики через `SharpAbp.Abp.OpenTelemetry.Exporter.Prometheus` |
| **Sentry** | ошибки, интегрирован с Serilog |
| **Health checks** | `/health` с проверками MySQL всех модулей и Redis |
| **Docker + Kubernetes + Werf + Helm** | сборка и деплой ([[Kubernetes: минимум для разработчика]]) |

Health checks в `Startup.ConfigureServices` проверяют каждую базу отдельно:

```csharp
services.AddHealthChecks()
    .AddMySql(_configuration[CatalogConnectionString]!, name: "CatalogMysql")
    .AddMySql(_configuration[ModerationConnectionString]!, name: "ModerationMysql")
    .AddMySql(_configuration[CartConnectionString]!, name: "CartMysql")
    .AddRedis(_configuration[CatalogRedisConnectionString]!, name: "CatalogRedis");
```

Именованные проверки на каждый модуль — при падении сразу видно, чья база недоступна, вместо общего «нездоров». Про сам механизм — [[Health checks]].

Самая полезная метрика для этой архитектуры — **количество необработанных записей в `outbox_messages`, `inbox_messages`, `internal_commands`**. Их рост означает, что конвейер событий встал, и ловится это раньше, чем жалобы пользователей.

## Вопросы с собеседований

> [!question]- Почему в проекте FluentMigrator, а не EF Migrations, если EF Core уже используется?
> Три причины. Контроль над DDL: автогенерация EF на базе с историей умеет предлагать деструктивные шаги вроде пересоздания таблицы, а на проде это неприемлемо. Покрытие: не вся схема описана EF-моделями — служебные таблицы Outbox/Inbox/InternalCommands, индексы под конкретные запросы, схема Cart в MySQL модели не имеют, и `dotnet ef migrations add` их просто не увидит. Явность: миграция, написанная руками, читается на ревью, а сгенерированный diff — нет. Цена — `Down()` пишется вручную, и связи со моделью нет, поэтому расхождение схемы и модели ничем не ловится.

> [!question]- Что такое архитектурные тесты и что они дают поверх code review?
> Это обычные юнит-тесты, которые через рефлексию проверяют структуру кода: у агрегатов нет публичных конструкторов, `Domain` не ссылается на `Application`, контроллеры инжектят только интерфейсы, админские эндпоинты имеют атрибут прав. Поверх ревью дают полноту и постоянство: ревьюер проверяет выборочно и зависит от загруженности, тест проверяет всё и всегда, и падает до мержа. Плюс сообщение теста работает документацией в момент нарушения. Отдельная ценность — механизм для живого проекта: правило включается сразу со списком зафиксированных исключений, новый код обязан его соблюдать, старый чинится постепенно.

> [!question]- Зачем корзине MongoDB, если весь остальной проект на MySQL?
> Из-за характера доступа: корзина всегда читается и пишется целиком, частичных обновлений отдельных позиций почти нет. Это идеальный случай для документной БД — один документ, один запрос, никаких джойнов. В реляционной схеме та же корзина — это `carts` плюс `cart_items` плюс `moderated_cart_items` плюс вложенные объекты, и каждое отображение корзины стоит джойна на пять-шесть таблиц. Второй аргумент: у позиции корзины десятки полей, скопированных из каталога, и они добавляются под каждую фичу — в Mongo это не требует миграции. Цена — `[Bson*]`-атрибуты просочились в доменный класс, и служебные таблицы Outbox всё равно пришлось оставить в MySQL, из-за чего атомарность «данные + событие» для Cart не полная.

> [!question]- Почему у каждого модуля своя строка подключения?
> Чтобы изоляция модулей держалась не только на уровне кода. С раздельными схемами модуль физически не может прочитать чужие таблицы — у него нет соединения к их схеме, и обойти это, написав SQL, невозможно. Второе следствие: изменение схемы одного модуля не может сломать другой, потому что никто снаружи от неё не зависит. Третье — возможность разнести схемы по разным серверам, если нагрузка потребует, не меняя код.

> [!question]- Что означает «миграции накатываются при старте приложения» для процесса деплоя?
> Что во время rolling update в Kubernetes старые и новые поды работают одновременно на **уже изменённой** схеме. Значит любая миграция обязана быть обратно совместимой с предыдущей версией кода. Удалить колонку одной миграцией нельзя — живые старые поды продолжат её читать и упадут. Такие изменения разносятся на два-три релиза: перестать писать, перестать читать, удалить. Плюс миграция не должна быть долгой блокирующей операцией — она задержит запуск пода и может уронить readiness probe.

> [!question]- Почему в проекте мало интеграционных тестов и как это исправить?
> Потому что каждый модуль хранит свой DI-контейнер в статическом поле composition root. Два теста, инициализирующих модуль по-разному в одном процессе, конфликтуют за это поле, а xUnit по умолчанию гоняет коллекции параллельно. Лечение — Testcontainers для реальных зависимостей плюс отказ от статического контейнера в пользу инстанса на тест, что означает переработку инициализации модулей. Это архитектурное ограничение, а не забытые тесты — и до его снятия основную нагрузку несут доменные юнит-тесты, которые благодаря DDD пишутся дёшево.

## Задачи

### Задача 1. Добавить колонку

В задаче: «нужно хранить у заказа комментарий менеджера». Перечислить шаги в правильном порядке.

> [!success]- Решение
> 1. **Миграция через скилл `create-migration`** — не руками. Скилл поставит реальный таймстемп и правильно назовёт файл и класс: `AddManagerCommentColumnToOrdersTable`.
> 2. Свойство в агрегате `Order` — с `private set`, меняется только доменным методом.
> 3. Доменный метод `SetManagerComment(string comment)` — с проверками, если они нужны.
> 4. Конфигурация EF (`OrderEntityTypeConfiguration`), если маппинг не выводится по конвенции.
> 5. Команда и хендлер, если менять комментарий должен пользователь.
> 6. Поле в ViewModel и SQL запроса, если его надо показывать.
> 7. `dotnet test ArchTests/`.
>
> Порядок 1 → 2 неслучаен: миграция ставится по реальному времени, и создав её позже, легко получить таймстемп новее, чем у миграции коллеги, которая на самом деле написана после твоей.
>
> Колонку нужно сделать nullable или с дефолтом — иначе старые поды во время rolling update не смогут вставлять строки.

### Задача 2. Написать архитектурный тест

Нужно правило: «класс бизнес-правила обязан называться `*Rule` и реализовывать `IBusinessRule`». Набросать тест в стиле проекта.

> [!success]- Решение
> ```csharp
> public class BusinessRulesShouldFollowNamingConventionTest : DomainTestBase
> {
>     [Theory]
>     [InlineData(OrdersDomainAssembly)]
>     [InlineData(CartDomainAssembly)]
>     public void Rules_ShouldImplementIBusinessRule(string assemblyName)
>     {
>         var domainAssembly = Assembly.Load(assemblyName);
>
>         var violations = domainAssembly.GetTypes()
>             .Where(t => t.Name.EndsWith("Rule") && !t.IsInterface && !t.IsAbstract)
>             .Where(t => !typeof(IBusinessRule).IsAssignableFrom(t))
>             .Select(t => t.FullName)
>             .ToList();
>
>         Assert.True(violations.Count == 0,
>             $"Классы с суффиксом Rule должны реализовывать IBusinessRule: {string.Join(", ", violations)}");
>     }
> }
> ```
> Две детали в стиле проекта. Первая: проверяется одно направление — «называется `*Rule` → реализует интерфейс». Обратное («реализует → называется») стоит сделать отдельным тестом, чтобы сообщение об ошибке указывало на конкретное нарушение, а не на оба сразу. Вторая: нарушения собираются в список и выводятся все, а не падают на первом — иначе исправление превращается в цикл «запустил, починил одно, запустил снова».
>
> Если в живом коде нарушения уже есть — добавить `KnownExemptions` со списком и комментарием «не пополнять», как в `QueryHandlersShouldNotInjectDomainRepositoriesTest`.

### Задача 3. Диагностика

Приходит жалоба: «изменил цену товара в админке каталога, в корзинах у клиентов цена старая». Как локализовать проблему, не читая код?

> [!success]- Решение
> Идти по цепочке событий из [[ServiceShop: Outbox, Inbox и обмен событиями]], проверяя таблицы:
>
> 1. `select count(*) from outbox_messages where processed_date is null` в базе **Catalog**. Пусто — событие не сгенерировано (не вызван `AddDomainEvent` или нет строки в `domainNotificationsMap`). Копится — джоба `ProcessOutboxJob` стоит или падает, смотреть логи по `Module=Catalog`.
> 2. `select count(*) from inbox_messages where processed_date is null` в базе **Cart**. Пусто, а Outbox отработал — событие не доставлено: проверить подписку в `Cart` `EventsBusStartup`. Копится — стоит `ProcessInboxJob`.
> 3. `select count(*) from internal_commands where processed_date is null` в базе Cart — обработчик поставил команду, но `ProcessInternalCommandsJob` её не выполнил.
> 4. Всё обработано, а цена старая → проблема в самой команде: смотреть логи по `Id` команды.
>
> Отдельная ветка, если речь про **отображение**, а не про хранение: цена могла прийти правильно, но отдаётся из кеша Redis или из read-реплики каталога с отставанием репликации.
>
> Общий вывод: три таблицы в этой архитектуре — основной инструмент диагностики, и мониторить их глубину надо постоянно, а не только по жалобам.

## Итог

- MySQL со своей схемой у каждого модуля; MongoDB только у Cart, потому что корзина читается и пишется целиком; Redis для кеша, сессий и ключей DataProtection.
- Раздельные строки подключения — часть механизма изоляции: модуль не может прочитать чужие таблицы даже SQL-запросом.
- Служебные таблицы Cart остались в MySQL, поэтому атомарность «данные + событие» для Cart не полная — известная слабость.
- Миграции — FluentMigrator, только через скилл `create-migration`; таймстемп в имени критичен для порядка накатки у всей команды.
- Миграции накатываются при старте приложения, значит обязаны быть обратно совместимыми с предыдущей версией кода.
- ArchTests — тринадцать проверок структуры кода; правила вводятся сразу со списком зафиксированных исключений и запретом его пополнять.
- Интеграционных тестов мало из-за статического DI-контейнера в composition root; основную нагрузку несут доменные юнит-тесты.
- `Fake(...)` в агрегатах — публичный обход инвариантов ради тестов; работает, но не образец.
