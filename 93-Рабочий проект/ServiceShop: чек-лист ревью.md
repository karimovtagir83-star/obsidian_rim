# ServiceShop: чек-лист ревью

> [!abstract] Коротко
> Прикладной чек-лист поверх общего [[Ревью сгенерированного кода: чек-лист]] — что именно проверять в PR конкретно этого проекта, включая то, что уже ловят автотесты, и то, что нет.

## Зачем это знать

Общий чек-лист говорит «проверь границы и побочные эффекты». В конкретном проекте границы известны заранее — это те самые правила из [[93 — Рабочий проект: Alif ServiceShop (обзор раздела)]]. Проверять их вслепую на каждом PR дольше, чем сверяться со списком.

## Модель: что ловит автоматика, а что — только человек

| Правило проекта | Ловит автоматика? | Чем |
|---|---|---|
| Логирование только через Serilog | Частично | Анализатор может не поймать `Console.WriteLine`, только явный `Microsoft.Extensions.Logging` |
| DI только через Autofac | Нет | Ревью |
| Конструкторы агрегатов — только `private` | Да | `ArchTests` |
| Хендлер — `*CommandHandler`, реализует `ICommandHandler<,>` | Да | `ArchTests` |
| Изменение схемы — только через `create-migration` | Нет | Ревью: проверить формат имени файла миграции |
| Межмодульное общение — только через событие/фасад | Частично | `ArchTests` ловит прямые ссылки между сборками модулей, но не логическую утечку через общие типы |
| Публикация события — только через Outbox, не синхронно | Нет | Ревью |
| Сложные запросы — через Specification, не сырой SQL в хендлере | Нет | Ревью |
| `TreatWarningsAsErrors`, StyleCop | Да | Сборка падает |
| `Nullable enable` | Да | Компилятор |

Строки без автоматики — это ровно то место, где ревью не может быть формальным «CI зелёный, аппрув». Именно здесь чаще всего проходит сгенерированный код, который синтаксически безупречен, но нарушает правило, которое ничем не защищено технически.

## Чек-лист по шагам

1. **Модуль и границы.** Изменение находится в файлах своего модуля; нет прямого обращения к внутренним типам другого модуля, только к его публичному фасаду или через событие.
2. **Домен, а не сервис.** Новое бизнес-правило — класс в `BusinessRules/`, а не `if` в хендлере или контроллере. Конструктор агрегата приватный, создание — через `static Create(...)`.
3. **DI.** Регистрация нового сервиса — в `<M>Startup.cs` через Autofac, не через `IServiceCollection` напрямую.
4. **Логи.** `using ILogger = Serilog.ILogger;`, не `Microsoft.Extensions.Logging.ILogger`.
5. **Миграция.** Файл создан скиллом `create-migration`, имя и таймстемп не редактировались вручную.
6. **Событие.** Если действие должно быть видно другому модулю — публикация идёт через Outbox (запись в `outbox_messages`), не прямым синхронным вызовом; контракт в `IntegrationEvents` обратно совместим с существующими потребителями.
7. **Запросы.** Нетривиальный запрос на чтение — через Ardalis.Specification, не сырой SQL внутри хендлера команды.
8. **Тесты.** `dotnet test ArchTests/` пройден; на новое бизнес-правило есть юнит-тест, включая негативный сценарий.

## Где ошибаются

> [!warning] Специфика проекта, которую легко упустить
> - **Правило 6 (Outbox) нарушается тихо.** Прямой синхронный вызов между модулями работает в моменте, тестами может быть не пойман, если тест написан вокруг синхронного пути, и проявляется только под нагрузкой или при временной недоступности одного из модулей.
> - **StyleCop падает на форматировании, а не на логике.** Не путать красный CI из-за пробелов с реальной проблемой — но и не отключать анализатор, чтобы «побыстрее замержить», это часть контракта проекта.
> - **Агент часто:** предлагает валидный с точки зрения C#/.NET способ решить задачу (например, встроенный `IServiceCollection` вместо Autofac, `Microsoft.Extensions.Logging.ILogger` вместо Serilog), потому что это статистически более распространённый паттерн в обучающих данных — ни один из них не упадёт на компиляции, оба нарушают правило проекта незаметно для беглого ревью.

## Проверка на ревью

Сама эта заметка и есть чек-лист — использовать пункты 1–8 выше построчно на каждом PR, особенно на строках без автоматической проверки (DI, публикация события, сырой SQL, миграция вручную).

## Проверь себя

> [!question]- Почему изоляция модулей защищена автотестом лишь частично?
> `ArchTests` может проверить отсутствие прямых ссылок между сборками модулей на уровне зависимостей проекта — это структурная проверка. Но логическая утечка (например, дублирование бизнес-знания одного модуля в другом без формальной ссылки между сборками) тестом не ловится — она требует понимания смысла кода, а не только его структуры.

> [!question]- Почему нельзя считать PR готовым к мержу только по зелёному CI в этом проекте?
> Половина правил проекта (DI-контейнер, способ публикации событий, использование Specification вместо сырого SQL, порядок создания миграции) не проверяется автоматически. Зелёный CI подтверждает компиляцию, часть архитектурных правил и юнит-тесты — не подтверждает соответствие остальным конвенциям проекта.

## Разбор

### Разбор 1. Найди нарушения без подсказок

Дан фрагмент PR:

```csharp
public class MarkOfferOutOfStockCommandHandler : ICommandHandler<MarkOfferOutOfStockCommand>
{
    private readonly ICatalogDbContext _db;
    private readonly Microsoft.Extensions.Logging.ILogger<MarkOfferOutOfStockCommandHandler> _logger;

    public async Task HandleAsync(MarkOfferOutOfStockCommand command)
    {
        var offer = await _db.Offers.FirstOrDefaultAsync(o => o.Id == command.OfferId);
        offer.IsAvailable = false;
        await _db.SaveChangesAsync();
        _logger.LogInformation("Offer marked out of stock");
    }
}
```

Примени чек-лист и перечисли нарушения.

> [!success]- Разбор
> Пункт 4: используется `Microsoft.Extensions.Logging.ILogger` вместо Serilog — нарушение правила логирования. Пункт 2: изменение состояния (`offer.IsAvailable = false`) выполняется прямым присваиванием поля через DbContext, минуя метод агрегата и бизнес-правило — доменная логика не защищена (например, нет проверки, что оффер вообще можно перевести в этот статус). Пункт 6: если модуль Cart должен узнать о недоступности оффера — здесь нет публикации интеграционного события, изменение останется незаметным для других модулей.

## Итог

- Часть правил проекта защищена автотестами (`ArchTests`, компилятор), часть — только ревью
- Синтаксически валидный C#/.NET-код может нарушать правило проекта, не спотыкаясь ни о один автоматический барьер
- Чек-лист из 8 пунктов покрывает модуль, домен, DI, логи, миграции, события, запросы, тесты
- Сгенерированный код статистически чаще выбирает распространённый паттерн (встроенный DI, стандартный логгер), а не паттерн конкретного проекта
