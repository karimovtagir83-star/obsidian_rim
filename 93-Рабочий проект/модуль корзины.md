# Курс: модуль Cart (корзина) в Alif ServiceShop

  

Уровень: для новичка в проекте и в стеке (.NET, DDD, CQRS, Autofac, EF Core/MongoDB, MediatR, Kafka).

Формат: пошаговый, с объяснением всех терминов "с нуля".

  

---

  

## Шаг 0. Что вообще такое этот проект

  

Это **modular monolith** — одно .NET-приложение (один запускаемый процесс), но код внутри разделён на независимые **модули** (Orders, Catalog, Cart, Marketing, Moderation), как будто это отдельные микросервисы, только они не разворачиваются отдельно. У каждого модуля своя база/хранилище, свой домен, и они общаются друг с другом не напрямую, а через события (Kafka) или через явные интерфейсы-фасады.

  

Внутри каждого модуля используется:

- **DDD (Domain-Driven Design)** — код организован вокруг бизнес-понятий (Cart, CartItem, Buyer), а не вокруг таблиц БД.

- **CQRS (Command Query Responsibility Segregation)** — отдельно классы для "изменить состояние" (Command) и отдельно для "прочитать данные" (Query). Они физически разделены по папкам `Commands/` и `Queries/`.

- **MediatR** — библиотека-медиатор. Вместо того чтобы контроллер напрямую вызывал сервис, он отправляет объект-команду в "шину" (`IMediator.Send(command)`), а MediatR сам находит нужный handler и вызывает его. Это убирает прямые зависимости между слоями.

  

**Прежде чем идти дальше, важно понять на уровне интуиции:** контроллер API создаёт объект-команду ("добавь товар в корзину") → отправляет его через MediatR → MediatR находит единственный класс-обработчик с подходящей сигнатурой → обработчик достаёт агрегат, дёргает у него бизнес-метод, сохраняет через репозиторий.

## Шаг 1. Структура модуля Cart на диске

  

```

Alif.ServiceShop.Modules.Cart.Domain/ ← ядро бизнес-логики, ничего не знает о БД/HTTP

Alif.ServiceShop.Modules.Cart.Application/ ← команды, запросы, их обработчики (use cases)

Alif.ServiceShop.Modules.Cart.Infrastructure/ ← реализация репозиториев, DI-регистрация, фоновые джобы

Alif.ServiceShop.Modules.Cart.IntegrationEvents/ ← публичный "фасад" модуля для других модулей + события наружу

Alif.ServiceShop.Modules.Cart.Domain.UnitTests/

Alif.ServiceShop.Modules.Cart.Application.UnitTests/

Alif.ServiceShop.API/Modules/Cart/ ← HTTP-контроллеры (MiniApp и WebAndMobile — разные "фронты")

```

  

Это классическая **слоистая (layered) архитектура**, где зависимости идут в одну сторону:

  

```

API (контроллеры) → Application (handlers) → Domain (агрегаты, правила)

↑

Infrastructure (реализует интерфейсы из Domain/Application)

```

  

**Почему так:** Domain-слой не должен зависеть ни от MongoDB, ни от HTTP, ни от Kafka — так его проще тестировать (юнит-тесты без базы данных) и легче переиспользовать/менять инфраструктуру, не трогая бизнес-логику.

  

### Важная особенность именно Cart: он хранит данные в MongoDB, не в MySQL

  

В CLAUDE.md для всего проекта заявлен MySQL + EF Core как основной стек. Но если посмотреть на `Cart.cs`, там атрибуты `[BsonId]`, `[BsonElement]`, `[BsonConstructor]` — это атрибуты **MongoDB.Bson**, а не EF Core. Значит корзина хранится как документ в MongoDB, а не как строки в реляционных таблицах.

  

**Why (почему так решили, предположительно):** корзина — это документ с вложенной структурой (список товаров внутри одной корзины, у каждого товара — вложенные объекты Store/Category/Brand/LoanCondition). Для такого "дерева внутри одной сущности" документная БД (Mongo) удобнее, чем набор связанных таблиц — не нужны JOIN'ы, вся корзина читается и пишется одним документом атомарно.

  

**Термин "документная база данных":** в отличие от реляционной БД (таблицы со строго заданными столбцами и связями через внешние ключи), документная БД хранит данные как JSON-подобные документы (в Mongo — BSON, бинарный JSON). Один документ = одна корзина со всеми товарами внутри.

## Шаг 2. Aggregate Root — главное понятие DDD

  

Открываем `Alif.ServiceShop.Modules.Cart.Domain/Aggregates/Cart/Cart.cs`.

  

```csharp

public class Cart : Entity, IAggregateRoot

{

[BsonId]

public string? Id { get; private set; }

  

public Buyer Buyer { get; private set; } = null!;

  

private readonly List<CartItem> _cartItems = new();

public IReadOnlyCollection<CartItem> CartItems => _cartItems;

...

private Cart() { }

private Cart(Buyer buyer) { ... }

  

public static Cart Create(Buyer buyer)

{

return new Cart(buyer);

}

```

  

**Термины:**

  

- **Entity (сущность)** — объект, у которого есть идентичность (Id), а не просто набор полей. Два `CartItem` с одинаковыми полями, но разными Id — разные сущности.

- **Aggregate (агрегат)** — группа связанных сущностей, которая должна изменяться *только вместе* и *только через одну точку входа*. Здесь агрегат — это `Cart` вместе со всеми его `CartItem` и `ModeratedCartItem`.

- **Aggregate Root (корень агрегата)** — единственная сущность агрегата, с которой можно взаимодействовать снаружи. Здесь это класс `Cart`. Нельзя взять `CartItem` напрямую и изменить его в обход `Cart` — весь код снаружи обязан звать методы `Cart` (`AddModeratedCartItem`, `RemoveModeratedItem` и т.д.), а `Cart` уже сам решает, что делать с внутренними `CartItem`.

  

**Почему `CartItems` — это `IReadOnlyCollection`, а не `List`:**

Приватное поле `_cartItems` — это `List<CartItem>` (можно менять), но наружу торчит `IReadOnlyCollection<CartItem>` — только для чтения. Это защищает инвариант агрегата: снаружи нельзя сделать `cart.CartItems.Add(...)` в обход бизнес-логики. Единственный способ добавить товар — вызвать метод `cart.AddModeratedCartItem(...)`, который по пути проверит бизнес-правила.

  

**Приватный конструктор + фабричный метод `Create(...)`:**

```csharp

private Cart(Buyer buyer) { ... } // приватный — снаружи модуля не вызвать

public static Cart Create(Buyer buyer) // единственный официальный способ создать Cart

{

return new Cart(buyer);

}

```

Это требование из CLAUDE.md проекта: *"Конструкторы агрегатов — только private. Создание — только через фабричные методы"*. Проверяется автоматическим ArchTest (архитектурным тестом), который упадёт в CI, если кто-то сделает публичный конструктор.

  

**Зачем это нужно:** фабричный метод — это единственное "бутылочное горлышко" для создания объекта. Через него легко гарантировать, что объект создаётся только в валидном состоянии (например, что нельзя создать `Cart` без `Buyer`). Если бы конструктор был публичным, любой код мог бы создать "сломанный" `Cart` в обход всех проверок.

## Шаг 3. Value Object — что это и где используется

  

`Buyer` — это **Value Object (объект-значение)**: у него нет собственной идентичности (Id как у сущности), он описывается только своими значениями (например, тип покупателя + его идентификатор — авторизован он или нет). Два одинаковых `Buyer` считаются равными, если равны их поля — в отличие от Entity, где важен Id, а не содержимое.

  

Ещё примеры Value Object в этом агрегате: `LoanCondition`, `BnplDetails`, `PurchaseRestrictions`, `ItemImage`, `Category`, `Brand`, `Store` (в файлах рядом с `Cart.cs`).

  

**Отличие Value Object от Entity:**

| | Entity | Value Object |

|---|---|---|

| Идентичность | есть Id | нет, сравнение по значению |

| Изменяемость | обычно может меняться со временем (тот же Id) | часто иммутабельный — при "изменении" создаётся новый объект |

| Пример здесь | `Cart`, `CartItem` | `Buyer`, `LoanCondition`, `Store` |

  

Обратите внимание на переопределение `Equals`/`GetHashCode` в `CartItem.cs`:

```csharp

public override bool Equals(object? obj)

{

return obj is CartItem cartItem && OfferId == cartItem.OfferId;

}

```

Хотя `CartItem` — Entity (у него нет Id в привычном смысле, но он идентифицируется через `OfferId`), здесь сравнение переопределено по `OfferId` — то есть по сути `OfferId` играет роль идентичности этой сущности внутри агрегата.

## Шаг 4. Business Rules (`IBusinessRule`) — как в DDD оформляются проверки

  

Смотрим `BusinessRules/ModeratedOfferMustBeAvailableRule.cs`:

  

```csharp

public class ModeratedOfferMustBeAvailableRule : IBusinessRule

{

private readonly Guid _moderatedOfferId;

private readonly ushort _moderatedOfferAvailableQuantity;

private readonly ushort _requestedQuantity;

  

public async Task<bool> IsBrokenAsync()

{

return await Task.FromResult(_requestedQuantity > _moderatedOfferAvailableQuantity);

}

  

public string Message => $"Offer is out of warehouse. ...";

}

```

  

**Что такое паттерн Business Rule / Specification для правил:**

Вместо того чтобы писать `if (...) throw new Exception(...)` прямо внутри метода агрегата, правило выносится в отдельный класс, реализующий `IBusinessRule` с методом `IsBrokenAsync()` (правило нарушено?) и текстом ошибки `Message`. Затем в агрегате это выглядит так (см. `Cart.AddModeratedCartItem`):

  

```csharp

await CheckRuleAsync(new PartnerMustHaveCreditForLoanPurchaseRule(loanCondition, store));

...

await CheckRuleAsync(new ModeratedOfferMustBeAvailableRule(moderatedOfferId, moderatedOfferAvailableQuantity, quantity));

```

  

`CheckRuleAsync` (унаследован от базового `Entity`, определён в BuildingBlocks) вызывает `IsBrokenAsync()` и, если правило нарушено, бросает исключение с текстом из `Message`.

  

**Why (зачем так усложнять, а не просто `if`):**

1. Каждое правило — маленький, тестируемый в изоляции класс с понятным именем (`ModeratedOfferMustBeAvailableRule` — уже само по себе документация).

2. Правила можно комбинировать, переиспользовать, легко находить все бизнес-правила проекта одним запросом (`implements IBusinessRule`).

3. Метод агрегата (`AddModeratedCartItem`) остаётся читаемым — это последовательность "проверь правило → сделай действие", а не стена условий.

  

В этом агрегате правил несколько:

- `AuthorizedBuyerPurchaseLimitRule` / `UnauthorizedBuyerPurchaseLimitRule` — лимит покупки товара на одного покупателя (разная логика для залогиненных и незалогиненных).

- `ModeratedOfferMustBeAvailableRule` — товара достаточно на складе.

- `ModeratedOfferQuantityMustNotBeMoreThenInWarehouseRule` — нельзя запросить больше, чем есть на складе.

- `PartnerMustHaveCreditForLoanPurchaseRule` — у партнёра/продавца должен быть доступен кредитный лимит для рассрочки (loan/BNPL).

## Шаг 5. Command + CommandHandler — как выглядит один use case

  

Файлы: `AddModeratedItemToCartCommand.cs` + `AddModeratedItemToCartCommandHandler.cs`.

  

```csharp

public class AddModeratedItemToCartCommandHandler : ICommandHandler<AddModeratedItemToCartCommand, ViewCartVm>

{

private readonly ICartRepository _cartRepository;

private readonly IBuyerProviderFactory _buyerProviderFactory;

private readonly IItemProvider _itemProvider;

private readonly ICheckOfferPurchaseLimitForBuyer _checkOfferPurchaseLimitForBuyer;

  

public async Task<ViewCartVm> Handle(AddModeratedItemToCartCommand request, CancellationToken cancellationToken)

{

var buyer = await _buyerProviderFactory.GetBuyerIdProvider().GetBuyer();

var itemDto = await _itemProvider.GetModeratedItemDto(request.ModeratedOfferId, request.ConditionId);

  

var cart = await _cartRepository.GetByBuyerAsync(buyer) ?? CartAggregate.Create(buyer);

  

await cart.AddModeratedCartItem(... /* данные из itemDto и request */);

  

await _cartRepository.SaveAsync(cart);

  

return ViewCartVm.FromEntity(cart);

}

}

```

  

**Термины:**

- **Command** — простой объект-DTO ("что нужно сделать"): `AddModeratedItemToCartCommand` содержит `ModeratedOfferId`, `Quantity`, `ConditionId` и т.д. Сам по себе ничего не делает.

- **CommandHandler** — класс, который *реализует* эту команду. По правилу CLAUDE.md проекта класс обязан называться `*CommandHandler` и реализовывать `ICommandHandler<TCommand, TResult>` (это тоже проверяется ArchTests).

- **ViewModel (`ViewCartVm`)** — DTO для ответа наружу (в API), отдельный от доменной модели `Cart`. Домен никогда не отдаётся наружу напрямую — сначала конвертируется в ViewModel/DTO. Это защищает домен от изменений в контракте API и наоборот.

  

**Логика обработчика — это типичный сценарий "use case":**

1. Узнать, кто покупатель (`IBuyerProviderFactory` — абстракция, скрывающая, авторизован пользователь или нет, откуда брать его идентификатор — из JWT токена или из сессии).

2. Получить актуальные данные о товаре из каталога (`IItemProvider` — под капотом наверняка ходит в модуль Catalog через его публичный фасад/интеграционные события, а не напрямую в БД Catalog).

3. Достать существующую корзину или создать новую через фабричный метод `Create`.

4. Вызвать доменный метод `cart.AddModeratedCartItem(...)` — вся бизнес-логика и проверка правил происходит внутри агрегата, а не в хендлере.

5. Сохранить агрегат целиком через репозиторий.

6. Вернуть ViewModel.

  

**Важный архитектурный принцип, который здесь виден:** хендлер — это "оркестратор" (достал зависимости, вызвал метод агрегата, сохранил), а вся бизнес-логика (проверки, вычисления) — внутри самого агрегата `Cart`. Это и есть суть DDD: "толстый домен, тонкое приложение" (rich domain model).

## Шаг 6. Репозиторий (`ICartRepository`) — абстракция над хранилищем

  

```csharp

public interface ICartRepository

{

Task<Cart?> FindAsync(string id);

Task<Cart?> GetByBuyerAsync(Buyer buyer);

Task SaveAsync(Cart cart);

Task SaveManyAsync(List<Cart> carts);

Task DeleteAsync(Cart cart);

...

}

```

  

**Термин "Repository pattern":** интерфейс, описывающий, *что* можно сделать с хранилищем данных агрегата (найти, сохранить, удалить), без указания *как* это делается (Mongo-запрос, SQL и т.д.). Интерфейс лежит в `Domain`-слое, а реализация — в `Infrastructure`-слое. Это позволяет писать unit-тесты для `Cart` и хендлеров, подменяя реальный репозиторий фейковым/моком, без поднятия настоящей MongoDB.

  

Заметьте: методов много и они специфичны для конкретных сценариев (`GetByCategoryIdAsync`, `GetByModeratedOfferIdAsync`, `Get14DaysOldCarts`) — в отличие от "обобщённого" `IRepository<T>` из учебников, это осознанно широкий, заточенный под use case интерфейс (в духе Ardalis.Specification-подхода: конкретные запросы вместо общих CRUD-абстракций поверх LINQ).

## Шаг 7. Синхронизация с Catalog: Integration Events + MediatR notifications

  

Это самое интересное — как корзина "узнаёт", что товар в каталоге подешевел, закончился на складе, или продавец его деактивировал.

  

Смотрим `ChangeModeratedItemWarehouseQuantityOnModeratedOfferQuantityChangedIntegrationEventHandler.cs`:

  

```csharp

public class ChangeModeratedItemWarehouseQuantityOnModeratedOfferQuantityChangedIntegrationEventHandler

: INotificationHandler<ModeratedOfferQuantityChangedIntegrationEvent>

{

private readonly ICommandsScheduler _commandsScheduler;

  

public async Task Handle(ModeratedOfferQuantityChangedIntegrationEvent notification, CancellationToken cancellationToken)

{

await _commandsScheduler.EnqueueAsync(new ChangeModeratedItemWarehouseQuantityCommand(

Guid.NewGuid(),

notification.ModeratedOfferId,

notification.Quantity));

}

}

```

  

**Термины:**

- **Integration Event (интеграционное событие)** — сообщение о том, что *что-то произошло* в другом модуле ("количество товара изменилось", "оффер деактивирован", "цена изменилась"). Событие `ModeratedOfferQuantityChangedIntegrationEvent` определено в модуле **Catalog** (`Alif.ServiceShop.Modules.Catalog.IntegrationEvents`), а обрабатывает его модуль **Cart**.

- **`INotificationHandler<T>`** — интерфейс MediatR для обработчиков *уведомлений* (в отличие от `ICommandHandler` для команд с одним обработчиком, у notification может быть много обработчиков — все, кто подписан).

- **Kafka** — реальная транспортная шина. Событие публикуется модулем Catalog в Kafka-топик; где-то на инфраструктурном уровне (KafkaFlow) есть consumer, который читает сообщение из Kafka, десериализует его в `ModeratedOfferQuantityChangedIntegrationEvent` и публикует его в MediatR (`IMediator.Publish(...)`) внутри процесса — и вот тогда вызывается этот handler.

  

**Почему обработчик не меняет `Cart` напрямую, а кладёт команду в `_commandsScheduler` (Outbox/Inbox паттерн)?**

  

Здесь используется двухступенчатая схема:

1. Kafka-consumer получает событие → триггерит `INotificationHandler`.

2. Хендлер **не выполняет бизнес-логику сразу**, а *планирует* (enqueue) выполнение команды `ChangeModeratedItemWarehouseQuantityCommand` через `ICommandsScheduler`.

3. Отдельный механизм (обычно Quartz-джоба, читающая своего рода "Inbox"-таблицу/коллекцию) гарантированно выполнит эту команду, даже если процесс упадёт между шагом 1 и 2.

  

**Why:** это реализация **Inbox pattern** — паттерн идемпотентной и надёжной обработки входящих событий. Если сразу в хендлере менять состояние агрегата, а процесс упадёт посреди обработки — событие из Kafka может быть потеряно (если consumer уже подтвердил offset) или обработано дважды (если офсет не подтверждён и Kafka передоставит сообщение). Через `ICommandsScheduler` команда сохраняется во "внутреннюю очередь" (в БД/хранилище), и она гарантированно будет выполнена хотя бы один раз, независимо от сбоев процесса — а сама команда должна быть написана так, чтобы повторное выполнение было безопасно (идемпотентно).

  

Полный список событий каталога, на которые реагирует Cart (все в `Commands/ModeratedCartItems/*` и `Commands/Internal/*`):

- изменение количества на складе, цены, старой цены, цены+количества одновременно;

- активация/деактивация оффера;

- пометка "доступен/недоступен в фулфилмент-центре";

- изменение условий рассрочки (`LoanConditions`), привязка/отвязка события к условию партнёра;

- перенос оффера в другой магазин (`ActualizeCartItemStore`);

- ограничения на покупку (purchase restrictions) — добавление/снятие;

- статус ежедневного платежа (daily payment) для рассрочки;

- смена условий магазина (`ActualizeStoreConditions`);

- событие из модуля Orders: `AlifMobiNativeOrderMarkedNewOnSuccessPaymentIntegrationEventHandler` — при успешной оплате нативного заказа AlifMobi нужные товары удаляются из корзины.

  

**Важный вывод для новичка:** корзина в этом проекте — не пассивное хранилище "что положил, то и лежит". Она *активно поддерживается в актуальном состоянии* реакцией на события из Catalog (цена/наличие) и Orders (заказ создан → товары убрать из корзины). Это классический пример **eventual consistency (согласованность в конечном счёте)**: данные в корзине могут на короткое время отставать от каталога, но рано или поздно (после обработки события) придут в соответствие.

## Шаг 8. Как Cart отдаёт данные другим модулям — Module Facade

  

Файл `ICartModuleFacade.cs` (в проекте `Cart.IntegrationEvents`):

  

```csharp

public interface ICartModuleFacade : IModuleFacade

{

Task<CartDetailsForOrderVm> GetCartDetailsForOrderAsync(string cartId);

Task RemoveSelectedItemsFromCartOnOrderCreated(int clientId, IEnumerable<Guid> moderatedOfferIds);

Task<CartDetailsForOrderVm> GetCartForCurrentBuyerAsync();

...

}

```

  

**Термин "Module Facade":** это правило проекта — *"модули общаются через `I<Module>Module` интерфейс, не напрямую через классы инфраструктуры"*. Если модулю Orders нужно узнать детали корзины при оформлении заказа, он не лезет в `ICartRepository` или в MongoDB напрямую — он вызывает метод интерфейса `ICartModuleFacade`, реализация которого находится внутри модуля Cart. Это единственная "дверь" в модуль снаружи.

  

**Why:** такой фасад — это явная граница модуля (bounded context в терминах DDD). Модуль Cart может полностью поменять внутреннее устройство (структуру агрегата, хранилище, бизнес-правила), и пока сигнатура методов `ICartModuleFacade` не меняется — остальной код проекта не заметит изменений. Это то, что отличает modular monolith от "большого комка грязи" (big ball of mud), где все части знают друг о друге напрямую.

  

Обратите внимание, что часть коммуникации идёт через синхронный вызов фасада (`GetCartDetailsForOrderAsync` — Orders прямо сейчас спрашивает у Cart актуальные детали), а часть — через асинхронные Kafka-события (Cart узнаёт о смене цены не синхронным запросом, а подпиской на событие). Выбор зависит от сценария:

- Нужен ответ *прямо сейчас* для текущего запроса (оформление заказа) → синхронный вызов через facade.

- Нужно *в реальном времени поддерживать консистентность* данных, дублируемых в корзине (цена, наличие) → асинхронная подписка на событие.

## Шаг 9. Прочие модули и файлы, которые стоит знать (кратко)

  

- `SharedCarts` — отдельный агрегат "общая корзина" (например, ссылка на корзину, которой можно поделиться) со своим набором команд (`AddItemsToSharedCart`, `AutoDeleteExpiredSharedCarts`).

- `WishlistAggregate` — список желаемого, отдельный от корзины агрегат в том же модуле.

- `Infrastructure/Configuration/Processing/AutoDeleteAbandonedCarts` и `AutoDeleteExpiredSharedCarts` — фоновые задания (вероятно, Quartz-джобы), которые чистят "брошенные" корзины — метод `Cart.IsAbandoned()` как раз это проверяет (`DateTime.Now - UpdatedAt >= 14 дней`).

- `MergeCarts` (метод в `Cart.cs`) — сценарий "пользователь ходил по сайту без логина, потом залогинился" — нужно объединить анонимную корзину с корзиной авторизованного пользователя. Обратите внимание на логику: при слиянии учитываются лимиты покупки (`ICheckOfferPurchaseLimitForBuyer`) и наличие на складе.

## Что нужно знать заранее (prerequisites), если термины выше были непонятны

  

- **HTTP request/response, REST** — базовое понимание того, как контроллер API получает запрос и отдаёт ответ.

- **Асинхронное программирование в C# (`async`/`await`, `Task`)** — весь код здесь асинхронный, потому что почти каждая операция — это либо поход в базу, либо в очередь сообщений.

- **Интерфейсы и внедрение зависимостей (Dependency Injection)** — то, почему в конструкторах хендлеров и агрегатов встречаются `ICartRepository`, `IBuyerProviderFactory` и т.д., а не конкретные классы. В этом проекте DI-контейнер — **Autofac** (не встроенный `Microsoft.Extensions.DependencyInjection`).

- **Понятие очереди сообщений (message queue) / шины событий**, хотя бы на уровне "издатель кладёт сообщение, подписчик его читает позже, независимо" — нужно для понимания Kafka + Outbox/Inbox.
