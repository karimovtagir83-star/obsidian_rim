# ServiceShop: работа с агентом в этом репозитории

> [!abstract] Коротко
> Применение общих правил из раздела [[16 — Агентная разработка (обзор раздела)]] к конкретному репозиторию: что в контексте проекта уже сформулировано для агента, чего не хватает, и какие задачи в этом конкретном модульном монолите стоит поручать агенту свободно, а какие — только под жёстким контролем.

## Зачем это знать

Общие принципы («спецификация вместо инструкции», «границы доверия») становятся полезны только тогда, когда применены к конкретным правилам конкретного репозитория. Здесь — как это выглядит в ServiceShop.

## Модель

### Что в проекте уже работает как контекст для агента

Правила из [[93 — Рабочий проект: Alif ServiceShop (обзор раздела)]] — это фактически содержимое `CLAUDE.md` независимо от того, оформлены они в файл с таким именем или переданы агенту текстом задачи. Они закрывают ровно то, что общий трек 16 называет разрывом между «как принято в .NET вообще» и «как принято в этом репозитории»: DI через Autofac, а не встроенный контейнер; Serilog, а не `Microsoft.Extensions.Logging`; MVC-контроллеры, а не Minimal API; миграции — только через скилл.

### Что не выводится из кода и должно проговариваться в задаче явно

- **Какому модулю принадлежит фича.** Агент видит текст задачи и, возможно, открытый файл — но не бизнес-контекст владения (Orders против Cart против Marketing), см. [[ServiceShop: путь фичи от задачи до релиза]].
- **Синхронность или асинхронность флоу.** Обычный CRUD-хендлер синхронен; кредитный флоу в Orders — асинхронен по своей природе, см. [[ServiceShop: модуль Orders и флоу оплат]]. Без явного указания агент чаще выбирает более распространённый синхронный паттерн.
- **Существование Outbox/Inbox как единственного канала межмодульной связи.** Эта связь не выражена прямым вызовом кода — агент не восстановит её по умолчанию, см. [[Агент в большой кодовой базе: поиск и чтение]].

### Практическая матрица доверия для этого репозитория

| Задача | Доверие |
|---|---|
| Command/Handler по существующему образцу в том же модуле | Высокое — механическая работа по шаблону |
| Юнит-тест на существующее правило | Высокое, но тест на **новое** правило пишет человек до реализации |
| Новое бизнес-правило в домене | Среднее — спецификация условия и результата обязательна, ревью построчное |
| Изменение контракта `IntegrationEvents` | Низкое без явной проверки — обратная совместимость с реальными потребителями события проверяется отдельно |
| SQL-миграция | Черновик — можно, накатка и ревью SQL — только человеком, только через скилл `create-migration` |
| Всё, что касается флоу Nasiya/BML | Низкое — денежная логика и распределённая транзакция с внешней системой, ошибка дорога и не всегда заметна автоматикой |

## Где ошибаются

> [!warning] Специфичные для проекта ловушки
> - **Просят агента «добавить фичу как в похожем модуле» без уточнения различий.** Модули похожи по структуре (`Domain`/`Application`/`Infrastructure`/`IntegrationEvents`), но различны по хранилищу (MySQL против MongoDB в Cart) и по синхронности (обычный флоу против кредитного в Orders) — копирование по аналогии без этой поправки переносит не то допущение.
> - **Полагаются на то, что `ArchTests` поймает всё архитектурное нарушение.** Они ловят структурные правила (приватные конструкторы, изоляцию сборок), но не логические (публикация события синхронно вместо Outbox, сырой SQL в хендлере вместо Specification) — см. [[ServiceShop: чек-лист ревью]].
> - **Агент часто:** при задаче «почини баг в Х» без указания, что баг может быть межмодульным, ищет причину только в коде модуля Х — не проверяя `outbox_messages`/`inbox_messages` как возможное место разрыва, потому что это не выражено прямым вызовом кода этого модуля.

## Проверка на ревью

- Задача агенту явно называет модуль, синхронность/асинхронность флоу и наличие межмодульной связи, если она есть — не полагается на то, что агент восстановит это сам.
- Для задач из зоны низкого доверия (событие, миграция, кредитный флоу) в PR виден отдельный шаг ручной проверки, а не только «агент сгенерировал и тесты прошли».
- Копирование «как в похожем модуле» явно сверено с различиями (хранилище, синхронность) между этим модулем и образцом.

## Проверь себя

> [!question]- Почему для этого конкретного проекта общий совет «дай агенту контекст проекта» недостаточен без разбора по модулям?
> Потому что пять модулей проекта неоднородны: одинаковая структура папок скрывает разные модели данных (MySQL против MongoDB) и разную природу флоу (синхронный CRUD против асинхронного кредитного процесса). Общий контекст уровня всего репозитория («используем Autofac, Serilog») не передаёт этих различий — их нужно проговаривать на уровне конкретной задачи.

> [!question]- Почему нельзя доверять агенту находить межмодульные баги так же, как баги внутри одного модуля?
> Связь между модулями в этом проекте выражена не прямым вызовом кода, а таблицами `outbox_messages`/`inbox_messages` и конфигурацией подписок. Агент, ищущий причину бага по коду одного модуля, не видит эту связь без явного указания проверить и таблицы, и конфигурацию другого модуля — структурно она вне области, которую он просканирует по умолчанию.

## Разбор

### Разбор 1. Сформулируй задачу правильно

Нужно добавить в модуль Marketing обработку события об одобрении кредитной заявки Nasiya, чтобы отправить покупателю уведомление. Сформулируй задачу агенту так, чтобы она учитывала: модуль-источник события, асинхронную природу решения скоринга, и необходимость идемпотентной обработки.

> [!success]- Пример решения
> «В модуле Marketing нужен обработчик интеграционного события `CreditDecisionMadeEvent`, публикуемого модулем Orders через Outbox после решения скоринга Nasiya (см. `domainNotificationsMap` в `OrdersStartup.cs`). Обработчик должен подписаться в `MarketingEventsBusStartup` через `SubscribeToIntegrationEvent<T>` и отправить пуш-уведомление через существующий `IPushNotificationService`. Обработка обязана быть идемпотентной — повторная доставка события (проверить по `inbox_messages`) не должна отправить повторное уведомление. Критерий готовности: юнит-тест на однократную отправку при повторной доставке одного и того же события».

## Итог

- Правила проекта из обзора раздела 93 — это и есть контекст для агента в этом репозитории, оформлен он в CLAUDE.md или нет
- Модуль, синхронность флоу и наличие межмодульной связи не выводятся из кода — их нужно называть в задаче явно
- Матрица доверия неоднородна даже внутри одного репозитория: механический CRUD и кредитный флоу Nasiya требуют разного уровня контроля
- `ArchTests` защищают структуру, не логику — публикацию через Outbox, идемпотентность, корректность SQL проверяет человек
