# ServiceShop: модуль корзины

> [!abstract] Коротко
> Cart — самый простой из пяти модулей ServiceShop и поэтому опорная точка для первого знакомства с проектом: одна база (MongoDB, а не MySQL, как у остальных), короткий сценарий, минимум внешних зависимостей. Разбор пути `POST /api/cart/moderated-items` — маршрут первого дня из [[93 — Рабочий проект: Alif ServiceShop (обзор раздела)]].

## Зачем это знать

Разбирать модульный монолит стоит с самого простого модуля, а не с самого важного (Orders) — иначе первое знакомство с архитектурой смешивается с сложностью бизнес-логики. Cart даёт схему («эндпоинт → команда → хендлер → агрегат → правило») в чистом виде, без асинхронных внешних интеграций, которые есть в Orders.

## Модель

### Агрегаты модуля

| Агрегат | Роль |
|---|---|
| `Cart` | обычная корзина одного покупателя |
| `SharedCart` | корзина, доступная нескольким пользователям одновременно (семейный/групповой сценарий) |
| `Wishlist` | список избранного — не участвует в оформлении заказа напрямую |

### Почему MongoDB, а не MySQL

Остальные модули хранят данные в MySQL через EF Core, потому что там нужны согласованные реляционные связи и транзакции (заказы, каталог, модерация). Корзина — документ с коротким временем жизни, часто перезаписываемый целиком, без сложных связей между сущностями и без требований к строгой реляционной целостности. MongoDB как документное хранилище (см. [[NoSQL: когда и зачем]]) подходит этому шаблону доступа лучше, чем реляционная таблица с JOIN-ами.

### Путь запроса «добавить оффер в корзину»

```
CartController.AddModeratedItem
   → AddModeratedItemToCartCommand
   → AddModeratedItemToCartCommandHandler
   → Cart.Domain/Aggregates/Cart/Cart.cs (метод добавления позиции)
   → BusinessRules/ModeratedOfferMustBeAvailableRule
   → репозиторий сохраняет документ корзины целиком в MongoDB
```

Ключевое отличие от Orders: результат синхронный и однозначный — либо оффер добавлен, либо правило отклонило операцию с конкретной причиной. Никакого промежуточного статуса ожидания, никакой асинхронной внешней системы.

### Синхронизация с каталогом

Корзина хранит по позиции достаточно данных, чтобы не запрашивать каталог при каждом обращении (цена, доступность на момент добавления), но эти данные могут устареть — цена изменилась, оффер сняли с модерации. Синхронизация с каталогом — отдельная операция, которая либо выполняется явно (запрос пользователя открыть корзину подтягивает актуальность), либо реагирует на событие об изменении оффера из модуля Catalog.

## Решения

| Задача | Подход в Cart | Почему не как в Orders |
|---|---|---|
| Хранение состояния | Один документ MongoDB на корзину | Нет сложных связей между сущностями, не нужна реляционная модель |
| Согласованность с ценой/доступностью оффера | Явная или событийная синхронизация, а не постоянный запрос к Catalog | Постоянный запрос при каждом обращении к корзине — лишняя нагрузка на Catalog при коротком времени жизни корзины |
| Обработка ошибки бизнес-правила | Синхронный явный отказ | Нет внешней асинхронной зависимости, которая заставила бы вводить промежуточный статус |

## Где ошибаются

> [!warning] Подводные камни модуля
> - **Считают, что раз хранилище документное, то и правила проверять не нужно.** `ModeratedOfferMustBeAvailableRule` и подобные правила всё равно живут в домене — документное хранилище меняет модель данных, а не отменяет бизнес-правила.
> - **Забывают про устаревание данных в корзине.** Цена или доступность оффера, сохранённые в корзине на момент добавления, могут разойтись с актуальным состоянием каталога — без синхронизации покупатель увидит в корзине то, чего уже нет в продаже.
> - **Агент часто:** при работе с MongoDB-репозиторием предлагает паттерны, характерные для EF Core (LINQ-провайдер с трансляцией в SQL, `Include` для навигационных свойств) — они здесь не применимы буквально, репозиторий работает с документом целиком.

## Проверка на ревью

- Новое бизнес-правило по-прежнему лежит в `BusinessRules/`, а не в контроллере или сервисе — типовой соблазн для «простого» модуля.
- Изменение цены/статуса оффера в Catalog имеет путь синхронизации с уже существующими корзинами, а не оставляет их с устаревшими данными бессрочно.
- Код репозитория для MongoDB не пытается воспроизвести EF Core API там, где это не нужно.

## Проверь себя

> [!question]- Почему для корзины выбрали MongoDB, а не ту же MySQL, что и для остальных модулей?
> Корзина — короткоживущий документ без сложных связей между сущностями и без требований к строгой реляционной целостности, часто перезаписываемый целиком. Документная модель хранения подходит этому шаблону доступа естественнее, чем реляционные таблицы с JOIN — при этом другие модули (Orders, Catalog) выбрали MySQL именно потому, что там связи и транзакционность важны.

> [!question]- Почему модуль Cart — правильная точка входа для первого знакомства с проектом, а не Orders?
> Cart даёт архитектурную схему (эндпоинт → команда → хендлер → агрегат → правило) в чистом виде: без асинхронных внешних интеграций, без множественных путей оплаты и статус-машин, которые есть в Orders. Разобравшись в Cart, легче читать более сложные модули по той же схеме, не путая архитектурную сложность с бизнес-сложностью.

## Разбор

### Разбор 1. Пройди сценарий

Открой в проекте (или, если проекта нет под рукой, опиши по памяти шаблон) файлы в порядке: `CartController.cs` → `AddModeratedItemToCartCommand.cs` → `AddModeratedItemToCartCommandHandler.cs` → `Cart.cs` → `ModeratedOfferMustBeAvailableRule.cs`. Сформулируй вслух за три-пять минут, что происходит на каждом шаге и что произойдёт, если оффер уже недоступен.

> [!success]- Как оценить себя
> Если пересказ включает: контроллер принимает запрос и создаёт команду → MediatR/module передаёт её в хендлер → хендлер загружает агрегат `Cart` и вызывает его метод → метод проверяет правило доступности оффера → при провале правило возвращает явный отказ, а не тихо игнорирует добавление → при успехе агрегат меняет состояние и сохраняется целиком — сценарий понят. Если пересказ остановился на «контроллер как-то добавляет товар» — вернись и пройди шаги ещё раз с открытыми файлами.

## Итог

- Cart — самый простой модуль, опорная точка для первого знакомства с архитектурой ServiceShop
- Хранилище — MongoDB, а не MySQL: короткоживущий документ без сложных связей, а не реляционная модель
- Путь запроса синхронный и однозначный — без промежуточных статусов, характерных для Orders
- Данные в корзине (цена, доступность) могут устаревать относительно каталога — нужна явная или событийная синхронизация
